# 6.20 Checklist and learning log

> **[Gate]** · Chapter 06: Authentication API

This is the **gate** for Chapter 6. Tick every box honestly and answer the learning log below before opening Chapter 7.

<BigWordAlert term="JSON Web Token (JWT)" plainEnglish="A compact signed string encoding a user id and an expiry, sent in the Authorization header on API calls." whyItMatters="Midad access tokens prove identity for Studio, cart and library routes without a server side session lookup on every request." />

Chapter 6 built an API that can answer one question about a stranger: who are you? Every item below is a way of checking that the answer is produced by the server, stored safely and refused correctly when it is wrong. The boxes are not a summary of the chapter. They are the smallest set of facts that, taken together, mean the authentication API can carry the client work in Chapter 7.

Read the groups in order, because later items depend on earlier ones. An endpoint cannot answer 403 for an unverified account until the OTP route can set `isVerified`, and no security item can be checked until a login returns a token to inspect. The prose above each group says why the items exist, what evidence proves them and how a reviewer reads the evidence, so a box ticked without that evidence is a guess.

One naming note before you start, because it confuses readers who joined the course mid-way. The role field stored on User uses the two values `vendor` and `customer`. In the marketplace language this course uses, a vendor is a creator who owns a Studio, and a customer is a buyer who holds a License. Same two groups of people, two vocabularies: the API and the checklist use the stored values, while the interface chapters talk about creators and buyers. Do not rename the enum to match the prose, because every guard, seed file and test already reads the stored values.

## Chapter 6: Authentication API checklist (gate)

Do **not** open Chapter 7 until every box is ticked and learning log answers are written below.

### Environment and config

These four items exist because a token is only as trustworthy as the key that signs it. `JWT_SECRET` is the signing key, and the two expiry values decide how long an access token stays useful and how long a refresh token may be exchanged. Listing all three in `.env.example` is what lets a second person run the API at all, and keeping the real value out of Git is what stops every deployment that reuses the key from being forgeable.

The third item is the one that separates a working configuration from a hopeful one. `config.js` should read the environment once, at startup, and throw when `JWT_SECRET` is missing. A server that starts without a signing key and fails on the first login is harder to diagnose than a server that refuses to start and names the missing variable. Failing fast also means the person who deploys without the key finds out in ten seconds instead of in a support ticket.

- [ ] `JWT_SECRET`, `JWT_ACCESS_EXPIRY`, `JWT_REFRESH_EXPIRY` in `.env.example`
- [ ] `JWT_SECRET` in local `.env`, not committed
- [ ] config.js fails startup if JWT_SECRET missing
- [ ] bcrypt and jsonwebtoken in package.json

A reviewer reads this group by opening `.env.example` and comparing it with the keys `config.js` reads. A key in the code and missing from the example is a setup trap for the next person. A key in the example and never read is dead weight. Then the reviewer runs the server once with `JWT_SECRET` removed and expects a named error, not a listening port.

### Endpoints

The five endpoints are one conversation, in the order a real person has it. Register creates the account with a hashed password and a pending verification, and answers 409 when the email already exists, because a second account on one email would split a buyer's Licenses across two records. Verify OTP flips `isVerified`, which is the difference between an account that exists and an account that may log in.

Login is where three answers must be distinguished. A correct password on a verified account returns 200 with tokens. A wrong password returns 401, because the caller failed to prove identity. A correct password on an unverified account returns 403, because the caller is identified and is not allowed yet. Collapsing those into one status is the most common failure in this chapter, and it forces the client to guess why it was refused.

Refresh exchanges a long lived token for a new short lived one, and answers 401 when the presented refresh token does not match the hash stored on the user. `GET /api/auth/me` is the proof that the middleware works end to end: it returns the user and profile behind `requireAuth`, and answers 401 without a token.

- [ ] POST `/api/auth/register` answers 201, hashes with bcrypt, issues an OTP and rejects a duplicate email with 409
- [ ] POST `/api/auth/verify-otp` flips `isVerified`, and a wrong code earns 400
- [ ] POST `/api/auth/login` returns 200 with tokens, 401 for a bad password, 403 while unverified
- [ ] POST `/api/auth/refresh` mints a fresh access token and answers 401 for an invalid refresh token
- [ ] GET `/api/auth/me` sits behind `requireAuth`, returns 200 with user plus profile, and 401 with no token

The evidence for this group is a curl transcript with five requests and their status lines. Read it as a reviewer by checking that each request uses a different account state: a fresh email, a wrong password, an unverified account and a missing token. A transcript where every request succeeds proves the happy path only, and the interesting half of an authentication API is the refusals.

### Security

The first item is absolute: no response body may contain `passwordHash`. The reason is not embarrassment, it is that a hash in a response travels into browser caches, logs, screenshots, analytics and support threads, and every one of those copies extends the life of a value you can never take back. The check is a search rather than a memory exercise: read the serializer that builds the user response and confirm it names its fields instead of spreading the document.

The second item covers the refresh token, which is the credential that can mint new access tokens. Store a hash of it, not the token itself, for the same reason passwords are hashed: a leaked database should not hand an attacker a working credential. Comparing a hash on refresh also means a logout or a rotation invalidates the stored value, which is a property you will need in Chapter 7.

The third item ties the two halves of identity together. The `role` in the access token must match `User.role` at the time the token was issued. When they disagree, the token is stale or was built from the wrong field, and a stale role is how a demoted account keeps creator access.

The fourth item is about the register surface. Only `vendor` and `customer` are accepted, so a request that posts `role: "admin"` is refused rather than trusted. The fifth is about honest limits: the development OTP is delivered through the console or a development-only response field, and that shortcut is written down where a reviewer can find it. An undocumented shortcut becomes a production vulnerability the moment someone deploys without reading the code.

- [ ] No response body ever carries `passwordHash`
- [ ] `refreshTokenHash` on User stores a hash, never the plain refresh token
- [ ] The `role` claim in an access token equals `User.role`
- [ ] Register accepts `vendor` and `customer` only
- [ ] The dev OTP delivery path is documented (console log or a dev-only response field)

A reviewer reads this group in three moves. Search the codebase for `passwordHash` and confirm every hit is either the model, the hash call or a deliberate `select: false`. Decode an access token from the transcript and compare its `role` and `sub` with the user document in Compass. Then grep for the OTP delivery line and confirm it is guarded by a development check or written in the README.

### Testing

The curl flow from 6.18 is the artefact, not the act of testing. Keeping it in the repository means a later change to the auth module can be re-tested without rebuilding the sequence from memory, and it means a reviewer can repeat your evidence in one paste.

The negative tests are what make the transcript worth reading. A 401 for a wrong password, a 403 for an unverified account and a 409 for a duplicate email each prove that a specific guard is reached. A suite of only successful calls cannot tell a working check from a missing one.

The seed item exists because Chapter 5 created accounts before the password hashing rule was final. If the seeded vendor account still holds a plain password, login fails through no fault of the login handler, and the fix is to re-run the seed rather than to edit the handler.

- [ ] Full curl flow documented (6.18)
- [ ] Negative tests pass (401, 403, 409)
- [ ] Seed vendor-a login works after bcrypt alignment

The reviewer's version of this group is one command and one expectation: log in as the seeded vendor and receive a token. If that fails, nothing above it can be trusted, because the seed is the fixture every later module reuses.

### Prior gates

These items keep the chapter from quietly breaking what earlier chapters proved. The models and seed from Chapter 5 are the data contract; a rename or a missing field arrives as a confusing 500 in a later chapter rather than as an obvious model error here. The health route still answering is a cheap regression check on the boot sequence, and it is the route you will use again when a deployment looks dead.

The last item is a scope guard. This chapter ends with an API and no screens, so a login form at this point would mean the chapter's work bled into the next one, and the client in Chapter 7 would be built on parts nobody verified.

- [ ] Models and seed from Ch 5 intact
- [ ] Health route still works
- [ ] No React auth UI yet, API only

### Explain these aloud

No command proves the next five, so the evidence is a sentence a mentor can hear. Say each one before ticking it. If an explanation trails off, the corresponding chapter section is worth one more read, and the box is worth leaving empty for now.

- [ ] Explain bcrypt vs plain storage
- [ ] Explain access vs refresh token roles
- [ ] Explain 401 vs 403 in this chapter
- [ ] Explain why JWT payload must stay minimal
- [ ] Explain refresh rotation benefit

The strongest answer about bcrypt names the work factor and the per-password salt, then says what it does not protect: a weak password still matches, so hashing buys time rather than immunity. The strongest answer about the payload says that a token is readable by anyone who holds it, so it carries an id, a role and an expiry rather than a profile.

Question one is graded on the stored document, not on the status code. A complete answer names the collection, the fields written at register time, the fields left empty until verification, and the hash rather than the password. Question two wants both halves: what hashing prevents and what it cannot, which is a leaked hash list tested offline at leisure.

Question three wants the payload you actually saw, with three claims explained: which user, which role and when it expires. Question six should quote the request and the status. Question seven is a preview, and the right answer already knows that an access token in localStorage is readable by any script on the page. ## Troubleshooting

| Blocker | Look at |
|---|---|
| 401 on valid token | JWT_SECRET mismatch, clock skew |
| 403 on seed login | isVerified false, re-seed or verify |
| 404 on auth | route mount path from 6.11 |
| bcrypt compare false | seed stored a plain password, re-hash |

Read the table right to left: each row names the symptom first and the cause second, because you arrive with the symptom. A 401 on a token you believe is valid is almost always a secret mismatch between the process that signed the token and the process that verified it, so compare the two `.env` files before reading any handler.

A 404 on every auth route points at the mount path rather than the handler. The router is fine, the prefix is wrong, and the fix is in the line that mounts it. A bcrypt comparison that returns false for a seeded account means the seed wrote a plain password, which is why the seed is part of this gate rather than an assumption.
