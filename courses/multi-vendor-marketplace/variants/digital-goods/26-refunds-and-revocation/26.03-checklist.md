# Refund and revocation gate

This gate settles one question with evidence: when one creator's Order is refunded out of a payment that covered two creators, does the system take back exactly one creator's access? Everything else in the module is preparation for that demonstration. A license that stays downloadable after a refund, or a license that dies when its creator was not part of the refund, both fail, and the second failure is the one a buyer will report as theft.

Build the fixture deliberately. Amina pays once for Nour's personal font at 1,200 minor units and Salma's commercial template at 1,800. Both Orders end `fulfilled`, both License rows are `active`, and the font License has three downloads left. Copy the payment intent id, both Order ids, both License ids and both license keys into a private note. Then download once from each license and keep the two links; you will need both of them later, one to show expiry and one to show that a link keeps working.

## Refund one creator only

Sign in as Nour and request a refund for her Order. The route should return 201 with a Refund record in `requested` state, the provider dashboard should show a partial refund of 1,200 against a 3,000 payment, and the Order should carry a `refundRequestedAt` timestamp. Immediately after that, have Amina request a fresh download link for the font. The request must be refused, and the refusal must come from the API query rather than from a hidden button, so check with curl as well as through the library page.

Then let the confirmation arrive. Within a pass of the CLI listener the Refund record moves to `succeeded` with a `providerRefundId` and a `confirmedAt` time, Nour's License becomes `revoked` with `revokedByRefundId` pointing at the Refund, and her Order becomes `refunded`. Salma's Order must be untouched: same state `fulfilled`, no `refundRequestedAt`, and her License still `active`. Capture both Order documents and both License documents in the same screenshot or the same file so the comparison is visible.

Now the proof that matters most. As Amina, request a new download link for the template and confirm it works, with the remaining count dropping by one. Then fetch the link you saved before the refund, the one issued for the template, and confirm it still works until its expiry. A revocation that breaks an unrelated creator's link is a defect, and it is invisible in a single creator demo, which is why the gate asks for a two creator fixture every time.

Do the same expiry check on the font link you saved. Fetch it before its five minutes are up, then wait past the expiry and fetch again. It must fail on the second attempt, because the link carries its own expiry and the storage provider enforces it. Say the honest sentence in your learning log: the refund stopped new links at the request, the revocation stopped the license at the confirmation, and the link issued before both was only bounded by its own expiry.

## The refund that arrives first

Repeat the module's ordering case because it is the one a reviewer will probe. Start a second Checkout for one line only, pay it, and refund it from the creator route before the CLI listener has handled the payment event. The refund confirmation arrives, and the payment event arrives after it. When the dust settles there must be no License for that Order, the Order must be `refunded`, and the fulfilment log must show a `skipped_due_to_refund` record rather than a grant that was revoked a second later.

Then deliver the payment event once more and take counts. Nothing changes: no License appears, the Order stays `refunded`, and no receipt is sent for an Order that was refunded before fulfilment. A guard that only checks the Order state after creating the grant would leave a License that is immediately revoked, which looks correct in the library and is wrong in the audit trail.

## The partial state at the order level

Amina buys two fonts from Nour in one cart, so her Order for that Studio has two lines and one total. Refund one line. The Refund record names the line, the revocation touches only that line's License, the other License stays active, and the Order becomes `partially_refunded`. Then refund the second line and watch the Order move to `refunded` with no further refund record beyond the second one.

Check the arithmetic against the documents rather than against the screen. The sum of succeeded refunds equals the Order total at the end, and it was less than the total in the middle. If your implementation puts the Order in `refunded` after the first line, the state function is reading a flag instead of a sum, and the second refund will not change anything it should.

## The verify endpoint under test

Call `POST /api/licenses/verify` with Nour's key and assert the body is exactly `{"status":"revoked"}` and nothing else. Call it with Salma's key and assert `{"status":"active"}`. Call it with a key that does not exist and assert the same shape with `{"status":"unknown"}` and a 200 status, not a 404. Then call it with no body, with a number instead of a string, and with a very long string, and confirm a 400 for each, with no query reaching the database for the malformed cases.

Inspect the response for what is absent rather than what is present. There is no buyer id, no email, no Order id, no product title, no download count and no seat list. Save the raw responses in the evidence file, because the point of the endpoint is its thinness and a screenshot of a rendered page cannot show an absent field.

Now the limit. Send eleven requests in a row as one client and confirm the eleventh returns 429 with a `Retry-After` header. Confirm the same from a second client, so the count is per client rather than global. Then send thirty one requests with the same key across four clients, keeping each one under ten in the minute, and confirm the key bucket rejects while the client bucket stays quiet. Wait out the window in the test configuration and confirm a normal request passes again. A limit that never resets is an outage with a status code.

## What this gate does not prove

It does not prove that a refunded buyer loses the file they already saved, because nothing can. It does not prove that a chargeback or a dispute revokes access, because that path is named in the roadmap and not built. And it does not prove the provider's event set for any API version other than the one you pinned, which is why the handler reads the refund rather than assuming a shape. What it proves is the product rule: one Order's refund ends one Order's access, and the verify endpoint tells the truth about a key without telling anything else.

## Gate checklist

- [ ] One payment of 3,000 covers two Orders, both `fulfilled`, with two `active` License rows before the refund.
- [ ] Nour's refund request creates a Refund in `requested` and sets `refundRequestedAt` on her Order only.
- [ ] A new download link for the font is refused immediately after the request, proven with curl and with the library page.
- [ ] The provider dashboard shows a partial refund of 1,200 against the 3,000 payment, and the Refund record stores the `providerRefundId`.
- [ ] On confirmation, Nour's License is `revoked` with `revokedByRefundId`, her Order is `refunded`, and the Refund is `succeeded` with a `confirmedAt` time.
- [ ] Salma's Order is still `fulfilled`, has no `refundRequestedAt`, and her License is still `active`.
- [ ] A fresh download link for Salma's template is issued after the refund, and the remaining count drops by exactly one.
- [ ] A font link issued before the refund fails once its expiry passes, and the evidence states the window honestly.
- [ ] A refund confirmed before the payment event leaves no License for that Order, with a `skipped_due_to_refund` record in the fulfilment log.
- [ ] Refunding one line of a two line Order leaves it `partially_refunded` and revokes one License, and refunding the second line moves it to `refunded`.
- [ ] Delivering the same refund confirmation twice changes no count and writes no second revocation.
- [ ] `POST /api/licenses/verify` returns exactly one key for a revoked key, an active key and an unknown key, all with status 200.
- [ ] The verify response contains no buyer id, email, Order id, product title, download count or seat data.
- [ ] The eleventh request in a minute returns 429 with `Retry-After`, the per key bucket rejects independently, and the window resets.
- [ ] The cross creator test runs inside the suite, not only by hand, and fails if revocation matches on the payment intent instead of the Order.
- [ ] Two Order documents, two License documents, the refund record, the verify responses and the rate limit output are committed with no secrets, keys or session cookies visible.

## Learning log

1. The provider refunds part of a charge and Midad refunds one Order. Explain where the link between them is stored and what breaks if it is missing from the provider call.
2. Why does revocation filter on the Order rather than the payment intent? Show the failure that the filter prevents, with the two creator fixture.
3. State the two moments at which access changes during a refund, what changes at each, and what an already issued link can still do between them.
4. Your verify endpoint answers `unknown` for a key that does not exist and for a key that belongs to another product. Defend that choice against the alternative of a 404.
5. A refund confirmation arrives before the payment event. Walk through the fulfilment guard, and name the two records that prove it worked rather than the one page that looks right.

Commit the refund route, the webhook branch, the revocation query, the order state function, the verify route with its limiter, and every test this gate lists. Add a short section to `docs/FULFILMENT.md` describing how a support person finds the Refund record for a creator complaint and which two fields tell them whether the money moved and whether access ended. The capstone demo will use this path with a stopwatch, so the note should be readable by someone who has not opened the module.
