# Refunding one creator in a split payment

Amina bought a font from Nour's Studio for 1,200 minor units and a template from Salma's Studio for 1,800, in one payment of 3,000. Two days later she asks Nour for a refund on the font. Nour agrees, and now Midad has to do something the payment provider finds strange: give back part of one payment, and take away exactly one creator's access. The provider knows about a charge. Midad knows about two Orders. Everything in this module lives in the space between those two facts.

The space is where the mistakes are. The easy implementation refunds the charge and revokes every license attached to it, which takes Salma's template away from a buyer who paid for it and never complained. The other easy implementation revokes nothing, because the Order still looks fulfilled in the database, and Nour's font stays downloadable after the money went back. Both versions pass a demo if the demo only ever refunds a single creator's purchase. This chapter builds the mental model that survives the two creator case.

Read the third step twice. The provider moves money at the level of the charge, and the only thing that tells it which creator that money belonged to is the metadata Midad attached when it asked for the refund. Without that link, the confirmation that comes back describes an amount and nothing else. With it, the confirmation names an Order, which names a Studio, which names the Licenses to revoke.

## Refunds are payments, and revocation is orders

A refund in this system is two records with two lifetimes. The provider's refund object is a money movement against a payment, it has an amount, a status and an id, and it can fail. Midad's `Refund` document is a decision about one creator's Order, taken by a creator, and it is the record the product reasons about. Keeping them separate is what lets the app answer a seller's question, which is "did my order get refunded", without asking a payment API.

So the Refund document carries `orderId`, `studioId`, `requestedBy`, `amountMinor`, `currency`, `reason`, `status` (`requested`, `succeeded`, `failed`), `providerRefundId`, `requestedAt`, `confirmedAt` and the idempotency key used with the provider. Put a unique index on `orderId` for the live refund, because one order is refunded once in this course. A second call for the same order returns the existing record rather than starting a second refund, which is the same "guard at the effect" rule that has protected Licenses, receipts and seats.

The amount comes from the Order snapshot, never from the request body and never from the Checkout. Nour has no business refunding more than her own order took, and a client can send any integer. Sum the OrderLine amounts for a whole order refund, or take one frozen line amount for a line refund, and compare the total with the amount the provider confirms. Integer minor units, one currency, no rounding, exactly as in Module 18.

There is a reason the creator is the actor rather than an administrator. Module 8 kept the role model to two roles, creator and buyer, and this route continues that: a creator can refund an Order that belongs to their Studio and nothing else. The ownership check is the same predicate used on every creator route since Module 9, and the test for it is the same test with a different URL.

## Partial at the payment, whole at the order

The phrase "partial refund" hides two different shapes, and Midad needs both. A refund is partial at the payment level whenever it returns less than the whole charge, which is the normal case in a split payment: 1,200 out of 3,000. A refund is partial at the order level when it returns less than the whole Order, which happens when a buyer bought two Fonts from Nour in the same cart and asks to return one.

The first shape is the one this module is built around, because it is the one where the wrong implementation is dangerous. The second shape is a smaller extension with the same machinery: the Refund names the Order and, optionally, the OrderLine, and the revocation touches only the Licenses created from the refunded lines. Compute the Order's state from arithmetic rather than from a flag someone sets by hand. If the sum of succeeded refunds equals the Order total, the Order is `refunded`. If it is greater than zero and less than the total, the Order is `partially_refunded`. If it is zero, the Order keeps whatever state it had.

That arithmetic is worth writing as one function and testing on its own, because every other record in the module reads its answer. `orderStateAfterRefund(order, succeededRefundTotalMinor)` returns one of three values and takes two numbers, so it can be tested with a table of cases in a few lines and no database. A route that recomputes the same rule in two places will disagree with itself the first time somebody refunds a line.

What is out of scope here deserves a sentence, because a reviewer will ask. Refunding a single OrderLine as a buyer facing self service, prorating a bundle, and refunding fees are not built in the core path. The Refund record already has the fields for a line level refund, and the arithmetic above already handles it, but the UI and the policy are separate work. Name that boundary in `docs/FULFILMENT.md` rather than implying the product does more than it does.

## When access ends

There are two moments in a refund, and they are minutes or days apart. The first is the request: a creator decides to give the money back, and Midad creates the Refund record. The second is the confirmation: the provider reports that the money actually moved, which arrives as a webhook. Access has to change at both moments, and it changes in different ways.

At the request, block new downloads immediately. Set `refundRequestedAt` on the Order and add that field to the download predicate Module 21 already runs. A buyer who is being refunded should not be able to pull three more links while the money is in flight, and a predicate that ignores the refund request makes the request meaningless. The block is a database field read by the same query that decides everything else, not a flag in the browser.

At the confirmation, revoke. Set the License status to `revoked` with a timestamp and the refund id, so the library can explain why the item is no longer downloadable and support can trace the decision. Do not delete the License, the OrderLine or the grants. A revoked license that still exists is the explanation for a support conversation; a deleted one is a mystery.

The window between the two moments is the honest part of this design. A link issued a second before the block may work until it expires, which in this course is about five minutes. Bytes already saved on the buyer's device are beyond recall, and no revocation design changes that. What the design buys is that every new request after the block fails, and that the license state stops claiming access as soon as the money is confirmed. Say that in the UI and say it in the viva, in those words.

There is a third ordering problem worth naming here, because it is easy to miss and impossible to fix later: a refund can be confirmed before fulfilment. Both facts arrive as webhooks from the same provider, and delivery order across different events is not guaranteed. If the money went back before the success event was handled, the fulfilment path must not create fresh Licenses for an Order that is already being refunded. The next chapter puts the guard in the fulfilment function; this chapter asks you to accept that it is needed.

## What the confirmation actually names

The refund confirmation arrives as an event about a charge or a refund, and the exact event set depends on the API version you pin. In current versions a refunded charge emits a `charge.refunded` event whose object is the Charge, carrying `amount_refunded` and a list of its refunds; separate refund events also exist. The course does not ask you to memorise the set. It asks you to check the pinned version, then read one real payload and answer a narrower question: does this event tell me which refund happened, and does that refund carry the metadata Midad attached when it asked?

If the answer is yes, the handler matches the provider refund id to the local `Refund.providerRefundId`, or matches the metadata order id when the id is not yet stored, and continues. If the answer is no, the handler retrieves the refund by id and reads the metadata from the retrieved object. Either way the decision is made against a refund, never against the charge as a whole.

That distinction is the difference between revoking one creator and revoking two. A handler that reacts to "this charge was refunded" and revokes every License whose payment intent matches will take Salma's template away on Nour's refund. It is not a hypothetical: it is what the shortest possible implementation does, and it is the reason the next chapter's first test asserts that Salma still downloads.

The third option is the tempting one, because 1,200 is smaller than 3,000 and it is easy to read the amount as the condition. The condition is not the size of the refund. The condition is whether money moved for a particular Order.
