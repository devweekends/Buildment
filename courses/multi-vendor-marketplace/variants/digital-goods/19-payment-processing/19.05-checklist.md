# Payment gate and test-mode evidence

This gate proves four things with evidence rather than assertion. Midad asks for the amount it froze in Module 18. A buyer can complete a test payment through the Payment Element. A decline leaves the Checkout unpaid and grants nothing. And the webhook route accepts a verified event once, refuses a forged one, and records what it decided.

Prepare one Checkout that contains a font from Nour's Studio at 1,200 minor units and a template from Salma's Studio at 1,800, for a total of 3,000 in one currency. Record the Checkout id, both Studio Order ids, both OrderLine ids and the frozen total before you touch the payment page. Keep everything in test mode. Use test cards only, and never enter a real card number anywhere in this module.

## Set the stage

Start the API, the client and the Stripe CLI listener, and set `STRIPE_WEBHOOK_SECRET` to the local secret the listener prints. Confirm the Checkout is `pending_payment`, that no Order is paid, and that no License exists for either line. Open the buyer's Order list and check that both Studio Orders describe the same frozen amount the Checkout holds.

Build the payment page around the Payment Element. The page fetches `POST /api/checkouts/:checkoutId/payment-intent`, receives the client secret, creates the Element with `stripe.elements({ clientSecret })`, mounts the payment element, and calls `stripe.confirmPayment({ elements, confirmParams: { return_url } })` when Amina submits. The page never sends an amount, a currency or a Studio id, because the route refuses those fields. On a weak connection this is the part that fails most often, so check that a reload of the page reuses the same PaymentIntent rather than starting a second attempt.

The return page must read state rather than assert it. It calls an authenticated status endpoint for the Checkout id and shows `pending_payment`, `paid` or `preparing your files`. In this module a paid Checkout is the end of the chain, because Module 20 has not created licenses yet. A page that said "your files are ready" here would be lying, and the lie would survive into the next module if nobody noticed.

## Pay with the success card

Use the success test card number from Stripe's testing documentation, with any future expiry date, any three-digit security code and any postal code the form asks for. The Payment Element may show a processing state for a second or two, then redirect to the return URL. The redirect on its own proves nothing, so watch the other two surfaces at the same time.

In the listener terminal, a `payment_intent.succeeded` delivery should appear with a 200 response. In the API, the event log should contain one row for that event id with a valid signature, the Checkout id, an accepted decision and the time. In the database, the Checkout should now be `paid`, with `paymentIntentId` set, `paidEventId` set to the delivered event id, and `totalMinor` still 3,000. Both Studio Orders stay `pending_payment`, and the License collection stays empty. That combination is the correct outcome for this module: payment confirmed, access not yet granted.

If the redirect arrives before the event, the return page shows an unpaid or processing state for a few seconds. That is the honest display. Refresh it and it settles once the event is recorded. If it never settles, check the listener, the signing secret and the event log in that order before touching the payment page again.

## Pay with the decline card

Open the same Checkout in a fresh tab and use the decline test card from the testing documentation. The Payment Element reports a declined card, and the intent stays payable with another card. Nothing else in Midad should move. The Checkout remains `pending_payment`, the Studio Orders remain unpaid, and the License count stays at zero. The event log records `payment_intent.payment_failed`, and no accepted success row appears.

Then pay the same Checkout with the success card. The route returns the existing PaymentIntent rather than creating a second one, and the successful attempt confirms the one Checkout. Record the PaymentIntent id from before the decline and after the success. It must be the same id. If you see two, the idempotency key or the local intent check is wrong, and you should fix that before collecting any other evidence.

## Reject what should be rejected

Three refusals belong in this gate because each one protects a different boundary. Send a request to the payment route with a body containing `amountMinor` of 1 and confirm the response is a 400 with no new PaymentIntent. Send a webhook body with a tampered signature and confirm a 400, a rejection record, and no accepted row. Deliver a correctly signed success event whose amount disagrees with the Checkout, and confirm a mismatch record with the Checkout left alone.

For the duplicate, resend the accepted success event from the CLI or the dashboard and compare counts before and after. There should be one accepted row, a delivery counter of two, one `paidAt` value and no second PaymentIntent. For the out-of-order case, deliver the success event first and load the return page afterwards, then show the page reading the state the event already wrote. The page must never be the thing that makes the payment true.

## What this gate does not prove

Fulfilment does not exist yet. A paid Checkout with no license is the expected state at the end of Module 19, and the success page says so in plain words. Do not insert licenses by hand to make the library look complete, and do not add a fulfilment call to the webhook handler to make the demo shorter. Module 20 builds that effect with its own idempotency guard, and it will need the confirmed Checkout this module leaves behind.

## Gate checklist

- [ ] The payment route returns a PaymentIntent whose amount equals the frozen Checkout total, shown in the Stripe test dashboard and in the API response.
- [ ] A request body containing `amountMinor` or `currency` is refused with 400, and no PaymentIntent is created for that attempt.
- [ ] The Payment Element completes a payment with the success test card and redirects to the return URL.
- [ ] The return page shows `pending_payment`, `paid` or `preparing your files` from an authenticated read, and never marks anything paid.
- [ ] The event log contains one accepted `payment_intent.succeeded` row with a valid signature, the event id and the Checkout id.
- [ ] The Checkout row is `paid` with its `paymentIntentId`, `paidEventId`, amount and currency unchanged from the frozen values.
- [ ] Both Studio Orders remain `pending_payment` and the License collection is empty after the successful payment.
- [ ] The decline test card leaves the Checkout unpaid, creates no License, and the same Checkout can then be paid with the success card on one PaymentIntent.
- [ ] A resent success event adds no second accepted effect: one PaymentIntent, one `paidAt`, unchanged counts.
- [ ] A webhook body with an invalid signature returns 400 and writes no accepted event row.
- [ ] A correctly signed event with a mismatched amount writes a mismatch record and changes no Checkout state.
- [ ] The Stripe CLI listener transcript, the event log rows and the Checkout and Order documents are saved as evidence with no secret keys or client secrets visible.

## Learning log

1. Which three values must agree before a signed success event may confirm Amina's Checkout, and which stored record supplies each of them?
2. The Payment Element closed and the return page says the payment was accepted. Explain why that is still not permission to create a license, and name the record that is.
3. Walk through two deliveries of the same event id, one second apart, row by row. Which row is inserted, which is rejected by the unique index, and what does the handler return each time?
4. A valid signature arrives on an event reporting 1,500 minor units while the Checkout holds 3,000. What does your handler do, and why is a 500 response the wrong answer for a permanent mismatch?
5. Module 23 moves slow work off this request path. Which part of the webhook handler must stay inline, and what would break if the confirmation write moved to a queue?

Commit the payment route, the webhook route, the event model with both indexes, the client payment page and the tests. Then write two sentences in `docs/FULFILMENT.md` naming the value a support person checks first when a buyer says they paid and sees nothing. The next module reads the confirmed Checkout and creates one license per paid OrderLine.
