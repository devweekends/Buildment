# Tables and documents for entitlements

Six facts decide this comparison, and none of them is a preference. Nour's font has two license options with different prices, seat limits, download limits and terms versions. It has three stored file versions. A buyer's cart can hold her font and Salma's template. One checkout covers both, so two creators each receive an order. A paid order line becomes one license, and that license issues download grants over time. Hold those six facts next to a table design and a document design, and the argument stops being abstract.

The question is not which store is better in general. The question is which unit of work must succeed or fail as one. Every database gives you atomicity inside that unit and nothing outside it, and the shape you choose decides where the unit boundary falls. Midad has two writes where that boundary matters, and the rest of this lesson finds them.

## The same catalogue in two shapes

In a relational design the catalogue is five tables. `products` holds the shared listing facts. `license_options` holds one row per option with a foreign key back to the product. `product_files` holds one row per stored version. `studios` holds the owner. Rendering one product page with its options takes a join of two tables, and adding the previews takes a third. Rendering a buyer's library takes a join across `licenses`, `order_lines`, `products` and `studios`.

In a document design the product page is one read. The `licenseOptions` array sits inside the product document, the previews sit beside it, and the studio is one reference away. The library is a query on `licenses` by buyer, then a batched lookup of product and studio names. Nothing about this is free: a document store will let you embed options with no bound on a price unless the team installs schema validation, and it will let you store a license that names an order line that never existed.

The shapes agree on one thing, and it matters more than the disagreement. The license is its own record in both designs, because a license is written after the sale, changed by limits and revocation, and read by a different person from the one who edits the product. Only the small numbers that belong to one license travel with it.

## Where the unit of atomicity falls

The first atomic write in Midad is granting a license. One paid order line yields exactly one license, and no payment event may ever create a second. In a document store the guard is a unique index on `orderLineId`: the second insert fails, the handler reads the winning row and continues. In a relational store the same pattern works, and a transaction also lets you write the license, the order status and an audit row together.

The second atomic write is the one that decides the model. Issuing a download has to check the remaining allowance and decrease it in the same operation, because two requests that both read `downloadsRemaining: 1` will both pass a check performed in application code. The fix is one conditional update whose filter contains the allowance, and that works in one document. Assigning a commercial seat has the same shape: push a name only if the seat list is shorter than the seat limit and the name is not already there.

Embedding the seats is what makes that second write a single-document operation. A separate `seats` collection would need a count, a uniqueness check and an insert to agree with each other, which means a transaction on a replica set or a careful compensating design. A bounded array inside the license, with `$expr` comparing `$size` to `seatLimit` in the filter, needs no transaction at all. Module 25 builds the parallel test that proves it under twenty racing requests.

## Why license options are embedded

Two to four options per product is the real range. A creator offers personal and commercial, and occasionally adds an extended option for agency work. That is a small, bounded list read on the same screen as the product, priced by the server, and edited by one creator in one form. Embedding it turns the product page into one read and the price lookup at checkout into one field access.

The alternative is a table of options with a foreign key, and it buys one real thing: a unique index on `(productId, key)` and a check constraint that a price is positive, enforced by the database rather than by a schema validator the team has to remember to install. If a product could carry forty options written by different people at different times, the separate collection would be the better design. At four options, the document wins, and the validation moves into the model plus one test.

The same reasoning does not extend to the files. File versions grow without a natural bound, a creator may replace a broken release, and no screen reads a file version together with the listing. Files stay in their own collection with a `productId` reference, because a list that grows is a list that should not be embedded.

## Order lines and the snapshot

An order line freezes what the buyer accepted: product title, license option key, license type, price in minor units, currency, seat limit, download limit and terms version. Later, a creator may change a price or publish new terms, and the paid order must not move. In a document design the order holds an array of these snapshots, which is exactly the shape a buyer's order page and a creator's sales page both read.

A relational design stores the same facts as columns on an `order_lines` row, and it is a good shape for reporting: summing revenue per creator is one aggregate over one table. Duplicate data is not a defect in either design, because the duplication is the point. A receipt that changes when the catalogue changes is not a receipt.

The snapshot is where a reviewer trained on normal forms will push back, so write the defence into the draft. The order line is not a copy of the product kept up to date; it is a record of one instant that nobody updates afterwards. Test it by changing a product price after a checkout and asserting the stored line is unchanged.

## Versioned terms

Terms are short text attached to a license option, and they change. A creator adds a clause about client work, or clarifies what personal use allows. Each published revision gets a version number, and the option points at the current one. When a buyer checks out, the order line records the version it sold, and the license records the same version, so a later revision cannot be applied to an earlier sale by accident.

In a table design the natural move is a `terms` table with a version column and a foreign key from the option. In a document design the option carries `termsVersion` and the terms text lives in its own small collection keyed by product and version. Both shapes store the same three facts, and both need the same rule: never rewrite an old version, publish a new one.

The rule matters because the course later asks what happens on a refund, and the answer has to name the terms the buyer accepted. If the terms text were mutable, a defensible answer would be impossible. A version number plus an immutable copy is the cheapest thing that makes the question answerable.

## One checkout, many orders

A cart with Nour's font and Salma's template is one payment and two orders. The checkout document holds the buyer, the currency, the server-calculated total in minor units, the payment reference and a status. Each order holds the checkout reference, the studio, the buyer and its own snapshot lines. The per-studio totals must add up to the checkout total, and that sum is the reconciliation rule to write next to the model.

In a relational design the same records are rows, with a foreign key from order to checkout and a unique constraint on `(checkoutId, studioId)`. In a document design the unique index does the same work and `findOneAndUpdate` with `upsert` makes the create idempotent when a verified event arrives twice. Neither store removes the need for the key; both simply express it differently.

This is also where a document store's weaker reference handling is cheap. A missing order for one studio is a bug you find with one query: count orders per checkout and compare with the distinct studios in the cart. A sum check is a test you can run after every fulfilment in the test suite.

## Where PostgreSQL would be stronger

Say this plainly, because a reviewer will ask. A foreign key from `licenses.orderLineId` to `order_lines.id` is a declaration that the database enforces on every insert, including inserts made by a script, a migration or a future service. MongoDB gives you no such declaration, so the application must check, and the unique index only prevents duplicates rather than orphans.

A check constraint on `downloadsRemaining >= 0` and on `array_length(seats) <= seatLimit` is also a declaration. In MongoDB those rules live in the update filter and in schema validation, and a future writer that forgets the filter can break the rule. A unique constraint on `(licenseId, lower(email))` for seats is the third example: the document design enforces seat uniqueness in application logic, and the table design enforces it in the index.

The fourth is money across rows. A report that sums revenue per creator per month is one aggregate over one table in SQL, and in MongoDB it is an aggregation over embedded lines that must unwind the array first. That is more code and more chances to get a unit wrong, but it is not slower at Midad's size, and the same aggregation runs in one pass.

Record these four in the draft as costs, not as disqualifications. They are the reason the decision paragraph in the next lesson names a guarantee the application has to supply itself.

## Choose with the write in mind

If you remember one rule from this lesson, keep this one: pick the shape from the write that must not split, then check the reads are still cheap. Midad's writes that must not split are the per-line license grant and the license allowance change, and both are single-document operations in the design this course builds. That is why the decision in the next lesson is MongoDB with explicit references at three boundaries, not because documents are newer or because the stack is JavaScript.

Two conditions would change the answer. A regulated money ledger that had to be reconciled across tables would push the payments records into a relational store. A catalogue with forty options per product, edited by different people, would push options into their own collection. Neither is true for Midad at this size, and saying so honestly is stronger than claiming the choice is obvious.

Check yourself with three questions before moving on. Which write in Midad needs one document? What does a foreign key give you that a unique index does not? And why does a file version stay in its own collection while a seat list does not?
