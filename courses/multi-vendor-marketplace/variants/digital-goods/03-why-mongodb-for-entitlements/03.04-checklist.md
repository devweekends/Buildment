# Data model decision gate

The draft exists, the comparison is written, and one failing test shows what the database will not do for you. This gate asks one question in several forms: can a second person read your draft and predict which record answers which question, without reading your code? If they can, the model is ready for Module 4. If they cannot, the next three weeks will be built on a shape nobody agreed with.

Run the two tests again on a clean database before you start, and keep both outputs. The failing one proves that MongoDB accepted an orphan license, which is the gap your fulfilment service closes. The passing one proves that the unique index stops a second license for the same paid line. A gate that shows only successes is a gate that has not looked for the weak spot.

## Prove the three records are separate

Take one product and trace it through your draft. The listing holds the title, the previews and the two license options. The private file holds the storage identifier, the byte size, the checksum and the version. The license holds the buyer, the paid line, the key, the terms version, the seat list and the downloads remaining. Say out loud which of those three a stranger may read, which one a buyer may read, and which one only the server reads after a check.

Then test the boundary that is easiest to break later. Fetch the public catalogue response as an anonymous caller and search the raw JSON for the seeded storage identifier, the checksum and the license key. All three must be absent, and absence has to come from a serializer that names its fields. If your draft says the file record is private but the response is built by spreading the product document, the draft and the code disagree, and the code wins in production.

Do the same for the entitlement side. Ask a second buyer for the first buyer's license id and confirm that the answer carries no product title, no terms version and no remaining downloads. This is not the module that builds the route, and it is the module that decides the answer must be possible. If your model needs the license to be read before you can compare the buyer, the query is in the wrong order and the leak is already designed in.

## Defend the embed and reference choices

Go through the decision table row by row and say the cost out loud. License options are embedded, so a product page is one read, and the price bound is checked by the model rather than by the database. File versions are referenced, so a list that grows does not sit inside every product read, and the version boundary is enforced by the service. Seats are embedded, so one conditional push can compare the list size with the seat limit without a transaction. Order lines are embedded, so a receipt is one document and cannot be edited by a catalogue change.

Then defend the two rows where Midad accepted a weaker guarantee. A license can name an order line that does not exist, and nothing in the database refuses it. The answer is that exactly one function writes licenses, it loads paid lines from the database rather than from a request body, and its test suite replays the same event twice and crashes it halfway through. A seat list can exceed its limit if a future writer forgets the filter, and the answer is that the filter sits in one function with a parallel test in Module 25. Neither answer is as strong as a constraint. Both are checkable, and a reviewer can run both.

Answer the question about the file next, because it comes up in every review. The bytes do not live in the document because of the 16 MB limit, because a backup that contains deliverables grows with every version, and because the database would then sit on the only path to a file that must leave through a five minute link. The model keeps facts about the file and storage keeps the file, which is what makes an expiring link possible at all.

## Show the failing test and the passing one

Put the two test outputs side by side in your learning log and read them aloud. The orphan insert succeeded, so the test failed, and that failure is the evidence for every sentence you wrote about the application supplying a guarantee. The duplicate insert failed with error 11000 from the index, which is the evidence that one rule lives in the database.

If the first test already passes, stop and investigate before claiming the gate. Either the license model has a validation rule that rejects a missing line, in which case say so and show it, or the test is inserting into a database that already contains the line id, in which case the test proves nothing. A gate built on a test that passes for the wrong reason is worse than no test, because it teaches you to trust a green line.

```quiz
type: mcq

  - "The license, because it carries the status that becomes revoked"
  - "The order, because it names one studio and its licenses follow it"
  - "The checkout, because it holds the total that was refunded"
  - "The download grant, because it records every link that was issued"
correct: 1
explanations:
  - "The license is where revocation is recorded, but it is not the record that decides scope."
  - "Right. One payment can cover two studios, and the order is the per-studio record a refund names."
  - "The checkout spans every studio in the payment, so a refund scoped to it would take both."
  - "A grant is history of one issued link and carries no money state."
```

```quiz
type: mcq
question: "Your draft embeds the seat list inside the license. Which property does that choice buy for the seat limit?"
options:
  - "The limit can be checked and the name added in one conditional write"
  - "The limit is enforced by a database check constraint on the array"
  - "Seat names are searchable across every license with one text index"
  - "A seat can be reused after a refund without touching the license"
correct: 0
explanations:
  - "Right. A single filter compares the array size with the seat limit, so two parallel adds cannot both pass."
  - "MongoDB has no array size check constraint. That protection would need the relational shape."
  - "Seat search across licenses is an aggregation over the array, not a property of embedding."
  - "A refund revokes the license, and the seats go with it."
```

```quiz
type: mcq
question: "Where does the draft put the downloaded file, and why?"
options:
  - "Inside the product document, so the catalogue read returns everything a page needs"
  - "In storage, with the database holding the identifier, size and checksum"

  - "Right. Storage holds the bytes, the database holds the facts, and the server issues the short-lived link."
```

## What this gate does not prove

It does not prove that the catalogue response is clean, because no route exists yet. It does not prove that the seat limit holds under concurrent writes, because the update is built in Module 25. And it does not prove that a refund revokes only one creator's licenses, because the refund path arrives in Module 26. What it proves is that the shape can hold all three without being rebuilt, and that you know which guarantee the application now owns.

Write that limit into the bottom of `docs/erd-draft.md`, in one short paragraph. A reviewer who finds the honest boundary will trust the rest of the file, and a future you will know where to look when a test starts failing.

## Gate checklist

- [ ] `docs/erd-draft.md` has the decision paragraph, the decision table, the ERD, the field list and the open questions.
- [ ] The decision paragraph names one benefit and two costs, and no sentence claims a general speed advantage.
- [ ] The decision table has a row for license options, file versions, terms, order snapshots, the order to license link, seats, download grants and refund scope.
- [ ] The ERD shows ownership from user to studio to product, reference from product to file version, one checkout splitting into per-studio orders, and one order line granting at most one license.
- [ ] The field list carries no price on the file, no download counter on the product and no storage identifier in any shape a buyer can read.
- [ ] The orphan-license test output is saved and fails with the license inserted.
- [ ] The duplicate-license test output is saved and fails with error 11000 from the unique index.
- [ ] The public catalogue response, checked by hand from the seeded data, contains no storage identifier, checksum or license key.
- [ ] The relational strengths section names four constraints and the condition that would move the payments side to a relational store.
- [ ] The open questions section names at least two unsolved problems, and the known limits paragraph says what this gate does not prove.

If a crossed request answers with a full record inside an error body, the boundary is cosmetic. If a draft table row has no cost column value, the row is a description rather than a decision, and the gate is not finished.

## Learning log

Answer these in `docs/learning-log.md`, with the record name and the field behind each answer.

1. Which record answers who may download a specific file version right now, and which field decides that?
2. Which write in Midad must happen in one document, and what would it cost if the seats moved to their own collection?
3. Name the two guarantees PostgreSQL would have supplied with a declaration, and name the function and the index that supply them instead.
4. Why does the deliverable stay out of the product document, and what would you lose if the bytes lived there?
5. Which row of the decision table was hardest to defend, and what answer will you give the next reviewer who challenges it?
6. Which open question is still open after this gate, and which module is expected to close it?

The first answer should name the license and its status, not a middleware. The third should name the foreign key on the order line and the check on the remaining downloads, and then name the unique index and the fulfilment function beside them. If the sixth answer is "none", your draft is hiding a decision rather than making one.

Commit the draft, both test outputs and the learning log together. Module 4 connects the database to the configuration loader, Module 5 writes the models and the seed, and every relationship you drew here comes back as code that must match it.
