# Studio API gate

This gate proves that a creator owns exactly one studio, that the studio has one public address, and that another creator cannot read or change it. None of that is visible in a page that renders correctly for a single account. The evidence is a set of raw requests with their status codes, plus the database counts that show which writes happened and which were refused.

Prepare two creators and one buyer in a disposable test database. Nour owns `nour-type`. Salma owns `salma-templates`. Amina is a buyer with no creator role. Build the unique indexes before the first request, and print the index list once, because every conflict test below depends on the database enforcing the index rather than a schema annotation in a file.

## Check the ownership root

Create Nour's studio through `POST /me/studio` and confirm a 201 whose body includes `name`, `slug`, `bio` and `status` but no `ownerId`. Then read the raw document in the database and confirm `ownerId` equals Nour's user id. The two views are deliberately different: the database holds the join, the response does not.

Send the same create request again, unchanged. Expect a 409 with the field named, and expect `Studio.countDocuments({ ownerId: nour.id })` to still return 1. Repeat with two requests fired at the same moment through a small script rather than two browser tabs, because the browser serialises your clicks in a way that hides the race. One request creates, the other receives a conflict, and the count stays at one.

Ask Amina, signed in as a buyer, to post the same body. The role middleware answers before any database work, so the expected result is 403 and an unchanged collection. Then send the request with no token and expect 401. These two refusals look similar in a log and are worth separating in the evidence, because they come from different middleware and fail for different reasons.

## Check the slug

Request `POST /me/studio` as Salma with the slug `Nour-Type`. Upper case is not a different address. The normaliser lowercases it and the unique index refuses it, so the result is a 409 and Salma has no studio afterwards. Try `nour type` with a space and `nour_type` with an underscore; both normalise to the same value and both are refused. This is the test that catches a slug validator that runs before normalisation.

Then create Salma's real studio with `salma-templates` and confirm the public route answers for it. Fetch `GET /studios/nour-type` and `GET /studios/salma-templates` without a token and confirm both answer 200. Fetch `GET /studios/Nour-Type` and confirm a 404, because an address is not a search query.

## Check the public projection

Compare the sorted key list of the anonymous response with the expected four keys. Compare it again after the catalogue module adds products, if you are running this gate late, and update the expected list on purpose rather than accepting whatever appears. Search the raw response for the owner's email, the owner id and the internal document id. A reviewer should be able to read the response and see that nothing on it identifies a login.

## Check the denial from another creator

Sign in as Salma and send `PATCH /me/studio` with a body of `{ "bio": "Salma was here" }`. The route has no studio id, so this is a request about Salma's own studio and it should succeed. That success is the control: it proves the route works. Now have Salma try to change Nour's studio by sending `ownerId` of Nour in the body, and by sending a guessed studio id in the path. Both must be refused, because neither value is read. Read Nour's studio in the database before and after and compare the `bio` and `updatedAt` values. An unchanged document is the evidence; the status code alone is a claim.

## Check the closed state

Close Nour's studio with `status: closed`, read the public route and confirm the page still answers with `status: closed`. Reopen it. Nothing about closing removes the studio or its address. A later module refuses new purchases for a closed studio, and this gate only proves the state is stored and visible.

## What this gate does not prove

There is no product route yet, so a studio with no products is the correct state at the end of Module 9. Do not add an empty product to make the dashboard look busy. The gate also does not prove that the form works on a phone, that a creator with no studio is redirected anywhere, or that a slug change keeps old links alive. Module 10 covers the first two and this course leaves the third as a documented choice.

## Keep the evidence usable

Save one file, not a folder of screenshots. Put the four raw requests with their status codes, the before and after `bio` values, the index list and the sorted key list from the public response in `docs/STUDIO.md`. Remove bearer tokens and the test database connection string from anything you paste, and replace real email addresses with the seeded fixtures. A mentor should be able to read the file in five minutes and see which request was refused by which middleware.

If one check fails, debug in a fixed order: the index list, then the query in the handler, then the serializer. A missing index explains a duplicate studio. A query that filters by id instead of owner explains a cross-creator write. A serializer that spreads the whole document explains an email in a public response. Those are three different defects with three different fixes, and naming the right one is most of the work.

## Gate checklist

- [ ] `POST /me/studio` returns 201 and the stored document has `ownerId` set from the token, not from the request body.
- [ ] A second create from the same creator returns 409 and the studio count for that owner stays at 1.
- [ ] Two simultaneous create requests produce one studio and one conflict.
- [ ] A buyer posting to `/me/studio` receives 403, and an anonymous request receives 401.
- [ ] Slugs `Nour-Type`, `nour type` and `nour_type` are refused as duplicates of `nour-type`.
- [ ] `GET /studios/nour-type` answers 200 without a token and returns exactly `name`, `slug`, `bio` and `status`.
- [ ] The anonymous response contains no owner id, no email and no internal studio id.
- [ ] `GET /studios/Nour-Type` returns 404, so the slug is an address rather than a lookup.
- [ ] `PATCH /me/studio` from the owning creator updates the bio and changes `updatedAt`.
- [ ] `PATCH /me/studio` from another creator, with a body `ownerId` or a guessed path id, changes no field in the target document.
- [ ] Closing and reopening the studio through `status` leaves the public route answering with the current state.
- [ ] The index list from the test database, the four raw denials and the unchanged before and after documents are saved in `docs/STUDIO.md`.

## Learning log

1. Which value in `POST /me/studio` decides the owner, and what happens if a client sends an `ownerId` that disagrees with it?
2. Why is a unique index on `ownerId` needed when the handler already checks for an existing studio before creating one?
3. Your public studio route is asked for a slug that belongs to another creator. Why does this course answer 404 rather than 403 on the creator routes, and what does that choice hide?
4. A creator renames the studio and the slug changes. Trace what happens to a link a buyer saved last week, and state the rule your project follows.
5. Name one field you deliberately kept out of the public studio response and explain what an attacker could do with it.
