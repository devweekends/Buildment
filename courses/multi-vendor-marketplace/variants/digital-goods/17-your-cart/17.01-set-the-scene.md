# A cart grouped by creator

Amina has five items in her cart: a font from Nour, two templates and an icon pack from Salma, and a short ebook from Rania. The cart page shows five rows and one total. She pays once, and a few seconds later three separate Orders exist, one per creator. When she wants a refund for the ebook, she has to work out which of those Orders it belongs to.

The page could have told her that before she paid. Five flat rows describe a shopping list, not a purchase with three sellers behind it. Grouping the rows by creator is the smallest change that makes the structure of the payment visible while the buyer can still walk away.

This chapter is about that grouping: where it happens, what each group must contain, and the one value in it that must not be computed in the browser. The build in the next chapter turns it into a page that works at 360 pixels wide.

## One payment, several sellers

Midad's checkout takes one payment for the whole cart and then creates one Order per Studio. That split is not an implementation detail. It is what lets Nour see only her own sales, what lets her refund her own line without touching Salma's, and what lets two creators be paid from a single charge.

A buyer who cannot see that split before paying meets it as a surprise afterwards. The surprise has three parts. The library lists the items under three headings. A refund only covers one creator's Order. And a support question about one item has a different recipient from a question about the next. A cart that groups by creator teaches all three at the moment the buyer is deciding, which is the cheapest possible time.

## The group is a view, not a record

Grouping does not change what a cart is. The API from Module 16 returns a flat array of lines, each carrying the product, the license type, the option, the Studio id and the Studio name. The client turns that array into an array of groups. No new document is stored, no new route is added, and the checkout in Module 18 still reads the flat lines.

```js
// client/src/cart/group-lines.js (partial)
export function groupByStudio(lines) {
  const groups = new Map();

  for (const line of lines) {
    const group = groups.get(line.studioId) ?? {
      studioId: line.studioId,
      studioName: line.studioName,
      lines: [],
      subtotalMinor: 0,
    };

    group.lines.push(line);
    group.subtotalMinor += line.priceMinor;
    groups.set(line.studioId, group);
  }

  return [...groups.values()].sort((a, b) => a.studioName.localeCompare(b.studioName));
}
```

The function is pure and has no network calls, which is why it can be unit tested in three cases without a browser: an empty cart returns an empty array, two lines from one Studio make one group, and two Studios make two groups in name order.

The alternative is worth stating because it is defensible. The API could return groups directly, with the subtotals computed on the server. That puts the rule in one place for every client, and it is the right choice once the group total becomes a business rule, for example a per-creator fee or a minimum order per creator. It costs a shape that no other endpoint needs, and Module 18 would then unwrap groups to get back to the lines it splits. Midad has one client and no per-creator pricing rule, so the grouping stays on the client. If a second client appears and the two disagree about ordering, move it to the server and test it there.

## Group by id, label with the name

The grouping key is `studioId`. The visible label is `studioName`. Doing it the other way round is a defect that is easy to ship because it looks correct with seed data.

Two Studios can share a display name. Midad does not enforce a unique Studio name, only a unique slug, and two creators called Nour Studio are entirely possible. Groups keyed on the name would merge two sellers into one row with one subtotal, and the buyer would see a single Order in the interface and two in the library. A rename has the opposite failure: the same Studio appears twice in one cart, once under its old name in a cached response and once under its new one.

Using the id as the key and the name as a label removes both failures. The worst case is a group whose heading is out of date until the next load, which is a cosmetic problem rather than a split that does not match the payment.

## What each group must show

A group needs four things, and each one answers a question the buyer would otherwise ask at checkout.

- The creator's name, so the buyer knows who made the item and who will see the sale.
- The number of items from that creator, so a two-line group reads as two purchases rather than one.
- A subtotal in the same currency as the cart, so the per-creator amount is visible before the Orders exist.
- The lines themselves, each with its license badge and its own price.

The badge belongs to the line and not to the group, because one creator can sell a template under a personal license and an icon pack under a commercial one in the same cart. A badge on the group heading would have to choose between them, and whichever it chose would be wrong for the other line.

The cart total stays at the bottom, once. The sum of the group subtotals must equal it, and a test should assert that with money in minor units rather than with formatted strings. The total is a summary of what the server last said, not a promise about the amount that will be charged. A creator can edit a price between this render and the checkout request, and Module 18 answers that with a 409 and a re-priced cart rather than a silent difference. Say "cart total" in the interface, and let the payment page state the amount.

## The owned flag comes from the server

Module 16 refuses an add when the buyer already holds an active License for that product under that license type. The cart page has to show the same fact, and the obvious shortcut is wrong.

The shortcut is for the client to load the buyer's licenses once and match them against the cart lines. It is easy, it needs no API change, and it drifts. The client's copy is a different query with a different age. A license revoked by a refund ten minutes ago is still in the client's array, so the page says "you already own this" for an item the buyer no longer holds. Or the client forgets to filter on `status` and treats a revoked license as current, which is the same defect in the opposite direction.

The cart response therefore carries the answer. Each line includes the license types the buyer holds for that product, computed by the same query the refusal uses.

```json
{
  "lines": [
    {
      "productId": "66f1c0a41b9e4a0b7c8d2e10",
      "title": "Nour Grotesk, 4 weights",
      "studioId": "66f1c0a41b9e4a0b7c8d2f01",
      "studioName": "Nour Studio",
      "licenseType": "personal",
      "priceMinor": 1200,
      "ownedLicenseTypes": ["personal"]
    }
  ],
  "currency": "usd"
}
```

The logic is then a comparison of two strings: if `ownedLicenseTypes` contains `licenseType`, the row shows the owned message. If it contains the other type only, the row shows the "you own the other license" note instead. The client never decides what ownership means. It only renders what the server already decided, and the badge and the refusal can no longer disagree.

## Why rows must not move

The sort order is by creator name, and it must be stable across a license switch. Sorting by subtotal looks helpful until you watch it: a buyer switches one row from personal to commercial, the subtotal of that group changes, and the group jumps to a different position on the page. On a phone, mid-tap, that is a real failure. The row the buyer was about to press is now under their thumb where another row used to be.

Name order costs nothing and never changes when a price changes. Within a group, keep the order the buyer added items, which is the order the API returned. If you later add a sort control, make it an explicit choice the buyer makes, not a side effect of editing a line.
