# Seed, inspect and final ERD

This chapter advances the data model for Midad. The working example follows a creator studio and a buyer. Seed two creators and two buyers, inspect isolation and commit a truthful ERD that distinguishes public product, private file and entitlement. Before writing code, keep one distinction visible: A creator controls a Product and its private files. A buyer controls only their own paid entitlement. Public catalogue responses must never contain a storage identifier, license key or reusable download URL. That distinction will be tested through raw requests and database records, not only through a screen that looks correct.

Nour Studio sells a font under personal and commercial terms. Amina buys the personal license while Kareem buys the commercial one. Their library rows point to the same product but must carry different license terms, limits and ownership. As you work, write down which facts are current state and which are evidence of an earlier sale. Current state can change under a rule; purchase evidence needs a durable snapshot. Use the development seed as a small experiment so every relationship has at least two actors and an observable denial path.

The diagram is a route map for the decision in this chapter. Follow a request from the actor through the authoritative record before deciding what the UI may show or what the API may change. It is intentionally smaller than the final ERD; you will add fields and indexes as the module continues.



Run the seed in a disposable local database and make it repeatable. Create two named fictional studios, two buyers and at least three products across different license options. Generate small sample files that you own rather than copying another creator's font or ebook. Label every account as demo data and keep passwords out of committed output. Seed a released ProductFile for each product, one uploaded but unreleased version, and a pending cart. If you also seed paid orders and licenses for a screenshot, mark them explicitly as test fixtures; do not imply that a seed proved Stripe fulfillment.

Inspect every relationship with a database client. A Product belongs to exactly one Studio; a ProductFile belongs to that Product; a Checkout belongs to a Buyer; each OrderLine points to its snapshot and one Product; a License belongs to the buyer of its paid line; DownloadGrants belong to that License. Check indexes that guarantee one studio owner and one license per order line. Count a second seed run and verify it updated or preserved the same fictional rows rather than duplicating them. A reset command must refuse a non-development database by default.

Write `docs/erd.md` with two visual chains, field choices, indexes and ownership predicates. Note why public previews live with catalogue data while originals live behind ProductFile. Show which fields are mutable (description, next file release) and which are purchase evidence (OrderLine price and terms snapshot). A reviewer should be able to point to an arrow and know whether it means ownership, reference, or historical snapshot. Label any relationship that a later module has not implemented yet, so the ERD does not pretend functionality exists.

Now try to break the data. Insert a second Studio for the same owner; the database should reject it. Insert two Licenses for the same OrderLine; the unique index should reject the second. Ask Buyer B's library endpoint for Buyer A's License and expect denial. Request public catalogue JSON and search for the private storage ID. Change Product price after creating an order fixture and confirm the OrderLine amount does not move. Release a new file version and confirm an old license's update rule still makes a deliberate choice.

The gate passes when the seed script, index list, ERD and raw-response tests agree. Submit the seed command output, collection counts, index evidence, one cross-buyer denial and one snapshot immutability result. Explain aloud how Midad answers two separate questions: who owns the digital product, and who currently has permission to download a particular version. If you cannot answer both without pointing to a public URL, revisit the model before building a payment route.

## Explain the final picture

The ERD should make a four-step path clear: creator owns Studio and Product; Product has private versioned ProductFiles; buyer pays for an option captured in OrderLine; License and DownloadGrant govern access. Put the public preview on the catalogue side of the diagram and private storage ID on the file side. Mark Checkout as one payment across creators and Orders as separate seller views. If a peer reads the diagram and thinks an Order contains a permanent download link, the labels still need work.

Inspect a seed Product in the raw database and public API response. The database may contain references to private ProductFiles, while the public response must not contain storage IDs or signed URLs. Inspect Buyer A's library and Buyer B's library with separate sessions. A cross-buyer License ID should not produce another buyer's row. Then edit a Product price after creating a clearly labeled fixture OrderLine; the historical amount must remain the same. These checks give the schema a behavioral interpretation.

Record the actual index list: one Studio per owner, stable Product option handling, unique License per OrderLine and any ProductFile version uniqueness you declared. Explain which rules Mongoose validation can check before save and which require database indexes under concurrent requests. Two simultaneous writes are the test for uniqueness, because a serial form submission cannot reveal a missing index. Keep a short log of the two request results and final collection count.

The seed is not a payment demonstration. If you inserted a License fixture, label it as a fixture and keep the verified webhook outcome for Module 20. If you generated small file bytes, confirm you own them and that the storage IDs are development-only. If a released fixture version points to a missing file, either generate the asset or mark the row clearly as non-downloadable. A seed that presents a working library card but fails on every download teaches the wrong expectation.

Finish with a short oral defense: why are `licenseOptions` embedded in Product while purchased Licenses are separate rows; why is ProductFile private; why does OrderLine snapshot terms; and what happens when a refund arrives after a URL was issued? Your answers should refer to a concrete record and test for each claim. Commit `docs/erd.md`, the repeatable seed, index evidence and raw-response denials. The next module may assume a coherent shape, but it must still build authentication, verified payment and secure file delivery.
