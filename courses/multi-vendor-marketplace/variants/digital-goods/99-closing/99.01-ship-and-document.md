# Ship and document Midad

The deployed Midad is a running system. The repository is the argument that you understood it. A reviewer will not read twenty six modules of your work; they will open the README, look at one diagram, run the demo, and ask you three questions about a number you wrote down. This lesson creates those artefacts while the decisions are still in your head.

Documentation here is not marketing. Each file answers a question that a mentor, an interviewer or a future you will ask: what runs where, why a license is not a product field, how a payment becomes one license per line, and what happens to a link that was already handed out. Write the answer next to the thing it explains, and cite the file or command that proves it.

## A README that answers the first minute

The top of the README has one job: let a stranger decide in sixty seconds whether to look further. Put the live client URL, the API health URL and the demo recording link above everything else, because those are the first three things a reader checks. Then say what Midad is in two sentences, without adjectives: creators sell licensed digital work, buyers pay once for a cart that may span several studios, and access is granted by a verified payment event rather than by a browser redirect.

The skeleton below is the shape, not the finished text. Fill each heading with three to six lines, and delete any heading you cannot fill honestly. A short README that links to real evidence beats a long one that repeats the marketing.

```markdown
# Midad

A marketplace where independent creators sell licensed digital work.

## Live
- Client: the URL served by the client host
- API health: the `/health` URL on the API host
- Demo recording: unlisted link, four to six minutes
- Seeded accounts: creator and buyer test accounts, test data only

## What this project demonstrates
- One product listing, one private versioned file, one entitlement record
- One cart, one payment, one order per studio with frozen snapshot lines
- Licenses created from a verified payment event, exactly once per paid line
- Downloads through five minute links issued after a license check
- Download and seat limits that hold under parallel requests
- Refunds that revoke one studio's licenses and no other
- README, ERD, fulfilment states, security note and evidence index in `docs/`

## Run it locally
## Deploy it
## Tests and evidence
## Docs
```

Two rules keep the README honest. Do not paste a credential, even a test one, and do not claim a feature you cannot demonstrate. If the reconciliation job exists but has only been run by hand, write "implemented, tested by hand on 12 March" rather than listing it beside the webhook path as though the two had the same evidence.

The "Run it locally" section is where most READMEs fail a reader on a slow connection. Give the exact commands, the Node version, the databases and the worker that must all run, the seed command, and the smallest Stripe CLI command that triggers a fulfilment in test mode. A reader who cannot get a paid checkout will see an empty library and conclude the project is broken. For this audience, also state the size of the seed files, because a 40 MB upload on a weak connection looks like a hang.

## The environment file a reviewer can check

`.env.example` is a contract between the code and the person deploying it. It lists every required key, grouped by which process needs it, and the grouping says where each value comes from. Values stay empty, because a value in this file is a value in Git.

```dotenv
# Shared by API and worker
NODE_ENV=production
TZ=UTC
MONGODB_URI=
REDIS_URL=

# API only
PORT=
CLIENT_ORIGIN=
JWT_ACCESS_SECRET=
JWT_REFRESH_SECRET=
CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
DOWNLOAD_LINK_TTL_SECONDS=300
```

A file that drifts from the code is worse than no file, because it teaches a deployer to skip a key. Add a test that compares the keys the configuration loader requires with the keys documented here, and run it in the same suite as the rest. The failure names the missing keys, so the fix takes a minute.

```js
// tests/docs/env-example.test.js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { requiredConfigKeys } from '../../src/config/index.js';
import { envExampleEntries } from './parse-env.js';

test('.env.example documents every required key', () => {
  const documented = new Set(envExampleEntries('.env.example').map(([key]) => key));
  const missing = requiredConfigKeys().filter((key) => !documented.has(key));
  assert.deepEqual(missing, []);
});

test('.env.example leaves every secret key empty', () => {
  const risky = envExampleEntries('.env.example')
    .filter(([key, value]) => /(SECRET|KEY|PASSWORD|URI)/.test(key) && value !== '');
  assert.deepEqual(risky, []);
});
```

```text
FAIL .env.example documents every required key
  missing: STRIPE_WEBHOOK_SECRET, DOWNLOAD_LINK_TTL_SECONDS
```

The second test catches the reverse mistake, a real value pasted into a file that is about to be committed. `DOWNLOAD_LINK_TTL_SECONDS` has a default and still belongs in the file, so a deployer can see that the five minute lifetime is a decision rather than a constant someone typed into a service.

## Review the ERD against the code

`docs/erd.md` was committed in Module 5. Do not redraw it here; read it and check that every entity has a writer, an owner and a relationship that exists in the code. The table below is the review sheet, and it belongs in the README under a heading that links to the diagram.

| Entity | Who writes it | Relationship that must be visible |
|---|---|---|
| User | registration | role decides which routes are reachable |
| Studio | creator onboarding | one studio per `ownerId` |
| Product | creator dashboard | `studioId` is the ownership path |
| ProductFile | creator upload | versioned, referenced by product, never public |
| Cart | buyer | lines keyed by product and license option |
| Checkout | buyer at checkout | one payment across studios |
| Order | fulfilment | one per studio, unique per checkout and studio |
| License | fulfilment | one per paid order line, unique `orderLineId` |
| DownloadGrant | download route | one per issued link, names one file version |
| Refund | creator refund route | one per order, never per checkout |

Two entries are easy to leave out of a review and both matter. A `DownloadGrant` is not an entity that appears on any screen, so a reader may skip it, and it is the record that proves what was issued and when. A `Refund` is scoped to an order rather than to the checkout, which is the fact that makes a partial refund of a split payment possible.

Then check the one direction the ERD cannot show: the projection. Name the fields a public catalogue response may carry and the fields it may not, and confirm the serializer names them. A diagram shows relationships, and it never shows what a response leaves out.

## Draw the states a payment and a license move through

The second diagram is the fulfilment path, and it is the one the viva will circle. It combines the order states from Modules 18 and 20 with the license outcome from Module 26, because a status without its revocation state tells half the story. Step through it rather than reading it, and say which event moves each arrow.

<StateMachine title="Order and license states from checkout to revocation" chart={'stateDiagram-v2\n  [*] --> pending_payment: checkout created\n  pending_payment --> paid: verified payment event\n  pending_payment --> expired: attempt abandoned\n  paid --> fulfilled: one license per paid line\n  fulfilled --> partially_refunded: refund for one studio order\n  fulfilled --> refunded: full refund\n  partially_refunded --> refunded: remaining order refunded\n  refunded --> [*]: licenses revoked'} />

Read it with the written rules beside it. There is no arrow from `pending_payment` to `fulfilled`, because a browser redirect is not proof of payment. There is no arrow back from `refunded`, because a revoked license is not restored by paying again; a new purchase creates a new license with a new key. `partially_refunded` exists because one payment can cover two studios and a buyer may be refunded for one of them while the other keeps working.

Label the arrows with the evidence rather than with the actor. An arrow labelled "system" invites the question you cannot answer, while an arrow labelled "verified payment event" tells the reviewer exactly which record moved the state. Write the same six arrows into `docs/erd.md` as a short paragraph under the diagram, and link the file from the README.

## Write the download security note

`docs/download-security.md` is the file the capstone is judged on, because it is where you show that you know what your design cannot do. Give it one table of threats and controls, then a short section on residual risk, then a section on what is out of scope.

| Threat | How it happens | Control | What is left open |
|---|---|---|---|
| A link is shared in a group chat | The buyer copies the URL | Five minute expiry, one grant per issue, per license rate limit | Anyone with the link can fetch the file until it expires, and a saved copy stays saved |
| An id is guessed or enumerated | A caller sends another buyer's license id | The license is loaded with `buyerId` in the filter, and a miss answers 404 | None beyond traffic volume, which the rate limit covers |
| A refunded buyer keeps downloading | Refund confirmed, library still open | New issues blocked when the refund is requested, licenses revoked on confirmation | A link issued before the block lives until its expiry |
| A license key leaks | A key is pasted into a shared document | The key is not a credential: verify answers status only, rate limited | The key holder can prove a purchase happened, and owns no files by holding it |
| A payment event is replayed | The provider redelivers the same event | Signature check, then a unique index on `orderLineId` | A duplicate delivery costs one wasted write |
| A private asset is fetched directly | The storage URL is copied | Authenticated delivery type, unsigned URL fails, identifiers never serialized | Storage configuration is one dashboard setting away from a leak, so test it |
| A signed link appears in logs | Request logging includes the full URL | Log the grant id and the license id, never the URL | Anyone with log access sees the id, which opens nothing |
| A creator account is compromised | A stolen creator password | Writes are scoped to that studio, and no creator route reads a buyer license | The attacker can edit that creator's own catalogue |

The residual risk column is the part that earns marks, because it shows the difference between a control and a guarantee. A five minute link is not revocation. A download count counts issued links rather than finished downloads, and the honest sentence says so. A buyer who saves a file keeps it, and no access control changes that.

Name the out of scope items in the same file: DRM, watermarking, piracy detection, subscriptions, creator payouts, tax and chargebacks. Naming them is stronger than letting a reviewer discover them, and it stops a viva question from becoming a criticism of a promise you never made.

## Keep the evidence index honest

`docs/EVIDENCE.md` maps each claimed outcome to the artefact that proves it. One row per outcome, with a link, a command or a short file path, and a status that is either proven, partial or not done.

| Outcome | Evidence | Status |
|---|---|---|
| One license per paid line under replay | `docs/evidence/replay.log` | proven |
| Download limits hold under parallel requests | `docs/evidence/parallel-downloads.txt` | proven |
| A refund revokes one studio's licenses | refund walkthrough plus verify response | proven |
| Missed webhook repaired by reconciliation | worker log excerpt | partial |
| Seats refuse a sixth name on a five seat license | parallel seat output | proven |

The partial row is the most valuable one in the file. It tells a reviewer that you know the difference between built and proven, and it protects you from a question you would otherwise answer with a guess. Keep the evidence files small and dated, and never commit a response that contains a token, a key or a signed URL.

## Ship checks before the gate

Add one test that keeps the README from drifting. Every file in `docs/` should be linked from the README, because a document nobody links is a document nobody reads.

```js
test('README links every document in docs/', () => {
  const readme = readFileSync('README.md', 'utf8');
  const missing = readdirSync('docs')
    .filter((name) => name.endsWith('.md'))
    .filter((name) => !readme.includes(`docs/${name}`));
  assert.deepEqual(missing, []);
});
```

```text
FAIL README links every document in docs/
  missing: [ 'docs/download-security.md' ]
```

Then open the deployed client in a fresh browser profile with the network tab visible and confirm that no request goes to localhost. Check that `/health` reports the database, that the worker log shows a consumed job after the latest deploy, and that the Stripe webhook endpoint still points at the deployed origin with that endpoint's own signing secret rather than the CLI secret.

The live URL is necessary and it is not sufficient. A reviewer who opens it and finds an empty catalogue, a dead worker or a login that loops will not read the diagrams. The gate in the next lesson asks for a recorded demo and a defense without notes, and both are easier when these artefacts already exist.
