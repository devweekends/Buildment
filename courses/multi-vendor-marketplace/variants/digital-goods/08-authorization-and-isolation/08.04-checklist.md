# Isolation gate

Two creators, two buyers and one seat holder are seeded, the guards are registered, and `docs/AUTHORIZATION.md` exists. This gate asks one question in several forms: can a signed-in person reach a license or a product they do not own, and when they are refused, do they learn something they should not? A recorded demo cannot answer that. Only a request with another person's token can.

Run the suite against a clean database, then run the four most important requests by hand in a terminal. A suite that passes while a manual request returns a full record means one of the two is pointed at a different server, and the manual request is the one a reviewer will repeat.

## Prove the refusals one boundary at a time

The buyer boundary is the first. Kareem sends Amina's license id to the details route and to the download route with his own valid buyer token. Both answer 404 with the same body an unknown id returns, neither body contains a product title, a license type or a remaining download count, and Amina's stored allowance is unchanged. If the allowance moved, the handler spent a download before it refused, and every other passing test in the suite is now suspect.

The creator boundary is the second. Salma sends a price change to Nour's product and then tries to upload a file to it. The edit answers 403 with no product fields, and a reload as Nour shows the original price. The upload answers 403 before any bytes reach storage, which you prove by checking the storage client was never called rather than by reading a log line.

The state boundary is the third, and it is the one a reviewer will circle. A revoked license answers 403 with `LICENSE_REVOKED`, an expired license answers 403 with `LICENSE_EXPIRED`, and neither creates a download grant. The two fixtures must be separate, because a route that checks only the status field passes the revoked case and fails the expired one.

The seat boundary is the fourth. Yusuf opens the license that names his email, sees the product, the license type and a download action, and does not see the key. He then tries to add a seat and to request a refund, and both answer 403. This is the case that a two-actor test suite misses entirely, because a seat holder is neither the buyer nor a stranger.

## Check the code you did not change

Three smaller checks belong in this gate because they cost a minute each. Send a buyer token to a creator route and a creator token to a buyer route, and confirm the role guard refuses both before a record is loaded. Inspect every handler that reads an id from a request body, and confirm none of them chooses which record to update after the ownership check has passed.

Then read the matrix coverage test output. Every mutating route should have a row, and the three routes that failed on the first run should now appear in `docs/AUTHORIZATION.md` with a scope field and a proof name. If a row exists with an empty proof column, the row is a wish rather than a decision.

## Present it in five minutes

Show the matrix, then the failing line from the cross-buyer download test before the fix, then the passing suite. That order, because the failure is the interesting part: it shows the check is doing work rather than being present by accident.

Then answer one question without notes. Why does a seat holder get a download and not the license key? The strong answer separates two facts: the key proves a purchase and belongs to the person who paid, while a seat proves permission to use the files and belongs to the person named. It then says what would happen if the key were shared, which is that five agencies could resell one purchase and the verify endpoint would report a key belonging to nobody in particular. The weak answer is that the key is private, which explains nothing. The unacceptable answer is that the button is hidden, because the button is not the boundary.

## What this gate does not prove

The suite proves the routes that exist. It does not prove that a future aggregate endpoint avoids leaking counts, and it does not prove that an error handler added in a later module keeps refusals quiet. Both belong in `docs/AUTHORIZATION.md` under known limits, so a later reviewer knows what to re-check.

It also does not prove the payment path. Creating a license from a verified event, revoking it on a refund and counting issued links are writes owned by Modules 20, 21 and 26. This gate proves that no person can reach them through a route that trusts an id, which is a smaller and more useful promise.

## Gate checklist

- [ ] `docs/AUTHORIZATION.md` lists every protected action with a scope field, an expected status and the test that proves it.
- [ ] The matrix has separate rows for the download, the seat add and the refund, and a row for the verify endpoint that answers status only.
- [ ] Kareem's read of Amina's license answers 404 with a body identical to an unknown id.
- [ ] Kareem's download request for Amina's license answers 404, carries no link, and leaves her allowance unchanged.
- [ ] Kareem's own expired license answers 403 `LICENSE_EXPIRED` and creates no download grant.
- [ ] A revoked license answers 403 `LICENSE_REVOKED` and creates no download grant.
- [ ] Salma's edit of a Nour product answers 403 with no product fields, and the stored price is unchanged.
- [ ] Salma's upload to a Nour product answers 403 before the storage client is called.
- [ ] Yusuf can open the license and request a download, and cannot see the key, add a seat or request a refund.
- [ ] A buyer token on a creator route and a creator token on a buyer route are both refused by the role guard.
- [ ] No handler picks the record to update from a request body field.
- [ ] The matrix coverage test passes, with a row for every mutating route.
- [ ] `docs/EVIDENCE.md` holds the run summary, the four manual requests and the branch name.

Read a failure before you read a success. A 200 where you expected a refusal means the handler wrote first and refused afterwards, so the state reload matters more than the status. A 500 on a crossed request usually means the helper returned nothing and the handler read a property of nothing. A 403 where the matrix promised 404 tells you the ownership condition moved out of the query and into an `if`. Each of those points at one function, and none of them is fixed by editing a component.
