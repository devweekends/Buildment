# Shop the marketplace gate

This gate is passed with a narrow browser window, a keyboard and the network panel open. A shop page is easy to approve from a laptop screenshot and hard to pass when you stand where the buyer stands: a 360 pixel screen, a thumb, one hand and a metered connection. The gate checks what a screenshot cannot show, which is whether the facts survive the layout and whether anything private travelled with them.

The buyer path is short and that is the point. Filter the grid, open one product, compare two license options, choose one. Nothing is bought in this module, so every check below can run without a payment, a webhook or a license. The cart arrives in Module 16 and will consume exactly one value from this page: the license type the buyer chose.

Bring three artefacts to the review. The first is a filtered grid URL and its response. The second is the product page at 360 by 640 CSS pixels. The third is the saved JSON of the public product request, opened in a text editor so a reviewer can search it.

## Seed a shop with two real options

Use Nour's font with a personal option at 1,200 and a commercial option at 4,800, with one seat and three seats, and five downloads on each. Add Salma's template with a commercial option only, so the single option case is covered too. Keep one draft product and one archived product in the same Studios, because the grid and the public product route must both refuse to show them.

Give each product a cover preview and at least two more previews, each with alt text, so the gallery has something to reorder and something to describe. Keep the descriptions short enough to read at 360 pixels without scrolling for a minute.

## Filter, refresh and share

Walk the grid from the address bar, because the URL is the filter state. For each row below, change one parameter, refresh, and record what comes back.

| URL | Expected | What it proves |
|---|---|---|
| `/shop` | Published products, newest first | The default grid works |
| `/shop?category=template` | The CV template only | A category filter narrows the grid |
| `/shop?licenseType=commercial` | The font, the template and the ebook | Options decide the license filter |
| `/shop?maxPriceMinor=1500` | Products with any option at or below the ceiling | The price filter reads the cheapest option |
| `/shop?category=font&page=2` | A second page or an honest empty state | The page parameter survives a filter change |
| `/shop?category=nothing` | A message that clears the filters | Bad input is a sentence, not a blank grid |

Refresh on two different filtered URLs and confirm the grid is identical each time. Copy one URL into a second browser profile and confirm it opens the same list. A grid that keeps filters in component memory passes the first check and fails both of these, and the buyer loses their place every time the phone reloads the tab.

## Read one product page as a buyer

Open the font and read it top to bottom before touching anything. The first screen names the product, the Studio and the from price. The gallery shows the cover and the thumbnails. The description is readable at body size. The comparison is below, and it lists allowed use, seats, downloads and price for both options, in the same order for each.

Check the numbers against the stored document rather than against your memory: 1,200 and 4,800 in minor units, one seat and three seats, five downloads each, and the terms version that the option stores. A comparison that prints a seat limit nobody stored is a comparison that will disagree with the cart, the order and the license.

Confirm three absences. No option is selected when the page opens. The action button is disabled and says what is missing rather than showing a price it cannot charge. And the words for allowed use come from the server response, not from a string typed into the component, so the personal sentence says one person and non-commercial use while the commercial sentence names client work.

## Stand at 360 pixels

Set the browser to 360 by 640 CSS pixels and reload. Nothing may scroll sideways, and the price must be in the same full colour as the body text rather than faded into a caption. The comparison becomes one block per option, each block repeating its labels, so a buyer never has to remember a column header from two screens up.

Then put the mouse away. Tab to the gallery thumbnails, use the arrow keys to change the large preview, tab to the license group, choose with the arrow keys, and reach the enabled action. Every control must show a visible focus ring, and every tap target must be at least 24 by 24 CSS pixels, with the radio rows comfortably larger than that.

Repeat on a device if you have one, because a desktop browser resized to 360 pixels still has a desktop network and a desktop font rendering. Note in the evidence which one you used. This is not a formality: a comparison that fits at 360 pixels in a resized window can still overflow on a phone whose text is set larger in the system settings, so check one larger text setting too.

## Prove nothing private arrived

Save the public product response and search it for `storageId`, `sha256`, `sizeBytes` and any address that looks like a file delivery URL. All four must be absent. Then check the preview addresses: they are public images, they load anonymously in a fresh window, and they carry alt text. A preview that requires a signed request is a preview that will break on a shared link.

```js
// client/scripts/check-public-detail.mjs (shape only)
const body = await (await fetch(`${API_BASE}/catalogue/${id}`)).text();
const forbidden = ["storageId", "sha256", "sizeBytes", "deliveryUrl"];
const leaked = forbidden.filter((field) => body.includes(field));
if (leaked.length) {
  console.error(`product response leaked: ${leaked.join(", ")}`);
  process.exitCode = 1;
}
```

Run the same search against the preview image requests in the network panel. A gallery that fetches a private asset to render a thumbnail has already handed the buyer the deliverable, and no button in the interface can take it back.

## Gate checklist

- [ ] A filtered grid keeps its filters through a refresh and through a copied URL.
- [ ] Category, license type and price filters each return the expected products and no draft or archived product.
- [ ] An impossible filter renders a message with a way to clear it, not an empty page.
- [ ] The product page shows allowed use, seats, downloads, price and terms for every option.
- [ ] Every compared number matches the stored license option, including the seat and download limits.
- [ ] No option is selected on first render, and the action button is disabled until one is chosen.
- [ ] The gallery is operable with the keyboard alone and every preview has alt text.
- [ ] At 360 by 640 CSS pixels there is no horizontal scroll and every label repeats in the stacked layout.
- [ ] Tap targets are at least 24 by 24 CSS pixels and focus is visible on every control.
- [ ] The saved detail JSON contains no storage identifier, checksum, byte size or delivery address.
- [ ] The grid URL, the 360 pixel screenshot and the saved JSON are committed under `docs/SHOP.md`.

If the grid forgets its filters, the state is in the component. If a draft appears, the grid route is trusting a parameter. If a limit is wrong, the comparison is reading a copy instead of the option. If the action is enabled before a choice, something is preselected. If the page scrolls sideways at 360 pixels, the wide table is still rendering.

## Check the decision that caused the layout

```quiz
type: mcq
id: digital-goods-shop-q2
question: "At 360 CSS pixels the comparison shows one block per option with repeated labels. What must the gate still prove about the wide layout above 640 pixels?"
options:
  - "That the wide layout is the only one a keyboard user can reach, because tables are the accessible form"
  - "That both layouts read the same options array, so every fact and the chosen key are identical in each"
  - "That the narrow layout is hidden from screen readers, so the facts are announced once"
  - "That the price is formatted differently in each layout to fit the available width"
correct: 1
explanations:
  - "Both layouts must be reachable and usable. A table is not a substitute for a block that keeps its labels."
  - "Two renders from one source is the whole point: the layout changes, the facts and the chosen key do not."
  - "Hiding one layout from assistive technology creates two different pages for two buyers."
  - "A price that appears in two forms is a price that can disagree with the stored amount."
```

## Learning log

Answer these in `docs/learning-log.md` with the screenshot, the URL or the saved response beside each answer.

1. Which filtered URL did you refresh, and what proved the filters stayed in the address bar?
2. Which two facts in the comparison did you check against the stored option, and what were the values?
3. What does the page say when no option is chosen, and what changes when you choose the commercial option?
4. What did the keyboard walk look like, and which control was hardest to reach?
5. What did you change after the first look at 360 pixels, and what still did not fit?
6. Which forbidden string would you expect to leak first, and which file list would a careless serializer spread?

The sixth answer connects this gate to the previous module. The grid and the page are two views of a field list that lives on the server, and the day somebody spreads a document into JSON, both views leak together.
