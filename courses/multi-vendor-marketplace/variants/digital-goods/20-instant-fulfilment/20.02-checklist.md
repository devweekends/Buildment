# Fulfilment gate and replay evidence

Prepare two creator studios, one buyer and a checkout containing at least one product from each creator. Give one product a personal license and the other a commercial license with a different terms version. Record the server-priced amount, currency, checkout ID, PaymentIntent ID and order-line IDs. Keep the payment provider in test mode. The gate passes only when the database, API and browser agree on the same paid lines and the library access is created by a verified event.

## Show the first fulfillment

Pay once using the course's test card flow. Watch the webhook route verify the signature. Then inspect the database: there must be one order per creator, and each paid line must have exactly one license grant. The grants must refer to the buyer who paid, the correct product, selected license option and accepted terms version. The total of the order snapshots must equal the stored checkout amount in minor units. Open the library as that buyer and see both creators' products. Open the success page in a second tab; it should display the state that already exists and must not make a second grant.

If the library is briefly empty after the redirect, show its “Preparing your files” state. Refreshing this page cannot create access. Trace the webhook or reconciliation log to learn whether a verified event arrived. This is an important part of the demo: instant fulfillment means the normal path is fast, while the error path stays honest about delay. A buyer should not be asked to submit payment again merely because the library has not updated yet.

## Replay and reject

Replay the same valid event. Count orders and licenses before and after, then compare their IDs and keys. The counts and IDs should be identical. Trigger two fulfillment calls together and repeat the count. If a unique-index collision occurs, the code must read the existing row and finish the other lines rather than fail the whole checkout forever. Run a test that stops after one of several lines, restarts fulfillment and reaches a complete set of grants. An order must not show `fulfilled` while one paid line has no grant.

Send a request with a bad webhook signature. It must receive an error and create no order or grant. Try a provider object whose ID locates a checkout but whose amount or currency does not match it. The server must stop and log the mismatch. Do not repair the amount by trusting metadata from the browser or event. Login as a different buyer and request the first buyer's library. No license or private-file field from the first buyer may appear.

## Learning log

1. Explain why a browser redirect cannot create a license, even when the browser displays a success message. Name the server record that holds the price accepted at checkout.
2. Draw the unique keys for the per-creator order and for each license grant. Explain which effect each one makes idempotent.
3. Describe a crash after the first of three grants. Show how a second call fills the remaining grants without changing the first grant's ID.
4. Explain why you mark an event complete after the effects exist. What goes wrong if you mark it complete first and then the process stops?

Commit the tests, indexes, fulfillment function, webhook integration and success-page state. Save the replay log with the three grant IDs visible. A mentor must be able to rerun the replay test without resetting the database. Keep private storage identifiers out of the library response; the next module will introduce the download endpoint that reads them only on the server. If you cannot prove the invalid-signature and cross-buyer denials, the license is not ready to protect a private file.

## Inspect what a retry actually did

Take one run that included a duplicate event and write a three-column table in your learning log: the event or call, the rows it found, and the rows it created. A second delivery should find existing orders and grants, create none, and still return success so the provider stops retrying. If your logs show a duplicate-key error, include the line ID and the successful read of the winning grant. Do not log the license key or a private file URL. The log should explain the repair without exposing an asset or a buyer's credential.

Then stop the API process immediately after the first grant is written in a test fixture. Restart it and call the same fulfillment function. Record the before and after IDs for both lines. This exercise distinguishes a reliable retry from a handler that only works when every write succeeds at once. Check that the buyer's success page remains in a waiting state until all grants exist and that it never tells the buyer to pay again. If the page jumps to the library after one of two lines, fix the aggregate order-state condition rather than hiding the missing item in the UI.

Finally, verify the privacy boundary independently of fulfillment. Fetch the public catalogue as an anonymous visitor and inspect the raw JSON for storage IDs, private asset paths, license keys and signed links. There should be none. Fetch the library as Buyer B and inspect the same fields. It should not include Buyer A's grant. These raw-response checks are required even if both pages look correct, because a hidden field can be read by someone inspecting network traffic. Save the assertions beside the replay test so later changes to serializers cannot silently reopen this path.
