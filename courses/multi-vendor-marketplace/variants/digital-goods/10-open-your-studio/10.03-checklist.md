# Open-your-studio gate

This gate is about the first ten minutes of a creator's life on Midad, and it is checked on the device most fellows actually hold. You will create a fresh creator account, sign in on a 360 pixel wide browser, and confirm that the platform routes you to the onboarding form instead of an error, that the form finishes in one go, and that no product page opens before a studio exists. Then you will prove the same two rules from the server side, because a screen can only ask.

Start clean. Use an account that has no studio and has never had one, and confirm it by reading `GET /me/studio` with the creator's token and getting a 404 with the code `STUDIO_NOT_FOUND`. A reused test account from an earlier module will pass half of this gate by accident and teaches nothing.

## Walk the phone path

Open the browser at 360 pixels wide with the network throttled to a slow profile, sign in, and go straight to the products route. The expected result is the onboarding form, not an empty table and not a red bar with a status code. If your build shows a loading spinner forever, the hook is swallowing the 404; if it shows the form and then jumps away, the gate is re-reading stale state.

Fill the form with one hand. Type a studio name, watch the slug preview update, edit the slug by hand and confirm the preview stops following the name. Submit with the keyboard open. The form should save once, land on the dashboard, and show the studio name in the header without a page refresh.

Then break the connection on purpose and repeat the load, before submitting anything. The gate must show a retry panel rather than the onboarding form, because a failed request is not a missing studio. Restore the connection, tap retry once, and confirm you land where you were. This check takes a minute and it is the one that proves the four state model from the lesson.

## Prove no product page opens early

With a second fresh creator account and no studio, ask for the product routes. Two refusals belong in the evidence. In the browser, `/studio/products` sends you to onboarding and never renders a product table. In the terminal, `POST /api/v1/me/studio/products` with a valid token and a valid body returns 409 with the code `STUDIO_REQUIRED`, and the product collection count stays at zero. Run the terminal check because the browser cannot prove it: the client guard would pass even if the server rule were missing.

Close the studio with the settings toggle and confirm that a new visitor can still read the studio page and its address. Nothing about this gate depends on purchases yet, so the closed state only has to be visible and reversible at this point.

## Prove settings

Open settings on the same phone width. The three fields are pre-filled, the save button is disabled until you change something, and one edit followed by save changes the stored record. Then change the slug and confirm the warning appears before the save, not after it. Read the studio through the public route and confirm the new address answers and the old one returns 404, which is the behaviour this course chose and the reason the warning exists.

Finally, confirm that a creator cannot reach another creator's studio through any page in this module. The settings page has no studio id in the address, so there is nothing to guess, and that absence is itself the finding you write down. If you added a studio id to the settings URL, remove it before recording the evidence.

## What this gate does not prove

There is no product form yet, so the only product route that exists is the create endpoint the server refuses. The gate does not prove that the studio page looks good on a desktop, that the slug redirects are handled, or that a creator can recover a forgotten address. Those are named limits, not defects, and the module is finished when they are written down rather than discovered later.

## Keep the record short

One page in `docs/STUDIO.md` is enough: the phone screenshot of the form, the desktop screenshot of the dashboard, the raw 409 body, the retry proof and the two addresses after the slug change. Replace the account email with a fixture name and remove the bearer token from anything you paste. A mentor reading it should see the route Salma took from a fresh login to a working dashboard, and the two places where the platform could have refused her instead.

When a check fails, the cause is usually one of three. A redirect loop means the onboarding route sits inside the gate. An onboarding form that appears for a creator who has a studio means the hook is caching the first `missing` answer. A product create that succeeds with no studio means the server guard is missing and only the client guard was built. Each has a different fix, so name the fault before touching code.

## Gate checklist

- [ ] A fresh creator account with no studio is routed from `/studio/products` to the onboarding form, with no error status shown.
- [ ] A dropped connection during the creator area load shows a retry panel, and retry recovers without creating a studio.
- [ ] The onboarding form submits once, lands on the dashboard and shows the studio name without a refresh.
- [ ] The slug preview follows the name until the slug is edited by hand, and then stops.
- [ ] A 409 on the slug keeps the rest of the typed form and places the message under the slug field.
- [ ] The form is usable at 360 pixels wide with the keyboard open: no horizontal scroll, labels attached, submit reachable.
- [ ] The form works with the keyboard alone, with a visible focus ring on every field and on the status toggle.
- [ ] `POST /api/v1/me/studio/products` returns 409 `STUDIO_REQUIRED` for a creator with no studio, and no product is written.
- [ ] Settings loads pre-filled, keeps the save button disabled until a value changes, and saves one edit.
- [ ] The slug warning appears before the save, the new address answers 200 and the old address answers 404.
- [ ] The studio page still answers for a visitor after the creator closes the studio.
- [ ] One phone screenshot, one desktop screenshot, the raw 409 response and the retry proof are saved in `docs/STUDIO.md`.

## Learning log

1. Why does a 404 from `GET /me/studio` need its own state in the client, rather than a generic error handler?
2. What happens on your build if the studio state is updated after navigation instead of before it, and how did you prove the order?
3. The client guard redirects a creator away from the products page. Why is that not enough, and which request did you use to show the server enforces the same rule?
4. Name the two layout faults you found at 360 pixels and what you changed to fix each one.
5. A creator already has a studio and opens `/studio/new`. What does your build do, and why is showing the form a defect?
