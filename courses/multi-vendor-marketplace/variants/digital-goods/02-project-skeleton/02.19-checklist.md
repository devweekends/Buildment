# 2.19 Checklist and learning log

> **[Gate]** · Chapter 02: Project skeleton

This is the **gate** for Chapter 2. Tick every box honestly and answer the learning log below before opening Chapter 3.

<BigWordAlert term="Chapter gate" plainEnglish="A checklist of runnable proof points you must pass before the next chapter unlocks." whyItMatters="Midad gating is enforced on the platform, and skipping the health check means later chapters assume wiring that was never proven." />

A gate is not a form to fill in. It is the point where you stop being the person who followed the chapter and become the person who can defend the result. Everything below is written so that a mentor who has never seen your machine can run the same commands and reach the same answer. That is why most items name a command, a path or a visible state rather than a feeling.

Read the whole page before you start ticking. The items are grouped by the part of the system they test, and the prose above each group explains why the items exist and what evidence proves them. If an item surprises you, that is usually a sign the matching sub-chapter was skimmed, and the fix is to return to it rather than to argue with the box.

## Chapter 2: Project skeleton checklist (gate)

Do **not** open Chapter 3 until every box is ticked and learning log answers are written below.

Ticking order matters less than honesty. A box ticked because the command once worked in a different folder is worse than a box left empty, because the empty box still asks a question and the false tick does not. If something is genuinely broken and you cannot fix it today, write what you tried in the learning log and leave the box empty. The platform gate is the only thing standing between a small confusion and twenty chapters built on it.

### Repository and structure

The first group proves that your code lives somewhere you own and that its history is clean from the first commit. Item one exists because the course folder is a textbook, and an application built inside it mixes your commits with the material you are reading, which makes every later instruction about "your project root" ambiguous. Item two exists because ignore rules written after a mistake are too late: a deleted file keeps its place in the commit that held it, so the rule has to be in force before the first `git add`.

The third item is the one a reviewer treats as evidence rather than decoration. `git log --all -- "**/.env"` searches every commit on every branch for a path ending in `.env`, and the expected answer is no output at all. An empty result is a positive proof: it means no commit ever contained an environment file, not merely that the file is absent from the working tree today. The fourth item exists for the next reader, who needs two commands and two folders and nothing else. A README that is missing the client command is how a reviewer ends up guessing.

- [ ] An app Git repository lives at your own marketplace root, outside the course content folder
- [ ] Root `.gitignore` lists `node_modules/`, `.env` and build output
- [ ] `git log --all -- "**/.env"` prints **empty** output (an env file has never been committed)
- [ ] Root `README.md` spells out the two-terminal run steps for server and client

A reviewer reads this group from the bottom up. The README is the fastest thing to open and the fastest thing to falsify, because the commands either exist or do not. Then the history search, then the ignore file, then the repository root. If the repository root is a folder inside the course content, everything above it is suspect, so check the root first if you are the one reviewing.

### Server

This group proves the API half is real. The two script items exist because `dev` and `start` answer different questions: `dev` restarts on change during the chapter work, and `start` runs the code once the way a host will run it. A project with only a `dev` script works until the day it is deployed.

The `app.js` and `server.js` split is the most consequential structural item in the chapter, and it is the one learners most often collapse into a single file. `app.js` builds the Express app, registers middleware and routes, and exports it without opening a port. `server.js` imports that app, reads the port and calls `listen`. The split exists so the app can be exercised without a network socket, which matters immediately when you test a route and later when a request has to be replayed against a running instance. When both live in one file, every test needs a real port and every port clash looks like a code bug.

The module folder item exists because every later chapter names an exact path. The folder is not busywork, it is the address the next twenty lessons post to, and a missing folder turns each instruction into a translation exercise. `shared/` gets its own item because database and config code will not belong to any single capability, and a home for it now prevents a `utils.js` that grows in every direction later.

The last two items are the runnable proof. `npm run dev` in `server/` proves the process starts and stays up, which catches a missing dependency or a syntax error. The curl item proves the request path with the exact command a reviewer will type, and the evidence is the status line and the body together, not a browser page that might be cached.

- [ ] `server/package.json` defines both a `dev` and a `start` script
- [ ] `server/src/app.js` assembles the Express app, adds JSON middleware and exports it without listening
- [ ] `server/src/server.js` calls listen on `process.env.PORT`, falling back to `5000`
- [ ] Module folders in place: `auth`, `studios`, `products`, `cart`, `orders`
- [ ] `server/src/shared/` folder present
- [ ] `npm run dev` inside `server/` boots without crashing
- [ ] `curl -i http://localhost:5000/health` answers **200** with JSON carrying `"status":"ok"`

To read this group as a reviewer, open `package.json`, then read `app.js` and confirm the file has no `listen` call, then run the curl and look at three parts of the output: the HTTP status line, the `Content-Type` header and the body. A 200 with an empty body usually means the route was matched by a catch-all. A 404 with a JSON body usually means the route is mounted under a prefix you forgot. A connection refused means the server is not listening on that port at all, which sends you back to `server.js`.

### Client

This group proves the browser half exists and that it is wired to the API rather than pretending to be. The folder item is checked first because the shape of the client decides where every later screen goes. The router item exists because Midad has more than one screen by design: the Home page is a route, not an exception, so the router arrives before the second page does.

The environment item and the helper item belong together. `client/.env.example` documents the one variable the client needs, and the helper reads it in a single place. The extra clause in that item, that components contain no hardcoded localhost, is the actual test: one `fetch("http://localhost:5000/health")` inside a page is enough to make the base URL unfixable later, because a deployed bundle would point at the learner's laptop.

The last two items carry the most weight, and they are deliberately paired. The live health item proves the client can reach the API when it is running. The error state item proves the page is showing a value that came over the network rather than a string typed into the file. A page that shows "status ok" with the server stopped is not a working demo, it is hardcoded output, and it fails the gate even though it looks successful at first glance.

- [ ] Vite React app under `client/` with `pages/`, `components/`, `api/` and `hooks/`
- [ ] React Router serves Home at the `/` path
- [ ] `client/.env.example` records `VITE_API_URL`
- [ ] `client/src/api/client.js` takes the base URL from env, and no component hardcodes localhost
- [ ] `npm run dev` inside `client/` boots without crashing
- [ ] Home page shows the **live** health status while the API is running
- [ ] Home page shows an **error state** once the server stops (proof it is not hardcoded)

A reviewer tests this group in one order: stop the server, reload the page, and read the screen. Only then start the server, reload again and watch the message change. If the page looks identical in both states, the health check was never connected. If the page shows an error with the server running, read the browser console before reading the server code, because a CORS refusal and a wrong URL look the same on screen and different in the console.

### Integration

These three items are about the seam between the two applications, which is where a scaffold that passes every individual check can still fail. CORS exists because the browser enforces it: the client on port 5173 and the API on port 5000 are different origins, and without a rule the response is blocked before your code sees it. The Network tab item exists because it is the only view that shows the request the browser actually made, with the origin, the status and the headers, rather than the request you meant to make.

The reference to 2.16 exists so this gate is not a second, softer version of the end to end verification. Do that step once properly, then tick the item and point at your screenshot.

- [ ] CORS configured so browser can call API from Vite origin
- [ ] Browser Network tab shows successful `GET` to `/health` with 200
- [ ] End-to-end verification from **2.16** completed

Read a failed CORS case from the console message, not from the server log. The request often appears in the Network tab with a status of blocked and a note that the response lacked the allow origin header. That tells you the server answered and the browser refused, which is a different fix from a request that never arrived.

### Understanding (self-check, explain aloud)

No command proves these four, which is why they are phrased as sentences you say out loud. Reading your own tree is a different skill from writing it, and a person who cannot explain the layout will not be able to debug a path error in Chapter 6 under time pressure. Say each answer to yourself or to a mentor before ticking it. A sentence that trails off is a box that should stay empty for now.

- [ ] I can explain the **module-based** layout against a layer-based one, and why Midad picked modules
- [ ] I can explain which work happens in the **browser** and which in the **Node server**
- [ ] I can explain why **`app.js` and `server.js` stay separate files**
- [ ] I can point at the folders where **auth** and **products** code will sit in my tree

The strongest version of the first answer uses a change rather than a definition: adding a discount code or a license option touches one folder instead of five layers. The strongest version of the second answer names the secret that must never reach the browser, because that is the practical consequence of the boundary rather than a diagram of it.

### Learning log, write now

Answer **in your own words** in the fields below:

1. **Draw or paste your folder tree** (server + client) as it stands after Chapter 2. Annotate one sentence per module folder describing its future job.

2. **Why did this course require module-based folders instead of layer-based?** Use the "add discount codes" or "add products feature" argument, not "because the course said so."

3. **What happens at runtime when a user opens your Home page?** Trace the path: browser → React → fetch → Express → response. Mention ports and CORS.

4. **Why must secrets like `MONGODB_URI` (coming Chapter 4) live only in `server/.env` and never in the React app?**

5. **What did you verify in the failure-mode test (server stopped)?** Why is error UI important even for a health check demo?

6. **What will change on `/health` in Chapter 4 when MongoDB connects?** Speculate based on the course outline, one paragraph.

Write full sentences, and prefer a concrete detail over a definition. In question three, a strong answer names port 5173, port 5000, the helper that holds the base URL, and the allow origin rule that lets the browser accept the response. In question four, the answer that scores is about where the bundle runs: client code is served to every visitor, so a value inside it is public the moment the page loads, while the server keeps its environment to itself.

Question five is the one to answer with evidence rather than opinion. Describe the screen, the console message and the Network entry you saw with the server stopped. Question six is speculation and is graded as such, but a good answer notices that a health route which reports database state changes from a constant to a value that can fail, which is why the surrounding error handling has to exist before the check is added.
