# Products and licence gate

This gate proves four things about the product API: the wrong creator cannot read or change a product, an option list is validated before it is stored, prices and limits are integers that survive arithmetic, and a product cannot be published without a live option. Each one is checked with a raw request and a database read, because a product table that renders correctly proves none of them.

Prepare two draft products for Nour and one draft for Salma. Give Nour's font a personal option at 1200 and a commercial option at 4800, and give Salma's template a personal option at 900. Keep Amina as a buyer with no creator role and keep the studio indexes and the compound product index built before the first request.

## Check isolation on every route

Sign in as Salma and request `GET /me/studio/products`. The response must contain her draft and nothing of Nour's. Then request Nour's product by id through `PATCH` and through the publish route with Salma's token. Both must answer 404, and both documents must be unchanged afterwards: same `updatedAt`, same status, same option array. Compare the two documents before and after rather than trusting the status code, because a handler can deny and still write.

Repeat the publish attempt with Amina's buyer token. The role middleware answers 403 before any query, and the expected result is an unchanged product. That failure is different from the 404 above and both belong in the evidence, since one is a role refusal and the other is an ownership refusal.

## Check option validation

Send a create request with `priceMinor: 12.5`. Expect a 400 that names the field, and no product in the collection. Send `seatLimit: 0` and `downloadLimit: -1` and expect the same. Send two options with the key `personal-v1` and expect a refusal from the offer service rather than from the schema. Send `termsVersion: "personal-v99"` and expect a refusal, then fetch `GET /terms/personal-2026-01` and confirm the text a buyer would read is served.

Send a valid create with one personal option, then update it with a commercial option added under a new key. Both options now exist, and the personal one still holds its original price. This is the shape the cart and the checkout depend on, so confirm it in the raw document rather than in the product form.

## Check the publish rule

Publish Nour's font and confirm the status and `publishedAt` in the database. Try to publish it again and expect a refusal that leaves the first `publishedAt` intact. Now build a fresh draft with no options, attempt to publish, and confirm a 400 with `NOT_SELLABLE` and a product still in draft. Then retire every option on a third draft, attempt to publish, and confirm the same refusal, because a retired option is not purchasable.

Try to publish through the public route, which has no publish action and answers 404. Then try a direct database write that sets `status: "published"`. The second is the interesting one: if the document accepts the state, add the guard you wrote in the lesson and prove it with a saved test. A rule that lives only in the route is a rule that the next import script will bypass.

## Check the public boundary

Fetch `GET /studios/nour-type/products/minimal-serif` for a published product without a token. The response contains the title, the studio name and both option summaries with `priceMinor` as an integer. It contains no draft product, no retired option shown as purchasable, and no storage field. Fetch the draft product under the same studio address and expect a 404. Then check the option key list and confirm every key a buyer can see resolves to a terms version that `GET /terms/:version` can serve.

## Check the arithmetic

Add the two options of Nour's font together in a test and assert `6000`, not `"$60.00"`. Format the value only in the assertion that renders it. Send a cart-like payload with `priceMinor: 1` for the commercial option and confirm the server ignores it, because the price comes from the stored option and not from the request. That refusal is the boundary Module 18 will rely on when it freezes the checkout total.

## What this gate does not prove

No file is attached to these products yet, so a published product here is not yet deliverable. Module 13 adds the private file and the second publish condition. The gate also does not prove that the product form works on a phone, that the option editor reorders rows without losing input, or that a buyer can compare two options on a page. Module 12 and Module 15 own those checks.

## Gate checklist

- [ ] `GET /me/studio/products` returns only the signed-in creator's products.
- [ ] A wrong creator receives 404 on update and on publish, and the target document is unchanged.
- [ ] A buyer receives 403 on the creator product routes.
- [ ] `priceMinor: 12.5`, `seatLimit: 0` and `downloadLimit: -1` are each refused with a field-level 400 and no write.
- [ ] Two options with the same key are refused by the offer service.
- [ ] An unknown `termsVersion` is refused, and `GET /terms/personal-2026-01` serves the text.
- [ ] A product may hold one personal and one commercial option at the same time.
- [ ] Publishing sets `status` and `publishedAt`; a second publish attempt changes neither.
- [ ] A draft with no options and a draft with only retired options both return 400 `NOT_SELLABLE` and stay in draft.
- [ ] The public route returns no draft product and no storage field, and every option key resolves to a terms version.
- [ ] A total built from two options is an integer sum, and a client-supplied price is ignored.
- [ ] The raw requests, the before and after documents and the option key list are saved in `docs/PRODUCTS.md`.

## Learning log

1. Which value scopes every product query, and where does it come from when the client sends a product id in the path?
2. Why is validation split between the Mongoose schema and the offer service, and name one rule that only the service can enforce.
3. A creator changes the personal price after three paid orders exist. Walk through what changes for the next checkout and what stays fixed for those three orders.
4. Your publish route checks for a live option. What second check does Module 13 add, and why does it belong in the same function rather than in the route?
5. A product document was set to published by a seed script with no options. What does the app do when a buyer opens it, and which test would have caught this earlier?
