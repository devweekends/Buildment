# A public catalogue with private files

Amina has 600 megabytes left on her data plan and a client presentation at nine tomorrow. She needs a CV template she can edit tonight, and she is holding a phone whose screen is 360 CSS pixels wide. She opens Midad, chooses a category, sets a maximum price and scrolls. Every extra kilobyte and every wasted tap is a real cost to her, and she has no patience for a page that loads in three steps.

That screen is one route. `GET /api/v1/catalogue` answers an anonymous request with a page of published products, filtered, sorted and paginated. It is the most read endpoint in the product, and it carries two promises at once. It must be fast on a weak connection, and it must never contain a field that leads to a private deliverable. The first promise is about queries and indexes. The second is about a serializer, and it is the one that ends companies.

## One request, five steps, two ways to fail

Follow a single request before you write it. Amina's browser sends a category, a price ceiling and a page number. The route parses those values, builds a filter, reads one page of products, resolves the Studio names, and serializes each document into a card. The trace below marks the two steps where this route goes wrong in practice.

Read the trace downwards and look for the two fragile steps. The fourth step is where the N+1 problem appears: the moment a card shows a Studio name, the obvious implementation looks up that name inside the loop over cards, and the request becomes one query plus one query per row. The fifth step is where a private file escapes: the moment somebody spreads a database document into JSON, every field the Product or its file records carry goes to the browser.

The private file is not part of this document at all. Module 5 put the deliverable in a separate `ProductFile` collection with a storage identifier, a size and a checksum, and Module 13 uploads it as an authenticated asset. The catalogue does not join that collection. It cannot leak a field it never loads, which is a stronger guarantee than a filter applied after loading everything.

## What a card may carry

A card exists to help a buyer decide whether to open a product. It carries the product identifier, the title, the category, the file format, the Studio display name and slug, the public preview images with their alt text, the license options reduced to what a comparison needs, and the date it was published. That is enough for a grid, a filter and a price label.

The card must not carry a storage identifier, a checksum, a byte size, a delivery URL, a download count, a license key, a buyer identifier, an internal upload status, a moderation note or a creator email. Most of those fields do not exist on a Product, and the serializer should not be able to include them even after somebody adds one. An allowlist does that. A serializer that spreads the document and deletes three keys does the opposite: the next field a developer adds is public until somebody remembers to exclude it.

That decision has a cost worth naming. Refusing unknown parameters makes the route stricter than most public APIs, and a client that adds a tracking parameter will break. Keep the accepted list documented in one place, name it in the error, and treat any change to it as a change to the contract.

## Anonymous means published

The catalogue has no token, so it can never ask who is calling. Everything it returns is public, and the only status it may read is `published`. A `draft` product must answer `404` by identifier even when the visitor guesses the identifier correctly, and an `archived` product must answer `404` as well, because the creator withdrew it. A `404` with no title in the body is the honest answer for both.

Do not rely on the list filter alone. A visitor who copies a product identifier out of an old link will call the detail route, and the detail route needs the same rule. Two routes, one predicate, and the predicate lives in the service so that a third route cannot invent its own version of it.

The same rule explains why the public card never shows a draft's option prices. A creator may try three prices on a draft and settle on one. A catalogue that shows the discarded prices has published a decision she has not made, and a buyer who saw 900 will argue about the 1,200 she charges tomorrow.

## Speed is a field list and an index

Two things make this route fast, and neither is a cache. The first is a small page: twenty cards, each with a short description trim and a preview address rather than an image payload. A page of twenty should weigh the same as a handful of photographs, well under a hundred kilobytes, because Amina is paying for each of those kilobytes.

The second is an index that matches the filter and the sort of the default request. Most visitors arrive with no filter at all, so the default query is the one to index: published products, newest first, twenty at a time. The next lesson builds the filters and the indexes together, because a filter that no index covers is a slow route waiting for a large collection to reveal itself.

There is a third thing that looks like speed and is not. A cache in front of an unscoped or leaky route hides a defect until the cache is cold, and then returns it to everyone at once. Module 22 adds caching on top of a correct route, with invalidation on every product change. This module earns the correctness first.

The query budget is a test, not a target. A page of twenty cards that runs three queries will run three queries when the page holds sixty, and that property is what you assert in the repository. Without the assertion, a later feature that adds the creator's display name to each card quietly turns a three query route into a twenty-three query one, and the page still looks right in development where the database is on the same machine, empty and fast.

Bad input deserves the same care as a fast query. A visitor who sends `page=abc`, `minPriceMinor=-5` or `minPriceMinor=9000` above `maxPriceMinor=100` should receive a `400` that names the parameter, not an empty grid and not a `500`. The two wrong answers have different costs: an empty grid tells Amina that no template matches her filter, and a `500` tells her the site is broken. Both are false.

The grid and the product page are different routes on purpose. The grid answers "which products should I open", so it carries one preview address per card and a short description. The product page answers "what exactly am I buying", so it carries the ordered preview gallery, the full description and the complete license comparison. Module 15 builds that page on top of the public product route from Module 11, which keeps the same status rule and its own field list.

## What the next two lessons add

Lesson 14.2 builds the route: validated filters for category, format, license type and price, pagination with a total and a stable sort, one lookup for the Studio names on the page, indexes for the filters, and a serializer with a field list. It also builds the test that counts queries, because a page that costs forty queries and a page that costs three return the same JSON.

Lesson 14.3 is the gate. It checks a filtered page, a page boundary, the index evidence and the raw JSON, and it asks you to search that JSON for a private field. If the search finds anything, stop: the rest of the course depends on the catalogue being unable to reveal a deliverable.
