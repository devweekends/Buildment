# Browse catalogue gate

This gate is passed with a seeded catalogue, a query counter log and a raw JSON file, not with a screenshot of a grid. A catalogue route looks finished as soon as products appear, and that appearance hides three separate failures: a filter that runs after the read, a query count that grows with the page, and one private field that a serializer copied because it was in a hurry.

Bring three artefacts to the review. The first is the counter output for two page sizes. The second is an `explain("executionStats")` plan for the default request. The third is the whole response body for a filtered page, saved as a file so a reviewer can search it. Without those three, a reviewer can only confirm that something loaded.

## Seed a catalogue worth filtering

Four published products across two Studios are enough to test every filter, and they must differ in ways the filters can see. Give Nour a font with a personal and a commercial option, and an icon pack with a personal option only. Give Salma a CV template with a commercial option only, and an ebook with both options. Publish all four at dates at least a minute apart, then set the same timestamp on two of them so the sort has a tie to break.

Add one draft product and one archived product, both belonging to a Studio that already has published work. Those two are the traps. A draft that belongs to a Studio with no published products can disappear for the wrong reason, and the gate would pass without testing the status filter.

## Walk the filter matrix

Send each request anonymously and record the identifiers that come back.

| Request | Expected | What it proves |
|---|---|---|
| `GET /api/v1/catalogue` | The four published products, newest first | The default request works and the draft is absent |
| `GET /api/v1/catalogue?category=font` | One product | Category is an equality filter |
| `GET /api/v1/catalogue?format=pdf` | One product | Format is an independent equality filter |
| `GET /api/v1/catalogue?licenseType=commercial` | The font, the template and the ebook | The license type is read from the derived array |
| `GET /api/v1/catalogue?maxPriceMinor=1500` | Every product with an option at or below the ceiling | The ceiling compares with the cheapest option |
| `GET /api/v1/catalogue?minPriceMinor=4000` | Only products whose highest option reaches the floor | The floor compares with the most expensive option |
| `GET /api/v1/catalogue?status=draft` | 400 naming `status` | Status is not an offered parameter |
| `GET /api/v1/catalogue?page=abc` | 400 naming `page` | Bad input is refused, not emptily answered |
| `GET /api/v1/catalogue?limit=1000` | At most 60 cards | The cap is enforced on the server |

The fifth and sixth rows are the ones people skip. A single price per product cannot answer either question when a product has two options, and the two rows together are what prove the derived fields are honest. Change the personal price of the font from 1,200 to 900 and repeat the ceiling request: the font must now appear where it did not before.

## Prove the page boundaries

Request `limit=5` on page one and page two, with five published products in the collection. Concatenate the two pages and compare the identifiers with the full list. A product must not appear twice, and none may be missing. Then set three products to the same `publishedAt` and repeat. The `_id` tiebreak is what makes the order stable, and without it this check fails intermittently, which is worse than failing once.

Request a page past the end and expect `200` with an empty array, a `total` that still matches the collection, and `hasMore` false. That combination is the distinction between "no more products" and "no products at all", and the client needs both to draw an honest empty state.

## Count the queries

Run the counter test twice, once with `limit=20` and once with `limit=5`, and save the two operation lists. The numbers must be equal and no larger than three. Write the two counts and the model names into `docs/CATALOGUE.md`, next to the command you ran. A reviewer who sees `Product, Product, Studio` twice can tell at a glance that the per row lookup is gone. A single number with no operation names cannot be checked.

If the count is four or higher, one of the three queries has been split. The likely cause is a lookup inside the map that builds the cards, and the fix belongs there rather than in a cache.

## Read the plan

Run `explain("executionStats")` for the default request and for a request with `category`, `format` and `maxPriceMinor`. Save both plans. In each one, find the winning plan, the index name it used, `nReturned` and `totalDocsExamined`. The two last numbers should be close: a plan that examines thousands of documents to return twenty is a collection scan with extra steps.

If the default request scans, check the key order of your first index. It must start with the status the service always writes, then the sort field, then the tiebreak. If the filtered request scans, check whether the index for that filter starts with the field the request actually uses, because an index beginning with a field the request omits cannot serve it.

## Search the response for what must not be there

Save the full JSON body of a filtered page, then search it for five strings: `storageId`, `sha256`, `sizeBytes`, the title of the draft product, and the title of the archived product. Five misses is the pass. Do the same search on the public product response from Module 11 for a published product, because that serializer is where a join to private records is tempting.

```js
// server/scripts/audit-public-json.mjs (shape only)
const body = await (await fetch(url)).text();
for (const forbidden of ["storageId", "sha256", "sizeBytes", "Draft font", "Archived pack"]) {
  if (body.includes(forbidden)) {
    console.error(`leaked: ${forbidden}`);
    process.exitCode = 1;
  }
}
```

A blunt string search is the right tool here. It does not care which route added the field, which serializer built it or whether the field name was nested one level deeper than you expected.

## Gate checklist

- [ ] The default request returns every published product, newest first, and no draft or archived product.
- [ ] Category, format, license type and both price bounds each return the expected set on the seeded catalogue.
- [ ] Changing one option's price changes the result of a price bound request.
- [ ] A status, page or limit value that cannot be served returns 400 naming the parameter.
- [ ] `limit=1000` returns at most 60 cards.
- [ ] Two consecutive pages contain no duplicate and no missing product, including when timestamps tie.
- [ ] A page past the end returns 200 with an empty array, the true total and `hasMore` false.
- [ ] The query counter reports at most three operations, and the same number at both page sizes.
- [ ] The saved plan for the default request uses an index and examines close to the number of documents it returns.
- [ ] The saved response bodies contain no storage identifier, checksum, byte size or unpublished title.
- [ ] The counter output, both plans and the two JSON files are committed under `docs/CATALOGUE.md`.

If a draft appears, the status is coming from the query string or from the client. If a price bound is wrong, the derived fields were not recomputed on the save that changed the option. If the query count grows with the page, a lookup moved inside the card loop. If the plan scans, the index key order does not match the request.

## Check the reason, not the symptom

```quiz
type: mcq
id: digital-goods-catalogue-q2
question: "The default catalogue request returns twenty correct cards, the counter reports three operations, and the saved plan shows a collection scan examining 4,000 documents. Which change addresses the plan?"
options:
  - "Raise the query limit and take the first twenty rows in the client"
  - "Put a cache in front of the route and keep the index list as it is"
  - "Reorder the default index so its first key is the status the service always writes, then the sort field"
  - "Add a text index on the title and another on the tags so the database can find products faster without changing the plan"
correct: 2
explanations:
  - "A larger limit returns more wrong rows and moves the work to a phone."
  - "A cache hides the scan until the first miss and leaves every cold request slow."
  - "A compound index is usable only when the request supplies its leading field, and the default request always supplies the status."
  - "A text index serves text search, and the default request has no text term."
```

## Learning log

Answer these in `docs/learning-log.md` with the artefact that supports each answer.

1. Which request did you use as the default, and which index did the plan choose for it?
2. What were `nReturned` and `totalDocsExamined` for the default request, and what does the gap mean?
3. Which two page sizes did you count, and which model names appeared in each list?
4. Which price bound did you break by editing an option, and what did you change in the save path so it healed?
5. Which forbidden string did you search for last, and why was that one the easiest to leak?
6. Why does the route refuse an unknown parameter instead of ignoring it, and what does that decision cost a client?

The fifth answer is worth keeping. Private fields rarely leak through a field somebody meant to publish. They leak through a nested object that was copied whole, and the search is cheap enough to run before every release.
