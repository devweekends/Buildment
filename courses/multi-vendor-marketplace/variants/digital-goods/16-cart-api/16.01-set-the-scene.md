# A digital cart line is a licence

Amina finds Nour's font on Midad and presses Add to cart. The page she is using was built from a template that also serves shops that sell physical items, so it shows a small box with the number 1 in it and two arrows beside it. She has a personal use for the font and a paid client job in the same month, so she moves the number to 2 and continues. Nothing she does next will give her two of anything.

That box is the first lie a digital cart tells. A cart for downloadable work is not a smaller version of a cart for objects. It holds a different kind of claim: which product the buyer wants, and the terms under which they may use it. Every rule in this module follows from that one sentence, and this chapter settles the record before any route is written.

By the end you can explain why a cart line has no quantity, why a product appears at most once in one cart, why changing the license replaces the line instead of adding one, and why a product the buyer already holds is refused. You can also say who a cart belongs to and what it borrows from the Product.

## Count what can run out

A retail cart counts units because units are consumed. Two chairs leave with two buyers, and the seller has two fewer. The buyer's second copy has a cost to the seller, so a second line with a quantity of two is an honest description of what will happen: another unit moves, another charge is due.

A font does not work that way. Nour uploads one ProductFile. When Amina downloads it, the file is copied to her device and Nour still has the original. A second copy costs Nour nothing to make, holds no inventory, and cannot be handed over twice in any meaningful sense. Charging twice for it would be charging twice for the same bytes.

What Amina actually needs more of is permission. Permission is already a first-class record in Midad: the license option. Module 11 gave every Product at least one option with a type, a price in minor units, a download limit, a seat limit and a terms version. Nour's commercial option on the font allows three named seats. If Amina needs the font for herself and two colleagues, she does not need two copies. She needs the commercial option, once.

A quantity field on top of that would be a second and contradictory way to express the same need. Two sources of truth for "how many people may use this file" leave a system where the order says two, the License says three seats, and support cannot say which one the buyer is entitled to. So the cart line in Midad carries the fields below, and there is no quantity among them.

```js
// server/src/modules/cart/cart.model.js (fields only, imports omitted)
const cartLineSchema = new Schema(
  {
    productId: { type: Schema.Types.ObjectId, ref: 'Product', required: true },
    licenseType: { type: String, enum: ['personal', 'commercial'], required: true },
    licenseOptionKey: { type: String, required: true },
    studioId: { type: Schema.Types.ObjectId, ref: 'Studio', required: true },
    addedAt: { type: Date, default: Date.now },
  },
  { _id: false }
);
```

The line stores `licenseOptionKey` as well as the type, because the seat count, the download limit and the price belong to the option rather than to the type alone, and the key is the stable name Module 11 gives it. That stored option is a convenience for rendering and validation. It is not the price of record. Module 18 re-reads the Product and the option at checkout and freezes a snapshot on the OrderLine, so a creator who edits a price cannot change a total that was already shown to a buyer.

## One line per product

The second rule is that a Product appears at most once in a buyer's cart. Adding a product that is already there does not create a second line. The route either replaces the license type on the existing line or returns the line unchanged.

Three failures follow from breaking that rule, and all three are expensive. The first is the obvious one: two lines mean two charges for one deliverable, and the buyer notices on the payment page. The second is worse. Module 20 creates one License per paid OrderLine, so two lines become two Licenses for the same file, each with its own key, its own download limit and its own seat list. The library then shows two identical entries, and the buyer cannot tell which one they should use. The third is the refund case: a creator refunds one of the two lines, one License is revoked, and the buyer's access to a file they paid for twice becomes a support conversation about which row in the library is the real one.

There is a near-miss worth seeing because most people write it first. It looks like this.

```js
// The version that passes every manual test
await Cart.updateOne({ buyerId }, { $push: { lines: line } });
```

A human clicks Add once, sees one line, and moves on. Then a double click arrives in two requests, or a request times out on a weak connection and the client retries, and the same product is pushed twice. The guard that prevents it is a filter on the same write, not a separate read before it, and the next chapter builds it.

## A license switch is a change of terms, not a second purchase

When Amina decides the personal license is not enough, she is not buying something new. She is changing the terms of the one claim she holds. So the cart route for that decision is a patch on the existing line: the license type and the option change, the price changes with them, and the number of lines stays at one.

This is where the digital cart and the retail cart part company for good. In a retail cart, "make it the large one" and "add another one" are two different operations on two different attributes. Here they would be the same operation, because the size is the permission.

The stretch module on pricing adds the upgrade that buyers expect from this point: pay the difference between the personal and commercial price and keep the same purchase. The core path does not prorate. It charges the full commercial price for the commercial license, and the interface has to say so in plain words rather than let a buyer discover it at the payment page.

## Refuse what the buyer already owns

The fourth rule is the one that saves the most support time. If the buyer already holds an active License for this Product under the same license type, the file is already in their library. A second purchase grants nothing that the first did not, and it creates a second License that can only confuse the library and the refund path.

The refusal is a 409 with a code such as `already_owned` and a pointer to the library, not a 403. The buyer is allowed to make this request. It is the state of their own account that stops it. The message names the product and the license type, because "already owned" on a cart with eight lines across four creators is not actionable.

The predicate behind the refusal has three parts, and each one matters. It matches the same buyer, taken from the session and never from the request body. It matches the same Product. It matches the same license type, and it requires the License to be active, which excludes a revoked or refunded one.

That last condition is the one people forget. If the check were `License.exists({ buyerId, productId })`, a buyer whose refund was processed could never buy the product again. Support would have no normal route to fix it, and the buyer would be told they own something they cannot download. A revoked License means the buyer needs the product again, so it must not block the add.

A buyer who owns the personal license and asks for the commercial one is a different case. Commercial grants rights the personal license does not: paid client work and several named seats. The cart accepts that line. The interface has to state that the personal purchase does not reduce the commercial price, because a buyer who just paid for one license reasonably expects the second to cost less.

## One cart, several creators

Amina's cart can hold a font from Nour, a CV template from Salma and an icon pack from Salma. That is three lines, two Studios and one Cart. She pays once. Module 18 splits the cart into one Order per Studio at checkout, and that split is the reason every cart line records `studioId`.

The Studio on the line comes from the Product that was loaded on the server. It is never read from the request body. If a client could send a Studio with a line, it could move a charge into another creator's order, and the creator would see revenue for a product they do not own. Taking the value from the Product closes that door without a permission check.

The cart is also the first place the buyer can see that one payment covers several creators. A flat list of eight lines with a single total does not show that. Grouping the rows is the subject of Module 17, and it exists because the buyer's Orders and the buyer's refunds will be per creator even though the payment is not.

## The cart belongs to one buyer

Every cart route resolves the cart from the session. `GET /api/cart` for a buyer with no cart answers with an empty cart rather than a 404, because an empty cart is a state the interface must render, not an error.

A request body that contains `buyerId`, `studioId`, `priceMinor`, `licenseType` on the wrong route, or `quantity` is refused with a 400 and a named code instead of being quietly ignored. Ignoring is how a stale client keeps sending two of something for a year while every server-side symptom looks healthy. A visible refusal in development is cheaper than a wrong charge in production.

There is no route in the core path for one buyer to read another buyer's cart, and no admin override. If you later need one for support, it is a new decision with its own row in `docs/AUTHORIZATION.md`, not a query parameter on an existing route.

## The life of one line

The diagram shows the states a single cart line can be in. Read it as a claim about what an add request is allowed to do.

<StateMachine title="States of one cart line" chart={`stateDiagram-v2
  [*] --> empty
  empty --> in_cart_personal: add with the personal option
  empty --> in_cart_commercial: add with the commercial option
  in_cart_personal --> in_cart_commercial: switch license, same line
  in_cart_commercial --> in_cart_personal: switch license, same line
  in_cart_personal --> empty: remove
  in_cart_commercial --> empty: remove

  in_cart_commercial --> frozen: checkout freezes the lines
  frozen --> [*]
`} />

Notice what is missing. There is no state for a second line of the same product, because nothing may create one. There is also no transition out of `empty` for an add that names a product the buyer already owns: a refused add is not a state change at all, and the buyer stays where they were with an explanation and a link to their library.

The two switch arrows both point at the other license state on the same line. That is the whole argument of this chapter in one picture. A license switch is a self-replacing move inside `in_cart`, not an edge into a second line, and `frozen` is reached once per product no matter how many times the buyer changed their mind before checkout.

## Choose where the cart lives

The cart is stored in MongoDB with one document per buyer, not in the browser. That is a decision with a cost, so state it plainly.

The choice was made because Amina moves between a phone and a shared laptop, often on a weak connection, and a cart that vanishes when she changes device is a lost sale. The database also puts the owned-license check on the same server that will price the cart, which is the only place the check can be trusted.

The cost is a write on every add, a document per buyer to clean up when carts are abandoned, and one more collection to index and test. The alternative is a `localStorage` cart that the server validates only at checkout. That is a legitimate design for a single seller with one client, and it is worth naming rather than dismissing: it needs no writes, no cleanup and no schema. It fails here for a specific reason. A cart in browser storage cannot answer "do I already own this" without a server round trip anyway, and it cannot survive the device switch that this audience makes every day. If Midad ever ships one web client used on one device, the calculation changes.
