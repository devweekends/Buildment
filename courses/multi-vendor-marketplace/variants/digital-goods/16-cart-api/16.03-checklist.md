# Cart API gate

This gate is passed with a terminal and a database window, not with an opinion about the code. You need two creators, one published product from each, one product Amina already owns, and two buyer accounts. Keep one product unpublished so you can prove the route will not add it.

Prepare the evidence folder first. Every check below gives you a request, a status code and a document state, and the three together are what a mentor reads. A screenshot of a green test run is not evidence that the guard exists in the database you are using.

Start by signing in as Amina and calling the cart. The first response must be an object with an empty `lines` array and a 200, not a 404 and not `null`. The interface needs an empty cart to render, and a route that hides that state forces every client to guess.

```bash
curl -s -b amina.cookies http://localhost:4000/api/cart
curl -s -b amina.cookies -X POST http://localhost:4000/api/cart/lines \
  -H 'content-type: application/json' \
  -d '{"productId":"<nour-font>","licenseType":"personal"}'
```

## Prove one line per product

Add Nour's font once. The response carries `status: "added"` and a cart that holds one line, and its status code is 200 because the route returns the whole cart rather than a single addressable row. Add the same product with the same license type again, and the response carries `status: "unchanged"` while the line count stays at one.

Then do it the hard way, because a human clicking twice is not the failure this guard is for. Fire the same POST twice in parallel with a small script or with two curls joined by `&`. Inspect the cart afterwards. There must be one line. If there are two, the insert path is not using the `$ne` guard, and no amount of sequential testing will show it.

Add Salma's template with the personal license. The cart now holds two lines and two Studios. That count is the baseline for the next section, so record the exact line ids or the product ids in your evidence note.

## Prove the license switch replaces the line

Patch Salma's line to commercial. The response carries `status: "replaced"`, the line count is still two, and the line's `licenseType` and `licenseOptionKey` have both changed. The price shown for that line must now be the commercial price from the Product, not the personal one, and the other line must be untouched.

Patch the same line to commercial a second time. The route answers with the same cart and changes nothing. An idempotent switch matters because a buyer on a weak connection will retry, and a route that treated the retry as a conflict would leave the interface showing an error for a state that is already correct.

Patch a product that is not in the cart and confirm a 404 with `line_not_in_cart`. Then confirm the cart still holds two lines, because a patch that quietly creates the line it was asked to update is how a client with a stale tab writes into someone's cart through the wrong door.

## Prove the refusal and its exceptions

Create an active License for Amina on Nour's font under the personal license, then try to add that product with the personal license. The response is 409 with `already_owned`, the body names the product and the license type, and the cart is unchanged. This is the refusal that saves a buyer from paying twice for one file.

Two exceptions matter as much as the refusal. First, change the seeded License to `revoked` and repeat the add. It must succeed, because a buyer whose refund was processed needs a normal path back to the product. Second, keep the personal License active and add the same product with the commercial license. It must also succeed, because commercial grants named seats and paid client work that personal does not. Record both statuses and the cart line count after each call.

Send a body containing `quantity: 2`. The response is 400 with `unsupported_field` and the message names `quantity`. Send a body containing `studioId` set to a Studio that does not own the product, and confirm the same 400. If either request is accepted, the route is ignoring fields it should refuse, and the next module will price whatever the client believes it sent.

## Prove the cart belongs to the buyer

Sign in as Kareem and call the cart. It is empty even though Amina's cart holds two lines. Call `PATCH /api/cart/lines/:productId` with Amina's product id as Kareem. The 404 confirms that Kareem has no such line, and the body must not describe Amina's line, her Studio names or her prices.

Read Amina's cart as Kareem through any route that takes a buyer id, if you built one by accident. There should be none. The only buyer identity in this module is the session, and a route that accepts a buyer parameter is a finding to fix before the gate passes.

## Prove the multi-creator cart

With both lines in place, inspect the raw JSON. Each line must carry the `studioId` and `studioName` of the product's own creator, and the two lines must carry different Studios. The total number of lines is two and the total number of Studios represented is two.

Then unpublish Nour's product and try to add it again from a fresh cart. The 404 proves the route checked the current Product rather than trusting the id the client sent. Republish it, remove it from the cart with `DELETE`, and confirm the remaining line and the cart total are what you expect. Removal is the one operation in this module that changes nothing else, and it is worth seeing that it does not delete the cart document.

## What this gate does not prove

This gate says nothing about prices being frozen and nothing about payment. A cart is a statement of intent, and its prices are read from the Product each time the cart is rendered. Module 18 is where those prices are copied onto OrderLines and frozen, and where a change to Nour's price stops mattering to a Checkout that already exists. Do not describe a passing cart gate as a checkout feature.

It also does not prove the interface. Module 17 builds the grouped cart and the license switch in the browser, and it depends on a flag this module has not added yet: whether the buyer already owns a product, and under which type. Add that field to the cart response now, because the badge in the next module has to be driven by the same predicate that returned the 409 here.

## Gate checklist

- [ ] `GET /api/cart` for a buyer with no cart returns 200 with an empty `lines` array, not a 404.
- [ ] Adding the same product with the same license type twice returns `unchanged` and leaves one line.
- [ ] Two parallel add requests for the same product leave exactly one line in the cart.
- [ ] `PATCH` from personal to commercial returns `replaced`, keeps the line count, and changes both `licenseType` and `licenseOptionKey`.
- [ ] A repeated `PATCH` to the same type is idempotent and writes nothing.
- [ ] A `PATCH` for a product not in the cart returns 404 with `line_not_in_cart` and creates no line.
- [ ] Adding a product the buyer holds an active License for, under the same type, returns 409 with `already_owned`.
- [ ] The same add succeeds after that License is set to `revoked`.
- [ ] Adding the same product under the other license type succeeds, and the response lists only that other type in `ownedLicenseTypes`.
- [ ] A body containing `quantity` or `studioId` returns 400 with `unsupported_field`, and no cart document changes.
- [ ] Buyer B's cart is empty, and Buyer B's `PATCH` against Buyer A's product returns 404 with no details of Buyer A's line.
- [ ] The raw cart JSON contains no `quantity` field on any line, and each line carries the Studio id of the product's own creator.
- [ ] The cart response includes the license types the buyer already holds for each product, taken from the same query that returned the 409.

## Learning log

1. Explain why the duplicate-line guard is a filter on the write instead of a read before it. Name the exact request pattern that defeats the read-first version.
2. The `buyerId` unique index and the `$ne` product guard protect different things. State what each one prevents, and what would still go wrong if only one of them existed.
3. Your add route refuses a `quantity` field rather than ignoring it. Give the two outcomes a buyer would experience if the route ignored it, and say which one reaches production quietly.
4. A buyer's License for a product is revoked after a refund. Walk through the add route and say why the refusal no longer applies, and what would break for that buyer if the query dropped its `status` condition.
5. Module 18 will split this cart into one Order per Studio. Which field on the line makes that split possible, and where does its value come from?

Commit the cart model, the service, the three routes, the validation helper and the test suite. Save one evidence file with the status code and the cart line count for each check above. The next module reads the same cart response in a browser, groups the lines by Studio, and needs the owned-license flags this gate requires.
