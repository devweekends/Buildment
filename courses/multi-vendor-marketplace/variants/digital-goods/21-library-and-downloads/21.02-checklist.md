# Library and download gate

Prepare one public product with a preview and a private file, two buyer accounts, one creator account and one active license belonging to Buyer A. Record the product ID, grant ID and file-version ID in a private test note. Do not put the Cloudinary API secret or an issued URL in that note. The gate passes when the API and storage enforce the boundary even when a caller knows a valid ID. A hidden button in the browser is useful guidance but cannot be the only denial.

## Prove the public side

Fetch the catalogue anonymously and inspect the raw response. It should show the public title, creator, preview and license choices. It should not contain a private ProductFile record, storage ID, license key or signed URL. Load the preview without signing in. Then try the deliverable's unsigned storage URL. It must fail. If it succeeds, stop: the asset may have been uploaded with the wrong delivery type. A short-lived application link cannot protect an asset that is already public.

## Prove the buyer side

Sign in as Buyer A, open the library, and see the active grant with its accepted terms. Request a download. Inspect the response for a link with a short expiry and record only the issued time and expiry time. Fetch it before expiry in the test environment, then attempt it after expiry. The expired link must fail. Issue links until the course's limit is reached; the next request must return a clear 429 response. Restart the API and confirm the limit still applies. This shows that the counter or events live in persistent storage rather than one Node process.

Now sign in as Buyer B and submit Buyer A's grant ID to the download endpoint. The API must deny it without returning a storage ID or link. Repeat as the creator who uploaded the file. Product ownership is not the buyer's license. Revoke Buyer A's grant through the refund test path, then request another link as Buyer A. The API must deny it and the library should display a revoked state while retaining purchase history. A link issued just before revocation may live until its short expiry; record that as a known limit, not a test failure.

## Learning log

1. Draw the public catalogue serializer and private library serializer. Name three fields that must not appear in the public response and explain where each lives on the server.
2. Describe the full predicate for issuing a download link: identity, license state, refund block, file version and rate limit. Explain why a creator account does not satisfy the buyer predicate.
3. Explain the difference between recording a link issued and claiming a download finished. Which one can this architecture know reliably without proxying file bytes?
4. State what a refund can stop immediately, what may continue until URL expiry, and what no software can undo after the buyer saves a copy.

Commit the serializer tests, library screen, download route, rate-limit persistence test and private-file boundary document. Save HTTP status codes for the anonymous, cross-buyer, creator, revoked and rate-limited requests. A reviewer should be able to rerun the denials with a fresh grant ID. If the private file is accessible through an unsigned URL or a revoked grant can issue a new one, do not proceed to the refund module. That module relies on the download route to enforce the final access decision.

## Test a file update and a provider outage

Upload a second version of the same product file. Query Buyer A's license and verify which version it names. Request a new link and confirm it delivers that version, not whatever file happens to be latest on the product. If the product's policy grants later versions, show the explicit entitlement rule and a test proving it; the core path keeps the purchased version fixed. This matters because license terms and file contents can change after a sale, and a buyer's receipt should explain what they bought.

Temporarily make the storage provider call fail in a test. The API should return a retriable error with a request ID, retain the active license, and avoid incrementing a successful issued-link count for a link it never received. Restore the provider and retry. The buyer should receive a link without another payment or a manual database edit. Inspect logs for the request ID, license ID and failure stage, but not the signed URL or API secret. This exercise helps distinguish an authorization denial from a storage outage when a real buyer asks for help.

## Review the claims you will make in the demo

Show the library as Buyer A, then ask another learner to name the checks that happen after a Download click. Point to the API query and persisted limit, not just the React component. Show the same product's public preview in an anonymous window and its unsigned private URL failing. If you say a revoked link cannot ever work, correct your wording: the app blocks issuing new links, while an already issued URL may remain valid briefly and a saved copy remains with the buyer. The strength of the design is a narrow, explicit window and clear rights enforcement for future access, not a promise that cannot be kept.
