# What may be cached, and what never is

The catalogue is the most read part of Midad and the least written. A hundred visitors load the browse page for every product a creator edits, and each of those loads runs the same filter, the same count and the same two queries. Module 14 already fixed the N+1 problem and added the indexes. A cache is the next step for the same reason a printed price list is worth pinning up: the answer has not changed since the last visitor asked.

The library is the other kind of page. Amina loads it after a purchase, and it must be exactly right every time, because it answers "what may I download". It is read far less often, and it is the page where a stale answer is a security problem rather than a slow page.

The gap between those two paragraphs is the whole of this module. The technique is small: a key, a value, a time to live and an invalidation call. The judgement is what you are allowed to put in it.

## One question decides it

Ask whether the response depends on who is asking. If two visitors with different accounts would receive byte-identical bodies, the response is public and a shared cache may hold it. If the answer changes when the session changes, the response is private and a shared cache must never see it.

That question is not the same as "is this endpoint expensive". The library endpoint is cheap and must never be cached. The search endpoint is expensive and may be cached for anonymous visitors, not for a buyer, because the result depends on which products are published rather than on who searched. Cost decides whether caching is worth doing. Identity decides whether it is allowed.

There is a third category that people miss: responses that depend on nobody but carry a secret for one person. A download response contains a URL signed for one buyer, valid for five minutes. Nobody else's account changes it, so the naive identity test says it is safe. It is not. The secret is the reason the response exists, and a cached copy hands that secret to whoever asks next.

## What may be cached

Four public shapes carry almost all the read traffic.

- The catalogue list for one combination of filters, page and page size. The key has to include all three, or page two serves page one.
- A product page by slug, with title, description, tags, formats, preview URLs and license option summaries.
- A Studio's public profile and its published product list.
- The category and format lists used to render the filter controls.

None of these contains a buyer id, a License, a key, a seat list, a private file id or a signed URL. That last clause is the test you can run as a script: fetch the response as an anonymous visitor and search the raw JSON for the field names of private records. If any appears, the response is not cacheable yet, whatever its read rate.

## What must never be cached

The list is short and each entry has a reason.

- License records, including keys, seat lists, download limits and status. These are the entitlement itself.
- The library response, which is a view of those licenses grouped for one buyer.
- Any download response, because it contains a short-lived signed URL that works for anyone holding it.
- DownloadGrant records and the counters that limit how many links a buyer may request.
- The cart, which is per buyer and changes on every tap.
- The `ownedLicenseTypes` flags on cart lines, because they are the per-buyer half of a public-looking response.
- Refund and revocation state, which is the thing an attacker would most like to be stale.

A shared cache holding any of those is not a performance bug. It is a data leak with a time to live.

## A cache key that includes the buyer is still wrong

The tempting fix for the list above is to add the buyer id to the key: `library:v1:<buyerId>`. Each buyer then gets their own entry, and the leak seems closed.

It closes the leak and opens a worse problem. The entry now has a lifetime independent of the record it copies. Amina refunds Nour's font at noon, the refund webhook sets the License to `revoked`, and the cached library keeps serving an active state until the key expires. Every consumer of that cache now needs to know every write that could touch it: refunds, seat assignment, download counts, file version changes, order state transitions. Missing one is a buyer downloading a file they no longer own.

A per-buyer cache of mutable entitlement is the same architecture with more places to be wrong. Read entitlement from the database on every request, keep the query indexed, and spend the cache on the catalogue instead.

## Say it in the response, not only in the code

Set `Cache-Control: no-store` on the library, download and license responses, and keep the buyer's session cookie out of anything that could be shared. The header tells browsers and proxies not to keep the response, and it is the difference between a mistake that lives in one tab and a mistake that lives in a proxy for an hour.

Be honest about what the header cannot do. A misconfigured intermediate proxy may ignore it, and a response that is cached before the header is checked has already leaked. The controls that actually hold are the ones inside the response: a URL signed for one buyer, expiring in minutes, and an authorization check on every issuance. Headers are a second layer. The signature is the layer that survives a mistake in the first.

The same reasoning applies to the preview images. They are public and cacheable, so they may sit in a CDN for a day. The deliverable is `authenticated` in the storage provider and has no public URL at all. Module 13 built that boundary; this module must not undo it by caching a response that contains a signed link.

## Freshness, and why a time to live is not enough

Sixty seconds is a reasonable starting point for the catalogue. It bounds how long a stale copy can live if invalidation fails, and it costs a creator at most a minute of seeing an old price.

A TTL alone is not acceptable, because the writer is the same platform. When Nour edits a typo in her product title, she expects the browse page to show the fix when she reloads it. Waiting up to a minute to see your own edit reads as a broken save button, and the support conversation that follows is about trust rather than performance. So the write path deletes the affected key, and the TTL becomes the backstop for a failed delete rather than the mechanism.

## The choice, and when it changes

The alternative to a cache is no cache: keep the indexes from Module 14, accept the query cost, and spend the time on correctness instead. That is a legitimate answer for a marketplace with a few hundred products, and it is the answer most teams should start with. The browse page at that size answers in tens of milliseconds from an index, and a cache adds a second source of truth, a key scheme and an invalidation path that all have to be right.

A process memory `Map` is the middle option and the one to avoid here. It is free to write and it disappears on deploy, so the first request after every deploy is slow. Worse, it is per instance: with two API processes behind a load balancer, an invalidation reaches one of them and the other keeps serving the old copy for the rest of its TTL.

Midad uses Redis because the stack already has it for the queue in Module 23, it is shared by every instance, and it expires keys without a job. The cost is another service to run, a connection that can fail, and the fallback path this module has to build and test. If the catalogue never grew past a few hundred products and the queue used something else, the honest recommendation would be no cache at all.
