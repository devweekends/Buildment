# Cache and search gate

This gate is passed with three windows open: the API log, a `redis-cli` session and a browser. Every claim in this module leaves a trace in one of them, and the trace is the evidence. A statement that the cache works because the second page load felt fast is not evidence, and it will not survive a reviewer who asks which key was read.

Prepare one creator with two published products and one unpublished draft, one buyer with an active License, and the Redis instance the API uses. Note the port and database index before you start, because `redis-cli` defaults to database 0 and a test that cleans the wrong database is worse than no test.

## Prove the catalogue is cached

Request a catalogue URL twice and watch the log. The first request logs a miss and a database query; the second logs a hit and no query. The response bodies must be byte identical, which is the property that makes the entry safe to share.

```bash
curl -s "http://localhost:4000/api/products?category=fonts&page=1" | sha256sum
curl -s "http://localhost:4000/api/products?category=fonts&page=1" | sha256sum
redis-cli --scan --pattern 'midad:v1:catalogue:*'
```

Then change one input and confirm a second key appears. Ask for page two, then for a different category, then for a different page size. Four distinct keys is the correct outcome. If page two returns page one, the key is missing the page. If a different page size returns the cached twenty, the key is missing the size.

Repeat for a product page by slug. Fetch it, confirm the miss and the hit, and confirm the key contains the slug.

## Prove invalidation

Fetch Nour's product page and the catalogue list that contains it, so both are warm. Change the product title in the dashboard, save it, and immediately fetch the product page again. The new title must appear on the first request after the save, not after a delay. Then fetch the catalogue URL again and confirm it also shows the new title.

Watch the version key before and after the save. It must increase by one, and the list key must be built with the new value. Confirm the old list key still exists in Redis and is no longer read; that is the intended behaviour, and it is worth showing a reviewer that the expiry, not a delete, retires it.

Rename a Studio and repeat. The creator's new name must appear on the product page and in a search result, because the rename writes the denormalised field onto the products before it bumps the version. If the old name survives, the rename path updated the Studio and forgot the products, and the search index now holds a name that no longer exists anywhere.

## Prove the private routes are not cached

Flush the cache, then call the library, the cart, a license read and one download request as the buyer. After all four, list the keyspace. It must be empty. This is the single most important check in the module, and it is a check no manual inspection of the pages can replace.

```bash
redis-cli flushdb
curl -s -b amina.cookies http://localhost:4000/api/me/library > /dev/null
curl -s -b amina.cookies http://localhost:4000/api/cart > /dev/null
redis-cli --scan --pattern '*'
```

Inspect the response headers for the library and the download route. Both must carry `Cache-Control: no-store`. Inspect the bodies and confirm that the library contains no `url` field and the download response contains no license key. A library response that carries a link has already failed before caching enters the picture, and the cache would only decide who receives it.

Then sign in as Kareem and load his library while Amina's is warm. Kareem's page must show his own items. If it shows Amina's, a key was built without the buyer or a response was cached at a layer that ignores the header, and no amount of header work will fix the first case.

## Prove Redis can be absent

Stop Redis with `redis-cli shutdown nosave` or by stopping the container. Load the catalogue, a product page and a search result. All three must answer 200 with real data, and the API log must carry one warning per request that the cache was skipped. The response must not be a 500.

Watch the timing for the first few requests. The breaker opens after the first failure and skips Redis for ten seconds, so the second request should be no slower than the database query itself. If every request waits a full connection timeout, the breaker is missing and a cache outage has become a site outage.

Restart Redis. Within ten seconds the next request must reach the cache again and log a miss, then a hit. A breaker that never closes is a cache you paid for and do not use.

Then stop Redis while a buyer is on the library page. The library must still load, because it never used the cache. If it fails, something in that route is reading Redis for a value it should read from the database.

## Prove search uses the index, and learn its edges

Search for a word from a title, a tag, and a creator's name. Each must return the expected published products, and the unpublished draft must appear in none of the three. Search for two letters and confirm an empty result rather than an error, because the route refuses to run a one character query.

Run the explain and read the winning plan. It must name the `product_search` index and use an `IXSCAN`. Compare `totalKeysExamined` with `nReturned` and record both numbers in your evidence file.

```js
// a one-off script, not a test
const plan = await Product.find({ status: 'published', $text: { $search: 'salma' } })
  .explain('executionStats');
console.log(plan.executionStats.totalKeysExamined, plan.executionStats.nReturned);
```

Then try the limits on purpose, because you will be asked about them. Search for a prefix such as `grot` and confirm it does not find "Grotesk". Search for a misspelling and confirm it finds nothing. These are not failures to fix in this module; they are the documented behaviour of the index, and knowing them is what stops you promising a buyer a search box that does fuzzy matching.

## What this gate does not prove

Nothing here proves the cache survives a deploy with several API instances. That is a property of using Redis rather than process memory, and the way to show it is to run two API processes behind the client and confirm an edit is visible through both. If you have time, do it; it takes ten minutes and it is the difference between a cache and a lucky one.

The gate also does not prove the download path is safe. It proves only that the response is not stored. The signature, the expiry and the holder check belong to Module 21, and a passing cache gate says nothing about them.

## Gate checklist

- [ ] The same catalogue URL twice gives one miss and one hit in the log, with identical response bodies.
- [ ] Page, page size, category and format each get a distinct cache key.
- [ ] A product page is cached under a key that contains its slug.
- [ ] A saved product title appears on the next product page request and on the next catalogue request.
- [ ] The catalogue version key increases on every product save, and the new list key carries the new version.
- [ ] A Studio rename appears in the product page and in search, not only on the Studio page.
- [ ] After calling the library, the cart, a license read and a download, the Redis keyspace is empty.
- [ ] Library and download responses carry `Cache-Control: no-store` and contain no link or key field.
- [ ] A second buyer sees their own library while the first buyer's library is warm.
- [ ] With Redis stopped, the catalogue, a product page and a search all return 200 from the database.
- [ ] The breaker skips Redis after the first failure and reconnects within ten seconds of it returning.
- [ ] Search finds a title word, a tag and a creator name, and never returns the unpublished draft.
- [ ] The explain plan names `product_search` with an `IXSCAN`, and the key counts are recorded.
- [ ] A prefix and a misspelling are shown to return nothing, and that limit is written down rather than hidden.

## Learning log

1. State the question that decides whether a response may enter a shared cache, and apply it to the product page, the library and a download response in three sentences.
2. Explain why the catalogue list is invalidated by a version bump while a product page is invalidated by a delete. Which one could you not name, and what would it cost to name it?
3. Your cache key for the catalogue includes the filters, the page and the page size. Add the buyer id to the key and describe what stops working, and when.
4. Redis is down for ten minutes. Trace what a visitor sees, what a creator sees when they save a product, and what the operator learns from the log.
5. Search returns nothing for a buyer who typed the first half of a product name. Say what the index can and cannot do, and what you would tell that buyer and why.

Commit the cache wrapper with its breaker, the key builders, the invalidation calls, the search route and index, and the four tests. Save the log lines, the keyspace listing, the explain output and the key counts. A reviewer should be able to rerun the whole gate against a fresh Redis without editing the application.
