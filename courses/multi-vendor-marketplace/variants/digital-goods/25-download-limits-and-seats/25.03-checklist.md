# Limits and seats gate

This gate is judged on numbers from parallel requests, not on a page that looks correct. Everything before Module 25 works when requests arrive one at a time, and the defects in this module only appear when they do not. So the evidence has to show a starting state, a burst, and an exact count of outcomes, repeated often enough to be believable.

Prepare three fixtures and write their starting values down. Amina holds a personal font license with `downloadsRemaining: 3`. She also holds a commercial template license with `seatLimit: 3` and an empty `seats` array. One paid Checkout exists with two OrderLines, one per creator, and its Licenses have been deleted so that duplicated deliveries have something to create. Keep the API, the worker and MongoDB running, and log in the buyer and one creator through the real routes so every cookie is a real token.

## Downloads under a burst

Fire twenty download requests for the personal license at the same moment, each with its own `requestId`, and count the statuses. Exactly three must return 200 with a link, seventeen must return 409 with the limit reason, and the license must end at `downloadsRemaining: 0`. Record the count of `DownloadGrant` rows: three, each in `issued` state with a different request id.

Then repeat the burst on a fresh license with three remaining, and this time stop the storage provider from answering by pointing the configuration at an unreachable host. Nothing should be issued, and after the failures are handled the license must be back at three. That run proves the compensation path, and the count is the part that matters: a repair that gives back more than it took leaves the buyer with a bigger allowance than the terms allow, and it is invisible unless the test starts and ends the counter deliberately.

Finish with the retry case. Take one `requestId` that already returned a link and send it again with the same body. The response should show the same grant state and the counter must not move. Then send it with a new `requestId` and confirm the counter does move, because a new attempt is a new download. Those two requests look identical in a browser and mean different things to the license, which is exactly why the id comes from the client rather than from a timestamp on the server.

## Seats under a burst

With the commercial license at `seatLimit: 3` and an empty array, fire five assignments at the same moment with five different addresses. Exactly three must succeed, two must return 409 with `seat_limit_reached`, and the array must hold three elements. Then fire the same address four times at once against a fresh license and confirm one seat exists and three requests answer with `seat_already_assigned`.

Now the case people forget. Assign two addresses to a license whose limit is one, in parallel, and record which one won. The winner is not interesting; the count is. One seat, one success, one refusal, and the refusal must be a limit refusal rather than a duplicate refusal. If both refusals say the same thing, the classification read is not distinguishing the two causes, and the buyer cannot tell whether to pick another colleague or buy another seat.

Release one seat and reassign it to a sixth address. The release must be scoped to the buyer, the reassignment must succeed because the array is short again, and the array must show the new address with its own `assignedAt`. Then try to release a seat as the creator who owns the product and confirm the request is refused. Product ownership is not seat management, and the boundary has to hold in the same filter as everything else.

## Duplicate webhooks in parallel

Delete the Licenses for the paid Checkout, then deliver the same `payment_intent.succeeded` event twice at the same moment, ideally to two API processes. When the deliveries finish, there must be one License per OrderLine, both Orders must be `fulfilled`, and the log must show one handler inserting and the other reading the winner after a duplicate key error. A log that shows both handlers inserting means the unique index is missing from the database the test used, which is a more common cause than a logic error.

Run the same delivery a second time, now sequentially, and confirm the counts do not change. That is the Module 20 replay test repeated under the new conditions, and it costs one command. Keeping it in this gate is deliberate: the concurrent case and the sequential case fail for different reasons, and a system that handles one and not the other is not finished.

## Two processes, one database

The bursts above are enough to expose the gap, because the gap is an `await` and a single Node process runs other requests inside it. They are not enough to prove that Midad works when it runs the way it will run after Module 24. Start a second API process on another port against the same MongoDB and repeat the download burst against both ports, split evenly across twenty requests.

The expected output is the same as the single process run: three issued, seventeen refused, counter at zero. If the two process run reports more than three, something holds state that should live in the database, and the likely candidates are an in-memory counter, a cached license document, or a limiter keyed by process. Record both outputs in the evidence file. The comparison is the point of the exercise, and a difference between them is a finding you should be able to explain before the refund module builds on top.

## What this gate does not prove

It does not prove that the file cannot be copied after it arrives. A buyer who downloads a font can send the file to anyone, and Module 21 said so plainly. What this gate proves is narrower: the allowance the buyer paid for is enforced exactly, the seat list respects its own limit, and two simultaneous deliveries grant access once. It also does not prove behaviour at a scale beyond twenty requests. Twenty is enough to break a read then write handler every time, which is all the module claims.

## Gate checklist

- [ ] The download burst prints an exact table: 20 requests fired, 3 succeeded with a link, 17 refused with the limit reason, no other status.
- [ ] `downloadsRemaining` ends at 0 for that license, and the three `DownloadGrant` rows are `issued` with distinct request ids.
- [ ] Repeating the same `requestId` returns the same grant state without moving the counter, and a new `requestId` spends a download.
- [ ] A storage failure during the burst leaves the counter at its starting value, and a retried failure does not give the download back twice.
- [ ] Five parallel seat assignments against a limit of three leave three seats, return two limit refusals, and end with an array of length three.
- [ ] Four parallel assignments of one address leave one seat and return three duplicate refusals.
- [ ] Two parallel assignments against a limit of one leave one winner and return a refusal classified as a limit, not as a duplicate.
- [ ] Releasing a seat and reassigning it works, and a creator who owns the product cannot assign or release a seat on a buyer's license.
- [ ] Two simultaneous deliveries of one payment event create exactly one License per paid OrderLine, and both Orders are `fulfilled`.
- [ ] The duplicate key path appears in the log as a caught error followed by a read of the winning row, not as a failed request.
- [ ] The same event delivered a second time, sequentially, changes no count and no id.
- [ ] The burst repeated across two API processes against one database reports the same numbers as the single process run.
- [ ] `docs/evidence/m25-parallel.txt` holds the starting state, the bursts, the exact counts and both process runs, with no secrets or session cookies in it.
- [ ] The suite passes twice in a row without reseeding the whole database, and each scenario prints the documents it resets.

## Learning log

1. Show the filter you use for the download decrement. Name each clause and the failure it prevents, then explain what the route can and cannot learn from a null result.
2. Your storage provider fails after the decrement succeeds. Walk through the repair, and explain why the conditional close on the grant is what prevents a second refund of the download.
3. Why can seat assignment be one atomic update while a seat collection would need a transaction? State the fact that makes the difference.
4. Two deliveries of the same event create one License. Which mechanism decided the winner, what did the losing handler do next, and what would the counts look like if the handler simply threw on the duplicate key?
5. Your two process run and your single process run reported the same numbers. Explain why the single process run is still a valid test of a race, and name the state that would make the two runs disagree.

Commit the two limit functions, the seat routes, the duplicate key handling in the fulfilment path, the three concurrency tests and the parallel script with its output file. Write three sentences in `docs/evidence/m25-parallel.txt` at the top: what was fired, what was allowed, and what the counter read at the end. A mentor should be able to rerun the file and compare it with your committed output, which is the difference between evidence and a claim.
