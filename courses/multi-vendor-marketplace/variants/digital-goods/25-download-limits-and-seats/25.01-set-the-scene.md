# The stock moved to the licence

A physical marketplace runs out of things. A digital one does not, which is why people assume Midad has nothing to protect. That assumption lasts until the first support message. Nour sells a personal font license with three downloads, and Amina opens four tabs. Salma sells a commercial template license with five seats, and a design team of eight pastes the same key into a shared document. Nothing ran out of files; what ran out was the allowance, and an allowance that leaks under load is a license that means nothing.

So the scarce thing in Midad is the right, not the work. A License document carries two limits. `downloadsRemaining` counts the file requests the holder may still make, and it has been the counter behind the download endpoint since Module 21. A commercial Option carries a `seatLimit`, and the seats a buyer assigns live in the same License as an embedded array. Both are numbers that a customer can exhaust, and both are written by a route that several people can call at the same instant.

The heading above keeps the roadmap's wording. Everywhere else, in this course and in the code, the word is spelled license, so a search for it finds every use. What matters is the idea in the heading: the limit that used to sit on a catalogue item now sits on one buyer's entitlement, which means the limit is per buyer, per license option, and per purchase. Amina's three downloads are not shared with Kareem's three, and Nour cannot change them by editing her product page.

## Two counters in two shapes

The download limit is a number that only ever goes down. It starts at the value frozen on the paid OrderLine, and every issued download link spends one. There is no path that puts one back except the narrow compensation case for a storage failure, which Module 21 introduced and which is tied to one recorded attempt. That shape, a number that decreases under a predicate, is exactly the shape the conditional decrement was invented for.

Module 21 left the precise policy open and mentioned a rolling daily allowance as one option. Midad ships a counter instead, because a counter is the number the buyer read on the license option and the number the OrderLine snapshot froze. A rolling window would need a separate table of issued links per day and a rule about what happens at midnight, and it would make the library show a number the terms never promised.

The seat limit is a list that only ever grows, up to a bound. Amina buys the commercial template license for five seats and assigns four colleagues by email. The fifth assignment has to succeed; the sixth has to fail, and a repeated address has to fail without changing anything. The count is not a stored field. The count is the length of the array, and the bound lives beside it as `seatLimit`.

Keeping those two shapes inside one License document is the decision this module defends. A counter and a small list both belong to one buyer's entitlement, both are touched by one route, and both are small. Splitting them into their own collections would buy nothing at this size and would cost the thing you are about to rely on, which is a single document update that either happens completely or not at all.

## The handler that passes every sequential test

Here is the handler almost everyone writes first. It reads the License, checks the counter in JavaScript, decides, saves, and then does the work.

```js
// server/src/modules/licenses/download.route.js (the naive version)
const license = await License.findOne({ _id: licenseId, buyerId });
if (!license) return res.status(404).json({ error: 'not_found' });
if (license.status !== 'active') return res.status(403).json({ error: 'revoked' });
if (license.downloadsRemaining < 1) return res.status(409).json({ error: 'limit_reached' });

license.downloadsRemaining -= 1;
await license.save();
const url = await storage.issueLink(license.productFileId);
return res.json({ url, expiresAt: fiveMinutesFromNow() });
```

Run it once and it behaves perfectly. Run ten requests one after another in a test and every count is right: three links issued, then a limit error, and `downloadsRemaining` ends at zero. Point it at a hundred buyers and it keeps behaving, because each buyer owns a different document and the requests rarely touch the same one at the same time.

Then put twenty parallel requests on Amina's license with three downloads left, which is a single line in a load script and a very ordinary thing for one buyer with a flaky connection to do. More than three requests read a counter above zero. Every one of them passed the check, because at the moment each check ran the counter had not been written yet. Every one of them then saved its own decrement, and the last save wins, so the final counter reads 2 no matter how many links were issued. Three links were paid for; more than three were handed out.

Follow the third and fourth steps and you have the entire bug. The two writes do not conflict, because both write the same value. The database cannot tell that one of them was wrong, because each write on its own was legal. The error is in the gap between the read and the write, and the database never saw the gap.

## Why the database does not save you

MongoDB gives you atomic writes on a single document. A single update either applies completely or not at all, and no other writer can see a half applied update. That guarantee is real and it is useful, and it does not cover this handler. The handler performs two operations, a read and a later write, and the guarantee applies to each of them separately, not to the pair.

The same reasoning explains why a transaction does not automatically fix it either. A transaction that reads the counter, computes in application code and writes does hold a snapshot, but a concurrent writer that commits first invalidates that snapshot, and the transaction aborts with a write conflict. You then have to retry it, and you have to catch the conflict rather than letting it become a 500. That path works and it is heavier than the shape of the problem needs.

The most common wrong instinct is to reach for a lock. A JavaScript mutex or an in-process map of license ids that are currently being handled looks like a fix and is worse than the bug, because Midad runs at least two processes, the API and the worker, and a deploy runs two copies of the API. An in-process lock protects a single process from itself. It cannot protect the document from the other process, and it fails silently, which is the worst way for a safety measure to fail.

## Four ways to close the gap

There are four credible answers, and the second one is the one Midad uses. The first is a database transaction with a retry loop. It is correct when the decision needs more than one document, for example when a download must decrement a counter and insert a grant row at the same time, and it costs a replica set, a retry policy and a write conflict path you have to test. Keep it in your notes as the answer for a two document rule.

The second is a conditional update whose filter carries the decision. The predicate that the handler checked in JavaScript becomes part of the query, and the database applies the predicate and the change as one operation. If the predicate no longer holds when the update runs, no document matches, and the route learns that it lost the race instead of guessing. One round trip, no lock, no retry loop, and the decision is expressed where it is enforced.

The third is an unconditional `$inc` followed by a check of the returned value. It never loses an update, because `$inc` is atomic, and it can go below zero, which means you must compensate when you discover the overshoot. That compensation is another write that another request can interleave with, and the counter ends up as a slightly wrong number that needs repair. It is a reasonable choice for a metric. It is a poor choice for an allowance a customer paid for.

The fourth is an application level queue that serialises all work on one license. It is correct and it adds a dependency, a delay and a new failure mode to a route that must answer in a few hundred milliseconds. Choose it only when the work behind the decision is slow and unavoidable, which issuing a link is not.

| Approach | Correct under parallel requests | Cost | When it is the right answer |
|---|---|---|---|
| Read, check in code, save | No | None until it fails | Never for a limit |
| Transaction with retry | Yes | Replica set, conflict handling | When two documents must change together |
| `$inc` then check the result | Yes, but it can overshoot | Compensation write and repair | Counters where a small overshoot is acceptable |
| Conditional update with the limit in the filter | Yes | One extra thought about the filter | A paid allowance, a seat, a claim |
| Serialise through a queue | Yes | A dependency and a delay | When the decision is genuinely slow |

Read the table as a set of trade-offs rather than as a ranking. The conditional update wins here because the decision fits in a filter. It stops winning the moment a rule needs two documents, because a filter cannot span a collection, and that is the honest boundary of this technique.

## Embedding is what makes seats atomic

Seat assignment looks harder than the download counter, because an array has a length and a maximum and a duplicate rule. Embedding makes it the same problem. The seats live inside the License document, so one update can check the array length against `seatLimit`, check that the address is not already present, and push the new seat. The database applies all three as one operation on one document.

If seats lived in a separate collection, the same rule would need three facts at once: how many seats exist for this license, what the limit is, and whether this address is already assigned. That is a count over one collection, a read of another, and an insert, and no single write can enforce it. You would need a transaction, or a unique index on the pair of license and email plus a counter you keep in step by hand. Embedding removes the problem rather than solving it, and that is the argument worth remembering.

There is a limit to the trick. An embedded array is right because a commercial license has a handful of seats, not thousands. A product that assigned seats to an entire company would outgrow the array, and the design would move to a collection with a unique index on license and address plus a transaction for the count. Say where that line is before someone argues about it during the viva.

## Two deliveries of the same event, at the same moment

The third race in this module is not in the buyer's browser. Two deliveries of `payment_intent.succeeded` can arrive at the same second, and with more than one API process each can be handled at the same time. Both handlers confirm the Checkout and both call `fulfilCheckout`, and each one reads the Licenses for the paid OrderLines and finds none.

A `findOne` before the insert cannot stop this, for the same reason the read in the download handler cannot. Both handlers read an empty state, both decide to create, and both insert. What stops it is the unique index on `orderLineId`: the second insert fails with a duplicate key error, the handler catches that specific error, reads the row the other handler created, and continues. That is the same wrapper you wrote in Module 20, now exercised by a real concurrent arrival rather than by a replay you triggered yourself.

The license key generator has the same shape. Keys come from `crypto.randomBytes`, and a unique index on the key means a collision surfaces as a duplicate key error rather than as two licenses sharing one reference. The generator retries on that error. The probability is tiny and the handling is three lines, and the reason to write it is that the alternative is a bug you would never see twice.

## What counts as evidence

A sequential test cannot see any of these bugs. Three requests made one after another will always agree with the counter, because each one finishes before the next begins. The only test that matters fires the requests at the same moment and then counts outcomes.

```js
// server/test/concurrency/downloads.test.js (partial)
const responses = await Promise.all(
  Array.from({ length: 20 }, () => request(app).post(`/api/me/licenses/${license._id}/downloads`).set('Cookie', aminaSession))
);
const issued = responses.filter((r) => r.status === 200).length;
const limited = responses.filter((r) => r.status === 409).length;
assert.equal(issued, 3); // the counter started at 3
assert.equal(limited, 17);
assert.equal((await License.findById(license._id)).downloadsRemaining, 0);
```

Run that test against the naive handler and watch it report something like 11 issued and 9 limited, with a counter of 0. That number is the shape of the bug, and it is worth keeping in the learning log: it shows why a limit that is checked in application code is a suggestion. Run it against the conditional update and the counts become exact, every time.
