# Public-preview and private-file gate

Start with one draft product owned by Creator A. Give it a license option, one generated placeholder preview and a generated ZIP or PDF deliverable. Use generated assets so the seed does not depend on third-party license rights. Keep Creator B and an anonymous browser session ready. The gate passes only when the public preview loads, the private file remains inaccessible without a signed time-limited route, and the raw catalogue response contains no private storage metadata.

## Check the public path

As an anonymous visitor, fetch the product page and its API JSON. The preview image should load. The JSON may include preview URL, dimensions, alt text and order. It must not include a ProductFile row, authenticated asset ID, checksum, license key or signed download URL. Inspect the network response directly; a React component can hide a field while still sending it to every browser. Remove accidental fields from a whitelist serializer on the server.

Upload a second preview, reorder the gallery as Creator A, then reload anonymously. The order should remain stable after a server restart. Creator B must get a denial when trying to reorder or delete Creator A's preview. A buyer should not be able to reach the creator upload routes. Record raw status codes and response bodies for each denial, with no asset secret in the test log.

## Check the private path

Upload the generated deliverable as an authenticated raw asset. Inspect the private ProductFile record in the database: it should name the owner product, version, resource type, size, server-computed checksum and storage ID. The public product response must remain free of those fields. Try the unsigned storage delivery URL in a fresh anonymous session. It must fail. If it succeeds, stop and inspect the asset's delivery type; an application login gate cannot protect a file already public at storage.

Try to publish a product with a preview but no private file, then with a file but no valid license option. Both actions should fail with a specific field-level error and keep the product in draft. Publish a product with both and confirm the catalogue shows its license choices. Remove or mark its active private version unavailable in a test fixture; the purchase path must stop rather than sell a product that cannot be fulfilled. A previous license that points to an older file version must not silently switch to the new upload.

## Check interruption and recovery

Simulate a storage failure while uploading the deliverable. The product remains a draft and the creator sees a retriable error. Simulate an interruption after storage succeeds but before the database row is committed. The route should log an orphaned asset for cleanup or remove it as compensation. Neither case should show a false published state. Restart the API and inspect the same product: public previews still load, private metadata remains server-side, and the publish rule still sees the right active file version.

## Learning log

1. Draw separate public-preview and private-deliverable paths. Explain why one upload setting cannot safely serve both.
2. Name every ProductFile field that remains server-only and the fields that the anonymous catalogue may return.
3. Explain why an ordinary signed URL is not automatically an expiring access grant and where Module 21 applies an expiry.
4. Describe what happens when storage succeeds but the database write fails. Which state does the product show, and how is the orphaned asset found?

Commit the two upload services, ownership tests, whitelist serializers, publish-rule test and failure-path test. Save the anonymous response and unsigned-URL denial in `docs/PRIVATE-FILES.md` without a secret key. A mentor should be able to replace the generated file and see a new version while an old grant keeps its recorded version. If the private file can be fetched anonymously or Creator B can alter Creator A's product, the Week 2 checkpoint fails and the payment path must wait.

## Review a raw failure trace

Pick one upload that failed in your test and record the sequence: ownership check, file validation, storage call, ProductFile write and product publish check. Mark the step that failed. If ownership failed, no storage call should have occurred. If file validation failed, there should be no new asset. If storage succeeded but the database write failed, the asset needs cleanup and the product remains draft. The trace helps a reviewer see that the route does not accidentally publish on a partial success.

Repeat the raw catalogue request after the failed upload and after a successful retry. The public response should never gain a private storage ID. A successful retry may create a new ProductFile version; it should not overwrite the earlier row in place if an active grant points at it. Compare the two versions and the grant's recorded version in a test assertion. This catches a subtle bug in which a creator's “replace file” action changes what an earlier buyer receives without any change to the order or license terms.

Finally, ask another person to explain which file is public by looking at the product page and which file is private by looking at the API test. They should be able to identify the exact server route that later creates a short-lived download URL and the active-license check that route will use. If their answer is “the link is hidden until payment,” revisit the storage test. The boundary is enforced by server and storage behavior, not by the visibility of a button.
