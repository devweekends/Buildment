# 7.18 Checklist and learning log

> **[Gate]** · Chapter 07: Login and registration

This is the **gate** for Chapter 7. Tick every box honestly and answer the learning log below before opening Chapter 8.

<BigWordAlert term="Token storage" plainEnglish="Where the browser keeps JWTs: memory, sessionStorage or an httpOnly cookie, each with different exposure to scripts and to cross site requests." whyItMatters="Midad's client must hold an access token long enough to call the API and a refresh token where page scripts cannot read it." />

Chapter 6 proved that the server can answer who a caller is. This chapter proved that a person can sign in through a browser and stay signed in while they move between screens. The items below check the second claim, and the interesting ones are not about the happy path: they are about what happens when a token expires mid session, when a page reloads, and when someone opens a route they are not allowed to see.

The risk in this gate is a demo that looks right. A login form that redirects to a dashboard can be built with a hardcoded token, a menu item that hides itself is not a route guard, and a page that works until you press refresh is not a session. Each group below therefore names the evidence rather than the appearance, and a reviewer reads the evidence in the order written, because that is the order a real session moves through.

Two vocabulary notes. The stored role values remain `vendor` and `customer`, so the redirect rules compare those strings even when the screen says Studio or library. And the words protected route mean two different jobs in this chapter: the router guard in the client decides what to render, while `requireAuth` on the server decides what to answer. Neither replaces the other, which is the last explanatory item in this gate.

## Chapter 7: Login and registration checklist (gate)

Do **not** open Chapter 8 until every box is ticked and learning log answers are written below.

### Pages and routing

The first group proves that the three screens exist as routes rather than as files nobody can reach. Register, verify and login are separate routes because they are separate moments with separate failures: a bad email at register, a wrong code at verify, a wrong password at login. Merging them into one page with a step counter is a design choice you can make later, but the gate asks for the three addresses the next chapters will link to.

The full flow item exists because each route can work alone and the sequence can still break. A register page that never navigates to verify leaves an account pending forever, and a verify page that returns to login without a message looks like a failure. Walk it once end to end before ticking.

The role redirect item is about where a person lands, not about what they may do. A vendor lands on the Studio path and a customer lands on the catalogue or library path, because the two accounts exist for different jobs. The last item is paired with it: an error must be visible for a wrong password and for an unverified account, and the two messages should differ, because one says try again and the other says check your email.

- [ ] `/register`, `/login`, `/verify-otp` routes work
- [ ] Register → verify → login flow completes in browser
- [ ] Role-based redirect after login (vendor vs customer)
- [ ] Login shows error for wrong password and unverified user

A reviewer reads this group by opening each route in a fresh tab, then by signing in with one account of each role. The redirect is checked with the browser history, not with the screen, because a redirect that pushed no entry leaves the back button behaving strangely on the next screen.

### Auth state

These three items are the heart of the chapter, and the first is deliberately specific: the access token lives in memory, inside a context or a module level variable, and never in localStorage or sessionStorage. Memory means a script injected into the page cannot read it from storage, and it also means the token disappears on reload, which is why the second item exists.

Boot refresh is the recovery path. When the app starts, it calls the refresh endpoint once with credentials, receives a new access token and restores the session before rendering protected screens. A page that shows the login form for a moment and then the dashboard is a boot refresh running after the first render, and the fix is a loading state rather than a faster request.

Logout clears the in-memory token, tells the server to clear the refresh cookie, and leaves the client unable to reach protected screens. If logout only navigates home, the next page still has a valid cookie and the session quietly continues.

- [ ] useAuth or AuthProvider manages user + access token in memory
- [ ] Boot refresh restores session on page reload (or documented limitation fixed)
- [ ] Logout clears state and blocks protected routes

Read this group in the developer tools. Search application storage for a token and expect nothing. Reload a signed-in page with the Network tab open and expect one refresh call before the protected content appears. Then log out and confirm the refresh call is refused afterwards.

### API client

The helper is the only place that knows how to talk to the API, so these four items are about everything that must happen in one function. Attaching the bearer header keeps authentication out of every page. The single retry after a 401 keeps an expired token from turning into a broken screen, and the word once matters: a retry loop that repeats on every 401 will hammer the refresh endpoint and lock the account out.

`credentials: 'include'` is required on the refresh request because the refresh token travels in an httpOnly cookie and the API sits on a different origin during development. Without it the browser sends no cookie and every refresh answers 401 for a reason that looks like a server bug.

The last item is the boundary of the whole design. If an access token appears in localStorage or sessionStorage anywhere in the client, the in-memory decision has already been undone, and the person who wrote the second copy usually did it to survive a reload.

- [ ] apiFetch attaches Authorization Bearer when authenticated
- [ ] 401 triggers refresh once then retry (tested or short-expiry verified)
- [ ] credentials: 'include' on refresh request
- [ ] Access token **not** in localStorage or sessionStorage

A reviewer proves the retry without waiting an hour: set the access expiry to something short in the server environment, sign in, wait past it, and click a protected action. Two network calls should appear in order, the refused one and the retried one, and the screen should show data rather than an error.

### Protected routes

A router guard and a server guard answer different questions, and this group is about the client half. `ProtectedRoute` decides whether to render a page at all, so an unauthenticated visitor is redirected to login instead of seeing an empty shell. The vendor stub item proves the guard can also check a role, so a customer who types the Studio URL is sent away rather than shown a page that will fail on its first request.

`isLoading` is the small item with the largest effect. During boot refresh the app does not yet know whether the visitor is signed in, so a guard that redirects before the refresh resolves sends a signed-in person to the login screen on every reload. The loading flag holds the redirect until the answer is known.

- [ ] ProtectedRoute redirects unauthenticated users to login
- [ ] Vendor stub page reachable only when logged in as vendor (if role prop used)
- [ ] isLoading prevents redirect flash during boot

Read this group by signing out and typing a protected URL directly, then by signing in and reloading the same URL. The first should land on login with a way back to where you were going. The second should render the page without a visible flash of the login screen.

### Integration

The seeded accounts are the fixtures every later module reuses, so both must sign in through the interface rather than through curl. A vendor login that only works in a terminal means the client and the server disagree about the response shape, and that disagreement will surface again in Module 9 when the Studio pages read the same response.

CORS with credentials is stricter than CORS without it: the server cannot answer with a wildcard origin, and the browser will send the cookie only when the allow origin names the exact Vite origin and credentials are allowed. That one rule is the most common reason a correct logout still leaves a working refresh.

The third item is a scope check. Chapter 7 adds no new server authentication endpoints. If your solution needed one, such as a logout route that clears the cookie, that is allowed and worth writing in the learning log, because a reviewer will see the new route in the diff and ask why.

- [ ] Seed vendor-a and customer-a login via UI
- [ ] CORS allows credentials from Vite origin
- [ ] No new server auth endpoints required beyond Ch 6 (cookie Set-Cookie OK)

A reviewer reads this group in the Network tab, filtering for the refresh request. The request should carry the cookie, the response should set a new one, and the headers on both should name the Vite origin exactly. If the request appears twice per reload, the boot refresh is mounted twice.

### Prior gates

These two items exist because the client is the first consumer of the API, and a consumer is where a broken fixture first becomes visible. Run the Chapter 6 curl flow again and the Chapter 5 seed before blaming the browser. A 403 on a seeded login is not a client bug; it is an account that was never verified.

- [ ] Ch 6 auth API still passes curl tests
- [ ] Ch 5 models/seed intact

### Explain these aloud

The next four items have no command behind them, so the evidence is a spoken answer. Say each one before ticking it, and leave the box empty if the sentence does not finish. These are the questions a reviewer asks while your browser is still open.

- [ ] Why access in memory vs localStorage?
- [ ] Explain 401 refresh loop step by step
- [ ] Difference between ProtectedRoute and server requireAuth
- [ ] What happens on full page reload?

The strongest answer about memory names both sides: what a script on the page can reach, and what you pay for the safety, which is a refresh on every reload. The strongest answer about the refresh loop names the four steps in order: refused call, refresh with credentials, new access token in memory, one retry of the original request. The strongest answer about the two guards says that the client guard protects attention and the server guard protects data, and that only the second one survives a crafted request.

## Learning log, write now

Answer **in your own words** in the fields below:

1. **Token storage:** Where do access and refresh live in your implementation? Why?

2. **Refresh loop:** Describe network sequence when access expires mid-session.

3. **Register flow:** UX path from register to first authenticated page, any friction?

4. **Role redirect:** How does login decide vendor vs customer destination?

5. **CORS/cookies:** What server CORS changes were needed for refresh cookie?

6. **Failure test:** One UI error state you tested (wrong password, unverified, etc.).

7. **Chapter 8 preview:** Why is login not enough to PATCH another vendor's store?

8. **Reload test:** Does session survive hard refresh? If not, what did you fix?

Question one is graded on the reason, not the location. A complete answer says where each token lives, what that choice prevents and what it costs. Question two should be a numbered sequence with the status codes, because "it refreshes automatically" describes nothing a reviewer can check.

Question three wants the friction you noticed, including the ones you decided not to fix. Friction the course expects you to mention: the code delivery in development, the length of the password rule, and what happens if the buyer closes the tab on the verify screen. Question five wants the exact origin and the credentials flag rather than the word CORS.

Question six should describe a screen, the message a person sees, and the console entry behind it. Question seven is the bridge into Module 8: a valid token says who you are, and it says nothing about whose Studio record you may write to. The honest version of question eight names the fix if your session did not survive, which is almost always a boot refresh that ran after the first render or a missing credentials flag.
