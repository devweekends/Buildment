# What leaves the webhook

By the end of Module 20 the payment webhook did four things inside one request: verify the signature, match the event against a stored Checkout, create one License per paid OrderLine, and answer the provider. That path was short on purpose, because a buyer's access depends on it. Then the friendly additions arrived. Amina should learn that her license keys exist, Nour and Salma should learn that they sold something, and a Checkout that nobody paid should close instead of sitting open in a dashboard. Each of those is a good idea. Building all of them inside the handler turns a four step request into a request that also depends on a mail server.

The payment provider measures the time between sending an event and receiving a non error answer. A handler that waits on a slow mail API is a handler that can be cut off, and a cut off delivery comes back while the first copy may still be running. The retry is not a rare fault to plan for later. It is the ordinary consequence of doing slow work on a path that someone else controls. This chapter draws the boundary: what the buyer's access depends on stays in the request, and what a human reads later leaves it.

You have already met the two queues that matter here without naming them. Module 20 held a decision back to this module, and the roadmap made it explicit: database writes inline so access is instant, emails and notices queued. Module 23 pays that decision off, and adds the piece the webhook cannot provide on its own, which is a sweep for payments whose event never arrived.

Read the trace from left to right and notice where the provider stops waiting. Everything above the third step changes what Amina may download. Everything below it changes what somebody reads in an inbox, which is a much weaker promise and one that a second run can repair. If you can move a step below that line without making a paid buyer wait, move it.

## The tail the webhook grew

Picture the handler as it looked when the receipt was added. Amina's Checkout covers a font from Nour's Studio and a template from Salma's Studio, so a full notification pass sends three messages: one receipt to Amina, one sale notice to Nour, one sale notice to Salma. If a mail provider call takes 200 to 1,200 milliseconds on a good connection, that is three calls in series, on top of the database work. On a weak connection the same three calls take several seconds, and the webhook answer time becomes something the provider might not accept.

Now add the second reason the tail is slow. The receipt needs Amina's license keys, and those keys exist only after fulfilment has created the Licenses. A handler that sends the receipt in the same request has to finish the grants, read them back, format three messages, and only then answer. None of that reading and formatting makes a key exist. It is presentation work sitting on the critical path of a payment.

The third problem is coupling, and it is the one that turns a small delay into an outage. If the mail provider answers with a 503, a naive handler throws, returns a server error, and the payment provider retries an event whose database work already succeeded. Every retry repeats the mail call, because nothing in the handler remembers that the message was already attempted. A mail outage now looks like a payment endpoint that cannot answer, and the people debugging it start from the wrong service.

## Work that must stay in the request

The test for keeping work inline is not speed. It is this question: if this step were delayed by thirty seconds, would a buyer be denied access, or granted access twice? Verification, matching, the Checkout state change and the creation of the Licenses all fail that question in one direction or the other, so they stay. A receipt, a creator notice, a reconciliation sweep and a cleanup job all pass it, because their failure is a message that nobody read yet or a report that arrives late.

| Work | Runs where | Why it belongs there |
|---|---|---|
| Signature check and Checkout match | Inline | A queued decision could confirm a payment the buyer was already told had failed |
| Conditional Checkout status write | Inline | That single write is the guard against two people deciding the same payment |
| One License per paid OrderLine | Inline | This is the access itself; a queue delay leaves the library empty while the success page polls |
| Receipt email to the buyer | Worker | A mail outage must not make the payment endpoint look unhealthy |
| Sale notice per creator Order | Worker | A notice is not access, and it is read later in any case |
| Reconciliation sweep | Scheduler | It repairs a missed event; it is not part of any single payment |
| Abandoned Checkout cleanup | Scheduler | It protects a dashboard, not a buyer's rights |

That table is the decision this chapter is asking you to make, so read the right hand column as a set of reasons rather than as labels. Notice that the queue never carries work whose failure removes access. The queue carries work whose failure leaves a written record missing, and a written record can be regenerated by running the same job again with the same id.

There is one more candidate people try to queue, and it deserves a sentence of its own. Do not queue the License creation to make the webhook faster. It is the most tempting move in the module, because it would remove the last database write from the request, and it is wrong for this product. The success page polls for Licenses that the buyer already paid for. A queue delay of two seconds is invisible; a queue outage is a paid buyer with an empty library and no way to tell whether the payment worked. The inline path is what makes the word instant honest.

## A receipt that is useful and harmless

The obvious receipt says "here is your font" with a download button, and that receipt is a defect. Module 21 issued file links that expire after about five minutes and carry a signature made with a secret only the server holds. An email outlives five minutes by design, so the button in the message would usually be dead before Amina reads it. A receipt that offers a download and then fails teaches the buyer that the product is broken.

The stronger objection is about who can use the link. A signed URL is a bearer capability: whoever holds it can fetch the file until it expires, with no identity check at all. An inbox is a forwarding machine. A receipt sent to a work address, printed into a shared support ticket, or copied into a backup carries a live capability to a private file with it. Module 21 spent a whole chapter making every file request pass an identity check on the server, and an emailed link walks around that check for as long as it lives.

So the receipt carries two things that are safe and one thing that is not. It links to the library page, which is an ordinary authenticated route and asks for a session. It lists the license keys Amina bought, which are references she can read again after logging in, and which prove a purchase without fetching anything. It does not carry a signed file URL, a storage public id, a DownloadGrant token or a Cloudinary API secret. A key proves a purchase; it does not open a file. Write that distinction into `docs/PRIVATE-FILES.md`, because it is the sentence a future maintainer will need.

There is a second scope question inside the receipt, and it is about the buyer rather than the creators. Amina paid once for items from two studios, so her receipt is the one place where both creators appear together. That is correct, because it is her payment. It is also the only message that may mention both, and the next section explains why.

## A sale notice each creator can read

Each creator is paid by one Order, and the sale notice must be built from that Order. The Checkout total covers Nour's font and Salma's template, so a notice that reports the Checkout amount tells Nour she earned money she did not earn. The mistake is easy to make because the Checkout is the record the webhook already loaded, and it is the record that carries the number the buyer actually paid. Passing that number along is the natural thing to do and it is wrong by the price of a template.

The safe shape is a job payload that carries an Order id or a Studio and Order pair, never a Checkout id. The processor loads the Order with its Studio predicate, renders only that Order's lines, and reports only that Order's total. A job that takes a Checkout id and filters lines by studio later also works, until someone forgets the filter during a refactor, and then Salma's template detail lands in Nour's inbox. Scope the query, not the template.

The same discipline covers the buyer's details. A creator needs enough to answer a support question about a sale, so the notice shows the buyer's display name and the order reference. It does not show the buyer's full purchase history, the other creator's order from the same Checkout, or the amount the buyer paid in total. Those facts exist, and none of them belong to this creator's Order. Treat that as a privacy decision with a test behind it, not as a formatting choice.

```js
// server/src/queues/payloads.js (partial, comments explain the contract)
// Every payload is an id or a pair of ids. No prices, no keys, no URLs.
const receiptPayload = { orderId: 'ord_66f1c0a4' };
const saleNoticePayload = { studioId: 'stu_9a2', orderId: 'ord_66f1c0a4' };
const reconcilePayload = { windowMinutes: 120 }; // the sweep's own bound
```

Read those three lines as a security rule rather than as types. Job data sits in Redis until the job is removed, and anything in Redis is readable by every process that has the connection string. A price or a license key in a payload becomes a second copy of data that only the database and the library route should hold. Ids keep the payload cheap and keep the sensitive records where the access rules already live.

## The payment that arrives without a webhook

A webhook is a notification, not a guarantee. Your API can be down during a deploy, the endpoint secret can be rotated at the wrong moment, a delivery can exhaust its retries during a long outage, and the provider will then stop trying. In all of those cases the money moved and Midad never heard about it. Amina paid, her library is empty, and the success page polls a Checkout that will stay pending forever.

The repair is a repeatable job that reads the provider instead of waiting to be told. Every few minutes it looks for Checkouts still in `pending_payment` past a short grace period, retrieves each stored PaymentIntent, and asks whether the provider says it succeeded. When the answer is yes, and the amount and currency match the frozen Checkout, the sweep runs the same confirmation path and the same `fulfilCheckout` the webhook runs. Same function, same unique indexes, same result.

That last point is the design. The sweep is not a second fulfilment path, and it must not contain its own copy of the grants. It is the same path with a different trigger, which is why a checkout that was already fulfilled cannot be fulfilled twice: both triggers end in the same conditional write and the same unique index on `orderLineId`. If you find yourself writing a second implementation for the repair, the repair is wrong.

Two limits keep the sweep honest. It must be bounded, reading a window of time and a page of rows rather than the whole collection, so that a busy marketplace does not turn a repair into a scan. And it must not invent a payment. A Checkout created before the PaymentIntent existed has no provider reference to retrieve, so the sweep skips it and lets the expiry rule close it. The sweep can only confirm what the provider already knows; it cannot make a payment true.

## Retry is a promise, dedup is a guard

BullMQ retries a job when the processor throws an error. You set `attempts` and a backoff policy, and the built in exponential strategy waits `2 ^ (attempts - 1) * delay` after each failure, which is the right shape for a mail provider: a quick first retry for a blip, then longer waits that give an outage time to clear. A job that exhausts its attempts lands in the failed set, where a person has to look at it. Do not set the queue to drop failures silently, because the failed set is the only place a mail problem becomes visible.

A retry means the processor can run twice, so the send has to be safe at the effect. Two guards, again with two different jobs. A `jobId` derived from the recipient record, for example `receipt:<orderId>`, stops the same receipt from being queued twice, because BullMQ keeps one job per id and ignores a second add with the same one. A `Receipt` document with a unique index on `orderId` and a `sentAt` field stops a second message when a job is retried after the mail call already succeeded but before the job was marked complete.

Be honest about what those guards buy. A queue that delivers at least once cannot promise exactly once delivery to a mailbox. If the worker dies after the mail provider accepted the message and before the record was marked sent, the retry sends again, and Amina gets two receipts. The unique record narrows the window, makes the duplicate countable, and gives support a way to see what happened. It does not close it. Say that in the operations note, and prefer the small risk of a second receipt to the large risk of no receipt at all.

```quiz
explanations:
  - A signed URL is a bearer capability, so a forwarded receipt hands the file to whoever receives it, and five minutes makes the button dead on arrival anyway.
  - The library link asks for a session and a key proves a purchase without fetching anything, so neither one is a file capability.
  - The storage public id is the address of the private asset, and with the account delivery rules it becomes a route to the file.
  - The client secret belongs to the payment session, is useless after payment, and is a credential that should never leave the browser.
```

The two distractors in that question are the two mistakes people actually make. A generated link feels helpful, and a storage id feels internal because it looks like a database key rather than a URL. Neither is safe in a message that leaves the system and is stored by a party you do not control.

## Before you build

Write the boundary down before writing the worker. Name the work that stays inline and the work that leaves, and for each queued item name the guard that stops a second run from doing harm. Then build in the order the next chapter uses: the worker process first, so you can see a job run before you rely on it, then the receipt, then the creator notice, then the reconciliation sweep, then the retry and cleanup settings that the gate will ask you to prove.

The gate for this module drops a webhook on purpose and shows the sweep repairing the sale, restarts the worker in the middle of a job, and reads the mailer output to confirm that nothing in it expires. Keep the mailer a console mock for now. The message format is what you are testing, not a mail provider account, and a console line is easy to search for the one string that must never appear in it.
