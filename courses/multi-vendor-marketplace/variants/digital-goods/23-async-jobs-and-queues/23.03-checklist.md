# Async jobs gate

This gate asks for behaviour you cannot see in a browser. A receipt that arrives is easy to show; a receipt that arrives once when the worker is killed mid job is a claim that needs evidence. So the gate has four parts. Drop a webhook and let the sweep repair the sale. Kill the worker during a job and watch the retry finish it without a second message. Queue the same receipt twice and show one job. Then read every message the module sent and confirm that none of them contains something that expires.

Start from a named state and write it down before you touch anything. One Checkout, two paid OrderLines, one from Nour's Studio at 1,200 minor units and one from Salma's Studio at 1,800, one buyer called Amina, the API, the worker and the Stripe CLI listener all running, and an empty outbox. Record the Checkout id, both Order ids and both License ids. If you begin from a messy database, every count you take later is a guess and the gate turns into an argument about fixtures.

## Drop the webhook on purpose

The point of this drill is to recreate the failure the sweep exists for. Stop the CLI listener or remove the dashboard endpoint, then pay the Checkout with a test card. The money moves, the provider is happy, and Midad knows nothing: the Checkout stays `pending_payment`, both Orders stay unpaid, and no License exists. Take a count and keep the number. That empty library is not a bug in this drill, it is the condition the sweep repairs.

Now start the maintenance queue and let the reconcile job run, or call the processor once by hand. Within one pass the Checkout should be `paid`, both Orders should be `fulfilled`, and there should be exactly two Licenses, one per OrderLine. Run the sweep a second time and compare the License ids. They must be identical, because the second run finds the confirmed Checkout and the unique index on `orderLineId` refuses a second grant. A sweep that creates new rows on the second pass is not a repair, it is a second fulfilment path, and it will double the library the first time a late webhook also arrives.

Finish the drill by restoring the listener and paying a second Checkout normally, so that both triggers are in play at once. The webhook confirms this one and the sweep finds nothing to do. Save the two runs side by side: one checkout repaired by the sweep, one confirmed by the event. They should end in the same state, and the evidence should show the same counts and the same unique ids in both.

## Kill the worker in the middle of a job

Add a test only delay to the receipt processor, or use a debugger breakpoint, and stop the worker process after the mailer has accepted the message but before the `Receipt` row reaches `sent`. Then restart the worker. BullMQ recovers the stalled job and the processor runs again. The gate wants two things from that restart: the message is sent again, because the process cannot know it succeeded, and the `Receipt` row ends in `sent` with a message id.

Record the outbox count before the restart and after. A duplicate is the expected outcome of the crash window, and saying so plainly is the difference between understanding the system and hoping. What must not happen is a missing receipt or a `Receipt` row that stays in `sending` after a successful retry. If the row never reaches `sent`, the guard in the processor is wrong, and the next run will send a third message.

If your build uses a mailer whose send is slow enough to observe without a breakpoint, that is easier to demonstrate and worth the extra second. Stop the worker with the process id from the startup log rather than with a terminal shortcut, so the log shows the job started and the process ended in that order. The startup log is also how the marker proves the process is separate from the API: two process ids, two logs, one database.

## Queue the same receipt twice

Add the receipt job with the same `jobId` twice in a row and inspect the queue. There must be one waiting job, not two, and the second add should return the existing job rather than a new one. That is the queue level guard, and it protects against an API path that enqueues the receipt on every retried delivery of the same payment event.

Then prove the record level guard separately, because the two guards fail differently. Delete the waiting job, run the processor once by hand so the `Receipt` row becomes `sent`, and enqueue the receipt again with a fresh job id. The processor should read the existing row and stop before the mailer is called. One guard is about the queue, the other is about the effect; a system that has only the first one sends a second receipt whenever the queue is drained or a job is added by hand.

## Read the messages as a buyer and as a creator

Open the outbox and read the buyer receipt as Amina would. It names both creators, because she paid once for both, and that is correct for her message. It lists the license keys and the license type for each line, and it links to the library. It does not contain a URL that expires, a storage host, a DownloadGrant token or anything that fetches a file. Search the message for the words `expires`, `signature` and the storage hostname, and show the empty result.

Now read Nour's notice. It names her font, her Order total and the buyer's display name, and it says nothing about the template, the other Order or the 3,000 minor units that Amina paid in total. Then run the notice job once with Salma's Studio id and Nour's Order id on purpose. Nothing should be sent, and the log should show the job completing without a message, because the scoped query found no Order. That silent completion is the evidence that scope lives in the query rather than in a filter you remembered to apply.

The last read is the one people skip. Look at the job payloads in Redis for the receipts you just ran. They should contain ids and nothing else: no price, no key, no email body. If you find a license key in a payload, the processor was tested against data that a second system already holds, and you should move the lookup into the processor before calling the gate done.

## What this gate does not prove

This gate does not prove that a mail provider delivers. The course uses a console mock, and a mock cannot fail the way a real provider fails, so the retry path is exercised by throwing from the mock rather than by waiting for a slow network. It also does not prove exactly once delivery to a mailbox, which no queue can promise. What it proves is narrower and more useful: the payment path stays short, the readable work is idempotent at the record, and a missed webhook has a second trigger that reaches the same function.

## Gate checklist

- [ ] `npm run worker` starts a second process that logs its queue names and process id, and the API keeps serving requests with the worker stopped.
- [ ] Redis holds three queues, and a job payload contains only ids, never a price, a license key, an email body or a URL.
- [ ] A dropped webhook leaves the Checkout pending with no License, and the reconcile sweep then confirms the Checkout and creates exactly one License per paid OrderLine.
- [ ] A second sweep run leaves the same License ids and the same counts, and the log shows the candidates it inspected and skipped.
- [ ] A Checkout with no stored PaymentIntent is skipped by the sweep and later closed by the cleanup job, with no invented payment.
- [ ] A provider amount that disagrees with the frozen Checkout writes a mismatch record from the sweep and changes no Checkout state.
- [ ] Killing the worker mid receipt and restarting it ends with the `Receipt` row `sent` and a message id, and the duplicate message is stated in the evidence rather than hidden.
- [ ] Adding the same receipt job twice with one `jobId` leaves one waiting job.
- [ ] A receipt already marked `sent` is not sent again when a fresh job id arrives, because the processor reads the record first.
- [ ] The buyer receipt contains the library link and the license keys, and contains no expiring URL, no storage host and no grant token.
- [ ] Nour's notice shows only her font Order, and a notice job run with another Studio id sends nothing.
- [ ] The cleanup job moves an expired `pending_payment` Checkout to `expired` without touching a Checkout confirmed in the same interval, and deletes no history.
- [ ] The queue settings show `attempts`, exponential backoff and retained failed jobs, and one deliberately failed receipt appears in the failed set with its error.
- [ ] The worker log, the sweep log, the outbox, the `Receipt` documents and the Redis payload inspection are committed as evidence with no secret keys visible.

## Learning log

1. Which four steps of the payment path stayed inside the webhook, and which four moved out? For each queued item, name the guard that stops a second run from doing harm.
2. A mail provider returns an error on the receipt. Walk through what the API, the queue and the worker each do, and explain why returning a 500 from the webhook would be the wrong repair.
3. The sweep and the webhook both call `fulfilCheckout`. Show the two mechanisms that keep the second call from creating a second License, and say which one fails if the sweep had its own insert.
4. Your receipt job is retried after a crash between the mail call and the record update. State honestly what the buyer sees, and explain why the design accepts that risk.
5. Nour's sale notice must not mention Salma's template. Where is that enforced: the payload, the query or the message builder? Defend the choice with the test that would fail if it moved.

Commit the worker entry, the queue module, the three processors, the `Receipt` and `Notice` schemas with their unique indexes, and the tests. Add a short section to `docs/FULFILMENT.md` naming the log line that shows a sweep pass, the query that lists paid but unfulfilled Checkouts, and the rule that a mismatch is recorded rather than corrected. A mentor should be able to rerun the dropped webhook drill from that note alone.
