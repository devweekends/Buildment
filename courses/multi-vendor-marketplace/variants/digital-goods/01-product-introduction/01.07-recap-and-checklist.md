# Recap and checklist

Before creating folders and routes, explain Midad to another learner in two sentences. One sentence should say what a creator publishes and what stays private. The other should say how a buyer pays, gains current access and requests a short-lived download. If the explanation says only "sell files online," add the entitlement and refund constraint. The course's data model and payment gates depend on that distinction.

## Show the product flow

Draw upload, public preview, license choice, server-priced Checkout, verified payment event, License, library, DownloadGrant and refund. Put a mark where the browser is allowed to display state and where the server is allowed to create access. The success page can show pending fulfillment; it cannot grant a License. A copied link may work until expiry; a refund blocks future grants but cannot erase downloaded bytes. Explain those limits without pretending the course has implemented them yet.

## Check actors and scope

Name a valid and invalid action for a creator, buyer and public visitor. A creator edits only Products in their own Studio. A buyer reads only their own Library. A visitor may see a public preview but not an original file. The payment provider reports test-mode payment state to the server; it is not a source of browser-supplied user identity. Then name two excluded features, such as real payouts and physical shipping, and say why they are outside this digital product's core path.

Review the entry diagnostic. If two or more foundations were missing, complete the repair exercises and save the revised answers before Module 2. If one was weak, name the repair you will do alongside the skeleton build. An honest diagnostic result is more useful than a guessed correct answer. Keep a local commit with `docs/learning-log.md` and the first product-flow sketch so an interrupted session has a known resume point.

## Learning log

1. Which record will later prove what price and license terms a buyer accepted, and which record will say whether they may download today?
2. A buyer lands on a success page while the verified webhook is delayed. What should the page say, and which action must it avoid?
3. A buyer copies a brief signed URL before a refund. What can Midad stop after the refund, and what can it not recall from the buyer's device?
4. Which diagnostic task was hardest for you, and what exact repair or practice command will you use before the related module?

The gate passes when your diagram, two-sentence explanation, actor matrix, diagnostic answers and recovery note agree. A mentor should be able to read them without guessing which feature is already built. Keep this evidence as text where possible so it works on weak connections. Module 2 will create the client and server skeleton; this gate only establishes the product contract and your working method.

## Verify the working method

Open your repository and show the local commit containing the learning log, the actor matrix and the one-line flow sketch. A commit can exist before the app skeleton; it records the product decision you are about to implement. Ask another learner to read the flow without your explanation and point at the step where price is authoritative and the step where access is granted. If they point at the browser success page, revise the diagram caption and the two-sentence description.

Use the diagnostic as a concrete action plan. A missed route question leads to an Express practice task; a missed query question leads to a small Mongoose filter exercise; a missed Git question leads to a local add/commit rehearsal; a missed minor-unit calculation leads to a server-total exercise. Do not carry an unnamed "need to review basics" note into Module 2. Name the repair and the command or artifact that will show it is done.

A peer can also challenge the scope. Ask whether a buyer needs a shipping address for a font. The answer is no for this core path, so remove any inherited form that asks for one. Ask whether a public preview can be the original ProductFile. It should not, because the preview must remain safe for an anonymous visitor. Ask whether a refund can retrieve downloaded bytes. It cannot. These questions turn the product brief into engineering constraints before code makes them expensive to change.

Finally, save a one-paragraph week-one target in the learning log: client and server talk; two creators and two buyers exist in a repeatable seed; a Product preview is public; an original file remains private; and the first ownership denial is visible in a raw test. Later weeks extend this slice into verified payment and bounded download. The target is specific enough to check after an interruption and small enough to show on a weak connection.

A final check is to compare your actor matrix with the one-line flow. Every change to private file, price, payment or access should have one named authority and a denied actor. If a box has no owner, note it for Module 5 rather than inventing a rule during implementation. This makes the introduction a working contract for the project, not a decorative overview.
