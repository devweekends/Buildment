# Creator dashboard gate

This gate is passed with two creator sessions and one buyer session, not with a screenshot of a table. A dashboard that reads products looks correct from the outside whenever the signed in creator happens to be the only creator with data. The failure appears on the day a second creator logs in, and by then the query is buried under a form, a filter and a status tab. Bring the tokens, the response bodies and the stored documents, so a reviewer can see which query built each row.

The gate has three jobs. It proves the scope, because every read and write on the dashboard must resolve the Studio from the session. It proves the price, because a product sold under two licenses must show two amounts. And it proves the editor's refusal, because an option that a paid order line holds must survive an edit that tries to remove it.

## Prepare two Studios with different work

Nour has two published products, one draft and one archived. Salma has one published product and one draft. Give both creators a personal and a commercial option on at least one product, with different prices and different seat and download limits, so a mixed up price is visible rather than plausible. Keep one archive record, because restore is the action that most often forgets its status check.

Write down the identifiers of a Nour product and a Salma product before you start. The direct requests below use them, and a reviewer will want them in `docs/DASHBOARD.md` beside the responses that refused them.

## Walk the scoping matrix

Send each request with the token in the first column and record the status and the body. The screen check comes after this table, never before it, because a client cannot prove a server rule and a hidden button is not a refusal.

| Request | Expected | What it proves |
|---|---|---|
| `GET /me/studio/products/counts` as Salma | 200, Salma's counts only | The count resolves the Studio from the session |
| `GET /me/studio/products?status=draft` as Salma | 200, Salma's drafts only | The list filter includes the Studio |
| `PATCH /me/studio/products/{Nour product}` as Salma | 404 | The write filter includes the Studio, not only the role |
| `GET /me/studio/products/counts` as a buyer | 403 | The surface is role gated |
| `GET /me/studio/products` with no token | 401 | Authentication runs before any database read |
| `POST /me/studio/products/{Nour product}/publish` as Salma | 404 | An action route repeats the ownership check |

The `PATCH` row is the one that matters most. A route that loads the product by identifier and then checks `role === "creator"` will let Salma rewrite Nour's price, and the next buyer pays it. The Studio identifier belongs in the query that performs the write, not in a comparison that runs after the document is loaded.

Module 11 chose a `404` for a foreign product, so a wrong creator cannot learn whether an identifier exists. Keep that choice here and repeat it in the checklist. A refusal also needs a shape: an answer that returns the product title in the body confirms the existence of another creator's work, whatever the status code says. Send the code and the field, not the document.

## Prove the price column

Open the dashboard as Nour with the network panel visible and find the response for the table. Every product in it must carry its full option array: key, type, price in minor units, seat limit, download limit and terms version. The rendered row must print each option with its own formatted amount, and the amounts must match the stored integers after dividing by 100 exactly once.

Change one personal price in the editor, save, and reload. The draft tab and the published tab must both show the new amount for the products they list, and the counts must not move. Then change the price of a commercial option and confirm the personal amount is untouched. A row that shows a single "from" figure cannot pass this check, because there is no way to see which option changed.

## Prove the editor's refusals

Four saves must fail, and each must fail with a field name rather than a generic message. An empty options array returns `400` naming `licenseOptions`. A price of `12.5` minor units returns `400` naming `priceMinor`. A second option with an existing key returns `400` naming the duplicate key. A personal option with three seats returns `400` naming `seatLimit`.

The fifth save is the interesting one. Seed an OrderLine fixture that holds a Nour product identifier and its commercial option key, then remove that option from the array and save. The server must answer `409 OPTION_IN_USE` and the stored option array must be unchanged. Read the document back and compare it with the array you sent. A `409` with a mutated document is the worst outcome of the five, because the message says nothing changed while the record says otherwise.

```js
// server/tests/dashboard.gate.test.js
test("a sold option survives the edit that removes it", async () => {
  const before = await Product.findById(soldFont.id).lean();
  const res = await request(app).patch(`/me/studio/products/${soldFont.id}`)
    .set("Authorization", `Bearer ${nourToken}`)
    .send({ licenseOptions: [personalOnly] });
  expect(res.status).toBe(409);
  expect(res.body.code).toBe("OPTION_IN_USE");
  const after = await Product.findById(soldFont.id).lean();
  expect(after.licenseOptions.map((o) => o.key)).toEqual(before.licenseOptions.map((o) => o.key));
});
```

Then restore the archived product and confirm it returns as a draft with its options intact. Archive it again and confirm the public catalogue no longer lists it. That pair is the whole archive rule in two requests: leaving the catalogue and losing the record are different events.

## Gate checklist

- [ ] Salma's counts contain no identifier, title or total from Nour's Studio.
- [ ] Every list and count route resolves the Studio from the session and accepts no Studio parameter.
- [ ] A buyer token is refused on every dashboard route, and a missing token returns 401 first.
- [ ] A cross creator write is refused by the writing query and the stored document is unchanged.
- [ ] Each row prints every license option with its own price, seat limit and download limit.
- [ ] A price edited in the editor appears on both the draft and published tabs with the same amount.
- [ ] An empty options array, a fractional price, a duplicate key and a personal option with extra seats each return a named field error.
- [ ] Removing a sold option returns 409 OPTION_IN_USE and leaves the stored array untouched.
- [ ] Archive removes the product from the public catalogue, and restore returns it as a draft with its options.
- [ ] No refusal body contains another creator's product title, price or option key.
- [ ] Raw requests with both tokens are saved in `docs/DASHBOARD.md` beside the stored documents they protected.

If a count or a list leaks, move the Studio identifier into the query. If a refusal carries a title, project fewer fields. If a sold option disappears, the service is validating the array without loading the lines that depend on it. If restore returns a published product, the restore action is copying the previous status instead of starting from draft.

## Check the retire rule

```quiz
type: mcq
id: digital-goods-dashboard-q2
question: "Nour wants to stop offering the commercial license on a published font that three buyers already own. Which action keeps her buyers' records intact and stops new sales of that option?"
options:
  - "Remove the commercial option from the array so new buyers cannot choose it"
  - "Set retired true on the option and keep its key, price and terms version in the array"
  - "Archive the whole product, which withdraws every option from new buyers and hides the font from browse"
  - "Lower the commercial price to one minor unit so nobody chooses it"
correct: 1
explanations:
  - "Removal strands every order line that names the key, and the gate refuses it for that reason."
  - "Retiring keeps the record that paid buyers point at, hides the option from buyers, and leaves the personal option on sale."
  - "Archive withdraws the entire product, including the personal option she still wants to sell."
  - "A near zero price still creates obligations and does not withdraw the offer."
```

## Learning log

Answer these in `docs/learning-log.md`, with the request, response or document that supports each answer.

1. Which field resolved the caller's Studio on the counts route, and where did that value come from?
2. What did the table response weigh for Nour's five products, and how many requests did the page make to draw it?
3. Which option did you change in the editor, and how did you prove the other option kept its price?
4. What did the sold option removal return, and what did the stored array look like afterwards?
5. Why is archiving a product not the same as revoking a license that was sold before the archive?
6. If a creator asks for a delete button, what will you offer instead, and which record would a delete destroy?

The fifth answer is the one to carry into Module 13. The dashboard edits an offer, and an offer can change or leave the catalogue. Access belongs to a paid order line, and only a refund takes it away.
