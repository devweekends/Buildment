# Order routes and checklist

Build `GET /orders/my` for the authenticated Buyer and `GET /studios/:studioId/orders` for an authenticated creator who owns that Studio. Both routes should query the database with ownership predicates. A Buyer can see all their own per-Studio Orders under one Checkout; a creator sees only Orders for their Studio. A seller should not see another Studio's private line details because both shared a payment. A public Product page should not expose Order IDs or buyer identities.

## Prove the split

Seed Nour and Salma Studios and Amina as Buyer. Confirm a two-line Cart. Inspect exactly one Checkout and two pending Orders, one per Studio. The sum of their snapshot amounts equals Checkout total in one currency. A retry with the same buyer request key returns the existing Checkout and does not increase any count. The test database must have the unique keys built; print their names or inspect them in the test setup. A happy page with two cards is not evidence that the underlying Orders are split correctly.

Ask Nour for her Order list and verify she sees only the font line. Ask Salma and verify she sees only the template line. Ask Amina and verify she sees both. Then use Kareem's Buyer account to request Amina's Order ID directly, and use Nour's creator account to request Salma's Order ID. Expect the course's chosen 403 or 404 response and no line or buyer details in the body. Inspect the database after any denied mutation attempt; the read denials should not trigger state changes.

## Prove pending is not paid

Before a verified provider event, Orders remain `pending_payment` and the library has no License for either line. Refresh a success page or call its read endpoint twice. License count remains zero. This is the important boundary between this module and payment processing. A test fixture can simulate an eventual verified event in a later module, but do not manually mark an Order paid to make the current gate look complete. Explain where Module 19 will compare provider amount and currency and where Module 20 will grant entitlement.

Change Nour's current Product price and license terms after the pending Checkout exists. Its OrderLine and Checkout total remain unchanged. Start a new Checkout for another Buyer and show the new current offer. Change Salma's Product title and confirm Amina's old line still records the title shown at confirmation. These raw snapshot checks catch accidental `populate` of current catalogue fields. If the old line changes, fix the serializer or data mapping before connecting Stripe.

## Learning log

1. Why does a two-Studio Cart create one Checkout but two pending Orders, and which unique key keeps a retry from duplicating them?
2. A creator changes Product price after Amina confirms Checkout. Which stored record sets the provider amount for that attempt, and which record shows the new price to a later Buyer?
3. Why must the success page remain read-only while the webhook is delayed, and what should Amina see instead of a second Pay prompt?
4. Show a wrong-Buyer Order read and wrong-Studio creator read. Which database predicates deny them, and what private fields stay absent?

The gate passes when the route tests, database counts, current-versus-snapshot comparison and raw denials agree. Commit the Checkout and Order schemas, indexes, route, transaction or documented recovery path, and tests. Keep provider secrets and private file IDs out of evidence. The next module connects Stripe in test mode; it may rely on stable pending OrderLine IDs, but it still must verify payment before changing them or creating Licenses.

## Test a partial local failure

Inject a failure after the first pending Studio Order is prepared in a disposable test database. Under the chosen transaction path, neither Checkout nor first Order remains after abort. Under a documented recovery path, the Checkout remains explicitly incomplete and a retry creates the missing second Order before payment can begin. State which path the learner implemented and show its database counts. A route that leaves one apparently ready Order while charging the combined total is not acceptable.

Also test a provider timeout boundary without pretending this module verifies payment. The local pending records may exist while the provider adapter has no confirmed reference. A retry uses the same Checkout identity and later the same provider idempotency key. It does not create new per-Studio Orders. The next module will determine whether a PaymentIntent exists and compare amount and currency; this gate only proves the local plan is stable and recoverable.

## Inspect the seller and buyer wording

Amina's page should say payment pending or access preparing, not "download now" before verified fulfillment. Nour's dashboard should not add a pending Order to completed revenue. Salma should not see Nour's order line. These interface statements follow directly from stored state and scoped routes. A route test can prove data isolation; a quick narrow-screen review can show whether a human can understand the state without retrying Pay unnecessarily.

Keep one concise evidence packet: Checkout and two Order IDs, the equality of frozen totals, one retry result with unchanged IDs, two raw unauthorized reads, and a Product edit that leaves old snapshots fixed. Redact buyer contact details and provider credentials. The packet is enough for a mentor to verify the module before Stripe integration, even if the external sandbox is unavailable that day.
