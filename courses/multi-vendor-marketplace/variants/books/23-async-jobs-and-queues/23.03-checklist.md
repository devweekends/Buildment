# Async jobs gate

This gate is read from timestamps and queue state. A learner who says the notification is asynchronous has said nothing a reviewer can check. A learner who shows a publish response at 22:41:07.140 and a worker log line at 22:41:07.902 has shown the boundary working, and can then show what happens when the worker is not running at all.

Set up two terminals, one for the API and one for `npm run worker`, plus a Redis you can stop. Use one shop owner account and one copy that is not yet published. Write the times down as you go, with the job ids, because the learning log asks for them.

## Gate checklist

- The publish response carries a timestamp, and the worker log line for the same Listing carries a later one.
- `docs/JOBS.md` names each queue, each job name, the id rule, the attempt count, the backoff and the removal policy.
- A paid checkout produces one `order-paid` job per order, with the order id inside the job id and a payload holding only ids.
- Republishing the same copy with an unchanged revision leaves one job, and the sent message count stays at one.
- A forced processor error produces a second attempt after a visible delay, and both attempts appear in the log with their attempt numbers.
- With the worker stopped, the publish response is still a success, one job waits in Redis, and starting the worker processes it once.
- A Listing withdrawn before the job runs finishes as a completed job with no message, and does not sit in the failed set.
- The API process does not depend on the worker to answer any student or shop route.

## Read the two timestamps together

Publish a copy and capture the exact response time, then find the worker line for that Listing id. The gap is the queue latency, and on a laptop with a running worker it is usually between 100 and 900 ms. That number is not a target; it is evidence that the work moved. The property that matters is that the response time did not change when you slowed the worker down.

Prove that by adding a deliberate wait inside the processor, three seconds is enough, and publishing again. The response time should stay where it was, and the worker line should arrive three seconds later. Then remove the wait. A learner who skips this step has shown that two processes exist, not that the request stopped waiting for them.

Do the same reading for a paid checkout. The webhook response to Stripe must be fast, because Stripe retries slowly and a slow route produces duplicate events that make every later investigation harder. Capture the response body and the two job ids, one per order, and confirm the ids contain the order ids rather than the checkout id.

## Republish and read the job id

Publish the copy, then subtract one from the revision and publish again with the same revision, which simulates a double submit. Read the waiting count before and after. It must not grow. Read the worker log and count the lines for that Listing id: one, not two.

Now change a purchase term, the price is the easiest, and publish again. The revision increases, the id changes, and a second job appears. That is correct behaviour, and the gate wants to see both readings side by side: same facts, one job; changed facts, two jobs. A learner who deduplicates everything by Listing id cannot send the second alert that a genuine price drop should produce.

Finally, let a completed job be removed and republish with the old revision. Whether a job is created depends on the removal policy you set, and the reading should match what `docs/JOBS.md` says. If your policy says completed jobs are kept for a day and a republish after two days creates a new job, that is the documented cost of using the queue as a short lived guard. The durable guard is the unique index in module 24.

## Force a failure and read the backoff

Make the processor throw on the first attempt only, with a condition on `job.attemptsMade`. Publish a copy and watch the log. You should see the first failure, the job moving to the delayed set, and a second attempt after the configured delay. Read the delay from the timestamps and compare it with the backoff number in `docs/JOBS.md`. With exponential backoff seeded at two seconds, the first retry lands about two seconds later and the next about four.

Then make the processor throw every time and let the attempts run out. The job must end in the failed set with five attempts recorded, and the failure listener must log it once with the final attempt number. A job that vanishes after the last attempt is worse than a job that fails loudly, because the shop is left waiting and nobody knows.

Check the permanent failure case as well. Withdraw a Listing after its job is enqueued but before the worker runs it, then start the worker. The job must complete with no message. If it throws, the log fills with five failures for a copy that no longer exists, and a real failure hides among them.

## Stop the worker and recover

Stop the worker process with Ctrl and C, or with the process manager you use, then publish a new copy. The HTTP response must still be a success. Read `listingsQueue.getWaitingCount()` from a small script or from the queue's summary page and see one waiting job. Restart the worker and watch the job run once, with the same job id it had before the restart.

Repeat with three publishes while the worker is down. Three jobs, three messages after the restart, in an order the queue chooses rather than the order you sent them. That detail matters in module 24, where a run over three copies must not alert one student twice. The worker does not owe you ordering across jobs, so every job must be correct on its own.

The last reading is the API's independence. With the worker down, open the edition page, add a copy to the cart, and check out with a test card. Every route must behave normally. A route that waits for a queue event before responding is a route that has put the worker back inside the request, which undoes the whole module.

## Debug the three failures you will meet

A job that never appears has three likely causes. The enqueue call sits in a branch the request did not take, which is common when a publish and an edit share a route. The queue name in the route differs from the queue name in the worker by one character. Or the worker is connected to a different Redis database index than the API, which is easy to do when two environment files disagree.

A job that runs twice usually has an unstable id. Check the id string for a timestamp, a random value or a database generated id that changes on each request. Then check whether the work is being enqueued twice by the route itself, which happens when a loop or a retried request runs the enqueue before the write. The id catches the second case only if both emissions carry the same revision.

A job that runs late is not usually a queue problem. Check the worker concurrency, the duration of the previous job, and whether the processor is awaiting a slow external call with a long timeout. One worker with concurrency four and a mail provider that takes eight seconds per message will show a growing wait under a burst, and the fix is a timeout, not a bigger queue.

## Learning log

1. What were the response timestamp and the worker timestamp for one publish, and how did both change when you added a three second wait in the processor?
2. Which job id did the republish with an unchanged revision produce, and what did the waiting count do?
3. What was the measured delay between the first failure and the first retry, and how does it compare with the backoff in `docs/JOBS.md`?
4. What did the API return with the worker stopped, and what did the queue hold before the restart?
5. Which failure mode did you find hardest to diagnose, and which log line would have shortened the diagnosis?

The gate fails if the response waits for the worker, if a double publish sends two messages, or if a stopped worker loses a job. It also fails if `docs/JOBS.md` describes a policy the code does not implement, because a document that disagrees with the running system is worse than no document. Fix the code or fix the document before moving to the next module.
