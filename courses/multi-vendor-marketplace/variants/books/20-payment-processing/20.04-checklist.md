# Payment gate, double submit and test cards

Prepare Hana's Checkout with two pending Orders, one at North Street Books for 1,800 and one at Campus Shelf for 2,700, giving 4,500 minor units in test mode. Keep Bilal signed in on a second browser profile with the Campus Shelf copy in his own cart, and leave the API log and the Stripe CLI output side by side. Write the expected numbers before you pay: two Orders, two Listings sold, one intent id on all three records, one `paidAt` per Order that never changes after the first verification.

This gate is about evidence, not about a working demo. A payment that looks right on the success page can still have created a second charge, rewritten a sold copy, or accepted an unsigned body. Each section below asks for a stored record and a raw response, because that is what a reviewer can re-run when the browser lies.

## Pay once and read the records

Use a documented test card for the successful payment and watch the CLI print the event. Then read the database directly: the Checkout must be `paid` with `payment.paymentIntentId` set, both Orders must be `paid` with that same id, and each Listing must be `sold` with `soldCheckoutId` naming Hana's Checkout. Sum the OrderLine `priceMinor` values and the Campus Shelf fee and confirm the total equals the intent amount and the amount on the Stripe dashboard. A receipt that shows a different total from the intent means the route repriced something between the card form and the event.

Then close the tab before the return page loads and run the same flow on a fresh Checkout. The Orders must still become paid from the webhook alone. Open `GET /checkouts/:checkoutId` afterwards and confirm it returns `paid` without any client call having written it. This is the simplest way to show that the success page is a reader.

## Double submit the same intent

On a fresh Checkout, tap Pay twice in quick succession, or send the intent route twice with the same request key from a script. Expect one intent id, one client secret, and no second charge on the dashboard. Then confirm once and count the Orders, the paid transitions and the event records. The second request may return the stored intent with a 200, and that is the behaviour this build wants: the same payment, described twice.

Replay the succeeded event with `stripe events resend` and compare `paidAt` before and after. Both Orders must show the original instant, and the Listing `soldAt` must be unchanged. A replay that moves a timestamp or rewrites `paymentIntentId` fails the gate even if the totals still add up, because it means the transition is not conditional.

## Break the amount on purpose

Change the stored Checkout total to 4,100 in a test fixture while its OrderLines still sum to 4,500, then request a payment intent. The route must answer 409 with `amount_mismatch`, create nothing in Stripe, and leave both holds in place. Then build a signed event whose amount is 4,100 for an attempt stored at 4,500. The handler must return 200, write `needs_review`, and leave both Orders in `pending_payment`. Returning 500 here is also a fail, because Stripe will retry a mismatch until the dashboard is unreadable.

After both checks, restore the fixture and confirm a normal payment still works. A guard that blocks every payment is not a guard, and the gate should show the difference between a refused attempt and a broken route.

## Race the second buyer for one copy

This is the test a bookshop needs and a shop with many identical units does not. Let Hana start a Checkout that holds the Campus Shelf statistics guide, then let her hold expire while the intent stays payable. Bilal buys the same Listing with his own Checkout and succeeds, so the Listing is `sold` with `soldCheckoutId` naming Bilal. Now confirm Hana's stale intent with the test card.

Hana's event must not mark her Orders paid, must not move Bilal's Listing back to held or sold for her, and must leave her Checkout in `needs_review` with a reason such as `copy_no_longer_held`. Her attempt then waits for the refund path in S5. Check the Order records for both students afterwards: Bilal's `paidAt`, `paymentIntentId` and snapshot fields are unchanged, Hana's OrderLines keep their own `listingId` and price, and no Order carries an intent id that belongs to another Checkout. Run the two attempts in the reverse order as well, so the test proves an invariant rather than one lucky sequence.

## Check the boundary the browser cannot cross

Sign in as Bilal and request Hana's Checkout status and payment intent route. Both must refuse. Send an unsigned or wrongly signed webhook body and confirm a 400 with no writes. Send a correctly signed event whose `metadata.checkoutId` names Hana's Checkout but whose intent id belongs to a different attempt; the handler must ignore it and log the event id.

Inspect the raw JSON of the status route for the client secret, the Stripe secret key, hold ids and the other student's name. The browser needs the client secret once, at the intent route, for the buyer who owns the Checkout. It never needs another buyer's secret, and no response ever carries `sk_test_`. Confirm the API refuses to boot when `STRIPE_SECRET_KEY` is replaced with a value that is not a test key, then restore the test key.

## Gate checklist

- [ ] One Checkout, one PaymentIntent id, and the same id stored on every Order under that Checkout.
- [ ] The intent amount equals the Checkout total, which equals the sum of OrderLine `priceMinor` values plus each shop's fee, in integer minor units and one currency.
- [ ] A request body that carries `amountMinor` cannot change the created amount, and the test asserts both the rejection and the stored value.
- [ ] A stored total that disagrees with its lines returns `amount_mismatch` and creates no intent in Stripe.
- [ ] A second request for a payment intent on the same Checkout returns the same intent id instead of creating another.
- [ ] `stripe listen` output shows the event delivered, and `STRIPE_WEBHOOK_SECRET` in `.env` is the secret the CLI printed.
- [ ] A body with a bad signature returns 400 and changes no Order or Listing.
- [ ] Replaying the succeeded event leaves `paidAt`, `soldAt` and `paymentIntentId` unchanged on every record.
- [ ] The paid transition is conditional, and a matched count of zero is logged rather than treated as success.
- [ ] Each Listing moves from held to sold only while its `hold.checkoutId` matches the paying Checkout, and `soldCheckoutId` is written once.
- [ ] The stale intent race leaves the second buyer's sold copy untouched and puts the first Checkout in `needs_review`.
- [ ] The status page returns `paid` after a payment completed with the tab closed, and no client route writes paid state.
- [ ] The status and intent routes refuse another student's Checkout id.
- [ ] No response, log line or Git commit contains the secret key or a client secret for another buyer.
- [ ] The API refuses to start with a key that does not begin with `sk_test_`.
- [ ] `stripe --version`, the test card numbers used, and the date you checked them are recorded in the learning log.

## Learning log

1. Which value did the intent amount come from, and what happens to that value when North Street regrades or reprices the copy after Hana confirms? Name the stored field and the record it lives on.
2. How many intents existed after your double submit, and how did the second request find the first one? Quote the idempotency key and the conditional write that made that true.
3. What did the duplicate event delivery change, and what did it leave alone? Compare `paidAt` and `paymentIntentId` before and after, and explain why a 200 was the right response.
4. In the amount mismatch test, which record held the wrong number, which route refused, and why was the Stripe call never made?
5. In the second buyer race, which update matched zero for Hana, and what prevented her late payment from overwriting Bilal's sale? Include the filter you used and the state Hana's Checkout ended in.
6. Explain in three sentences why the success page cannot be the record that a payment happened, and name the two server facts that can.

A passing gate leaves four artefacts behind: the CLI log with event ids, the test run that covers the double submit, the mismatch and the race, the stored records for both students, and the row of test card numbers with the date you verified them. Save them beside the module so a mentor can re-run the same commands without resetting the database. Screenshots of a green card form are not evidence of any of this.

Two honest limits belong in the write-up. The refund for a late success is not built here, so a `needs_review` Checkout is a correct ending for this module rather than a finished resolution. And live keys have never been used, so nothing in this gate proves production behaviour; it proves that the server, not the browser, decides what a payment means, which is the promise of the module.
