# Browse editions gate

The gate is one page of editions, one card read against the fixtures by hand, and one filtered copy list. Use the seeded catalogue: three shops, the College Algebra edition `9781938168383`, and enough editions that a page of twenty is a real page rather than the whole collection. If your seed has fewer than twenty editions, add fixtures until it does, because a query count on a page of three proves nothing about the endpoint a student will use.

Write the expected summary before you run anything. For `9781938168383` the fixture set should give Acceptable at 1,600 with one copy, Good at 2,300 with two copies from two shops, and Very Good at 3,100 with two copies from two shops. If your own seed numbers differ, write your numbers down and check the response against them. The habit matters more than the values.

## Count the queries before you believe the page

Turn the counter on, request page one with the default page size, and record the number. Then switch to the aggregation, request the same page with the same filters, and record it again. Keep both numbers and the fixture description in the log. A before and after taken on different data is not a measurement, and a mentor will ask.

The baseline should be in the dozens. One query for the editions, one per edition for its copies and roughly one per copy for a shop name, multiplied across twenty cards. If your baseline is three, your loop is not running or your page is empty, and you should fix the fixtures before you fix the code.

The target is three round trips: the count, the pipeline and one spare. Six is acceptable if you can name what each trip does and why it earns its place. Nine is a sign that part of the work drifted back into JavaScript, usually a `populate` inside a map.

## Read one card against the fixtures

Find the College Algebra card in the response and read it line by line. The shared facts should appear once: title, authors, edition label and ISBN. The offers should be one row per grade with available copies, sorted by rank from best to worst or the reverse, and each row should carry the grade code, the lowest price, the copy count and the shop count.

Check the arithmetic by hand. Two Good copies from two shops means a count of two and a shop count of two. If the same shop has both copies, the shop count must be one, and that case belongs in your fixtures because it is the normal case for a bookshop with two copies of the same edition. A summary that reports two shops when there is one is a summary a student will use to plan a trip she does not need to make.

Now break it. Mark the cheaper Good copy as sold and reload the page. The Good row must drop to 2,600 with a count of one, or disappear if that was the only Good copy in your fixtures. If the card still shows a lower price, the status filter inside the lookup is missing, and every other check in this gate is worth less until it is fixed.

Also confirm what is absent. No listing id, no defect note and no shop document should appear on the card beyond the summary. The card is a summary, and the detail belongs to the copy route. A response that carries full listing documents for twenty editions is the same N+1 problem wearing a different hat, measured in bytes instead of queries.

## Filter copies by floor and ceiling

Return the Good copy you sold in the previous section to `available` first, so the list below is the one the fixtures describe. Then request the copy list for the same edition with `minGrade=2` and `maxPriceMinor=3000`. The response must contain the Good copies at 2,300 and 2,600 and nothing else: the Acceptable copy is below the floor and the Very Good copy is above the ceiling. Both exclusions are the point, so test them in that order and note which one removed which copy.

Send `minGrade=9`, `minGrade=good`, `maxPriceMinor=-100` and `limit=500`. Each must come back as a 400 with `INVALID_QUERY` and a message naming the parameter. A route that passes `minGrade=9` straight into Mongo returns an empty list and tells the student there are no copies, which is a wrong answer dressed as a valid one.

Send `maxPriceMinor=2300` and confirm the 2,600 copy leaves the list. Then remove both parameters and confirm the full set returns, including the Very Good copy at 3,100 and the Acceptable copy at 1,600. The unfiltered list is what the edition page shows before a student sets anything, and it is the list that proves the filters are filtering and not just always applied.

## Paginate without repeating or skipping

Take the unfiltered copy list and page through it with a page size of two. Collect the ids across every page and compare them with a single request that returns all of them. The sets must be identical, with no duplicate and no missing copy. Then make two editions share a title and repeat the test on the edition list, because the sort key is where this breaks.

Change a price between two page requests and note what happens. The copy can move between pages, which is expected with offset pagination and worth stating in the log. What must not happen is a response that returns the same id twice within one page.

## Gate checklist

- [ ] The query count for page one is recorded before and after, on the same fixtures, and the after figure is three to six.
- [ ] The count query uses the same filter as the pipeline, so the total matches the pages a student can reach.
- [ ] The College Algebra card shows one offer row per grade with available copies, and the prices match the fixtures by hand.
- [ ] A sold or held copy changes neither the summary price nor the copy count on the next request.
- [ ] The card carries shared edition facts once, plus the summary, and no full listing or shop document.
- [ ] `minGrade=2` and `maxPriceMinor=3000` return the 2,300 and 2,600 Good copies and exclude the other two.
- [ ] Removing the filters returns every available copy of the edition, including the ones the filters excluded.
- [ ] Bad query parameters return 400 `INVALID_QUERY` with a message per parameter, and a limit above the maximum is clamped or refused.
- [ ] Paging through the copy list repeats no id and skips none, and the same holds for two editions that share a title.
- [ ] `explain("executionStats")` on the copy query shows an `IXSCAN` on the compound listing index with a small number of documents examined.
- [ ] The edition list query uses an index for its sort rather than sorting the whole collection in memory.
- [ ] `countDocuments` is not called once per edition, and no `populate` appears inside a loop in either route.
- [ ] The response size for a page of twenty cards is recorded and is small enough to load on a phone.
- [ ] Both routes work with the API started from a clean clone and the seed re-run, so a mentor can repeat the gate.

## Learning log

1. What was the query count for page one before the aggregation, what was it after, and which three queries replaced the loop? Name each one.
2. Read the College Algebra card aloud: which grade rows appear, what is the lowest price in each, and how many shops stand behind each row? Then say which fixture would change each number.
3. A sold copy disappeared from the summary. Which stage excluded it, and what would a student have seen if that stage had been missing?
4. With a Good floor and a 3,000 ceiling, which copies came back and which two were refused? Name the field and the operator that refused each one.
5. What did `explain("executionStats")` show for the copy query, and what would a `COLLSCAN` have told you about the index you declared?

## What a passing gate leaves behind

Four artefacts. The two query counts with the fixtures they were taken on. The saved response for the College Algebra card, with the numbers you checked by hand beside it. The saved response for the filtered copy list, plus the four 400 responses from the bad parameters. And the explain output for the copy query and the edition list, both showing an index scan.

Two honest limits belong in the write-up. Offset pagination means a copy can move between pages when a price changes mid-session, and the fix is a cursor or a snapshot, which this module does not build. And the summary is computed on every request, so the endpoint trades database work for freshness until module 22 adds a cache with an invalidation rule that names every write path.

Module 15 builds the screen a student actually uses. It reads the two routes you just proved, shows grade as a word and a rank rather than a colour, and puts the defects and photographs from module 13 next to the price. The gate there is a student journey, and it depends on this module's numbers being true.
