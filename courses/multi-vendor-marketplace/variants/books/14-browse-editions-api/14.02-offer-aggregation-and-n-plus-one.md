# Offer summaries, grades and the N+1 trap

Two routes carry this module, and both answer a question a student can phrase in one sentence. The list route asks which editions match this search and what each one costs by grade. The copy route asks which copies of this edition are available inside my grade floor and my price ceiling. Neither route may answer by loading documents in a loop, because a browse page is the most requested endpoint in a book marketplace and its cost per page is a design decision, not an accident.

Start by writing down the response you want. A card shows the shared edition facts once, then a list of offers, one entry per grade that has at least one available copy, each with the lowest price in minor units, the number of copies and the number of distinct shops. Nothing else on the card needs a listing document. That constraint is what makes a small number of queries possible.

## The browse contract

```js
// server/src/modules/editions/edition.routes.js (signatures only)
router.get("/editions", listEditions);                 // ?q= &page= &limit=
router.get("/editions/:id/copies", listEditionCopies); // ?minGrade= &maxPriceMinor= &page= &limit=
```

```ts
// the card the client renders, one per edition
type EditionCard = {
  id: string;
  title: string;
  authors: string[];
  editionLabel: string;
  isbn13: string;
  offers: Array<{
    gradeCode: "new" | "like_new" | "very_good" | "good" | "acceptable";
    gradeRank: number;          // 5 down to 1
    lowestPriceMinor: number;
    copyCount: number;
    shopCount: number;
  }>;
  lowestPriceMinor: number | null;   // null when no copy is available
};
```

Pagination defaults to page 1 and limit 20, and the server clamps limit to 50. Reject a page below 1, a non-integer limit or a limit above the clamp with a 400 and the code `INVALID_QUERY`, with one message per bad parameter. A browse route that silently accepts `limit=100000` is a route that will be abused by the first person who notices, and the failure looks like a database problem rather than an input problem.

Sort with a unique field at the end, for example title then id. Without it, two editions with the same title can swap places between requests, and a student paging forward sees one twice and never sees the other. The same rule applies to the copies route, where price then id is the stable order.

## Measure before you fix

Add a query counter before you write the aggregation. Enable it in development and in tests, count every `find`, `countDocuments`, `populate` and `aggregate` call, reset the counter at the start of each request, and expose the total on `res.locals.queryCount`. The audit module already has a logger you can borrow; the point is that the number comes from the application, not from reading the code and estimating.

Take the baseline with a seeded page of twenty editions that have two to three copies each. Write the number down. Then write the aggregation and take it again, with the same fixtures and the same page size. A before and after with different fixtures is not evidence of anything.

Three round trips is the target for a page. One for the total, one for the pipeline, and one spare for a lookup you add later without noticing. If your count is above six, one of the stages is not doing the work it claims.

## Match, group, lookup

The pipeline is four ideas in order. `$match` selects the editions the student asked for. `$sort`, `$skip` and `$limit` choose the page. A `$lookup` with a sub-pipeline collects the available copies of each edition and groups them by grade in one pass. A second `$lookup` resolves the shop names behind those summaries. Only the first three are shown in full below, because the shop join is the same pattern applied to an array of ids and you should write it yourself.

```js
// server/src/modules/editions/edition.service.js (skeleton, response mapper omitted)
const rows = await Edition.aggregate([
  { $match: editionFilter },                       // the same filter the count uses
  { $sort: { title: 1, _id: 1 } },
  { $skip: (page - 1) * limit },
  { $limit: limit },
  { $lookup: {
      from: "listings",
      let: { editionId: "$_id" },
      pipeline: [
        { $match: { $expr: { $and: [
            { $eq: ["$editionId", "$$editionId"] },
            { $eq: ["$status", "available"] },
        ] } } },
        { $group: {
            _id: "$gradeRank",
            gradeCode: { $first: "$gradeCode" },
            lowestPriceMinor: { $min: "$priceMinor" },
            copyCount: { $sum: 1 },
            shopIds: { $addToSet: "$shopId" },
        } },
        { $sort: { _id: -1 } },
      ],
      as: "offers",
  } },
]);
```

Three details decide whether this works. The first is the `$expr` inside the sub-pipeline, which compares the outer edition id with the inner copy's `editionId`. Mongoose will not cast types for you here, so if one side is a string and the other an ObjectId, the lookup returns empty arrays and every card shows no offers. Convert the outer id once, or keep both as ObjectId and test on real data.

The second is the status filter inside the lookup. Without it, sold, held, draft and archived copies all enter the summary, and the lowest price on the card belongs to a copy that is not for sale. This is the same failure as the price guidance in module 12, in a place where it is easier to miss because the test data looks plausible.

The third is the projection at the end. The response must not carry the listing documents that the lookup collected, only the summary. A `$project` that names the fields explicitly is also the place to compute `lowestPriceMinor` across grades and `shopCount` per grade, so the client renders numbers instead of loops.

## Indexes that let the group run once

The lookup runs once per edition on the page, so it needs an index that starts with `editionId`. Add status, grade and price after it, in the order the stage uses them.

```js
// server/src/modules/listings/listing.model.js
listingSchema.index({ editionId: 1, status: 1, gradeRank: -1, priceMinor: 1 });
```

The edition list itself needs its own index for search and sort: a text index on title and authors for the `q` parameter, and a compound index that supports the sort you chose. Run `explain("executionStats")` on both stages and look for `IXSCAN` with a small `totalDocsExamined`. A `COLLSCAN` on the listings collection means the compound index is missing, misordered or not built in the database you are testing.

Declaring an index in a Mongoose schema does not prove it exists. Check the collection's index list, the same way module 5 checked the unique ISBN index. A reviewer asking "what makes this fast" wants the index name and the explain output, not the word "indexed".

## Filtering copies by grade and price

The second route is simpler and gets its own validation. Parse `minGrade` as an integer from 1 to 5, `maxPriceMinor` as a positive integer, and reject anything else with a 400 and one field message per parameter. Then apply both to a single query so the database returns only acceptable copies.

```js
// server/src/modules/editions/copies.service.js (filter shape only)
const filter = {
  editionId,
  status: "available",
  ...(minGrade ? { gradeRank: { $gte: minGrade } } : {}),
  ...(maxPriceMinor ? { priceMinor: { $lte: maxPriceMinor } } : {}),
};

Listing.find(filter).sort({ priceMinor: 1, _id: 1 }).skip(offset).limit(limit)
  .populate("shopId", "name area pickupNotes");
```

Populating the shop name here costs one extra query and returns two in total for the page, which is a fair price for a filtered list where every card needs a shop name, a pickup area and a defect note. It is not the same situation as the browse list, where a loop over editions multiplied the cost. The difference is that this query already knows its rows.

Filtering in the browser is not an option, for two reasons. The response would carry copies the student has already excluded, which wastes the data she pays for, and the count in the response would describe a set she cannot see. The filter belongs in the query, and the count belongs to the same filter.

## The trade-offs, stated plainly

| Approach | Round trips for a page | Freshness | What it costs |
|---|---|---|---|
| Load editions, then copies in a loop | Dozens, growing with the page | Live | Simple code, linear cost, the trap |
| Populate copies onto editions | Three or four | Live | Cannot group by grade in the database |
| Aggregation with `$lookup` and `$group` | Two or three | Live | Pipeline complexity, type pitfalls |
| Stored summary field on Edition | One | Stale until every write updates it | Write amplification, sold copies on cards |
| Cached summary in Redis | One after the first hit | Stale until the TTL or a write | Invalidation work, module 22 |

The course takes the aggregation now. It is live, it groups in the place that has the data, and it makes the next module's cache a measurement rather than a guess. The stored field is the alternative to reject out loud: it is faster on read and it moves the grouping cost to every write path in the system, including the background worker that marks a copy sold, and one forgotten path shows a student a price for a book that has gone.

`$facet` is worth knowing as a smaller refinement. It runs the count and the page inside one pipeline, which takes the page from three round trips to two. Use it when the count query is measurably expensive, and keep the simpler pair of queries while you are still learning to read the pipeline.

## Two tests that fail first

```js
// server/tests/editions.browse.test.js
test("a page of 20 editions stays within four queries", async () => {
  const res = await request(app).get("/editions?page=1&limit=20");

  expect(res.status).toBe(200);
  expect(res.locals.queryCount).toBeLessThanOrEqual(4);
});
// currently 62: 1 edition query, 20 copy queries, 41 shop queries
```

```js
// server/tests/editions.summary.test.js
test("a sold copy does not set the summary price", async () => {
  // fixture: Very Good available at 3100, Very Good sold at 2400
  const res = await request(app).get("/editions?limit=20");
  const card = res.body.data.find((edition) => edition.isbn13 === "9781938168383");
  const veryGood = card.offers.find((offer) => offer.gradeCode === "very_good");

  expect(veryGood.lowestPriceMinor).toBe(3100);
  expect(veryGood.copyCount).toBe(1);
});
// currently 2400 with a count of 2
```

The first failure is a performance claim and the second is a correctness claim, and the gate needs both. A fast endpoint that advertises sold copies is worse than a slow one that tells the truth, because the student only finds out at checkout.

## Acceptance criteria

A page of twenty editions returns in at most four counted queries, with one card per edition, one offer row per grade that has available copies, and the shop count behind each row. A sold or held copy never appears in a summary or a copy list. A copy list with `minGrade=2` and `maxPriceMinor=3000` on the College Algebra edition returns the 2,300 Good copy and the 2,600 Good copy and nothing else. A bad parameter returns 400 with `INVALID_QUERY` naming the field. Paging forward and back with the same filters never repeats or skips an edition.

## Bridge to the gate

The gate asks for the numbers and the response side by side: the query count before and after, the summary checked against the fixtures by hand, the filtered copy list, and the explain output for both indexes. Module 15 builds the screen that reads these two routes, and it will show grade as text and rank rather than colour alone, because a student who cannot distinguish two shades of green still has to choose a copy.
