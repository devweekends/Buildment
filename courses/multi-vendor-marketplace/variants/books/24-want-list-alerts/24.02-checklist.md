# Want-list alert gate

Set up an exact Edition that has no eligible copy. Student A has an active want entry with a minimum grade of Very Good and a price ceiling; Student B has a different ceiling; Student C excludes a defect that the coming copy has. Show these entries through the authenticated API, not by editing the database after the test begins. A bookshop then publishes one Listing for that Edition. The gate proves which students should be alerted, why the third should not, and how retries remain safe.

## Run the matching path

Publish a Listing whose grade, defects and price satisfy A and B but not C. Observe one queued job for that Listing revision. Let the worker process it. Query the Alert collection: A and B should each have one alert, C none. Open A's inbox as A and see the edition, shop, copy grade, price at alert time and a link to the current offer. Open the same endpoint as B and confirm A's private want entry is not in B's response. A shop owner should not be able to enumerate the students waiting for its books.

Replay the job twice. The count and IDs of the two alerts must not change. Mark A's alert read, replay again, and confirm it remains read. The unique `(wantEntryId, listingId)` index must exist in the test database. A queue job ID can reduce redundant processing while the job is present, but it is not the permanent record of what the student was told. Show this by scheduling a new revision job for the same Listing after a markdown: the Alert count for that pair stays one.

## Test delayed supply and a price change

Stop the worker, then publish a second eligible Listing. The HTTP request that publishes it should complete without waiting for alert delivery. Restart the worker. Each eligible student receives one alert for the second physical copy, and no extra alert for the first copy. Next, publish a Listing initially above Student B's price ceiling, then mark down its server-owned price below the ceiling. The price-change job should find B's want entry and produce one new alert. A client-supplied “sale price” that never reached the database must not trigger an alert.

Open an alert after its Listing has sold to another student. The offer page should say the copy is unavailable and show an alternative or the still-active want entry. It must not say “reserved for you.” The notification process never changed inventory. A two-buyer checkout race should still be decided by the Listing hold, not by who received an alert first. This is an honest limitation to mention in the final demo.

## Learning log

1. Draw the query direction for a one-time reading-list search and for a new-Listing want-list job. Explain why indexing accepted Edition IDs helps the second direction.
2. Name the unique Alert key. Explain why retrying a queue job or lowering a price does not create a second alert for the same student and physical copy.
3. Describe a worker-down run and the observable result after restart. Which user action completed before the worker resumed?
4. Explain why the alert cannot guarantee a copy. Name the later operation that decides whether a buyer owns a hold at checkout.

Commit the want-list API, matching processor, indexes, inbox and tests. Save `explain()` output for the reverse Edition query and a worker-down log with the final alert IDs. If you cannot reproduce the denial of cross-student access or the replay leaves new unread copies of the same alert, the gate fails. Recheck authorization and the actual unique index before considering the capstone ready.

## Debug and recover

If Student B receives no alert after a qualifying markdown, inspect the saved price in integer minor units first. A changed number in React state does not trigger the worker. Next inspect the Listing revision job and worker log. Then query B's want entry for active state, accepted Edition IDs, grade floor, defect exclusions and price ceiling. The first failed condition should explain the miss. Add that case to an automated test before changing matching logic, so a fix for price does not accidentally make a wrong edition eligible.

If the worker created an alert but the inbox is empty, inspect the authenticated student filter and pagination cursor. Do not broaden the query to all alerts just to make one row appear; that would leak other students' reading needs. If the inbox shows an offer that sold after the alert, use the current Listing status and show an unavailable state with a path back to matching offers. A stale notification is not a reason to return a deleted Listing as available.

Repeat the worker-down sequence with a paused want entry. Publish a copy while the worker is stopped, pause the want, then restart. The worker should see the current paused state and send no alert. Resume the want and run the bounded catch-up job; if the copy is still available and eligible, one alert appears. Replay catch-up and verify the same Alert ID remains. This sequence tests state at processing time and persistence across downtime, the two points where a simple “send email when listing is created” implementation usually breaks.
