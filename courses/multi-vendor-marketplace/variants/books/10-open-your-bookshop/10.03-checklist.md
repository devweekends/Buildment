# Open-your-bookshop gate

This gate uses one fresh account that has never had a shop, one phone sized browser window and the network panel open. The account is the evidence, so create it at the start and do not reuse an owner who already has a shop from module 9. If the account already has a shop, the guard's most important branch is untestable and the rest of the gate proves very little.

Work at 360 CSS pixels wide for the whole pass, either in a device emulator or by narrowing a desktop window. A layout that passes at 1200 pixels tells you nothing about the device the owner actually holds, and the failures at 360 pixels are specific: a time input that pushes the page sideways, a save button that scrolls away from its error message, a row of links too small to tap.

## Prove the redirect, not the empty page

Sign in as the new owner and watch where the app goes. It must arrive at the setup page, and the network panel must show one request to the shop endpoint and nothing else. Then type `/shop/listings` into the address bar, confirm the redirect to setup carries the listings path in the `next` parameter, and confirm again that no listing request was sent. The console must be empty of 404s, because a 404 that arrives after a page has mounted is a redirect that happened too late.

Then do the same with `/shop` and `/shop/settings`. Three routes, one destination, three preserved `next` values. Replace one of them with a full address such as `?next=https://example.com` and confirm that the app ignores it and goes to the dashboard after creation, because a guard that trusts a query parameter is an open redirect.

Finish the create and land where `next` pointed. If you started from listings, you should now be on listings, empty and correct, rather than on a dashboard you did not ask for.

## Prove no second shop

Open `/shop/setup` again after the shop exists. The app must redirect to the dashboard and the create form must not render, not even for a frame. Then go back to the previous page with the browser's back button and confirm it does not bounce between the two. The redirect uses replacement navigation precisely so that the back button has nothing to return to.

Now test the double submit on a second fresh account. Throttle the network to slow, tap save twice quickly, and watch the network panel: exactly one create request, and the button disabled with a progress label between the first tap and the answer. If you see a 409 in the panel, the form sent twice, and the owner paid for it with a message that reads like a failure after a success.

If a 409 does appear for another reason, for example because the same account was created in a second tab, check that the app recovers: the provider should refetch, move to the dashboard and show a short message rather than a red form.

## Prove the hours, on a keyboard

Fill the hours with a normal week and one early close: Friday open from 09:00 to 13:00, Saturday closed. Submit with six days only, then with Friday open and no closing time, then with a close time before the open time. Each attempt must come back with a message beside the hours, naming the day, and the form must keep every value the owner typed. Focus must land on the first invalid control so that a screen reader user hears the problem rather than the page title.

Then clear the mouse for the rest of the journey. Tab from the top of the page to the save button without touching a pointer, operate the closed switch and both time inputs for one day, and submit. If any control needs a hover to reveal it, or focus disappears behind a sticky element, fix it before recording the gate. Two checks make this concrete: the focus ring must be visible on every control you tab to, and the tab order must follow the visual order of the page.

## Prove settings and persistence

Open settings, change the pickup notes to a sentence about the side entrance and the exam week hours, save, and reload the page. The values must still be there, because they came from the server and not from component state. Then open the public shop address in a private window with no token and confirm the same sentence appears on the public page, which proves the write reached the record students read.

Try to change the address while the shop has no copies and confirm the old address still resolves. Create any copy for the shop, or use the seed, then try again and confirm the address field is disabled with the locked explanation. A disabled control with a visible reason is honest; a control that looks editable and returns a conflict is not.

Finally, drop the connection, reload a page inside the shop area, and confirm the retry screen appears instead of a setup form. Reconnect and retry, and the shop pages must come back without a second create.

## Gate checklist

- [ ] The account used had no shop before the first request, and the network panel was open for the whole pass.
- [ ] Signing in lands on setup, and no request to a listings or dashboard endpoint fires.
- [ ] Typing `/shop/listings`, `/shop` and `/shop/settings` each redirect to setup with the path preserved.
- [ ] `?next=https://example.com` is ignored and the app lands on the dashboard after creation.
- [ ] After creation the owner reaches the preserved destination rather than a fixed page.
- [ ] Visiting `/shop/setup` with a shop redirects to the dashboard and the form never mounts.
- [ ] The back button after that redirect does not bounce between setup and the dashboard.
- [ ] Two quick taps produce one create request, one shop and no visible 409.
- [ ] A deliberately injected 409 moves the app to the dashboard with a short message.
- [ ] Six days, a missing close time and a reversed range are each refused with a message naming the day, and every typed value survives.
- [ ] Focus moves to the first invalid control after a refused submit.
- [ ] The whole create journey completes with the keyboard only, in visual order, with a visible focus ring on every control.
- [ ] The journey completes at 360 pixels with no horizontal scrolling, and every button is at least 44 pixels tall.
- [ ] Settings shows saved values after a reload, and the change appears on the public shop page with no token.
- [ ] The address field is disabled with a reason once the shop holds a copy.
- [ ] An offline reload shows a retry screen and not the setup form, and reconnecting restores the shop pages.
- [ ] A student account is refused by every route in the shop area.

## Learning log

1. Which route did you type directly, what did the address bar show after the redirect, and what did the network panel show? Name the requests that did not fire.
2. What did the `next` parameter contain when you were redirected from `/shop/settings`, and what happened when you replaced it with a full address?
3. How did the form behave when you tapped save twice on a slow connection, and what prevents the second request in your code?
4. Which validation rule on the hours was hardest to write a message for, and where exactly does that message appear on the page?
5. Which control failed your keyboard pass first, and what did you change to fix it?
6. What does the app show for an offline reload inside the shop area, and how does that differ from the answer for an owner with no shop?

## What a passing gate leaves behind

Four pieces of evidence. A short screen recording or three screenshots of the 360 pixel journey, including the setup form with a field error and the retry screen. The network panel captures for the direct URL and the double tap. The public shop page opened without a token, showing the pickup notes the owner saved. And the learning log with the six answers.

Two honest limits go in the write-up. The gate proves the route guard, not the shop data: a shop created with a misspelled name and wrong hours passes every check here, because the correctness of a shop's facts is the owner's to decide. And the 360 pixel pass is a person with a pointer and a keyboard, not a real device with a real camera notch and a real thumb, so the plan is to re-run the journey on a phone before the demo in week two.

Do not delete the fresh account. Module 11 adds editions and the first listing form inside this frame, and a shop owner who is one minute old is the best tester of every screen that follows.
