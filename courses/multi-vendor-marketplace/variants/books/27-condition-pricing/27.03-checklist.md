# Pricing gate and audit trail

This gate is about four pieces of evidence, and a working screen is none of them. Have the API log, the worker log, the MongoDB shell and the Stripe CLI open at the same time before you start, and note the clock you are using. A price gate that passes only because nothing was aged and nothing raced has proved nothing.

Bring a seeded shop with an active pricing rule, an aged copy the schedule will move, a student with a want entry whose ceiling that copy will cross, and a checkout holding one copy. Add a deliberate manual clearance copy priced below its floor. That last fixture is the one that turns a plausible job into an honest one, because a job tested only against ordinary prices never meets the case that matters.

## Prove the total on the server

Start with the money. Put two copies in Hana's cart, read the total the page displays, and then change that number in the cart fixture while leaving the OrderLine snapshots alone. Request a payment intent. The route must answer 409 with `amount_mismatch`, create nothing in Stripe, and leave both holds in place. Then restore the fixture and repeat with a request body that also carries `totalMinor`. The route must refuse the body, or ignore it while still computing from the snapshots, and the created intent amount must equal the sum of the OrderLine prices plus each shop's fee.

The second half of that check is the one learners skip. A route that quietly strips an unknown field and charges the correct amount is acceptable. A route that reads the field is not, and a status test alone cannot tell them apart. Assert the stored `amountMinor` on the attempt, then open the Stripe dashboard and read the amount on the intent. Three numbers must be identical: the sum of the OrderLine snapshots, the stored attempt amount, and the intent in the dashboard.

Then make the market move under a stale page, which is the accident this rule exists for. Load the checkout, leave the tab open, and run the markdown job for that shop while the copy sits in the cart. If the copy's price changes before the snapshots are written, checkout uses the new price and the student sees it first; if the snapshots already exist, the intent keeps its frozen amount and the student pays what she agreed to. Say in your log which of the two happened and which record proved it.

## Read the audit instead of trusting the dashboard

Run the markdown job twice for one shop and compare the collections between runs. The first run should write one `PriceChange` row per copy that actually changed. The second run should write none, because every target now equals the stored price and the conditional update matches nothing worth writing. Count the rows before and after and write both counts down.

For each row, check that `fromPriceMinor` equals the previous `priceMinor`, that `toPriceMinor` equals the current one, that `source` is `markdown`, that `jobId` names the BullMQ job, and that `actorUserId` is null. A row with a null `fromPriceMinor`, or two rows for the same change, means the writer runs in the wrong place. Query the shop's history route afterwards and confirm it returns the same sequence through the API, scoped to the authenticated owner.

Now read the arithmetic from the rows rather than from the code. Pick the aged copy and confirm that `toPriceMinor` matches the reference times the grade share times one minus the total elapsed drop, until the floor binds. If the copy is at 1,305 where the floor is 1,350, the row proves the clamp is missing and the gate fails. If the row says `FLOOR_REACHED` and the stored price is 1,350, the promise held.

## Force the floor to fail

The interesting case is the one you build on purpose. Take the copy that is already at its floor and age it another thirty days. Run the job. The price must not move, no row may be written, and no alert may fire. That is the behaviour that makes an automatic markdown safe to leave switched on overnight.

Do the same for the manual clearance copy priced at 900 with a 1,350 floor. A job that clamps the value up to the floor has just raised a price, which is worse than lowering one. The copy must stay at 900 and the audit must stay silent, because nothing happened.

Then break the job on purpose and watch the test catch it. Remove the floor clamp from the processor, run the same fixture, and read the failure. The received value is the computed target with no clamp, so the difference between the two numbers is how far below the shop's own floor it would have sold. Restore the clamp afterwards and confirm the test passes again. A guard that blocks every markdown is not a guard, so the gate must also show a normal aged copy dropping by the expected amount on the same run.

## Show the re-match after a drop

Hana's want entry has a ceiling the copy exceeds before the run and satisfies after it. Trigger the job and wait for the worker. Exactly one alert should appear in her inbox, linked to that copy, and none should appear for a student who was already alerted about the same copy under Module 24's rules.

Replay the `listing.published` job the price change emitted and confirm the alert count and the alert ids do not change. Stop the worker, run the job again on a second copy that also crosses the ceiling, and restart. The alert must arrive once after the restart, with the API having answered immediately. That sequence is the same proof as Module 24's worker-down test with a pricing cause, and it is the evidence the Week 4 demo depends on.

If no alert appears, check three things in order: whether the price actually moved in the database, whether a `listing.published` job with a new revision exists for that change, and whether the want entry is active with the ceiling you think it has. Do not widen the matcher to make one alert appear. A matcher that ignores the ceiling will alert every student on the platform for every copy.

## Refuse a burst on both routes

Two routes on Hamesh invite automation. `GET /editions/lookup` is a cheap read that a script can hammer with guessed ISBNs, and `POST /me/wants` creates standing work for the worker. Both need a limit that a real student never meets.

```js
// server/src/modules/limits/rate-limit.middleware.js (partial)
export function limit({ bucket, max, windowSeconds }) {
  return async function rateLimit(req, res, next) {
    const key = `rl:${bucket}:${req.user.id}`;
    const hits = await redis.incr(key);
    if (hits === 1) await redis.expire(key, windowSeconds);
    const ttl = await redis.ttl(key);
    if (hits > max) {
      res.set("Retry-After", String(Math.max(1, ttl)));
      return res.status(429).json({ reason: "TOO_MANY_REQUESTS", retryAfterSeconds: Math.max(1, ttl) });
    }
    next();
  };
}

router.get("/editions/lookup", limit({ bucket: "isbn", max: 30, windowSeconds: 60 }), lookupByIsbn);
router.post("/me/wants", limit({ bucket: "want", max: 10, windowSeconds: 3600 }), createWant);
```

Key by the authenticated user, not by address, because a campus shares one address and a student behind a shared connection should not inherit somebody else's block. `incr` and `expire` are two commands, so a process that dies between them leaves a counter with no expiry; either accept that the key lingers until the next flush or wrap the pair in one Lua script. When Redis is unavailable, log the counter miss and allow the request. Refusing every ISBN lookup because a cache is down is a worse outcome for a student on a weak connection than accepting a short burst.

Send thirty one lookup requests in a minute and confirm the last one is a 429 with a `Retry-After` header and a body a client can act on. Then wait out the window and confirm the same request succeeds, because a limit that never releases is an outage. Send eleven want-list creations and confirm the same shape. Use a second account to prove the key is per user rather than global.

## What this gate does not prove

The audit does not prove that a price was fair, only that it was recorded. A rule with a wrong share still writes clean rows. Nothing here prevents a shop owner from pricing a Good copy at ten times the market rate, and nothing should, because that is a commercial decision rather than a defect.

The re-match proves that one eligible student heard about one copy. It does not prove the copy was still available when she opened the alert, and it does not reserve anything. Module 26's hold remains the only thing that decides who buys a copy, and this gate leaves it untouched.

Finally, the schedule has run only against backdated fixtures. Whether a nightly run at 03:00 finishes before the first student of the day opens the app is an operational question you will answer on the live deployment in Module 25, with a log line and a duration, not with a passing test.

## Gate checklist

- [ ] The created PaymentIntent amount equals the sum of OrderLine `priceMinor` values plus each shop's fee, in integer minor units and one currency.
- [ ] A checkout whose stored total disagrees with its lines returns `amount_mismatch`, creates no Stripe object, and leaves the holds in place.
- [ ] A request body carrying a total cannot change the created amount, and the test asserts the stored attempt amount rather than only the status code.
- [ ] The Stripe dashboard amount, the stored attempt amount and the OrderLine sum are the same three numbers.
- [ ] Two consecutive markdown runs write one `PriceChange` row per changed copy in the first run and none in the second.
- [ ] Every row has a `fromPriceMinor` equal to the previous price, a `toPriceMinor` equal to the current one, a `source`, a `jobId` for scheduled changes and a null actor.
- [ ] The aged copy that reaches the floor stores the floor value with `reasonCode: FLOOR_REACHED`.
- [ ] Removing the clamp makes the floor test fail with the unclamped target, and restoring it makes the test pass.
- [ ] A copy priced at 900 by hand with a 1,350 floor stays at 900 and gains no audit row.
- [ ] A normal aged copy drops by the expected amount on the same run that skipped the two refused copies.
- [ ] The price drop that crossed a student's ceiling sent exactly one alert, and replaying the job sent none.
- [ ] A copy whose worker was down during the run sent one alert after restart, and the API answered before the worker logged.
- [ ] The thirty first ISBN lookup in a minute returns 429 with `Retry-After`, and the same request succeeds after the window.
- [ ] The eleventh want-list creation in an hour returns 429, and a second account is not affected by the first account's block.
- [ ] The pricing rule route refuses a second active rule for one shop through the unique index, not through a UI check.
- [ ] No response returns another shop's price history, and the history route filters by the authenticated owner.

## Learning log

1. Which two records hold a price, and why is the reference frozen on the copy rather than recomputed from the market each night? Name the spiral you avoided.
2. Give the three numbers from your payment check, name the record each came from, and explain what the route did when they disagreed.
3. For the copy that reached the floor, write the reference, the grade share, the total drop, the computed target and the stored price. Which value would the job have written without the clamp?
4. How many `PriceChange` rows did the first run create and how many did the second? Explain what the second run's conditional update matched and why that is a success rather than an error.
5. Which student received the re-match alert, what was her ceiling, and what did the count look like after the replay? Name the index that made the replay safe.
6. Which key did each rate limit use, what happened when you sent one request too many, and what did the second account prove?

Commit the rule model, the suggestion route, the markdown processor, the audit writer, the re-match enqueue, the limit middleware and the tests. Save the two run counts, the failing floor test output, the alert ids before and after the replay, and the 429 body with its `Retry-After` header beside them. If the intent amount and the server total can differ, or if a nightly run can cross a shop's floor, the module is not done, whatever the dashboard shows.
