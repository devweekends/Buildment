# Tables and documents for a shared catalogue

Two engineers model the same Monday morning. The first opens PostgreSQL and writes six tables with foreign keys and constraints. The second opens MongoDB and writes four collections, two of them with embedded arrays. Both can show Hana three copies of one edition. They break in different places, and the breaks cost different amounts of work.

This lesson builds both shapes in enough detail that the difference becomes a set of constraints rather than a matter of taste. Treat the relational version seriously. It is not a strawman, and in at least three places it is the better home for this catalogue. Knowing exactly which three is what makes the choice you commit in the next lesson defensible.

## The relational shape, table by table

The relational version starts with `works`, holding the title and the authors. An `editions` table holds one row per published form, with a foreign key to the work, a canonical thirteen digit ISBN, a nullable ten digit ISBN, the edition label, the format, the publisher and the year. A `shops` table holds the shop name, the area, the pickup notes and the owner user ID.

Then `listings` holds one row per physical copy, with a foreign key to its shop, a foreign key to its edition, a grade code, a grade rank, a defect summary, a price in minor units, a status and a nullable hold reference. A `reading_lists` table holds the student and the course code, and `reading_list_items` holds one row per required title with a grade floor and a price ceiling. Because one item may accept two editions, the many-to-many relation goes into `reading_list_item_editions`.

Orders split the same way. An `orders` table holds one row per shop per checkout, and `order_lines` holds one row per copy sold, with the snapshot columns written once at sale. The snapshot columns duplicate data on purpose, and a reviewer should read them as a copy of facts, not as a normalisation mistake.

```sql
create table editions (
  id            bigserial primary key,
  work_id       bigint not null references works(id),
  isbn13        char(13) not null unique,
  isbn10        char(10),
  edition_label text not null,
  format        text not null check (format in ('paperback', 'hardback', 'pdf')),
  publisher     text,
  published_year smallint
);
create unique index editions_isbn10_key on editions (isbn10) where isbn10 is not null;

create table listings (
  id          bigserial primary key,
  shop_id     bigint not null references shops(id),
  edition_id  bigint not null references editions(id),
  grade_rank  smallint not null check (grade_rank between 1 and 5),
  price_minor integer not null check (price_minor >= 0),
  status      text not null check (status in ('draft', 'available', 'held', 'sold', 'archived'))
);
```

Read the declarations as guarantees you do not have to write code for. The unique ISBN stops two rows for one published edition. The partial unique index does the same for the optional ten digit field without colliding on rows that have none. The two foreign keys stop a copy from pointing at a shop or an edition that does not exist. The checks stop a negative price and a grade rank outside the scale.

## The document shape, collection by collection

The document version groups fields by what is read together and what is written together. A `Work` document holds the title and the authors. An `Edition` document holds the work reference, the canonical ISBN, the optional ten digit ISBN, the edition label, the format and the publisher. A `Shop` document holds the owner and the pickup details. A `Listing` document holds the shop reference, the edition reference, the grade, the defects, the photo references, the price and the status with a hold subdocument.

The reading list becomes one document per student, with an array of items. Each item carries its own ID, the label shown to the student, the accepted edition IDs, the grade floor and the price ceiling. The order becomes one document per shop per checkout, with lines embedded, each line carrying its own snapshot fields.

```js
// Shape only. Validation, error handling and the photo pipeline come later.
const EditionSchema = new Schema({
  workId: { type: Schema.Types.ObjectId, ref: 'Work', required: true },
  isbn13: { type: String, required: true },
  isbn10: { type: String },
  editionLabel: { type: String, required: true },
  format: { type: String, enum: ['paperback', 'hardback', 'pdf'], required: true },
  publisher: String,
  publishedYear: Number,
}, { timestamps: true });
EditionSchema.index({ isbn13: 1 }, { unique: true });
EditionSchema.index({ isbn10: 1 }, { unique: true, partialFilterExpression: { isbn10: { $type: 'string' } } });

const ListingSchema = new Schema({
  shopId: { type: Schema.Types.ObjectId, ref: 'Shop', required: true },
  editionId: { type: Schema.Types.ObjectId, ref: 'Edition', required: true },
  gradeCode: { type: String, enum: ['acceptable', 'good', 'very_good', 'like_new', 'new'], required: true },
  gradeRank: { type: Number, min: 1, max: 5, required: true },
  defectFlags: [String],
  defectNote: { type: String, maxlength: 400 },
  photoUrls: [String],
  priceMinor: { type: Number, min: 0, required: true },
  currency: { type: String, default: 'ILS' },
  status: { type: String, enum: ['draft', 'available', 'held', 'sold', 'archived'], default: 'draft' },
  hold: { checkoutId: Schema.Types.ObjectId, expiresAt: Date },
}, { timestamps: true });
ListingSchema.index({ editionId: 1, status: 1, priceMinor: 1 });
```

The unique ISBN index survives the move from tables to documents, and so does the partial filter. What does not survive is the pair of foreign keys and the two checks. MongoDB can validate a document shape with a JSON schema validator, and the course asks you to add one, but the validator does not confirm that `editionId` names a real edition. Nothing in the database stops a bug from writing a copy that points at a catalogue page that was never created.

## Where the relational shape is simply better

The first honest win is referential integrity. In PostgreSQL a copy cannot point at a missing edition, and an edition cannot point at a missing work. Deleting a work with editions under it is refused unless you say what should happen to them. In MongoDB the application owns every one of those checks, on every write path, including the seed script, the admin correction route and the one-off repair you run at midnight. If one path forgets, the catalogue collects a copy that renders as an empty card and a reading-list match that points nowhere.

The second win is the check constraint. `grade_rank between 1 and 5` and `price_minor >= 0` are declarations the database enforces for every client, every script and every future service. In MongoDB the equivalent is a validator that must be attached to the collection and kept in step with the schema, plus a server-side grade map, plus tests that prove the validator is actually installed in the database you deployed. Module 5 asks for exactly that proof, and the request exists because the guarantee is weaker.

The third win is reporting across the many-to-many relation. A question such as "how many students accept this edition on a reading list" is one join in PostgreSQL. In MongoDB the accepted edition IDs live in arrays inside reading-list documents, so the same question is a match on an array field and an aggregation to count distinct students. It is fast with a multikey index, and Module 24 uses exactly that index for want-list matching, but the query is longer and a beginner is more likely to write it wrongly.

## Where the document shape is simply better

The edition page is the read that matters most. A student opens one edition and needs the shared title, the ISBN, the format, and then each available copy with its grade, defects, photo and price, plus the shop name and pickup area. In the document store that is one read on the edition, one indexed read on listings by edition and status, and one read on the shops by ID. In the relational store it is a four way join with a group by, which the planner handles well and which a beginner reads slowly.

The order snapshot is the second win, and it is not about performance at all. An order line is a historical record of facts that belonged to other records at one instant. In a document store the natural shape is a line with the fields copied in, and reading a receipt is one read with no join that could accidentally pick up today's price. In the relational shape you can do the same thing with snapshot columns, and good teams do, but the normalised instinct pulls the other way and a reviewer has to check that the line did not keep a foreign key to a mutable price.

The third win is the reading list as a unit. A student's list is read whole by one screen, edited one item at a time, and has a natural cap of a handful of items. Storing it as one document with an items array means one read and one write per edit, no join table, and no risk of an item existing without its parent. The array also makes the grade floor and price ceiling sit next to the editions they qualify, which is where a reader looks for them.

  <TraceStep actor="API" label="Compose one header and three offers" detail="Shared fields once, copy fields per offer, no price on the edition" />
  <TraceStep actor="API" label="Claim one copy at checkout" detail="Conditional update from available to held on a single listing document" status={200} />
  <TraceStep actor="DB" label="Repeat the same claim" detail="Filter no longer matches, so the second student gets a conflict" status={409} />
</TraceRequest>

The fifth and sixth steps are the ones worth keeping. The claim is a conditional update on one document, filtered on the current status and the hold expiry, and the matched count tells the caller whether it won. PostgreSQL does the same thing with an update that filters on status and returns the row, so neither store wins here. What matters is that the claim targets the copy, never the edition, because an edition has no status to change.

## The near-miss to avoid

A tempting middle design embeds listings inside the edition document. The edition page then needs exactly one read, and the diagram looks tidy. Three problems arrive with it. The array grows without a known limit, because any shop can add a copy at any time. Every shop that adds a copy writes the same shared document, so two shops adding copies at the same moment contend on one record. And the claim becomes a positional update inside an array, where the filter has to identify one element and the code has to prove it changed exactly one.

The second near-miss goes the other way and copies the edition fields onto the listing. A title and an ISBN on every listing look convenient, and they remove a read. They also create two sources of truth, and the day an admin corrects the shared title, every listing still shows the old one. If a denormalised field is genuinely needed for search later, declare it as derived, name the code that refreshes it, and test that it does not drift.

## What would change the answer

Three conditions would move Hamesh to a relational store, and you should be able to name them in a viva. A hard requirement that the database itself refuses a copy that points at a missing edition is the first. A daily reporting surface that joins students, reading lists, editions and shops is the second. A multi-table money path, where an order, its lines and a payment record must commit together, is the third.

None of those is in the core path as this course builds it. The core path needs one canonical edition per ISBN, copies owned by shops that are read as a group, a reading list read as one document, an order that freezes its own facts, and one copy that can be claimed exactly once. That is the case you will write down next, with one row per decision and one honest cost beside each benefit. The next lesson turns the comparison into the decision record and the first ERD.
