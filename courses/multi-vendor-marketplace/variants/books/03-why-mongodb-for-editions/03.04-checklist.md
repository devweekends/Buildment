# Catalogue model decision gate

The draft is written and both tests have run at least once. This gate is not a summary of the module. It is the point where a second person reads your decision and tries to break it with the questions a reviewer will ask when you defend the capstone.

Bring three things to the conversation: `docs/erd-draft.md`, the terminal output from both tests, and your answer to one question. Why does the copy own the price? If the answer mentions performance or popularity, go back to lesson 3.1 and rebuild it from Hana's three copies.

## Defend three claims

The first claim is that the edition is shared. A reviewer will ask what happens when the shop that typed the ISBN first closes. Nothing should happen to the edition: it stays, the other shops keep selling their copies, and Hana's reading list keeps pointing at it. If your draft makes the edition a child of the shop, the arrow is wrong and the answer collapses.

The second claim is that the copy is owned and sell-once. The reviewer will ask who may change a defect note, and the answer names the shop ID stored on the listing, compared with the shop that owns the signed-in account. The follow-up is harder: what stops two students buying the same copy? The answer is a conditional update on one listing document, filtered on the current status, with the matched count deciding the winner. A draft that says the edition is marked sold has failed here, because an edition can have several copies and only one of them went.

The third claim is the honest one. The reviewer will ask where PostgreSQL would be the better home, and you name referential integrity and the check constraints, then say what Hamesh does instead and what that costs. A learner who cannot name the loss has compared nothing, only repeated a preference.

## Check the draft against Hana's three copies

Open the worked row and walk through it aloud. One work, one edition, three listings. North Street Books holds Acceptable with handwriting at 1,600 minor units. Campus Shelf holds Good with a clean interior at 2,300. Corner Books holds Very Good at 3,100. Hana's list item accepts that edition and asks for Good or better, so the matcher must return two offers and exclude the first with a reason.

Then change one input and see whether the draft still answers. Campus Shelf sells its Good copy and replaces it with an Acceptable copy at 1,500. The edition record must not change, the other two listings must not change, and Hana's list item must still exclude the new copy on grade rather than on price. If your draft cannot show a cheap copy being excluded on condition, the grade does not live where it should.

Change a second input. Corner Books withdraws its copy and archives the listing. The edition stays, the archived listing stays as history, and Hana sees one eligible offer instead of two. A draft that deletes the listing on withdrawal has no way to explain the archived copy to a later reviewer, and the order that once sold it points at a record that no longer exists.

## Name the rule the database keeps and the rule it does not

Show both test outputs side by side, because together they are the decision in one page. The duplicate-ISBN test fails with a unique index error, which proves the store supplies edition identity without application code. The orphan-listing test passes only after your service check loads the edition, which proves the store supplies no reference integrity at all.

A reviewer will ask the obvious follow-up: what happens on the day someone writes a repair script that forgets the check? The strong answer is that the script calls the same function as the route, and that the function is tested. The weak answer is that it will not happen. Write the strong answer into the draft, next to the table row, so the next person to run a repair sees it.

## What this gate does not prove

The draft is not a schema. It has no validators, no defaults, and only the indexes your two tests touched. Do not tell a reviewer that the model works. Say what the draft decides and which later lesson proves each part of it.

Module 5 turns the shapes into Mongoose models and seeds three shops with copies in several grades, and that seed is where a wrong reference becomes visible on a page. Module 11 proves that two shops typing the same ISBN end with one edition, and Module 14 proves that one edition page reads its offers in a bounded number of queries. Module 19 proves the snapshot under a regrade. Until then, the strongest honest sentence is that the decision is recorded and two database rules have been demonstrated, one kept by the store and one kept by the service.

## Gate checklist

- [ ] `docs/erd-draft.md` opens with a decision paragraph that names one benefit and two costs.
- [ ] The decision table has one row each for edition identity, the copy link, the reading list, the order snapshot and the copy claim.
- [ ] The ERD labels ownership arrows and reference arrows with different verbs.
- [ ] No shared record in the draft carries a price, a condition grade or a count of copies.
- [ ] The orphan-listing test fails before the service check exists and passes afterwards, with both outputs saved.
- [ ] The duplicate-ISBN test fails with error 11000 from the unique index.
- [ ] The draft names the write paths that create a listing and the one function they all call.
- [ ] The open questions section names at least two unsolved problems, including where pickup instructions live.
- [ ] The worked row lists one work, one edition, three listings and three shops with their IDs.
- [ ] No connection string, token or password appears in the commit.

A missing box is not a documentation problem. If the price is on the edition, move it. If the order line reads today's listing, freeze it. If the orphan test passed on the first run, your service already had the check and you have not seen the gap yet.

## Learning log

Answer these in `docs/learning-log.md` with a field name or a command output for each sentence.

1. Which record owns the 2,300 minor unit price, and which two records must not carry it?
2. Which guarantee does the unique index on `isbn13` provide, and which guarantee does it not provide about the record it protects?
3. What did the orphan-listing test show before your service check, and which function now prevents it on every write path?
4. When would a foreign key from the copy to the edition serve Hamesh better, and what would have to change for that to matter?
5. Which reading-list question would be a join in a relational store, and why does the course accept the document version here?

The first answer should name the Listing and say why the Edition and the Work are wrong homes. The fourth should name a concrete failure, not a general preference. If the fifth answer is only "arrays are easier", say which query the array makes longer and which index makes it fast enough.

Commit the gate evidence with the learning log entries. Module 4 connects the database behind a validated configuration module, and Module 5 turns this draft into schemas and a seed. Keep the draft where those lessons can point at it, and reopen it when a later lesson disagrees with it rather than letting two versions drift.
