# Upload the real copy, require evidence below Very Good

A photograph is the only part of a used copy that a buyer can inspect before paying, so the upload route carries more weight than its size suggests. It has to accept a file from a phone, prove that the shop owns the copy before spending anything on storage, keep at most four photos per listing, and refuse to publish a low grade that has no photograph at all. It also has to change photos without breaking an order that already points at one.

Start with the contract. Two routes handle the write side, and both are scoped to the shop that is signed in. The publish route stays the one from module 12, but it gains a rule. Everything else in this lesson is the detail behind those three statements.

```js
// server/src/modules/listings/listing.routes.js (shape only)
router.post("/listings/:id/photos", requireAuth, requireRole("shop"),
  upload.single("photo"), addPhoto);
router.delete("/listings/:id/photos/:photoId", requireAuth, requireRole("shop"), removePhoto);
```

The delete route uses the photo subdocument id, not the storage public id. A Cloudinary public id looks like `hamesh/listings/665f.../cover`, and the slashes would be read as path segments by Express, which turns a delete into a 404 and a confusing afternoon. Address the subdocument and let the server read the public id from the stored record.

## Add photo subdocuments to the Listing

Photos belong on the Listing as an ordered array of small subdocuments. Subdocuments give each photo a stable `_id` for the delete route, a `createdAt` for sorting, and a shape that can grow a caption later without a migration. Keep the array on the copy and never on the shared Edition, because the damage in the picture belongs to one object.

```diff
// server/src/modules/listings/listing.model.js
+const photoSchema = new Schema(
+  {
+    url: { type: String, required: true },
+    publicId: { type: String, required: true },
+  },
+  { timestamps: { createdAt: true, updatedAt: false } }
+);
+
+  photos: {
+    type: [photoSchema],
+    default: [],
+    validate: {
+      validator: (photos) => photos.length <= 4,
+      message: "A copy holds at most four photographs",
+    },
+  },
```

The validator is a safety net, not a concurrency control. Two uploads that arrive at the same moment can both read a listing with three photos, both pass the check in application code, and both write, leaving five. The fix is to make the count and the write one database operation, so MongoDB evaluates the condition against the document it is about to change.

```js
// server/src/modules/listings/photo.service.js (the guard, not the whole function)
const updated = await Listing.findOneAndUpdate(
  {
    _id: listingId,
    shopId,
    status: { $in: ["draft", "available"] },
    $expr: { $lt: [{ $size: "$photos" }, 4] },
  },
  { $push: { photos: { url: uploaded.secure_url, publicId: uploaded.public_id } } },
  { new: true }
);
```

A null result from that call can mean four different things: the copy is gone, it belongs to another shop, it is frozen, or it already holds four photographs. The route has to tell them apart before it responds, because "this copy is sold", "this copy is not yours" and "this copy already has four photographs" are three different sentences on screen. Re-read the listing with only the id to decide which, and keep the ownership answer a 403.

## Where a copy may change its evidence

The state machine below is the rule that protects a buyer. Photographs can be added, replaced or removed while a copy is a draft or available. The moment a checkout holds it, the set is frozen, because a student has already agreed to buy what the photographs show. A sold copy keeps the same set forever, because the order snapshot points at one of those URLs.

Read the two self transitions as the only writing states, and the two labelled exits as the lock. The gate tests both: a replace on an available copy succeeds and destroys the old asset, and a replace on a sold copy returns 409 with the photo set unchanged.

## Check the shop before the bytes

Order the checks by cost and by consequence. Load the listing by id. If it does not exist, return 404. If it exists but its `shopId` is not the shop resolved from the signed-in user, return 403 before the upload helper is called, because a cross-shop upload that reaches storage has already spent quota and created a file nobody owns. If the status is held or sold, return 409. Only then read the file and stream it.

This ordering matters at the counter. A shop owner who has lost their session, or who has two shops open in two tabs, will eventually send a file to the wrong listing. The refusal has to arrive in a second, with a message that names the problem, and the API log should show a refused attempt rather than a successful upload and a rejected write.

File checks come after ownership and before storage: one file per request, an image MIME type, and a size limit you state in the interface. Five megabytes is a reasonable ceiling for a phone photograph and keeps a slow connection from looking like a broken app. The upload middleware enforces the size; your route maps its error to a 400 with `fields.photo`, not a 500.

## Refuse to publish below Very Good

The publish rule is one function with one input and a list of problems, so it can be tested without a database and reused by the status route and by any later bulk publish. The threshold is a named constant, because the number will be discussed by people who are not reading the code.

```js
// server/src/modules/listings/publish-rules.js
export const PHOTO_REQUIRED_MAX_RANK = 2;   // Good and Acceptable

export function publishProblems(listing) {
  const problems = [];
  if (listing.gradeRank <= PHOTO_REQUIRED_MAX_RANK && listing.photos.length === 0) {
    problems.push({
      field: "photos",
      code: "PHOTO_REQUIRED",
      message: "A copy graded Good or Acceptable needs at least one photo of the actual copy",
    });
  }
  return problems;
}
```

The status route calls it before the update, returns 400 with the first problem when the list is not empty, and otherwise performs the conditional draft-to-available update from module 12. One test proves the rule, and it fails on the code as module 12 left it.

```js
// server/tests/listings.publish.test.js
test("a Good copy cannot publish without a photograph", async () => {
  const res = await request(app)
    .patch(`/listings/${goodDraft.id}/status`)
    .set("Authorization", `Bearer ${shopAToken}`)
    .send({ status: "available" });

  expect(res.status).toBe(400);
  expect(res.body.error.code).toBe("PHOTO_REQUIRED");
});
// currently 200, and the copy appears in browse with a grade and no evidence
```

Add the mirror case in the same file: a Very Good copy with no photographs must publish, because the rule is a threshold and not a blanket requirement. Without that test, the next refactor will quietly require a photo from everyone, and shops will stop listing clean copies.

## Replace and delete without breaking a receipt

Replacing a photo is three operations in a fixed order: upload the new bytes, write the new pointer, destroy the old asset. The order is not arbitrary. If you destroy first and the upload fails, the listing has no photograph at all. If you write the pointer and the destroy fails, you leak one file and keep a working listing. The second failure is the one you want.

```js
// the order that keeps a listing usable (logging and rollback omitted)
const uploaded = await streamToStorage(buffer, listingId);
const updated = await Listing.findOneAndUpdate(
  { _id: listingId, shopId, status: { $in: ["draft", "available"] } },
  { $set: { photos: [{ url: uploaded.secure_url, publicId: uploaded.public_id }] } },
  { new: true }
);
if (!updated) {
  // held or sold: the new asset is an orphan from this moment
  await destroyAsset(uploaded.public_id).catch(logOrphan);
}
```

Deletion has one hard rule: never destroy an asset that an order line references. The order snapshot from module 19 stores the first photo URL, and a buyer opening a paid receipt months later should still see the copy they bought. That is why the freeze belongs in the update filter rather than in a comment. If the status is held or sold, the write does not match, and the route turns the empty result into a 409 with a message about a frozen photo set.

A shop that genuinely needs to record new damage on a sold copy has a different problem, and it needs a different tool. The dispute flow in the stretch lab attaches new evidence to the order without touching the sold listing. Keeping those two paths apart is the difference between a marketplace that respects its receipts and one where history is editable.

Orphaned assets are a small cost and a large signal. Log every destroy that fails with the public id, and write one note in your README about how a future cleanup job would find them by folder. A folder convention such as `hamesh/listings/{listingId}` makes that cleanup a prefix listing rather than a database scan.

## Configure storage once

Keep the cloud name, API key and API secret in environment variables, add them to `.env.example` with placeholder names and no values, and refuse to boot the server when one is missing. Module 4 built the config module that does this; reuse it rather than reading `process.env` inside the photo service. A secret that reaches a commit is a secret you must rotate, and rotation during a gate week is a waste of a day.

Use memory storage in the upload middleware and stream the buffer to storage. A temporary file on a server disk works on a laptop and fails on a platform with an ephemeral filesystem, which is exactly the bug that appears on deploy day and not before.

## Verify before the gate

Four checks belong in this lesson. Upload four photographs to a draft copy and confirm the Mongo document holds four small objects and no bytes. Send a fifth and confirm a 400 with `PHOTO_LIMIT` and still four stored photos. Try to publish the Good draft with no photograph and confirm the refusal, then add one and publish. Ask the second shop to upload to the first shop's listing and confirm a 403 with no new object in the storage folder.

Acceptance criteria for the route are narrow. A shop can attach up to four images to its own draft or available copy, see them in order, delete one by its subdocument id, and publish a Good copy only after at least one exists. A sold copy refuses every photo write with 409. No response contains the API secret, and no listing document contains image bytes.

## Bridge to the gate

The gate puts these pieces in one sequence with a real order behind them. It asks for a Good copy that cannot publish until a photograph exists, a fifth upload that is refused, a cross-shop upload that is refused, and a paid order whose stored photograph still loads after the shop replaced the listing's pictures. That last check is the one that separates a working upload feature from one that survives a month of real trading.
