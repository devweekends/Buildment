# Condition photo gate

This gate needs one shop, two drafts and one order. North Street Books has a draft copy graded Good at 2,300 and a draft copy graded Very Good at 3,100, both for the College Algebra edition. Separately, a copy of that edition has already been sold to Hana, its order line stores a photograph URL, and the listing is `sold`. Keep all three in front of you, because the gate is about the difference between a copy that can still change and a copy that cannot.

Before you start, note what you expect. The Good draft should refuse to publish with no photograph and should publish after one upload. The Very Good draft should publish with no photograph at all. The sold copy should refuse every photo write. A fifth upload on either draft should be refused. None of those four expectations needs a database query to state, and all four need one to prove.

## Publish a low grade without evidence

Open the Good draft in the back office and press publish. The response must be a 400 with the code `PHOTO_REQUIRED` and a message naming the photographs, and the listing must still be a draft afterwards. Read the raw response, not only the banner. A form that silently stays on the page has proved nothing.

Now take one photograph of the actual copy, a close view of the highlighted pages, and upload it. Publish again. The copy becomes available. Open the listing document in Compass and confirm the photo entry holds a URL and a public id, that the URL starts with `https`, and that the document size is a few kilobytes rather than a few megabytes. A listing document that grew by the size of the image means the bytes took the wrong path.

Repeat the refusal on an Acceptable copy if you have one in the seed, and confirm the Very Good draft publishes with no photograph. Those two runs together prove a threshold and not a blanket rule, and they are the pair that a reviewer will ask for first.

## Four is the limit, and five is a bug

Upload four photographs to the Good copy and count them in the API response and in the document. Send a fifth. The response must be a 400 with `PHOTO_LIMIT`, and the stored array must still hold four entries. Then send two uploads at the same moment with separate requests, starting from three photos, and confirm the count ends at four and not five. That second test is the one that catches a length check written in JavaScript instead of in the update filter.

Now try the same upload against the sold listing. The answer is not a validation error: it is a 409, because the copy is frozen and the request was reasonable but the state forbids it. The photo set must be unchanged after the attempt, and the storage folder must not contain the refused file. A 409 with an orphaned object next to it is a half fix.

## Prove the boundary and the storage

Sign in as Corner Books and send an upload to North Street's Good listing with a valid image. The response must be 403, the listing's photo array must not change, and the Cloudinary folder for that listing must not gain an object. This is why the ownership check runs before the upload helper: a refusal after the bytes arrive has already cost quota and created a file whose owner is nobody.

Then inspect the storage side by hand. The asset should live under a folder that names the listing, the public id in Mongo should match the asset, and deleting the asset from the dashboard should make the stored URL fail while the document still shows it. That last experiment is destructive, so run it on a disposable copy and restore the photograph afterwards. It teaches the one thing the schema cannot: the URL is a promise that the object still exists.

## Replace on a copy, then open the receipt

Replace the photograph on the available Good copy. The new URL should be stored, the old asset should be destroyed, and the order you performed those steps in should be visible in your log. Then open Hana's paid order for the sold copy. Its photograph must still load, and the listing's frozen photo set must still match the URL the order points at.

That pair of checks is the point of the module. A marketplace can let a shop improve the pictures of a copy that is still for sale. It cannot let a shop rewrite the evidence attached to a completed sale, because the buyer's only record of what she agreed to is that image. Write one sentence in the log about which filter enforces the freeze and which field the order line relies on.

## Gate checklist

- [ ] A Good copy with no photograph returns 400 `PHOTO_REQUIRED` on publish and stays a draft.
- [ ] The same copy publishes after one upload, and the Very Good copy publishes with no photograph.
- [ ] The stored photo entry has a URL, a public id, a subdocument id and a creation time, and the listing document stays small.
- [ ] A fifth upload returns 400 `PHOTO_LIMIT`, and two simultaneous uploads from three photos end at four.
- [ ] A photo write on a sold copy returns 409 and leaves the array unchanged.
- [ ] A cross-shop upload returns 403, with no new object in the listing's storage folder.
- [ ] Replacing a photograph on an available copy stores the new URL and destroys the old asset.
- [ ] The paid order page still shows its image after the sold listing was targeted by a refused write.
- [ ] The storage public id matches the asset that the stored URL resolves to.
- [ ] No response body or log line contains the Cloudinary API secret.
- [ ] `.env.example` lists the storage variables with placeholder names and no values, and the server refuses to boot when one is missing.
- [ ] The upload middleware rejects a non-image file and a file over the stated size with 400s, not 500s.
- [ ] The four-photo limit is enforced in the database operation, and the test that proves it sends concurrent requests.

## Learning log

1. Which request did the publish rule refuse, what code came back, and which field of the stored Listing did the form highlight? Quote the response.
2. Where does an image byte live after a successful upload, and what exactly does MongoDB store? Give the document size you measured.
3. Two uploads arrived at once on a copy with three photographs. Explain what made the count stop at four, and what would have happened if the check had run in JavaScript before the write.
4. Why does the ownership check run before the bytes leave the phone? Name the two costs a wrong-order implementation pays.
5. Hana opens her paid order six weeks later. Which record holds the image URL, which record was frozen, and what would have broken if the shop had deleted the old asset?

## What a passing gate leaves behind

Four artefacts. The public id of one stored image next to the URL in its Listing document. The 400, 403 and 409 responses saved as raw JSON. The order page for the sold copy, screenshotted with the photograph visible and the date of capture. And a short note stating the upload order you use, the size and type limits you chose, and where a future cleanup job would look for orphaned files.

Two honest limits belong in the write-up. Nothing here proves that a photograph shows the worst defect on the copy; the marketplace requires evidence and cannot audit every frame. And a photo set is not a grade. A shop can upload four honest pictures and still choose a grade you would not choose yourself, which is why the grade rubric, the defect flags and the photographs are shown together rather than one replacing another.

Module 14 turns to the other side of the exchange. A student will not browse shops, she will browse editions, and every offer card she sees has to carry the grade, the price, the shop and one honest picture from the set you just built.
