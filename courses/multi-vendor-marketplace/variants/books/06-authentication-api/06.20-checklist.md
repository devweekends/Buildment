# 6.20: Checklist and learning log
> **[Gate]** · Chapter 06, Authentication API

This is the **gate** for Chapter 6. Tick every box honestly and answer the learning log below before opening Chapter 7.

<BigWordAlert term="JSON Web Token (JWT)" plainEnglish="A compact signed string encoding user id and expiry, sent in the Authorization header on API calls." whyItMatters="Hamesh access tokens prove identity for cart and Listing routes without a server-side session lookup." />

## How a reviewer reads this gate

This gate is about an API that issues identity, so almost every box is a claim about what a server refuses to do. Refusals are harder to demonstrate than successes: anyone can show a login that works, and only a deliberate test shows that a wrong password returns 401 rather than a token. Read the page with that in mind, because half of the evidence a reviewer wants is a request that was supposed to fail.

The reviewer's method is the same for each group. Send the request, read the status code, then read the body. A status code alone can lie: a 200 carrying an error message passes a careless check, and a 500 carrying a valid JSON body looks healthy until you read the number. Both parts together, plus the database document the request left behind, are what count as evidence.

The second rule is that no secret reaches a response. That is not a box you can tick by remembering to be careful. A reviewer decodes a token, greps a JSON body for `passwordHash`, and opens the Compass document to see what actually persisted. If the hash is not in the database in the expected form, the request that reported success did something else.

## Chapter 6, Authentication API checklist (gate)

Do **not** open Chapter 7 until every box is ticked and learning log answers are written below.

### Environment & config

- [ ] `JWT_SECRET`, `JWT_ACCESS_EXPIRY`, `JWT_REFRESH_EXPIRY` in `.env.example`
- [ ] `JWT_SECRET` in local `.env`, not committed
- [ ] config.js fails startup if JWT_SECRET missing
- [ ] bcrypt and jsonwebtoken in package.json

These four boxes cover the difference between a configuration and a guess. `.env.example` is the file that travels with the repository, so it names every variable a new machine must set, including the two expiry values, because an access token lifetime that lives only in someone's head cannot be reviewed. The real `.env` holds the value and stays out of history, which is the rule Chapter 2 established and this chapter finally needs.

Fail-fast startup is the box that turns a missing secret into an error you see in ten seconds rather than a token that verifies for nobody. A reviewer reads `config.js`, finds the check that throws when `JWT_SECRET` is absent, then removes the line from `.env` and restarts to watch the process exit. A server that boots without its signing secret is worse than one that refuses, because the failure moves to the first login attempt, far from the cause.

The dependency box is small but specific: `bcrypt` for password and refresh-token hashing, `jsonwebtoken` for signing and verifying. A reviewer checks `package.json`, not `node_modules`, because a package that exists only in a local install is invisible to the next clone.

### Endpoints

- [ ] POST `/api/auth/register`, 201, bcrypt hash, OTP, 409 duplicate
- [ ] POST `/api/auth/verify-otp`, sets isVerified, wrong OTP 400
- [ ] POST `/api/auth/login`, 200 tokens, 401 bad password, 403 unverified
- [ ] POST `/api/auth/refresh`, new access, invalid refresh 401
- [ ] GET `/api/auth/me`, requireAuth, 200 user+profile, 401 without token

Each of these five boxes is really two claims: a happy path and a refusal. Register returning 201 with a hashed password and an OTP is only half the evidence; the other half is a second register with the same email returning 409 because a unique index refused it. A reviewer sends the duplicate on purpose, since a register that quietly overwrites an account is a security hole disguised as convenience.

The verify and login boxes carry the flow that Chapter 7 will drive from the browser. A verified student or bookshop owner can log in and receive two tokens; an unverified account is refused with 403, which is a different number from 401 on purpose. A reviewer keeps those two responses side by side, because a chapter that returns 401 for both has collapsed two distinct problems into one message.

Refresh and `me` complete the pair that proves the token is usable. `refresh` exchanges a valid refresh token for a new access token and rejects an invalid one with 401, and `me` reads the identity from the token through `requireAuth` and returns the profile without a password field. A reviewer reads `me` first with a token and then without one, since the interesting response is the second.

### Security

- [ ] No passwordHash in any API response
- [ ] refreshTokenHash stored hashed on User, not plain refresh
- [ ] role in access JWT matches User.role
- [ ] Only vendor/customer roles accepted on register
- [ ] OTP dev delivery documented (console or dev response)

These five boxes are the ones a reviewer checks without trusting any endpoint. The first is a search rather than a request: send register, login and `me`, then look at all three bodies for a hash. A single equality check in a serializer can leak the field that breaks a breach wide open, so the absence has to be verified in the response, not assumed from the code.

Storing the refresh token as a hash extends the same reasoning to the server's own storage. A plain refresh token in the database is a working credential to anyone who reads the collection, while a hash is only useful to the process that compares it. A reviewer opens a User document in Compass and expects a digest, plus an expiry, and nothing that looks like a token.

The role claim is the box that later chapters depend on. `role` inside the access token must match `User.role` in the database, because Chapter 8's authorization decisions will read one of them and assume the other agrees. In Hamesh the two accepted values mean a student account and a bookshop account; a reviewer sends a register with an invented role and expects a 400 rather than a new account with an unrecognised permission.

The OTP box is documentation rather than behaviour. In development the code is printed to the server console or returned in a dev-only response field, and either choice has to be written down where the next person looks. A reviewer reading that note should be able to complete verification without asking you how.

### Testing

- [ ] Full curl flow documented (6.18)
- [ ] Negative tests pass (401, 403, 409)
- [ ] Seed vendor-a login works after bcrypt alignment

This group is about evidence you can hand over. The curl flow from 6.18 should read as a sequence a reviewer can paste: register, capture the OTP, verify, login, call `me`, refresh. Each step needs the request and the response, because a transcript with only requests cannot be checked.

The negative tests are the part that most submissions omit, and they are the part that proves the guards exist. A reviewer looks for three specific refusals: 401 without a token, 403 for the unverified account, 409 for the duplicate email. One line each, with the status code visible, is enough.

The seed box connects this chapter back to Chapter 5. The seeded bookshop account was written with a plain password, so it can only log in once the seed hashes it with the same library and cost factor the register route uses. A reviewer logs in as the seeded bookshop, and a failure here usually means the seed and the route disagree rather than that the password is wrong.

### Prior gates

- [ ] Models and seed from Ch 5 intact
- [ ] Health route still works
- [ ] No React auth UI yet, API only
- [ ] Explain bcrypt vs plain storage
- [ ] Explain access vs refresh token roles
- [ ] Explain 401 vs 403 in this chapter
- [ ] Explain why JWT payload must stay minimal
- [ ] Explain refresh rotation benefit

The first three boxes check that this chapter did not break the two before it. The User model gained hashed fields, so a reviewer re-runs the seed and confirms the existing documents still satisfy it. The health route is a two-second check with curl and worth doing, because a broken `/health` hides a much larger mistake about where the auth module was mounted.

That third box states a boundary: Chapter 6 issues and verifies tokens, and Chapter 7 decides how a browser keeps them. A reviewer looks for client folders that already contain login pages, and treats their presence as scope creep rather than progress, because a half-built UI in this chapter makes the next chapter's debugging ambiguous.

The explanation boxes are the part a mentor tests by asking. The five questions cover the ideas this API is built from: hashing versus storage, the two token lifetimes, the difference between unauthenticated and forbidden, why a token should carry an id and a role rather than a profile, and what rotation buys you when a refresh token is stolen. If the vocabulary is not yet comfortable, the chapter is not finished even when every curl command passes.

Answer **in your own words** in the fields below. Eight questions follow, and they are written to be answered from your own terminal output rather than from the chapter text.

The first four reconstruct what you built: the documents a register leaves behind, the protection a hash gives you and the risk it does not remove, the claims inside a decoded token, and how a refresh token is stored and invalidated. The last four ask you to read your own evidence: how the OTP arrived, which negative test you ran, where Chapter 7 will keep the access token, and what `req.user` carries for the chapters after that.

## Troubleshooting

| Blocker | Look at |
|---|---|
| 401 on valid token | JWT_SECRET mismatch, clock skew |
| 403 on seed login | isVerified false, re-seed or verify |
| 404 on auth | 6.11 mount path |
| bcrypt compare false | seed plain password, re-hash |

The table is ordered by how often each cause appears in practice, and the first row is the one that wastes the most time. A token that was valid a minute ago and is rejected now usually means the process was restarted with a different `JWT_SECRET`, because the value changed in `.env` or the file was not loaded at all. Read the server log before decoding the token again.
