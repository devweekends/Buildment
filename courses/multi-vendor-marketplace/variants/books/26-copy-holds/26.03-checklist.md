# Two-tab race and hold gate

This gate is performed in a browser, by two people or by one person with an incognito window, because that is where the promise becomes real. The service tests from the previous lesson prove the predicates. The two tab race proves the routes, the session handling, the 409 body and the client rendering, all at once, under the timing that a student actually experiences.

Set up one edition with exactly one available copy at North Street Books, and a second copy of the same edition at Campus Shelf at the same grade or better. Student A signs in on the normal window. Student B signs in on an incognito window, so the two sessions cannot share a cookie. Both open the edition page before either taps checkout. Keep the browser network panel open on both windows, and keep a database shell open for the readings afterwards.

## Gate checklist

- Both tabs see the one copy as available before the race starts.
- One tab reaches a payable checkout and the other receives a 409 whose reason is `copy_unavailable`.
- The 409 body contains a substitute at the same grade or better, from an accepted edition, within the ceiling, and the substitute is not held.
- The Listing document names exactly one checkout as its hold owner, with a deadline in the future.
- Only one paid order exists for the copy after the winner pays with a test card.
- The losing tab can claim the substitute in a second attempt and reach payment with it.
- A hold released past its deadline is not released again by a second run of the expiry job.
- A payment that lands after its copy was released records `copy_not_held_at_payment` on that order and leaves the copy with its new owner.

## Run the race in two tabs

Both students tap checkout within a second of each other. Run it once with A first and once with B first, because the winner should be whichever request the database served first, not whichever window you clicked. The losing tab must receive a conflict, not a spinner and not a second payable checkout.

Read the winner's checkout id from the response and the Listing's `hold.checkoutId` from the database. They must be the same value. Read the deadline and compare it with the server clock: a hold created now should expire about fifteen minutes later. A hold with no deadline is a copy frozen forever, and a hold with a deadline in the past is a copy that another student can take while the first student is typing a card number.

Then let the winner pay with a Stripe test card. After the webhook arrives, read the Listing again: status sold, hold field gone, buyer and order consistent. Count the paid orders for that Listing id. One. A count of two is the failure this whole module exists to prevent, and it is worth checking twice, once in the order collection and once through the student order route.

Run the same race with the same student in two tabs as a second scenario. The result should be one payable checkout and one conflict, because the second attempt is a different checkout with a different owner token. A build that keys the hold on the student id rather than the checkout id will show two successful attempts here, and the bug will only appear in this scenario.

## Read the conflict body

A 409 with an empty body passes a status code check and fails the student. Read the JSON and answer three questions. Is the substitute a real Listing that exists and is available? Is its grade at or above the grade of the copy that was lost? Is its price at or below the ceiling the student set?

Check the ceiling case explicitly. Set a student's reading list ceiling below the only substitute and run the race again. The response must return `substitute: null`, and the client must offer the want-list path rather than a broken link. A substitute that ignores the ceiling teaches the student that Hamesh does not listen, and it also produces a purchase at a price the student never agreed to if they tap it without reading.

Then claim the substitute from the losing tab and complete the purchase. This proves the substitute is a suggestion that can become a real claim, not a decoration in an error message. Read the second Listing afterwards: held, then sold, under the correct checkout id.

The substitute must not be held by the conflict response. Check the substitute Listing's status immediately after the losing tab receives the 409. It should still be available, with no hold field. A held substitute is a copy frozen for a student who may never return, and on a small catalogue that is how one abandoned checkout removes two books from sale.

## Expire a hold while a payment is in flight

This is the reading that the service test predicts and the browser confirms. Claim the copy, start the card form, and before completing the payment move the server clock forward past the hold deadline, or wait for a short deadline you configured for the test. The expiry job runs, sees a payment attempt in progress, and extends the hold by two minutes instead of releasing it. Read the Listing: still held, deadline moved, extension counter at one.

Complete the payment inside the extension. The copy becomes sold, the order is paid, and no second student can claim it. A build without the extension shows the opposite: the copy released, the second student claiming it, and the first payment arriving with nowhere to go.

Then test the bound. Keep the payment attempt in progress and let the expiry job run a third time. The copy must be released, because the extension counter has reached its limit. A late payment after that release must produce `copy_not_held_at_payment` on the order and leave the copy with whoever claimed it next. Both readings are required: the extension saves the patient student, and the bound stops a stuck attempt from freezing a copy all evening.

## Check what the pages say while a copy is held

A hold is invisible to other students unless the interface mentions it, and an edition page that hides a held copy looks exactly like an edition with one fewer copy. Decide which one your product does and make both pages agree. If the summary excludes held copies, the offer page should not show the copy as available a second later, and the conflict should explain that another student is checking out.

Read the copy detail page during a hold. It must not offer a Buy button that ends in an error every time. It can say the copy is being checked out by another student, with the deadline if you choose to show it, and point at the substitute. Hiding the deadline is safer than showing a countdown that is wrong by a few seconds, and either choice is defensible as long as the page never claims the copy is yours.

Check the shop side too. A shop should not receive a collection instruction for a held copy that has not been paid for. The shop order page may show a pending order, and it must not invite handing the book over. The collection code belongs after the paid transition, which module 21 already built, and this gate is a good place to confirm that a held copy produces no code.

## Debug the failures this gate finds

If both tabs reach a payable checkout, the claim predicate is not being used or is being evaluated outside the update. Read the service and confirm the status condition is inside the filter rather than in an `if` above it. Then check whether the checkout route calls the claim twice with different checkout ids for the same student, which happens when a retry creates a second attempt instead of reusing the first.

If the losing tab gets a 500 instead of a 409, the substitute query is probably throwing on a missing edition or a missing photo reference. Wrap the substitute lookup so a failure produces `substitute: null` with a logged reason, and never let an optional suggestion turn a clean conflict into an error page.

If the paid order count is two, the webhook is not requiring the hold owner. It may be updating by `listingId` alone, which is the pattern that overwrites another checkout's claim. Check the confirm filter for `status: "held"` and `hold.checkoutId`. Then check the order creation path for a second write that marks copies sold without reading the claim.

If the expiry job releases a sold copy, the release filter is missing the status condition or is using `_id` only. That is the same mistake module 19 warned about in the cleanup path, and it reappears here because the code was copied without the predicate.

## Learning log

1. Which window won the race, and what were the two response statuses? Include the checkout id in the Listing's hold field after both requests finished.
2. What did the 409 body contain for the substitute, and which condition made it acceptable? What happened when the ceiling excluded every substitute?
3. What did the expiry job do while a payment was in flight, and what changed on the second and third run?
4. After the late payment, which order field recorded the problem, and who owned the copy at that moment?
5. Which page did you read during a hold, and what exactly did it say instead of offering a Buy button?

The gate fails if two paid orders exist for one copy, if the 409 has no usable substitute when one exists, or if a release can overwrite a sale. It also fails if the only evidence is a screenshot of a success page, because a success page cannot show that the second attempt was refused. Keep the two response bodies, the Listing document before and after, and the order count. Those four artefacts answer every question a reviewer will ask about this module.
