# Reading-list matcher gate

Seed three shops with copies of three textbook editions and one student reading list. Include a cheap wrong edition, a copy below the student's grade floor, two equal-price eligible copies from different shops and an item with no copy. Write the expected output before running the matcher. The gate is about a decision the student can inspect: each chosen Listing has a reason, each missing item has an honest gap, and no physical copy is selected twice.

## Check eligibility before price

Run the pure matcher tests. The cheap wrong edition must be excluded before price ranking. A Good copy must be excluded by a Very Good floor even when it is inexpensive. A listing with a forbidden defect must be excluded even if its grade rank is high. The result should show the first failing rule in plain language. Change one preference at a time and predict which candidate becomes eligible before rerunning. This makes the filter visible to the learner rather than hiding it behind a composite score.

Give two list items the same accepted Edition and provide only one available physical Listing. The matcher may choose it for one item, but must leave the other unmatched. Add a second Listing and rerun; now each item can receive a different ID. No amount of UI quantity editing may duplicate a single Listing. The later cart and checkout must still recheck status because a second buyer can act after matching.

## Check the tie-break and privacy

Offer equal-price eligible copies for one item at Shop A and Shop B. Make an earlier item available only at Shop A. The tie-break should prefer Shop A and show the lower pickup-shop count. Reverse list item order and check that the result remains consistent with the documented bounded algorithm. If the implementation is only heuristic, the UI and test names must not claim an optimal route. Price remains the primary objective; do not choose a more expensive copy merely to save a stop unless the student explicitly asks for that trade-off in a later feature.

Sign in as Student B and request Student A's reading-list ID. The API must deny it. A shop owner may publish a course template but cannot read a named student's copy or budget ceilings. Copy a template as Student A, edit a grade floor, and confirm the template itself did not change. Inspect the raw API response for owner IDs and unrelated student data, not just the rendered page.

## Check the handoff to cart

Match the list and add all selected Listing IDs to cart. Before checkout, mark one Listing unavailable through a second buyer's test action. The cart API must reject or remove that stale line and tell the first student which reading-list item needs rematching. It must not keep the old price as an authoritative charge. The student's list stays saved, so they can match again without retyping the course code and preferences. No order or inventory hold should exist from the match operation alone.

## Learning log

1. Explain why title similarity cannot overrule an accepted Edition ID and why a Listing is the sell-once object.
2. Write the eligibility checks in order. Give one rejected example for edition, grade, defect, price and availability.
3. Describe the equal-price shop tie-break and its documented computational limit. Why does the item order test matter?
4. Explain what the match result promises and what only checkout can promise under two-buyer concurrency.

Commit the private-list routes, pure matcher tests, API route, page and cart handoff. Save a before-and-after query count and `explain()` output for the candidate fetch. A mentor should be able to change one seeded grade or price and predict the new result. If the list can leak to another student, a wrong edition can win, or one Listing is selected twice, stop before enabling the want-list worker. That worker will reuse the same eligibility meaning when a new copy appears.

## Review a result with another person

Give a partner only the reading-list page and ask which copy was chosen for one item. They should be able to name the exact Edition, the copy's grade and defect notes, its shop, price and why it beat another eligible offer. Ask them what the unmatched label means and what action they can take next. If the page merely says “no result,” add the specific exclusion reason. If the page shows an old price after a listing changed, distinguish a previous match snapshot from the current offer and force a fresh server check before cart or checkout.

Then compare the student's saved list before and after copying a shop template and before and after matching. Copying creates a private student record; matching should not mutate that record's accepted editions or grade preferences. A shop correction to the public template should not silently change the student's copy. Test this as a raw API assertion so a later UI refactor does not accidentally broaden data access. A private budget ceiling reveals something about a student; it should not appear in shop or public catalogue responses.
