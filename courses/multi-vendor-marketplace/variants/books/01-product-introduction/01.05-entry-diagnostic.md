# Entry diagnostic

The course assumes JavaScript functions and promises, an HTTP request and response, one CRUD app, Git and basic data modelling. You do not need to arrive knowing the book trade. This 20-minute check asks you to reason from a short rule and a small API situation. Work without a prepared solution, save your answers, then use a targeted repair if you miss two or more parts. The aim is to protect your time before the catalogue and checkout modules become complex.

## Task 1: Read an Express route

Imagine `PATCH /listings/:id` loads a Listing by the URL ID and updates its price from the body. What is missing if only the owner Shop may edit it? Name the authenticated value and the stored relationship the server must compare. A good answer says the session User must resolve their Shop, then the Listing update must filter by both Listing ID and that Shop ID. A hidden Edit button is not enough. Write pseudocode or a route sketch with a denied branch.

If this is unfamiliar, practice a two-owner CRUD route before Module 2. Create one row per owner, send a direct PATCH using the other owner's row ID, and inspect that the database remains unchanged. The book domain is not the hard part of this question; the skill is server-side ownership.

## Task 2: Write a filtered Mongoose query

Write a query that finds available Listings for one Edition ID with `gradeRank >= 2` and `priceMinor <= 2500`, sorted by price. Then explain why a query by Work title alone cannot guarantee the edition a student needs. A valid sketch identifies the exact Edition ID and all three filters. It may use pseudocode if you cannot recall every Mongoose method name. The conceptual predicate matters more than punctuation in this diagnostic.

If you miss the filter, use a disposable collection with four fixture rows: wrong Edition, low grade, high price and one eligible. Run the query and check which row remains. Keep the fixture small. This repair becomes the basis of the later reading-list matcher and helps you spot a silent false match early.

## Task 3: Show a Git checkpoint

You have added Work and Edition schemas but a seed fails halfway through. State what `git status` tells you, which files you would commit once the narrow test passes, and how a local commit helps after a power cut. A commit does not need network access. If you have never made one, create a practice repository, edit a small Markdown file, inspect its diff and commit it. Record the command you used in your learning log.

Do not commit real student details, Shop contact lists, Stripe keys or copied textbook pages as a shortcut to a reproducible seed. Fictional accounts and publisher-verified ISBN metadata are enough. This is a working-habit check as much as a command recall check.

## Task 4: Compute an ISBN-13 check digit

Use the first twelve digits `978193816838` from a printed OpenStax College Algebra ISBN. Multiply digits in alternating positions by 1 and 3, add the products, then choose the last digit that makes the total divisible by ten. The published final digit is 3. Show your sum and the final step. You do not need to know this rule in advance; it is written here to test careful application of a numeric specification. Do not guess from the book title.

If the arithmetic is difficult, repeat with a second valid ISBN from a publisher source and write a small pure JavaScript function. The function should take a string so leading zeros are preserved. The full ISBN lesson later covers ISBN-10, X and 979. The diagnostic only checks whether you can turn a stated rule into a careful calculation and test.

## Choose the next step

A confident core-path answer identifies the owner predicate, filters Listing by exact Edition and constraints, saves a local Git checkpoint, and calculates the final ISBN digit with a worked sum. If two or more are missing, complete the relevant repair tasks before Module 2. If one is weak, repair it alongside the skeleton and ask an instructor to review your reasoning. Keep both original and repaired answers. A learner who already knows these skills should move on; a learner who repairs one now avoids a much longer debugging session later.

The next chapter outlines the four weeks and their demo targets. Use the diagnostic result to plan effort, not to label yourself as good or bad at the subject. Every task has a small path back into the core.
