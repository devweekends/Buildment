# 7.18: Checklist and learning log
> **[Gate]** · Chapter 07, Login and registration

This is the **gate** for Chapter 7. Tick every box honestly and answer the learning log below before opening Chapter 8.

<BigWordAlert term="Token storage" plainEnglish="Where the browser keeps JWTs: memory, sessionStorage, or httpOnly cookies, each with different XSS and CSRF trade-offs." whyItMatters="Hamesh's client must store tokens safely and attach them to API calls without leaking them in URLs or logs." />

## How a reviewer reads this gate

Chapter 6 proved an API could issue identity. This gate is about what a browser does with it, and the difference matters because almost every failure here is invisible in the page. A login that appears to work while the token sits in localStorage passes a visual check and fails the security intent of the chapter.

The reviewer therefore watches the network, not the screen. Two panes of DevTools carry most of the evidence: the Network tab shows which requests were sent, with which headers and status codes, and the Application tab shows what the browser kept afterwards. A box that cannot be checked in one of those two panes is usually being checked by memory rather than by evidence.

The third thing a reviewer does is reload the page. Session behaviour on a hard refresh is where in-memory tokens and cookie-backed refresh tokens show their real cost, and it is the single most common place for a Chapter 7 implementation to be honest or to quietly cheat.

## Chapter 7, Login and registration checklist (gate)

Do **not** open Chapter 8 until every box is ticked and learning log answers are written below.

### Pages & routing

- [ ] `/register`, `/login`, `/verify-otp` routes work
- [ ] Register → verify → login flow completes in browser
- [ ] Role-based redirect after login (vendor vs customer)
- [ ] Login shows error for wrong password and unverified user

These four boxes cover the visible half of the chapter. The route box is checked by typing each URL directly rather than by clicking through, because a link can reach a page whose route does not exist and the difference only appears on a refresh. A reviewer opens all three addresses in a fresh tab and expects a rendered form, not a blank router outlet.

The full-flow box is the one that has to be walked end to end without shortcuts. In Hamesh terms a new student registers, reads the OTP, verifies, logs in and lands on a page that reflects their account; a new bookshop owner does the same and lands somewhere different. A reviewer follows the whole path once as a brand new account, because a flow tested only against pre-seeded accounts skips the register and verify steps entirely.

The role redirect is checked with two logins in the same browser session. In the checklist the two roles are named vendor and customer, which on Hamesh mean a bookshop owner and a student: one lands on a bookshop workspace, the other on a student landing page. A reviewer looks for a redirect that reads the role from the authenticated user rather than from a form field the browser could change.

The error box exists because a login form that fails silently teaches the wrong lesson. A wrong password must show a visible message, and an unverified account must show a different one, since "check your password" for an account that needs OTP verification sends a learner in circles. A reviewer checks both messages, and treats two identical strings as one box left unticked.

### Auth state

- [ ] useAuth or AuthProvider manages user + access token in memory
- [ ] Boot refresh restores session on page reload (or documented limitation fixed)
- [ ] Logout clears state and blocks protected routes

This group is about where the truth about the current user lives. The provider box is structural: one context or hook owns the user object and the access token, and every screen reads it from there. A reviewer looks for a single source and for pages that consume it, because two independent copies of the user state drift apart in exactly the situations that matter, such as after a refresh or a logout.

The boot box is where honest implementations separate from shortcuts. An access token in memory disappears on reload, so the app has to re-establish the session from the refresh token before it decides what to render. A reviewer reloads a protected page and watches the Network tab for the refresh call, then watches the page settle into the authenticated view. A documented limitation is acceptable; an undocumented one presents itself later as a "random logout" bug.

Logout is a two-part claim, and the second part is the one people forget. Clearing the context hides the token from the interface, and a reviewer then opens a protected URL directly to confirm the route guard also refuses. A logout that only navigates to the home page leaves the session alive for anyone who presses Back.

### API client

- [ ] apiFetch attaches Authorization Bearer when authenticated
- [ ] 401 triggers refresh once then retry (tested or short-expiry verified)
- [ ] credentials: 'include' on refresh request
- [ ] Access token **not** in localStorage or sessionStorage

These four boxes are the mechanical heart of the chapter. The Bearer box is checked in the Network tab: an authenticated request shows an `Authorization: Bearer ...` header and an anonymous one does not. A reviewer compares the two requests rather than reading the helper, because the helper can look correct while a component bypasses it with its own fetch call.

The retry box is the most common place to find a half-finished implementation. The sequence should be one request, one 401, one refresh call, and one repeat of the original request, in that order. A reviewer sets the access token expiry to a few seconds, waits for it to lapse, then reads the Network sequence. More than one refresh attempt in that sequence means the retry is looping rather than recovering.

The credentials box is a one-line setting with an outsized effect. A refresh token delivered as an httpOnly cookie is not sent by default on a cross-origin request, so `credentials: 'include'` is what makes the cookie travel from the Vite origin to the API. A reviewer opens the refresh request and looks for the Cookie header, then opens the response and looks for `Set-Cookie`.

The storage box is a negative check, and it is deliberate. A reviewer opens the Application tab after logging in, reads localStorage and sessionStorage, and expects to find no access token in either. Anything found there is a finding, regardless of how short the expiry is.

### Protected routes

- [ ] ProtectedRoute redirects unauthenticated users to login
- [ ] Vendor stub page reachable only when logged in as vendor (if role prop used)
- [ ] isLoading prevents redirect flash during boot

This group is the client-side counterpart of the server's `requireAuth`, and the two are often confused. A client guard decides which screen to show; it protects nothing on its own, because anyone can call the API directly. The reviewer checks that both exist and that the client guard does not stand in for the server middleware.

The redirect box is checked in a fresh window with no session, by typing a protected URL. The expected behaviour is a redirect to the login page and, after a successful login, a return to where the request started. A reviewer also checks the reverse case: a logged-in student visiting the bookshop-only stub page should be refused, not shown an empty dashboard.

The loading box is the one that needs a slow network to observe properly. During boot the app does not yet know whether the user is authenticated, so a redirect decision made too early throws a real user out to the login screen for a moment. A reviewer throttles the network, reloads a protected page, and watches for that flash. If the guard renders before the session check resolves, the fix is a loading state rather than a shorter timeout.

### Integration

- [ ] Seed vendor-a and customer-a login via UI
- [ ] CORS allows credentials from Vite origin
- [ ] No new server auth endpoints required beyond Ch 6 (cookie Set-Cookie OK)

These three boxes connect the browser work back to the API built in Chapter 6. The seed accounts are the fastest end-to-end test: in Hamesh they are one bookshop owner and one student, each with a known password, and both should log in through the form rather than through curl. A reviewer tries both, because an account that works in curl and fails in the browser points at the transport rather than the credentials.

The CORS box is where credentials change the rules. A server that allows the Vite origin with `credentials: true` also has to name the origin explicitly, since a wildcard is rejected for credentialed requests. A reviewer reads the response headers for `Access-Control-Allow-Origin` with the exact client origin and `Access-Control-Allow-Credentials: true`, then looks for the preflight request in the Network tab.

The last box sets the boundary for the chapter. Chapter 7 should be solvable without inventing new auth endpoints: the only server change allowed is setting the refresh cookie, and that is a response header rather than a route. A reviewer diffing your server work expects a small change, and a large one usually means a second identity system has appeared beside the first.

### Prior gates

- [ ] Ch 6 auth API still passes curl tests
- [ ] Ch 5 models/seed intact
- [ ] Why access in memory vs localStorage?
- [ ] Explain 401 refresh loop step by step
- [ ] Difference between ProtectedRoute and server requireAuth
- [ ] What happens on full page reload?

The first two boxes are regression checks, and they are cheap because the evidence already exists in your Chapter 6 notes. Re-run one register, one login and one call to `me`, and confirm the seed still has a bookshop and a few copies. A chapter that adds a browser cannot be allowed to break the API underneath it.

The remaining four items have no artifact, so a mentor tests them in conversation. The first two ask for the reasoning behind the storage decision and the retry sequence, and the second two ask you to separate two things that look similar: a client route guard and a server middleware. If you cannot explain the refresh loop without reading your own code, the chapter is not finished.

### Learning log, write now

Answer **in your own words** in the fields below. The eight questions are ordered to follow a single session from register to reload, so answering them in sequence gives you a walkthrough rather than eight unrelated notes.

Where a question asks about behaviour, quote what you saw rather than what you expected: the network sequence, the error message, the redirect target. Where a question asks about a choice, name the alternative you rejected and why. That is what makes the log useful to you in Chapter 8, when an authorization decision has to rest on a session you now understand.

1. **Token storage:** Where do access and refresh live in your implementation? Why?

2. **Refresh loop:** Describe network sequence when access expires mid-session.

3. **Register flow:** UX path from register to first authenticated page, any friction?

4. **Role redirect:** How does login decide vendor vs customer destination?

5. **CORS/cookies:** What server CORS changes were needed for refresh cookie?

6. **Failure test:** One UI error state you tested (wrong password, unverified, etc.).

7. **Chapter 8 preview:** Why is login not enough to PATCH another vendor's store?

8. **Reload test:** Does session survive hard refresh? If not, what did you fix?

Mark this chapter complete in the platform, then continue to **Authorization and isolation** (Chapter 8).

## Final gate statement

*"Login, register, verify work in browser; access in memory; refresh on 401; protected routes redirect correctly. Ready for Chapter 8 authorization."*

Read that statement as four separate claims, each with a place to check it. The browser flow is the walkthrough you did twice, once per role. The in-memory claim is the empty storage panes in the Application tab. The refresh claim is the request sequence under a short expiry. The redirect claim is a protected URL typed into a window with no session.

**All boxes ticked? Open Chapter 8.**
