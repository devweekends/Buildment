# Isolation gate

Two shops, two students and an admin are seeded, the guards are registered, and `docs/AUTHORIZATION.md` exists. This gate asks one question in several forms: can a signed-in person reach a record they do not own, and when they are refused, do they learn something they should not?

Run the suite against a clean database, then run the three most important requests by hand in a terminal. A suite that passes while a manual request returns a full record means one of the two is pointed at a different server.

## Prove the refusals one boundary at a time

The shop boundary is the first. Campus Shelf sends a price change to a copy owned by North Street Books, using the listing ID and its own valid shop token. Expect 403, no listing fields in the body, and an unchanged price when North Street reloads the copy. If the price moved, the handler wrote before it refused, and every other passing test in the suite is now suspect.

The student boundary is the second. Bilal requests Hana's reading list, her cart and one of her want entries. Each answers 404, and each body is identical to the body for an ID that was never created. Compare the two bodies directly rather than reading them, because a difference of one field is the leak.

The projection boundary is the third, and it is the one teams skip. North Street reads its own listing and must not receive the student behind the current hold, the contents of that student's cart or her budget ceiling. Hana reads her own matched offers and must not receive a shop's draft copies, a shop account email or another student's hold. Both requests are allowed, and both can still leak.

The shared-record boundary is the fourth. A shop patch to an edition with copies answers `403 EDITION_LOCKED`, and the stored title is unchanged. Do it from the shop that created the edition, not from a stranger, because the interesting case is the caller who typed the record in the first place. Then sign in as the admin, send the same change and confirm 200 plus one audit document with the old value, the new value and the actor.

## Check the code you did not change

Two smaller checks belong in this gate because they cost a minute. Send a student token to a shop route and a shop token to an admin route, and confirm the role guard refuses both before any record loads. Then inspect every handler that reads an ID from a request body, and confirm none of them chooses which record to update after the ownership check has passed. A body field that selects the target is the same bug as no check at all, with better manners.

One more: read the success response for a sold copy. A listing that is sold may still render as a public record, which is fine, but its response must not carry the buyer ID, the checkout ID or the collection code. The collection code belongs to the student and the shop that fulfils the order, not to anyone who opens the edition page.

## Present it in five minutes

Show the matrix, then the failing line from the cross-shop test before the fix, then the passing suite. That order, because the failure is the interesting part: it shows the check is doing work rather than being present by accident.

Then answer one question without notes. Why can North Street not fix a title typo on an edition it created? The strong answer names the other shop's copy and the student's reading list: both depend on the shared record, and a title change moves what they are selling and what she is buying. It then names the report and the admin route as the path that exists instead. The weak answer is that a shop cannot be trusted, which is a statement about people rather than about data. The unacceptable answer is that the field is hidden in the app, because the app is not the boundary.

## What this gate does not prove

The suite proves the routes that exist. It does not prove that an aggregate endpoint avoids leaking counts, and it does not prove that an error handler added in a later module keeps refusals quiet. Both belong in `docs/AUTHORIZATION.md` under known limits, so a later reviewer knows what to re-check.

It also does not prove the checkout path. Holding a copy, splitting a payment and marking a copy sold are writes performed by the checkout and payment modules, and Module 19 owns those tests. This gate proves that no person can reach them through a user route, which is a different and smaller promise.

## Gate checklist

- [ ] `docs/AUTHORIZATION.md` lists every protected action with a scope field and the test that proves it.
- [ ] Campus Shelf's edit against a North Street copy answers 403 and a reload shows the price unchanged.
- [ ] Bilal's read of Hana's list, cart and want entry each answer 404 with an identical body to a missing record.
- [ ] North Street's own listing response carries no student name, cart contents or budget ceiling.
- [ ] Hana's edition page carries no draft listing, shop email or other buyer's hold.
- [ ] A shop patch to a locked edition answers `403 EDITION_LOCKED` and changes no stored field.
- [ ] The admin correction answers 200 and leaves exactly one audit document behind.
- [ ] A student token on a shop route and a shop token on the admin route are both refused by the role guard.
- [ ] No handler picks the record to update from a request body field.
- [ ] A sold listing response carries no buyer ID, checkout ID or collection code.
- [ ] `docs/EVIDENCE.md` holds the run summary, the three manual requests and the branch name.

If a crossed request answers 401, the route is missing the guard or the guard is registered after the handler. If it answers 200 with a filtered object, the write happened and the refusal was cosmetic. If a private record answers 403, revisit lesson 8.1: the caller may not be allowed to know the record exists at all.

The two codes are not an inconsistency to fix. A listing edit answers 403 because the offer page already told the caller the copy exists. A reading list answers 404 because its existence is private. A reviewer who asks you to make both codes the same is asking you to disclose one of those two facts, so answer with the policy rather than with the code.

## Learning log

Answer these in `docs/learning-log.md` with the request, the response and the stored record behind each answer.

1. Which stored field turned Campus Shelf's valid token into a refused request, and which function read it?
2. Why does a refused read of another student's list answer 404 while a refused edit of another shop's copy answers 403?
3. Name two fields you removed from a shop's view of a held copy, and one task the shop can still complete without them.
4. What does the edition lock protect, and what would break for a student if a shop could bypass it once?
5. Which second test proves the admin correction is audited rather than merely permitted?
6. Where could a body field still choose a record after an ownership check, and what does your code do instead of trusting it?

The first answer should name `shopId` on the listing and the shop lookup by `ownerId`, not a middleware name. The third should describe a real task at the counter, not just a field that is now hidden. If the sixth answer is "nowhere", open every handler that reads an ID from the body and read it again.

Commit the matrix, the tests, the evidence and the learning log together. Module 9 builds the shop profile and the pickup details on these guards, and Module 11 adds the listing routes. Every route those modules add arrives with a matrix row, so the file you commit now is the one they extend.
