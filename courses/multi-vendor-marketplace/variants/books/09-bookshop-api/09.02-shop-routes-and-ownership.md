# Shop fields, slugs and ownership

Three routes and one schema carry this lesson. The schema is where the shop's facts are held to a shape: a name, an area, seven days of hours, pickup notes, a slug and an owner. The routes are where the ownership rule is enforced: one shop per owner, your own shop for reading, and your own shop or nothing for writing.

Most of the work is in the refusals. A create request from an owner who already has a shop must not write. A patch from a different owner must not touch a field. A slug that another shop already holds must not collide. Each of those is a line of code you can write in one minute and a test you may never run, and running the test first is what separates a shop API from a shop-shaped hole.

## The schema, and why each field is shaped that way

Start with the model, because every route is a thin wrapper over it. The field list is short and each type is chosen to make a wrong value hard to store rather than easy to send.

```js
// server/src/modules/shops/shop.model.js (fields and validators, not the whole file)
const daySchema = new mongoose.Schema({
  day:    { type: Number, required: true, min: 0, max: 6 },        // 0 is Sunday
  closed: { type: Boolean, default: false },
  open:   { type: String, match: /^([01]\d|2[0-3]):[0-5]\d$/, default: null },
  close:  { type: String, match: /^([01]\d|2[0-3]):[0-5]\d$/, default: null },
}, { _id: false });

const shopSchema = new mongoose.Schema({
  ownerId:      { type: ObjectId, ref: "User", required: true, unique: true },
  name:         { type: String, required: true, trim: true, minlength: 2, maxlength: 80 },
  slug:         { type: String, required: true, unique: true, lowercase: true, trim: true },
  slugHistory:  { type: [String], default: [] },
  area:         { type: String, required: true, trim: true, minlength: 2, maxlength: 60 },
  openingHours: { type: [daySchema], validate: sevenDays },
  pickupNotes:  { type: String, trim: true, maxlength: 500, default: "" },
  contactPhone: { type: String, trim: true, maxlength: 20, default: null },
  status:       { type: String, enum: ["active", "suspended"], default: "active" },
}, { timestamps: true });
```

The hours use a twenty four hour string in fixed width, such as `"09:00"` and `"17:30"`, rather than a `Date`. A shop's hours are a weekly pattern with no date attached, and a `Date` would drag a timezone into a question that has no timezone. Fixed width also buys a free ordering check: `"09:00" < "17:30"` is true as a plain string comparison because every value has the same number of characters. That is the reason `"9:00"` must be refused, and the reason the regex is strict about the leading zero. A lenient parser that accepts `"9:00"` silently breaks the comparison for one day of the week.

The validator below is the whole rule, and it is worth reading twice because it encodes four decisions at once: there are exactly seven entries, each day appears once, a closed day carries no times, and an open day closes after it opens.

```js
// server/src/modules/shops/shop.validators.js
export function sevenDays(days) {
  if (!Array.isArray(days) || days.length !== 7) return false;
  if (new Set(days.map((d) => d.day)).size !== 7) return false;
  return days.every((d) => {
    if (d.closed) return d.open === null && d.close === null;
    return typeof d.open === "string" && typeof d.close === "string" && d.open < d.close;
  });
}
```

Overnight opening is out of scope, and the validator says so by refusing a close time earlier than the open time. A bookshop that trades past midnight is not the shop this course is built for, and pretending to support it would mean a second field, a second display rule and a second set of errors on the form. Write the limit in `docs/erd.md` beside the shop record so a reviewer sees a decision rather than an oversight.

## A slug that collides safely

The slug is derived from the name once, at creation, and it has to be unique. The naive version writes `slugify(name)` and lets the database refuse the second Corner Books with a duplicate key error that the owner reads as a 500. That is a bug with a one line fix, and the fix is a loop.

```js
// server/src/modules/shops/slug.js
export function slugify(name) {
  return name
    .toLowerCase()
    .normalize("NFKD")
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-+|-+$/g, "")
    .slice(0, 60);
}
```

The loop below tries the plain slug first and then numbered suffixes, and it inspects the duplicate key error before deciding what to do. That inspection is the interesting part. MongoDB reports both a duplicate slug and a duplicate owner with the same error code 11000, so a handler that treats every 11000 as "slug taken" would answer `corner-books-2` to an owner who already has a shop, which is the wrong refusal in a way that is hard to spot.

```js
// server/src/modules/shops/create-shop.js (the retry loop only)
const base = slugify(input.name);
for (let attempt = 0; attempt < 5; attempt += 1) {
  const slug = attempt === 0 ? base : `${base}-${attempt + 1}`;
  try {
    return await Shop.create({ ...input, slug });
  } catch (error) {
    if (error.code === 11000 && error.keyPattern?.ownerId) {
      throw httpError(409, "SHOP_ALREADY_EXISTS");   // the one shop rule, not a slug clash
    }
    if (error.code === 11000 && error.keyPattern?.slug) continue;  // next suffix
    throw error;
  }
}
throw httpError(409, "SLUG_UNAVAILABLE");
```

Five attempts is a judgement, not a law. It is enough for a platform where three shops share a name, and it ends with an honest conflict rather than an unbounded loop. The alternative is to fall back to a random suffix after the fifth try, which guarantees a slug and gives the shop an address nobody can read. Between an ugly refusal and an unreadable address, refuse.

The index itself must exist in the running database, not only in the schema file. Check it once with `db.shops.getIndexes()` and record the output in your notes, because a schema declaring `unique: true` on a collection that never built the index is the quiet version of this bug.

## Create, and what the body may not say

The create route reads five fields from the body and writes four more of its own. The body supplies `name`, `area`, `openingHours`, `pickupNotes` and `contactPhone`. The server supplies `ownerId` from the session, `slug` from the name, `slugHistory` as an empty list and `status` as active. A body that carries `ownerId`, `status` or `slug` is not an error; those keys are dropped, because a client that sends them is guessing and a route that honours them is a hole.

The order of operations is short and it matters. Validate the body first, so a malformed request is a 400 before any database work. Then check whether the owner already has a shop, which answers the ordinary second attempt with a 409 and a message a person can act on. Then attempt the insert with the slug loop, which answers the race. Returning the created shop is a 201 with the owner view, because the owner is the only caller of this route.

```json
{
  "error": {
    "code": "SHOP_ALREADY_EXISTS",
    "message": "This account already has a shop",
    "fields": {}
  }
}
```

A validation failure uses the same envelope with field keys, so the client has one handler rather than two. The hours are the field most likely to fail, and the message should name the day rather than the array index.

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Some fields need attention",
    "fields": {
      "openingHours": "Friday is marked open but has no closing time"
    }
  }
}
```

## Reading your own shop, and the 404 that is not a failure

`GET /shops/mine` finds the shop by the owner in the token and returns the owner projection. There is no id in the path, no query parameter and no way to ask for somebody else's shop, which makes this the simplest route in the module and the one that module 10 depends on most.

When the owner has no shop, the route answers 404 with the code `SHOP_NOT_FOUND`. That status is easy to misread as a failure, and the next module treats it as the normal answer for a new shop owner: it is how the client learns to send Mariam to the setup page instead of the dashboard. Keep the code stable, because a redirect rule built on an English message breaks the first time somebody improves the wording.

The projection itself is a field list, not the whole document. The owner view adds `contactPhone`, `status`, `createdAt`, `slugHistory` and two counts, and it never includes the password hash, the refresh token state or anything from the user record. Join those facts with one extra read only if the page needs them, and do not populate the owner into the response by default.

## Patching a shop, and refusing the wrong one

The update route is the only one with an id in the path, so it is the only one that needs an ownership check. Module 8 already wrote the helper, and this route calls it rather than inventing a second version.

```ts
// the fields this route may change, and the ones it may never change
const SHOP_EDITABLE = ["name", "area", "openingHours", "pickupNotes", "contactPhone", "slug"];
// ownerId, status, slugHistory, createdAt are not editable from here
```

The handler picks those fields from the body, then calls `assertShopOwner` with the id from the path. A shop page is public, so a wrong owner gets 403 with `NOT_OWNER` rather than 404: the caller can already see that the shop exists, and pretending otherwise would only confuse the two owners involved. The refusal carries a code and no fields.

The write is a conditional update, not a read followed by a save. Filter on the id and the owner together, set only the allowed fields, and read the matched count. A handler that loads the record, checks the owner and then saves by id re-opens the window it just closed, and it also lets a validation error on one field discard a valid change to another.

Slug changes get one extra rule. A shop that has never held a copy may change its slug, and the old value moves into `slugHistory` so an old link still resolves. A shop with any copy at all, in any state, gets `409 SLUG_LOCKED`, because the address may already be printed, shared or written on a receipt. That rule is deliberately stricter than the display need and deliberately simpler than tracking which links are live.

## The public page, by slug

The public read is the only unauthenticated route in the module and the only one whose response a stranger can see. It resolves a slug, falls back to `slugHistory` for an address that moved, and projects seven fields: the id, the slug, the name, the area, the hours, the pickup notes and the count of available copies. The response also carries `canonicalSlug`, so a client that arrived through an old link can rewrite its address instead of showing two different URLs for one shop.

Two details keep this route honest. Unknown slugs get a plain 404 with no hint about how close the guess was, because a shop's existence is public and a searchable error message is an invitation to enumerate every name on the platform. And the available copy count is computed in the same request with one indexed count, not stored on the shop as a number that every listing write has to remember to update.

## Two tests that fail on a naive route

Write both before the fix. The first proves the one shop rule survives a second request, and it is the test most implementations pass by accident because their route happens to check first. Run it twice in a row, then run the two requests through a barrier so they overlap, because the check is not what makes the rule true.

```js
// server/tests/shops.create.test.js
test("an owner cannot create a second shop", async () => {
  await request(app).post("/api/shops").set(auth(ownerA)).send(northStreet).expect(201);
  const second = await request(app).post("/api/shops").set(auth(ownerA)).send(northStreetAnnex);

  expect(second.status).toBe(409);
  expect(await Shop.countDocuments({ ownerId: ownerA.id })).toBe(1);
});
// currently 201, and /shops/mine returns whichever document sorts first
```

```js
// server/tests/shops.patch.test.js
test("another owner cannot patch this shop", async () => {
  const res = await request(app)
    .patch(`/api/shops/${northStreetId}`)
    .set(auth(ownerB))
    .send({ area: "Somewhere else" });

  expect(res.status).toBe(403);
  expect((await Shop.findById(northStreetId).lean()).area).toBe("Rimal");
});
// currently 200, and the area is now "Somewhere else"
```

The second failure is the one that matters commercially. An owner who can move another shop's area can send every student in the city to the wrong door, and nothing in the interface would look broken while they did it.

## The diff that closes both

The fix is a filter and a field list, and it is small enough to read in one screen. Everything else in the handler stays as it was.

```diff
 export async function updateShop(req, res, next) {
-  const shop = await Shop.findByIdAndUpdate(req.params.id, req.body, { new: true });
-  if (!shop) return next(httpError(404, "SHOP_NOT_FOUND"));
-  res.json(shop);
+  const changes = pick(req.body, SHOP_EDITABLE_FIELDS);
+  const shop = await assertShopOwner(req.params.id, req.user, { Shop });
+  const ownerView = await applyShopChanges(shop, changes);
+  res.json(ownerView);
 }
```

`pick` is three lines and it is the only thing standing between the request body and the document. A spread of `req.body` would let a caller set `status` to suspended, rewrite `ownerId` to another user, or push arbitrary strings into `slugHistory`. None of those fields is displayed anywhere, which is exactly why nobody notices for a month.

## Acceptance criteria

- [ ] `POST /api/shops` creates one shop, ignores `ownerId`, `slug` and `status` in the body, and returns 201 with the owner view.
- [ ] A second create for the same owner returns 409 `SHOP_ALREADY_EXISTS`, and the document count stays at one, including when the two requests overlap.
- [ ] Two shops with the same name receive different slugs, and the second one carries a numeric suffix.
- [ ] `GET /api/shops/mine` returns 404 `SHOP_NOT_FOUND` for an owner with no shop and never reads an id from the query string.
- [ ] `PATCH /api/shops/:id` from another owner returns 403 and the stored record is unchanged.
- [ ] `PATCH` accepts only the six editable fields, and a body carrying `ownerId` or `status` changes neither.
- [ ] A slug change is refused with 409 `SLUG_LOCKED` once the shop holds any copy, and the old slug answers the public route after a permitted change.
- [ ] `GET /api/shops/:slug` returns the public projection with no `ownerId`, `contactPhone`, `status` or `slugHistory`.
- [ ] Hours validation refuses six days, a duplicate day, a closed day with times and a close time before the open time, each with a field message naming the day.
- [ ] The unique indexes on `ownerId` and `slug` exist in the running database, and the index list is saved with the gate evidence.
