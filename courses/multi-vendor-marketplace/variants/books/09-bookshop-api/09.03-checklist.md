# Bookshop API gate

This gate runs on three tokens and one database you can reset. Mariam owns North Street Books. A second owner runs Campus Shelf. Hana is a student with no shop and no reason to reach these routes. Every request below is sent with curl and read as raw JSON, because a shop page that looks fine on screen proves nothing about who may write to it.

Write the expected table before you send anything. Six rows are enough: create for Mariam returns 201, create for Mariam again returns 409, read mine returns the same id, patch my own shop returns 200, patch Campus Shelf's shop returns 403, and the public read of North Street contains the seven public field names and no others. When a response disagrees with the table, the table is the authority and the route is the bug.

## Prove one shop, once

Create North Street Books with a full body: name, area, seven days of hours, pickup notes and a contact phone. Read the response and note the slug, which should be `north-street-books`, the id, and the fact that the body you sent did not contain a slug. Then count the documents in the Shop collection for that owner, which must be one.

Send the same create again with a slightly different area. The correct answer is a conflict with `SHOP_ALREADY_EXISTS`, and the important half of that answer is the absence of a new document. Confirm it with a count, not with the status alone, because a route can return 409 after it has already inserted. Then send a body that carries `ownerId` set to the other owner's user id and a `status` of suspended. The stored shop must still name Mariam and must still be active, which proves the route picks fields rather than spreading the body.

If you want the harder version of this check, send two creates at the same moment from two terminals and count again. One may answer 201 and the other must answer 409, and the count is still one. A sequential pair passes on a route with no unique index, so the parallel pair is the one that proves the database is holding the rule.

## Prove the boundary between two shops

Sign in as the Campus Shelf owner and patch North Street's shop id with a new area and a new name. The answer must be 403 with `NOT_OWNER`, the body must carry no shop fields, and a re-read of the document must show the old area and the old name. Save the raw request and the raw response together, because the pair is what makes the refusal evidence rather than a claim.

Then patch your own shop and confirm the change lands. Change the pickup notes to a sentence about the side entrance, then patch again with hours that break the rule: six days, a duplicate day, and a close time before the open time. Each attempt must return 400 with a field message that names the day, and each attempt must leave the stored hours exactly as they were. A partial write here is worse than a refusal, because the owner would see a saved form and a student would read half a week.

## Prove the slug behaves

Change the shop address while it has no copies: send a new `slug` value on the patch. The change is allowed, and the old slug must still answer the public route with the shop and a `canonicalSlug` that names the new address. Then create one listing for the shop, or set a copy to available through the seed, and try the same patch again. The answer must be 409 `SLUG_LOCKED` and the stored slug must be unchanged.

Create a second shop whose name is also Corner Books, from a different owner, and read both slugs. The second one must be distinct, must be readable, and must not be an empty string or a bare number if you can avoid it. This is also the moment to check the indexes in the running database, because a unique index that exists only in a schema file is the most common way for this section to pass in a test and fail in an interview.

## Prove the public payload is small

Read `GET /shops/north-street-books` with no token at all. The response must contain the shop id, slug, name, area, hours, pickup notes and the available copy count, and it must not contain the owner id, the contact phone, the account status, the slug history or the creation date. Read it again with Mariam's token and confirm the answer is identical, because the public route does not vary by caller and should not start to.

Then try a slug that does not exist and read the error. It must be a plain 404 with a fixed body. A message that suggests a similar shop name is a search box for every shop on the platform, and it belongs nowhere near an unauthenticated route.

## Prove the role check

Send all three authenticated routes with Hana's student token. Each must answer 403 with `ROLE_NOT_ALLOWED` and no record fields. A student has no shop, and a route that creates one for any authenticated user is a small bug now and a confusing one in module 10, when the client starts using `GET /shops/mine` to decide where to send a signed-in account.

The same check belongs in your test suite rather than only in this gate. A gate proves a route worked on one afternoon. A test proves it keeps working after the next refactor, and role checks are the first thing a refactor deletes because they look like decoration.

## Gate checklist

- [ ] The six expected responses were written down before the first request was sent.
- [ ] A create with a full body returns 201, and the returned slug is derived from the name rather than sent by the client.
- [ ] A second create for the same owner returns 409 `SHOP_ALREADY_EXISTS` and the Shop count for that owner is one.
- [ ] Two overlapping creates end with one document, and the response that lost is a 409 rather than a 500.
- [ ] A create body carrying `ownerId` and `status` leaves both fields at the server's values.
- [ ] `GET /shops/mine` returns the shop created by the same token and never reads an id from the query string.
- [ ] A patch from the other shop owner returns 403 with no shop fields, and the stored area and name are unchanged.
- [ ] A patch with six days, a duplicate day, a closed day with times, and a close before an open is refused four times with a field message naming the day.
- [ ] The pickup notes edit is stored, survives a reload, and appears in the public payload.
- [ ] A slug change before any copy exists answers the old slug with the shop and a `canonicalSlug`.
- [ ] A slug change after a copy exists returns 409 `SLUG_LOCKED` and leaves the stored slug alone.
- [ ] The public payload contains the seven public fields and none of `ownerId`, `contactPhone`, `status`, `slugHistory` or `createdAt`.
- [ ] An unknown slug returns a plain 404 with a fixed body and no suggested names.
- [ ] A student token is refused by all three authenticated routes.
- [ ] `db.shops.getIndexes()` shows a unique index on `ownerId` and a unique index on `slug`, and the output is saved.
- [ ] The raw 400, 403 and 409 responses are saved with their `error.code` values and no live tokens.

## Learning log

1. How many shop documents existed for Mariam after the second create, and what did the raw response contain? Name the status, the code and the count you read.
2. Which field in the create body did you send with a wrong value to prove the route picks fields, and what did the stored document contain instead?
3. What did the cross-shop patch return, and how did you prove the record was unchanged? Quote the response code and the two field values you compared.
4. Explain why the slug is allowed to change before the first copy and refused afterwards. Name the artefact that makes the change expensive once a shop has been trading for a week.
5. Which fields did the public payload omit, and why is the contact phone shown on an order page but never on a shop page?
6. Why does this module answer 403 rather than 404 when the wrong owner patches a shop, and which property of a shop record decides that choice?

## What a passing gate leaves behind

Three artefacts, not a screenshot. First, the raw responses for the six planned rows, with the document counts beside them. Second, the index list from the running database, because the one shop rule and the slug rule both live there. Third, the learning log with the numbers you actually received, including any row where the first response was wrong. A gate with no wrong row in it usually means the table was not written first.

Two honest limits belong in the write-up. Nothing here proves that the hours are correct, only that they are a valid pattern: a shop that says it opens at 07:00 and unlocks at 09:00 has passed every check in this module. And nothing here is reachable by a person yet, because the screens do not exist. Module 10 builds them, and its gate is the first place where a shop owner's experience is judged instead of a route's.

Do not commit tokens, and do not leave a development database seeded with a shop whose name you did not choose. The next module starts from a clean second account with no shop at all, and that account is easier to create now than to reconstruct under time pressure.
