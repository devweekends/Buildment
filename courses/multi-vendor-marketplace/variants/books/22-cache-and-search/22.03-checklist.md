# Cache and search gate

The gate is a set of readings, not a description of code. Bilal's ghost copy and a search that scans every edition are both invisible to a learner who reads the source and believes it. Five artefacts settle the question: two request timings on one edition, one sale that clears the summary immediately, one `explain()` output for each search branch, one page rendered with Redis stopped, and one failed lookup that returns an honest empty state.

Set up the fixture before the first reading. One edition with three available copies in three grades at three shops, one student session, one shop owner session, and a Redis server you can stop and start from the terminal. Record the edition id, the three Listing ids and the shop ids in the learning log, because every later claim refers to them.

## Gate checklist

- A first request for the edition reports `source: "database"` and a second within the TTL reports `source: "cache"`, with both durations recorded.
- A sold copy is absent from the very next edition request, with no wait for the TTL.
- A regraded or repriced copy shows its new grade and price on the very next request.
- A withdrawn copy disappears from the summary, and its shop no longer appears as an offer.
- The ISBN branch of `GET /search` returns one edition with `mode: "isbn"` and an index scan in `explain()`.
- The text branch returns matches sorted by text score, and `explain()` names a text stage with a small number of documents examined.
- With Redis stopped, both the edition route and the search route return 200, and the log records the cache failure without a stack trace per request.
- A search for an unheld ISBN returns an empty list with `mode: "isbn"`, and the page says the ISBN was not found rather than "no results".

## Read the two timings together

Run the miss and the hit back to back, from the same client, with the key deleted before the first call. Write down both durations and the response sizes. A hit that is faster by only a few milliseconds on a laptop is not a failure of the cache; it is a small dataset. On a laptop the database answer may be 8 ms and the cached answer 3 ms. The difference that matters is the shape: the cached response did not run the aggregation at all.

Say which number you measured: server time from the log, or total time in the browser. Both are useful and they answer different questions. Server time shows the handler cost. Browser time on a phone also includes the network, and that part does not shrink because you cached a document. Do not present a laptop timing as a claim about the fellowship's phones.

A hit also has a second cost that a timing table hides. The cached summary can be two minutes old. Make the test after the invalidation run, not only after the timing run, so the artefact shows both speed and correctness rather than speed alone.

## Sell a copy and read again

Mark one copy sold through the real paid transition from module 20, not with a direct database edit. Then request the edition page once, immediately, and count the copies for that grade. The count must drop by one and the minimum price must be recomputed for the grade if the sold copy was the cheapest. If the grade had one copy, the grade should disappear from the list rather than appear with a count of zero.

Repeat the reading after a regrade and after a withdrawal. A regrade moves a copy between two grades, so two counts change at once, and a summary that only recomputes one of them is wrong in a way that looks like a rounding error. A withdrawal removes a shop from the grade row, which is the case learners usually miss because the Listing still exists in the database.

Then test the same sequence with Redis stopped and started between the write and the read. If the write happened while Redis was down, the delete failed. Start Redis again and request the page: the summary may still be stale until the TTL ends. That is the documented cost of the fallback, and the gate wants you to state it rather than discover it in front of a reviewer.

## Read the query plan honestly

For the ISBN branch, run the lookup in `mongosh` with `explain("executionStats")` and read three fields: the winning plan stage, `totalDocsExamined` and `nReturned`. An indexed identifier lookup examines one document and returns one. If the stage names a collection scan, the index is missing, the query is filtering on a different field, or the value you passed is a string that does not match the stored type.

For the text branch, run the same query with the same verbosity. The plan names a text stage, and the documents examined should be in the range of the matches. Compare it against a regular expression query on the same field, which examines every edition. Save both outputs side by side. The contrast is the evidence that the index is doing work, and it is more convincing than a duration measured on forty documents.

Do not edit the explain output to look tidy. Keep the raw JSON in `docs/EVIDENCE.md` under a heading that names the collection, the query and the date you ran it.

## Check the fallback, then check the recovery

Stop Redis, request the edition page, and read the response. It must be a 200 with the full summary, and the log should carry one warning naming the edition and a short error code. Restart Redis and request again. The first request after the restart rebuilds the key and reports `source: "database"`; the second reports `source: "cache"`. No request in the sequence may return a 500, a timeout page, or an empty list that looks like "this edition has no copies".

The same reading applies to search, which some learners forget because it does not use the offer cache. If the search route touches Redis at all, it follows the same rule. If it does not, request it anyway with Redis down and show a 200, because the gate should cover the routes a student reaches with one thumb rather than only the route with the cache.

Check the log volume too. A cache failure that logs a full stack trace on every request fills a disk on a small server and buries the useful line. One warning per failed request with a code and an edition id is enough, and a counter in `/health` is a cheap way to see whether the cache is degraded right now.

## Debug the three failures you will meet

The ghost copy has four likely causes, and they are worth checking in order. The invalidation call is missing from the sell path. The call passes an edition id taken from the request instead of from the stored Listing. The key builder in the delete differs from the key builder in the read, by a prefix or a separator. The write path commits and returns before the delete runs, and the process exits in between. The fourth is the hardest to see, and a log line immediately after the delete is the fastest way to confirm it ran.

The empty search has three likely causes. The text index was never created on the running database, because a schema declaration only takes effect when the index build runs. The query uses `$text` but the input went through normalisation that emptied it. The indexed fields do not include the field the student typed, which is common when a title is stored in a field the index does not cover.

The slow summary has two. The key is never hit because the value is written under a different id, or the TTL is so short that most requests miss. Read the hit ratio from the `source` field over twenty requests before changing the TTL, and remember that a cache with a low hit rate is not a bug if the traffic is genuinely spread across many editions.

## Learning log

1. Which edition, Listing and shop ids did you use, and what were the two durations you recorded for the miss and the hit?
2. Which call site clears the cache on a sale, and which field supplies the edition id it uses? What would go wrong if the request body supplied it?
3. Paste the winning plan for the ISBN lookup and for the text query. What did `totalDocsExamined` say in each case, and what did the regular expression query say?
4. What happened to the edition page with Redis stopped, and what does the first request after a restart report as its source?
5. Which of the four write paths would you test first in a code review, and which failure would a student notice soonest?

A gate that passes on the happy path and fails on a sale is worse than no gate at all, because it certifies the ghost copy. If the sale reading shows the copy still present, stop and fix the invalidation before running the rest. Do not lower the TTL and call the reading a pass: a shorter window makes the ghost shorter and leaves the defect in place.
