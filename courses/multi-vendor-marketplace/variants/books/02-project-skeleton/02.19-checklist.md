## How a reviewer reads this gate

Every box on this page is a claim, and every claim has evidence behind it that someone other than you can inspect. That is the difference between this gate and a quiz. A quiz asks what you remember. A gate asks what a stranger could confirm by looking at your repository, running two commands and reading the output.

So the useful question for each box is not "did this feel done?" but "what would I show someone?" A commit hash is evidence. A terminal paste of `curl -i` output is evidence. A screenshot of the Network tab is evidence. "It worked earlier" is not, because the reviewer cannot reproduce it, and neither can you next week.

A reviewer reads this page in order and applies one rule: if a claim cannot be reproduced from a fresh clone with the README, it counts as missing. That rule is strict on purpose. The point of Chapter 2 is not that the app once started on your machine: it is that the skeleton still starts on any machine that follows the instructions inside it.

## Chapter 2, Project skeleton checklist (gate)

Do **not** open Chapter 3 until every box is ticked and learning log answers are written below.

### Repository & structure

- [ ] Git repository exists at your marketplace project root (separate from course content folder)
- [ ] Root `.gitignore` excludes `node_modules/`, `.env`, and build output
- [ ] `git log --all -- "**/.env"` returns **empty** (no env file ever committed)
- [ ] Root `README.md` documents how to run server and client in two terminals

These four boxes prove that the repository is yours, that it is safe to share, and that someone else can start it. The first box settles scope: the app lives in its own history, not inside the guides folder, so nothing you commit here can be confused with course content. The second and third boxes are the pair that protects credentials, and they are not the same claim. The second inspects a file that exists now; the third inspects every commit that has ever existed.

That third box is the one people skip, and it is the only one that reaches backwards. A reviewer runs the exact command rather than trusting a glance at `.gitignore`, because deleting a secret in a later commit leaves it readable in the earlier one. An empty result is the proof; a single commit in the output means the ignore rule arrived late and the credential inside that file needs rotating.

The README box is where a reviewer starts, before any command of their own. They clone, they read, and they try the two commands you wrote. If the README names the folders, the two terminals and the ports, the clone reproduces your machine.

### Server

- [ ] `server/package.json` has `dev` and `start` scripts
- [ ] `server/src/app.js` creates Express app, uses JSON middleware, exports app without listening
- [ ] `server/src/server.js` starts server on `process.env.PORT || 5000`
- [ ] Module folders exist: `auth`, `stores`, `products`, `cart`, `orders`
- [ ] `server/src/shared/` exists
- [ ] `npm run dev` in `server/` runs without crash
- [ ] `curl -i http://localhost:5000/health` returns **200** with JSON containing `"status":"ok"`

These boxes cover the structure of the server and the proof that it starts. The two-script requirement exists because development and production start the same code differently: `dev` watches files and reloads, `start` runs the plain entry point that a host would use. A project with only a `dev` script runs on your laptop and nowhere else.

The `app.js` and `server.js` split is the box worth reading twice. `app.js` builds the Express application and exports it without binding a port, which is what makes the app testable: a test can import it and send a request without a real socket. `server.js` is the only file that calls `listen`, so the port belongs to it alone. A learner who puts `listen` inside `app.js` passes the curl check and still fails the intent, because the app and the process have been fused.

The module folders and `server/src/shared/` are the structural decision the rest of the course depends on. `auth`, `stores`, `products`, `cart` and `orders` exist as empty homes now and fill up one chapter at a time, which is why a missing folder is cheap to fix today and expensive in Chapter 9. A reviewer opens the tree and looks for those five names plus `shared/`; then runs `npm run dev` and waits for the listening message rather than assuming it.

The curl box is the only functional evidence in this group, and a reviewer reads three parts of the output. The status line should say `200 OK`, the `Content-Type` header should say JSON, and the body should contain `"status":"ok"`. A 200 with an HTML error page, or a JSON body without that key, fails the box even though the server answered.

### Client

- [ ] Vite React app in `client/` with `pages/`, `components/`, `api/`, `hooks/`
- [ ] React Router renders Home at `/`
- [ ] `client/.env.example` documents `VITE_API_URL`
- [ ] `client/src/api/client.js` reads base URL from env, no hardcoded localhost in components
- [ ] `npm run dev` in `client/` runs without crash
- [ ] Home page displays **live** health status from API when server is running
- [ ] Home page displays **error state** when server is stopped (not hardcoded success)

This group moves the proof from the terminal to the browser. The folder and router boxes are structural: the four folders exist so later chapters have named addresses, and the router renders Home at `/` so the app has a real URL rather than a component that happens to be mounted. A reviewer opens `src/App.jsx`, finds the route table, and checks that `/` maps to the Home page they can see.

The environment-variable pair is about where the server's address lives. `client/.env.example` documents the variable so a clone knows what to set, and `client/src/api/client.js` is the only file that reads it. A reviewer greps the client for `localhost` and expects to find it in the API helper and the example file, nowhere else. A hardcoded address inside a component works today and breaks the moment the API moves.

The last two boxes are the pair that cannot both be faked. A page showing "status ok" from a constant passes the live box and fails the error box, because stopping the server changes nothing. Doing the failure test in reverse is the honest order: stop the server, reload, confirm the page says something is wrong, restart the server, reload, confirm it recovers. Two screenshots from that sequence are stronger evidence than any description.

### Integration

- [ ] CORS configured so browser can call API from Vite origin
- [ ] Browser Network tab shows successful `GET` to `/health` with 200
- [ ] End-to-end verification from **2.16** completed

These three boxes are the reason Chapter 2 exists. Each half working alone proves two programs start; only a completed request proves they are wired to each other. CORS is the box that most often fails quietly, because the server can be perfectly healthy while the browser refuses to hand the response to your code.

The Network tab box is how a reviewer reads that failure. They open DevTools, load Home, find the `GET` request to `/health`, and check the status, the request URL and the response headers. A request that appears in red with a CORS message and no status is a server header problem, not a client bug, and the fix belongs in the Express CORS configuration rather than in the React component.

The end-to-end box is a summary rather than a new action: it asks you to have done the 2.16 sequence once, with both terminals running and both screens visible. A reviewer who sees a screenshot of the Home page showing a live status, next to a terminal showing the server log line for that request, has seen the whole loop in one image.

### Understanding (self-check, explain aloud)

- [ ] I can explain **module-based** vs layer-based structure and why this course chose modules
- [ ] I can explain what runs in **browser** vs **Node server**
- [ ] I can explain why **`app.js` and `server.js` are separate**
- [ ] I can point to where **auth** and **products** code will live in my tree

These four items have no artifact to submit, which makes them the easiest to tick dishonestly. The evidence is a conversation: a mentor points at a folder and asks what will live there, or asks what happens when a student opens Home. If the answer needs the notes, the chapter is not finished.

They are also the items that predict Chapter 3 onward. Someone who can explain the client and server boundary will not try to query MongoDB from a React component in Chapter 13. Someone who can explain the `app.js` split will not add `listen` to a route file when a later chapter adds a test. Explaining aloud is the cheapest test of whether the structure has become obvious.

### Learning log, write now

Answer **in your own words** in the fields below. The log is not a summary of the chapter, it is your record of the decisions you made and the evidence you collected, written for a reader who was not there.

Six questions follow, and each one has a different job. Two ask you to reconstruct structure (the tree, the module argument), two ask you to trace behaviour (the request path, the failure test), and two ask you to reason forward (secrets, and what Chapter 4 will add to `/health`). Answer them in that spirit: a tree with one sentence per folder is worth more than a paragraph of praise for folder structure.

1. **Draw or paste your folder tree** (server + client) as it stands after Chapter 2. Annotate one sentence per module folder describing its future job.

2. **Why did this course require module-based folders instead of layer-based?** Use the "add discount codes" or "add products feature" argument, not "because the course said so."

3. **What happens at runtime when a user opens your Home page?** Trace the path: browser → React → fetch → Express → response. Mention ports and CORS.

4. **Why must secrets like `MONGODB_URI` (coming Chapter 4) live only in `server/.env` and never in the React app?**

5. **What did you verify in the failure-mode test (server stopped)?** Why is error UI important even for a health check demo?

6. **What will change on `/health` in Chapter 4 when MongoDB connects?** Speculate based on course outline, one paragraph.
