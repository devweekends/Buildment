# Cart API gate

This gate is about refusals and ownership, because those are the two things a cart API can get wrong without looking wrong. A cart that adds an available copy looks correct in a demo. The same cart can still let two students share a cart, add a sold copy, or keep a line for a copy another student is paying for. None of that shows up unless you test it on purpose.

Set up three fixtures before you start. Student A and Student B, each with a token, and five copies: one available at North Street, a second available copy of the same edition at Campus Shelf, one sold copy, one held by a checkout, and one archived. Write the expected table of five results and one warning before you send a single request. When the results disagree with the table, the table is the authority, not the response.

## Prove one line per copy

Add the North Street copy as Student A, then add it again. The first call is a 201 with a cart that contains one line. The second is a 409 with the duplicate code and the same cart body, and the stored cart still has one line. If the second call created a second line, the unique index is missing from the database rather than from the schema, which is a common way to be wrong: the schema declares it and the running database never built it.

Then send both adds through a barrier so they overlap. A learner who tests sequentially will pass while the race is still open, because the read in the first request finishes before the second request starts. Assert one line and one 201, and inspect the second response for a 11000 translation rather than a 500.

Remove the line and confirm the cart is empty and the Listing is unchanged. Adding to a cart must not change a copy's status, so read the Listing document before and after every cart operation in this gate and confirm it still says available.

## Prove each refusal

Work down the fixture table. A sold copy returns a conflict naming the sale, not a generic failure. A held copy returns a conflict that says another student is paying, which is a different sentence from sold. An archived copy returns a conflict about the shop withdrawing it. A copy id that does not exist returns not found, and an id that is not a valid object id returns a request error with a field name.

Then check that the codes, not only the messages, are distinct. Search your client code for string matching against the message. If the cart page decides what to render by comparing English text, the codes are decorative and the next wording change will break the page.

Confirm the response body for each refusal also carries enough for the page to offer a next step. A sold copy should be able to lead to other copies of the same edition, which means the response or a follow-up request knows the edition. A page that can only say "cannot add" leaves the student with a dead end on the one screen where she was ready to buy.

## Warn on two copies of one edition

With the North Street copy in the cart, add the Campus Shelf copy of the same edition. The add succeeds and the cart comes back with a warning that names the edition and both lines. Reload `GET /cart` and confirm the warning is still there, because it has to be computed on read rather than stored from the add.

Then remove one of the two lines and confirm the warning disappears. A warning that persists after the condition is gone is worse than no warning, because the student cannot clear it. Check the warning does not appear for two copies of different editions, which is the ordinary three book cart from module 15.

Read the cart response with two copies of one edition and confirm the subtotal counts both lines, because both are real purchases. The warning is advice, not an exclusion, and a subtotal that quietly drops the second copy would understate the amount the student is about to pay.

## Revalidate when a copy changes state

Add an available copy as Student A, then change that copy to sold in the database. Call `GET /cart` and confirm the line comes back with the sold state, the copy's facts intact, and no path to purchase. The line must still be present, because a cart that silently removes it hides the sale from the student who is now short a book.

Repeat for held, archived and deleted. A deleted Listing is the interesting one, because a join that drops missing rows would make the line vanish without explanation. Return the state as missing and keep the line until the student removes it.

Then confirm the totals react to the state change. A sold line must leave the payable subtotal and enter the attention count. Write the two numbers in the learning log before and after the change, because that pair is the evidence that the page will not charge for a book the student cannot receive.

## Scope the cart by session

Sign in as Student A, add two copies, and record the cart body. Sign in as Student B and call `GET /cart` with A's token replaced by B's. B must receive an empty cart, not A's, and no field in B's response may contain A's line ids or A's student id.

Then try to make the API accept an identity. Add a `studentId` query parameter and a `cartId` parameter with A's values to B's requests. The route must ignore them, and the test should assert that the response is still B's cart. A route that honours a parameter for convenience is an authorisation hole with a helpful name.

Try to remove A's line with B's token. The delete must fail or match nothing, and A's cart must still have both lines afterwards. Check the raw response and the database, because a 404 from a filter that scoped by B and matched nothing is a correct outcome and a 200 with an empty cart is not.

Finally, sign in as a shop owner and call all three routes. Each must return a role failure. A shop owner has no cart, and a route that creates one for any authenticated user is a small bug now and a confusing one in module 19, when checkout asks which student owns the attempt.

## Gate checklist

- [ ] The five expected results and the one warning were written down before any request was sent.
- [ ] Adding the same copy twice returns one 201 and one 409, and the stored cart has one line.
- [ ] The overlapping double add also ends with one line, and the duplicate key error is translated rather than surfacing as a 500.
- [ ] Removing a line never changes the Listing's status, and the Listing is still available before and after the gate.
- [ ] Sold, held, withdrawn, missing and invalid ids each return a distinct code with a usable message.
- [ ] No client code branches on the English message text instead of the code.
- [ ] A refusal for a sold copy leaves the page able to offer other copies of the same edition.
- [ ] Two copies of one edition raise a warning that survives a reload and clears when one line is removed.
- [ ] Two copies of different editions raise no warning, and both count toward the subtotal.
- [ ] A copy sold after it was added comes back as sold, keeps its facts, and leaves the payable subtotal.
- [ ] A deleted Listing comes back as missing rather than disappearing from the cart.
- [ ] Student B cannot read, remove or influence Student A's cart, and injected identity parameters are ignored.
- [ ] A shop owner token is refused by all three cart routes.
- [ ] `GET /cart` runs a bounded number of queries for a cart of twelve lines, and the number is recorded.
- [ ] The three cart routes, the schema indexes and the duplicate test are committed together.

## Learning log

1. What did you predict for each of the five fixtures, and which prediction was wrong? Name the copy and the code you expected against the code you received.
2. How did the overlapping double add behave, and what did the second request receive after the duplicate key error? Quote the index that made it true.
3. What were the payable subtotal and the attention count before and after you sold a line, and which function decides that split?
4. Which request did you use to try to read Student A's cart as Student B, and what did the raw response contain? Did any field leak A's identity?
5. Why does the cart keep a stale line instead of deleting it, and what does the page offer the student in that state?
6. How many queries does `GET /cart` run for twelve lines, and which lookup would you remove first if the number were too high?

A passing gate leaves a test file, a fixture description, the two-number total pair and the raw responses for the cross-student attempts. A browser screenshot of a cart with three books proves almost none of it.

Commit the routes, the schema and the tests with a message that names the gate. Do not build the cart page in module 17 against untested routes: the page will render whatever the API returns, including another student's cart, and it will look perfectly normal while it does.
