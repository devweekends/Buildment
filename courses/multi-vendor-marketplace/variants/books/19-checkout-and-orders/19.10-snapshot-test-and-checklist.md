# Snapshot test and checklist

Hana's reading list may contain three exact physical copies from three Shops. The matcher recommends; checkout revalidates and holds. A conditional single-Listing update gives one Checkout ownership of each copy. The multi-Shop procedure either secures every selected Listing and writes complete pending Shop Orders, or unwinds its own claims and leaves no payable partial plan. Each OrderLine freezes the Edition and condition offer Hana accepted. Student and Shop routes query under their own identities and show pending status accurately. Payment and the final held-to-sold transition remain for Hamesh M20.

## Show the one-winner evidence

Run two authenticated students against one available Listing. Both may have seen the same public offer before the test begins. Capture the successful pending response and the losing conflict. Query the Listing afterward: exactly one Checkout ID owns its current hold, with an expiry in the future. Count pending payable OrderLines for that Listing; there must be no more than one. Repeat on a fresh fixture with request start order reversed. The assertion should allow either student to win while preserving the one-holder invariant.

Test a sold, draft and archived Listing separately. None can be claimed. Test an expired hold takeover and then run the former holder's delayed cleanup; the new holder remains. Test another Listing of the same Edition and show it can still be claimed independently. These fixtures prove the status rule applies to a physical copy, not to every copy that shares an ISBN.

## Show the split and recovery evidence

Create a Cart with two North Street Listings and one Campus Shelf Listing. After valid checkout, inspect one Checkout, two pending Shop Orders and three held Listings with the same Checkout ID. Sum line amounts and Shop fees in minor units, then compare the sum of Shop Orders with the Checkout total. Send the same request key again and confirm the IDs and counts do not change.

Pre-hold the Campus Shelf Listing for another student, then run Hana's attempt. North Street claims must be released by Hana's Checkout ID, Campus Shelf's other holder must remain, and Hana must have no payable partial Shop Order. Force a stop after the first claim and after the first Shop Order insert in separate tests. Recovery must find the attempt, release own holds, remove or cancel partial Orders and reach a non-payable state. Run recovery twice and inspect that the second pass does no harm. A UI conflict alone is not enough evidence if records remain inconsistent.

## Show the condition snapshot evidence

Before checkout, change a selected Listing from Good to Acceptable or raise its price. The route should return a changed-offer conflict rather than quietly creating a payable Order. After a successful pending OrderLine, change the live Listing's grade, defects, price and first photo, and archive it. Read the stored OrderLine and the student and Shop routes. The frozen ISBN, Edition label, title, grade, defect notes, agreed price and photo reference remain what Hana accepted. If the seller API correctly blocks a held-Listing edit, use a controlled administrative fixture to test historical rendering without weakening normal seller permissions.

Show that Hana sees her own split Orders, Bilal cannot read them, North Street sees only its Order, and Campus Shelf sees only its own. Search full JSON for another Shop's note or fee, not just top-level counts. The Order routes must keep an archived Listing's history readable and avoid leaking hold IDs, internal review notes or payment credentials.

## Learning log

1. Which conditional update won the single-Listing race, and what did the other student receive? Include the final Listing status and Checkout owner.
2. How many Shop Orders came from three Listings when two belonged to North Street? Write each Order total and the Checkout total in integer minor units.
3. When one Shop's Listing was unavailable, which previously claimed Listings were released, and how did the release predicate avoid clearing a later holder?
4. Which Work, Edition and Listing fields were frozen on Hana's OrderLine? What changed on the live Listing after checkout, and what remained on both Order routes?
5. Which query conditions denied Bilal access to Hana's Order and North Street access to Campus Shelf's Order? Did the full JSON omit the other Shop's note and fee?
6. Why does the Checkout leave Listings held rather than sold, and which late-payment problem must M20 resolve before marking a copy sold?

A passing gate includes executable tests against the learner database behavior, safe HTTP traces, stored-record assertions and a short state diagram or transition table. A screenshot by itself cannot prove there was only one OrderLine. A mock-only test cannot prove the real database conditional update. A written claim that several sequential writes are atomic is incorrect unless the implementation uses a supported transaction spanning all of them. If the build uses compensation, show crash recovery and an idempotent second run.

The Hamesh roadmap's wording about marking copies sold during checkout needs instructor reconfirmation because payment occurs in M20. This learner chapter teaches a pending hold and postpones sold until verified payment and current ownership checks. Keep the variant unavailable until that refinement and the rest of the learner path are reviewed. A student should never be told a book is sold or ready for collection merely because a pending Checkout record exists.
