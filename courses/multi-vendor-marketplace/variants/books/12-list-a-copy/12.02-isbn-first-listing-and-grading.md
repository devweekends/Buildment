# ISBN-first listing, grade and price guidance

The form has one job: turn a book on the counter into a draft listing that points at the right shared edition, carries an honest grade and a price the owner chose with evidence in front of them. Everything else in this lesson serves that job. The route below is the contract the browser builds against, and the two error shapes in it are the difference between an owner who fixes a mistake in five seconds and an owner who reloads the page and gives up.

Start from the data you already have. Module 5 created the Listing model with `shopId`, `editionId`, grade code and rank, defect notes, `priceMinor`, currency and status. Module 11 created the ISBN module and the find-or-create route for editions. This lesson adds the write path that connects them and the read path that tells the shop what the market looks like.

## One contract for one typed copy

The create route belongs to the shop that is signed in, and the shop in the path must match the shop the server resolves from the session. The body carries the number the owner read off the book, the grade the owner chose, the defects they ticked, and a price in integer minor units. Title and authors are not part of the body unless the edition does not exist yet, and even then they are a suggestion to the shared catalogue, not a claim over it.

```js
// server/src/modules/listings/listing.routes.js (signatures only)
router.post("/shops/:shopId/listings", requireAuth, requireRole("shop"), createListing);
router.patch("/listings/:id", requireAuth, requireRole("shop"), updateListing);
router.patch("/listings/:id/status", requireAuth, requireRole("shop"), changeListingStatus);
router.get("/editions/:editionId/price-guidance", getPriceGuidance);
```

```ts
// the request body the form sends, plus the fields the server owns
type CreateListingBody = {
  isbn: string;                 // exactly what the owner typed, spaces and hyphens allowed
  editionTitle?: string;        // used only when no edition exists for this ISBN
  editionLabel?: string;        // e.g. "2nd edition, print"
  gradeCode: "new" | "like_new" | "very_good" | "good" | "acceptable";
  defects: Array<"highlighting" | "handwriting" | "water_damage"
    | "missing_access_code" | "torn_pages" | "ex_library">;
  defectNotes?: string;
  priceMinor: number;           // integer, in the currency's smallest unit
};
```

Three fields are deliberately absent. `gradeRank` is derived by the server, because a client that sends a label and a rank can send a pair that disagrees. `shopId` is resolved from the session, because a body field is a suggestion from the browser. `status` is not accepted on create at all, because every new copy starts as a draft.

The Listing level fields the route writes are these, and they are the ones the gate checks in Mongo, not only in a rendered page.

```js
// server/src/modules/listings/listing.model.js (fields that matter here)
shopId:      { type: ObjectId, ref: "Shop", required: true, index: true },
editionId:   { type: ObjectId, ref: "Edition", required: true, index: true },
gradeCode:   { type: String, enum: ["new", "like_new", "very_good", "good", "acceptable"], required: true },
gradeRank:   { type: Number, required: true, min: 1, max: 5 },
defects:     [{ type: String, enum: ["highlighting", "handwriting", "water_damage",
                "missing_access_code", "torn_pages", "ex_library"] }],
defectNotes: { type: String, maxlength: 500, default: "" },
priceMinor:  { type: Number, required: true, min: 1 },
currency:    { type: String, required: true },
status:      { type: String, enum: ["draft", "available", "held", "sold", "archived"], default: "draft" },
```

## Normalise first, and only once

Call the module 11 ISBN function. Do not copy its rules into the listing service, and do not trust the browser to send a clean number. The function returns either a canonical ISBN-13 or a field error with a message a person can read. The listing route turns that into a 400 and stops before it touches the Edition collection.

A valid ISBN the catalogue has never seen is a second case. The route asks for the minimum bibliographic fields, inserts the edition under the unique `isbn13` index, and on duplicate-key error 11000 reads the winning edition and continues. The shop's typed title is not written over the winner. This is the same insert-and-read path module 11 tested with two shops, reused rather than rebuilt.

A third case is the one that costs the most time at the counter: the ISBN is valid but the edition metadata is wrong in the catalogue. The route must not let the owner edit it. It returns a 403 with a message that names the reporting path, and the listing can still be created against the existing edition if the physical copy matches what the catalogue says. That distinction is a design decision, and it belongs in your notes: a wrong title is a catalogue problem, a wrong grade is a listing problem, and the same shop fixes only one of them.

## Location comes from the shop, not the copy

Where the book is picked up is part of what a student buys, and it is tempting to add an address field to the listing so the form feels complete. Resist that. Hamesh already stores the shop name, the area and the pickup notes from module 9, and a copy is collected from the shop that owns it. Duplicating the address on every listing means a shop that moves, or changes its opening hours for the exam period, has to edit every copy it sells, and the one it forgets sends a student to a locked door.

So the listing form shows the pickup area read-only, taken from the signed-in shop, with a link to the shop settings page where the owner can change it. The copy keeps its grade, defects, price and, from module 13, photographs of the actual copy. The shop keeps everything about where a person stands to collect it. When the browse route later joins shop names onto an offer summary, it reads the same record, so a student sees one location per shop rather than one per copy.

If a shop ever needs two collection points, that is a second shop record with its own owner and its own listings, not an address field on a copy. Write that decision in `docs/erd.md` next to the Shop to Listing arrow, because it is the kind of shortcut that gets added quietly during a busy week.

Notice what the trace does not contain: a quantity field, or a step that decrements anything. One submission creates one Listing for one physical copy. A shop with four copies of the same edition sends four submissions, and each gets its own grade, defects, photographs and sale state. If you find yourself adding `qty` to make the counter faster, stop. The whole catalogue model depends on that number not existing.

## Grade is a code, rank is derived

The grade is the marketplace's promise about condition, so it needs a written rubric, one canonical code per grade, and a rank the server derives. Store the code, derive the rank, and reject any request that tries to set both. A client that sends Acceptable with rank 5 would otherwise hand a water-damaged copy to every student who filtered for Good or better.

```js
// server/src/modules/listings/grades.js
export const GRADES = {
  new:        { rank: 5, label: "New" },
  like_new:   { rank: 4, label: "Like New" },
  very_good:  { rank: 3, label: "Very Good" },
  good:       { rank: 2, label: "Good" },
  acceptable: { rank: 1, label: "Acceptable" },
};

export function rankFor(code) {
  const grade = GRADES[code];
  if (!grade) return null;   // the route turns null into a field error
  return grade.rank;
}
```

The rubric is what the owner reads while holding the book. Write it once, put it beside the grade dropdown, and keep the same wording in the student-facing offer card.

| Rank | Grade | What the copy may show | Typical evidence |
|---|---|---|---|
| 5 | New | Unread, no marks, no shelf wear | Shrink wrap or perfect corners |
| 4 | Like New | Read once, no marks inside | Sharp corners, clean spine |
| 3 | Very Good | Light shelf wear, no markings | Creased cover, clean pages |
| 2 | Good | Visible wear or markings that do not hide text | Highlighting, name inside |
| 1 | Acceptable | Heavy wear, damage, or missing extras | Water damage, loose pages |

Defects are separate from the grade on purpose. A Very Good copy can have a name written inside, and a Good copy can have no marks at all but a badly creased cover. If defects are folded into the grade, a student cannot tell what they are accepting, and the later order snapshot cannot record it. Tick the defect flags, add a short note in the owner's own words, and let the grade sit beside them as a summary rather than a replacement.

Validation for this section is short and strict. An unknown grade code is a field error. A defect flag outside the enum is a field error. Notes longer than 500 characters are a field error. A grade of Acceptable with no notes at all is worth a soft warning in the UI, because "it is damaged" is not a description a student can use.

## Price in minor units, guidance from live copies

Prices are integers in minor units, the same convention the cart and the payment module use later. A price of `2300` means 2,300 minor units, and there is no floating point in the path anywhere. Validate a positive integer, reject anything with a decimal point, and take the currency from config rather than from the body, because a shop should not be able to price one copy of an edition in a different currency from the rest of the catalogue.

The guidance endpoint answers one question per grade: the lowest price among available copies of this edition, and how many copies are at that grade. It is a read over live listings, so it costs one aggregation rather than a stored field that has to be kept true by every write in the system.

```js
// server/src/modules/listings/price-guidance.js (the grouping, not the whole route)
const rows = await Listing.aggregate([
  { $match: { editionId, status: "available" } },          // drafts and sold copies are not the market
  { $group: {
      _id: "$gradeRank",
      gradeCode: { $first: "$gradeCode" },
      lowestPriceMinor: { $min: "$priceMinor" },
      copyCount: { $sum: 1 },
  } },
  { $sort: { _id: -1 } },                                   // best grade first
]);
```

The response shape the form consumes is a list, one entry per grade that has at least one available copy: `gradeCode`, `gradeRank`, `lowestPriceMinor` and `copyCount`. A grade with no available copies is absent rather than zero, because zero would read as a price. The route validates the edition id, returns 404 for an unknown edition, and never includes shop ids, seller notes or anything that identifies another shop's private data.

Two tests keep this honest, and both of them fail on a first implementation. Write them before the route.

```js
// server/tests/listings.create.test.js
test("rejects a rank that contradicts the grade code", async () => {
  const res = await request(app)
    .post(`/shops/${shopA.id}/listings`)
    .set("Authorization", `Bearer ${shopAToken}`)
    .send({ isbn: "1938168380", gradeCode: "acceptable", gradeRank: 5, priceMinor: 1600 });

  expect(res.status).toBe(400);
  expect(res.body.error.fields.gradeCode).toBeDefined();
});
// currently 201, and Mongo stores gradeRank 5 on an Acceptable copy
```

```js
// server/tests/price-guidance.test.js
test("ignores copies that are not available", async () => {
  // fixture: Very Good at 3100 available, Very Good at 2400 sold
  const res = await request(app).get(`/editions/${editionId}/price-guidance`);
  const veryGood = res.body.grades.find((grade) => grade.gradeCode === "very_good");

  expect(veryGood.lowestPriceMinor).toBe(3100);
});
// currently 2400, because the $match above has no status filter
```

The second failure is the one that matters commercially. Guidance that counts sold copies tells a shop to price against a book that is no longer for sale, and it does so silently, on every edition where something has ever sold.

## The two responses the form must render

A 400 is a field problem, and the browser should put each message beside the input that caused it. Use one envelope for every validation failure, so the form has one handler rather than a special case per route.

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Some fields need attention",
    "fields": {
      "isbn": "The check digit does not match this number",
      "priceMinor": "Enter a whole number of minor units, 1 or more"
    }
  }
}
```

A 403 is an identity or ownership problem, and it is not fixed by editing a field. The form shows a banner with the server's message and leaves the typed data in place.

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "This copy belongs to another bookshop"
  }
}
```

| Status | Code | Where it appears on screen |
|---|---|---|
| 400 | `VALIDATION_FAILED` | Under the ISBN, grade or price input named in `fields` |
| 400 | `EDITION_FIELDS_REQUIRED` | Under the title field, when the ISBN is new to the catalogue |
| 403 | `FORBIDDEN` | Banner above the form, no field highlighted |
| 403 | `EDITION_LOCKED` | Banner with the report-a-problem link |
| 404 | `EDITION_NOT_FOUND` | Offer to create the edition instead of a dead end |
| 409 | `LISTING_STATE_CONFLICT` | Banner, with a reload action |

The client helper stays small, because a large error handler is a sign the server sends too many shapes.

```js
// client/src/api/listings.js (shape only, no retry logic shown)
export function fieldErrorsFrom(error) {
  if (error.status === 400) return error.body?.error?.fields ?? {};
  return {};                      // 403 and 5xx are banners, not field errors
}

export function bannerFrom(error) {
  if (error.status === 403) return error.body?.error?.message ?? "You cannot change this copy";
  if (error.status >= 500) return "The server did not answer. Try again.";
  return null;
}
```

Two habits make this work on a phone. Clear a field's message as soon as the owner edits that field, so the red text does not follow them through the form. And never show the raw error object, because the owner is a bookseller, not the person who wrote the route.

## Draft, then publish

A create request returns 201 with a draft. Publishing is a separate call, and it re-checks every rule that matters, because the state of the world can change between two requests. The checks are cheap: the listing still belongs to this shop, the grade and price are still valid, and the copy has the evidence its grade requires. Module 13 adds the last one. This module's publish check is shorter and still refuses an incomplete draft.

Return a specific code when the publish check fails, so the listings table can show a reason instead of a generic error. `LISTING_INCOMPLETE` with a `fields` map is enough for this module, and it lets the same handler that renders a 400 from create render the publish failure too. One shape, two routes, one piece of form code.

The status transition itself should be a conditional update rather than a read, a check and a save. Filter on `_id`, `shopId` and `status: "draft"`, set `status: "available"`, and inspect the matched count. If it is zero, the copy moved, and the owner gets a 409 instead of a success message about a listing that is already held by another student's checkout.

## Verify with a path that fails

Three checks prove the route before the gate. First, the cross-shop denial: a PATCH from Shop B on Shop A's listing returns 403 and the stored price is unchanged. Read the raw response, not the rendered page, because a greyed-out button proves nothing.

Second, the grade pair: send an Acceptable code with rank 5 and confirm a 400 with `fields.gradeCode`. Then send the code alone and confirm the stored document has rank 1. The second half is what stops the bug from coming back through a different client.

Third, the guidance: with one available Very Good copy at 3,100 and one sold Very Good copy at 2,400, the guidance reports 3,100 and a count of one. Change the available copy to `held` and the Very Good row disappears instead of dropping to 2,400.

Acceptance criteria for this lesson are plain. A shop owner can type an ISBN, see the edition preview or create the edition, choose a grade, tick defects, read guidance per grade and save a draft. A second shop cannot edit that draft. A bad ISBN gets a field message that names the problem and keeps the typed text. An Acceptable copy cannot carry the rank of a New one.

## Bridge to the gate

The gate asks for three copies of the College Algebra edition from one shop, graded Acceptable, Good and Very Good, priced against the guidance it showed. That is the pile on the counter reduced to the smallest set that still tests the model: one shared edition, three owned copies, three real conditions, three prices. Module 13 adds the photographs that make the two lower grades defensible.
