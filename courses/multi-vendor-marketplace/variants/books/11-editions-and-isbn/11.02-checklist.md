# Edition identity gate and learning log

The gate starts with two independent shop accounts and an empty Edition collection in a disposable development database. Both shops will enter the same valid ISBN through differently formatted strings. The result must be one shared edition and two separately owned listings. A screenshot that happens to show one edition after a serial manual run is not enough; run a concurrent API test so both requests may reach the database before either receives a response.

## Validate the number, not just its shape

Run the ISBN unit tests. Show a valid ISBN-10 becoming a 978-prefixed ISBN-13 with a newly calculated check digit. Show a valid 979-prefixed ISBN-13 staying in 13-digit form. Try a bad check digit, a final `X` in the middle of a string and an input with a letter `O` in place of zero. Each invalid input must return a field error without inserting an Edition. Try the same valid ISBN with spaces and hyphens, and show that both forms produce the same canonical key. Save the test output; it is evidence that the server owns identity before a shop creates a listing.

## Race the shops

Send two `POST /editions` requests together from Shop A and Shop B. The requests should use the same ISBN but slightly different typed titles, so a silent overwrite would be visible. Query the database by normalized ISBN-13 and count exactly one Edition. One response may say created and the other reused. Both must return the same Edition ID. The stored title should match the row that won creation; a later request must not rewrite it. If a duplicate-key error appears in logs, the losing request should read and return the winner rather than fail the student's listing flow.

Verify the index itself. A query against the test collection's index list should show unique `isbn13`; the optional `isbn10` index should exclude documents without that field. Remove or disable the ISBN-13 unique index in a disposable copy of the test database and observe why the race test becomes unsafe; restore it before proceeding. Do not try this experiment on shared or production data. The lesson is that the database constraint, not a prior browser lookup, decides identity under concurrent writes.

## Keep copies owned and separate

Have each shop add one Listing pointing to the shared Edition. Give the copies different grades, defects, prices and photos. The edition page should show one title and two offers. Query both Listing rows and confirm each has its shop ID. Shop B must get 403 when PATCHing Shop A's listing; Shop A can change its own available listing. A shop owner must not rewrite the shared Edition title once copies use it. If the admin correction route exists, it should create an audit record and should not be callable by a shop account.

## Learning log

1. Explain why ISBN normalization happens before the Edition lookup and why check-digit validation is more than a length check.
2. Draw Work, Edition, Listing and Shop with arrows. Mark which record has the unique ISBN-13 key and which record is sold exactly once.
3. Describe the two-shop race. Name the database constraint and the response the losing request receives.
4. Explain why a shop that creates an Edition first does not own the shared Edition. Name the fields it does own on its Listing.

Commit the ISBN unit tests, concurrent API test, cross-shop authorization test, index declarations and updated ERD. Keep a log of the two Edition responses and the final database count. A mentor should be able to run the race test twice without producing a second Edition. If your implementation passes only when the tests run one request at a time, do not continue to reading-list matching. That later module assumes one canonical edition identity for every eligible copy.

## Debug the result before moving on

If the race creates two editions, inspect the canonical strings returned by normalization. They must be identical before you investigate concurrency. Next, inspect the actual database index list. A Mongoose schema declaration may not have built the index in the database you are testing. If the index exists, inspect its field and collation; the route must insert the same normalized field the index protects. Then rerun the test enough times to expose the competing requests without assuming that one successful run proves correctness.

If one shop's listing is missing after both requests return, follow the losing create path. It must receive the winning Edition ID and continue to create its own Listing under its own shop ID. A duplicate-key error should not end the whole user journey with a generic 500 response. If both listings exist but the second shop can edit the first, inspect the ownership predicate on PATCH. A frontend filter or a hidden Edit button does not protect the API. Capture the raw status code and response body for the unauthorized request.

Look at the edition page as a student, too. It should place shared title and edition metadata once at the top and show the two physical offers below it. Each offer needs its own grade, defects, photo, price and shop. If those facts appear on the shared Edition, another shop may overwrite them or the UI may imply every copy has the same condition. Correct the schema while only two seed listings exist; a later migration will be harder after orders and reading lists point at these records.
