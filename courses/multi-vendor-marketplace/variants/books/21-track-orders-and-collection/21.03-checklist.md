# Collection gate

This gate is the Week 3 demo, run as evidence rather than as a performance. It starts with a reading list for a course, goes through matching, cart, checkout and a test card payment, and ends with one copy collected at a shop with a code and a timestamp. Everything the earlier modules promised has to hold at the same time, in one run, with the records inspected afterwards.

Prepare the demo as a script with expected values. Write down the reading list, the grade floor, the four titles, the expected matched copies and the one title that nobody has. Then write the expected orders: which shop, which copies, which snapshot price, which collection fee, and the total in minor units. A demo that diverges from the script is a finding, not an improvisation, and the finding is the useful part of this gate.

## Run the demo from the reading list

Import or create the reading list for the course, set the grade floor to Good, and run the matcher. Three of the four titles should match copies at two shops, and the fourth should come back unmatched with a reason the student can act on. Add the matches to the cart and check the cart shows one line per copy, grouped by shop, with no quantity anywhere on the screen.

Pay with a documented test card and keep the Stripe CLI output and the API log side by side. When the payment succeeds, the checkout must show two orders, one per shop, each with its own snapshot lines and its own collection code. Read the orders back from the API rather than from the confirmation page, and confirm the paid timestamp, the payment intent id and the snapshot grade on every line.

Then compare the snapshot against the live copies. Change one sold copy's price and grade in the database, reload the student order page, and confirm the order still shows the grade and price that were paid for. This is the module 19 promise, and the demo is where it is easiest to break: a page that was built from a join to the live copy will look perfect until this exact test.

## Prove the code is server checked

Open the shop's queue and confirm it shows paid orders, the student's first name, the copies and the amount, and no collection code anywhere. Then mark one order ready for collection, reload the student order page, and read the code aloud from the screen. Note that the other shop's order is still in the paid state and still hides its code, because readiness is per order, not per checkout.

Type a wrong code at the shop's collect action. Expect a conflict with the mismatch code, the order still ready, and the attempt counter at one. Repeat until the limit and confirm the order locks with a distinct code rather than a generic failure. Reset the code as the shop owner, record the reason, and confirm the old code no longer works and the new one does.

Then type the correct code. The order becomes collected with a timestamp and the staff account, and the student order page reports collected with the same timestamp and no longer promises a collection. Try to collect it again and expect the already collected conflict, with the original timestamp unchanged. That last assertion is easy to skip and it is the one that proves the transition was conditional.

## Prove the ownership boundaries

Sign in as the second student and request the first student's order id. The response must refuse, and the raw JSON must not contain the first student's code, name or amount. Sign in as a shop owner from the other shop and request the collected order. It must not be found, because the query is scoped by stored shop ownership and not by the order id in the path.

Sign in as the student and attempt the ready action and the collect action. Both must be refused by role, and neither may change the order. A student who can mark her own order collected can claim a book she never picked up, which turns a handover record into a wish.

Finally, inspect what the shop can see about the student. The queue may show a first name and a contact method the handover needs. It must not show the student's other orders, budget, reading list or the codes for orders that are not ready.

## Check the phone screens

Run the checkout, the student order page and the shop queue at 360 by 640. The Payment Element must fit without sideways scroll, the collection code must be readable at arm's length, and the state must be text rather than a coloured bar. Check the student page with a screen reader: the code should be announced character by character and the state as a word.

Close the tab after the card confirmation and before the return page loads, then reopen the order list. It must show paid, because the webhook wrote it. This is the last time in the course where a browser can lie about money, and the demo is a good place to prove it does not.

Read the pickup notes on the student page for both shops. If one shop has no notes, the page must not invent opening hours. If a shop's notes say it closes at 15:00 on Friday, the student should see that next to the code and not three taps away.

## Gate checklist

- [ ] The demo script with expected matches, orders, snapshot prices and totals was written before the run.
- [ ] The matcher filled three titles from two shops and returned one unmatched title with a reason.
- [ ] The cart showed one line per physical copy, grouped by shop, with no quantity anywhere.
- [ ] The test card payment created two orders, one per shop, each with its own collection code.
- [ ] Every order line carries the snapshot grade, defects and price, and changing the live copy left the order unchanged.
- [ ] The checkout return page and the order list read paid from the database, including when the tab was closed before the return.
- [ ] The shop queue shows no collection code and no code hash at any state.
- [ ] Marking ready is per order, and the other shop's order stayed paid and hidden.
- [ ] A wrong code returns the mismatch code, leaves the order ready and increments the attempt count.
- [ ] Past the attempt limit the order locks with a distinct code, and the owner reset is logged with a reason.
- [ ] The correct code sets collected with a timestamp and the staff account, and the student page reports the same instant.
- [ ] Collecting a collected order returns already collected and does not overwrite the first timestamp.
- [ ] A second student cannot read the order, the code, the name or the amount in the raw response.
- [ ] Another shop cannot fetch the order by its id, and a student cannot call ready or collect.
- [ ] Checkout, student order and shop queue all work at 360 by 640 with readable state text.
- [ ] The collection code reaches the student and never the shop, and it is stored only as a hash and a sealed value that the shop never receives.

## Learning log

1. Which copies did the matcher choose for the reading list, and which title came back unmatched? Name the shop and grade for each matched copy.
2. What was the total in minor units for each order, and does it equal the sum of its snapshot line prices plus the shop's fee? Show the arithmetic.
3. Which live copy did you change after payment, and what did the student order page still show? Which stored field made that possible?
4. Where was the wrong code rejected, what did the shop page receive, and what did the order record look like afterwards?
5. Which filter in the collect route prevented a second collection from overwriting the first timestamp, and what happened to the attempt counter?
6. Which request as the second student or the other shop was refused, and did any field of the first student's data appear in the raw JSON anyway?
7. What did the student page show after you closed the tab during the payment redirect, and which server path wrote that state?

A passing gate leaves six artefacts: the demo script, the Stripe CLI log for the payment, the two student order responses before and after the live copy changed, the shop queue response showing no code, the collect attempts with their responses, and the screenshots at 360 pixels for the three screens. A video of a happy path with no records behind it does not pass.

Two honest limits belong in the write-up. Delivery is out of scope, so every order in this demo depends on a trip the student makes, and the pickup notes are the only thing standing between her and a wasted journey. And the refund path for a copy that cannot be handed over is stretch work, so a damaged copy found at the shelf is currently a cancellation conversation rather than a tested flow.

Commit the checkout page, the two order surfaces, the code issue and verify paths, and the tests with a message that names the Week 3 demo. Do not move to the performance layer with a collection flow that only works once: the next modules cache offer summaries and run background jobs, and both of them will expose any route here that reads state it should have checked.
