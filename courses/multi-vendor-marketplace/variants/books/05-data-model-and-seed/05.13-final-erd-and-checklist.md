# Final ERD and checklist

Open `docs/erd.md` next to the database. The ERD must show User to Shop to Listing as ownership, Listing to Edition to Work as catalogue reference, Student to ReadingList to WantListEntry as private demand, and OrderLine as a historical snapshot of one Listing sale. Label arrows by meaning. If a reviewer mistakes "references Edition" for "owns Edition," rewrite the label. A shared catalogue must remain shared even when only one shop currently has a copy.

Run the seed twice and show stable counts for three fictional Shops, Works, Editions, graded Listings and a demo ReadingList. Show the actual unique ISBN-13 index and partial unique ISBN-10 index. Create two simultaneous Edition requests with the same canonical ISBN and show one Edition survives. Then create separate Listings from two Shops and show one Edition page with two offer cards. A serial screenshot alone does not prove the uniqueness rule.

Test a Good-or-better filter with one Acceptable and several qualifying copies. Verify the returned Listings include their defect notes and prices, and a missing reading-list item creates one WantListEntry rather than one per page refresh. Ask another student for the ReadingList ID and confirm a raw API denial. Ask Shop B to edit Shop A's Listing ID and confirm denial. Inspect the database after both denied requests for accidental writes.

Create a fixture OrderLine for a chosen Listing, then reprice or regrade the current Listing. Its receipt snapshot must retain the agreed title, ISBN, grade, defects and price. Mark the fixture as a model test, not evidence of a verified payment. The later checkout module will claim an available Listing atomically and split paid orders by Shop. The model now needs the fields to support those transitions, but it does not yet implement them.

The gate passes when the committed ERD, seed counts, index list, raw denials, edition race and snapshot check agree. In a short oral explanation, identify which record an ISBN names, which record a student buys, and why a shared Edition must not carry one shop's price or condition. If you need to point at a generic Product record to answer, revise the model before moving to authentication and the listing workflow.

## Learning log

1. Draw Shop ownership of Listing separately from shared Work and Edition identity. Which record names a physical copy?
2. Show one ISBN race result and the actual unique index. Why is a prior findOne check insufficient?
3. Regrade an available Listing after a fixture sale. Which OrderLine facts remain unchanged, and how does the reading-list grade floor use current Listing data?

## Defend the shared identity aloud

Ask a peer to take one seeded ISBN and find its Edition, Work, and every Listing under it. They should see one shared bibliographic record and separately owned physical copies. Ask them to identify the Listing a student actually bought and the fields preserved in its OrderLine snapshot. If the answer is "the Edition was sold," revise the ERD caption and the Cart link. An Edition can have no available offers temporarily while still being required on a reading list and still being listed again later.

Run one concurrent duplicate-Edition test and keep both raw results. Show the unique index in the database. Then run a wrong-Shop Listing edit and wrong-student ReadingList read; both must be denied without a write or private response. Filter Listings by a Good grade floor and one accepted Edition, and show that a cheaper Acceptable copy and a Very Good wrong-edition copy are excluded for different reasons. The evidence should make the model's relationships observable, not just visible in a diagram.

Check the seed after two runs and one interrupted repair run. The Shops, Editions and Listings keep stable IDs and counts; a missing fixture is restored without multiplying the others. Link every real ISBN to a publisher source and mark all Shops and students fictional. A reviewer should be able to inspect the fixture offline while using the committed source note to verify bibliographic identity when connected.

Finally, state the boundary of this gate. It establishes Work, Edition, Listing, grade, ReadingList, WantListEntry, Cart and OrderLine shapes with initial privacy and uniqueness checks. It does not yet prove exact edition entry UI, concurrent last-copy checkout, verified Stripe payment, background want-list alerts or deployment. Those later modules must supply their own tests. A green schema audit is a foundation, not evidence that a student can already buy a book safely.

For the learning log, include the exact edition ISBN, the Listing ID selected for a fixture sale, and the owner Shop ID. Explain how the grade threshold query uses the current Listing, while the receipt reads the historical OrderLine. Then describe a wrong-Shop PATCH and a wrong-student GET with their raw statuses and unchanged records. A short answer with these IDs gives a mentor evidence that the model is connected end to end instead of a memorized definition of normalization.
