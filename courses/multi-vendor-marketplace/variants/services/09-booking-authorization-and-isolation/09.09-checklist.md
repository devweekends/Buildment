# Booking authorization gate

Demonstrate an authenticated client who can read their own Booking and cannot read another client's by swapping only the Booking ID. Demonstrate a provider who can see their own agenda and confirmed delivery details but cannot see another provider's Booking, Order share or private TimeOff reason. The evidence should show the HTTP status and response body shape, not only a green test count. A valid login is a precondition for most of these requests, not proof of object permission.

Commit `docs/AUTHORIZATION.md` with rows for client Booking detail and list, provider agenda, Service update, TimeOff update, Order share detail, checkout status, cancellation request and calendar export. For each row, name the caller relation, allowed action, Booking state predicate and field projection. If a route is scheduled for a later module, label it planned rather than implemented. A reviewer should be able to point from a route to its row, helper and direct HTTP test.

The evidence that counts is a short transcript, not a coverage percentage. For one protected route, paste the request line, the response status and the response body with private values replaced by fixture tokens. Do that once for the rightful participant and once for the cross-party caller. A reader should be able to see that the first response carried the allowed keys and the second carried none of them. Two routes are enough to show the pattern: Booking detail and Service update. The gate is not a test count; it is proof that the decision model reached the wire.

## Gate checklist

- [ ] `requireRole` uses trusted authentication context and denies missing or stale capability where policy requires current state.
- [ ] `assertProviderOwner` resolves Provider.userId from the session and rejects a foreign Provider ID or Service ID.
- [ ] `assertBookingParticipant` distinguishes clientId from Provider.userId and checks the exact Booking for the requested action.
- [ ] Service and Booking writes include owner and state conditions in the final database update, not only a distant pre-read.
- [ ] Private Booking detail uses the documented nonrevealing response for both foreign and nonexistent IDs.
- [ ] Client lists are scoped to session userId; provider agendas are scoped to the caller's owned Provider ID.
- [ ] Held provider views omit client home address and private online link; confirmed views include only delivery fields required by location type.
- [ ] Provider Order views contain only that provider's share of a multi-provider CheckoutAttempt.
- [ ] Direct two-client, two-provider ID swaps are denied on read, write, list and export paths without side effects or private values in errors.
- [ ] A dual-role User keeps their own client rights without gaining another Provider's data.
- [ ] Support or admin access is an explicit narrow audited policy, not a blanket helper bypass.
- [ ] Matrix, helpers, route tests and exact response projection assertions are committed.

Read the list as one decision model rather than twelve separate chores. The first three items place the checks, the fourth keeps them at the write boundary, the middle items cover the shapes that leak most often, and the last three cover the cases that a single-role fixture hides. A gate that ticks the helper items while leaving the route tests unwritten has built the tool and not the proof. Work down the list in order and the last item will be true by the time you reach it.

## Learning log

1. Rami has a valid access token and knows Amal's Booking ID. Which relationship must the route check before returning the record?
2. Omar has a provider role and knows Sara's Service ID. Why is `requireRole('provider')` insufficient for an update?
3. Sara owns an unpaid at-home hold. What can her calendar show, and which field should wait for confirmation?
4. A client list route accepts `?clientId=amal`. What must establish its base owner filter, and what can the query parameter still do safely?
5. A User is both a provider and a client of another provider. Which relationship decides their view of the purchased Booking?

Answer with M6 field names and one direct HTTP request for each example. If an answer uses a path parameter as proof of ownership, revisit the helper. If an answer says the whole Booking document is safe because the caller is a participant, revisit field projection. If the learner cannot find an authorization row for a route, keep the gate open and add it.

Take question 4 as a worked trace, because it is the one most often answered wrongly. A client list route receives `?clientId=amal` from Rami's browser. The base filter must come from `session.userId`, so the query is scoped to Rami before the parameter is read. The parameter can then narrow the result inside that scope, which for Rami matches only his own ID. If the handler instead builds the filter from the parameter, Rami becomes Amal by editing a URL, and no amount of authentication prevents it. The safe version ignores the parameter when it disagrees with the session, or returns an empty list, and the test asserts both outcomes.

Run the cross-party suite in a scratch database. Include fixture names, command, positive and negative status counts and one redacted response per route family. Verify that a denied mutation left the database unchanged and generated no notification. Verify a rightful client and provider can still complete their allowed tasks. A system that denies everyone is isolated but not usable, so positive evidence matters.

Ask a reviewer to choose one route not highlighted in the lesson, such as a calendar export or cancellation preview. They should trace its principal, object lookup, action rule, state rule and serializer. Record one issue they found and the exact change made. The module passes when the same decision model covers a direct API call, a nested Order path and a response property, rather than relying on UI visibility.

Keep later policy decisions visible. M19 checkout idempotency, M20 webhook authority and M22 cancellation rules add new routes and states. They must extend the matrix and tests. This gate establishes a deny-by-default foundation; it does not pre-authorize every future Booking mutation. Preserve the reviewed matrix as a living contract while the remaining course modules build their features.

One failure mode is worth naming before you close the gate. The helpers exist, the tests pass, and a route added during the same week never calls either. Nothing in the suite fails, because nothing tests the new route. That is why the route count in the review matters: compare the routers to the matrix rows and to the test names, and treat any route with a row but no test as unfinished. A gate that stays open for one honest gap is more useful than a closed gate with a silent one.
