# Practice setup gate

The gate is a walk through the browser with a new account, and it takes about ten minutes when the code is right. Sign in as a provider who has no practice record. Open `/provider`. You should land on the setup page, and the address bar should say so. Fill the form, confirm the suggested zone, submit once, and arrive at the provider area. Then open `/provider/settings`, change the headline, save, and reload to see the saved value.

Record the walk in three places. Put the request and response evidence in `docs/EVIDENCE.md`, put the decision and the open questions in `docs/LEARNING-LOG.md`, and put the screenshots or text transcripts in the evidence file at 360 pixels wide. A mentor who cannot repeat the walk from your notes cannot review this module, no matter how good the screenshots look.

## Show the routing decision

The first observation is the redirect itself. Note the status the profile request returned, the code in the body, and the route you were sent to. A redirect that arrives for the wrong reason is a defect even when the destination looks right, so read the network entry rather than the address bar alone.

The second observation is the return path. Sign out, clear the practice record for a scratch account, then open `/provider/settings` directly. After setup completes, the browser should arrive at settings rather than the provider home. That shows the guard passes a location and the setup page honours it. Try the same walk with a location outside the provider area by editing the stored state in a scratch client, and confirm the redirect stays inside the provider area.

The third observation is the failure case that must not redirect. Stop the API process, reload `/provider`, and confirm the page shows an error panel with a retry rather than the setup form. Start the API again, press retry, and confirm the provider area appears. This is the check that separates a routing gate from a redirect loop, and it is the one most likely to be missing.

## Show one record and one zone

Count the providers for the test account after setup: one. Then submit the setup form twice in a row by pressing the button twice while the first request is pending. The client should send one create, or the second should receive the conflict and load the existing profile. Either way the database holds one row, and the count is the evidence.

Show the zone decision in the form. Note the value the picker suggested, the value you submitted, and the current time shown beside it. If the browser zone and the practice zone differ, use that case: it proves the picker is a suggestion rather than a hidden default. Then open settings, change the zone, and confirm the dialog appears before any request is sent. Cancel once, and check that no request reached the server.

## Show the phone layout

Set the browser to 360 CSS pixels wide and walk the same three pages. There should be no horizontal scrolling at the page level, every control should be comfortably tappable, and the save button should be reachable without an overlay covering it. Tab through the setup form with the keyboard, from the display name to the submit button, and confirm the focus order matches the visual order and that each error message is announced when it appears.

A text transcript is acceptable evidence when a screenshot is hard to capture on your device. Record the element sizes you measured, the scroll width and the client width, and the order of the fields. The point is to leave something another learner can reproduce, not to create a polished image.

## Gate checklist

- [ ] A provider with no record who opens any provider route lands on `/provider/setup`.
- [ ] The redirect uses a replace navigation, so pressing back does not bounce.
- [ ] The intended path is restored after a successful create, and the redirect stays inside the provider area.
- [ ] A failed profile request with a `500` shows an error panel with a retry and never redirects to setup.
- [ ] The setup form creates one record, disables the button while pending, and maps `409 PROVIDER_EXISTS` to the existing profile.
- [ ] The zone picker defaults to a recognised browser zone, is editable, and shows the current time beside the chosen zone.
- [ ] The submitted zone reaches the API as a named zone and is stored as one.
- [ ] Settings saves through `PATCH /api/providers/:providerId` with the caller's own identifier and the loaded revision.
- [ ] A zone change in settings requires confirmation that names the consequence for published hours.
- [ ] No page scrolls horizontally at 360 CSS pixels, and every control has a target of at least 44 by 44 CSS pixels.
- [ ] Form errors are attached to their fields and announced, not shown as colour alone.
- [ ] `docs/EVIDENCE.md`, `docs/LEARNING-LOG.md` and the decision note record this walk.

## Learning log

1. Which API results send a provider to setup, which send her to sign in, and which keep her on the current route with an error? Name the status and code for each.
2. Why does the setup page sit outside the guarded route group rather than inside it with an exception?
3. A provider signs in on her phone in Berlin while her practice is in `Asia/Gaza`. Which zone should the picker suggest, which should it submit, and what does the preview show her?
4. After a successful create, why must the cached `missing` result be replaced before navigating?
5. What breaks for a learner on a phone when a form is wider than 360 CSS pixels, and which measurement proves the fix?

Answer with the status code, the route and the field name where they exist. For the first question, "it shows an error" is incomplete; the failure case that matters is the one that must not redirect. For the fourth, describe what the guard reads on the next render. For the fifth, name the two numbers you compared.

Then write the two gaps this module leaves open, in your own words. The first is readiness: setup creates a record, but a provider with no service and no weekly hours is not bookable, and the readiness decision arrives in Module 13. The second is the hours page, which is a placeholder until the weekly grid exists. Naming both keeps the module's claim honest: the provider can start, and she cannot yet sell.

## Bridge to services

The provider can now create and edit a practice in the browser. The next module gives her something to sell. It builds the Services API with a duration in whole blocks, a price in minor units, a buffer, a location type and a cancellation policy, along with create, edit and archive routes that refuse a cross-provider write and stop an archived service from being booked.

Before you move on, check one thing that will matter there. Open the provider row you created and read the `scheduleRevision` value. The next module increments it on some writes and the module after that relies on it, so a profile that cannot return a stable number will cause conflicts you cannot explain later.
