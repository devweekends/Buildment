# Onboarding, settings and the routing gate

The four provider pages can be written in any order, and the guard is usually written last. That order creates the loop this lesson is designed to prevent. Each page assumes a profile exists, the setup page assumes one does not, and the guard ends up guessing which page the person should see. Build the guard first, with its three outcomes, and the pages become simple.

The provider area is a route group with its own layout. The layout renders the practice name, the working zone and a short navigation between the dashboard, services, hours and settings. It loads nothing about readiness yet. What it does share is the profile query, so every page reads one cached object rather than four nearly identical requests.

| Route | Requires a profile | Purpose |
|---|---|---|
| `/provider/setup` | No | Create the practice record, then continue |
| `/provider` | Yes | Practice home, empty states and next steps |
| `/provider/settings` | Yes | Edit profile fields, with a zone change warning |
| `/provider/hours` | Yes | Placeholder until Module 13 builds the weekly grid |

`/provider/setup` sits outside the guarded part of the group on purpose. A guard that also protects setup would redirect a provider with no profile to setup, then redirect again from setup to setup. Placing the unguarded route first is cheaper than special-casing the guard.

## One query, four explicit states

The client needs a hook that returns the profile and the reason it is missing. A boolean `isLoading` plus a nullable `profile` is not enough, because `null` then means "not loaded", "not created" and "request failed" at the same time.

```ts
type ProfileQuery =
  | { state: 'loading' }
  | { state: 'missing' }
  | { state: 'ready'; profile: OwnerProviderView }
  | { state: 'error'; retryable: boolean };
```

The hook maps `404 NO_PROVIDER_PROFILE` to `missing`, `401` to a sign-in redirect, `200` to `ready`, and everything else to `error`. That mapping is four lines and it is the whole security of the routing decision, so it deserves a test of its own. Write the test before the pages: stub a `404` and assert `missing`, stub a `500` and assert `error` with `retryable: true`, and assert that `error` never ends in a redirect.

The guard sits inside the group and reads the hook. While loading, it renders a skeleton with the layout's header so the page does not jump. When the state is `missing`, it renders a redirect to `/provider/setup` and passes the current path as the return location. When the state is `error`, it renders the retry panel in place. When the state is `ready`, it renders the route.

```tsx
function RequireProviderProfile() {
  const query = useProfileQuery();
  const location = useLocation();
  if (query.state === 'loading') return <ProviderSkeleton />;
  if (query.state === 'missing') {
    return <Navigate to="/provider/setup" replace state={{ from: location.pathname }} />;
  }
  if (query.state === 'error') return <ProfileErrorPanel onRetry={query.retry} />;
  return <Outlet context={{ profile: query.profile }} />;
}
```

The `replace` matters. A redirect that pushes a history entry leaves the broken route behind the back button, and a provider pressing back arrives at the page that just refused to render, which redirects again. Replacing the entry gives one history step instead of two.

The cache needs the same care. After the create call succeeds, the cached `missing` result is still the truth the guard holds, so the provider lands on the area and is immediately redirected back to setup. Invalidate the profile query on success rather than waiting for the next window focus, and make the setup page write the new profile into the cache before it navigates. A stale negative result is the second most common cause of a routing loop after a misread status code.

## The setup form

The setup page asks for the fields from Module 10 and one decision the form makes on the provider's behalf only as a suggestion: the working zone. Read the browser zone once when the page mounts, check that the runtime recognises it, and select it in the picker. Leave the picker fully editable, and place the current time in the chosen zone beside it.

```ts
function suggestedZone(): string {
  const zone = Intl.DateTimeFormat().resolvedOptions().timeZone;
  try {
    new Intl.DateTimeFormat('en-GB', { timeZone: zone });
    return zone;
  } catch {
    return 'Asia/Gaza';
  }
}
```

The fallback is the course's reference zone, and the form shows it as a selection the provider can change, not as a hidden default. A device that reports an empty or unrecognised zone is rare and it is still worth one line, because the alternative is a form that cannot submit and a validation error the provider cannot connect to anything she did.

The submit handler must do three things a first version usually skips. It disables the button while the request is in flight, because a phone on a weak connection invites a second tap. It maps `409 PROVIDER_EXISTS` to a reload of the existing profile instead of showing an error, because the conflict means another tab already finished the job. And it navigates to the return location only after a `201`, so a failed create cannot look like a successful one.

The form keeps its values on every failure except the conflict. A validation error from the server names a field, the form highlights that field, and the provider edits one value instead of retyping six. This is the same discipline Module 13 applies to schedule errors, introduced here on the smallest form in the course.

## The settings page and the zone warning

Settings loads the owner view and fills the same fields, so one component can serve both pages with a mode flag. The difference is the update path and the zone warning. Saving calls `PATCH /api/providers/:providerId` with the caller's own identifier, which the client already knows from the owner view, and sends the revision it loaded.

When the provider changes the zone, the save does not happen immediately. A dialog states the consequence in her words: published weekly hours are set in the old zone and will need review before new openings can be sold. Existing bookings keep the time the client accepted. Two buttons, one to keep the old zone and one to confirm the change. The confirmation carries the revision, so a provider who edited the same profile in another tab receives a conflict rather than overwriting the newer values.

The dialog is not decoration. A zone change with no warning looks like a display setting, and a provider who changes it on a trip will later wonder why her Monday hours moved on her students' clocks. Warning at the moment of the change, with the consequence named, is the cheapest place to prevent that support conversation.

A successful save returns the updated owner view, and the client stores the new revision with it. Do not compute the next revision in the browser, and do not assume the server returned the same object minus the changed field. The response is the new truth, and the form should rerender from it so the provider sees exactly what was stored, including any trimmed whitespace or rejected character.

Trace the failure version beside it. If the guard maps every non-200 result to a redirect, the third step becomes a `500` during a bad connection, and the provider is sent to a form that will create a duplicate. The unique index refuses it, the client shows a conflict, and the provider concludes that the product is broken. One correct status mapping prevents that sequence.

## Verify at 360 pixels

Test the three pages at 360 CSS pixels wide before testing them on a desktop. Check four things. No horizontal scrollbar appears at the page level, which you can confirm by comparing `document.documentElement.scrollWidth` with `window.innerWidth`. Every interactive control has a 44 by 44 CSS pixel target, including the zone picker and each location type option. The submit button is reachable without scrolling past an overlay. Error text appears under its field and is announced, so a screen reader user hears the message when focus returns to the input.

Add the width check to the test suite as a rendered assertion rather than a note in a document. A layout regression is easy to introduce with one long headline or one unbroken URL, and a check that runs on every build catches it before a learner on a phone does. The same test can assert that the form's labels are associated with their inputs, which is the cheapest accessibility guard available.

## Failing tests to write

- `guard_redirects_on_missing_profile` stubs `404 NO_PROVIDER_PROFILE` and expects a navigation to `/provider/setup` with the original path in state.
- `guard_shows_error_on_server_failure` stubs `500` and asserts no navigation occurred and a retry control is present.
- `setup_submits_once_while_pending` clicks submit twice and asserts a single `POST`.
- `setup_defaults_zone_from_browser` stubs `Intl.DateTimeFormat` to return `Europe/Berlin` and asserts the picker value, then changes it to `Asia/Gaza` and asserts the submitted body.
- `setup_conflict_loads_existing_profile` stubs `409 PROVIDER_EXISTS` and asserts the page moves on without a second create.
- `settings_zone_change_requires_confirmation` changes the picker, submits, and asserts no request was sent before the dialog was confirmed.
- `setup_has_no_horizontal_overflow_at_360` renders the form in a 360 pixel container and compares scroll width with client width.

Run them in that order. The first two protect the routing decision, the third and fifth protect against duplicate writes, the fourth protects the time zone, and the last two protect the phone layout. Together they cover the module's four claims: the right page, one record, a deliberate zone and a usable screen.

## Acceptance criteria

A provider with no record who opens any provider route lands on setup and can create her practice in one submit. A provider with a record who opens the same route sees the provider area. A server error shows a retry and no redirect. The setup form suggests the browser zone, shows the current time in it, and submits whatever the provider confirms. Saving a zone change in settings requires one confirmation that names the consequence for published hours. All three screens pass the 360 pixel checks.

The next lesson is the gate. It asks for a browser walk from an empty account to a settings save, a recorded redirect with its return path, and one screenshot or text transcript at 360 pixels.
