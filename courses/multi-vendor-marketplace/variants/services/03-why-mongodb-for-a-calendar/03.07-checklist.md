# Calendar data-model gate

This module began with three different meanings of time: a provider's recurring rule, a dated candidate slot and a committed booking. Its gate is the design file you can show to another developer. Commit `docs/erd-draft.md` in your SkillSlot project. The file must let a reviewer answer where each kind of time is stored, how a client and a provider find an appointment, and what prevents two overlapping purchases from both succeeding. A polished diagram with no invariants does not meet this gate. A long explanation with no diagram is hard to review against the implementation that follows.

Open the draft from lesson 3.6 and read it without looking at the lesson. The diagram must include Provider, Service, AvailabilityRule, TimeOff, CartItem, Order, Booking and SlotClaim. It may show User as an external identity. Check each relationship from both directions: one provider can offer many services; one service belongs to one provider; one client can make many orders; each order belongs to one provider; each booking belongs to one order while remaining independently addressable by client and provider. If your application intentionally changes a cardinality, write a reason and the new authorization consequence in the file. Do not let an unexplained arrow become a hidden product policy.

## Demonstrate the two database choices

Show the mentor a paragraph in the file comparing MongoDB with PostgreSQL for this particular calendar. PostgreSQL range types and an exclusion constraint can reject overlapping intervals for the same provider directly. In the chosen MongoDB design, a unique compound index rejects two SlotClaim documents with the same provider and UTC block. The application expands each booking interval to 15-minute blocks and inserts the complete set with the booking in a transaction. State the limitation honestly: the index only protects the grid represented by those keys. A different duration policy or off-grid start requires the claim algorithm and tests to change. A calendar read or cache is not a lock.

Walk through 09:00 to 09:30 and 09:15 to 09:45 for one provider. The first interval needs 09:00 and 09:15; the second needs 09:15 and 09:30. The shared 09:15 key means the two requests cannot both own all required blocks. Now walk through 09:00 to 09:30 and 09:30 to 10:00. The first interval does not claim its end boundary, so the second may begin there. This half-open interval convention must appear in the document. If a reviewer needs to guess whether the end block is included, the model is not precise enough for checkout.

## Gate checklist

- [ ] `docs/erd-draft.md` is present in the learner repository and its Mermaid ERD renders.
- [ ] All eight required collections are named, with IDs and cardinalities that support client and provider lookup.
- [ ] AvailabilityRule records local weekday and wall time with an IANA zone; Booking records dated UTC instants.
- [ ] CartItem is labelled as a proposed choice, not as an exclusive reservation.
- [ ] Booking has an independent ID, status and references, plus purchase-time price and policy snapshots.
- [ ] Order is scoped to one provider and contains one or more bookings for that provider.
- [ ] SlotClaim states the 15-minute block key, half-open interval rule and unique `{ providerId: 1, blockStartAt: 1 }` constraint.
- [ ] The file explains the transaction that prevents a partial claim set or a confirmed booking without its claims.
- [ ] The two overlapping-client and later-service-edit stories have concrete expected results.
- [ ] PostgreSQL's interval constraint advantage and MongoDB's grid limitation are stated without claiming either database solves time-zone policy automatically.

Run a Mermaid preview in your editor or repository viewer and fix syntax errors before committing. Read the field notes beside the rendered diagram. A visible arrow can still be wrong if the Booking has no `clientId` or if a SlotClaim is tied only to a Service rather than a provider and UTC block. Ask a peer to explain the 09:15 race using only your file. If they answer that the second client refreshes the page, add the missing unique-key and transaction explanation. Refreshing a view is useful after a conflict, but it does not prevent the conflict.

If a checklist item is missing, revise the document and repeat the two stories. Do not copy a schema from the shelf-stock track simply because its Order fields look familiar. SkillSlot sells a time commitment with a separate lifecycle. A paid appointment can be cancelled or rescheduled without changing the historical service terms. Conversely, an unpurchased weekly opening can move when the provider edits a rule. The model should make those different outcomes possible without rewriting old receipts or moving paid sessions silently.

Commit only after the file explains the current decision. Use a message such as `docs: draft SkillSlot calendar ERD`. Record the commit ID in your learning log or mentor notes. The gate does not claim the schemas or transaction are already implemented; later modules must prove them with database tests. A design document is useful precisely because it gives those tests a target. Keep unresolved product choices, such as hold expiry length or whether multiple bookings can share a group-service slot, in an explicit open-decisions section. Do not quietly treat an open choice as a passing invariant.

## Learning log

1. Explain why a weekly Monday 09:00 AvailabilityRule and a paid Booking cannot store time the same way. Give a dated example in which an offset changes.
2. For a 30-minute booking at 09:00 UTC, list its SlotClaim keys. Then list the keys for a 09:15 booking with the same provider and identify the conflict.
3. A provider changes the Service price after a client pays. Name the live reference and the frozen snapshot the receipt should read. Explain why both remain in the model.
4. Which PostgreSQL feature would simplify interval exclusivity, and what must the SkillSlot application do because it chose MongoDB?

Answer in your own words beneath the questions in a learning log or mentor note. Use exact field names and one concrete value for each answer. A mentor should be able to distinguish an actual invariant from a diagram label. If you cannot explain what happens when a transaction inserts one claim and then meets a duplicate on another, return to the write-boundary contract in lesson 3.6 before moving on.

The next module sets up configuration and a database connection. It will also verify that the MongoDB deployment can run transactions. Keep your ERD open while you implement the connection so the chosen database capability is tested early. The later booking modules will implement claims and payment states; they will need to pass the two stories you wrote here. This gate is passed when the committed design is reviewable and its open decisions are named, not when future booking code is assumed complete.
