# Calendar model and seed gate

This gate is a review of what the database can actually preserve. Show a mentor the registered models, the real indexes, a twice-run seed and `docs/erd.md`. Trace a client and provider through the same Booking, then demonstrate that two clients cannot insert the same provider/block claim. The ERD should say which fields are local recurring intentions, which are dated UTC facts, which are live references and which are purchase-time snapshots. A pretty diagram without a duplicate-index test does not pass the overlap requirement.

Start with the ownership chain. User owns one Profile and may own one Provider. Provider owns Services, rules and TimeOff. A Booking references its client User, Provider, Service and one provider-scoped Order. An active held or confirmed Booking owns every required SlotClaim block. A cancelled or expired Booking remains as history after its claims are released. If your diagram shows one Order belonging to two providers or a Booking with no independent identity, correct it before review.

## Show the actual database evidence

Run the seed script twice in a scratch development database. The second run should keep eight User/Profile fixtures and five Provider fixtures, with stable IDs and no duplicate-key surprise. Show the seed summary and the database name. Inspect the Provider.userId unique index, Profile.userId unique index and SlotClaim provider/block unique compound index. A schema's `unique` declaration is an instruction to create an index; the Compass or database index list is evidence that it exists.

Insert a SlotClaim for Provider A at 09:00 UTC, then try another with the same provider and block. The second must fail with duplicate-key code 11000. Insert the same block for Provider B and another block for A; both should succeed. Clean up the temporary test data. This proves the key's scope. It does not yet prove a five-block booking is atomic; Module 19 supplies that transaction and parallel checkout evidence. State the remaining guarantee honestly in the review.

Show two time representations. Point to an AvailabilityRule with local weekday, `HH:mm` bounds and `Asia/Gaza`. Point to a Booking and TimeOff with UTC Date instants. Format one stored Booking instant in Berlin and Qatar and show that the labels differ while the stored ISO value stays fixed. Explain what happens if the provider edits next week's hours or the client changes display zone. Neither action silently reschedules the paid Booking.

## Gate checklist

- [ ] User, Profile and Provider have consistent roles and one-to-one unique indexes where required.
- [ ] Provider working zone and Profile viewer zone are valid IANA names with separate meanings.
- [ ] Service duration and buffer use whole 15-minute blocks; price uses integer minor units; policy fields are validated.
- [ ] AvailabilityRule has local weekday and wall times; TimeOff has dated UTC intervals and a private reason.
- [ ] SlotClaim has one scalar UTC block per document and a real unique provider/block index.
- [ ] Booking has independent state, participant and order references, UTC instants, purchase snapshots and a bounded history plan.
- [ ] CartItem is an unreserved proposed slot; Order belongs to one provider and has server-calculated totals.
- [ ] Seed creates five Gaza providers and clients in Gaza, Berlin and Qatar; rerunning it preserves counts.
- [ ] The ERD's reference arrows and snapshot notes match the saved documents, and two UTC values were inspected by hand.
- [ ] Cross-provider and cross-client fixture queries remain scoped to the requested actor.

If an index test fails, do not replace it with a `findOne` pre-check. The pre-check can race. Wait for index creation and inspect the actual collection; fix a wrong key or a duplicate fixture before rerunning. If a time conversion looks wrong, compare the raw stored ISO value, the zone name, date and runtime data before editing a Booking. If the second seed run changes counts, fix the upsert identity rather than clearing the database to make the gate green.

## Learning log

1. Two clients read an empty Booking list for 09:00. What exact database key prevents both from owning the provider's 09:15 block?
2. Why does AvailabilityRule store local wall time with an IANA zone, while Booking stores a UTC startAt? Give one future-rule edit that must not move a paid appointment.
3. A Service price changes after purchase. Which live reference and which snapshot explain the old Booking receipt?
4. A cart contains a tutor and designer. How many provider Orders are created, and what prevents either provider from reading the other's fulfillment record?

Answer with field names and one concrete UTC example. A mentor should be able to tell which property the database index enforces and which properties later service logic still must enforce. The unique SlotClaim index handles one provider/block key; the transaction for an entire booking, time-off edit race, payment state and authorization need their own tests in later modules. A gate is useful only when its evidence is accurately scoped.

Commit `docs/erd.md`, the seed script, fixture note and model tests together. The next modules implement authentication and provider APIs on this foundation. If a later route needs a different ownership or time field, update the ERD and the tests deliberately rather than adding a parallel source of truth. This gate is passed when another learner can inspect the database and explain the same promises you wrote in the lesson.

After the review, list any open policy decisions next to the ERD: hold duration, exact release behavior after cancellation, provider-zone migration and the coordinated write rule for TimeOff versus checkout. Name the later module that will close each decision. A clean schema does not make those choices for you. Recording them prevents a later implementer from treating an unstated assumption as a tested guarantee. Keep the module gate scoped to the database foundation it actually proves.

Do not mark the whole course ready because this gate passes. The provider APIs, availability engine, checkout transaction, payment webhook and cancellation workflows still have to use these records consistently and pass their own tests.
