# A zone is a rule set, not one offset

Imagine a provider copies `+02:00` from today's phone screen into SkillSlot's weekly-hours form. The form looks correct today. Three months later, a client books what appears to be 10:00 while the provider's agenda says 09:00. The mistake was storing today's offset as if it described every future Monday.

An IANA zone name such as `Asia/Gaza` names a place's time rules. The rules can assign different UTC offsets on different dates and can be updated when local policy changes. An offset such as `+02:00` is only a number of hours and minutes from UTC at one point in time. It cannot tell the app when a region changes its clocks, whether it has changed policy, or whether a future date has a different offset.

## Check one date, then another

Use Luxon in a scratch Node session after installing `luxon` in `server/`. This is a learning probe, not yet the shared time module. Keep the output in `docs/time-decisions.md` with the Node version you used. Your local time-zone data comes from the runtime; record the observed values rather than copying an offset into a schema.

```js
import { DateTime } from 'luxon';

for (const date of ['2024-01-15T07:00:00Z', '2024-07-15T06:00:00Z']) {
  const instant = DateTime.fromISO(date, { zone: 'utc' });
  const provider = instant.setZone('Asia/Gaza');
  const client = instant.setZone('Europe/Berlin');
  console.log({
    utc: instant.toISO(),
    provider: provider.toFormat("yyyy-LL-dd HH:mm ZZZZ"),
    client: client.toFormat("yyyy-LL-dd HH:mm ZZZZ"),
    providerOffsetMinutes: provider.offset,
  });
}
```

Do not assume that those two example UTC instants are corresponding appointments. They are two independent points chosen to inspect the zone. The important observation is that an IANA zone lets the library choose the offset for each date. If the output surprises you, inspect the runtime's time-zone data and the zone spelling before changing your code. Never "fix" a failed time test by inserting a hard-coded offset.

The provider and client zones have different jobs. The provider zone interprets weekly working rules. The client zone formats a concrete slot. You can change the client zone and reformat a UTC instant without recomputing the provider's rule. You must recompute future slots from the provider's rule if the zone database changes. Already confirmed bookings remain fixed UTC instants; show a clear notice if a zone-rule change makes a future booking's local label different from what was shown when paid.

## Validate a zone at the boundary

A browser can report a default zone with `Intl.DateTimeFormat().resolvedOptions().timeZone`. That is a useful suggestion for the registration form, not proof that the user's preferred zone is correct. Let a user inspect and change it. On the server, accept a named IANA zone that the installed runtime recognises; reject an empty string, a fixed numeric offset and an unknown name. Put the validation in one helper so registration, provider setup and profile editing agree.

```js
import { IANAZone } from 'luxon';

export function requireIanaZone(value) {
  if (typeof value !== 'string' || !IANAZone.isValidZone(value)) {
    throw new Error('Choose a supported time zone, such as Asia/Gaza.');
  }
  return value;
}
```

This checks recognition by the runtime. It does not prove that the user lives there. That is why the UI also shows a human-readable preview, for example "Monday 09:00 in Asia/Gaza" and the current time there. A provider can work remotely from another place; the product asks for the zone of their working schedule, not their nationality or physical address.

## Time-zone data is operational data

SkillSlot's source code can stay unchanged while the time-zone database in Node or the host environment changes. Future slot expansion may then return a different UTC instant for the same local rule. That can be correct after a policy change, but it needs an operational check. Record the runtime version used by API and worker processes. Make the availability engine compute future openings from current zone rules, and keep paid bookings as fixed instants. During deploy, inspect a known provider's next-week agenda in their local zone and in a client's zone. If a change appears, decide whether to notify affected people rather than silently moving a promise.

The worker deserves the same attention as the API. A reminder job running with older time-zone data could format a different local label from a newly deployed web process. Its scheduled execution should use the paid booking's UTC instant, not recalculate the provider's weekly rule. The message can include the provider-zone snapshot and a UTC reference if support needs to compare it with a receipt. A worker restart or a time-zone-data update must not move the scheduled instant.

The API also needs a measured way to handle future unbooked offers after a zone-data update. The simplest policy is to invalidate generated availability for affected providers and recompute it from their local rules. A generated slot is a projection; it is not the authoritative promise until held and confirmed. Do not rewrite confirmed bookings during this refresh. If a fresh projection overlaps an existing confirmed claim, the availability engine subtracts that claim before offering a start. This is why rule expansion and claim subtraction are separate steps.

The database stores a snapshot of `providerZoneAtBooking` and `clientZoneAtBooking` with the booking for explanation. It stores `startAt` and `endAt` as UTC instants for the actual promise. It does not store a permanent `providerOffsetHours` on the weekly rule. An offset snapshot can help debugging, but it cannot replace the zone name.

## A test that catches fixed-offset thinking

Write a test with two dated Mondays separated by a clock-rule change in a zone where that change is documented. Expand a provider rule of 09:00 in that zone on both dates. Assert both resulting values format back to 09:00 in the provider zone. Then assert the UTC instants do not necessarily have the same UTC clock hour. This tests the property SkillSlot cares about: the provider's weekly local promise stays local. It does not hard-code the assumption that every zone changes on the same weekend.

For a client test, take one fixed UTC instant and format it in two zones. The result should show two labels but keep one ISO instant. Add a third test that supplies `'+02:00'` where an IANA zone is expected and receives a validation error. These tests separate an input boundary from conversion behavior. They also make a future library change visible: if Luxon or Node returns different offsets for a future date, the test can be reviewed against current zone data instead of patched with a magic number.

Do not write a test that asserts a particular future Gaza offset forever. Time-zone rules are policy, and policy can change. Use fixed historical transition examples for the conversion algorithm, and use an operational smoke check for the provider's next seven days. The historical test catches code regressions; the smoke check catches environment or rule-data changes that could affect real users.

## Explain the trade-off to a provider

Imagine the provider asks why SkillSlot needs a zone picker when their phone already knows the local time. A precise answer is that the phone reports the zone where the browser is now, while the provider's weekly practice can be anchored somewhere else. A tutor visiting Doha may still run sessions advertised as 09:00 Gaza time. Their phone's zone should not move those sessions. The picker makes the working rule explicit, and the preview shows its meaning before it is published.

The app should show the next dated occurrence of a newly entered rule, not only the text "Mondays 09:00." That preview is a check against a typo or wrong zone choice. It is not a guarantee that every future date has the same offset. When the provider changes a zone, the UI must explain that new openings may move on clients' clocks, while confirmed bookings will stay at their paid instants. This turns an abstract storage rule into a decision the person can verify.

## Decide before building

Write two acceptance criteria for profile editing. One must say what happens to existing paid bookings. The other must say what happens to future unbooked weekly rules. A good policy preserves paid instants and requires explicit confirmation before applying a new provider zone to existing rules. In the next lesson, you will handle the harder case: a local wall-clock time that maps to zero or two instants even when you have the right IANA zone.
