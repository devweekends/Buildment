# Time module gate

You began with a provider's sentence, "I work Mondays at nine." You can now distinguish that local recurring rule from a dated UTC slot and from the label a client sees. This gate asks for executable proof. A written explanation without a passing test is not enough, because a date library can normalize a skipped hour or choose one occurrence of a repeated hour without making that policy obvious.

## Evidence to show a mentor

Open `server/src/shared/time.js` and `server/src/shared/clock.js`. Demonstrate that the converter receives explicit date fields and a named zone, returns UTC, and rejects a numeric offset. Then run the test suite while the mentor watches. Show the ordinary Berlin round-trip, the New York spring gap, the New York autumn overlap, two viewer zones for one UTC instant, and the exact minimum-notice boundary. Run the suite under two different `TZ` values. The UTC outcomes must be the same in both processes.

Show `docs/time-decisions.md` with a four-column table for the provider rule, dated slot, paid booking and client display. The table needs to say who owns each value and when it can change. A weekly rule can be edited by its provider. A dated offer can be recomputed until held. A paid booking's UTC instant changes only through rescheduling. A display label can change when the viewer selects a different zone. These are product rules, not merely formatting tips.

Include one screenshot or text transcript of the controlled Berlin example from lesson 5.5. The provider sees Monday 09:00 in both dated weeks. A Qatar client sees different local hours because Berlin's offset changed between those dates. The first and second dated offers have different UTC clock hours. State the historical dates and runtime version used for the calculation, so another learner can reproduce the result.

## Gate checklist

- [ ] The time module validates IANA zone names and rejects fixed numeric offsets for provider rules.
- [ ] A normal dated local start converts to UTC and formats back to the same provider wall-clock fields.
- [ ] A nonexistent local boundary returns `NONEXISTENT_LOCAL_TIME` rather than silently moving forward.
- [ ] A repeated local boundary returns `AMBIGUOUS_LOCAL_TIME` rather than silently choosing an occurrence.
- [ ] Formatting one booking instant in two viewer zones leaves the stored UTC instant unchanged.
- [ ] Notice-period tests cover before, exactly at, and after the boundary with a fixed clock.
- [ ] The test suite passes with two different process `TZ` settings.
- [ ] The decision note explains what changes when a provider edits a weekly rule, when a client edits a display zone, and when a booking is rescheduled.

If a check fails, fix the input boundary or the test. Do not add a one-hour correction for one date. That would hide the same bug for another place or year. Use the named zone and dated local fields to ask the library for the applicable rule. If a gap or overlap is found, keep the provider action explicit. A checkout endpoint must never turn a rejected local boundary into a paid booking.

If the suite does not run, inspect the `test` script in `server/package.json` and run the file directly with the chosen runner before changing any expected value. If the gap case fails, compare the requested fields with the candidate's formatted fields. If the overlap case fails, inspect all possible offsets rather than taking the library's first one. If the two `TZ` runs differ, search for an unzoned date string or implicit host-zone formatting. Record the actual failing input in the learning log so a mentor can reproduce it.

Show one negative example during the review: an invalid provider boundary that receives 422 and never reaches a booking or claim write. This proves the API boundary rejects ambiguity before money is involved. A green converter unit test is useful; a route test showing that the invalid value cannot become a public offer completes the story. If the route does not exist yet, write this as a required integration test for the availability module and do not claim that later gate has passed.

## Learning log

1. Explain, without using the word "format" as the whole answer, why `09:00` plus today's UTC offset cannot be a weekly provider rule. Give one future-date failure.
2. A paid lesson starts at `2024-01-15T08:00:00Z`. The client changes their profile from `Europe/Berlin` to `Asia/Qatar`. List the database fields that stay identical and the screen label that changes.
3. Your test runner says New York `2024-03-10 02:30` is a valid `DateTime`. What additional check would prove that the library represented the requested local fields instead of moving them?
4. The provider moves to a new zone but has three paid sessions next week. State a policy for the paid sessions and a separate policy for their unbooked weekly openings. Explain how the UI makes the difference visible.

Write the answers in your own words. Your mentor should be able to identify the distinction between rule, instant and display from your explanation. If an answer is vague, include the exact field names and one dated example. This gate is complete when the code, tests and note agree, not when the checkbox text alone is copied.

## Bridge to the data model

The next module stores providers, services, availability rules, time off, claims and bookings. The time module tells it how to represent a dated promise. It does not yet stop two clients booking the same promise. That requires a unique claim key and a transaction later in the course. Keep `docs/time-decisions.md` open while you design the schemas, so every date field has a clear owner and every stored instant has a reason to exist.

Before starting that model, point to one line of code that converts a provider's wall-clock input and one line that formats a stored instant for a client. Explain why those lines sit in different functions. The converter can reject a nonexistent or repeated boundary, while the formatter cannot face that ambiguity for an already fixed instant. That explanation is the smallest useful handoff to the next module: it tells a reviewer which kind of value each new schema field should hold.
