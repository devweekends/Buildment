# When 02:30 happens zero or two times

Most local times map to one UTC instant. On a clock-change day, that rule can fail. When clocks move forward, part of the local clock is skipped. When they move back, part of it repeats. SkillSlot cannot accept a provider's local boundary without deciding which instant it means. A wrong choice can offer a slot that never existed or reserve only one of two different hours with the same label.

Use the well documented 2024 New York transitions as a controlled example. On 10 March, the local clock jumped from 01:59 to 03:00. `02:30` did not occur. On 3 November, the local clock went from 01:59 back to 01:00. `01:30` occurred twice with different offsets. Those exact dates are examples for `America/New_York`, not rules to copy into Gaza's calendar. SkillSlot must ask its time-zone library about the date and zone being expanded.

| Local input | Zone and date | Possible UTC instants | Product decision |
|---|---|---:|---|
| 02:30 | New York, 10 March 2024 | 0 | Reject this dated boundary; ask for another time |
| 01:30 | New York, 3 November 2024 | 2 | Require an explicit earlier or later offset choice |
| 09:00 | New York, 4 November 2024 | 1 | Accept normally |

The safest first version of SkillSlot rejects a weekly rule whose start or end boundary is ambiguous or nonexistent on a particular expansion date. It can omit that day's slots and flag the rule for the provider. A later product could ask the provider which occurrence they intend, but it must store the decision, test it and show the selected offset to both parties. Silent normalization is not acceptable for a paid appointment.

## Recognise the two directions

Converting a stored UTC instant into a zone is deterministic. Converting a local date, time and zone into UTC is the risky direction. In Luxon, an ambiguous `DateTime` can expose possible offsets with `getPossibleOffsets()`. For a gap, some date libraries normalize an invalid local time into a valid later one. Do not use `isValid` alone as the gap test. After constructing the value, compare its local year, month, day, hour and minute with what the provider entered. A changed field means the library did not represent the requested wall time.

Keep this as a policy table before writing implementation:

| Result count | Meaning | API response |
|---:|---|---|
| 0 | Requested wall time did not occur | `422 INVALID_LOCAL_TIME` with zone and local date |
| 1 | One unambiguous instant | Return its UTC ISO string |
| 2 | Repeated wall time | `422 AMBIGUOUS_LOCAL_TIME` with both offset choices |

Do not rely on the phone's locale for the answer. The provider might be editing hours from a phone in Qatar while their published schedule uses `Asia/Gaza`. Pass the provider zone explicitly into every conversion function. Likewise, a Berlin client must receive UTC slot starts from the API, then format them using the client's chosen zone. The server owns whether the slot exists; the browser owns its presentation.

## A worked failure

Suppose a rule is Sunday 01:00 to 03:00 in New York and a 60-minute service starts at 01:30 on the autumn transition day. A label of "01:30 to 02:30" does not reveal whether the appointment lasts one hour or two on the UTC timeline. If you add one to the displayed hour, you can charge for an interval different from what was reserved. The service duration must be an absolute number of minutes. Once a start instant is chosen explicitly, calculate the end instant by adding the duration on the UTC timeline and format both instants for display. Do not add an hour to the wall-clock string.

The availability engine will expand rules into dated instants, step through actual instants and subtract claims. The claim key is an instant, so two distinct occurrences of 01:30 are not the same lock. A slot picker must display a zone abbreviation or UTC offset when a repeated label occurs. Our first version omits ambiguous boundaries, which keeps the booking path simpler. The tests will verify that omission rather than assuming every day has 24 ordinary hours.

## Specify the converter before coding it

Give the converter one input object: year, month, day, hour, minute and IANA zone. It should return either one UTC ISO value or a structured error. It should never return a local string as if that were an instant. The error includes the original local fields so the form can show exactly which boundary the provider needs to change. It must not expose a vague "invalid date" that leaves the provider guessing whether the zone name, calendar date or local hour failed.

To detect a gap, create a candidate in the requested zone and compare every local field of the result with the input. Some libraries move a nonexistent 02:30 forward to 03:30. A candidate that formats back to 03:30 did not represent the requested 02:30 and must be rejected. To detect an overlap, inspect every possible offset for the candidate, convert each to UTC, and count distinct instants that format back to the requested local fields. Reject a count of two under our first product policy. A count of one is safe to use. This is a decision about the product, not a universal law; another booking system could offer both occurrences with clear labels.

Validate the whole interval, not only its start. A provider can set a weekly range whose start is ordinary and end falls inside a skipped or repeated hour. If the end boundary cannot be resolved, do not offer slots from that range on that date. Report the affected date in the provider dashboard. It is better to miss one unusual opening than to sell a session whose duration or finish time is unclear. A confirmed booking's duration is calculated in absolute minutes from a chosen start, so the end instant remains unambiguous even when its displayed label crosses a clock change.

The booking horizon reduces how far into the future the app needs to interpret rules. It does not remove the need for correct conversions. A seven-day range can include a clock change; the first week of a new season is exactly when users notice errors. Add a boundary test for both a short 30-minute service and a longer 90-minute service. The slot engine should step through UTC blocks and check every block needed by duration plus buffer, not count labels on a wall clock.

## Diagnose a bad test result

If a gap test unexpectedly returns a valid instant, print both the entered fields and the fields obtained after formatting the candidate in the same zone. Check the zone spelling and the historical date. A test that uses the current year without verifying its transition date can be wrong even if the converter is correct. If an overlap test returns one value, inspect `getPossibleOffsets()` and confirm that the library version implements it. Do not weaken the test to accept either value; the course's policy requires an explicit ambiguity result.

If a browser displays a different local label from the server's diagnostic output, compare their runtime time-zone data and the exact UTC instant used. A display mismatch is not permission to rewrite the booking's UTC fields. Reconcile the formatting and give the user an accurate label. A paid booking is already a fixed promise. The ambiguity check belongs before that promise is accepted.

## Practice

In `docs/time-decisions.md`, write the API response you expect for New York `2024-03-10 02:30` and `2024-11-03 01:30`. Include the error code, the zone, and what the provider can do next. Then answer a harder question: a confirmed booking starts at one of November's two 01:30 instants. If the user changes their display zone, can its instant become ambiguous? No. Formatting an existing instant has one answer; the ambiguity is only in the reverse mapping from local input.
