# An instant is not a wall-clock rule

The provider says, "I work Mondays at nine." The client says, "I booked next Monday at nine." Those sentences look similar but name different things. The first is a rule that can produce many future slots. The second must identify one interval on one date. If SkillSlot stores both as the same kind of string, a calendar change can move or duplicate a paid booking.

An **instant** is a point on one worldwide timeline. A JavaScript `Date` and an ISO string ending in `Z` can represent one. A **wall-clock time** is what a person reads on a clock in a place, such as Monday at 09:00 in Gaza. It does not identify a worldwide instant until you supply a date and time-zone rules. An **offset**, such as `+02:00`, is the difference from UTC for one instant. It is not the permanent identity of a region.

## A model with different fields

Write the model sketch below in `docs/time-decisions.md`. Do not copy it into Mongoose yet; the data-model module will decide validation, ownership and indexes. The sketch makes the meaning of each field visible before code makes it harder to change.

```js
const weeklyRule = {
  providerId: 'provider-17',
  weekday: 1,              // Monday in the provider's local calendar
  startLocal: '09:00',
  endLocal: '12:00',
  providerZone: 'Asia/Gaza',
};

const booking = {
  providerId: 'provider-17',
  startAt: new Date('2024-01-15T07:00:00.000Z'),
  endAt: new Date('2024-01-15T08:00:00.000Z'),
  providerZoneAtBooking: 'Asia/Gaza',
  clientZoneAtBooking: 'Europe/Berlin',
};
```

For this January date, 07:00 UTC reads 09:00 in Gaza and 08:00 in Berlin. Those values are examples you can verify with a library. Do not derive next week's UTC start by adding seven days to this booking. The provider's next Monday rule must be resolved again for the next local date, because the offset may change between dates.

The booking keeps the provider and client zones as snapshots for receipts and support. The UTC instants decide overlap and reminders. The current client zone can change after booking; that only changes a UI label. A historical receipt may show the zone used when the booking was accepted, while the agenda can show the current viewer zone. Both views refer to the same `startAt`.

## Work the conversion by hand

Take the example above. The provider starts at 09:00 Gaza time on 15 January 2024. On that date Gaza's offset is two hours ahead of UTC, so the instant is 07:00 UTC. Berlin's offset is one hour ahead of UTC on that date, so the client reads 08:00. Now imagine the client travels to Qatar and changes their display setting. The app formats 07:00 UTC in `Asia/Qatar`, which reads 10:00 on that date. Nothing has moved in the booking row.

The reverse direction needs more care. Given a UTC instant and an IANA zone, formatting has one answer. Given a local time and a zone, a clock-change day may have zero or two answers. A provider who writes a repeating rule has not chosen a specific UTC instant yet. That choice happens when SkillSlot expands the rule for a dated calendar range. The next two lessons establish the ambiguity policy.

## The database boundary

Use UTC instants for `Booking.startAt`, `Booking.endAt`, `TimeOff.startAt`, and individual `SlotClaim.blockStartAt` values. Use local `HH:mm` fields plus an IANA zone for `AvailabilityRule`. Never compare two `HH:mm` strings from different providers to decide booking order. Never use the client's browser clock as the authority for whether a slot has passed; the server checks its own clock before reserving a claim.

If a provider changes their profile zone from Gaza to Doha, do not change existing booking instants. Future weekly rules need a clear policy: either keep each rule's original zone or migrate rules by an explicit provider action. This course will store the zone on each rule and ask for confirmation before changing it. This avoids silently moving next week's promised time. The provider can still choose new rules in a new zone.

## Compare two tempting schemas

One tempting design stores every provider opening as a UTC date seven weeks ahead. It makes a simple slot query possible today, but the repeating schedule disappears into a list of generated rows. When a provider edits Monday hours, the app must decide which rows to replace, which have paid bookings, and whether a newly announced time-zone rule changes future rows. Generated slots can be a cache, but they should not become the only record of the provider's intention.

Another tempting design stores only `startLocal: '09:00'` on the booking. It keeps the provider's preferred label, but it cannot tell a reminder worker when to run. A client in another zone cannot reliably infer the instant, and a repeated local hour can map to two instants. The booking must carry a dated UTC start and end. We keep the local zone snapshots for explanation, not as substitutes for the instants.

The two-layer design makes updates explicit. Editing a weekly rule changes future offers. It does not rewrite a paid booking. Rescheduling a paid booking creates a guarded transition to a new UTC interval, releases the old claims and acquires the new claims as one operation. A display-zone change changes only the presentation. Those are different product actions, so they deserve different storage paths and authorization checks.

## Debug a moved appointment

Suppose a client says a confirmed lesson moved from 08:00 to 09:00 after they changed phones. Check `Booking.startAt` and compare it with the value on the payment receipt. If the UTC value is unchanged, format it with the old and new display zones. A one-hour label change can be correct if the viewer zone changed. If the UTC value changed without a reschedule event, that is a data integrity defect: find the write path and stop it from using a formatted label as input. Write a regression test that changes `client.timeZone` and asserts the booking's `startAt` and `endAt` are byte-for-byte equal before and after.

Also test a provider's profile edit. Changing a display name may update the profile immediately; changing the provider zone needs an explicit choice for existing availability rules. Even if a provider moves, a confirmed appointment remains at its accepted instant. Show both the old provider-zone snapshot and the current provider-zone label when support needs to explain a discrepancy. This is more useful than silently rewriting history.

## An acceptance contract for the API

`GET /providers/:id/availability` will return UTC ISO starts, service duration and the provider zone. It will not return a preformatted client-local time as the only representation. A browser can then format the UTC start in the selected client zone and show the provider's zone alongside it. The server will validate the UTC start again at checkout. The exact API shape comes in the availability module, but this representation is a commitment now. Put it in `docs/time-decisions.md` so a future route implementation cannot quietly replace instants with ambiguous strings.

For the opening example, a useful response would include `startAt: '2024-01-15T07:00:00.000Z'`, `providerZone: 'Asia/Gaza'`, and `durationMinutes: 60`. The UI can show "08:00 your time; 09:00 provider time" for a Berlin client on that date. The booking row uses the same UTC start if checkout wins the slot. The string shown on the button is never used as a database key.

## Practice and evidence

Make a three-row table in `docs/time-decisions.md`: a weekly rule, a booked appointment, and the time shown on a travelling client's screen. For each, name the authoritative stored fields and the fields that may change without moving the appointment. Then answer: why does `2024-01-15T07:00:00Z` not tell a client which local wall-clock label to display? It gives an instant, but the label still needs a zone.

In the next lesson, you will see why `+02:00` cannot replace `Asia/Gaza` in a weekly rule. The two can be equal on one date and differ later.
