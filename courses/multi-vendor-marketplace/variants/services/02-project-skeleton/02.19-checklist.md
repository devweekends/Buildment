## How to read this gate

A gate is not a quiz about what you remember. It is a list of things that must be true in your repository and in your running app before the next chapter assumes them, and every box below can be checked by running a command or opening a URL. That is deliberate: if a claim cannot be checked, the box would only measure confidence, and confidence is what fails in Chapter 15 when availability code lands in the wrong folder.

Read each box as three questions. What am I claiming, what proves it, and how would a reviewer confirm it without me in the room. "The health route works" is a claim, `curl -i http://localhost:5000/health` printing 200 with a JSON body is the proof, and a mentor running the same command against your repository is the review. Write the proof down in your learning log when it is not obvious, because the same evidence feeds the evidence index you assemble in 28.1.

The groups are ordered for that reason, not alphabetically. Repository health comes first because nothing else can be verified if the code is only on your machine. Server checks come next because the client needs something to call. Client checks follow, and integration comes last, because integration is the outcome the first three groups exist to reach. If you fail a box in a late group, walk back through the earlier ones before debugging anything.

## Chapter 2 ,  Project skeleton checklist (gate)

Do **not** open Chapter 3 until every box is ticked and learning log answers are written below.

### Repository & structure

The first group proves the work is reviewable. Four boxes stand for one sentence: your code lives in a Git repository a stranger can open, generated files and secrets stay out of it, and the README explains how to run what you built. A reviewer starts exactly here, opens the repository page, reads the README, and only then runs a command. If the README is missing or wrong, everything after it is discounted.

The ignore-history box deserves the weight it carries. `git log --all -- "**/.env"` searching every commit and returning nothing is stronger evidence than a `.gitignore` that happens to contain the right line, because history is what a leak actually exposes. A reviewer reads an empty result as proof the policy existed from the first commit, and a non-empty result as a key that must be rotated no matter how clean the current tree looks.

- [ ] Git repository initialised at the SkillSlot project root (kept outside the course content folder)
- [ ] Root `.gitignore` covers `node_modules/`, `.env`, and build output
- [ ] `git log --all -- "**/.env"` prints **nothing** (no environment file was ever committed)
- [ ] Root `README.md` explains how to start server and client in two terminals

### Server

The server group proves the API is a real process with a structure, not one file that happens to answer. The entry files, the module folders, and the shared folder together are the structural claim every later chapter relies on, and the split between `app.js` and `server.js` is what lets the app be tested without opening a port. A reviewer opens `server/package.json` for the scripts, then the two entry files, and can tell in a minute whether the folder is a skeleton or a pile of pasted snippets.

The last two boxes are the runnable ones, and they are the only boxes here that return output instead of structure. `npm run dev` running without a crash proves the dependency tree and the entry point agree with each other. The curl check proves the route is mounted at the path later chapters will call, and a reviewer reads the status line and the JSON body rather than the word "ok", because a 404 with a friendly message is the most common way this box gets ticked dishonestly.

- [ ] `server/package.json` defines `dev` and `start` scripts
- [ ] `server/src/app.js` builds the Express app, adds JSON middleware, and exports it without listening
- [ ] `server/src/server.js` binds the port from `process.env.PORT || 5000`
- [ ] Module folders exist for `auth`, `stores`, `products`, `cart` and `orders`
- [ ] `server/src/shared/` exists
- [ ] `npm run dev` inside `server/` starts with no crash
- [ ] `curl -i http://localhost:5000/health` answers **200** with JSON carrying `"status":"ok"`

### Client

The client group checks that the second app exists, that its folder convention matches 2.12, and that it can show both success and failure. The success half is easy: a Home page displaying the health response proves the browser reached the API. The failure half is the one that matters, because an error state proves the page reads live data instead of printing a hardcoded string, and that is the difference between a demo and a mock.

A reviewer reads this group by stopping the server and reloading the page. If the page still reports the API as healthy, the claim is false and the box should come unticked. The environment example is checked by opening the file, and the API helper box is checked by searching your pages for a literal `localhost`, which must appear nowhere outside that helper.

- [ ] Vite React app in `client/` with `pages/`, `components/`, `api/`, `hooks/`
- [ ] React Router renders Home at `/`
- [ ] `client/.env.example` documents `VITE_API_URL`
- [ ] `client/src/api/client.js` reads base URL from env ,  no hardcoded localhost in components
- [ ] `npm run dev` in `client/` runs without crash
- [ ] Home page displays **live** health status from API when server is running
- [ ] Home page displays **error state** when server is stopped (not hardcoded success)

### Integration

Integration is one claim expressed three ways: the browser is allowed to call the API, it actually does, and you watched the exchange in the tool that shows the raw truth. The CORS box exists because a request from a disallowed origin fails in the browser while succeeding in curl, which is the most confusing symptom in this chapter. The Network tab box exists because it puts the status code, the request URL, and the response body in one place, so no part of the claim rests on memory.

A reviewer asks for one screenshot or one live walkthrough of that Network entry. It takes ten seconds to read and settles the whole group, and the same evidence belongs in your learning log now and in the evidence index described in 28.1.

- [ ] CORS configured so browser can call API from Vite origin
- [ ] Browser Network tab shows successful `GET` to `/health` with 200
- [ ] End-to-end verification from **2.16** completed

### Understanding (self-check ,  explain aloud)

These four boxes have no command behind them, and they are the ones learners skip on the way to finishing. Each asks you to explain a decision rather than prove a fact: why modules instead of layers, what runs where, why the two entry files are separate, and where a feature you have not written yet will live. The test is simple and slightly uncomfortable. Say the answer out loud in under a minute without opening your notes.

A reviewer uses this group in the viva. Each answer takes about a minute, and a learner who can recite file paths but cannot explain why they exist shows the same gap as a learner who cannot find them, because the next twenty chapters ask you to place new code without being told the exact path.

- [ ] I can describe **module-based** structure beside a layer-based one, and say why SkillSlot picked modules
- [ ] I can say which code runs in the **browser** and which runs in the **Node server**
- [ ] I can justify keeping **`app.js` and `server.js` as separate files**
- [ ] I can name the folder where **auth** and **products** code will sit in my tree

### Learning log ,  write now

Answer **in your own words** in the fields below:

A good answer names a file, a command, or a screen rather than a feeling. "Health check works" is not an answer; "curl returned 200 with status ok after I restarted the server, and the Home page showed an error while it was stopped" is one. Write the version you would paste to a mentor who cannot see your machine, because that is the standard the next chapter assumes.

6. **What will change on `/health` in Chapter 4 when MongoDB connects?** Speculate based on course outline ,  one paragraph.
