# Check the entry skills and repair date basics

You should be able to write a small Express route, call it from a React page, read a MongoDB document, run a test, and use Git to keep a change. You do not need to have built a booking engine. This check shows which foundation to repair before the time module. An uncertain answer is useful evidence; guessing correctly is not a reason to skip the repair if you cannot explain it.

The special entry skill for SkillSlot is reading a JavaScript date without confusing an instant with a wall-clock rule. `new Date('2024-03-25T08:00:00.000Z')` names one instant. Its `toISOString()` value stays the same on every machine. A formatter can show that instant as 09:00 in Berlin on that date or 11:00 in Qatar. A weekly provider rule such as "Monday at 09:00 in Berlin" is not a `Date` yet. It needs a particular Monday and the zone rules for that date before it has a UTC instant. An offset like `+01:00` describes one relationship at one time; it is not a permanent substitute for `Europe/Berlin`.

Before the questions, predict what changing a browser's display zone should do to a paid booking. The booking's stored UTC instant must stay fixed. Only its label changes. Then answer without running code. If you are unsure, make a small file after this check and use `Intl.DateTimeFormat` with an explicit `timeZone` to compare two views of one `Date`.

If the first two questions were difficult, run a five-minute repair. In a local JavaScript file, create one `Date` from the ISO string in the first question. Print `toISOString()`. Use two `Intl.DateTimeFormat('en-GB', { timeZone, dateStyle: 'full', timeStyle: 'short' })` formatters, one for `Europe/Berlin` and one for `Asia/Qatar`, on that same object. Write down the two labels and confirm that `toISOString()` did not change. This exercise does not convert a local rule to UTC; the time module will teach that separately. It repairs the simpler direction first: one instant can have several truthful local labels.

Do a second repair with a dated rule, without trying to write a full conversion helper yet. Write "Monday 09:00, Europe/Berlin" next to 25 March 2024 and 1 April 2024. Run a trusted zone-aware formatter or the time canvas in Module 5 to inspect the two resulting UTC hours. Berlin changes its clock between these Mondays. The local rule stays at 09:00, while the UTC hour changes. If you had saved only `+01:00` beside the weekly rule, the April appointment would be wrong. Record this as a question for the time module: what should the app do when a local time is missing or repeated on a change night? Do not settle that policy by guessing from these two ordinary Monday morning examples.

Notice also what this repair cannot prove. It does not show that a slot is free, that a client may read a booking, or that a payment succeeded. Those are separate server decisions with separate tests. A correct date formatter can still display a slot that another client already claimed. A safe unique claim can still be shown in the wrong zone. The course tests both because a booking needs an exclusive interval and a truthful label. In your learning log, keep one test idea for each promise instead of writing a single broad test named "booking works."

If the ownership question was difficult, make a tiny two-account test plan. Provider A owns Service A; Provider B owns Service B. A price change from A for Service A should succeed after validation. The same request from B for Service A should fail without changing the record. This is the pattern the authorization module will turn into a running test. If the HTTP or Git parts of the prerequisite list are unfamiliar, use the project-skeleton module slowly and ask your mentor for a short repair exercise before starting checkout work.

Record one line in `docs/LEARNING-LOG.md`: which part felt uncertain, what small check you ran, and what result would prove you repaired it. The next chapter maps the four weekly demos so you can see where this entry skill will be used.

Bring that log entry to your first mentor check. A mentor can suggest a narrower repair task when they see the exact failed assumption. You should be able to explain your answer aloud before relying on it in booking code.
