# Working rhythm and introduction gate

The first module is complete when you can explain what SkillSlot sells, who uses it, and what the app must prove. You do not need a finished repository yet. You do need a small product brief and a way to keep decisions and evidence as the build grows. A gate is a promise to your future self and reviewer: the next module begins with a clear target rather than an attractive screen and an unclear booking rule.

Work in short, repeatable sessions. At the start of a session, read the current acceptance check and predict what you expect to observe. At the end, run the check, record the result, and commit a small change. If power or network access stops the session, write the next command in your learning log before leaving. When you return, `git status` and the last entry should show where to continue. A daily rhythm of one checked behavior is stronger than a long weekend of unverified code.

## Build the brief

Create `docs/product-brief.md` in the repository you will use for SkillSlot. Give it one sentence for the product promise: clients can book paid time from independent providers without a double booking or a time-zone surprise. Name one provider and one client, their IANA zones, one fixed-price service, its duration, and the dated appointment you will use in examples. Keep the example consistent when later lessons add fields. If your provider is Lina in Gaza and your client is Sami in Berlin, the time tests should use those names and zones until you have a reason to change them.

Add a journey for each person. Lina registers, publishes a service and weekly hours, blocks time off, receives a paid booking, and completes or cancels the session. Sami finds the service, reads a dated slot in his selected zone, adds it to a cart, pays, and sees the appointment and receipt. Mark every place where the server must decide ownership, time, price, claim, or payment state. The browser may explain a decision, but it must not be the only place that enforces it.

Add a scope table with `Core`, `Later`, and `Reason`. The core includes provider profiles, services, availability, dated slots, short holds, server-priced payment, paid bookings, provider-specific views, cancellation, reschedule, reminders, tests, and deployment. Later includes video calls, provider payouts, two-way calendar sync, route planning, and open-ended quotes. Give a real reason for each later item. For example, calendar sync adds another source of truth and conflict resolution; it is not merely "too large."

## Set the evidence rhythm

Create `docs/LEARNING-LOG.md` with an entry for Module 1. Use the headings `Decision`, `Reason`, `Proof`, and `Open question`. Under Proof, link your product brief and note the three test ideas from the previous lesson: one winner for one provider hour, a stable UTC booking when the viewer zone changes, and no stolen claim after a late payment succeeds. These tests are not implemented yet. Label them as planned evidence so a reader cannot mistake a test name in a document for a passing test in the repository.

Write one command you will run at the end of the next build session. It may be `git status` before the first commit, then a health-route test after the project skeleton exists. Record what a passing output should look like. This habit turns a general intention to "make progress" into a check you can repeat. If a check is blocked by an external account, write the exact block and continue with independent work. Do not replace a Stripe test with a browser alert that says payment succeeded.

## Gate checklist

- [ ] `docs/product-brief.md` names the provider, client, zones, service, duration, and one dated appointment.
- [ ] The brief traces both journeys from first visit to finished or cancelled session.
- [ ] The brief marks server decisions for ownership, time, price, claim, and payment.
- [ ] The scope table explains why video calls, payouts, calendar sync, route planning, and open-ended quotes are later work.
- [ ] `docs/LEARNING-LOG.md` has the four headings and three planned test ideas, clearly marked as not yet run.
- [ ] You can explain why a listing is different from a booking and why the provider ID, not only a service ID, owns a calendar claim.
- [ ] You can name the four weekly demos and point to the evidence each needs.

## Learning log

Answer these questions in your own words. Use a dated example from your brief rather than a generic definition.

1. Lina offers Monday 09:00 in `Asia/Gaza`. Sami views the slot in `Europe/Berlin`. Which value is the provider's repeating rule, which value is the dated booking instant, and which value is only a display label?
2. Two clients pay for one provider hour at nearly the same time. What final state is forbidden, and why would hiding a button after the first click fail to enforce that rule?
3. A Stripe success event arrives after Sami's hold expired and Mariam won the slot. Which facts must the server check before creating a booking, and what must Sami see if the slot cannot be recovered?
4. Why does a provider's public service page not give a stranger permission to read that provider's full calendar, client addresses, or meeting links?

A useful answer names a stored record, a server decision, and an observation you can test. For the first question, "use UTC" alone is incomplete because a weekly local rule is not an instant yet. For the second, "check the database" is incomplete because two requests can both read an empty result before writing. For the third, "refund" is only the beginning; the event may replay, so the refund decision must be idempotent. For the fourth, a hidden React control is not a permission boundary. If your answer stops at a slogan, return to the worked journey and add the missing actor or state.

Show your brief and log to a peer or mentor. Ask them to challenge one assumption. A good challenge might ask what happens when a provider changes their zone after bookings exist or when a client switches display zones while travelling. Record the question even if the implementation comes later. Once the checklist and answers are complete, continue to the project skeleton. You now know the product path that the code must support.
