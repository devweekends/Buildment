# Block a dated interval and show conflicts

Weekly rules describe usual hours. TimeOff describes an exception on a dated interval: a holiday, power cut, workshop closure or personal break. Build an authenticated `POST /provider/time-off` route that accepts provider-local date and clock fields, resolves both boundaries using Module 5's `localToUtc`, stores UTC Date values and returns any existing held or confirmed Bookings that intersect the interval. The TimeOff removes new offers. It does not cancel, reschedule or refund those Bookings automatically.

The provider may enter a range across midnight. Resolve each boundary with its own local date in Provider.timeZone. Do not compute the end by adding a number of UTC hours to the start unless the user explicitly selected an elapsed duration; they selected local date and time fields. A clock-change date can make a local boundary nonexistent or ambiguous. The tested converter returns a specific error; the API responds 422 and saves nothing. It must not silently shift a power-cut start or pick one occurrence of a repeated hour.

```mermaid

  participant P as Provider dashboard

  P->>A: Local dated start and end
  A->>C: Resolve both in Provider zone

```

The conflict list is protected provider information. It may contain Booking IDs, UTC starts, local labels and status, plus minimal client identity if the provider is authorized to see it. It should not be returned by public availability. A client querying slots only sees that conflicting candidates are absent. The provider dashboard must give a next action for each existing appointment, such as contact the client or start an explicit reschedule or cancellation flow.

## Resolve and validate once on the server

The route derives Provider from the authenticated User. It reads the Provider.timeZone and ignores any client-supplied zone as an authority. It validates complete date/time fields, calls `localToUtc` for start and end, checks `endAt > startAt`, and enforces a reasonable maximum exception length. A provider should be able to block a full day or a short incident, but an accidental range of ten years should be rejected with a field error. Keep the accepted maximum in the API contract and test it.

```js
function resolveTimeOff(input, providerZone) {
  const startIso = localToUtc({ ...input.start, zone: providerZone });
  const endIso = localToUtc({ ...input.end, zone: providerZone });
  const startAt = new Date(startIso);
  const endAt = new Date(endIso);
  if (endAt <= startAt) throw new InputError('INVALID_TIME_OFF_RANGE');
  if (endAt.getTime() - startAt.getTime() > 31 * 24 * 60 * 60_000) {
    throw new InputError('TIME_OFF_TOO_LONG');
  }
  return { startAt, endAt };
}
```

Import `localToUtc` and the application's typed `InputError` in the actual file. The maximum is an elapsed-time bound for this MVP; if the product wants calendar-month closures, define a separate administrative flow. For a one-tap "rest of today" action, the server calculates the input interval from its own clock and next provider-local date, then passes it through the same validation path. The browser should not send `Date.now()` as the start authority.

## Find the affected bookings

Query Bookings for this provider with status in `held` or `confirmed` and half-open overlap: `startAt < timeOff.endAt && occupiedEndAt > timeOff.startAt`. The occupied end should include the Booking's purchased buffer, derived from its purchase snapshot if not stored separately. A 10:00 to 11:00 client session with a 15-minute buffer intersects TimeOff beginning at 11:05; a query that checks only Booking.endAt would miss it. An appointment whose occupied end equals TimeOff.startAt does not overlap.

Add an index or query plan appropriate to provider and start range. A booking that starts before TimeOff but ends inside it must be found, so a `startAt >= timeOff.startAt` predicate is too narrow. A bounded query can include starts before the exception by the maximum allowed service plus buffer, then apply exact overlap in code, or use a stored occupiedEndAt field and suitable MongoDB predicates. Document which approach your Booking model supports. Do not scan every Booking in the marketplace.

Save TimeOff and read conflicts within a consistent transaction or immediately after save with a documented response semantics. A concurrent checkout can still change the conflict list after response. The provider should see the current agenda and an explicit "refresh conflicts" action. The later checkout path must coordinate with provider schedule edits at its own write boundary; this route alone cannot guarantee a client will never hold a slot while a provider blocks it. Keep that open race visible in the M19 plan.

Touch Provider.scheduleRevision in the same transaction as the TimeOff write. That serializes this edit with other provider schedule writes and gives the dashboard a fresh version. It also creates the coordination point that the later checkout path must use when it rechecks rule and exception state. Merely reading the revision without a shared write or version predicate at claim time would not stop a concurrent provider change. Document that requirement explicitly rather than declaring the race solved here.

If the request repeats after a lost response, a stable client request ID can let the route return the existing TimeOff and conflict list. The idempotency record should be scoped to the authenticated provider, not globally to a raw string from a browser. A duplicate block-the-day action should not create overlapping exceptions that are hard to cancel separately. This is especially relevant on weak connections, where a provider may tap twice because the first result did not appear.

## Test that a paid appointment survives

Create a confirmed Booking at 10:00 to 11:00 UTC with a 15-minute buffer. Submit TimeOff from 10:30 to 11:30 in the provider's local zone, using a date whose conversion is known from the test fixture. Expect the TimeOff to be stored as UTC Dates and the Booking ID in the protected conflict list. Reload the Booking and assert its status, UTC start and purchase snapshot are unchanged. Reload its SlotClaims and assert they remain until an explicit booking workflow releases them. A successful TimeOff save is not evidence of a cancellation.

Add an adjacent case: TimeOff begins exactly at the Booking occupied end. The conflict list should be empty for that Booking. Add a cancelled Booking and verify it is excluded. Add a Booking for Provider B at the same UTC time and verify it is excluded. Test invalid local gap and overlap boundaries with stable 422 codes, and a cross-provider POST that cannot create TimeOff for another provider ID.

After saving, return a response with `timeOff` fields, `conflicts` and a `scheduleRevision` or current version for the dashboard. Keep the reason private. The UI can say "Time off saved; 1 existing booking needs attention" and link to that provider-owned Booking. If the database write fails, return an error and do not show success. If the conflict query fails after save, report the partial outcome honestly and provide a safe retry path; a transaction can avoid that split when the replica set is available.

Commit the route and tests. Put one example in `docs/provider-schedule-decisions.md` showing local input, stored UTC interval and a paid Booking that remained unchanged. The next lesson turns weekly rules into a readable weekday grid so the provider can manage this schedule without thinking in raw JSON.

Test a TimeOff interval that begins before a Booking and ends during its buffer, then one that begins during the Booking and ends after it. Both overlap under the half-open formula. Test an interval ending exactly at Booking.startAt and one beginning exactly at occupiedEndAt; neither overlaps. These four cases catch the common mistake of checking only start times or using inclusive comparisons at both ends.

Finally, test a provider who has no Booking in the interval. The response should contain the saved TimeOff and an empty `conflicts` array, not a 404. That empty result is a valid instruction: future offers are blocked, and no existing client needs attention. A database outage, by contrast, should surface as a failed save or explicit partial outcome. Do not make both situations look like an empty conflict list.
