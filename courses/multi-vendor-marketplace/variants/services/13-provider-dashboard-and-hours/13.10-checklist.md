# Provider schedule gate

This gate asks you to run the provider's work from the dashboard, not merely show that route files exist. Sign in as one seeded Gaza provider. Create an active Service with whole-block duration and buffer, save weekly hours in `Asia/Gaza`, add a dated TimeOff interval, and inspect a protected list of existing Bookings that overlap it. Show that the public listing appears only after the provider deliberately publishes with at least one active Service and one valid active rule. The review should also prove that none of these edits silently moves or cancels a paid Booking.

Keep `docs/provider-schedule-decisions.md` beside the UI. It should record local form input, the saved rule fields, the saved UTC TimeOff interval, exact overlap convention, schedule revision behavior and one existing Booking that remained unchanged. Include the provider zone and runtime versions for any clock-change example. A mentor should be able to reproduce the date conversion rather than accept a screenshot of a friendly label.

## Show one complete provider flow

Begin from a draft Provider with no active Service. The dashboard should say what is missing. Create a 60-minute tutoring Service with a 15-minute buffer and a clear price and cancellation policy. It should still say weekly hours are missing. Add Monday 09:00 to 12:00 local hours with an effective date. The dashboard can now say "Ready to publish," while the public route remains closed until the provider chooses Publish. After publishing, the listing may appear, and Module 15 can compute dated UTC starts.

Add TimeOff over part of one dated Monday. The availability response for that date should omit starts whose full Service plus buffer interval intersects it. The weekly rule still exists for later Mondays. If a confirmed Booking overlaps, the dashboard should list it as action needed while its UTC start, status, Order and claims remain unchanged. Show the Booking before and after the TimeOff save. A route response saying "saved" without this comparison is not enough to prove the client promise survived.

## Gate checklist

- [ ] Services table and forms create, edit and archive only the authenticated provider's Services.
- [ ] Service duration and buffer reject off-grid values; price uses integer minor units and old Booking snapshots remain fixed after edits.
- [ ] Weekly grid displays local `HH:mm` hours and Provider.timeZone, even when the browser zone differs.
- [ ] Rule API rejects overlapping time and effective-date ranges, invalid dates and stale schedule revisions.
- [ ] A provider-zone change requires rule review; active mismatched rules cannot make the provider ready.
- [ ] TimeOff API stores resolved UTC intervals and returns protected held or confirmed Booking conflicts without cancelling them.
- [ ] "Block the rest of today" uses the injected server clock and next provider-local day boundary.
- [ ] Listing readiness requires permitted status, at least one active Service and one valid active rule; TimeOff only removes dated offers.
- [ ] Cross-provider direct requests cannot read or edit another provider's Service, rule, TimeOff or conflict list.
- [ ] The decision note, route tests, dashboard tests and a dated sample response are committed.

Run a same-weekday overlap test with two tabs or two concurrent requests against the replica-set database. The pure overlap helper should identify an intersection, and the schedule-revision transaction should stop two stale writes from both committing conflicting active rules. A client checkout needs a later coordinated write policy with provider edits; do not claim this module has proved that race safe. Write the open cross-workflow test in the decision note for Module 19.

Run an error-path review with a skipped local boundary, a stale revision, an unauthorized provider and a database outage. The dashboard must preserve the draft values and say whether the change saved. A 422 asks for a valid time; a 409 asks for conflict review or reload; a 401 asks for sign-in; a server error must not look like an empty schedule. Check focus, keyboard path and text status at phone width. A colored timetable alone is not an accessible explanation.

## Learning log

1. Why does the provider enter Monday 09:00 in their working zone while a paid Booking stores a UTC start? Give one clock-change or travel example.
2. A provider blocks today from 11:31 until local midnight while a confirmed session begins at 12:00. What does TimeOff change immediately, and what still requires an explicit booking workflow?
3. Two tabs add overlapping Monday rules at once. Why is a pure `rulesOverlap` check insufficient without a serialized write boundary?
4. An active Service and rule exist, but the Provider is still draft. What does the dashboard say, and what does the public route return?

Answer with field names, one dated UTC value and the exact status or error code where relevant. If an answer says that a rule edit changes Booking.startAt, revisit Module 6's separation of recurring intentions and commitments. If it says a public calendar slot is guaranteed, revisit Module 15's advisory read and Module 19's future claim transaction.

Commit the provider flow and test evidence. The next module handles portfolio images, then the availability engine turns these saved Services and rules into UTC candidates. Keep the Provider.timeZone, active rule.timeZone and M15 adapter contract aligned as you continue. This gate is passed when another person can make the same edits, see the same server outcomes and explain which client promises remain unchanged.

Before closing the gate, have the mentor choose one saved rule and one TimeOff record. Ask them to point out why one has local `HH:mm` fields and the other has UTC Date boundaries. Then ask what happens if the provider changes their working zone tomorrow. The correct response includes rule review, unchanged paid Booking instants and a changed display label only where appropriate. If the saved records cannot support that explanation, revise the model contract before moving to the availability engine.

Record the result in the learning log, including one issue the mentor found and the change made to resolve it. A checklist with every box ticked but no reproducible route response or test output does not pass this gate.
