# Step through windows in UTC

After lesson 15.5, each valid rule occurrence has a dated UTC `startMs` and `endMs`. Now enumerate candidate starts inside those boundaries. This operation uses absolute elapsed minutes. A provider's wall clock can skip from 01:59 to 03:00 or repeat an hour, but UTC milliseconds remain ordered. Step through the resolved interval in 15-minute increments and test whether the service plus its buffer fits before the window end. Do not return local time labels from this function; the route can format UTC starts for each viewer later.

The rule expander and candidate stepper answer different questions. The expander asks which local dates and wall times the provider intended. The stepper asks which instants inside that dated interval can hold a fixed elapsed service. Mixing them invites a bug: `localTime.plus({ minutes: 15 })` may move over a gap or through a repeated hour in a way that is hard to compare with claims. Once both boundaries are resolved, use UTC arithmetic for the service duration and the 15-minute block grid.

```mermaid
flowchart LR
  A[Local Sunday 01:00 to 04:00] --> B[Resolve in named zone]
  B --> C[UTC 06:00 to 08:00 on spring change]
  C --> D[Step 06:00, 06:15, 06:30...]
  D --> E[Keep starts whose occupied end fits]
```

## Implement the candidate generator

Add the following helper in `engine.js`. It does not know about time off, claims or notice yet. Its only condition is that every returned candidate is aligned to the absolute UTC grid and has enough room for the client session plus provider buffer. Keep the start and end values as numbers inside the pure engine so comparisons are not repeated string parses. Convert to ISO strings at the API edge.

```js
export const BLOCK_MINUTES = 15;
const BLOCK_MS = BLOCK_MINUTES * 60_000;

export function candidateStarts(window, durationMinutes, bufferMinutes) {
  const total = durationMinutes + bufferMinutes;
  if (!Number.isInteger(durationMinutes) || durationMinutes <= 0 || durationMinutes % BLOCK_MINUTES !== 0) {
    throw new Error('Service duration must use whole 15-minute blocks');
  }
  if (!Number.isInteger(bufferMinutes) || bufferMinutes < 0 || bufferMinutes % BLOCK_MINUTES !== 0) {
    throw new Error('Service buffer must use whole 15-minute blocks');
  }
  if (!Number.isFinite(window.startMs) || !Number.isFinite(window.endMs) || window.endMs <= window.startMs) {
    throw new Error('Expected a valid UTC window');
  }
  const occupiedMs = total * 60_000;
  const first = Math.ceil(window.startMs / BLOCK_MS) * BLOCK_MS;
  const starts = [];
  for (let startMs = first; startMs + occupiedMs <= window.endMs; startMs += BLOCK_MS) {
    starts.push(startMs);
  }
  return starts;
}
```

The `Math.ceil` aligns the first candidate to the UTC block grid. It does not round the provider's saved rule in place. If an old rule begins at 09:07 local, the earliest candidate could be 09:15 UTC after conversion, depending on its zone. That may surprise the provider, which is why the rule API should reject off-grid boundaries and expose migration errors rather than rely on this rounding silently. The stepper's alignment is a defensive guarantee for claim-key consistency, not permission to accept arbitrary rule input.

Test a straightforward 09:00 to 11:30 UTC window with a 60-minute service and 15-minute buffer. The first start is 09:00. The last is 10:15 because 10:15 plus 75 minutes is 11:30. There are six candidates at quarter-hour steps. A 10:30 start is excluded. If your loop includes it, the condition probably checked only the 60-minute client session and forgot the provider buffer.

Test an interval whose start is not aligned, such as 09:07 to 11:30 UTC, without changing the stored rule. The helper should begin at 09:15 and still end at 10:15. Then fix the upstream rule validation. This test documents the stepper's defensive behavior while making the editor's stricter contract clear. It also protects against floating-point stepping: every candidate is an integer UTC millisecond value divisible by the block size.

## Let the historical clock change alter the count

Use the `expandWindows` result for New York 2024-03-10 01:00 to 04:00. The resolved UTC window is 06:00 to 08:00. With a 60-minute service plus 15-minute buffer, candidate starts run from 06:00 through 06:45. That is four starts, not the nine starts you might infer by counting a three-hour wall-clock span. For New York 2024-11-03 00:00 to 03:00, the UTC interval spans four hours, so the corresponding candidate count is larger. You do not need a special DST branch in `candidateStarts`; correct endpoint conversion plus UTC stepping produces the difference.

For each generated UTC start, format it back in the provider's zone during a test and inspect the local label. A spring gap should have no 02:xx local label. A fall overlap may produce repeated local labels with different offsets and different UTC instants. If the product UI cannot distinguish those, it should show the offset or zone abbreviation beside the dated label. The engine must not deduplicate by a local `HH:mm` string, because two different instants may share that visible clock reading.

The first version's provider rule input policy rejects a gap or overlap at a rule boundary. A window can still span a transition with valid boundaries, as these tests show. If the business decides to forbid all windows spanning a transition, that is a different explicit policy and would require a clear provider notice. Do not achieve it accidentally by assuming a constant 24-hour local day or by truncating at the offset change.

## Check upper bounds and duplicate rules

The request is capped at seven dates, but a provider might have several daily rule windows. A malicious or corrupt rule record could create thousands of starts. Set a reasonable per-request maximum and return a controlled error if it is exceeded; do not slice silently and tell the client the truncated list is complete. M13 should reject overlapping rules for the same weekday. The planner should still deduplicate identical UTC start instants after combining valid windows, because the endpoint may receive old data created before that validation existed.

When deduplicating, sort numbers and compare exact UTC milliseconds. Do not compare formatted strings in a client zone. The same UTC start could appear in two overlapping rule occurrences, while two different UTC starts could share one local label during a fall overlap. The equality key is the instant. Keep the engine's output sorted ascending so pagination or a slot picker does not depend on MongoDB document order.

The next lesson adds the blockers. For now, print the six 09:00 to 10:15 candidates and the four spring-transition candidates. Commit the helper and its tests. These results are the candidate universe; they are not yet bookable offers. Time off, claims, notice and horizon will remove starts without changing the original weekly rule or any existing Booking.

If you find yourself storing these candidates in a new `Slot` collection, pause and revisit lesson 15.1. The durable records are rules, exceptions, claims and bookings. The generator can run again when the provider changes hours or when a claim appears. That repeated calculation is the point of the availability engine.

## Inspect the generated instants, not just the count

For the spring-transition fixture, print each candidate UTC ISO string and its provider-local label with offset. The labels jump over the missing hour, while the UTC values move by exactly fifteen minutes. For the fall fixture, two UTC candidates may format to the same local clock label with different offsets. Assert the UTC values remain distinct. A test that only counts candidates can pass even if the engine accidentally deduplicates by `HH:mm` later. Save a short transcript in `docs/availability-decisions.md` to help a reviewer see the relationship.

Check the candidate nearest the window end by hand. With a 09:00 to 11:30 UTC window and 75 occupied minutes, 10:15 ends at 11:30 and fits; 10:30 ends at 11:45 and does not. Change only the buffer from 15 to 30 minutes. The latest start moves to 10:00. This is a useful mutation test because it proves `candidateStarts` uses both service and buffer, rather than returning a fixed array of quarter-hour labels. Run it before adding blockers, so a missing start can only come from the window fit rule.

If the provider has two disjoint windows on the same date, run the helper once per window. Do not combine their earliest and latest boundaries into one large interval or you will publish slots during the break. After filtering each window, combine numeric UTC starts and deduplicate exact values. A weekly rule editor that rejects overlapping rules should make duplicates rare, but old data and special exceptions can still create them. The engine's result should be deterministic without trusting document order.
