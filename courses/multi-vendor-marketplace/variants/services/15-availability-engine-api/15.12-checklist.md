# Availability engine gate

This gate asks for executable evidence, not only a route that appears to return plausible times. Show a mentor the pure rule expansion, UTC candidate stepping, full-interval blocker filter, notice and horizon filter, bounded database adapter and public route. Run the tests in front of them or provide the recorded test output from a clean run. The evidence should let someone else explain why the 09:00 candidate disappears when the 10:00 buffer block is claimed, and why the same weekly local rule can resolve to a different UTC hour after a clock change.

Commit `docs/availability-decisions.md` with a compact sample of the actual API response from your project. Include provider and service identifiers that are safe to share, the provider IANA zone, the request's `startDate`, the fixed or recorded server timestamp, and at least two UTC starts. Do not include a client's name, meeting link, home address, TimeOff reason or payment identifier. The public contract returns offers only. A sample that includes private blockers is evidence of a leak, not extra thoroughness.

## Evidence to put beside the response

Your decision note needs the seven-day provider-local date interpretation, the strict notice boundary, the exclusive horizon boundary and the half-open occupied interval convention. Write one example of each with actual values. For example, a 60-minute service plus 15-minute buffer at 09:00 UTC occupies through 10:15 and claims 09:00, 09:15, 09:30, 09:45 and 10:00. A TimeOff that begins at 10:00 removes that start; one that begins exactly at 10:15 does not. A displayed candidate at 09:00 is not a hold and may receive a 409 later.

Show the clock-change test with its historical date and the installed Node and Luxon versions. It must assert both resolved UTC boundaries and the count of candidate starts after stepping in UTC. Show a gap or overlap boundary that produces a visible rule issue rather than a guessed offer. Run the same test with two process `TZ` settings. If the UTC output changes with the server host zone, the engine has an implicit time dependency and the gate fails.

## Gate checklist

- [ ] The `GET /providers/:id/availability` route requires a scoped, active service and validates a provider-local `startDate`.
- [ ] Each matching weekly rule resolves both dated boundaries through the named-zone helper; invalid dated occurrences are reported and omitted.
- [ ] Candidate starts advance by absolute UTC 15-minute blocks and fit the full duration plus buffer before the rule window end.
- [ ] One TimeOff overlap query and one SlotClaim block query cover the entire expanded range for the selected provider.
- [ ] Every offer avoids the full TimeOff interval and all claimed service and buffer blocks.
- [ ] Exact notice and horizon boundaries match the documented comparisons and use one injected server instant.
- [ ] The route returns sorted UTC `Z` starts and a server timestamp without private blocker data.
- [ ] A fully booked day returns an ordinary empty list; a database failure does not.
- [ ] Clock-change, gap or overlap, buffer, time-off, full-day, provider-scope and HTTP error tests pass.
- [ ] The sample response and test commands are committed in `docs/availability-decisions.md`.

If a check fails, keep the module open. A green normal-day route does not compensate for a red transition test. A successful pure planner does not compensate for a repository query missing claims near the last window end. A safe query does not compensate for a route that accepts Provider B's service under Provider A's path. Fix the narrow failing boundary, rerun its test and then rerun the full module suite. Record the failing input and the correction in the decision note so a future reviewer can see why the guard exists.

Ask the mentor to choose an untested candidate. Let them name a start, service length, buffer and one blocker. Calculate the needed blocks by hand, then call the engine with that fixture. The result should follow the same half-open rule as the examples. If the code and explanation disagree, do not change the test to make it green until you find which model is wrong. The point of a gate is to expose a mistaken mental model before the client slot picker and checkout rely on it.

## Learning log

1. A 60-minute appointment at 09:00 has a 15-minute buffer. List every claim key and explain why a 10:00 claim blocks it but a 10:15 claim does not.
2. A weekly 09:00 provider rule produces a different UTC start after a clock change. Which part of the engine uses the local calendar, and which part steps in UTC?
3. A client sees 10:15 in the API response, but another client claims one needed block before checkout. What does the GET response guarantee, and what must the checkout transaction decide?
4. A TimeOff record starts before the requested seven-day range and ends inside its first window. Which repository predicate must include it?

Answer in your own words with at least one dated value. A mentor should be able to tell whether you understand the distinction between a read snapshot and an exclusive write. If your answer says the API "books" the slot, revisit the claim model in Modules 3 and 15.3. If it says a weekly rule stores UTC forever, revisit Module 5's zone work. This module is complete only when the code, test evidence, sample response and explanation agree.

The next module uses these UTC starts for public provider browsing. A client-facing picker will show both the viewer and provider zones, but it will not recompute eligibility on the phone. Checkout later repeats the critical checks and writes SlotClaims atomically. Keep the availability decision note beside those modules so a changed buffer or notice policy cannot silently split display and write behavior.

Before closing the gate, inspect the public response one more time as an unfamiliar client. It should contain enough data to choose a dated start and display both zones, but no explanation of another person's booking or the provider's private reason for time off. If you need an internal diagnostic, put it in a protected log or provider view. The public slot list is a compact offer surface, not a calendar export. Record this privacy review alongside the test output so a later response-shape change triggers a deliberate review.
