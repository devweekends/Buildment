# Checkout and hold gate

Run a complete purchase hold from an owned cart. Choose two Services from different providers and show the server's offered UTC starts before checkout. Press Checkout once and inspect one CheckoutAttempt, two pending provider Orders, one held Booking per line, and every SlotClaim block through each Service's duration plus buffer. Show the common deadline and grouped response. Do not call this a paid appointment. Module 20 will create the external payment request and confirm or release the hold under its payment state machine.

The gate is passed by observed state and reproducible tests, not by a screenshot of a successful button. Use a replica-set database with required unique indexes built. Keep the test command and output in `docs/checkout-evidence.md`, with the seed date, provider zone, Service duration/buffer, selected UTC starts and database index names. A reviewer should be able to rerun the tests and know which records to count after each request.

## Gate checklist

- [ ] Checkout authenticates the client, loads only their cart lines and rejects tampered or overlarge requests.
- [ ] It re-reads Provider, Service, rule and TimeOff state after a shared Provider-document fence write; provider edits use the same write boundary.
- [ ] It computes occupancy with Module 15's pure `blocksFor` helper and inserts every required unique provider/block claim inside one transaction.
- [ ] A taken block aborts the entire multi-provider attempt and returns 409 with the affected line and start, leaving no partial Order or Booking.
- [ ] One pending Order exists per provider, one held Booking per line, and purchase snapshots preserve price, duration, buffer, policy and zone.
- [ ] A repeated checkout ID with identical intent returns the same attempt and original deadline; changed intent returns `CHECKOUT_ID_REUSED`.
- [ ] An unpaid eligible expiry preserves Booking and Order history while releasing exact claims in one payment-safe transition.
- [ ] Active-hold quota is atomic for concurrent attempts, and distributed rate limits apply to new attempts without blocking recovery of an existing ID.
- [ ] Held and confirmed claims both hide overlapping offered starts; a live claim remains hidden until safe release commits.
- [ ] Twenty distinct clients racing for one slot produce exactly one 201 and nineteen 409 responses, one complete winner and zero loser records.
- [ ] A provider schedule edit racing checkout and a two-provider late claim failure have dedicated integration tests.
- [ ] The checkout route performs no external payment call or irreversible notification inside a retryable MongoDB transaction callback.

## Learning log

1. Draw the two-phone timeline. Identify the database operation that decides ownership and explain why a free availability read cannot decide it.
2. For a 45-minute appointment plus 15-minute buffer at 15:00, list every claimed block and explain why 16:00 is excluded.
3. A two-provider cart loses one block after another line's claims were inserted inside the transaction. Which records persist, and what should the client see?
4. A checkout response is lost after commit. Name the stable client input, the server's stored comparison and the deadline returned on retry.
5. The hold deadline passes while a payment webhook may still be in flight. Explain why neither TTL deletion nor a browser timer can decide claim release alone.

Answer with field and index names from your implementation. Include one date and UTC instant in the block example, not only a drawing of local clock labels. If the learner claims the provider's schedule edit can silently move a paid Booking, revisit Module 13. If they claim the database transaction automatically reverses an external card charge, revisit the transaction boundary before proceeding to Module 20.

## Evidence to commit

Commit the route and model changes, migrations or index verification, the twenty-client test output, a two-provider abort test, a schedule-edit race test, a same-ID retry test, a quota concurrency test, and an expiry/release test. Include a sample 409 response with a safe line reference and a sample 201 held response with server time and deadline. Verify the API never returns raw database duplicate-key text. Show the old Booking and Order snapshots still present after safe expiry while the SlotClaim collection no longer has their keys.

Ask a reviewer to inspect one successful multi-provider attempt without using the browser. They should be able to reconstruct the client, two providers, accepted terms, UTC obligations, occupied blocks, deadline and payment state from persisted records. Then ask them to inspect a losing attempt: it should have no partial purchase records. If the evidence is ambiguous, tighten the model or test assertions before declaring this module complete.

Record one issue found in review and the change made. An empty issue log is acceptable only if the reviewer notes what they tested and why the evidence was sufficient. Keep the Module 20 handoff explicit: payment provider creation, webhook confirmation, late success, refunds and final release coordination remain open. This gate proves reliable temporary ownership and safe recovery from concurrency and network failure; it does not certify that money has moved.

## Review three traces

Trace one is the ordinary winner. Show the date and zone of each provider's offered local start, the resolved UTC Booking instants, the occupancy block list, the common hold deadline and the per-provider Order totals. Confirm that the summed provider totals equal the attempt total. Refresh availability from another client and show that starts overlapping the held blocks disappear. The UI should name the hold and countdown while avoiding a paid label.

Trace two is the late loser. Prepare two valid clients at the same start, pause them before the claim boundary, and release them together. Keep the winner's attempt and claim IDs in the evidence. The loser's 409 should identify its stale cart line without exposing the winning client's identity. Query the database after the response and show no loser Order, Booking, claim or consumed quota. Reversing request arrival should change which client wins, not the one-winner invariant.

Trace three is a lost response. Suppress the first HTTP response after commit, then retry with the same checkout ID. Show that the second response names the same attempt, Orders, Bookings, claim count and original deadline. Move the test clock forward before retry to make a deadline reset detectable. Then change one cart line but reuse the ID and show `CHECKOUT_ID_REUSED`, with no new records. This trace distinguishes safe network recovery from an unauthorized change of purchase intent.

Finally, run a due unpaid release and a confirmed-booking no-op. The due attempt's history remains while its exact claims disappear and quota falls once. A confirmed Booking keeps its claims even after the former hold deadline. If Module 20 payment state has not yet been built in the reference application, label the confirmed case as a model-level fixture and record the missing integration rather than claiming a real card flow was tested. A reviewer should understand exactly where this module's evidence ends.
