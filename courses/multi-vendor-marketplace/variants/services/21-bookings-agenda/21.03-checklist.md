# Bookings agenda gate

This gate closes the client experience week, so it asks for the demo a mentor will actually watch. One client in Berlin pays for two sessions from two providers, and both people see their own week afterwards. The evidence is a short recording plus the raw responses behind the two screens, and the checks below tell you what must be visible in each.

Record it in one take if you can, but do not fake the payment. Use a Stripe test card, keep the webhook running, and let the confirmation page render from the confirmed records. A demo that backdates a Booking in the database proves the read model and nothing about the flow, so label any prepared data before you use it and say why it was prepared.

## Run the booking end to end

Sign in as Amal in Berlin and pay for a lesson with Sara in `Asia/Gaza` and a review with Omar in `Asia/Doha` in one checkout. Before payment, both bookings are held and the confirmation page names a deadline. After the test card succeeds, both are confirmed and the deadline disappears.

The confirmation page shows one card per Booking, grouped by provider, with the amount paid for each and the total matched against the payment. On the recording, say the amount out loud and point at the same figure on the Stripe test event. Then open each booking and confirm the two labels: Amal's Berlin time first and the provider's local time second, both with a zone abbreviation.

## Show both agendas updating

Open Amal's booking list. The two confirmed sessions sit in upcoming, in start order, with the earlier one first. Open Sara's agenda for the same date and confirm the lesson appears once, at the right hour of her own day. Open Omar's agenda and confirm the review appears there and only there. Then check the other direction: Sara's agenda must not contain Omar's review, and Omar's agenda must not contain Sara's lesson.

Wait for the hold to be irrelevant before you trust this. A held booking may appear on both agendas in its quiet band, so do the comparison after payment, and mention that held appointments look different on purpose. This is also the moment to show a second provider account with an empty agenda, because an agenda that shows everything is indistinguishable from one that shows nothing when you only have one account.

## Open the file in a real calendar

Download the calendar file for the confirmed lesson. Open it in a calendar application, not a text editor, and show the event placed on the correct day and hour in the device's own zone. Then read the file as text on screen and point at three lines: `DTSTART` ending in `Z`, the stable `UID`, and the description carrying the provider's local label and zone.

Import the same file a second time and show one event rather than two. That is the only check that proves the `UID` is derived from the booking and not from the download time. Then delete the event and import once more, so the recording ends with the entry present.

Finally, try the file for a booking that is not yours. Use Rami's token against one of Amal's booking ids and show 403 for both the booking view and the file. A screen that hides a button proves nothing, so the terminal result is the evidence that matters here.

## Prove the place rule

For the online lesson, the meeting link must appear to both participants after confirmation and to nobody else. For the in-person review, the address must appear to Amal once the booking is confirmed, and it must be absent from the JSON before payment. Show the response body for the held state and for the confirmed state side by side, and point at the missing key rather than an empty string.

If your build returns an empty location field rather than omitting it, note it as a defect and fix it before finishing. The difference looks cosmetic in a response body and decides whether a component renders an empty row that the next change fills from somewhere less careful.

## Check the day boundary

Pick the booking that is closest to midnight in one of the two zones. Show its instant in the database, its label on Amal's list and its label on the provider's agenda. The provider's day must contain it under the provider's local date, which may differ from Amal's date. If both screens show the same calendar date for a booking at 00:30 Gaza time that a Berlin client sees before midnight, one of them is formatting with the wrong zone.

Run the same check across a clock change in your seeded data, or with a fixed test clock if the demo window does not contain one. The label may legitimately change; the instant may not. Say which of the two moved and why, because a reviewer will ask.

## What this gate does not prove

There is no cancellation or rescheduling yet, so nothing here shows what happens to an agenda when a session moves or ends early. The reminder messages do not exist yet either, so a moved appointment cannot yet send a stale reminder. Both arrive in Module 22 and Module 24, and the gate in Module 22 tests the swap.

The gate also does not prove the file opens in every calendar. You tested one application on one device. Say which one, and leave the untested ones as named limits rather than claims.

## Gate checklist

- [ ] One paid cart created two confirmed Bookings under two provider Orders, and the confirmation page shows one card per Booking grouped by provider.
- [ ] Each card shows the viewer's local time first and the other party's local time second, and both carry a zone label.
- [ ] The paid amounts on the cards match the Stripe test event, and the sum matches the cart total from Module 18.
- [ ] Amal's list splits upcoming and past against the server clock, with the earlier session first in upcoming.
- [ ] Each provider agenda contains only their own bookings, in their own zone, grouped by their own local date.
- [ ] A held booking is visible in its quiet band and disappears from the agenda on expiry, while remaining readable in history.
- [ ] The calendar file opens in a calendar application at the correct instant, and a second import updates one event rather than adding two.
- [ ] The file contains `DTSTART` and `DTEND` in UTC with a trailing `Z`, a `UID` derived from the booking id, and the provider zone in the description.
- [ ] The file is refused with 409 for a held booking and with 403 for a request from a non-participant.
- [ ] The location key is absent from a held booking's JSON, present for a confirmed participant, and absent for a stranger.
- [ ] The booking closest to midnight appears under the provider's local date on the provider agenda and under the client's local date on the client list.
- [ ] The recording, the two raw booking responses, the file text and the 403 bodies are saved in `docs/agenda-evidence.md`.

## Learning log

1. Why does the confirmation page read Bookings rather than Orders, and which figure on that page comes from an Order?
2. Amal's booking is confirmed and Omar's is held. Which of the two returns a calendar file, and what does the other return instead?
3. Explain how your file's `DTSTART` is derived from the stored document, and why the description repeats the provider's local time as words.
4. A booking at 00:30 in `Asia/Gaza` appears on two dates in two screens. Which screen is wrong, and which zone did each one use?
5. Name the field that is absent from a held booking's response and describe the response body that proves the rule.

Answer with route names, field names and the values you observed. If you cannot say which screen formats which zone without opening the code, the boundary is in the wrong place, and Module 22 will move instants under a display layer you do not yet trust.
