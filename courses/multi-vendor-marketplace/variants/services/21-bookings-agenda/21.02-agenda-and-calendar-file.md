# My bookings, provider agenda and the calendar file

You have paid bookings in the database and two people who need to see them. Rami wants his week, in his zone, with a way to put Tuesday's lesson into his phone. Sara wants her Tuesday, in her zone, as a grid she can read at a glance. Both screens read the same documents and neither may read the other's private facts.

Build the read model first, then the two list routes, then the file. The read model is the part that decides what a viewer may see, and every route below reuses it. If you write the calendar file before the read model, you will find yourself writing a second projection inside the file builder, and the two will disagree about whether a held booking shows a meeting link.

```ts
// server/src/modules/bookings/booking.types.ts
export type BookingStatus = "held" | "confirmed" | "completed" | "cancelled" | "expired";

export interface BookingListItem {
  bookingId: string;
  status: BookingStatus;
  title: string;
  durationMinutes: number;
  startAt: string;
  sessionEndAt: string;
  occupiedEndAt: string;
  priceMinor: number;
  currency: string;
  providerName: string;
  providerTimeZone: string;
  viewerLabel: string;
  counterpartLabel: string;
  isOnline: boolean;
  location?: { detail: string };
}

export interface BookingsPage {
  viewerZone: string;
  serverNow: string;
  upcoming: BookingListItem[];
  past: BookingListItem[];
}

export interface AgendaPage {
  zone: string;
  from: string;
  to: string;
  days: { date: string; items: BookingListItem[] }[];
}
```

`viewerLabel` and `counterpartLabel` are computed strings, and they are the only place a formatted time appears. The document keeps instants only. If a later change to a zone's rules moves a label, one read regenerates it, and no stored string goes stale.

One booking reaches three surfaces, and the trace below is the path all three take. Follow it once before you write a route, because the fourth step is the one that decides what a stranger may read.

Steps two to four are shared by every screen, which is why the projection is a function and not a route. Step five is the only one that leaves the application, and it is the only one that cannot be corrected after the client downloads it.

## Query each agenda by its own key

The client list needs bookings where the client is the viewer. The provider agenda needs bookings where the provider is the viewer and the start falls inside a day or a week. Both are indexed range reads from Module 6, and neither touches the Service or Provider collections.

```js
// server/src/modules/bookings/booking.queries.js
export async function clientPage({ clientId, serverNow }) {
  const upcoming = await Booking.find({
    clientId,
    startAt: { $gte: serverNow },
    status: { $in: ["held", "confirmed"] },
  }).sort({ startAt: 1 }).limit(20).lean();

  const past = await Booking.find({
    clientId,
    $or: [{ startAt: { $lt: serverNow } }, { status: { $in: ["cancelled", "expired", "completed"] } }],
  }).sort({ startAt: -1 }).limit(20).lean();

  return { upcoming, past };
}

export async function providerDay({ providerId, from, to }) {
  return Booking.find({
    providerId,
    startAt: { $gte: from, $lt: to },
    status: { $in: ["held", "confirmed", "completed"] },
  }).sort({ startAt: 1 }).lean();
}
```

The two filters differ on purpose. A cancelled booking that starts next Friday is not a plan, so it leaves the client's upcoming list and appears in past, where the refund history lives. It never appears on the provider's day grid, because that grid is capacity, and capacity that has been released is not capacity. `held` appears on both, in a separate visual band, because a provider deciding whether to accept an extra student needs to know that an hour may go away within ten minutes.

Pagination matters more than it looks. A client with two years of history must not download all of it in one response. The limits above are fixed pages for this course; a cursor on `startAt` and `_id` is the honest upgrade, and a page number is not, because rows are inserted between loads.

## Project one document for one viewer

Every route builds its response through one function. It checks participation first, then decides which optional fields exist. The check throws, so no route can accidentally render a booking it should have refused.

```js
// server/src/modules/bookings/booking.view.js
export function toBookingView(booking, viewer, viewerZone, nowUtc) {
  const isClient = String(booking.clientId) === viewer.id;
  const isProvider = viewer.providerId && String(booking.providerId) === viewer.providerId;
  if (!isClient && !isProvider) {
    throw new ApiError(403, "BOOKING_FORBIDDEN", "This booking is not yours.");
  }
  const maySeePlace = booking.status === "confirmed" || booking.status === "completed";
  const view = {
    bookingId: String(booking._id),
    status: booking.status,
    title: booking.purchase.title,
    durationMinutes: booking.purchase.durationMinutes,
    startAt: booking.startAt.toISOString(),
    sessionEndAt: new Date(booking.startAt.getTime() + booking.purchase.durationMinutes * 60000).toISOString(),
    occupiedEndAt: new Date(
      booking.startAt.getTime() + (booking.purchase.durationMinutes + booking.purchase.bufferMinutes) * 60000
    ).toISOString(),
    priceMinor: booking.purchase.priceMinor,
    currency: booking.purchase.currency,
    providerName: booking.purchase.providerName,
    providerTimeZone: booking.purchase.providerZone,
    viewerLabel: formatInZone(booking.startAt, viewerZone),
    counterpartLabel: formatInZone(booking.startAt, isClient ? booking.purchase.providerZone : booking.purchase.clientZoneAtPurchase),
    isOnline: booking.purchase.locationType === "online",
  };
  if (maySeePlace && booking.purchase.location) view.location = { detail: booking.purchase.location.detail };
  return view;
}
```

The `location` key is absent for a held booking, not empty. A key that exists with an empty value is the field a component will render as an empty row, and the next developer will fill it from somewhere less careful. Deleting the key makes the missing permission visible in the response body, which is exactly what you want when you read a test failure.

`clientZoneAtPurchase` is one field this snapshot needs and Module 6 did not have. Add it to the purchase subdocument and fill it in the checkout transaction, next to `providerZone`. A provider greeting a student at the wrong hour is a small annoyance with the same root cause as every other wrong time in this course: a zone was read from the current profile instead of from the moment of the sale.

Sara's view needs the client's name to greet a student at the door. Rami's view needs the provider's name and headline. Both are display facts copied into the purchase snapshot at checkout, so neither route joins to a profile. Neither view contains the other party's email, phone number or full address until the place rule allows it.

## Format for the viewer, and label the zone

`formatInZone` is one small function over `Intl.DateTimeFormat`, created once per request rather than once per row, because building a formatter is the expensive part on a cheap phone's browser and it is not free on the server either.

```js
// server/src/shared/format-zone.js
const cache = new Map();
export function formatInZone(date, zone) {
  if (!cache.has(zone)) {
    cache.set(zone, new Intl.DateTimeFormat("en-GB", {
      timeZone: zone, weekday: "short", day: "2-digit", month: "short",
      hour: "2-digit", minute: "2-digit", timeZoneName: "short",
    }));
  }
  return cache.get(zone).format(date);
}
```

Rami's next Tuesday lesson reads `Tue, 13 Jan, 14:00 GMT+1` on his list, and the line below reads `15:00 EET` for Sara. Sara's agenda header says `Asia/Gaza` once, and every row is in her own day. Two clients in two zones looking at the same Booking see two different label pairs and the same `startAt`, which is the test that proves the boundary is in the right place.

For the provider's day view, compute the day window in the provider's zone: midnight to midnight in `Asia/Gaza`, converted to instants, then used as `from` and `to`. Do not build the window from the server's own midnight, because a provider in Doha will see a grid that starts three hours late and one appointment in the wrong day on a clock-change weekend.

## Draw both agendas on a phone

Rami reads his list while walking, and Sara reads hers between lessons, so both screens are phone screens first. The client list is a stack of cards, one per booking, in start order. Each card carries the service title, the primary time label, the secondary label, the status word and a 44 pixel download control. Do not put the download behind a menu: a client who has just paid is the person most likely to want the file, and the confirmation page is where that intent peaks.

A week grid does not survive 360 pixels. Render the provider agenda as a list grouped by local date, with one sticky date header per day and a count of confirmed sessions beside it. Sara scans for the day, then reads the hours. A grid of seven columns and twelve rows at that width gives every cell a label she cannot read, which is a calendar that looks professional in a screenshot and is useless in a corridor.

Handle the two empty states separately. A client with no bookings sees an invitation with a link to the provider list. A request that failed on a weak connection sees a retry button on the same screen, because the two states mean different things and the wrong one teaches Rami that his purchase vanished. The provider's empty day says the day is free, not that the agenda failed to load.

## Generate a calendar file that cannot be misread

The file route takes a booking id, loads it, runs the same participation check, and refuses anything that is not confirmed or completed. A held booking has a deadline attached; a file on a phone outlives that deadline in seconds, and a durable copy that asserts an appointment which may never exist is worse than an error message.

```js
// server/src/modules/bookings/ics.js
const stamp = (date) => date.toISOString().replace(/[-:]/g, "").replace(/\.\d{3}/, "");

export function icsForBooking(booking, { nowUtc, viewerZone }) {
  const start = booking.startAt;
  const end = new Date(start.getTime() + booking.purchase.durationMinutes * 60000);
  const local = formatInZone(start, booking.purchase.providerZone);
  const lines = [
    "BEGIN:VCALENDAR",
    "VERSION:2.0",
    "PRODID:-//SkillSlot//Bookings//EN",
    "CALSCALE:GREGORIAN",
    "METHOD:PUBLISH",
    "BEGIN:VEVENT",
    `UID:${booking._id}@skillslot`,
    `DTSTAMP:${stamp(nowUtc)}`,
    `DTSTART:${stamp(start)}`,
    `DTEND:${stamp(end)}`,
    `SUMMARY:${escapeText(booking.purchase.title)}`,
    `DESCRIPTION:${escapeText(`${local} in ${booking.purchase.providerZone}`)}`,
  ];
  if (booking.purchase.location && booking.status === "confirmed") {
    lines.push(`LOCATION:${escapeText(booking.purchase.location.detail)}`);
  }
  lines.push("END:VEVENT", "END:VCALENDAR");
  return lines.flatMap(fold).join("\r\n");
}
```

Three properties make this file portable. `DTSTART` and `DTEND` end in `Z`, so no calendar application needs time zone data for `Asia/Gaza` to place the event at the right instant. `UID` is derived from the booking id, so downloading twice updates one entry instead of creating a second. And the description carries the provider's local label as words, so the person reading it in Berlin can still see the hour the tutor calls it.

The choice of UTC over a `TZID` parameter is a trade-off, not a law. A `TZID=Asia/Gaza` event is more readable in a client that already knows that zone, and it breaks when a calendar application has old time zone data or does not recognise the identifier. The UTC form is correct in every calendar, which is why this course uses it, and it costs you one line of description to keep the human context.

## Tests that fail first

```js
// server/src/modules/bookings/bookings.routes.test.js
test("one client cannot read another client's booking or its calendar file", async () => {
  const booking = await confirmedBooking({ client: amal, provider: sara });
  expect((await agent(rami).get(`/api/v1/bookings/${booking.id}`)).status).toBe(403);
  expect((await agent(rami).get(`/api/v1/bookings/${booking.id}/calendar.ics`)).status).toBe(403);
  expect((await agent(amal).get("/api/v1/bookings")).body.upcoming).toHaveLength(1);
});

test("a held booking shows no place and no calendar file", async () => {
  const booking = await heldBooking({ client: amal, provider: sara });
  const view = (await agent(amal).get(`/api/v1/bookings/${booking.id}`)).body;
  expect(view.location).toBeUndefined();
  expect((await agent(amal).get(`/api/v1/bookings/${booking.id}/calendar.ics`)).status).toBe(409);
});

test("the file carries the stored instants, not a local time", async () => {
  const booking = await confirmedBooking({
    client: amal, provider: sara, startAt: "2026-01-13T13:00:00.000Z", durationMinutes: 45,
  });
  const ics = (await agent(amal).get(`/api/v1/bookings/${booking.id}/calendar.ics`)).text;
  expect(ics).toContain("DTSTART:20260113T130000Z");
  expect(ics).toContain("DTEND:20260113T134500Z");
  expect(ics).toContain("15:00");
  expect(ics).toContain("Asia/Gaza");
  expect(ics.split("\r\n").every((line) => Buffer.byteLength(line, "utf8") <= 75)).toBe(true);
});

test("a cancelled booking leaves the provider grid and stays in the client's past", async () => {
  const booking = await confirmedBooking({ client: amal, provider: sara, startAt: plusDays(2) });
  await cancelBooking(booking.id);
  const agenda = (await agent(sara).get("/api/v1/provider/agenda?range=week")).body;
  const page = (await agent(amal).get("/api/v1/bookings")).body;
  expect(agenda.days.flatMap((day) => day.items)).toHaveLength(0);
  expect(page.upcoming).toHaveLength(0);
  expect(page.past.map((item) => item.bookingId)).toContain(booking.id);
});
```

Add a fifth test that a provider sees only their own agenda, with a second provider who has a booking in the same hour. Add a sixth that the description label equals `formatInZone(startAt, "Asia/Gaza")` for a booking on a clock-change week, so the file and the screen cannot drift apart.

## Acceptance criteria

The module is done when Rami's list splits upcoming from past against the server clock, when Sara's week grid contains only held, confirmed and completed work in her own zone, when a stranger gets 403 from both the view and the file, when a held booking carries no place and no file, and when the file's `DTSTART` equals the stored instant for a booking in a clock-change week.
