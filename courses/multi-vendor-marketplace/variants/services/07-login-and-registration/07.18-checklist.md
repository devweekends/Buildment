# 7.18 ,  Checklist and learning log
> **[Gate]** · Chapter 07 ,  Login and registration

This is the **gate** for Chapter 7. Tick every box honestly and answer the learning log below before opening Chapter 8.

<BigWordAlert term="Token storage" plainEnglish="Where the browser keeps JWTs ,  memory, sessionStorage, or httpOnly cookies ,  each with different XSS and CSRF trade-offs." whyItMatters="SkillSlot's client must store tokens safely and attach them to API calls without leaking them in URLs or logs." />

## How to read this gate

Chapter 6 could be checked with curl. Chapter 7 cannot, because the thing being checked is what a browser does over time: a page reload, an expiring token, a redirect that must not flash, a cookie the server has to accept. Every box below is therefore proved in the browser with the Network tab open, and the honest check is to watch the request rather than infer it from a screen that happens to look right.

Each box answers three questions. What is the claim, what proves it, and how would a reviewer confirm it without you. For the flow boxes the proof is the sequence of requests and their status codes. For the storage boxes the proof is an inspection of Application storage and a grep of the client source, because a token that never reaches `localStorage` is an absence and absence must be seen rather than assumed.

The groups move from what a user can do, to what the client remembers, to how requests carry identity, and finally to what the server refuses. That last group is the one that matters in Chapter 8: a client that hides a page from a client account is a convenience, and a server that rejects the same request is the actual protection.

## Chapter 7 ,  Login and registration checklist (gate)

Do **not** open Chapter 8 until every box is ticked and learning log answers are written below.

### Pages & routing

This group proves the three screens exist and that the flow between them completes without help. Register, verify and login are three routes but one journey, and a journey that needs a manual step in the middle is not finished. A reviewer reads this group by opening the browser at the register page, completing the flow with a fresh email, and watching where they land, because the redirect target is the visible proof that the client knows who just logged in.

The role redirect box carries more weight than it looks. Providers (the vendor side of SkillSlot) and clients see different destinations after login, and that decision is read from the token or the profile rather than chosen by the user. A reviewer tests it by logging in as one seeded account of each role, and if both land on the same page, the client is guessing rather than reading the claim the server issued.

- [ ] `/register`, `/login`, `/verify-otp` routes work
- [ ] Register → verify → login flow completes in browser
- [ ] Role-based redirect after login (vendor vs customer)
- [ ] Login shows error for wrong password and unverified user

### Auth state

These three boxes describe what the client remembers and for how long. Storing the access token in memory is the decision this chapter makes, and the consequences are all in this group: a reload loses the token, the boot refresh has to restore the session, and logout has to empty both the token and the user object it belonged to. A reviewer reads this by logging in, reloading the page, and then logging out and reloading again, watching the header change after each step.

The boot refresh box is where most learners discover a real bug. A page reload with no access token must call refresh once before rendering a protected route, and if the restore is missing, the symptom is a logged out user who was never logged out. A reviewer confirms it by watching the Network tab on reload and looking for the refresh request before any protected data request leaves the browser.

- [ ] useAuth or AuthProvider manages user + access token in memory
- [ ] Boot refresh restores session on page reload (or documented limitation fixed)
- [ ] Logout clears state and blocks protected routes

### API client

The API client group is where the token meets every other request. `apiFetch` attaching the Authorization header is the single change that makes the whole client authenticated, and doing it in one place is why every later chapter's pages are short. A reviewer reads this by opening the helper, then by watching one authenticated request in the Network tab and checking that the header is present and the token is the one currently in memory.

The refresh-and-retry box is the most interesting box on the page, because it describes behaviour that only appears when the access token expires. A reviewer verifies it with a short expiry, by waiting for the failure and watching for the refresh followed by the retry, and the same result is available by forcing a 401 from the server. The storage box is a search, not a memory test: no `localStorage` or `sessionStorage` write should exist in the client source, and that includes the places a developer adds late at night.

- [ ] apiFetch attaches Authorization Bearer when authenticated
- [ ] 401 triggers refresh once then retry (tested or short-expiry verified)
- [ ] credentials: 'include' on refresh request
- [ ] Access token **not** in localStorage or sessionStorage

### Protected routes

Protected routes are a client-side convenience, and this group checks that the convenience behaves. The redirect box proves an unauthenticated visitor cannot see a page that assumes identity, the role box proves the route can be narrower than logged in, and the loading box proves the client does not decide before it knows. Each of those is observable in one browser session, and the third one is the easiest to miss because it only shows for a fraction of a second.

A reviewer reads this group by loading a protected route in a fresh tab and watching the address bar. A flash of the protected page before the redirect is the loading box failing, and it is worth fixing now because Chapter 8 adds pages where that flash would show a client another provider's data before the guard runs.

- [ ] ProtectedRoute redirects unauthenticated users to login
- [ ] Vendor stub page reachable only when logged in as vendor (if role prop used)
- [ ] isLoading prevents redirect flash during boot

### Integration

Integration closes the loop with Chapter 6: the client must work against the real API, with the real seeded accounts, from the real Vite origin. A reviewer reads this group by logging in as one seeded account of each role through the UI, which proves the client and the server agree about request shape, cookie policy, and CORS. If either account fails, the cause is almost always an origin that does not match the one in the server's allowed list.

The last box is a boundary rather than a task. No new server auth endpoint should be needed in this chapter, and if you added one to make the client work, write down why, because the next chapter's authorization review will ask whether that endpoint checks ownership.

- [ ] Seed vendor-a and customer-a login via UI
- [ ] CORS allows credentials from Vite origin
- [ ] No new server auth endpoints required beyond Ch 6 (cookie Set-Cookie OK)

### Prior gates

The prior gate group guards Chapters 5 and 6 while asking you to explain the decisions this chapter added. The two regression boxes are cheap to run and expensive to skip: re-run the auth curl flow from 6.18, and confirm the seed still creates accounts that can log in. A reviewer runs both before reading any client code, because a broken server makes every client symptom a lie.

The four explanation boxes are the viva material. They ask you to describe the storage trade-off, the refresh loop, the difference between hiding a route and protecting data, and what a full reload costs. Answering them out loud in a minute each is the standard, and it is the same standard Chapter 8 uses when it asks who is allowed to read another provider's bookings.

- [ ] Ch 6 auth endpoints still answer their curl tests
- [ ] Ch 5 models and seed still hold
- [ ] Why keep the access token in memory instead of localStorage?
- [ ] Walk through the 401 refresh loop, step by step
- [ ] How ProtectedRoute differs from the server's requireAuth
- [ ] What is lost when the page fully reloads?

### Learning log ,  write now

Answer **in your own words** in the fields below:

Name the request, the status code or the file you changed. "Refresh works" is not an answer; "with a ten second access expiry, the next call returned 401, the client called refresh once, retried, and the second 200 carried the new token" is one, and it is the kind of sentence that survives a viva question.

1. **Token storage:** Where do access and refresh live in your implementation? Why?

2. **Refresh loop:** Describe network sequence when access expires mid-session.

3. **Register flow:** UX path from register to first authenticated page ,  any friction?

4. **Role redirect:** How does login decide vendor vs customer destination?

5. **CORS/cookies:** What server CORS changes were needed for refresh cookie?

6. **Failure test:** One UI error state you tested (wrong password, unverified, etc.).

7. **Chapter 8 preview:** Why is login not enough to PATCH another vendor's store?

8. **Reload test:** Does session survive hard refresh? If not, what did you fix?

## All boxes ticked?

Mark this chapter complete in the platform, then continue to **Authorization and isolation** (Chapter 8).

Fix a failed box before writing the log, unless the failure is a genuine limitation you decided to keep. A documented limitation with a reason is honest engineering; an undocumented one becomes a surprise in Chapter 8, where the first request that reveals it will be a client reading a Booking that does not belong to them.
