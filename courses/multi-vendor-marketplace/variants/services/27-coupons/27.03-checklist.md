# Coupon gate

This gate asks for money evidence in three places that must agree: the database, the payment provider's test dashboard and the client's screen. A coupon feature that is only tested in one of those places will disagree with the others at the worst moment, usually during a cancellation when the client is already unhappy.

Start with one discounted checkout and record every number. The service list price, the quote the server returned, the per-booking allocation, the PaymentIntent amount, the order amounts after payment and each booking `purchase.chargedMinor` value. They must satisfy one equation: the sum of booking paid amounts equals the payment amount, and the sum of discounts equals the difference between list and paid. Paste the numbers into your note rather than a screenshot of a page, because numbers can be checked and a screenshot cannot.

Then run the concurrency check. Seed a coupon with a cap of one and two clients, and send both checkouts at the same moment. Exactly one must succeed and the other must fail with a specific code that names the campaign, not a generic conflict. Inspect the coupon afterwards: `reservedCount` is one and `redeemedCount` is zero, because a hold has not been paid yet. Complete the winning payment and inspect again: `reservedCount` is zero and `redeemedCount` is one. This is the shape a reviewer is looking for, and it is impossible to reach with a count-then-write implementation.

Next, prove idempotency twice over. Replay the same paid webhook and show the counters unchanged. Then create a second checkout with the same checkout ID from the same client and show that only one redemption document exists. The two checks are different: one protects against a repeated event, the other against a repeated user action on a weak connection.

Finally, cancel a discounted booking and compare the refund with the amount paid. Inside the free window the refund equals `purchase.chargedMinor`. In the late window it equals the policy percentage of `purchase.chargedMinor`, rounded in integer minor units. Then cancel the other booking from a two-provider payment, where only one order carried a discount, and add up all refunds against the original charge. The total must not exceed it, and the second refund must still be accepted by the payment provider.

One more number belongs in the note. Record the value of a released reservation over a week: how many holds took a coupon slot and never paid. A campaign of twenty where six seats are occupied by abandoned carts is a campaign that sold less than it promised, and the release path is the only thing that returns those seats. Show the released count and the consumed count side by side, so a reviewer can see that the counters move in both directions.

Write `docs/pricing-decisions.md` with the funding model, the cap semantics, the remainder rule and the refund base. One paragraph each is enough. A future reviewer needs to know that the provider funds the discount and that the refund base is the paid amount, without reading the code to discover it.

## Gate checklist

- [ ] The coupon model carries a provider, a kind, the cap fields, the validity window and both counters, validated on write.
- [ ] `priceWithCoupon` is pure, uses integer minor units, and returns per-booking allocations whose sum equals the total discount.
- [ ] The payment amount equals the server total, and a client-supplied total that differs returns `QUOTE_CHANGED` with the server numbers.
- [ ] The redemption is reserved inside the checkout transaction with a conditional counter update, so a cap of one admits exactly one hold under concurrent checkouts.
- [ ] The per-client limit blocks a second checkout from the same client and allows the same checkout ID to retry idempotently.
- [ ] A replayed paid webhook consumes once, and an expired hold releases its reservation once.
- [ ] Each booking stores its paid amount and discount, and the refund path reads those fields rather than the current service price.
- [ ] A discounted refund in the free window returns the paid amount, and the late window returns the policy share of it.
- [ ] A rejected code returns a specific reason without disclosing another provider's campaign, and the apply route is rate limited.
- [ ] `docs/pricing-decisions.md` records the funding model, cap semantics, remainder rule and refund base.

If a check fails, keep the module open. A cap that leaks under concurrency is missing the conditional update, not a retry. A refund that exceeds the charge is reading the wrong base. A duplicated redemption is missing the unique index on coupon and checkout, or the index was never created on the database you are testing. Do not weaken the test to match the code. The equation at the top of this gate is the requirement, and the code either satisfies it or it does not.

## Learning log

1. Why is a provider-funded coupon a price change rather than a line item at the end of the order? Name one field that would have to exist for a platform-funded model.
2. Two checkouts read `redeemedCount: 19` with a cap of twenty. Describe the exact write that stops both from succeeding, and where it lives.
3. The discount on two bookings is 750 and the split is 500 and 250. Explain why the split is recorded rather than recomputed at refund time.
4. A late cancellation refunds 2000 from a charge of 4000. Which number was used as the base, and what would the client have seen with the other base?
5. A client says a code "stopped working". Which record answers the question, and which state would explain it?

Answer with amounts, codes and state transitions from your own project. A mentor should be able to follow 3000 from list price to 2400 paid to 1200 refunded and see the same three numbers in the quote, the payment provider and the booking. If one answer depends on editing a booking record by hand to fix a total, this module has not passed.

Before closing, read your own gate note as a support agent would. It should explain, without code, what a provider has committed to when they publish a coupon and what a client is owed when they cancel. Keep that note beside the ERD, because the demo script asks about refunds and the answer is written there.

The course closes next with the ship checklist, the documentation set and the five-minute demo. The coupon evidence belongs in that demo, since it is the shortest path to showing that the server owns the money.
