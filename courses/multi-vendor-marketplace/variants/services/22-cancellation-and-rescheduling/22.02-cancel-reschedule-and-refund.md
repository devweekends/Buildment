# Cancel, reschedule and refund by policy

Two routes carry this lesson, and both are small enough to read in one sitting. The cancellation route turns a policy snapshot into an amount of money and a state change. The reschedule route moves one appointment from one set of blocks to another without ever leaving the client with neither. Build the quote as a pure function first, because you will test it a dozen times and you do not want a database in the way.

Start from what the Booking already stores: the four policy numbers, the amount paid for this session in minor units, the two instants, and the claims that belong to it. Nothing in this module reads today's Service to decide money. If you find the module reaching for `Service.cancellationPolicy` inside a cancel handler, the snapshot has been bypassed and the dispute from the last lesson is one edit away.

```ts
// server/src/modules/bookings/cancellation.types.ts
export interface CancellationPolicy {
  freeCancelHours: number;
  lateRefundPercent: number;
  rescheduleCutoffHours: number;
  maxReschedules: number;
}

export interface RefundQuote {
  window: "free" | "late" | "after_start";
  policy: CancellationPolicy;
  paidMinor: number;
  refundMinor: number;
  retainedMinor: number;
  currency: string;
}

export interface CancelResult {
  bookingId: string;
  status: "cancelled";
  quote: RefundQuote;
  refundId: string;
  refundStatus: "pending" | "succeeded";
}

export interface RescheduleResult {
  bookingId: string;
  previousStartAt: string;
  startAt: string;
  sessionEndAt: string;
  reminderVersion: number;
  claimsReleased: number;
  claimsAdded: number;
}
```

`CancelResult` returns the quote, not only the amount. A client who sees 1800 without seeing the window and the percentage will ask support why she lost half a lesson, and the answer is already in the object you almost did not send.

## Write the quote as a pure function

The quote takes a Booking-shaped input and one instant, and returns the window, the amounts and the policy it used. No database, no payment provider, no clock of its own.

```js
// server/src/modules/bookings/refund-quote.js
export function quoteClientCancel(booking, nowUtc) {
  const policy = booking.purchase.cancellationPolicy;
  const paidMinor = booking.purchase.priceMinor;
  const currency = booking.purchase.currency;
  const hoursBefore = (booking.startAt.getTime() - nowUtc.getTime()) / 3600000;

  if (hoursBefore <= 0) {
    return { window: "after_start", policy, paidMinor, refundMinor: 0, retainedMinor: paidMinor, currency };
  }
  if (hoursBefore < policy.freeCancelHours) {
    const refundMinor = Math.floor((paidMinor * policy.lateRefundPercent) / 100);
    return { window: "late", policy, paidMinor, refundMinor, retainedMinor: paidMinor - refundMinor, currency };
  }
  return { window: "free", policy, paidMinor, refundMinor: paidMinor, retainedMinor: 0, currency };
}
```

The client path and the provider path share the arithmetic but not the window test. A provider cancellation skips `hoursBefore` and returns `refundMinor: paidMinor` with a window value of `provider_cancel`, so the history entry and the notification both say who ended the session and why. Keep the two functions separate even though one is four lines, because the difference between them is the whole argument about who broke the promise.

Write the unit table before the routes. For a paid amount of 4500 with a late percentage of 40, expect 1800 refunded and 2700 retained. For 4501, expect 1800 refunded and 2701 retained, which pins the rounding direction. At exactly 48 hours before the start with `freeCancelHours: 48`, expect the full amount, because the boundary is inclusive. At 47 hours and 59 minutes, expect the late percentage. One hour after the start, expect nothing and the `after_start` window. A percentage of 0 gives nothing back and a percentage of 100 gives everything, which are the two values a provider will actually configure.

## Cancel inside one transaction, refund outside it

The state change and the claim release belong in one transaction. The external refund call does not, because a Stripe call is not a database write and a retryable transaction callback must not repeat it.

```js
// server/src/modules/bookings/cancel.routes.js
router.post("/:id/cancel", async (req, res) => {
  const booking = await loadBookingForParticipant(req);            // 403 for a stranger
  const quote = quoteClientCancel(booking, clock.now());
  if (quote.window === "after_start") {
    throw new ApiError(409, "CANCEL_WINDOW_CLOSED", "This session has already started. Contact your provider.");
  }

  const cancelled = await connection.transaction(async (session) => {
    const updated = await Booking.findOneAndUpdate(
      { _id: booking._id, status: "confirmed" },
      {
        $set: { status: "cancelled", cancelledAt: clock.now() },
        $push: {
          history: {
            at: clock.now(),
            from: "confirmed",
            to: "cancelled",
            reason: quote.window === "free" ? "client_cancel_free" : "client_cancel_late",
            refundMinor: quote.refundMinor,
          },
        },
        $inc: { reminderVersion: 1 },
      },
      { session, new: true }
    );
    if (!updated) throw new ApiError(409, "BOOKING_NOT_CANCELLABLE", "This booking already changed.");
    await SlotClaim.deleteMany({ bookingId: booking._id }, { session });
    await Order.updateOne(
      { _id: booking.orderId },
      { $inc: { refundedMinor: quote.refundMinor } },
      { session }
    );
    await Outbox.create([{
      kind: "refund.request",
      key: `refund:booking:${booking._id}:cancel`,
      payload: { bookingId: String(booking._id), amountMinor: quote.refundMinor },
    }], { session });
    return updated;
  });

  const refund = await stripe.refunds.create(
    {
      payment_intent: booking.paymentIntentId,
      amount: quote.refundMinor,
      metadata: { bookingId: String(booking._id) },
    },
    { idempotencyKey: `refund:booking:${booking._id}:cancel` }
  );

  res.status(200).json({ bookingId: String(cancelled._id), status: "cancelled", quote, refundId: refund.id, refundStatus: refund.status });
});
```

Three details in that handler do the work. The update names `status: "confirmed"` in its filter, so a second cancellation of the same booking matches nothing and a reschedule that already moved it cannot be cancelled by a stale request. The `reminderVersion` increment happens in the same write as the state change, so a reminder job cannot observe a cancelled booking at its old version. And the idempotency key is derived from the Booking and the action, so a retried request with the same key returns the first refund instead of sending a second one.

The `refundedMinor` increment records what this application believes it has returned, and the Stripe refund event later confirms or corrects it. Do not set an Order to `refunded` in this transaction. An Order becomes `partially-refunded` when `refundedMinor` is greater than zero and less than the total, and `refunded` when it equals the total, and that comparison belongs where the money is known to have left.

## Record refunds from events

A refund has its own lifecycle. `refunds.create` may answer `pending`, a card refund may settle minutes later, and the event that proves it carries a refund identifier you did not choose. Handle `refund.updated` and `charge.refunded` behind the same signature check and the same event store that Module 20 built, and key the local record by the Stripe refund id so a redelivered event updates one row.

Each local refund record stores the payment intent, the booking, the amount, the reason, the status and the event that proved it. Recompute the Order's refunded total from those records rather than trusting an increment, because a manual reconciliation in the dashboard will otherwise leave a total that matches nothing in your database. Then set the Order state from that recomputed total.

Test the duplicate case explicitly. Deliver the same refund event twice and assert one row, one recomputed total and one state transition. Then deliver the success event after a pending one and assert the row moves forward rather than being inserted again.

## Reschedule as one swap

The swap needs four steps inside one transaction: work out the block set difference, claim what is new, release what is no longer needed, and update the Booking. The difference matters, because a reschedule from 15:00 to 15:15 shares three of its four blocks with the old time, and inserting the new set while the old claims still exist would collide with the booking's own documents.

```js
// server/src/modules/bookings/reschedule.js, inside one transaction
const policy = booking.purchase.cancellationPolicy;
const hoursBefore = (booking.startAt.getTime() - clock.now().getTime()) / 3600000;
if (hoursBefore < policy.rescheduleCutoffHours) {
  throw new ApiError(409, "RESCHEDULE_CUTOFF", "This session can no longer be moved.");
}
if (booking.rescheduleCount >= policy.maxReschedules) {
  throw new ApiError(409, "RESCHEDULE_LIMIT_REACHED", "This session has used its moves.");
}

const oldBlocks = blocksFor(booking.startAt, booking.purchase.durationMinutes, booking.purchase.bufferMinutes);
const newBlocks = blocksFor(nextStart, booking.purchase.durationMinutes, booking.purchase.bufferMinutes);
const toInsert = newBlocks.filter((block) => !oldBlocks.includes(block));
const toDelete = oldBlocks.filter((block) => !newBlocks.includes(block));

try {
  await SlotClaim.insertMany(
    toInsert.map((blockStartAt) => ({ providerId: booking.providerId, blockStartAt, bookingId: booking._id, state: "confirmed" })),
    { session, ordered: true }
  );
} catch (error) {
  if (isDuplicateKey(error)) throw new ApiError(409, "SLOT_TAKEN", "That start was taken while you chose it.");
  throw error;
}

await SlotClaim.deleteMany({ bookingId: booking._id, blockStartAt: { $in: toDelete } }, { session });

const moved = await Booking.findOneAndUpdate(
  { _id: booking._id, status: "confirmed", startAt: booking.startAt },
  {
    $set: { startAt: nextStart, endAt: newSessionEnd },
    $inc: { reminderVersion: 1, rescheduleCount: 1 },
    $push: { history: { at: clock.now(), from: "confirmed", to: "confirmed", reason: "rescheduled", previousStartAt: booking.startAt } },
  },
  { session, new: true }
);
```

Claim before you release. The insert is the step that can fail, so it goes first, and a duplicate key error aborts the whole transaction with the old claims untouched and the Booking still on its original instants. The Booking update also filters on the old `startAt`, so two swaps racing on the same booking cannot both apply.

The `reminderVersion` increment travels with the move. In Module 24 the reminder processor compares the version stored on the job with the version on the Booking and drops the job when they differ, so a message about Tuesday cannot be sent for a session that now happens on Thursday. Until that queue exists, test the counter itself: one move increments it once, and a failed move increments nothing.

Write the move instruction in the same transaction, as an outbox row keyed by the booking and the new version. That row is what lets a later worker cancel or replace the scheduled jobs, and it is written atomically with the change it describes.

The trace below is the same swap in five steps, and it is worth reading in order once before you type it. The step that can fail runs before the step that destroys anything.

Steps three and four are the pair that makes a swap safe. A swap that released before it claimed would open the provider's calendar for the length of one transaction, and a lost race would then cost the client a session instead of an error message.

## Show the quote before the button

A cancel button that fires on the first tap is a trap. Show the quote first: the window, the percentage, the amount coming back and the amount the provider keeps, in one sentence a client can read on a phone. She confirms, and the confirmed request carries the quote she was shown so the server can detect that the amount moved between the two calls, which happens when the free window closes while she is reading.

```ts
// client/src/bookings/cancel-dialog.tsx
export interface CancelPreview {
  window: "free" | "late";
  refundMinor: number;
  retainedMinor: number;
  currency: string;
  deadlineLabel: string;
}
```

The reschedule picker has one rule of its own. It lists only starts the engine currently offers, and it keeps the session's own duration from the snapshot. A picker that lets a client choose an hour-long start for a 45-minute booking leaves the server a swap it has to refuse, and that refusal reads as a broken page to the person who chose it.

## Tests that fail first

```js
// server/src/modules/bookings/refund-quote.test.js
test.each([
  { hours: 48, paid: 4500, percent: 40, refund: 4500, window: "free" },
  { hours: 47.98, paid: 4500, percent: 40, refund: 1800, window: "late" },
  { hours: 2, paid: 4501, percent: 40, refund: 1800, window: "late" },
  { hours: 2, paid: 4500, percent: 0, refund: 0, window: "late" },
  { hours: 2, paid: 4500, percent: 100, refund: 4500, window: "late" },
  { hours: -1, paid: 4500, percent: 40, refund: 0, window: "after_start" },
])("a cancel $hours hours before the start returns $refund", async (row) => {
  const quote = quoteClientCancel(bookingAt(row.hours, row.paid, row.percent), clock.now());
  expect(quote.window).toBe(row.window);
  expect(quote.refundMinor).toBe(row.refund);
  expect(quote.refundMinor + quote.retainedMinor).toBe(row.paid);
});
```

test("a lost new start leaves the booking and its claims exactly as they were", async () => {

  const booking = await confirmedBooking({ startAt: "2026-01-13T13:00:00.000Z", durationMinutes: 45, bufferMinutes: 15 });

  const results = await Promise.all(moves.map((move) => move("2026-01-15T13:00:00.000Z")));
  expect(results.filter((r) => r.status === 200)).toHaveLength(1);
  expect(results.filter((r) => r.status === 409)).toHaveLength(19);

Add three more. A second cancellation of the same booking returns 409 and creates no second refund. A provider cancellation refunds the full amount paid even at ten minutes before the start. A cancellation and a reschedule sent together leave one success and one 409, never two state changes.

## Acceptance criteria

The module is done when the quote table passes with the boundary at exactly 48 hours, when a late cancellation records the floored percentage and leaves the other provider's Order untouched, when a provider cancellation returns the full amount paid, when a lost reschedule changes nothing except the response, and when a won reschedule moves all four claims and increments `reminderVersion` once.

Keep the raw responses for the lost swap and the parallel race in `docs/change-evidence.md`, with the claim counts before and after. The gate next asks for a partial refund visible in test mode and one winner in a race between a cancellation and a reschedule.
