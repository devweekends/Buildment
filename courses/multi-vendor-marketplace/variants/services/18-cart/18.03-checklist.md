# Slot cart gate

This gate is about a cart that makes a promise it can keep. You will build one cart from two providers, refuse a start that is already gone, watch a rival claim turn one line stale, and try to reach another client's cart with a valid token. Every check runs against the real API and the real database, because a cart is exactly the kind of screen where a passing button hides a missing rule.

Start from a known state. Reset the cart collection for your two test clients, keep the seeded providers, and record the server clock value before the first request. Write the clock value in `docs/cart-evidence.md`. Almost every failure in this lesson depends on when a line was read, so evidence without a timestamp cannot be repeated by the person reviewing your work.

## Build the two-provider cart on a phone

Open the client at 360 pixels wide with the network throttled to a slow profile and sign in as Amal. Pick a 45-minute English conversation lesson with Sara, whose profile is set to `Asia/Gaza`, and add a start. Then pick a 60-minute design review with Omar in `Asia/Doha` and add a second start.

The cart must show two groups, one per provider, each with its own subtotal and a total for the whole cart. Each line shows Amal's Berlin time and the provider's local time, both labelled with a zone, plus the duration and the amount. Nothing about a group should require a tap to reveal, because the reason for the grouping is that the two halves of this purchase have different cancellation policies.

Now check the same cart at that width for the four faults that a desktop screenshot hides. A long service title must wrap to two lines rather than truncate. The remove control must sit at the end of the line with a 44 pixel target and must not be reachable by a stray scroll. The policy sentence must be readable without horizontal scrolling. And when you open the keyboard in the note field, the total must still be reachable by scrolling, not fixed behind the keyboard.

## Refuse a sold start and prove nothing was written

Pick one start that is still offered for Sara's service. Before you touch the client, claim the blocks it needs with a second account through the checkout route, or insert the claims with your test helper if Module 19 is not finished. Then, as Amal, try to add that same start.

The add must answer 409 with the code `SLOT_NOT_OFFERED`, and no cart line may appear. Count the documents. The claim count for Sara's provider must be unchanged by the refused add, and Amal's cart line count must be zero for that start. This is the check that separates a cart from a hold: a refused add may not consume provider time as a side effect of being refused.

Then add the same offered start twice in a row, slowly, and confirm one line exists rather than two. The unique index on client, service and start is what makes that true, so show the index in the evidence with its name and its partial filter. A reviewer should be able to see that the filter covers proposed lines only, which is why a stale line does not block Amal from requesting the same start again later.

## Watch a line go stale without disappearing

Add an offered start for Omar's service as Amal, then claim the blocks for that start with Rami's account. Reload Amal's cart. The line must still be there, marked stale, with a reason code of `block_claimed` and the original start still visible. Her other line must still read as proposed and still be payable.

Now archive the service behind Amal's other line and reload again. The reason code changes to `service_archived`, and the line is still present. This second case matters because the fix is different: one needs a new time, the other needs a different service. A cart that answers "unavailable" for both teaches the client nothing.

Finally, let a stale line become valid again. Release Rami's claims through the release path from Module 20, or delete them in a test fixture if that path does not exist yet, then reload Amal's cart. The line returns to proposed with no reason code. Note in the evidence whether your implementation recalculates on read, and what would have happened if the reason had been stored as a final verdict.

## Prove the cart belongs to one client

Sign in as Rami with a real token and ask for the cart. It must be empty, and the response must not contain any identifier that belongs to Amal's lines. Then take one of Amal's line identifiers and send a remove request with Rami's token. Expect 404, and confirm afterwards that Amal's line is still there.

Repeat the same two requests with no token at all and expect 401 on both. The pair of checks is worth writing down separately, because a route that filters by client but forgets to authenticate answers 500 or, worse, answers 200 with an empty cart. The refusal has to name the reason: unauthenticated is 401, not yours is 404.

## Check the money and the policy copy

Read one line's amount, multiply nothing, and confirm the group subtotal equals the sum of its lines in integer minor units. Change Sara's price in the database, reload the cart, and confirm the line reports the new amount with `priceChanged` true while the original snapshot is still readable in the document. Change only the free cancellation window and confirm the line's policy text changes with it, because the snapshot is only useful if something compares it with the current service.

Decide what your interface says at that moment and write the sentence in the evidence. The acceptable answers are that the amount was updated and the client must confirm before checkout, or that the line is marked for reconfirmation. The unacceptable answer is a silent rewrite with no marker, which is how a client ends up paying a figure she never saw.

## What this gate does not prove

There is no hold and no payment in this module, so nothing here shows that a slot survives checkout or that money moves. The refused add is a read that said no, not a claim that said no, and a rival checkout can still take a start milliseconds after your cart read it. Those guarantees arrive in Modules 19 and 20, and the gate there tests them under parallel requests.

The gate also does not prove the cart page works on a device you have not tried. If you have only tested in a desktop browser resized to 360 pixels, say so, and test once on a real phone with a slow connection before you call the module finished.

## Gate checklist

- [ ] The cart shows one group per provider, each with a subtotal, and a total equal to the sum of the group subtotals in integer minor units.
- [ ] Every line shows the client's local start and the provider's local start, each labelled with a zone.
- [ ] At 360 pixels wide with the keyboard open there is no horizontal scroll, titles wrap, and the remove target is at least 44 pixels.
- [ ] Adding a start that is already claimed returns 409 `SLOT_NOT_OFFERED`, creates no cart line and creates no SlotClaim.
- [ ] Adding the same offered start twice leaves exactly one line, and the unique index name and partial filter are shown.
- [ ] A rival claim marks the affected line stale with `block_claimed` and leaves the document in place.
- [ ] An archived service marks its line stale with `service_archived`, and a released claim returns a line to proposed.
- [ ] A second client reads an empty cart and a remove request with the wrong token returns 404 with the first client's line untouched.
- [ ] Both cart routes return 401 without a token.
- [ ] A price change after the add shows the new amount with `priceChanged` true while the snapshot stays readable.
- [ ] One phone screenshot of the grouped cart, the raw 409 body, the index listing and the two before and after document counts are saved in `docs/cart-evidence.md`.

## Learning log

1. A cart line and a hold both mention a provider and a start instant. State the difference in one sentence and name the module that writes the second one.
2. Why does the unique index on cart lines include the client, when the checkout claim index does not include the client at all?
3. Amal's line went stale at 14:10 and was payable again at 14:25. What does that tell you about storing the stale flag instead of computing it?
4. Describe the request you used to prove that a refused add writes nothing, and the two counts you compared.
5. Two of Amal's own lines overlap and belong to different providers. Why does the cart warn instead of refusing, and what would refusing break?

Answer with route names, field names and the counts you observed. If your answer to question two describes the cart as locking a provider's time, reread lesson 18.1 before starting Module 19, because checkout will assume the cart never locked anything.
