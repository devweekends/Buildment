# Add slots, group by provider and price the cart

Module 17 left you with a provider page that can list offered starts in the client's own zone. This lesson turns a tap on one of those starts into a stored request, and turns the stored requests into a cart the client can read. Three files carry the work: a model that grows four snapshot fields, a route module with add, list and remove, and a grouping helper that the later checkout will reuse.

Build in this order: model, then read, then write, then revalidation. The read path is easier to shape when the response type exists, and the write path is easier to test when the read path can show you what it wrote. Leave the client page until the API answers the shape you want, because a page built against a guessed response is the reason front ends and back ends drift apart by Thursday.

```ts
// server/src/modules/cart/cart.types.ts
export interface CartLineView {
  lineId: string;
  serviceId: string;
  serviceTitle: string;
  startAt: string;
  endAt: string;
  occupiedEndAt: string;
  durationMinutes: number;
  bufferMinutes: number;
  priceMinor: number;
  priceChanged: boolean;
  status: "proposed" | "stale";
  staleReason: "service_archived" | "start_passed" | "notice_window" | "block_claimed" | null;
  overlapsLineId: string | null;
}

export interface CartGroupView {
  providerId: string;
  providerName: string;
  providerTimeZone: string;
  subtotalMinor: number;
  lines: CartLineView[];
}

export interface CartView {
  currency: string;
  groups: CartGroupView[];
  totalMinor: number;
  serverNow: string;
  staleLineCount: number;
}
```

The three instants on a line answer three different questions. `startAt` and `endAt` are the session the client is buying. `occupiedEndAt` includes the provider's buffer, so the overlap warning and the later claim set use the same boundary instead of two nearly equal ones. `serverNow` is the clock the response used, so the client can label a line as passed without trusting the phone's date.

Step four is the only step that leaves a document behind, and it leaves exactly one. If a refused add can still reach step four, the soft check is running after the write instead of before it, and the cart will slowly fill with requests nobody can pay for.

## Extend the cart line with what the client saw

The CartItem model from Module 6 already sets the shape: client, provider, service, a proposed start and a status of `proposed` or `stale`. Add the four fields that let a line render honestly without another lookup, and add the two indexes the routes need.

```js
// server/src/modules/cart/cart-item.model.js
cartItemSchema.add({
  priceMinorAtAdd: { type: Number, required: true, min: 0 },
  currency: { type: String, required: true, uppercase: true, trim: true },
  policySnapshot: {
    freeCancelHours: { type: Number, required: true },
    lateRefundPercent: { type: Number, required: true, min: 0, max: 100 },
    rescheduleCutoffHours: { type: Number, required: true },
  },
  staleReason: { type: String, default: null },
});

cartItemSchema.index({ clientId: 1, createdAt: -1 });
cartItemSchema.index(
  { clientId: 1, serviceId: 1, startAt: 1 },
  { unique: true, partialFilterExpression: { status: "proposed" } }
);
```

The unique index is scoped to one client, one service and one start, and it only covers proposed lines. That combination does two things at once. A double tap on a slow connection cannot create two identical lines, and two different clients can still both request the same tutor hour, because the client is part of the key. Never widen that key to provider and start alone. Doing so would convert a shopping action into the reservation this module exists to avoid.

Price stays in integer minor units. A price stored as `45.0` in a floating point field will eventually total to `44.99999` on a receipt, and a client reading a subtotal is entitled to the exact number she will be charged. Store the currency per line as well, and refuse a mixed currency cart at the route with a clear code rather than converting silently.

## Add a line only for an offered start

The add route takes a service and a start instant. It never takes a provider, a price or a client, because all three can be derived and a derived value cannot be tampered with. Load the service, confirm it is active, ask the availability engine whether that start is offered right now, and only then write the line with its snapshots.

```js
// server/src/modules/cart/cart.routes.js, outline
router.use(requireAuth);

router.post("/items", async (req, res) => {
  const clientId = req.user.id;
  const { serviceId, startAt } = parseAddLineBody(req.body);
  const service = await Service.findOne({ _id: serviceId, status: "active" }).lean();
  if (!service) throw new ApiError(404, "SERVICE_NOT_FOUND", "That service is not available.");

  const offered = await availability.isOffered({
    providerId: service.providerId,
    serviceId: service._id,
    startUtc: new Date(startAt),
    nowUtc: clock.now(),
  });
  if (!offered) {
    throw new ApiError(409, "SLOT_NOT_OFFERED", "That start is no longer offered. Pick another time.");
  }

  const line = await CartItem.findOneAndUpdate(
    { clientId, serviceId: service._id, startAt: new Date(startAt), status: "proposed" },
    {
      $setOnInsert: {
        providerId: service.providerId,
        priceMinorAtAdd: service.priceMinor,
        currency: service.currency,
        policySnapshot: pickPolicy(service),
      },
    },
    { upsert: true, new: true }
  );
  res.status(201).json(await toLineView(line, service));
});
```

Note what is missing: no SlotClaim insert, no transaction, no payment provider call. The upsert makes the second identical request harmless, and the absence of a claim keeps the block sellable to anyone else until a real checkout claims it. If your handler has a `$inc` on some counter, or a TTL, or a document that another client's availability read must now exclude, you have built a hold in the wrong module.

Return 409 with the code and one sentence. Do not return the rival client's identity, the winning Booking id or the exact block that was taken. The client needs to know that this start is gone and what to do next, and nothing more. The same rule applies to the message the interface renders: it says the start is no longer offered, not that someone else was faster.

## Group the response by provider and total it on the server

The read route loads the client's proposed and stale lines, resolves the services in one query, and returns groups. Grouping is a pure function so it can be unit tested without a database, and so Module 19 can import the same function instead of writing its own version during checkout.

```js
// server/src/modules/cart/group-by-provider.js
export function groupByProvider(lines) {
  const groups = new Map();
  for (const line of lines) {
    const key = String(line.providerId);
    const group = groups.get(key) ?? { providerId: key, lines: [], subtotalMinor: 0 };
    group.lines.push(line);
    group.subtotalMinor += line.priceMinor;
    groups.set(key, group);
  }
  return [...groups.values()].sort((a, b) => a.providerId.localeCompare(b.providerId));
}
```

Total every group from the same integers you return to the client, then assert the sum in the route before responding. A total computed from a different field than the visible lines is the bug that makes a payment form show one number and a receipt another. `priceMinor` on a view is the current service price when the two differ, with `priceChanged` set to true, so the line can say the price moved without pretending the old figure is still payable.

Sorting by provider id looks unfriendly and is deliberate. It gives the same cart the same order on every load, which makes a fixture comparison possible and stops a group from jumping position when a name changes. The interface can sort for display if a designer insists, but the API stays deterministic.

## Mark stale lines without deleting them

The list route revalidates every line before it responds. Load the claims that could intersect the latest occupied end across all lines with one range query, load the services with one `$in` query, then decide each line's state in memory. A cart of six lines must not run the availability engine six times.

```js
// server/src/modules/cart/revalidate.js
export function revalidateLines(lines, { services, claimedBlocks, nowUtc, noticeMinutes }) {
  const byService = new Map(services.map((service) => [String(service._id), service]));
  for (const line of lines) {
    const service = byService.get(String(line.serviceId));
    if (!service || service.status !== "active") line.staleReason = "service_archived";
    else if (line.startAt <= new Date(nowUtc.getTime() + noticeMinutes * 60000)) line.staleReason = "notice_window";
    else if (line.occupiedEndAt <= nowUtc) line.staleReason = "start_passed";
    else if (line.neededBlocks.some((block) => claimedBlocks.has(`${line.providerId}:${block}`))) {
      line.staleReason = "block_claimed";
    }
    line.status = line.staleReason ? "stale" : "proposed";
  }
  return lines;
}
```

A stale line stays in the document. It changes status, keeps its start visible, and gains a reason the interface can turn into one sentence. Deleting it instead would make the cart appear to lose a session at random, and the client would add the same start again to see whether the app is broken.

Staleness is computed on read and not stored as a permanent verdict, because a rival hold can expire and release its blocks. A line marked stale at 14:10 can be payable again at 14:25. That is why the reason is recalculated on every read and why nothing in this module writes to `staleReason` as if it were final.

## Warn about overlaps in the client's own day

Two of Amal's lines can overlap without breaking any provider rule, because the providers are different people. She cannot attend both, so the cart should say so and still allow the purchase. Warn, do not refuse: a client may be arranging sessions for two family members on one account.

```js
// server/src/modules/cart/mark-overlaps.js
export function markOverlaps(lines) {
  const ordered = [...lines].sort((a, b) => a.startAt - b.startAt);
  let furthest = null;
  for (const line of ordered) {
    if (furthest && line.startAt < furthest.occupiedEndAt) line.overlapsLineId = furthest.lineId;
    if (!furthest || line.occupiedEndAt > furthest.occupiedEndAt) furthest = line;
  }
  return lines;
}
```

The running `furthest` matters. Comparing each line only with its immediate predecessor misses the case where a long session swallows two short ones that do not overlap each other. Keep the comparison in absolute time, not in the client's local clock, so a Berlin client whose day contains a clock change still gets one correct answer.

## The cart page at 360 pixels

Render one column at 360 pixels wide. Each line shows the service title, the client's local start, the provider's local start in smaller text, the duration, the price and a remove control with a 44 pixel target. Put the warning for a line above that line, never in a banner at the top of the page, because a warning the client cannot connect to a line is noise.

```css
/* client/src/cart/cart.css */
.cart-lines { display: grid; gap: 0.75rem; padding: 0.75rem; max-width: 34rem; }
.cart-line { display: grid; gap: 0.25rem; padding: 0.75rem; border-radius: 0.5rem; }

```

Use tabular numbers for every amount, so two prices in a stack line up and the client can compare them without reading twice. Format both times with `Intl.DateTimeFormat` and the correct zone on each label, and include the zone abbreviation so `15:00` never appears alone. Check the result at 360 pixels with the keyboard open and with one stale line in the list, because that combination is the one that pushes a recovery control off screen.

## Tests that fail first

Write these before the routes work. Each one describes a promise from the last lesson, and each will fail in a specific way if you lose that promise.

```js
// server/src/modules/cart/cart.routes.test.js
test("a second client reads an empty cart and cannot remove the first client's line", async () => {
  const line = await addLine(amal, saraService, "2026-01-14T13:00:00.000Z");
  const read = await agent(rami).get("/api/v1/cart");
  const remove = await agent(rami).delete(`/api/v1/cart/items/${line.id}`);
  expect(read.body.groups).toHaveLength(0);
  expect(remove.status).toBe(404);
  expect(await CartItem.countDocuments({ _id: line.id })).toBe(1);
});

test("adding a start that is already claimed writes no line and no new claim", async () => {
  await claimBlocks(sara.providerId, "2026-01-14T13:00:00.000Z", 4);
  const res = await agent(amal)
    .post("/api/v1/cart/items")
    .send({ serviceId: String(saraService._id), startAt: "2026-01-14T13:00:00.000Z" });
  expect(res.status).toBe(409);
  expect(res.body.code).toBe("SLOT_NOT_OFFERED");
  expect(await CartItem.countDocuments({ clientId: amal.id })).toBe(0);
  expect(await SlotClaim.countDocuments({ providerId: sara.providerId })).toBe(4);
});

test("a rival claim marks the line stale and keeps the document", async () => {
  const line = await addLine(amal, saraService, "2026-01-14T13:00:00.000Z");
  await claimBlocks(sara.providerId, "2026-01-14T13:00:00.000Z", 4, ramiBooking);
  const res = await agent(amal).get("/api/v1/cart");
  expect(res.body.groups[0].lines[0].status).toBe("stale");
  expect(res.body.groups[0].lines[0].staleReason).toBe("block_claimed");
  expect(await CartItem.countDocuments({ _id: line.id })).toBe(1);
});

test("two providers give two groups and a total equal to their subtotals", async () => {
  await addLine(amal, saraService, "2026-01-14T13:00:00.000Z");
  await addLine(amal, omarService, "2026-01-15T17:00:00.000Z");
  const res = await agent(amal).get("/api/v1/cart");
  const sum = res.body.groups.reduce((total, group) => total + group.subtotalMinor, 0);
  expect(res.body.groups).toHaveLength(2);
  expect(res.body.totalMinor).toBe(sum);
});
```

Add three more yourself. The same start added twice leaves one document. A service archived after the add turns the line stale with `service_archived`. A service whose price rose shows `priceChanged` true and the new amount, with the snapshot still readable.

## Acceptance criteria

The module is done when a cart of two providers renders as two groups with a subtotal each, when the total equals the sum of those subtotals, when an unoffered start is refused with no claim written, when a rival claim marks one line stale without deleting it, and when the page is usable at 360 pixels with one stale line in the list. Keep the test names in `docs/cart-evidence.md` beside the response bodies you used.

The next lesson is the gate. It asks you to run the same checks with two accounts on a phone, and to show the collection counts before and after the refused add. Bring the clock value you used, because a stale line's reason depends on when it was read.
