# Concurrency and clock gate

This gate is a review of experiments, not of features. The features were reviewed in Modules 19, 20 and 22. What a reviewer checks here is whether your evidence would still be convincing if they did not trust you: whether the commands run, whether the output is raw, whether the counts match the claim, and whether the mechanism that produces exclusivity is visible rather than assumed.

Book thirty minutes with a mentor and share `docs/EVIDENCE.md` before the call. The call itself should be mostly them reading and you answering. If you spend the call narrating a browser, the evidence is not doing its job.

## What to show, in order

Start with the plan you wrote before any run: the provider, the service, its duration and buffer, the offered start, the expected counts. Then show the race tally from the live URL. One `201`, nineteen `409` with `SLOT_TAKEN`, zero other outcomes. Read the winner's checkout ID from the saved JSON file and use it for the record counts, so the reviewer can see that the numbers come from that run and not from a luckier earlier one.

Show the database counts next. One checkout attempt, one booking, one order for the winning cart, four claims at 15:00, 15:15, 15:30 and 15:45, and zero records owned by the nineteen losing clients. The 16:00 boundary should be free, which you can show by asking availability for the next start after the booking and seeing 16:00 offered.

Then show the index output and the broken-index run. This is the part reviewers remember, because it is the only part where something goes wrong on purpose. Expect questions about how you cleaned up the duplicate claims before rebuilding the index, and be ready to show that the rebuild used the same index name and the `unique: true` option.

Allow time for the clock evidence and the expiry test. The clock week is the one place where the product's time story becomes visible in one table, and the expiry race is the one place where money and calendar ownership meet. Both deserve five minutes each.

## Gate checklist

- [ ] `docs/EVIDENCE.md` records the plan before the results, with the provider, service, duration, buffer, offered start and expected counts.
- [ ] The race script is committed at `server/scripts/race-booking.mjs`, uses twenty distinct authenticated clients, one checkout identifier each, and one shared start barrier.
- [ ] The race starts from a start returned by the availability endpoint, and the run log prints that start.
- [ ] The live run shows exactly one `201` and nineteen `409` with code `SLOT_TAKEN`, and the script exits non-zero for any other tally.
- [ ] Post-run counts show one attempt, one booking, one provider order, four claims for the winner and zero purchase records for the losers.
- [ ] `db.slotclaims.getIndexes()` output shows `unique_provider_block` with `unique: true` on `{ providerId, blockStartAt }`.
- [ ] The broken-index run is committed, shows more than one success, and is followed by a rebuild and a clean rerun.
- [ ] A hand-run duplicate insert shows the `E11000` message naming `unique_provider_block` and the exact key.
- [ ] The clock report prints the 2026 transition dates for `Europe/Berlin` and `America/New_York` before any table is written.
- [ ] One week shows the provider label stable while the stored instant moves, and another week shows the client label moving on the client zone's own transition date.
- [ ] The expiry test fails against the naive release and passes against the state predicate, with both outputs committed.
- [ ] A confirmed booking keeps its four claims when the sweep runs after the deadline, and a repeated sweep changes nothing.
- [ ] The webhook replay changes no booking, claim, order or refund record.
- [ ] The committed evidence names the commit, Node version, Luxon version, database host and run times, and contains no keys, addresses, meeting links or client contact details.

## Learning log

1. Your race returns one success and nineteen conflicts. Name the four records a reviewer should count to accept that result, and the count each should have for a 45-minute service with a 15-minute buffer.
2. Explain what the broken-index run proves that the healthy run cannot prove. Then explain why the duplicate claims it created had to be removed before the index could be rebuilt.
3. In the March week, the provider's rule stays at 09:00 while the stored instant moves from `08:00Z` to `07:00Z`. Explain why the client in New York also changes label that morning, and why the earlier week changes the client label on a different date.
4. A payment success and an expiry sweep reach the same held booking at the same second. State which field decides the winner, what the loser does, and what the client and provider see afterwards.
5. Your race script returned twenty conflicts on the first attempt. Describe the three checks you ran, in order, and what each check would have told you.
6. A reviewer asks whether a stale Redis availability cache can cause a double booking in your build. Answer with the mechanism, not with a general statement about caches.

Write the answers in your own words, with field and index names from your implementation and at least one dated instant from the run. If an answer needs a diagram to be clear, draw the two requests on a timeline and label the read, the claim insert and the commit. Do not copy the checklist text back as an answer.

## When a check fails

A failing check here is usually a setup problem before it is a code problem. If the race shows two successes, confirm the index exists on the database the API actually uses, then confirm that `blockStartAt` is stored as a date in both claims. If it shows no winner, verify the offer and the notice window, then check whether the database is a replica set, because a standalone server cannot run the checkout transaction.

If the clock table shows a provider label that moves on the transition date, your engine is deriving later weeks from an earlier UTC instant. Find the helper that adds seven days and replace it with a per-day local resolution. If the client label never moves, the display path is formatting in the provider zone.

If the expiry test passes before the fix, the fixture is not exercising the race. Check that the booking is `held` with four claims and a `holdExpiresAt` in the past before the sweep runs, and that the confirmation path actually commits a state change. A fixture that seeds a booking with no claims passes every assertion about zero claims.

Fix the cause, rerun, and add the failing output to the evidence file above the passing output. The pair is more persuasive than a single clean result, and it is honest about how the fix was found.

## What this gate does not certify

This gate proves that the booking calendar stays exclusive under the tested load, that the clock logic survives two zones changing on different dates, and that an expiry sweep cannot erase a paid appointment. It does not prove behaviour at a hundred concurrent clients, because twenty is the number this course tests, and it does not prove latency or throughput. It does not prove the payment provider's own behaviour under retries beyond the replay you ran.

It also does not prove that the variant is ready for learners. Readiness needs the full roadmap path, a runnable reference build, and instructor review, and none of those are established by one module gate. Say what you tested, in the environment you tested it, and leave the rest open.
