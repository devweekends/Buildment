# 6.16 OTP verification

> **[Build]** · Chapter 06 · Authentication API · *`POST /auth/verify-otp`, block login until verified*

**Why this step matters:** `isVerified` separates real accounts from spam registrations, and a provider should not be able to publish a Service until the address is confirmed. Chapter 7's verify page is useless without this endpoint returning a clear success and a clear failure.

<BigWordAlert term="One-time password (OTP)" plainEnglish="A short code sent to an email address to confirm the person controls it before the account becomes active." whyItMatters="SkillSlot requires a code after registration, which reduces fake provider accounts and abandoned signups that never verify." />

**Where the project is now:** register generates the code and login refuses unverified accounts. The verify endpoint is missing or still a stub.

**After this step:** `POST /api/auth/verify-otp` checks the code against the stored value, sets `isVerified` to true, and clears the code fields. The account can log in afterwards.

## The problem this endpoint solves

Registration cannot prove that an address belongs to the person typing it. A form that accepts any string will happily create accounts for addresses that do not exist, and every one of them can occupy a Service listing, hold a slot, or trigger a booking email to a stranger. The one time code is the cheapest proof of ownership available without a third party identity provider, because it requires access to the mailbox rather than access to the form.

The endpoint is therefore not a formality after registration. It is the step that turns a request into an account, and its failure responses are part of the interface. A client who mistypes a code needs to know that the code was wrong rather than that the server broke, and a client whose code expired needs to know that a new one is required. Ambiguity here turns into a support conversation about an account that cannot be opened.

## The mechanism, step by step

Registration writes two fields on the User document: the code, or a hash of it, and an expiry timestamp. Verification reads the user by email, compares the submitted code against the stored value, checks the expiry against the current time, then sets `isVerified` and removes the code fields. The order of those checks matters, because each one answers a different question.

| Check | Question answered | Failure answer |
|---|---|---|
| User exists by email | Is there an account to verify | 404 |
| Already verified | Is this a repeat of a finished step | 200, idempotent |
| Code matches | Did the caller read the mailbox | 400 |
| Expiry is in future | Is the proof still fresh | 400 |
| Save and clear | Did the state actually change | 500 on write failure |

Three of those rows are 400 responses on purpose. The client is not authenticated yet, so 401 would be misleading, and the code is a value the caller supplied, so a bad value is a client error. The already verified case returns 200 rather than an error, because a duplicate submission from a page refresh should not look like a failure to a client who did nothing wrong.

## The account lifecycle as a diagram

<StateMachine title="States of one SkillSlot account before and after verification" chart={`stateDiagram-v2
  [*] --> pending: register writes a code and an expiry
  pending --> pending: wrong code, still counted
  pending --> pending: resend issues a fresh code
  pending --> verified: code matches and is fresh
  pending --> expired: expiry passes with no successful attempt
  expired --> pending: a new code is issued
  verified --> verified: a second submit is idempotent
  verified --> [*]
`} />

Read the diagram as a statement about what a provider can do in each state. In `pending` the account exists but cannot publish a Service, and login refuses it. Only the arrow into `verified` unlocks the marketplace, and it has two conditions joined by "and", which is why the service function checks the code and the expiry in that order. The `expired` state is not a dead end, because a new code returns the account to `pending` without creating a second account.

## The request contract

**POST** `/api/auth/verify-otp`

| Field | Required |
|---|---|
| email | yes |
| otp | yes, six digits |

Validate both fields before the service layer runs. An `email` that is missing returns a 400 with a field error, and an `otp` that is not six digits returns the same. This is cheaper than a database read and stops malformed input from reaching a comparison.

## Success and failure responses

```json
{
  "message": "Email verified successfully",
  "verified": true
}
```

| Status | Condition |
|---|---|
| 400 | missing fields or invalid format |
| 400 | wrong code |
| 400 | expired code |
| 404 | no account for that email |

Returning tokens on verification would auto log the account in. That is a design decision, not a requirement, and if you implement it, document it in the learning log so the client behaviour in Chapter 7 matches.

## The service function

Write the steps before the code, because the order is the specification.

1. Find the user by email.
2. If no user, return a 404 result.
3. If already verified, return success without touching the record.
4. Compare the submitted code with the stored value, or with the hash when hashed.
5. Check that the expiry is later than the current time.
6. Set `isVerified` to true and clear the code fields.
7. Save the user and return success.

Two details in that list are easy to get wrong. Checking the expiry before the code comparison leaks less information in logs but costs the same, while checking the code first matches the order a user thinks in. Either order is defensible, and the important part is doing both before the write. And clearing the code fields after success is what makes the code single use, which is the property that stops a captured address bar value from working twice.

## OTP generation rules from registration

The register handler sets the rules, and this endpoint enforces them. The code is six numeric digits, the expiry is ten minutes by default, and the development environment logs the code to the console instead of sending mail. Keep those numbers in one place, so a later change to the expiry cannot drift between the two handlers.

## A worked example with two attempts

A provider registers at 10:00 and receives a code that expires at 10:10. They mistype the code at 10:02 and receive a 400 with a message about the code. They enter the correct code at 10:03 and receive a 200, and the record now shows `isVerified` true with both code fields removed. A second submit of the same code at 10:04 receives a 200 from the already verified branch, which is correct: the code is not reused, the state is simply already correct.

Now change one detail. Suppose the provider waits until 10:12 and submits the correct code. The response is a 400 with a message that the code expired, and the account is still `pending`. The fix is a resend, which issues a fresh code and a fresh expiry. This is the failure path that most implementations forget, and it is the one a real user hits after leaving a tab open over lunch.

## Failure modes worth recognising

A 404 for an address that just registered usually means the email was normalised differently in the two handlers, so store and query the lowercase form in both places. A 400 for a code the user copied correctly usually means the code has a leading zero that was sent as a number, so keep the code as a string end to end. A 200 that does not change `isVerified` usually means the save was skipped on the already verified branch before the write. A 500 in a deployment with several API instances usually means the code was stored in memory rather than in the database.

Debug from the document, not the client. Open the user record during a failing attempt and read the code field, the expiry and the flag. If the code field is empty, registration never wrote it. If the expiry is in the past, the attempt is late and the client needs a resend. If the flag is true, the endpoint already succeeded once and the client is retrying.

## Rate limiting and the brute force ceiling

A six digit code is a million possibilities, and an endpoint that accepts unlimited attempts turns that into a short script. Limit attempts per account and per address, and count failures on the account rather than only on the IP, because a botnet distributes addresses. A simple counter on the user document with a reset on a successful verify is enough for this stage, and saying so in the learning log shows you saw the problem rather than inheriting it.

The same reasoning applies to resend. A resend endpoint with no limit is an email amplifier, and it is the part an attacker will find first.

Then run the same three calls again and watch the middle one fail with an expired code after you change the expiry field by hand. An endpoint that has only been tested on the happy path is an endpoint that will be debugged in Chapter 7.

## Seed accounts and the ERD

The seed script sets `isVerified` true so that the demo provider accounts can log in without a mailbox. New registrations go through the endpoint. If you added the code fields to the User schema, update `docs/erd.md` in the same commit, because the data model is evidence for the build review.

```bash
git add server/src/modules/auth/ server/src/modules/users/
git commit -m "feat(auth): implement OTP verification endpoint"
```

## Do and do not

**Do:** expire the code, so a week old value is refused. **Do:** clear the code after success, so it cannot be replayed. **Don't:** skip verification to move faster, because the client page in Chapter 7 then has nothing to call. **Don't:** block on real mail delivery in development, since a console log is enough to test the flow.

## Verify checklist

- [ ] Register, verify, then login succeeds.
- [ ] Login before verify is refused.
- [ ] A wrong code returns 400.
- [ ] An expired code returns 400.
- [ ] `isVerified` is true in the database after a successful verify.
- [ ] A second submit of the same code returns 200 and changes nothing.
