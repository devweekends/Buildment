# 6.20 ,  Checklist and learning log
> **[Gate]** · Chapter 06 ,  Authentication API

This is the **gate** for Chapter 6. Tick every box honestly and answer the learning log below before opening Chapter 7.

<BigWordAlert term="JSON Web Token (JWT)" plainEnglish="A compact signed string encoding user id and expiry ,  sent in the Authorization header on API calls." whyItMatters="SkillSlot access tokens prove identity for cart and provider routes without server-side session lookup." />

## How to read this gate

Chapter 6 built an API with no screens, so the only way to check it is to call it. Each box below names something you can prove with a file, a command, or a response body, and the honest check is to run the proof rather than remember writing the code. A gate passed from memory is a gate that has to be repeated when Chapter 7's login form starts returning 401 for a reason nobody can name.

Every box answers three questions in order. What is the claim, what proves it, and how would a reviewer confirm it without you. For the endpoints that proof is a curl command and its status line. For the security boxes it is an inspected response body or a database document, because a missing field is a claim about absence and absence has to be seen. Write the command next to the box when you tick it; that habit is the difference between evidence and assertion.

The groups run from configuration to endpoints to security to behaviour and finally to the earlier chapters. That order is the order failures appear: a missing secret makes every endpoint fail, a missing route makes one endpoint 404, and a wrong response field survives all the way to Chapter 7 where the client suddenly shows a password hash in a profile page.

## Chapter 6 ,  Authentication API checklist (gate)

Do **not** open Chapter 7 until every box is ticked and learning log answers are written below.

### Environment & config

This group exists because authentication is the first part of the course that depends on secrets, and a secret is the one thing a reviewer cannot see in the repository. Three of the four boxes are about where the values live, and the fourth is about the library install that makes them usable. A reviewer reads `.env.example` and confirms the names are there with empty values, then reads `.gitignore` and the history to confirm the real values are not.

The startup check is the box learners question most. A server that refuses to boot without `JWT_SECRET` is not fragile; it is honest, because the alternative is signing tokens with `undefined`, which yields tokens that verify against nothing and fail in a way that looks like a client bug. A reviewer proves it by removing the variable from a local `.env` and watching the process exit with a message naming the variable.

- [ ] `JWT_SECRET`, `JWT_ACCESS_EXPIRY`, `JWT_REFRESH_EXPIRY` in `.env.example`
- [ ] `JWT_SECRET` in local `.env` ,  not committed
- [ ] config.js fails startup if JWT_SECRET missing
- [ ] bcrypt and jsonwebtoken in package.json

### Endpoints

Five boxes, five routes, and each one names the success case and at least one failure case. That shape is the point: an endpoint that only works is half tested, and the failure code is what later chapters rely on. A reviewer reads this group with a terminal open, runs each request, and compares the printed status with the number beside the box, because 201 and 200 look identical in a browser tab and mean different things in an API contract.

Register and verify come as a pair, since a registration that leaves the account unusable is a registration that failed. Login carries three distinct outcomes and the 403 for an unverified account is the one that proves the verification step has teeth. Refresh is the box that proves the token pair is a pair, and `/me` is the proof that `requireAuth` reads the token rather than trusting a header the caller typed.

- [ ] POST `/api/auth/register` ,  201, bcrypt hash, OTP, 409 duplicate
- [ ] POST `/api/auth/verify-otp` ,  sets isVerified, wrong OTP 400
- [ ] POST `/api/auth/login` ,  200 tokens, 401 bad password, 403 unverified
- [ ] POST `/api/auth/refresh` ,  new access, invalid refresh 401
- [ ] GET `/api/auth/me` ,  requireAuth, 200 user+profile, 401 without token

### Security

These five boxes are the ones an assessment actually cares about, because they describe what an attacker can and cannot do rather than what a happy path returns. Each box rules out a specific mistake: returning `passwordHash`, storing a refresh token in readable form, letting the token claim a role the database disagrees with, accepting a third role at registration, and leaving OTP delivery undocumented so nobody can log in on a fresh clone.

A reviewer reads this group by inspecting three things and comparing them: one response body from login, one User document, and one decoded access token. If the role in the token matches the role in the document, and neither the body nor the document exposes a hash, the group is done. The OTP box is read as documentation, because a delivery channel nobody wrote down is a step Chapter 7 will be unable to reproduce.

- [ ] No passwordHash in any API response
- [ ] refreshTokenHash stored hashed on User ,  not plain refresh
- [ ] role in access JWT matches User.role
- [ ] Only vendor/customer roles accepted on register
- [ ] OTP dev delivery documented (console or dev response)

### Testing

Testing here means the three things that are easy to fake and hard to prove: a recorded flow, the negative cases, and at least one real account that can log in. A documented curl flow is evidence a reviewer can follow in order, and it is worth more than a screenshot of a single green response because it can be replayed against a fresh database.

The seed box connects this chapter to Chapter 5. A seeded provider or client whose password was written in plain text by the seed script will fail at login, and that failure is a seed defect rather than an auth defect. A reviewer runs the seed, logs in as the seeded account, and if it fails, checks whether the stored value is a hash before reading any auth code.

- [ ] Full curl flow documented (6.18)
- [ ] Negative tests pass (401, 403, 409)
- [ ] Seed vendor-a login works after bcrypt alignment

### Prior gates

The last group guards the two earlier chapters and asks you to explain five decisions aloud. The first three boxes are regression checks: a model deleted while debugging auth, or a health route broken by a middleware change, is the most common way a green chapter hides a red one. A reviewer runs the Chapter 5 seed again and calls `/health` before reading anything new.

The five explanation boxes are the viva material. Answering them out loud in a minute each is a different skill from writing working code, and it is the skill the defense measures, because a learner who can describe why a refresh token is hashed separately can debug a real session problem and a learner who cannot will guess.

- [ ] Models and seed from Ch 5 intact
- [ ] Health route still works
- [ ] No React auth UI yet ,  API only
- [ ] Explain bcrypt vs plain storage
- [ ] Explain access vs refresh token roles
- [ ] Explain 401 vs 403 in this chapter
- [ ] Explain why JWT payload must stay minimal
- [ ] Explain refresh rotation benefit

### Learning log ,  write now

Answer **in your own words** in the fields below:

A strong answer names the command you ran or the document you inspected. "Refresh works" is not an answer. "Refresh returned a new access token, and the old refresh token then returned 401 on the second attempt" is one, because it shows what changed and what the server refuses afterwards.

1. **Register flow:** Step through register from curl to Compass documents created.

2. **Password security:** How does bcrypt protect you if MongoDB is leaked? What is still at risk?

3. **JWT payload:** Paste decoded payload structure (redact sub if desired) ,  what claims and why?

4. **Refresh design:** How is refresh stored server-side? What happens on logout or rotation?

5. **OTP:** How is OTP delivered in dev? How would you change for production email?

6. **Failure test:** Describe one negative curl test and the status code returned.

7. **Chapter 7 preview:** Where will access token live in the browser and why not localStorage?

8. **requireAuth:** What does req.user contain and who consumes it in later chapters?

## All boxes ticked?

Mark this chapter complete in the platform, then continue to **Login and registration** (Chapter 7).

Fix a failed box before you write the learning log, not after. The log is read as your account of what the API does, and an answer written beside a known broken endpoint is a description of something that does not exist. If you are stuck on a single failure for more than twenty minutes, write what you tried in the log and continue, because a documented dead end is useful evidence and an undocumented one is lost time.

## Troubleshooting

| Blocker | Look at |
|---|---|
| 401 on valid token | JWT_SECRET mismatch, clock skew |
| 403 on seed login | isVerified false ,  re-seed or verify |
| 404 on auth | 6.11 mount path |
| bcrypt compare false | seed plain password ,  re-hash |

Read the table by matching your symptom, not your guess. A 401 on a token you believe is valid is almost never a signing bug; it is a different secret loaded by a restarted process, or a token that expired because the clock on the machine is behind. A 404 is never an auth problem at all, which is why the mount path row exists: check where the router is attached before you read a single line of handler code.
