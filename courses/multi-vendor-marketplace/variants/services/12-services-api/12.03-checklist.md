# Services API gate

This gate is a written record of five observations and one accepted gap. The observations are a rejected off-grid duration, a rejected fractional price, a refused cross-provider update, an archived service that disappears from the public route while its booking survives, and a purchase snapshot that does not move when the live service changes. The gap is the checkout revalidation of an archived service, which Module 19 owns and this module only plans.

Record the evidence in `docs/EVIDENCE.md` under a Module 12 heading, with the request line, the status, the error code and the redacted body for each case. Record the decisions in `docs/LEARNING-LOG.md`. A reviewer should be able to repeat the five cases from your notes with the identifiers you used, and should be able to see which one is still open.

## Show the block rule

Create three services for one provider: a sixty minute session with a fifteen minute buffer, a forty five minute session with a thirty minute buffer, and a ninety minute session with no buffer. Write the occupied interval and the claim count for each in the evidence file. Five blocks, five blocks and six blocks. The middle case is the one that catches a hard coded assumption: a forty five minute session and a sixty minute session both occupy seventy five minutes, so code that assumes five blocks per booking looks correct for the first two and fails on the third.

Then send a duration of 20 and a buffer of 25 through the same route. Both must return `422` with a field named in the body, and neither may create a row. Read the stored rows afterwards and confirm the rejected values are absent rather than rounded. This is the check that distinguishes validation from normalisation, and it takes one query.

## Show the price rule

Create a service with `priceMinor` set to 4500. Read the row and confirm the stored value is an integer. Then send `45.1` and send `"4500"`. The float must be rejected, and the string must either be rejected or converted deliberately, not by JavaScript coercion that turns an unexpected value into zero.

Open the public route for that service and confirm the response carries the amount and the currency, and that the interface formats them for display without sending the formatted label back to the server. A single test on the parser is enough evidence: `4500` renders as `45.00 USD`, and `45.00` typed into a form becomes `4500` before the request leaves the browser.

## Show the refusal

Authenticate as a second provider and send `PATCH` with the first provider's service identifier and a changed price. Expect `403 SERVICE_NOT_OWNED`, and then read the service row: the price, the duration, the policy and the updated timestamp must all be unchanged. Read the denial body too, and confirm it contains no title, price or identifier from the target service.

Repeat the call with an identifier that does not exist at all and confirm the response is a not-found rather than the ownership refusal. The two responses are different on purpose, and a route that returns the same status for both has lost the distinction between a public record the caller may not change and an identifier that resolves to nothing.

## Show the archive

Create a confirmed booking fixture against the first service, with its purchase copy filled from the service as it exists today. Archive the service. The owner list must still return it, with the archived status. The public route must return `404`. Reload the booking and compare the whole purchase subdocument with the copy you recorded before the archive: price, duration, buffer, currency, location type, policy and zone must match field for field.

Then change the live service before archiving, in a second case. Set a new price and a new late refund percentage, save, and reload the booking again. The booking must still show the values it was created with. That pair of cases proves the two halves of the same rule: an archive preserves records and a price change does not rewrite history.

Note the open test in the evidence file with the code it expects. A stale cart line or a client page open across the archive must be refused by checkout with `409 SERVICE_ARCHIVED`. The test is written and skipped, and Module 19 makes it pass. Do not mark it done because the public route returns `404`, which is a different enforcement point.

## Gate checklist

- [ ] Service create, list, update, archive and restore routes resolve the provider from the session.
- [ ] No route accepts a provider identifier from the request body as ownership.
- [ ] `durationMinutes` and `bufferMinutes` reject values that are not multiples of fifteen, with a named field.
- [ ] `priceMinor` rejects fractional and unsafe values, and currency is validated against the supported set.
- [ ] Cancellation policy fields are validated as integers in range and stored on the service.
- [ ] The owner list returns active and archived rows; the public route returns active rows only.
- [ ] A cross-provider update returns `403 SERVICE_NOT_OWNED` and leaves the target row unchanged.
- [ ] The denial body contains no field from the target service.
- [ ] Archiving sets the status, keeps the document and leaves bookings, claims and snapshots untouched.
- [ ] An archived service returns `404` on the public route.
- [ ] A purchase snapshot is identical before and after a price, buffer and policy edit.
- [ ] The planned checkout refusal of an archived service is recorded as an open test with its module number.
- [ ] `docs/EVIDENCE.md` and `docs/LEARNING-LOG.md` record the five cases and the open gap.

## Learning log

1. Why is a twenty minute service rejected instead of rounded, and what would rounding change for the client and for the provider?
2. A forty five minute session with a thirty minute buffer occupies which interval, and how many claims does it need?
3. A provider raises her price after a client has paid. Which record keeps the old amount, and which record supplies the next client's price?
4. Provider B holds the provider role and sends provider A's service identifier. Which predicate in the update query prevents the write, and what does the failure branch read to choose between `403` and not-found?
5. An archived service still has a confirmed booking next Tuesday. What must the archive leave alone, and what must it stop?

Answer with field names, the block count and the interval. For the first question, name the two possible roundings and who loses under each. For the third, name the booking subdocument. For the fifth, separate the offer from the commitment in your answer.

Then write the gap you are carrying forward, in one sentence each. The first is the checkout revalidation of service status, which belongs to the claim path. The second is the availability engine's use of duration plus buffer, which belongs to Module 15. Naming both keeps this gate honest: the service record is complete and correct, and two later modules still have to consume it properly.

## Bridge to the dashboard

The API can now hold a provider's price list, and no page uses it yet. The next module builds the provider dashboard and the weekly hours grid, which turn a service list into a working practice. That module archives services from the interface, warns before a duration change that affects future bookings, and adds the weekly rules the availability engine needs.

Before you move on, read the three services you created and confirm every active row has a duration, a buffer, a price, a location type and all three policy numbers. A missing policy field discovered during a refund conversation is the most expensive kind of missing field in this product, and the row you created today is the one a demo will use next week.
