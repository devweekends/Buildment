# Service fields, duration, buffer and cancellation policy

A provider opens her services page in two tabs. In the first she lowers her price for a slow month. In the second, from yesterday, she edits the same service and saves a form that still carries the old price and a new cancellation window. The second save wins and the price change disappears. A week later a client asks why a lesson costs more than the listing said. Nothing in the database records that two writes existed, so the provider and the support desk have to guess.

This lesson builds the routes that make service writes explicit: one create, one list, one update, one archive, all scoped to the authenticated provider, all validated on the server, and all leaving already purchased bookings untouched. It also sets the rule that an archived service cannot be booked, which needs enforcement in more than one place because a client's page can be minutes old.

## The route set

Five routes cover the provider's work on a service, plus one public read for the client-facing page.

| Method and path | Caller | Success | Notes |
|---|---|---|---|
| `POST /api/provider/services` | Service owner | `201` owner service | Creates under the caller's provider |
| `GET /api/provider/services` | Service owner | `200` list | Includes archived rows, with a status filter |
| `PATCH /api/provider/services/:serviceId` | Service owner | `200` owner service | Allowlisted fields, revision checked |
| `POST /api/provider/services/:serviceId/archive` | Service owner | `200` owner service | Sets the archived state |
| `POST /api/provider/services/:serviceId/restore` | Service owner | `200` owner service | Returns the row to active |
| `GET /api/services/:serviceId` | Anyone | `200` public service | Active services only |

No route accepts a provider identifier in the body. The provider is resolved from the session through the helper built in Module 9, and the service query carries both the service identifier and that provider identifier. Two separate facts are being checked: the caller owns a practice, and the service belongs to that practice. A route that checks only the first lets any provider edit any service.

## Ownership and the 403

The public service page is public, so a service identifier is not a secret. A provider who reads another provider's page knows a real identifier, and the update route must refuse her attempt to use it. The documented response for that case is `403 SERVICE_NOT_OWNED`, with no service fields in the body. That differs from the `404` used on booking routes, where the identifier must not confirm that a private record exists. A public catalogue makes existence a public fact, so a `403` reveals nothing a search page did not already show.

```js
router.patch('/api/provider/services/:serviceId',
  requireAuth, requireRole('provider'),
  async (req, res) => {
    const provider = await assertProviderOwnerFromSession(req.principal);
    const patch = parseServicePatch(req.body);
    const updated = await Service.findOneAndUpdate(
      { _id: req.params.serviceId, providerId: provider._id },
      { $set: patch },
      { new: true, runValidators: true, projection: OWNER_SERVICE_PROJECTION },
    ).lean();
    if (!updated) {
      const exists = await Service.exists({ _id: req.params.serviceId });
      if (exists) throw forbidden('SERVICE_NOT_OWNED');
      throw notFound('SERVICE_NOT_FOUND');
    }
    res.json(toOwnerService(updated));
  });
```

The second query in the failure branch is what separates a foreign service from a missing one. It runs only after the scoped update already failed, and it returns one boolean rather than a document, so the denial body cannot leak a title or a price. Put that shape in the route once, and every later service route copies it.

## Validation before the database

The validator rejects six kinds of input and names a field for each. A route that relies on Mongoose alone returns a message written for a developer, and the provider's form cannot attach it to an input.

- `durationMinutes` must be an integer from 15 to 240 and a multiple of 15. Anything else returns `422 INVALID_DURATION`.
- `bufferMinutes` must be an integer from 0 to 120 and a multiple of 15, or `422 INVALID_BUFFER`.
- `priceMinor` must be a non negative safe integer, or `422 INVALID_PRICE`. Reject `45.1` rather than rounding it.
- `currency` must be a supported code, or `422 INVALID_CURRENCY`.
- `freeCancelHours`, `lateRefundPercent` and `rescheduleCutoffHours` must be integers in range, or `422 INVALID_POLICY`.
- `locationType` must be one of the three course values, or `422 INVALID_LOCATION_TYPE`.

```ts
export interface ServiceInput {
  title: string;
  description: string;
  durationMinutes: number;
  bufferMinutes: number;
  priceMinor: number;
  currency: 'USD';
  locationType: 'online' | 'at-home' | 'at-workshop';
  cancellationPolicy: {
    freeCancelHours: number;
    lateRefundPercent: number;
    rescheduleCutoffHours: number;
  };
}

export interface OwnerService extends ServiceInput {
  id: string;
  status: 'active' | 'archived';
  revision: number;
  updatedAt: string;
}
```

The public read returns the same commercial fields with the status removed and a boolean that says whether the service can currently be booked. It does not return the revision, the provider's account link or any booking count. A client needs the duration, the price, the location type and the policy in order to decide; the rest is the owner's business.

A validator that lives only in the client form is the near miss this lesson is written against. The form prevents a learner from typing 20 into the duration field, every manual test passes, and a month later a script or a repair sets the value directly in the database. The availability engine then tries to place a 20 minute session on a 15 minute grid and either fails at claim time or, worse, rounds. Keep one validator module, call it from the route, and call the same functions from the model hooks so a second write path cannot skip the rule.

Field names in the error response are part of that validator's contract. Return `durationMinutes`, not `duration`, and `cancellationPolicy.lateRefundPercent`, not `latePercent`. The provider's form attaches each message to an input by that path, and a rename in the API becomes a silent generic toast in the interface. A contract test over the serialized error shape costs a few lines and prevents that drift.

## Archive instead of delete

Archive is a state change, not a removal. The route sets `status` to `archived` and returns the owner view. The document stays, so the bookings that reference it stay explainable, and a restore can return it to the catalogue without recreating anything.

Archiving must not cancel or move a booking. A provider who archives a service still has sessions to deliver under the terms clients accepted. The route therefore refuses to take a shortcut: it does not release claims, does not change booking status and does not touch a purchase snapshot. If a provider wants to cancel an appointment, that is the cancellation workflow with its own policy and its own refund.

Two enforcement points make "archived services cannot be booked" true. The public read stops returning archived services, so a client cannot start a new purchase from a stale search result after a reload. The checkout path revalidates the service status when it claims time, so a page left open for twenty minutes cannot complete a purchase for a service that was archived in the meantime. This module builds the first point and writes the failing test for the second, which Module 19 turns green.

A cart line that already holds an archived service is the case between those two points. The line was created while the service was active, so it is not a defect in the client. Treat it as a stale line: the cart shows it with a clear message, and checkout refuses it with `409 SERVICE_ARCHIVED` rather than silently removing the line or charging for a service that no longer exists. The client then removes it or picks another service, and the rest of the cart still works.

```js
test('archived_service_is_not_bookable', async () => {
  await archiveService(serviceId, providerToken);
  const publicRead = await request(app).get(`/api/services/${serviceId}`);
  assert.equal(publicRead.status, 404);

  const checkout = await startCheckout(clientToken, { serviceId, startAt });
  assert.equal(checkout.status, 409);
  assert.equal(checkout.body.code, 'SERVICE_ARCHIVED');
});
```

The second half of that test will fail until the checkout route exists. Keep it in the suite as a skipped case with the module number in its name, rather than deleting it and trusting memory. A planned test that is visible in the file is better evidence than a sentence in a document.

## Rewrites, revisions and conflicts

A service update carries a revision, and the route compares it before writing. Two tabs editing the same service then give one success and one `409 SERVICE_VERSION_CHANGED`, instead of a silent overwrite. Reuse the `scheduleRevision` idea from the provider profile if you prefer one counter per provider, but keep the semantics clear: the revision protects a record, and a provider wide counter means an edit to one service makes a concurrent edit to another service retry as well.

A price change passes through the same update as any other field, which means it needs no special endpoint. What it must not do is reach a purchased booking. The booking keeps its own copy of the title, duration, buffer, price, currency, location type and policy, written at purchase. A test that edits the live service and reloads an old booking proves the separation, and it is one of the three tests the gate asks for.

Work one example through the whole record before writing the tests, because the numbers catch mistakes that prose does not. A forty five minute design review with a thirty minute buffer and a price of 4500 minor units occupies seventy five minutes, so a booking needs five blocks. A client who cancels three hours before the start, against a free window of twenty four hours and a late percentage of 50, receives 2250 minor units. Every one of those numbers comes from the service row at purchase time and from integer arithmetic, and none of them comes from the formatted label "45.00" that the interface displayed.

The list route deserves one more decision before the code. The owner list returns active and archived rows together, because a provider needs to find a service she stopped selling in order to restore it. Sort active rows first, then archived rows by their archive date, and let the client filter by status. A public list, which arrives with the catalogue module, returns active rows only and never includes the owner fields. Two lists over one collection, two predicates, and no shared default that quietly serves the wrong one.

## Tests to write first

- `create_service_rejects_off_grid_duration` sends 20 and expects `422 INVALID_DURATION`.
- `create_service_rejects_fractional_price` sends `45.1` and expects `422 INVALID_PRICE`.
- `owner_list_includes_archived_services` archives one and asserts both rows return with their statuses.
- `update_other_provider_service_returns_403` calls `PATCH` as a second provider and expects `403 SERVICE_NOT_OWNED` with no title in the body.
- `update_leaves_booking_snapshot_unchanged` edits price and buffer, then compares the stored purchase copy.
- `archived_service_returns_404_publicly` archives and reads the public route.
- `archived_service_cannot_be_booked` starts from a stale client page and expects `409 SERVICE_ARCHIVED`.

Write the third and the fourth first. The list test forces the route to return archived rows, which a naive `status: 'active'` filter would drop, and the refusal test is the one that catches a missing provider predicate in the update.

## Acceptance criteria

The module is done when a provider can create a service with a whole block duration, a buffer, a minor unit price, a location type and a policy, see it in her own list, edit it without changing any purchased booking, and archive it while keeping its history. A second provider attempting the same update receives `403` and changes nothing. A client reading the public route cannot obtain an archived service, and the planned checkout test records the remaining enforcement point.
