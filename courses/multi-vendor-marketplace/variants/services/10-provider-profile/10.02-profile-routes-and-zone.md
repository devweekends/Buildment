# Profile fields, time zone and ownership

The scaffolded profile page looks right on the first account. Then a second provider signs in, sends a crafted request with the first provider's identifier in the path, and renames a practice she does not own. Nothing in the browser offered that button. A direct HTTP client does not need one. This lesson builds the routes that make the ownership rule true at the server, and the two projections that decide what each caller may read.

The provider model already exists from Module 6. It holds `userId` with a unique index, `timeZone`, `locationType`, `noticeMinutes`, `horizonDays` and `status`. This lesson extends it with the fields a client reads and settles the naming. Rename `practiceName` to `displayName` and add `headline`, `bio` and `avatarUrl`. Keep `category` and `serviceArea` in place. If seed data already uses `practiceName`, migrate it in one script and update the seed, rather than keeping two names alive in different routes.

## The field set and its validators

Each field gets one rule at the model and one rule at the route. The model rule protects stored data from any write path. The route rule returns a message a form can display. A field that is validated only in the route will eventually be written by a script, a seed or a repair, and a field validated only in the model returns a Mongoose message that leaks implementation detail to a client.

| Field | Validation | Error code |
|---|---|---|
| `displayName` | Trimmed, 2 to 80 characters | `INVALID_DISPLAY_NAME` |
| `headline` | Trimmed, 3 to 90 characters | `INVALID_HEADLINE` |
| `bio` | Trimmed, up to 1200 characters, may be empty | `INVALID_BIO` |
| `timeZone` | `requireZone` accepts a named IANA zone only | `INVALID_TIME_ZONE` |
| `locationType` | One of `online`, `at-home`, `at-workshop` | `INVALID_LOCATION_TYPE` |
| `avatarUrl` | HTTPS URL, or null | `INVALID_AVATAR_URL` |

The zone validator is the one built in Module 5. Reuse `requireZone` instead of writing a second regex or an allowlist of three zones. A learner who lives in Gaza and teaches students in Berlin needs `Asia/Gaza` on the rule, and a visitor reading the page needs their own zone for the label. Both sides depend on the same named zone data, so both must pass the same check.

The route must also reject unknown fields rather than dropping them silently. A client that sends `status: "listed"` or `scheduleRevision: 0` is trying to write fields the profile form does not own. Dropping them quietly teaches the client author that the request worked, and the next version of the client keeps sending them. Return `400 UNKNOWN_FIELD` with the offending key, and list the writable keys in the error documentation.

## Four routes and one rule each

The module exposes four routes. Each has a single job and a single ownership rule.

| Method and path | Who may call | Success | Main failures |
|---|---|---|---|
| `POST /api/providers` | Authenticated user with the provider role | `201` owner view | `409 PROVIDER_EXISTS`, `422` validation |
| `GET /api/providers/me` | Authenticated provider | `200` owner view | `404 NO_PROVIDER_PROFILE` |
| `PATCH /api/providers/:providerId` | Owner of that provider | `200` owner view | `403 PROVIDER_NOT_OWNED`, `422` validation |
| `GET /api/providers/:providerId` | Anyone | `200` public view | `404 PROVIDER_NOT_PUBLIC` |

The public read returns the six display fields and nothing else, and it returns them only when the provider has published. A draft profile is not a public page with hidden fields; it is absent. A client who bookmarked a profile URL before the provider paused should see the same not-found response as a client who mistyped an identifier, because the marketplace has nothing to show in both cases.

The create route takes the account from the session. It does not accept a `userId` in the body, and it does not accept a provider identifier it did not generate. The unique index on `userId` turns a double submit into a conflict, and the route maps the duplicate key error to `409 PROVIDER_EXISTS` with the existing profile identifier so a second browser tab can load what the first tab created.

Two stored fields stay out of this projection on purpose. `category` is the filter value the catalogue listing returns in Module 16, and `serviceArea` describes an in-person practice for a search that does not exist yet. Neither is needed to introduce a person on a profile page, and keeping the response to six display fields makes the key assertion in the test exact. If you decide a category badge belongs on the profile, add the field to both projections, to the key assertion and to the gate checklist in the same commit rather than widening the response quietly.

## Interfaces before handlers

Write the shapes first, in one small module the routes and tests both import. A shape that exists only in a controller comment drifts the moment a second route needs it.

```ts
export type LocationType = 'online' | 'at-home' | 'at-workshop';

export interface ProviderProfileInput {
  displayName: string;
  headline: string;
  bio?: string;
  timeZone: string;
  locationType: LocationType;
  avatarUrl?: string | null;
}

export interface PublicProviderView {
  id: string;
  displayName: string;
  headline: string;
  bio: string;
  timeZone: string;
  locationType: LocationType;
  avatarUrl: string | null;
}

export interface OwnerProviderView extends PublicProviderView {
  status: 'draft' | 'listed' | 'suspended';
  noticeMinutes: number;
  horizonDays: number;
  scheduleRevision: number;
  updatedAt: string;
}
```

The owner view extends the public view instead of repeating it, so a field added to the public profile appears in both projections or in neither. The `id` is a string in the response and an ObjectId in the database. Convert at the serializer, once, so no route accidentally serializes an ObjectId and no test has to guess which shape it received.

## Ownership on the update path

The update route is where a role check alone fails. The caller holds the provider role, so `requireRole` passes. The provider they own may be a different record from the one named in the path. Resolve the caller's own Provider row from the session first, then compare it with the target, then write with both identifiers in the filter so a concurrent change cannot slip between the check and the write.

```js
router.patch('/api/providers/:providerId', requireAuth, requireRole('provider'), async (req, res) => {
  const owned = await assertProviderOwner(req.principal, req.params.providerId);
  const patch = parseProfilePatch(req.body);
  const updated = await Provider.findOneAndUpdate(
    { _id: owned._id, userId: req.principal.userId },
    { $set: patch, $inc: { scheduleRevision: 1 } },
    { new: true, runValidators: true, projection: OWNER_PROJECTION },
  ).lean();
  if (!updated) throw notFound('PROVIDER_NOT_FOUND');
  res.json(toOwnerView(updated));
});
```

`assertProviderOwner` is the helper from Module 9. It loads the Provider whose `userId` matches the principal, compares identifiers as strings, and throws a mapped error when they differ. Because this route takes an identifier in the path, the documented response for a foreign target is `403 PROVIDER_NOT_OWNED`: the caller has a provider role, the target exists, and the relationship is wrong. The public read uses `404` for both absent and unpublished profiles, because that response must not confirm that a person has an account.

Two details in the filter matter. The `userId` condition means an ownership change between the helper and the write cannot redirect the update. The `$inc` on `scheduleRevision` gives later modules a version to compare, and it makes every profile edit visible in an audit trail without a separate event collection.

The last row of the trace is the one a status code cannot prove. A handler can deny the request after loading the document, and a future refactor can move the write above the check. The test therefore reloads provider A after the denied call and asserts the headline, the revision and the updated timestamp are all unchanged.

## Write the failing tests first

Each test below should fail before the route exists, and fail again if the route loses the rule it protects. The names describe the rule, not the file.

- `create_provider_twice_returns_conflict` expects `201` from the first call and `409 PROVIDER_EXISTS` from the second, with one Provider row for the account.
- `create_provider_rejects_offset_as_zone` sends `timeZone: "+02:00"` and expects `422 INVALID_TIME_ZONE`.
- `public_view_returns_exactly_six_display_fields` asserts the sorted key list of the response body, so a later field addition fails the test until a reviewer decides where it belongs.
- `public_view_hides_unpublished_profile` sets `status: "draft"` and expects `404 PROVIDER_NOT_PUBLIC`.
- `update_other_provider_returns_403` calls `PATCH` as provider B on provider A, expects `403`, and then reloads provider A to assert no field moved.
- `update_rejects_privileged_field` sends `{ "status": "listed" }` and expects `400 UNKNOWN_FIELD`.

Start with the third and the fifth. They take the least setup and they protect the two decisions that are expensive to discover later: a response shape that leaks an owner field, and a write that crosses an owner boundary. Then add the duplicate-profile conflict, because it needs a real index and a mongodb-memory-server instance configured with a replica set will not enforce a unique index the same way a scratch database does.

```js
test('public_view_returns_exactly_six_display_fields', async () => {
  const response = await request(app).get(`/api/providers/${providerId}`);
  assert.equal(response.status, 200);
  assert.deepEqual(Object.keys(response.body).sort(), [
    'avatarUrl', 'bio', 'displayName', 'headline', 'id', 'locationType', 'timeZone',
  ]);
});
```

## A zone change is a profile edit with consequences

The update route accepts a new `timeZone` and increments the revision. It does not rewrite weekly rules, and it does not touch a Booking. That restraint is deliberate. A paid booking holds a UTC instant, and a provider who moves from Gaza to Doha must not silently move a client's appointment. Future rules are a different problem, because a rule of "Monday 09:00" under a new zone describes a different set of instants.

For this module, record the consequence and leave the mechanism to Module 13. An active rule whose `timeZone` no longer matches the profile should make the provider unready for listing rather than silently reinterpret its hours. The profile response can carry the mismatch as a repair reason once that readiness check exists. The route stays small: validate, write, increment the version, return the owner view.

## Acceptance criteria and a manual check

The module is done when four statements are true and observable. A new account can create one profile and receives the owner view. A second create on the same account returns a conflict and does not create a row. A stranger reads the public view of a published profile and cannot see `userId`, `status`, `noticeMinutes`, `horizonDays` or `scheduleRevision`. A second provider is refused when editing the first provider's profile, and the first provider's row is unchanged.

Run it with curl against two seeded accounts. Create a profile as the tutor, request the public view without a token, then send the same patch as the designer and read the status line and the body. Compare the two response bodies key by key rather than by eye. Then open the tutor row in Compass and confirm the unique index is present on `userId`, because a test suite that runs against a database where the index never built will pass the duplicate case for the wrong reason.

The next lesson is the module gate. It asks for the conflict, the cross-provider denial and the two projections as evidence, plus a written answer about why a time zone lives on the profile while a booking stores an instant.
