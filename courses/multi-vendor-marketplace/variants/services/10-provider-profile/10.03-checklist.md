# Provider profile gate

This gate asks for four observations, not four opinions. A second profile for the same account is refused by the database. A zone that is an offset instead of a name is refused by validation. A stranger reading a published profile receives six fields and nothing about the account behind them. A second provider editing the first provider's record is refused, and the first provider's row is unchanged after the attempt.

Gather the evidence in one session and keep it in one place. Put the requests and the redacted responses in `docs/EVIDENCE.md` under a heading for Module 10, and put the decision in `docs/LEARNING-LOG.md`. A mentor should be able to repeat the four calls with the identifiers you recorded and reach the same statuses. If a call depends on a seeded account, record which seed row you used rather than a display name that could belong to two people.

## Show the conflict

Sign in as the tutor and create a profile with a display name, a headline, a biography, `Asia/Gaza`, a location type of `online`, and an avatar URL. The response should be the owner view, with the status, the notice and horizon settings and the revision visible. Repeat the same request with the same token. The second response must be a conflict, and a count of Provider documents for that account must still be one.

The count is the part that matters. A route can return `409` after inserting a second row and the status line will look correct. Query the collection by `userId` and show the number. Then show the index that caused the refusal, because a test that passes on a database without the unique index is testing the pre-check, not the invariant. If you cannot show the index, the gate stays open until it builds on a fresh database.

## Show the zone validation

Send the create request with `timeZone` set to `+02:00` and again with `Asia/Nowhere`. Both must fail with `422` and an error code that names the field, and neither may create a document. Then send `Asia/Gaza` and confirm the stored value is the zone name. The reason to test both a fixed offset and an unknown name is that a validator written as a loose shape check will accept the first and reject the second, and the first is the one that breaks a weekly rule next season.

Record the provider's local working window in words beside the request, for example "Monday 09:00 to 12:00 in Asia/Gaza". That sentence is what the zone field makes possible. Without it, the next module has no way to interpret a weekly rule, and the availability engine cannot resolve a dated start.

## Show the two projections

Request the public profile without a token and list the returned keys. There should be seven keys when the identifier is included: `id`, `displayName`, `headline`, `bio`, `timeZone`, `locationType` and `avatarUrl`. Then request the owner view with the tutor's token and list its keys. The difference must be exactly `status`, `noticeMinutes`, `horizonDays`, `scheduleRevision` and `updatedAt`.

Do the same for a draft profile. Set the status back to `draft` in the database, request the public route, and confirm `404`. Remember to restore the status after the check, because a later module's readiness test may depend on the tutor being published. If the public route returns a body for a draft profile, the projection is filtering fields but not records, and the module is not done.

## Show the refusal

Sign in as the second provider and send the update route with the tutor's identifier in the path and a changed headline in the body. Expect `403 PROVIDER_NOT_OWNED`. Then query the tutor row and read the headline, the revision and the updated timestamp. All three must be unchanged. Finish with the body of the denial and confirm it contains no display name, biography or zone from the tutor's record.

The last check is easy to skip and it is the one that catches a common implementation: the route authorizes the caller, then builds the error response from the document that was already loaded. The status is right and the private fields are in the response. Read the denial body rather than only its status line.

## Gate checklist

- [ ] `POST /api/providers` creates one profile for the authenticated account and returns the owner view.
- [ ] A second create for the same account returns `409 PROVIDER_EXISTS` and the database still holds one row.
- [ ] The unique index on `userId` exists in the database you tested, and its name is recorded.
- [ ] `timeZone` accepts a named IANA zone and rejects `+02:00` and unknown names with `422`.
- [ ] `GET /api/providers/:id` returns exactly the six display fields plus the identifier for a published profile.
- [ ] `GET /api/providers/:id` returns `404` for a draft profile.
- [ ] `GET /api/providers/me` returns the owner view and `404 NO_PROVIDER_PROFILE` when the account has none.
- [ ] `PATCH /api/providers/:providerId` refuses a foreign identifier with `403 PROVIDER_NOT_OWNED`.
- [ ] The refused update left the target row unchanged, including its revision and updated timestamp.
- [ ] The denial body contains no field from the target profile.
- [ ] `docs/erd.md` records the one-per-account rule and the public and private field lists.
- [ ] `docs/AUTHORIZATION.md` has a row for each of the four routes with its relation and projection.

## Learning log

1. Why does the time zone live on the provider profile rather than on each Service or on the account's login record?
2. A provider changes her profile zone from `Asia/Gaza` to `Europe/Berlin` while three future bookings exist. What stays fixed, what needs review, and what would be wrong to do automatically?
3. The public view and the owner view read one document. Why is that safer than maintaining a separate public collection?
4. Provider B holds the provider role and sends provider A's identifier in the path. Which two values does the server compare, and where does each one come from?

Answer with field names and one dated example where a date matters. For the first question, "use UTC" is not an answer; the profile zone is what makes a local weekly rule resolvable. For the second, name the Booking field that must not move and the record type that needs republishing. For the third, describe what happens to a new owner-only field added next month. For the fourth, say which value is untrusted input and which is derived from the session.

A useful learning log entry also names what is still missing after this module. Two answers are expected here. The profile stores an avatar URL but no upload path, which Module 14 adds. The profile stores a publication status but no readiness check, which Module 13 adds. Write both as open items rather than describing the profile as finished.

## Bridge to the practice page

The API can now create and read a provider. Nobody has used it from the browser. The next module builds the pages that call these routes: an onboarding screen for an account with no profile, a settings screen for the owner, and a routing gate that sends a provider to setup before she can reach anything else. That work will exercise the `404 NO_PROVIDER_PROFILE` response this module defines, so check that the code is stable and documented before the interface depends on it.

Bring the four pieces of evidence to your mentor review. If one is missing, name it plainly instead of describing the module as complete. A gate that stays open for one honest gap is more useful than a closed gate with a silent one.
