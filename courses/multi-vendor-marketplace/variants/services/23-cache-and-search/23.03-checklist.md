# Cache and search gate

This gate asks for evidence that the fast path and the honest path agree. A cached page is allowed to be a few seconds late. It is not allowed to keep offering an hour that a client already holds, and it is not allowed to be the only path that works. Show a mentor four things: a cache key sequence around a hold, a response from a stopped Redis, an `explain` output for one search, and a reschedule that changes the next availability read.

Run the checks against your own project, not against a story. Start with a clean availability key space, request one provider and service for a dated range, and note the `X-Cache` header and the revision segment. Create a hold on one returned start, then request the same range again. The claimed start must be absent and the header must read `miss`, because the checkout transaction moved `calendarRevision` and the key changed. If the header still reads `hit`, the key is missing a revision and this gate is not passed.

Next, stop Redis and request the same range. The route must answer 200 with `X-Cache: bypass` and the same correct list, because the engine reads rules, time off and claims from MongoDB. Time the two responses and put both numbers in your note, with the caveat that a laptop timing is not a production measurement. A cache that turns a dead memory store into a 500 has made availability worse than it was in Module 15, when there was no cache at all.

Then exercise search. Run a skill query, a language filter, a zone filter and a combined query. For the skill query, run `explain('executionStats')` and paste the winning plan. A plan that names `provider_text` with a non-zero keys examined count is evidence. A plan that shows a full collection scan means the index was not created on the database you are querying, which is a common local mistake after a model change.

Measurement belongs in this gate as well, because a cache that is not measured is a guess. Record the hit rate over a short scripted run, the slow-path latency with Redis stopped and the miss latency on a cold key. Compare those numbers with the Module 15 response you recorded before the cache existed, and write one sentence on whether the gain is worth a second moving part. If the hit rate is low because keys move on every claim, say so plainly: for a busy provider the cache is short lived by design, and the revision is still doing its job.

Finally, reschedule a confirmed booking. Before the reschedule, request availability for the provider and the affected day and keep the response. Change the booking to a new start in the same week, then request the same range again. The old start must be back and the new start must be gone. This is the one test that separates a cache keyed by revision from a cache keyed by nothing.

## Gate checklist

- [ ] `server/src/cache/keys.ts` is the only place that builds a cache key, and every key carries both revision counters.
- [ ] The cache port returns `hit`, `miss` or `bypass`, and no route handler catches a Redis exception itself.
- [ ] A hold created through checkout changes the next availability response for that service and day.
- [ ] A confirmed booking, a cancellation and a reschedule each change the next availability response.
- [ ] A service edit, an archive, a time-off range and a zone change each change the next public service list or availability response.
- [ ] Availability still returns 200 with a correct list while Redis is stopped, and the fallback is logged once per bypass.
- [ ] Checkout rejects a start that only a warm cache still calls free, with `SLOT_TAKEN` and the cart intact.
- [ ] The skill query plan names `provider_text` and the filter indexes are used for language, zone and listing.
- [ ] The search response returns no archived service, no private field and no unrefreshed next free time.
- [ ] TTLs are recorded per key in `docs/cache-keys.md`, with the stale window each value permits.

If a check fails, keep the module open and fix the narrow cause. A missing revision belongs in the key builder. A fallback that returns 500 belongs in the adapter, not in the route. A search plan that scans belongs in the schema and in a migration step that creates the index on every environment you use. Do not relax the invariant to make a check pass. The invariant is that the cache may decide what a client sees and may never decide what a client owns.

## Learning log

1. Name every record whose change should make a cached availability list unusable, and say which revision counter covers each one.
2. A hold commits while a cache delete fails. Explain in your own words why the next reader is still correct.
3. Redis is down for ten minutes during a busy evening. Describe what the client experiences, what the operator sees and what does not change.
4. Why does a composite revision of two counters beat one summed counter? Give a concrete sequence of two changes that would collide.
5. A search result shows a next free time from twenty minutes ago. What is the client told, and which route corrects it?

Write the answers with dates, provider identifiers and observed headers. A mentor should be able to follow one start through: shown on a page, held in a transaction, absent from the next page, restored after a cancellation. If any step in that story is explained by "the cache clears eventually", revisit the revision keys in 23.2.

Before closing, run the module tests once more from a clean database and a clean key space. Note the versions of MongoDB, Redis and the Node runtime beside the output, so a later reviewer can tell a configuration difference from a logic bug. This module is complete when the slow path is proven, not when the fast path is.

The next module moves scheduled work into a worker process. The revision counters built here become the signal that a reminder is out of date, so leave them where other services can read them.
