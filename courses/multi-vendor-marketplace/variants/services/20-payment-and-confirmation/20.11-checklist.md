# Payment and confirmation gate

Begin with an M19 held checkout containing at least two provider Orders. Show the accepted line allocations, their single-currency sum and the original hold deadline. Create exactly one test-mode PaymentIntent from that snapshot total. Confirm it with a test card, process a signed webhook and show the CheckoutAttempt paid, both Orders paid, both Bookings confirmed and all occupied SlotClaims retained. The provider dashboards should show only their own confirmed share. The client should see both appointments with clear local time labels and one payment result.

Do not pass this gate from a client-side success callback alone. The reviewer needs Stripe test evidence, a raw-body signature test, stored webhook event identity and post-transition database records. Keep secrets, full card data and client personal data out of the committed evidence. The runnable reference build, not only lesson snippets, must demonstrate the route, worker and UI states before a human G5/G6 approval can be recorded.

## Gate checklist

- [ ] The payment endpoint authorizes the checkout owner and uses only accepted Order and Booking snapshots for amount and currency.
- [ ] One PaymentAttempt and one Stripe PaymentIntent represent the CheckoutAttempt, with stable external idempotency keys for creation and cancellation.
- [ ] The webhook verifies `Stripe-Signature` against the exact raw body before any purchase state changes.
- [ ] Event IDs are stored durably; duplicate or out-of-order delivery cannot repeat confirmation, quota change or notification.
- [ ] A timely trusted success atomically pays all provider Orders, confirms all Bookings and claims, and releases active hold quota once.
- [ ] A declined card leaves the original hold and deadline intact while a permitted retry can use the same Intent.
- [ ] Expiry cancels or resolves an existing Intent outside the MongoDB transaction before it releases exact claims.
- [ ] An uncertain or processing external status keeps claims live and exposes a resolving state until safe disposition.
- [ ] A late successful charge after release never confirms a Booking without full re-claimed blocks.
- [ ] SkillSlot's line-by-line recovery confirms recoverable provider Bookings and creates idempotent partial refunds for lost charged allocations; Order shares reconcile to the one original payment.
- [ ] Refund requests run from durable records outside the database transaction and retries cannot duplicate money movement.
- [ ] Success, decline, authentication-required, duplicate event, invalid signature, expiry race and mixed late-success cases have test output.

## Learning log

1. Why is a PaymentIntent created after the database hold, outside the transaction callback? Name what happens if either system succeeds while the other is temporarily unavailable.
2. A browser says payment succeeded but the webhook has not run. Which local records remain held, and what should the client screen say?
3. A failure event arrives after a signed success event. Which persisted state predicate stops a paid Booking from regressing?
4. At the hold deadline, Stripe reports `processing`. Why can the expiry worker not delete claims simply because the clock reached the deadline?
5. A 10,500-unit late charge has a 4,500-unit tutor line that cannot be recovered and a 6,000-unit music line that can. State the Booking, provider Order and refund outcomes and show the accounting equation.

Answer with exact model fields, state names and one dated UTC hold deadline from the test. A response that says MongoDB rollback reverses a Stripe charge is incorrect. A response that marks a lost Booking confirmed without its claims is also incorrect. Revisit the diagram in 20.1 and the recovery worker in 20.8 before checking those boxes.

## Evidence and review

Commit `docs/payment-policy.md` and `docs/payment-evidence.md`, the environment example with placeholders, index checks, webhook tests, expiry and refund worker tests, and redacted test-mode results. Include a two-provider success trace and the mixed late-success trace. The latter must show `chargedTotalMinor = retainedTotalMinor + refundedMinor` after refund completion, with provider Order shares consistent with their Booking lines. An outstanding refund can be recorded as `refund_pending`; it must not be misreported as completed.

Ask a reviewer to deliver the same signed success event twice and inspect the event store, outbox and quota counter. Ask them to block Stripe cancellation temporarily and run expiry: claims must remain live while the attempt is resolving. Ask them to change a Service's current price after hold creation: the Intent amount and any refund allocation must remain based on the accepted snapshot. These checks expose the three most tempting shortcuts in a payment integration.

Record one issue found during review and the exact change made. If the module cannot run the test-mode flow against an executable reference application, keep that as an open gate instead of marking the variant ready from prose alone. The next module can build my-bookings and provider schedules on top of confirmed and reconciling states only after these transitions are coherent.

## Review a complete record set

Give a reviewer a redacted PaymentAttempt ID and ask them to reconstruct the purchase without opening the browser. They should find the owning CheckoutAttempt, its original deadline, each provider Order, each Booking's accepted charged allocation, the one Stripe PaymentIntent ID, the signed event records and the final claim state. For the ordinary success, the provider Order amounts must sum to the charge and the Bookings must retain all occupied blocks. For a release, historical Bookings remain while claims are gone. For a mixed recovery, confirmed claims and refund records account for every charged line.

The reviewer should also inspect what the client and provider see. A client can view the whole payment outcome and refund status. Sara can see only her tutor Order and Booking; Omar sees only his music share. Neither provider receives the client's card secret or the other provider's subtotal. A test that updates database rows correctly but leaks the whole CheckoutAttempt in a provider route does not pass the product gate.

Finally, demonstrate that a worker can resume after a crash at each external boundary. One test stops after local PaymentAttempt creation but before Stripe responds; retry uses the same create key. Another stops after Stripe cancellation but before database release; retry sees the cancelled status and finishes. A third stops after a partial refund request succeeds remotely but before local acknowledgment; retry uses the same refund key. Show one external object per operation and a consistent local terminal state. This evidence is more persuasive than a generic statement that webhooks are idempotent.

Have the reviewer sign the evidence table with the date, environment and outstanding limitations. A passing test-mode flow does not prove live provider settlement, payout handling or a production reference build. Keep those items open in the course readiness record until separate implementation and review exist.
