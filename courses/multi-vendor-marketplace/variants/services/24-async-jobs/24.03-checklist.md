# Async jobs gate

This gate asks whether the work outside the request is trustworthy. The evidence is a worker log, a moved reminder, one released hold and a written retry policy. A demonstration of a single happy message is not enough, because the whole reason for a worker is what happens when something goes wrong between the payment and the message.

Show the process separation first. Start the API and the worker as two commands, stop the worker, and take a booking through checkout. The booking must succeed, the response must be a normal held or paid result, and the outbox row must be visible as pending. Start the worker again and show the same row becoming published and the message appearing once. This single exercise proves the request path no longer depends on the message path, and it is the clearest answer to "what happens when the worker is down".

Then demonstrate a reschedule. Confirm a booking whose start is more than a day away so both reminders exist, record the two job IDs, reschedule to a different start, and record the queue contents again. The old IDs must be gone or, if one refused removal, the old job must return `superseded` when it runs. The new job must carry the new reminder version and the new delay. Keep the two log lines: one skip with a reason and one scheduled job with a computed delay.

Next, sweep. Create a hold, use an injected clock to pass `holdExpiresAt`, run the sweep twice, and show the claim count at zero with one release event recorded. Then repeat with a hold whose PaymentIntent already succeeded, or whose attempt is in the resolving state, and show the claim still present. Those two runs together are what a mentor needs to see: the sweep is safe to repeat and it does not decide money outcomes on its own.

Review the payloads before you finish. Open one stored job for each name and read what it carries. A booking identifier, a reminder version and an offset are enough for a reminder. A client's home address, a meeting link, a card detail or a full rendered message is too much, because job payloads are stored in Redis, printed in failures and kept for a week. The worker renders private content at the moment of sending, from the current booking and the caller's relationship to it, which is the same need-to-know rule Module 9 applied to the API. Write one line in `docs/jobs.md` saying which fields each payload may contain, and check a stored job against that line.

Finally, write `docs/jobs.md` with four short sections: the job names and what each one does, the retry policy per job with the errors marked unrecoverable, the dedup key for each side effect, and the operational signal that tells you the worker is behind. Put the age of the oldest pending outbox row and the queue depth in the last section, with the threshold you would alert on.

## Gate checklist

- [ ] `server/src/worker.ts` starts without the API, takes its configuration from the environment and closes cleanly on `SIGTERM`.
- [ ] The API takes a booking while the worker is stopped, and the pending outbox row is visible in the database.
- [ ] Starting the worker publishes that row and delivers exactly one message per party, each rendered in the recipient's zone.
- [ ] A reschedule moves both reminders to the new reminder version, and an old job that still runs returns `superseded`.
- [ ] A reminder processed twice sends one message, and the delivery key is recorded.
- [ ] The repeatable sweep is registered once, runs on a schedule, and releases a due unpaid hold exactly once across two runs.
- [ ] A hold whose payment is unresolved keeps its claims through a sweep.
- [ ] A stale `provider.nextAvailable` job writes nothing, and a current one updates only the revision it read.
- [ ] Retry attempts, backoff and unrecoverable error classes are written in `docs/jobs.md`, with one log line per job carrying name, ID and attempt.
- [ ] The oldest pending outbox age and queue depth are visible, with a threshold and a reason for that threshold.

When a check fails, keep the module open and repair the cause rather than the symptom. A message that never arrives is usually a relay that marks a row published before the queue accepted it. A duplicate message is usually a missing delivery key or a payload rendered before the state check. A hold released twice is usually a sweep that deletes claims directly instead of calling the release service. Each of those is a small fix in a known place, and each is worth a named test so it cannot return.

## Learning log

1. Why does the confirmation message belong in an outbox row written by the transaction rather than a `queue.add` call after the commit?
2. A reschedule removes the old reminder jobs and one remove call fails. Walk through what happens, naming the value the processor compares.
3. The sweep runs every minute. Explain why running it late, twice or on two workers does not release the same hold twice.
4. A reminder job is retried after a worker crash. Which two mechanisms stop the client from receiving two messages?
5. The oldest pending outbox row is nine minutes old at 22:00. What would you check first, and what would you tell the client?

Answer with the job IDs, reminder versions and timestamps from your own project. A mentor should be able to trace one booking from the paid webhook to one message per party, and one reschedule from the API call to a skipped stale job. If any answer depends on the queue never repeating a job, revisit the version check and the delivery key in 24.2.

Before closing, restart the worker while a delayed reminder is pending and confirm the job still fires at its scheduled instant. A worker restart that loses scheduled jobs is the most common way this module appears to pass in a demo and fails in week four of real use.

The next module deploys the API and the worker as separate services. Keep the two start commands and the environment variable list from this gate, because that list is the deployment checklist.
