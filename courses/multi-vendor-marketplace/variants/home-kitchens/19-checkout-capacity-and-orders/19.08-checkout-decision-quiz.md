```quiz
type: mcq
id: sufra-checkout-q1
question: A ten-unit window receives twenty simultaneous three-unit claim requests, each with a unique attempt key. What result is safe?
options:
  - Four holds and a remaining counter of zero
  - Ten holds because the counter began at ten
  - Three holds and one unit still available
  - Twenty holds followed by worker releases
correct: 2
explanations:
  - Four claims consume twelve units and would overbook the kitchen.
  - The dish load is three units, not one.
  - Three claims consume nine of ten units; a fourth cannot fit.
  - Releasing after accepting too many is not a safe checkout decision.
```

```quiz
type: mcq
id: sufra-checkout-q2
question: Kitchen A is held, but kitchen B is full. The API process stops before returning. What should recovery do?
options:
  - Release A once and abort the attempt
  - Charge for A only because its claim already succeeded
  - Reset both windows to their original weekly capacity
  - Delete the attempt so the first hold cannot be found
correct: 0
explanations:
  - Deterministic claim IDs let recovery find and idempotently release A.
  - The diner reviewed a two-kitchen cart and must not be charged for one kitchen silently.
  - Resetting a window can make other held or paid units available twice.
  - Deleting the attempt removes the recovery map and leaks capacity.
```

```quiz
type: mcq
id: sufra-checkout-q3
question: A maqluba hold expires at 11:10. Stripe reports payment success after expiry, and the claim was already released. What is safe?
options:
  - Reopen the released claim without checking the window
  - Mark the draft paid because Stripe succeeded
  - Create another claim with the same old attempt key
  - Record a refund and keep the claim released
correct: 3
explanations:
  - Another diner may have claimed the restored units.
  - Money arriving late cannot make expired cooking capacity valid.
  - Reusing the old key must recover the old attempt, not start a hidden second one.
  - The payment event needs reconciliation and a refund path, not a silent meal promise.
```

```quiz
type: mcq
id: sufra-checkout-q4
question: A retry uses the same attempt key but changes one dish quantity. How should the server respond?
options:
  - Reuse the first claim and silently charge the higher total
  - Reject key reuse and ask for a reviewed new attempt
  - Increase the old claim's units without changing its identity
  - Trust the browser's new total because the user changed it
correct: 1
explanations:
  - The first attempt is bound to its original cart snapshot and amount.
  - A changed cart requires a new reviewed attempt and fresh server validation.
  - Changing a held claim's units breaks retry and release accounting.
  - Browser totals are display values, not payment authority.
```
