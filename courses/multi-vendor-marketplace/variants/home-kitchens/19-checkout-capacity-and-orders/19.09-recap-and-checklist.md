# Capacity checkout gate

Sufra can now prepare a multi-kitchen checkout without overselling a dated window. A kitchen group has one atomic claim on its window. A checkout attempt records every group and compensates if one fails. Draft orders preserve each kitchen's price and delivery promise. The payment module comes next; this gate does not claim a card was charged or a webhook was handled. It asks for evidence that the capacity and order side is safe enough to hand to that module.

## Recap the claim path

One dated window owns its capacity counter and embedded claims. The conditional update checks units, open status, time and claim identity while it subtracts units and records a held claim. An attempt groups one such claim per kitchen. If a later kitchen fails, an idempotent release returns earlier units. Only an attempt with all claims and immutable draft orders can cross into the payment module. The state machine preserves a clear answer after retries and process stops.

Show a reviewer the actual database rows after a race. A ten-unit window with twenty three-unit attempts has three held claims and one unit remaining. Every prepared attempt has one matching draft order for that kitchen. Every conflict response lacks a payment path. Then show the same attempt retried with the same key: order IDs, claim IDs, counter and deadline remain unchanged. This evidence is stronger than a screenshot of a green button.

## Demonstrate the full path

Start with a two-kitchen cart for a single delivery interval. Kitchen A offers maqluba with three load units; kitchen B offers sweets with two. Both dated windows have enough units and their cutoffs are still open. Prepare checkout and inspect the persisted attempt, both embedded claims, both draft orders and the fixed server total. The attempt can progress to one PaymentIntent in M20, but the order states remain `awaiting_payment` now. The kitchen dashboard must not treat them as cooking tasks yet.

Next make B full before checkout. The API may briefly hold A, but it must return a conflict for the whole cart. Run recovery and show A's claim released and exactly three units restored. A second recovery run changes nothing. If the process stops after claiming A, restart the worker and show it discovers A's deterministic claim ID from the attempt's planned groups. A local exception handler is not sufficient evidence for a process stop.

Then freeze the clock around maqluba's 11:10 cutoff. At 11:09:59 the claim may succeed if capacity remains. At 11:10:00 it must fail. Make the clock advance across the boundary while the database write is in progress. The post-write guard must release the temporary claim and withhold payment. A phone with a wrong clock gets the same backend decision. A reviewer should see the exact UTC instants in the test output, plus the kitchen zone used to format the label.

## Checklist and evidence

- [ ] Each dated window maintains `remainingUnits + heldUnits + confirmedUnits = capacityUnits` after claim, release and retry.
- [ ] Every claim checks enough units, open status, general cutoff, per-dish preparation lead and a new claim ID in the state-changing path.
- [ ] The same attempt key returns the same claim and orders; changed cart contents with that key are rejected.
- [ ] A two-kitchen failure releases earlier held groups once and never offers payment for a partial cart.
- [ ] Draft orders are split by kitchen and retain name, price, preparation, load, window and zone snapshots.
- [ ] One persisted attempt total equals the sum of kitchen order totals in integer minor currency units.
- [ ] Twenty parallel requests and a forced process stop have saved commands, outputs and database rows in `docs/EVIDENCE.md`.
- [ ] Held claims expire at the earliest useful deadline; a late payment event has a recorded refund path rather than a new capacity debit.

If any item fails, keep the attempt out of payment. Identify the failing boundary before adding code. A negative counter points to an unsafe update filter. Correct arithmetic with four payable drafts points to a weak preparation gate. An aborted attempt with a held claim points to incomplete compensation. A released claim whose units were added twice points to a release transition that did not require `state: held`. A late dish accepted at 11:10 points to a missing strict time condition or a stale clock read.

## Questions for the walkthrough

Ask the learner why a one-window atomic update does not make a two-kitchen cart atomic. They should be able to name the temporary partial hold, the attempt record, the release worker and the customer-visible payment boundary. Ask why the claim is embedded on the window. The answer should connect the counter debit and claim identity to MongoDB's single-document atomicity, while admitting that the window document must stay bounded. Ask what a MongoDB transaction would improve and what it would not: it could commit the two window writes together, but Stripe would still need webhook and refund reconciliation.

Ask a second question about time. Why can falafel still be offered at 11:31 while maqluba cannot, even when both use the same window? The learner should compute each effective cutoff from the dated 13:00 start, preparation time, travel buffer and general 12:00 cutoff. They should explain why the server checks again at claim time. A statement such as "the frontend disables the button" is not enough; the database path must reject the late attempt.

Finally, ask what happens if Stripe reports success after an expired claim was released. The correct response is not to add units back or revive an old claim. The payment module records the late-success condition, prevents a kitchen job from appearing, and starts a traceable refund. The exact API and webhook code belongs to M20. This gate establishes the required contract for that work.
