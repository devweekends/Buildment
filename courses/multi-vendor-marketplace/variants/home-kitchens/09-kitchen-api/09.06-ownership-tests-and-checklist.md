# Ownership tests and gate

The Kitchen API now has a public profile boundary, an owned weekly template, a named time zone and a dated pause. This gate asks you to show that these pieces agree and that a second cook cannot change them. It also asks you to explain what the API does not yet prove. M14 still needs to generate current dated windows and reconcile exceptions. A profile or template save by itself is not an orderable lunch.

Use two cook accounts and one diner account. Cook A creates Umm Yousef's Kitchen with area codes, `Asia/Gaza`, a Monday 13:00 lunch rule, ten capacity units and a 60-minute general cutoff lead. Cook B creates a separate kitchen. The diner can read approved public fields but cannot edit either kitchen. Run every edit route as cook B against cook A's ID and check that no saved field changes. A hidden Edit button is not the evidence; a denied API request and unchanged database row are.

## Recap what each record owns

The Kitchen record owns public identity, service areas, time zone and weekly rules. The weekly rule describes a local recurring interval and planned capacity. The `ScheduleException` owns a closure for one kitchen-local date, including the wildcard case for a whole-day pause. The `DeliveryWindow` owns a dated UTC interval and mutable capacity. A paid Order snapshots its window and price promise. A cook can change future settings through owned routes, but cannot erase a paid historical promise by editing a profile.

Show the 13:00 rule in both human and machine form. The saved weekly row should have `localStart: '13:00'`, weekday, capacity and cutoff lead, plus the kitchen's `Asia/Gaza` zone. It should not have one UTC start date pretending to represent every Monday. A dated window created later will have `startAt`, `endAt`, `cutoffAt` and `kitchenZoneAtGeneration`. If those fields are currently only in the model fixture, say so; do not present a static fixture as proof that live generation works.

For the pause case, freeze the server clock on a Thursday that is Thursday in the kitchen's zone. Save the exact UTC instant used and the resolved local date. The first pause call should create one wildcard closed exception, and the second should return that same exception. Inspect the weekly Thursday rule after both calls; it must still be present. Then inspect an existing dated row for this Thursday and one for next Thursday. This week's row is closed to new claims; next week's remains governed by the normal rule. A paid order pointing to this week stays readable and needs a resolution path.

Do the ownership test again after this setup, not only on an empty kitchen. Cook B should not be able to read a private list of cook A's affected paid orders by calling the pause route with A's kitchen ID. The denial must happen before a response is built from those orders. A diner may see a public closed-window result, but not the number or identity of people whose meals were affected. This proves that the new schedule operation preserved the permission boundary established for the profile.

## Gate checklist

- [ ] Cook A can create and edit a draft kitchen profile with normalized service-area codes.
- [ ] The public kitchen response excludes owner account fields and private addresses.
- [ ] A weekly template rejects duplicate keys, overlapping same-day windows, invalid times, fractional units and stale revisions.
- [ ] The kitchen stores a validated named IANA zone, and raw offset input is rejected under the course policy.
- [ ] A zone edit that would affect held or paid future windows returns a conflict and leaves those promises unchanged.
- [ ] Pause-today resolves the kitchen-local date on the server, writes one wildcard closed exception and leaves next week's template intact.
- [ ] An existing paid order survives the pause and is reported for follow-up; no new claim is offered for the closed date.
- [ ] Cook B and the diner cannot edit cook A's profile, schedule, zone or pause state through direct API calls.
- [ ] Commands, request IDs, response codes and before/after database values are saved in `docs/EVIDENCE.md`.

If an ownership test fails, inspect the service query filter for `ownerUserId`. Do not patch only the route's UI. If an overlapping rule saves, run the whole-set validator before the update. If a timezone edit shifts an existing order, separate prospective template data from dated and paid snapshots. If a pause appears to work but a generator rerun reopens today, check the wildcard exception lookup and `$setOnInsert` behavior before changing the weekly rule.

## Learning log

Answer these in `docs/learning-log.md` with the saved request and row that support each conclusion. Keep a date and zone on time examples so another learner can repeat them.

1. Which authenticated field and saved relationship stopped cook B from editing cook A's weekly schedule?
2. Why does a Monday 13:00 weekly rule need `Asia/Gaza` and a specific date before it can become a UTC `DeliveryWindow.startAt`?
3. What remained in the database after pause-today, and what extra action is needed if a diner already paid for that date?

The answers should name fields and state changes rather than saying only that the API is secure or the kitchen is closed. If one answer depends on the browser hiding an action, rerun it as a direct API request. If the pause explanation deletes the weekly rule, compare this Thursday with the following Thursday. The goal is a data path a peer can defend without relying on the form's current display.

Ask a peer to challenge one saved response. They might ask whether an `open` kitchen necessarily has lunch today, whether the phone's timezone decided the pause date, or whether closing a date canceled a paid order. Use the saved records to answer: dated windows decide the offer, the kitchen zone decides the local date, and an explicit order lifecycle resolves paid promises. If the response fields make those answers unclear, improve the API contract before building the onboarding screen.

The next module builds the cook onboarding interface for a phone. It will use these routes and their field-specific errors. The later delivery-window module will expand the validated schedule, and checkout will consult both dated state and any closure before payment. Keep this gate's ownership tests as regression evidence while those paths grow.
