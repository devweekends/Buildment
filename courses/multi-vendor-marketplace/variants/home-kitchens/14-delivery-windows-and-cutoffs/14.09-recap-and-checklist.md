# Delivery-window gate

The kitchen's weekly schedule now generates dated delivery windows. Each row has UTC start and end instants, a kitchen-zone snapshot, capacity, a general cutoff and a stable identity. A dish's effective cutoff uses the earlier of the kitchen cutoff and its preparation deadline. The server checks that cutoff against its own clock. This gate asks you to show those decisions together, including what happens when generation retries or a cook changes one day.

## Demo one lunch window

Seed a kitchen in `Asia/Gaza` with lunch from 13:00 to 14:00, a 12:00 general cutoff and a 20-minute travel buffer. Add maqluba with 90 prep minutes and falafel with 30. Open the diner view at a fake server time of 11:31. Show that maqluba is closed at 11:10 while falafel is still timely until 12:00. Explain that falafel may still fail a separate capacity check. The UI should offer a later window for maqluba rather than saying every dish is sold out.

Next show the generated rows for seven kitchen-local dates. Run generation a second time and compare row IDs. Add a held claim to one window, run it again, and show that `remainingUnits` did not reset. Close one unclaimed date with a dated exception. The following week's same weekday should still follow the weekly template. If a row has a paid order, show that the row and its order link remain while new claims stop. No gate can pass by deleting a paid promise to make the public list look clean.

## Checklist

- [ ] A weekly kitchen rule expands into seven dated windows using the kitchen's IANA zone.
- [ ] Every dated window has UTC start and end, zone snapshot, capacity, remaining units, general cutoff and status.
- [ ] Unique indexes prevent duplicate occurrence rows when generation runs concurrently.
- [ ] A retry preserves existing window IDs, held claims and remaining units.
- [ ] A slow dish closes at its preparation deadline; a fast dish can close at the general kitchen cutoff.
- [ ] One second before cutoff passes; exactly at and after cutoff fail under the documented rule.
- [ ] A dated closure does not delete the weekly template or a paid order's window.
- [ ] A replacement window is validated in the kitchen zone and does not overlap another window.
- [ ] Tests pass under two process `TZ` settings and include a historical clock-change week.

If a check fails, identify which boundary owns the problem. A wrong UTC start belongs to local-rule expansion. A duplicated row belongs to idempotency and unique keys. A reset `remainingUnits` belongs to a retry that updated an existing row. A late dish belongs to cutoff calculation or a checkout path that trusted stale browse data. Do not fix one by changing an unrelated number. Write the failing dated example and the exact server instant in `docs/window-decisions.md` before editing code.

The review should include one negative API result. At the cutoff, a late dish returns a specific code and no capacity claim. After the cutoff, a diner who changes their phone time does not become eligible. A second generator run leaves the same paid or held row intact. These are the points where a learner might be tempted to show only a happy-path screen. The mentor should ask for the failed request and the unchanged database row because those demonstrate that the promise is protected when conditions change.

If the public UI says a dish is unavailable but the API says it is timely, compare the response's server time with the phone clock and any stale cache. If the API says it is timely but checkout rejects for capacity, that can be an expected race; refresh the available windows and explain the difference. If a second worker run creates another row, inspect the unique index and local occurrence key before changing front-end code. Each failure has a different owner and a different recovery action.

## Learning log

1. At 11:31 the kitchen has four units left. Why may maqluba be unavailable while falafel is still orderable? Name both cutoffs.
2. Why does `Math.min(prepCutoffAt, window.cutoffAt)` express the promise more safely than `Math.max`? Work one numerical example.
3. A generator runs twice after a worker restart. Which fields must remain unchanged on an already held window, and how does the database enforce one occurrence?
4. A cook closes tomorrow's lunch after one diner paid. What changes for new diners, and which order and window records remain for the paid diner?

Answer with field names and dated instants, not only labels such as "earlier" or "later." The mentor should be able to trace one order from the weekly rule through a dated window and a dish cutoff. If you cannot yet explain where the kitchen zone is used, rerun the Berlin clock-change test. If you cannot explain why a paid row survives a closure, inspect the order snapshot and exception reconciliation flow.

## What comes next

The next browse module will let diners choose a window first, then see kitchens and dishes that are timely and have visible remaining capacity. That list is a view, not a guarantee. The cart and checkout modules will revalidate the cutoff and use atomic conditional updates to claim units. This module has prepared the dated, explainable window that those later decisions need. Its gate does not claim that concurrent checkout is safe yet; that proof comes from the capacity-claim race test.

Before moving on, ask a peer to take one dated window and independently calculate both dish cutoffs from the documented inputs. Compare their answer with the API. A disagreement means either the description, stored zone, or code is unclear. Resolve it here, while the example is small. The later multi-kitchen checkout will be harder to debug if the basic lunch window cannot be explained by another person.
