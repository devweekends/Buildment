# Kitchen dashboard gate

A cook's dashboard is the first surface in Sufra that reads from four collections at once and shows a person their own business: their dishes, their capacity, their orders. That makes it the first place where a scoping mistake looks like a normal screen. A list that returns every kitchen and filters in the browser looks correct to whoever built it, and it fails the moment a cook with a token and a command line asks for it directly.

This gate is a scoping test, not a layout review. The layout was checked in lesson 12.1. Here you prove that a second cook, with a valid token and a real kitchen of her own, cannot read or change anything that belongs to the first, and that a diner cannot reach the surface at all.

## Set up two kitchens with something to hide

Seed cook A with Umm Yousef's Kitchen, two dishes, one dated window and at least one order. Seed cook B with her own kitchen, one dish and no orders. Keep both in `Asia/Gaza` so the labels are easy to compare, and keep cook B's kitchen deliberately smaller, because one of the checks is that A's numbers do not appear in B's screen by accident.

Then collect the identifiers of A's records: the kitchen, both dishes, the window and the order. You will need them for direct requests, and a reviewer will want them in the evidence file next to the responses that refused them.

The screen test comes second. Open the dashboard as cook B and confirm that no name, dish, window or count from A appears. That check is necessary and it is not sufficient, because a client cannot prove a server rule. The rest of the gate is run with `curl` or an HTTP client, using B's token.

## Walk the isolation matrix

Every route that the dashboard calls, and every route the dashboard's buttons call, gets the same treatment. For each one, send B's token with A's identifier and record the response.

| Request | Expected | What it proves |
|---|---|---|
| `GET /api/v1/cook/dashboard` as B | 200 with B's data only | The route resolves the kitchen from the session |
| `GET /api/v1/cook/dishes?kitchenId=A` as B | 200 with B's dishes, or 400 for the unknown parameter | A query parameter cannot widen scope |
| `PATCH /api/v1/cook/dishes/{A dish}` as B | 403 | The write filter includes the resolved kitchen |
| `POST /api/v1/cook/orders/{A order}/accept` as B | 403 | The action route checks the kitchen, not only the role |
| `GET /api/v1/cook/dashboard` as a diner | 403 | The surface is role gated |
| `GET /api/v1/cook/dashboard` with no token | 401 | Authentication comes first |

The second row is the one people argue about. A route that accepts a `kitchenId` parameter and then compares it to the resolved kitchen is safe in the sense that it refuses the mismatch, and it is still a worse design than one that has no parameter, because the next developer copies the route and forgets the comparison. Where the parameter exists for a cook who owns two kitchens, the comparison must be explicit, tested, and paired with a switch action that is itself authorized.

The fourth row is where a dashboard becomes dangerous. Accepting an order is a state change with a real diner on the other side. A route that loads the order by identifier and then checks `role === 'cook'` will let B accept A's order, and the diner will see a kitchen that is not cooking their food mark it accepted. The predicate has to include the kitchen identifier, in the query that performs the write.

## Watch what a refusal still reveals

A refusal is not automatically safe. Three shapes of response leak information while returning a denial, and each has a cheap fix.

The first is a count. A dashboard that returns `orderCount: 0` for B but takes 900 milliseconds because it scanned every order in the database tells an observer something. More practically, a route that returns "you have 0 of 4 orders" for a kitchen the caller does not own has confirmed the existence and size of another kitchen's day. Filter before you count, not after.

The second is an error message that distinguishes "not found" from "not yours". This module chose `403 NOT_KITCHEN_OWNER` for dish writes and the choice is written down, so honour it consistently. What must not happen is a mixed response where a missing record returns `404` and an existing one returns `403` with the dish name in the body, because that turns the API into a lookup service for other cooks' menus.

The third is a shared identifier in a nested object. A dashboard payload that includes the parent checkout attempt identifier for an order lets a caller who collects enough of them pivot to a route that groups orders by attempt. Send only the identifiers the screen needs, and treat every extra field as a small piece of someone else's record.

```js
// server/test/dashboard/isolation.test.js (failing first)
it('returns only the calling cook\'s records', async () => {
  const res = await request(app).get('/api/v1/cook/dashboard')
    .set('authorization', 'Bearer ' + cookBToken);
  assert.equal(res.status, 200);
  const body = res.body;
  assert.equal(body.kitchenId, kitchenB.id);
  assert.deepEqual(body.dishes.active.map((d) => d.dishId), [dishB.id]);
  assert.equal(JSON.stringify(body).includes(kitchenA.id), false);
  assert.equal(JSON.stringify(body).includes(dishA.id), false);
});
```

The last two assertions are blunt, and that is the point. They fail on a payload that leaks A's identifier anywhere, including in a field nobody reads yet.

## Actions the screen offers must be actions the route allows

The dashboard renders buttons from `allowedActions`, and the route that receives the tap enforces the same table. A gate check that only tests the screen leaves the interesting half untested. For each action in the table for a placed order, send the request as the wrong cook, as the right cook before the deadline, and as the right cook after it. The wrong cook must be refused every time. The right cook must succeed before the deadline and be refused after it, with a body that names the current state.

That combination is what makes the button honest. A button that appears when the action will fail is a usability defect. A route that allows an action the button never shows is a security hole with a friendly face.

## Gate checklist

- [ ] Cook B's dashboard response contains no identifier, name or count from cook A's kitchen.
- [ ] The dashboard route resolves the kitchen from the session and accepts no kitchen identifier from the query or the body.
- [ ] A diner token is refused on the dashboard and on every cook action route.
- [ ] A missing token returns 401 before any database read.
- [ ] Cross cook dish reads, writes, publishes and hides are refused with the module's documented code.
- [ ] A cross cook order action is refused by the writing query, not by a hidden button.
- [ ] A refusal does not reveal a record's existence, name, size or parent attempt identifier.
- [ ] `allowedActions` matches the route's enforcement for a placed order before and after its deadline.
- [ ] The dashboard renders one section's failure without blanking the other two.
- [ ] Direct requests with both tokens are saved in `docs/EVIDENCE.md` beside the stored documents they protected.

If a count leaks, move the filter into the query. If a refusal returns a name, project fewer fields. If a cross cook action succeeds, the writing query is missing the kitchen identifier. If the screen shows an action that the route refuses, both places are reading different tables.

## Check the scoping rule

```quiz
type: mcq
id: sufra-dashboard-q1
question: Cook B sends GET /api/v1/cook/dashboard with her own valid token. Which result shows the route is scoped correctly?
options:
  - Every kitchen in the database, filtered in the browser before anything is drawn on the screen
  - A 403 for the whole dashboard even though B owns a kitchen, because the route cannot tell kitchens apart
  - Cook A's windows with cook B's dish names mixed into the same rows, which the client then separates
  - B's own kitchen, and a 403 when B sends any of A's identifiers
correct: 3
explanations:
  - A payload that contains every kitchen has already leaked the data, whatever the browser does next.
  - A cook with her own kitchen must be able to read her own dashboard, so a blanket denial is a defect too.
  - Mixing two kitchens into one row means the query never filtered, and no client step can repair that.
  - Scope from the session plus a refusal on a foreign identifier is the pair of behaviours that proves the rule.
```

## Learning log

Answer these in `docs/learning-log.md` with the request, response or document that supports each answer.

1. Which field did the dashboard route use to resolve the caller's kitchen, and where did that value come from?
2. Which response was the first to leak something during your testing, and what did you change to remove it?
3. What did the cross cook accept request return, and what did the order look like afterwards?
4. How does the dashboard keep one failing section from hiding the other two, and which section did you test?
5. Why is a `kitchenId` query parameter on a cook route a risk even when the route compares it correctly?

The fifth answer is the one to keep for the next time you add a cook route. A parameter that must be checked is a rule that can be forgotten, and the session is the only value a client cannot choose.

When the isolation suite passes with both tokens and the two screenshots show only the caller's data, the cook side of the product has a menu, a fixed layout and a dashboard. The next modules add dish photographs, then the delivery windows that turn the weekly template into dated offers a diner can actually choose. Keep this gate's suite in the repository. Every later cook route reads the same records, and the cheapest time to catch a scoping mistake is before the route exists.
