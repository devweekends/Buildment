# 7.18 Checklist and learning log
> **[Gate]** · Chapter 07 · Login and registration

This is the **gate** for Chapter 7. Tick every box honestly and answer the learning log below before opening Chapter 8.

Chapter 6 proved that the auth API works when curl calls it. This chapter proved something harder: that a browser can hold a session, lose it on reload, rebuild it from a cookie, and recover from an expired token without the person using the app noticing. A gate on this material cannot be satisfied by a login that happened to work once. It has to show the same flow surviving a reload, a deliberate expiry, and a logout, because those are the three moments where client-side auth breaks in practice and where the failure looks like a random logout rather than a bug.

## How to read this gate

Each section states a claim and names the evidence that settles it. For client auth there are only two kinds of evidence, and neither is a screenshot of a working page. The first is the **Network tab**, where the order of requests tells you whether the refresh loop actually ran: a page load that shows 401 on `/api/auth/me` followed by 200 on `/api/auth/refresh` followed by 200 on the retried request is the whole mechanism in three rows. The second is **application state read from the browser**, meaning the AuthProvider's values and the storage areas, which prove what is in memory and, more importantly, what is not in localStorage.

A reviewer reads this page by reproducing the awkward cases rather than the happy path. They log in, reload the page, and watch whether the session survives. They wait for the access token to expire, or shorten the expiry to a few seconds, and watch the retry. They log out and try to open a protected route by typing its URL. They open DevTools, run `localStorage` and `sessionStorage` in the console, and confirm that neither contains a token. A demo that only shows the successful login is not evidence for this gate, because the failure modes are the subject.

Run your checks in the same browser profile you built in, then repeat the reload test in a private window. The private window proves that nothing about the session depends on a value cached somewhere you forgot about.

## Chapter 7 · Login and registration checklist (gate)

Do **not** open Chapter 8 until every box is ticked and the learning log answers are written below.

### Pages and routing

The routing boxes prove that the three screens exist as real routes, not as conditionals inside one component. Separate URLs are what make the OTP step shareable, bookmarkable, and testable, and they are what lets a reviewer open `/verify-otp` directly to check that it behaves without a login attempt in front of it.

- [ ] `/register`, `/login`, and `/verify-otp` routes work
- [ ] The register, verify, login flow completes in the browser
- [ ] Role-based redirect after login sends a cook and a diner to different places
- [ ] Login shows an error for a wrong password and for an unverified user

The third box uses the stored role values `vendor` and `customer`, where a vendor is a cook who owns a Kitchen and a customer is a diner. Check that your redirect reads the role from the login response or from `/api/auth/me` rather than from a form field, because a client that decides the destination from something the user typed is not making an authorization decision at all.

The fourth box is the one that separates two error states that a rushed implementation merges. A wrong password and an unverified account are different problems with different fixes, and the API already returns 401 and 403 for them. The evidence is two login attempts and two distinct messages on screen; a page that prints "Login failed" for both has thrown away the information the server was careful to send.

### Auth state

These boxes are about one source of truth. Auth state read from three components that each keep their own copy drifts the first time a token rotates, and the symptom is a header that shows a logged-in user beside a page that redirects to login.

- [ ] `useAuth` or `AuthProvider` manages the user and the access token in memory
- [ ] Boot refresh restores the session on a page reload, or the limitation is documented and fixed
- [ ] Logout clears state and blocks protected routes

The proof for the first box is that every consumer reads the same values: add a temporary render of `user` and `isLoading` in the header and on a protected page, then log in and watch both update from one login call. The second box is proved by a reload with the Network tab open, which should show a refresh request before any protected request succeeds. The third is proved by logging out and then pressing the browser's back button, which must not restore the previous page's protected content from cache.

If boot refresh is not implemented, the box is not ticked by explaining that it is hard. It is ticked by writing down the limitation in your learning log and fixing it, or by demonstrating that a reload lands on login with no stale state left behind.

### API client

The API client boxes are about one place where the token is attached and one place where it is refreshed. Every later chapter calls this helper, so a mistake here repeats on every screen in the course.

- [ ] `apiFetch` attaches `Authorization: Bearer` when authenticated
- [ ] A 401 triggers one refresh and then a retry, tested or verified with a short expiry
- [ ] `credentials: 'include'` is set on the refresh request
- [ ] The access token is **not** in localStorage or sessionStorage

The Network tab is the evidence for the first three. Confirm the header on an authenticated request, then shorten `JWT_ACCESS_EXPIRY` in `server/.env`, restart the server, and watch the 401, the refresh call, and the retried request succeed in that order. Two details are easy to get wrong and easy to see once you look: the retry must happen once rather than in a loop, and the refresh call must carry `credentials: 'include'` or the httpOnly cookie never leaves the browser, which gives a silent 401 that looks like a server bug.

The fourth box is checked in the console rather than the Network tab. Run `Object.keys(localStorage)` and `Object.keys(sessionStorage)` and confirm no token appears. The reason is the one Chapter 7 opened with: anything in web storage is readable by any script on the page, so a single injected script exfiltrates a long-lived credential, while a token held in a variable dies with the tab.

### Protected routes

These three boxes are the client-side mirror of `requireAuth`, and they are intentionally weaker than it. A protected route hides a page from someone who is not logged in; it does not protect data, because the browser is not a trust boundary.

- [ ] `ProtectedRoute` redirects unauthenticated users to login
- [ ] The vendor stub page is reachable only when logged in as a vendor, if a role prop is used
- [ ] `isLoading` prevents a redirect flash during boot

The evidence for the first and third boxes is a reload of a protected URL with the Network tab open. During boot, `isLoading` is true and the route must render nothing or a loading state; if it redirects immediately, the refresh has not finished and a logged-in user is thrown to the login page on every reload. That flash is the most common report in this chapter, and it is a rendering order problem rather than an auth problem.

The second box is worth testing from both sides: log in as a customer, type the vendor URL directly, and confirm you are not shown the page; then log in as a vendor and confirm you are. Chapter 8 will show why this check is convenience rather than security, since the server still has to reject a request from a diner who forges the call outside the browser.

### Integration

The integration boxes connect the client to the API you built in Chapter 6 and prove the two agree about cookies and origins.

- [ ] Seed `vendor-a` and `customer-a` log in through the UI
- [ ] CORS allows credentials from the Vite origin
- [ ] No new server auth endpoints are required beyond Chapter 6, though a `Set-Cookie` header is fine

The first box is the end-to-end proof of the whole chapter, and it is worth running for both accounts because the role redirect is part of the flow. The second box is the one that fails with a message most people misread: when CORS is configured with a wildcard origin and credentials, the browser refuses the response even though the server answered 200. The fix is an explicit origin plus `credentials: true` on the server, and the console is where the mismatch is named.

The third box is a guardrail rather than a task. If you find yourself inventing a new endpoint to make the client work, the client is probably fighting a contract that already passed curl in Chapter 6, and the right move is to fix the client.

### Prior gates

These boxes carry earlier proof forward. Auth is the first module that depends on everything below it, so a regression here usually means a change made in this chapter reached back into a model or a route it should not have touched.

- [ ] The Chapter 6 auth API still passes its curl tests
- [ ] Chapter 5 models and seed data are intact
- [ ] Explain why the access token lives in memory rather than localStorage
- [ ] Explain the 401 refresh loop step by step
- [ ] Explain the difference between `ProtectedRoute` and the server's `requireAuth`
- [ ] Explain what happens on a full page reload

The first two boxes are re-runs, not recollections: paste the 6.18 curl flow again and confirm the status codes have not moved, then open Compass and confirm the seed accounts and their `isVerified` flags are what Chapter 5 left behind. A client change that required a server change is not automatically wrong, and it is worth knowing about, because Chapter 8 builds ownership checks on the exact payload shape this chapter consumes.

The four explanation boxes are one argument told from four angles. The access token lives in memory because storage readable by scripts turns any injected line into a stolen session, and the price is a refresh on reload. The refresh loop is a sequence: a request returns 401, the client calls `/api/auth/refresh` with credentials so the httpOnly cookie travels, receives a new access token, stores it in memory, and retries the original request once. `ProtectedRoute` decides what to render and can be bypassed by anyone with the API's address, while `requireAuth` decides what to return and cannot. A full reload tears down memory, so the boot sequence refreshes before rendering anything protected, which is exactly why `isLoading` exists.

### Learning log · write now

Answer **in your own words** in the fields below. Each answer should name the component, header, or storage location involved.

1. **Token storage:** Where do the access and refresh tokens live in your implementation? Why?

2. **Refresh loop:** Describe the network sequence when the access token expires mid-session.

3. **Register flow:** Describe the UX path from register to the first authenticated page. Was there any friction?

4. **Role redirect:** How does login decide between the cook destination and the diner destination?

5. **CORS and cookies:** What server CORS changes were needed for the refresh cookie?

6. **Failure test:** Describe one UI error state you tested (wrong password, unverified account, and so on).

7. **Chapter 8 preview:** Why is login not enough to PATCH another kitchen's profile?

8. **Reload test:** Does the session survive a hard refresh? If it did not at first, what did you fix?

The answers a reviewer values most are two and eight, because they describe mechanisms rather than outcomes. On question two, a good answer lists four requests in order and says which one carried the cookie. On question eight, a good answer names the boot sequence and the state that prevents a redirect before the refresh resolves.
