# 6.20 Checklist and learning log
> **[Gate]** · Chapter 06 · Authentication API

This is the **gate** for Chapter 6. Tick every box honestly and answer the learning log below before opening Chapter 7.

Chapter 6 is the first module in this course where a mistake is a security problem rather than a broken page. A wrong status code in the cart API annoys a diner; a password hash returned in a login response, or a JWT signed with a secret that also lives in the client, hands an attacker a key. That is why this gate leans on evidence you can reproduce with curl and Compass instead of on a demo that looks correct on screen. Every box below is checkable by someone who did not watch you build it, and that is the standard this chapter is held to.

<BigWordAlert term="JSON Web Token (JWT)" plainEnglish="A compact signed string encoding user id and expiry, sent in the Authorization header on API calls." whyItMatters="Sufra access tokens prove identity for cart and kitchen routes without a server-side session lookup." />

## How to read this gate

Each section pairs a claim with the evidence that settles it. For this chapter, three kinds of evidence carry the weight. A **curl transcript** proves the HTTP contract, because it shows the request, the status line, and the response body without a browser interpreting any of it. A **database read** in Compass or mongosh proves what was stored, which is where password and refresh-token questions are actually decided. A **written explanation** proves that you understand why the arrangement resists an attack, and that is the part a reviewer will push on, because a correct implementation copied from a lesson and a correct implementation understood look identical until someone changes one requirement.

Read the sections in order, and treat the order as a story: configuration that refuses to start without a secret, endpoints that behave predictably, storage that never keeps a readable password, and tests that prove all three. A reviewer checking your submission runs the curl commands in 6.18 themselves, opens the Users collection to read two fields, and asks you one question about tokens. If any of those three fails, the gate does not pass, no matter how many boxes are ticked.

Run your checks against a fresh server process. A dev server that has been running since you wrote the register handler can still answer with code you have since replaced, and the most confusing way to fail this gate is to pass it against a stale process.

## Chapter 6 · Authentication API checklist (gate)

Do **not** open Chapter 7 until every box is ticked and the learning log answers are written below.

### Environment and config

These four boxes are about failing early. A server that starts without `JWT_SECRET` will sign tokens with `undefined`, and those tokens are valid to nobody and impossible to verify tomorrow. A startup that refuses to boot is a louder and much cheaper failure.

- [ ] `JWT_SECRET`, `JWT_ACCESS_EXPIRY`, `JWT_REFRESH_EXPIRY` in `.env.example`
- [ ] `JWT_SECRET` in local `.env`, not committed
- [ ] `config.js` fails startup if `JWT_SECRET` is missing
- [ ] bcrypt and jsonwebtoken in package.json

The evidence for the first two is a pair of files read side by side. `.env.example` is committed and lists the names with safe sample values, while `.env` holds the real secret and never appears in `git status`. The evidence for the third box is a deliberate failure: rename or comment out `JWT_SECRET` in `.env`, start the server, and watch it exit with a message that names the variable. Restore the value afterwards, and note the message in your learning log. A config module that logs a warning and continues has not passed this box, because a warning is invisible in production.

### Endpoints

The endpoint boxes are the HTTP contract of the auth module, one line per route. They are written as "route, status, behaviour" because all three parts are the contract: a register route that returns 200 instead of 201 breaks a client that checks for 201, and a login route that returns 401 for an unverified account instead of 403 hides the exact problem from the person trying to log in.

- [ ] POST `/api/auth/register` returns 201, stores a bcrypt hash, issues an OTP, and returns 409 on a duplicate email
- [ ] POST `/api/auth/verify-otp` sets `isVerified`, and a wrong OTP returns 400
- [ ] POST `/api/auth/login` returns 200 with tokens, 401 for a bad password, and 403 for an unverified user
- [ ] POST `/api/auth/refresh` issues a new access token, and an invalid refresh returns 401
- [ ] GET `/api/auth/me` uses `requireAuth`, returns 200 with user and profile, and 401 without a token

The proof for each line is a curl call and the status line it prints. Two of them are worth reading carefully rather than glancing at. The 409 on duplicate registration is the only box that proves your unique index or your pre-check actually works, and it must be tested with an email that already exists in the database, not with a fresh one. The 403 on login for an unverified user is the box that proves `isVerified` gates the flow; if you get 401 there instead, your login handler is checking the password before it checks verification, or it is not checking verification at all. For a cook who registered on a phone in Gaza City and never opened the OTP screen, that difference is the difference between stale access and clear guidance.

GET `/api/auth/me` earns its place for a different reason. It is the smallest protected route in the course, so it isolates the middleware from the business logic: if `/me` works with a token and returns 401 without one, then `requireAuth` reads the header, verifies the signature, and attaches the payload correctly, and any later route that misbehaves is misbehaving for its own reasons.

### Security

These five boxes are the reason this chapter gets its own gate. Each one is about what you store or return, and none of them can be verified by watching a browser.

- [ ] No `passwordHash` in any API response
- [ ] `refreshTokenHash` stored hashed on User, not a plain refresh token
- [ ] `role` in the access JWT matches `User.role`
- [ ] Only the `vendor` and `customer` roles are accepted on register
- [ ] OTP dev delivery is documented (console or a dev-only response field)

The first box has a mechanical test: run login, verify, refresh, and `/me`, then read all four response bodies and search them for `passwordHash`. The correct result is zero hits, and the most common failure is a handler that spreads the whole Mongoose document into the response. The second box is checked in Compass, where the User document must show a long hash under `refreshTokenHash` and no field holding the token in readable form; a readable refresh token in the database turns a leaked backup into permanent sessions for every account it contains.

The role line needs one clarification that the shared chapters assume. The stored role values are `vendor` and `customer`, and in Sufra a vendor is a cook who owns a Kitchen while a customer is a diner. The tokens, guarded routes, and seed accounts use those two strings throughout the course, so check the values rather than renaming them; the third box is asking whether the claim inside the token equals the value on the document, and the fourth is asking whether your register handler rejects a role it does not recognise instead of trusting whatever the request body sent.

### Testing

The three testing boxes prove that the contract was exercised rather than assumed. A route that has only ever been called with valid input has not been tested; it has been demonstrated.

- [ ] The full curl flow is documented (6.18)
- [ ] Negative tests pass (401, 403, and 409)
- [ ] Seed `vendor-a` login works after bcrypt alignment

The transcript for the first box is evidence only if it shows the request and the response together, which is why the course asks for `curl -i` output rather than a screenshot of a 200. The second box is where learners discover that their error responses leak detail: a 409 that includes the existing user's id, or a 403 that says whether the email exists, is a smaller problem than a leaked hash but still a problem. The third box closes a loop that opens in Chapter 5, where seeded users were written before hashing existed; if `vendor-a` cannot log in, the seed script and the register handler disagree about how a password becomes a hash, and Chapter 7's browser login will fail for every account created before the fix.

### Prior gates

These boxes connect this chapter to the two it stands on. The first three are inherited proof; the last five are the reasoning you should already have without notes.

- [ ] Models and seed from Chapter 5 are intact
- [ ] The health route still works
- [ ] No React auth UI yet, API only
- [ ] Explain bcrypt versus plain storage
- [ ] Explain access versus refresh token roles
- [ ] Explain 401 versus 403 in this chapter
- [ ] Explain why a JWT payload must stay minimal
- [ ] Explain the benefit of refresh rotation

"Intact" means you did not loosen a schema to make auth pass: if `passwordHash` became optional, or `isVerified` was dropped to simplify a query, the models are no longer the ones Chapter 5 gated. The health route is checked for the same reason it was checked in Chapter 2, because it is the cheapest signal that the boot path still works after you added a config module, a database connection, and a router. "No React auth UI yet" keeps the boundary clean: an API proven with curl is a contract, while an API half-wired to a form is a debugging session where the client and the server can both be wrong at once.

The five explanation boxes map onto one question each, and the answers share a shape. bcrypt is a deliberately slow one-way function with a per-password salt, so a leaked database yields guesses rather than passwords, and the risk that remains is a weak password that a guesser eventually finds. An access token is short-lived and sent on every request, while a refresh token is long-lived, stored hashed, and exchanged only at one endpoint, which is what keeps the blast radius of a stolen access token to minutes. 401 means the server does not know who you are; 403 means it knows and you may not act. A minimal payload keeps the token small and keeps sensitive data out of a string the browser can decode. Rotation turns a stolen refresh token into a race that the legitimate client usually wins, and it gives you a place to invalidate a session.

### Learning log · write now

Answer **in your own words** in the fields below. Each question asks for a trace, a comparison, or a decision, and a good answer names the field, route, or header involved.

1. **Register flow:** Step through register from curl to the documents created in Compass.

2. **Password security:** How does bcrypt protect you if MongoDB is leaked? What is still at risk?

3. **JWT payload:** Paste the decoded payload structure (redacting `sub` is fine). What claims are there, and why those?

4. **Refresh design:** How is the refresh token stored server-side? What happens on logout or rotation?

5. **OTP:** How is the OTP delivered in development? How would you change it for production email?

6. **Failure test:** Describe one negative curl test and the status code it returned.

7. **Chapter 7 preview:** Where will the access token live in the browser, and why not localStorage?

8. **requireAuth:** What does `req.user` contain, and who consumes it in later chapters?

The answers worth writing are the ones a reviewer could check. On question four, "stored hashed" is a start, and the answer the course wants also says what is compared with what at refresh time and what happens to the old hash. On question eight, `req.user` should be described as the verified payload, which means `id` and `role` rather than a full document, and the consumers are the ownership checks in Chapter 8 and the cart routes in Chapter 17.

## Troubleshooting

| Blocker | Look at |
|---|---|
| 401 on a valid token | `JWT_SECRET` mismatch, or clock skew between signing and verifying |
| 403 on seed login | `isVerified` is false; re-seed, or verify the account first |
| 404 on auth routes | The mount path in 6.11, and whether the router is mounted before the 404 handler |
| bcrypt compare false | A seed that stored a plain password; re-hash it through the register path |

Read the table by symptom first and cause second. Each row names a place to look rather than a fix, because the fix depends on which of the two causes you find, and a 401 from a secret mismatch looks identical to a 401 from an expired token until you decode the token and check the signature.
