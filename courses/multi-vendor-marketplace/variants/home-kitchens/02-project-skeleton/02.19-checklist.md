# 2.19 Checklist and learning log
> **[Gate]** · Chapter 02 · Project skeleton

This is the **gate** for Chapter 2. Tick every box honestly and answer the learning log below before opening Chapter 3.

A gate is not a memory test and it is not a formality. It is the point where the course asks you to prove that the work you believe you did is the work that actually exists on disk. Every box on this page maps to something a mentor could check from outside your head: a command with output, a screen with a response, or a written answer in your own words. If you cannot show that artefact, the box stays unticked, and finding out now is far cheaper than finding out in Chapter 7 when login pages assume a client folder that was never committed.

## How to read this gate

Treat each section as a claim and a proof. The claim is the ticked box; the proof is the thing you can show. Three kinds of proof appear here, and they are not interchangeable. A **command output** proves that a program behaves as described, and it can be reproduced by anyone with your repository. A **browser observation** proves that two programs agree with each other, which no terminal alone can show. A **written explanation** proves that you understand why the arrangement works, which is the part that survives after you close the laptop and which a review will actually probe.

A reviewer reads this page in the order it appears. They run the commands from the repository root rather than trusting a transcript, they open the browser with the server stopped to see the error state for themselves, and they read your learning log looking for one specific thing: whether your explanation mentions the mechanism or only the outcome. "It works" is an outcome. "The client reads `VITE_API_URL` and sends a browser request that CORS allows because the server lists the Vite origin" is an explanation, and it is what the answers in this course are training you to write.

Self-review is the same activity done honestly. Close your old terminals, open a fresh one at the repository root, and run each command as if you had never seen the project. Memory is the enemy here: a project that worked yesterday because the server was still running in a lost terminal will fail this gate, and the failure is information you want now.

## Chapter 2 · Project skeleton checklist (gate)

Do **not** open Chapter 3 until every box is ticked and the learning log answers are written below.

### Repository and structure

The first four boxes prove that the boundary you created in 2.8 still holds. A repository is only useful if everything that belongs with the product is inside it and nothing private has leaked in, and both halves of that statement can be checked with one command each.

- [ ] Git repository exists at your marketplace project root, separate from the course content folder
- [ ] Root `.gitignore` excludes `node_modules/`, `.env`, and build output
- [ ] `git log --all -- "**/.env"` returns **empty** (no env file ever committed)
- [ ] Root `README.md` documents how to run server and client in two terminals

The third box is the one learners skip because it looks like a formality, and it is the only box that searches history rather than the current tree. `git log --all` walks every commit on every branch, and `-- "**/.env"` filters that history to commits that touched a file named `.env`. Empty output is the proof that no secret was ever recorded, which matters because deleting a file in a later commit does not remove it from the commits before it. If the command prints a commit, rotate the secret before you tick anything else.

### Server

The server boxes prove that the API exists as a program with a clear boot path, not as a pile of files that happen to contain JavaScript. The separation between `app.js` and `server.js` is the item people question most, so make sure your own answer to it is the one in the learning log and not a paraphrase of the instructions.

- [ ] `server/package.json` has `dev` and `start` scripts
- [ ] `server/src/app.js` creates the Express app, uses JSON middleware, and exports the app without listening
- [ ] `server/src/server.js` starts the server on `process.env.PORT || 5000`
- [ ] Module folders exist: `auth`, `stores`, `products`, `cart`, and `orders`
- [ ] `server/src/shared/` exists
- [ ] `npm run dev` in `server/` runs without crashing
- [ ] `curl -i http://localhost:5000/health` returns **200** with JSON containing `"status":"ok"`

Two folder names in the fourth box carry Sufra's meaning even though the shared chapters keep their original labels: `stores` is where a kitchen profile lives, and `products` is where a kitchen's dishes live. Keep the names the chapters use, because every later file path depends on them, and read them through the domain rather than through the label.

The last box deserves a closer look at what you paste into the learning log. `curl -i` prints the response headers before the body, so the proof is the status line that reads `HTTP/1.1 200 OK` followed by a JSON body containing `"status":"ok"`. A 200 with an HTML body means you reached a dev server that is serving a page instead of your route, and a 404 means the router was mounted at a different path. Read the first line before you read the body.

### Client

The client boxes prove that the four-folder convention landed and that the UI is wired to the API rather than to a lie. The distinction between a hardcoded success message and a live response is the single most important idea in this section, and the only way to demonstrate it is to run the app twice.

- [ ] Vite React app in `client/` with `pages/`, `components/`, `api/`, and `hooks/`
- [ ] React Router renders Home at `/`
- [ ] `client/.env.example` documents `VITE_API_URL`
- [ ] `client/src/api/client.js` reads the base URL from env, with no hardcoded localhost in components
- [ ] `npm run dev` in `client/` runs without crashing
- [ ] Home page displays **live** health status from the API when the server is running
- [ ] Home page displays an **error state** when the server is stopped, not a hardcoded success

Run the last two boxes as one experiment, back to back. With both terminals running, reload the page and confirm the status appears. Then stop the server, reload again, and confirm the page says something has failed instead of showing the previous message. A page that keeps its success message while the API is down is worse than one that breaks, because it teaches a diner or a cook to trust a signal that is no longer connected to anything.

### Integration

The integration boxes are about the two programs agreeing. Everything up to here can be true while the pair still fails, because a client can be correct and a server can be correct and the request between them can still be blocked.

- [ ] CORS is configured so the browser can call the API from the Vite origin
- [ ] Browser Network tab shows a successful `GET` to `/health` with 200
- [ ] End-to-end verification from **2.16** is completed

The Network tab is the reviewer's evidence for this section, and it is worth knowing how to read it. Open the request for `/health`, then look at three things: the status code in the headers panel, the JSON in the response panel, and the absence of a red CORS message in the console. A CORS failure shows as a request that never produced a response the page could read, and the console names the origin that was refused, which is why the fix belongs on the server rather than in the client.

### Understanding (self-check, explain aloud)

These four boxes have no command behind them, and they are the ones that predict how Chapter 3 will go. The point of saying them aloud is that speech refuses the shortcuts writing allows: you cannot half-recall an explanation at conversational speed.

- [ ] I can explain **module-based** versus layer-based structure and why this course chose modules
- [ ] I can explain what runs in the **browser** versus what runs in the **Node server**
- [ ] I can explain why **`app.js` and `server.js` are separate**
- [ ] I can point to where **auth** and **dish** code will live in my tree

Explain each one to someone who is not a developer, or write it in the learning log as if you were. If the explanation depends on a word you cannot define, such as CORS or middleware, define that word in the same answer. That habit is what a technical review is testing for.

### Learning log · write now

Answer **in your own words** in the fields below. Answers that restate the checklist items are not answers; each one asks for a reason, a trace, or a prediction.

1. **Draw or paste your folder tree** (server + client) as it stands after Chapter 2. Annotate one sentence per module folder describing its future job.

2. **Why did this course require module-based folders instead of layer-based?** Use the "add a discount code" or "add a dish feature" argument, not "because the course said so."

3. **What happens at runtime when a user opens your Home page?** Trace the path: browser, React, fetch, Express, response. Mention ports and CORS.

4. **Why must secrets like `MONGODB_URI` (coming in Chapter 4) live only in `server/.env` and never in the React app?**

5. **What did you verify in the failure-mode test with the server stopped?** Why is error UI important even for a health check demo?

6. **What will change on `/health` in Chapter 4 when MongoDB connects?** Speculate based on the course outline, in one paragraph.

Question four is the one most often answered with a version of "it is safer", and the answer the course is looking for is mechanical: Vite inlines every `VITE_`-prefixed value into the bundle it serves to the browser, so anything you put there becomes public the moment someone opens the site, and a connection string in the bundle hands every reader the ability to read and write your database.
