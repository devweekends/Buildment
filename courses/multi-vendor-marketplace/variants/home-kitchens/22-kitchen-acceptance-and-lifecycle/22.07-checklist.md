# Lifecycle gate and timeline evidence

The lifecycle is built. Transitions are conditional and atomic, the deadline is an instant with a job behind it, a rejection returns capacity and asks for a refund, and the board shows a cook what to do next. This gate asks you to show that those parts work together on one real purchase and that the database records the whole story. A screenshot of an Accept button is not evidence. Order rows, timeline sequences, claim states, a refund object in Stripe test mode and a named refusal are.

Set up one paid attempt from one checkout, with two kitchens cooking for the same 13:00 delivery window. Use the seeded kitchen in `Asia/Gaza` for the cook who answers and a second kitchen in the same zone for the one who does not. Pay with a Stripe test card after M20 confirms both claims, and record the attempt ID, both order IDs, both window IDs, both claim IDs, both `acceptBy` instants and the two paid shares before you touch the board.

## The order the cook accepted

Open the board as the first cook and act through the whole path: accept, start cooking, mark ready, hand off, then deliver through the confirmation endpoint. The timeline should hold six events, from `placed` at sequence 1 to `delivered` at sequence 6, each with `fromStatus`, `toStatus`, `actorType`, `actorId` and a UTC `occurredAt`.

Check the acceptance event against the stored deadline. The order should show `acceptBy` before the accept timestamp, and the `acceptByRule` value should match the arithmetic you can repeat by hand from the window start, the preparation lead and the response cap. Then check that no event has a client-supplied timestamp, that the sequences increase by exactly one, and that `timelineSeq` equals the number of events. A missing or repeated sequence fails this section even if every screen looked right.

## The order nobody answered

Do not tap anything on the second kitchen's order. Let the stored `acceptBy` pass, then check that the deadline job rejected it. If the worker was stopped during that interval, start it and run the overdue scan instead, and say in your notes which path did the work and why the result is the same. The order should be `rejected` with reason `NO_RESPONSE`, actor type `system`, and exactly one new timeline event after `placed`.

Then read the other two records. The claim on that kitchen's dated window should be `released` with reason `ORDER_REJECTED`, and `remainingUnits` should have increased by the order's claimed load units, once. The refund request should exist with the frozen paid share, and the Stripe test dashboard should show one partial refund against the original PaymentIntent for that amount. The sibling order must still be `delivered` or whatever state it reached, with its claim still `confirmed` and its own timeline untouched.

Replay both paths. Run the deadline job again and run the rejection route once by hand. The timeline must stay at two events for that order, the counter must not move, and Stripe must show one refund. Then confirm the receipt: the original total, the refunded share and the remaining paid amount, with no line that says the whole purchase was cancelled.

## The refusals

Four refusals belong in the evidence, and each one needs the response body, not just the status code.

Ask the accepted kitchen's cook to mark `ready` on an order that is still `placed`. Ask the ignored kitchen's cook to accept an order whose deadline has passed. Ask the second kitchen's cook to act on the first kitchen's order. Ask a diner token to call the transition route. Record the status the server used for each, and the current state it returned. The first two should be 409 with the order's actual status and its allowed actions. The third and fourth should be 403, and the target order must be byte-identical afterwards.

Save one hash or full document dump of an order before and after a refused request. That comparison is what proves a rejected call wrote nothing, including no timestamp and no sequence increment. A test that only asserts the status code cannot distinguish a clean refusal from a refusal that already appended an event.

## Gate checklist

- [ ] One paid attempt with two kitchen orders, both claim IDs and both `acceptBy` instants recorded.
- [ ] Accepted order timeline has six events with sequences 1 to 6 and UTC timestamps, and no client-supplied time.
- [ ] `acceptBy` matches a hand calculation from window start, preparation lead and response cap, and the winning rule is stored.
- [ ] Ignored order is `rejected` with reason `NO_RESPONSE`, actor type `system`, and one new event.
- [ ] Rejected order's claim is `released` and `remainingUnits` increased by the stored units exactly once after a replay.
- [ ] One refund request for the frozen paid share, matching a partial refund in the Stripe test dashboard, with no second refund after a retry.
- [ ] Sibling order, claim and timeline unchanged by the rejection.
- [ ] Illegal transitions return 409 with current status and allowed actions; another kitchen and a diner token get 403.
- [ ] Board groups orders by kitchen window and shows deadline labels in the kitchen's zone, with no accept action after the deadline.
- [ ] `docs/order-lifecycle-decisions.md` holds both rows, the replay results and the refused-request evidence.

## Learning log

1. Which filter condition decided your late acceptance race, and what did the losing request receive instead of a write?
2. Why is `acceptBy` stored as a UTC instant with a policy version, and what would break if the board recomputed it from the phone's clock?
3. Your rejection path stops between the status change and the refund. What does the repair scan read, and how does it avoid a second release or a second refund?
4. Which two records did the ignored order change besides its own status, and which record proves the sibling order was not affected?
5. What did the board offer on an order past its deadline, and where does that decision live in the code?

## What this gate does not prove

The diner still has to refresh to see any of this, because pushed updates arrive in M23. The capacity claim races under parallel checkout were proven in M19, and the refund ledger arithmetic was proven in M20, so this gate checks only that the lifecycle reaches those systems with the right identities. Nothing here demonstrates a load test, a deploy, or a stream that survives a dropped connection.

Write the two rows into `docs/order-lifecycle-decisions.md` before you close the gate, including the times you froze the clock and the exact commands you ran. A reviewer should be able to rerun the deadline job from your notes and reach the same rejected order, the same released units and the same single refund. If any of those three disagree, leave the gate open and fix the path before M23 adds a stream on top of it.
