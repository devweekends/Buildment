# Query plan and gate

The browse API now answers Lina's real question: which kitchens can still offer at least one suitable dish for the selected dated interval? The pipeline starts with matching open windows, removes closures and kitchens outside the area, joins active dishes from the same kitchen, computes each dish's cutoff, applies weekday and dietary filters, then pages the remaining cards. This gate asks for two kinds of evidence: correct negative results and a query plan that shows the database is not scanning everything for one lunch.

Use the 13:00 fixture at a fake server time of 11:31. Umm Yousef has a 12:00 general cutoff, a 20-minute travel buffer, maqluba at 90 preparation minutes and falafel at 30. The public card should include falafel with an `orderableUntil` of 12:00 and omit maqluba, whose deadline was 11:10. A second kitchen with no area match should be absent. A closed window and a wildcard close-today exception should each remove a candidate. A wrong-kitchen dish must not appear under any other card.

## Recap the safety boundary

The API uses server time for one page and returns that instant to the client. It does not reserve units. The card's capacity hint can become stale before Lina taps. Cart rechecks the dish and dated window; M19 checkout uses a conditional claim and a fresh cutoff decision. Explain this distinction during the review. A browse test that returns the right card does not prove safe checkout, while a checkout test cannot excuse a browse page that knowingly offers a late dish.

The response must be small and public. Show a JSON example with kitchen and window IDs, UTC interval, display name, dish price and cutoff, and the server instant. Check that it does not contain embedded claims, attempt IDs, cook email, private address or another diner's order. A response mapper or final projection should make the allowlist obvious. If a new private field is later added to Kitchen or DeliveryWindow, it should not appear automatically on this endpoint.

## Inspect the plan with a realistic fixture

Seed enough kitchens, windows and dishes that a collection scan would be visible. Run the exact aggregation with `explain('executionStats')` in the learner MongoDB version. Save the pipeline, indexes, plan and response time in `docs/EVIDENCE.md`. Look for an indexed search on the selected `startAt` and `endAt` pair, an indexed kitchen lookup, and a dish lookup that uses `kitchenId` and status. Record documents examined and returned; one application call can still do too much database work if joins lack indexes.

Run the same plan after doubling the fixture size. The numbers need not be identical, but the query should remain bounded by one selected interval rather than reading every historical window. If the plan scans all windows, inspect the leading `$match` and index before adding a cache. If the dish join examines every dish for every kitchen, inspect the `{ kitchenId: 1, status: 1 }` index. If the exception lookup is expensive, check the kitchen-local-date-rule key index from M9. Do not claim an index is used merely because it is declared in a schema; show the actual plan.

## Gate checklist

- [ ] A request selects an existing dated UTC interval and normalized diner area; malformed inputs receive field feedback.
- [ ] Closed, full, generally late and wildcard-exception windows are absent from orderable results.
- [ ] Only open kitchens serving the area join, and each returned dish belongs to that exact kitchen.
- [ ] Maqluba closes at 11:10 while falafel remains until 12:00 in the dated lunch example.
- [ ] Kitchen-local weekday and dietary filters run before pagination and remove cards with no matching dishes.
- [ ] A page cursor uses stable window IDs and rejects reuse after filters change.
- [ ] The response contains `serverNow` and per-dish dated cutoff but no private claim, owner or diner fields.
- [ ] One aggregation serves a page; the saved `explain()` output shows which indexes and document counts it used.
- [ ] Cart and checkout still perform fresh validation; browse is not treated as a hold.

If a kitchen disappears unexpectedly, follow the pipeline one stage at a time and count rows after each. A wrong area may be a normalization mismatch. A wrong date may be a kitchen-local weekday calculation from the server host's zone. A wrong cutoff may come from `prepMinutes`, the snapped travel buffer or an incorrectly resolved window start. A short page may mean `$limit` ran before the final dish filter. A privacy leak may mean the route returned a raw Mongoose document after a safe aggregation projection was removed. Name the failed stage before changing code.

The purpose of this gate is to make a public browse answer useful without letting it become a false payment guarantee.
