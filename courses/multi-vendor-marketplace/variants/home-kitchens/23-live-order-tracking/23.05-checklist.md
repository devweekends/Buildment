# Offline test and tracking gate

The feature is built and it works while you watch it. This gate is about the minute when you are not watching: the phone is offline, the cook keeps working, and the screen has to come back to the truth on its own. That is the evidence the roadmap asks for, and it is the evidence a reviewer will ask to see first, because every part of this module can look correct in a video where nothing goes wrong.

If M25 has not happened yet and the local app is all you have, run the test locally and say so in your notes. Use a real order from a real paid attempt, in the 13:00 window for a kitchen in `Asia/Gaza`, with two kitchens in the purchase if you want the sibling case as well. Record the attempt ID, the order ID, the window ID, the claim ID and the `timelineSeq` before you start.

## The sixty second test

The order starts at `placed` with sequence 1, paid, with the cook's board open in a second window. Do not edit the database at any point in this test; every status change must come from the transition route so the timeline, the sequence and the publish all happen the way they will in production.

1. Note the current sequence and status on the diner's screen, and confirm the connection label reads "Live".
2. Put the diner's device offline. On a phone, airplane mode. In a desktop browser, the network panel's offline setting. Leave the page open and do not reload it.
3. Within the same minute, move the order twice from the kitchen board: accept and then start cooking, or start cooking and then mark ready, depending on where the order already sits.
4. Wait until at least sixty seconds have passed with the device offline.
5. Put the device back online and touch nothing else. Do not pull to refresh and do not press the manual refresh button.
6. Watch the screen and the network panel until the timeline catches up, then leave it for another minute to confirm the label settles.

The result you are recording has four parts, and all four must be true.

The final status on the screen matches the status in the database, including the estimate line, which should show a time in the kitchen's zone and not in UTC. The timeline contains every event from sequence 1 up to the current sequence, in ascending order, with no repeated sequence and no repeated status text. The catch-up happened without a page reload and without a manual refresh. And the connection label told the truth during the gap: it stopped claiming "Live" within the watchdog interval and showed a time that counted up until the data arrived.

Save four artefacts: a screen recording of the phone with the network panel or the airplane mode toggle visible, the server log lines for the reconnect and the snapshot, the order document dump after the test, and a one paragraph note naming the mechanism that repaired the gap (a reconnecting stream, a gap detected by sequence, or the silence watchdog falling back to the timeline query). If two mechanisms could have done it, say which one fired first and how you know.

## No duplicates, no reordering

The duplicate check is not decorative. The snapshot and the buffered delta can both contain the same event, and a client that applies frames in arrival order without comparing sequences will show "ready" twice and move the estimate backwards when the older frame lands. Both are visible in a screenshot of the timeline, which is why the check is on the rendered list and not on the network log.

Take one screenshot of the whole timeline and read it out loud. Then count the events in the rendered list and compare the number to `timelineSeq`. They should be equal, because every committed transition appends exactly one event. If the rendered list has more, the client is not dropping duplicates. If it has fewer, the client applied a snapshot and then discarded a delta it still needed, which is the more dangerous of the two failures.

Run the same test twice on the same order by advancing it once more with the device offline. The second run should behave the same way, and the timeline should still be a clean ascending sequence. A test that passes once and corrupts the second time is telling you that some state survived the first catch-up and was not reset.

## The isolation test

The offline test proves the diner receives what is theirs. It says nothing about what they must not receive, so the second piece of evidence is the stream isolation test. It was written in 8.3 at `tests/authz/stream-isolation.test.js` as an expected failure, and this module is the owner that turns it into a normal test. It opens a stream as diner B, advances diner A's order, and asserts that B receives no events.

If your copy of that file went missing, write it now, before the gate closes, and record it failing against a deliberately unscoped handler first. A test that has never failed is a test you cannot trust. The assertion should cover the frame payload and the snapshot, because a leak can happen in either place: the publish path can be scoped correctly while the snapshot query forgets the diner filter, and the leak then only appears on connect.

Add the third case while you are there: a diner token asking for another diner's order timeline should get `404`, and the response body should not echo the order ID. That covers the fallback route, which is the part of the design most likely to be written quickly and forgotten.

## If a pub/sub message is lost

The viva question for this module is what happens when a Redis pub/sub message disappears. The answer is short, and it is worth practising until you can give it without notes: the diner sees an old status for a bounded time, and nothing is lost for good, because no message was ever the record.

Walk the failure through. The cook marks the order ready. `applyTransition` commits the status and appends the event with its sequence, and that write is durable before the publish is attempted. Then `publishOrderEvent` runs and the message is lost, because the API process lost its connection to Redis for a second, or a subscriber was reconnecting, or a process restarted between the publish and the delivery. The order document still says ready at sequence 4, and the timeline still explains how it got there.

Now the repair. If another transition follows, the next delta carries a sequence two or more beyond what the screen holds, and the client treats the jump as a gap and asks the timeline route for everything after its last sequence. If the phone reconnects for any reason, the new connection begins with a snapshot that carries the current status and sequence, so the gap never surfaces. And if no further transition happens at all, the silence watchdog treats ninety seconds without a frame as a reason to revalidate, which is exactly the case a gap detector cannot see.

That last sentence is the one to emphasise in a review. A missing message that is followed by another message is easy. A missing message followed by silence is the case that leaves a diner staring at "cooking" while the meal cools on the counter, and the watchdog is the only mechanism that finds it. Pair it with the fallback query and the worst case is bounded by the watchdog interval rather than by the rest of the evening.

```openquestion
prompt: A pub/sub message that carried the "ready" transition is lost while Lina's stream is open, and the cook advances nothing else for ten minutes. What does Lina see, and which two mechanisms bring the screen back in line?
minWords: 90
sampleAnswer: She keeps seeing "cooking" until the silence watchdog fires, then reads "last updated" with a time that counts up, which is honest about what the screen knows. The watchdog revalidates the timeline after her last sequence, and any reconnect sends a fresh snapshot carrying the current status and sequence. Neither path depends on the lost message, because the ready status and its sequence were committed to the order document before the publish was attempted.
```

## Gate checklist

- [ ] A paid order in a real DeliveryWindow, with order ID, window ID, claim ID and starting sequence recorded before the test.
- [ ] Sixty seconds offline recorded, with two status changes made from the kitchen board during the gap.
- [ ] Recovery without a reload or a manual refresh, and the screen matches the database status and estimate.
- [ ] Timeline has every sequence from 1 to the current one, ascending, with no repeats and the count equal to `timelineSeq`.
- [ ] Connection label stopped claiming "Live" during the gap and counted the elapsed time until data arrived.
- [ ] Stream isolation test passes: diner B receives no frame and no snapshot containing diner A's order.
- [ ] Another diner's order timeline returns `404`, and the timeline route returns `304` with the same `ETag` on an unchanged cursor.
- [ ] A written answer to the lost message question, naming the record, the snapshot, the gap check and the watchdog.
- [ ] `docs/stream-decisions.md` holds the transport choice, the validator rule and the repair paths.

## Learning log

1. Which mechanism repaired your offline gap first: the reconnecting stream, a sequence jump or the silence watchdog, and what in the logs proves it?
2. What did the connection label say at the moment the phone came back online, and what would it have said if you had shown "Live" whenever a frame was expected rather than received?
3. Why does the timeline query include the cursor inside the ETag, and what would a cache have done to your timeline if it did not?
4. Your publish call fails after a committed transition. What does the diner see, what does the cook see, and which of the two is wrong for longer?
5. What part of this feature survives a total Redis outage, and what part stops working until Redis returns?

## What this gate does not prove

The stream has not yet met a real proxy or a real host. M25 asks you to confirm that the deployed platform does not buffer the response, that the heartbeat survives its idle timeout, and that a restart with a diner connected gives a reconnect and a fresh snapshot rather than a blank screen. Nothing here is a load test either: the number of concurrent streams one API process can hold is a capacity question for M26, not a correctness question for this gate.

Write the four artefacts into `docs/stream-decisions.md` and keep the recording with the demo materials for M99. A reviewer should be able to replay your steps on a fresh order and see the same sequence of frames, the same gap and the same recovery. If the recovery only happens when you press refresh, the gate stays open, because the feature being graded is the one that works when nobody presses anything.
