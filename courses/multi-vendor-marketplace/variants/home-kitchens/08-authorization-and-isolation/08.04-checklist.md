# Isolation gate

Two cooks and two diners are seeded, the guards are registered, and the matrix exists. This gate asks one question in several forms: can a signed-in person reach a record they do not own, and when they are refused, do they learn something they should not?

Run the suite with a clean database, then run the two most important requests by hand in a terminal. A suite that passes while a manual request returns a full document means one of them is testing a different server.

## Prove the four boundaries

The cook boundary is the first. Cook B sends a dish edit for cook A's kitchen. Expect 403, an empty record, and an unchanged price when cook A reloads the dish. If the price moved, the handler wrote before it refused, and every other passing test in the suite is now suspect.

The diner boundary is the second. Diner B requests diner A's order. Expect 404, a body identical to a missing order, and no name, address or amount from the real record. Compare the two bodies directly rather than looking at them, because a difference in length is the leak.

The projection boundary is the third, and it is the one most teams skip. Cook A reads their own order and must not receive the diner's payment method or the platform's fee breakdown. Diner A reads their own order and must not receive the cook's phone number or an internal kitchen note. Both requests are allowed, and both can still leak.

The fourth boundary is the one you cannot close yet. The stream isolation test is written and marked as an expected failure. Name the module that owns it when you present the evidence, so nobody reads the skip as an oversight.

## Present it in five minutes

Show the matrix, then the failing line, then the passing suite. In that order, because the failure is the interesting part: it shows the check is doing work rather than being present by accident.

Then answer one question without notes. A cook asks why they cannot see the diner's phone number when they need to call about a handover. The strong answer separates the need from the field: the cook needs a way to reach the diner for one order, and the platform can provide a contact channel that does not hand over the diner's personal number to every cook who ever cooks for them. A weaker but acceptable answer is that the course's projection is deliberately narrow and that a contact field belongs to a later fulfilment design. The unacceptable answer is that the field is hidden in the app, because the app is not the boundary.

## Gate checklist

- [ ] `docs/authz-matrix.md` lists every protected action with a scope field and the test that proves it.
- [ ] Cook B's dish edit against cook A's kitchen answers 403, and a reload shows the price unchanged.
- [ ] Diner B's order read answers 404 with a body identical to a missing order.
- [ ] Cook B's order read against cook A's kitchen answers 404, not 403.
- [ ] Cook A's own order response contains no payment method and no fee breakdown.
- [ ] Diner A's own order response contains no cook phone number and no internal kitchen note.
- [ ] A diner token on a cook route and a cook token on a diner route are both refused by the role guard.
- [ ] No protected route loads a private record by an ID taken from the request body after the check.
- [ ] The stream isolation test exists as an expected failure and names Module 23 as its owner.
- [ ] `docs/EVIDENCE.md` holds the run summary, the two manual requests and the before and after rows.

If a crossed request returns 401, the route is missing the role guard or the guard is registered after the handler. If it returns 200 with a filtered object, the handler performed the write and then hid the result, which means the data changed and the refusal was cosmetic. If it returns 403 for a private record, revisit the policy in lesson 8.1 and decide whether the caller is allowed to know the record exists at all.

The two status codes are not an inconsistency to fix. A dish edit is refused with 403 because the menu already told the caller the dish exists. An order read is refused with 404 because that order's existence is private. A reviewer who asks you to make both codes the same is asking you to disclose one of those two facts, so answer with the policy rather than with the code.

## Learning log

Answer these in `docs/learning-log.md` with the request, the response and the database row that supports each answer.

1. Which field turned cook B's valid token into a refused request, and which route condition applied it?
2. Why does a refused read of another diner's order answer 404 while a refused edit of another cook's dish answers 403?
3. Name two fields you removed from the cook's order view and one request from the cook that still works without them.
4. What does the stream isolation test prove today, and what will it prove once Module 23 serves the event stream?
5. Where could a user-supplied identifier still change a record after the ownership check has passed, and how does your code prevent it?

The first answer should name `ownerUserId` and the scoped query rather than a middleware name. The third should describe a task the cook still completes, not only a field that is now hidden. If the fifth answer is "nowhere", look again at every handler that reads an ID from the body.

## What this gate does not prove

The suite proves the routes that exist. It does not prove that an aggregate endpoint avoids leaking counts, and it does not prove that an error handler in a future module keeps refusals quiet. Both are worth a sentence in the matrix file under known limits, so a later reviewer knows what to re-check.

It also does not prove the claim path. Claims are changed by the checkout service, and Module 19 owns those tests. This gate ensures that no person can change one through a user route, which is a different and smaller promise.

Commit the matrix, the tests, the evidence and the learning log together. Module 9 builds the kitchen profile and the weekly schedule on these guards, and Module 11 does the same for dishes. Every route those modules add comes with a matrix row, so the file you commit now is the one they extend.
