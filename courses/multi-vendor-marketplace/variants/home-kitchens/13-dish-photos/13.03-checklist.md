# Dish photo gate

This gate is not a tour of the upload form. It runs the four things a photo pipeline can get wrong, with real requests, and it asks you to show what the database and the storage folder look like afterwards. A screenshot of a card with a picture on it proves that one upload worked once. It does not prove that a stranger cannot upload, that a twelve megabyte file is refused, or that a receipt from last week still shows the food a diner bought.

Set up two cooks and one diner. Cook A owns Umm Yousef's Kitchen in `Asia/Gaza`, with maqluba at ninety preparation minutes and three load units, and falafel at twenty minutes and one unit. Cook B owns a smaller kitchen of her own with one dish and no photos. The diner has one delivered order from last Tuesday, whose maqluba line carries a snapshot with the old photo URL and the old public identifier. If your project has no order collection yet, create that fixture by hand and label it as a fixture in your evidence, so nobody mistakes a seeded receipt for a working checkout.

Keep the identifiers for A's kitchen, both dishes, both photos and the snapshot in one note. Every check below sends one of them with the wrong identity attached, and a reviewer will want to see the request next to the response.

## Walk the five failure paths

Each row of this table is one terminal command or one form submission. Run them in order and keep the response bodies. The statuses are the contract from lesson 13.2 and the module does not accept a different code for the same rule.

| Request | Expected |
|---|---|
| Upload a document renamed to `maqluba.jpg` | `400 UNSUPPORTED_TYPE`, no new asset, `photos` unchanged |
| Upload a 7 MB photo of the whole table | `413 PHOTO_TOO_LARGE`, no new asset |
| Upload a fifth photo on a dish that holds four | `409 PHOTO_LIMIT_REACHED`, the four stay and keep their order |
| Send cook B's token with cook A's dish identifier | `403 NOT_KITCHEN_OWNER`, no new asset, no buffered upload |
| Send the diner's token at any photo route | `403 ROLE_FORBIDDEN` before the dish is loaded |
| Delete the photo that the old order snapshot references | `200`, dish loses the photo, snapshot URL still loads |
| Delete a photo no order references | `200`, and the asset returns an error from the CDN afterwards |
| Paste the snapshot URL into a browser | The maqluba photo from last week still renders |

The type check is the one that surprises people, because the file looks like a photo in every file manager. Open the refused request and read the code before you read the message: `UNSUPPORTED_TYPE` covers both a format outside the allowlist and a file whose bytes disagree with its declared type. If your route accepted the renamed document, the check reads the extension or the declared header alone, and both are claims made by the client.

The size check must fail while the parser is still reading. Watch the server log during the seven megabyte upload: if the whole body is buffered before the refusal, the limit sits in the handler instead of the parser, and a phone on a slow connection will spend a minute uploading a file you were always going to refuse. The five megabyte limit is also the number the form quotes, so a cook sees the same figure in the browser and in the error.

The four photo cap is a rule about the dish, not about the request. Send five uploads in a row from the same session and confirm the fifth is refused without touching the first four, including their order. A route that drops the oldest photo to make room has silently edited a cook's menu, and the diner's card changes without the cook choosing anything. If your implementation does drop the oldest, that is the defect this check exists to find.

The ownership check has the same shape as module 11 and a stricter ordering requirement. Send cook B's token with A's dish identifier and then look at two things the response does not show you: the `photos` array on A's dish, and the number of assets in the storage folder. Both must be unchanged. A `403` with a new asset behind it means the file was parsed and uploaded before the owner was proved, and the refusal was cosmetic.

Then the snapshot. Delete the maqluba photo that the delivered order references, and open the URL recorded in that order item. It must still render the dish. This is the check a reviewer will watch you perform, because it is the only one where a clean implementation of every other rule gives the wrong answer. The dish is allowed to change. The record of what a diner bought is not.

A broken URL is the last path and the cheapest to test. Take one photo, read its public identifier, and delete the asset from the storage console. Reload the cook's dish table and the diner's card. The dish must still be orderable, the name must still render, and the placeholder must appear in place of the image. If the whole card fails because one image failed, the client is treating a photo as required data when the API says it is optional.

## Measure the bytes

The roadmap added one outcome to this module that a photograph alone does not prove: a diner on a weak connection gets a small file. Measure it rather than describing it.

Request the card URL and the original URL for the same maqluba photo with the transfer size printed, on a throttled profile with the cache disabled. Record both numbers, then multiply by the number of dish cards a diner scrolls through in one window. Illustratively, the comparison lands near 38 KB for the 480 wide version and 2.4 MB for the original, which is about sixty times less data per card, and roughly 456 KB against 28 MB across twelve cards. Your numbers will differ; the ratio is what you are checking.

| View | Width requested | Illustrative transfer | What it is for |
|---|---|---|---|
| Cook table thumbnail | 480 | about 38 KB | Scanning a list on a phone |
| Diner dish card | 480 | about 38 KB | One card, one tap |
| Dish detail page | 960 | about 120 KB | The larger frame after the tap |
| Original | none | about 2.4 MB | Source, and order snapshots |

Write two sentences in your evidence beside the numbers. The first says what the original is for, given that no diner downloads it. The second says what you would change if the derived sizes started to dominate the bill, and why that change is not worth making on this plan. A learner who can say both has understood the trade-off; a learner who can only quote a kilobyte figure has copied a number.

## What the screen must show

Open the cook's dish table at 360 pixels wide and the diner's card on the same device profile. The cook sees a thumbnail per dish, the dish name, and the photo count, with an upload control beside the name. The diner sees the leading photo, or a placeholder with the dish name when there is none, and the card does not jump while images arrive.

Check three states that a happy-path screenshot never shows. A dish with no photo must render the placeholder and stay orderable, because module 11 never made a photo a condition of publishing and this module does not change that. A dish whose asset has been removed must show the placeholder rather than a broken icon. And a dish with four photos must show the first as its cover after the cook promotes another photo, without a page reload.

The last thing to check is what the gate does not prove. It does not prove that a photo shows the cook's own food, because no test can. It does not prove that a stored asset is ever cleaned up after the last order that referenced it, because the sweeper belongs to a later module and this one only logs the identifiers it keeps. Say both of those in your evidence note rather than leaving a reader to assume more than the module built.

## Gate checklist

- [ ] Cloudinary credentials load from `server/.env`, are documented as placeholders in `.env.example`, and no secret appears in the client bundle.
- [ ] A real maqluba photo uploads from cook A's session, and the response carries a `photoId` plus the card and page URLs.
- [ ] The Dish document holds a `photos` array with `url`, `publicId`, `width`, `height` and `bytes`, and no field contains image data or a base64 string.
- [ ] A renamed document is refused with `400 UNSUPPORTED_TYPE` and creates no asset.
- [ ] A file above 5 MB is refused with `413 PHOTO_TOO_LARGE` while the body is still being read.
- [ ] A fifth photo is refused with `409 PHOTO_LIMIT_REACHED`, and the first four remain in order.
- [ ] Cook B's token on cook A's dish returns `403 NOT_KITCHEN_OWNER`, with an unchanged array and an unchanged asset count.
- [ ] A diner token is refused on all three photo routes before the dish is loaded.
- [ ] Deleting the photo referenced by the delivered order leaves that order snapshot URL rendering, and the dish loses the photo.
- [ ] Deleting a photo no order references removes the asset from storage.
- [ ] The cook table and the diner card render a placeholder for a missing photo, and the dish stays orderable.
- [ ] Two byte measurements and the twelve card multiplication are saved in `docs/EVIDENCE.md` with the requests and documents they came from.

If a refusal returns `200`, the route handler is doing the check that the middleware should have done. If the asset count moves on a refused upload, the parser runs before the ownership filter. If the receipt breaks after a photo deletion, the destroy has no snapshot condition. If the card downloads megabytes, the client renders the stored `url` instead of the derived one, and the network panel will say so.

## Check the delete rule

```quiz
type: mcq
id: sufra-dish-photos-q1
question: A cook replaces the cover photo of maqluba, and three delivered orders carry the old photo in their snapshots. What must the delete step do with the old asset?
options:
  - Destroy the asset right after the dish save, and accept that an older receipt shows a broken image
  - Rewrite every order snapshot so that each receipt points at the new photo
  - Keep the asset while an order snapshot references it, then destroy it
  - Block the replacement until every diner has opened their receipt
correct: 2
explanations:
  - The dish would be correct and the diner's record wrong, which is the one order of priorities this module refuses.
  - Rewriting a snapshot changes a record of what a diner bought, which is exactly what the snapshot exists to prevent.
  - The dish can change today and a receipt from last week can still show the food that was bought.
  - A cook would wait on diners she cannot see, and the photo would never change, so the guard would never clear.
```

## Learning log

Answer these in `docs/learning-log.md` with the request, response or document that supports each answer. One short paragraph each is enough.

1. Which middleware returned the `403` for cook B, and what two observations told you the file was never uploaded?
2. What did the server do with the seven megabyte upload, and where is the limit enforced so that the bytes are not held in memory?
3. What did you store instead of image bytes on the Dish document, and which field do you pass to the storage service when a photo is deleted?
4. What did the delivered order snapshot show after you deleted the photo it referenced, and where in the code does the condition sit?
5. What were your two byte measurements, and what would change your mind about deriving sizes at delivery instead of at upload?

The first and fourth answers are the ones to keep. A refusal that uploads first is the defect this gate is built around, and a snapshot that survives a menu edit is the promise the order model makes in module 19. When both are true with evidence beside them, the cook side of the product has a menu with faces, and the delivery windows in module 14 can start deciding which of those dishes a diner may order at 11:31.
