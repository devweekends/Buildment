# Onboarding gate on a phone

A cook can now arrive at Sufra with nothing, be routed to onboarding, save a profile with an area, a pickup note and an IANA zone, enter capacity for the week, and record a declaration with a server timestamp. This gate asks you to show that the whole path works on the device the cook owns, not on the laptop where you wrote it. It also asks you to be precise about what the path does not yet do: no dated window exists, and no diner can order anything from this kitchen.

Use two cook accounts and one diner account. Clear the first cook's kitchen so the flow starts from zero. Keep the second cook's kitchen untouched, because one of the checks is that her onboarding state does not appear in the first cook's browser. Record the screen at 360 pixels wide, either on a phone or in the browser's device mode, and throttle the connection for at least one pass so a slow save is visible.

## Walk the path in order

Sign in as the first cook and open `/cook`. The redirect must land on the profile step with a sentence explaining why, not on an empty dashboard. Save the profile with `Europe/Berlin` as the zone, then with an empty name, then with a valid set of values; each answer must name the field that failed and keep the values she already typed.

Continue to the schedule step. Choose Monday, set lunch to 10 units, switch to Thursday, set dinner to 6, and come back to Monday to confirm 10 is still there. The day strip must remain visible while a row is edited, and no screen in the flow may scroll sideways. Check the smallest control with a ruler or the browser's element inspector: below 44 pixels it fails, even if it looks tidy in the screenshot.

Finish at the declaration step. Read the copy as a cook would. It must state what she affirms, and it must not claim that Sufra inspected, certified or approved her kitchen. After the save, inspect the kitchen row and confirm the declaration version and a timestamp that came from the server. Then set the phone clock forward by two hours, reopen the flow on a second device with a changed declaration wording, and confirm the stored timestamp did not move with the phone.

Finally, close the tab in the middle of the schedule step and open `/cook` again. The redirect should land on the schedule step, not back at the profile. A cook who has to re-enter her name after a power cut learns the wrong thing about the product.

Evidence for this gate is a recording plus the payloads, not a sentence saying the flow works. A screenshot of a filled form proves that a form can be filled. The reviewer needs to see the redirect decision, the field error, the rejected stale revision and the stored timestamp, because those are the four places where a flow that looks complete can be quietly wrong. Put the file names in `docs/EVIDENCE.md` next to a one line caption for each, so a reviewer can find the frame without watching six minutes of video. If a step cannot be recorded on the phone, record it twice: once at 360 pixels in the browser, and once on the device for the parts the browser cannot imitate, such as the keypad covering the schedule rows.

The diagram in lesson 10.1 is the thing to test, so keep it beside the demo. If a branch in that diagram has no screenshot behind it, the branch is unverified.

## Gate checklist

- [ ] A cook with no kitchen is routed to onboarding, and the page states why she is there.
- [ ] A cook with a draft kitchen lands on the step the server named, not on step one.
- [ ] A paused kitchen opens the dashboard and is not treated as unfinished onboarding.
- [ ] A diner account gets an explanation of the cook role and no onboarding form.
- [ ] Network failure during the resolve keeps the last known answer and offers a retry; it never starts onboarding.
- [ ] The profile save reports field specific errors for a bad name, an unknown time zone, an empty area list and an over long pickup note.
- [ ] The weekly editor fits 360 pixels with no horizontal scrolling and every capacity control is at least 44 pixels in both directions.
- [ ] The schedule save produces rules keyed by weekday and window, with capacity and cutoff lead, and a stale revision is refused.
- [ ] The declaration records a version and a server timestamp, ignores a client supplied timestamp, and contains no safety certification claim.
- [ ] Reloading in the middle of onboarding returns to the same step, and a second tab cannot create a second kitchen.
- [ ] Screenshots at 360 pixels, the saved requests and responses, and the stored rows are in `docs/EVIDENCE.md`.

If the redirect loops, check whether the onboarding routes sit inside the guarded layout. If a second kitchen appears, check the unique index on the owner and the conflict handling on the create route. If the schedule loses Monday when Thursday is saved, the editor is rebuilding its draft from props on every render. If the width test passes but the error text is cut off, the row has no space reserved for a message.

## Check the redirect rule

```quiz
type: mcq
id: sufra-onboarding-q1
question: A signed in cook opens /cook and the resolve call returns 404 with code KITCHEN_NOT_FOUND. What should the router do?
options:
  - Render the dashboard with an empty dish list, because the page itself still works and the cook can look around
  - Show a retry banner on the dashboard, because a missing record usually means a slow database read that will settle
  - Open the first onboarding step, save the intended path, and return there when onboarding finishes
  - Create a draft kitchen automatically so the dashboard has something to load before the cook fills anything in
correct: 2
explanations:
  - An empty dish list cannot tell a cook whether she has no kitchen or has not published a dish yet.
  - A missing record is a definite answer from the database, not a transient read failure.
  - A parsed not found code is the only signal that starts onboarding, and the saved path avoids dropping her work.
  - An empty draft created behind her back hides the onboarding steps she still has to complete.
```

## Learning log

Answer these in `docs/learning-log.md` with the screenshot, request or row that supports each answer. Keep each answer to a short paragraph that a peer could check.

1. Which response field stopped the client from guessing between an unfinished kitchen and a missing one, and what did the client do with it?
2. What happened to the schedule draft when you switched days, and which state did you have to change to make it survive?
3. Where did the declaration timestamp come from, and what did you observe when the phone clock was wrong?
4. Which control on the schedule screen failed the 44 pixel rule first, and what did you change in the layout?
5. What does this gate still not prove about a diner being able to order from this kitchen?

The last question matters as much as the others. A saved profile, a weekly template and a declaration are inputs. Nothing in this module creates a dated window, claims capacity, or takes money, and the delivery window module is where the template becomes an offer a diner can see.

When a reviewer can watch the recorded demo and find every branch of the redirect diagram covered, move on to the dish API. Keep the width test in the suite. It is cheap, and it catches the first component that adds a fifth column to a phone layout.
