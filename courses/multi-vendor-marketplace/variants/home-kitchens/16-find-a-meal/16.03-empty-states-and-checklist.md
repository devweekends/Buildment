# Find-a-meal gate

The browse screen is built and it looks right on the machine you developed it on. That is not the same as working. This gate asks for four pieces of evidence: a slow dish that disappears while a fast dish from the same kitchen stays, a full window whose empty state offers a real later window, a run at 360 pixels with the network slowed, and an audit of every place the client touches a time value. Each one can pass while the screen is still lying, so each one needs a saved observation rather than a description.

Set up the fixture before you start. Umm Yousef's kitchen has a 13:00 window in `Asia/Gaza` with a general cutoff at 12:00, a 20-minute travel buffer, maqluba at 90 preparation minutes and a falafel plate at 30. That gives maqluba an effective cutoff at 11:10 and falafel one at 12:00, where the general cutoff wins over its later preparation deadline of 12:10. Abu Sami's kitchen has a 13:00 window with two load units left and one dish that uses one unit per portion. Beit Hanan's kitchen has no 13:00 window at all, so it should never appear for that interval.

## Two dishes, one deadline

Load the browse screen at a fake server instant of 11:31. Maqluba must be absent and falafel must be present, with its own deadline shown as 12:00, which here is the kitchen cutoff winning over the later preparation deadline of 12:10. Nothing on the screen may say that maqluba is sold out, because it is not sold out; it is too slow for this window. Screenshot the card and keep the JSON response beside it.

Then repeat the run at 11:09, when both dishes are orderable, and leave the page open until 11:11. The maqluba row must disappear on its own while the falafel row stays. Record the two timestamps you observed and the offset your code derived from `serverNow`. If the row stayed, something is comparing against `Date.now()` without the offset, or the row is not ticking at all.

Now the decision this screen cannot avoid, because the browse response is a snapshot and the diner's finger arrives later.

```quiz
type: mcq
id: sufra-find-a-meal-q1
question: The browse page was read twenty minutes ago. Lina taps Add on a dish that was orderable then. Where does the decision about that line belong?
options:
  - The cart rechecks and may refuse the line
  - The browse page stays authoritative until she reloads it, so the cart should accept what she saw
  - The dish row hides its button after twenty minutes, so no later check is needed
  - The browse response reserved the dish, so the cart only has to record her choice
correct: 0
explanations:
  - The browse view is a snapshot; the cart repeats the cutoff and eligibility checks with fresh data.
  - A page read twenty minutes ago describes a marketplace that has moved on.
  - A client timer is guidance for the diner, not an authority the server can rely on.
  - Browse never claims capacity, so there is nothing to reserve or record.
```

The other three options share one mistake: they treat a rendered page as a decision. Whatever the screen does with a countdown, the line is accepted or refused on the server.

## The window that has no space

Remove both load units from Abu Sami and empty Umm Yousef's remaining capacity by recording a claim that uses the rest. Reload the browse screen for 13:00. Both cards must be gone and the empty state must appear, with a message that names the interval and a button that names a real later window. Tap it. The picker changes, a new read runs, and at least one kitchen appears if your fixture has one cooking at 18:00.

Then break the fixture on purpose. Delete every later window for the next two days and reload. The empty state must now say that nothing is open, with no button. A button that leads to the same empty message is worse than no button, and this is the case that exposes it.

Check the response for the suggestion field. If your empty state builds its own suggestion by adding three hours to the interval, it will offer 16:00 on a day when the platform runs lunch and dinner only. The suggestion has to arrive from the server or it is a guess with a timestamp on it.

## The 360 pixel review

Open the browser device toolbar, set the viewport to 360 by 740, and load the screen on the lunch fixture. Check four things with your eyes and your thumb. Every window button is at least 48 pixels tall and its two lines fit without truncation. The sticky header keeps showing the selected interval after you scroll past the third kitchen. The dish rows do not push the price off screen, and allergen words wrap as whole phrases. No element produces a horizontal scrollbar.

Then slow the network to 3G, clear the browser cache and reload. The first paint should show a skeleton or the word "Loading" rather than an empty page that looks like a result. When the response lands, the cards must appear without the layout jumping a full screen, which is what fixed image heights are for. Disconnect the network and reload again. The screen should tell the diner that the read failed and offer a retry, not sit on a spinner forever.

Repeat the whole pass with a keyboard only. Tab through the picker, press Enter on the second window, tab into the first card, reach the Add button and press it. The focus ring must be visible at every step on both themes. If the selected window cannot be identified without colour, the state is not accessible yet.

## The time and freshness audit

Search the client source for `Date.now`, `new Date()` and any comparison against a minute string. Every hit must either be the single offset hook or a formatting call. A component that subtracts a cutoff from the phone's clock is a defect even if it currently looks right.

Then search for hard-coded deadlines, labels such as "order by 12:00" and any capacity word that is not produced by a lookup from the server value. If "few spots left" appears in your JSX as a literal, it will appear on a full window too. The label must be a function of `capacityHint`.

Finally, read the network panel and confirm the browse request sends `Cache-Control: no-store` and does not repeat on a timer. One request per window selection is the budget. A screen that polls every five seconds costs Lina data she is paying for and gains nothing that a manual refresh and the cart's recheck do not already provide.

## Gate checklist

- [ ] At 11:31 the maqluba row is absent and the falafel row from the same kitchen is present, with both response and screenshot saved.
- [ ] A row left open past its `orderableUntil` disappears without a reload, and the fast row survives.
- [ ] Every deadline and countdown uses one offset derived from `serverNow`, proven by a test with a phone clock four minutes ahead.
- [ ] Kitchen cards print `orderableBy` and a server capacity hint, with no local arithmetic on remaining units.
- [ ] Windows are stacked, at least 48 pixels tall, marked selected in text and reachable with the keyboard.
- [ ] The layout at 360 by 740 has no horizontal scroll and no truncation of allergen or price text.
- [ ] A full interval shows a server-supplied next window that selects a different interval on tap.
- [ ] An interval with no later window shows a message and no button.
- [ ] A failed read shows a retry and a stale label rather than a blank screen or an endless spinner.
- [ ] `docs/find-a-meal-decisions.md` holds the fixture IDs, the fake instants, the offset value and the audit hits you fixed.

## Learning log

1. Which two values in your response decided that maqluba was hidden at 11:31, and what exact UTC instants did you compare?
2. What did your screen show when the phone clock was deliberately set six minutes fast, and which line of code produced that behaviour?
3. Which part of the empty state would break first if the platform stopped running a dinner window, and how would you notice?
4. Where in your implementation could a client value still reach the cart as if it were server truth, and what stops it?

## What this gate does not prove

Nothing here claims capacity, splits an order or takes money. A card can disappear a second after Lina reads it, and this gate does not prevent that; the cart and checkout repeat every check. The gate also says nothing about anonymous browsing, about browser back navigation across window selections, or about a diner who changes her saved neighbourhood while the page is open. Those are real cases, and they belong to the modules that own their data.

Module 17 has already built the cart API that this screen's Add button calls. If your Add button currently logs to the console, keep the fixture and finish the screen before the next module, where the cart page will ask the same data for grouped lines and a window change. A browse screen that cannot name its own deadline is not a foundation for a cart that has to survive a change of window.
