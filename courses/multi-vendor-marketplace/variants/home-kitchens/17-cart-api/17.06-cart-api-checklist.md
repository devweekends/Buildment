# Cart API gate

The diner can now save a selection across kitchens for one dated delivery interval. The cart checks a new line's current dish, kitchen and window records; previews a proposed interval change; calculates requested load for each kitchen; and keeps every route within the authenticated diner's scope. This gate asks you to demonstrate those behaviours together. A successful happy-path request is not enough, because the important rules appear when a cook pauses, a deadline passes or another browser tab changes the cart.

Prepare two kitchens with windows for the same UTC start and end, one slow dish and one fast dish, and a diner cart at revision 1. Add both lines. Show that each line names its own kitchen's window ID while the cart names one selected UTC pair. The response should include server-derived current details and no capacity claim. Inspect the windows after the add: `remainingUnits` must be unchanged. If adding a cart line changed that value, remove the claim logic and keep it for M19 checkout.

Run the following checks through the API routes, not only isolated helpers. Keep the request, response and final database state together so a reviewer can see that a rejected request did not modify the cart.

## Decision evidence

First, set the fake server instant one second before the slow dish's effective cutoff and add it successfully. Reset the fixture and try at the exact cutoff. The strict rule rejects it. Pause the kitchen with M9's wildcard closed exception while its window row still says open; the add also rejects. These cases show that the cart uses current server time and the exception lookup, rather than trusting browse or a phone countdown.

Second, send a dish from Kitchen A with Kitchen B's window ID. Expect a wrong-kitchen conflict and no revision change. Send a correct dish and kitchen window for 18:00 into a cart whose selected pair is 13:00. Expect a window mismatch. Try a quantity above `maxPerOrder`, and an increment that crosses the cap. Both must fail. A client-sent price or load value should not affect the saved line or summary. The response may identify which field was ignored or rejected, but it must never use it as a trusted total.

Third, preview a move to 18:00 when Kitchen A has a dated window there and Kitchen B does not. Show a per-line result with one valid mapping and one named conflict. Verify the stored cart remains at 13:00 after preview. Commit only after the diner explicitly approves removal of the invalid line; the route must revalidate and update selected pair, retained window IDs, lines and revision in one conditional write. Pause Kitchen A between a second preview and commit, and prove the commit rejects without changing the cart.

Fourth, calculate requested load. Two wraps at one unit each and one tray at three units must produce separate group loads of two and three. The result should include the corresponding window IDs and `serverNow`. Change a dish's `loadUnits` after the cart was saved and reload; the summary must reflect the current dish setting. It may compare that load with current `remainingUnits`, but it must label the result as an estimate. No cart route creates or releases a capacity claim.

Finally, use Diner A, Diner B and Cook C. B and C must fail to read, add to, preview or commit A's cart. Sending A's ID, diner ID and revision from B must not help. A random cart ID and A's cart ID must have the same public not-found response for B. Read A's cart after every failed mutation to prove its revision and lines did not change. Two A tabs using one revision must result in one successful update and one `CART_CHANGED` response.

## Review the implementation boundary

Inspect the route handlers for a shared validation policy. Add, preview, commit and checkout should use the M14 cutoff calculation and the M9 closure rule, with checkout rechecking independently at the final decision. A duplicated, slightly different cutoff formula is a gate failure even if the current fixture passes. The implementation must compare UTC instants and exact kitchen ownership. Displayed local labels are useful for people but insufficient to identify dated windows.

Check that MongoDB updates match `_id`, authenticated `dinerUserId` and `revision`. The route must construct an allowlisted update. It must not spread client JSON into `$set`, allow a body owner field to decide scope, or reload a foreign cart by ID in an error handler. Verify logs do not contain session tokens, full cart documents or another diner's choices.

This module produces a cart API, not a complete checkout. The cart retains intent and gives current explanations; it does not promise stock, lock price or settle money. M19 will create short-lived capacity holds and split orders, and M20 will verify payment. A reviewer should be able to point to the exact handoff: the cart's kitchen load summary is input for review, while checkout recomputes load and makes its own atomic capacity decision.

## Learning log

1. Which exact UTC pair did your two kitchen windows share, and which separate window IDs and cutoff instants did the cart retain?
2. Which rejected request would have changed the cart in a weaker implementation, and what database predicate or validation rule prevented that change?
3. What current cart information may change before checkout, and how will your UI ask the diner to review the difference before payment?
