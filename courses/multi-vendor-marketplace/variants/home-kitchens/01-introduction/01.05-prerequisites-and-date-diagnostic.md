# Prerequisites and the date diagnostic

Sufra assumes you can write small JavaScript functions, make an HTTP request, read a JSON response, use Git and model a few related records. You do not need prior experience with live streams, queues, Stripe webhooks or MongoDB concurrency. The course teaches those mechanisms through the kitchen and diner product. You do need to know that the server, not the browser, decides whether an order is timely. This diagnostic checks the date ideas that the delivery-window module will use.

Before answering, write one sentence about the difference between a clock label and an instant. A clock label such as "13:00" needs a date and a region to become a precise moment. An instant such as `2024-01-15T11:00:00.000Z` names one moment regardless of who reads it. On that historical January date, the instant can display as 13:00 in Gaza. A different viewer may see a different local hour without changing the stored instant.

The quiz asks for reasoning, not a memorized offset for a future date. Use the feedback to find a gap before building a schedule generator. If you miss two or more date questions, work through the repair read below and retake them with a new dated example. A wrong answer is not a judgment about your ability. It points to a boundary that becomes costly if it reaches checkout code.

## Repair read: three time values

If a question was hard, start with three separate values. A recurring rule is a local weekday and clock time plus an IANA zone, such as Monday 13:00 in `Europe/Berlin`. A dated window is a start and end instant in UTC for one specific Monday. A display label is the way a cook or diner sees that instant in their chosen zone. Do not store a display label as the only truth for an order. It can change if the viewer changes their preference, while the paid promise must remain attached to the same instant.

JavaScript `Date` represents an instant as milliseconds from the Unix epoch. `toISOString()` writes that instant in UTC. Comparing `dateA.getTime() < dateB.getTime()` compares instants, not text labels. A string such as `"2024-01-15 13:00"` is a poor input for a cross-zone promise because it has no named zone. Use a time-zone-aware library when turning a cook's local weekly rule into a dated instant. M14 will show that conversion and a clock-change test.

The `Z` at the end of an ISO value means UTC. For example, `2024-01-15T11:00:00.000Z` names one instant. On that historical date it can display as 13:00 in Gaza, but a diner elsewhere may see another hour. The instant does not move when the display zone changes. Write both the stored UTC value and the kitchen-local label in a test fixture so you can catch a conversion mistake without treating the label as the database value.

Try a comparison by hand before relying on code. If the server reads `2024-01-15T09:09:59.000Z` and a dated dish cutoff is `2024-01-15T09:10:00.000Z`, the request is one second early. At the cutoff instant, it is late under the strict rule. The timezone used to print either value does not change their ordering. This simple boundary is the one the later checkout test must preserve under concurrency.

An offset is the difference between local clock time and UTC for one moment. An IANA zone is a named set of regional rules that can give different offsets on different dates. `+02:00` may describe Gaza on one date, but it is not a substitute for `Asia/Gaza` in a recurring kitchen schedule. The course tests a historical Berlin clock change because its before-and-after result is stable evidence for the algorithm. Avoid hard-coding a guessed future Gaza transition date as a unit test.

Finally, separate display from authority. The diner may see a countdown made from server time and a phone estimate. It helps them act, but it can be stale. The backend reads its clock when adding a cart line and again when claiming capacity. Under Sufra's rule, `now < cutoffAt` is timely; exactly at the cutoff is late. Work the 11:10 example with 11:09:59, 11:10:00 and 11:10:01. The same rule applies regardless of the phone's local zone.

If the date questions now make sense, record one new example in `docs/decisions.md`: a dated window start in UTC, its kitchen-local label, a slow dish's cutoff, and a server instant that should fail. Ask a peer to check the arithmetic. If JavaScript functions, arrays or HTTP responses are the gap instead, use the starter project's small practice tasks before moving to the data-model chapters.
