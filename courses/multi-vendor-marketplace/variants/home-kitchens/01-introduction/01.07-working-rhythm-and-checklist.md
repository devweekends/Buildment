# Working rhythm and checklist

The introduction has named the product, the people, the core scope and the four demos. Before opening the starter project, set up a working rhythm that lets you stop and resume without losing the last decision. Many learners work on phones or unstable connections. A useful plan saves small, tested changes and keeps the next action visible. This gate asks for a product brief, one dated lunch calculation and a simple evidence plan, not a finished kitchen API.

Work in short units that produce a visible result. Read the next chapter, write the expected behavior, change one model or route, run the narrow test and save its output. Commit after the boundary passes. If a larger feature takes several sessions, leave a failing test or a small note that says exactly what remains. A vague "continue backend" reminder is hard to use after a pause; "14.05 exact cutoff test fails at 11:10, inspect strict comparison" gives you a starting point.

## Keep a local path through interruptions

Clone or download the course and project instructions while the connection is available. Keep the small reference pages for your current module accessible offline. Do not download large videos to make progress; the written path contains the needed explanation. If a command requires a service that is unavailable, record the command and the expected result, then return to it when the service works. Do not mark the gate passed until the command actually runs.

Start `docs/learning-log.md` with a compact entry: date, current branch, last passing command, next small task and one open decision. After an interruption, rerun the last passing command before editing more files. If it fails, inspect environment and uncommitted changes first. That prevents an unrelated setup issue from being mistaken for a new capacity bug. Keep secrets out of the log and out of screenshots.

Use Git as a checkpoint tool. Before a commit, inspect `git diff` and `git status`, then run the test for the work you changed. Commit the related source and test together. A message such as "add dated window cutoff tests" tells a reviewer what boundary the commit protects. Keep experimental changes on a branch, and do not mix an unrelated interface color tweak into a capacity claim fix. Small commits make a lost session or a rejected approach easier to recover from.

## Recap the product decisions

Sufra starts with a cook's weekly rule and ends with a diner's dated meal promise. A weekly 13:00 label needs a date and an IANA zone before it becomes a UTC start instant. A slow dish can close earlier than the kitchen's general cutoff. Load units determine how many orders fit; preparation minutes determine whether an order is still timely. Checkout checks both again, claims each kitchen safely, and does not offer payment for a partial cart. After payment, a cook's decision and the diner's reconnecting timeline keep the promise visible.

Your product brief should make these distinctions in plain language. Write two sentences naming the cook, diner and primary constraint. Use the 13:00 lunch example to calculate maqluba's 11:10 effective cutoff and falafel's 12:00 effective cutoff. Name the general cutoff, both preparation times and the travel buffer. A reader should be able to check the arithmetic without opening code. Then name one failure response for a late dish and one for a full window; they are different conditions.

The date diagnostic should also be complete. If you missed two or more questions, use the repair read and try a new dated example. A future kitchen schedule cannot be built safely from one fixed UTC offset. A countdown on Lina's phone cannot decide if a checkout is late. These are entry concepts, not a demand that you already know the final algorithm. Write any remaining question in the log so the M14 time module has a specific gap to answer.

## Gate checklist

- [ ] `docs/product-brief.md` names Sufra's cook, diner, dated delivery promise and two main constraints.
- [ ] The brief gives one fictional kitchen zone, one dated 13:00 window, a general cutoff, a travel buffer and two dishes with different preparation times.
- [ ] The maqluba and falafel effective cutoffs are calculated by hand, with the earlier rule identified in each case.
- [ ] Three core promises and three out-of-scope features are recorded with reasons.
- [ ] `docs/EVIDENCE.md` has four weekly headings and an intended command or test for each demo, with unrun results left blank.
- [ ] `docs/learning-log.md` records the last passing command, next small task and one open decision without private personal details.
- [ ] The date diagnostic is passed or its repair path is completed with a new example.

If a brief says only "food ordering app," make it more specific before moving on. Name the interval, cutoff, capacity and split order. If a cutoff calculation disagrees with the example, write every duration in minutes and subtract from the dated window start. If a test plan says only "test checkout," name the parallel request count and capacity invariant you will need later. This gate is small, but it gives the later technical modules a common set of numbers and a reviewable target.

## Learning log

Answer these in `docs/learning-log.md`. Use the fictional meal example so no personal experience is required. The aim is to expose an assumption that could make a later order unsafe.

1. At 11:31, why is maqluba closed while falafel can still be timely for the same 13:00 window? Give both cutoffs and the remaining capacity condition separately.
2. Which value will the database store for a particular lunch window, and why is the cook's recurring `13:00` label insufficient on its own?
3. Which week will prove that two diners cannot claim the same last cooking units, and what exact test result will count as evidence?

Ask a peer to read one answer without your explanation. If they cannot tell whether a time is a local label or a UTC instant, add the date and zone. If they cannot tell whether an order is merely held or paid, name the state. Those clarifications matter more than polished prose because they will guide the first schema and API decisions.

The next module makes the server and client run. Keep this brief and log nearby. The skeleton is useful only because it will eventually carry a kitchen's dated promise through checkout and order tracking.
