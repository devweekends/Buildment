# Final ERD and gate

The Sufra model now has two kinds of time data and two kinds of purchase data. A kitchen's weekly schedule is a recurring local rule. A `DeliveryWindow` is one dated UTC promise with its own capacity. A cart is an editable request for one interval. A kitchen order is a snapshot of one part of a shared purchase. An embedded `CapacityClaim` connects a window counter to a checkout attempt. This gate asks you to make those relationships visible and show that the seed preserves them on retry.

## Recap the model's boundaries

The cook owns a kitchen. The kitchen lists stockless dishes and offers dated windows. Dishes provide preparation and load inputs; windows own mutable remaining units. A claim is embedded on a window so its identity and counter change together. A diner owns one cart and their split kitchen orders. Each order references a claim and window, but also stores its own purchase snapshot. The order timeline will later show status changes after payment. These relationships prevent a grocery-style product counter from hiding time and shared effort.

Open `docs/erd.md` and draw User, Kitchen, Dish, DeliveryWindow, embedded CapacityClaim, Cart, Order and embedded status event. Label every ownership and reference arrow. Mark fields copied at purchase separately from live references. A peer should be able to point to the record that answers each question: who may edit this dish, which 13:00 occurrence has capacity left, which claim consumed three units, what price did the diner pay, and what status did the diner see after reconnect.

The ERD should also show one-to-many relationships clearly. One cook may own a kitchen with many dishes and dated windows. One window can hold several claims until its units are exhausted. One diner cart can request lines from several kitchens for one selected interval. One checkout attempt can create one order per kitchen. Do not draw one shared Order document containing all kitchens if the cook dashboard and partial refund need separate kitchen outcomes.

## Show the seed twice

Run `server/scripts/seed-sufra.js` on a development database and record counts and IDs. Expect three fictional kitchens, at least six distinct dishes, dated samples across seven days for each kitchen and two diner accounts. Check that every dish and window points at its own kitchen, every window has UTC dates and a kitchen zone label, and no dish has `stockQty`. Show a window with ten capacity units and ten remaining.

Add a held three-unit fixture claim to one window and lower remaining to seven using a deliberate test setup. Rerun the seed. The same window ID, claim ID and seven remaining units must remain. Remove the fixture hold through the test cleanup after recording evidence. If the seed resets remaining to ten, it fails this gate even if the document count stays the same. A counter reset can make already promised work available twice.

Now ask the database to insert a second window with the same kitchen and UTC start. The compound unique index should reject it. A different kitchen may have a window at that same UTC start. Save the index list and both outcomes. A schema declaration without an applied index is not enough. If the duplicate insert succeeds, fix index setup before moving to the generator module.

## Gate checklist

- [ ] `docs/erd.md` shows cook and diner ownership, all seven core records, embedded claims and embedded order status events.
- [ ] Kitchen weekly rules keep a local clock label and IANA zone; dated windows keep UTC start, end and general cutoff.
- [ ] Dish models have preparation minutes and load units, with no `stockQty` field.
- [ ] A window starts with equal total and remaining units; held and confirmed claim units account for the difference later.
- [ ] The unique kitchen-start index rejects duplicate dated windows after it has been built.
- [ ] Seed reruns preserve a held window's ID, claim and remaining units.
- [ ] A cart has one selected interval and does not claim capacity merely by holding a line.
- [ ] An order item keeps name, price, preparation and load snapshots, and an order keeps its dated window promise.
- [ ] Saved commands, counts and inspected rows in `docs/EVIDENCE.md` can be rerun without private credentials.

If a check fails, locate the owner of the value. A duplicated lunch belongs to the window index or generator key. A reset counter belongs to an unsafe seed update. A paid price that changes with the menu belongs to a missing order snapshot. A diner who can read another cart belongs to the ownership service. Do not add a new field to every document in hope that the problem disappears; each invariant has one place where it must be enforced.

## Learning log

Answer these in `docs/learning-log.md` using your saved seed rows and ERD, not only the chapter diagram. A reviewer should be able to verify each answer from the named fields and indexes.

1. Which record owns the ten-unit lunch capacity, and how do a three-unit hold and a later release change its accounting equation?
2. Why do the kitchen-start unique index and the claim-ID retry filter protect different duplicates?
3. Which fields in a kitchen order must remain after a cook edits the live dish and weekly schedule, and why are live references still useful?

If you cannot answer the first question without mentioning `stockQty`, revisit the stock trap. If the second answer calls both guards "the same unique rule," point to the two different failure cases: duplicate window documents and duplicate claims inside one window. If the third answer relies on today's menu to explain yesterday's payment, add the purchase snapshot before checkout builds on it.

Commit the ERD, schema files, seed script, index verification and evidence together. The next modules add authentication and role-aware routes. They will follow the ownership arrows you have just drawn. M14 will generate current dated windows from recurring rules, and M19 will perform the claim transitions under concurrency. This gate establishes their data contract; it does not claim those later services already work.
