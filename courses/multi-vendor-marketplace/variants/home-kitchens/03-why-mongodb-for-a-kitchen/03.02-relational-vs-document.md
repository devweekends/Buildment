# Relational and document shapes for a kitchen schedule

Imagine two engineers modelling the same Thursday lunch. The first opens a relational database and writes five tables with foreign keys. The second opens MongoDB and writes four collections, two of them with embedded arrays. Both can serve Lina a tray of maqluba at 13:00. They fail in different places, and the failures cost different amounts.

This lesson builds both shapes in enough detail that you can see the difference in constraints rather than in taste. The relational shape is not a strawman. PostgreSQL holds kitchen schedules very well, and in two specific places it holds them better than MongoDB can. Knowing exactly where the document model gives something up is what makes your eventual decision defensible.

## The relational shape, table by table

The relational version starts with `kitchens`, holding the name, the owner and the IANA zone. A `weekly_rules` table holds one row per weekday interval with a start time, an end time, a capacity and a cutoff lead, and a foreign key to the kitchen. A `delivery_windows` table holds one row per dated occurrence with a `tstzrange` or two `timestamptz` columns, a capacity, a remaining count and a status. A `capacity_claims` table holds one row per hold with a window reference, units, state and expiry. An `orders` table and an `order_items` table hold the purchase.

The interesting part is not the columns. It is the four constraints a beginner forgets and a relational platform gives you for free. The first is a check that remaining units never go negative and never exceed capacity. The second is a foreign key from a claim to a window, so a claim cannot point at a lunch that was never generated. The third is a unique constraint on the kitchen and the window start. The fourth is an exclusion constraint that stops one kitchen from having two overlapping windows on the same date.

```sql
select * from delivery_windows
where kitchen_id = 'kitchen-umm-yousef'
  and tstzrange(start_at, end_at) && tstzrange('2026-11-05 11:00Z', '2026-11-05 12:00Z');
```

A PostgreSQL exclusion constraint uses exactly that range operator, so the fourth guarantee is one declaration rather than application logic. If the generator runs twice in parallel, the database rejects the second overlapping insert. No code in your service has to be right for the rule to hold.

```sql
alter table delivery_windows
  add constraint windows_do_not_overlap
  exclude using gist (kitchen_id with =, tstzrange(start_at, end_at) with &&);
```

That declaration is the honest strength of the relational model in this domain. Time is continuous, and a range type with an overlap operator expresses "these two intervals share a minute" directly. MongoDB has no equivalent operator in an index, so the document version has to prevent overlapping windows with a generator key, an idempotent upsert and a review of the schedule editor.

## The document shape, collection by collection

The document version starts from what a screen reads and what a transactional step changes, then groups fields by that boundary. A `Kitchen` document holds the profile, the zone and the weekly template as an array of small rule objects. It is read whole by the cook's schedule editor and is small, so an array is honest here.

A `DeliveryWindow` document holds the dated interval, the capacity, the remaining count and an array of claims. A `Dish` document holds the kitchen reference, the name, the price, the preparation minutes and the load units. An `Order` document holds the kitchen reference, the diner reference, the frozen window times, the item snapshots and the status timeline as an array of events.

```js
// Server-side shape only, error handling and validation are omitted.
const DeliveryWindowSchema = new Schema({
  kitchenId: { type: Schema.Types.ObjectId, ref: 'Kitchen', required: true },
  startAt: { type: Date, required: true },
  endAt: { type: Date, required: true },
  cutoffAt: { type: Date, required: true },
  kitchenZone: { type: String, required: true },
  capacityUnits: { type: Number, min: 1, required: true },
  remainingUnits: { type: Number, min: 0, required: true },
  claims: [{
    id: { type: String, required: true },
    attemptId: { type: String, required: true },
    units: { type: Number, min: 1, required: true },
    state: { type: String, enum: ['held', 'confirmed', 'released'] },
    expiresAt: { type: Date, required: true },
  }],
});
DeliveryWindowSchema.index({ kitchenId: 1, startAt: 1 }, { unique: true });
```

The unique index on the kitchen and start replaces the third constraint, the unique pair. The claim array beside the counter replaces the first and the second, because one conditional update can subtract units only while the filter holds, and a claim nested in the parent cannot point at a window that does not exist. The overlap rule has no replacement at all.

## A cutoff is computed, not stored

The per-dish cutoff deserves its own paragraph because it is the field most likely to be copied into the wrong place. A maqluba tray needs ninety preparation minutes, the kitchen allows a twenty-minute travel buffer, and the window's general cutoff is 12:00 for a 13:00 start. The dish cutoff is therefore 11:30, and it is derived from the window start, the preparation minutes, the buffer and the general cutoff.

Storing that value on the dish would be wrong, because the same dish has a different cutoff in every window. Storing it on the window would be wrong too, because each dish closes at a different moment and the window holds many dishes. The correct home is the read path: compute the effective cutoff when you build the offer, and compare it with one server instant.

Neither store has an advantage here. PostgreSQL would compute the same expression in a view or a generated column, and MongoDB computes it in the service. The difference is only where the logic lives, which is why the honest comparison says both shapes carry it and both must test the boundary.

## Where the two shapes pay and charge

Read the comparison as a list of trades, not a scoreboard. Each row names what you get and what it costs, and the cost is the part you must repeat in your own write-up.

| Question | Relational shape | Document shape |
|---|---|---|
| Is this kitchen free at 13:00 on a date? | Range overlap query, indexed | Equality on a generated start, indexed |
| Can two windows overlap by mistake? | Rejected by an exclusion constraint | Prevented only by generator code and review |
| Can remaining units go negative? | A check constraint, always | A conditional filter on every update |
| Can a claim point at a missing window? | Foreign key refuses the insert | Impossible: the claim lives inside the window |
| What did Lina buy? | Join order, items and dish rows | One order read, snapshots already inside |
| Claims per kitchen per day | One grouped query across rows | Aggregation with `$unwind` on claim arrays |
| Two writes across kitchens | One transaction, always available | A transaction needs a replica set |

The last row matters in a laptop course. A MongoDB transaction requires a replica set, so a local Docker setup would need a single-node replica set before the all-or-nothing claim path could use one. That is why the approved path for Sufra in Module 19 is compensating release with deterministic claim IDs, and the transaction stays a comparison.

## Say plainly where PostgreSQL wins

If Sufra ever needed a hard guarantee that no two windows for the same kitchen overlap, PostgreSQL would be the safer home for that table. A range column with an exclusion constraint is a promise the database keeps even when two generator processes start at the same second, a backfill script runs twice, or a developer later adds a manual window through a support tool. In MongoDB the same rule lives in your generator and in the unique index on the exact start time, which does not catch 13:00 to 14:00 and 13:30 to 14:30.

The second relational advantage is reporting across rows. A question such as "how many load units did Umm Yousef's kitchen sell this week, grouped by day" is a `GROUP BY` on a date column in PostgreSQL. In MongoDB it is an aggregation that unwraps claim arrays, and the shape of that query changes if you move claims to their own collection. Neither is impossible, but the relational version is shorter and harder to get wrong.

There is a third advantage worth naming because it is common in payment work: a ledger across many tables with foreign keys and a transaction that is available without extra infrastructure. Sufra's core path keeps money inside one payment intent and one split order, so this advantage does not bite in the core. It would bite if Sufra paid cooks out, which this course does not build.

## Say plainly where the document shape wins

The document shape wins on the screen the learner is actually building. The browse request for one window returns the window with its counter, and the dish list for that kitchen comes from one indexed read on `kitchenId`. On a weak phone connection, two round trips instead of five is a real difference, not a micro-optimisation.

It also wins on change. A `Dish` gains allergens, then a per-dish maximum per order, then a photo URL. Those fields arrive without a migration that blocks a table of live menus. A relational platform handles this fine with nullable columns, so treat flexibility as a convenience here rather than a decisive advantage.

The last win is the boundary itself. A window and its claims change together, and an order and its timeline change together. MongoDB's single-document atomicity gives that boundary without a transaction and without a replica set, which keeps the course's checkout lesson focused on the race rather than on infrastructure. That is the argument you can defend, because it names the mechanism rather than the brand.

## The near-miss to avoid

A tempting middle design puts claims in their own `claims` collection and keeps `remainingUnits` on the window. It looks cleaner on an ERD. It also reintroduces the exact bug the single document removed: a crash between the counter update and the claim insert leaves a window with fewer units and no claim to release.

If you choose the separate collection, you must also choose a transaction for every claim and release, and you must accept the replica set requirement. Write that consequence in your draft. A reviewer should be able to see that you knew the cost rather than that you missed it.

## What would change the answer

Three conditions would move Sufra to a relational store. A hard overlap guarantee enforced by the database rather than by the generator is the first. A reporting surface that groups claims and orders across kitchens every day is the second. A ledger with several related tables and a payout obligation is the third.

None of those is in the core path. The core path needs dated windows with a counter, per-dish cutoffs computed from the window, embedded capacity claims, and orders with frozen snapshots and a timeline. That is the case you will write down in the next lesson, with one table row per decision and one honest cost beside each benefit.
