# Data model decision gate

The draft is written and the uniqueness test has failed at least once in your terminal. This gate is not a summary of Module 3. It is the point where a second person reads your decision and tries to break it with the same questions a reviewer would ask in a viva.

Bring three things to the conversation: `docs/erd-draft.md`, the test output from before and after the index existed, and your answer to one question. Why does a window own capacity instead of a dish? If the answer includes a phrase about performance or popularity, go back to lesson 3.1 and rebuild it from Lina's tray.

## Defend three claims

The first claim is that a delivery window is the unit of capacity. A reviewer will ask what stops two kitchens from sharing one lunch window. Nothing should: the window names one kitchen, and the unique index covers the kitchen and the start together. Two kitchens may both serve 13:00, and each keeps its own units. If your draft shows one global lunch window, the ownership arrow is wrong.

The second claim is that a claim lives inside the window. The reviewer will ask what happens when the process stops between decrementing the counter and recording the claim. Your answer names the single update and the deterministic claim identity. If the draft keeps claims in a separate collection, the answer must name a transaction and the replica set it requires. Either answer can pass; an answer that says "the database handles it" cannot.

The third claim is the honest one. The reviewer will ask where PostgreSQL would be the better home. Name the overlap rule, and name the grouped reporting query across many windows. Then say what Sufra does instead and what that costs. A learner who cannot name the loss has not compared anything, only repeated a preference.

## Check the draft against a real Thursday

Open the worked row in your draft and walk through it aloud. Umm Yousef offers Thursday 13:00 to 14:00, capacity ten. The general cutoff is 12:00. Maqluba needs ninety preparation minutes, so its own cutoff is 11:30 once the travel buffer is applied. Lina claims three units at 11:31 for falafel, which is still within its own cutoff. The window goes from ten remaining to seven, and the accounting line must show seven plus three equals ten.

Then change one input and see whether the draft still answers. Set the clock to 11:31 for maqluba instead of falafel. The window still has seven units and the general cutoff has not passed, but the dish is late for that window. The draft must show that the per-dish cutoff is computed from the window start and the dish fields, and that the block comes from the dish, not from a full window. If your draft cannot show a late dish in a window with room, the cutoff has no home.

## Hand in the evidence

Put the files in one commit: the draft, the test, and the short output showing the failing insert and the passing one after the index. Name the commit after the decision, not after the tool. Do not include a connection string or a screenshot of a database browser; both are hard to review and one is unsafe.

Add the answer to the overlap question in writing, even if nobody asked it in the session. A committed answer is what a later reviewer reads when the generator in Module 14 changes.

```quiz
type: mcq
id: sufra-datamodel-gate-q1
question: Umm Yousef pauses Thursday lunch. Which record must survive so next Thursday can still be offered?
options:
  - The weekly rule, closed for that date only
  - The dated window, deleted for every future Thursday
  - The dish documents, hidden until the cook resumes
  - The diner orders, cancelled to match the pause
correct: 0
explanations:
  - A dated exception closes one occurrence and leaves the repeating rule and future dates intact.
  - Deleting window rows removes evidence of paid promises and cannot stop future generation.
  - Hiding dishes removes the whole menu rather than one date, and it does not close a window.
  - A pause stops new claims; it does not erase the purchase records it did not cause.
```

## What this gate does not prove

The draft is not a schema. It has no validators, no default values and no indexes except the one your test applied. Do not tell a reviewer that the model works. Say what the draft decides and which later lesson proves each part of it.

Module 5 turns the shapes into Mongoose models and seeds three kitchens with a week of dated examples, and that seed is where a wrong reference becomes visible. Module 14 proves that generation from a template creates one window per date and does not reset a consumed counter. Module 19 proves the claim under concurrent checkout, which is the only place the atomic update is really tested. Until then, the strongest honest sentence is that the decision is recorded and one database rule has been demonstrated.

## Gate checklist

- [ ] `docs/erd-draft.md` opens with a decision paragraph that names one benefit and two costs.
- [ ] The decision table has one row each for window identity, the counter, the claim, the order snapshot and the timeline.
- [ ] The ERD shows cook ownership of Kitchen and Dish, diner ownership of Cart and Order, and the claim embedded in the window.
- [ ] No document in the draft carries a per-dish quantity counter; the window owns the only consumed number.
- [ ] The order stores frozen window times and item fields, so a later menu edit cannot rewrite a purchase.
- [ ] The uniqueness test fails before the compound index exists and passes after it, with both outputs saved.
- [ ] The draft names the overlap rule as a generator responsibility and says which condition would move Sufra to a relational store.
- [ ] The open questions section names at least two unsolved problems, including where a diner address lives.

A missing checkbox is not a documentation problem. If the counter is on the dish, move it. If the order reads the live price, freeze it. If the test passed on the first run, the index already existed and you have not seen the database refuse anything yet.

## Learning log

Answer these in `docs/learning-log.md` with a field name or a command output for each sentence. A reviewer should be able to check the answer without asking you.

1. Which record owns Thursday's ten units, and which two fields must balance after Lina's three-unit claim?
2. Why can a dish be late for a window that still has spare units, and which two values give that answer?
3. Which single guarantee does the compound unique index on kitchen and start fail to provide, and where does that guarantee live instead?
4. When would a relational range type with an exclusion constraint serve Sufra better, and what would have to change for that to matter?
5. What would you have to add if claims moved from the window document into their own collection, and what would that addition cost on a laptop?

The first answer should mention `capacityUnits`, `remainingUnits` and the held claim units without reaching for a per-dish counter. The third should name the overlap case rather than a duplicate. If the fifth answer is only "a transaction", say what the transaction needs to run and which local setup would change.

Commit the gate evidence together with the learning log entries. Module 4 connects the database and adds an injectable clock, and Module 5 turns this draft into schemas and a seven-day seed. Keep the draft where those modules can point at it, and reopen it when a later lesson disagrees with it rather than letting the two versions drift.
