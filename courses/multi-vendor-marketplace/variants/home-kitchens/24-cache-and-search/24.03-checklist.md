# Cache and search gate

Everything in this module is easy to demo badly. A cache that is never invalidated still looks fast. A menu fragment that quietly carries `remainingUnits` still renders. A search route that ignores the delivery window still returns dish names. This gate asks for evidence that survives a second look: the failing test now passing, the forbidden field absent from the stored payload, recorded numbers from a harness you can rerun, a browse screen that keeps working when Redis stops, and a search that finds a dish by its Arabic name.

Prepare one kitchen with two published dishes, one window pair for 13:00 in `Asia/Gaza`, a menu key present in Redis and no traffic against the server. Note the Redis key names you expect before you start, because a demo that claims a cache hit without showing the key has not shown a hit.

## The save that must show up

Read the kitchen menu and record the maqluba price. Save a new price through the cook's dish route, then read the menu again without waiting for the TTL. The new price must appear on the next read, and the response header must say the second read came from the database, because the invalidation deleted the key and the route rebuilt it.

Then repeat the save with a second field, the allergen list, and confirm the change appears as well. This catches an invalidation hook that was wired only into the price path, or one that keys the menu by something other than the kitchen that owns the dish.

Show the git diff or the current file with the invalidation call in the dish service, and run the test from the previous lesson in front of the reviewer. Paste the earlier failing output next to the passing one in `docs/cache-decisions.md`. The pair of outputs is the evidence; a passing test alone cannot show that the risk was ever real.

## The field that must be missing

Read the cached value directly from Redis and print it. Search the printed payload for `remainingUnits`, `capacityUnits`, `cutoffAt`, `orderableUntil` and `capacityHint`. None may appear. Then change a window's remaining units in MongoDB without touching any dish, request the browse screen and confirm that the capacity hint changed while the cache header still reports a hit.

That second step is the one that catches the near miss. A team can keep capacity out of the cached document and still cache the assembled browse response, which is the same mistake one layer up. If the hint did not change, the cached object is an availability answer wearing a menu's clothes. Find the route that sets that key and remove the availability fields from what it stores.

Also check the reverse direction. Hide a dish as the cook and confirm it disappears from the next menu read. A cache that busts on price but not on status serves a dish the cook has taken off her menu, which is worse than a stale price because the diner cannot order it at all.

```quiz
type: mcq

question: A cook saves a price change while Redis is unreachable. What is the correct outcome for that request?
options:
  - Reject the save and ask the cook to try again later
  - Save the dish and log the failed invalidation
  - Save the dish and keep the old cached price until the TTL expires
  - Flush the whole cache so every kitchen rebuilds from scratch
correct: 1
explanations:
  - A cook's edit is a database fact and must not depend on a cache being available.
  - The write succeeds, the invalidation is logged for repair, and the TTL bounds staleness.
  - The dish path must still attempt the delete, and skipping it turns a fault into silent staleness.
  - Redis is unreachable, so a global flush cannot succeed and would discard healthy keys.
```

## Measure before and after

Run the harness from the previous lesson three times with the cache disabled and three times with it warm, and record the medians. The table must include p50, p95 and the MongoDB dish read count, because latency on a developer laptop will look flattering in both rows.

Write one sentence that describes the result in words, for example that the database read count fell from two hundred reads to one while the median moved by less than a millisecond on localhost. If that is what happened, say exactly that and do not claim a speed improvement the numbers do not support. A cache justified by its database savings is still a real improvement, and an honest small number is more convincing than an invented large one.

Then read the same numbers on the deployed instance if Module 25 has run by the time you reach this gate. If it has not, mark that row as not measured and leave it in the table. A missing row is honest; a copied row from another machine is not.

## Redis stopped

Stop the Redis container while the API keeps running. Load the browse screen, add a dish to a cart, and read the kitchen menu. All three must succeed from MongoDB. The response headers should report `database`, the pages should render without an error banner about caches, and the server log should show a bounded number of degradation notices rather than one per request.

Start Redis again and read the menu twice. The first read rebuilds the key, the second reports a hit. Confirm that the key exists with the expected prefix and the TTL you configured. If the key never appears, the write path is swallowing an error: check how your client reports a connection refused state and whether the `set` call is inside the same guard as the `get`.

Restart the API while Redis keeps running and repeat the read. The cache must still serve the fragment after the API comes back, because the cache lives outside the process. If the read goes to MongoDB instead, the key includes something process-specific, such as a worker ID, and it will never be shared between instances in Module 25.

## Search in both scripts

Ask the search route for "Maqluba" and then for "مقلوبة". Both must return Umm Yousef's dish, and both must include the kitchen name so a diner knows which cook she is looking at. Then remove that kitchen's window for the selected interval and search again. The dish must disappear from the results, even though the text still matches, because the kitchen is not cooking then.

Run `explain('executionStats')` on the search and save the output. The plan must name the `dish_name_text` index, and the examined document count must be well below the collection size. If the plan shows a collection scan, the index is missing: check that the model was registered before the connection opened and that the seed database had the index built.

Finally, search for a token that appears in no name, and for a query shorter than two characters. The first returns an empty list with a 200, and the second should return a validation message rather than a full scan of every dish. Both behaviours belong in the checklist because both are the kind of request a real phone makes by accident.

## Gate checklist

- [ ] A price change and an allergen change are visible on the next menu read, with no wait for the TTL.
- [ ] The earlier failing invalidation test and its passing version are both saved in the evidence file.
- [ ] The raw cached payload contains no capacity, cutoff or orderability field.
- [ ] A capacity change in MongoDB changes the browse hint while the menu cache still reports a hit.
- [ ] A hidden dish disappears from the next menu read.
- [ ] Harness output is recorded three times cold and three times warm, with p50, p95 and database dish reads.
- [ ] One sentence states the result honestly, including a small or absent latency change.
- [ ] With Redis stopped, browse, cart and menu reads succeed from MongoDB with bounded log noise.
- [ ] After Redis restarts and the API restarts, the cache is reused rather than lost.
- [ ] Search finds the dish by Latin and Arabic name, hides it when the kitchen has no window, and uses the text index in `explain()`.
- [ ] A query with no matches returns an empty list, and a two character query returns validation feedback.
- [ ] `docs/cache-decisions.md` holds the key names, the payload, the timings, the plan and the fallback run.

## Learning log

1. Which write paths bust the menu key in your code, and which one would a future route most easily forget?
2. What exactly did the cache save, in database reads or in latency, and which measurement supports that claim?
3. What happened to a diner's browse request while Redis was stopped, and how would you have noticed if the fallback were missing?
4. What does `default_language: "none"` change about how a dish name is indexed, and which query would behave differently if you removed it?
5. Which value in the browse response is still allowed to be a few seconds old, and what does the cart do about it?

## What this gate does not prove

A menu cache and a text index do not make the marketplace correct under load. Capacity claims, payment and the order lifecycle have their own concurrency evidence in earlier modules, and nothing here tests them. This gate also does not cover cache behaviour across several API instances, a Redis failover with data loss, or a search relevance ranking beyond the text score MongoDB returns. Those are operational questions for Module 25 and honest limits to write in your notes.

Leave the gate open if any measurement row is missing rather than filling it from another machine. Module 25 deploys this service, and the deploy is where a cache that assumed a single process starts to fail; a clean local measurement gives you a baseline to compare against. Keep the fixture, the key names and the harness command in `docs/cache-decisions.md` so the deployed run can reuse them unchanged.
