# Deploy gate and restart survival

This gate asks for one public HTTPS origin and a set of measurements taken from outside it. A URL alone is not evidence. Anyone can paste a link to a page that loads. The evidence is a paid test order that both cooks can see, a stream whose heartbeat arrives on time through the host's proxy, and a restart after which Lina's phone recovers without a manual refresh.

Set the frame before you start. You are demonstrating the deployed system, not your laptop. Keep the client and API origins visible in the address bar and the network tab, and keep one terminal open with the stream probe from 25.02 so timings come from a program rather than from memory. Write the release revision for the API, the worker and the client at the top of `docs/deploy-decisions.md`; if the client was built from a different commit, say so and explain why the bundle is still compatible.

## The deploy record

The record has four parts, and each has to be readable by someone who was not there. The first is the host and plan, with the date you checked that a long-lived streaming response works there. The second is the environment key list, with the source of each value and no values in the file. The third is the release revision for each of the three processes. The fourth is the rollback target: the previous known-good revision and configuration, and whether the API and worker must move together because a queue payload changed.

A missing rollback target fails this section even when everything runs. You cannot claim operational control over a system you cannot leave. Rehearse it once with a low-risk redeploy of the same revision, confirm readiness afterwards, and note the time it took. Do not rehearse with a database reset; application rollback cannot undo a placed order or a captured payment.

## Secrets and configuration evidence

Show three things. First, `git log -S 'sk_test_' --oneline --all` and `git log -S 'MONGODB_URI' --oneline --all` return nothing. Second, `grep -r "localhost" client/dist/assets | head` returns nothing, and no `VITE_` variable in the bundle is a secret. Third, the only place a credential appears in your evidence is the host's settings page, captured with the values masked.

Then explain one rotation you performed. The usual candidate is the access and refresh secrets, because a development value may have appeared in a screen recording or a pasted log. State what invalidating every session cost you, which is one redeploy and one forced login. That answer shows you understand the difference between hiding a value and changing it.

## One traced order on the live system

Run a single order end to end and connect every row with one attempt ID. Log in as a diner in the deployed client, pick today's 13:00 window in `Asia/Gaza`, and order from two kitchens. Note that the client never shows a dish past its own cutoff; a slow dish should already be absent while the fast dishes remain. Pay with a Stripe test card, then open the cook board for each kitchen and confirm each cook sees only their own group.

Then have one cook accept and move the order to cooking while the diner's tracking screen is open. This is the moment the whole module exists for. The status should arrive without a refresh, on a connection that the proxy passed through as it was written. Record the cook action time, the API publish time from the log, and the time the new status appeared on the screen. A two-second gap is fine. A thirty-second gap points back to 25.02's buffering layers, not to the state machine.

The refusals belong in the same section. Request the API over plain HTTP and show the redirect or the refusal. Send a login from an origin you did not allow and show the browser blocking it while curl succeeds. Open the stream without a cookie and show `401`. Try to open another diner's stream with Lina's cookie and show `403` from the isolation test written in M8. These four responses prove that production still enforces what development enforced.

## Stream measurements

Paste the probe output before and after your fixes. The failing run should show a compressed response or batched heartbeats, and the passing run should show a first frame in well under a second and two heartbeats roughly twenty seconds apart. If you never had a failing run, say so and show the header that would have failed: a stream served with `content-encoding: gzip` and no `X-Accel-Buffering: no`.

Include the raw header block from `curl -N -D -` for the stream route. It must show `content-type: text/event-stream`, `cache-control: no-cache, no-transform`, and no content encoding. Also show the server's `retry:` value and the heartbeat comment as the client receives them, because a value you set in code and a value that leaves the process are not always the same.

## Restart survival

Restart the API while the tracking screen is open and the probe is running. Then restart the worker while one job is queued. These are two different tests and both are required.

For the API, record the restart time, the time the second stream connection was accepted, and the time the post-restart status appeared. The client should pass through a reconnecting label and return to live without a page reload. The timeline should contain each event once. If you see a duplicate row, the client is not applying the snapshot plus delta rule from M23, and that is a stream correctness bug rather than a deploy bug.

For the worker, stop it, place one test order, and confirm the queued job completes after the worker starts again. The paid order must exist on the kitchen board during the outage, because placement is database state and the alert is a convenience. Then restart the worker a second time and show that the notification effect does not double. Do not flush Redis between steps; the queued job is the evidence.

## Gate checklist

- [ ] Live client and API both answer on HTTPS, with the API origin serving `/health`.
- [ ] `docs/deploy-decisions.md` records host, plan, date checked for streaming support, and the three release revisions.
- [ ] Environment key list is documented with sources, and no secret value appears in the repository or the client bundle.
- [ ] `.env.example` lists every required key with empty or safe values.
- [ ] A previous known-good revision and configuration are recorded, and a low-risk rollback was rehearsed.
- [ ] One traced two-kitchen test order on the deployed app, with one attempt ID, both orders and both cook views.
- [ ] A dish past its own cutoff is absent from the live browse while a fast dish in the same window remains.
- [ ] Stream probe output shows a first frame under 3 seconds and heartbeats at least 15 seconds apart.
- [ ] Stream response headers include `text/event-stream`, `no-cache, no-transform`, and no `content-encoding`.
- [ ] API restart while tracking: reconnect is automatic, the diner sees a fresh snapshot, and the timeline has no duplicate event.
- [ ] Worker restart: a queued job completes after restart, and a second restart does not duplicate the notification effect.
- [ ] Plain HTTP, a disallowed origin, an unauthenticated stream and another diner's stream all fail with the documented status.
- [ ] CORS origin and cookie attributes are set for the deployed origins, and browser login survives a page refresh.
- [ ] Stripe webhook endpoint points at the deployed API, and a test event is accepted with a valid signature.
- [ ] README deploy section lets a reader repeat the release without reading this lesson.

## Learning log

1. Which layer held your stream bytes, and which single measurement identified it before you changed any code?
2. What did the API restart cost Lina in seconds, and which two values in your client made the reconnect invisible?
3. Which production value did you rotate rather than hide, and what did that invalidate?
4. What is your rollback target, and why must the API and the worker move together or separately for your release?
5. Your worker is down for ten minutes at lunch. What does a diner see, what does a cook see, and which record proves the order was still placed?

## What this gate does not prove

This gate does not prove that the deployed system survives a busy window. Twenty parallel checkouts, hold expiry under load and reconciliation drift are M26's evidence, and they need the deployed app precisely because localhost timing hides races. It also does not re-prove stream correctness, which M23 owns, beyond the single reconnect in the restart test.

Close the gate only when the evidence files are committed. If the live URL is reachable but the stream buffers, leave the gate open: the deploy is the foundation for the load evidence, and a hidden buffering defect will look like a slow cook during the demo.
