# Payment processing gate

Sufra now has a payment design for one diner checkout across two kitchens. M19 prepares held claims and draft orders. M20 creates one PaymentIntent from a fixed server total, verifies Stripe's webhook, confirms both claims, and publishes both kitchen orders only when the whole attempt is consistent. It also records paid but unfulfillable attempts for refund and returns one kitchen's share when that kitchen later rejects. This gate requires evidence for all of those boundaries, not a card form screenshot.

Prepare a two-kitchen attempt with known claim IDs, draft order IDs, stored shares and one total. The shares must add exactly to the total in integer minor units and use one currency. Run the payment route as the owning diner. Show that Stripe receives one creation request for the stored total and that the browser receives only the client secret for that attempt. Refresh or double-submit; the same PaymentIntent returns. Send the request as a second diner; no secret or attempt details appear.

## Payment and webhook evidence

Verify that an incomplete M19 attempt cannot create a PaymentIntent. Release one kitchen claim, remove one draft or corrupt the share sum, and show zero Stripe creation calls. The route must not repair an incomplete checkout by charging for what remains. A valid attempt should carry a stable Stripe idempotency key and persisted intent ID so a lost response can be recovered without a second intent.

Send a signed snapshot `payment_intent.succeeded` event through the actual raw-body route. Show signature verification, a durable inbox row, the intent-to-attempt mapping, amount and currency comparison, and the resulting claim and order states. Both claims change from `held` to `confirmed` without another capacity debit. Both orders change from `awaiting_payment` to `placed` and become visible only after the placement publication condition is complete. The cook's view remains scoped to their own kitchen order.

Send the same event again and send it concurrently. The result must be unchanged: one attempt, one PaymentIntent, two confirmed claims, two placed orders and one notification outbox row per kitchen. Change one byte of the signed body and prove the request fails before state changes. Send a signed `processing` event and prove it does not place orders. These tests separate a trusted payment signal from an untrusted browser result and from a payment that has not completed.

## Failure and refund evidence

Stop the reconciler after confirming only one claim, then restart. The retry must finish or enter a durable conflict state without exposing one kitchen job. Stop after the first order write and verify the kitchen query still hides the entire purchase until publication completes. A green HTTP response with a partially placed cart fails this gate.

Let M21's expiry worker release a hold before a verified success event arrives. The webhook must not revive the released claim or place either order. It records `refund_required`, compensates any other retained group, and starts one full-refund request for the original attempt total. Replay the success and refund work; the same refund identity should be recovered. The diner sees that payment was received but the order could not be placed, with a truthful refund status. Neither cook sees a job.

For the partial-refund case, first complete a valid payment and placement. Reject only Beit Hanan's stored 700-minor-unit share. Stripe receives one refund request for 700 against the original PaymentIntent, while Umm Yousef's 1800-minor-unit order continues. Change the current sweets price and prove it does not change the refund. Repeat the rejection and worker; the refund ledger and Stripe object stay singular. Test the total refundable balance if both kitchens later reject.

## Review the security and state boundaries

Inspect configuration. Stripe's secret key and webhook signing secret are server-only; the test and deployed webhook secrets are not mixed. The raw body reaches signature verification unchanged. The client secret is returned only to the attempt owner and is absent from URLs, logs and analytics. The event inbox has a unique event ID and a recovery path for a worker that stops mid-event. The refund ledger has stable operation keys, a unique rejection request per order and an aggregate amount guard.

Read the diner and cook screens. A payment result is not kitchen acceptance. The diner may see "confirming" before the webhook finishes. The cook sees a placed kitchen order only after the whole paid attempt is published. A rejected kitchen order has its own refund status; another kitchen's active order remains visible. An expired paid attempt has no kitchen jobs and a support trace. These views should agree with the attempt, claim, order and refund rows, not with a browser callback flag.
