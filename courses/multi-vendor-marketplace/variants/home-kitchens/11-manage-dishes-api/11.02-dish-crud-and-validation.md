# Dish fields, validation and ownership

The dish model from lesson 5.4 already has the fields. What it does not have is a contract: which values the API accepts, which values it refuses, and what it says when a second cook tries to change the first cook's menu. A Mongoose schema with `min: 1` will happily accept `loadUnits: 7.5` if the field is declared as a plain Number, will accept `activeWeekdays: [1, 1, 2]`, and will not tell a cook anything about the refusal in a way the form can show.

This lesson writes the dish API: five routes, one validation contract and one ownership rule. The ownership rule is the part that most projects get wrong, because it is easy to check a role and call it permission. A cook role says the account may manage a menu. It does not say whose menu.

## Five routes, one owner

```txt
GET    /api/v1/cook/dishes?status=active       list dishes for the caller's kitchen
POST   /api/v1/cook/dishes                     create a dish in the caller's kitchen
PATCH  /api/v1/cook/dishes/:dishId             update allowlisted fields
POST   /api/v1/cook/dishes/:dishId/publish     move draft or paused to active
POST   /api/v1/cook/dishes/:dishId/hide        move active to paused
```

None of these take a `kitchenId`. The kitchen is resolved from the authenticated account, through `Kitchen.findOne({ ownerUserId: principal.userId })`. A path parameter invites a client to send someone else's identifier, and a body field invites the same thing with fewer characters. Keeping the resolution server side means the only way to write a dish is to own the kitchen it belongs to.

Status is not a `PATCH` field either. Publishing and hiding are separate routes because they carry different preconditions, and the module gate will check both of them. A generic update that accepts `{ status: 'active' }` would skip the fit check that lesson 11.3 adds, and the check would then only exist in the form.

The update route accepts a fixed allowlist: `name`, `description`, `priceMinor`, `currency`, `prepMinutes`, `loadUnits`, `maxPerOrder`, `allergens`, `allergenNote`, `activeWeekdays`. Everything else is refused rather than ignored. Silently dropping a field the client thought it saved is worse than refusing it, because the cook sees a success message and a value that never changed.

## Write the validation contract

Put the rules in one function that the create and update routes share. The schema keeps its bounds as a backstop for direct database writes, and the service narrows them to what the product actually means.

| Field | Rule | Error code |
|---|---|---|
| `name` | trimmed, 2 to 60 characters | `INVALID_NAME` |
| `priceMinor` | safe integer, 50 to 50000 (0.50 to 500.00) | `INVALID_PRICE` |
| `currency` | `ILS` for this course | `INVALID_CURRENCY` |
| `prepMinutes` | integer, 5 to 360 | `INVALID_PREP_MINUTES` |
| `loadUnits` | integer, 1 to 20 | `INVALID_LOAD_UNITS` |
| `maxPerOrder` | integer, 1 to 20, not above `floor(capacity / loadUnits)` | `INVALID_MAX_PER_ORDER` |
| `allergens` | array of values from the closed list, no duplicates | `INVALID_ALLERGEN` |
| `allergenNote` | trimmed, 0 to 200 characters | `ALLERGEN_NOTE_TOO_LONG` |
| `activeWeekdays` | 1 to 7 distinct integers from 0 to 6 | `INVALID_WEEKDAYS` |

Three of those rows need an explanation, because a reader can see the number and miss the reason.

`prepMinutes` starts at 5 rather than 1. A one minute dish is almost always a typing accident in a form that expects minutes, and no cook starts and finishes a listing in under five minutes. The upper bound of 360 is generous on purpose: a long preparation time is legitimate, because a diner orders ahead of the window and a slow dish simply closes earlier. Above six hours the cook is describing a pre-order product that this course does not model, and a value in the thousands is nearly always a slip such as 900 typed into a minutes field.

`maxPerOrder` is checked against capacity as well as the schema bound. A dish with `loadUnits: 3` in a kitchen whose largest window holds 10 units cannot allow a max of 5, because five orders would need 15 units from a window that only has 10. The check uses the same largest window capacity that the publish route uses, so the two rules cannot disagree.

`activeWeekdays` refuses an empty array. An empty list could mean "never" or "every day" depending on who wrote the query, and a field with two plausible readings produces a bug that depends on which module reads it first. The client offers an "every day" button that fills all seven values, and the API stores what it receives.

```js
// server/src/modules/dishes/validate-dish.js (excerpt)
export const ALLERGENS = ['gluten', 'dairy', 'egg', 'sesame', 'nuts', 'fish', 'shellfish', 'soy'];

export function validateDishInput(input, { maxWindowUnits }) {
  const errors = [];
  const add = (field, code) => errors.push({ field, code });

  if (typeof input.name !== 'string' || input.name.trim().length < 2 || input.name.trim().length > 60) {
    add('name', 'INVALID_NAME');
  }
  if (!Number.isSafeInteger(input.prepMinutes) || input.prepMinutes < 5 || input.prepMinutes > 360) {
    add('prepMinutes', 'INVALID_PREP_MINUTES');
  }
  if (!Number.isSafeInteger(input.loadUnits) || input.loadUnits < 1 || input.loadUnits > 20) {
    add('loadUnits', 'INVALID_LOAD_UNITS');
  }
  if (!Number.isSafeInteger(input.maxPerOrder) || input.maxPerOrder < 1 ||
      input.maxPerOrder > Math.floor(maxWindowUnits / input.loadUnits)) {
    add('maxPerOrder', 'INVALID_MAX_PER_ORDER');
  }
  const days = input.activeWeekdays;
  if (!Array.isArray(days) || days.length < 1 || new Set(days).size !== days.length ||
      days.some((d) => !Number.isInteger(d) || d < 0 || d > 6)) {
    add('activeWeekdays', 'INVALID_WEEKDAYS');
  }
  return errors; // empty array means valid; the route maps this to 422 VALIDATION_FAILED
}
```

The function returns every failure, not the first one. A cook on a phone who submits three bad fields should see three messages, not three round trips. It is also easier to test: one call, one expected array.

## Allergens need honest copy

Allergens are a closed list because free text produces a menu where one cook writes "nuts", another writes "tree nuts", a third writes "no nuts" in the same field, and no browse filter can be trusted. The closed list keeps filtering possible.

It does not keep anyone safe, and the API must not imply that it does. An empty array means the cook listed no allergens, not that the dish is free of them. The public dish response says `allergens: []` and the client renders "No allergens listed by this kitchen". A badge that reads "allergen free" is a claim about the food, and Sufra has no evidence for it.

`allergenNote` exists for the sentence the list cannot hold, such as "fried in the same oil as the fish". It is short, it is the cook's own words, and it is copied into the order snapshot so a diner's record does not change when a menu is edited.

## Prove the owner, not the role

Here is the failure that the test suite has to catch. Cook B has a valid token, a valid cook role, and a real kitchen of her own. She sends `PATCH /api/v1/cook/dishes/:dishId` using the identifier of a dish that belongs to cook A. A route that checks only the role will accept the request and change A's price.

The fix is a filter, not a branch. Resolve B's kitchen, then update with both identifiers in the query:

```js
// server/src/modules/dishes/dish.routes.js (excerpt)
const kitchen = await Kitchen.findOne({ ownerUserId: req.user.userId }).lean();
if (!kitchen) return res.status(403).json({ code: 'NO_KITCHEN' });

const updated = await Dish.findOneAndUpdate(
  { _id: req.params.dishId, kitchenId: kitchen._id },
  { $set: changes, $inc: { revision: 1 } },
  { new: true, runValidators: true }
).lean();
if (!updated) return res.status(403).json({ code: 'NOT_KITCHEN_OWNER' });
```

The conditional filter is the rule. A dispatch table of permissions in a controller does the same job, and it drifts away from the query the first time someone adds a route, so put the scope in the write itself.

<TraceRequest title="Cook B edits cook A's dish">
  <TraceStep actor="Cook B" label="PATCH /cook/dishes/:dishId" detail="Valid token, own kitchen, A's dish id" />
  <TraceStep actor="API" label="Resolve B's kitchen from the session" detail="Never from the body or the path" />
  <TraceStep actor="Database" label="Look up dish id plus B's kitchen id" detail="No document matches" />
  <TraceStep actor="API" label="Return 403 NOT_KITCHEN_OWNER" detail="A's dish is unchanged, revision unchanged" />
</TraceRequest>

The trace stops at the database filter, and that is the point. Nothing was read, validated against the body, or partially written before the owner was proved. If the request body had an error as well, the caller receives the ownership refusal and learns nothing about A's dish.

Use `403` rather than `404` here, and know why. A dish identifier appears in the public browse response, so hiding its existence buys nothing. A `403` tells cook B plainly that the identifier is real and not hers, which is honest and stops a debugging session that would otherwise last twenty minutes. Some routes in this course do return `404` for unowned records, and the rule is consistent inside each module even if it is not identical between modules. Write the choice down in `docs/dish-decisions.md` so the next module inherits it.

A diner token on any of these routes gets `403 ROLE_FORBIDDEN` before the dish is loaded. The order of the checks is authenticate, then role, then resolve kitchen, then load the dish owned by that kitchen, then validate the body. Reordering those steps leaks information or performs work for a caller who will be refused anyway.

## Start with the failing test

Write the ownership test before the route is finished, and watch it fail against the version that checks only the role.

```js
// server/test/dishes/ownership.test.js (failing first)
it('refuses a cross-cook edit and leaves the dish unchanged', async () => {
  const res = await request(app)
    .patch('/api/v1/cook/dishes/' + cookADish.id)
    .set('authorization', 'Bearer ' + cookBToken)
    .send({ priceMinor: 900 });
  assert.equal(res.status, 403);
  assert.equal(res.body.code, 'NOT_KITCHEN_OWNER');
  const after = await Dish.findById(cookADish.id).lean();
  assert.equal(after.priceMinor, 1800);
  assert.equal(after.revision, cookADish.revision);
});
```

Then add the field cases: a fractional `loadUnits`, an unknown allergen, duplicate weekdays, an empty weekday array, a `maxPerOrder` above the capacity floor, and an unknown field sprayed into the body. Each should return `422` with the field name and no write. Finish with the positive case: cook A edits her own description and sees `revision` increase by one.

If a test writes successfully through a direct call, the validation is in the client only. If a test returns `200` and the value is unchanged, the allowlist is dropping an allowed field. If a cross-cook request returns `500`, the query threw instead of returning no match, which usually means the two identifiers had different types.

## Verify the contract

Seed two kitchens and two cooks. Create maqluba through cook A's session with the Tuesday values from lesson 11.1: 90 minutes, 3 load units, max 2, 1800 minor units, Sunday to Thursday. Read it back and confirm the fields you sent, plus `kitchenId`, `status: 'draft'` and `revision: 0`. Try each invalid value and keep the responses.

Send one request with `kitchenId` set to cook B's kitchen and confirm the value is refused as an unknown field rather than quietly ignored. Then run the cross-cook patch, the diner patch and the unknown dish id, and record the three codes. They are the evidence for the gate in lesson 11.4.
