# Dish API gate

The dish API now has five routes, a validation contract, an ownership filter, a fit check and a price rule. This gate asks you to show that all five agree with each other, using two cooks, one diner and one order. It also asks you to name what the module does not do, because a menu API is easy to overstate: nothing here creates a dated window, claims capacity, or takes money.

Set up two kitchens on the same platform windows. Cook A owns Umm Yousef's Kitchen with a largest window of 10 units and a 60 minute general cutoff lead in `Asia/Gaza`. Cook B owns a second kitchen with its own dishes. The diner account has an order already placed against one of A's dishes, from whichever earlier module gave you a checkout path. If your project has no order yet, create a fixture order with `priceAtPurchase` set by hand and say so in your evidence note.

## Recap what each record owns

The Dish owns name, description, price, currency, preparation minutes, load units, the per order limit, allergens, the weekday pattern and a revision counter. It owns no availability, no remaining quantity and no dated deadline. The Kitchen owns the time zone, the service area, the pickup note and the weekly template, and the largest template capacity is the number the publish check compares against. The Order item owns the copied name, price, preparation minutes, load units and window times from the moment of purchase.

Those three lists are the reason the gate has four separate checks instead of one. A single "dish CRUD works" screenshot cannot show that the copies exist or that the ownership filter is in the query rather than in a hidden button.

## Run the four checks

The first check is ownership. With cook B's token, patch, publish and hide cook A's dish. Each of the three must return `403 NOT_KITCHEN_OWNER`, and afterwards A's dish must have the same price, status and revision. Then run the same three with the diner's token and expect `403 ROLE_FORBIDDEN`. A hidden button in the browser is not evidence for either case.

The second check is validation. Send a fractional load, a preparation time of 2, an unknown allergen, a duplicated weekday, an empty weekday array, a `maxPerOrder` above the capacity floor, and a body containing a `kitchenId` field. Each must return `422` with the field name, and the stored dish must not change. Group them in one table in your evidence file with the request and the response for each row.

The third check is fit. Publish a 12 unit dish and read `DISH_CANNOT_FIT` with `largestWindowUnits: 10`. Publish a dish with 130 preparation minutes and read a `201` carrying an `EARLY_CUTOFF` warning, not a refusal, then find the early cutoff label the cook now sees on that dish. Lower A's Monday lunch capacity to 8 and read the `affectedDishes` list in the schedule response, then confirm the affected dish is still active and now flagged on the cook's list.

The fourth check is the price snapshot. Read the diner's order total before the edit. Change the dish price, then read the order again: the total, `priceAtPurchase` and `prepMinutesAtPurchase` must be identical. Change the preparation time as well and confirm the order's cutoff and window times did not move. This is the check that a reviewer should watch you perform live, because it is the one where a `populate` sneaks back in during a later refactor.

## Gate checklist

- [ ] A cook can create, update, publish and hide a dish in her own kitchen, and each response carries the new revision.
- [ ] Cook B is refused on A's dish for update, publish and hide, with `403 NOT_KITCHEN_OWNER` and no change to the stored document.
- [ ] A diner token is refused on every dish write route before any dish is loaded.
- [ ] Every validation rule in the table rejects with a field specific code, and an unknown field such as `kitchenId` is refused rather than ignored.
- [ ] Status changes happen only through the publish and hide routes, and neither route accepts a status in the body.
- [ ] A dish whose load exceeds the largest window is refused at publish with both numbers in the response.
- [ ] A dish with a long preparation time is published with an `EARLY_CUTOFF` warning, and the cook sees the resulting cutoff label.
- [ ] Lowering a weekly capacity reports affected dishes without unpublishing them or touching any window or claim.
- [ ] Changing a price or a preparation time leaves an existing order's purchased fields, total and window times unchanged.
- [ ] A cart re-prices at checkout and shows the new total before the payment step starts.
- [ ] Requests, responses and before and after database rows are saved in `docs/EVIDENCE.md`.

If the cross-cook patch returns `200`, the update filter is missing `kitchenId`. If it returns `404`, the course chose `403` for this module and the response is inconsistent with the written decision. If a valid edit returns `200` with an unchanged value, the allowlist is missing a field. If the order total moves after a price edit, a receipt path is reading the dish instead of the snapshot.

## Check the fit rule

```quiz
type: mcq
id: sufra-dish-q1
question: A cook publishes a dish with 12 load units in a kitchen whose largest weekly window holds 10 capacity units. What should the publish route do?
options:
  - Refuse it and name the largest window capacity
  - Publish it and rely on the cart to reject every attempt until the cook raises capacity during a later week
  - Reduce the dish load to 10 so that it fits, and record the adjustment in the audit log
  - Publish it as a draft so it stays hidden, and block the hide route until the schedule grows
correct: 0
explanations:
  - A dish that no window can accept is a menu defect, and the cook needs the two numbers to fix it.
  - The cart is not a menu editor, and a dish that can never be ordered teaches diners to distrust the list.
  - Silently rewriting a cook's declared effort changes the promise she made about the work.
  - A draft is a state a cook chooses, not a hiding place for a rule the API refused to apply.
```

## Learning log

Answer these in `docs/learning-log.md` with the request, response or document that supports each answer. One short paragraph each is enough.

1. Which part of the update query stopped cook B, and what did you see in the database to confirm nothing was written?
2. Why does `maxPerOrder` depend on capacity rather than on the schema's upper bound alone, and what value did you compute for maqluba at three load units in a ten unit kitchen?
3. What did the schedule save report when a dish stopped fitting, and why was the dish not unpublished automatically?
4. Which field on the order item made the receipt survive a price change, and where is that value written?
5. What does the dish API still not answer about a diner ordering this dish at 11:31 today?

The last question is the bridge to the next two modules. A dish declares what it costs to cook. It does not know which dated window will offer it, how many units remain in that window, or whether its cutoff has already passed. Those answers need generated windows from the delivery window module, and the capacity claim from checkout.

When the checklist has evidence behind every line, the cook can manage a menu safely. Keep the ownership suite as a regression test, because the dish dashboard in the next module adds a second surface that reads the same records, and it will be tempting to give that surface a route that trusts its identifiers.
