# Cart UI gate

A cart page can pass a click-through and still be unusable. The failures this gate looks for are quiet ones: a header that says 13:00 above a line that points at 18:00, a total that falls after a window change with no sentence explaining it, a quantity stepper that double-fires on a slow connection, and an error state that replaces the diner's cart with a blank page. None of those show up when you tap through the happy path with a warm cache on a fast laptop.

Prepare the fixture from Module 17. One diner, two kitchens, one shared 13:00 to 14:00 interval in `Asia/Gaza`, a falafel plate that uses one load unit and a maqluba tray that uses three. Give Abu Sami an 18:00 window for the falafel plate, and give Umm Yousef an 18:00 window where the maqluba still misses the deadline because of its 90 preparation minutes. Record the cart ID, both kitchen IDs, both window IDs and the first revision before you touch the screen.

## The cart at 360 pixels

Open the page at 360 by 740. The delivery window appears in the header and stays visible while the groups scroll. Each kitchen has its own heading, its own subtotal and its own requested load, and no single pooled load number appears anywhere on the page. Read the subtotal and the requested load for each kitchen aloud and check them against the API response.

Then walk the page with the keyboard only. Reach the first stepper, increase it, reach the remove button, open the confirmation and cancel it. Focus must stay visible at every step on the light and dark themes, and cancelling must not send a request. A remove control that fires on focus loss is a real defect on a phone, where a stray scroll is enough to trigger it.

Slow the network to 3G and tap the stepper twice quickly. Exactly one increment must reach the server, the button must be disabled while the request is in flight, and the final quantity must match the cart after a refresh. If both taps land, the revision check will reject the second one only if you send the same expected revision, so check the network panel to see which request the server refused.

## A line removed on purpose

Remove the maqluba line and confirm. The response must return the cart at revision plus one, with the Umm Yousef group gone, since that line was its only content. Reload the page from the server and confirm the line is still gone, which proves the removal persisted rather than living in local state.

Then reproduce the stale write. Keep the page open in one tab, change a quantity in a second tab, and return to the first tab and press remove. The server should answer `409 CART_CHANGED`, the page should repaint from the returned cart, and the banner should say that the cart changed in another window. Screenshot the banner together with the repainted quantities. An implementation that shows an error and keeps the old numbers has not passed, because the diner cannot tell which version is real.

## A window change that drops one line

Open the change-window sheet and pick 18:00. The preview must leave the stored cart untouched; verify this by reading the cart from the API while the sheet is open and comparing the revision. The sheet should show the falafel line as available at Abu Sami's 18:00 window and the maqluba line as a named conflict with a sentence about preparation time, not a generic invalid marker.

Approve the removal of the maqluba line and commit. The stored cart must move to the 18:00 pair, keep only the falafel line under Abu Sami's new window ID, and increment the revision once. Both kitchens have a matching 18:00 window here, so the maqluba conflict comes from preparation time alone. That is the case which catches a UI that treats a matching window as availability, and a UI that only inspects the first conflict.

Now test the race. Preview again from a new cart state, and pause Abu Sami's kitchen through the schedule exception before pressing commit. The commit must fail, the cart must stay on its previous interval and lines, and the page must show the fresh conflict. The reviewer should be able to see the cart before, the paused kitchen record, the failed commit response and the unchanged cart after.

## The window that moved under the diner

Leave the cart page idle with the 13:00 interval selected, then move the server clock past the window's general cutoff, or fill the window from a second diner account. Trigger a read by changing a quantity or by returning to the tab.

The page must keep the lines on screen, name the cause and offer the right action. For a passed cutoff the message is that orders for this window have closed, with a button to choose a later window. For a full window the message is that the window has no space, with the same choice. Neither case may empty the cart silently, and neither may show a bare status code.

Check the same path with the network disconnected. The read fails, and the page must show that it could not reach the server rather than pretending the cart is empty. An empty cart and an unreachable cart look identical if you render both as zero lines, and one of those mistakes leads a diner to rebuild an order that already exists.

## Gate checklist

- [ ] Header shows one delivery window, each group shows its own kitchen, subtotal and load, and no capacity is pooled.
- [ ] The layout at 360 by 740 has no horizontal scroll, no truncated dish name and a reachable sticky footer.
- [ ] Keyboard-only navigation reaches every control with a visible focus state, and cancelling a removal sends no request.
- [ ] A double tap on the stepper produces one increment, proven from the network panel and the stored quantity.
- [ ] A stale write returns `CART_CHANGED`, repaints from the returned cart and shows the banner.
- [ ] The window preview leaves the stored cart and revision untouched.
- [ ] A preview shows one available line and one named conflict, and the commit applies only the approved removal.
- [ ] A kitchen paused between preview and commit leaves the cart unchanged and shows the fresh conflict.
- [ ] A passed cutoff or a full window keeps the lines visible with a cause and a next action.
- [ ] `docs/cart-ui-decisions.md` holds the fixture IDs, both revisions, the screenshots and the failed-commit response.

## Learning log

1. Which exact UTC pair did the cart header claim, and which window IDs sat under each kitchen group after the change?
2. What did the page show at the moment the revision conflicted, and which response field let it repaint without a reload?
3. Which line did you approve removing, and what sentence did the preview print instead of a generic invalid message?
4. How would your page behave if a cook deleted a dish that is in the cart, and which code would the diner read?

## What this gate does not prove

The cart still does not reserve cooking capacity, lock a price or take money. Those belong to Module 19 and Module 20, and a comfortable cart page proves nothing about a race between two checkouts. This gate also does not test a diner with two carts, an anonymous visitor who adds a line before signing in, or a saved cart opened on a second device a day later. Each of those is a real case with its own decision, and none of them is solved by a nicer layout.

If a check fails, leave the gate open and fix the state that produced it rather than the sentence in the banner. A `CART_CHANGED` that repaints correctly is good behaviour; a banner that hides a silent repaint is not. Module 19 will call this cart's load summary and then claim capacity from each kitchen, so the grouping and the totals you proved here become the input to a decision that moves real units. Keep the fixture and the evidence.
