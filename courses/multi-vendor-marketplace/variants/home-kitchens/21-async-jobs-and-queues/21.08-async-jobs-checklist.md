# Async jobs gate

Sufra now has a separate worker for work that outlives an HTTP request. The checkout path still claims capacity before payment is offered, and the verified payment path still decides paid versus refund-required state. The worker generates future dated windows, releases expired unpaid holds, and alerts cooks after complete paid placement. This gate asks you to show that each job can run late or twice without changing a diner promise incorrectly.

Start the API and worker as separate processes with one Redis queue and the same MongoDB domain records. Show `npm run worker` starting cleanly, subscribing to the named jobs and reporting safe IDs. Trigger a placed two-kitchen order. The API or webhook path should finish its durable state transition before the worker logs two notification jobs. Stopping the worker should delay alerts without losing the placed orders or changing their paid status. Restarting it should complete the pending work.

## Generator and expiry evidence

Run nightly window generation twice for one kitchen and local date. The second run should create no duplicate row under `{ kitchenId, startAt }`. Give the existing row a held claim and a reduced `remainingUnits` before the second run; both must remain unchanged. Pause a date through M9's `ScheduleException` and show no new public window for it. Change the host process time zone and show that the generated UTC instants still follow the kitchen's IANA zone.

Stop the worker before a scheduled generation tick, then run the recovery horizon scan after restart. It should fill missing future dates without resetting any claimed row. Save before-and-after window IDs, UTC instants, local labels, capacity counters and claim IDs. A scheduler log alone is not evidence that the desired seven-day horizon exists.

For hold expiry, seed a ten-unit window with a three-unit held claim and seven remaining. Let its stored deadline pass. The delayed job releases it and returns the counter to ten. Replay the job; the counter stays ten. Confirm a different claim before its expiry job runs; that job must leave the confirmed claim and counter untouched. Stop the worker before one expiry job is enqueued, then run the due-claim scanner and show that the hold is still released. A queue message is a wake-up hint; the claim's stored deadline and state control the transition.

Run a two-kitchen expiry with a forced stop after the first release. On restart, the worker or scanner finishes the second group and leaves the first unchanged. The attempt remains non-payable while compensation is incomplete. Race expiry against a verified Stripe success. If confirmation wins for both claims, the paid purchase may place. If release wins for either, the attempt enters the full-refund path and neither kitchen sees a job. No test result may show one placed sibling and one expired sibling.

## Notification and ownership evidence

Place two orders under one paid attempt with M20's `placementCompleteAt` set. Assert one outbox row and one job identity per kitchen. Each worker reloads only its kitchen order. A cook for Kitchen A must not receive Kitchen B's items or address. Remove the publication marker and replay the jobs; both should skip. Reject one order before its delayed alert runs; the worker should not send a new-order message for it.

Force the notification provider to fail after the first kitchen. Kitchen A's delivery record remains complete, Kitchen B retries, and neither order or capacity counter changes. Simulate a worker crash after a provider send but before job acknowledgement. Document whether the provider's idempotency key prevents a duplicate, or whether the alert may repeat while the kitchen board still shows one order. Do not claim exactly-once delivery from a BullMQ `jobId` alone.

## Review the boundaries

Inspect the job payloads. They should contain IDs and due times, not client secrets, card data or the full combined cart. Inspect the outbox and due scans. There must be a recovery path when MongoDB commits but Redis enqueue fails. The worker must use the M14 generator and M19 release service rather than a second, weaker copy of their rules. It must log errors and retry without hiding an overdue held claim indefinitely.

The API's observable status must remain truthful during a worker outage. A prepared attempt is not paid. A paid but not fully published attempt is confirming. A placed order is visible on the kitchen board even if its alert is delayed. A late paid attempt with released capacity enters refund reconciliation, not a cooking queue. Explain these states from durable database records in your gate review.

## Learning log

2. Which database predicate made your expired-hold retry safe, and what happened when payment confirmation raced that release?
3. Which outbox and order fields let a stopped notification worker resume without exposing one kitchen's order to another cook?

Save exact commands, process restart times, job IDs, outbox rows, claim states, window counters and fake notification calls in `docs/jobs-decisions.md`. A passing prose audit does not prove a running Redis worker. If the complete Sufra reference build and restart tests are absent, leave this gate open and the track unavailable.
