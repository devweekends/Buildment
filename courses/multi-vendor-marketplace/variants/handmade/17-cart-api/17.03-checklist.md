# Cart API gate

This gate is passed with two signed-in buyers, one piece in each state, a curl transcript and a total you can add on paper. A cart page that looks correct can still be holding two lines for the same bowl or reading another buyer's document, and neither is visible in a screenshot.

Set up the seed plus one fixture: an available piece, a sold piece, a held piece with a future expiry, an archived piece and a draft piece. Give the sold and held pieces different workshops so the grouping is visible in the response. Keep both buyer tokens in a scratch file that does not go into Git.

## Walk the add and the duplicate

Add the available piece as Lina. The response should be 200 with a line count of one and the piece's current price. Add it again and read the refusal: 409 with reason `already_in_cart`, not a 200 and not a second line. Reload the cart and confirm one line. Then open a second browser profile, sign in as Lina, and confirm the same cart appears, because the cart belongs to the account rather than the device.

Send the same piece with Omar's token. He gets his own cart with one line, and Lina's cart still has one line. Neither response should mention the other buyer. Then send `GET /api/v1/cart?buyerId=` with Omar's ID attached to Lina's token. The parameter must change nothing, and Lina's cart must come back.

## Walk the four refusals

Post the sold piece and read 409 with reason `sold`. Post the held piece and read 409 with reason `reserved`. Post the archived piece and read 409 with reason `withdrawn`. Post the draft piece and read 404, because a draft is not public and a refusal that confirms its existence is a leak. Post a random ObjectId and read 404 for the same reason.

Then run the same four posts without a token and confirm every one is refused with 401 before any database work happens. The order matters: authentication, then validation, then the piece lookup. A refusal that runs a query first is a small inefficiency now and an information leak later, when the lookup is on another buyer's record.

## Put the same piece in two carts

This is the case the design exists for. Lina has the bowl in her cart. Omar adds the same bowl and succeeds, because a cart is interest and not a hold. Both carts should contain the bowl, and both responses should show it as available.

Now claim the bowl for Lina with a direct fixture update: set status held, a hold checkout ID and a future expiry, the same shape module 19 will use. Reload Omar's cart. The line must still be there, with state `reserved` and a message, and the line count must not change. Reload Lina's cart and confirm her line shows the same reserved state, because her cart does not own a hold merely because she is the buyer.

This is the evidence that the cart does not reserve. If Omar's line disappeared instead, the read is filtering unavailable pieces out of the response, and the buyer loses the record of what she chose.

## Add up the money

Send a cart with pieces from two workshops and a country that one of them does not serve. The response should contain two groups. Each group has its own subtotal from current piece prices, and its own shipping state: a rate with a transit range for the workshop that ships, and `not_shipped` with a null amount for the one that does not.

Add the two subtotals and the one shipping amount on paper and compare with `totalCents`. They must match exactly, with no rounding step anywhere. Then change one piece's current price in the database and reload the cart: the subtotal and total should move, and the line should show the new price, because the cart does not store one.

If your cart shows a line whose price differs from the piece document, find the field that copies it and remove it. A copied price is a promise the checkout cannot keep.

## Remove, repeat and confirm

Delete the available line and read 200 with `removed` true. Delete it again and read 200 with `removed` false. Neither answer is an error, because the buyer reached the state she wanted both times. Reload the cart and confirm the line is gone and the totals moved by exactly that line's amount.

Delete every line and read the empty cart: `itemCount` 0, no groups, and a total of 0. The cart document should still exist. Adding a piece again should work without a duplicate key error.

## Gate checklist

- [ ] Adding an available piece returns 200 and exactly one line, and adding it again returns 409 `already_in_cart`.
- [ ] Sold, held, archived and draft pieces are refused, and the draft and unknown IDs answer 404 without confirming existence.
- [ ] Every cart route answers 401 without a token, before any piece lookup runs.
- [ ] Two buyers have separate carts in the same database, and no response contains the other buyer's ID.
- [ ] A `buyerId` query parameter is ignored, because the session is the only source of the buyer.
- [ ] A second cart document for one buyer is refused by the unique index on `buyerId`, shown from the shell.
- [ ] One piece can sit in two carts at once, and a held piece stays in the cart as `reserved` rather than disappearing.
- [ ] The cart response line count equals the stored line count, including sold and reserved lines.
- [ ] Prices are current piece prices, and the grouped subtotals plus shipping equal `totalCents` in integer minor units.
- [ ] Shipping is answered once per workshop, with a rate, not-shipped, quote-required or paused state named separately.
- [ ] Deleting a line is safe to repeat, and an empty cart still exists and can accept a new line.
- [ ] The Cart schema stores an array of piece IDs with no quantity field and no stored price.

## Learning log

1. Show the conditional update that makes a duplicate add impossible, and explain what the ambiguous null result meant before the second read resolved it.
2. Which four refusals did you test, and which status code did each return? Explain why draft and unknown share one code.
3. What happened to Omar's line after Lina's piece became held, and why is that better than removing the line?
4. Write the two group subtotals and the shipping amounts in minor units, and show that they add to the total. Name the workshops.
5. What did the unique index do when a second cart was inserted for one buyer, and which database did you run that against?
6. Which test would catch a read that filters out unavailable pieces, and what did it report when you broke the read on purpose?

Write the answers with IDs shortened to their last six characters, amounts in minor units, and status codes. Keep tokens out of the log. A reviewer should be able to rebuild your two-cart state from the log and reproduce the reserved line without guessing which fixture you used.

## What this gate does not prove

No hold is created by anything in this module, so the gate does not prove that a piece is sold exactly once. That claim needs the conditional claim in module 19 and the payment webhook in module 20, and neither exists yet. The cart total is a display value; the payable amount is computed again at checkout from current records.

The gate also does not prove multi-currency behaviour, because the platform uses one currency. It does not cover a shipping quote for a destination marked as quote required, and it says nothing about deposits or balances, which belong to the commission path in modules 23 and 24. Currency formatting and a right-to-left layout are not tested here.

The next module renders this API as the cart page, with workshop groups, shipping lines and the warnings this response already carries.
