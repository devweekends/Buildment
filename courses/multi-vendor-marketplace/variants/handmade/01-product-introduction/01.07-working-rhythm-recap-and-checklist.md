# Working rhythm, recap and checklist

Ghurza's code and craft copy both need careful review. Work in small slices: model one relationship, test one valid action and one denied action, save a local commit, and record the next step. If power stops during a Workshop form, the last passing test and commit should tell you where to resume. A long uncommitted branch containing Piece, Cart, Quote and payment changes is harder to recover and explain. Local Git commits do not require a network connection.

## Recap the product contract

Describe a finished Piece in one sentence and a CustomRequest in another. The Piece has an exact physical identity, current status and Workshop price; the request asks for work that may be declined or quoted later. Name the Workshop owner, credited Artisan and Buyer. Explain which relationship grants seller edit permission and which only controls public attribution. A mentor should be able to read your ERD and reach the same answer.

Review one draft product description. It should state confirmed materials and technique, approximate dimensions, care and approved maker credit. Remove an invented motif meaning or guaranteed arrival date. Use handling and transit ranges when the Workshop has supplied them, and say when no estimate is confirmed. These writing rules are part of the buyer's technical contract: wrong words can create a promise the state machine and shipping profile cannot keep.

## Check your recovery plan

Run `git status` and record the last passing command in `docs/learning-log.md`. Write the next file to open and the smallest test to rerun. Keep any provider secret or buyer reference photo out of the commit. If the network is down, commit locally and push later. A small seed with fictional Workshops and owned placeholder photos is enough to start; large copied craft images are not required.

The entry check should produce a route ownership predicate, a filtered Piece query, a local Git checkpoint and a server-calculated total. If two answers are weak, complete their repair exercises before Module 2. If one is weak, name the exact practice task you will do alongside the skeleton. Do not carry a vague note such as "review backend" into a Week 3 payment race.

## Learning log

1. A sold Piece inspires a new request. Which record remains sold, which new record is private, and who may read it?
2. An Artisan is credited on a Piece. Which stored relationship lets a User change that Piece's price, and what does credit allow?
3. A Workshop says a custom order will arrive on Friday before a Quote exists. Which part of that sentence is unsupported, and what range or uncertainty should the UI show?
4. What is your last passing test or exercise, and what exact command will you run when you return after an interruption?

The gate passes when the two-sentence product explanation, actor matrix, respectful copy revision, Week 1 demo plan, diagnostic answers and recovery note agree. None of these artifacts claims that payment or production is built yet. Module 2 creates the running skeleton; the following weeks will turn this product contract into a marketplace and test each harder promise separately.

## Show the first recovery checkpoint

Open the learning log and read the last line as if you had been away for a week. It should identify a passing command, a current question and the next file or test. If it says only "continue Ghurza," make it specific. A useful note might say that the owner query sketch passes, the cross-Workshop Artisan assignment is still a planned negative test, and the next file is the Workshop model. This takes less than a minute to write and can save a long rediscovery session after a power cut.

Check your local Git state. The introduction artifacts can be committed before any API code: an actor matrix, respectful listing rewrite, two-path flow sketch and diagnostic answers. A local commit works without internet. Remove real names, secret keys and private reference images from the commit. Fictional test data is enough to explain the product and prepare the first seed.

## Challenge the opening promise

Ask a peer to read the finished-Piece sentence and custom-request sentence without seeing the roadmap. They should know that a Piece can be bought now only if available, while a request may be declined or quoted later. If they think the request is already an order, revise the language. Ask who edits the listing and who receives public credit. If they point to the same identity by default, revise the actor diagram. These misunderstandings will otherwise become schema fields that are expensive to unwind.

Try a date question, too. A buyer asks whether a commissioned tray will arrive next Friday before the Workshop has even reviewed the brief. The truthful response is that no date has been promised; the Workshop may provide a production and shipping range in a Quote after review. This does not make the product vague. It makes the state of the promise visible, which the later Commission timeline can preserve and update.

The checklist is complete when a mentor can inspect the product flow, actor matrix, entry repair plan, one respectful listing revision and one local recovery note. Keep them short enough to share over a weak connection. The project skeleton will now turn these decisions into folders and a health endpoint, then the data-model module will give every arrow a stored ID and test.
