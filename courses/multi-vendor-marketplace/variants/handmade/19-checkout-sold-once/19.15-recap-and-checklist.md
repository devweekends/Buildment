# Recap and checklist

The cushion cover exists once. Two buyers may read it as available, but one conditional database update may hold it for one Checkout. A multi-Workshop Cart can proceed only when every Piece is held for that same Checkout and the agreed offer remains valid. Failed attempts release only their own holds, using an owner predicate that cannot clear a later buyer's claim. A successful attempt creates one pending Order per Workshop with immutable line and shipping snapshots. Buyer and maker reads use session-derived scope. These are the guarantees this module has taught; payment and sale finalization remain in Ghurza M20.

## Evidence to bring to review

Show the route's conditional claim filter and update fields. The reviewer should be able to see Piece ID, eligible state, and the atomic transition to `held` with Checkout ID and expiry. Show the conditional release filter with the same Checkout ID. Include the test where an expired Lina hold is taken over by Omar and Lina's delayed cleanup matches zero. A comment that says "atomic" is not evidence if the update checks status in one operation and changes it in another.

Show the two-buyer race trace with one successful pending Checkout and one conflict. Name which Checkout owns the final Piece, and count pending payable OrderLines for that Piece. The count must be one. Run the test without assuming Lina wins every time. Show the multi-Workshop failure trace where the cover is claimed, the tray is lost, and the cover is released or safely placed in a durable recovery state. If a process stops after the first Order insert, demonstrate that recovery leaves no payable partial split Order. Run recovery twice and inspect that the second pass is harmless.

Show the two-Workshop successful plan: Checkout total, each Order total, line amounts and shipping amount in integer minor units. The totals must add exactly. Show the buyer route returning both Orders and each maker route returning only its Workshop Order. Include an attempted cross-Workshop Order ID read and its denied result. Show a post-checkout catalog edit and archive while the OrderLine retains the prior title, price, craft, maker credit, cover reference, shipping amount and range. Show a pre-checkout price or shipping change that triggers renewed buyer confirmation rather than silently changing the payable amount.

## Learning log

1. In the two-buyer run, which exact database write decided the winner, and what did the losing call receive? Include the final Piece status and Checkout ID comparison.
2. When Kareem's tray was unavailable after Amina's cover was held, which record made the partial claim recoverable, and which predicate prevented cleanup from releasing another Checkout's hold?
3. Which fields were frozen on each OrderLine and Workshop Order, and how did the totals compare with the Checkout total? Include actual minor-unit values.
4. Which query predicate protects Lina's buyer route, and which ownership relationship protects Amina's maker route? Describe the cross-Workshop denial test.
5. What changed on the live Piece after checkout, and what stayed the same in the Order response? How did the route behave when the price changed before checkout?
6. What remains for the payment module when a provider success arrives after a hold expires or after another buyer has claimed the Piece?

A passing submission includes executable tests, safe response traces, the state transition notes and a short explanation of the chosen multi-document strategy. If the implementation uses claim-and-compensate, include the crash and retry recovery path. If it uses MongoDB transactions, show the replica-set-backed local setup and that every participating operation uses the session. Do not state that independent writes are atomic because each individual Piece update is atomic; the group still needs its own failure design.

Mark the gate as passed only when the race, rollback, snapshot and access tests actually run against the learner build. A diagram without executable evidence is a design proposal. A UI screenshot without database counts cannot prove there is only one OrderLine. A test against a mock store alone cannot prove MongoDB's conditional update behavior. Use the checklist as a reviewer handoff: another engineer should be able to reproduce the one-winner result and identify a specific failed invariant if the test breaks.

The next module will create one payment attempt for the Checkout, handle provider webhooks idempotently, and resolve late success when a hold is no longer owned. Until that work exists, this Checkout is pending and not a completed sale. Keep the buyer language precise and never expose a paid receipt or maker fulfilment action from this module's pending records.

## Review one honest boundary

A reviewer should ask what happens if a provider reports payment success after Lina's hold expires and Omar owns the cover. The correct answer for this module is that payment processing is not yet authored here. The pending Order should not be presented as a guaranteed sale, and the payment module must compare the event with current hold ownership, prevent a second sale, and handle a charge that cannot be fulfilled through refund or an explicitly approved resolution. Record this as an open M20 test, not as a passed M19 case. That boundary matters to learner trust: a reservation deadline cannot be a hidden promise that payment will always complete.

Before marking the gate, have another learner read the conflict response and the two maker dashboards. They should be able to explain why one buyer sees a pending plan, another sees an unavailable Piece, and neither maker sees a paid fulfilment action. If the UI labels any pending Order as sold, fix that label even if database tests pass. The state machine should be understandable to the people using it as well as correct in the database.
