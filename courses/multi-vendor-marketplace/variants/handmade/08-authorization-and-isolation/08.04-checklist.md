# Isolation gate

The gate is a set of attempts, not a screenshot of a dashboard. Five sessions, three objects, and a written record of what each session received. A denied request that returns the buyer's name in its message is a failure even when the status code is 404, so every denial is checked twice: once for the code and once for the body.

Prepare the fixture before you start. Two workshops with visibly different names, two buyers, and one credited artisan with a buyer account. One piece owned by the first workshop, one custom request addressed to it from the first buyer, and one commission created from an accepted quote on that request. Write the three ids in the log before making a single call, because a test that cannot name the record it asked for cannot be repeated by a mentor.

## Gate checklist

- [ ] `docs/AUTHORIZATION.md` is committed with the request, quote and commission tables
- [ ] The third table covers published and draft pieces plus artisan credit
- [ ] Every route that returns a collection filters by the session owner in the query
- [ ] The five fixture sessions exist and their ids are recorded in the log
- [ ] Second workshop reading the commission returns 404 and no private fields
- [ ] Second workshop reading the request returns 404 and no brief, budget or photo id
- [ ] Second buyer reading the request returns 404 and no private fields
- [ ] Credited artisan reading the request and the commission returns 404
- [ ] Credited artisan editing the credited piece returns 403
- [ ] Buyer attempting to start production or post progress returns 403
- [ ] Workshop owner attempting to approve finished work returns 403
- [ ] Every denial body is checked for buyer name, budget, terms and amounts
- [ ] The transcript is saved under the isolation gate in `docs/EVIDENCE.md`
- [ ] The learning log below is answered in your own words

## Run the three objects

Start with the piece. The second workshop's owner tries to edit the first workshop's piece. Expect 403, and confirm the document is unchanged in the database afterwards. Then the credited artisan tries the same edit and expects the same 403, because credit is not ownership. Keep both attempts, because they fail through different checks and a later refactor may pass one while failing the other.

Move to the request. The second workshop's owner guesses the request id and asks for it. Expect 404 with a body that contains only an error code and a message. The second buyer makes the same request and expects the same answer. The credited artisan makes it a third time, and the answer must not change. Three sessions, one object, three denials, and none of them may mention the craft, the budget range, the wished date or a reference photo id.

Finish with the commission. Read the timeline as the buyer party and as the workshop party, and confirm both see the accepted terms but not each other's private material. Then attempt the actions in the wrong direction: the buyer starts production, the workshop approves its own finished work, the buyer adds a tracking reference, the workshop creates a balance payment. Each attempt is a 403 with no state change. A 200 on any of them means a route is checking the role and forgetting the side.

## Read the denial bodies, not only the codes

Copy each denial body into the log exactly as received. Then read it as if you were the attacker: does it confirm that a record exists, name a person, quote an amount or describe work in progress? A message like "this commission belongs to another workshop" is a small disclosure, and "the buyer asked for a large tray in walnut with a budget of 400" is a serious one. Rewrite the message until it says what the caller may do next and nothing about the record.

Check the list routes in the same pass. Ask for the maker inbox as the second workshop and confirm the response is an empty list rather than the first workshop's requests. Ask for "my commissions" as the second buyer and confirm the first buyer's commission is absent. An empty list and a 200 is a correct result here, and it is only correct if the filter was in the query. Confirm that by reading the handler, not by trusting the response.

Then repeat the whole run from a clean seed. A gate that passes only on the fixture you built by hand proves that you can click, not that the boundary holds. Rerun the seed, create a fresh request and a fresh commission through the API, and copy the new ids into the log. If any denial changes its code or its body on the second run, the difference points at state that the first run left behind, and that state is worth understanding before you close the module.

## Record what the gate does not prove

This gate proves object-level access for the records you created. It does not prove that every future route will use the helpers, that a new field will stay out of a serializer, or that a worker job will respect the same checks. Those risks are managed by review and by the tests you keep. Say so in the log, and add one line about the next route you will build and which helper it will call first.

The gate also does not prove the commission workflow itself. A transition service that checks the actor, the current state and the target state arrives in module 24, and it will reuse these helpers rather than invent new ones. What you prove here is the boundary those transitions will sit inside.

## Learning log

1. Which route did you test first, and what did it return before the fix? Paste the failing assertion and the line you changed.
2. Explain how your commission check finds the caller's side. Which stored field decides buyer from maker, and where does the caller's identity come from?
3. Why does a credited artisan receive 404 on a request and 403 on a piece edit? Explain the two different questions behind those codes.
4. Name one field you removed from a response and where the caller loses information. How does the client still do its job without it?
5. Show one list route and its query filter. What would a client see if the filter moved into JavaScript after the fetch?
6. What will you add to the matrix when module 22 adds request messages and reference photos, and which helper will both routes call?

## After the gate

Commit the matrix, the helpers, the tests and the transcript together. Then move to the workshop API. That module creates the workshop record this whole boundary depends on, and it must reject a second workshop for the same maker rather than quietly creating a second ownership chain. Keep the five fixture sessions; modules 9 through 12 will reuse them, and module 99 will ask you to demonstrate the same denials on the live URL.
