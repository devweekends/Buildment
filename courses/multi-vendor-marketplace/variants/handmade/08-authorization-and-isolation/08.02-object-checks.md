# Object checks on workshops, pieces and commissions

Here is the shape of the bug from 8.1, written as code that looks careful:

```js
router.get("/commissions/:id", requireAuth, requireRole("maker"), async (req, res) => {
  const commission = await Commission.findById(req.params.id);
  res.json(commission);
});
```

Two guards run and both pass. The caller has a session and holds the maker role. Then the route loads whatever id arrived and returns the whole document, terms, payments and progress included. Rana owns a ceramics studio in another city and this commission belongs to Bayt al Zayt. Nothing in the route noticed, because a role is a property of a person and access here is a property of a pair: this person, this record.

Function-level checks and object-level checks sit at different depths. A function-level check answers "may a maker send a quote at all", and it is the same answer for every maker in the system. An object-level check answers "may this maker send a quote on this request", and it needs the record in hand. Most real breaches come through the second. Keep both, and never let the first stand in for the second.

## Three helpers, one job each

Write the checks once, in one file, and call them from routes. Keep them small enough that a reviewer can read the whole file in two minutes.

```js
// server/src/modules/access/assert-access.js

// Returns the Workshop document. Throws 403 when the user does not own it.
export async function assertWorkshopOwner(userId, workshopId) {}

// Returns the Piece. Throws 404 when the piece is not inside this workshop.
export async function assertPieceInWorkshop(workshopId, pieceId) {}

// Returns "buyer" or "maker". Throws 404 when the user is neither party.
export async function assertCommissionParty(commission, userId) {}

// Returns "buyer" or "maker". Throws 404 when the user is neither party.
export async function assertRequestParty(request, userId) {}

// Middleware. 401 without a session, 403 when the role is not in the list.
export function requireRole(...roles) {}
```

Each helper returns the record or the caller's role on that record, and throws when the answer is no. The party helpers are async because a maker's side is not stored on the record: the helper resolves the caller's workshop by owner id once, then compares. Returning the loaded document matters: the route does not read the same record twice, and the serializer can choose fields by the role the check just returned. A helper that returns `true` forces every caller to fetch the object again, and the second fetch is where a different filter quietly creeps in.

The 404 in the request and commission helpers is a deliberate policy from 8.1. A buyer's request exists only for its buyer and its workshop, so a stranger receives the same answer as for an id that was never created. The alternative, a 403, tells the stranger that the id is real and that a private record sits behind it.

## Workshop ownership is resolved, never accepted

A maker owns at most one workshop in this course. Every seller route resolves ownership from the session, not from the request body. The pattern is short and it removes a whole class of bug:

```js
router.patch("/pieces/:pieceId", requireAuth, requireRole("maker"), async (req, res) => {
  const piece = await Piece.findById(req.params.pieceId);
  if (!piece) return res.status(404).json({ error: { code: "PIECE_NOT_FOUND" } });

  const workshop = await assertWorkshopOwner(req.user.id, piece.workshopId);
  const updated = await updatePieceFields(workshop._id, piece._id, req.body);
  res.json(toMakerPiece(updated));
});
```

The order matters. The route loads the piece, then asks whether the caller owns the workshop that holds it. It never trusts `req.body.workshopId`, because a body is client input and the client can send any value. If a future route creates a piece, it takes the workshop from `assertWorkshopOwner` or from the maker's own workshop document, and it ignores any workshop id in the body.

Ownership also has an invariant worth a test. One workshop per maker means a second `POST /workshops` must fail rather than create a second workshop whose pieces are invisible to the first dashboard. That rule is enforced with a unique index on the owner field and a service check that returns a clear 409.

## Artisan credit stays outside every check

`piece.artisanId` never appears in an authorization predicate. It appears in exactly two places: the write that validates the credit belongs to the same workshop, and the serializer that renders the approved display name. Write the first one as a data invariant, not a permission:

```js
// Write-time invariant, not an access check.
export async function assertArtisanBelongsToWorkshop(artisanId, workshopId) {}
```

Call it when a maker creates or edits a piece with a credit. A valid artisan from another workshop must be rejected with a field error, and the piece must not save. This protects attribution and stops one workshop from borrowing another workshop's maker as a marketing device.

The access side is simpler: an artisan has no seller route at all. There is no artisan login in this course, and if a credited person later receives a buyer account, the account carries the buyer role and nothing else. Include that person in every access test. A request from their token must return the same 404 as a stranger's, and a piece edit must return 403. Credit is the relationship most likely to be promoted into permission by a well-meaning refactor, so the test is the guard.

## Requests belong to a buyer, quotes and production to a maker

A custom request is buyer-only at creation. The route sets `buyerId` from the session and ignores any buyer id in the body, because a request written on someone else's behalf is a forged brief. Listing is scoped twice: `GET /me/custom-requests` filters by the session buyer, and the workshop inbox filters by the workshop the caller owns. Withdrawal is buyer-only and only while the request has no accepted quote. Review and decline are workshop-owner-only, and the owner is resolved through `assertWorkshopOwner`.

Quotes and production sit on the maker side. Sending, revising and expiring a quote are actions of the workshop that received the request, so the route resolves the request, checks the party relationship, and then requires the `maker` side. Starting production, posting progress, presenting the finished work and adding a shipping reference are the same: maker only. The buyer side of the commission is narrow by design: read the timeline, accept or refuse the finished work, pay the balance, mark delivery received.

Both sides read the same timeline. That shared read is where a careless serializer causes a leak. The dashboard for the workshop can include an internal note about material cost. The buyer view must not. Two serializers, named by audience, keep the difference visible in the code rather than in a comment.

## Deny without describing what you denied

A denial has three parts and no more: a status code, a machine-readable code, and a short message. `{ "error": { "code": "COMMISSION_NOT_FOUND", "message": "No commission with that id is visible to you." } }` is enough for the client and says nothing about the record. Do not include the buyer's name, the craft, the amount or a field list. Do not explain that the commission exists but belongs to another workshop.

Serializers are the second half of the rule. A route that returns `res.json(doc)` publishes every field the schema has now and every field someone adds next month. Write allowlists by audience: public piece, maker piece, buyer request, maker request, buyer commission, maker commission. The list is boring, and boring is the point. A test that asserts on the raw JSON keys catches a new private field before a buyer ever sees it.

```js
// One audience, one serializer, one test.
export function toBuyerCommission(commission) {
  const { _id, state, terms, payments, progress, shipping } = commission;
  return { id: String(_id), state, terms, payments, progress, shipping };
  // artisanCostNote and internalFlags are never copied here
}
```

Two questions decide whether a field belongs in a serializer. Who needs to see it for this screen to do its job, and what does a stranger learn if it leaks. A workshop's private cost note fails the first question for the buyer view and fails the second everywhere public. The approved artisan credit passes both, which is why it appears on a piece and on the buyer's commission, and never carries an account id.

One habit closes this lesson. When you write a route, say out loud which object it touches and which relationship authorizes it. If the sentence is "any maker may", you have written a function-level check and the route is not finished. If the sentence names the record and the relationship, the object check has a home, and the test in the next lesson has something precise to prove.
