# Browse collection gate

This gate is passed with a query log and four saved responses, not with a screenshot of a grid. A collection page can look finished and still carry three defects: a query count that grows with the page, a draft piece that leaks through a guessed ID, or a workshop whose sold work has disappeared from the product entirely. Each of those breaks a different promise, and each one is cheap to prove now.

Run everything against the module 5 seed so the numbers are comparable with the rest of the course. Three workshops, twelve pieces, two sold, one draft and one held. Clear any pieces you created by hand before the run, because an extra available piece changes the totals and makes the gate harder to review.

## Prove the default and the portfolio switch

Request the default collection and save the JSON. It should contain only available pieces, with a `page`, `limit`, `total` and `hasMore` envelope. Confirm the total matches the number of available rows in the database, counted directly, rather than matching what the client rendered. Then request `include=sold` and save that response too. Exactly the two sold pieces should be added, each with the word "Sold" in the card data and `canAddToCart` false.

Look for the states that must never appear. A draft piece has an unfinished title and unpublished photos, so its presence in a public list is a privacy defect rather than a cosmetic one. A held piece is promised to one checkout and would raise a conflict at the next buyer's checkout, which the card could have prevented. An archived piece is withdrawn by the workshop and has no business on a public page. Send one request per state and keep the empty results.

## Count the queries at two page sizes

This is the evidence a reviewer will ask for first. Run the counter at `limit=5` and at `limit=20` and put both numbers in the learning log with the operation names. The numbers must be equal. If the larger page costs more, something in the serializer or the card builder is reading the database per row, and the fix belongs in the route rather than in a cache.

Repeat with `limit=1000`. The route should clamp to 60 and still run the same number of operations. A route that accepts any limit is a performance risk, and it also lets one request ask for the whole catalogue, which on a metered phone is a real cost to the buyer rather than an abstract one.

## Break the filters on purpose

Each filter needs one passing case and one failing case. A ceramics request returns only ceramics and never a tatreez cushion. A price band from 2,000 to 4,000 minor units contains no piece outside it. `maxReadyDays=7` excludes the workshop with a two-week handling range, and `shipsTo` for the excluded country returns no piece from that workshop while returning pieces from the other two. Combine two filters and check that the result is the intersection rather than the union.

Then send input that should be refused. An unknown craft returns 400 with a field message, not an empty list. A minimum above the maximum returns 400. A negative price returns 400. A limit of zero returns either 400 or a clamped page, whichever you documented, and the same answer every time. A filter that silently ignores bad input teaches the client to send bad input.

## Check the leak a buyer would never see

Request a draft piece by its exact ID and expect 404 with no title, price or workshop name in the body. Do the same for an archived piece. Then request the held piece and read the whole response. It may say the piece is reserved, and it may show its public description, but it must not contain a checkout ID, a hold expiry or a buyer ID. Those fields describe someone else's payment, and a returned checkout ID would let a curious buyer poll another person's pending order.

Open the same three pieces through the client as well. The screen is not the boundary, but a page that renders a draft title after a 404 would suggest the client is using cached data from somewhere it should not have. Clear it and treat that as a defect.

## Gate checklist

- [ ] The default collection returns available pieces only, inside a response with page, limit, total and hasMore.
- [ ] `include=sold` adds exactly the sold pieces, each marked in text and each with `canAddToCart` false.
- [ ] Draft, held and archived pieces never appear in a public list, proven by one request per state.
- [ ] Query counts at five cards and twenty cards are equal, and the operation names are in the learning log.
- [ ] A limit of 1000 is clamped to 60 and still runs the same number of operations.
- [ ] Craft, price, ready range and destination filters each have a passing case and a failing case from the seed.
- [ ] An unknown craft, a negative price and an inverted price range each return 400 with a field message.
- [ ] A draft piece requested by ID returns 404 with no title, price or workshop name in the body.
- [ ] A held piece page shows a reserved state and no checkout ID, hold expiry or buyer ID.
- [ ] `explain("executionStats")` on the default request shows an index scan with documents examined close to rows returned.
- [ ] No database call sits inside a loop over cards, and the serializer is the only place that decides which fields are public.

## Learning log

1. What were the query counts at five cards and twenty cards, and which operation names appeared? If they differ, name the line that reads the database per row.
2. Which index serves the default request, and what did `explain` report for documents examined and rows returned? If you changed the index, show the before and after numbers.
3. How is the ready range stored, and which two save routes keep it fresh? Describe the test that fails when one of them forgets.
4. Which fields did you remove from the public serializer, and which test proves a draft piece cannot be read by ID?
5. What does a sold card offer instead of a purchase action, and why is that different from promising to tell the buyer when a piece returns?
6. Why does `canAddToCart` exist if checkout revalidates the piece anyway? What would break if the client trusted it as permission?

Write the answers as sentences with numbers, operation names and status codes. A reviewer should be able to repeat the two query counts from your log without opening your editor, and should be able to point at the exact index behind the plan you recorded.

## What this gate does not prove

The collection is served straight from the database, so nothing here proves behaviour under a cache, and the cache module later changes where the query count goes rather than whether the underlying route is sound. Text search is not built yet, and a craft filter is not a search index. The page has no personalised ranking, no recommendation and no translation, so a buyer reading Arabic in a right-to-left layout is out of scope for this module.

The gate also says nothing about payment, holds or carts. A card that says a piece is available is a statement about the moment the query ran. Between that moment and a checkout the piece can be held, and the later modules handle that conflict with a conditional write rather than with a friendlier list. Record that boundary in the log so the next reviewer does not read the collection as a reservation.

The next module takes this API and builds the buyer-facing gallery and piece page on top of it, including the one action a sold piece still supports.
