# Open-your-workshop gate

This gate uses one fresh account that has never had a workshop, one phone sized browser window and the network panel open. The account is the evidence, so create it at the start and do not reuse a workshop owner from module 9. If the account already has a workshop, the guard's most important branch cannot be tested and the rest of the gate proves very little.

Work at 360 CSS pixels wide for the whole pass, either in a device emulator or by narrowing a desktop window. A layout that passes at 1,200 pixels says nothing about the device the maker holds, and the failures at 360 are specific: a number input that pushes the page sideways, a save button that scrolls away from its error message, a row of navigation links too small to tap.

## Prove the redirect, not the empty page

Sign in as the new maker and watch where the app goes. It must arrive at the setup page, and the network panel must show one request to the workshop endpoint and nothing else. Then type `/workshop/roster` into the address bar, confirm that the redirect to setup carries the roster path in the `next` parameter, and confirm again that no roster request was sent. The console must be empty of 404 responses, because a 404 that arrives after a page has mounted is a redirect that happened too late.

Repeat with `/workshop/settings`, `/workshop/commissions` and `/workshop/pieces`. Four routes, one destination, four preserved `next` values. Then replace one of them with a full address such as `?next=https://example.com` and confirm that the app ignores it and goes to the workshop home after creation. A guard that trusts a query parameter is an open redirect.

Finish the create and land where `next` pointed. If you started from the roster, you should now be on the roster, empty and correct, rather than on a home page you did not ask for.

## Prove no second workshop

Open `/workshop/setup` again after the workshop exists. The app must redirect to the workshop home and the create form must not render, not even for a frame. Then press the back button and confirm the app does not bounce between the two addresses. The redirect uses replacement navigation precisely so that the back button has nothing to return to.

Now test the double submit on a second fresh account. Throttle the network to slow, tap save twice quickly, and watch the network panel: exactly one create request, and the button disabled with a progress label between the first tap and the answer. If a 409 appears in the panel, the form sent twice, and the maker paid for it with a message that reads like a failure after a success.

If a 409 does appear for another reason, for example because the same account created a workshop in a second tab, check that the app recovers: the provider should refetch, move to the workshop home and show a short message rather than a red form.

## Prove the making range, on a keyboard

Fill the form with a name, an area, a two paragraph story and a making range of 21 to 35 days. Then submit with a range of 40 to 14, and again with a maximum of 400. Each attempt must come back with a message beside the pair, the text must stay in every field, and focus must land on the first invalid control so that a screen reader user hears the problem rather than the page title.

Then clear the pointer for the rest of the journey. Tab from the top of the page to the save button without touching a mouse, type in both making fields, and submit. If any control needs a hover, or focus disappears behind a sticky element, fix it before recording the gate. Two checks make this concrete: the focus ring must be visible on every control you tab to, and the tab order must follow the visual order of the page.

## Prove the roster and the commission settings

Open the roster and add two credits. The first shows a name and a short bio. The second hides the name. Read the public sentence beside each switch: the first must name the Artisan and the second must read "Made by this workshop". Save, reload, and confirm both credits came back from the server rather than from component state.

Open the workshop's public page with no token at all and read the roster. The hidden name must not appear anywhere in the response, including in a property the page does not render. Then retire the first credit and reload both views: the public roster must lose the row and the owner roster must keep it in the retired section.

Now open the commissions page. Turn off accepting work, set the deposit default to 35 percent and the validity to 10 days, and save. Reload and confirm the values persisted. Then send a deposit of 95 percent and a validity of 300 days from the form and confirm that each is refused with a message naming the bound, and that the stored values are unchanged.

## Prove the retry, not the setup form

Drop the connection with the browser's offline mode, reload a page inside the workshop frame, and confirm that a retry screen appears. It must not be the setup form, because a maker with a workshop who sees a create form will fill it in and earn a 409. Reconnect, retry, and the page must come back without a second create request appearing in the panel.

## Gate checklist

- [ ] The account used had no workshop before the first request, and the network panel was open for the whole pass.
- [ ] Signing in lands on setup, and no request to a roster, settings, commissions or pieces endpoint fires.
- [ ] Typing `/workshop/roster`, `/workshop/settings`, `/workshop/commissions` and `/workshop/pieces` each redirects to setup with the path preserved.
- [ ] `?next=https://example.com` is ignored and the app lands on the workshop home after creation.
- [ ] After creation the maker reaches the preserved destination rather than a fixed page.
- [ ] Visiting `/workshop/setup` with a workshop redirects to the home page and the form never mounts.
- [ ] The back button after that redirect does not bounce between setup and the home page.
- [ ] Two quick taps end in one create request, one workshop and no visible 409.
- [ ] A deliberately injected 409 moves the app to the workshop home with a short message.
- [ ] A range of 40 to 14 and a maximum of 400 are each refused with a message beside the pair, and every typed value survives.
- [ ] Focus moves to the first invalid control after a refused submit.
- [ ] The whole create journey completes with the keyboard only, in visual order, with a visible focus ring on every control.
- [ ] The journey completes at 360 pixels with no horizontal scrolling, and every button is at least 44 pixels tall.
- [ ] Two Artisan credits exist with different display choices, and the public sentence beside each switch matches the choice.
- [ ] The hidden Artisan name appears nowhere in the public workshop response, including in unrendered properties.
- [ ] A retired credit leaves the public roster and stays visible in the owner's roster.
- [ ] Settings keeps the story, the area and the commission numbers after a reload.
- [ ] A deposit outside 10 to 90 percent and a validity outside 1 to 60 days are refused with the stored values unchanged.
- [ ] An offline reload inside the frame shows a retry screen and not the setup form, and reconnecting restores the pages.
- [ ] A buyer account is refused by every route in the workshop area.

## Learning log

1. Which route did you type directly, what did the address bar show after the redirect, and what did the network panel show? Name the requests that did not fire.
2. What did the `next` parameter contain when you were redirected from the commissions page, and what happened when you replaced it with a full address?
3. How did the form behave when you tapped save twice on a slow connection, and what in your code prevents the second request?
4. Which rule on the making range was hardest to write a message for, and where exactly does that message appear on the page?
5. Which control failed your keyboard pass first, and what did you change to fix it?
6. What does the app show for an offline reload inside the workshop frame, and how does that differ from the answer for a maker with no workshop?
7. Which two values decide whether a new Artisan's name appears on the public workshop page, and where does the public page show the hidden case?

## What a passing gate leaves behind

Four pieces of evidence. A short recording or three screenshots of the 360 pixel journey, including the setup form with a field error and the retry screen. The network panel captures for the direct address and the double tap. The public workshop page opened without a token, showing one credited name and one hidden credit. And the learning log with the seven answers.

Two honest limits go in the write-up. The gate proves the route guard and the form plumbing, not the workshop's facts: a workshop created with a misspelled name and an optimistic making range passes every check here, because the accuracy of those facts belongs to the maker. And the 360 pixel pass is a person with a pointer and a keyboard, not a real device with a camera notch and a thumb, so the plan is to run the journey once on a phone before the week two demo.

Do not delete the fresh account. Module 11 adds the Pieces routes inside this frame, and a maker who is one minute old is the best tester of every screen that follows.
