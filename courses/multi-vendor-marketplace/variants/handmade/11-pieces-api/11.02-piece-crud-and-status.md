# Piece fields, status and ownership

Four routes carry this lesson and one schema holds them all to a shape. Create writes a Piece inside the caller's workshop. Edit changes the descriptive fields a maker is allowed to change in the Piece's current state. Publish moves a draft to available, if the work is complete enough to show. Archive withdraws an available or draft Piece without deleting it.

The interesting part is not the create path, which is a short insert. It is the edit path, because the fields a maker may change depend on the status the Piece is in, and because status itself must never be a field a client can set. A build that accepts `status` in an edit body is one curl request away from selling a Piece twice or returning a sold object to the shelf.

## The schema

Start with the model. Every type here is chosen so that a wrong value is refused at write time rather than discovered on a page.

```js
// server/src/modules/pieces/piece.model.js (fields and validators, not the whole file)
const dimensionsSchema = new mongoose.Schema({
  heightCm: { type: Number, required: true, min: 0.5, max: 300 },
  widthCm:  { type: Number, required: true, min: 0.5, max: 300 },
  depthCm:  { type: Number, default: null, min: 0.5, max: 300 },
}, { _id: false });

const holdSchema = new mongoose.Schema({
  checkoutId: { type: ObjectId, required: true },
  expiresAt:  { type: Date, required: true },
}, { _id: false });

const pieceSchema = new mongoose.Schema({
  workshopId:  { type: ObjectId, ref: "Workshop", required: true, index: true },
  artisanId:   { type: ObjectId, ref: "Artisan", default: null },
  title:       { type: String, required: true, trim: true, minlength: 3, maxlength: 120 },
  craft:       { type: String, required: true, enum: ["tatreez", "olive_wood", "ceramics", "weaving", "other"] },
  materials:   { type: String, trim: true, maxlength: 300, default: "" },
  dimensions:  { type: dimensionsSchema, required: true },
  description: { type: String, trim: true, maxlength: 2000, default: "" },
  careNotes:   { type: String, trim: true, maxlength: 500, default: "" },
  priceMinor:  { type: Number, required: true, min: 1, validate: Number.isInteger },
  currency:    { type: String, required: true },
  photos:      { type: [String], default: [], validate: atMostSix },
  status:      { type: String, enum: ["draft", "available", "held", "sold", "archived"], default: "draft" },
  hold:        { type: holdSchema, default: null },
}, { timestamps: true });

pieceSchema.index({ workshopId: 1, updatedAt: -1 });
pieceSchema.index({ status: 1, craft: 1 });
```

The dimensions are an object with numbers, not a string, because module 16 filters and sorts on size and a sentence cannot be compared. The price is an integer with an explicit `Number.isInteger` validator, because a float that reaches this field will eventually reach a payment amount, and a payment amount of 239.99998 is a support ticket with no clean fix.

```js
// server/src/modules/pieces/piece.validators.js
export function atMostSix(photos) {
  return Array.isArray(photos) && photos.length <= 6;
}
```

Two indexes are enough at this stage. The workshop plus update time index serves the maker's own table in module 12. The status plus craft index serves the public browse in module 15. Add an index only when a query exists, and note the query beside it in `docs/erd.md`, because an index nobody can name a query for is a write cost with no reader.

## What the body may not say

The create route reads the descriptive fields from the body and writes five more of its own. The body supplies the title, craft, materials, dimensions, description, care notes, price and the photo URLs. The server supplies `workshopId` from the session, `artisanId` only after a check, an empty hold, the currency from config and `status` as draft.

A body that carries `workshopId`, `status` or `hold` is not an error. Those keys are dropped, because a client that sends them is guessing and a route that honours them is a hole. The most dangerous of the three is `hold`, because a client that could write a checkout id could reserve an object it has no order for.

The Artisan check runs before the insert and has three parts. The id must parse, the Artisan must exist, and the Artisan's `workshopId` must equal the workshop resolved from the session. A fourth check refuses an Artisan whose `retiredAt` is set. All four return a 400 with a field message on `artisanId`, because the maker can fix it by choosing a different credit, and a 403 would suggest she is not allowed to credit anyone at all.

## The edit route and its status aware field list

The edit route is where the status earns its place. A draft is fully editable. An available Piece may have its description, care notes, photos and price changed, because nothing has been promised yet and module 26 busts the cached collection when a price moves. A held Piece allows changes to the description, care notes and photos, and refuses the title, price, craft, materials and dimensions, because a checkout is holding a promise about this exact object. A sold Piece allows nothing through this route. An archived Piece allows nothing either, because it is out of the catalogue and comes back as a draft if the maker reworks it.

| Status | Fields this route may change | Why |
|---|---|---|
| `draft` | all descriptive fields, price, photos | Nobody can see it yet |
| `available` | price, description, care notes, photos, materials | Nothing has been promised |
| `held` | description, care notes, photos | A checkout holds a promise about title and price |
| `sold` | none | The object has an owner and an order line |
| `archived` | none | Relisting goes through a draft and a review |

Encode that table on the server as a function that takes the current status and returns the allowed field list, then pick from the body with it. A route that reads the table from the request, or that keeps a single list for every status, has moved the rule into the client where nobody can enforce it.

```js
// server/src/modules/pieces/editable-fields.js
const DESCRIPTIVE = ["title", "craft", "materials", "dimensions", "description", "careNotes", "photos", "priceMinor"];

const BY_STATUS = {
  draft:     DESCRIPTIVE,
  available: ["materials", "description", "careNotes", "photos", "priceMinor"],
  held:      ["description", "careNotes", "photos"],
  sold:      [],
  archived:  [],
};

export function editableFor(status) {
  return BY_STATUS[status] ?? [];
}
```

The route loads the Piece inside the caller's workshop, returns 403 if the filter matched nothing, and returns 409 `PIECE_NOT_EDITABLE` with an empty field list when the status allows no changes. A 409 is the right status here rather than a 403, because the caller does own the Piece. What she is asking for conflicts with the Piece's state, and the message should say so in one sentence.

## Publish is a conditional update

Publishing is a separate route, `POST /pieces/:id/publish`, and it does three things in one database call: it checks that the Piece is still a draft, it checks the publish requirements, and it moves the status. The requirements are a title of at least three characters, a price above zero, at least one photo and a description of at least forty characters. Those are the fields a buyer needs to decide anything, and the check runs on the server because a client that has an older copy of the form will happily send a publish request for a Piece that changed.

```js
// server/src/modules/pieces/publish.js (the update, not the handler around it)
const published = await Piece.findOneAndUpdate(
  { _id: pieceId, workshopId, status: "draft" },
  { $set: { status: "available" } },
  { new: true }
);
if (!published) throw httpError(409, "PIECE_STATE_CONFLICT");
```

The filter is the whole guard. Two tabs that both press publish end with one winner and one 409, and no read followed the write. A route that loads the Piece, checks `status === "draft"` in JavaScript and then saves by id passes a single tab test and fails on the second tab, which is the same failure module 19 will make the centre of its two buyer race.

## Archive is the same shape, with a different filter

Archive moves a draft or an available Piece to archived, and its filter allows both starting states in one query.

```js
const archived = await Piece.findOneAndUpdate(
  { _id: pieceId, workshopId, status: { $in: ["draft", "available"] } },
  { $set: { status: "archived" } },
  { new: true }
);
```

A held Piece is not in that list, so an archive attempt during a checkout returns 409 rather than withdrawing an object somebody is paying for. A sold Piece is not in the list either. Those two absences are the rule from the state diagram, written where it can actually be enforced.

There is no route that sets `status` to an arbitrary value, and no route that moves a sold Piece anywhere. Relisting an archived Piece is a deliberate two step: patch the archived record back to draft through a small `relist` route that requires a fresh review of the price and photos, then publish again. That is slower than a single toggle, and the slowness is the feature.

## What the routes look like

```ts
// server/src/modules/pieces/piece.routes.js (signatures only, mounted under /api)
router.post("/workshops/:workshopId/pieces", requireAuth, requireRole("maker"), createPiece);
router.patch("/pieces/:id", requireAuth, requireRole("maker"), updatePiece);
router.post("/pieces/:id/publish", requireAuth, requireRole("maker"), publishPiece);
router.post("/pieces/:id/archive", requireAuth, requireRole("maker"), archivePiece);
router.get("/workshops/:workshopId/pieces", requireAuth, requireRole("maker"), listWorkshopPieces);
```

Step four is the one to remember. The completeness check can run before the update, because a list of missing fields is a message and not a state change. The status check must not run before the update as a read, because between the read and the write a second tab can publish the same Piece.

## Three tests that fail on a naive route

Write all three before the fix. The first two are the pair from the read lesson, and the third is the one most builds forget.

```js
// server/tests/pieces.patch.test.js
test("another workshop cannot edit this piece", async () => {
  const res = await request(app)
    .patch(`/api/pieces/${coverId}`)
    .set(auth(kareem))
    .send({ title: "Something else", priceMinor: 1000 });

  expect(res.status).toBe(403);
  const stored = await Piece.findById(coverId).lean();
  expect(stored.title).toBe("Stitched cushion cover");
  expect(stored.priceMinor).toBe(24000);
});
// currently 200, and the title and the price both changed
```

```js
// server/tests/pieces.status.test.js
test("a sold piece cannot return to available", async () => {
  await Piece.updateOne({ _id: coverId }, { $set: { status: "sold" } });
  const res = await request(app)
    .patch(`/api/pieces/${coverId}`)
    .set(auth(amina))
    .send({ status: "available" });

  expect(res.status).toBe(409);
  expect((await Piece.findById(coverId).lean()).status).toBe("sold");
});
// currently 200, and a piece somebody paid for is on sale again
```

```js
// server/tests/pieces.publish.test.js
test("publish refuses a piece with no photo", async () => {
  const res = await request(app)
    .post(`/api/pieces/${draftId}/publish`)
    .set(auth(amina));

  expect(res.status).toBe(400);
  expect(res.body.error.code).toBe("PIECE_INCOMPLETE");
  expect(res.body.error.fields.photos).toBeDefined();
  expect((await Piece.findById(draftId).lean()).status).toBe("draft");
});
// currently 200, and an empty Piece appears in the catalogue
```

The second failure is the expensive one. A Piece that returns to available after it sold can be claimed again by the next checkout, and the first buyer's order line now describes an object that has been promised to two people. Nothing in the interface would look broken while that happened.

## The diff that closes the first two

```diff
 export async function updatePiece(req, res, next) {
-  const piece = await Piece.findByIdAndUpdate(req.params.id, req.body, { new: true });
-  if (!piece) return next(httpError(404, "PIECE_NOT_FOUND"));
-  res.json(piece);
+  const current = await Piece.findOne({ _id: req.params.id, workshopId: resolvedWorkshopId });
+  if (!current) return next(httpError(403, "NOT_YOUR_PIECE"));
+  const changes = pick(req.body, editableFor(current.status));
+  if (Object.keys(changes).length === 0) return next(httpError(409, "PIECE_NOT_EDITABLE"));
+  res.json(await applyPieceChanges(current, changes));
 }
```

The read is back in this handler on purpose, and it is not the race the publish route avoids. A descriptive edit does not change the status, so a read before a save cannot lose a sale. The status changes have their own routes with their own conditional updates, which is the division that keeps the race out of the general edit path.

## Acceptance criteria

- [ ] `POST /api/workshops/:workshopId/pieces` creates a draft in the caller's workshop and ignores `workshopId`, `status` and `hold` in the body.
- [ ] An `artisanId` from another workshop, a retired Artisan, and an id that does not exist are each refused with a message on `artisanId`, and nothing is written.
- [ ] A price with a decimal part and a price of zero are both refused.
- [ ] A seventh photo URL is refused, and six are accepted.
- [ ] `PATCH /api/pieces/:id` from another workshop returns 403 and the stored record is unchanged.
- [ ] The edit route refuses the fields its status table excludes, with 409 when nothing may change.
- [ ] `POST /api/pieces/:id/publish` refuses a Piece with no photo, no description, no price or a title under three characters, names each field, and leaves the status as draft.
- [ ] Two publish requests in a row end with one 200 and one 409 `PIECE_STATE_CONFLICT`.
- [ ] `POST /api/pieces/:id/archive` succeeds from draft and available, and returns 409 from held and from sold.
- [ ] A sold Piece cannot reach `available` through any route in the module.
- [ ] `GET /api/workshops/:workshopId/pieces` returns only the caller's Pieces and never accepts a workshop id from the query string.

## Bridge to the gate

The gate puts four Pieces into one workshop and proves the moves in the diagram: a draft that publishes, an available Piece that archives, a Piece that sells and then refuses every edit, and a Piece from the second workshop that refuses a cross-workshop patch. It is the smallest set that still catches a status field a client can set, which is the defect this module exists to prevent.
