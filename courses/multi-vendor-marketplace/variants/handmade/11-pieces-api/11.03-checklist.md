# Pieces API gate

This gate runs on two workshops, four Pieces and the same tokens you used in module 9. Amina's workshop owns a draft cover, an available bowl and a Piece that has already sold. Kareem's workshop owns one Piece of its own. Every request goes out with curl and comes back as raw JSON, and every claim in the checklist is answered by reading a stored document afterwards.

Write the expected table before the first request. Nine rows is enough: create returns 201 as a draft, publish on the complete draft returns 200, a second publish returns 409, archive on the available Piece returns 200, archive on a held Piece returns 409, a patch on the sold Piece returns 409 with no change, a patch from Kareem returns 403 with no change, a create with Kareem's Artisan id returns 400, and a seventh photo URL returns 400. When a response disagrees with the table, the table is the authority and the route is the bug.

## Start from a state you can describe

Begin with a development database whose seed you can re-run, and note the counts for Workshop, Artisan and Piece before you start. The gate is evidence, and evidence you cannot rebuild after a power cut is not evidence. One line with the database name, the seed command and the three counts is enough.

Record the ids of four Pieces: the draft, the available bowl, the Piece you will sell, and the archived one. Then change two of those states by hand in the database, because this module has no route that sells or holds a Piece. A direct `updateOne` that sets `status` to `sold`, and one that sets a `hold` subdocument with a checkout id and an expiry, are the fixtures this gate needs. Write them down as fixtures and never as evidence of a working checkout.

## Put four Pieces through the moves

Create the draft cover through the API with every descriptive field, one photo URL and a price of 24,000 minor units. Read the response and confirm three things: the status is draft, the `workshopId` is the one from the session and not a value in the body, and the currency came from config. Then create a Piece with a decimal price, and confirm a 400 with a message on `priceMinor` and no document written.

Publish the draft. The response must be 200 and the stored status must be available. Publish it again immediately and confirm a 409 `PIECE_STATE_CONFLICT` with the status still available. That pair is the cheapest proof that the transition is conditional rather than a read followed by a write.

Archive the available bowl and confirm the stored status is archived and that a second archive returns 409. Then attempt the same archive on the held Piece, which must return 409 with the status still held and the `hold` subdocument still present. A withdrawal that succeeds during a checkout is the failure this row exists to catch.

## Prove the credit rule

Send a create with the id of an Artisan belonging to Kareem's workshop while the path names Amina's workshop. The id is valid and the document exists, so this is the test that a malformed string would not catch. The response must be 400 with the message on `artisanId`, and the Piece count for Amina's workshop must be unchanged.

Retire the Artisan credited on an existing Piece and try to create a new Piece with that same id. It must be refused, and the existing Piece must still read with its credit intact. Then create a Piece with no `artisanId` at all and confirm it saves, because a workshop may choose to publish work without naming a maker.

Finally, send a create whose body carries `workshopId` set to Kareem's workshop and `status` set to available. The stored document must belong to Amina and must be a draft. Three fields, two rules, one request.

## Prove the boundary and the forbidden moves

Sign in as Kareem and patch Amina's sold Piece with a new title and a new price. The answer must be 403 `NOT_YOUR_PIECE`, the body must carry no Piece fields, and a re-read must show the old title, the old price and the status still sold. Save the raw request and the raw response together, because the pair is what turns a refusal into evidence.

Then use Amina's own token on the same sold Piece. Patch the description, patch the price, patch the status to available, and archive it. Four requests, four refusals, and the stored document unchanged after each one. The status attempt is the important row: a build that accepts `status` in a general edit body passes the first three and returns a sold cover to the shelf on the fourth.

Do the same against the archived Piece, then relist it through the two step path your build chose, and confirm the relist lands in draft and not in available. A relist that publishes directly is the same defect wearing a different route name.

## Prove the list is scoped

Call `GET /workshops/:workshopId/pieces` with Amina's token and confirm the response contains her four Pieces and nothing from Kareem. Call the same route with Kareem's token and confirm a 403. Then call it with a query parameter naming Kareem's workshop while holding Amina's token, and confirm the parameter is ignored.

Check the response shape while you are there. A Piece in the list may carry its title, craft, price, status, cover photo and credited name. It must not carry a buyer id, an order id, a checkout id from a hold, or another workshop's internal note. If a hold id appears in a workshop list response, remove it from the serializer now rather than after module 19 makes it valuable.

## Gate checklist

- [ ] The nine expected responses were written down before the first request was sent.
- [ ] Four Piece ids were recorded, and the sold and held states were created as documented fixtures rather than through a route.
- [ ] A create with a full body returns 201 as a draft, with the workshop from the session and the currency from config.
- [ ] A decimal price returns 400 on `priceMinor` and writes no document.
- [ ] A body carrying `workshopId`, `status` and a foreign `artisanId` changes none of the three.
- [ ] Publishing a complete draft returns 200 and stores available.
- [ ] A second publish returns 409 `PIECE_STATE_CONFLICT` and the status stays available.
- [ ] Publishing a Piece with no photo returns 400 `PIECE_INCOMPLETE` with the field named, and the status stays draft.
- [ ] A seventh photo URL is refused and six are accepted.
- [ ] Archive succeeds from available and stores archived.
- [ ] Archive on a held Piece returns 409, and the hold subdocument is still on the stored document.
- [ ] A patch from the second workshop returns 403 with no Piece fields and no stored change.
- [ ] Four patch attempts by the owner on the sold Piece each fail, and the stored document is identical afterwards.
- [ ] The same four attempts on the archived Piece fail, and a relist lands in draft rather than available.
- [ ] The workshop list returns only the caller's Pieces, ignores a workshop id in the query, and carries no buyer, order or checkout ids.
- [ ] The index list from the running database shows the workshop plus update time index and the status plus craft index.
- [ ] The raw 400, 403 and 409 responses are saved with their `error.code` values and no live tokens.

## Learning log

1. Which single write decided that your draft became available, and what did the second publish request receive? Quote the filter and the matched count.
2. Which field in the create body did you send with a wrong value to prove the route picks fields, and what did the stored document contain instead?
3. What did the cross-workshop patch return, and how did you prove the record was unchanged? Quote the code and the two values you compared.
4. Why is the refusal for a sold Piece a 409 and not a 403? Name the thing the caller does own and the thing that blocks the change.
5. Which Artisan id did you send to test the credit rule, and which two stored values did you compare to prove the rule held?
6. What did the held Piece's stored document contain after a refused archive, and why does a withdrawal during a checkout matter to a buyer?
7. Which fields in the list response would you remove before module 15 makes this route public, and why should they go now?

## What a passing gate leaves behind

Four artefacts. The four Piece documents as Mongo shows them, with status, price, photos and credit visible. The nine planned responses with the document counts beside the repeated ones. The raw 400, 403 and 409 bodies with their `error.code` values. And the learning log with the seven answers, including any row where the first response was wrong.

Two honest limits belong in the write-up. Nothing here proves that a Piece is worth its price, that its dimensions are accurate, or that its photo is of the actual object. The gate proves that the workshop's claim is recorded, that the object's state can only move in the allowed directions, and that no other workshop can change the claim. A buyer still has to trust the maker, and the product's answer to that is the story, the credit and the photographs, not this module.

The second limit is that the transitions a buyer drives are not built yet. Holding a Piece in module 19, selling it in module 20 and releasing a claim belong to the checkout and payment modules, and they use the state field and the hold subdocument you have just gated. A seeded sold Piece is a fixture, and you should not present it as a working sale.

Do not commit tokens, and do not leave the development database holding a Piece whose title you invented for a test. Module 12 puts a table and two forms in front of these routes, and it is easier to read that table when the rows are the seed's own work.
