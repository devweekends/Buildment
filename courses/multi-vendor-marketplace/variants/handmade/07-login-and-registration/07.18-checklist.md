## Chapter 7, Login and registration checklist (gate)

Do **not** open Chapter 8 until every box is ticked and learning log answers are written below.

Chapter 6 proved the API can issue identity. This gate proves the browser can hold it, use it and lose it cleanly. That is a different kind of proof. A curl transcript shows what the server returns, while this gate asks what a buyer sees when a session expires mid checkout, what a Workshop owner sees after a refresh, and where a token can be found by anyone who opens the developer tools.

The evidence here is mostly recorded in a browser: the Network panel, the Application panel and the address bar after a redirect. A reviewer reproduces three journeys. A customer registers, verifies and reaches the collection. A vendor signs in and reaches a Workshop dashboard. A signed out visitor is sent to login from a protected address. Every checklist group below supports one of those journeys.

### Pages and routing

The routing group proves the three public pages exist and that the transitions between them are real navigation, not a single page pretending. Registration is a two step journey in Ghurza because of the OTP: a buyer submits details, receives a code, and only then can log in. If the verify page does not exist as a route, that journey has nowhere to go, and the failure looks like a silent redirect rather than a missing page.

The role redirect item is where the two Ghurza audiences separate. A customer lands on the collection so they can browse Pieces from any Workshop. A vendor lands on the Workshop dashboard, because a maker who has just signed in wants the draft list, open questions and unpaid Commissions rather than a shopping page. The item does not require a finished dashboard, only that the destination is chosen from the role in the verified token, not from a form field.

The error item is a user experience requirement with a security edge. A wrong password must say so without revealing whether an account exists, and an unverified account must say that the email needs confirmation, because that is actionable. A single generic error for both leaves a buyer stuck, and a message that distinguishes a missing account from a wrong password hands an attacker a way to enumerate registered emails.

- [ ] `/register`, `/login`, `/verify-otp` routes work
- [ ] Register to verify to login flow completes in browser
- [ ] Role-based redirect after login (vendor vs customer)
- [ ] Login shows error for wrong password and unverified user

### Auth state

The auth state group is about who owns the truth in the browser. One provider, `useAuth` or `AuthProvider`, keeps the current user and the access token, and every page reads from it. A second copy of the user in a page component is how sessions drift: the header shows one name while the dashboard fetches another account's data.

Keeping the access token in memory is the decision this chapter defends. Memory is lost on reload, which sounds like a bug until you see the alternative. Storage that survives a reload is also readable by any script on the page, so a single injected script can copy a token and use it from anywhere. In memory, the token dies with the tab.

The boot refresh item is the price of that decision. On reload, the app calls the refresh endpoint once, receives a new access token and restores the session. The item adds "or documented limitation fixed", because an early version that flashes the login page on every reload is a real state a learner can be in, and the honest move is to name it, then fix it before the gate. The logout item completes the loop: clearing state and sending the refresh cookie back for invalidation, so a signed out browser cannot silently restore the session.

- [ ] `useAuth` or `AuthProvider` manages user and access token in memory
- [ ] Boot refresh restores session on page reload (or documented limitation fixed)
- [ ] Logout clears state and blocks protected routes

### API client

The API client group keeps the token handling in one file. `apiFetch` attaches the `Authorization: Bearer` header when the provider has a token, which means no component ever assembles that header itself. When the header format eventually changes, one function changes.

The 401 retry item is the heart of the chapter. An expired access token must trigger exactly one refresh, then exactly one retry of the original request. Two refreshes race each other and rotate the refresh token twice, which can invalidate the very session the user is trying to keep. The evidence is either a short expiry you set deliberately and a Network panel showing the refresh followed by the retried call, or a documented test with a mocked 401. The item accepts either, and rejects an untested claim.

`credentials: 'include'` is required on the refresh call because the refresh token lives in an httpOnly cookie. Without it the browser sends no cookie, and the refresh returns 401 for a user who is genuinely signed in. The final item is the negative one: the access token must not be in `localStorage` or `sessionStorage`, and the evidence is an empty entry for the key you would have used. A reviewer opens the Application panel and looks.

- [ ] `apiFetch` attaches Authorization Bearer when authenticated
- [ ] 401 triggers refresh once then retry (tested or short-expiry verified)
- [ ] `credentials: 'include'` on refresh request
- [ ] Access token **not** in localStorage or sessionStorage

### Protected routes

The protected route group is client side convenience, not security. `ProtectedRoute` redirects an unauthenticated visitor to login so the interface never shows a page that cannot load data. The server still refuses the data, and the gate expects you to know both layers exist. A redirect is a courtesy; a 401 from the API is the actual control.

The vendor stub item checks the role branch inside the guard. A vendor only page reachable by a customer is a visible bug, while a customer only page reachable by a vendor is a smaller one. The `isLoading` item is the detail that makes the first two usable. During boot the provider has neither a user nor a confirmed absence of one, so a guard that treats "no user yet" as "signed out" redirects every reload through the login page. Rendering a loading state until the boot refresh resolves removes that flash.

- [ ] `ProtectedRoute` redirects unauthenticated users to login
- [ ] Vendor stub page reachable only when logged in as vendor (if role prop used)
- [ ] `isLoading` prevents redirect flash during boot

### Integration

The integration group confirms both audiences can sign in through the interface. `vendor-a` proves a Workshop owning account can reach the maker side, and `customer-a` proves a buyer account lands on the collection. Both come from the Chapter 5 seed, so this group also confirms bcrypt alignment survived from the auth module.

The CORS item is required because the refresh cookie crosses origins. The API must allow the Vite origin and allow credentials, which means an explicit origin rather than a wildcard. A wildcard with credentials is rejected by the browser, and the error appears as a failed refresh with no obvious cause. The last item is a scope check: Chapter 7 should not invent new server endpoints. A small cookie setting change is allowed, and a second auth surface is not.

- [ ] Seed `vendor-a` and `customer-a` login via UI
- [ ] CORS allows credentials from Vite origin
- [ ] No new server auth endpoints required beyond Ch 6 (cookie Set-Cookie OK)

### Prior gates

The prior gate boxes stop a client fix from hiding a server regression. The Chapter 6 curl flow must still pass, because a change made for the browser, such as moving the refresh token into a cookie, can break the response the curl script asserts. The Chapter 5 models and seed must still match the documented counts, which catches a schema edit made while adjusting the user payload.

The four explanation boxes are the viva questions for this module. Access in memory versus `localStorage` is the storage trade-off. The 401 refresh loop is the sequence a reviewer will ask you to draw. `ProtectedRoute` versus server `requireAuth` is the difference between a redirect and a refusal. The full page reload question is where memory storage shows its cost. A learner who can answer those four without notes is ready for Chapter 8, which starts comparing what a token says with what a record allows.

- [ ] Ch 6 auth API still passes curl tests
- [ ] Ch 5 models and seed intact
- [ ] Why access in memory vs localStorage?
- [ ] Explain 401 refresh loop step by step
- [ ] Difference between ProtectedRoute and server requireAuth
- [ ] What happens on full page reload?

### Learning log, write now

Write this section as a record of what you observed, not what the chapter said. Name the storage key you checked and found empty, the cookie you saw in the Network panel, the status code of the refresh request, and the address you were sent to when you opened a protected page while signed out. Those details are what a reviewer can verify against your running app.

Answer **in your own words** in the fields below:

1. **Token storage:** Where do access and refresh live in your implementation? Why?

2. **Refresh loop:** Describe network sequence when access expires mid-session.

3. **Register flow:** UX path from register to first authenticated page, any friction?

4. **Role redirect:** How does login decide vendor vs customer destination?

5. **CORS/cookies:** What server CORS changes were needed for refresh cookie?

6. **Failure test:** One UI error state you tested (wrong password, unverified, etc.).

7. **Chapter 8 preview:** Why is login not enough to PATCH another vendor's store?

8. **Reload test:** Does session survive hard refresh? If not, what did you fix?

Question 3 asks for friction rather than praise. If the OTP arrived only in the server console, say so, and say how a buyer would learn that. If the verify page lost the email between steps, say how you passed it. Friction named honestly is the material the later polish modules use.

Question 7 is the bridge to authorization. A token proves who is asking. It does not prove that the Workshop being edited belongs to that account, so a signed in vendor could still change another Workshop's profile, archive another maker's Piece or accept a CustomRequest on someone else's behalf. Chapter 8 adds the ownership comparison that a token cannot make on its own.

Question 8 should be answered with a stopwatch in mind. A hard refresh throws away memory, so the session survives only if the boot refresh runs before the guard decides to redirect. Describe the order you observed and what changed after the loading state was added. If your session does not survive, say what is still missing and fix it before marking the gate complete, because Chapter 8 tests protected routes for both audiences and a broken boot makes every result after it unreliable.
