## Chapter 6, Authentication API checklist (gate)

Do **not** open Chapter 7 until every box is ticked and learning log answers are written below.

This gate is the first one in the course where the evidence is a security claim rather than a running page. Anyone can build a login route that returns a token. The gate asks whether the token is issued to the right person, stored in a form that survives a database leak, and rejected when it should be. Each group below tests one part of that claim, and each box leaves something a reviewer can inspect: a status code, a decoded payload, a database document, or a shell transcript.

A reviewer will not read your code line by line. A reviewer runs the negative cases first, because they are cheap and because a broken negative case invalidates every positive result beside it. Prepare the gate with that order in mind, and keep the transcripts. A screenshot of a Compass document is evidence for one box, and a curl command with its status line is evidence for three.

### Environment and configuration

The configuration group exists because a missing secret must stop the server, not degrade it. A server that starts with an empty `JWT_SECRET` will happily sign tokens that any attacker can forge, and nothing in the logs will say so. The item requiring `config.js` to fail startup when `JWT_SECRET` is missing is therefore a security item disguised as a configuration item. The evidence is the crash itself: remove the variable, start the server, and record the error it prints.

The `.env.example` items separate what must be shared from what must stay secret. The example file lists `JWT_SECRET`, `JWT_ACCESS_EXPIRY` and `JWT_REFRESH_EXPIRY` with placeholder values, so another reader knows which variables exist. The local `.env` holds the real values and is never committed, which the Chapter 2 gate already proved with `git log --all -- "**/.env"`. The dependency item is the smallest box on the page and still matters, because a missing `bcrypt` package turns every registration into a 500 and sends a learner hunting through route code for a problem that belongs in `package.json`.

- [ ] `JWT_SECRET`, `JWT_ACCESS_EXPIRY`, `JWT_REFRESH_EXPIRY` in `.env.example`
- [ ] `JWT_SECRET` in local `.env`, not committed
- [ ] config.js fails startup if JWT_SECRET missing
- [ ] bcrypt and jsonwebtoken in package.json

### Endpoints

The endpoint group is a contract list, and each line names a status code that a reviewer can reproduce. Register returning 201 with a bcrypt hash and a pending OTP is the entry point for both Ghurza roles: a customer who will buy Pieces and a vendor who will run a Workshop. The 409 duplicate case proves the unique index on email is doing its job and that the handler translates the database error instead of leaking a stack trace.

Login is deliberately split into three answers. Correct credentials return 200 with tokens, a wrong password returns 401, and a correct password on an unverified account returns 403. Those two failures mean different things to a buyer: 401 says the credentials are wrong and retrying is pointless, while 403 says the account exists and the email was never verified, which is fixable. A route that returns 401 for both is easier to write and worse to use.

Refresh and me complete the identity loop. Refresh accepts a valid refresh token and issues a new access token, and rejects a bad one with 401. The me route is the only place in this chapter that exercises `requireAuth` end to end, so it doubles as the middleware test. Calling it without a token must return 401 before any database read happens, and calling it with a valid token must return the user with the profile attached and no password field anywhere in the response.

- [ ] POST `/api/auth/register` returns 201 with a bcrypt hash, sends an OTP, and returns 409 on a duplicate email
- [ ] POST `/api/auth/verify-otp` sets `isVerified`, and a wrong OTP returns 400
- [ ] POST `/api/auth/login` returns 200 with tokens, 401 for a bad password, and 403 for an unverified account
- [ ] POST `/api/auth/refresh` returns a new access token, and an invalid refresh token returns 401
- [ ] GET `/api/auth/me` uses `requireAuth` and returns the user and profile, and 401 without a token

### Security

The security group is where the gate earns its place. No password hash in any response is the first rule, and the evidence is a full response body from register, login and me, pasted into the learning log with the hash absent. A single route that returns the user document unfiltered breaks the rule for every endpoint that shares the serializer.

Storing a hash of the refresh token on the User document is the second rule, and it is subtle. The server must be able to compare a presented refresh token, so it cannot store only a random identifier, and it must not store the token itself, because a leaked database would then hand an attacker working sessions. The item asking that the role in the access JWT matches `User.role` catches a different bug: a token signed with a role taken from the request body lets a buyer mint a vendor token. Only vendor and customer roles are accepted on register for the same reason, since an admin role chosen by the client would skip every later authorization check.

The OTP delivery item is about honesty in development. In this chapter the code is printed to the server console or returned in a development-only response, and that has to be written down. A reviewer who finds a real OTP in an API response with no note will treat it as a production leak, and a learner who forgets the shortcut exists will spend an hour looking for an email that was never sent.

- [ ] No `passwordHash` in any API response
- [ ] A hash of the refresh token is stored on User, never the refresh token itself
- [ ] role in access JWT matches `User.role`
- [ ] Only vendor and customer roles accepted on register
- [ ] OTP dev delivery documented (console or dev response)

### Testing

The testing group turns the contract above into a repeatable script. The full curl flow documented in 6.18 is the artefact: register, verify, login, call me, refresh, call me again. Anyone can run it against a fresh database and watch each status code appear in order. The negative tests are the other half, and they are the ones a reviewer reads first, because a 401, a 403 and a 409 cannot be faked by a happy path that happens to work.

The seed item connects this module back to Module 5. The seed script wrote `vendor-a` with a known password, and if that password was stored as plain text, `bcrypt.compare` will return false and login will fail with a confusing 401. Re-seeding after the hashing change, or re-hashing the seeded password, is the fix, and the proof is a successful login for `vendor-a` followed by a me call that returns a Workshop-owning account. That account will later own Pieces, Quotes and Commissions, so this box is also the first proof that a Workshop can be reached through authentication at all.

- [ ] Full curl flow documented (6.18)
- [ ] Negative tests pass (401, 403, 409)
- [ ] Seed `vendor-a` login works after bcrypt alignment

### Prior gates

The prior gate boxes exist so that a fix in this module does not quietly break an earlier one. The User, Workshop, Artisan and Piece models from Chapter 5 must still load, and the seed must still match the documented counts. A change to the User model during auth work is common, and a forgotten field or a new required property can empty the seed on the next run.

The health route item is a five second check that the server still boots. The React item is a scope statement rather than a task: Chapter 6 is an API chapter, and no login form exists yet. A learner who builds the login page now will build it twice, once without refresh handling and once after Chapter 7 explains where tokens live.

- [ ] The Chapter 5 models and seed still load
- [ ] The health route still answers
- [ ] No React auth screens yet, this chapter is API only
- [ ] I can explain what bcrypt gives you over plain storage
- [ ] I can explain what the access token and the refresh token each do
- [ ] I can explain when this chapter answers 401 and when it answers 403
- [ ] I can explain why the JWT payload stays minimal
- [ ] I can explain what refresh rotation buys you

### Learning log, write now

The learning log is where the reasoning behind the transcripts lives. Write answers that quote real output: the document Compass shows, the decoded payload from a token you actually received, the status line from a failing curl. An answer built from memory of what the code should do is easy to spot and easy to mark wrong, because the point of this chapter is that claims about identity must be checkable.

Answer **in your own words** in the fields below:

1. **Register flow:** Step through register from curl to Compass documents created.

2. **Password security:** How does bcrypt protect you if MongoDB is leaked? What is still at risk?

3. **JWT payload:** Paste decoded payload structure (redact sub if desired), what claims and why?

4. **Refresh design:** How is refresh stored server-side? What happens on logout or rotation?

5. **OTP:** How is OTP delivered in dev? How would you change for production email?

6. **Failure test:** Describe one negative curl test and the status code returned.

7. **Chapter 7 preview:** Where will access token live in the browser and why not localStorage?

8. **requireAuth:** What does `req.user` contain and who consumes it in later chapters?

Question 2 has a second half that learners often skip. Bcrypt slows an offline guessing attack, and it does nothing about a leaked session, an insider reading the database through the application, or a user who reused a weak password. Naming that remainder is what separates a security answer from a slogan.

Question 8 points forward without solving Chapter 8. `req.user` carries the id and role taken from the verified token, and the Workshop, Piece, CustomRequest, Quote and Commission routes all read it. A vendor's id becomes the owner filter for a Workshop. A customer's id becomes the buyer on a request. Credit for an Artisan is not an account, so it never appears in `req.user` at all, which is exactly the distinction Module 5 drew and Module 8 enforces.

Question 5 should mention that a development shortcut in an API response is a leak in production. The fix is a mail provider behind the same service function, with the response returning no code at all. Write the name of the function you would leave alone and the one you would replace, because that is the actual design decision.

## Troubleshooting

| Symptom | Where to look |
|---|---|
| A valid token answered with 401 | The two processes disagree about `JWT_SECRET`, or their clocks drift |
| A seeded account answered with 403 | `isVerified` is false, so verify it or re-seed |
| Every auth route answers 404 | The mount path from 6.11 |
| `bcrypt.compare` returns false | The seed stored a plain password, so hash it and re-seed |
