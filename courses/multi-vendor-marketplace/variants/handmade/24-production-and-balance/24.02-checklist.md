# Commission timeline and balance gate

Use the Commission created from the accepted quote in Module 23. Keep two buyer accounts and two workshop accounts available so you can test who may act. Record the quote version, deposit amount, balance amount, stage terms and current Commission ID. The normal demonstration runs from a verified deposit to delivered. The denial demonstration tries to skip an arrow or use the wrong account. Both are required; a timeline animation alone does not prove the backend state machine.

## Demonstrate one real timeline

As Workshop A, start production and post two craft-specific updates with permitted photos. For example, an embroidery workshop may show a pattern drafted and then a stitched panel. The buyer sees those updates in order, with a date range that is still described as an estimate. Mark the work ready for approval. As Buyer A, inspect the final evidence and approve. The Commission should enter `awaiting_balance`, not `ready_to_ship`. Complete the separate balance payment in test mode. Compare the PaymentIntent amount and currency with the accepted quote snapshot, then let a verified webhook make the Commission ready to ship. Add carrier and tracking reference, mark shipped, and complete the delivered path. Reload from both accounts; the same events and amounts must remain visible.

## Test who cannot move it

Buyer A must not start production or set shipping details. Workshop B must not post progress, upload a private progress image or change the status. Buyer B must not approve or request a revision. Workshop A must not approve its own finished work. Before the balance webhook, Workshop A's Ship route must reject the request even if an old tab shows a button. Record raw HTTP status and unchanged state for each attempt. A response that hides an error while the database still changes is a failure.

Open two Buyer A tabs at the approval step. Approve in one and request the included revision in the other. Only one action can win. The loser sees 409 and the current timeline. If the quote includes one revision, complete a revision path and then attempt a second included revision. The API must reject it or start a new quoted agreement; it cannot silently grant unlimited maker work. Preserve the first and second action attempts in an audit trail that names actor and state.

## Test money after a cancellation

Create a second Commission and cancel it at a stage allowed by the accepted terms. Show the captured deposit, any captured balance, the stage, the terms version and the computed refund. The refund request must use a stable key and must not exceed the unrefunded captured amount. Replay the request and any provider event; no second refund should be created. Simulate a provider failure and verify that the timeline says pending or failed, not refunded. Change the workshop's current cancellation policy afterwards; this Commission still uses the accepted version.

## Learning log

1. Draw the Commission states from deposit paid to delivered. For each arrow, write the actor and the evidence needed before the move.
2. Explain why buyer approval and balance payment are separate transitions. What would go wrong if approval alone enabled shipping?
3. Describe the two-tab approval-versus-revision race and the conditional database update that gives one winner.
4. Compute a refund from one accepted quote, captured amounts and stage. Explain how replay avoids refunding the same capture twice.

Commit the transition service, audit history, progress photo authorization, timeline UI, balance PaymentIntent and refund tests. Save a five-minute video or repeatable script that walks request to delivered on the live URL. A mentor should be able to interrupt at any step and ask which stored record authorizes the next action. If you cannot answer from a conditional transition and an accepted terms snapshot, do not mark the Commission workflow complete. The final course capstone uses this very path to defend long-running orders over weeks.

## Review the evidence for a real buyer

Ask a second person to open the buyer timeline without an explanation from the builder. They should be able to identify the accepted scope, original estimated range, later progress, approval request, deposit paid, balance paid and shipping reference. If two steps use the same “paid” label, clarify which payment it means. If a revised date range appears to replace the original with no history, show the change as another event. The timeline is part of the contract between people, not only an admin debugging screen.

Take one cancellation trace and ask the second person to explain it. The trace should say which accepted rule applied at the stage, what had already been captured, what refund was requested, what Stripe confirmed and what amount remains. A generic “refund complete” chip with no amount cannot support a dispute or a viva answer. Keep the accepted terms snapshot visible beside the refund result. Then replay the provider event and verify that the visible timeline does not gain a second identical refund entry.

Finally, stop and restart the API and worker in the middle of production. Open the Commission again from a fresh session. The same actor permissions and next allowed action should apply. If a delayed payment event for an already-cancelled Commission moves it forward, record the failure and fix the webhook's current-state check. This restart and delay test is the clearest proof that a weeks-long workflow is backed by durable state rather than a sequence of browser screens.
