# Payment gate and race evidence

This gate is passed with records, not screenshots. You need one checkout containing Amina's cover and Kareem's tray, a confirmed test payment, a replayed event, an invalid signature attempt, and a late success for a piece that another buyer already owns. Everything stays in Stripe test mode. Nothing in this module says anything about a live charge.

Bring the numbers with you. The checkout total should read 41,000 minor units, split as 28,500 for Amina's Order (24,000 for the cover plus 4,500 shipping) and 12,500 for Kareem's (9,500 for the tray plus 3,000 shipping). If your seed uses different prices, keep your own values and show the addition. What matters is that the same integers appear on the checkout record, the intent, the two Orders and any refund.

## Start from the sale that works

Run the happy path first, because every later case is a deviation from it. Pay with `4242 4242 4242 4242`, watch the forwarding session print the event, and inspect the database immediately after the route answers. Both Pieces should read `sold` with no hold subdocument. Both Orders should read `paid` with the same intent id and the event id that moved them. One payment event record should exist with `processedAt` set. The buyer's order view must show the frozen titles, maker credits and prices, and each maker dashboard must show only its own Order.

Then confirm the negative half of the same run. Reload the success page. Press back and forward. Refresh the orders page. None of those actions may sell a Piece or create a second intent. If your client still calls a mark-paid endpoint, this is the moment to delete it rather than to explain it.

## Then break it on purpose

Replay the event from the CLI. Count pieces sold, Orders paid and refunds before and after. The counts must be identical, and the event record must still be there once. If the count of payment event records grows, the unique index is missing from the test database, not from the schema file.

Send a request with no signature header, then one with a signature forged from a wrong secret. Both must be refused with a 400 and both must leave the database untouched. This is the test that proves the route verifies bytes rather than trusting a JSON body, so run it against the raw body configuration you actually run in development, not against a hand-built fixture.

Test a tampered amount. A forged signature cannot pass verification, so exercise the equivalent case by calling the internal apply function with an event whose intent amount is 40,000 against your stored 41,000 checkout. Expect no Piece sold, no Order paid, and a recorded mismatch with the intent id. A handler that "fixes" the amount from the event has failed this check even if the totals look plausible.

Finally, reproduce the late success. Take a checkout, let its hold expire with the injected clock, let a second buyer claim and pay for the cover, then deliver the first buyer's success event. Expect the cover to stay sold to the second buyer, the first buyer's Orders to read `refunded`, and one refund record in test mode with the checkout total. Deliver the event again, and confirm the refund id does not change.

## Gate checklist

- [ ] One checkout with two workshop Orders, one shared intent id, and a total computed on the server in minor units.
- [ ] No route accepts an amount, a price or a paid flag from the client. The mark-paid path is deleted, not disabled.
- [ ] Signature verification runs on the raw body and rejects a missing or forged header with a 400 and no writes.
- [ ] The payment event record stores the provider event id under a unique index, and `processedAt` is written after the effects exist.
- [ ] The sold transition filters on Piece id, `status: held` and `hold.checkoutId`, and writes status and hold removal in one update.
- [ ] The paid transition filters on Order id, `status: pending_payment` and the stored intent id.
- [ ] Replaying the same event twice leaves Piece, Order and refund counts unchanged.
- [ ] The amount mismatch case stops the handler and records an incident instead of charging or selling.
- [ ] A lost hold cancels an unsucceeded intent, and the branch is visible in the log with the provider status.
- [ ] A late success is refunded in test mode, the amount matches the stated policy, and every affected Order reads `refunded` with the refund id.
- [ ] A refunded Order never returns a Piece to `available` and never alters the buyer who actually owns it.
- [ ] Buyer and maker order reads stay scoped, and the maker view shows a paid Order with a place for a tracking reference, filled later.
- [ ] The three automated tests (duplicate delivery, amount mismatch, invalid signature) run in the suite and are named in the learning log.

## Learning log

1. Which exact database write decides that Lina's cover is sold, and what does the losing branch receive when the cover belongs to Omar's checkout? Include the filter you used and the matched count.
2. Why is the payment event marked processed after the effects rather than before? Describe the crash you tested and what the retry repaired.
3. Show your four totals in minor units: checkout, Amina's Order, Kareem's Order, and the refund you issued. Do they add up, and where does the shipping amount come from?
4. Which policy did your build adopt for a checkout that lost one Piece, whole intent or recorded per Order choice, and what would break if the server guessed?
5. What happens to a refunded Order in the buyer's view and in the maker's view, and why is the Piece not released?
6. What does a passing test card prove about money, and what does it not prove?

Write the answers as sentences with values, not as a list of statuses. A reviewer should be able to reconstruct your runs from the log alone and then rerun the duplicate delivery test against the same database without resetting it. Keep private provider secrets, buyer card data and the content of `.env` out of the log.

## What this gate does not prove

Several things are out of scope, and the honest thing is to name them. A live charge is not tested, because the course runs in test mode only. Payouts to makers are not implemented; the Artisan credit on the OrderLine is a record, not a payment. A commission deposit has its own intent and its own refund rules in module 23, and passing this gate says nothing about it. Refund arithmetic across a cancellation stage belongs to module 24.

The gate is also not a claim that a real card would behave the same way. Test mode simulates success, decline and authentication, but it does not simulate a bank's own delay policy, a network failure mid confirmation, or a dispute. Those are worth one sentence in your log as known limits.

The next module takes the paid Orders this one creates and gives both sides a way to follow the parcel: packed, shipped with a carrier and a tracking reference, then received.
