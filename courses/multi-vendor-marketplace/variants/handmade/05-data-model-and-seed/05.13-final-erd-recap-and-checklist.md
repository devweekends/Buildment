# Final ERD, recap and checklist

Open `docs/erd.md` beside the running database. The diagram must show User to Workshop to Piece as the ownership chain; Artisan as a credit relationship; Buyer to CustomRequest to Quote to Commission as the future-work chain; and Cart to Piece plus OrderLine snapshots for ready-made sales. Label each arrow as owns, credits, references or snapshots. An unlabeled line could be read as permission, which is exactly the confusion this module must prevent.

Inspect counts from a clean seed: three fictional workshops, six artisans, twelve Pieces, two sold and one open request. Run the seed again and show the same counts. Query a sold Piece and confirm it is visible only as a portfolio page, with no active purchase operation. Query the open request as its buyer and intended workshop owner, then deny another buyer, another workshop and a credited artisan. The raw API or service response is evidence; an invisible button is not.

Try a second checkout intent for the same Piece in a disposable fixture and identify where Module 19 will make a conditional hold claim. The model should have a status and hold subdocument capable of that test, even if the route is not built yet. Explain why `stockQty: 1` would not identify held, sold and archived separately. Change the Piece's current price after an example OrderLine exists and show the embedded snapshot remains unchanged. The order test may use a fixture rather than a payment provider; say so.

Review shipping and commission skeletons honestly. A ShippingProfile can state served countries and ranges, but later checkout still must validate a destination and preserve a snapshot. A CustomRequest, Quote and Commission can be stored, but they do not yet perform negotiation or payments. The ERD should mark those later behaviors by module number. A learner should be able to start Module 22 without assuming that a `status` enum is a working workflow.

The gate passes when the committed ERD, seed counts, index list, cross-workshop denial, private-request denial and snapshot check all tell the same story. In a short defense, say who owns a Piece, who receives maker credit, when a request becomes a quoted commission, and why a held Piece is not a stock decrement. If an answer depends on a generic Product field inherited from FreshMarket, revise the data model before continuing.

## Learning log

1. Draw User to Workshop to Piece and mark Artisan as credit. Which link authorizes a price edit?
2. Compare one available Piece, one sold Piece and one open CustomRequest. Which buyer action is valid for each and why?
3. Show the seed counts after two runs and a denied wrong-workshop request. Which stored relationship caused the denial?

## Demonstrate the gate aloud

Use the ERD to tell the story of one completed ready-made sale and one request that has not yet been accepted. For the sale, name the Workshop owner, Piece ID, buyer Cart, held state and immutable OrderLine snapshot. For the request, name the buyer, intended Workshop, optional inspiration Piece and the future Quote version. If you cannot tell those stories without using the same Product row for both, the model has not preserved the product's key distinction.

Show a raw denial for a foreign Artisan ID and another for a foreign private request. These errors test different promises: a Workshop cannot take another maker's credit, and a bystander cannot read a buyer's brief. Then query a sold Piece through the public catalogue and attempt to add it to a Cart. Its page may remain a portfolio, but the purchase operation must fail. Save the status and unchanged database row for each case.

Finally, state what this gate does not yet prove. It proves data shape, seed repeatability, relationships and initial access checks. It does not prove a concurrent one-off hold, verified deposit, balance payment or cancellation refund. Those have their own later gates. This distinction helps a learner carry accurate evidence forward rather than treating a schema and a green seed as a finished marketplace.

The learning log should include the actual query predicate used for a wrong-workshop edit and the ID of the unchanged Piece. An answer such as "the server checks permission" is too broad to review. Show `workshopId` in the filter, explain where the authenticated owner ID came from, and name the denied actor. For the request privacy check, show the analogous buyer or Workshop relationship. These two examples prove the ERD supports both public sale and private future work.

Before marking the gate complete, ask a second learner to interpret the diagram without your narration. They should identify the status that prevents another buyer from purchasing a held bowl, the link that allows a Workshop owner to edit a Piece, and the record that keeps a request private. If they confuse Artisan credit with Workshop ownership, revise the arrows and captions. The diagram is useful only if it predicts the raw API behavior the tests demonstrate.
