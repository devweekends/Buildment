# Async jobs gate

The evidence for a queue is not a diagram of a queue. It is a log where the response line appears above the notification line, a notification table with one row per fact after a duplicate delivery, and a quote that stays acceptable when its expiry job never runs. This gate collects those three pieces and refuses the shortcuts that look like they work.

Prepare the fixture. One commission from Module 24 with an accepted quote, a deposit paid and status `in_queue`. One quote from Module 23 that is `sent` and still valid. One paid order from Module 21. Keep the commission ID, the quote ID with its version, the order ID and the two PaymentIntent ids in a note beside the evidence.

## The request answers first

Start the API and the worker in two terminals. Send the deposit webhook with a valid signature and watch both terminals at once. The API writes its response line, then the worker writes the notification line. The gap should be visible. If the notification appears before the response, or if the response time is measured in seconds whenever the mailer is slow, the send is still on the request path.

Prove it the harder way. Point the mailer at a stub that sleeps for five seconds, and send the event again. The webhook must still answer in well under a second, and the worker must carry the delay alone. Then stop the worker entirely, send the event, and confirm the API still answers and the job waits in the queue. That last run is the one a learner fails when the enqueue call is awaited inside a transaction that later rolls back.

Now record the size of the queue. Run your inspection helper and read the waiting, active, delayed and failed counts. A job in the waiting set with no worker running is a correct state, and it must be readable without opening Redis by hand.

## One fact, one message

Send the same webhook a second time. The commission must stay in `in_queue`, the notification count for `commission.deposit.paid` must stay at one, and the worker must log a skip or fail an insert on the unique index rather than sending a second message. Read the job id in the queue and confirm it is built from the commission ID, not from a timestamp.

Do the same for a production stage notice. Post the same progress update twice from the maker's form. One notification reaches the buyer, and the message names the stage that was actually posted. Then post a second, different stage and confirm the buyer receives that one too. A job id built from the commission ID alone fails this check, because the second stage would collide with the first and never arrive.

Finally, force a send failure. Make the mailer throw once and read the retry: one job, three attempts, growing delays, and one notification row that ends with a `sentAt` value. If the retry writes a second row, the insert happens after the send instead of before it.

## The quote that outlives its job

Create a quote with `validUntil` two minutes in the future. Watch the delayed set: one reminder job and one expiry job, each with a delay that matches the deadline. Do not wait for a real week to test this. Two minutes is enough, and a shorter deadline is easier to read.

Before the deadline, accept the quote. On the next run of the reminder handler, no message may go to the buyer, because the quote is no longer `sent`. Then create a second quote, let its deadline pass with the worker stopped, and call the acceptance route directly. The route must refuse it, because the route compares `validUntil` itself. Start the worker afterwards and confirm the quote then moves to `expired` with no change in what the route would have allowed.

## Survive a restart and a missing Redis

Start the worker, enqueue a delayed reminder thirty seconds out, and stop the worker with `SIGTERM` before it fires. Restart it. The job must still fire, once, at roughly the expected time. A job that lived in a `setTimeout` inside the API would be gone, and this is the test that tells the difference.

Then stop Redis. Send the deposit webhook again on a fresh commission. The API must answer success, the commission must be in `in_queue`, and a log line must record that the notification could not be queued. When Redis returns, your inspection helper should show the gap, and a sweep or a manual replay should be able to fill it. A 500 because the queue was down is the wrong answer: the payment already happened.

## Gate checklist

- [ ] The webhook response line appears before the notification line in the two terminals, and the response is fast with a slow mailer.
- [ ] With the worker stopped, the API still answers and the job waits in the queue.
- [ ] A duplicate webhook leaves one commission state and one notification row.
- [ ] Two identical progress submits send one message, and a later different stage sends its own.
- [ ] A send failure retries with backoff and leaves exactly one notification row.
- [ ] The delayed set shows a reminder and an expiry job with delays that match the quote's deadline.
- [ ] An accepted quote receives no reminder, and an early expiry job leaves the quote acceptable.
- [ ] Acceptance of an expired quote is refused by the route while the worker is stopped.
- [ ] A delayed job survives a worker restart and fires once.
- [ ] With Redis down, the API answers success and records the unannounced fact instead of returning an error.
- [ ] `docs/jobs.md` lists every job name, its payload, its job id pattern, its retry policy and the one row it writes.

## Learning log

1. Which line of your webhook handler runs last, and what does it return to the provider before any message is sent?
2. What job id pattern did you choose for each job, and why is a commission ID alone wrong for a production stage notice?
3. Which unique index makes a duplicate notification impossible, and what error does the handler treat as "already sent"?
4. What does the expiry handler check before it changes a quote, and which route still enforces the same rule without it?
5. What happened to the delayed job when you restarted the worker, and what would have happened with an in-process timer?

## What this gate does not prove

This is not a queue tutorial and it does not prove that every slow operation in Ghurza has left the request path. Image uploads still happen inside a request in this build, and that is a deliberate limit. The gate also does not cover a real email provider, a dead letter review process, or the auto-complete job that closes an unconfirmed order after the maker's chosen number of days. Those are named as boundaries, not delivered.

Module 26 adds caching to the same read path, and Module 27 deploys the worker beside the API. Both depend on the assumption proved here: a job either writes a record or moves a record under a guard, and a missing job never changes a rule. If a check fails, fix the order of the work rather than the wording of the log line.
