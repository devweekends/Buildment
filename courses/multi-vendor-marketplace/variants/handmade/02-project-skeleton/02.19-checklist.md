## Chapter 2, Project skeleton checklist (gate)

Do **not** open Chapter 3 until every box is ticked and learning log answers are written below.

A gate is not a formality at the end of a chapter. It is the point where you stop describing what you intended and start showing what runs. Every box below corresponds to a promise the rest of the course makes on your behalf. If the promise is false, the failure appears three modules later, inside code that assumes a working foundation and gives you an error that points at the wrong file.

Read the gate as a reviewer would. A reviewer does not ask whether you followed the lessons. A reviewer asks what happens when the server is stopped, whether history contains a secret, and how many commands it takes to reproduce your app on a clean machine. Each checklist item is a small experiment that answers one of those questions. The prose under each heading says why the item exists, what evidence proves it, and how a reviewer reads that evidence.

### Repository & structure

The first group proves the repository is yours and that its history is safe. The item asking for a root `.gitignore` that covers `node_modules/`, `.env` and build output is not about tidiness. It is the mechanism that stops a database password from reaching GitHub, where a scanner can find it within minutes. The neighbouring item, `git log --all -- "**/.env"` returning empty, is the evidence behind that mechanism: it asks history directly whether an environment file was ever committed, on any branch.

A reviewer reads those two together. The ignore file shows intent, and the empty log shows the intent held. If the log returns a commit, the credential must be treated as compromised and rotated, whatever the file says today, because deleting a file in a later commit does not remove it from earlier ones. The README item is the third piece: two run commands at the root prove the project is reproducible by someone who has never seen your terminal.

- [ ] A Git repository is initialised at your Ghurza project root, kept apart from the course content folder
- [ ] The root `.gitignore` covers `node_modules/`, `.env` and build output
- [ ] `git log --all -- "**/.env"` comes back **empty** (no env file was ever committed)
- [ ] The root `README.md` explains how to run server and client side by side in two terminals

### Server

The server group proves the API is a real program with a clear boot sequence rather than a folder of files. The split between `app.js` and `server.js` is the item most learners want to skip, and it is also the one that pays off in testing. `app.js` builds and configures the Express application and exports it without binding a port. `server.js` imports that app, reads `process.env.PORT`, falls back to 5000 and starts listening. A test can import `app.js` without opening a port, and a second environment can start the same app on a different port.

The module folder item is about path alignment. Every later chapter names a path such as `modules/auth/` or the Piece routes, and those paths only work if the folders exist with the names this build chose. In this scaffold the seller folder is `stores` and the catalogue folder is `products`. Read `stores` as the Workshop module, where ownership and Artisan credit are enforced, and `products` as the Piece module, where a maker creates, publishes and archives work. The names are plain, and the responsibilities are Ghurza's.

The curl item is the proof that the wiring is alive. `curl -i http://localhost:5000/health` must return a 200 status line and a JSON body containing `"status":"ok"`. A browser tab that shows JSON is not the same evidence, because it hides the status code and the headers. A reviewer reads the status line first and the body second, and rejects a 200 with an HTML error page just as firmly as a 500.

- [ ] `server/package.json` declares both a `dev` and a `start` script
- [ ] `server/src/app.js` builds the Express app, registers the JSON middleware and exports it without calling listen
- [ ] `server/src/server.js` binds the app to `process.env.PORT || 5000`
- [ ] The module folders are present: `auth`, `stores`, `products`, `cart`, `orders`
- [ ] `server/src/shared/` is in place
- [ ] `npm run dev` inside `server/` starts with no crash
- [ ] `curl -i http://localhost:5000/health` answers **200** with a JSON body that includes `"status":"ok"`

### Client

The client group proves the browser application exists and that it talks to the API through one controlled door. `client/.env.example` and `client/src/api/client.js` are a pair. The example file documents the variable name `VITE_API_URL` so a fresh clone knows what to set, and the helper reads that variable so no component hardcodes `localhost`. Vite only exposes variables prefixed with `VITE_`, which is why the name is exact and why a differently named variable silently arrives as undefined.

The two health items are where this group becomes honest. Showing a live status proves the request path works. Showing an error state when the server is stopped proves the page is not printing a hardcoded success message. A reviewer tests this by stopping the API, reloading the page and watching the UI change. A page that still says "ok" with the server down has taught the reviewer that the demo cannot be trusted, which is worse than a page with no status at all.

- [ ] A Vite React app sits in `client/` with `pages/`, `components/`, `api/` and `hooks/`
- [ ] React Router serves Home from `/`
- [ ] `client/.env.example` lists `VITE_API_URL`
- [ ] `client/src/api/client.js` takes its base URL from env, and no component hardcodes localhost
- [ ] `npm run dev` inside `client/` starts with no crash
- [ ] With the API running, the home page renders the **live** health status it fetched
- [ ] With the API stopped, the home page renders an **error state** instead of a hardcoded success

### Integration

The integration group covers the boundary between the two applications. CORS is a browser rule, not a server preference: the page is served from port 5173 and the API answers on port 5000, so the API must name the allowed origin or the browser blocks the response before your code sees it. The Network tab item is the evidence. A request that shows 200 with a JSON response body proves the browser accepted the response, while a blocked request shows a CORS error and an empty response, and no amount of server logging will fix it from the client side.

A reviewer reads the end-to-end verification as a single story: browser loads React, React calls the helper, the helper calls the API, the API answers, the page renders the answer. Each link in that story has its own failure mode, and the gate asks you to have seen the whole chain work at least once.

- [ ] CORS configured so browser can call API from Vite origin
- [ ] Browser Network tab shows successful `GET` to `/health` with 200
- [ ] End-to-end verification from **2.16** completed

### Understanding (self-check, explain aloud)

These boxes are not ticked against a file. They are ticked against your ability to explain a decision out loud, because the next chapters assume you can. The module versus layer question matters because Chapter 9 adds Workshop routes and Chapter 11 adds Piece routes, and a learner who understands modules adds one folder per domain instead of scattering handlers across three technical folders.

The `app.js` and `server.js` question, and the browser versus Node question, both test whether you know where code runs. A buyer's cart total is computed on the server because the browser can be edited. A Piece's draft status is enforced on the server because the client can lie. A reviewer asks these questions in a viva and expects the answer to name the process, not the file.

- [ ] I can explain **module-based** versus layer-based structure, and why Ghurza chose modules
- [ ] I can explain which code runs in the **browser** and which runs in the **Node server**
- [ ] I can explain why **`app.js` and `server.js` are kept separate**
- [ ] I can point at the folders where **auth** and **products** code will live in my tree

### Learning log, write now

The learning log is the part of the gate that survives after the boxes are ticked. It records your reasoning in your own words, and a mentor reads it to see whether the build made sense or merely ran. Answer in full sentences, name real files and ports, and avoid answers that could have been written before you started the chapter.

Answer **in your own words** in the fields below:

1. **Draw or paste your folder tree** (server + client) as it stands after Chapter 2. Annotate one sentence per module folder describing its future job.

2. **Why did this course require module-based folders instead of layer-based?** Use the "add discount codes" or "add products feature" argument, not "because the course said so."

3. **What happens at runtime when a user opens your Home page?** Trace the path: browser to React to fetch to Express to response. Mention ports and CORS.

4. **Why must secrets like `MONGODB_URI` (coming Chapter 4) live only in `server/.env` and never in the React app?**

5. **What did you verify in the failure-mode test (server stopped)?** Why is error UI important even for a health check demo?

6. **What will change on `/health` in Chapter 4 when MongoDB connects?** Speculate based on course outline, one paragraph.

A good answer to question 3 names both ports and says what CORS would have blocked without the configuration. A good answer to question 4 explains that anything shipped to the browser is readable by the buyer, and that a database string in the client is a published password. A good answer to question 5 describes what the page showed, not only that you stopped the server. A reviewer can tell the difference between a remembered command and an observed result.

Question 6 is intentionally speculative. The health route will likely report the database state beside the server state, because Chapter 4 needs a way to prove the connection exists. Write your expectation now and compare it later. Being wrong is useful evidence that you learned something, and the comparison is a better record than a paragraph written after the fact.
