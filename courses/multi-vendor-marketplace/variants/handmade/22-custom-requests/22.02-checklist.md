# Custom-request gate and learning log

This gate is about one private conversation. A polished inbox screenshot is insufficient if another buyer can fetch its API response. Put two buyer accounts, two workshop accounts and one credited artisan in your local seed. They must have different IDs and visibly different names so you can tell which session made each request. Clear old requests before the run, then record the IDs produced by the new run in your learning log.

## Demonstrate the normal path

As Buyer A, open a sold piece from Workshop A and click “Request something similar.” Check that the form names Workshop A and links the inspiration piece, then edit the brief to include size, material, preferred colour, budget range and a wished date. Submit it. The response should identify one new request in `submitted` state. In Buyer A's “My requests” page, open the thread and read the exact brief you sent. There should be no quote price or deposit button yet. A custom request is only an invitation to discuss work.

Sign out and enter as Workshop A's owner. The inbox should show that request and no request addressed to Workshop B. Ask a clarifying question about the tray's finish. Sign back in as Buyer A and reply. The thread should show both messages in creation order, with an unambiguous sender label. Reload the page and verify the messages came from the API rather than transient React state. With a narrow browser viewport, inspect the brief and status without horizontal scrolling.

## Try to cross the boundary

Send the same `GET /custom-requests/:id` as Buyer B. The API must return the course's forbidden or not-found response and no part of the brief. Repeat for the photo list and any photo-view route. Now use Workshop B's owner token for the request and message routes. That owner may run a workshop, but it is not this request's workshop. It must see neither the brief nor the reference photo and must not be able to post a reply. Finally, use the credited artisan's account. Credit on a piece must not become workshop ownership. Record the status codes and verify that the response bodies contain no private fields.

Pause commissions for Workshop A and attempt another `POST` from Buyer A. The server should reject it even if a stale browser still shows the button. Unpause, submit a fresh request, then decline it from the workshop inbox with a reason. Have Buyer A try to post from a tab opened before the decline. A server-side state check must reject the late message. This demonstrates why hiding the composer after a UI refresh cannot be the only rule.

## Learning log

1. Draw the relationship among `buyerId`, `workshopId` and `inspiredByPieceId`. Explain why a photo or piece ID alone cannot authorize access to a request.
2. Write the predicate used to fetch the workshop inbox and the predicate used for “My requests.” Explain what data would leak if the code fetched all requests and filtered only in the browser.
3. Describe the race between a decline in one tab and a message in another. Show the database condition that decides which transition wins, and name the response shown to the loser.
4. Name two fields that are only a buyer's wishes, and two fields that become commitments only after an accepted quote. Explain why the request API must not capture a deposit.

Commit the API tests, both screens, the initial state document and this learning log. Save a short curl transcript showing one allowed access and each denied access. The mentor should be able to repeat the requests with fresh IDs. If any denial works only because the UI omitted a button, revisit the route guard before moving to quotes. Module 23 will trust the party relationship established here when it presents terms and a deposit to the buyer.

## Debugging notes to leave for the next module

Write down one failure you met while building the inbox. If Workshop B unexpectedly saw the request, record the exact query filter before and after the fix. If a reply appeared twice, record whether the client submitted twice or the server saved twice. If a photo was inaccessible to its own buyer, record where you checked the party relationship and whether the asset record used the same request ID. These observations are useful because the quote module will reuse the same authorization helper. A helper that worked only for one route will spread the defect to every quote route.

Take a final pass through the API response shape. A buyer needs the workshop's public name and the messages in their own request. A workshop owner needs the buyer's display name and request details for that workshop. Neither side needs an authentication token, a private storage credential, or internal notes for another workshop. Remove fields from the serializer, not merely from the screen. Then rerun the access tests with the serialized JSON visible in the test assertion. Your evidence should show that the boundary holds on data returned over HTTP, which is the boundary a guessed URL actually crosses.
