# Workshop API gate

This gate runs on three tokens and a database you can reset. Amina owns the tatreez workshop. Kareem owns the olive wood workshop. Lina is a buyer with no workshop and no reason to reach these routes. Every request below is sent with curl and read as raw JSON, because a page that looks correct in a browser proves nothing about who may write to a workshop.

Write the expected table before you send anything. Seven rows are enough: create for Amina returns 201, create for Amina again returns 409, read mine returns the same id, patch my own workshop returns 200, patch Kareem's workshop returns 403, add an Artisan to my own workshop returns 201, and the public read of the tatreez workshop carries the public field names and none of the owner ones. When a response disagrees with the table, the table is the authority and the route is the bug.

## Prove one workshop, once

Create the tatreez workshop with a full body: name, area, a two paragraph story, making days of 21 and 35, and a contact phone. Read the response and note three things: the slug, which should be derived from the name, the id, and the fact that the body you sent contained no slug at all. Then count the documents in the Workshop collection for that owner. The count must be one.

Send the same create again with a different area. The correct answer is a conflict with `WORKSHOP_EXISTS`, and the important half of that answer is the absence of a new document. Confirm it with a count, not with the status alone, because a route can return 409 after it has already inserted. Then send a body that carries `ownerId` set to Kareem's user id and a `status` of paused. The stored workshop must still name Amina and must still be active, which proves the route picks fields rather than spreading the body.

If you want the harder version of this check, send two creates at the same moment from two terminals and count again. One may answer 201 and the other must answer 409, and the count is still one. A sequential pair passes on a route with no unique index, so the parallel pair is the one that proves the database holds the rule.

## Prove the boundary between two workshops

Sign in as Kareem and patch Amina's workshop id with a new area and `acceptingCommissions: false`. The answer must be 403 with `NOT_OWNER`, the body must carry no workshop fields, and a re-read of the document must show the old area and commissions still on. Save the raw request and the raw response together, because the pair is what makes a refusal evidence rather than a claim.

Then patch your own workshop and confirm the change lands. Change the story to a sentence about the wood you use, then patch again with a making range of 40 to 14. The attempt must return 400 with a message about the pair, and the stored values must be exactly as they were. A partial write here is worse than a refusal, because the owner would see a saved form and a buyer would read a making time that cannot be true.

While you are signed in as Kareem, try to change Amina's slug. The correct answer depends on the state of her workshop: with no Piece listed the change is allowed only for her own workshop, and for Kareem it is a 403 either way. The lock rule is tested in the next section with the owner's own token.

## Prove the roster

Add two Artisan credits to Amina's workshop. The first chooses to show her name, with a short bio about hand stitching. The second chooses not to show it, so the public page must present her as the workshop's maker. Read both responses and confirm the `workshopId` on each is the id from the path and not a value you sent.

Now send the same create with a body that carries Kareem's workshop id while the path names Amina's. Only one of the two can be authoritative and the session must win: the stored credit has to belong to Amina's workshop. Then sign in as Kareem and patch Amina's first credit by its id. The answer must be 403 and the stored display name must be unchanged.

Retire the second credit and read the workshop's public page. The retired name must be gone from the public roster, and any existing Piece that credits that Artisan must still show the credit. A retirement that deletes the record breaks the portfolio piece and the order snapshot later, which is why the date exists.

## Prove the slug behaves

Change the workshop address while it lists nothing: send a new slug on a patch with Amina's own token. The change is allowed, and the old slug must still answer the public route with the workshop and a `canonicalSlug` that names the new address. Then create one Piece for the workshop, or use the seed, and try the same patch again. The answer must be 409 `SLUG_LOCKED` and the stored slug must be unchanged.

Create a second tatreez workshop under another owner with the same name and read both slugs. The second one must be distinct, readable and derived from the name with a suffix. This is also the moment to check the indexes in the running database, because a unique index that exists only in a schema file is the most common way for this section to pass in a test and fail in a review.

## Prove the public payload is small

Read `GET /workshops/:slug` with no token at all. The response must contain the workshop id, slug, name, area, story, the two making values, whether a shipping profile exists and the count of available pieces. It must not contain the owner id, the contact phone, the account state, the slug history, the commission settings or the draft and sold counts. Read it again with Amina's token and confirm the answer is identical, because the public route does not vary by caller and should not start to.

Then request a slug that does not exist and read the error. It must be a plain 404 with a fixed body. A message that suggests a similar workshop name is a search box for every workshop on the platform, and it belongs nowhere near an unauthenticated route.

## Prove the role check

Send the four authenticated routes with Lina's buyer token. Each must answer 403 with `ROLE_NOT_ALLOWED` and no record fields. A buyer has no workshop, and a route that creates one for any authenticated account is a small bug now and a confusing one in module 10, when the client starts using `GET /workshops/mine` to decide where to send a signed-in account.

Move that check into your test suite as well, because a one-off curl proves only that the route answered on one afternoon. A test is what keeps it answering after the next refactor. Role assertions are also the cheapest thing for a refactor to drop, since they read like decoration beside the happy path, and a dropped role check is a buyer who can create a Workshop.

## Gate checklist

- [ ] The seven expected responses were written down before the first request was sent.
- [ ] A create with a full body returns 201, and the returned slug is derived from the name rather than sent by the client.
- [ ] A second create for the same owner returns 409 `WORKSHOP_EXISTS` and the Workshop count for that owner is one.
- [ ] Two overlapping creates end with one document, and the response that lost is a 409 rather than a 500.
- [ ] A create body carrying `ownerId` and `status` leaves both fields at the server's values.
- [ ] `GET /workshops/mine` returns the workshop created by the same token and never reads an id from the query string.
- [ ] A patch from the other workshop owner returns 403 with no workshop fields, and the stored area and commission flag are unchanged.
- [ ] A making range of 40 to 14 is refused with 400 and leaves both stored values alone.
- [ ] Two Artisan credits exist under one workshop, and each carries the workshop id from the session rather than from the body.
- [ ] A credit edit from the other owner returns 403 and the stored display name is unchanged.
- [ ] A retired credit disappears from the public roster and still appears on any Piece that credits it.
- [ ] A slug change before any Piece exists answers the old slug with the workshop and a `canonicalSlug`.
- [ ] A slug change after a Piece exists returns 409 `SLUG_LOCKED` and leaves the stored slug alone.
- [ ] The public payload contains the public fields and none of `ownerId`, `contactPhone`, `status`, `slugHistory`, the commission settings or the draft and sold counts.
- [ ] An unknown slug returns a plain 404 with a fixed body and no suggested names.
- [ ] A buyer token is refused by all four authenticated routes.
- [ ] `db.workshops.getIndexes()` shows a unique index on `ownerId` and a unique index on `slug`, and the output is saved.
- [ ] The raw 400, 403 and 409 responses are saved with their `error.code` values and no live tokens.

## Learning log

1. How many Workshop documents existed for Amina after the second create, and what did the raw response contain? Name the status, the code and the count you read.
2. Which field in the create body did you send with a wrong value to prove the route picks fields, and what did the stored document contain instead?
3. What did the cross-workshop patch return, and how did you prove the record was unchanged? Quote the response code and the two field values you compared.
4. Which workshop id ended up on the first Artisan credit, and which two values did you compare to prove the session won over the body?
5. Explain why the slug may change before the first Piece and is refused afterwards. Name the artefact that makes a change expensive once a workshop has been trading for a week.
6. Which fields did the public payload omit, and why is the contact phone shown on an order page but never on a workshop page?
7. Why does this module answer 403 rather than 404 when the wrong owner patches a workshop, and which property of the workshop record decides that choice?

## What a passing gate leaves behind

Four artefacts, not a screenshot. First, the raw responses for the seven planned rows, with the document counts beside them. Second, the index list from the running database, because the one workshop rule and the slug rule both live there. Third, the roster reads: two credits in the owner view and one name in the public view. Fourth, the learning log with the numbers you actually received, including any row where the first response was wrong. A gate with no wrong row in it usually means the table was not written first.

Two honest limits belong in the write-up. Nothing here proves that a story is accurate or that a making time is realistic. A workshop that writes 3 to 4 days for a table sized cover has passed every check in this module, and only the buyer who waits six weeks will find out. And nothing here is reachable by a person yet, because the screens do not exist. Module 10 builds them, and its gate is the first place where a maker's experience is judged instead of a route's.

Do not commit tokens, and do not leave a development database seeded with a workshop whose name you did not choose. The next module starts from a clean second account with no workshop at all, and that account is easier to create now than to reconstruct under time pressure.
