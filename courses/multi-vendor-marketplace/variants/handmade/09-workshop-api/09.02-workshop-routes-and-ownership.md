# Workshop fields, slugs and ownership

Four routes and two schemas carry this lesson. The schemas hold the workshop's facts to a shape: a name, an area, a story, a making range, a shipping link, a slug and an owner, plus the Artisan credits that belong to it. The routes hold the ownership rule: one workshop per owner, your own workshop for reading, your own workshop or nothing for writing.

Most of the work is in the refusals. A create request from an owner who already has a workshop must not write a document. A patch from a different owner must not touch a field. A slug that another workshop already holds must not collide. A credit record for another workshop's Artisan must not be edited. Each of those is a line of code you can write in a minute and a test you may never run, and running the test first is what separates a workshop API from a workshop shaped hole.

Build in the order below. The schema first, because every route reads it. The slug second, because the create route cannot answer without it. Then create, read and patch, then the two Artisan routes, then the public projection. Each piece is testable on its own, and a mistake in an earlier piece hides inside a later one.

## The schema, and why each field is shaped that way

Start with the model, because the routes are thin wrappers over it. The field list is short and every type is chosen so that a wrong value is hard to store rather than easy to send.

```js
// server/src/modules/workshops/workshop.model.js (fields and validators, not the whole file)
const workshopSchema = new mongoose.Schema({
  ownerId:               { type: ObjectId, ref: "User", required: true, unique: true },
  name:                  { type: String, required: true, trim: true, minlength: 2, maxlength: 80 },
  slug:                  { type: String, required: true, unique: true, lowercase: true, trim: true },
  slugHistory:           { type: [String], default: [] },
  area:                  { type: String, required: true, trim: true, minlength: 2, maxlength: 60 },
  story:                 { type: String, trim: true, maxlength: 1200, default: "" },
  makingDaysMin:         { type: Number, required: true, min: 1, max: 365 },
  makingDaysMax:         { type: Number, required: true, min: 1, max: 365 },
  shippingProfileId:     { type: ObjectId, ref: "ShippingProfile", default: null },
  contactPhone:          { type: String, trim: true, maxlength: 20, default: null },
  status:                { type: String, enum: ["active", "paused"], default: "active" },
  acceptingCommissions:  { type: Boolean, default: true },
  maxActiveCommissions:  { type: Number, default: 3, min: 0, max: 20 },
  defaultDepositPercent: { type: Number, default: 50, min: 10, max: 90 },
  quoteValidityDays:     { type: Number, default: 14, min: 1, max: 60 },
}, { timestamps: true });

workshopSchema.path("makingDaysMax").validate(function longerThanMin(value) {
  return value >= this.makingDaysMin;
}, "The longest making time cannot be shorter than the shortest");
```

The two date free integer fields deserve a note. A making time is a range of days, so a number is the right type and a `Date` is not: a `Date` drags a timezone, a calendar and a start instant into a question that has none of the three. The same reasoning is behind the absence of an opening hours field. A workshop that answers messages in the evening does not need a seven day pattern on its public page, and a pattern that is wrong is worse than a sentence in the story field.

The commission settings carry bounds rather than free numbers. The deposit default sits between 10 and 90 percent, and the quote validity sits between 1 and 60 days. Those limits are a course choice, not an industry figure. They exist so that a form in module 10 cannot save a 0 percent deposit that leaves the workshop with no commitment from the buyer, or a 400 day quote that outlives the material it prices.

The Artisan schema is deliberately smaller than the workshop, because a credit record answers one question: who made this, and may we say so.

```js
// server/src/modules/workshops/artisan.model.js (fields only)
const artisanSchema = new mongoose.Schema({
  workshopId:  { type: ObjectId, ref: "Workshop", required: true, index: true },
  displayName: { type: String, required: true, trim: true, maxlength: 60 },
  showName:    { type: Boolean, default: true },
  bio:         { type: String, trim: true, maxlength: 400, default: "" },
  imageUrl:    { type: String, default: null },
  retiredAt:   { type: Date, default: null },
}, { timestamps: true });
```

A retired Artisan is not deleted. A Piece listed before the retirement still credits her, and a sold Piece's order snapshot still names her. Deleting the record would break both, so retirement sets a date and the public roster hides the row. Module 11 refuses to credit a retired Artisan on a new Piece, which is the only place where the date matters at listing time.

## A slug that collides safely

The slug is the readable part of a page address: `ghurza.app/workshops/bayt-al-zayt` instead of a 24 character id. The page is public, so a maker may print the address on a card or send it to a buyer in a message. Both uses mean the slug has to be readable, unique and stable.

```js
// server/src/modules/workshops/slug.js
export function slugify(name) {
  return name
    .toLowerCase()
    .normalize("NFKD")
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-+|-+$/g, "")
    .slice(0, 60);
}
```

The naive create writes `slugify(name)` and lets the database refuse a second workshop with the same name, which arrives at the owner as a 500. The fix is a small loop with one subtlety: MongoDB reports a duplicate slug and a duplicate owner with the same error code, so the handler has to read the key that collided before it decides what to say.

```js
// server/src/modules/workshops/create-workshop.js (the retry loop only)
const base = slugify(input.name);
for (let attempt = 0; attempt < 5; attempt += 1) {
  const slug = attempt === 0 ? base : `${base}-${attempt + 1}`;
  try {
    return await Workshop.create({ ...input, slug });
  } catch (error) {
    if (error.code === 11000 && error.keyPattern?.ownerId) {
      throw httpError(409, "WORKSHOP_EXISTS");        // the one workshop rule, not a slug clash
    }
    if (error.code === 11000 && error.keyPattern?.slug) continue;   // try the next suffix
    throw error;
  }
}
throw httpError(409, "SLUG_UNAVAILABLE");
```

Five attempts is a judgement, not a law. It is enough for three workshops that share a name and it ends in an honest conflict rather than an unbounded loop. The alternative is a random suffix after the fifth try, which always succeeds and gives the workshop an address nobody can read. Between an ugly refusal and an unreadable address, refuse.

Check the index once with `db.workshops.getIndexes()` and save the output. A schema that declares `unique: true` on a collection whose index was never built is the quiet version of this bug, and it ships.

## Create, and what the body may not say

The create route reads seven fields from the body and writes five more of its own. The body supplies `name`, `area`, `story`, `makingDaysMin`, `makingDaysMax`, `contactPhone` and an optional `slug` request. The server supplies `ownerId` from the session, the derived `slug`, an empty `slugHistory`, `status` as active and the commission defaults. A body that carries `ownerId`, `status` or `shippingProfileId` is not an error; those keys are dropped, because a client that sends them is guessing and a route that honours them is a hole.

The order of work is short and it matters. Validate the body first, so a malformed request is a 400 before any database call. Then check whether the owner already has a workshop, which answers the ordinary second attempt with a readable 409. Then insert with the slug loop, which answers the race. The response is a 201 with the owner view, because the owner is the only caller of this route.

```json
{
  "error": {
    "code": "WORKSHOP_EXISTS",
    "message": "This account already runs a workshop",
    "fields": {}
  }
}
```

A validation failure uses the same envelope with field keys, so the client has one handler rather than two. The making range is the most likely field to fail, and the message should name the pair rather than the individual number: "The longest making time cannot be shorter than the shortest" is a sentence an owner can act on.

## Reading your own workshop, and the 404 that is not a failure

`GET /workshops/mine` finds the workshop by the owner in the token and returns the owner projection. There is no id in the path, no query parameter and no way to ask for somebody else's workshop, which makes this the simplest route in the module and the one module 10 depends on most.

When the owner has no workshop, the route answers 404 with the code `WORKSHOP_NOT_FOUND`. That status is easy to misread as a failure, and module 10 treats it as the normal answer for a new maker: it is how the client learns to send her to the setup page. Keep the code stable, because a redirect rule built on an English message breaks the first time somebody improves the wording.

The projection is a field list, not the whole document. The owner view adds the contact phone, the account state, the four commission settings, the creation date, the slug history and three counts. The counts are one indexed query each over the Piece collection, grouped by status. They never include anything from the user record, and they never populate the owner into the response by default. A password hash in a workshop payload is a bug that survives until the first reviewer reads the raw JSON.

## Patching a workshop, and refusing the wrong one

The update route is the only one with a workshop id in the path, so it is the only one that needs the ownership filter. Module 8 wrote the helper and this route calls it rather than inventing a second version.

```ts
// the fields this route may change, and the ones it may never change
const WORKSHOP_EDITABLE = [
  "name", "area", "story", "makingDaysMin", "makingDaysMax", "contactPhone", "slug",
  "acceptingCommissions", "maxActiveCommissions", "defaultDepositPercent", "quoteValidityDays",
];
// ownerId, status, slugHistory, shippingProfileId, createdAt are not editable from here
```

A slug change is allowed through the same route with one extra rule. A workshop that has never listed a Piece may change its address, and the old value moves into `slugHistory` so an old link still resolves. A workshop with any Piece in any state gets 409 `SLUG_LOCKED`, because the address may already be shared, printed or written in a message. That rule is stricter than the display need and simpler than tracking which links are live.

Read the trace for the missing step. There is no point at which the route loads a workshop and then asks whether the caller owns it. A refusal that has already read the record is one careless serializer away from leaking the contact phone, and the filter is the whole authorization.

## Two Artisan routes

The roster needs two routes, and both derive the workshop from the session rather than from the body. `POST /workshops/:workshopId/artisans` resolves the caller's workshop, compares it with the id in the path, and inserts a credit with the resolved `workshopId`. `PATCH /artisans/:id` filters on the credit id and the resolved workshop together, so another owner's credit id matches nothing.

Three rules sit inside those routes. The display preference is stored, not applied: an Artisan with `showName: false` keeps her name on the owner view and is shown to buyers as the workshop's maker. A retirement is a date, not a delete, and a retirement leaves every existing Piece's credit intact. And an edit by the wrong owner returns 403 with no fields, even though the id in the path is a real credit.

The retirement rule has a second half that belongs to module 11. A new Piece may not credit a retired Artisan, so the Piece route checks `retiredAt` before it writes. Writing that check now, in a comment beside the retire handler, saves you from discovering it as a listing bug in three lessons.

## The public page, by slug

The public read is the only unauthenticated route in the module and the only response a stranger can see. It resolves a slug, falls back to `slugHistory` for an address that moved, and projects eight fields: the id, the slug, the name, the area, the story, the two making values and whether a shipping profile exists. It also returns `availablePieceCount` and `canonicalSlug`, so a client that arrived through an old link can rewrite its address instead of showing two addresses for one workshop.

Two details keep this route honest. An unknown slug gets a plain 404 with a fixed body, because a message that suggests a similar name is a search box for every workshop on the platform. And the available count is computed in the same request with one indexed count, not stored on the workshop as a number that every Piece write has to remember to update.

## Two tests that fail on a naive route

Write both before the fix. The first proves the one workshop rule survives a second request, and it is the test most implementations pass by accident because their route happens to check first. Run it twice in a row, then run the two requests through a barrier so they overlap, because the route check is not what makes the rule true.

```js
// server/tests/workshops.create.test.js
test("an owner cannot create a second workshop", async () => {
  await request(app).post("/api/workshops").set(auth(amina)).send(tatreez).expect(201);
  const second = await request(app).post("/api/workshops").set(auth(amina)).send(tatreezAnnex);

  expect(second.status).toBe(409);
  expect(await Workshop.countDocuments({ ownerId: amina.id })).toBe(1);
});
// currently 201, and /workshops/mine returns whichever document sorts first
```

```js
// server/tests/workshops.patch.test.js
test("another owner cannot patch this workshop", async () => {
  const res = await request(app)
    .patch(`/api/workshops/${tatreezId}`)
    .set(auth(kareem))
    .send({ area: "Somewhere else", acceptingCommissions: false });

  expect(res.status).toBe(403);
  const stored = await Workshop.findById(tatreezId).lean();
  expect(stored.area).toBe("Rimal");
  expect(stored.acceptingCommissions).toBe(true);
});
// currently 200, the area is "Somewhere else" and commissions are paused
```

The second failure is the one that costs money. An owner who can pause another workshop's commissions stops that workshop taking new work, and every screen in the browser still looks correct while it happens.

## The diff that closes both

The fix is a filter and a field list, small enough to read in one screen. The handler keeps its validation and its projection.

```diff
 export async function updateWorkshop(req, res, next) {
-  const workshop = await Workshop.findByIdAndUpdate(req.params.id, req.body, { new: true });
-  if (!workshop) return next(httpError(404, "WORKSHOP_NOT_FOUND"));
-  res.json(workshop);
+  const changes = pick(req.body, WORKSHOP_EDITABLE);
+  const workshop = await assertWorkshopOwner(req.params.id, req.user, { Workshop });
+  const ownerView = await applyWorkshopChanges(workshop, changes);
+  res.json(ownerView);
 }
```

`pick` is three lines and it is the only thing standing between the request body and the document. A spread of `req.body` would let a caller set `status` to paused, point `shippingProfileId` at another workshop's profile, or rewrite `ownerId` to another user. None of those fields is displayed anywhere, which is exactly why nobody notices for a month.

## Acceptance criteria

- [ ] `POST /api/workshops` creates one workshop, ignores `ownerId`, `status` and `shippingProfileId` in the body, and returns 201 with the owner view.
- [ ] A second create for the same owner returns 409 `WORKSHOP_EXISTS`, and the document count stays at one, including when the two requests overlap.
- [ ] Two workshops with the same name receive different slugs, and the second one carries a numeric suffix.
- [ ] `makingDaysMax` below `makingDaysMin` returns 400 with a message about the pair, and nothing is written.
- [ ] `GET /api/workshops/mine` returns 404 `WORKSHOP_NOT_FOUND` for an owner with no workshop and never reads an id from the query string.
- [ ] `PATCH /api/workshops/:id` from another owner returns 403 and the stored record is unchanged.
- [ ] `PATCH` accepts only the eleven editable fields, and a body carrying `ownerId` or `status` changes neither.
- [ ] A slug change is refused with 409 `SLUG_LOCKED` once the workshop lists any Piece, and the old slug answers the public route after a permitted change.
- [ ] `GET /api/workshops/:slug` returns the public projection with no `ownerId`, `contactPhone`, `status`, `slugHistory`, commission settings or counts other than the available total.
- [ ] Both Artisan routes insert and edit only inside the caller's own workshop, and a credit edit from another owner returns 403 with the record unchanged.
- [ ] The unique indexes on `ownerId` and `slug` exist in the running database, and the index list is saved with the gate evidence.

## Bridge to the gate

The next lesson is the gate, and it runs these routes with curl from two workshop accounts and one buyer. It proves that a second workshop is refused, that a cross-workshop patch is refused, that the public payload is smaller than the owner payload, and that a buyer token reaches none of the writing routes. It also adds two Artisan credits to one workshop, because module 10 sends a new owner to a page that expects the roster routes to exist.

The screens that call all of this come in module 10, where the first request a new maker makes is the 404 you have just made a normal answer.
