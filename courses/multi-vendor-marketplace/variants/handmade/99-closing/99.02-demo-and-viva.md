# Five-minute demo and capstone defense

The demo is not a tour of the app. It is a claim that Ghurza handles the hard case: a piece that is sold once, a commission that runs for weeks, two payments, and an artisan whose credit never becomes access. Five minutes is enough for that claim and too short for anything else, which is why the script from 99.1 exists.

Before you start, check four things from the reviewer's side. The live URL answers `GET /health` with the database connected. The worker process is running, because a quote expiry or a notification that never arrives turns into a silent failure in the middle of the demo. The seed is the one described in the README, with fictional workshops only. And `docs/EVIDENCE.md` is open in a second tab, because every question after the demo will be answered from it.

## What the five minutes prove

| Minute | Action on the live URL | What the reviewer is checking |
|---|---|---|
| 0 to 1 | Cart with two workshops, one refused line for a country the workshop does not ship to | The shipping answer is per workshop and it is honest |
| 1 to 2 | Test card checkout, two orders with two shipping amounts | One cart splits into per-workshop orders, each with a frozen snapshot |
| 2 to 3 | "Request something similar", quote version 1, then version 2, then a failed acceptance of version 1 | A revised quote supersedes the old one and the server decides, not the browser |
| 3 to 4 | Deposit, two progress updates with photographs, buyer approval, balance payment | Two payments at two stages, and production is visible between them |
| 4 to 5 | Maker adds a tracking reference and marks it shipped, buyer sees the whole timeline | The long workflow ends where the buyer can see it |

Say one sentence before each beat, name what you are about to prove, and stop talking while the page loads. A reviewer who hears a claim and then sees it happen remembers both. A narrator who talks through the whole five minutes leaves nothing checkable behind.

Two pieces of evidence stay out of the headline and go in the file instead. The two-tab race that ends in one order and one 409 is hard to perform live on a phone connection, and the late-success refund is invisible when it works. Show the transcript for each if you are asked, and say plainly that they are recorded rather than performed. That honesty is worth more than a risky live race.

## Answer from the record, not from memory

The questions below are the ones a reviewer should ask. Each has a shape of a good answer: the mechanism, the place in the code, and the evidence that it works. If your answer is only the mechanism, you have described an intention.

**How is a piece sold exactly once?** Name the conditional update on the piece document, the status and hold predicate that must match, and the 409 the loser receives. Then show the race test and its saved output. The answer fails if it describes a read followed by a write, because two buyers can both read available.

**Why two payments instead of one authorisation captured later?** Explain the lifetime of a card authorisation, the weeks a commission takes, and what expires in between. Then name the two amounts from the accepted terms and the rounding rule that makes them add to the total. An answer that only says the provider supports it has missed the product reason.

**What happens if the deposit webhook arrives twice, or the balance event arrives before the deposit?** Describe the recorded event identifier and the state check that makes a repeat do nothing. For the early balance event, describe the guard that refuses to move a commission that has not reached the balance stage, and where that refusal is logged. Naming the file and the condition is the difference between an answer and a hope.

**The quote expires while the buyer is on the payment page. What happens, and which line decides it?** Point at the acceptance guard that compares the validity time with the server clock, and at the response the buyer sees. Then say why the browser countdown is not the rule.

**Who can read the buyer's reference photographs, and how did you test it?** Name the two parties, the authorized listing route and the denial for everyone else. Show the module 8 transcript row with the credited artisan and the second buyer. An answer that starts with the file identifier being unguessable has answered the wrong question.

**Why does the product show a date range and never a delivery date?** Explain the three clocks: production, handling and transit. A maker controls the first, partly controls the second, and does not control the third, so the product promises a range and shows the assumptions. Then say what happens when a range changes, which is a new event, not an edit that erases the old one.

**What does the credited artisan see and control?** Nothing, unless a separate role is granted and tested. Credit is presentation, the piece page shows the approved display name, and no route accepts an artisan as an actor. Say how you tested that with a real account, because this is the answer most likely to be wrong in a project that reused a role check.

**If you had to pay artisans for real, what would change?** Name the ledger you would add, the constraints it needs, and the questions you would check first: which entity is paid, what happens to a refund after a payout, and which records finance needs to reconcile. Saying that this table wants a relational store is a strong answer, because it shows you know where your chosen model stops helping.

## What to do when something fails live

Something may fail, and the response matters more than the failure. If a page returns an error, read the response code out loud, open the server log and say what it means. If the provider is slow, use the prepared fallback and name it as a fallback. If the deploy is down, show the evidence file and the last successful run with its date. A reviewer is checking whether you can diagnose your own system, and a calm read of a 409 is stronger evidence than a rehearsed success.

Do not repair the demo by editing the database in front of the reviewer. If the only way to show a state is to write it by hand, the state is not reachable through the product, and the honest answer is to say so. That sentence is uncomfortable and it is the one that gets remembered for the right reason.

## What the capstone does not claim

Say the limits in your own words before you are asked. Stripe test mode only, no payout to any maker, one currency, no carrier integration, no tax or duty calculation, and no admin panel. The artisan credit is a record and not an account. Those limits are part of the design, and a candidate who states them shows judgement rather than a gap.

## Learning log

1. Which beat of the demo took longest on the rehearsed connection, and what did you cut or prepare as a fallback because of it?
2. Take one defense answer you gave from memory and rewrite it with the file name, the condition and the evidence row beside it.
3. Which piece of evidence in `docs/EVIDENCE.md` would be hardest for another person to repeat, and what did you change to make it repeatable?
4. Name one limit you stated, and one sentence you removed from the README because it claimed more than the app does.
5. What is the first thing you would build next, and which stored record would it read or change?

## After the defense

Commit the demo script, the evidence rows and any answer you improved. Then write one page for yourself: what you would change first if this product had real users next month. The course ends with a defendable system, and the next project starts with the same habit: name the operation, choose the shape, prove the boundary, and keep the proof where someone else can run it.
