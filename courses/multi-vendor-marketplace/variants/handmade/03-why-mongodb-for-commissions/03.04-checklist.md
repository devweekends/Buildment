# Data model decision gate

This gate is a short conversation about one file. Bring `docs/erd-draft.md`, the decision table inside it, and the contract test from 3.3. A mentor will point at a box and ask which operation needs it, then point at a field and ask what breaks if it is copied, and finally ask when you would leave this model behind. If the answers need the file open in front of you, the file is a sketch rather than a decision.

The gate exists because the rest of the course builds on these shapes. Module 5 writes the schemas from this draft. Module 19 claims a piece with a conditional write that only makes sense if the hold lives inside that piece. Module 23 copies accepted terms onto a commission that must survive weeks of workshop edits. A wrong box now becomes a wrong route in three weeks, and the cost of changing it grows each time a module trusts it.

## Gate checklist

- [ ] `docs/erd-draft.md` is committed with the decision table, the ERD and the field list
- [ ] Every table row names a cost and a credible alternative, not only a benefit
- [ ] The ERD draws one ownership edge from User to Workshop and labels the artisan edge as credit
- [ ] The hold appears as a field on Piece, with a note that only one claim is current
- [ ] The Commission shows an accepted terms snapshot and exactly two payment entries
- [ ] The Quote appears as its own collection with a version and a status
- [ ] `server/src/tests/erd-contract.test.js` passes, and its earlier red run is recorded
- [ ] The committed file says where a relational schema would enforce more than this model
- [ ] One deliberate break of the contract test is recorded, then reverted
- [ ] The learning log below is answered in your own words

## Walk three records aloud

Start with the piece. Name a bowl in your seed, its workshop, its price in minor units and its status. Then say what the claim writes: the status becomes held, and a hold object with a checkout identity and an expiry instant lands in the same document. Say why one update matters. If the status and the hold were separate documents, a reader could find a piece that says available while a live claim exists, and nobody could say which record is right. Then say what happens when the claim expires with no payment: the same field allows a later claim to match, and the piece returns without a repair job.

Next, the copy. Say the sentence a buyer uses, "make me another like this", and then say what your model does with it. A `CustomRequest` appears with a buyer, a workshop, a brief, a budget range and a reference to the sold piece. Nothing is cloned. The sold piece stays sold and stays visible as portfolio. The request carries no price, because no price has been agreed. If your draft has a route from a sold piece to a new available piece, the gate stops here and you fix the draft.

Then the commission. Name the quote version the buyer accepted and the fields the acceptance copies. The total, the deposit, the balance, the currency, the included revision, the production range and the cancellation terms all move into the commission's own `terms`. Then the two payments: the deposit at acceptance and the balance at approval, each with its provider reference and its confirmed time. Say why one payment cannot serve, in one sentence a buyer would understand. A card authorisation expires in days and the work takes weeks.

## Test the guard, then break it

Run the contract test and show it green. Then open the draft, delete the word that marks the hold as embedded, and run the test again. It must fail with a message that names the missing claim. Restore the line and show it green again. That small cycle is the evidence that the test protects the decision rather than decorating the repository.

Record both runs in your learning log, including the assertion message. A reviewer who sees only a green run cannot tell whether the test ever looked at your file. If the test stayed green after the edit, the pattern is too loose, and you fix the pattern before the gate passes. If the test failed for a missing module instead of a missing sentence, the test itself is broken and needs the same attention.

## Name where the relational schema wins

The gate is not a loyalty test for one database. Say plainly which rules this model cannot enforce and how you will test them instead. A piece pointing at a workshop that does not exist is an application check. A deposit plus a balance that fails to equal the total is a service check with a unit test around the rounding helper. Two live claims on one piece are prevented by the conditional predicate, and that predicate gets a concurrent test in module 19.

Then name the case where you would reach for Postgres: a payout record that says what each credited artisan is owed per sale and per commission, appended by several services and reconciled by a person. That table wants foreign keys, a numeric money type and reporting joins, and no document collection gives you those for free. Saying this out loud is stronger evidence of judgement than defending one database for everything.

## What this gate does not prove

This gate proves a shape, a written argument and a guard. It does not prove a claim under concurrency, a verified payment, an isolated read or a refund. Those arrive with their own gates in modules 8, 19 and 23. Carry the draft forward and keep it honest as each of those modules lands, because the next reader will design against what the file says.

## Learning log

1. Paste the two contract test runs, before and after you wrote the draft. What did the failing assertion name, and what did you change to make it pass?
2. Which record can a buyer purchase today, and which record only asks for future work? Quote the line in your draft that keeps them apart.
3. Where does the hold live, and what goes wrong if it becomes its own collection? Give the failure in one concrete sequence.
4. Which fields did you copy onto the Commission, and which did you leave as references? Explain one choice that a reviewer might challenge.
5. Name one rule that Postgres would enforce with a constraint and this model must check in code. Say where you test that rule.
6. What will you add to `docs/erd-draft.md` when module 5 creates the Order and OrderLine models, and which edge will you label?

## After the gate

Commit the draft, the contract test and this log. Then open module 4, which connects the database this model lives in and fails loudly when the connection is wrong. Keep the draft editable: the first thing module 5 will do is disagree with one box, and that disagreement is cheaper to settle in a document than in a running server.
