# Tables and documents for one-off work

The database question is not about which system is newer. It is about which shape matches the operations you run. Ghurza runs two operations far more often than any other. A buyer claims one piece for fifteen minutes. A buyer or maker opens one commission and needs the agreed terms, the progress and the money in one view. Put those two operations beside a table schema and a document shape and the trade becomes concrete.

Start with the claim. In a relational schema the piece is a row, and the hold is either three more columns on that row or a separate hold table. The claim is one statement, and it is correct:

```sql
UPDATE pieces
   SET status = 'held', checkout_id = $1, hold_expires_at = now() + interval '15 minutes'
 WHERE id = $2
   AND (status = 'available'
        OR (status = 'held' AND hold_expires_at <= now()))
RETURNING id, price_cents, currency, workshop_id;
```

That statement is atomic, and it is the same guarantee the document version gives. Anyone who tells you that only a document database can claim a row safely is selling something. Postgres is strong here, and the returning row is all the checkout needs.

Now the read. A buyer opens an accepted commission. In tables, the page needs the commission row, the accepted quote version row, the quote terms row, the two payment rows, the progress rows and a piece or snapshot row. That is five or six tables joined on a primary key, and the code has to know which quote version is the accepted one. None of that is hard, and the query planner will do it quickly at this size. The cost is not speed. The cost is that the agreement is spread across tables, so every route author has to remember which join makes the terms of this commission rather than the terms of the quote before last.

The document shape answers the same read with one lookup. The commission holds its own copy of the accepted terms, its own two payments and its last twenty progress notes. One `findById` returns everything the page shows.

```js
// Shape sketch only. The Mongoose schema is written in module 5.
{
  _id: ObjectId,
  buyerId: ObjectId,
  workshopId: ObjectId,
  requestId: ObjectId,
  acceptedQuoteId: ObjectId,
  state: "awaiting_balance",
  terms: {                         // copied at acceptance, then never edited
    version: 2,
    totalCents: 48000,
    depositCents: 24000,
    balanceCents: 24000,
    currency: "GBP",
    revisionIncluded: true,
    productionDaysMin: 18,
    productionDaysMax: 24,
    cancellation: "deposit refundable before production starts"
  },
  payments: [                      // exactly two in this domain
    { kind: "deposit", amountCents: 24000, providerRef: "pi_test_1", confirmedAt: "2026-11-02T10:14:00Z" },
    { kind: "balance", amountCents: 24000, providerRef: null, confirmedAt: null }
  ],
  artisanCredit: "Huda, Bayt al Zayt"
}
```

The duplication in `terms` is the point, not an accident. A buyer who agreed to twenty four days did not agree to the thirty days the workshop now quotes by default. Keeping the terms on the commission means a later settings change cannot edit an agreement in force. The same rule covers `artisanCredit`: it records the credit shown when the buyer accepted.

## Mark every field as a reference or a snapshot

Two kinds of copy exist, and mixing them up creates quiet bugs. A snapshot is frozen at a moment and must never be refreshed. The terms, the artisan credit on a sale and the price on an order line are snapshots. A reference points at a living record and must always be read live. The workshop name, the artisan's current display choice and the piece's current status are references. The rule is simple to say and easy to break: a snapshot that gets updated is no longer evidence, and a reference that gets copied goes stale on the next edit.

| Field | Kind | Read behaviour | If you copy it |
|---|---|---|---|
| `commission.terms` | Snapshot | Frozen at acceptance, never refreshed | Correct: the agreement stays as agreed |
| `orderLine.priceCents` | Snapshot | Frozen at purchase | Correct: the receipt cannot be rewritten |
| `commission.artisanCredit` | Snapshot | The credit shown at acceptance | Correct: attribution is evidence |
| `piece.workshopId` | Reference | Resolved live on each read | Wrong: a rename becomes a mass update |
| `artisan.displayName` | Reference | Current approved choice | Wrong: a withdrawn name lingers |
| `piece.hold` | Current value | One claim, replaced on takeover | Wrong: an array of old claims grows forever |

Read the table as two rules. Nothing in the snapshot rows is ever written again after the moment it records, and nothing in the reference rows is ever copied into a document that outlives the read. The hold is a third case: it is a single current value that belongs to the piece's own state, so it is written in the same operation that changes that state.

## Why the hold is embedded and its history is not

The current hold is one value, it changes with the piece's own state, and it must be written in the same operation as that state. Embedding it is a small, bounded field that is replaced, never appended. Its history is a different object with a different question: who tried to claim this piece last Thursday. That question belongs in an order or an audit record, because it grows without a limit and nobody reads it on the piece page. An embedded array that grows on every claim would make the piece document bigger on each write and eventually reach the sixteen megabyte document ceiling. You will never reach that ceiling with a hold, and you will reach it with an unbounded list of attempts if the product runs long enough.

The same test applies to progress updates. Twenty notes with photo ids fits comfortably inside a commission, and the timeline page shows the recent ones. If the product wanted every note ever written on one page, the notes would earn their own collection. The course keeps the last twenty in the commission and stores the full trail in the audit history written by the transition service in module 24.

## Why the workshop, the artisan and the buyer stay referenced

A workshop is shared by many pieces, many commissions and one shipping profile. A bad copy of the workshop name on every piece means every rename is a mass update, and any missed document tells a different story. An artisan is shared by many pieces and may change display choice, including asking to be shown by first name only. A buyer is a login identity used across carts, orders and requests. All three are living records with their own write paths, so all three stay referenced.

References cost something. Resolving a page with ten pieces, each with a workshop and an artisan, tempts you into a query per row. Module 15 measures that cost and fixes it. The decision here is not that references are free; it is that a copy of a living record is worse than a join.

## Quote versions get their own collection

A quote version is immutable once sent, has a status, an expiry instant and a version number, and the worker scans for expired ones. That combination earns a collection with a unique index on `requestId, version`. The request document keeps only `latestSentVersion` and `acceptedVersion` as small integers, so acceptance can be a conditional update that fails when the buyer clicked an older version.

An array of versions inside the request is defensible when negotiation stops after two rounds. The course does not rely on that assumption. A negotiation can run several rounds, the worker needs to find expired quotes without reading every request, and an immutable document is easier to reason about than a slot in an array. If your own project never revises a quote, the array is simpler and you should say so in your decision table.

## Where a relational database genuinely wins

Say the honest part out loud. Postgres can enforce things this document model has to check in code. A foreign key guarantees that a piece points at a workshop that exists, so a deleted workshop cannot leave orphan pieces behind. A check constraint can assert that the deposit plus the balance equals the accepted total, which the document model can only test in a service and re-test in a job. A partial unique index can make it impossible for two live holds to exist for one piece, where the document model relies on one carefully written conditional update. Money as a `numeric` type arrives with the arithmetic rules you want.

The stronger case is a payout record. Imagine Ghurza growing a ledger that records what each credited artisan is owed per sale and per commission, appended by several services and reconciled by a finance person. That table wants strict keys, a stable audit trail and reporting joins. A relational store beside the document store is a reasonable answer, and module 3.3 lists it as the case where the course would switch. What you should not do is keep the ledger in a loose document collection and hope that nothing drifts.

The decision for Ghurza is therefore narrow rather than ideological. Documents for the two aggregates that must move as one unit: the piece with its hold, and the commission with its terms, payments and recent progress. References for the shared records. Application invariants with tests for the rules the database cannot see. If your team already runs Postgres with confidence, you can build this product in Postgres and be right; you would trade a heavier read for constraints that hold you up.

One more point belongs in prose rather than in a question. A workshop reference is not only cheaper to maintain than a copied name; it is the only version that can answer "which pieces belong to this workshop" without scanning every piece. Copies of a name cannot be grouped reliably once one of them goes stale.
