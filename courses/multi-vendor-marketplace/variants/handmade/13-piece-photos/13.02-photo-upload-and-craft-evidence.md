# Upload real piece photos and craft evidence

A photograph route looks like the easiest route in the project and carries more risk than most. It accepts a file from a phone, which is untrusted input, it spends money on storage for every request that reaches the provider, and it writes a pointer that a buyer's receipt may depend on months later. The order of the checks is therefore part of the design, not an implementation detail.

Three routes handle the write side and all three resolve the workshop from the session. A replace is a new file plus a pointer change, and a delete is a pointer change plus a storage removal. The piece already has a `photos` array in its model from the data model module. This lesson gives that array rules, a limit and a lifetime.

```js
// server/src/modules/pieces/photo.routes.js (shape only)
router.post("/maker/pieces/:id/photos", requireAuth, requireRole("maker"),
  upload.single("photo"), addPhoto);
router.patch("/maker/pieces/:id/photos/:photoId", requireAuth, requireRole("maker"),
  upload.single("photo"), replacePhoto);
router.delete("/maker/pieces/:id/photos/:photoId", requireAuth, requireRole("maker"), removePhoto);
```

The photo is addressed by its subdocument identifier, not by the storage public identifier. A public identifier looks like `ghurza/pieces/665f0a9c/cover`, and the slashes are read as path segments by Express, which turns a delete into a not found error and a confusing hour. Address the subdocument, then let the server read the stored public identifier from the record it already owns.

## The photo subdocument

Each photo is a small object inside the piece document. Keep it small, because the buyer's page needs at most four of them and only a few short fields: a URL to display, a public identifier to delete later, a short description that doubles as alt text, a kind that says which job the photo does, and a creation time for ordering.

```js
// server/src/modules/pieces/piece.model.js
const photoSchema = new Schema(
  {
    url: { type: String, required: true },
    publicId: { type: String, required: true },
    alt: { type: String, required: true, maxlength: 200 },
    kind: { type: String, enum: ["cover", "detail", "scale", "flaw"], required: true },
  },
  { timestamps: { createdAt: true, updatedAt: false } }
);

photos: {
  type: [photoSchema],
  default: [],
  validate: {
    validator: (photos) => photos.length <= 4,
    message: "A piece holds at most four photographs",
  },
},
```

The alt text is required because the description is what a buyer using a screen reader receives instead of the image. Writing it is also a check on the photograph: if you cannot say what the picture shows in one sentence, it probably does not show the stitch. A caption such as "close up of red cross stitch on cream cotton" is useful. A caption such as "photo" is not.

The validator is a safety net, not a concurrency control. Two uploads that arrive together can both read a piece with three photos, both pass a check in application code, and both write, leaving five. The limit has to be evaluated by the database against the document it is about to change.

```js
// server/src/modules/pieces/photo.service.js (the guard, not the whole function)
const updated = await Piece.findOneAndUpdate(
  {
    _id: pieceId,
    workshopId,
    status: { $in: ["draft", "available"] },
    $expr: { $lt: [{ $size: "$photos" }, 4] },
  },
  { $push: { photos: { url: uploaded.secure_url, publicId: uploaded.public_id, alt, kind } } },
  { new: true }
);
```

A null result from that call can mean four different things: the piece is gone, it belongs to another workshop, its photographs are frozen, or it already holds four. The route has to tell them apart before it answers, because "this piece is sold", "this piece is not yours" and "this piece already has four photographs" are three different sentences on screen. Re-read by identifier only, then decide, and keep the ownership answer a forbidden response rather than a not found.

## Check the workshop before the bytes

Order the checks by cost and by consequence. Load the piece by identifier. If it does not exist, answer not found. If it exists and its workshop is not the workshop resolved from the signed in user, answer forbidden before the upload helper runs at all, because a cross workshop upload that reaches storage has already spent quota and created a file nobody owns. If the status is held, sold or archived, answer a conflict. Only then read the file and stream it.

This ordering matters in a real workshop. A maker with two tabs open, or a session that expired an hour ago, will eventually send a file to the wrong place. The refusal has to arrive in a second with a message that names the problem, and the API log should show a refused attempt rather than a successful upload followed by a rejected write.

File checks come after ownership and before storage. One file per request, an image content type, and a size limit you also state in the interface. Five megabytes is a reasonable ceiling for a phone photograph and keeps a slow connection from looking like a broken application. Configure the upload middleware with memory storage rather than a temporary file, because a server with an ephemeral disk loses the file between the upload and the stream, which is the bug that appears on deploy day and never before.

Where the file comes from matters as well. A file name, a content type and the first bytes can disagree. Check the magic number for the image types you accept rather than trusting the extension, and re-encode the image before storing it if your provider makes that easy. Re-encoding also removes the metadata that could carry the coordinates of a maker's home.

## When the set may change

Photographs can be added, replaced and removed while a piece is a draft or available, and they display in creation order with the cover first. The moment a checkout holds the piece the set freezes, because a buyer has agreed to buy what the photographs show. A sold piece keeps the same set, because the order snapshot points at one of those addresses.

<StateMachine title="When a piece may change its photographs" chart={`stateDiagram-v2
  [*] --> draft

`} />

Read the two self transitions as the only writing states and the two labelled exits as the lock. The gate tests both: a replace on an available piece succeeds and destroys the old asset, while a replace on a sold piece returns a conflict with the photo set unchanged.

## Publishing needs a photograph

Module twelve published a draft once its title, price, materials and care notes were present. This lesson adds one more condition in the same place, because a listing that offers a one-off object without a picture of it asks a buyer to pay for something she cannot see. Put the rule in the publish filter rather than in the form, so a stale tab cannot skip it.

```js
// the same publish action from module 12, with one more condition
const updated = await Piece.findOneAndUpdate(
  { _id: pieceId, workshopId, status: "draft", priceCents: { $gt: 0 }, "photos.0": { $exists: true } },
  { $set: { status: "available" } },
  { new: true }
);
```

Refusing with `PHOTO_REQUIRED` and a field message is better than a generic conflict, because the maker can fix it in one action. Keep the two rule sets together in the service that owns publication, so the dashboard, the piece page and any later bulk publish all refuse the same draft for the same reason. A rule that exists in three places will disagree with itself within a week.

The test below fails on the code module twelve left behind, and it feeds the gate.

```js
// server/tests/pieces.publish.test.js
test("a draft with no photograph cannot publish", async () => {
  const res = await request(app).patch(`/maker/pieces/${draftNoPhoto.id}/status`)
    .set("Authorization", `Bearer ${tokenA}`).send({ status: "available" });
  expect(res.status).toBe(400);
  expect(res.body.error.code).toBe("PHOTO_REQUIRED");   // currently 200 and the piece is for sale
});
```

## Replace and delete without breaking a receipt

Replacing a photograph is three operations in a fixed order: upload the new bytes, write the new pointer, destroy the old asset. The order is not arbitrary. Destroy first and a failed upload leaves the piece with no photograph at all. Write the pointer and let the destroy fail, and you leak one file while keeping a usable listing. The second failure is the one you want.

```js
// the order that keeps a piece usable (logging and rollback omitted)
const uploaded = await streamToStorage(buffer, pieceId, kind);
const updated = await Piece.findOneAndUpdate(
  { _id: pieceId, workshopId, status: { $in: ["draft", "available"] }, "photos._id": photoId },
  { $set: { "photos.$.url": uploaded.secure_url, "photos.$.publicId": uploaded.public_id,
            "photos.$.alt": alt, "photos.$.kind": kind } },
  { new: true }
);
if (!updated) {
  // held, sold or gone: the new asset is an orphan from this moment
  await destroyAsset(uploaded.public_id).catch(logOrphan);
}
```

Deletion has one hard rule: never destroy an asset that an order line references. The checkout module stores the cover address on the order line, so a buyer opening a paid receipt next month must still see the piece she bought. That is why the freeze belongs in the update filter rather than in a comment. When the status is held or sold the write does not match, and the route turns the empty result into a conflict with a message about a frozen photo set.

A workshop that genuinely needs to record new damage on a sold piece has a different problem and needs a different tool. The stretch lab attaches new evidence to the order without touching the sold listing. Keeping those two paths apart is the difference between a marketplace that respects its receipts and one where history is editable.

Choose the cover deliberately. When the first photo arrives and no cover exists yet, set its kind to cover. When a maker picks a different cover, or deletes the current one, reassign the cover to the first remaining photograph in the same update so a piece never sits in available with no cover. A listing card without an image is a listing a buyer scrolls past.

Orphaned assets are a small cost and a large signal. Log every failed destroy with its public identifier, and use a folder convention such as `ghurza/pieces/{pieceId}` so a future cleanup job is a prefix listing rather than a database scan. State in your README that orphans are possible and where they come from, because a reviewer who finds an unexpected file should not have to guess.

## Failing tests

Four more tests fail against the code as the pieces module left it, and every one of them is about a boundary rather than about pixels.

```js
// server/tests/pieces.photos.test.js
test("a fifth photograph is refused and four remain", async () => {
  const res = await request(app).post(`/maker/pieces/${pieceWithFour.id}/photos`)
    .set("Authorization", `Bearer ${tokenA}`).attach("photo", buffer, "five.jpg");
  expect(res.status).toBe(400);
  expect(res.body.error.code).toBe("PHOTO_LIMIT");
  const after = await Piece.findById(pieceWithFour.id).lean();
  expect(after.photos.length).toBe(4);          // currently 200 and five stored
});

test("workshop B cannot upload to workshop A and no asset is created", async () => {
  const res = await request(app).post(`/maker/pieces/${pieceA.id}/photos`)
    .set("Authorization", `Bearer ${tokenB}`).attach("photo", buffer, "shot.jpg");
  expect(res.status).toBe(403);
  expect(storageCalls()).toBe(0);               // currently 200 and one upload
});

test("a sold piece refuses every photo write", async () => {
  const res = await request(app).delete(`/maker/pieces/${soldPiece.id}/photos/${photoId}`)
    .set("Authorization", `Bearer ${tokenA}`);
  expect(res.status).toBe(409);
  const after = await Piece.findById(soldPiece.id).lean();
  expect(after.photos.length).toBe(soldPiece.photos.length);
});

test("a file that is not an image is refused before storage", async () => {
  const res = await request(app).post(`/maker/pieces/${draftPiece.id}/photos`)
    .set("Authorization", `Bearer ${tokenA}`).attach("photo", Buffer.from("not an image"), "note.jpg");
  expect(res.status).toBe(400);
  expect(storageCalls()).toBe(0);
});
```

The second test is the important one, because it asserts a count of storage calls and not only a status code. A route that returns 403 after uploading has failed the requirement while looking correct from the browser.

## Acceptance criteria

A maker can attach up to four photographs to a piece in her own workshop, each with a description and a kind, and see them in order with one marked as cover. A fifth upload is refused with a field error and the stored set is unchanged. A replace on a draft or available piece writes the new pointer and destroys the old asset, while a replace on a held or sold piece is refused and changes nothing. A delete removes the pointer and the asset, and reassigns the cover when the deleted photo held it. No response contains the storage secret, no piece document contains image bytes, and the metadata from the original file is gone.

Keep the piece table from the previous module in view while you test. After an upload it should show the new cover without a page reload, and after a publish it should show the piece as available with its photograph. The gate asks you to bring four honest photographs, a refused fifth and a receipt that still loads after the set changed.
