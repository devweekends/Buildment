# Piece photo gate

This gate is passed with a page a stranger can inspect on a phone. Four photographs, each doing a named job, a fifth upload refused without spending storage, a second workshop refused before storage, and a paid receipt that still shows the piece after the maker changed the set. Every check has a number beside it, because a photograph route fails in ways that look fine on screen.

## Set the piece up properly

Choose one finished piece from the seed and give it four photographs that match the plan from the first lesson: the whole object, a craft detail, a scale reference and one honest flaw. Write the description for each one as you would want to read it with a screen reader, and set the kind on each so the page can render them in a sensible order. Nothing here is decoration. The four kinds are the evidence a buyer in another country relies on.

Keep a second piece in the sold state and one order fixture that points at its cover address, so the receipt check has something to load. Keep the second workshop with its own piece ready for the cross workshop attempt. Say in the learning log which fixtures came from the seed and which you injected, because the checkout module does not exist yet and an injected order must not be presented as a payment.

## Walk the checks in order

Start with the happy path. Upload four files to the draft piece and watch the document. Mongo should hold four small objects with a URL, a public identifier, a description and a kind, and no bytes. The storage folder named after the piece should hold four files and no more, and the piece page should show a cover, a detail, a reference and a flaw, with the cover first and the rest in the order you uploaded them.

Then push on the limits. Count the files in the storage folder, upload a fifth photograph, and count again. The answer must be a field error and the same file count, because the guard has to run before the bytes are sent. If the folder grew, the route checked the limit after the upload, and a busy workshop will fill the account one refused request at a time.

Try the same upload as the other workshop's owner. The status must be a refusal, the folder must not change, and the API log should show the attempt against the piece identifier. A route that refuses after uploading has spent money to say no, and the test that only checks a status code will not catch it.

Replace one photograph on the available piece. The new address must render, the old address must stop working, and the public identifier stored on the document must be the new one. Then delete a photograph and confirm the cover moves to the first remaining photo rather than leaving the listing blank. A listing with no cover is invisible in the collection even though its page still works.

Finally, try a delete and a replace on the sold piece. Both must return a conflict, and the order fixture must still load its cover address in the buyer view. Open the old cover address directly in a browser tab as well; a sold piece whose image was destroyed is a receipt with a hole in it, and no amount of correct status coding repairs that for the buyer.

## Read the page the way a buyer does

Test the rule that guards publication next. Create a fresh draft with a title and a price but no photograph, and press publish. It must be refused with a field error that names the photograph, and the piece must stay a draft, so the catalogue never shows a one-off object with nothing to look at.

Open the piece page at a phone width. The cover should fill the frame without cropping the shape of the piece, the detail should be sharp enough to see the stitch or the grain, the scale photograph should include the object that gives size, and the flaw should be visible before the buyer taps anything. Zoom into each one. If the detail photograph is only soft colour, it is not evidence of technique.

Check the alt text with a screen reader or with the accessibility panel in your browser. Each description must say what the photograph shows, not that a photograph exists. Check the original file metadata as well: the stored image must not carry the coordinates of the workshop, which means the server stripped it rather than trusting the phone.

## Gate checklist

- [ ] One available piece carries four photographs, each with a description and a kind, and one is marked as the cover.
- [ ] The database holds URLs, public identifiers, descriptions and kinds only, and no image bytes.
- [ ] The storage folder is named after the piece, so a cleanup job can list a prefix instead of scanning documents.
- [ ] A fifth upload returns 400 `PHOTO_LIMIT`, and the storage file count is unchanged by the attempt.
- [ ] A cross workshop upload returns a refusal, and the storage call count is zero.
- [ ] A file that is not an image is refused before storage, with a field error and no asset.
- [ ] Ownership and status are checked before the file is read, and the order of those checks is visible in the code.
- [ ] A draft with no photograph cannot publish, and the refusal names the photograph as the missing field.
- [ ] A replace writes the new pointer, destroys the old asset and leaves the old address unusable.
- [ ] A delete removes the pointer and the asset, and the cover moves to the first remaining photograph.
- [ ] A replace or delete on a held or sold piece returns a conflict and changes nothing.
- [ ] A paid order fixture still loads its cover address after the maker changes the set on another piece.
- [ ] Every stored image has metadata removed, and the description reads as a sentence about the photograph.
- [ ] The five automated tests run in the suite, including the one that asserts zero storage calls on a refused upload.

## Learning log

1. List your four photographs with their kinds and descriptions. Which one carries the craft evidence, and what would a buyer lose if you deleted it?
2. Paste the update filter that enforces the four photograph limit. Which part of the filter could a concurrent second upload beat, and which part could it not?
3. Show the storage file count before and after the refused fifth upload and after the refused cross workshop upload. Two numbers, two sentences.
4. Which filter condition returns the conflict on the sold piece, and what did the losing request receive? Include the photo count before and after.
5. Which address does the order fixture load, and why did deleting or replacing a photograph not change it?
6. What did you remove from the original files, and where in the server does that removal happen?

Write the answers as sentences with addresses, counts and status codes, and keep the storage secret out of the log. A reviewer should be able to repeat the fifth upload and the cross workshop attempt against the same workshop and get the same two refusals, with the folder still holding four files.

## What this gate does not prove

The gate does not prove image moderation, because nothing in this course detects an inappropriate photograph automatically. It does not prove signed delivery URLs, image transformations or bandwidth cost control either; the course stores public addresses and states that limit in the README. If a build adds transformation presets for a phone, say which preset and why, and do not present it as a security control.

It also does not prove that the seller and the buyer see the same thing. The buyer's page is built in a later module, and this gate only checks the maker's view and the stored data. Keep the boundary honest in the log so that a later reviewer does not read this pass as evidence of a finished catalogue page.

The next module leaves the piece behind for a while and asks how it travels. A photograph can show a bowl in good light, but it cannot tell a buyer in another country whether the parcel leaves this week, how long it spends in transit, or what happens if it crosses a border.
