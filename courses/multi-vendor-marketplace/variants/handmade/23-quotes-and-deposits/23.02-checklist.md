# Quote and deposit gate

Start from a request created in Module 22 by Buyer A for Workshop A. Have the workshop send a first quote with a total, deposit percent, scope, production range and cancellation terms. Ask the buyer to request a material change, then send version two with a different total. Keep both versions visible in the thread. The gate passes when the browser, API and database agree that version two is current, version one is historical, and a verified deposit creates exactly one paid commission from the accepted terms.

## Reject stale acceptance

Open version one in a buyer tab before version two is sent. After version two appears, click Accept in the old tab. The server must return 409 and must not make a Commission. The UI must load version two for fresh review without silently pressing Accept again. Confirm that Buyer B cannot accept either version and Workshop B cannot read or revise them. Record the raw status codes and response bodies. A hidden Accept button after refresh is not evidence that the server enforces version and party rules.

Accept version two twice from separate tabs. There should be one Commission in `awaiting_deposit`, with a snapshot of the version-two scope, total, deposit, balance, date range and terms. Change Workshop A's default deposit percentage after acceptance. The Commission must keep the amounts the buyer accepted. For an odd total, check that the stored deposit and balance add exactly to the total. If a one-unit difference appears, fix the helper that rounds the deposit once and computes the balance as a remainder.

## Pay once and replay

In Stripe test mode, pay the deposit once. Compare the PaymentIntent amount and currency with the Commission's stored deposit amount and currency. Send a browser payload with a lower amount while creating the intent; it must have no effect. Let the verified webhook move the Commission to `in_queue`. Replay the same event and compare Commission ID, paid amount and event history. Nothing should double. Stop the browser before the webhook arrives and repeat the test; the server path still advances the Commission when the verified event arrives.

Send an invalid-signature webhook and a success event with a different amount. Neither may mark the deposit paid. Record how the server reports these faults for investigation without leaking the buyer's payment details. A success page that says “paid” before the API sees verified payment is a failure. It should show a waiting state and a way to get help if confirmation takes longer than expected.

## Learning log

1. Explain why a new quote is a new version instead of an edit of version one. Name the field that tells the acceptance route which version is current.
2. Write the single money-rounding rule and calculate deposit plus balance for an odd total. Explain why both halves are not rounded independently.
3. Describe the two-tab acceptance race and the database condition that permits only one Commission.
4. Explain why a browser redirect and an unverified webhook cannot move work into the maker's queue.

Commit the quote model, unique indexes, guarded acceptance route, PaymentIntent route, webhook tests and both buyer and maker UI states. Save a test transcript with the stale 409, one accepted Commission, the matching PaymentIntent amount and the replay result. A mentor should be able to change the quote total and rerun the checks without editing source code. If an old version can be accepted or a second deposit can be requested for the same Commission, stop before the production module. That module will use this exact terms snapshot as its legal and technical boundary.

## Leave a failure trace that can be repeated

Record one case where your first implementation behaved incorrectly. If the old quote was accepted, capture the version fields that the route compared and the conditional update after the fix. If the PaymentIntent had a different amount, capture the stored quote amount, deposit percentage and rounding helper output; do not save a card number or secret key. If a replay produced a second Commission, capture the database index list and the request ID used as its uniqueness key. The purpose of the trace is to let a reviewer reproduce the failure without guessing what you clicked.

Then check the timeline from both accounts. The workshop owner sees `awaiting_deposit` after acceptance and `in_queue` only after verified payment. The buyer sees the same accepted quote version and the same amount. Disconnect the buyer's browser before sending the verified test event, reconnect, and confirm the state came from the API. This proves the transition belongs to the server rather than to a success-page callback. Change the workshop's default terms once more and verify that neither account's Commission view changes. If either does, the UI is reading mutable defaults instead of the accepted snapshot.

Finally, ask whether the quote has an expiry and what happens after it. An expired quote should not be accepted, even if the buyer kept its tab open. A new quote may be sent, but it must have a new version and a visible opportunity for the buyer to review. This deadline is a business rule, not a browser timer. Test it with an injectable server clock so the result does not depend on waiting for a real day. Keep this test beside the stale-version test because both protect a buyer from accepting terms that are no longer offered.
