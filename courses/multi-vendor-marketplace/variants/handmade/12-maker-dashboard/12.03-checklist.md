# Maker dashboard gate

This gate is passed with two signed in makers and one refused buyer, not with a screenshot of a table. The dashboard is the first page in the course where several collections are read for one person, so a single missing filter can expose drafts, briefs and orders at once. Bring the session tokens, the response bodies and the database counts, and be ready to show that the numbers on screen came from a query you can run by hand.

## Prepare the run before you present it

Set up the fixtures first, because a dashboard gate is easy to fake with a workshop that has one piece. Both seeded workshops need at least one available piece, one draft and one sold piece, so a zero count can only come from a filter and never from an empty collection. Bayt al Zayt also needs the seeded open request, and the second workshop needs to exist with no requests at all. That single asymmetry is what the whole page is tested against.

Prepare one piece in the held state before you start, and keep a second browser tab on its edit page. The checkout module has not been built yet, so set the hold directly in the database for this gate and say in the log that the state was injected rather than paid for. An injected state is honest preparation. Presenting it as a checkout would be evidence of something that does not exist in week two.

Write the five expected counts on paper before you open the page, then compare. A reviewer who watches a learner predict the numbers and then find them is watching a test. A reviewer who watches numbers appear and be read back is watching a demo, and the two are not the same thing.

## Run the page twice, as two people

Sign in as Amina, who owns Bayt al Zayt, and open the dashboard. Read the five panel numbers aloud and write them in the learning log. Sign out, sign in as the owner of the second seeded workshop, and open the same page. The second maker must see a different response, including zero open requests, because the seeded request was addressed to the first workshop. Two screens that look identical are the signature of a query that forgot its scope.

Then open the piece table and press each of the five status tabs. Every tab must change the URL or the query, and every result must belong to the signed in workshop. Check one row by identifier against the database: the title, price, status and credited artisan in the table must match the document, and the credited artisan must belong to that workshop. A row that shows a name from another workshop is a cross document check that never ran.

Finally, open a piece and try an edit that the state should refuse. Set the injected hold on that piece, leave its edit page open in a second tab, and save a title change. The correct answer is a conflict with a message that asks for a reload, and the database row must still hold the old title. If the title changed, the update filter was missing the status condition and the dashboard is now able to rewrite a live offer.

## Break it on purpose

Call the dashboard route with a workshop identifier in the query string and confirm the server ignores it. Call the table with `status=reserved` and confirm a 400 with a field error rather than an empty list. Call both as a buyer and confirm a refusal with no partial payload. Call them as a maker account that has not opened a workshop and confirm a message that tells the person what to do next rather than a stack trace.

Then look at the four panels that wait for later modules. Each one must show zero with a sentence, and each one must be able to fail alone: break one count by renaming a field, and that panel shows an error while the piece table still renders. A dashboard where one failing count blanks the whole page is a dashboard a maker cannot use during a slow evening, which is exactly when she needs it.

## Gate checklist

- [ ] `GET /maker/dashboard` resolves the workshop from the session and accepts no workshop identifier from the client.
- [ ] The piece counts come from one aggregation whose `$match` on `workshopId` runs before the `$group`.
- [ ] Every one of the five panel counts contains the resolved workshop identifier in its filter.
- [ ] The response has a fixed shape, and a status with no records returns 0 rather than a missing key.
- [ ] The table lists only the signed in workshop's pieces and sorts by most recently updated.
- [ ] The five status tabs work, and an unknown status returns 400 `BAD_STATUS` with a field message.
- [ ] A buyer calling the dashboard or the table receives a refusal with no records in the body.
- [ ] A maker with no workshop receives a message that names the missing workshop, not an empty page.
- [ ] The create form saves an incomplete draft, and publish refuses a draft without a price, materials or care notes.
- [ ] Publish and archive are conditional updates on the current status, so a double tap cannot skip a state.
- [ ] Editing a held or sold piece returns a conflict, and the stored row is unchanged after the attempt.
- [ ] The credited artisan on every row belongs to the workshop that owns the piece.
- [ ] Each waiting panel shows zero with an explanation, and a failed panel does not blank the page.
- [ ] The three tests from the lesson run in your suite, including the one that fails if scope is removed.

## Learning log

1. Write the two dashboard responses from the two makers as counts only. Which panel number proves the scope, and which panel would have looked identical even with the filter removed?
2. Paste the aggregation pipeline you ran. Point at the stage that decides ownership and say what the result would be if that stage moved after the `$group`.
3. Which filter condition caused the conflict on the held piece, and what did the losing request receive? Include the matched count and the stored title before and after.
4. Which two fields on a piece row come from a different collection, and where does the server check that the credited artisan belongs to this workshop?
5. What does each empty panel say, and how does that sentence differ from the sentence a maker sees when the panel fails to load?
6. What did you delete from the browser that a client could have sent, and why is that deletion part of the security of this page rather than a tidy up?

Write the answers with identifiers, counts and status codes. A sentence such as the server checks the owner cannot be reviewed, while `workshopId: 665f0a` in the filter and a 403 for the second session can. Keep the access tokens out of the log and out of any screenshot you paste with the answers.

## What this gate does not prove

The gate proves one page reads one workshop with correct counts and refuses the obvious wrong actor. It does not prove the requests, quotes, commissions and orders panels are correct, because those panels count records the course has not built yet. When each later module lands, revisit this page and confirm the count moved for the right workshop and stayed still for the other one.

It also does not prove that a maker is the only role that can act on a piece. The authorization module tested the credited artisan problem, and the commission module will add a second party with its own view. This gate only covers the account that owns the workshop. Keep those separate in your evidence so that a later reviewer does not read this pass as a wider claim than it is.

The next module gives a piece its photographs. The dashboard currently shows an empty frame where a cover photo belongs, and that empty frame is the right preparation: upload, ordering, replacement and the freeze after sale all arrive before the table has a real image to show.
