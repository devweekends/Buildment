# Cache and search gate

Two numbers decide whether this module worked. The first is the count of database queries for twenty identical collection requests, which should fall from twenty to one. The second is the number of documents a search examines, which should fall from the size of the collection to a handful. A screenshot of a fast page proves neither.

Prepare the fixture from the seed. Twelve pieces across three workshops. A stitched cushion cover and a glazed bowl from Bayt al Zayt, a carved olive wood tray from the second workshop, and a ceramic piece from the third. Amina owns Bayt al Zayt and credits an artisan whose display name the buyer sees. Write down the cover ID, the tray ID, the workshop names and the artisan credit text.

## Twenty requests, one query

Turn on query logging for the API process. Request the same filtered collection twenty times in a row and count the database queries. Before the cache, twenty. After it, one query and nineteen Redis reads. Run the same count for a second filter and confirm it also settles at one.

Read the key from Redis and check its parts against the query you sent: the craft, the workshop, the ships-to country, the page and the version. Then change one parameter, such as the country, and confirm the request misses and builds a new key. Two different questions must never share one entry, and the country is the field most likely to be forgotten because it usually sits in a shipping profile rather than the request.

Let the lifetime pass with no other request and read the key again. It must be gone, and the next request must query the database once. That is the safety net working, and it should be boring to watch.

## A sale, then a read

Buy the cover in a second browser with a second buyer. Watch the payment webhook return and read the version key before and after: it must have changed by the time the response reached the provider. Then request the collection again and confirm the cover is absent from the list.

Repeat the check for an archive. As Amina, archive the bowl from the maker dashboard and reload the collection. The bowl must leave the available list, and the sold portfolio view must still show the cover, because a sale does not delete a piece's public story.

Now plant a stale list by hand. Write a cached collection value under the current version that includes a piece you know is sold, then call checkout for that piece. The response must be 409 with the piece named, and no order may be created. That test proves the claim path reads the document rather than the list, and it is the only test that catches a future shortcut.

```quiz

question: A buyer loads the collection, the cover sells, and she presses checkout for the cover from that stale page. What must happen?
options:
  - Checkout succeeds, and the cover is sold twice
  - Checkout returns 409 and names the cover
  - Checkout waits for the cache to refresh first
  - Checkout drops the cover and charges the rest
correct: 1
explanations:
  - The claim is a conditional write, so a second sale cannot pass it.
  - The claim reads the document, finds it sold, and reports the conflict.
  - No request may depend on a cache entry expiring in time.
  - Silently changing the basket charges for something she did not choose.
```

## Search by craft, material and maker

Search for an olive wood tray. The tray appears, and the plan for the query names the `piece_search` index with a small examined count. Search for embroidery and confirm only embroidered pieces return. Search the workshop name and confirm its pieces return, then search the credited artisan's display name and confirm the same pieces return through `makerText`.

Record the two plans side by side: the text query that names the index with a small examined count, and a regular expression on the same field that shows a collection scan. Keep both in your evidence, because the pair explains the cost better than any sentence.

Rename the workshop, reload the collection and search the new name. The pieces must appear. If they do not, `makerText` was not updated on the pieces during the rename, and the search index is now describing a workshop that no longer exists under that name.

Then combine a search term with a filter. Search for olive wood and select the second workshop. The result must be the tray alone, and the cache key must include the search term, so a later search for embroidery does not return the tray from the earlier entry.

## Keyboard, phone and the empty state

At 360 pixels the search input takes the full width, the filter chips wrap under it, and the result count stays visible after a search. Type with the keyboard only, submit with Enter, clear with the clear control, and confirm focus returns to the input. Share the URL of a search in a second tab and see the same results with the term visible in the input.

Search for a phrase that matches nothing, such as a colour no workshop uses. The page must show an empty state that names the term and suggests a broader search, not an apology and not a bare zero.

## Gate checklist

- [ ] Twenty identical collection requests make one database query, and the cache key contains every filter, the page and the version.
- [ ] Changing the country or the workshop in the query misses the cache and builds a new key.
- [ ] A sale increments the version key before the webhook response, and the sold piece leaves the next collection read.
- [ ] An archived piece leaves the available list, and a sold piece remains in the portfolio view.
- [ ] A hand written stale cache entry that includes a sold piece still returns 409 at checkout with no new order.
- [ ] Search by craft, by material and by workshop name each return the right pieces.
- [ ] Search by the credited artisan's display name returns that artisan's pieces through `makerText`.
- [ ] A rename of the workshop is reflected in search results after the update loop runs.
- [ ] `explain("executionStats")` names the `piece_search` index for the text query and shows a collection scan for the regular expression, with both examined counts recorded.
- [ ] With Redis stopped the collection still renders, the log carries the warning and no route returns a 500.
- [ ] The search URL is shareable, the clear control works from the keyboard, and the empty state names the term.
- [ ] `docs/cache-and-search.md` records the TTL, the invalidation events, the version key, the index definition and the two query counts.

## Learning log

1. Which responses did you cache, and which reads did you refuse to cache even though they are slower without it?
2. What exactly changes when a piece sells, and which component turns that change into a cache miss on the next read?
3. How did you prove the checkout claim does not read the cached list? Describe the planted entry and the response.
4. What does `makerText` contain, where is it written, and what breaks if a workshop renames itself and the field is not updated?
5. What did the collection page do with Redis stopped, and what would have happened if the cache had been the only source for the list?

## What this gate does not prove

There is no content delivery network here, no cache warming job and no per user caching. The search has no relevance tuning, no synonyms and no Arabic support, which is a stretch path item rather than a promise of this module. The index is correct for the fields declared and says nothing about a search that spans two collections.

Nothing in this gate changes the rule from Module 19 either. A cache miss means a database read, a cache hit means an old list, and only the conditional update on the Piece document decides a sale. Module 27 deploys this cache and this worker beside the API, and the deployed smoke test repeats the two counts above on the live URL. If a check here fails, fix the invalidation or the index rather than the wording on the page.
