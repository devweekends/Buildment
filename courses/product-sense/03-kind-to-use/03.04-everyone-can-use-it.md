People use a screen in many ways. Some use one thumb on a small phone, a keyboard or a screen reader. Others need large text, work in strong sunlight, or read a language that goes from right to left. Maryam asks Reem, a classmate, to try Halaqa her own way. Colour that is never the only message was covered in 2.5, and the checks below assume it. The course's bar is WCAG 2.2 at level AA, and this chapter says when a rule belongs to a higher level.

## Bigger targets are easier to hit

<InteractiveCanvas slug="product-m3-tap-targets" />

Drag along the sizes. At 16 the three icons touch, and Reem hits the wrong one. AA asks for 24 by 24, though a smaller target passes if a circle of 24 pixels around it touches no other target, which is why 16 with 12 of space passes. Aim for about 44 to 48: the icon stays the same size and only the area around it grows.

<GoDeeper title="Go deeper: four sources, four numbers">

A <GlossaryTerm term="target" definition="The area a finger or a pointer has to hit to use a control, such as a button or a link." /> has no single right size. The sources give different numbers, and they are not the same kind of rule. At the time of writing (checked 2026-10-25), these pages say the following.

| Source | Number | Kind of rule |
|---|---|---|
| WCAG 2.5.8, level AA | 24 by 24 CSS pixels, or smaller with space around it | Standard |
| WCAG 2.5.5, level AAA | 44 by 44 CSS pixels | Standard, a higher level |
| Apple's Human Interface Guidelines | Default 44 by 44 points, minimum 28 by 28 | Platform guidance |
| Material Design 3 | 48 by 48 dp, 8 dp between targets | Platform guidance |

The AA rule has an exception for smaller targets: enough space around each one that a circle of 24 pixels centred on it touches no other target. It has other exceptions too, such as an equivalent control that is large enough, a link inside a sentence, or a control the browser draws. At 16 pixels with 12 pixels between, the three icons in the picture pass by spacing. With no space, they fail.

Two mistakes are common. "WCAG requires 44" is wrong: AA asks for 24, and 44 appears only at AAA. "Apple requires 44" is wrong too: 44 is the default and 28 is the minimum. The units also differ: CSS pixels, points and dp (the density-independent pixel from 2.4) are not the same, so do not mix them. The advice that fits all four is to aim for about 44 to 48. The AA floor is 24 by 24, and only targets smaller than that need the spacing exception.

Material adds a useful idea: an icon can look 24 dp wide while its touch target is 48 dp. You do not have to make the icon bigger. Add padding around it. Halaqa's Join button shows this. It was 36 by 36 pixels. After the fix it is 44 pixels tall and full width.

</GoDeeper>

## Read the Tab order down the form

<InteractiveCanvas slug="product-m3-tab-order" />

Some people move through a page with the Tab key, and the numbers show where focus lands on each press. In order, they count down the page. In the second picture, Seats comes before Where, and in the third the button has no number, so Tab never reaches it. You can check this by reading, with no keyboard.

<GoDeeper title="Go deeper: keyboard and visible focus">

<GlossaryTerm term="keyboard focus" definition="The control that will react when the person presses Enter or Space. A ring or outline normally shows which control it is." /> is the position of the keyboard on the page. A <GlossaryTerm term="screen reader" definition="Software that reads a screen aloud or sends it to a braille display." /> user often moves through a page with the keyboard too, so one fix helps both.

Three standards apply. WCAG 2.1.1 Keyboard (level A): all functions work from a keyboard. WCAG 2.4.7 Focus Visible (level AA): when the keyboard is used, the focus indicator is visible. WCAG 2.2 adds 2.4.11 Focus Not Obscured (Minimum), level AA: the focused control is not hidden behind other content such as a sticky bar.

Frameworks do not always help. At the time of writing, Bootstrap's Reboot notes that links get no special focus style by default. A project that removes the browser's outline, or never adds one, must add a visible style. A small rule is enough:

```css
:focus-visible {
  outline: 3px solid #1d4ed8;
  outline-offset: 2px;
}
```

Pick a colour that stands out from both the control and the page, and check it as you did in 2.5.

Here are two ways to test. With a keyboard, put your mouse away and finish the create-group form with Tab, Shift plus Tab and Enter. With only a phone, read the order of the controls in the page code and write the numbers down, as the picture does. If you have no access to the code, ask a friend with a laptop to press Tab on your page and read the order aloud. Then search the style sheet for `outline: none`. That one line removes the indicator unless the code adds another style back. This applies to code an AI tool wrote too.

</GoDeeper>

## Meaningful images need words, decorations none

<MermaidDiagram title="One question for every image" chart={`flowchart TD
  S["An image on the page"] --> I{"Does it carry information?"}
  I -->|"yes"| Y["A text alternative says the same thing"]
  I -->|"no"| N["An empty alt text, so tools skip it"]
  S --> C["If it is a control, its name says what it does"]
`} />

A chart of seats left needs a sentence that gives the same facts. A wavy line between sections carries none, so it gets an empty alt and is skipped. An icon that works as a button needs a name for what it does, such as "Save group".

<GoDeeper title="Go deeper: text alternatives">

A <GlossaryTerm term="text alternative" definition="Words that give the same information as an image, so that a person who cannot see it can still use the page. In HTML it is the alt attribute." /> must serve the equivalent purpose of the image. WCAG 1.1.1 Non-text Content (level A) says so. For pure decoration, the page should be built so that assistive tools ignore it: an empty alt attribute makes assistive tools, such as screen readers, skip it (technique H67). A non-empty alt text on a decoration is listed as a failure (F39). A control needs a name that describes its purpose.

"Add alt text to every image" is a half-truth. Decorative images should get an empty alt, and that is a deliberate choice, not a missing one.

How to write one, as practice: say what the image tells the person, not what it is. For a picture of tonight's groups, "Three study groups tonight, the first Data structures at 8 pm with 2 seats left" is better than "screenshot".

The same test works for icons. If an icon beside a word repeats the word, the icon is decoration. If the icon stands alone, it needs a name.

</GoDeeper>

## Design for the small screen first

<MermaidDiagram title="Small first, then check the large screen" chart={`flowchart TD
  A["Small screen: what matters most?"] --> B["Large screen: add room"]
  B --> C{"Can people still do the same tasks?"}
  C -->|"no"| A
  C -->|"yes"| D["Ship both"]
`} />

A small screen has no room for extras, so it forces a choice about what matters. Start there, then check the large screen with the same tasks. If a task is lost, go back to the small screen. Parity means the same content and abilities, not an identical layout.

<GoDeeper title="Go deeper: why small first, and what the evidence says">

A practitioner gave three reasons in 2009: growth in mobile use, constraints that force choices, and new capabilities. The article says a 320 by 480 screen has no room for extraneous elements. It is a practitioner argument, and that screen size is old. The idea holds without the number: you cannot add everything to a small screen, so you must decide.

NN/g adds a warning. A design ported from mobile to the desktop can underperform there. Aim for the same content and features on both, not the same interface, and use a plan for several platforms. Fourteen features would not fit on one phone screen, which is one more reason for the cuts Maryam made in 1.4.

You may meet thumb zone maps, with green, yellow and red areas on a phone. Treat them as weak evidence. The researcher who collected the data gathered 1,333 observations of how people hold phones. He later said the reach diagrams were unreliable and should be ignored, because later studies found that people touch the centre of the screen most often.

Text size is part of the small screen. WCAG 1.4.4 (level AA) asks that text can be resized to 200% without losing content or function. Test it: set the text to 200% and look for text cut off or buttons pushed off the screen.

</GoDeeper>

## Arabic mirrors the card, not only the words

<InteractiveCanvas slug="product-m3-rtl-card" />

Switch to Arabic. The words change, and so does every position: the text starts on the right and is aligned to the right, and the Join button, which sat at the right end, now sits at the left end. Put the direction in the markup once, then use start and end instead of left and right.

<GoDeeper title="Go deeper: right to left in practice">

The W3C advice is to put `dir="rtl"` on the `html` element of a right-to-left page, and to give the language with `lang`, separately. Direction belongs in markup, not only in CSS. For forms and for text inserted from users, `dir="auto"` lets the browser pick the direction, but it is not always right.

In CSS, <GlossaryTerm term="logical properties" definition="CSS properties named by the direction of the text, such as start and end, instead of left and right. They flip with the page's direction." /> map to the flow of the text. `margin-inline-start` is the left margin in English and the right margin in Arabic, so you do not need a second stylesheet.

```css
.group-card {
  padding-inline: 16px;
  margin-inline-start: 8px;
}
```

A page with hard-coded `left` and `right` values will break in an Arabic-first product: a back arrow on the wrong side, a margin on the wrong edge.

What this chapter does not say matters too. The course's sources give numbers for text size, line length and line height for Latin text, and one for CJK text, and none for Arabic. So there are no Arabic numbers here. The Arabic in the picture is short on purpose. The course rule is to check with a native reader on a real phone. The sources also do not say which icons to mirror, so ask a native reader for that.

</GoDeeper>
