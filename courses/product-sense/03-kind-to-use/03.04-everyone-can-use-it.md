People use a screen in many ways. Some use one thumb on a small phone, a keyboard or a screen reader. Others need large text, work in strong sunlight, or read a language that goes from right to left. Maryam asks Reem, a classmate, to try Halaqa her own way. They check six things together. The course's bar is WCAG 2.2 at level AA, and this chapter says when a rule belongs to a higher level.

## Bigger targets are easier to hit

<InteractiveCanvas slug="product-m3-tap-targets" />

Drag along the sizes. At 16 the three icons touch, and Reem hits the wrong one. At 24 they reach the AA floor. Aim for about 44 to 48. The icon stays the same size and only the area around it grows. In the picture, one unit is one pixel of the drawn phone.

<GoDeeper title="Go deeper: four sources, four numbers">

A <GlossaryTerm term="target" definition="The area a finger or a pointer has to hit to use a control, such as a button or a link." /> has no single right size. The sources give different numbers, and they are not the same kind of rule.

| Source | Number | Kind of rule |
|---|---|---|
| WCAG 2.5.8, level AA | 24 by 24 CSS pixels, or smaller with space around it | Standard [A4] |
| WCAG 2.5.5, level AAA | 44 by 44 CSS pixels | Standard, a higher level [A16] |
| Apple's Human Interface Guidelines | Default 44 by 44 points, minimum 28 by 28 | Platform guidance [A38] |
| Material Design 3 | 48 by 48 dp, 8 dp between targets | Platform guidance [A39] |

The AA rule has an exception for smaller targets: enough space around each one that a circle of 24 pixels centred on it touches no other target. It has other exceptions too, such as an equivalent control that is large enough, a link inside a sentence, or a control the browser draws [A4]. At 16 pixels with 12 pixels between, the three icons in the picture pass by spacing. With no space, they fail.

Two mistakes are common. "WCAG requires 44" is wrong: AA asks for 24, and 44 appears only at AAA. "Apple requires 44" is wrong too: 44 is the default and 28 is the minimum. The units also differ: CSS pixels, points and <GlossaryTerm term="dp" definition="A density-independent pixel, the unit that Material Design uses. It keeps about the same physical size on different screens." /> are not the same, so do not mix them. The advice that fits all four is to aim for about 44 to 48. The AA floor is 24 by 24, and only targets smaller than that need the spacing exception.

Material adds a useful idea: an icon can look 24 dp wide while its touch target is 48 dp [A39]. You do not have to make the icon bigger. Add padding around it.

</GoDeeper>

## Tab moves through the form in order

<MermaidDiagram title="Keyboard focus through the create-group form" chart={`flowchart TD
  T["Tab key"] --> C["Course"]
  C --> D["Day and time"]
  D --> S["Seats"]
  S --> B["Start the group"]
`} legend="Each tap of Tab moves keyboard focus to the next control. On every stop, a visible ring must show where focus is." />

Not everyone taps. Some people use a keyboard or a screen reader, and they move through the page in this order. Every control must be reachable, in a sensible order, and the person must always see where focus is. If the ring is removed, the person is lost.

<GoDeeper title="Go deeper: keyboard and visible focus">

<GlossaryTerm term="keyboard focus" definition="The control that will react when the person presses Enter or Space. A ring or outline normally shows which control it is." /> is the position of the keyboard on the page. A <GlossaryTerm term="screen reader" definition="Software that reads a screen aloud or sends it to a braille display." /> user often moves through a page with the keyboard too, so one fix helps both.

Three standards apply. WCAG 2.1.1 Keyboard (level A): all functions work from a keyboard [A11]. WCAG 2.4.7 Focus Visible (level AA): when the keyboard is used, the focus indicator is visible [A5]. WCAG 2.2 adds 2.4.11 Focus Not Obscured (Minimum), level AA: the focused control is not hidden behind other content such as a sticky bar [A17].

Frameworks do not always help. Bootstrap's Reboot notes that links get no special focus style by default. A project that removes the browser's outline, or never adds one, must add a visible style [A52]. A small rule is enough:

```css
:focus-visible {
  outline: 3px solid #1d4ed8;
  outline-offset: 2px;
}
```

Pick a colour that stands out from both the control and the page, and check it as you did in 2.5. Then test it: put your mouse away and finish the Start a group form with Tab, Shift plus Tab and Enter. If you ever lose track of the focus, so will a user.

When you review code, including code an AI tool wrote, search for `outline: none`. That one line removes the indicator unless the code adds another style back.

</GoDeeper>

## Colour cannot be the only cue

<InteractiveCanvas slug="product-m3-colour-not-alone" />

On the first screen, three coloured bars should tell Reem how many seats are left. They do not say it. Someone who cannot tell the colours apart, or who reads the screen in bright sun, gets nothing. The second screen adds words. Colour stays as an extra cue, not the only one.

<GoDeeper title="Go deeper: use of colour">

WCAG 1.4.1 Use of Color (level A) says colour must not be the only way to convey information, indicate an action, prompt a response or tell elements apart. Add a shape, an icon or text [A3]. The same idea appears in 3.3.1 for errors: colour may add to the text, but cannot replace it [A7].

The test is simple. Look at your screen with the colour taken away, for example in a grey screenshot, and ask what you lost. In Halaqa, check the seats left, the Full label and any error first. If you lose information, add a word.

This is not a rule against colour. A green pill that says "4 seats left" is better than a plain pill, because two cues agree. It is also not a claim about how many people have colour vision differences. This course gives no figure for that, because it has no reliable source.

</GoDeeper>

## Meaningful images need words, decorations need none

<MermaidDiagram title="One question for every image" chart={`flowchart TD
  S["An image on the page"] --> I{"Does it carry information?"}
  I -->|"yes"| Y["A text alternative says the same thing"]
  I -->|"no"| N["An empty alt text, so tools skip it"]
  S --> C["If it is a control, its name says what it does"]
`} legend="Meaningful images get words. Decorations get an empty alt. Controls get a name for their purpose." />

Every image asks one question: does it carry information? A chart of seats left needs a sentence that gives the same facts. A wavy line between sections carries none, so it gets an empty alt and is skipped. An icon that works as a button needs a name for what it does, such as "Save group".

<GoDeeper title="Go deeper: text alternatives">

A <GlossaryTerm term="text alternative" definition="Words that give the same information as an image, so that a person who cannot see it can still use the page. In HTML it is the alt attribute." /> must serve the equivalent purpose of the image. WCAG 1.1.1 Non-text Content (level A) says so. For pure decoration, the page should be built so that assistive tools ignore it: an empty alt attribute makes assistive tools, such as screen readers, skip it (technique H67). A non-empty alt text on a decoration is listed as a failure (F39). A control needs a name that describes its purpose [A10].

"Add alt text to every image" is a half-truth. Decorative images should get an empty alt, and that is a deliberate choice, not a missing one.

How to write one, as practice: say what the image tells the person, not what it is. For a picture of tonight's groups, "Three study groups tonight, the first Data structures at 8 pm with 2 seats left" is better than "screenshot".

The same test works for icons. If an icon beside a word repeats the word, the icon is decoration. If the icon stands alone, it needs a name.

</GoDeeper>

## Design for the small screen first

<MermaidDiagram title="Small screen first, then check the large one" chart={`flowchart LR
  A["Small screen: decide what matters"] --> B["Large screen: add room, keep the content"]
  B --> C["Check both on the same tasks"]
`} legend="Mobile first is an order of work. The large screen is checked, not forgotten." />

A small screen has no room for extras, so it forces a choice about what matters. Start there. Then check the large screen with the same tasks. Parity means the same content and abilities, not an identical layout. Mobile first does not mean the large screen is an afterthought.

<GoDeeper title="Go deeper: why small first, and what the evidence says">

A practitioner gave three reasons in 2009: growth in mobile use, constraints that force choices, and new capabilities. The article says a 320 by 480 screen has no room for extraneous elements [A60]. It is a practitioner argument, and that screen size is old. The idea holds without the number: you cannot add everything to a small screen, so you must decide.

NN/g adds a warning. A design ported from mobile to the desktop can underperform there. Aim for the same content and features on both, not the same interface, and use a plan for several platforms [A61]. Fourteen features would not fit on one phone screen, which is one more reason for the cuts Maryam made in 1.4.

You may meet thumb zone maps, with green, yellow and red areas on a phone. Treat them as weak evidence. The researcher who collected the data gathered 1,333 observations of how people hold phones. He later said the reach diagrams were unreliable and should be ignored, because later studies found that people touch the centre of the screen most often [A59].

Text size is part of the small screen. WCAG 1.4.4 (level AA) asks that text can be resized to 200% without losing content or function [A15]. Test it: set the text to 200% and look for text cut off or buttons pushed off the screen.

</GoDeeper>

## Write direction in markup, not CSS

<MermaidDiagram title="One direction, set once" chart={`flowchart LR
  H["html lang ar, dir rtl"] --> B["The browser flows the page right to left"]
  B --> L["CSS with start and end works in both directions"]
`} legend="Direction belongs in the HTML. Logical CSS properties follow it." />

Halaqa is read in Arabic and in English. Put the direction in the HTML once, on the html element, with the language set separately. Then write start and end instead of left and right in CSS, so one rule works in both directions. For text a user types, use dir auto. Check Arabic with a native reader on a real phone.

<GoDeeper title="Go deeper: right to left in practice">

The W3C advice is to put `dir="rtl"` on the `html` element of a right-to-left page, and to give the language with `lang`, separately. Direction belongs in markup, not only in CSS. For forms and for text inserted from users, `dir="auto"` lets the browser pick the direction, but it is not always right [A78].

In CSS, <GlossaryTerm term="logical properties" definition="CSS properties named by the direction of the text, such as start and end, instead of left and right. They flip with the page's direction." /> map to the flow of the text. `margin-inline-start` is the left margin in English and the right margin in Arabic, so you do not need a second stylesheet [A79].

```css
.group-card {
  padding-inline: 16px;
  margin-inline-start: 8px;
}
```

A page with hard-coded `left` and `right` values will break in an Arabic-first product: a back arrow on the wrong side, a margin on the wrong edge [A78, A79].

What this chapter does not say matters too. The course's sources give numbers for text size, line length and line height for Latin text, and one for CJK text, and none for Arabic. So there are no Arabic numbers here. The course rule is to check with a native reader on a real phone. The sources also do not say which icons to mirror, so ask a native reader for that.

</GoDeeper>
