Rand and Omar each built a booking page this week, Rand for library group rooms and Omar for lab printers, with the same CSS framework and no changes. Side by side, the two pages look like one product.

## Same framework, same start, same look

<MermaidDiagram title="Why two pages look alike" chart={`flowchart TD
  F["Same framework, defaults unchanged"] --> R["Rand's room page"]
  F --> O["Omar's printer page"]
  R --> S["Two products that look like one"]
  O --> S
`} legend="Both builders start from the same type scale, spacing and colours. If neither changes anything, both end in the same place." />

A framework gives you a type scale, a spacing step and a set of colours, so that you can start fast. Each <GlossaryTerm term="default" definition="What a tool or framework uses when you choose nothing." /> is made to work for everyone. Rand and Omar kept all of them. The framework did nothing wrong. Unchanged defaults look like everyone else's.

<GoDeeper title="Go deeper: what the defaults are">

Tailwind CSS describes its default theme as a starting point. The theme includes a colour palette of 26 colour families plus black and white, a type scale, shadows and fonts. The default spacing unit is 0.25rem, which is 4 pixels at a 16 pixel root size. The default body size, called `text-base`, is 1rem with a line height of 1.5 [A49, A50]. Its documents show how to extend, override or remove the theme [A49].

Bootstrap's Reboot sets a system font stack, a body size of 1rem, a white background and box sizing that includes borders. Bootstrap documents how to customise with Sass variables, CSS variables and colour modes [A52, A51]. Both frameworks expect you to change things.

So the sources show what the defaults are, and that the makers expect you to change them. The claim that unchanged defaults look alike is this course's own observation, not a measured finding. There is older evidence for the same drift. A 2021 study, as a later paper describes it, found that web page layouts grew more alike after 2007, and it linked this to shared frameworks such as Bootstrap [B10]. That is research, described second-hand. It shows that sameness is older than AI tools.

Do not blame the framework. A tool that works for everyone cannot also be shaped to your product. That part is your job.

</GoDeeper>

## Three choices move a page off its defaults

<InteractiveCanvas slug="product-m4-default-or-choice" />

Switch through the four versions. In Type, the title is larger and the only serif line, and the sizes differ clearly. In Colour, the accent marks the one action, and green plus a word marks a free room. In Content, real hours replace "Room 1" and "Welcome". Each change has a job.

<GoDeeper title="Go deeper: why these three">

Type, colour and content are the three places where a page tells people what it is for. Type decides what is read first and how easily. Colour can mark the one action and the state of a room. Content decides whether a page says anything about this product at all.

Look at what each change gave up. In Type, Rand now uses two faces on one page, so she must check that the serif title reads well on a phone. In Colour, the category pills lost their accent and are less noticeable. In Content, the generic "Quiet, Group, Online" pills left the page, so she must find another way to filter if students need one.

A choice always costs something. Naming what was given up is part of the reason. The critique log in chapter 4.6 and the capstone both ask for it.

For Arabic text, no source in this course's research gives sizes, line lengths or line heights, and the numbers you may have seen are for Latin text. Check your type with a native reader on a real phone. That is a course rule, not a finding.

</GoDeeper>

## A default you can explain is a choice

<MermaidDiagram title="Default or choice" chart={`flowchart TD
  Q["Is this part a default?"] --> W["Can I say why it fits this job?"]
  W -->|"Yes"| K["Keep it. It is now a choice"]
  W -->|"No"| T["Check it, then keep or change it"]
`} legend="A default you can explain, you chose. A default you cannot explain needs a check before you keep it." />

A default is a choice you did not make. If you can say why it fits the job, you did make it, so keep it. If you cannot, check it against the Good list, then keep it or change it. Keeping 16 pixel text with a line height of 1.5 is a choice. Not looking at it is not.

<GoDeeper title="Go deeper: defaults to keep and defaults to check">

Some defaults are good starts. A body size of 16 pixels with a line height of about 1.5 is what Tailwind uses by default. Material 3 recommends the same line height for body text (design-system guidance) [A36, A50]. Readers can still scale text to 200 percent (a standard, WCAG 1.4.4) [A15]. Keep it, and say why.

Some defaults need work. Bootstrap's Reboot gives links no special focus style [A52]. If a project removes the browser's outline and adds none, a keyboard user cannot see where they are, which fails a Good check (WCAG 2.4.7) [A5]. The GOV.UK Design System says default placeholder styles often fail the contrast rule, and that is one reason it tells makers not to use placeholders as labels [A74].

Some defaults hide your product. These are the palette, the font and the generic words such as "Welcome to". These are the places where a choice shows most.

Do not change everything. A page where every default is replaced has many changes that nobody can explain, and each one can break a check. Change a few, with reasons. Anthropic, which makes Claude, publishes a design skill that calls the looks its tools produce by default "defaults rather than choices" and says the brief always wins [B3]. The same idea applies to people. Module 5 shows what it looks like when nobody chose.

</GoDeeper>

## A choice still has to pass the checks

<MermaidDiagram title="Change one thing on purpose" chart={`flowchart TD
  P["Pick one part to change"] --> W["Write the reason"]
  W --> C["Change it"]
  C --> K["Run the Good checks again"]
  K --> L["Look again at the job"]
`} legend="Each change gets a reason before it is made and the Good checks after it is made." />

A new colour can fail contrast. A new font can be harder to read on a phone. So change one part, write the reason first, and run the Good checks again afterwards. Then look at the job: does the page now help the person more? A change that fails a check is not a choice, it is a new problem.

<GoDeeper title="Go deeper: one change, step by step">

Rand picks colour. Her reason: booking is the one action on the page, and she wants people to notice it first. She makes the Book button for the free room the only accent, and she marks rooms with the words Free and Taken, with green only as an extra. She does not rely on colour alone to say a room is free (a standard, WCAG 1.4.1) [A3].

Then she runs the checks. The button text on the accent still needs a contrast ratio of at least 4.5 to 1 [A1]. The edge of the button, if she keeps one, needs 3 to 1 against the page [A2]. The focus ring still shows when she presses Tab [A5]. If one fails, she changes the shade, not the idea.

Last, she looks at the job. Can a student find a free room tonight? In the first version, "Room 1" and "Room 2" said nothing about hours. In the last, "Free 4 to 6 pm" does. The colour helped, and the content helped more. That is worth writing down.

</GoDeeper>

## Write the choice in one line

<MermaidDiagram title="One line for each choice" chart={`flowchart LR
  A["I changed this"] --> B["For this job"] --> C["I checked it"]
`} legend="One line that a reader can check: what changed, why it fits the job, and what you checked." />

Write each choice in one line. I changed this, for this job, and I checked it. For example: I made the Book button the only accent colour because booking is the one action, and I checked its text at more than 4.5 to 1. A line like this is what a critique log holds.

<GoDeeper title="Go deeper: from one line to a critique log">

The one line has three parts, and each part answers a different question from a reader. "I changed this" answers what is different. "For this job" answers why. "I checked it" answers how you know. If a part is missing, the reader has to guess.

Add a fourth part when it matters: what you gave up. The capstone's critique log has columns for what was wrong, the rule or evidence, the change and what was given up. The one line is the middle of that row.

A line can also be wrong. Suppose Rand writes "I made the title serif because it looks classic". A reader cannot check "classic". A better line names the job: "the title is the only serif line, so the page title is the one thing set apart. I checked that it reads at a phone size". Chapter 4.4 teaches how to check someone else's lines the same way.

</GoDeeper>

```quiz
type: mcq
question: "Nisreen changes the framework's blue accent on her booking page. Which change is a choice that a reader can name?"
options:
  - "Teal on the Book button only, since booking is the one action on the page"
  - "Teal on every button, link, heading and icon, since teal is her favourite colour"
  - "A gradient across the header, so that the page looks more modern than before"
  - "A new font for every line, since the framework font looks plain to her"
correct: 0
explanations:
  - "Right. It names the job (booking is the one action) and a change (one accent). It also gives a way to check it: do people notice Book first, and does its text pass 4.5 to 1?"
  - "Accent colour on everything gives colour no job, and her favourite colour is a taste, not a reason tied to the page. A reader cannot check it."
  - "'Looks modern' is a feeling a reader cannot check, and a gradient needs its own contrast check. It names no job."
  - "'Looks plain' names no problem the person has. Changing every line also makes many changes with one weak reason."
```
