## Four ways the same link can open

<InteractiveCanvas slug="product-m7-one-click-access" />

A login wall shows nothing of the work. A guest button that opens an empty app shows nothing either. Sample groups put the core in one tap. If the live demo is down, a short video and screenshots still show the work. Touch each version and see what a reviewer gets in the first moment. The sample version is the only one that shows the job.

<GoDeeper title="Go deeper: guest mode, demo mode and demo accounts">

There are three ways to let a stranger in. A guest button opens the app with no account. A demo mode loads sample data in a safe copy of the app. A demo account is a shared email and password that you print on the page. The first two are better, because a reviewer does not have to type anything. A demo account is acceptable when your app cannot work without a login. If you use one, make it read-only or reset it often, and never put real people's data in it.

Sample data means invented names, invented groups and invented times. Halaqa's guest mode shows "Data structures, exam Thursday" and a few seats left, not real classmates. Guest mode must also be separate from anything private. It should not reach real data, an admin screen or a key.

Is this a rule? Not quite. We found no source on whether reviewers run deployed apps or open repository links, so "open in one click" is this course's recommendation. There is one useful comparison. App stores ask developers for demo account details when an app has a login. That is an analogy, not hiring evidence. It shows that people who review apps for a living expect a way in that needs no sign-up.

</GoDeeper>

## A chain of fallbacks, not one link

<MermaidDiagram title="The fallback chain" chart={`flowchart TD
  L["Reviewer opens your link"] --> D{"Does the live demo open?"}
  D -->|"Yes"| G["Guest mode shows the core"]
  D -->|"No"| V{"Does the video play?"}
  V -->|"Yes"| W["The story, with captions"]
  V -->|"No"| S{"Is the page up?"}
  S -->|"Yes"| P["Screenshots show the work"]
  S -->|"No"| R["The README still does"]
`} legend="Each fallback lives in a different place." />

Any live demo can break. Free hosts pause or limit sites, and a link can fail on the day a reviewer opens it. Plan a chain: the live demo, then a short video, then screenshots on the page, then the README. Once a week, open the whole chain signed out, on a phone, and write the date you checked.

<GoDeeper title="Go deeper: building each step of the chain, and the weekly check">

The video is the one from 7.2: 60 to 90 seconds, working muted, with captions. Host it where it will not depend on your app, and link it from the case study page. The screenshots go directly on the page, each with a short text alternative, so the page still works when every link outside it fails.

The README is the first thing a visitor sees in a repository. Put four things in its first screen: one sentence about the job, the result, the link to the guest demo and the link to the video. Below that, say how to run the project. This is practice, not research.

Free plans have limits and rules, and they change. A host can pause a site that breaks its rules or passes its limits, so read the plan page on the day you publish. That is why the chain exists. You do not plan for a failure you expect. You plan so that a failure you did not expect does not cost you the first impression.

The weekly check matters because links break quietly. Open your own link signed out, because if you are signed in you see what you built, not what a stranger sees. Use a private window or a different phone. On a phone, turn on flight mode to see how the page behaves with no connection, or use a weak signal if you have one. Check the guest button first. Does it still open the core, with sample data, in one step? Then check the video: does it play, and are the captions still right? Open one screenshot and read the first screen of the README.

Keep a short note with the date and what you found. Over a month, the note shows whether a free host keeps pausing your site, and then you can change the host. The check is practice, not research. It costs two minutes and a little mobile data.

</GoDeeper>

## Put the link where people look

<InteractiveCanvas slug="product-m7-where-links-go" />

People meet your work in a message, on a resume or on a profile. Each of the three puts the result beside the same link, and the link leads to the same case study page. That page leads to the guest demo. Nobody has to search for the work. Course 16 teaches the words for the resume and the profile.

<GoDeeper title="Go deeper: places to put the link">

This is practice, with tool facts. At the time of writing (checked 2026-10-25), LinkedIn's Featured section can hold posts, articles, links to other sites and uploaded media such as images, documents and videos. You must have already published a post or article to feature it. The help page states no maximum number of items. It is an old page, so menus may have changed. LinkedIn is for people 16 or over. Read the wording of any remove button before you press it. One option only takes an item out of Featured and keeps it, and deleting a post cannot be undone.

LinkedIn plays some feed videos without sound unless the reader changes the setting. That is one more reason the demo must work muted.

A GitHub repository is another place. GitHub is for people 13 or over. Its README is its front page, so the guest link and the result belong in the first screen. A personal site is a third place. The best choice is the place a reviewer in your target field actually looks, and only you can find that out, by asking people who hire.

Public posting is your choice. The capstone accepts a private submission to your mentor. If you do post in public, never show a client's or employer's screens or data without permission. Course 13 teaches the full privacy habit.

</GoDeeper>

## Check the host's rules before you share

<MermaidDiagram title="Which host fits" chart={`flowchart TD
  Q["Are you paid for this site?"] -->|"Yes"| A["A free personal plan may forbid it. Read the terms"]
  Q -->|"No"| B["Does the demo need a server?"]
  B -->|"No"| C["Static site: GitHub Pages, public repository"]
  B -->|"Yes"| D["Use a host with a server, or a video"]
`} legend="Two questions decide most cases. Read the host's terms on the day you publish." />

At the time of writing (checked 2026-10-25), Vercel's free Hobby plan is for personal, non-commercial use, and paid client work counts as commercial. GitHub Pages needs a public repository on a free plan, serves static files and is not for running an online business. A demo that needs a server needs another host.

<GoDeeper title="Go deeper: hosting terms in plain words">

These are the hosts' terms, not design rules, and they change. On the same check date, Vercel's terms say the free Hobby plan is for personal or non-commercial use. Its fair use page says that receiving payment to create, update or host the site counts as commercial, and that donations do not. People using it must be at least 16. So if a client pays you to build their booking site, the Hobby plan is not for that site.

GitHub Pages on a free plan needs a public repository. GitHub sets limits on site size, bandwidth and builds, and it says Pages is not for running an online business. Read those limits on GitHub's page on the day you publish, because they change. Pages serves static files, which is our inference from those limits, so check before you rely on it. A demo with a server needs a mock mode with sample data, or the video.

Netlify and Cloudflare Pages also list free plans. Check their limits and their age rules in their terms, because they change often. We did not check whether they open in Gaza. GitHub's trade controls page does not name Palestine, Gaza or the West Bank. Payment and network blocks are a separate matter. Check whether each tool opens for you, and keep the video as the path that always works.

A public repository is public to everyone. Before you switch it on, search it for keys, passwords and real people's data, using the secret check from course 13.

</GoDeeper>
