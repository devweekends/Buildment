```quiz
type: mcq
question: "Bilal's bakery has 300 sales rows for today. The price list has one row for each product code. 3 of the sales have a product code that is not in the price list. He needs one table with all 300 sales, showing a price where one exists. Which join does that?"
options:
  - "An inner join of sales and the price list, which returns 297 rows"
  - "A left join from sales to the price list, which returns 300 rows"
  - "A left join from the price list to sales, which returns every product"
  - "An inner join, then adding the 3 missing sales by hand afterwards"
correct: 1
explanations:
  - "An inner join keeps only the sales that match. The 3 sales with unknown codes disappear, so the table has 297 rows and not 300."
  - "Right. A left join starts from the sales and keeps every one of them. The 3 unknown codes stay, with NULL where the price should be, so you can also list them. The price list has one row for each code, so the rows do not multiply."
  - "This starts from the products. It shows products with no sales, and the 3 sales with unknown codes have no product to attach to, so they are lost."
  - "That fixes the count by hand, and the next day's unknown codes would be lost again. A left join keeps them without any manual step."

  - "Fees were entered twice, so delete the older half of the fee rows"
  - "The join type is wrong, so change the inner join to a left join"
  - "Students are counted twice, so use COUNT(DISTINCT student_id)"
  - "10 students are repeated, which adds 1,000; add up fees first"

explanations:
  - "The fee book says 4,000, so the fees themselves are not repeated. The extra 1,000 appears only after the join."
  - "Every student has at least one parent row, so a left join returns the same rows as the inner join and the total stays 5,000."
  - "That counts students, but the wrong number is a sum of fees. The fees of the 10 repeated students are still added twice."
  - "Right. The 10 students with two parent rows appear twice, which adds 10 x 100 = 1,000 and gives 5,000. Adding up the fees before the join, or joining to one parent row for each student, brings it back to 4,000."

type: mcq
question: "Reem keeps a pharmacy table named doses with 5 rows. The values are 2, 4, NULL, 6 and NULL. She runs COUNT(*), COUNT(doses), AVG(doses) and SUM(doses). Which results do the facts support?"
options:
  - "5, 3, 4 and 12"
  - "5, 5, 2.4 and 12"
  - "3, 3, 4 and 12"
  - "5, 3, 2.4 and 12"
correct: 0
explanations:
  - "Right. COUNT(*) counts all 5 rows. COUNT(doses) counts the 3 values. SUM adds 2 + 4 + 6 = 12, and AVG divides by the 3 values, so it is 4."
  - "This treats the NULL rows as zeros: 5 values and an average of 12 / 5 = 2.4. The two rows are NULL, not 0, so COUNT(doses) is 3."
  - "COUNT(*) counts rows, whatever they hold, so it returns 5. Only COUNT(doses) skips the two NULL rows."
  - "AVG skips NULL, so it divides 12 by the 3 values and returns 4. Dividing by 5 would be right only if the NULLs were zeros."
```

question: "Tareq's online shop has three orders: A101 for 20 shekels from customer 7, A102 for 20 from customer 8, and A103 for 35 from customer 9. Customer 7 has two addresses. After joining orders to addresses, the total shows 95 and the true total is 75. An AI assistant answers: 'Use SUM(DISTINCT amount) and the total will be right.' What does that query return?"
options:
  - "75, because DISTINCT removes the repeated row of order A101"
  - "95, because DISTINCT has no effect on a sum after a join"
  - "55, because equal amounts such as A102's 20 are dropped too"
  - "55, which is right, because A102 repeats order A101"
correct: 2
explanations:
  - "DISTINCT works on the amounts, not on the orders. The rows are 20, 20, 20 and 35, and it keeps one 20, so the result is 55 and not 75."
  - "DISTINCT inside SUM does change the result: it adds each different amount once. The sum is 55, not 95."
  - "Right. The joined rows hold the amounts 20, 20, 20 and 35. DISTINCT keeps one 20 and drops the other two, including A102's real 20, so the sum is 55. The fix belongs in the join, not in DISTINCT."
  - "A102 is a different order from a different customer, 8, with the same amount by chance. It is not a repeat of A101, so dropping it loses real money."
