```quiz
type: mcq
question: "Zaid's bakery job has five tasks. Upstream tasks: read_sales none, read_prices none, join (read_sales, read_prices), report (join), email (report). Tonight read_prices fails for good with a plain error. Which tasks does the runner mark skipped?"
options:
  - "join, report and email, since each one is downstream of read_prices"
  - "Only join, because it is the one task that lists read_prices"
  - "All four other tasks, because a failure anywhere stops the whole run"
  - "Only report and email, because join already has read_sales"
correct: 0
explanations:
  - "Right. Join needs read_prices, report needs join and email needs report, so all three are downstream and are skipped. Read_sales has no upstream task and keeps its ok status."
  - "Join is skipped, but report needs join and email needs report. A skipped task cannot succeed, so the tasks after it are skipped too."
  - "Read_sales has no upstream task and does not wait for read_prices. It runs and ends ok, so not every other task is skipped."
  - "Join needs both read_sales and read_prices. One good upstream task is not enough, so join is skipped, and the others follow."
```

```quiz
type: mcq
question: "Dalia's job builds a water delivery list from a tank file on a shared drive. The drive goes down for 50 minutes. Her runner allows 4 retries, a first wait of 3 minutes and waits that double. The first attempt fails at minute 0. What is the result?"
options:
  - "It works on attempt 5 at minute 45, because the retries cover 45 of the 50 minutes"
  - "It gives up at minute 12, because every wait is 3 minutes and 4 retries make 12"
  - "It works on attempt 4 at minute 21, because the fourth wait is 12 minutes"
  - "It gives up at minute 45 after five attempts, because the outage ends at minute 50"
correct: 3
explanations:
  - "An attempt works only if it starts after the drive is back. Minute 45 is before minute 50, so the fifth attempt still fails. Covering most of the outage does not count."
  - "The waits double: 3, 6, 12 and 24 minutes. Equal waits of 3 minutes would stop at minute 12, but this runner doubles them, so the last retry starts at minute 45."
  - "Attempt 4 starts at minute 21, after waits of 3, 6 and 12. That is before minute 50, so it fails. The twelve-minute wait is the third wait, not the fourth."
  - "Right. The attempts start at minutes 0, 3, 9, 21 and 45. All five fall before minute 50, so the task fails on every attempt and gives up at minute 45."
```

```quiz
type: mcq
question: "Rawan's laptop was off on 18 and 19 March because of a power cut. Her tasks are idempotent, and the daily command runs yesterday in UTC. On 20 March she wants both missing days in the report. Which command fits best?"
options:
  - "Run daily twice, because daily fills in the missing days one by one"
  - "Run run --date 2026-03-20 once, because the report is built today"
  - "Run backfill --start 2026-03-18 --end 2026-03-19, one run per date"
  - "Delete the lake and the warehouse, then land every date from the start"
correct: 2
explanations:
  - "Daily always runs for yesterday in UTC. Run twice on the 20th, it processes the 19th both times and never touches the 18th."
  - "A run for 20 March processes the 20th. It does not cover the 18th or the 19th, so both days would still be missing."
  - "Right. A backfill takes a start date and an end date and runs each date once, oldest first. Because the tasks are idempotent, it is safe, and it repairs exactly the missing days."
  - "Deleting is not needed. The tasks are idempotent, so running two dates again changes nothing else. Starting from the beginning only wastes time."
```

```quiz
type: mcq
question: "Ammar asks an AI chat tool whether it is safe to add 3 retries to his daily job, which appends the day's orders to a table. It answers: 'Yes. Retries run only after a failure, so rows cannot be doubled, and appending is fine because the job only runs once a day.' What is wrong with the answer?"
options:
  - "Nothing is wrong: a failed job writes nothing at all, so a retry cannot repeat rows"
  - "A job that fails halfway may leave rows behind, so a retry can write them twice"
  - "Three retries are too few for a daily job, so it would still fail on bad days"
  - "A daily job should never be retried, because one day cannot be run twice"
correct: 1
explanations:
  - "A job can fail after it has written some rows. The failure does not undo them, so the retry starts with rows already in the table."
  - "Right. A retry runs the whole job again. If the first try wrote some rows before it failed, an append writes them a second time. The write must be safe to repeat, for example by replacing the day's partition or merging on the report id."
  - "The number of retries is not the problem. Even one retry doubles rows when the write is an append, and more retries would double them more often."
  - "Retries are fine when the job is idempotent, and a backfill runs dates again on purpose. The problem is the append, not the retry."
```

```quiz
type: mcq
question: "Rawan reads the log for 12 March. extract_registry: ok. land: retry, then ok with 135 rows. publish: ok. dbt_build: retry, retry, failed, with the detail 'dbt failed: could not set lock'. checks: skipped. report: skipped. Exit code 1. What should she do first?"
options:
  - "Close the program holding the warehouse file, then rerun the date"
  - "Run land again, because it needed a retry before it finally worked"
  - "Rewrite the checks, because checks did not run on 12 March at all"
  - "Raise the retries of report, because report did not finish its run"
correct: 0
explanations:
  - "Right. The first failed line is dbt_build, and its detail says the warehouse file is locked. Another program holds it. Once it is closed, running the date again works, because the tasks are idempotent."
  - "Land ended ok on its second attempt, with 135 rows. A task that needed a retry and then succeeded is not a problem to fix."
  - "Checks was skipped because dbt_build failed before it. A skipped task is a result of the failure, not a cause, and there is nothing in checks to rewrite."
  - "Report was skipped, not failed. It never ran, so its retries were never used. Changing them would not touch the real failure in dbt_build."
```
