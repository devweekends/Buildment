The nightly dbt build shows: stg_stock OK, stg_sales OK, dim_drug ERROR, fct_sales SKIP, mart_weekly SKIP. Where should he start?"
```quiz
options:
  - "With dim_drug, because the two skipped models only wait for it"
  - "With fct_sales, because it is the first model that was skipped"
  - "With stg_sales, because fct_sales reads it and was skipped"
  - "With mart_weekly, because the readers see that model first"
correct: 0
explanations:
  - "Right. dim_drug is the only model with an ERROR. fct_sales and mart_weekly were skipped because a parent failed, so fixing dim_drug lets both build again."

  - "stg_sales shows OK. It built without a problem, so the reason fct_sales was skipped is not there."
  - "mart_weekly is skipped and has no error. Readers see it first, but the failure is upstream, at the model with the ERROR."
```

```quiz
type: mcq
question: "Layla's table fct_orders has three tests: order_id is unique, customer_key is not null, and every customer_key exists in dim_customer. dim_customer holds c1, c2 and c3. The table holds these rows: (o1, c1, 40.00), (o2, c9, 25.00), (o3, c2, 250.00) and (o3, c2, 250.00). The amount 250.00 should have been 25.00. What does dbt build report?"
options:
  - "Only relationships fails, because c9 is not in dim_customer"
  - "All three fail, and the amount 250.00 is flagged as well"
  - "unique and relationships fail; no test flags the amount 250.00"
  - "unique and not_null fail, because o3 repeats the same customer, c2"
correct: 2
explanations:
  - "relationships does fail for c9, but o3 also appears twice, so unique fails as well."
  - "not_null passes, because every row has a customer_key. No test looks at amounts either, so 250.00 is not flagged."
  - "Right. unique fails because o3 appears twice, and relationships fails because c9 is missing from dim_customer. The wrong amount is above 0 and breaks no written rule, so it passes."
  - "not_null checks for empty values, and every row has a customer_key. Repeating a customer is normal, and only the repeated order_id breaks unique."
```

```quiz
type: mcq
question: "Shahd asks an AI tool whether she can publish the weekly report. She tells it: 'dbt build shows PASS=39 WARN=0 ERROR=0.' The tool answers: 'Then every number in the report is correct and you can publish.' She knows the tests are unique, not_null and relationships on keys, and a price above 0 check. She also knows that one flour price was typed as 80 instead of 8. What is wrong with the answer?"
options:
  - "Nothing is wrong, because a build with no errors means correct data"
  - "dbt tests compare each price with last week's price, and the tool skipped that"
  - "PASS=39 counts only the models, so none of the tests were part of it"
  - "Tests only show that the written rules held, not that the price is right"
correct: 3
explanations:
  - "A price of 80 is above 0, so it breaks none of the four tests. A clean build can still hold a wrong price, so the tool's claim is too strong."
  - "None of these tests compares a price with an earlier week. They check keys and a price above 0 only, so there is no such comparison to skip."
  - "PASS=39 includes the data tests and the unit test as well as the models, so the tests did run. They passed, and that is the limit of what they show."
  - "Right. Each test checks a rule someone wrote. A price of 80 is above 0 and breaks no written rule, so every test passes while the number is wrong."
```

```quiz
type: mcq
question: "Nabil's shop has an incremental model fct_sales with unique_key sale_id and the delete+insert strategy. Each run reads only sales from the last 2 days. Today the source corrects the price of a sale that is 5 days old. What happens to that row in fct_sales on the next run?"
options:
  - "It is updated, because the unique_key finds the row wherever it sits in the table"
  - "It is not read, so the old price stays until a backfill or full refresh"
  - "It is added as a second row that holds the new price"
  - "The build stops with an error, because an old row has changed"
correct: 1
explanations:
  - "The key is used only for rows that the run reads. A 5 day old sale is outside the 2 day window, so the run never sees the correction."
  - "Right. The window decides which rows are read. The corrected sale is outside it, so the old price stays until a full refresh or a backfill re-reads that range."
  - "A second row would appear only if there were no unique_key. With the key, a row that is read replaces the old one, and this row is not read at all."
  - "dbt does not compare old rows with the source. A change outside the window is invisible, so there is no error to raise."
```

```quiz
type: mcq
question: "Layla's reports use a list of 6 product categories. The list has 6 lines, changes about once a year, holds no personal data, and two models need it. Where should the list live in dbt?"
options:
  - "As a snapshot, because a list can change over time"
  - "Copied into each model, so every model stands alone"
  - "As a seed: a small CSV file that dbt loads as a table"
  - "As an incremental model, because a list only gets longer"
correct: 2
explanations:
  - "A snapshot keeps the history of a table that changes. Here nobody needs the old versions of a 6 line list, and a snapshot is hard to rebuild."
  - "Two copies mean two places to change. That is the repetition from the 312 line file, and one copy will be forgotten."
  - "Right. A seed is a small static CSV in the project. Both models can read it with ref, it is in version control, and it holds no personal data."
  - "An incremental model reads recent rows from another model. A hand-made list has no source to read, and it can lose lines as well as gain them."
```
