This page is the board and nothing else. Chapter 35.1 listed the eleven checks. Here you build a design, press Run, and watch it meet them. The board starts with the smallest design that works: one load balancer (it spreads requests over the servers), one app server (it runs the code) and one database. It can save a trip. It has nowhere to keep where the drivers are, and finding out what that costs is the lab.

There is no single right answer. Many designs pass, and one that passes at $2.30 an hour beats one that passes at $5. Aim for green first, then make it cheaper without turning anything red.

## How the board works

<MermaidDiagram title="The board, in four moves" chart={`flowchart LR
  P["Palette<br>on the left"] -->|"drag or tap"| B["Board<br>link the dots"]
  B -->|"hover a part, click Tune"| S["Settings cassette<br>beside the part"]
  B -->|"press Run"| R["Four scenes,<br>then every check"]`} />

The palette is on the left: drag a part onto the board, or tap it. Link two parts by dragging from a dot on one to a dot on another. Settings are not on the page until you ask: hover a part and click Tune on its corner, and a dark cassette opens beside it.

<GoDeeper title="Go deeper: the cassette, names, and what Run shows">

The board only allows links where requests really flow, and it tells you when a link is not allowed. The settings drawer holds the part's size, how many there are, which zones they live in, and any setting special to that part, such as a cache's hit rate or a worker's group size (batch size). Only one cassette is open at a time. On a phone it docks along the bottom while the part moves into view above it, and you tap a part to show its Tune key. Press Escape or the close key to put it away. The Names switch in the header changes the parts to real AWS names and sizes, with a line on what each one means. The numbers do not change.

Press Run and the board plays four scenes. Dots travel along the links, a part turns amber and then red as it fills, and a part that dies is marked DOWN. When the scenes end, each check shows pass or fail, the number the board measured, the number it needed, and why a failed check failed. Press Show on any check to replay its scene on the board.

</GoDeeper>

## Build it on the board

<Lab slug="hld-visual-ride-matching" />

Run the starting design first, before you change anything. It has one load balancer, one app server and one database. Read the failures in order. Each one names a part and a number, and each number points at a setting. The first failure is a missing part, and it is the one the whole module is about.

<GoDeeper title="Go deeper: reading a failure">

A failure has three lines. The first says what was measured and what was needed. The second says why, usually naming the busiest part and how busy it was. For example, "Load balancer is 250% busy, so it cannot serve the whole load" says that more requests arrive than that part can pass on, and every part behind it is starved. Fix the part named, run again, and a different part is usually the next one named. That is the loop of chapter 4.9: the busiest part on the path sets the ceiling, and you move the ceiling by raising one part at a time.

Two failures deserve a closer look. "Everyone is still served when one app server dies" runs the scene with one app server fewer. A fleet of one has nothing left, so it fails at once. A fleet of two may serve only 60% if each server cannot carry the whole load alone. And "No trip events are lost when the worker dies" needs the events to wait somewhere while the worker is down, which is what a queue is for. It then needs the workers to be fast enough, once back, to catch up on the waiting events (the backlog) as well as the new ones.

</GoDeeper>

## Put the location map in front

<MermaidDiagram title="Where 4,000 requests a second go" chart={`flowchart LR
  APP["App servers<br>4,000 req/s"] --> C["Location map<br>95% answered"]
  APP -->|"the rest: about 200 req/s"| DB[("Database")]`} />

Link a cache from the app server and call it the location map. Set its hit rate. A request the map answers never reaches the database, only the rest go on. At 95% the database sees about 200 requests a second instead of 4,000, and p99 drops. Then run again and watch the map scene.

<GoDeeper title="Go deeper: the map scene, and why nodes matter">

In the map scene one node of the map goes dark. With a map of a single node, nothing is left, and every request asks the database. A database of the small size cannot serve 4,000 a second, so the check fails, and the board names the database as the busiest part. The fix is not a bigger database. Give the map two nodes, and the second keeps serving while the first is away. In a real map the lost node comes back empty and refills in one report interval, which is 4 seconds in Safar (chapter 24.3). The board cannot show those 4 seconds. It shows only whether the others can carry on.

Each link on the board shows its own numbers: requests going to the map with the share it answers, and the rest going on to the database. You may also link the cache onward to the database, so the cache loads from it on a miss. The database gets the same load either way, but then the cache sits in the path, and its death cuts the database off. Chapter 35.3 follows the map failure in detail.

</GoDeeper>

## Recording events is where designs differ

<MermaidDiagram title="Two ways to record an event" chart={`flowchart LR
  subgraph inline["No queue: write inline"]
    A1["App server"] -->|"4,000 writes a second"| D1[("Database")]
  end
  subgraph queued["Queue and worker"]
    A2["App server"] --> Q["Queue"] --> W["Worker<br>batch of 500"] -->|"8 writes a second"| D2[("Database")]
  end`} />

You can write each event to the database before the request answers, with no extra part. The board lets you, and shows the price: 4,000 extra writes a second on the database. Or add a queue and a worker. Try both, and compare the cost and the busiest part each time.

<GoDeeper title="Go deeper: why inline recording is expensive">

The simplest way needs no extra part. Its price is that the database must take 4,000 extra writes a second on its one main copy, and a read-only copy cannot help with writes. It can be done with a much bigger database, and then the design fails on cost and on speed.

The other way is the one from chapter 20.4. The app server hands the event to a queue and carries on. A worker takes events from the queue and writes them in groups (batches). The request never waits for the save, and the database sees a few large writes. The price is two more parts to run and pay for, and a short delay before an event shows in the history. In Safar the events are the history log of chapter 24.3: the map keeps only the latest place, and the log keeps the trail for receipts, safety checks and trip replays.

</GoDeeper>

## Make it cheaper

<MermaidDiagram title="Pass first, then trim" chart={`flowchart LR
  G["All checks green"] --> T["Trim the part with spare room"]
  T --> R["Run again"]
  R -->|"a check turns red"| U["Undo that trim"]
  R -->|"still green"| T`} />

When every check is green, look at the cost. Find the part with the most spare room, shrink it one step, and run again. If a check turns red, undo that step. The budget is $2.50 an hour, and a design that passes costs a little less. Two extra instances or two sizes too large fail on cost alone.

<GoDeeper title="Go deeper: stuck? One design that passes">

One design that passes all eleven checks: a load balancer of size general-medium in two zones. Three app servers of size compute-small in two zones. A location map of two cache nodes of size memory-small at a 95% hit rate in two zones. A database of size memory-small with an extra copy that takes over (a failover standby) in a second zone, no read-only copy, set to 50% reads. A queue, and three workers of size compute-small with a batch size of 500. The app server links to the cache, the database and the queue. The queue links to the workers. The workers link to the database.

The board reports a ceiling of 6,400 requests a second, p99 near 69 ms, availability near 99.99% and about $2.31 an hour. The two checks that depend most on one choice are the map checks, which need a second node, and the worker check, which needs a third worker. Try taking each away, and read what the board says.

</GoDeeper>
