A run is a small experiment, and every red check is a result. This chapter reads the scenes one at a time. For each, it says what the board did and what to change. All numbers come from the board's model. There is no code lab for this design yet, so none of them was measured on a real stack, and the milliseconds are model milliseconds. Read them as relative. The shape is what matters.

The reference design here is the one the Solution button opens: a load balancer in two medium zones, three app servers, a location map of two nodes, a database with a standby, a queue and one worker that saves the few trip events.

## Scene 2: an app server dies

<MermaidDiagram title="Losing one of three app servers" chart={`flowchart LR
  LB["Load balancer"] --> A1["App server"]
  LB --> A2["App server"]
  LB -.->|"stopped"| A3["App server"]`} />

One app server of three goes dark, and the load balancer sends its share to the others. Everyone is still served, and p99 rises from about 69 to about 144 ms. The lesson is one spare machine (N+1): size the fleet so that losing one still leaves enough.

<GoDeeper title="Go deeper: the numbers behind scene 2">

On the board, three servers are each 56% busy at 4,000 requests a second. With one gone, the two left are 83% busy each, and a busier part makes every request wait longer, which is why p99 doubles. The check asks only that everyone is served, and they are. With only two servers to begin with, each is already 83% busy at the peak and p99 is 144 ms. Losing one leaves the other with 167% of what it can carry, and only 60% of requests are served.

This is the rule from chapter 4.2 meeting a failure. The extra server is not waste, it is the part that makes the death invisible. When an app server dies the load balancer's load does not change, so the board names the app server as the busiest part. If it named the load balancer, the balancer would have been too small before the failure, and "Serves the whole peak" would already be red.

</GoDeeper>

## Scene 3: a node of the map dies

<MermaidDiagram title="With one node, the database finds out" chart={`flowchart LR
  APP["App servers<br>4,000 req/s"] -.->|"only node gone"| C["Location map"]
  APP -->|"all 4,000 req/s"| DB[("Database<br>small")]`} />

The map answers 95% of requests, so the database sees about 200 a second. If the map is one node and it dies, the database sees all 4,000. It reaches 168% busy, only 60% of requests are served, and p99 is 594 ms. With two nodes, the other carries on and nothing changes. A map protects the database only while a node is there.

<GoDeeper title="Go deeper: the numbers behind scene 3, and why the map has no copy">

On the board, a one-node map that dies sends the database from 9% to 168% busy, serves 59.7% of requests, and takes p99 from 69 to 594 ms. A bigger database passes, but memory-large with a standby brings the bill to $2.24 an hour, over the $1.65 budget. A second node of the map costs $0.15 an hour.

Look at what the second node is. It is not a copy of the first. In chapter 24.3 the map is sharded: each node holds the boxes of its own drivers, and the map "has no database behind it". Its only copy of a driver's place is the next report from the driver. A lost node comes back empty and fills itself within 4 seconds, because every driver reports again. So the second node does one job in the model, which is to keep answering while the first is away, and it does another in real life, which is to hold half of the drivers in the first place. The board shows the first job and cannot show the 4 seconds.

A design that needs its map to survive has a hidden dependency. Either the map has spare nodes, or the database must carry the full load without it. The first is far cheaper, because the map costs little and the database is priced by the size you need at the worst moment.

</GoDeeper>

<GoDeeper title="Go deeper: why not write each place to the database at all?">

The first check of the starting board fails because it has no map, and the board's other numbers say why the check matters. With no map, the small database takes all 4,000 requests a second and is 168% busy: it serves 2,388 a second and p99 is 594 ms. A place report replaces the last place, and the next one comes in 4 seconds, so a durable row for each report buys almost nothing (chapter 24.3). It would also cost 4,000 writes a second, and at the size of a million drivers, 250,000.

</GoDeeper>

## Scene 4: the trip worker dies

<MermaidDiagram title="The queue holds events while the worker is away" chart={`flowchart LR
  APP["App server"] -->|"20 events/s"| Q["Queue<br>1,200 waiting"]
  Q -.->|"stopped 60 s"| W["Worker"]
  W --> DB[("Database")]`} />

Requests do not notice a dead worker. The queue keeps each event. Only 1 request in 200 leaves one, so after 60 seconds the queue holds 1,200, and a single small worker, which handles 2,400 a second, clears them about a second after it returns. The queue is there so that nothing is lost and no request waits. The cost is small because the share is small.

<GoDeeper title="Go deeper: the numbers behind scene 4, and what a bigger share would change">

The share comes from the module's own chapters: ride requests are about 0.2% of requests (chapter 24.1), and a ride makes about 2.4 events (a request, about 1.4 offers because 7 in 10 are accepted per chapter 24.4, and an acceptance), a course assumption. So the lab uses 1 in 200, which is 20 events a second at 4,000 requests a second. One worker is 1% busy, the database sees 20 writes a second, and the queue costs about a cent an hour.

Compare that with counting every location report. Chapter 24.3 also appends each accepted report to a history log, which would be 4,000 events a second. Then 60 seconds of waiting events would be 240,000, one small worker would handle 2,400 a second against 4,000 arriving and never catch up, and saving in groups (batching) would turn 4,000 database writes a second into a few. The board does not model that log. The lesson has the same shape either way: a queue buys time only if the consumer has spare capacity, and the size of the share decides how much spare capacity you need.

If you remove the queue, the check fails, not because 20 events a second is heavy, but because the events have nowhere to wait while the worker is away. If you keep the queue and remove the worker, the events pile up and are never saved.

</GoDeeper>

## Solution walkthrough

<MermaidDiagram title="From a failing run to the reference design" chart={`flowchart LR
  R["Run once"] --> S["Solution"]
  S --> P["Pick a part:<br>why, checks, without it"]
  S --> C["Compare with mine"]
  S --> K["Copy to my board"]`} />

After you press Run once, the Solution button opens the reference design on the same board. Pick any part to see why it is there, which checks it helps pass, and what fails without it. Compare with mine lists what differs from your design. Try first: a failing run you can explain teaches the most.

<GoDeeper title="Go deeper: how to use the solution well">

The solution is never locked behind a score, and nothing is recorded when you open it. Your own board stays untouched while you look: Back to my design returns to it, and Copy to my board asks before it replaces anything. The link labels in the solution show each hop on its own: requests going to the map with the share it answers, the rest going on to the database, and the event saves counted separately.

A good way to use it is to compare after one more try. Fix the failure you understand, run again, and only then press Compare with mine. It lists parts, settings and links that differ, in words such as "lower" and "smaller", and names the failing checks each one helps explain. It does not print the reference's numbers.

The same design will run for real in the code lab, which is coming: a stack with the same parts, where you stop each one yourself. The names of the parts and the checks are meant to match, so a design you built on the board can be replayed there.

</GoDeeper>

## The failure the board cannot show

<MermaidDiagram title="One box gets the whole crowd" chart={`flowchart LR
  F["20,000 fans leave a stadium"] --> B["One box"]
  B --> N["One map node<br>75 times a quiet box"]
  N -.->|"overloaded: other nodes idle"| X["Slow map"]`} />

After a match, 20,000 fans open the app in one box. In chapter 24.3 that box carries about 75 times the work of a quiet one, on one shard, while the other nodes sit idle. The board spreads load evenly over the nodes of a part, so it is too kind. It also cannot show a place that has gone stale, or a late report. What would you change?

<GoDeeper title="Go deeper: honest answers to the crowded box">

The board's map has two nodes, and each takes half of the 4,000 requests a second, so each is 7% busy. It has no boxes, so no node can be hot. A real map is sharded by box (chapter 24.3), and the stadium's box lands on one shard. Giving the map more nodes does not help when one key is the hot one. Averaging hides it: check the busiest box, not the average of all of them.

There are real answers, and each costs something. Split the crowded box with a quadtree (chapter 24.2) so that its parts can live on different shards. Cache the map view of that box for 2 seconds, so that thousands of fans share one answer and a car moves only about 17 metres in that time. Slow the refresh in a crowded box from 5 to 10 seconds and show only the nearest 8 cars. A good design names which cost it chose, and what number would make it change its mind.

The board also cannot show how fresh a place is. A report that arrives late must not replace a newer one, which is why chapter 24.3 numbers the reports. And a driver who goes through a tunnel and stops reporting must disappear after 12 seconds. Both are real concerns that need a clock and an order, and the model has neither.

</GoDeeper>

<GoDeeper title="Go deeper: in an interview">

**In an interview.** Walk the failures in order. Say what you lose when each part stops, and what each choice costs. "If an app server dies, the others carry on, because I kept one spare machine and the servers hold no state. If a node of the location map dies, the other node keeps serving, and the drivers it held report again within 4 seconds. If I had only one node, the database would take every request, so I would not accept that. If the trip worker dies, the few trip events, about 1 request in 200, wait in the queue and are saved after the restart. And I have not shown how I handle a stadium, where one box gets most of the traffic. I would split that box and cache its view for 2 seconds."

Interviewers like the last sentence most. They want to hear that you looked for the failure your tools cannot show, and that you can name what you would pay to remove it.

</GoDeeper>
