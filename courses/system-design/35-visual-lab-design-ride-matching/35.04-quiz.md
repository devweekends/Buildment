```quiz
type: mcq
question: "A design has a location map of one node at a 95% hit rate and a small database. At 4,000 requests a second the board shows it passing every check in the peak scene and failing both checks in the map-node scene. What explains the difference?"
options:
  - "The map is too small and drops places when it gets busy"
  - "The load balancer is the busiest part in the map-node scene"
  - "The app servers stop when a map node is lost"
  - "Without the map, the database sees all 4,000"
correct: 3
explanations:
  - "The map's size is not the problem here. In the peak scene it works and the database is almost idle. The failure appears only when the map is gone."
  - "The load balancer is not behind the map. Its load is 4,000 requests a second in both scenes, so it cannot be what changed."
  - "The scene takes only the map's node down. The app servers carry the same load as before, so they are not what fails."
  - "Right. At a 95% hit rate the database sees about 200 requests a second. When the only node dies it sees all 4,000, which is more than a small database can serve. A second node would have kept answering."
```

```quiz
type: mcq
question: "About 1 request in 200 leaves a trip event, at 4,000 requests a second. The worker stops for 60 seconds, then returns. One worker handles 2,400 events a second. How long do the waiting events take to clear?"
options:
  - "About 1 second, because only 1,200 are waiting"
  - "About 100 seconds, because 240,000 are waiting"
  - "They never clear, because 4,000 arrive each second"
  - "They clear at once, because a queue empties itself"
correct: 0
explanations:
  - "Right. 4,000 divided by 200 is 20 events a second, so 60 seconds leaves 1,200 waiting. One worker clears 2,380 a second on top of the new events, so it needs about 1 second."
  - "240,000 is 4,000 events for 60 seconds, which counts every request as an event. Only 1 in 200 makes one."
  - "4,000 is the request rate, not the event rate. The events arrive at 20 a second, far below what one worker handles."
  - "A queue only holds events. A worker must take them out, and it does so at its own speed, so the clearing takes a moment."
```

```quiz
type: mcq
question: "A team writes every place report straight to a database row, and keeps no map in memory. Each driver's place is replaced by the next report 4 seconds later. What should they conclude?"
options:
  - "The database is the right home, because no place is ever lost"
  - "Almost every write buys nothing, and the load is huge"
  - "Reports should be sent less often than every 4 seconds"
  - "Only searches need memory, and reports can stay on disk"
correct: 1
explanations:
  - "A place that is lost is replaced by the next report within 4 seconds, so keeping every one safe buys almost nothing. A trip is different, and belongs in a store that keeps it."
  - "Right. Each row is out of date in 4 seconds, and the writes are the biggest load in the system. Keep the latest place in memory and give a separate home to history and trips."
  - "Sending less often makes the map staler and does not remove the problem, which is writing data that is replaced almost at once."
  - "A search needs the current place, and a report is the thing that replaces it. Both belong in the same fast store, and putting either on disk keeps the cost of the writes."
```

```quiz
type: mcq
question: "After a football match, 20,000 fans open the app in one box. The lab board shows every check green for the design. Why can the board still be too kind?"
options:
  - "It gives each node an equal share, so none is hot"
  - "It ignores the cost of the extra map nodes you would add"
  - "It only tests the peak scene and never loses a node"
  - "It assumes places never expire, so searches are always right"
correct: 0
explanations:
  - "Right. The model gives each node of the map an equal share, so it cannot show one node carrying 75 times a quiet box's work while the others idle. You split the box and cache its view to fix that."
  - "The board prices every node. Cost is one of its checks, and it is not what hides a crowded box."
  - "The board loses an app server, a map node and the worker. It tests three failures, and none of them is a crowd."
  - "Expiry is another thing the board cannot show, but it is not what makes a crowded box invisible. The even spread of load is."
```
