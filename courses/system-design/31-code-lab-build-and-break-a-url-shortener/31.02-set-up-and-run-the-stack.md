This chapter gets the real system running on your laptop. It takes about ten minutes, most of it waiting for Docker to build the first time. Nothing here is graded. The goal is that, by the end, you can make a short link, open it, send a burst of traffic and see which part of the system answered each request.

The repository is public: github.com/ZeeshanAdilButt/system-design-labs. This lab lives in the folder `labs/lab-1-url-shortener`.

## What you need

<MermaidDiagram title="Two tools" chart={`flowchart LR
  D["Docker<br>runs the parts"] --> L["Your laptop"]
  U["Python with uv<br>runs the experiments"] --> L`} />

You need Docker installed and running, and Python with a tool called uv, which runs the experiment scripts. If `docker --version` and `uv --version` both print a version, you are ready. Nothing else needs installing, because the rest runs inside Docker. Open a terminal now and run both commands.

<GoDeeper title="Go deeper: what each tool is for">

Docker runs each part of the system (the gateway, the API copies, Redis, the worker, Postgres) in its own container, which is a small isolated box with its own files. A file called `docker-compose.yml` lists all the containers and how they connect, so one command starts the whole system. uv is a fast way to run Python scripts together with the packages they need. The experiment scripts use it to send traffic, stop containers on purpose and measure what happened. If a command fails with "not found", the tool is missing or not on your path: install it, open a new terminal and try again. On Windows, the Docker command line needs Docker Desktop to be running, so start it first and wait until it says it is running. You do not need to know Python to follow this module. You will read a few small files and edit one or two short ones, and the tasks tell you where to look.

</GoDeeper>

## Start the stack

<MermaidDiagram title="One command starts everything" chart={`flowchart LR
  C["docker compose up"] --> G["gateway"]
  C --> A["api x3"]
  C --> R["redis"]
  C --> W["worker"]
  C --> P["postgres"]
  C --> S["seed: adds sample links"]`} />

Clone the repository, go to the lab folder and start everything. The first build takes a minute or two. A small helper then adds a dozen named links and about 180 clicks, so the page is not empty.

```bash
git clone https://github.com/ZeeshanAdilButt/system-design-labs
cd system-design-labs/labs/lab-1-url-shortener
docker compose up -d --build
```

<GoDeeper title="Go deeper: ports, and when one is taken">

The page is at http://localhost:8080. Postgres is on `127.0.0.1:5451` and Redis on `127.0.0.1:6391`, in case you want to look inside. The API documentation, generated by the framework, is at http://localhost:8080/api/docs. If another program already uses one of these ports, set `GATEWAY_PORT`, `PG_PORT` or `REDIS_PORT` before you run the command, for example `GATEWAY_PORT=8090`. To add the sample links again at any time, run `docker compose run --rm seed`.

</GoDeeper>

## Make a link and send traffic

<MermaidDiagram title="What the page does for you" chart={`flowchart LR
  M["Make a link"] --> V["Visit it"]
  V --> T["Send 500 requests"]
  T --> D["Watch the diagram"]`} />

Open http://localhost:8080. Make a short link, press **Visit**, then press **500** under "Send traffic". The diagram lights up the path each request took. Green means the answer came from the cache (fast memory). Orange means the database had to be asked.

<GoDeeper title="Go deeper: reading the diagram">

Each request goes through the gateway to one of the three API copies. The API asks the cache first. If the cache has the answer (a hit), it replies at once. If not (a miss), it reads the database, stores the answer in the cache for next time and replies. Only after the reply has gone out does it drop a click event on the queue, and the worker counts the click a moment later. So the diagram shows two paths: the one the person waits for, and the one that happens afterwards. The hit ratio at the top climbs as the cache fills with the links you open. Try it: open the same link five times and watch the path turn green after the first visit, then open a link you have never opened and watch it turn orange once. That one orange, followed by green, is the whole story of a cache in two clicks, and it is the pattern the next chapters ask you to predict and then measure. A fresh link starts orange because nobody has asked for it yet, so the cache has nothing stored for it.

</GoDeeper>

## What a healthy run looks like

<MermaidDiagram title="Healthy and not healthy" chart={`flowchart LR
  OK["All parts green<br>hit ratio climbing<br>clicks counted"] --- BAD["A part red or grey<br>check docker compose ps"]`} />

The status pill at the top shows every part as healthy. After a few hundred requests the cache hit ratio is high, and the click counter on your link rises to match the number of visits. If something is red or grey, run `docker compose ps` to see which container is not running, and `docker compose logs` followed by its name to read why.

<GoDeeper title="Go deeper: the first things that go wrong">

The most common problem is a port that is already in use: the build finishes, but the page does not open. Change the port as above. The second is Docker not running at all: start Docker Desktop and wait until it says it is running. The third is a slow first build on a small laptop: wait for the command to finish, because the page is only ready after the sample links have been added. If a container keeps restarting, the logs name the reason, and the repository's README lists the usual causes. When you ask for help, copy the output of `docker compose ps` and the last twenty lines of the logs of the container that is not healthy. Those two pieces tell a helper more than any description, and reading them yourself is the first skill of running a real system.

</GoDeeper>

## Put everything back

<MermaidDiagram title="Reset, then stop" chart={`flowchart LR
  R["scenario.py reset<br>back to the full design"] --> X["docker compose down<br>stop it all"]`} />

Later chapters change the design and stop parts on purpose. One command puts the full design back: run `scenario.py reset` from the repository folder (the next chapter shows the full command). When you are finished for the day, `docker compose down` stops everything, and adding `-v` also forgets the data.

<GoDeeper title="Go deeper: why reset matters">

Every experiment starts from the same design, or the numbers cannot be compared. The reset command sets all the settings back to the default (three API copies, cache on, queue on, worker on) and waits until every part reports healthy. Get into the habit: reset, change one thing, run, read the result, reset. If a result looks strange, the first question is always "did I start from a reset?".

</GoDeeper>
