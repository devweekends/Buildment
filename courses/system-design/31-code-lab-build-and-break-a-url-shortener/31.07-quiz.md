```quiz
type: mcq
question: "You stop the API copy that was answering your requests, and no redirect fails. Which part of the stack made that possible?"
options:
  - "The gateway tries another copy"
  - "The cache stores every link forever"
  - "The worker repeats failed requests"
  - "Postgres answers instead of the copy"
correct: 0
explanations:
  - "Right. The gateway tries another copy when one does not answer, and the copies keep nothing of their own, so any copy can serve any request."
  - "The cache helps speed, but it does not decide where a request goes. A request still needs a running copy of the API to reach the cache."
  - "The worker counts clicks after the reply has gone out. It never sees a redirect request."
  - "Postgres does not take requests from the gateway. Only the API copies do, and the gateway chooses among them."
```

```quiz
type: mcq
question: "Postgres is stopped. A link you opened a minute ago still redirects, but a brand new link fails with a clean error after about 2 seconds. Why?"
options:
  - "The cache is faster than the gateway"
  - "The worker keeps a copy of old links"
  - "A new link must be saved in Postgres"
  - "Redis refuses links it has not seen"
correct: 2
explanations:
  - "Speed is not the reason. The cache can answer a hot link because it already holds the answer, whatever the gateway does."
  - "The worker only counts clicks. It does not store links."
  - "Right. Opening a hot link needs only the cache. Making or opening a link nobody asked for needs Postgres, which is down, so the API returns an error after its timeout of about 2 seconds."
  - "Redis would store a new link happily. The link is refused because it cannot be saved in the database, which is the source of truth."
```

```quiz
type: mcq
question: "Redis, which holds both the cache and the click queue, is stopped for a few seconds under traffic. What do you lose that nobody sees as an error?"
options:
  - "The links that people made before"
  - "The clicks made while it was down"
  - "The three copies of the API service"
  - "All of the data stored in Postgres"
correct: 1
explanations:
  - "Links are saved in Postgres. They are safe while Redis is down, and redirects still work, slowly, from the database."
  - "Right. The queue lives in Redis, so clicks made while it was down had nowhere to wait. About 42 percent were lost in the real run, and no redirect failed."
  - "The API copies keep running without Redis. They skip the cache for a short time and read the database."
  - "Postgres is a separate container with its own storage. Stopping Redis does not touch it."
```

```quiz
type: mcq
question: "The board failed a design with no read-only copy when the cache died, but on your laptop the same event only made redirects slower. What explains it best?"
options:
  - "The real database is always much faster"
  - "The board has a bug in its model of it"
  - "Redis keeps all the links after it stops"
  - "Your laptop's load is far below the limit"
correct: 3
explanations:
  - "The real database is not faster in general. It simply was not asked to do more than it could."
  - "The board is a model with stated limits. It was set at 3,000 requests a second, which is above what one database serves, so it fails there."
  - "A stopped Redis keeps nothing. After it stops, the API reads the database for every link."
  - "Right. At a small load the database keeps up, slowly. Near its limit the same event is an outage. Both pictures are true, and the board shows the second one."
```
