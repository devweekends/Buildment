You have the stack running. Now you stop watching and start doing. The repository has a file called `YOUR-TURN.md` with nine tasks, numbered T1 to T9. This chapter is your map to them: what each task asks, how to start, and which check on the visual lab board it mirrors. The full directions for every task are in the repository file, and the answers are in neither place.

## How a task works

<MermaidDiagram title="Guess, do, check, then look" chart={`flowchart LR
  G["Write a guess<br>with a number"] --> D["Do the task<br>directions only"]
  D --> C["Check yourself<br>a command"]
  C --> S["Open a solution<br>only if you must"]`} />

Every task has the same four parts: a goal in plain words, a guess you write down before you run anything, directions that never give the answer, and a command to check yourself. Run every command from the repository root, the `system-design-labs` folder, not from the lab folder inside it.

<GoDeeper title="Go deeper: the two tools and the code exercises">

Two small tools are used again and again. The ruler is `uv run labs/lab-1-url-shortener/your-turn/redirect_timer.py`. It makes some links, opens them 2,000 times through the gateway and prints how many failed, how many were answered from the cache, the typical wait (p50), the slowest 1 in 100 (p99) and how many clicks are still waiting to be counted. The numbers move a little every run, so compare shapes, not decimals. The reset is `uv run labs/lab-1-url-shortener/tools/scenario.py reset`. Run it whenever a task changed a setting.

Five tasks (T3, T5, T7, T8 and T9) are code exercises. Each has a starter file named `tN_*.py` in the `your-turn` folder, and a test file named `test_tN_*.py`. Do not edit the test files. The tests are red when you start, and that is the point. These exercises are small copies, so they never touch the running system, apart from one optional last step in T8 that says so. Run them all with `uv run pytest labs/lab-1-url-shortener/your-turn`, or one at a time by adding `-k t3`. A plain `uv run pytest` skips this folder, so the repository's own checks stay green while your exercises are unfinished.

</GoDeeper>

<GoDeeper title="Go deeper: which board check each task mirrors">

Each result on the real stack has a check on the visual lab board from module 30, and a stable id in the repository's contract file. Some tasks have no board check, because the board does not model them. Say so honestly when you write your notes.

| Task | What it does | Board check it mirrors | Contract check id |
|---|---|---|---|
| T1 | Measure when random codes first repeat | none: the board does not model codes | `unique_codes` |
| T2 | Take away ids handed out in blocks | Shortening works | `create_link` |
| T3 | Fix a shuffle that repeats a code | none: the board does not model codes | `unique_codes` |
| T4 | Switch the cache off, measure the wait | Slowest 1 in 100 redirects is fast enough; Serves the whole peak | `redirect_p99_ms`, `throughput_rps` |
| T5 | Fix a new link that answers 404 | Opening a short link returns the long address | `redirect_302`, `unknown_404` |
| T6 | Stop the worker, watch clicks queue up | No clicks are lost when the worker dies | `worker_loss_clicks_caught_up` |

## Part 1: the codes (T1 and T2)

<MermaidDiagram title="Where a code comes from" chart={`flowchart LR
  R["Random pick<br>repeats early"] --> C["T1: when?"]
  B["Ids in blocks<br>fewer trips"] --> T["T2: how many?"]`} />

T1 asks how soon random short codes repeat, and T2 takes away the saving from handing out ids in blocks, so you can see what the database was spared. Both start with a number you write down first.

<GoDeeper title="Go deeper: T1 and T2 directions">

**T1: how soon do random codes repeat?** The goal is to feel the birthday problem (the surprise that a repeat comes far sooner than you would think). Predict first: random 5 character codes can take about 916 million different values. After how many links do you expect the first repeat? Pick one of hundreds, thousands, tens of thousands, hundreds of thousands, millions, and write one number. Do the same for 6 characters. Then run the short form of part 1, which needs no Docker, and read its first table. Run it twice.

```bash
uv run labs/lab-1-url-shortener/part-1-the-codes/the_codes.py --quick
```

Compare your guess with the median column and the formula column. Count how many times too high or too low you were. Then write two sentences: why is the real number so much smaller than "about a billion", and why does it differ on the second run? Hint if you are stuck: think about how many pairs of links exist, not how many links.

**T2: block size one.** The goal is to see what ids in blocks of 1,000 save the database, by taking the saving away. Each API copy normally reserves a block of ids in one trip to Postgres and hands them out from memory. Predict first: how far will the shared counter (a sequence called `link_id_blocks`) move after 10 new links with the default block size, and how far with a block size of 1? Read the counter, make 10 links with the ruler, read it again. Then change one setting with `scenario.py apply '{"block_size": 1}'`, repeat, and put it back with `scenario.py reset`.

```bash
docker compose -f labs/lab-1-url-shortener/docker-compose.yml exec postgres psql -U shortener -d shortener -c "SELECT last_value FROM link_id_blocks"
uv run labs/lab-1-url-shortener/your-turn/redirect_timer.py --links 10 --requests 10
```

Subtract the two readings in each case, and explain how many trips each case made. Then look at the `CREATE SEQUENCE` line in `system/db/init.sql` and say how much of each reserved block gets used when the block size is 1. Hint: the counter does not move by 1 per trip. Find out how much it moves by.

</GoDeeper>

## T3: a shuffle that is not a shuffle

<MermaidDiagram title="A counter becomes a code" chart={`flowchart LR
  N["Counter value"] --> S["shuffle"]
  S --> K["Code"]
  K --> U["unshuffle<br>runs it backwards"]`} />

T3 is a planted bug. A copy of the code that turns a counter into a code gives two links the same code. The real one never repeats a value. You find the bug, fix `shuffle` and turn the tests green.

<GoDeeper title="Go deeper: T3 directions">

The file is `your-turn/t3_shuffle.py`, and its test is `your-turn/test_t3_shuffle.py`. Predict first, before you read the code: out of the first 50,000 counter values, how many different outputs do you expect from a working shuffle, and from this broken one? Write both numbers.

Run the tests and read why they fail. Then read the file. The function `unshuffle` is correct and runs the shuffle backwards, so compare what one round of `shuffle` does with what one round of `unshuffle` undoes. Fix `shuffle`.

```bash
uv run pytest labs/lab-1-url-shortener/your-turn -k t3
```

The test is red at the start, and the one that counts different outputs tells you how many it got. It is green when you are done. Then compare your first guess for the broken version with the number the failing test printed. Hint if you are stuck: whatever one round does to the two halves, you must be able to get both of the old halves back from the two new ones.

</GoDeeper>

## Part 2: the cache (T4 and T5)

<MermaidDiagram title="Cache on and off, and a stale answer" chart={`flowchart LR
  ON["T4: cache on<br>then off"] --> R["Compare the waits"]
  A["T5: open, create,<br>open again"] --> S["Stale 404?"]`} />

T4 puts a number on what the cache buys by taking it away. T5 is a planted bug: a link is saved, yet it still answers "no such link" for a short while.

<GoDeeper title="Go deeper: T4 directions, switch the cache off">

Predict first, with three guesses. Out of 2,000 redirects, how many reach Postgres with the cache on, and how many with it off? Does the typical wait change, and by how much? How big is the difference between two runs of the same setup (the run-to-run noise), and is the cache's effect on the wait bigger or smaller than that noise on your laptop?

```bash
uv run labs/lab-1-url-shortener/your-turn/redirect_timer.py
uv run labs/lab-1-url-shortener/tools/scenario.py apply '{"cache": false}'
uv run labs/lab-1-url-shortener/your-turn/redirect_timer.py
uv run labs/lab-1-url-shortener/tools/scenario.py reset
```

Run each setup at least three times, and write every p50 and p99 down. Then repeat with `--concurrency 1` (nobody waiting in line) and with `--concurrency 16`. Compare what you see with the tables in part 2, and if your numbers disagree, say why that could be. Check yourself: the cache-off report should show 0 percent answered from the cache and no failures, and every redirect that is not from the cache was a read of Postgres. Hint: a cache protects two things, the person waiting and the database. Which of the two does your table show most clearly?

</GoDeeper>

<GoDeeper title="Go deeper: T5 directions, the link that answers 404">

The file is `your-turn/t5_create_path.py`. Predict first: someone opens `/launch` before it exists, then you create `launch`, then someone opens it again. What do you expect on that last open, and for how long? Why would the system remember the first answer at all? The row about unknown codes in the lab README's table of choices may help.

Run the tests, find the line where the sequence goes wrong, and fix `make_link`. Read the second test before you write the fix, because some fixes that satisfy the first test break the second.

```bash
uv run pytest labs/lab-1-url-shortener/your-turn -k t5
```

You want three tests, all green. Then say in one sentence why the cache write has to happen where you put it and not somewhere else. Hint if you are stuck: there are two places the cache could be told about the new link, and only one of them is safe when the name turns out to be taken.

</GoDeeper>

## Part 3: clicks (T6 and T7)

<MermaidDiagram title="Clicks wait, then catch up" chart={`flowchart LR
  W["Worker stopped"] --> Q["Clicks wait<br>in the queue"]
  Q --> B["Worker back<br>queue empties"]`} />

T6 stops the worker and watches the click queue do its job. T7 is a planted bug in a click counter: when the database blinks, some clicks are never counted. You guess how many clicks survive before you run either one.

<GoDeeper title="Go deeper: T6 and T7 directions">

**T6: stop the worker.** Predict first: you stop the worker and open links 1,000 times. How many redirects fail, how many clicks are waiting in the queue afterwards, and how long after the worker starts again until the queue is empty? Seconds or minutes?

```bash
docker compose -f labs/lab-1-url-shortener/docker-compose.yml stop worker
uv run labs/lab-1-url-shortener/your-turn/redirect_timer.py --requests 1000
curl -s http://localhost:8080/api/stats
docker compose -f labs/lab-1-url-shortener/docker-compose.yml start worker
curl -s http://localhost:8080/api/stats
```

Repeat the last command every second or two and watch `click_backlog`. In PowerShell write `curl.exe`. Then answer: would a person using the service have noticed anything while the worker was down, and what would change if each redirect wrote its click to the database before answering?

**T7: the clicks that vanish.** The file is `your-turn/t7_click_counter.py`. The queue hands each event out once. Predict first: if the counter reads a batch of 500 clicks and the database write fails, where are those 500 now? Out of 1,200 clicks, how many do you expect to be counted if the database fails on the first two tries and works afterwards? Run the tests, read the failing assertion and work out where the failed batch goes. Fix `step`. The rule is that a click may be counted twice after a crash, but never zero times.

```bash
uv run pytest labs/lab-1-url-shortener/your-turn -k t7
```

Both tests should go green. Then compare with the way the real worker does it in `system/shortener/src/shortener/worker.py`, and note one thing that is the same and one thing that differs. Hint: `step` is called again and again by a loop. What does the loop need to find the second time?

</GoDeeper>

## T8: a breaker for the database

<MermaidDiagram title="Three states of a breaker" chart={`flowchart LR
  C["Closed<br>calls go through"] -->|"fails"| O["Open<br>fail at once"]
  O -->|"cooldown ends"| H["Half open<br>one test call"]
  H -->|"works"| C
  H -->|"fails"| O`} />

T8 asks you to build a missing piece. With Postgres stopped, a new link takes about 2 seconds to fail. A circuit breaker (a switch that stops asking a part that is known to be down) turns that wait into an instant error. You build it from the three states in the file.

<GoDeeper title="Go deeper: T8 directions">

The file is `your-turn/t8_db_breaker.py`. The class `BreakerStore` wraps a store and sends every call through `_guard`, which is empty. Predict first: Postgres is stopped and 20 people try to open uncached links. How long does the first one wait with a breaker, and how long the other 19? Which of the five store calls would you protect?

Build it from the three states written in the file's header, and run the tests after every small step.

```bash
uv run pytest labs/lab-1-url-shortener/your-turn -k t8
```

You want five tests, all green. The second test fails the first call for real and then expects 20 more to fail in well under a tenth of a second without touching the database again. There is an optional last step that edits the running system, so work on a branch if you try it: copy your finished file into the `shortener` package, wrap the store that `build_store` returns, rebuild, stop Postgres and time two requests for codes that do not exist. Undo it with `git restore` on the `system` folder. Hint: there are three things to remember between calls. Whether the breaker is open, when it opened and whether a test call is already out.

</GoDeeper>

## T9: a breaker that sends one scout

<MermaidDiagram title="One scout tests Redis" chart={`flowchart LR
  A["20 requests<br>at once"] --> S["One scout<br>tests Redis"]
  A --> K["The other 19<br>skip Redis"]`} />

T9 is the last build. When Redis is down, the cache already has a breaker, but once the cooldown ends every waiting request tries Redis at once. You change it so exactly one request tests Redis while the rest keep skipping it.

<GoDeeper title="Go deeper: T9 directions">

The file is `your-turn/t9_half_open_cache.py`, a copy of the real cache with its breaker. Predict first: Redis is down, the cooldown has just ended, and 20 requests arrive at the same moment. With the cache as it is, how many go and wait on Redis? How many should?

Change it so that, once the cooldown ends, exactly one request tests Redis while the rest keep skipping it. If the test works, everybody goes back to Redis. If it fails, the breaker opens again. Read all five tests first, because they say exactly what must hold, including for `set` and `ping`.

```bash
uv run pytest labs/lab-1-url-shortener/your-turn -k t9
```

You want five tests, all green, the first one counting how many calls reached Redis out of twenty. Hint: the tricky part is not the one scout itself, it is making sure the scout is released when it fails, when it succeeds and when something unexpected goes wrong.

</GoDeeper>
