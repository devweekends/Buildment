A run is a small experiment, and every red check is a result. This chapter reads the scenes one at a time. For each, it says what the board did, what a real stack of the same shape did when the same part was stopped, and what to change.

The real numbers come from a Docker stack run on a laptop: three API copies behind a gateway (the front door), Redis (a fast store that keeps data in memory), a worker and Postgres (the database). Read them as relative. The shape is real, and the milliseconds depend on the machine.

## Scene 2: an app server dies

<MermaidDiagram title="Losing one of three app servers" chart={`flowchart LR
  LB["Load balancer"] --> A1["App server"]
  LB --> A2["App server"]
  LB -.->|"stopped"| A3["App server"]`} />

One app server of three goes dark, and the load balancer sends its share to the others. Everyone is still served, and p99 rises from about 58 to about 77 ms. In the real stack, stopping one copy failed none of 4,344 redirects. The lesson is one spare machine (N+1): size the fleet so that losing one still leaves enough.

<GoDeeper title="Go deeper: the numbers behind scene 2">

On the board, three servers each carry 42% of their capacity. With one gone, the two left carry 63% each, and a busier part makes every request wait longer, which is why p99 rises. With only two servers to begin with, the one left would need to carry 125% of what it can, and about 80% of requests would be served.

In the real stack, stopping two of the three copies also failed none of 4,330 redirects, and p99 rose from 8.7 ms to 19.6 ms. The gateway tried another copy when one did not answer, and the copies kept nothing of their own, so any copy could serve any request. One spare machine is the rule from chapter 4.2 meeting a real failure. The extra server is not waste, it is the part that makes the death invisible.

When an app server dies, the load balancer is the same size as before, and its load does not change, so the board names the app server as the busiest part. If it named the load balancer, the balancer would have been too small before the failure, and "Serves the whole peak" would already be red.

</GoDeeper>

## Scene 3: the cache dies

<MermaidDiagram title="When the cache goes, the database finds out" chart={`flowchart LR
  APP["App servers<br>3,000 req/s"] -.->|"cache gone"| C["Cache"]
  APP -->|"all 3,000 req/s"| DB[("Database<br>primary and replica")]`} />

The cache answers 95% of redirects, so the database sees about 150 a second. When the cache dies, it sees all 3,000. With a read-only copy it rises to 62% busy and everyone is served. Without one it reaches 124%, and about a fifth of requests fail. A cache protects the database only while it is there.

<GoDeeper title="Go deeper: the numbers behind scene 3">

On the board, a database with one read-only copy rises from 3% to 62% busy, p99 goes from 58 to 71 ms, and everyone is still served. A database with no read-only copy goes to 124% busy, serves only 81% of requests, and p99 jumps to about 580 ms.

The real stack agrees on the shape. Stopping Redis failed no redirects, and cache hits fell from 100% to 15%. But the slowest redirects went from 8.7 ms to 252.7 ms, about 29 times slower, because every request now read the database. Nothing was wrong while the cache worked, which is why the failure is easy to miss.

A design that needs its cache to survive has a hidden dependency. It must also carry the full load without it, or the cache's death becomes the database's death. The read-only copy is the cheap way to buy that room, and the board charges you $0.30 an hour for it.

</GoDeeper>

<GoDeeper title="Go deeper: why the board is harsher than the real stack here">

The real stack still served every redirect with Redis stopped, slowly. It could do so because it asked the database one row at a time and the load on the laptop was small. At 3,000 requests a second against a database that serves about 2,400, the board shows what would happen at that scale: not slow, but unable to keep up, so some requests are not served at all. That is the same cliff as chapter 2.5, met from another side. Keep both pictures: at low load, the cache's death is only slow. Near the database's limit, it is an outage.

</GoDeeper>

## Scene 4: the worker dies

<MermaidDiagram title="The queue fills while the worker is away" chart={`flowchart LR
  APP["App server"] -->|"3,000 clicks/s"| Q["Queue<br>backlog grows"]
  Q -.->|"stopped"| W["Worker"]
  W --> DB[("Database")]`} />

Redirects do not notice a dead worker. The queue keeps each click. After 60 seconds at 3,000 clicks a second it holds 180,000, and the workers must clear them as well as the new clicks. Two workers take 100 seconds, three take 43, and one never catches up. A queue buys time only if the consumer has spare capacity.

<GoDeeper title="Go deeper: the numbers behind scene 4, and saving in groups (batching)">

Each worker of the board's default size handles 2,400 clicks a second. Two workers have 4,800 of capacity. They must handle the new 3,000 a second and the waiting clicks (the backlog), so they have 1,800 a second to spare, and 180,000 divided by 1,800 is 100 seconds. Three workers have 4,200 to spare and need 43 seconds. One worker has a capacity of 2,400, below the 3,000 arriving, so the waiting clicks never shrink.

In the real stack, the worker was stopped for 8 seconds. The queue of waiting clicks grew by about 495 clicks a second to 3,865, no redirect was affected, and about 4 seconds after the restart no clicks were waiting. All 7,377 clicks were counted. A worker that barely keeps up in normal times has no spare capacity to clear a build-up of waiting clicks, so size the workers for the arrival rate plus the rate at which you want to recover.

The worker's group size (batch size) decides how many writes the database sees. In the real stack the worker takes up to 500 clicks and writes them in one update. On the board, a batch size of 500 turns 3,000 clicks a second into about 6 database writes a second. At a batch size of 1 the database sees 3,000 writes a second and becomes the busiest part. Batching has a price: a click is counted a little later, and if the worker dies halfway through a batch, those clicks are counted again after the restart. The real worker acknowledges after it writes, so a click may be counted twice but is never lost.

</GoDeeper>

## Solution walkthrough

<MermaidDiagram title="From a failing run to the reference design" chart={`flowchart LR
  R["Run once"] --> S["Solution"]
  S --> P["Pick a part:<br>why, checks, without it"]
  S --> C["Compare with mine"]
  S --> K["Copy to my board"]`} />

After you press Run once, the Solution button opens the reference design on the same board. Pick any part to see why it is there, which checks it helps pass, and what fails without it. Compare with mine lists what differs from your design. Try first: a failing run you can explain teaches the most.

<GoDeeper title="Go deeper: how to use the solution well">

The solution is never locked behind a score, and nothing is recorded when you open it. Your own board stays untouched while you look: Back to my design returns to it, and Copy to my board asks before it replaces anything. The link labels in the solution show each hop on its own: reads going to the cache with the share the cache answers, the misses going on to the database, and the click writes counted separately.

A good way to use it is to compare after one more try. Fix the failure you understand, run again, and only then press Compare with mine. It lists parts, settings and links that differ, in words such as "lower" and "smaller", and names the failing checks each one helps explain. It does not print the reference's numbers.

The same design runs for real in the code lab (coming soon): a Docker stack with the same parts, where you stop each one yourself. The names of the parts and the checks match, so a design you built on the board can be replayed there.

</GoDeeper>

## The failure the board cannot show

<MermaidDiagram title="One Redis, two jobs" chart={`flowchart LR
  APP["API"] --> R["Redis<br>cache + click queue"]
  R --> W["Worker"]
  R -.->|"stopped: cache and clicks both gone"| X["Lost"]`} />

In the real stack one Redis plays both the cache and the click queue. Stopping it kept redirects working and lost about 42% of the clicks, and four more runs lost 52% to 59%. Two jobs that sound separate shared one failure. The board draws two boxes, so it is too kind. What would you change?

<GoDeeper title="Go deeper: four honest answers">

In the real run, only 4,106 of 7,055 clicks were counted while Redis was stopped. The design looked redundant on paper, and a single stopped container took out both jobs.

There are real answers. Run the queue on its own Redis, so the cache can die alone. Use a queue that stores events on disk. Accept the loss and say so, if a count that is off by a few percent is fine for a poster campaign. Or write the click to the database before answering and pay for it, which is the inline design from the board. Each answer costs something, and a good design says which cost it chose.

</GoDeeper>

<GoDeeper title="Go deeper: in an interview">

**In an interview.** Walk the failures in order. Say what you lose when each part stops, and what each choice costs. "If an app server dies, the others carry on, because I kept one spare machine and the servers hold no state. If the cache dies, the database takes the full load, so I sized it, with a read-only copy, to survive that. If the worker dies, clicks wait in the queue and drain after the restart, because the workers have spare capacity. And if my cache and queue share one Redis, a single failure loses both, so I would separate them, or I would say that I accept losing some clicks."

Interviewers like the last sentence most. They want to hear that you looked for the failure that two parts share, and that you can name what you would pay to remove it.

</GoDeeper>
