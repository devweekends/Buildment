```quiz
type: mcq
question: "A design has a cache at a 95% hit rate and a database with no read-only copy (read replica). At 3,000 requests a second the board shows it passing every check in the peak scene and failing both checks in the cache scene. What explains the difference?"
options:
  - "The cache is too small and drops data when it gets busy"
  - "The load balancer is the busiest part in the cache scene"
  - "Without a cache, the database sees all 3,000"
  - "The cache scene removes the app servers as well"
correct: 2
explanations:
  - "The cache's size is not the problem here. In the peak scene it works and the database is almost idle. The failure appears only when the cache is gone."
  - "The load balancer is not behind the cache. Its load is 3,000 requests a second in both scenes, so it cannot be what changed."
  - "Right. At a 95% hit rate the database sees about 150 requests a second. When the cache dies it sees all 3,000, which is more than one database without read-only copies can serve."
  - "The scene only takes the cache down. The app servers carry the same load as before, so they are not what fails."
```

```quiz
type: mcq
question: "The worker takes a click off the queue and writes it to the database. Clicks arrive at 3,000 a second. The worker stops for 60 seconds, then returns. Each worker handles 2,400 clicks a second. How many workers clear the waiting clicks (the backlog) within 120 seconds?"
options:
  - "One, because it is faster than most databases"
  - "Two, with 1,800 a second to spare"
  - "Three, because the board needs one per 1,000 clicks"
  - "None, because a queue clears itself on restart"
correct: 1
explanations:
  - "One worker handles 2,400 a second, below the 3,000 arriving. The waiting clicks never shrink, because new clicks come in faster than it clears them."
  - "Right. Two workers handle 4,800 a second. After 3,000 for new clicks, 1,800 a second are spare, and 180,000 divided by 1,800 is 100 seconds."
  - "There is no such rule. Three workers work too, and clear the waiting clicks in 43 seconds, but they cost more than the lab needs."
  - "A queue only holds clicks. Something must take them out, and it must do so faster than they arrive, or the waiting clicks stay."
```

```quiz
type: mcq
question: "A team runs its cache and its click queue on one Redis server. During a test they stop Redis. Redirects keep working from the database, but nearly half the clicks are never counted. What should they conclude?"
options:
  - "Redis is unreliable and should be replaced by a database"
  - "The click queue needs more workers to keep up with Redis"
  - "Two jobs that looked separate shared one point of failure"
  - "Counting clicks cannot be done without losing some"
correct: 2
explanations:
  - "Redis did what a stopped server does. The flaw is in the design that put two jobs on it, so swapping Redis for something else would not fix the sharing."
  - "Workers only take clicks out of the queue. The clicks were lost when the queue's server stopped, before any worker could take them."
  - "Right. The cache and the queue looked like two parts, and one failure took both. The fix is to separate them, store the queue on disk, or state that losing some clicks is acceptable."
  - "Counting can be made reliable, for example by writing each click to the database before answering. It costs more, and that is a design choice, not a law."
```

```quiz
type: mcq
question: "Wasla drops the queue and writes each click to the database before the redirect answers. At 3,000 redirects a second, a cache hit rate of 95% and a read-only copy, what happens to the database?"
options:
  - "Nothing changes, because the cache absorbs the clicks"
  - "The read-only copy takes half of the click writes"
  - "About 3,000 extra writes a second on the main copy"
  - "About 150 extra writes a second, one for each miss"
correct: 2
explanations:
  - "The cache answers reads. A click is a write, and every redirect makes one, whether or not it hit the cache."
  - "Read-only copies copy writes from the main copy and serve reads. They cannot take writes off the main copy."
  - "Right. Every redirect writes one click, so 3,000 a second land on the main copy. That is more than a medium database can take, which is why the design needs a far bigger database or a queue."
  - "Misses are about reads. The click is written on every redirect, hit or miss."
```
