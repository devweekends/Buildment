Someone sends you a short link in a chat. You tap it, and a page opens before you notice anything. Somewhere, a server looked up six letters and answered "go here". Now picture that server stopping at the exact moment you tap. What would you want to happen? Keep that question in mind. In this module you build the short-link service on a board, and then the board breaks it for you.

Wasla (a made-up link shortener from module 20) is in its first launch week. Shops are printing its links on posters. At the busiest moment, 3,000 people a second open a short link. That is far below the 100,000 a second of module 20, and it is the size where one wrong choice already shows.

## Three jobs a shortener must do

<MermaidDiagram title="What Wasla must do" chart={`flowchart LR
  U["Someone with a long address"] -->|"1. shorten"| S["Wasla"]
  S -->|"short link"| U
  V["Someone who taps the short link"] -->|"2. open it"| S
  S -->|"redirect to the long address"| V
  S -.->|"3. count the tap"| C[("Clicks per link")]`} />

Wasla must **shorten** (save a long address and give back a short code), **redirect** (answer a tap with the long address) and **count** each tap. These are the **functional** requirements: what the system does. On the board, each is a check that asks whether a request can travel from the client to the part that does the job.

<GoDeeper title="Go deeper: what the three checks look at">

The board does not run your code, because there is none. It looks at the links you drew. "Shortening works" is true when a request can travel from a client, through an app server, to a database that saves the link. "A redirect returns the long URL" is true when the app server can read that link back from the database. A cache in between is allowed, but it is optional, because a cache only remembers answers and never holds the truth.

"Clicks are counted" has two ways to pass. A click can travel from the app server to a queue, from the queue to a worker, and from the worker to the database. Or, when there is no queue at all, the app server writes the click to the database itself before it answers. That second way works. Module 20.4 explains what it costs, and the board lets you see that cost as load on the database.

If design cannot do one of the three jobs, nothing else about it matters, so these checks come first.

</GoDeeper>

## Eight ways to be good, or not

<MermaidDiagram title="One design, four scenes" chart={`flowchart LR
  A["1. Peak traffic<br>3,000 redirects a second"] --> B["2. An app server dies"]
  B --> C["3. The cache dies"]
  C --> D["4. The click worker dies"]`} />

A design that does the three jobs can still be slow, fall over when a machine dies, or cost too much. These are the **non-functional** requirements: how well the system does its jobs. The board measures eight of them, in four scenes, when you press Run.

| In this scene | The board measures | What a good design shows |
|---|---|---|
| Peak traffic | capacity, p99 latency, availability, cost | all 3,000 a second served, p99 under 65 ms, under a budget per hour |
| An app server dies | the share of requests still served | everyone is still served with one server fewer |
| The cache dies | the share served, and p99 | everyone is still served, and p99 stays under 100 ms |
| The click worker dies | clicks lost, and how long to catch up | no click is lost, and the backlog drains within two minutes |

<GoDeeper title="Go deeper: reading the table, and what to do before you open the board">

**p99** is the time that 99 out of 100 requests beat. It is the wait of the unlucky one in a hundred, and chapter 2.4 showed why that number matters more than the average. A **replica** here means one of several identical copies of a server, so that losing one does not stop the service.

When you press Run, the board plays all four scenes in order. In scene 2 one app server turns red. In scene 3 the cache goes dark and the database fills up. In scene 4 the worker stops, and clicks pile up in the queue. After the last scene, every check is listed as pass or fail, with the number the board measured, the number it needed, and the reason when it failed.

Before you open the board, look at the table and ask yourself one thing: which of these eight do you think a first, simple design would fail? There is no wrong guess. Writing it down makes the result more interesting.

</GoDeeper>

<GoDeeper title="Go deeper: where the numbers come from, and how far to trust them">

The board is a model, not a cloud. Each part has a capacity that comes from its size and count, and a request waits longer as a part gets busier (the queueing knee from chapter 2.5). Prices are illustrative. Latency is in model milliseconds, so compare one design with another on the board and do not compare the board with a stopwatch.

The targets were tuned so that a good design passes with a little room, and a design with one missing idea fails for one clear reason. The same targets were compared with what a real Docker stack of the same shape did on a laptop. In that stack, stopping one API replica failed no redirects, stopping the cache failed none but made the slowest redirects about 29 times slower, and stopping the worker for eight seconds lost no click. The board's numbers differ in size, and they agree in shape. The lab spec records every number and how it was tuned.

</GoDeeper>

## Quick check

```quiz
type: mcq
question: "A design redirects every link correctly, but the whole service stops when its single app server crashes. Which kind of requirement does it fail?"
options:
  - "A non-functional one, because it works but is not resilient"
  - "A functional one, because it did not redirect during the crash"
  - "Neither, because a crash is an operations problem"
  - "A functional one, because the app server holds the links"
correct: 0
explanations:
  - "Right. The design does its jobs while it is up. How well it keeps doing them when a part dies is a non-functional requirement: availability."
  - "Redirecting is the job, and the design does it. What fails is staying up when a part dies, which is a quality of the service, not a feature."
  - "A crash is exactly the kind of event a design must expect. Surviving one is a requirement the board tests on purpose."
  - "The app server answers requests but the links live in the database. Where data is kept is a design choice, not a kind of requirement."
```
