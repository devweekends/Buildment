```quiz
type: mcq
question: "A design has a seen-URL memory at a 95% hit rate. In the peak scene its URL table is almost idle, at about 4% busy. In the memory scene the table is 68% busy. What explains the difference?"
options:
  - "The memory is too small and drops data when it gets busy"
  - "The balancer is the busiest part in the memory scene"
  - "Without the memory, the table is asked every question"
  - "The memory scene removes the fetchers as well"
correct: 2
explanations:
  - "The memory's size is not the problem here. In the peak scene it works and the table is far from full. The failure appears only when the memory is gone."
  - "The balancer is not behind the memory. Its load is 2,700 jobs a second in both scenes, so it cannot be what changed."
  - "Right. With the memory, the table sees about 135 questions a second. Without it, it sees all 2,700, which is 68% of one small node."
  - "The scene only takes the memory down. The fetchers carry the same load as before, so they are not what fails."
```

```quiz
type: mcq
question: "Downloaded pages arrive at 2,700 a second. The parsers stop for 60 seconds, then return. Each parser handles 2,400 pages a second. How many parsers clear the waiting pages (the backlog) within 90 seconds?"
options:
  - "One, because parsing is cheaper than fetching"
  - "Two, with 2,100 a second to spare"
  - "Four, because the board needs one per 700 pages"
  - "None, because a queue clears itself on restart"
correct: 1
explanations:
  - "One parser handles 2,400 a second, below the 2,700 arriving. The waiting pages never shrink, because new pages come in faster than it clears them."
  - "Right. Two parsers handle 4,800 a second. After 2,700 for new pages, 2,100 a second are spare, and 162,000 divided by 2,100 is 78 seconds."
  - "There is no such rule. Three parsers work too, and clear the backlog in 36 seconds, but they cost more than the budget allows."
  - "A queue only holds pages. Something must take them out, and it must do so faster than they arrive, or the waiting pages stay."
```

```quiz
type: mcq
question: "A team runs two fetchers. Each handles 2,400 jobs a second, and the peak is 2,700. During a test one fetcher stops. About what share of the jobs is still fetched?"
options:
  - "About 50%, because half the fleet is gone"
  - "About 89%, because 2,400 of 2,700 fit"
  - "100%, because the balancer retries every job"
  - "0%, because the pages are lost with the fetcher"
correct: 1
explanations:
  - "Half the fleet is gone, but the fleet was sized well above the peak. What matters is what the one left can carry, not the share removed."
  - "Right. The fetcher left can do 2,400 jobs a second, and 2,700 arrive. 2,400 divided by 2,700 is about 89%. A third fetcher would make this 100%."
  - "A retry cannot create capacity. A fetcher at its limit still cannot take more jobs, so the extra ones wait or fail."
  - "A crashed fetcher loses only the jobs in flight, which the frontier lends out again. The jobs after it go to the fetcher that is left."
```

```quiz
type: mcq
question: "A design passes all eleven checks on the board. Yet a small online shop complains that DalilBot sent it 40 requests in one second. What should the team conclude?"
options:
  - "The board is broken, and its checks should be rerun"
  - "More fetchers would have prevented the extra requests"
  - "The board has no idea of a website, so it cannot see this"
  - "A bigger balancer would have spread the requests out"
correct: 2
explanations:
  - "The board did what it was built to do. It measures capacity, delay, survival and cost. The complaint is about something it never measured."
  - "More fetchers add capacity, and capacity is what lets more requests reach one site in a second. It makes this worse."
  - "Right. The model treats every job the same and has no website to count requests for. Politeness needs one queue per host and a wait between calls, as in chapter 26.3."
  - "A balancer spreads jobs over fetchers, not over websites. Two fetchers can still call the same site in the same second."
```
