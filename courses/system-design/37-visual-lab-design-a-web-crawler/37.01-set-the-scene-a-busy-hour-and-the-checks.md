You search for a recipe, and Dalil (the made-up search engine of module 26) answers in a blink. It can only answer with pages it has already read. A program called DalilBot reads them. Now picture DalilBot stopping at the busiest hour of its day, with thousands of pages half read. What would you want to happen? Keep that question in mind. In this module you build DalilBot on a board, and then the board breaks it for you.

In chapter 26.1 DalilBot had to fetch 2 billion pages a month. That is about 770 pages a second on average. The busiest hour is about 3.5 times busier: 2,700 pages a second. That is the load the board uses. It is small enough to run on a few machines, and big enough that one wrong choice already shows.

Before you read on, make a guess. A shop has one till. When it is half busy, a customer waits about a minute. When it is 90 percent busy, how long do you think a customer waits? Choose, and keep your guess in mind. The board will show you the answer with real numbers.

## Three jobs a crawler must do

<MermaidDiagram title="What DalilBot must do" chart={`flowchart LR
  S["Scheduler<br>releases a URL"] -->|"1. fetch"| F["Fetcher<br>downloads the page"]
  F -->|"2. save the page"| P[("Page storage")]
  F -->|"3. record the address"| T[("URL table")]
  F -.->|"4. send the links back"| S`} />

DalilBot must **fetch and save** each page, **record** every address it has fetched, and **send back** the links it finds as new work. These are the **functional** requirements: what the system does. On the board, each is a check that asks whether a request can travel from the client to the part that does the job.

<GoDeeper title="Go deeper: what the three checks look at, and who the client is">

A crawler has no users clicking. On the board, the **client** stands for the **scheduler**: the part that releases a URL (a web address) when its turn has come. Chapter 26.3 builds that scheduler, the URL frontier, with a wait for every website. The board does not model websites, so it treats every released URL as one more fetch job.

The board does not run code, because there is none. It looks at the links you draw. "Fetched pages are saved" is true when a request can travel from the client, through a fetcher, to object storage. "Each fetched address is recorded in the URL table" is true when the fetcher can reach the table that holds every address DalilBot knows. A memory in front of the table is allowed, but optional.

"Links found on a page come back as new work" is true when a link can travel from the fetcher, to a queue, to a parser (a worker that reads the page), and into the URL table. If a design cannot do one of the three jobs, nothing else about it matters, so these checks come first.

</GoDeeper>

## Eight ways to be good, or not

<MermaidDiagram title="One design, four scenes" chart={`flowchart LR
  A["1. Peak traffic<br>2,700 pages a second"] --> B["2. A fetcher dies"]
  B --> C["3. The seen-URL memory dies"]
  C --> D["4. The page parsers die"]`} />

A design that does the three jobs can still be slow, fall over when a machine dies, or cost too much. These are the **non-functional** requirements: how well the system does its jobs. The board measures eight of them, in four scenes, when you press Run.

| In this scene | The board measures | What a good design shows |
|---|---|---|
| Peak traffic | capacity, the slowest 1 in 100 fetch jobs (p99), staying up (availability), cost | all 2,700 a second fetched, the slowest 1 in 100 under 55 ms, under a budget per hour |
| A fetcher dies | the share of pages still fetched | everything is still fetched with one fetcher fewer |
| The seen-URL memory dies | the share fetched, and the slowest 1 in 100 | everything is still fetched, and the slowest 1 in 100 stays under 65 ms |
| The page parsers die | downloaded pages lost, and how long to catch up | no page is lost, and the waiting pages are all parsed within 90 seconds |

<GoDeeper title="Go deeper: reading the table, and what to do before you open the board">

The slowest 1 in 100 requests (**p99**) is the time that 99 out of 100 requests beat. It is the wait of the unlucky one in a hundred, and chapter 2.4 showed why that number matters more than the average. The **seen-URL memory** is a cache that remembers which addresses DalilBot has already fetched, so most "did we fetch this already?" questions never reach the URL table (chapter 26.4 builds a smarter version, the Bloom filter).

When you press Run, the board plays all four scenes in order. In scene 2 one fetcher turns red. In scene 3 the memory goes dark and the URL table fills up. In scene 4 the parsers stop, and downloaded pages pile up in the queue. After the last scene, every check is listed as pass or fail, with the number the board measured, the number it needed, and the reason when it failed.

Before you open the board, look at the table and ask yourself one thing: which of these eight do you think a first, simple design would fail? There is no wrong guess. Writing it down makes the result more interesting.

</GoDeeper>

<GoDeeper title="Go deeper: where the numbers come from, and how far to trust them">

The board is a model, not a cloud. Each part has a capacity that comes from its size and count, and a request waits longer as a part gets busier (the point where waiting climbs, called the utilisation knee in chapter 2.5). Prices are illustrative. Latency is in model milliseconds, so compare one design with another on the board and do not compare the board with a stopwatch.

Two numbers are worth knowing before you start. A crawler pays for every page it saves, so object storage is the largest bill on the board whatever you choose. And a fetcher on the board is counted by a generic machine rule, not by the 100 downloads it keeps in flight in chapter 26.2, so the board's fleet is smaller than that chapter's. Compare shapes, not machine counts.

There is no code lab for DalilBot yet (coming soon), so no number in this module comes from a real stack. Every number comes from the board's model, and the lab spec records how each target was tuned.

</GoDeeper>

  - "Fetching is the job, and the design does it. What fails is staying up when a part dies, which is a quality of the service, not a feature."
  - "A crash is exactly the kind of event a design must expect. Surviving one is a requirement the board tests on purpose."
  - "The fetcher downloads pages, but the pages are kept in object storage. Where data is kept is a design choice, not a kind of requirement."
