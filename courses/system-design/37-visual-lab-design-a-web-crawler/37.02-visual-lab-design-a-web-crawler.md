This page is the board and nothing else. Chapter 37.1 listed the eleven checks. Here you build a design, press Run, and watch it meet them. The board starts with the smallest design that works: a load balancer, one fetcher, a URL table and object storage. It already fetches, saves and records pages. It will not pass much more than that, and finding out why is the lab.

The board uses the same part names for every system, so here is what each one stands for in DalilBot.

| Board part | In DalilBot |
|---|---|
| Client | the scheduler that releases URLs |
| Load balancer | spreads fetch jobs over the fetchers |
| App server | a fetcher: downloads one page |
| Cache | the seen-URL memory |
| NoSQL store | the URL table |
| Queue | downloaded pages waiting to be parsed |
| Worker | a page parser |
| Object storage | the saved pages |

There is no single right answer. Many designs pass, and one that passes at $5.40 an hour beats one that passes at $7.

## How the board works

<MermaidDiagram title="The board, in four moves" chart={`flowchart LR
  P["Palette<br>on the left"] -->|"drag or tap"| B["Board<br>link the dots"]
  B -->|"hover a part, click Tune"| S["Settings cassette<br>beside the part"]
  B -->|"press Run"| R["Four scenes,<br>then every check"]`} />

The palette is on the left: drag a part onto the board, or tap it. Link two parts by dragging from a dot on one to a dot on another. Settings are not on the page until you ask: hover a part and click Tune on its corner, and a dark cassette opens beside it.

<GoDeeper title="Go deeper: the cassette, names, and what Run shows">

The board only allows links where requests really flow, and it tells you when a link is not allowed. The settings drawer holds the part's size, how many there are, which zones they live in, and any setting special to that part, such as a cache's hit rate or a worker's group size (batch size). On the worker, the board words the batch size as "clicks saved per trip"; for DalilBot it counts URL records saved per trip. Only one cassette is open at a time. On a phone it docks along the bottom, and you tap a part to show its Tune key. Press Escape or the close key to put it away. The Names switch in the header changes the parts to real AWS names and sizes, with a line on what each one means. The numbers do not change.

Press Run and the board plays four scenes. Dots travel along the links, a part turns amber and then red as it fills, and a part that dies is marked DOWN. When the scenes end, each check shows pass or fail, the number the board measured, the number it needed, and why a failed check failed. Press Show on any check to replay its scene on the board.

</GoDeeper>

## Build it on the board

<Lab slug="hld-visual-web-crawler" />

Run the starting design first, before you change anything. Read the failures in order. Each one names a part and a number, and each number points at a setting.

<GoDeeper title="Go deeper: reading a failure">

A failure has three lines. The first says what was measured and what was needed. The second says why, usually naming the busiest part and how busy it was. For example, "Load balancer is 169% busy, so it cannot serve the whole load" says that more fetch jobs arrive than that part can pass on, and every part behind it is starved. Fix the part named, run again, and a different part is usually the next one named. That is the loop of chapter 4.9: the busiest part on the path sets the ceiling, and you move the ceiling by raising one part at a time.

Two failures deserve a closer look. "Every page is still fetched when one fetcher dies" runs the scene with one fetcher fewer. A fleet of one has nothing left, so it fails at once. A fleet of two may serve only 88.8% if each fetcher cannot carry the whole load alone. And "No downloaded pages are lost when the parsers die" needs the pages to wait somewhere while the parsers are down, which is what a queue is for, and then needs the parsers to be fast enough, once back, to catch up on the waiting pages (the backlog) as well as the new pages.

</GoDeeper>

## Put a memory in front of the table

<MermaidDiagram title="Where 2,700 questions a second go" chart={`flowchart LR
  F["Fetchers<br>2,700 questions/s"] --> C["Seen-URL memory<br>95% hits"]
  F -->|"misses: about 135/s"| T[("URL table")]`} />

Before it downloads a page, a fetcher asks "did we fetch this already?". Link a cache from the fetcher, and also link the fetcher to the table. A hit never reaches the table, only misses go on. At 95% hits the table sees about 135 questions a second instead of 2,700, and p99 drops.

<GoDeeper title="Go deeper: the memory scene">

In scene 3 the memory goes dark and every question asks the URL table. With one small table node, that is 68% busy, and p99 rises from 52 to 62 ms. That is under the 65 ms limit for this scene, so a design with a memory passes it. A design with no memory has that 62 ms in every scene, and fails the 55 ms limit at peak. The memory is a speed-up, and the design must also carry the load without it. This is the cache-aside pattern of chapter 5.3.

You may also link the memory onward to the table, so the memory loads from it on a miss. The table gets the same load either way, but then the memory sits in the path and its death would cut the table off. The board is kind here, because the parsers keep the table reachable, so link the fetcher to both and you will not depend on its kindness. Chapter 26.4 replaces this simple memory with a Bloom filter that needs far less space.

</GoDeeper>

## Pages wait in a queue

<MermaidDiagram title="Two ways to handle a downloaded page" chart={`flowchart LR
  subgraph inline["No queue: the fetcher saves it"]
    A1["Fetcher"] --> S1[("Object storage")]
  end
  subgraph queued["Queue and parsers"]
    A2["Fetcher"] --> Q["Queue"] --> W["Parsers<br>batch of 500"] --> S2[("Storage and URL table")]
  end`} />

A fetcher could save the page and read its links itself. The board lets you, and shows the price: the fetcher is slower, and the links never reach the table. Or add a queue and a worker (the parser). The fetcher hands the page over and carries on. Try both, and compare the checks each time.

```predict
prompt: "You add a queue and a parser and link fetcher to queue to parser to URL table, but leave the parser's batch size at 1. At 2,700 pages a second, how many writes a second does the URL table receive from the parsers?"
options:
  - id: all
    label: "About 2,700, one for every page"
  - id: few
    label: "About 5, one for every 500 pages"
correctOptionId: all
explanation: "With a batch size of 1, the parser sends one write to the table for each page, so 2,700 a second. The queue only moved the writes out of the fetch. Raising the batch size to 500 makes the parser send one write for every 500 pages, about 5 a second. Batching is what protects the table."
allowRetry: true
```

<GoDeeper title="Go deeper: why the parsers sit behind a queue">

The board counts capacity, p99 and the share served only along the path a request waits on. Parsers behind a queue are off that path: if they are slow, the queue grows, and no fetch job waits. That is why a slow parser shows up in the "parsers die" check and not in p99. The fetchers are the part that must keep up with the scheduler, so they are the app server on the board, and their death is a scene of its own.

The parsers cost two more parts to run and pay for, and a short delay before a page is parsed. In return the fetchers never wait for parsing, and the pages survive a parser outage. This is the queue of chapter 15.2 doing its usual job, and the batch size groups many small writes into one trip.

</GoDeeper>

## Make it cheaper

<MermaidDiagram title="Pass first, then trim" chart={`flowchart LR
  G["All checks green"] --> T["Trim the part with spare room"]
  T --> R["Run again"]
  R -->|"a check turns red"| U["Undo that trim"]
  R -->|"still green"| T`} />

When every check is green, look at the cost. The budget is $5.60 an hour. Object storage alone is $3.90 of it, because every saved page is a paid request, and nothing you choose can lower that. Find the part with the most spare room, shrink it one step, and run again. If a check turns red, undo that step.

<GoDeeper title="Go deeper: stuck? One design that passes">

One design that passes all eleven checks: a load balancer of size general-small in three zones. Three fetchers (app server) of size compute-small in two zones. One seen-URL memory node (cache) of size memory-small at a 95% hit rate in two zones. A URL table (NoSQL store) of one memory-small node in two zones. A queue, and two parsers (worker) of size compute-small with a batch size of 500. Object storage. The fetcher links to the memory, the table and the queue. The queue links to the parsers. The parsers link to object storage and to the table.

The board reports a ceiling of 4,800 jobs a second, p99 near 52 ms, availability near 99.99% and about $5.50 an hour. The checks that depend most on one choice are the fetcher check, which needs a third fetcher, and the parser check, which needs a second parser. Try taking each away, and read what the board says.

</GoDeeper>
