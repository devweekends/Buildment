A run is a small experiment, and every red check is a result. This chapter reads the scenes one at a time. For each, it says what the board did, what the numbers mean, and what to change.

Every number here comes from the board's model, run on the reference design of chapter 37.2. There is no code lab for DalilBot yet, so nothing here is a measurement from a real stack. Read the numbers as shapes: how much worse, and why.

## Scene 2: a fetcher dies

<MermaidDiagram title="Losing one of three fetchers" chart={`flowchart LR
  LB["Load balancer"] --> F1["Fetcher"]
  LB --> F2["Fetcher"]
  LB -.->|"stopped"| F3["Fetcher"]`} />

One fetcher of three goes dark, and the balancer sends its share to the others. Everyone is still served, and the fetchers go from 38% busy to 56% busy. In chapter 26.2 a crashed fetcher loses nothing, because the frontier lends each URL for a while and takes it back. The lesson here is one spare machine (N+1).

<GoDeeper title="Go deeper: the numbers behind scene 2">

On the board, three fetchers each carry 38% of their capacity at 2,700 jobs a second. With one gone, the two left carry 56% each, and a busier part makes every request wait longer, so p99 rises from 52 to 65 ms. That is allowed in this scene, because the check only asks that everyone is served.

With only two fetchers to begin with, the one left would need to carry 113% of what it can. The model reads this as 2,400 of 2,700 jobs served, 88.8%, and the check fails. The extra fetcher is not waste, it is the part that makes the death invisible. When a fetcher dies the load balancer is the same size as before and its load does not change, so the board names the fetcher as the busiest part. If it named the balancer, the balancer would have been too small before the failure, and "Fetches the whole peak" would already be red.

</GoDeeper>

## Scene 3: the memory dies

<MermaidDiagram title="When the memory goes, the table finds out" chart={`flowchart LR
  F["Fetchers<br>2,700 questions/s"] -.->|"memory gone"| C["Seen-URL memory"]
  F -->|"all 2,700/s"| T[("URL table")]`} />

The memory answers 95% of questions, so the table sees about 135 a second. When the memory dies, it sees all 2,700, and goes from 4% to 68% busy. One table node copes, but with little to spare. A memory protects the table only while it is there.

<GoDeeper title="Go deeper: the numbers behind scene 3, and the batch size">

On the board, the table rises from 4% to 68% busy and p99 goes from 52 to 62 ms. Everyone is still served. That passes both memory checks, with 3 ms to spare on the p99 limit. A table that was also taking 2,700 writes a second from the parsers (a batch size of 1) would be at 71% busy even with the memory working, and at 135% when it stops: 74.0% served and a p99 of 380 ms.

So the memory and the batch size protect the same part. A design that needs its memory to survive has a hidden dependency. It must also carry the full load without it, or the memory's death becomes the table's death. A second table node is the other way to buy room, and the board charges you $0.15 an hour for it. Chapter 26.4 shows the real memory, a Bloom filter, and what a false "yes" costs: a new page that is skipped.

</GoDeeper>

## Scene 4: the parsers die

<MermaidDiagram title="The queue fills while the parsers are away" chart={`flowchart LR
  F["Fetchers"] -->|"2,700 pages/s"| Q["Queue<br>backlog grows"]
  Q -.->|"stopped"| W["Parsers"]
  W --> T[("URL table and storage")]`} />

Fetching does not notice a dead parser. The queue keeps each downloaded page. After 60 seconds at 2,700 pages a second it holds 162,000, and the parsers must clear them as well as the new pages. Two parsers take 78 seconds, three take 36, and one never catches up. A queue buys time only if the consumer has spare capacity.

<GoDeeper title="Go deeper: the numbers behind scene 4, and saving in groups (batching)">

Each parser of the board's default size handles 2,400 pages a second. Two parsers have 4,800 of capacity. They must handle the new 2,700 a second and the waiting pages (the backlog), so they have 2,100 a second to spare, and 162,000 divided by 2,100 is 78 seconds. Three parsers have 4,500 to spare and need 36 seconds. One parser has a capacity of 2,400, below the 2,700 arriving, so the waiting pages never shrink. The limit for this check is 90 seconds, which a third parser would beat by a wide margin and the budget would not allow.

A parser that barely keeps up in normal times has no spare capacity to clear a build-up. Size the parsers for the arrival rate plus the rate at which you want to recover. The group size (batch size) decides how many writes the URL table sees: 500 turns 2,700 a second into about 5. Batching has a price: a page is parsed a little later, and if a parser dies halfway through a group, those pages are parsed again after the restart. That is harmless here, because fetching and parsing a page twice costs only a little time (chapter 26.2).

</GoDeeper>

## Solution walkthrough

<MermaidDiagram title="From a failing run to the reference design" chart={`flowchart LR
  R["Run once"] --> S["Solution"]
  S --> P["Pick a part:<br>why, checks, without it"]
  S --> C["Compare with mine"]
  S --> K["Copy to my board"]`} />

After you press Run once, the Solution button opens the reference design on the same board. Pick any part to see why it is there, which checks it helps pass, and what fails without it. Compare with mine lists what differs from your design. Try first: a failing run you can explain teaches the most.

<GoDeeper title="Go deeper: how to use the solution well">

The solution is never locked behind a score, and nothing is recorded when you open it. Your own board stays untouched while you look: Back to my design returns to it, and Copy to my board asks before it replaces anything. The link labels in the solution show each hop on its own: questions going to the memory with the share it answers, the misses going on to the table, and the parsers' grouped writes.

A good way to use it is to compare after one more try. Fix the failure you understand, run again, and only then press Compare with mine. It lists parts, settings and links that differ, in words such as "lower" and "smaller", and names the failing checks each one helps explain. It does not print the reference's numbers.

The same design will run for real in the code lab for DalilBot. It does not exist yet (coming soon). Until it does, no number in this module comes from a real stack, and the board's own numbers are the only ones to trust.

</GoDeeper>

## What the board cannot show

<MermaidDiagram title="Two sites, one fetcher, one rule" chart={`flowchart LR
  F["Fetcher"] -->|"1 request a second"| A["Small shop site"]
  F -->|"too many at once"| B["Another small site"]
  B -.->|"blocks DalilBot"| F`} />

A design can pass all eleven checks and still be rude. The board has no idea of a website, so it cannot see DalilBot send a small site 50 requests in one second, which gets DalilBot blocked. It cannot show crawler traps either. What would you check next?

<GoDeeper title="Go deeper: what is missing, and what you would change">

**Politeness.** Chapter 26.3 sets one request a second to each site. At 770 pages a second that needs about 770 different sites ready at the same moment, and a frontier with one queue for each host. The board treats every fetch job as the same, so it cannot tell a spread over 2,700 sites from 2,700 jobs on one. To check politeness you need a count of requests per host, over time.

**Crawler traps and duplicates.** A calendar page that links to the next day for ever (chapter 26.4) fills the queue with endless work, and the board would just call it load. A budget of pages for each site, and a check that a fetch has not seen the same body, are the defences. The board's model has no page content to compare.

**Link volume.** The board asks the seen-URL memory one question for each page. In chapter 26.1 a page has about 50 links, so the real question rate is about 50 times higher, and the memory's job is bigger than it looks here. A real check would need a higher offered load for the memory alone.

**robots.txt and revisits.** Reading each site's rules, and visiting a page again when it is stale, need state that the model does not have.

</GoDeeper>

<GoDeeper title="Go deeper: in an interview">

**In an interview.** Walk the failures in order. Say what you lose when each part stops, and what each choice costs. "If a fetcher dies, the others carry on, because I kept one spare machine and the fetchers hold no state. If the seen-URL memory dies, the URL table takes the full question rate, so I sized it to survive that. If the parsers die, downloaded pages wait in the queue and drain after the restart, because the parsers have spare capacity. And I have not shown that the crawler stays polite. For that I would count requests for each website, because no capacity number can tell me."

Interviewers like the last sentence most. They want to hear that you know which failure your numbers cannot see, and what you would measure to find it.

</GoDeeper>
