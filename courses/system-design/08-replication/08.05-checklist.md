## Replication checklist

- [ ] I can explain why a successful write can be absent from a replica read.
- [ ] I can distinguish read-your-writes from monotonic reads.
- [ ] I can trace which replica position is safe for a client's next read.
- [ ] I can name a cost of leader reads, sticky replicas, and position tokens.

## Learning log

1. Which refresh in Amna's story violated the promise that she sees her own write, and what information would the router need to prevent it?
2. If replica A has reached log position 42 and replica B has reached 39, where can a client with required position 41 safely read?
3. Which routing rule would you choose for a read-heavy forum, and what failure mode or operating cost would you monitor?

## Your design note

Write a short rule that another engineer could implement. Name the token or session state it needs, the comparison it makes, and its fallback when no replica is caught up. Include one test in which a user writes, then refreshes through a lagging replica. Explain the result your rule must produce. A decision is complete when it covers the user-visible promise and the cost of keeping it.

modelAnswer: "After a confirmed write, store its log position in the user's session. Send the next read only to a replica whose applied position is at least that value. The cost is more leader traffic during lag spikes and extra session state."
