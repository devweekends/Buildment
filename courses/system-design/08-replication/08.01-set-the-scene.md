## A message that vanishes

Imagine a forum with one database leader and two read replicas. Amna posts a message about her study group. The leader saves it and returns success. Her first refresh goes to replica A, which has already received the write, so the message appears. Her second refresh goes to replica B, which is still behind, so the message disappears. A later refresh goes back to A and the message returns.

The application did not delete anything. Each replica is answering honestly from its own current state. The problem is that the router sent one user's successive reads to copies at different points in the write history.

In this short lab you will inspect that failure and choose a routing rule. The next lesson contains a live simulation and three possible fixes. You do not need the rest of the planned system design curriculum to work through this example.

## Draw the path

Sketch four boxes: Amna's app, the leader, replica A and replica B. Draw a solid arrow for the post to the leader. Draw separate arrows from the leader to the two replicas. Label them "later" because the leader can acknowledge the post before either replica catches up. Finally draw two refresh arrows, one to A and one to B.

That picture gives you a useful question for every replicated read path: what does the client know about the last write it saw, and how does the router use that knowledge? A router that picks any replica at random has no answer. A router that checks a position token can compare the client's required position with a replica's applied position. It can wait, pick another copy, or fall back to the leader.

## Before the simulation

Write down which promise Amna expects after posting: should her own next read show her message, even if other users have to wait a little longer? Then decide whether routing every read to the leader is acceptable for a forum with many more reads than writes. Keep your answer. The simulation in the next lesson will show the correctness and load costs of several choices.
