You type "red running shoes" into a shop's search box. Before you finish the last word, a list of ideas drops down. You tap one, and products appear. Now picture one search machine stopping at the exact moment you tap. What would you want to happen? Keep that question in mind. In this module you build the search box on a board, and then the board breaks it for you.

Dalil (a made-up marketplace search box from module 23) is having its first sale night. Shoppers type, tap and search. At the same time, sellers are changing prices as fast as they can, and each change must reach the search index (the lookup table from words to products). At the busiest moment, 2,000 lookups a second arrive, and about as many product changes. That is far below the 7,000 searches and 35,000 suggestion calls a second of module 23, and it is the size where one wrong choice already shows.

## Four jobs a search box must do

<MermaidDiagram title="What Dalil must do" chart={`flowchart LR
  U["Shopper"] -->|"1. search"| S["Dalil"]
  S -->|"products, best first"| U
  U -->|"2. suggest while typing"| S
  S -.->|"3. show full product details"| D[("Product database")]
  V["Seller"] -->|"4. change a product"| S
  S -.->|"the change reaches the index"| X[("Search index")]`} />

Dalil must **search** (find products for the words), **suggest** (offer ideas while the shopper types), **show details** (read the product from the database) and **index changes** (make a seller's change searchable). These are the **functional** requirements: what the system does. On the board, each is a check that asks whether a request can travel from the client to the part that does the job.

<GoDeeper title="Go deeper: what the four checks look at">

The board does not run your code, because there is none. It looks at the links you drew. "A search returns products" is true when a request can travel from a client, through an app server, to a search node (one machine that holds a copy of the index, the part of chapter 23.2 that finds products from words). "A suggestion is served" is true when the app server can reach a cache, because suggestions are answered from memory, as chapter 23.3 explains. "Results show full product details" is true when the app server can read the product from the database.

"A product change reaches the index" needs a longer chain: app server to queue, queue to worker, worker to search node. The queue holds each change until a worker takes it, so the seller's save never waits for the index. There is no shortcut here. A design with no queue cannot pass this check, because nothing updates the index.

If a design cannot do one of the four jobs, nothing else about it matters, so these checks come first.

</GoDeeper>

## Eight ways to be good, or not

<MermaidDiagram title="One design, four scenes" chart={`flowchart LR
  A["1. Peak traffic<br>2,000 lookups a second"] --> B["2. An app server dies"]
  B --> C["3. A search node dies"]
  C --> D["4. The indexing worker dies"]`} />

A design that does the four jobs can still be slow, fall over when a machine dies, or cost too much. These are the **non-functional** requirements: how well the system does its jobs. The board measures eight of them, in four scenes, when you press Run.

| In this scene | The board measures | What a good design shows |
|---|---|---|
| Peak traffic | capacity, the slowest 1 in 100 requests (p99), staying up (availability), cost | all 2,000 a second served, the slowest 1 in 100 under 130 ms, under a budget per hour |
| An app server dies | the share of requests still served | everyone is still served with one server fewer |
| A search node dies | the share served, and the slowest 1 in 100 | everyone is still served, and the slowest 1 in 100 stays under 160 ms |
| The indexing worker dies | product changes lost, and how long to catch up | no change is lost, and the backlog is indexed within 30 seconds |

<GoDeeper title="Go deeper: reading the table, and what to do before you open the board">

The slowest 1 in 100 requests (**p99**) is the time that 99 out of 100 requests beat. It is the wait of the unlucky one in a hundred, and chapter 2.4 showed why that number matters more than the average. A **replica** is one of several identical copies of a machine, so that losing one does not stop the service. In a search index, a copy of the index on another machine is also a replica, and chapter 23.2 uses copies to share load.

The 30 seconds in the last row comes from chapter 23.1: a product that a seller adds or edits must be searchable within 30 seconds. The board turns that promise into a test. The worker stops for 30 seconds, comes back, and must clear the waiting changes within 30 more.

When you press Run, the board plays all four scenes in order. In scene 2 one app server turns red. In scene 3 one search node goes dark and the others fill up. In scene 4 the worker stops, and changes pile up in the queue. After the last scene, every check is listed as pass or fail, with the number the board measured, the number it needed, and the reason when it failed.

Before you open the board, look at the table and ask yourself one thing: which of these eight do you think a first, simple design would fail? There is no wrong guess. Writing it down makes the result more interesting.

</GoDeeper>

<GoDeeper title="Go deeper: where the numbers come from, and how far to trust them">

The board is a model, not a cloud and not a search engine. Each part has a capacity that comes from its size and count, and a request waits longer as a part gets busier (the point where waiting climbs, called the utilisation knee in chapter 2.5). Prices are illustrative. Latency is in model milliseconds, so compare one design with another on the board and do not compare the board with a stopwatch.

The board also has a story to tell about load. In module 23, Dalil gets about 58 product changes a second for 7,000 searches. The board sends the same load down every branch, so it cannot make changes rare. It uses a sale night instead, with sellers re-pricing so fast that changes arrive as fast as lookups. Read 2,000 changes a second as a story. The idea behind it is real: indexing competes with searching for the same machines.

There is no code lab for Dalil yet. The targets were tuned on the model alone, so nothing here was compared with a real stack. The lab spec records every number and how it was tuned.

</GoDeeper>

  - "A functional one, because it did not search during the restart"
  - "Neither, because a restart is an operations problem"

explanations:
  - "Right. The design does its jobs while it is up. How well it keeps doing them when a part dies is a non-functional requirement: availability."
  - "Searching is the job, and the design does it. What fails is staying up when a part dies, which is a quality of the service, not a feature."
  - "A restart is exactly the kind of event a design must expect. Surviving one is a requirement the board tests on purpose."
  - "Where data is kept is a design choice, not a kind of requirement. The index holds the words and the database holds the products."
