Chapter 20.4 followed one redirect through Wasla's cache. Now you build the whole read path for peak hour: 100,000 redirects a second. The load balancers and app servers are already sized for it. The database is not, and no database size on its own can be. In this lab you add the part that changes that, and size it so every target passes.

The targets are 100,000 redirects a second, p99 under 200 ms, 99.9% available, and under $17 an hour. The board scores each one as you change the design. Many designs pass. Look for one that passes with money to spare, and be ready to say which number forced each choice.

## The brief: the database is the wall

<MermaidDiagram title="Wasla's read path before the cache" chart={`flowchart LR
  U["Clicks<br>100,000 req/s"] --> LB["3 load balancers<br>extra-large, 3 zones"]
  LB --> APP["50 app servers<br>2 zones"]
  APP --> DB[("Links store<br>1 primary with a standby")]
  T["Targets: 100,000 req/s, p99 under 200 ms,<br>99.9% available, under $17 an hour"]`} />

Every redirect reads one tiny row from the links store. The front of the design can take 100,000 requests a second, but one database serves only about 2,400. The board starts with a ceiling of 2,424 and a p99 near 700 ms. The fix is not a bigger database. It is fewer trips to it.

<GoDeeper title="Go deeper: why no database size is enough">

The links store in this lab is a memory-optimised database with a standby in a second zone. At the default size it serves about 2,400 requests a second. The largest size serves about 9,600. Read replicas add more, but even the largest primary with five replicas stays far short of 100,000 reads a second, and it costs more than the whole budget.

That is the same conclusion as chapter 20.4: Wasla's read path is almost all reads of a few hot rows, and almost every read asks for something that was asked for a moment ago. A cache keeps those answers in memory. It answers in a fraction of the time and serves many times more requests per CPU than a database, because it does not parse queries, plan them or read from disk.

The write path is different. A new short link is written once, and Wasla makes far fewer links than it serves redirects. The database is the right home for the links; it just should not be on the path of every click.

</GoDeeper>

## Build it on the board

<Lab slug="hld-m20-wasla-redirects" />

Drag a cache onto the board and link it from the app servers. Click it to set its nodes and hit rate. With cache-aside, a hit never reaches the database; only misses go on. Then check the database again, because it still has a job to do.

<GoDeeper title="Go deeper: how the board treats a cache">

When an app server links to both a cache and a database, the board sends every request to the cache first. A share equal to the hit rate is answered there. The rest, the misses, go on to the database. This is cache-aside from chapter 5.3: the app asks the cache, and on a miss it reads the database and stores the answer in the cache.

A cache node's capacity comes from its size, like any other part. At the default size one node serves about 30,000 requests a second, so 100,000 a second needs at least four nodes before you think about headroom. More nodes cost more per hour.

The board's cache is always warm. A real cache starts empty after a restart, and chapter 20.4's last beat showed what that does to the database. The lab leaves that out so you can see the steady state; your design still has to survive it in an interview.

The model's milliseconds are model units, not the 0.55 ms hit and 3.05 ms miss from chapter 20.4. Compare designs on the board with each other, not with that chapter's numbers.

</GoDeeper>

## The misses still reach the database

<MermaidDiagram title="Where 100,000 requests a second go" chart={`flowchart LR
  APP["App servers<br>100,000 req/s"] --> C["Cache<br>95% hits: 95,000 answered"]
  APP --> DB[("Links store<br>5% misses: 5,000 req/s")]
  DB -. "fix: read replicas or a bigger size" .-> DB`} />

At 95% hits, 5,000 requests a second still miss and go to the links store, about twice what it serves. Add read replicas or a bigger size, and p99 drops under 200 ms. Now raise the hit rate instead and watch how fast the database's load falls.

<GoDeeper title="Go deeper: hit rate against database size">

Each point of hit rate removes 1,000 requests a second from the database at this load. Going from 90% to 95% halves the misses, from 10,000 a second to 5,000. Going from 95% to 99% cuts them five times more, to 1,000. That is why chapter 20.4 cared so much about the last few points of hit rate: near the top, each point is worth a lot of database.

A hit rate is not a dial in a real system, though. It comes from how much memory the cache has, how many distinct links people click, and how long entries live. You raise it by adding memory or by keeping hot entries longer, and both cost something. The lab lets you set it directly so you can feel its effect; in an interview, say what would make it true.

One design that passes level 1: four cache nodes at 95% hits, and the links store with two read replicas. The board reports a ceiling of about 115,000 requests a second, p99 near 170 ms and about $15 an hour.

</GoDeeper>

## Count the cache nodes too

<MermaidDiagram title="A cache is a fleet as well" chart={`flowchart LR
  APP["100,000 req/s"] --> N1["Cache node<br>about 30,000"]
  APP --> N2["Cache node<br>about 30,000"]
  APP --> N3["Cache node<br>about 30,000"]
  APP --> N4["Cache node<br>about 30,000"]`} />

A cache is a fleet too. Three default nodes serve about 90,000 requests a second, so three nodes cap the whole design below the target even at a perfect hit rate. Add a fourth node, then check the cost. Spread the nodes over two zones, or one zone outage empties the cache.

<GoDeeper title="Go deeper: in an interview, and further reading">

**In an interview.** Say the numbers out loud: 100,000 reads a second, a hit rate, the misses that follow from it, and how many cache nodes and database replicas those need. Then say what happens when the cache restarts empty, from chapter 20.4: the database suddenly sees every request. Name your answer, such as warming the cache from a snapshot, letting only one request refill each missing key, or shedding load until the cache fills.

Interviewers often ask "what if one celebrity link gets a million clicks a second?" That is a hot key from chapter 5.6. One cache node holds that key, and it becomes the bottleneck however many nodes you have. Copies of the hot key on several nodes, or a small cache inside each app server, spread it out.
