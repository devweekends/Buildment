Back to Tala and Munir from 6.1. Their question, "which cache?", has a cousin that many teams ask: "which tool should store our metrics?" Assistants answer both with a default. This chapter checks each default against context, starting with the licence story and its dates. Every choice here is a real one, and every fact comes from a page that the projects publish.

## Redis licences by version

<MermaidDiagram title="Which licence goes with which version" chart={`flowchart TD
  A["Redis 7.2 and earlier: BSD 3-clause"] --> B["Redis 7.4 to 7.8: RSALv2 or SSPLv1"]
  B --> C["Redis 8 and later: RSALv2, SSPLv1 or AGPLv3"]
  A --> V["Valkey from 7.2.4: BSD 3-clause"]
`} legend="Licences by version, as Redis's licence page and the Linux Foundation state them (checked 2026-10-25)." />

Redis 7.2 and earlier use the BSD licence. Redis 7.4 to 7.8 use RSALv2 or SSPLv1: you can read the code, but the licences limit some uses. Redis 8 and later add AGPLv3 as a third option. Valkey continues from Redis 7.2.4 under BSD.

<GoDeeper title="Go deeper: the dates and what each licence limits">

On 2024-03-20, Redis announced that from Redis 7.4 it would be dual-licensed under RSALv2 or SSPLv1 and would no longer be BSD. The post says neither licence is approved by the <GlossaryTerm term="OSI" definition="The Open Source Initiative, a non-profit that keeps the definition of open source and approves licences that meet it." />. It says the change is not retroactive, and that the reason was cloud providers selling Redis [B29]. Redis's licence page says RSALv2 forbids commercialising the software or providing it to others as a managed service. It says SSPLv1 is copyleft and asks service providers to release the source of their management layer [B31].

On 2025-05-01, Redis added AGPLv3, which is OSI-approved, as a third option from Redis 8. The post by Redis's chief executive says the 2024 change hurt the company's relationship with the community, and that AWS and Google now maintain their own fork [B30]. Redis 8.0 also folded the modules that used to ship separately into the core: search, JSON, time series, five probabilistic data types and a preview of a vector set. Its release notes warn that access-control changes can break existing rules [B32].

The Linux Foundation announced Valkey on 2024-03-28 as an open source alternative, continuing from Redis 7.2.4 under BSD 3-clause [B34]. Valkey's first release, 7.2.5, was about compatibility and licence continuity. Valkey 8.0, released on 2024-09-16, says it makes no backward-incompatible change to command syntax or responses. It does change threading, which may need a check of your infrastructure [B35].

| Version | Licence | Source |
|---|---|---|
| Redis 7.2.x and earlier | BSD 3-clause | Redis licence page [B31] |
| Redis 7.4.x to 7.8.x | RSALv2 or SSPLv1 | Redis licence page [B31] |
| Redis 8 and later | RSALv2, SSPLv1 or AGPLv3 | Redis licence page and CEO post [B30, B31] |
| Valkey, from Redis 7.2.4 | BSD 3-clause | Linux Foundation, repository licence [B34] |

Versions move fast, so open the release page on the day you decide. This is a plain reading of public pages, not legal advice.

</GoDeeper>

| Pick | It wins when | Source |

Compatibility is a limit to state plainly. Valkey forked at Redis 7.2.4, so what Redis added after that, such as the Redis 8 modules and vector sets, is not a Valkey feature [B34, B32]. Check each client library and each command you use.

Managed prices change. AWS's ElastiCache pricing page lists Valkey 20% lower than Redis OSS for node-based clusters and 33% lower for serverless. Serverless Valkey has a 100 MB minimum (vendor pricing, checked 2026-10-25) [B38]. Google's Memorystore for Valkey supports Valkey 7.2, 8.0, 9.0 and 9.1 and describes itself as backed by open-source Valkey [B39].

Two other names come up in answers. Dragonfly claims much higher throughput and Redis API compatibility, which are vendor claims. It uses the Business Source License 1.1, with a change date of 2030-11-01 to Apache 2.0 [B42]. KeyDB is a BSD-3 fork of Redis focused on multithreading. Its README compares itself with Redis 6, an older line, though its repository still received commits on 2026-10-22 [B43].

Tala's answer is "either", and her team keeps the one it knows. Munir's answer is Valkey unless his customers need the Redis 8 types. In that case he reads the three Redis licences with his company's lawyer before he builds the product.

</GoDeeper>

## One Prometheus server is one node

<MermaidDiagram title="Past one Prometheus server" chart={`flowchart TD
  P["One Prometheus: local disk, not clustered or replicated"] --> Q{"Need more than one node?"}
  Q --> O1["Remote storage, for example Mimir"]
  Q --> O2["Thanos on top: high availability and long-term storage"]
  Q --> O3["VictoriaMetrics: another store with PromQL and MetricsQL"]
`} legend="Options named in the Prometheus, Thanos, Mimir and VictoriaMetrics documentation." />

Prometheus keeps metrics, which are numbers over time such as requests per minute, in a local database on one server. Its docs say this storage is not clustered or replicated, so treat it as a single-node database. For more than one node, add Mimir, Thanos or another store such as VictoriaMetrics.

<GoDeeper title="Go deeper: what each project says about itself">

Prometheus's documentation says its local storage is "not clustered or replicated", so it is not arbitrarily scalable or durable if a drive or node fails. It says that with proper design, years of data can be kept locally, and it recommends snapshots for backups [B17]. For longer storage and scale beyond one node, it offers remote write and read interfaces. It warns that those systems "vary greatly in durability, performance, and efficiency" [B18]. By default it keeps 15 days of data and uses about 1 to 2 bytes per sample on average. It does not support NFS, including AWS EFS, for local storage [B19]. Each server is standalone by design. It values staying up during an outage, and it is not a good fit when you need 100% accuracy, such as per-request billing [B20]. It graduated from the CNCF in 2018, the second project to do so after Kubernetes [B21].

VictoriaMetrics's single-node and cluster versions are released under Apache License 2.0 and support both PromQL and its own MetricsQL [B22]. The project describes MetricsQL as backwards-compatible with PromQL and says Grafana dashboards written for Prometheus should work the same, with some intentional differences [B23]. That is the vendor's description, so test your own queries. It also has a separate Enterprise edition. Its documentation lists <GlossaryTerm term="downsampling" definition="Keeping fewer, coarser data points for old data, to save space." />, multiple retentions, backup automation, mTLS, Kafka ingestion and anomaly detection as enterprise-only features [B24]. The cluster documentation recommends the single-node version below one million data points per second and says to "think twice" before choosing the cluster version [B25].

Thanos adds high availability and long-term storage on top of existing Prometheus servers, under Apache 2.0 [B27]. Grafana Mimir is a horizontally scalable, multi-tenant store for long-term Prometheus data, licensed AGPLv3. It claims scale to 1 billion active series, a vendor claim [B28].

</GoDeeper>

## Pick the metrics store

<InteractiveCanvas slug="metrics-store-context" />

Start with one server, weeks of data and no pain: Prometheus. Now keep data for years, then add a memory or disk problem. Then say you run several servers, and then that you need downsampling. Downsampling keeps coarser points for old data. Each change gives a different answer and a reason.

<GoDeeper title="Go deeper: when each metrics store wins">

This is the course's reading of the project documents checked on 2026-10-25. It is not a ranking, because no independent benchmark was found.

| Pick | It wins when |
|---|---|
| Prometheus | You want the default, widely documented choice; one server holds your series and your retention (weeks, or years with good disk planning); you want a simple standalone design that keeps working during an outage; your team already knows PromQL [B17 to B20] |
| VictoriaMetrics | Memory or disk cost on one node is the pain, you want long retention in one program, and you accept a project with an Enterprise edition. Test it on your own data first, because its savings are the vendor's claim [B22 to B26] |
| VictoriaMetrics Enterprise | You need an enterprise-only feature such as downsampling [B24] |
| Thanos or Mimir | You already run several Prometheus servers and need a global view, several tenants or object storage for retention, and you accept more parts to run. Check Mimir's AGPLv3 against your use [B18, B27, B28] |

The picture cannot tell you the exact saving on your data. Nothing we read does either. Measure with your own number of series and your own retention.

</GoDeeper>

## A speed claim needs your own test

<MermaidDiagram title="From a claim to a test of your own" chart={`flowchart TD
  A["VictoriaMetrics says: up to 7x less RAM"] --> V["The maker wrote the test"]
  B["Valkey project says: 1.19M requests a second"] --> V
  V --> M["Your data and sizes differ: measure"]
`} legend="Each number is a maker's own claim. It is a reason to run a test, not a result you can rely on." />

VictoriaMetrics says up to 7x less memory than Prometheus. The Valkey project reports 1.19 million requests a second against 360 thousand for its own older version, in one setup with one command. Redis claims up to 87% faster commands without stating conditions. Each is the maker's own test, so each is a reason to run yours.

<GoDeeper title="Go deeper: reading each claim">

| Claim | Who made it | What it compares and under what conditions |
|---|---|---|
| Up to 7x less RAM and up to 7x less storage than Prometheus, Thanos or Cortex; 10x less RAM than InfluxDB | VictoriaMetrics, in its README and docs [B26] | Benchmarks written by VictoriaMetrics' own staff. We could not fetch them and found no independent comparison |
| 1.19M against 360K requests a second | Valkey project blog, 2024-08-05 [B36] | Valkey with 8 I/O threads against Valkey 7.2, on an AWS c7g.16xlarge, 3M keys, 512-byte values, 650 clients, SET only |
| Gains such as up to 40% with pipelining | Valkey 9.0 post, 2025-10-21 [B37] | "Up to" figures; the page gives partial or no conditions |
| About 999.8K against 729.4K SET requests a second for Valkey 8.1.1 against Redis 8.0 | Momento, a company that sells a Valkey-based cache [B40] | A commercial claim: heavy tuning, synthetic 1 KB values, 6 I/O threads, c8g.2xlarge |
| Up to 87% faster commands and 2x throughput | Redis, CEO post [B30] | No conditions stated in the post |

Read a speed claim with five questions. Who made it, and do they sell something? What job did it run? Against what? On what machine and with what sizes? Did it say how many clients ran at once? None of these claims is independent. We found no neutral lab benchmark of Valkey against Redis 8, and none of VictoriaMetrics against Prometheus. Until you measure on your own value sizes, connection counts or series counts, speed should not decide your choice. Licence, hosting and the features you need can.

</GoDeeper>
