Qusai's team builds an ordering app for a school café. When a customer places an order, the app saves it in its database. It must also send an <GlossaryTerm term="event" definition="A short message saying that something happened, such as 'order 17 was placed'. Other programs read events and react to them." /> to a <GlossaryTerm term="message broker" definition="A service, such as Kafka, that receives events from one program and keeps them until other programs read them." /> so that a payment service can charge the customer. Two systems must both hear about one order.

## Two writes and no shared transaction

<MermaidDiagram title="One order, two systems" chart={`flowchart LR
  A["App"] -->|"1. save order"| D[("Database")]
  A -->|"2. publish event"| K["Kafka"]
  X["Crash between 1 and 2"] -.-> A
`} legend="A database transaction covers step 1. Kafka's own guarantees cover step 2. Nothing covers both." />

The app writes to two systems: its database and Kafka. A transaction, as in 6.3, covers only the database. Kafka's exactly-once guarantee covers reading, processing and writing inside Kafka, not your database. So a crash between the two writes can leave an order with no event, or an event with no order.

<GoDeeper title="Go deeper: the dual-write problem and its sources">

Chris Richardson, who documents this pattern, states the problem as: how do you atomically update the database and send messages to a message broker? He notes that two-phase commit, a way to make two systems agree, is often not available or not wanted. He adds that if the database commit happens, the message must be sent [B57]. Gunnar Morling of the Debezium project says there cannot be one shared transaction spanning a service's database and Kafka [B59]. Confluent calls this the dual-write problem: two external systems that must be updated atomically [B62].

Kafka's own documentation draws the same line. By default it guarantees at-least-once delivery. Its exactly-once guarantee covers a read, process and write cycle inside Kafka. For any other system, it says, exactly-once "generally requires cooperation with such systems" [B61]. So the sentence "Kafka transactions solve this" is wrong, because Kafka cannot include your database in its transaction.

</GoDeeper>

## The outbox: write the event with the order

<MermaidDiagram title="The outbox in five parts" chart={`flowchart TD
  A["App: one database transaction"] --> T["Orders table: the new order"]
  A --> O["Outbox table: a new event row"]
  R["Relay: a separate process"] -->|"reads unsent rows"| O
  R --> K["Publishes the event to Kafka"]
  R --> M["Marks the row as sent"]
`} legend="The order and its event row are saved together. The relay runs later, on its own." />

The app saves the order and an event row in one database transaction, so both are saved or neither. A separate relay later reads unsent rows, publishes them to Kafka and marks them sent. The relay can poll the table on a timer, or read the database log.

<GoDeeper title="Go deeper: relay choices and the table">

Richardson names two ways to run the relay. A polling publisher works with any SQL database, but publishing in the right order is tricky. Transaction log tailing needs no two-phase commit, but it is specific to each database and it is tricky to avoid duplicates [B58]. Debezium is a tool that reads the database log. Its outbox event router expects columns such as `id`, `aggregatetype`, `aggregateid`, `type` and `payload`. It treats the table as a queue, so updates are not allowed and deletes are filtered out. It uses `aggregateid` as the Kafka key, which keeps order within a partition, and it offers `id` for removing duplicates [B60].

| id | aggregatetype | aggregateid | type | payload |
|---|---|---|---|---|
| e-1001 | order | 17 | OrderPlaced | the order's details, as text |

With log reading, Debezium's example inserts and deletes the outbox row in the same transaction. Both entries stay in the log, so no separate cleanup job is needed [B59]. With a polling relay, you must delete old rows yourself. That is this course's reading, because no source we read states a retention rule.

</GoDeeper>

## Consumers must expect repeats

<MermaidDiagram title="Two safe paths and one trap" chart={`flowchart TD
  E["Event e-1001 arrives, maybe twice"] --> W{"Where does the effect happen?"}
  W -->|"in your database"| A["One transaction: record the id and do the effect"]
  W -->|"at a payment provider"| B["Send e-1001 as the provider's idempotency key"]
  E -.-> X["Trap: check, act, then record. A crash after the act repeats it"]
`} legend="The dotted box is the common mistake. It looks safe and has the same crash gap as the dual write." />

At-least-once delivery means an event can arrive twice. The consumer must be idempotent: a second copy changes nothing. Record the event id and do the effect in one database transaction. If a payment provider does the effect, pass it the id as an idempotency key, a unique id it uses to spot repeats. Check, act, then record leaves the same crash gap.

<GoDeeper title="Go deeper: why not remove the repeat at the source">

The relay can crash after publishing and before recording that it published, so it can publish twice. Richardson says plainly that the relay may publish a message more than once, so consumers must be idempotent [B57]. The Debezium blog suggests that consumers use the event id to detect duplicates [B59]. Kafka's documentation agrees that exactly-once beyond Kafka needs cooperation from the other system [B61].

Notice what this means for the payment service. If it charged the customer for each copy, the outbox would have turned a lost event into a double charge. The fix belongs at the consumer, where the money moves. An outbox gives at-least-once delivery, not exactly-once, so the phrase to remember is: at-least-once delivery, idempotent consumers.

Why does check, act, then record fail? The service looks up the id and finds nothing. It charges the customer, and then it crashes before it stores the id. The second copy arrives, the lookup finds nothing again, and the customer is charged twice. The gap that the outbox closed on the sending side opens again on the receiving side. Two ways close it. When the effect is a row in the service's own database, save the id and the effect in one transaction, so both happen or neither. When the effect happens in another system, send the event id with the request as an idempotency key. Many payment services accept such a key to recognise a repeat of the same request. Open your provider's own documentation, because this course did not look at any provider. These two fixes are the course's reading of the sources, which say that consumers must be idempotent and can use the event id.

</GoDeeper>

## What the outbox costs

<MermaidDiagram title="Direct publish and outbox side by side" chart={`flowchart LR
  D1["Save order"] --> D2["Publish"]
  O1["Save order and outbox row"] --> O2["Relay wakes later"] --> O3["Publish"] --> O4["Mark sent"]
`} legend="The outbox adds a table, a wait and two steps. Repeats and ordering come with them." />

The outbox adds an extra table and a relay process to run. Delivery is at least once, so consumers must cope with repeats. Polling relays find ordering tricky. Events leave after the commit, so they arrive a little later than a direct publish. Nothing we read gives a number for that delay.

<GoDeeper title="Go deeper: each cost and where it comes from">

| Cost | What it means | Source |
|---|---|---|
| An extra table and a relay | One more thing to build, run and watch | [B57, B60] |
| Repeats | The relay can publish twice; consumers must be idempotent | [B57, B59] |
| Ordering | A polling relay finds ordering tricky; with Debezium, order holds per `aggregateid` key within a partition | [B58, B60] |
| Cleanup | Polling needs a job to delete old rows; log reading with insert and delete needs none | [B59], the course's reading |
| A small delay | The event leaves after the commit, by another process | the course's reading |
| Transactional database only | The pattern needs a database with transactions | [B62] |

No source gives numbers for the delay or for how long to keep old rows. Measure both in your own system before you promise anything to a customer.

</GoDeeper>

## Decide: does the outbox pay here?

<InteractiveCanvas slug="outbox-or-not" />

Start where the outbox fits: the order and the event must both happen. Now say a lost event can be rebuilt. Then say your database has no transactions, and then that other services need every row change. Read the reason each time. The answer is a fit for the facts, not a rule for every app.

<GoDeeper title="Go deeper: when each way wins">

This is the course's reading of the sources in this chapter. Confluent's article lists the alternatives and their costs [B62].

| Way | It wins when | Its cost |
|---|---|---|
| Outbox | The change and the event must both happen or neither, such as an order and its `OrderPlaced` event [B57] | The costs in the last beat |
| Direct publish | The event can be lost or rebuilt, such as metrics or a cache refresh, or there is no message broker | A lost event stays lost |
| CDC | Other services need every row change from existing tables [B62] | A tool such as Debezium to run |
| Listen to yourself | The service can accept a lag: write to Kafka first and update your own database by reading from Kafka | The database becomes eventually consistent, so a read right after a command can show old state [B62] |
| Event sourcing | The state can be rebuilt from events, with Kafka as the source of truth, so the second write disappears | Events are never deleted, so history keeps growing [B62] |

In the outbox row, the `OrderPlaced` event is the one that starts payment or shipping. Confluent presents CDC as a way to run the outbox relay, not as a separate fix [B62].

"Always use the outbox" is not what the sources say. The line to remember is: use it when the change and the event must both happen or neither.

</GoDeeper>
