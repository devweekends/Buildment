Ayman builds a loan tool for his school library. He asked an assistant for the fastest database and got one name. Fastest at what? A database that counts a billion rows quickly can be slow at saving one order. So the honest answer starts with questions about the job: what does it read, what does it write, how many programs do it at once, and what can you pay? This chapter walks through those facts one at a time.

## Rows or columns: what the query reads

<MermaidDiagram title="One query, two shapes of storage" chart={`flowchart LR
  Q["Total of one column over many rows"] --> R["Row store: reads whole rows"]
  Q --> C["Column store: reads only that column"]
  R --> R2["Better for: save or read one order"]
  C --> C2["Better for: totals and reports"]
`} legend="The shapes suit different jobs. Neither is a faster version of the other." />

A row store such as PostgreSQL keeps each record together, which suits saving and reading whole records. A column store such as ClickHouse or DuckDB keeps each column together. For a total over many rows, it reads only the column it needs. Different jobs, different shapes.

<GoDeeper title="Go deeper: rows, columns and who says so">

The 2005 C-Store paper, by Stonebraker, Abadi and others, argues that a column store reads only the columns a query needs. It reports a sizeable advantage for warehouse queries that add up many rows, and it contrasts this with row stores built for writing [B44]. It was a prototype tested with preliminary data, so read it as the origin of the idea, not as a current ranking.

PostgreSQL's documentation shows the other shape. It stores each row in a fixed-size page with a small header. The header includes transaction ids, so it can keep old and new versions of a row [B45]. That is a design for reading and writing whole records safely.

ClickHouse's documentation lists four reasons it is fast for analytics. It skips data it does not need, using primary keys and skipping indexes. It compresses each column. It works on batches of values at once. It runs in parallel lanes that grow with the number of CPU cores [B46]. These are the vendor's docs, and the page names no job where it is a poor fit. DuckDB's documentation says it is designed for analytical workloads, runs inside the host program by default, and uses a columnar engine [B47].

An <GlossaryTerm term="analytical workload" definition="Questions that scan and add up many rows, such as 'how many clicks did each link get last month?'. The opposite is a transactional workload: many small saves and reads of single records." /> and a transactional one are different jobs. A <GlossaryTerm term="transaction" definition="A group of changes that are saved all together or not at all, so that a crash in the middle never leaves half of them." /> is what a shop needs when an order and its payment must both be saved or neither.

</GoDeeper>

<GoDeeper title="Go deeper: the rules behind the picker, and what it leaves out">

Every rule in the picker is the course's reading of a project's own documents, checked on 2026-10-25. They are not a ranking and not a benchmark.

| Job, writers, setup | Fits | Why, and where it comes from |
|---|---|---|
| Orders, one writer, inside the app | SQLite | In write-ahead mode, readers and a writer work at the same time, but there is only one writer at a time and all programs must be on the same machine. SQLite's own guidance says it suits low writer concurrency [B52, B53]. |
| Orders, otherwise | PostgreSQL | A row store with transactions on a server. SQLite's guidance says many programs sending SQL over a network, or many writers, point to a client and server database [B45, B53]. |
| Totals, small table | SQLite or PostgreSQL | The course's reading. The sources say column stores help when a query adds up many rows [B44] and give no row count where that starts. A row store you already run may do the job, so measure before you add an engine. |
| Totals, very large table, inside the app | DuckDB | Built for analytics, runs inside your program [B47]. The sources we read say nothing about many writers here, so the picker ignores that fact for totals. |
| Totals, very large table, on a server | ClickHouse | A column store whose docs say speed grows with CPU cores [B44, B46]. |
| A heavy stream of writes | LSM store | Cheap writes, costlier reads. See the next beat [B48, B49]. |

SQLite's guidance calls fewer than about 100,000 hits a day a conservative fit for a website [B53]. That is the project's own advice about itself, not a limit that applies to every app.

Two facts the picker folds into "setup" are cost facts. An engine that runs inside your program needs no separate server to pay for or run [B47, B53]. If a database sits idle most of the day, a hosted service that pauses it can cut idle cost. Neon's documentation says its compute suspends after 5 minutes of inactivity by default. You cannot change this on the Free plan. It wakes again within a few hundred milliseconds, and large computes, above 16 compute units, stay on [B54]. Those are the vendor's docs, so check your own plan and price before you call anything free.

When the rules do not settle your mix, the picker says so and suggests you test. That is honest. Try PostgreSQL and one rival with your own data.

</GoDeeper>

## Heavy writes trade away easy reads

<MermaidDiagram title="How an LSM store takes a write" chart={`flowchart TD
  W["Write arrives"] --> M["Memory table and a log on disk"]
  M --> F["Flushed to sorted files"]
  F --> K["Background merging (compaction)"]
  F --> RD["A read may check several files"]
`} legend="Writes are cheap because they only append. Reads and background merging pay for it." />

A write-optimised (LSM) store adds each write to a log and to memory, flushes sorted files, and merges them later in the background. Writes get cheap. A read may check several files, and the merging uses disk and processor time. So "LSM is faster" is a trade, not a rule.

<GoDeeper title="Go deeper: what the two projects say">

The RocksDB overview describes the path in the diagram. A write goes to an in-memory table and a sequential log. The table is flushed to sorted files, and background compaction merges the files. Level compaction favours a smaller disk footprint. Universal compaction gives lower <GlossaryTerm term="write amplification" definition="The same data being written to disk more than once, for example when background merging rewrites files." /> but uses more space and makes reads check more files [B48].

Apache Cassandra's documentation describes the same family: an append-only commit log, a memory table and immutable sorted files. It contrasts this with the traditional relational design based on B-trees, and it states the cost plainly: read performance and write amplification, partly offset by Bloom filters [B49].

For your own choice, ask how nonstop the writes are and how slow your reads may be. A bakery that saves 60 orders a day has no write stream. A sensor network that sends a reading every second from thousands of devices does.

</GoDeeper>

## More cores help some queries, not others

<MermaidDiagram title="When PostgreSQL can use more cores" chart={`flowchart TD
  Q["A PostgreSQL query"] --> W{"Does it write or lock rows?"}
  W -->|"yes"| S["No parallel plan"]
  W -->|"no"| B{"Scans a lot, returns few rows?"}
  B -->|"yes"| P["Workers can share the scan"]
  B -->|"no"| N["Often no gain from more cores"]
`} legend="From PostgreSQL's parallel query documentation. A setting must also allow workers." />

More cores do not speed everything up. PostgreSQL can split a query that scans a lot of data and returns few rows across several workers, if its setting allows. A query that writes data or locks rows gets no parallel plan. Many queries cannot use extra cores.

<GoDeeper title="Go deeper: one core or many in three systems">

PostgreSQL's documentation says parallel query suits queries that touch a lot of data and return few rows, and that many queries cannot benefit [B50]. A query that writes data or locks rows gets no parallel plan, with a few exceptions for commands that create and fill a table. The setting `max_parallel_workers_per_gather` must be above zero [B51]. The version in the sources was PostgreSQL 18.

Redis runs commands on one thread, and its benchmark page says to run several instances to use several cores [B41]. That page predates the I/O threads of newer versions in places. Redis 8 adds an I/O threads setting [B32]. The Valkey project says it moves reading, parsing and writing to I/O threads, while commands still run on one thread [B36]. So the plain statement is: commands run on one thread, and network work can use more.

ClickHouse's documentation says its parallel lanes grow with CPU cores [B46]. SQLite works the other way for writes: one writer at a time, however many cores you have [B52].

| System | What more cores do, per its own docs |
|---|---|
| PostgreSQL | Help large scans that return few rows; not queries that write |
| Redis and Valkey | Help network work with I/O threads; commands still run on one thread |
| ClickHouse | Help analytics queries, per the vendor's docs |
| SQLite | Do not add writers; there is one writer at a time |

</GoDeeper>

## A benchmark answers one question

<MermaidDiagram title="Three benchmarks, three jobs" chart={`flowchart LR
  CB["ClickBench: one flat table, 43 queries, one at a time"] --> J1["Job: scans and totals"]
  TC["TPC-C: five kinds of transaction at once"] --> J2["Job: order processing"]
  TH["TPC-H: ad-hoc questions plus data changes"] --> J3["Job: decision support"]
`} legend="A benchmark is only as useful as the match between its job and yours." />

ClickBench has one flat table of about 100 million rows and 43 queries, run one at a time. Its authors list those limits, and the ClickHouse team made it. TPC-C measures order processing with five kinds of transaction at once. TPC-H measures ad-hoc decision questions. A win on one says little about the others.

<GoDeeper title="Go deeper: reading a benchmark, and a better question">

ClickBench's page says the original runs used AWS c6a.4xlarge machines, with hot and cold runs. Its authors list their own limits. It uses a single flat table, small by modern standards. It mostly runs on one machine. Queries run one at a time, with no test of many users at once. It was created by the ClickHouse team [B55]. TPC-C is an on-line transaction processing benchmark with a mix of five concurrent transaction types. TPC-H is a decision-support benchmark of ad-hoc queries with concurrent data modifications [B56]. We did not review any published results, only what each benchmark measures.

None of this says a benchmark is useless. It says to read the claim: who ran it, what job it ran, how many things ran at once, and on what machine.

A better question to an assistant names the job. For example: "I run a bakery order app. One program saves about 60 orders a day on one small rented server, and I want a monthly sales total. Which database fits, what would change your answer, and which of its own pages should I read?" Then read those pages and write down the date. You practise exactly this in 6.6.

</GoDeeper>
