## One week of Qasir, saved two ways

<InteractiveCanvas slug="dump-or-story" />

Switch between the two histories, then tap a dot. Both hold the same work: 448 lines changed. In one, a reviewer sees what changed, in what order, and why. In the other, a single commit called "update" holds everything.

<GoDeeper title="Go deeper: reading the two histories">

Check the totals yourself. The six small commits add 42, 61, 38, 9, 176 and 84 lines, which is 410. They remove 0, 4, 0, 14, 12 and 8 lines, which is 38. Together that is 448 lines changed, the same as the single commit (410 plus 38). The small commits touch seven different files in all, so the single commit also lists seven files. Only the shape of the history differs.

Look at day 4. Yara found a bug by opening a link that did not exist: Qasir still added a click. Her fix is a small commit of 23 changed lines, and its message says what was wrong. Six months later, she or a reviewer can find that day in seconds. In the single commit, the same fix is one hidden change among 448 lines, and nothing says that a bug ever existed.

The small commits also show how she worked. She wrote a test on day 3, the day the count first worked. She wrote a README on day 7 that lists one known gap. A reviewer who sees these steps learns what she checks, and what she is honest about. A history is not human because it looks natural. It is human because the steps in it really happened.

</GoDeeper>

## What a good commit message says

<MermaidDiagram title="Parts of a commit message" chart={`flowchart TD
  M["Commit message"] --> L["Line 1: what changed, about 50 characters"]
  M --> B1["Blank line"]
  M --> B2["Body: why, in plain words"]
`} legend="The first line helps a reader scan a list. The body helps the reader who asks why." />

Pro Git, the Git project's book, advises a first line of about 50 characters or fewer, then a blank line, then a body that says why. It also advises the imperative: write "Fix bug", not "Fixed bug". Yara's day 4 message says what changed. Its body says why.

<GoDeeper title="Go deeper: a message with a body, and one convention">

Here is Yara's day 4 message in full. The first line is short enough to read in a list. The body is for the person who asks why.

```text
Fix: do not count clicks on links that do not exist

A request for a short code that is not in the database
was still adding a row to the clicks table. Check that
the link exists first, and add a test for a dead link.
```

The word "Fix:" at the start follows a convention called Conventional Commits. Its form is a type, an optional scope and a description, with types such as fix and feat. Tools can use those words to build a list of changes. It is one common convention, not a rule of Git. Some teams use others, and a team project may ask for its own style, so follow the project.

Messages stay in the history for good. Do not put a password, a key or someone's private message in one, for the reason chapter 4.5 gave about the log. If you must say what a secret was for, say that it was changed, and never say what it was.

</GoDeeper>

## Commit when one small thing works

<MermaidDiagram title="The small-step loop" chart={`flowchart TD
  A["Change one thing"] --> B["Run the test"]
  B --> C{"Does it work?"}
  C -->|"no"| A
  C -->|"yes"| D["Commit with a message"]
  D --> A
`} legend="One loop, repeated. A commit is the saved result of a loop that worked." />

Pro Git says each commit should be a logically separate change. Yara commits when one small thing works: a table, a count, a test, a fix. If a day's work mixes two things, Git can split it so each commit holds one. A weekend of five changes should not become one commit on Monday.

<GoDeeper title="Go deeper: splitting one day's work">

Sometimes you only notice at the end of an evening that you changed two things. Git has a way to choose which parts of a file go into a commit: the command `git add --patch`. It shows each changed piece and asks whether to include it. You commit the first thing, then the second.

Splitting costs a few minutes. It gives you a history in which every commit has one purpose, so a bug can be traced to one change. It also helps your own review. Looking through the pieces before you commit makes you read your own work once more, and you often find a leftover test line or a debugging print.

If a project asks you to keep commits small, a pull request with six commits is easier to review than one with a single huge commit. If you are working alone, nobody enforces this. The habit pays you back anyway, the first time you need to find which change broke a page.

</GoDeeper>

## A green graph is easy to fake

<MermaidDiagram title="Why the graph is weak proof" chart={`flowchart TD
  A["A commit says when it was written"] --> B["GitHub places it on that date"]
  B --> C["The author can set that date"]
  C --> D["Squares are weak proof of effort"]
  D --> E["Readers open the work behind them"]
`} legend="The graph shows the dates that commits claim. Readers check the work itself." />

GitHub's profile graph uses the date that each commit says it was written. Git lets the author set that date. So a green graph can be faked in one command, and people who hire you read the work behind it. Never backdate commits, script empty ones or buy activity. Let your history be true.

<GoDeeper title="Go deeper: what the graph counts, and what it misses">

The green squares on a profile are called a <GlossaryTerm term="contribution graph" definition="The grid of squares on a GitHub profile. A darker square means more commits on that day, by the dates the commits claim." />. GitHub puts each commit on its <GlossaryTerm term="author date" definition="The date and time a commit says it was written. The person who makes the commit can set it." />. A commit counts only if its email is linked to your account, if it is on the repository's default branch, and if the repository is not a fork. So a real week of work can leave a graph with few squares, for example when you commit on another branch.

That is one more reason not to treat the graph as a score. It can show too much, because dates can be set, and too little, because of how commits are counted. We give no way to change dates, because faking activity is against this course's rule, and GitHub's rules list automated inauthentic activity as a violation. We also found no source on whether employers can detect a faked history, so we do not claim that they can. The honest reason to avoid it is simpler: it is a false statement about your work.

The same rule covers every number you show. Do not buy stars or likes. Do not write "2,000 users" for twelve testers. Do not invent a metric to make a post look stronger. If it did not happen, do not show it.

</GoDeeper>

## A pull request can carry the story

<MermaidDiagram title="What a squash merge keeps" chart={`flowchart TD
  A["Pull request with 6 commits"] --> B["Squash and merge"]
  B --> C["One commit on main"]
  A --> D["Pull request page keeps its story"]
`} legend="After a squash merge, the pull request page holds the title, description and review comments." />

Some projects use <GlossaryTerm term="squash and merge" definition="A GitHub setting that combines all the commits of a pull request into one commit on the project's main branch." />. The small commits are not kept there. So the story lives in the pull request: its title, its description and the review comments. Write it there.

<GoDeeper title="Go deeper: what to write in a pull request">

GitHub says that squash and merge combines all commits of a pull request into one commit on the base branch. The intermediate commits are not preserved there as separate commits. It recommends the setting for one logical change with many small fixup commits. Repository settings decide which merge methods a project allows, so check the project's contributing page. Pull requests were introduced in chapter 7.5.

Do not promise yourself that your small commits will show on the main branch of a project like this. Keep making them anyway. They help your own review, your own debugging, and the reviewer who opens your branch before the merge.

A good pull request description is short. Say what changed and why. Say how you tested it, and what you are unsure about. If the project asks for it, add an AI-use line, as chapter 10.3 describes. A reviewer who reads this can ask a good question, and that is how trust is built in a team.

</GoDeeper>

## A gap in the graph is honest

<MermaidDiagram title="What Samir does with a gap" chart={`flowchart TD
  A["Two weeks of exams, no commits"] --> B{"Fill the gap?"}
  B -->|"with fake commits"| C["Dishonest, and against the rules"]
  B -->|"leave it"| D["Say why in a post or README"]
  D --> E["Next real step: commit when one thing works"]
`} legend="A gap is a true record. A filled gap is a false one." />

Samir's squares stop for two weeks of exams. A friend says he could fill the gap with commits dated to those days. He does not. He writes one line in his next post, then commits the next real step.

<GoDeeper title="Go deeper: a history that is human because it is true">

A history is human because its steps are real: a test added, a bug found, a small restructuring, a note about a mistake. No trick makes a history look natural, and none is needed. Samir's gap tells a reader something true: he had exams. A reader who sees a note about it trusts the rest of his history more, not less.

If you want a steady habit, make it small and real. Commit when one small thing works, even if that is once a week. A habit you can keep for months is worth more than a burst that you must fake to keep going.

In the practice chapter 10.7, you turn a week of your own commits into one post. Everything the post says must be true of that week, and a mentor can open the commits to check it.

</GoDeeper>
