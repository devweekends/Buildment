<GoDeeper title="Go deeper: the full story">

Hadi is a developer at a small fictional software agency. On a Monday, a client asks for one new feature: when a customer pays, the shop's website should make a PDF invoice. Hadi has not made PDFs from code before. He quotes two days, because the work looks small: one library, one template, one test.

He opens a chat assistant and types one line: "What is the best library to make PDF invoices in a Node app?" The answer arrives in about five seconds. It names a library called pdfwand and calls it the most popular choice, with a simple interface. It does not say when the library was last updated. Hadi has no reason to doubt it. The answer reads like advice from a colleague who has done this before, and the client wants the feature soon.

He builds the first version and calls it finished on day 2. On day 3 the client's test server moves to a newer version of Node, the program that runs the website's code. The build fails inside pdfwand. Hadi opens the library's own page for the first time. Its last release is four years old. Sixty-three problems that users reported are still open, and nobody has replied to the newest ones. A note from the person who started it says the library is no longer maintained.

Now Hadi must choose a different library and rebuild the invoice layout with it. The feature is truly finished on day 7. That is seven days instead of the two he quoted, so the answer cost five extra days, and the client's launch moves by a week. His manager does not blame him for the library. She asks one question: what did you check before you started? He had checked nothing, because the answer already sounded finished.

Nothing in this story says the assistant lied. The library may have been a good choice some years ago, and a popular name can stay popular long after people stop looking after it. The problem is the order of work. Hadi asked first, took the answer as a decision, and built on it. Chapter 5.2 shows what to read before you ask. Module 6 explains why assistants often give the popular answer.

</GoDeeper>

## Ten minutes he did not spend

One page would have shown the problem: the library's own page, with its last release date. In this example, reading it takes ten minutes. The fast route only looks shorter, because its cost arrives later. This module teaches the second route.

```openquestion
prompt: "Look at the story again. In everyday words, what could Hadi have done in his first hour, before he built anything, that would have shown him the problem? Write two or three sentences."
required: true
minWords: 25
allowSpeechInput: true
modelAnswer: "He could have opened the library's own page and looked at when it was last updated and whether anyone was still fixing problems. That takes about ten minutes and would have shown him that nobody had looked after it for four years. He could also have asked the assistant for two or three other libraries and compared them, instead of building on the first name he was given. Any answer that checks the library itself before building is a good one."
```

<GoDeeper title="Go deeper: key words">

| Word | Plain English |
|---|---|
| **First answer** | The answer an assistant gives before you have checked anything or given it your own facts |
| **Researched answer** | An answer you reached after reading the primary page, writing your own facts and checking what the assistants said |
| **Primary page** | The page a project or company publishes about itself: rules, docs, licence file or release notes |
| **Decision record** | One page showing how you decided: the question, the answers, the pages you read and your decision |
| **Maintained** | Still looked after by people who fix problems and publish new versions |

</GoDeeper>
