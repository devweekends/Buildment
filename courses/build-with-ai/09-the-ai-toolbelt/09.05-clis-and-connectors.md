Wisam is a freelancer who helps a print shop with its online ordering page, which lives in a GitHub repository. He wants an AI tool to read the open issues and draft replies, and the tool asks for access to everything.

## A command line talks to GitHub for you

<MermaidDiagram title="One command, three steps" chart={`flowchart TD
  Y["You type: gh issue list"] --> G["gh, GitHub's command-line tool"]
  G --> H["GitHub, using your token"]
  H --> L["The list appears in your terminal"]
`} legend="gh does what you do in the browser, but by typing. The token says what it may do." />

A <GlossaryTerm term="command-line tool" definition="A program you use by typing commands in a terminal. People often call it a CLI." /> does the jobs you do in the browser, by typing. GitHub's is called gh, and it is free. If you only have a phone, the browser does the same jobs. One command only reads. Four change GitHub, so know which is which before you press Enter.

<GoDeeper title="Go deeper: five gh commands">

These five commands cover most of a small project's needs. Run them in the terminal you met in chapter 4.1, inside a repository you own.

```bash
gh issue list
gh issue create --title "Add a sound at the end of a round" --body "Details here"
gh pr create --title "Add a Try it section" --body "What changed and why" --draft
gh pr comment 12 --body "Thanks, I fixed the typo."
gh pr review 12 --comment --body "The steps work on my phone."
```

The first command only reads. It shows 30 open issues by default, and it takes options such as `--state`, `--label`, `--limit` and `--json`. The other four change GitHub: they create an issue, open a pull request, add a comment and leave a review. `gh pr create` takes `--title`, `--body`, `--draft` and `--fill`. `gh pr review` takes exactly one of `--approve`, `--comment` and `--request-changes`.

`gh auth login` uses a browser by default and keeps your token in your computer's credential store, or in a plain text file if there is none. GitHub is for ages 13 and over. If gh does not work for you, do the same steps in the browser. The habit is the same: know what a command changes before you run it.

</GoDeeper>

## A token can be wide or narrow

<MermaidDiagram title="A wide token and a narrow token" chart={`flowchart TD
  W["Wide token: every repository, many permissions, no end date"] --> WR["A leak or a trick reaches everything"]
  N["Narrow token: one repository, what you need, an end date"] --> NR["A leak or a trick reaches little, for a short time"]
`} legend="Same tool, same task. How wide the token is decides how much a mistake can cost." />

A <GlossaryTerm term="personal access token" definition="A long secret code, created on GitHub, that lets a tool act as you with only the permissions you choose." /> can be wide or narrow. GitHub recommends the fine-grained kind. It can be limited to chosen repositories and to separate permissions, some of them read-only. Always add an expiry date.

<GoDeeper title="Go deeper: making a narrow token">

In the browser, open your GitHub settings, then the developer settings, then personal access tokens, then fine-grained tokens. Menu names change, so read GitHub's own page. Choose your account as the owner. Choose "only select repositories" and pick one. Set permissions one by one: for reading issues, read access to issues is enough. Add pull request write access only on the day you need it. Set an expiry date, such as 30 days. That number is this course's habit, not a GitHub rule. Copy the token once, keep it where you keep secrets, and never put it in a repository or a chat. Delete it when the job is done.

A fine-grained token does not support every feature of the older classic tokens. If a command fails, add the one permission it needs, not all of them. For gh, the manual says to prefer the environment variable GH_TOKEN when you use a fine-grained token.

```bash
export GH_TOKEN="paste the token here, in your own terminal only"
gh issue list --repo your-name/your-repo
```

On Windows PowerShell, the first line is written `$env:GH_TOKEN = "..."`. Either way, type it only in your own terminal.

</GoDeeper>

## Pick the least access for the job

<InteractiveCanvas slug="least-access-picker" />

Change one fact at a time. Reading needs read-only. A pull request on your own repository needs write on that one repository. Money and deletions stay with a person. When an AI tool reads text that strangers wrote, it gets read-only, and you type the change yourself.

<GoDeeper title="Go deeper: what least access means in practice">

Least access has two parts: the smallest permission that does the job, and the shortest time. Start with read access. If a step fails, find which single permission it needs and add only that. When the job is done, delete the token or let it expire. Each added permission is a new thing that can go wrong, and each day a token lives is a day it can leak.

This habit also protects you from your own mistakes. A token that can only read cannot delete a branch by accident, and a token for one repository cannot touch the other ten. You do not need to trust the tool completely if the key it holds is small.

</GoDeeper>

## Instructions hidden in an issue

<InteractiveCanvas slug="toolbelt-hidden-instruction" />

The risk has a name: <GlossaryTerm term="prompt injection" definition="Text that an AI tool reads, such as an issue or a web page, that holds instructions meant for the tool, not for people." />. A wide token lets the hidden order reach private data. A narrow token limits the damage. The tool can still be tricked, so you read what it drafts and do risky steps by hand.

<GoDeeper title="Go deeper: connectors, MCP and a documented case">

A <GlossaryTerm term="connector" definition="A link that lets an AI tool read or act on one of your accounts, such as GitHub." /> gives a tool power over your account. Many connectors use the <GlossaryTerm term="Model Context Protocol" definition="MCP for short: a common way for AI tools to connect to services such as GitHub, so they can read data and run actions." />. Its specification, version 2026-07-28, says that tools represent arbitrary code execution and must be treated with care. It says tool descriptions should be treated as untrusted unless they come from a trusted server, and that the host must get the user's explicit consent before a tool runs.

GitHub's official MCP server is MIT licensed and has a read-only mode. In read-only mode it switches off every tool that is not read-only, even if the AI asks for one. It also has a lockdown mode, which shows only content in public repositories from people with push access. GitHub describes that as a best-effort content filter, not a security boundary. So the official server is not safe by being official. Use read-only mode and one repository at a time.

```text
Remote server: send the header X-MCP-Readonly, or use the /readonly path
Local server:  start it with --read-only, or set GITHUB_READ_ONLY
```

Check the server's own page for the exact current form. The risk is documented. On 26 May 2025, researchers at Invariant Labs, a security company, showed a leak. A malicious issue in a public repository made an agent with access to public and private repositories put private data into a pull request. They call it an architectural problem, not a bug in one server, and they say that the model's own alignment did not stop it. They suggest least privilege, such as one repository per session, and monitoring. The scene in this chapter is a made-up case in that shape.

</GoDeeper>

## A cost view is not only costs

<MermaidDiagram title="Two policies, two lists" chart={`flowchart TD
  B["AWS billing read-only policy"] --> C["Costs and budgets"]
  B --> P["Payment details and invoices"]
  B --> T["Tax and contract data"]
  K["A cost-only policy"] --> C
`} legend="The managed billing read-only policy shows costs and more. A cost-only policy shows the costs." />

A name can promise less than a policy delivers. AWS's managed billing read-only policy also lets the holder see payment instruments, invoices and tax data. Practise on the supplied sample cost report in chapter 9.7. The cloud material in the fold below is optional, and you can skip it without losing anything.

<GoDeeper title="Optional: only if you have a cloud account">

Ask your instructor for the tested cost-only policy before you touch a real account. On AWS, the command that reads costs needs a time period, a granularity (daily, monthly or hourly) and a metric. It can group by dimensions such as the service. AWS charges one US cent for each Cost Explorer API request, per page of results, and the history goes back up to 13 months. That is AWS's own price, so check its page.

```bash
aws ce get-cost-and-usage \
  --time-period Start=2026-10-01,End=2026-10-25 \
  --granularity MONTHLY \
  --metrics UnblendedCost \
  --group-by Type=DIMENSION,Key=SERVICE
```

Do not run this on a live account unless you accept the cent a request. Use the sample report in chapter 9.7. Check the syntax in the AWS CLI help for your version.

Budgets alert you, but they do not stop spending. AWS Budgets can email you or use Amazon SNS when actual or forecast cost passes a limit. Its data updates up to three times a day, and AWS warns that costs may pass the threshold before the alert arrives. Google Cloud's alert-only budgets also do not cap spending automatically. Set a budget before you start, and delete what you create.

A card may be needed. For AWS accounts opened on or after 15 July 2025, you choose a Free plan or a Paid plan. The Free plan ends after six months or when the credits run out. It gives US$100 in credit and up to US$100 more for activities. Then the account closes, and data is kept for 90 days unless you upgrade. AWS says a payment method is not required for most new customers, but it may ask for one to confirm who you are. Google Cloud's Free Trial gives a US$300 credit for 90 days and requires a credit card or another payment method. That is a temporary hold, not a charge. Azure also has a free account; check at sign-up whether it asks for a card. All of this is optional. With no card, use the supplied sample report, which needs no account at all.

</GoDeeper>

## Secrets: revoke first

<MermaidDiagram title="If a secret leaks" chart={`flowchart TD
  L["A key is pushed or pasted"] --> R["1. Revoke or rotate it at the provider"]
  R --> N["2. Make a new key and store it safely"]
  N --> C["3. Clean the history, if you must"]
  L --> D["Delete the commit only"]
  D --> K["The old key still works"]
`} legend="The order matters. Deleting the commit alone leaves a working key behind." />

If a secret leaks, treat it as stolen. First revoke or rotate it, so the old key stops working. Then make a new one. Deleting the commit does not cancel the key. Never paste a key into a chat, a repository or a screenshot.

<GoDeeper title="Go deeper: how common leaks are, and what GitHub does">

GitGuardian, a security company, counted about 28.6 million new hardcoded secrets in public GitHub commits in 2025, up 34%, including 1,275,105 secrets for AI services. That is a vendor's report, so read it as one company's count. GitHub's push protection is on by default for users and blocks pushes of known secrets to public repositories. Its secret scanning runs for free on public repositories and tells the provider when a partner's secret appears. Do not rely on either, as chapter 4.5 said.

GitHub's own guidance on removing sensitive data says the first step is to revoke or rotate the secret. Once the secret is dead, rewriting history may not be needed. OpenAI and Anthropic both give the same advice for API keys. Never commit a key, and keep it in an environment variable. Never put it in browser or mobile code, and rotate keys.

</GoDeeper>
