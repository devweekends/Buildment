Nabil built Shelf, a one-page list of which books are out at his school library. He asks an assistant to review his README and code. It starts with praise, then lists points, and Nabil cannot tell which to act on.

## Ask for problems, not praise

<MermaidDiagram title="The critique loop" chart={`flowchart TD
  R["Write a rubric of four things"] --> A["Ask for the three weakest points"]
  A --> T["Look at each point, or test it"]
  T --> D["Fix, test first, or reject"]
  D --> L["Log your reason"]
`} legend="You hold the rubric and you make each decision. The assistant only supplies points to check." />

AI feedback is a second opinion that tries to agree with you. Studies find that assistants lean towards agreeing. So ask for what is wrong, not for praise. Give a rubric, a short list of what your work should have, and ask for the three weakest points against it. Then you decide.

<GoDeeper title="Go deeper: a rubric and a request">

Here is a request Nabil can reuse. The rubric has four items, and the last line blocks the praise.

```text
Here is my README and my main file. Judge them against this list:
1. One sentence says what it does and who it is for.
2. Three steps let a stranger run it.
3. A picture or a recording shows it working.
4. It says what is not done yet.
Do not praise it. Give me the three weakest points, each with the line it is about.
```

Before you paste, run the check from chapter 2.2. Remove keys, other people's personal data and anything you would not show a stranger. Asking an assistant for the strongest case against your work is the course's own method. No study has tested that exact prompt, but it fits what we know about assistants that lean towards agreeing. It is also fine to ask twice, with a different rubric, and compare the points. A point that appears in both is not proof, but it tells you where to look first.

</GoDeeper>

## Fix, test or reject?

<InteractiveCanvas slug="act-on-feedback" />

Sort eight points from the assistant. Fix now what you can see is true. Test first what might be true. Reject what does not fit your goal, and write one reason. Praise is not a point. A wrong try tells you why.

<GoDeeper title="Go deeper: the three buckets">

Fix now means the point is true and you can confirm it by looking, such as a file that is missing. Test first means the point is about behaviour you have not seen. Run it, measure it, or read the source. If the point holds, fix it, and keep the test so the bug cannot return quietly.

Reject means the point does not fit your goal, costs more than it gives, or is praise. A rejection is a decision, so write one reason. The reason is what a mentor reads. Do not reject a point only because it hurts. A point that stings may be the useful one, so test it. These three buckets are the course's own method. The sources below give the cautions behind them, not the buckets.

</GoDeeper>

## One study, and what it does not show

<MermaidDiagram title="One study, four numbers" chart={`flowchart TD
  S["2023 study: GPT-4 commented on 3,096 Nature-family and 1,709 ICLR papers"] --> N["Nature: AI and humans overlap 30.85%, two humans 28.58%"]
  S --> I["ICLR: AI and humans overlap 39.23%, two humans 35.25%"]
  S --> U["Of 308 researchers, 57.4% found it helpful"]
  N --> L["Overlap is not proof that a point is right"]
  I --> L
`} legend="An independent study of scientific papers, with one 2023 model. It does not measure whether the points were correct." />

In a 2023 study, GPT-4 commented on thousands of scientific papers. Its points overlapped with human reviewers' points slightly more often than two human reviewers overlapped with each other. Of 308 researchers, 57.4% found the feedback helpful. Overlap is not proof that a point is correct.

<GoDeeper title="Go deeper: reading the study">

The study was posted on arXiv in 2023. It used the full text of 3,096 papers from Nature journals and 1,709 papers from the ICLR machine learning conference. The overlap numbers say how often a point by GPT-4 matched a point by a human reviewer. They do not say whether either point was right. The helpfulness figure comes from 308 researchers who tried the feedback on their own papers.

The limits are plain. The papers are scientific papers, not code or README files. The model is one from 2023. And a helpful rating is an opinion. So do not say that AI feedback is as good as a human reviewer. What the study supports is smaller: AI feedback can raise points that people also raise, and many people found it useful. For code review, no independent study was found, so treat each point as a claim to test.

</GoDeeper>

## Code review tools have limits too

<MermaidDiagram title="Two ways to review a pull request" chart={`flowchart TD
  Q{"Is Copilot code review on your plan?"} -->|"yes, a paid plan"| C["Use it as one voice"]
  Q -->|"no, the Free plan"| A["Give a chat assistant the changes"]
  C --> H["Then you decide, and a person if you can"]
  A --> H
`} legend="Whichever tool reads the pull request, a person decides." />

At the time of writing (checked 2026-10-25), GitHub Copilot can review a pull request, but the Free plan does not include it. GitHub says to add a human review, because the tool will make mistakes and may miss problems. The free route is a chat assistant given the changes. Never paste secrets.

<GoDeeper title="Go deeper: using a chat assistant as a reviewer">

GitHub's own page says that Copilot code review is not guaranteed to find all problems, that it will make mistakes, and that you should supplement it with a human review. It also skips some files, such as dependency files, log files and SVG files. So even where it is available, it is one voice among others.

For the free route, open your pull request in the browser, go to the Files changed tab, and copy the changes. Run the check from chapter 2.2 first, then paste them into a chat assistant with your rubric. Sort the points as in the picture above. A person is better still. Ask a classmate or a mentor to review one pull request, as teams do in module 8. Course 16 uses the same method on a resume and a LinkedIn profile, and the same rule applies: the assistant lists claims, and you decide.

</GoDeeper>

## Write down why you said no

<MermaidDiagram title="Where each critique point goes" chart={`flowchart TD
  P["One critique point"] --> S{"Sort it"}
  S -->|"true by looking"| F["Fix now: no run steps"]
  S -->|"could be true"| T["Test first: 31 January"]
  S -->|"costs more than it gives"| R["Reject: the page has 60 lines"]
  T -->|"test fails"| X["Fix it and log the fix"]
  T -->|"test passes"| Y["Reject and log the test"]
  F --> G["Log line: decision and reason"]
  X --> G
  Y --> G
  R --> G
`} legend="Every path ends in a log line with a decision and a reason." />

Keep a short critique log. For each point, write what you decided and why. A fix needs a note on how you checked it. A rejection needs one reason. The log shows a mentor that you judged the feedback. It is also the hand-in for this module's gate.

<GoDeeper title="Go deeper: one log entry">

Here is one entry, as Nabil writes it for the offline point.

```text
Point: The page needs the internet.
Decision: test first, then fix.
How I checked: I opened the page with the network off. A font failed to load.
What I changed: I switched to the phone's own font.
Commit message: Use the system font so the page works offline
```

A rejection reads differently: "Rejected: a framework rewrite. The page has 60 lines and my goal is a page a volunteer can read. A rewrite would cost weeks." If you cannot write a reason, that is a sign to test the point, not to skip it. A short log also helps in an interview, because you can say which advice you took, which you refused and how you knew.

</GoDeeper>

## Quick check

<MermaidDiagram title="The habit in one line" chart={`flowchart TD
  A["Ask for problems, with a rubric"] --> B["Look at each point, or test it"]
  B --> C["Fix, test first, or reject"]

Keep these four moves. Two questions follow, each on a new case.

```quiz
type: mcq
question: "Ghada's assistant reviews her bakery order page and says: 'The page is slow, so move to a bigger server.' She tested the page on a weak mobile connection, and it loaded in 2 seconds. The page has about 5 visitors a day. How should she treat this point?"
options:
  - "Fix it by renting a bigger server this month"
  - "Test it again on a faster connection"
  - "Drop the whole critique from her log"
  - "Reject it and write the reason in her log"
correct: 3
explanations:
  - "She has seen the page load in 2 seconds on a weak connection, so the claim does not match what she can see. A fix would cost money for nothing."
  - "A faster connection can only make the page load sooner. She already tested the harder case, so another test adds nothing."
  - "One weak point does not make the other points wrong. She should sort each point on its own."
  - "Right. Her own test contradicts the point, so no further test is needed. A rejection with a one-line reason goes in her log."
```

question: "Nabil wants honest feedback on his README. Which request is most likely to give him useful points?"

  - "Judge it against my list and give the weakest three"

explanations:
  - "This invites a yes. Assistants lean towards agreeing, so the answer is likely to be praise with little to act on."
  - "This asks for praise directly. It gives him nothing to fix or test."
