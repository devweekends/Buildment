This is the gate for module 11. Tick each box only when it is true, answer the learning log for yourself, and then size a deployment in writing. A mentor will read your answer. Your answers save as you type, so a power cut or a lost connection does not lose your work.

This module had no build chapter, because the real thing needs a data-centre GPU that you do not have. That is why the gate asks for a skill you can practise with a pen and a calculator: the fit estimate. A hands-on round may ask for something different, but questions such as whether a deployment fits, why one crashed under load, or how many GPUs a plan needs all come down to a few lines of arithmetic and a fix with its price. That is what your mentor will look for.

## Module 11 checklist

- [ ] I can explain prefill and decode, why decode is limited by reading the weights from memory at every step, and what continuous batching and paged memory change
- [ ] I can compute the KV cache bytes per token from layers, KV heads, head size and bytes per value
- [ ] I can budget GPU memory for weights, a reserve and the cache, and turn what is left into tokens held at once
- [ ] I can say what quantization and speculative decoding each change, and why FlashAttention does not shrink the cache
- [ ] I can say when a model needs tensor or pipeline parallelism, and weigh self-hosting against a hosted API with reasons and numbers
- [ ] I can choose between an FP8 cache, smaller weights, a shorter context, more GPUs and admission control, name the price of each, and say which one only suits a spike
- [ ] I finished the quiz in 11.10

## Learning log

1. **Your own cache number:** A model has 24 layers, 8 KV heads and head size 128, stored at 16-bit. How many bytes does one token take, and how many GB does a 16,384-token chat take? Write each multiplication.
2. **Tokens, not users:** Why can the same GPU serve 40 short chats or only 5 long ones? Explain it to a manager in three sentences, with no jargon.
3. **Which fix first:** Your estimate says the cache is 20% too large for the memory left, and this is the daily load, not a spike. Which fix would you try first, what does it cost, what would you test before launch, and why is admission control not the answer?
4. **The slow first word:** A user pastes a long document and waits before the first word appears, then the words stream at a steady pace. Explain to a manager in three sentences, with no jargon, why the wait comes first and the words after it come steadily.
5. **Split or call out:** A model has 141 GB of weights at 16-bit, and your GPUs have 80 GB each. Name two ways to run it yourself and the price of each. Then say what would make you call a hosted API instead.

## Your interview answer

The question arrives as a short story: a team, a model, a GPU, a number of users and a chat length. The interviewer then waits. A weak answer says "probably" or names a bigger GPU. A strong answer says the five steps aloud, with the arithmetic and the units, gives a verdict with a margin, and ends with a fix that has a price. You have practised this in 11.9. Now you do it in writing, on a new scenario, and a mentor reads it.

Build your answer in five parts. First, say your map in one sentence: weights, cache per token, tokens held at once, memory left, then compare. Second, do the five steps and show every multiplication, with units on every line. Third, give the verdict in the interview order: the answer, the number, then the reason. Say whether it fits, by how much, and how many chats of that length the memory can hold. Fourth, choose two fixes for the daily load. For each one, recompute the numbers with the fix in place, and name what it costs. Fifth, finish with two sentences: what protects the server on a day above the planned peak, and why a hosted API is or is not the answer here.

Watch for the easy slips. Check that you used 2 bytes for 16-bit and 1 byte for 8-bit. Check that you counted both keys and values, which is the first 2 in the cache formula. Check that you kept the 10% reserve, and that you used GB throughout, not a mix of GB and GiB. Check that you counted the load in tokens before you counted it in users. A wrong unit is easy for a reader to spot. If you are unsure of a number, show how you got it. A mentor can follow honest working and correct one slip, but cannot give credit for a number with no working behind it.

A fix changes one number in the estimate, and you should say which: the bytes per value, the tokens in each chat, the load held at once, the memory left, or the number of GPUs. Every fix has a price, so name it: a quality test, a changed product, a wait, or a bigger bill. The saving from FP8 is arithmetic, not a measurement, and it has to be tested on your own data. A fix that does not close the gap should be said clearly. You can show a fix that fails and say why. That shows your arithmetic is real. Admission control changes none of these numbers, so say where it belongs.
