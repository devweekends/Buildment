```quiz
type: mcq
question: "Yousef's server runs batches of 4 requests that need 100, 100, 100 and 500 new tokens. A static batch runs 500 steps, so it has 4 × 500 = 2,000 slot-steps, and a finished request leaves its slot idle until the whole batch ends. Continuous batching gives a freed slot to a waiting request at the next step. How many slot-steps could waiting requests use?"
options:
  - "800, the slot-steps that already hold a real token"
  - "1,200, the slot-steps left idle after a request finishes"
  - "1,500, the full 500 steps of each of the three short slots"
  - "500, the steps taken by the longest request"
correct: 1
explanations:
  - "800 is the work the static batch already does: 100 + 100 + 100 + 500 tokens. Waiting requests can use the other slot-steps, not these."
  - "Right. Each short request finishes after 100 steps and sits idle for 400 more, so 3 × 400 = 1,200 slot-steps. The check is 2,000 - 800 = 1,200. Continuous batching puts waiting requests into them."
  - "Each short slot works for its first 100 steps, so only 400 of its 500 steps are idle. Counting 3 × 500 treats the busy steps as free."
  - "500 is the length of the batch, not the idle slot-steps. The slot of the longest request is never idle."
```

```quiz
type: mcq
question: "Karim's older server reserves a full 8,192-token context in one block for each request. Chats average 1,500 tokens. The cache pool is 10 GB, at 131,072 bytes per token. A paged server rounds each request up to blocks of 16 tokens. How many requests fit in each server?"
options:
  - "Reserved 9, paged 9, because paging changes speed, not capacity"
  - "Reserved 50, paged 9, because block tables take cache memory"
  - "Reserved 9, paged 50, because only a request's last block is wasted"
  - "Reserved 9, paged 4,768, because each request needs one block"
correct: 2
explanations:
  - "Paging changes what is reserved. A request then holds only the blocks it uses, so many more requests fit in the same pool."
  - "This swaps the two results. Reserving 8,192 tokens each gives 10 GB ÷ 1.07 GB = 9 requests. Paged blocks cannot do worse than that."
  - "Right. A reserved request takes 8,192 × 131,072 = 1.07 GB, so 9 fit. A paged request rounds 1,500 up to 94 blocks, 1,504 tokens, 0.20 GB, so 50 fit."
  - "A block holds 16 tokens, which is 2 MiB, so the pool has about 4,768 blocks. A chat of 1,500 tokens needs 94 blocks, not one, and 4,768 ÷ 94 = 50."
```

```quiz
type: mcq
question: "Reem's team adds a draft model to a lightly loaded server. The draft is accepted 60% of the time (a = 0.60), proposes 3 tokens per step (g = 3), and each drafted token costs 0.10 of a target step (c = 0.10). What speed-up does the formula give over plain decoding?"
options:
  - "About 1.67 times faster: 2.18 tokens per step, divided by 1.3"
  - "About 2.18 times faster: each target step yields 2.18 tokens"
  - "About 4 times faster: 3 drafted tokens plus 1 of the target's own"
  - "About 1.3 times slower: each round adds 0.3 of a step of drafting"
correct: 0
explanations:
  - "Right. Tokens per step are (1 - 0.6^4) ÷ (1 - 0.6) = 2.18. The cost term is 3 × 0.1 + 1 = 1.3. The factor is 2.18 ÷ 1.3 = 1.67."
  - "2.18 is the tokens per step, but the drafting takes time too. Dividing by the cost term of 1.3 gives 1.67."
  - "Four tokens is the most a step can give, when every draft is kept. At a = 0.60 the average is 2.18."
  - "The drafting cost of 0.3 of a step is paid on every round, but each round also yields 2.18 tokens, so the net effect is a gain, not a slowdown."
```

```quiz
type: mcq
question: "Tamer's model has 480 GB of weights at 16-bit, and each GPU can use 72 GB. The team has two machines with 4 GPUs each. GPUs inside a machine are joined by fast links, and the two machines by a slower network. How should he split the model?"
options:
  - "Tensor parallelism across all 8 GPUs, so every layer is split 8 ways"
  - "Two full copies, one per machine, since 4 GPUs hold the weights"
  - "Pipeline inside each machine and tensor between the two machines"
  - "Tensor inside each machine and pipeline between the two machines"
correct: 3
explanations:
  - "Tensor parallelism exchanges results in every layer, so it needs fast links. Across the slower network between machines, that traffic would dominate."
  - "Four GPUs hold only 4 × 72 = 288 GB, and the weights are 480 GB. One copy needs at least 7 GPUs (480 ÷ 72 = 6.7), so it cannot fit in one machine."
  - "This reverses the rule. The chatty split, tensor, belongs on the fast links inside a machine, and the quiet split, pipeline, belongs across the slower network."
  - "Right. The weights need at least 7 GPUs, so the model spans both machines. Tensor parallelism stays inside each machine, where the links are fast, and pipeline parallelism passes results between the machines once per stage."
```

```quiz
type: mcq
question: "Wadi Labs (a fictional company) has 24 chats of 16,384 tokens open every working day, not only in a spike. The cache holds 420,000 tokens and the admission limit is 90%. One chat waits in the queue every day. What fixes it at its cause?"
options:
  - "Raise the limit to 100%, which admits 25 chats and leaves no headroom"
  - "Store the cache in FP8 after a quality test, which doubles the capacity"
  - "Bound the queue and answer 503, so the 24th chat is refused each day"
  - "Let the engine preempt the 24th chat and recompute it when memory is short"
correct: 1
explanations:
  - "A 100% limit admits 25 chats (420,000 ÷ 16,384 = 25.6), but chats grow while they run. With no headroom the server can run out of memory."
  - "Right. At FP8 the capacity doubles to about 840,000 tokens, so 90% of it, 756,000 tokens, holds 46 chats of 16,384. A steady load above the limit is fixed by changing the bytes, not by queueing."
  - "A 503 turns the daily wait into a daily refusal. The load is steady, so the server needs more room, not a quicker way to say no."
  - "Preemption is a safety net for rare spikes. Planning on it makes a chat redo its prefill every day and adds delay for everyone."
```
