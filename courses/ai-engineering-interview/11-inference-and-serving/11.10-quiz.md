```quiz
type: mcq
question: "Yousef's users paste a 12,000-token report and wait a long time for the first word. After that, words stream at a steady pace. Which phase causes the wait, and which change shortens it?"
options:
  - "Decode, because every step reads all the weights, so use a smaller batch"
  - "Prefill, because the whole prompt is read first, so send fewer tokens"
  - "Decode, because the cache grows with each step, so store the cache in FP8"
  - "Prefill, because the weights are read once, so add speculative decoding"
correct: 1
explanations:
  - "Decode starts after the first word, and the wait here is before it. A smaller batch would not shorten the time to first token."
  - "Right. Prefill processes all 12,000 prompt tokens before the first token appears, so its time grows with the prompt. Sending fewer prompt tokens shortens it."
  - "The wait is before the first word, so it is not the decode steps. An FP8 cache saves memory and does not shorten the prefill."
  - "Prefill is the right phase, but speculative decoding speeds up the decode steps that come after the first token. It does not shorten the prefill."
```

```quiz
type: mcq
question: "Ahmad compares two models. Both have 32 layers and head size 128 at 16-bit. Model P has 32 KV heads. Model Q has 8. Each has 10 GB left for the cache, and each user holds a 16,384-token chat. How many chats can each hold?"
options:
  - "P holds 1 chat and Q holds 4, because P stores 4 times more per token"
  - "P and Q both hold 4 chats, because their layers and head size match"
  - "P holds 2 chats and Q holds 9, because only the keys are counted"
  - "P holds 1 chat and Q holds 2, because sharing KV heads halves the cache"
correct: 0
explanations:
  - "Right. P needs 2 x 32 x 32 x 128 x 2 = 524,288 bytes per token, so a chat is 8.59 GB and one fits. Q needs 131,072 bytes per token, so a chat is 2.15 GB and four fit."
  - "The number of KV heads sets the cache size, so the match in layers and head size is not enough. P has 4 times the KV heads of Q and needs 4 times the memory."
  - "This leaves out the 2 for keys and values, which halves each cache. It gives P 2 chats and Q 9, and both numbers are too high."
  - "Going from 32 KV heads to 8 divides the cache by 4, not by 2. Q holds 4 chats, not 2."
```

She needs 30 chats of 8,192 tokens. The cache needs 32.21 GB, and 21.50 GB is left after the weights. Which single change makes all 30 chats fit?"

```quiz
  - "Raise the engine's memory share from 0.90 to 0.92 of the GPU"
  - "Store the weights in 8 bits, which halves them to 7.25 GB"
  - "Cap every chat at 6,144 tokens, three quarters of 8,192"
  - "Store the cache in FP8 instead, which halves the need to 16.11 GB"

explanations:
  - "At 0.92 the GPU gives 36.8 GB, so 36.8 - 14.50 = 22.30 GB is left. That is still 9.91 GB short of the 32.21 GB needed."
  - "At 8 bits the weights are 7.25 GB, which leaves 36 - 7.25 = 28.75 GB. The cache needs 32.21 GB, so it is still 3.46 GB short."
  - "30 x 6,144 = 184,320 tokens need 24.16 GB. Only 21.50 GB is left, so it is still 2.66 GB short."
  - "Right. At 1 byte per value the cache needs 16.11 GB, which is below the 21.50 GB left, with 5.40 GB spare."
```

```quiz
type: mcq
question: "Karim's older server reserves a full 8,192-token context in one block for each request. Chats average 1,500 tokens. The cache pool is 10 GB, at 131,072 bytes per token. A paged server rounds each request up to blocks of 16 tokens. How many requests fit in each server?"
options:
  - "Reserved 9, paged 9, because paging changes speed and not how many fit"
  - "Reserved 50, paged 9, because block tables take memory the cache needs"
  - "Reserved 9, paged 50, because only a request's last block is wasted"
  - "Reserved 9, paged 12, because rounding to blocks wastes about a quarter"
correct: 2
explanations:
  - "Paging changes what is reserved. A request then holds only the blocks it uses, so many more requests fit in the same pool."
  - "This swaps the two results. Reserving 8,192 tokens each gives 10 GB / 1.07 GB = 9 requests. Paged blocks cannot do worse than that."
  - "Right. A reserved request takes 8,192 x 131,072 = 1.07 GB, so 9 fit. A paged request rounds 1,500 up to 94 blocks, 1,504 tokens, 0.20 GB, so 50 fit."
  - "Rounding up to 16-token blocks wastes at most 15 tokens per request. Here it wastes 4 of 1,504 tokens, about 0.3%, not a quarter."
```
