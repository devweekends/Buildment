## The first word waits, then the rest stream

After the launch-day crash at Wadi Labs (a fictional remote software team of 12), Ahmad pasted a long design document into the assistant and asked a question. For a moment nothing happened. Then the words streamed out faster than anyone could read. Ahmad asked Nour: "Why does it wait first and then run fast? Why can't it start writing at once?"

By the end of this chapter you can describe the two phases of a request and name the three numbers that measure it. You can work out the fastest speed one request can reach. You can also explain why more users at once raise total output but can slow each user.

## One token at a time

A language model writes by repeating one step: given all the text so far, produce the next token. A token is a word or a part of a word. The model cannot write token 5 before token 4 exists.

A request has two parts in time. First the model reads the prompt. Then it writes the answer. Inside, the two parts use the GPU in opposite ways.

<BigWordAlert term="Prefill and decode" plainEnglish="Prefill is the first phase: the model reads the whole prompt at once and produces the first token. Decode is the second phase: the model writes the rest of the answer, one token per step." whyItMatters="The two phases use the GPU in opposite ways. Prefill is limited by arithmetic and decode by memory reads, so almost every serving technique is aimed at one of them." />

In **prefill**, the model processes all the prompt tokens in parallel, in one pass. If the prompt has 2,000 tokens, all 2,000 positions go through the model together. Each weight is read from memory once and used for all 2,000 tokens. The GPU's arithmetic units stay busy, so prefill is <GlossaryTerm term="compute-bound" definition="Limited by how fast the chip can do arithmetic. Getting data from memory is quick enough, so the calculating units are the bottleneck." />.

In **decode**, the model makes one token per step. Each step is a full pass through the model for one new token, and it still needs every weight. So the engine must read all 16.06 GB from memory to make a single token. The arithmetic takes very little time, and the units mostly wait for data. Decode is <GlossaryTerm term="memory-bound" definition="Limited by how fast data can be read from memory, not by arithmetic. The calculating units finish early and wait for the next data." /> when the <GlossaryTerm term="batch" definition="The group of requests that the engine runs together in one step. With one user, the batch is 1." /> is small. The diagram shows the order and how often the weights are read.

```mermaid
flowchart LR
  P[Prompt: 2,000 tokens] --> F[Prefill: one pass]
  F --> FR[16.06 GB read once]
  F --> T[First token]
  T --> D[Decode step]
  D --> DR[16.06 GB read again]
  D --> N[Next token]
  N --> D
```

Prefill reads the weights once for 2,000 tokens. Every decode step reads all 16.06 GB again for one token. A 300-token answer is one prefill plus 299 decode steps, so the weights are read 300 times in all.

## Why decode waits for memory

The reason is arithmetic you can do by hand. For each weight, the GPU does 2 operations per token: one multiply and one add. A 16-bit weight takes 2 bytes. So with B tokens in the batch, the GPU does 2 × B operations for every 2 bytes read. That is B operations per byte.

Now compare that with the chip. Take a data-centre GPU with a peak of about 312 trillion operations a second (an example, because peaks differ between generations) and an example <GlossaryTerm term="memory bandwidth" definition="How many bytes the GPU can read from its memory each second. For 80 GB-class data-centre GPUs it is about 2 to 3.4 TB per second." /> of 2 trillion bytes (2 TB) a second. Divided, that is roughly 156 operations for every byte it reads. In decode with one request, B is 1, so the GPU gets 1 where it needs 156 to stay busy. In prefill with a 2,000-token prompt, B is 2,000, so arithmetic is the limit.

This gives a useful number: the fastest one request can decode. Each step must read at least 16.06 GB. At 2 TB/s, that takes 16.06 ÷ 2,000 = 0.00803 s, or 8.03 ms. So one request makes at most about 1 ÷ 0.00803 = 125 tokens per second.

Treat 125 as a ceiling, not a measurement. It leaves out the KV cache reads and the software overhead, so real speed is lower. The 2 TB/s is the example's own choice.

Prefill shows the other side. A 2,000-token prompt needs 2 × 8,030,261,248 × 2,000 operations, about 32 trillion, which is at best 0.103 s at that peak. Decoding 2,000 tokens one by one would take 2,000 × 8.03 ms, about 16 seconds. Prefill is about 150 times faster because 2,000 tokens share each read.

## Three numbers: TTFT, TPOT and throughput

Three measures describe a request. They answer different questions.

<GlossaryTerm term="Time to first token (TTFT)" definition="The wait from the moment a request arrives until the first token of the answer appears. It includes any time spent in a queue plus the prefill." /> is the wait before anything appears. It decides whether the system feels alive. <GlossaryTerm term="Time per output token (TPOT)" definition="The average time between tokens after the first one. It decides how smooth the streaming looks, and how fast a person can read along." /> is the average gap between tokens after the first. It decides how smooth the stream feels. <GlossaryTerm term="Throughput" definition="The total number of tokens the server produces per second, added up across all users." /> is the total tokens per second across all users. It decides how many people one GPU can serve.

They connect: total time = TTFT + TPOT × (tokens after the first). In this example, a 300-token answer has a TTFT of 0.5 s and a TPOT of 25 ms: 0.5 + 299 × 0.025 = 7.975 s, about 8 seconds.

## Batching: one read for many users

Every decode step reads the weights. The engine can put the next tokens of several users into the same step. That group of requests is the batch. Ignore the KV cache for now. It is the saved work of the earlier tokens, and chapter 11.3 explains it.

Before the interactive model, predict what happens to the step time when a second user joins.

```predict
prompt: "One user is decoding and each step takes 8.03 ms. A second user joins, and both decode in the same step. Ignoring the KV cache, what happens to the step time?"
options:
  - id: same
    label: "It barely changes, since one read of the weights serves both"
  - id: double
    label: "It about doubles, since the GPU now has twice as much work to do"
correctOptionId: same
explanation: "Decode is limited by reading the weights, and the weights are read once per step for the whole batch. A second token adds a little arithmetic and no extra weight read, so the step time barely changes."
```

**What this shows.** One request travelling between four parts: the app, the engine, the weights and the KV cache. Prefill reads the weights once for all 2,000 prompt tokens and fills the cache with 2,000 tokens, about 262 MB (2,000 × 0.13 MB). Each decode step then reads all 16.06 GB again to produce one token. With a batch of 8 users, one read makes 8 tokens, so the cost of the read is shared.

**Try this.** Before you open the message called The first decode reads every weight again, predict how much of the weights decode must read to make one token. Then check the chips: all 16.06 GB, the same amount as the whole prefill read. Compare that message with the one called A batch of 8 shares one weight read. The weights are read once in both. How many tokens does that one read make in each?

**What changed.** From prefill to decode, the number of tokens sharing each read drops from 2,000 to 1. From one user to a batch of 8, the read stays the same size and the tokens per read grow eight times.

**Limits of the model.** The canvas has no real timings, one GPU and no activations. The 2,000-token prompt and the sizes are the example's own. In a real engine, every user in the batch also adds cache reads to each step.

## What batching costs each user

The cache reads are where batching stops being free. Each decode step reads the weights once, but it reads every user's KV cache in full. So the bytes per step grow with the batch.

Take the example numbers. Each of 8 users holds 2,000 tokens, 262 MB of cache. One user: 16.06 + 0.26 = 16.32 GB per step, so 16.32 ÷ 2,000 = 8.16 ms. Eight users: 16.06 + 8 × 0.262 = 18.16 GB per step, so 9.08 ms. One user gets 1 ÷ 8.16 ms, about 122 tokens a second. Eight users get 8 ÷ 9.08 ms, about 881 a second, 7.2 times more. Each user's TPOT rose from 8.16 to 9.08 ms, 11% slower.

This is the trade-off in one example: batching raises total throughput a lot and slows each user a little. It works until arithmetic, not memory, is the limit. By the estimate above that is near 150 tokens in the batch. A scheduling paper saw 500 to 600 in practice for some multi-GPU setups, so use 150 only as a rough guide. Memory space often stops the growth first, because every user brings a cache that must fit. That is chapter 11.4.

A second cost is easy to miss. A long prefill occupies the GPU for its whole pass, and other users' next tokens wait. A 2,000-token prefill takes at best 0.1 s, so users who saw a token every 9 ms see a pause more than ten times longer. Chapter 11.5 shows how engines avoid this.

## Failure modes and debugging

- **Reading the ceiling as a speed.** The weight-read figure is an upper bound from weights alone. Measure real speed under real load before you promise anything.
- **Mixing up TTFT and total time.** A slow first word and a slow stream have different causes. Prompt length and queueing affect TTFT. Batch size and cache size affect TPOT.
- **Quoting throughput without latency.** A server that makes 880 tokens a second for 8 users gives each about 110. If someone says "1,000 tokens a second", ask for how many users and with what TPOT.
- **Testing with one short request.** This is what happened at Wadi Labs. One short request has no queue, no batch and no large cache, so it hides the problems that appear under load.

<Callout type="warning" title="A ceiling is not a measurement">
The weight-read ceiling ignores cache reads, overhead and other work. Use it to see which resource limits you, and measure the real number on your engine.
</Callout>

## In the interview

A question on this topic checks that you know why a model behaves as it does under load. A strong answer gives the two phases, names what limits each, and uses one number. Answer each question aloud first, then open it.

<FaqGroup title="Practice questions">
<FaqItem question="Why is the first token slow and the later tokens fast?">

The first token must wait for prefill, where the model processes the whole prompt before it writes anything. Prefill is compute-bound, so its time grows with the prompt: 2,000 tokens need about 32 trillion operations, at best about 0.1 s. After that, each decode step makes one token and takes roughly the time to read the weights, about 8 ms in my example. Under load, queueing adds to the first-token wait.

**Follow-up probes:**

- What happens to TTFT if the prompt grows from 2,000 to 8,000 tokens?
- What else besides prefill can add to TTFT?

</FaqItem>
<FaqItem question="Why does batching raise throughput but can hurt each user's latency?">

A decode step reads the weights once however many requests share it, so more requests means more tokens per read. In my example, 8 users give about 881 tokens per second against about 122 for one, 7.2 times more. But each step also reads every user's cache, so each user waits 11% longer per token. The gain stops when arithmetic or memory space becomes the limit.

**Follow-up probes:**

- What happens when a long prompt joins a running batch?
- Which number would you watch to see that a batch is too big?

</FaqItem>
<FaqItem question="What limits the speed of one request on one GPU?">

For one request, decode is limited by memory reads. Every step reads all 16.06 GB of weights for an 8B model at 16-bit. At 2 TB/s a step takes at least 8.03 ms, so the speed is at most about 125 tokens per second. It is a ceiling, because it ignores cache reads and overhead. To go faster I would read fewer bytes, for example with 8-bit weights, or use a GPU with more memory bandwidth.

**Follow-up probes:**

- How would 8-bit weights change the ceiling, and what would you check before using them?
- Why does a faster arithmetic chip not help a single request much?

</FaqItem>
