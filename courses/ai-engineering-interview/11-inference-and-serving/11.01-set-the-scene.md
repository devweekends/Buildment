## Launch day at Wadi Labs

Wadi Labs (a fictional remote software team of 12) wanted an internal assistant. Engineers would paste design documents, logs and meeting notes into a chat and ask questions about them. The team did not want to send that text to an outside provider. So Nour was asked to run an open model with 8 billion parameters on the team's own server.

Nour rented one <GlossaryTerm term="GPU" definition="A graphics processing unit: the chip that does most of the arithmetic when a model runs. It has its own memory, and the model must fit in that memory." /> with 80 GB of memory. The setup took two days. In the demo, three colleagues chatted with the model at the same time. Answers came back fast, and nobody saw a problem.

On launch day, 20 people opened the assistant before 10 a.m. Many of them pasted long documents and kept the chat open for follow-up questions. At 10:40 the server stopped answering. The log said the GPU was out of memory.

Nour was confused. A week earlier, Nour had done the sum. The model has 8,030,261,248 parameters, and each one is stored in 2 bytes. That is 16.06 GB, on a GPU with 80 GB. The model used about a fifth of the memory. How can a GPU that is 80% empty run out of memory?

## The question Nour did not ask

Nour had asked the right question for the demo: does the model fit? The answer was yes, and it was still yes on launch day. The weights did not change between the demo and the crash. The <GlossaryTerm term="weights" definition="The numbers a model learned during training. They are loaded into GPU memory once and stay there, the same size for one user or for a hundred." /> are the model.

The better question is different: what else sits in memory while people use the model, and how does it grow with the number of users and the length of their chats? Nour had not asked that, because the demo could not show it. Three people sent short messages. The problem only appears with many users and long text.

Look at the numbers first, then guess the cause. Nour's server has 80 GB. Take the weights, 16.06 GB. Something else filled most of the other 64 GB. Before you read on, decide what that something is.

## Where the memory of a GPU goes

A GPU holds four kinds of things while it serves a model. The diagram shows them as shares of one pool.

```mermaid
flowchart LR
  G[80 GB GPU memory] --> W[Weights 16.06 GB]
  G --> K[KV cache grows]
  G --> A[Activations]
  G --> R[Engine reserve]
```

The **weights** are fixed. They take 16.06 GB whether one person or a hundred people use the model. The <GlossaryTerm term="KV cache" definition="Numbers the model keeps for every token it has already read in a chat, so it does not have to compute them again for each new token. Chapter 11.3 explains it step by step." /> is different. It holds a small amount of data for every <GlossaryTerm term="token" definition="A piece of text, often a word or part of a word, that the model reads and writes. Models count text in tokens, not words." /> that every open chat contains. More chats, or longer chats, mean a bigger KV cache. It is the part that grows.

The <GlossaryTerm term="activations" definition="The temporary numbers a model produces while it works on one step. They are used and then thrown away, so they take a small, steady amount of memory." /> are the temporary working numbers of one step. They are small and steady. The **engine reserve** is memory that the serving program (the engine) keeps for itself: working buffers and some headroom. Nobody wants to run at 100%, because an engine with no free memory can fail on the next request.

The diagram argues one thing. Three of the four boxes do not depend on the number of users. Only the KV cache does. So the question "will it fit?" is mostly a question about the KV cache.

## Nour's numbers

In this example, the server keeps 10% of the GPU back for activations and the engine. A real engine has its own setting for this share. In vLLM v0.32.0, an open-source serving engine from a university research lab, the default is 0.92, so the example uses a slightly more careful figure. The memory left for the KV cache is:

80 GB × 0.9 = 72 GB, and 72 − 16.06 = **55.94 GB**.

For the model in this example, one token in the cache takes 131,072 bytes, about 0.13 MB. Chapter 11.3 shows where that number comes from. Now a 32,768-token chat, which is a long document plus a long conversation, takes 32,768 × 131,072 bytes, about **4.29 GB**. That is more than a quarter of the weights, for one user.

| Quantity | Value | How it is found |
|---|---|---|
| Weights | 16.06 GB | 8,030,261,248 × 2 bytes |
| Memory left for cache | 55.94 GB | 80 × 0.9 − 16.06 |
| One 32,768-token chat | about 4.29 GB | 32,768 × 131,072 bytes |
| 20 such chats | about 85.9 GB | 20 × 4.29 GB |

The 20 chats need 85.9 GB, and 55.94 GB is available. The server is short by about 30 GB. The most it can hold is 55.94 ÷ 4.29, which is 13 chats. The 14th long chat pushes it over the edge. That is what happened at 10:40.

The demo hid all of this. Three chats of about 1,000 tokens each take 3 × 1,000 × 131,072 bytes, which is 0.39 GB. That is less than one percent of the GPU. The weights fit in the demo and they fit on launch day. The difference was the number of tokens held at once: about 3,000 in the demo and up to 655,360 on launch day (20 users × 32,768 tokens).

Two honest notes. First, the numbers are the example's own: a real engine, a real GPU and real traffic will differ in details. Second, this simple model leaves out waste. Chapter 11.5 shows that older servers wasted most of their cache memory, and how paging fixed it. The method does not change: bytes and tokens, counted carefully.

## Why interviewers ask this

"Will this model fit on this GPU for this many users?" is one of the most common estimation questions for AI engineers who run their own models. It is also a way to ask "why did it crash under load?" without saying so. Both questions have the same shape. The interviewer wants you to say the arithmetic aloud, check the units, and arrive at a clear answer.

A weak answer says: "The model is 16 GB and the GPU is 80 GB, so it fits." It stops at the weights, as Nour did. A strong answer names the KV cache, estimates it from the model's shape, compares it with the memory left, and offers a fix with its cost. For example: "No, it does not fit. About 86 GB of cache is needed and about 56 GB is free. I could store the cache in 8-bit numbers, which halves it to about 43 GB, if a quality check passes."

This also shows up in system design rounds. When a design says "we will self-host the model", a good interviewer asks how many users one GPU serves and what a million tokens costs. You will be able to answer both, with a method, by the end of this module.
