## Two questions from the product lead

The internal assistant at Wadi Labs (a fictional remote software team) now works well on one GPU. Then the product lead sends two messages in one day. First: "Hard questions need a much bigger model, around 70 billion parameters. Will it run on our GPU?" Second: "Why are we running GPUs at all? Can't we call an API?"

Both are fair, and interviewers ask both. The first is a memory question, and you already have the tools for it. The second is a decision with trade-offs, and it needs a method more than an opinion. This chapter answers the first with arithmetic and the second with a weighted comparison.

## When one GPU is not enough

The bigger open model has 70,553,706,496 weights. At 16 bits, which is 2 bytes each, that is 141.1 GB. An 80 GB GPU cannot hold it. Even if it could, the weights are only part of the budget from 11.4, because the cache still needs room.

One way out is smaller weights. At 8 bits the weights take 70.55 GB. They fit on one GPU, but the room left is 80 × 0.9 - 70.55 = 1.45 GB. That barely holds one short chat. So fitting the weights is not the same as being able to serve users. The other way out is to split the model across GPUs. At the top of the range, a 405-billion-parameter model at 16 bits needs 810 GB, but eight 80 GB GPUs hold 640 GB. A model provider's report says its model did not fit in one machine of eight GPUs, so they ran it across 16 GPUs on two machines, and also used FP8 as a second route.

<BigWordAlert term="Tensor parallelism" plainEnglish="Splitting each layer of a model across several GPUs, so every GPU holds a slice of every weight matrix and the GPUs combine their results at each layer." whyItMatters="It lets a model that is too big for one GPU run on a few, and it frees cache room on each GPU. Interviewers ask when you would use it and what it costs." />

In tensor parallelism, each layer is cut into slices. Every GPU computes its own slice of the same layer, then the GPUs combine their results with an <GlossaryTerm term="all-reduce" definition="A step in which every GPU sends its partial result to the others and all of them end up with the combined total." />. This happens in every layer, for every token. So the GPUs talk constantly, and they need fast links, which in practice means inside one machine. The attention heads are split too, so each GPU does the work of its own heads. The vLLM docs say its implementation includes this algorithm.

The split frees memory. With 4 GPUs, each holds a quarter of the weights, and the cache room grows on every GPU.

| Tensor-parallel size | Weights per GPU | Room for KV per GPU |
|---|---|---|
| 1 | 141.11 GB | Does not fit |
| 2 | 70.55 GB | 1.45 GB |
| 4 | 35.28 GB | 36.72 GB |
| 8 | 17.64 GB | 54.36 GB |

Each row uses the example's 10% reserve, so the room is 72 GB minus the weights per GPU. Two GPUs fit the weights and leave almost nothing for chats. Four give real room. The cost is the all-reduce time in every layer, and four GPUs to pay for.

## The other split: pipeline parallelism

**Pipeline parallelism** cuts the model by layers instead of inside them. For a 32-layer model, GPU 1 might hold layers 1 to 16 and GPU 2 layers 17 to 32. A batch is cut into small micro-batches that flow through the stages, so both GPUs stay busy. Idle time at the start and end is called the pipeline bubble. In the pipeline-parallel training paper the bubble was small when the number of micro-batches was at least 4 times the number of stages. The GPUs only pass activations at a stage boundary, so they can sit on different machines with slower links.

Both parallelism papers are about training. Serving engines reuse the same splits. The vLLM docs give a short rule. If the model fits on one GPU, you probably do not need distributed inference. If it fits in one machine, use tensor parallelism. If not, use tensor parallelism inside each machine and pipeline parallelism across them. Without fast links between GPUs, prefer pipeline parallelism.

```mermaid
flowchart TD
  A{Model plus cache fit?} -->|yes| B[One GPU per copy]
  A -->|no| C{Fits one machine?}
  C -->|yes| D[Tensor parallel]
  C -->|no| E[Tensor plus pipeline]
  B --> F[Add copies for traffic]
```

The takeaway: split the model only as far as memory forces you. More traffic on a model that fits is solved by running more copies, not by splitting. In Kubernetes each copy can be its own pod behind one address.

## What serving engines give you

You will not write the scheduler. You will choose an engine. The two open-source engines this module uses are vLLM, from a university research lab and now maintained by a community, and SGLang, from academic researchers. Both are Apache-2.0. GPU vendors and model hubs also ship their own serving engines.

The engines share most of what you learned in 11.2 to 11.6: continuous batching, paged KV memory, prefix caching, chunked prefill, quantization, speculative decoding and both kinds of parallelism. They also run an HTTP server that speaks a chat API in the same shape as hosted providers, so existing client code can point at it. Details differ, and the table shows four.

| Feature | vLLM v0.32.0 | SGLang v0.5.22 |
|---|---|---|
| Prefix caching | Automatic, on by default | RadixAttention, on by default |
| Cache block size | 16 tokens | Page size of 1 token |
| Chunked prefill | On by default | Set with a chunk-size option |
| Memory share | 0.92 of the GPU | Computed from the GPU |

Defaults move between releases, so pin the version and read the startup log. vLLM prints the cache size in tokens and the maximum concurrency it can offer. One safety note: the vLLM docs say its API-key option does not protect every endpoint, and they warn against relying on it alone. Put your own gateway in front.

## Self-host or call a hosted API?

Nour's team scored both options on five criteria, from 1 to 5, where a higher score is better for that option. These scores are the example's own judgement, not measurements.

| Criterion | Hosted API | Self-hosted |
|---|---|---|
| Data stays in network | 2 | 5 |
| Low cost at volume | 2 | 4 |
| Low team effort | 5 | 1 |
| Fast to launch | 5 | 2 |
| Latency and version control | 2 | 5 |

Each score is multiplied by a weight: 1 nice to have, 2 important, 3 very important. With every weight at 2, the hosted API scores 2 × (2 + 2 + 5 + 5 + 2) = 32. The self-hosted engine scores 2 × (5 + 4 + 1 + 2 + 5) = 34. The gap is small, so the weights decide.

Cost needs its own arithmetic. From 11.4, a GPU at 2 dollars an hour producing 2,500 tokens a second costs 2 ÷ (2,500 × 3,600) × 1,000,000 = 0.22 dollars per million tokens when it is always busy. At 25% busy the same GPU costs 0.89. Say a hosted API charges 0.50 dollars per million tokens. All of these are invented numbers. Self-hosting is cheaper only above 0.22 ÷ 0.50 = 44% utilization, and that leaves out the people who run it.

## What each side hides

Self-hosting is not only a bill for GPUs. Someone is on call when the server runs out of memory. Someone upgrades the engine, and the defaults change. The GPUs sit idle at night, and the 44% bar gets harder to reach. A hosted API hides all of that, but your prompts leave your network, the provider can change the model underneath you, and the price per token is the one you are given.

Many teams mix the two. A small model on their own GPU answers the easy questions, and a hosted API answers the hard ones, with a router like the one in chapter 4.5. The method does not change: score the options, weight what matters, and check the cost against real utilization.

## Failure modes and debugging

- **The model loads but every request is slow or preempted:** the weights fit and the cache does not. Compute the room per GPU, as in the table.
- **Tensor parallelism got slower than expected:** the GPUs are linked over slow connections. Keep tensor parallelism inside one machine.
- **The self-hosted bill beats the API in a spreadsheet and loses in reality:** utilization was assumed at 100%. Measure how busy the GPU is.
- **The engine's port is open to the internet:** an API key is not enough. Add a gateway that authenticates every route.

## In the interview

Expect "will it fit?" and "should we run it ourselves?" in the same round. Strong answers give the arithmetic, name the trade-off, and say what they would measure. Answer each question aloud first, then open it.
