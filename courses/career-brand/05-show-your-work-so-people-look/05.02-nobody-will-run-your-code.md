Moath's app was fine. The trouble was the path to it. This chapter is about the path a stranger takes to your work, and how to make it short.

## Nobody will clone and run it

<MermaidDiagram title="Two ways to meet your work" chart={`flowchart TD
  L["A reader gets your link"] --> A["Run the code: clone, install, set up, start a database"]
  L --> B["Open a page or a short recording"]
  A -->|"each step can fail"| X["Many readers leave"]
  B --> R["The reader sees the result"]
`} legend="On the first path, every step before the app is a place to leave. On the second path, the result comes first." />

A reader who gives you a moment will not spend it on setup. Setup costs time, and any step can fail on their machine, not yours. So do not make running the code the way in. Give the reader a faster way to see the work, and keep the code for the reader who wants it.

<GoDeeper title="Why code comes second">

A software company that publishes how it hires says it screens by cover letter and resume first, and looks at work later. That is one company, so treat it as an example. It still shows the usual order. A reader meets the top of your kit before they meet your code. By the time anyone might run it, they have already decided whether you are worth the effort.

A demo link has the same problem in a smaller form. A link alone can be asleep, expired or empty. So give the reader more than the link: a short recording, and a measured result. If the demo works, it is a bonus. If it does not, the reader still has something to look at.

Some readers will clone the code. A technical reviewer may, late in the process. Write the README so it also works for them. The point is only that running the code should never be the first thing you ask for.

</GoDeeper>

<GoDeeper title="Count the steps in your own project">

Open the README of one of your projects. Read it as a stranger. Count every step before a first screen appears: clone, install, set variables, create a database, set up its tables, start a server. Write the number down.

Each step is a place to leave. If the number is more than two or three, one of the next two ideas will help. A deployable unit with one command removes most of the steps. A page that needs nothing, such as a case study with screenshots, removes all of them. You will use both ideas in the rest of this module.

</GoDeeper>

## A deployable unit runs the same anywhere

<InteractiveCanvas slug="career-m5-same-box" />

Watch the box move. A container is a box that holds your app and what it needs. The same box is built on a laptop and runs on a cloud server without changes. So the README can hold one start command, not a list of setup steps. A deployable unit is a project that starts the same way anywhere.

<GoDeeper title="What a container promises, and what it does not">

Docker's documentation describes a container as an isolated process that carries all the files it needs (checked 2026-10). It says a container that runs on a developer's machine should behave the same in the cloud. That is the promise: the same start, in two places.

It does not promise speed. A slow query is still slow inside a box. It does not promise that the host will keep your app awake. And it does not put your secrets in a safe place, so never build a real key into the box (chapter 5.3 explains why).

A project with a database needs the database to start too. The usual way is one small file that describes both parts, so one command starts them together. Whichever tool you use, the test is the same. Write the command in the README. Then try it in a clean folder, or on another computer, or ask a classmate to try it. If it fails, the README is not finished.

This course asks for a one-command start written in the README. It does not ask for deep container skills. If you have no laptop for this, or cannot install the tools, say so in your showcase plan. Then use the no-hosting path in chapter 5.3. Areej's plan for Raqim Stock is a container with a one-command start and a README.

</GoDeeper>

## The stranger's path to a first screen

<InteractiveCanvas slug="career-m5-stranger-path" />

A stranger follows your link and spends a little patience on each step. A sleeping demo and a sign-up can use it all. Tap a block, then move it up or down. Put the case study page and the screenshot first, so a useful screen comes before the wait and the form.

<GoDeeper title="What a free plan does to the first minute">

The sleeping demo in the picture is real. One host's free web service spins down after 15 minutes without traffic and takes about a minute to wake (checked 2026-10; check before you rely on it). A reader who opens your link at the wrong moment meets that minute. Then, if the app asks for an account, they meet a form and an email.

The picture counts taps, not seconds. We have no reliable number for how long a founder will wait, and the costs in the picture are made up. What the picture teaches is the order. Whatever needs nothing from the reader goes first.

Here is the sentence to remember: reviewers give you seconds, not minutes. If they have to make an account, many will leave. Let them in with one click or a ready demo login. Chapter 5.3 shows how.

</GoDeeper>

<GoDeeper title="The stranger test, in advance">

In chapter 5.6 you will run a stranger test. Someone who has not seen your work opens your link on a phone, with no help from you. You record the time to the first useful screen, and the two questions they ask.

Think about the test now, because it changes how you build. If the first thing a stranger would meet is a sleeping app or a sign-up, you already know what the test will show. Fix the order first, then run the test to learn what you could not see yourself.

</GoDeeper>

## A README in reader order

<MermaidDiagram title="Two orders for a README" chart={`flowchart TD
  T["Tutorial order: install steps first"] -->|"the reader leaves here"| U["What it is, at the very end"]
  R1["Reader order: one line on what it is"] --> R2["A screenshot"]
  R2 --> R3["Try it in a minute"]
`} legend="In tutorial order the reader pays for setup before learning what the project is. In reader order the reader knows what it is after one line." />

Your README is the first page of your project. Use five parts, in this order. Say what it is. Show it. Tell how to try it in a minute. Say how it was measured. Say what is not finished. A reader may stop at any line, so the best parts come first.

<GoDeeper title="What GitHub says, and what a study found">

GitHub's guidance on READMEs (checked 2026-10) lists what a README should tell. It should say what the project does, why it is useful, how to get started, where to get help and who maintains it. GitHub shows a README from the `.github` folder, the root folder or the `docs` folder, in that order. It cuts content after 500 KiB. A repository named like your username shows its README on your profile page.

A study of README files looked at 4,226 sections from 393 repositories. Information on what a project is and how to use it was the most common. Many READMEs left out the purpose and the status of the project. The study does not say who reads them, but it shows the same gaps a stranger will meet.

</GoDeeper>

<GoDeeper title="Areej's README outline for Raqim Stock">

Areej is planning Raqim Stock, a small stock and invoice tool for a print shop owner. She has not launched it, so her README says what is true today.

Part one is one line: a small stock and invoice tool for a print shop, with a warning when paper runs low. Part two is a screenshot of the low-stock warning and a link to the 90-second demo, with its size written beside it. Part three is the one command that starts the app and its database, with the link to the demo account. Part four is how it will be measured. The owner's notebook shows 5 stockouts in August and September 2025. The tool will log each stockout. She will compare the two months after launch and note what else changed. Until then she writes "not measured yet", not a result. Part five lists what is not done: supplier ordering, more than one shop and a mobile app.

Nothing in that outline is a boast. A reader can check every line, and the gaps are named before anyone asks.

</GoDeeper>

## Links that still work in six months

<InteractiveCanvas slug="career-m5-links-in-six-months" />

Watch day 30 arrive. A resume link can outlive the plan behind it. On one free plan, a database expires 30 days after it is created and is deleted 14 days later (checked 2026-10). The demo breaks, and so does the link. A static case study page has no clock on it.

<GoDeeper title="Free plans sleep, expire and change">

Here is a snapshot of free plans, checked 2026-10. Check before you rely on it, because plans change often.

One host's free web service sleeps after 15 minutes without traffic. Its free database is 1 GB and expires 30 days after creation, with a 14-day wait before deletion. A free page host allows sites up to 1 GB, with a soft limit of 100 GB of traffic a month. That service is not for running a business, a shop or a paid software product. Another host's free plan is for personal, non-commercial use only. A third allows 500 builds a month on its free plan. A fourth gives 300 credits a month, with a hard limit.

The lesson is not to avoid free plans. It is to point your resume at something that lasts: a static case study page and a short recording, with the live demo as a bonus. A static page is only files, with nothing to start, so it has nothing to put to sleep or to expire. Free hosting plans sleep, expire and change their rules. Check the plan page the week you publish, and keep a screenshot and a short recording as a backup.

</GoDeeper>

<GoDeeper title="Areej, and your own links">

Areej met this problem at the youth coding club. Her first deploy of the sign-up form used a free hosted database that the host deletes 30 days after creation. She noticed the date and moved the data before it expired. Her resume would have pointed at a dead link if she had not.

Do the same check now. List every link in your kit. For each one, write which plan it runs on, when that plan can expire, and what a reader sees if it is asleep. A link with no answer is a risk.

Also try each service on your phone early. Some hosts and sign-in services may not load, or may refuse sign-ups, from some places. We have not confirmed which work from where you are. If one does not, ask your mentor. Never use a VPN to get around it.

</GoDeeper>
