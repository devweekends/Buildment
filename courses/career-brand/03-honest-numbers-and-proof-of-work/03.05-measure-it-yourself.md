A dashboard shows what already happened. Sometimes you can measure for yourself, and then the number is easier to defend, because you chose how to collect it. This chapter shows how to plan a before and after that you control. One word first: a p95 is the time that 95 of every 100 requests finish within.

## Control the test, not the calendar

<InteractiveCanvas slug="career-m3-fair-test-claim" />

A test plan that compares last month with this month has other changes hidden inside it. Tap each part of this plan that a reader cannot trust. Each one says why, and gives what Areej actually did. The card then becomes her controlled plan: same script, same data, same laptop, a stated load, and one change.

<GoDeeper title="What to keep the same, and what to say">

Comparing one month with another is a weak design, because the season, the traffic and other releases can all differ. A test you control removes most of that. You keep four things fixed. They are the script that makes the requests, the data the system holds and the machine it runs on. The fourth is the load, which means how many requests arrive and how fast. Then you change exactly one thing, and run again.

You do not need a perfect lab. You need a fair one, and an honest sentence about its limits. Areej's limits are that she tested on a laptop, not production, and that her cache can serve a list up to 30 seconds old. A reader who sees those limits stated trusts the numbers more, not less.

Keep the script. The script is the proof that you ran the same test twice, and a reader can run it too. If you cannot run a controlled test, for example because you have no laptop, say what else changed in the window, as you learned in chapter 3.2.

</GoDeeper>

## Same script, same data, same machine

<InteractiveCanvas slug="career-m3-k6-fair-test" />

Areej runs one load test twice against her team's events list. Before the cache, the p95 is 820 ms and the 200 ms threshold fails. After a 30-second cache it is 95 ms and the threshold passes. The script, the data and the laptop never change. Only one box changes: the cache.

<GoDeeper title="What the test says, line by line">

The tool is k6, a load testing tool (version 2.3.0 when we checked in 2026-10). Her test sends a constant 50 requests per second for 2 minutes, which is about 6,000 requests. It runs against a database seeded with 10,000 events (filled with made-up demo data on purpose). The laptop is the same each time. Her threshold is a pass or fail rule: the 95th percentile of the request duration must stay under 200 ms. In k6 that is written p(95)<200 on the metric http_req_duration. If the rule is broken, the run ends with a failure code, so the result is not a matter of opinion.

The metric http_req_duration covers the time to send the request, wait for the answer and receive it. It leaves out the time to look up the address and to open the connection. Say that when you quote it. Her error rate stayed under 1 percent in both runs, so the fast result is not a pile of quick errors.

One more choice matters. A closed test model waits for each simulated user to finish before it sends the next request. So when the server slows down, the test eases off and hides the slowness. This is called coordinated omission. An open model keeps sending at a fixed rate, whatever the server does. Areej used an open model with a constant arrival rate. If you use Locust instead (version 2.47.0 when we checked), look at which statistics your installed version shows before you quote a p95.

</GoDeeper>

## A query plan pair

<InteractiveCanvas slug="career-m3-plan-pair" />

Areej runs the slow query on a staging copy (a private copy of the app used for testing) with the same data volume. The plan shows a sequential scan, with an actual time of 3,840 ms. After the index, the same query shows an index scan, with an actual time of 46 ms. The proof for a database fix is a pair of plans with real times.

<GoDeeper title="Reading a plan, and the one number not to quote">

In PostgreSQL, a command named EXPLAIN shows the plan the database chooses and its estimated cost. A second command, EXPLAIN ANALYZE, actually runs the query and adds the real timings. Because it runs the query, wrap any command that changes data in a transaction and roll it back, so the test leaves nothing behind. These facts come from the PostgreSQL 18 documentation, checked in 2026-10.

A sequential scan means the database reads every row of the table. An index scan means it uses the index to jump to the matching rows. Areej's table holds about 2.4 million orders, which is why reading all of them took 3,840 ms.

The plan also prints cost numbers. Cost units are arbitrary. They are not milliseconds and cannot be compared with time. Quote only the actual time, as Areej does: 3,840 ms before, 46 ms after. Run both plans on the same copy of the data, so the pair is fair. A plan pair proves what the database did. The team dashboard in chapter 3.2 proves what users met. Strong evidence uses both.

</GoDeeper>

## One audit run can mislead

<InteractiveCanvas slug="career-m3-five-runs" />

The same page is audited five times, and the scores scatter from 88 to 98. The median, the middle score, of the five is 93. One run on its own would have said 88 or 98, and both would be honest runs. A page audit is noisy. Run it several times and quote the median.

<GoDeeper title="Why the median, and why not a score alone">

Lighthouse is an open-source tool that audits a web page. You can run it in the browser's developer tools, on the command line, or through a web service. Its scores change from run to run because of the network, the machine and the page itself. Its documentation recommends several runs and the median, and says the median of five runs is about twice as stable as a single run. These scores are made up to show the spread. We checked in 2026-10 (Lighthouse 13.5.0).

To find a median, sort the scores and take the middle one. The five scores in order are 88, 91, 93, 96 and 98, so the middle is 93. With an even number of runs, take the mean of the two middle scores.

One more limit. A Lighthouse score is lab data, from your own machine. Google's Core Web Vitals are judged on real users' page loads, at the 75th percentile. The targets are loading in 2.5 seconds or less, responsiveness at 200 ms or less, and layout shift at 0.1 or less. Lab tools cannot measure responsiveness. So "a Lighthouse 98 proves my site is fast" is a misconception. Say what you measured, how many times, and that it was a lab score.

</GoDeeper>

## Time it as it is done today

<InteractiveCanvas slug="career-m3-timing-sheet" />

Before the script, Areej and the shop's assistant timed 64 invoices over two weeks. The median was 7 minutes. Two weeks after, they timed 61. The median was 1 minute. Both were timed the same way, as the work is done today. That is why a reader can trust the difference.

<GoDeeper title="A timing sheet, step by step">

A timing sheet is a simple table: the date, the task, the minutes it took, and who timed it. Areej kept one for 10 working days before the script and 10 after. She did not guess from memory, because people remember a task as quicker than it was.

Use the median, not the average. Here is an illustrative sample of seven invoice times in minutes, not her sheet: 5, 9, 7, 6, 8, 7 and 12. Sorted, they are 5, 6, 7, 7, 8, 9 and 12, so the median is 7. The average is 54 divided by 7, which is about 7.7. One slow invoice pulled the average up, and the median stayed put.

Her arithmetic follows from the sheet. About 31 invoices a week, at 6 minutes saved each, is 186 minutes gross. After 7 minutes of upkeep, it is 179 minutes, about 3 hours a week. Her 9 build hours repay in about 3 weeks. Chapter 3.3 explained why the net, not the gross, goes on the card. Two fortnights are a small sample, so the sheet also says what else changed: the invoice counts were 64 and 61.

</GoDeeper>
