The router you built in challenge 2 works, but there is a problem. Send a packet from the laptop to the server, and the server cannot answer. The packet arrives with the source `192.168.1.23`, a private address, and the server has no way back to it. Real home routers fix this every second of every day. In this chapter, you make your router do the same. You add one rule, and then you watch the router's own table to see how it does its job.

This is the build that answers the question of the whole course. By the end, two devices behind your router will reach a server on the other side, and the server will see only the router's outside address. You will have the proof in your own capture, and you will have read the real NAT table with your own eyes.

## What you build

You build a small home. A laptop and a phone sit on one side of a router. A server sits on the other side and plays the part of the internet. The laptop is `192.168.1.23`, the phone is `192.168.1.24`, and the router's inside address is `192.168.1.1`. On the outside, the router has `203.0.113.1`, and the server is `203.0.113.80`. The router joins its two devices with a bridge, a virtual switch that lives inside the router, so both devices share the inside address `192.168.1.1`.

The server runs a tiny web server on port 8080. It has one special page, `/cgi-bin/whoami`. When you visit it, the page tells you the address and port the server sees for you. That one page is how you check your work: it prints the truth about the packet, as the server received it.

## The four gaps

Start from the folder, **in the lab**:

```
cd /work/challenges/challenge-4-home-router/part-1-masquerade
```

The script builds the four computers, the bridge and the cables for you. It then pauses at four marked places, each called `TODO`. The first gap repeats what you did in challenge 2, so open your own `router.sh` if you need a reminder. The Hint ladder in the README gives three steps for each gap: a nudge, then the name of the tool, then the shape of the command. Try the nudge first, and open the next step only when you are still stuck.

**Gap 1** is forwarding and routes. A router only passes packets on when forwarding is switched on, and the devices need a default route that points at the router. Without forwarding, the router throws away packets that are not for itself. Without a default route, a device does not know the way out. Three things must happen: forwarding on in the router, and a default route through `192.168.1.1` in the laptop and in the phone. The shapes are `sysctl -w SETTING=VALUE` and `ip route add default via ROUTER_ADDRESS`, and each runs inside the right computer through the helper `in_ns`.

**Gap 2** is the masquerade rule. Masquerade is the kind of NAT where every packet leaving by one interface gets that interface's address as its source. You write the rule in nft, the Linux tool for packet rules. The table and the chain are already in the script, and the chain runs at the `postrouting` hook, which is the moment just before a packet leaves. Add one rule inside the chain. It has a match and an action: the match is the outside plug, and the action is `masquerade`. The shape is `oifname "INTERFACE" masquerade`. In nft, an interface name with a hyphen needs double quotes. Which plug is the outside one? The script names it where it makes the cable to the server.

**Gap 3** is the same-port experiment. Both devices must connect from source port 41000. The tool `curl` has an option for the local port. The laptop asks for the slow page, `/cgi-bin/slow`. Put it in the background with `&`, so that its conversation stays open. One second later, the phone asks for the fast page. Each answer goes into its own file, for example `same-port-laptop.txt`. The shape is `in_ns NAMESPACE curl -sS --local-port PORT URL > FILE 2>&1`.

**Gap 4** is the table. Read the router's NAT table with `conntrack -L`, and keep only the lines for port 8080 with `grep 'dport=8080'`. Save them in `conntrack.txt`. Hide conntrack's own note with `2>/dev/null`. The shape is `in_ns NAMESPACE conntrack -L 2>/dev/null | grep 'dport=8080' > FILE`.

Read three places. In the middle section, each device was seen by the server as `203.0.113.1` with a different port. If your two files show different ports, the clash worked.

## The capture, and the test that must fail

Now watch one conversation on both sides of the router. You have one terminal, so run both captures in the background with `&`. **In the lab**:

```
cd /work/challenges/challenge-4-home-router/part-1-masquerade
ip netns exec router tcpdump -n -i br-home -c 3 tcp port 8080 > inside.txt 2>&1 &
ip netns exec router tcpdump -n -i veth-rout -c 3 tcp port 8080 > outside.txt 2>&1 &
sleep 1
ip netns exec laptop curl -s http://203.0.113.80:8080/cgi-bin/whoami
wait
cat inside.txt outside.txt
```

The option `-i br-home` watches the home side, and `-i veth-rout` watches the outside plug. The option `-c 3` stops after three packets, which is the handshake. The words `tcp port 8080` keep the ARP and IPv6 chatter out. You should see the first packet, the SYN, twice: once on the inside with the source `192.168.1.23` and a port, and once on the outside with the source `203.0.113.1` and the same port. The address changed. The port did not, because nothing else used it. If your capture looks different, trust it and tell your mentor. Copy both captures into `results.md`, and answer the two questions beside them: which field changed, and which did not and why.

There is also a test that must fail. From the server, try to reach the laptop's private address, **in the lab**:

```
ip netns exec server curl -sS -m 3 http://192.168.1.23/
```

This fails at once, with curl exit code 7, and does not wait three seconds. The server has no route to a private address, so it cannot even try. Masquerade changes nothing about that. It rewrites packets that leave, and it does not open a way in. You will use this fact in 6.8, where a forwarded port opens exactly one way in.

## If it does not work

Work through this list in order. First, does the router have forwarding on? Run `ip netns exec router sysctl net.ipv4.ip_forward`. It should say `1`. Second, does `ip netns exec router nft list ruleset` show the rule, on the outside interface? The interface name in the rule must be the one that faces the server. Third, does the server show the packet arriving? Capture on the outside plug. If the packet leaves with a `192.168.1.x` source, the rule is not matching. Fourth, is the interface name in the rule the one on the outside? Run `ip netns exec router ip addr` to check.

If you want to start from a clean network, run `bash masquerade.sh` again: it deletes the old network first. If you are still stuck, `bash /work/toolkit/restore.sh 4.1` builds the finished network of this part, and your test still checks your own files. It runs the course's own answer, so use it only after you have tried. If the lab is slow for you, plan for 110 minutes instead of 75 and finish the mid-point first. Reusing a fixed source port right after it closed may fail, which is why the test picks a new random port each time. If your own run fails for that reason, wait a few seconds and run it again.
