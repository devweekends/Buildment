In 6.2 you watched a router keep a table, and in 6.5 you saw that every row has a timer. Now you turn both ideas into a function. A router is a program, and its table is data. If you can write the table as a short function, you understand exactly what a real router has to remember.

By the end you will have `createNat`, a small NAT with three methods. It translates packets that leave, translates replies that come back, drops packets it does not know, and forgets rows that sit idle. Challenge 4 builds the real thing out of Linux rules. This chapter builds a model of it that you can test in a second.

## A NAT is a map plus a clock

Think about what the router has to remember. For each conversation it needs the inside address and port, the outside port it chose, and the other end. Looking a conversation up by its inside half answers outbound packets. Looking it up by its outside port answers replies. And each row needs the time of the last packet, because 6.5 showed that silence deletes a row.

The diagram shows both directions. Read it from the top. Notice that both paths end in the same table, and that only the outbound path can create a row.

The takeaway: a NAT is a lookup table with a clock. The code is short because the idea is short. The work is in the edge cases, and the tests check those.

## The contract

Fix the promises before you write code. A packet is a plain object with five fields: `protocol`, `srcIp`, `srcPort`, `dstIp` and `dstPort`. The protocol is the text `"tcp"` or `"udp"`. Every call also takes `now`, the time in seconds. Your code never reads a real clock, which makes it easy to test. A test can ask what happens an hour later without waiting an hour.

The function `createNat({ publicIp, portRange, idleTimeout })` returns an object with three methods. The `publicIp` is the router's outside address. The `portRange` is two numbers, the lowest and highest port the router may hand out when it has to choose one, for example `[50000, 50099]`. The `idleTimeout` is the number of seconds a row may sit unused.

The method `outbound(packet, now)` is for packets that leave. If a live row already exists for the same conversation, it reuses that row. Two packets belong to the same conversation when all five fields match. Otherwise it makes a new row. The new row keeps the source port if no live row of the same protocol already uses that port on the public side. If the port is taken, it uses the lowest free port in the range. It returns the translated packet: the same protocol and destination, with the public address as the source and the public port as the source port. Either way, the row's timer restarts at `now`. If the port is taken and no port in the range is free, it returns the text `"drop"` and changes nothing at all. Existing rows stay as they are. A real provider NAT does the same: it drops the new flow and never deletes old mappings to make room [S19].

The method `inbound(packet, now)` is for packets that come back. Its packet has the remote end as the source and the router's public address and port as the destination. If a live row matches the protocol, the public port and the remote address and port, it returns the packet translated for the inside: the same source, with the inside address and port as the destination. The row's timer restarts. If nothing matches, it returns `"drop"`. That includes a packet to a known public port from a remote end other than the row's own, and a packet for any address other than `publicIp`. This is the exercise's rule. Real routers vary here [S18].

The method `table(now)` returns the live rows, as an array. Each row is an object with `protocol`, `insideIp`, `insidePort`, `publicPort`, `remoteIp` and `remotePort`, sorted by public port and then by protocol. Rows that have expired are not in it.

A row is alive while `now` minus its last time is less than `idleTimeout`. At exactly `idleTimeout` it is already gone. That boundary is the edge case that the tests hit hardest, and it matches the boundary in the slider of 6.5.

<Callout type="warning" title="This is a model, not a capture">
The exercise keeps the port unless it is taken, on the public side, by any live row of the same protocol. Linux is more careful. It checks the whole conversation, which means the outside address, the port and the destination, so it may keep a port that this model changes. A full range makes the model drop the new flow [S19]. The number your lab router chose in 6.2 and the numbers here are not meant to match.
</Callout>

## A worked example, for a smaller pool

Here is a short run for a different case, so you can see the rules together without seeing your own tests. The router has the public address `203.0.113.1`, a range of only two ports, `[60000, 60001]`, and an idle timeout of 100 seconds. All the packets are UDP.

At time 0 a device at `192.168.1.30` sends from port 5000 to `203.0.113.80:53`. Port 5000 is free, so the router keeps it, and the translated packet leaves from `203.0.113.1:5000`. At time 10 a second device, `192.168.1.31`, also sends from port 5000, to the same server. Port 5000 is taken, so the router uses the lowest free port in its range, 60000. At time 20 a third device does the same and gets 60001. At time 30 a fourth device does the same. Port 5000 is taken, and both ports in the range are taken, so the router returns `"drop"`. Notice what does not happen. The router does not throw out the first row to make room for the fourth.

Now the clock. At time 100, the first row has been idle for exactly 100 seconds, so it is gone. The second row is still alive, since 90 seconds have passed. If the fourth device tries again at time 100, port 5000 is free again, and the router keeps it. That is how a freed port comes back. A reply from `203.0.113.80:53` to `203.0.113.1:60000` at time 50 would be sent to `192.168.1.31:5000`, and it would restart that row's timer. If no reply came, the row would expire at time 110, and the same reply at time 200 would be dropped.

## Four ways this goes wrong

**A key without the remote end.** If a row is found by the inside address and port alone, then one device talking to two servers shares one row, and a reply from the wrong server is accepted. The same-conversation test uses all five fields. The wrong-remote test catches this.

**Forgetting to delete expired rows first.** The expiry test passes only if every method removes the dead rows before it looks anything up. If your code looks first and removes later, a dead row answers a packet it should have dropped, and a dead row keeps its port from being reused. Do the clean-up at the start of every call.

**The wrong boundary.** If you test `now - lastSeen > idleTimeout`, a row survives one second too long. At exactly `idleTimeout` the row must be gone. This is the failure-mode test. Compare with `>=` when you decide a row is dead.

**Evicting to make room.** When the range is full, the tempting fix is to delete the oldest row. The contract says no. A full range drops the new flow and leaves every old row alone. The test counts the rows before and after.

solution: |
  function createNat({ publicIp, portRange, idleTimeout }) {
    const rows = [];
    const [low, high] = portRange;

    function purge(now) {
      for (let i = rows.length - 1; i >= 0; i--) {
        if (now - rows[i].lastSeen >= idleTimeout) rows.splice(i, 1);
      }
    }

    function taken(protocol, port) {
      return rows.some((r) => r.protocol === protocol && r.publicPort === port);
    }

    return {
      outbound(packet, now) {
        purge(now);
        let row = rows.find(
          (r) =>
            r.protocol === packet.protocol &&
            r.insideIp === packet.srcIp &&
            r.insidePort === packet.srcPort &&
            r.remoteIp === packet.dstIp &&
            r.remotePort === packet.dstPort
        );
        if (!row) {
          let port = packet.srcPort;
          if (taken(packet.protocol, port)) {
            port = null;
            for (let p = low; p <= high; p++) {
              if (!taken(packet.protocol, p)) {
                port = p;
                break;
              }
            }
            if (port === null) return "drop";
          }
          row = {
            protocol: packet.protocol,
            insideIp: packet.srcIp,
            insidePort: packet.srcPort,
            publicPort: port,
            remoteIp: packet.dstIp,
            remotePort: packet.dstPort,
            lastSeen: now,
          };
          rows.push(row);
        }
        row.lastSeen = now;
        return { protocol: packet.protocol, srcIp: publicIp, srcPort: row.publicPort, dstIp: packet.dstIp, dstPort: packet.dstPort };
      },

      inbound(packet, now) {
        purge(now);
        const row = rows.find(
          (r) =>
            packet.dstIp === publicIp &&
            r.protocol === packet.protocol &&
            r.publicPort === packet.dstPort &&
            r.remoteIp === packet.srcIp &&
            r.remotePort === packet.srcPort
        );
        if (!row) return "drop";
        row.lastSeen = now;
        return { protocol: packet.protocol, srcIp: packet.srcIp, srcPort: packet.srcPort, dstIp: row.insideIp, dstPort: row.insidePort };
      },

      table(now) {
        purge(now);
        return rows
          .map((r) => ({
            protocol: r.protocol,
            insideIp: r.insideIp,
            insidePort: r.insidePort,
            publicPort: r.publicPort,
            remoteIp: r.remoteIp,
            remotePort: r.remotePort,
          }))
          .sort((a, b) => a.publicPort - b.publicPort || (a.protocol < b.protocol ? -1 : a.protocol > b.protocol ? 1 : 0));
      },
    };
  }

## Check before you submit

Run four cases by hand before you press the button, using the example pool above and no replies. Say what the table holds at time 99 and at time 100: three rows at time 99, and two at time 100, because the first row has been idle for exactly 100 seconds. Say what a reply to port 60001 at time 100 returns: the third device's address, since its last packet was at time 20 and 80 seconds have passed. And say what the fourth device gets at time 100: port 5000, kept.

## What this unlocks

In 6.7 you build the real thing with Linux and read its table with `conntrack -L`. You will find the same parts there: a row for each conversation, a port that is kept or changed, and a timer that counts down. When your lab router shows a number you did not predict, you will have a model to compare it with, and a clear idea of where the model is simpler than Linux.
