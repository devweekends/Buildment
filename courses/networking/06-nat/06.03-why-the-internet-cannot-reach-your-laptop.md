A friend wants to open the website that runs on your laptop at home. They type your public address. What happens to their packet? Two separate things stand in the way, and this chapter takes them one at a time.

## A friend types your public address

<InteractiveCanvas slug="net-m6-inbound-unsolicited" />

Your friend's packet reaches the router's outside address, `203.0.113.1`. Your laptop has not sent anything, so the NAT table is empty. No row says which device the packet is for. This is the question from 6.2 asked from the other side. Press Next and tap your pick to see what the router does.

<GoDeeper title="Go deeper: two separate reasons">

Two different things stop your friend, and it helps to keep them apart.

The first reason is about routes. Your laptop's own address, `192.168.1.23`, is private. The internet does not carry private ranges, so it has no route to them [S8, S9]. In the course's lab test, a server with no route to `192.168.1.23` failed at once, with curl exit code 7 [D5.6]. A friend who types the laptop's private address gets nowhere.

The second reason is about the table. If your friend types the router's outside address instead, the packet does arrive. But it is addressed to the router, not to the laptop, and no row ties it to a device. A NAT row exists only because a device inside sent a packet first [S17, S18]. Cloud networks work the same way. One cloud provider's NAT gateway says it passes traffic only from private instances out [S51]. In the lab test, a request to the router's port 22 with nothing listening was refused at once, not left to time out [D5.6].

</GoDeeper>

## No row, no rule: the router refuses

<MermaidDiagram title="Does the router know where to send it?" chart={`flowchart TD
  P["Packet arrives at the router's outside address"] --> Q{"A row from an earlier outbound packet?"}
  Q -->|"yes"| D1["Rewrite the destination, deliver to that device"]
  Q -->|"no"| R{"A forwarding rule for this port?"}
  R -->|"yes"| D2["Rewrite the destination, deliver to the rule's device"]
  R -->|"no"| X["The router answers: connection refused"]
`} legend="Top to bottom: a packet for the router's outside address meets two questions. A row or a rule sends it to a device. With neither, the router itself answers connection refused." />

A packet for the router's outside address gets through in only two cases. An earlier outbound packet made a row, or someone wrote a forwarding rule. With neither, the router answers "connection refused" at once. The friend does not wait for a timeout. Remember this picture: it explains most of what follows.

<GoDeeper title="Go deeper: refused is not the same as silent">

These two failures look different, and the difference is a clue. A refused connection means a computer received your packet and answered "no". With `curl`, that is exit code 7, and it comes at once [D5.6]. A timeout means nobody answered. With `curl -m 3`, that is exit code 28 after three seconds, as in the recorded run of challenge 4 part 2.

In the lab, the router has nothing listening on port 22 and no rule for it. So it answers at once. You will record this observation yourself in 6.8. Later, in 7.7, the same clue helps you tell a blocked port from an absent one. A router that drops packets silently gives the other symptom: the friend waits. Which one a real router gives depends on the router.

</GoDeeper>

## With a route, the outside gets in

<InteractiveCanvas slug="net-m6-route-leak" />

Give the outside server a route to `192.168.1.0/24` through the router. A packet addressed straight to `192.168.1.23` is then forwarded and reaches the laptop. The masquerade rule did not block it. The real internet has no such route to private ranges, and that missing route is what keeps it out.

<GoDeeper title="Go deeper: NAT is not a firewall">

The router forwards any packet it has a route for. You saw that in module 4, where a router with forwarding switched on passed packets between its two networks. A masquerade rule does one job: it rewrites the source of packets that leave by the outside plug. It does not look at packets that come in.

In the course's lab test, the outside server added the route `192.168.1.0/24` via the router's outside address, and its connection to the laptop succeeded [D5.6]. Without the route, the same request failed at once. The packet arrived with its original source address, because the masquerade rule in the lab acts on the outside plug only: `oifname "veth-rout" masquerade`. The laptop saw the server's own address on it.

So a router that only masquerades is not a firewall. Two things together keep your laptop private from the internet in a real home. First, the internet has no route to private ranges. Second, nobody has written a rule that lets a stranger in.

</GoDeeper>

## A forwarding rule opens one port

<InteractiveCanvas slug="net-m6-forward-rule" />

With <GlossaryTerm term="port forwarding" definition="A rule that sends packets arriving at one of the router's ports on to a device inside." />, one rule says: what arrives at `203.0.113.1:8080` goes to `192.168.1.23:80`. The router rewrites the destination, not the source. Other ports stay refused. Press Next, and tap your pick when the picture asks about port 22. You write this rule yourself in 6.8.

<GoDeeper title="Go deeper: the rule as nft wrote it">

This is part of the router's rules in the recorded run of challenge 4 part 2. It was printed with `nft list ruleset`.

```
	chain prerouting {
		type nat hook prerouting priority dstnat; policy accept;
		iifname "veth-rout" tcp dport 8080 dnat to 192.168.1.23:80
	}
```

The word `dnat` means destination NAT: the router rewrites the destination address and port, where masquerade rewrites the source. The chain is called `prerouting` because it runs when a packet arrives, before the router decides where to send it. It has to be that early. After the routing decision, it would be too late to change the destination. The rule reads: for packets that arrive on `veth-rout`, the outside plug, for TCP port 8080, send them to `192.168.1.23:80`.

The outside port is 8080, and the inside port is 80. They do not have to match. Two web servers at home cannot both be reached on port 80 of one outside address, so each needs its own outside port. Chapter 6.9 uses that. In the lab test, `http://203.0.113.1:8080/` from the outside returned the laptop's page [D5.6].

</GoDeeper>

## A filter is a separate rule

<InteractiveCanvas slug="net-m6-filter-rule" />

NAT rewrites addresses. It never decides who may come in. A <GlossaryTerm term="filter rule" definition="A rule that lets a packet pass or throws it away." /> does that, and it is a different rule in a different chain. This one drops packets from the guest network to the home network, so the guest's request times out.

<GoDeeper title="Go deeper: the filter as recorded">

<Callout type="warning" title="Do not assume your router has a filter">
Whether a real home router also filters depends on the router. The lab router has no filter until you add one, so everything it forwards, it forwards.
</Callout>

The rule and the result come from the recorded run of challenge 4 part 2. The rule sits in the `forward` chain, which sees packets that pass through the router:

```
		ip saddr 192.168.50.0/24 ip daddr 192.168.1.0/24 drop
```

When the guest asked for the laptop's page, the recorded output was:

```
curl: (28) Connection timed out after 3002 milliseconds
```

A `drop` rule throws the packet away without telling anyone, so the guest hears nothing and times out. That is the opposite of the refusal in beat 2. In the same test, the guest could still reach the server on the outside, and the server saw the router's address [D5.6]. You build both rules in 6.8.

</GoDeeper>

## docker run -p uses the same idea

<MermaidDiagram title="A published port is a forwarded port" chart={`flowchart LR
  F["Another computer: host port 8080"] -->|"NAT rules"| H["Your computer: docker run -p 8080:80"]
  H -->|"sent on to"| C["Container: port 80"]
`} legend="A request for port 8080 on your computer is sent on, by NAT rules, to port 80 inside the container. The shape is the same as the forwarding rule on your router." />

The command `docker run -p 8080:80` publishes the container's port 80 on port 8080 of your computer. Docker does this with firewall rules that perform NAT [S75]. It has the same shape as your forwarding rule: a port on the outside is sent on to a port on the inside. If you have used Docker, you have already used a forwarded port without knowing it.

<GoDeeper title="Go deeper: what the Docker page says, and what it does not">

The Docker documentation says that `-p` publishes a container port on the host "using firewall rules to perform Network Address Translation (NAT)" [S75]. The page names no rule type. So this course does not say which rule Docker writes, only that the idea matches the one you just built.

Docker puts the container on a network of its own. On the course's test host, the default Docker bridge was `172.17.0.0/16` [D5.5].

</GoDeeper>
