In 10.9 you read how YouTube's traffic went to the wrong network in 2008: someone announced a smaller block inside YouTube's block, and the routers that heard it preferred it, because the longer prefix wins. You also read what RPKI checks: a signed record says which network may announce a block. In this chapter you see both sides in your own lab. First a wrong announcement pulls part of r1's traffic to r2. Then you give r3 a filter that accepts r1's block only from r1, and the wrong route stops working.

This is challenge 7, part 4. It is **gapped**: the script `hijack.sh` is almost complete, and three small things are missing, each marked `TODO`. The test tells you which gap is wrong. The script builds the triangle of part 3 again, so do part 3 first.

Do this only inside your own lab. Announcing a block that is not yours on the real internet breaks someone else's service, and it can be a crime. The lab uses blocks and AS numbers made for documentation, which no real network uses.

Read it slowly. Both blocks have a `*`, because they are two different blocks, and BIRD picks a best route for each block on its own. Linux gets both rows. For `198.51.100.130` both rows match, and the longest prefix wins, so the visit goes to r2 and r2's page answers. For `198.51.100.1` only the `/24` matches, so r1 still answers. The end of the path, `[AS64497i]`, says r2 is the origin. r3 has no way to know that the origin is wrong. This is the YouTube case of 10.9, in miniature.

## Gap 2: a filter that knows the owner

Now you tell r3 who owns the block. A BIRD filter is a small rule that runs on every route a neighbour sends, and accepts or rejects it. The script already has the filter's frame. Gap 2 is its one missing line, the line that accepts:

```
filter owner_only {
  # Gap 2: one line that accepts the owner's own block
  reject;
}
```

Your line has the shape `if ... then accept;`, and it checks two things at once, joined by `&&`, which means "and". First, the block of the route, which BIRD calls `net`, must be exactly `198.51.100.0/24`, so a `/25` inside it does not match. Second, the last number in the AS path, the origin, which BIRD calls `bgp_path.last`, must be 64496, the owner. A route that passes both checks is accepted, and the `reject;` line drops every other route. If you are stuck, the hint ladder for Gap 2 in the part's README ends with the whole line.

The real `/24` that comes to r3 through r2 still passes. Its path is `64497 64496`, and the last number is the owner's. The filter checks who first announced the block, not who passed it on. That is the same idea as RPKI origin validation in 10.9.

## Gap 3: use the filter

A filter does nothing until a session uses it. Gap 3 sets r3's import line for both of its sessions:

```
R3_IMPORT='import filter owner_only;'
```

The script then tells BIRD to read its file again with `birdc -s /tmp/bird-r3.ctl configure`. No session restarts. The `/25` leaves r3's table, and the third look shows r1 answering for both addresses again:

```
--- after the filter
...
### r3 visits 198.51.100.130
r1 (AS64496), the real owner of 198.51.100.0/24
### r3 visits 198.51.100.1
r1 (AS64496), the real owner of 198.51.100.0/24
```

The rejected route is not lost. r3's sessions also have the line `import keep filtered on;`, so BIRD keeps rejected routes in a side list you can read:

```
$ birdc -s /tmp/bird-r3.ctl show route filtered
BIRD 2.14 ready.
Table master4:
198.51.100.128/25    unicast [to_r2 16:40:48.279] * (100) [AS64497i]
	via 10.0.23.2 on veth-to-r2
                     unicast [to_r1 16:40:48.326] (100) [AS64497i]
	via 10.0.13.1 on veth-to-r1
```

One more look shows that r3 is protected and r1 is not. r1 has no filter, so it still takes the wrong route:

```
$ birdc -s /tmp/bird-r1.ctl show route all 198.51.100.128/25
BIRD 2.14 ready.
Table master4:
198.51.100.128/25    unicast [to_r2 16:40:48.238] * (100) [AS64497i]
	via 10.0.12.2 on veth-to-r2
	Type: BGP univ
	BGP.origin: IGP
	BGP.as_path: 64497
	BGP.next_hop: 10.0.12.2
	BGP.local_pref: 100
```

A filter protects only the router that runs it. That is why RPKI protects the most when many networks check routes, and why one network that does not check can still pass a wrong route on.

## What your filter is, and what it is not

Your filter is a list written by hand, with one line. It knows one block and one owner, and it rejects every other block, which is fine in this lab, where r3 needs only r1's block. Real origin validation does the same check with signed records, called ROAs, that block owners publish and any network can fetch, for a huge number of blocks. Nobody types them into each router. A real router also usually keeps a route that has no record at all, instead of rejecting everything that is not on its list.

Origin validation catches a wrong origin, like the announcement you just stopped, and a prefix longer than the owner signed. It does not catch a route with the right origin that went somewhere it should not go, which is a leak, like the 1.1.1.1 case in 10.9.

## If it does not work

Does BIRD accept r3's file? **In the lab**, `bird -p -c r3.conf` prints nothing when the file is fine. Does r3 use the filter? `birdc -s /tmp/bird-r3.ctl show protocols all to_r2 | grep -E "Input filter|Routes:"` must show `Input filter:   owner_only`. If r3 has lost the real `/24` too, your accept line rejects everything: check the block, the `&&` and the number 64496. If the `/25` is still in `show route`, check Gap 3 and that the script ran `configure`. If r2's page never answers, check Gap 1: `ip netns exec r2 ip addr show dummy0` must show `198.51.100.130/25`.
