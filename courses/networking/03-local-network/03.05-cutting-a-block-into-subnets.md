You have `192.168.10.0/24` and need networks for 100, 50, and 20 devices. A useful plan must fit the devices, keep the pieces apart, and leave each piece on a valid start.

## Every cut halves a block

<MermaidDiagram title="Halving a /24" chart={`flowchart TD
 A["/24: 256 addresses"] --> B["/25: 128 addresses"]
 A --> C["/25: 128 addresses"]
 C --> D["/26: 64 addresses"]
 C --> E["/26: 64 addresses"]
 E --> F["/27: 32 addresses"]
 E --> G["/27: 32 addresses"]`} legend="Each added network bit halves the available address count." />

Follow one branch down the picture: each extra network bit cuts the address count in half. A /24 has 256 addresses, a /25 has 128, and a /26 has 64. Each child takes one half of its parent, so the two children meet without sharing an address. The different sizes come from the same bit rule you used to find network endpoints.

<GoDeeper title="Go deeper: every cut halves a block">

A prefix fixes the leading bits. Adding one fixed bit leaves one fewer free bit, so the number of combinations halves. That gives powers of two, not arbitrary lengths chosen to match a device count exactly. A network needing 100 ordinary host addresses cannot become a block of exactly 100 addresses.

The cuts in this picture are a plan for address space. They do not by themselves create switches, router connections, or access rules. Chapter 3.4 separated those jobs. Here you are solving the size and placement part so a later network can use the plan.

A parent block includes both children completely. If you keep one child whole and divide the other, you can serve unequal groups without giving each the same amount of space. That is the reason this example follows only one branch further down.

</GoDeeper>

## Pick the size for each network

<InteractiveCanvas slug="net-m3-split-size" />

Choose a prefix for each group and compare its usable count with the device need shown beside it. An ordinary subnet reserves its first and last addresses, so 100 devices need 128 total addresses and fit a /25. The groups of 50 and 20 fit a /26 and /27. Check usable capacity instead of matching the raw device count to total size.

<GoDeeper title="Go deeper: pick the size for each network">

Start by adding two to the ordinary host need, then find the smallest power of two that is at least that large. For 100 hosts, 102 does not fit in 64 but fits in 128. The smallest block is /25, with 126 usable addresses. For 50, 52 fits in 64, giving /26 and 62 usable. For 20, 22 fits in 32, giving /27 and 30 usable.

The edge matters. A /25 holds 126 ordinary hosts. The next device, number 127, requires a /24 under this rule. Counting 128 total addresses as 128 assignable addresses would hide that change.

This planning exercise uses ordinary shared subnets. It does not use the /31 point-to-point exception from 3.2. A need of one or two ordinary hosts still receives at least a /30. Later code tests use exactly that contract.

</GoDeeper>

## Place the biggest block first

<InteractiveCanvas slug="net-m3-split-place" />

Drag the 100-device block into the parent and watch it occupy `192.168.10.0` through `192.168.10.127`. Its /25 uses the first half, leaving the second half available for smaller groups. The first free address is now `.128`, rather than the address after the hundredth device. Reserved addresses and unused host capacity remain inside the allocated piece, so later groups cannot take them.

<GoDeeper title="Go deeper: place the biggest block first">

Sort the needs from largest to smallest before placing them. Here that means 100, then 50, then 20. Starting at the parent's first address, allocate the whole block for each need, including its reserved endpoints and spare capacity. The next free address is the previous block's last address plus one.

The largest piece has the most restrictive placement choices inside the parent. Placing small pieces first can occupy space that a large aligned piece later needs. Largest first keeps the arithmetic clear for this exercise. It is a planning method for this list of host counts, not a claim that every possible allocation problem is solved by one ordering.

After the /25, half the parent remains. That free half is itself a /25 and can be cut into two /26 blocks. You already saw that cut in the first picture. The next beat applies it to actual starts.

</GoDeeper>

## Each piece starts on its own boundary

<InteractiveCanvas slug="net-m3-split-boundary" />

Try dropping the /26 at `.100`, then read why the picture refuses that start. A subnet boundary is a start where every host bit is zero; a /26 therefore starts at multiples of 64 within this /24. The possible starts are `.0`, `.64`, `.128`, and `.192`. Only a start that is both aligned and still free can hold the next piece.

<GoDeeper title="Go deeper: each piece starts on its own boundary">

The proposed start .100 has host bits set for a /26. Applying the /26 mask to 192.168.10.100 gives 192.168.10.64. Writing .100/26 does not create a new block from .100 to .163; it identifies the existing .64 to .127 block. That block overlaps the first /25.

Choose 192.168.10.128/26 for the 50-device network. It occupies .128 through .191. The next free address is .192, which is a multiple of 32, so the 20-device /27 can start there. It occupies .192 through .223. The remaining .224 through .255 forms an unused /27.

The full plan uses 128 + 64 + 32 = 224 total addresses and leaves 32. Those totals include all allocated endpoints. Do not label the 32 free addresses as another group's host capacity until you decide how that group will use them.

</GoDeeper>

## Cut a block by hand

<InteractiveCanvas slug="net-m3-split-drill" />

Answer the size and start questions before using the feedback, then check the highlighted block against its parent. Use the same order each time: choose capacity, place on a boundary, and inspect the occupied range. If the size is right but the start is refused, keep the size and fix the alignment. A successful split needs both decisions, not just enough addresses in total.

<GoDeeper title="Go deeper: cut a block by hand">

VLSM means using different prefix lengths for different subnets inside one larger block. The name describes what you just did: the three groups received /25, /26, and /27 rather than three equal pieces. You do not need a separate arithmetic rule for the name.

Check a plan from left to right. Every start must equal the network result for that CIDR. Each end must remain inside the parent's end. The next start must be greater than the previous end, so no address is counted twice. Adjacent ranges are fine: .127 followed by .128 leaves no shared address.

For practice, change the last group from 20 to 31 devices. A /27 has only 30 ordinary hosts, so the third group now needs /26. The remaining half after the first two groups is .192 through .255, which is exactly one aligned /26. That larger plan fits, but leaves no free block.

Sources: [S7] RFC 950, dossier 4.2, masks and subnetting. Sizes, boundaries, usable counts, and the worked plan follow from the bit arithmetic taught in 3.2.

</GoDeeper>
