Your laptop wants to send a file to a friend at `192.168.1.40` on the same Wi-Fi. It knows the local IP address, but still needs a hardware address before sending the frame. [S22]

## You know the IP, not the MAC

<InteractiveCanvas slug="net-m3-scene-need-mac" />

The picture separates what the laptop knows from what it still needs: an IP destination is present, but the destination MAC is missing. A MAC is the hardware address used for delivery on the local link. The laptop must fill that missing field before sending the data frame to its friend, even though its mask already says the destination is local.

<GoDeeper title="Go deeper: you know the IP, not the MAC">

An IP address and a MAC answer different questions in this exchange. The mask has already placed the friend's IP address in the laptop's local network. Delivery on that link still needs a hardware destination. ARP, the Address Resolution Protocol, finds the mapping between those two values. [S22]

The scene stops at that missing information. It does not show a failed application transfer or measure a delay. The pause is there to make the missing field visible. In the worked model, the laptop is 192.168.1.23 and the friend is 192.168.1.40. Their fictional MACs start with 02. They are made-up labels so that you can follow the roles.

Before continuing, recall the broadcast MAC from module 1: ff:ff:ff:ff:ff:ff means everyone on the link. That gives the laptop a way to ask without already knowing the friend's hardware address. Your capture in 1.4 showed that destination.

</GoDeeper>

## Ask everyone: who has this address?

<InteractiveCanvas slug="net-m3-arp-exchange" />

Step through the request, reply, and saved mapping in this exchange; its sample laptop and phone use `.10` and `.20`. The request goes to the broadcast MAC, so every other device on this link hears it. Only the device that owns the requested IP answers, sending directly back to the asker. That answer provides the MAC needed for the next data frame. [S22]

<GoDeeper title="Go deeper: ask everyone: who has this address?">

The request carries both the target IP and the sender's information. Think of it as: who has this IP, and where should the answer go? It is a question to the link, not a question sent to a remote internet service. The reply names the target's MAC and returns to the requester. [S22]

The sample canvas uses the lab pair .10 and .20. The following table canvas returns to .23 and .40 from the chapter's opening. Those are separate fictional examples of the same exchange, not a claim that one host changes its address midway through a packet.

A third device hears the request but does not answer for an IP it does not own. Once the reply arrives, the data frame can use the learned destination MAC. The broadcast is the discovery step, not a requirement to broadcast every later frame to everyone.

</GoDeeper>

## The answer is remembered

<InteractiveCanvas slug="net-m3-arp-table" />

Watch the model ARP table gain a row linking `192.168.1.40` with its MAC, then follow a second send using that row. An ARP table stores the mappings a host has learned for local delivery. Use Start over to clear this model and repeat the steps; the empty table needs discovery again, while the filled table supplies the known destination directly. [S22]

<GoDeeper title="Go deeper: the answer is remembered">

On Linux, inspect real neighbour information with the following command. It is a command to run, not an example of its output.

```text
ip neigh
```

On Windows or macOS, the corresponding inspection command in this course is:

```text
arp -a
```

Look for an IP address beside a hardware address. Compare that relationship with the model's two columns. The model omits operating-system state labels and interface details, so do not expect a real terminal line to look identical.

ARP mappings are learned when needed. They are not a permanent directory of every device. RFC 826 leaves ageing details to the implementer; this chapter gives no timeout number. [S22] Start over resets only the picture's steps and model rows. It is not a command that clears your computer's table, and it does not simulate the passage of a particular number of seconds.

</GoDeeper>

## A switch learns where each MAC lives

<InteractiveCanvas slug="net-m3-switch-learning" />

Follow the frame arriving on port 2 and watch its source MAC enter the switch table beside that port. The switch learns where senders are by observing incoming frames, then uses its table when forwarding toward known destinations. An unknown destination is flooded to the other ports in this model. Keep this MAC-to-port table separate from the laptop's IP-to-MAC table. [S76]

<GoDeeper title="Go deeper: a switch learns where each MAC lives">

The first table belongs to a host. It answers which MAC belongs to a local IP. The second belongs to a switch. It answers which port leads toward a MAC. Confusing them makes it seem that a switch needs an ARP reply before it can learn a sender. In the model it learns from the source of the frame that just arrived. [S76]

Suppose the friend's frame arrives on port 2 while the laptop's location is still unknown. The switch records the friend's source MAC on port 2, then floods the unknown destination out its other ports. It does not send the frame back through the arrival port. When a later frame arrives from the laptop, the switch learns that source too.

The next frame toward a learned MAC can use one port. Broadcast frames remain broadcasts even after tables fill. The model shows a few entries without ageing, loops, or timing. The Linux bridge documentation describes this learning behaviour [S76].

</GoDeeper>

## Nobody owns the address: no reply

<InteractiveCanvas slug="net-m3-arp-no-owner" />

Step through a request for `192.168.1.99`, which no device in this model owns. The broadcast still reaches the other devices, but no owner sends a reply and no successful mapping appears. Being inside the local range does not prove an address is in use. The empty answer explains why the sender cannot build the expected data frame to that neighbour. [S22]

<GoDeeper title="Go deeper: nobody owns the address: no reply">

This is the negative control from the earlier cable build: a test designed to fail for a known reason. The sender's mask includes .99, so it tries local discovery. The chosen address is deliberately unassigned in this lab, and there is nobody to supply its MAC.

In a test of the course lab, ping with -c2 -W1 showed two packets sent and none received. The ARP requests went unanswered. The test did not show a Destination Host Unreachable line with those flags, so that wording is not promised here.

Do not generalise from silence alone. A ping with no answer can have other causes. This model explains one controlled case because its device list tells you nobody owns the target. In 3.9 you compare it with a different failure on the same virtual cable.

Sources: [S22] RFC 826. [S76] Linux bridge documentation: a bridge learns source MAC addresses and floods frames for unknown destinations. The ping test and the broadcast capture come from the course lab, run on 2026-10-24 and 2026-10-26.

</GoDeeper>
