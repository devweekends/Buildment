The pictures in 3.2 used the same calculation for every address. Now write that calculation once and expose four small functions. The job is to turn a CIDR into a numeric range, then answer questions about that range.

Keep your address conversion skills from 2.5. The starter includes reference versions of those helpers so this exercise can run by itself. Your work here begins with the slash prefix. You do not need a network connection or a command-line tool to complete it.

## Four answers share one boundary

A shared helper keeps the four functions consistent. If each function parses the prefix differently, one could accept a bad value that another rejects. Decide the input rules first. Then every result comes from the same validated address, prefix, and mask.

The network function returns the first address as dotted text. The broadcast function returns the last address as dotted text. Size returns a number, not text. Contains returns true or false after checking whether the second address lies inside the inclusive range.

## The input contract

A CIDR is an address, one slash, and a prefix from 0 through 32. Each address part must contain decimal digits only, with no leading zero unless the part is exactly 0. There must be four parts, each from 0 through 255. Spaces, signs, missing parts, and extra slashes are invalid. These are the strict course parsing rules.

The prefix also has no leading zeros. A prefix written 024 is rejected even though a permissive number conversion could read it as 24. Validate the text before converting it. Otherwise an empty string or a space can quietly become a number and pass a range check.

An address inside the CIDR may have host bits set. For example, network("192.168.1.23/24") returns "192.168.1.0". This normalisation is intentional. The caller may provide a device address and ask which block contains it. Rejecting every nonzero host part would prevent that useful operation.

Bad input throws an Error whose message starts with invalid. Apply that rule in every function. Contains must validate its second argument even when the input looks outside the block. Do not use an invalid address as a shortcut to return false.

## Follow one address through the steps

Take the campus address from 3.1, `10.20.143.7/20`, and follow it by hand before you type any code. Your functions will do exactly this, so write each step on paper first.

Step one checks the text. The address has four valid parts, and the prefix is the plain number 20. Step two builds the mask. A /20 has twenty 1 bits followed by twelve 0 bits, which is `255.255.240.0` as four bytes. The mask depends only on the prefix, so you build it once and every function reuses it.

Step three is the AND. The first two parts, 10 and 20, meet mask bytes of 255, so they pass through unchanged. In the third part, 143 is `10001111` and 240 is `11110000`. The AND keeps the first four bits and clears the rest, which gives `10000000`, or 128. The last part, 7, meets a mask byte of 0 and becomes 0. The network is `10.20.128.0`.

Step four sets every host bit to 1. The host bits are the twelve bits where the mask has 0. In the third part they are the last four bits, so `10000000` becomes `10001111`, which is 143. The whole last part becomes 255. The broadcast is `10.20.143.255`. Step five is only arithmetic: twelve host bits give 2 to the power 12, which is 4,096 addresses. Step six is `contains`. It asks whether a number lies between the first and the last address. The address `10.20.144.0` is one above the last, so it is outside.

If your code gives a different answer for this one address, you now know which step to inspect, because you have the value of every step on paper.

## Numeric endpoints and host use

Size means total addresses. It does not subtract the network and broadcast reservations. Contains also includes both endpoints. Those choices make these functions useful for comparing address blocks, where the first and last numbers still belong to the range.

The smallest prefixes have explicit conventions. A /32 has one address, so network and broadcast both return that address. A /31 has two numeric endpoints. On a point-to-point link it has no directed broadcast, but this exercise's broadcast function still returns its higher number. [S70] This is a calculator convention, not a packet instruction.

A /0 contains the whole IPv4 space. Its size is 4,294,967,296, its first address is 0.0.0.0, and its last is 255.255.255.255. Those endpoints are numeric boundaries. They are not example public servers to contact. The same distinction applies to the /1 test's boundary at 128.0.0.0.

<Callout type="warning" title="A shift by 32 wraps">
In JavaScript, 1 &lt;&lt; 32 is 1, and -1 &lt;&lt; 32 is -1. Use 2 ** (32 - prefix) for size and a separate /0 mask branch.
</Callout>

The size can exceed the largest individual address by one. Do not force size through >>> 0, because that would turn the /0 count into zero. Apply unsigned conversion to address bit results, not blindly to every number in the program.

  function ipToNumber(ip) {
    if (typeof ip !== "string") throw new Error("invalid address: expected text");
    const parts = ip.split(".");
    if (parts.length !== 4) throw new Error("invalid address: need four parts");
    let value = 0;
    for (const part of parts) {
      if (!/^(0|[1-9][0-9]{0,2})$/.test(part) || Number(part) > 255)
        throw new Error("invalid address: bad part");
      value = value * 256 + Number(part);
    }
    return value;
  }
  function numberToIp(n) {
    if (!Number.isInteger(n) || n < 0 || n > 4294967295)
      throw new Error("invalid address number");
    return [n >>> 24, (n >>> 16) & 255, (n >>> 8) & 255, n & 255].join(".");
  }
  function subnet(cidr) {
    if (typeof cidr !== "string") throw new Error("invalid CIDR: expected text");
    const parts = cidr.split("/");
    if (parts.length !== 2 || !/^(0|[1-9][0-9]?)$/.test(parts[1]))
      throw new Error("invalid prefix");
    const prefix = Number(parts[1]);
    if (prefix > 32) throw new Error("invalid prefix");
    const ip = ipToNumber(parts[0]);
    const mask = prefix === 0 ? 0 : (0xffffffff << (32 - prefix)) >>> 0;
    const start = (ip & mask) >>> 0;
    const end = (start | ~mask) >>> 0;
    return { ip, prefix, start, end, size: 2 ** (32 - prefix) };
  }
  function network(cidr) { return numberToIp(subnet(cidr).start); }
  function broadcast(cidr) { return numberToIp(subnet(cidr).end); }
  function size(cidr) { return subnet(cidr).size; }
  function contains(cidr, ip) {
    const range = subnet(cidr);
    const n = ipToNumber(ip);
    return n >= range.start && n <= range.end;
  }

## What a test run shows you

The tests run in the order they are written, and each one has a name that tells you what it checks. The first uses ordinary ranges, including the campus /20 and a /23 whose network starts in a different third number than the address. The second uses the edge prefixes: /31, /32, /0, /1 and the highest address. The third checks `contains` at both endpoints and one step outside each. The last two check bad input. When a test fails, its message names the CIDR or the address that broke. Work on the first failing test before you look at the others, because one mistake often fails several tests at once.

## Mistakes that the tests are built to catch

Most failures come from a small set of habits. Know them now, and you will recognise them in the messages.

The first habit is to reject an address with host bits set. It feels careful, but the contract says to normalise. `192.168.1.23/24` is a valid question, and the answer for `network` is `192.168.1.0`.

The second habit is to subtract 2 from the size. Size means total addresses, and the tests expect 256 for a /24, not 254. The subtraction belongs to planning in 3.5, where you count devices. It does not belong in a function that describes a range.

The third habit is to convert the prefix with a forgiving function and check only the number. A space, an empty string or a leading zero can pass through that way. Check the text of the prefix first, with the same strictness as the address parts, and then convert it.

The fourth habit is to forget that `~mask` is a signed number in JavaScript. Taking the OR of the network with `~mask` gives the right bits, but the result can be negative. Finish with `>>> 0`, as the predict above showed, before you format it or compare it.

The fifth habit is to let `contains` skip validation when the answer looks obvious. A string such as `192.0.2.256` must throw even when the block is a /8 that would not have held it. A function that sometimes validates is harder to trust than one that always does.

## Read failures as evidence

Start with an ordinary /24, then run the campus /20. If only the /20 fails, look for a shortcut that treats whole bytes as the only possible boundary. If /0 fails, inspect the size expression and the zero-prefix mask branch before changing the ordinary cases.

Next inspect contains at both endpoints and immediately outside them. These tests distinguish inclusive membership from ordinary host assignment. Finally run malformed input tests through all four functions. A correct calculation does not excuse an input parser that silently accepts a broken CIDR.
