Until now, you gave every device its address by hand. That was fine for three devices. It does not work for a house full of phones and laptops, and it does not work for a guest who arrives with a new phone. Typing an address into each device does not scale. In this part you give both subnets leases and names, so a new device can join without you.

You did the same job once in challenge 5, with one subnet. Now the router has two inside subnets, and one program must serve both. The new question is small and sharp: how does one program give two different answers, one to the home and one to the guest?

## One program, two ranges

The program is dnsmasq. It is a DNS forwarder with a cache and a DHCP server in one program [S64]. You started it in challenge 5, in the router. It can serve more than one subnet at the same time. It does this with a range for each subnet. A range says which addresses it may hand out, and on which inside interface.

Each subnet also needs its own gateway and its own DNS address in the lease. For the home it is `192.168.1.1`, and for the guest it is `192.168.50.1`. Those are the router's addresses on each subnet. The trick is a tag. You put a label on each range, and you attach an option to a label, so that only devices in that range receive it. You met this word in the challenge README: a tag is a label you put on a pool, and options with that tag go only to that pool.

Look at the pools. Both start at `.100` and end at `.150`. They are in different subnets, so the same numbers do not clash. They start at `.100` for a reason: `homeweb` is `.20`, and the placeholders are `.30` and `.31`. A lease can never land on one of them. The lease time is one hour. That is the default in dnsmasq [S64], and it means a device must ask again after an hour. A client starts to renew at half of the lease time [S23].

## The guest and the home rule

There is one more thing to think about before you build. The isolation rule from part 2 drops packets from the guest subnet to the home subnet. But the guest needs to ask its own router for a name. Does the rule block that question?

```predict
prompt: "The guest rule drops packets from 192.168.50.0/24 to 192.168.1.0/24. A guest at 192.168.50.30 asks the router at 192.168.50.1 for a name. Does the rule match that packet?"
options:
  - id: all
    label: "Yes: it drops every guest packet"
  - id: source
    label: "Yes: the source is the guest subnet"
  - id: none
    label: "No: the destination is not 192.168.1.0/24"
correctOptionId: none
explanation: "The rule needs both halves to match: the source in the guest subnet and the destination in the home subnet. The question goes to 192.168.50.1, which is not in 192.168.1.0/24, so the rule does not match it."
allowRetry: true
```

The rule has two halves, and a packet must match both. The question comes from the guest subnet, so the first half matches. It goes to `192.168.50.1`, which is not in the home subnet, so the second half does not. The guest can still ask its router for names, and a lab test will show it.

<Callout type="warning" title="Do not call a guest isolated too early">
A guest that can reach the router is not the same as a guest that reaches your home. The README says the rule is written for packets passing through the router, and the router's own address is not part of the home network. The challenge does not test a guest ping to `192.168.1.1`, which is an address of the router itself. Try it yourself, and write down what you see.
</Callout>

Three details save time. The first is the wait. In a lab run, dnsmasq with two ranges worked when the clients started about 3 seconds after it and retried. With a 1 second wait and only three tries, the first runs got no lease [D5.8]. That is why the README says to wait 3 seconds and to let each client try up to five times, two seconds apart. The second is the hook script. Ubuntu's `busybox` ships no default hook, so `udhcpc` prints the lease and does not apply it. A short hook script sets the address, the default route and the resolver file, and the toolkit gives you one [D5.8]. The third is the resolver file. Each computer in the lab has its own file, `/etc/netns/<name>/resolv.conf`, and `curl` reads it. The hook script writes the lease's DNS address there [D5.6].

The README hint ladder starts small. Hint one says only: one range per subnet, and ask which interface each range belongs to. Hint two shows where to look when it fails. Stop as soon as you can go on.

## What the test checks

The test looks at the running network. It checks that dnsmasq runs, that `home1` and `home2` have different leases in the home pool, and that `guest1` has one in the guest pool. It checks the gateway and the resolver of each, and it asks for `web.test` two ways: with `dig`, which asks one server, and with `curl`, which uses the resolver file. This is a recorded run of the reference solution:

```
PASS all seven namespaces exist
PASS dnsmasq is running (started with bg_start dnsmasq)
PASS home1 has 192.168.1.126/24 and home2 has 192.168.1.103/24, both in 192.168.1.100 to 192.168.1.150
PASS guest1 has 192.168.50.111/24, in 192.168.50.100 to 192.168.50.150
PASS home1's gateway is 192.168.1.1 and guest1's is 192.168.50.1
PASS home1's resolver is 192.168.1.1 and guest1's is 192.168.50.1
PASS home1: dig @192.168.1.1 web.test returns 203.0.113.80
PASS guest1: dig @192.168.50.1 web.test returns 203.0.113.80 (the guest can ask the router for names)
PASS home1: curl http://web.test:8080/ works, and the server sees 198.51.100.2
PASS guest1: curl http://web.test:8080/ works, and the server sees 198.51.100.2
PASS dig @192.168.1.1 nosuch.test returns no answer
PASS a brand-new device gets a lease (192.168.1.145/24), so the home pool still has room
PASS with dnsmasq stopped, a new device gets no lease and ends with no address after about 3 seconds
PASS dnsmasq is running again with your dnsmasq.conf
RESULT: all checks passed
```

Find the line that proves the guest can ask the router for names. It is the one that says `the guest can ask the router for names`. That is the answer to your prediction, in the lab's own words.

Two checks must fail on purpose. A name the router does not know, `nosuch.test`, gets no answer. In a lab run, dnsmasq with no upstream returned status REFUSED for an unknown name, not NXDOMAIN [D5.8]. And with dnsmasq stopped, a brand-new device gets no lease and ends with no address after about 3 seconds. The lab's client, `busybox udhcpc`, does not fall back to a `169.254.x.x` address here. That fallback is what Windows and macOS do [D5.6] [S12]. So in this lab, an empty `ip addr` is the sign of a DHCP failure. You will meet it again in part 4.

The test adds two throwaway devices and removes them again. It also stops dnsmasq for a moment and starts it again with your `dnsmasq.conf`. This means your config file must be the one next to the test.

## One lease on camera

The title means one recorded lease. The captures for this part show DHCP, the program you cannot see otherwise. Start `tcpdump -n -v` on the home bridge, filter ports 67 and 68, and ask for a lease. You should see four packets. This is what the four looked like in challenge 5, with the second line of each packet showing the message type:

```
    0.0.0.0.68 > 255.255.255.255.67: BOOTP/DHCP, Request from 3e:44:4a:51:79:fa, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: Discover
    192.168.1.1.67 > 192.168.1.136.68: BOOTP/DHCP, Reply, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: Offer
    0.0.0.0.68 > 255.255.255.255.67: BOOTP/DHCP, Request from 3e:44:4a:51:79:fa, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: Request

```

The client has no address yet, so its first packet comes from `0.0.0.0` and goes to `255.255.255.255`. The server answers the client's address directly. The ports are 68 for the client and 67 for the server [S23]. Fill in the table in `results.md`: who sent each packet, and what it means.

## If it does not work

Read dnsmasq's own log first. The README names the file. Then watch ports 67 and 68 while one device asks. A Discover with no Offer means dnsmasq has nothing to offer on that interface: no range, no listener, or a full pool. Next, ask the router directly with `dig @192.168.1.1 web.test`, which separates a DHCP problem from a DNS problem. The README also suggests `ss -ulnp` in the router to see what listens on UDP.

If a device gets an address but not the right gateway, look at the tags. A range and its options must carry the same label. If the name works with `dig` but not with `curl`, the resolver file of that computer is wrong. If everything fails, remember that parts 1 and 2 still work without DHCP. Fix one thing at a time.
