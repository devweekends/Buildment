Your scripts from challenges 2 and 4 each built one piece. In challenge 2 you built a router between two subnets. In challenge 4 you built a home router with a bridge. Now you join the pieces into one network. This is part 1 of four. By the end of part 4 you will have built, broken and repaired a small internet, and you will explain it in a short video.

This chapter has no new tool. It has one new skill: planning. A network with seven computers and four links is too big to build by typing commands and hoping. So you write the address plan first, then you build from the plan, and then the tests tell you if the plan is true. You can leave this page at any time. Every script tears down what it built before it starts, so a rerun after a mistake is safe.

## Plan first: one subnet for every link

Count the links. The home computers share one link. The guest has a link of its own. A short cable joins your home router to the provider's router. A last link joins the provider's router to the public web server. That is four links, so you need four subnets. Two links cannot share a subnet, because each subnet is one broadcast link, as you saw in module 3.

The table is the plan. Read it once, then look at the picture.

| Link | Subnet | Addresses |
|---|---|---|
| Home LAN | `192.168.1.0/24` | `hrouter` `.1`, `homeweb` `.20`, `home1` `.30`, `home2` `.31` |
| Guest LAN | `192.168.50.0/24` | `hrouter` `.1`, `guest1` `.30` |
| Home router to provider | `198.51.100.0/30` | `prouter` `.1`, `hrouter` `.2` |
| Public side | `203.0.113.0/24` | `prouter` `.1`, `server` `.80` |

Each number has a reason. The two private subnets are different ranges, so they never overlap. On the home, guest and public subnets the router takes `.1`, which is only a habit. The web server `homeweb` has a fixed address, `192.168.1.20`, because in part 2 a forwarded port must point at something that does not move. The addresses `.30` and `.31` are placeholders. They sit below the pool `192.168.1.100` to `192.168.1.150` that part 3 will use, so a placeholder never clashes with a lease.

The link between the two routers is a `/30`. That leaves 2 host bits, so it has 4 addresses. Two of them are the network and broadcast addresses, and two are left for the two routers. This is the smallest ordinary subnet that fits one cable with two ends. A `/31` can also number the two ends of a cable, as 3.2 showed [S70], but this capstone keeps the usual rule. The public side uses a documentation range, and so does the provider link. Only three documentation blocks exist, and `192.0.2.0/24` stays unused in this capstone [S10]. No real website uses these addresses, so nothing you do can touch the real internet.

Look at the home router. It has three plugs on three subnets. That is why it must forward: a packet from `home1` to `guest1` enters on one plug and leaves on another. Linux does not forward by default, because `ip_forward` is 0 until you switch it on [S28]. So both routers need it switched on.

## A test that must fail, and why it fails

Before you build, think about the one path that will not work. Every path in this part works except one. A home device can send a packet all the way to the server, but it gets no answer. Think about why before you read on.

```predict
prompt: "In part 1 there is no NAT yet. home1, at 192.168.1.30, pings the public server at 203.0.113.80. What does home1 see?"
options:
  - id: reply
    label: "A reply, as normal"
  - id: silence
    label: "No answer at all"
correctOptionId: silence
explanation: "The packet leaves with the private source 192.168.1.30. The public side has no route to a private range, so the answer never returns, and home1 hears only silence. [S8] [D5.6]"
allowRetry: true
```

The reason is the main idea of module 6. The packet carries a private source address. The server would have to send its answer to `192.168.1.30`. The public side has no route to a private range, and the real internet has none either [D5.6]. So the packet arrives and the answer is lost on the way back. This is why NAT exists, and part 2 adds it. In this part the failure is the proof: a test that only passes proves little, so the part also has a test that must fail, for the right reason.

Start with the script's first job: delete anything the course built before. After that, build from the plan. The order that works best is the order of the table, link by link. Give each link its cable and its addresses, and test the link with one ping before you go on. A ping to the router on each link is the cheapest proof that the link works. Then add the routes.

Routes are where people often make mistakes, so think about who needs which one. Every device sends everything else to its own router. `hrouter` sends everything else to `prouter`. The server needs a default route through `prouter`, so it has a way to answer. The provider router needs no route of its own: it is plugged into every subnet it forwards between, and Linux adds a connected route for each of them. Use `ip route get` to see the choice a computer makes. It shows the next hop, which is the path a packet would take [S32]. If two rows match, the most specific one wins, as you learned in module 4 [S30].

## What the test checks

Run `bash test.sh` after your script. It checks the plan, the routes and the paths. This is a recorded run of the reference solution in the lab:

```
PASS all seven namespaces exist
PASS hrouter has 192.168.1.1/24, 192.168.50.1/24 and 198.51.100.2/30
PASS prouter has 198.51.100.1/30 and 203.0.113.1/24, and the server has 203.0.113.80/24
PASS homeweb has 192.168.1.20/24
PASS home1 (192.168.1.30) and home2 (192.168.1.31) are on 192.168.1.0/24, guest1 (192.168.50.30) is on 192.168.50.0/24
PASS forwarding is on in hrouter and prouter
PASS home1 reaches its router, 192.168.1.1
PASS home2 reaches its router, 192.168.1.1
PASS homeweb reaches its router, 192.168.1.1
PASS guest1 reaches its router, 192.168.50.1
PASS hrouter reaches homeweb, 192.168.1.20
PASS hrouter reaches prouter, 198.51.100.1
PASS prouter reaches the public server, 203.0.113.80
PASS hrouter reaches the public server, 203.0.113.80, through prouter
PASS the public server sees hrouter as 198.51.100.2
PASS hrouter can read the home web server's page at 192.168.1.20:80
PASS home1: the route to 203.0.113.80 goes via 192.168.1.1
PASS hrouter: the route to 203.0.113.80 goes via 198.51.100.1
PASS traceroute from hrouter shows 198.51.100.1, then 203.0.113.80
PASS no NAT yet: home1 gets no reply from 203.0.113.80 (100% loss), as it should
PASS the capture on veth-hout shows the private source 192.168.1.30 leaving the home router
RESULT: all checks passed
```

Read the list from the top. First the plan is checked: the computers exist and the addresses are right. Then forwarding, then every device and its router, then the routers and the server. The line `the public server sees hrouter as 198.51.100.2` is the proof that `hrouter` reaches the server through `prouter`. The route lines prove the choices that `ip route get` makes. The `traceroute` line shows two hops, `198.51.100.1` and then the server. A lab run with one router in the middle showed the same two-line shape [D5.5].

The last two PASS lines are the ones that pass because something fails. With no NAT, `home1` gets 100% loss, and the capture on the home router's outside plug shows the private source address `192.168.1.30` leaving. That is the packet you predicted: it goes out, and nothing comes back.

<Callout type="warning" title="Two common mistakes in part 1">
The first is forgetting to give `prouter` its address on `198.51.100.0/30`. Its connected route for that subnet comes from the address, so without the address the route is missing too. The second is leaving forwarding off in one router. A ping to the router works, a ping through it does not, and nothing says why.
</Callout>

## Save your proof

The test is only half of the work. Fill in `results.md` and commit it. It asks for your prediction and whether you were right. It asks for your address plan, and for the `ip addr` and `ip route` output of both routers. It asks for the route a packet takes from `home1` and from `hrouter`, and for the capture of the failing ping. It also asks why `prouter` does not need a default route. Use your own output. Never copy the recorded lines above, because the mentor wants to see your run. The file ends with three questions about your home network that you cannot answer yet. Keep them. By the end of part 4 you will answer some of them.

## If it does not work

Work down in this order. First, run `ip route get 203.0.113.80` in each computer, starting with `home1`. Each answer should name the next hop you planned. Second, ping hop by hop: the router on the same link, then the next router, then the server. The first ping that fails shows where the chain breaks. Third, check forwarding in each router with `sysctl net.ipv4.ip_forward`. It must say 1.

Two other causes are common. If a script stops with a message about line endings, your editor saved Windows line endings, and the script says so in plain words. If you broke more than you can fix, run the script again, because it deletes the old network first. As a last resort, `bash toolkit/restore.sh 6.1` rebuilds the end of this part, so you can start part 2 anyway. Use it only after you have tried, because the learning is in the stuck moment.
