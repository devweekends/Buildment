Your network works. All three test sets pass. Now someone changes three things, and you do not know which three. This happens every day in real networks. A change is made, something stops, and the person who must find it has only the symptoms. In this part you learn to find a fault from evidence, and not from guessing.

You write no network code here. A script called `break.sh` is given. Your work is to read the symptoms, choose the right command, and say in words what the output means. That is a skill you keep after the course. Most of the hard part is not typing. It is looking at the right place first.

## The method: work down the layers

When something is broken, the temptation is to try whatever comes to mind. Do not. Start at the bottom and go up. The first check that fails names the layer. This is the order from module 7, and the picture puts a command on each step.

<MermaidDiagram title="The layer order for finding a fault" chart={`flowchart TD
  T["1 The test: bash test.sh, read the first FAIL"] --> A["2 Address: ip addr"]
  A --> G["3 Gateway: ping the router"]
  G --> R["4 Route: ip route get 203.0.113.80"]
  R --> N["5 Name: curl by address, then by name, then dig @router web.test"]
  N --> P["6 Page: curl gets the page"]
`} legend="Work down these six steps. Stop at the first one that fails. That step names the layer to look at." />

Why this order? Each layer depends on the one below it. A name cannot be looked up if the device cannot reach its router. A page cannot load if the name is wrong. If you test the page first and it fails, you learn almost nothing, because ten things could cause it. If you test the address first and it passes, you can stop worrying about it. Every check that passes shrinks the search.

Read the words of an error with care. They come from different places. `Network is unreachable` is printed by the computer itself: its own route table has no row for that destination. `Destination Net Unreachable` comes from a router, which received your packet and found it had no way to send it on. Silence comes from nobody, and it is the hardest case, because nothing tells you where to look. The same word in a different place is a different fault.

## How the faults are chosen

The script `break.sh` has a menu of seven faults. You give it a seed, which is any word or number. The seed picks three faults from the menu, and the same seed always picks the same three. So a mentor can repeat your run. The script saves your seed in `fault-seed.txt`. You put the same seed in your write-up.

Some faults are never drawn together, because they would hide each other. A missing default route and switched-off forwarding both break the way out of the home router, and each hides the other. A missing default route and a missing masquerade rule hide each other too. A wrong mask on the web server and a missing guest rule are hidden when the way out is already broken, and they are never drawn together. A device without a lease cannot show a DNS fault, so the DNS fault and the DHCP fault are never drawn together. One pair can be drawn together even though it looks alike: forwarding off and masquerade missing. Fix the first one, and then the symptom of the second one shows.

The menu is published. The draw is not. You see the seven faults, with a symptom and a finder for each, but you do not see which three you have. Do not run `break.sh --list` on your own seed, because it prints the answer. A mentor uses it to check your write-up.

| ID | Fault | What you may see | A command that finds it |
|---|---|---|---|
| F1 | Wrong mask on the home web server | `Network is unreachable` at once from `homeweb`; silence from `hrouter` to it | `ip addr` in `homeweb`, then `ip route` |
| F2 | Forwarding off on the home router | `home1` reaches the router, but `curl` hangs; a SYN arrives inside and nothing leaves | `sysctl net.ipv4.ip_forward`, `tcpdump -n` on both interfaces |
| F3 | Default route missing on the home router | `Destination Net Unreachable` from the router; `curl` fails at once | `ip route` and `ip route get` in `hrouter` |
| F4 | DNS port blocked on the home router | Leases work, `dig` times out, `curl` by address works | `curl` by address, then by name; `nft list ruleset` |
| F5 | Masquerade rule missing | `curl` hangs; a private source leaves the outside plug | `tcpdump -n` on the outside plug, `nft list ruleset` |
| F6 | DHCP pool too small | A new device ends with no address after about 3 seconds | `ip addr` in the new device, `tcpdump -n port 67 or port 68` |
| F7 | Guest rule missing | Nothing visibly breaks, but the guest can now reach the home web server, so the part 2 check that must be blocked reports a FAIL | the guest check in part 2's test, `nft list ruleset` |

Use the table as a map, not as an answer sheet. Your output may differ a little from these words.

## One fault, worked from start to end

This example is not valid for your write-up. A mentor can get it with `bash break.sh --only F3`. It shows the method on a fault you will not be asked to write up: the home router has lost its default route. Follow it step by step.

First the symptom. From `home1`, a ping to `203.0.113.80` gets `Destination Net Unreachable`, and it comes from `192.168.1.1` [D5.7]. Read who sent it. The router at `192.168.1.1` answered. So the first hop is fine: `home1` reaches its gateway. The router received the packet and does not know where to send it. The `curl` fails at once instead of hanging, which fits the same story.

Next, the test. Right after the fault, `bash test.sh` fails in all three parts. This is a recorded run of the course's check script, which injected the fault and printed the FAIL lines that the test sets print. I cut it to the lines that matter:

```
    FAIL hrouter reaches the public server, 203.0.113.80, through prouter FAILED. Ping said: ping: connect: Network is unreachable
...
    FAIL hrouter: ip route get 203.0.113.80 should say 'via 198.51.100.1'. It said: RTNETLINK answers: Network is unreachable
    FAIL traceroute from hrouter should show 198.51.100.1 then 203.0.113.80. It showed: traceroute to 203.0.113.80 (203.0.113.80), 5 hops max, 60 byte packets
```

Read the first line. `hrouter` itself cannot reach the public server, and ping says `Network is unreachable`. That phrase comes from `hrouter`'s own table. The second line says it again, with the command that shows the choice: `ip route get 203.0.113.80` has no answer. The layer is the route, in `hrouter`.

Now the finder. In `hrouter`, `ip route` lists three connected subnets and no line that starts with `default via`. That is the cause. The fix is one command that adds the default route back through the provider router: `ip netns exec hrouter ip route add default via 198.51.100.1`. It prints nothing. The last step is to run the test again and see the earlier tests pass. In the recorded run, the check script reported:

```
PASS F3: after the fix, all three test sets pass
```

Look at what you did not do. You did not add a route to the server, and you did not restart anything. You found the one cause and removed it. That is called the root cause, and a fix that does not remove it is only a patch.

<Callout type="warning" title="Fix the cause, one fault at a time">
A stray route can make one test pass and leave the cause in place. In a lab test, a server with a route to a private range could reach the laptop [D5.6]. Such a route hides a missing NAT rule for a moment, but the test about the address the server sees still fails. And if you fix two faults in one go, you cannot say which fix worked. Fix one, run the test, write it down, then look for the next.
</Callout>

Some rules keep the exercise honest. Fix one fault at a time. Never run your build scripts to fix things, because they rebuild the healthy network and erase the faults, and then you have learned nothing. If you break more than `break.sh` did, run `bash break.sh YOUR_SEED` again with the same seed. It rebuilds a healthy network and injects the same three faults. And every command in your write-up must be a command you really ran.

If you are stuck, try these in order. Run `ip addr`. Run `ip route get 203.0.113.80`. `ping` the gateway and then a public address. Use `curl` by address and then by name. Run `tcpdump -n` on both sides of `hrouter`. Then try `nft list ruleset` and `conntrack -L`. The hint ladder in the README starts with the layer order and ends with the fix. Open it one step at a time.

## What to write down

The write-up is the evidence of this part. A mentor reads it. For each fault, write five things. First, the symptom, with the exact output you saw. Second, the command that found the cause, with its output. Third, what that output means, in two or three short sentences. Fourth, the command that fixed it. Fifth, the test running again. Begin the file with the seed. Add the `FAIL` lines from the first `bash test.sh`, and say which layer you checked first and why.

The "what it means" part is the one most people skip. Do not skip it. Pasting output is easy. Saying "this line shows that `hrouter` has no default row, so every packet for the public side stops there" proves that you understood it. At the end, write what you would check first next time. A good answer is short and true to your run.
