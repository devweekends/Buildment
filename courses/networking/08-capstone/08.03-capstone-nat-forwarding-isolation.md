At the end of part 1 you had a network that almost worked. A packet from `home1` reached the server, and the answer never came back. At the same time, your guest could walk into your home network, because nothing stopped it. In this part you fix both problems. You also add one door: a single port that the outside can use.

A home router does exactly these three jobs. It hides every device behind one address. It lets one port through to a computer inside. It keeps guests away from the rest of the home. After this chapter, you can point at each job in your own rules and say which packets it touches.

## Three jobs, three places in the router

A router handles a packet in steps. Each rule runs at one fixed place in those steps, and the place is called a hook. The picture shows the three places that matter here, in the order a forwarded packet meets them.

<MermaidDiagram title="Which rule handles which packet" chart={`flowchart LR
  A["Packet arrives"] --> B["prerouting: dnat changes the destination"]
  B --> C{"Routing decision"}
  C --> D["forward: the guest rule can drop it"]
  D --> E["postrouting: masquerade changes the source"]
  E --> F["Packet leaves"]
`} legend="One packet through the home router. The forwarded port acts first, before the routing decision. The guest rule acts on packets passing through. Masquerade acts last, just before the packet leaves." />

The first job is masquerade. It runs last, just before the packet leaves by the outside plug. It rewrites the source address to the address of that plug, `198.51.100.2`. The nftables wiki calls masquerade a special case of source NAT. It takes the source address from the output interface. It is valid only in a postrouting chain of type nat [S43]. After this rule, every home and guest device looks like one address to the server.

The second job is the forwarded port. It runs first, before the router chooses a route, because it changes the destination. A request that arrives on the outside plug for port 8080 is sent on to `192.168.1.20`, port 80. That is the static web server `homeweb`. Only this one port is forwarded. The public side asks for 8080, and the home web server listens on 80.

The third job is the guest rule. It is not NAT at all. It is a filter in the forward chain, the one that sees packets passing through the router. The rule says: a packet from `192.168.50.0/24` to `192.168.1.0/24` is dropped. A drop is silent. The guest does not get an error. It gets nothing.

<Callout type="warning" title="Masquerade is not a firewall">
It is easy to think that NAT keeps strangers out. It does not. In a lab test, the server added a route to the private range, and then its connection to the laptop worked [D5.6]. What stops the real internet is that it has no route to private ranges. If you want a wall between guest and home, you write a rule. That is the third job.
</Callout>

## One question before you build

Look at the second job again. Only port 8080 is forwarded. Now imagine that the server tries a different port on the router's outside address, port 22, where nothing is listening and nothing is forwarded. What does the server see?

```predict
prompt: "From the server, curl connects to 198.51.100.2 on port 22. Nothing listens there, and the router forwards only port 8080. What happens?"
options:
  - id: refused
    label: "Refused at once"
  - id: timeout
    label: "Waits, then times out"
  - id: connect
    label: "Connects to homeweb"
correctOptionId: refused
explanation: "The address 198.51.100.2 belongs to the router, and nothing listens on port 22, so the connection is refused at once, not dropped in silence. [D5.6]"
allowRetry: true
```

Keep the difference in mind: a refusal answers at once, and a drop answers never. In the tests, a refusal ends `curl` with exit code 7, and a silent drop ends it with exit code 28 after a timeout. That one number tells you which of the two you are looking at.

## What the test checks

First the test looks for your rules. Then it checks what must work: `home1` and `guest1` both reach the public server, and the server reports `198.51.100.2` for both. The test never checks the port, because the port changes only when two devices would clash [D5.6]. After that, the server visits the forwarded port and gets the home web page across the provider router. This is a recorded run of the reference solution:

```
PASS all seven namespaces exist
PASS hrouter has a masquerade rule
PASS hrouter has a rule that forwards a port to 192.168.1.20
PASS home1 reaches the public server, which sees 198.51.100.2
PASS guest1 reaches the public server, which sees 198.51.100.2
PASS conntrack -L in hrouter lists a connection to 203.0.113.80:8080
PASS the server reaches the home web server through 198.51.100.2:8080
PASS guest1 cannot reach the home web server (curl timed out, exit 28)
PASS the server cannot reach 192.168.1.20 directly (curl exit 7, at once)
PASS an unforwarded port, 198.51.100.2:22, is refused at once (exit 7, Connection refused)
RESULT: all checks passed
```

Three lines in the middle are about things that must fail. Each one proves that a wall is there. `guest1` cannot reach the home web server. The request times out, which is exit code 28. The server cannot reach `192.168.1.20` directly, because it has no route to a private range. That ends at once with exit code 7. And port 22 is refused at once, as you predicted. In challenge 4 the guest's timeout looked like this:

```
--- the guest asks for the laptop's page (this must be blocked, so it times out):
curl: (28) Connection timed out after 3002 milliseconds
(blocked or failed, exit 28)
```

A test that must fail has a danger: it can fail for the wrong reason. If `hrouter` had forwarding off, the guest would also time out, and the test would pass without any isolation rule. That is why the part 4 fault script can hide an isolation fault behind a forwarding fault. Remember this when you read a "cannot reach" line.

## Read the NAT table

The test also checks that `conntrack -L` in `hrouter` lists a connection to `203.0.113.80` on port 8080. This table is the real memory of NAT. Here is one recorded line:

```
tcp      6 119 TIME_WAIT src=192.168.1.30 dst=203.0.113.80 sport=38676 dport=8080 src=203.0.113.80 dst=198.51.100.2 sport=8080 dport=38676 [ASSURED] mark=0 use=1
```

Read it in two halves. The first half is what the device sent: the source `192.168.1.30`, the destination `203.0.113.80`, the source port `38676` and the destination port `8080`. The second half describes the answer as it comes back to the router: from `203.0.113.80` to `198.51.100.2`. When the router sees such a packet, it looks up the row and sends the answer to the private address. The port in this line stayed the same. It is random on every run, which is why your test must not check it.

The forwarded port leaves a row too. When the server visits `198.51.100.2` on port 8080, the router changes the destination, and the table keeps the pair:

```
tcp      6 119 TIME_WAIT src=203.0.113.80 dst=198.51.100.2 sport=57244 dport=8080 src=192.168.1.20 dst=203.0.113.80 sport=80 dport=57244 [ASSURED] mark=0 use=1
```

Now the first half is what the server sent: to `198.51.100.2`, port `8080`. The second half is the answer, which comes from `192.168.1.20`, port `80`. It is the same table and the same reading, with the other job making the rewrite. Find these two kinds of line in your own output, and you can say which job made each one.

## Captures to commit

Three pieces of evidence feed your demo in part 4. Run `tcpdump -n` on both interfaces of `hrouter` while `home1` does one `curl` to `203.0.113.80` on port 8080. The inside capture shows `192.168.1.x` going to the server. The outside capture shows `198.51.100.2` going to the same server. One field changed between them, and it is the source address. Save the `conntrack -L` line for that connection, and the output of `nft list ruleset` in `hrouter`. Then answer the questions in `results.md`: which rule rewrites the source, which one rewrites the destination, and which one is a filter.

## If it does not work

Run `bash test.sh` and read the first FAIL. Then look inside the router with `nft list ruleset`, and check that all three jobs are there. Next, run `tcpdump -n` on the outside interface and look at which source address leaves. If it is still `192.168.1.x`, masquerade is missing or sits on the wrong interface. If the forwarded port hangs, check the rule, the web server on `homeweb`, and the route back. Fix one rule at a time and run the test again. Your part 1 still works underneath. If you want a clean start, `bash toolkit/restore.sh 6.2` rebuilds the end of this part.
