You deployed your app, and a friend says it is slow. You open it yourself: about two seconds before anything appears. Two seconds is long. But where did they go? The name had to become an address. The connection had to open. Your server had to build the page. Then the page had to travel back. Each step has a different owner and a different fix. Guessing wrong costs a day.

**curl answers one question: how long did each step of one visit take?** You met curl in 5.6 and in 12.1, where it only fetched a page or failed. With `-v` it shows every step of the visit as it happens. With `-w` it prints the time of each step when the visit ends. curl is in the lab. On Windows, type `curl.exe`, not `curl`, in PowerShell: there `curl` can be a different command.

## The four times of one visit

<MermaidDiagram title="Four times, all counted from the start" chart={`flowchart LR
  A["start"] --> B["name has an address<br>time_namelookup"]
  B --> C["TCP handshake done<br>time_connect"]
  C --> D["first byte of the answer<br>time_starttransfer"]
  D --> E["whole answer arrived<br>time_total"]
`} legend="Left to right, one visit. Each time is counted from the same start, so each one is at least as large as the one before. The gap between two times is how long that step took." />

The curl manual defines each time as the seconds from the start of the visit until one moment [S147]. `time_namelookup` ends when the name has an address. `time_connect` ends when the TCP connection is open, the handshake from 5.4. `time_starttransfer` ends when the first byte of the answer arrives, and so it includes the time the server needed to start answering. `time_total` ends when the whole answer has arrived. For an `https` address there is one more, `time_appconnect`, which ends when the TLS handshake is done [S147].

The first three lines are curl's progress meter, which `-v` does not switch off; the first note starts at the end of the third line. Lines with `*` are curl's own notes: the name was resolved, the address is `203.0.113.80`, it tries port 80, and it is connected. Lines with `>` are what curl sent: the request line `GET / HTTP/1.1` and three headers. Lines that start with a less-than sign are what it received: the status line `HTTP/1.1 200 OK` and the server's headers. The last line is the page itself: `lab web server`.

**Command two: time a fast page.** `-w` prints a text after the visit, and curl fills in each field name written with a percent sign and curly brackets. `-o /dev/null` throws the page away, because you want only the times. `-sS` hides the progress meter but still shows errors. The command is long, so copy it exactly, on one line:

```
ip netns exec laptop curl -sS -o /dev/null -w 'time_namelookup=%{time_namelookup} time_connect=%{time_connect} time_starttransfer=%{time_starttransfer} time_total=%{time_total}\n' http://www.lab.test/
```

```
time_namelookup=0.001876 time_connect=0.002322 time_starttransfer=0.003723 time_total=0.003864
```

Every time is a few thousandths of a second. The name took 0.0019 seconds. The handshake ended at 0.0023, so it took about half a thousandth. The first byte came at 0.0037. Every cable in the lab is virtual and short, so the whole visit took under four thousandths of a second.

## How to read the times

Because every time counts from the same start, read the gaps, not the numbers. Take the slow page:

| Step | How to work it out | Slow page |
|---|---|---|
| Name lookup (DNS) | `time_namelookup` | 0.0028 s |
| TCP handshake | `time_connect` minus `time_namelookup` | 0.0006 s |
| Server work, until the first byte | `time_starttransfer` minus `time_connect` | 4.0078 s |
| The rest of the answer | `time_total` minus `time_starttransfer` | 0.0002 s |

Almost all of the 4.01 seconds sat in one row: the server. So for the slow page the answer to the hook is clear. It is not DNS and not the connection. It is the server. A large first row would point at the resolver, as in 12.5. A large second row would point at the path or a far server, as in 12.4 and 12.7. A large last row would point at a big page on a slow path.

For an `https` address, add `time_appconnect` to the command. Then the TLS handshake is `time_appconnect` minus `time_connect`, and the server's work starts after `time_appconnect` [S147].

Now time your own deployed app, or any public page, **on your own computer**. Use the same command without `ip netns exec laptop`, and with your own address. For an `https` address, add the TLS field. This is an example to adapt, with `example.com` in place of your address. The course did not run it, so no output is shown here.


On Windows, type `curl.exe` in place of `curl`. The course has not tested this command in PowerShell. If it does not work there, run it in the lab itself, not in the laptop: the lab can reach the internet. Your numbers will be much larger than the lab's, because a real path crosses many routers. Run it two or three times, because one visit can be unlucky.

Then open the same page in your browser, open the developer tools, and choose the **Network** tab. Reload the page, and click the row for the page itself. Its timing view shows the same kinds of steps, drawn as bars, so the long step is easy to see. A phone browser has no Network tab, so on a phone use the recorded lab times above.

## The trap: reading a time as one step

`time_starttransfer=4.011277` does not mean that the server worked for 4.011277 seconds. It means the first byte came 4.011277 seconds after the start. The server's share is that number minus `time_connect`. On a fast lab cable the difference is tiny. On a real path to a server far away, the name and the handshake can take a large part of a second. If you read every time as its own step, you count those parts twice, and blame the server for the network's time.

One more small trap. If you give curl an address instead of a name, there is nothing to look up, and `time_namelookup` is close to zero. That is right, but it hides DNS. To time DNS, use the name. The part 7 test checks this: it fails a line whose `time_namelookup` is 0.

<GoDeeper title="Go deeper: what the times cannot tell you, and the other fields">

curl times one visit to one address. A real page in a browser is many visits: the page, then its styles, scripts and pictures, often from other servers. The browser's Network tab shows all of them, and that is where you see that one large picture, not the page, made the wait. curl is better for the first question: is the first answer itself slow, and in which step? It also gives you the same numbers every time you run the same command, so you can compare before and after a change.

The fields have more friends in the curl manual [S147]. `time_pretransfer` ends just before the request is sent. `remote_ip` prints the address curl really connected to, which is a quick check after a DNS change: did this visit use the new address? `http_code` prints the status code, such as 200. You can put any of them in the same `-w` text.

Here is the hook again, with numbers. Suppose your app prints `time_connect` 0.08 and `time_starttransfer` 2.1. The name and the handshake are done after eight hundredths of a second. The next 2.02 seconds are the wait for the first byte, so the server is the slow part: a slow query, a slow call to another service, or a page that takes long to build. That is the place to look first. If instead `time_namelookup` alone were 1.9, you would look at the resolver, with dig.

</GoDeeper>
