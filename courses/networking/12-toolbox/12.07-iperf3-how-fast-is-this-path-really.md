The office network is sold as 100 Mbit/s. A 500 MB file to the server should take under a minute, and it takes ten. Ping is fast. The web page loads. Only big copies crawl. Is the link slow, or is it losing packets? Both make the same complaint, and in 12.1 the script warned you that two different faults make it. You cleared fault 1 in 12.4. Now find the other one.

**iperf3 answers one question: how much data does this path really carry each second, in each direction?** Its project describes it as a tool for active measurement of the maximum bandwidth a path can achieve [S136]. One computer runs `iperf3 -s`, the server. The other runs `iperf3 -c ADDRESS`, the client. The client sends as much as it can for a few seconds, and both sides count what arrived. In the lab, the server already runs `iperf3 -s` on port 5201, its default port [S137]. On Ubuntu the package is about 0.2 MiB [S141]. To test a real path, you need iperf3 on both ends, so it suits two computers you own.

Clear fault 1 in 12.4 first. With loss and a speed limit in the network at once, the numbers mix.

## Where the limit sits

  S -->|"back: leaves the server by its own cable"| R2

Linux's queue tool, `tc`, shapes only the traffic that leaves an interface: its manual says shaping happens on egress, and netem's examples act on outgoing packets [S152]. So a limit on one interface slows one direction of the path, not both. Keep that in mind for command two.

## How to read iperf3

The last three lines are the summary.

| Part | Meaning |
|---|---|
| `Bitrate ... sender` | What left the program. It can be too high: part of it may still wait in a queue when the time ends |
| `Bitrate ... receiver` | What really arrived. **This is the speed of the path** |
| `Retr` | Retransmits: TCP segments the sender had to send again because they were lost (5.4) |
| `0.00-5.95` on the receiver line | The receiver needed almost one more second to empty the queue |
| `Lost/Total` (UDP) | Packets lost out of packets sent, and the share in brackets |

In command one the sender line said `17.2 Mbits/sec` and the receiver line `12.3 Mbits/sec`. Read the receiver line. The sender's program handed data to the network faster than the limit let it out, so for a moment the extra waited in r2's queue. The sender counted it as sent. The receiver got it almost a second later.

## The trap: two lines that mislead

The first misleading line is the **sender line**. It counts what the program handed over, not what arrived. In command one it was 40% too high. Always quote the receiver line. The test for this part checks your receiver line, and the gate does too.

The second is the **`Retr` column at high speed**. On the clean network, with no fault at all, iperf3 also shows thousands of retransmits:

```
[ ID] Interval           Transfer     Bitrate         Retr
[  5]   0.00-5.00   sec  9.96 GBytes  17.1 Gbits/sec  2579             sender
[  5]   0.00-5.00   sec  9.96 GBytes  17.1 Gbits/sec                  receiver
```

`2579` retransmits at `17.1 Gbits/sec`. At that speed, queues inside the lab overflow now and then, and TCP sends a little again. That is not a broken cable. So read `Retr` together with the speed. Many retransmits at a few Mbit/s means loss on the path. Many retransmits at many Gbit/s means a fast path pushed to its edge.

<GoDeeper title="Go deeper: why a limit is steady, why loss is not, and UDP above the limit">

A speed limit is a queue that lets packets out at a fixed rate. Packets that arrive faster wait their turn. Nothing is lost, so the speed stays flat: `11.5 Mbits/sec` in every line of command one after the first second. The first second shows `39.8 Mbits/sec` because the sender's data was still filling the queue. That is one more reason to quote the receiver line, not one second.

Loss looks different. Each lost segment must be sent again, as 5.4 showed, and the `Retr` column counts those. With one packet in ten lost, that happens many times each second. In the recorded fault 1 run the speed jumped between 6.29 and 37.7 Mbits/sec from one second to the next. The average is low, but for a different reason than a limit.

UDP shows the difference without TCP in the way. Below the limit, UDP at 2 Mbit/s lost nothing with fault 4, and about the planted loss with fault 1. Above the limit, a speed limit can lose packets too, once its queue is full. This recorded run sent UDP at 20 Mbit/s with fault 4, above the 13 Mbit/s limit:

```
[ ID] Interval           Transfer     Bitrate         Jitter    Lost/Total Datagrams
[  5]   0.00-5.00   sec  11.9 MBytes  20.0 Mbits/sec  0.000 ms  0/8632 (0%)  sender
[  5]   0.00-5.92   sec  8.91 MBytes  12.6 Mbits/sec  0.254 ms  2180/8629 (25%)  receiver
```

The sender sent 20 Mbit/s, the receiver got 12.6 Mbit/s, close to the limit, and 25% was lost: the packets that did not fit. That is why the challenge uses `-b 2M`, below any limit a seed can give, so that UDP shows real loss and not a full queue.

Two more options are worth knowing [S137]. `-P` runs several streams at once, and `-1` makes the server stop after one test. And one note on comparisons: iperf3 measures one path between two computers you control. It does not measure "your internet". A test to a server far away measures every network between you and that server, which is a different question.

</GoDeeper>

In `faults.md`, under **Fault 4**, the tool is `iperf3`, the command is your step 1, the output line is your receiver line, and the fix is your `tc qdisc del` command. The test compares speeds, never one exact speed. Your slow direction must be near your seed's limit, between half of it and a little above it, with fewer than 100 retransmits. Your `-R` must be at least five times faster. Your UDP must lose no more than 1%. Your speed after the fix must be at least ten times the limit. And r2's queue must have no `rate` left.

If the test says you have hundreds of retransmits, fault 1 was still in the network: go back to part 3, or you ran `bash faults.sh` again, which plants every fault again. If it says your speed is not near the limit, check that you copied the receiver line, not the sender line.
