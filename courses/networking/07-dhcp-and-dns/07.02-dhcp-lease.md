Your phone joined a café Wi-Fi it had never seen, and a second later it had a working address. Nobody typed a number. Who told it what to use?

## A new phone has no address

<InteractiveCanvas slug="net-m7-scene-no-address" />

The phone has a Wi-Fi link but no address, so it cannot send to anyone by number. It does the one thing it can: it shouts to everyone on the link. It uses `0.0.0.0` as its source, because it has no address yet. Only a <GlossaryTerm term="DHCP server" definition="A server that hands out network settings." /> answers.

<GoDeeper title="Go deeper: why the phone must shout">

The phone knows nothing yet: not its own address, not the mask, not the router's address and not the DNS server. It cannot send to the router by number, because it does not know the router's number. So the first message goes to everyone on the link, in the way the ARP request did in 3.3.

Two special addresses make this work. The phone sends from `0.0.0.0` and to `255.255.255.255`. The registry of special addresses lists both as not forwardable, so a router does not pass the shout on, and it stays on the café link [S9]. The client uses port 68 and the server uses port 67 [S23]. Both ride on UDP, which has no delivery guarantee [S26].

This is the first line of a real lease, recorded in the course lab. The addresses here are the lab's own, `192.168.1.x`, not the café's. Read it as: from `0.0.0.0` port 68 to `255.255.255.255` port 67.

```
    0.0.0.0.68 > 255.255.255.255.67: BOOTP/DHCP, Request from 3e:44:4a:51:79:fa, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: Discover
```

Notice that the first line says `Request` even though the message is a Discover. The second line gives the message type. Follow the second line.

</GoDeeper>

## Four messages hand out an address

<InteractiveCanvas slug="net-m7-dhcp-four-messages" />

Step through the four messages. The phone sends DISCOVER. The server answers with an OFFER of `10.5.0.84`. The phone sends a REQUEST for it. The server confirms with an ACK. The client uses port 68 and the server uses port 67 [S23].

<GoDeeper title="Go deeper: what each message says, and one lease on camera">

Each name is a plain question or answer. DISCOVER: is anyone there? OFFER: take this address. REQUEST: I take it. ACK: it is yours, for this long. The challenge in 7.6 uses the same words.

Here is one real lease, captured in the lab with `tcpdump`. The tool printed each packet on two lines. Read the second line of each pair: Discover, Offer, Request, ACK.

```
    0.0.0.0.68 > 255.255.255.255.67: BOOTP/DHCP, Request from 3e:44:4a:51:79:fa, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: Discover
    192.168.1.1.67 > 192.168.1.136.68: BOOTP/DHCP, Reply, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: Offer
    0.0.0.0.68 > 255.255.255.255.67: BOOTP/DHCP, Request from 3e:44:4a:51:79:fa, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: Request
    192.168.1.1.67 > 192.168.1.136.68: BOOTP/DHCP, Reply, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: ACK
```

Three things to notice. The two messages from the phone both start at `0.0.0.0` and go to everyone, because the phone has no address until the ACK. The two replies come from the server, `192.168.1.1` port 67, and go to `192.168.1.136`, the address on offer. And all four lines share the number `xid 0x88af800e`, which ties the four messages to one lease.

The picture shows the café network, `10.5.0.0/24`, with the pool `10.5.0.50` to `10.5.0.200`. The capture shows the lab's network. The shape is the same.

</GoDeeper>

## A lease carries more than an address

<MermaidDiagram title="What one lease holds" chart={`flowchart LR
  S["DHCP server, pool 10.5.0.50 to 10.5.0.200"] -->|"one address per phone"| L["Lease for one phone"]
  L --> A["Address 10.5.0.84"]
  L --> M["Mask 255.255.255.0"]
  L --> G["Gateway 10.5.0.1"]
  L --> D["DNS server 10.5.0.1"]
  L --> T["Lease time 3600 s"]
`} legend="The server picks one address from its pool for each phone. The lease carries five things. The address that websites see for the café is not one of them." />

A <GlossaryTerm term="DHCP lease" definition="The settings a server gives a device for a limited time." /> holds five things: an address, a mask, a gateway, a DNS server and a lease time. The server takes the address from its pool, one address for each phone. The public address that websites see is not in the lease.

<GoDeeper title="Go deeper: the five settings, and where they land on the phone">

Look at the five settings as answers to five questions. Who am I? The address. Which addresses are on my own network? The mask, from 3.1. Where do I send everything else? The gateway, from 4.2. Who turns names into addresses? The DNS server. For how long is this mine? The lease time. The <GlossaryTerm term="pool" definition="The range of addresses a DHCP server may give out." /> is the range the server draws from; the phone never sees it.

The default lease of dnsmasq is one hour, 3600 seconds [S64]. The café in this chapter uses that default.

The lab shows where the settings land. After a lease, the lab's laptop has an address on its interface, a default route through the gateway, and the DNS server in its resolver file. These lines are copied from the recorded run. The first line is what the client printed when it applied the lease.

```
lease applied: 192.168.1.144/24 router=192.168.1.1 dns=192.168.1.1 lease=3600s
```

```
24: veth-laptop    inet 192.168.1.144/24 scope global veth-laptop\       valid_lft forever preferred_lft forever
default via 192.168.1.1 dev veth-laptop
192.168.1.0/24 dev veth-laptop proto kernel scope link src 192.168.1.144
nameserver 192.168.1.1
```

The mask appears as `/24`. The gateway is the `default via` line. The DNS server is the `nameserver` line. The time is in the first line, `lease=3600s`. The public address is nowhere in these lines. It belongs to the router's outside side, which module 6 explained, and a lease describes only the local network.

</GoDeeper>

## A lease is a timer

<MermaidDiagram title="The life of a lease, with a 3600 s lease" chart={`flowchart LR
  N["No address"] -->|"DISCOVER"| Q["Requesting"]
  Q -->|"OFFER, REQUEST, ACK"| B["Bound: the phone has the lease"]
  B -->|"T1, half the lease, 1800 s"| R["Renewing: asks to keep it"]
  R -->|"server agrees"| B
  R -->|"T2, 0.875 of the lease, 3150 s"| RB["Rebinding: still trying"]
  RB -->|"lease ends, 3600 s"| E["Expired: the address is gone"]
  E --> N
`} legend="The lease starts at the ACK. At half the lease the phone starts to renew. At 0.875 of the lease it moves to rebinding. If the lease ends before the server agrees, the address is gone and the phone starts again with no address." />

A lease lasts a set time, here 3600 s. At half the lease, 1800 s, the phone starts to renew it. At 0.875 of the lease, 3150 s, it is still trying to keep the address [S23]. If the time runs out first, the address is gone. The phone starts again with no address.

<GoDeeper title="Go deeper: T1, T2 and the trade-off in a lease length">

The two timers have names. T1 is the time to start renewing. T2 is the time to move on to rebinding. By default T1 is half the lease and T2 is 0.875 of it [S23]. For a lease of 3600 seconds the numbers are 1800 and 3150.

| Moment | Fraction of the lease | Seconds, for 3600 s |
|---|---|---|
| Lease starts (ACK) | 0 | 0 |
| T1: start renewing | 0.5 | 1800 |
| T2: start rebinding | 0.875 | 3150 |
| Lease ends | 1 | 3600 |

A phone that stays on the Wi-Fi renews before the end, so it keeps the same address. A phone that leaves does not renew. Its lease runs out, and the address becomes free to hand out again. The next beat plays that out.

The length of a lease is a choice the owner of the network makes. With a short lease an address returns to the pool sooner. With a long lease the phones ask less often. The owner of the café picks one hour; dnsmasq uses the same by default [S64].

</GoDeeper>

## A small pool runs out

<InteractiveCanvas slug="net-m7-dhcp-pool" />

Three addresses, three phones, and a fourth arrives. The server has nothing to offer, so phone 4 gets no OFFER and no address. When a lease ends, its address is free to hand out again. This pool is made up and small, and the case is hypothetical.

<GoDeeper title="Go deeper: why the case is hypothetical, and what it shows">

The dossier found no incident report of a real pool running out, so the course labels this case hypothetical (dossier, section 7). The pool of three is a made-up size, chosen to make the effect easy to see. The café pool in this chapter has 151 addresses, from `10.5.0.50` to `10.5.0.200`.

The picture shows the rule behind it. An address belongs to one phone for the length of its lease [S23]. A server cannot give the same address to two phones, so when the pool is empty, the fourth phone waits. It does not get a copy of someone else's address, and it does not get the oldest address. The picture does not draw renewals: a phone that renews keeps its address.

What does the fourth phone see? It depends on the device, and the next beat shows how. The lab has a similar case as a test, with a different cause. In challenge 5 the lab stops the DHCP server instead of filling its pool, and a client ends with no address.

</GoDeeper>

## Failure looks different on each device

<MermaidDiagram title="No OFFER arrives: three devices, three results" chart={`flowchart TD
  X["The phone asks, and no OFFER comes back"] --> W["Windows"]
  X --> M["macOS"]
  X --> L["Lab Linux client: busybox udhcpc -n -q -t 3 -T 1"]
  W --> S1["Gives itself a 169.254.x.x address"]
  M --> S2["Gives itself a 169.254.x.x address"]
  L --> S3["Gives up after about 3 seconds, no address"]
`} legend="When no server answers, each client does something different. A 169.254.x.x address works on the local link only. The lab's Linux client does not invent one." />

When no server answers, each device does its own thing. Windows and macOS give themselves a `169.254.x.x` address [S12]. The lab's Linux client gives up after about three seconds and has no address. So never read `169.254` as "DHCP failed" on every device. It depends on the client.

<GoDeeper title="Go deeper: what a 169.254 address can and cannot do">

A host that finds no DHCP server may give itself an address in `169.254.0.0/16`. Routers must not forward these addresses, and the host asks ARP for every destination, as if all of it were on the local link [S12]. The registry marks the whole block as not forwardable [S9]. So such a phone can talk to a neighbour with the same kind of address, and it cannot reach the internet.

The lab's client is `busybox udhcpc -n -q -t 3 -T 1`. The options say: give up if there is no lease (`-n`), quit when done (`-q`), send up to three requests (`-t 3`), one second apart (`-T 1`). With no server it ends after about three seconds and the interface has no address. The challenge test checks exactly that, and prints this line:

```
PASS with dnsmasq stopped, the phone gets no lease and ends with no address after about 3 seconds
```

That is the result for this client in this lab. The course teaches the behaviour as client dependent. It does not claim what every Windows or macOS version does in every case; it claims what [S12] describes, and what the lab measured.

<Callout type="warning" title="A symptom is not a cause">
A `169.254.x.x` address tells you that this device found no DHCP server. A missing address on a Linux client tells you the same. Neither tells you why: the server may be off, the pool may be full, or the link may be broken. Chapter 7.5 shows the next check.
</Callout>
