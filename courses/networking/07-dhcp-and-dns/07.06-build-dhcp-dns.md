The router you built in challenge 4 already routes packets and rewrites addresses. But every device behind it still needs its address typed in by hand, and nobody can use a name. A real home router does two more jobs. It tells each new device who it is, and it answers when a device asks what a name means. In this chapter you give your router both jobs. By the end, a laptop and a phone join with no address typed in. They receive an address, a gateway and a DNS server. And the name `web.test` turns into the server's address.

You will do this with one small program, `dnsmasq`. It is a DHCP server and a DNS server in one [S64]. You will fill in the lines that tell it what to do, run it inside your router, and read what it did.

## One program, two kinds of question

Before the lines, you need one idea. Two different kinds of question go to your router. The first is "who am I?". A device with no address asks it, and the DHCP half of dnsmasq answers with a lease. You met this in 7.2. The second is "what is this name?". A device asks it when a program needs an address for a name, and the DNS half of dnsmasq answers. You met this in 7.3.

A client only benefits if it asks the right place. This matters because two commands in this chapter look alike and ask in different ways. The command `dig @192.168.1.1 web.test` asks that one server and nobody else, whatever the computer's own settings say. The command `curl http://web.test:8080/` asks the servers in the computer's own resolver file, which the lease fills in. If `dig` works and `curl` does not, the server is fine and the resolver file is wrong. If `curl` works and `dig` does not, you asked `dig` the wrong server. Keep the two apart, and you will find faults much faster.

Before you read on, read the manual entries for the three options that matter most.

<MustRead title="dnsmasq manual: --dhcp-range, --no-resolv and --bind-interfaces" url="https://thekelleys.org.uk/dnsmasq/docs/dnsmasq-man.html" source="dnsmasq manual" description="Read the entries for --dhcp-range, --no-resolv and --bind-interfaces. Afterwards you should be able to say what the range line carries, and why the lab turns off the upstream resolver." readMinutes={10} />

The manual says that `--dhcp-range` gives a range of addresses with a netmask and a lease time. The default lease for IPv4 is one hour. The option `--no-resolv` stops dnsmasq from reading upstream servers from `/etc/resolv.conf`. And `--bind-interfaces` helps when another name server runs on the same host [S64].

## The four gaps in dnsmasq.conf, and the one in the script

Each gap is marked `TODO` in the file, with a reason. This chapter tells you the shape of each line, and the test tells you which gap is wrong.

The first gap is where dnsmasq listens. The line has the shape `interface=NAME`, and the name is the interface that faces your home devices. The file already says `bind-interfaces`. The challenge file explains it this way: listen on the address of that interface and on no other. Think about the router's two plugs. One faces the laptop and the phone. The other faces the internet. Only one of them should hear name questions.

The second gap is the pool. The line has the shape `dhcp-range=FIRST,LAST,MASK,LEASE_TIME`. You give the first and the last address of the pool, the mask as four numbers, and the lease time. The pool starts at `.100` so it never hands out an address that someone set by hand below it. The router itself is `.1`.

The third gap is what else the lease says. Two lines have the shape `dhcp-option=option:NAME,ADDRESS`. One names the default gateway and the other names the DNS server, and both point at the router. dnsmasq would send its own address for both even without these lines. You write them anyway, so that the file says what it means.

The fourth gap is a name of your own. One line has the shape `address=/NAME/ADDRESS`. The lab has no real DNS, so the router is the only place that knows `web.test`. The ending `.test` is a name reserved for tests, so it never clashes with a real website.

The fifth gap is in the script, in the function that asks for a lease. It is the command for the DHCP client, `busybox udhcpc`, run inside the computer's namespace. The script lists what the command needs. The option `-i` names the interface and `-s` names the hook script. The option `-n` gives up when there is no lease, and `-q` quits once the lease is applied. The pair `-t 5 -T 2` sends up to five requests, two seconds apart. The hook also needs the computer's name, so you put `NS_NAME="$ns"` in front of the command. You assemble the line from these parts.

Two details need an explanation. First, why a hook? On Ubuntu the `busybox` client prints a lease but does not apply it by itself, because Ubuntu's busybox ships no default hook script. The course gives you a short hook script. When the lease arrives, it sets the address, adds the default route and writes the resolver file for that computer, `/etc/netns/laptop/resolv.conf`. On your own computer your operating system does these steps for you. In the lab, the file stands in for them. Second, why up to five requests two seconds apart, when 7.2 showed a client that gives up after three tries one second apart? Because dnsmasq can take a moment to answer the first request. In the lab, clients that started about three seconds after dnsmasq and retried got their leases; with a one-second wait and three tries, the first runs got none.

## What you should see

After the script has run, the clients print how they got their leases. This is the start of a recorded run. Your addresses will differ, but each will be inside the pool, from `.100` to `.150`.

```
dnsmasq is running.
--- the laptop and the phone ask for addresses
udhcpc: started, v1.36.1
udhcpc: broadcasting discover
udhcpc: broadcasting discover
udhcpc: broadcasting select for 192.168.1.144, server 192.168.1.1
udhcpc: lease of 192.168.1.144 obtained from 192.168.1.1, lease time 3600
lease applied: 192.168.1.144/24 router=192.168.1.1 dns=192.168.1.1 lease=3600s
```

Read the lines in order. The client started and sent discover messages. It then selected the address offered by the server `192.168.1.1`, and the lease came with a lease time of 3600 seconds. The last line comes from the hook script: it says what was applied. After that, the script shows what each computer ended up with. The laptop has an address, a default route through the router and a resolver file:

```
--- laptop
24: veth-laptop    inet 192.168.1.144/24 scope global veth-laptop\       valid_lft forever preferred_lft forever
default via 192.168.1.1 dev veth-laptop
192.168.1.0/24 dev veth-laptop proto kernel scope link src 192.168.1.144
nameserver 192.168.1.1
```

Then the names. The first `dig` asks the router for `web.test` and prints the address. The second asks for a name the router does not know, and prints a status line. The `curl` line fetches a page by name through the resolver file, and the server tells you what address it sees.

```
--- dig asks the router directly: web.test
203.0.113.80
--- dig asks about a name the router does not know
;; ->>HEADER<<- opcode: QUERY, status: REFUSED, id: 13082
--- curl uses the resolver file from the lease
the server sees you as 203.0.113.1:53406
```

Look at three things. The name worked: `web.test` became `203.0.113.80`. The unknown name got `REFUSED`, not an address. That is an answer, not silence: dnsmasq here has no upstream server, because of `no-resolv`, so it refuses names it does not know. And the server saw `203.0.113.1`, the router's outside address, not the laptop's. The curl line therefore proves three things at once: the lease gave a resolver, the name resolved, and the masquerade rule from challenge 4 still works.

Then run the test. This is the recorded result:

```
PASS namespaces laptop, phone, router and server exist
PASS dnsmasq is running in the router
PASS GAP 2: the laptop has 192.168.1.144/24, inside the pool 192.168.1.100 to 192.168.1.150
PASS the phone has 192.168.1.136/24, a different address from the laptop
PASS GAP 3: the laptop has a default route via 192.168.1.1, from the lease
```

Notice the checks that pass because something failed. The server cannot ask for names on the outside plug. An unknown name gets no answer. And the phone gets no lease while dnsmasq is stopped. A test that only checks success proves little. These three prove that your router refuses what it should refuse.

## If it does not work

Try these in order, and stop at the first one that explains the symptom. First, is dnsmasq listening? Run `ip netns exec router ss -ulnp`. The output is not shown here, so use it to check that dnsmasq is on the list, and do not compare text. Second, watch the conversation with `ip netns exec router tcpdump -n -i br-home port 67 or port 68` while a client asks. If nothing appears, the question never reached dnsmasq, and the interface line is the first suspect. Third, read dnsmasq's own log with `cat /tmp/networking-course-pids/dnsmasq.log`. Fourth, ask the server directly with `ip netns exec laptop dig @192.168.1.1 web.test`. If that works and `curl` does not, the resolver file is the problem.

One symptom needs a special note. If the client prints that a lease was obtained but the interface has no address, the hook script did not run. Check the `-s` option in gap 5. Without it, the client finds a lease and applies nothing.
