Six phones show the same message: Connected, no internet. Each one has a different cause. Which command splits them fastest? You will not guess. You will check one thing at a time, in a fixed order, and the first check that fails will name the broken layer.

The interactive network lab, where you type the commands yourself, is not ready yet. This lab is a graded quiz on a fixed scenario, and an interactive version comes later. Everything you need to answer is in this chapter, so read it first and then answer the three questions at the end.

## The idea: each check rules out everything before it

A page needs five things in order, as chapter 7.1 showed. Add the link underneath them and you get six checks: the link, an address, the gateway, a route out, a name, and a plain web request. Each check proves that everything below it works. If the address check passes, the link must be up. If the DNS check passes, the address, the gateway and the route must all be fine. So you walk up from the bottom, and the first check that fails names the broken layer. You never need to look above it.

The order matters because a failure high up can look like a failure low down. A web page that does not load tells you almost nothing. A ping that gets no answer tells you a little. A missing address tells you exactly what is wrong. You want the most exact signal first, so you start at the bottom and move up only when a layer is proven.

There is one more idea to keep in your head. A route and a reachable place are different questions. `ip route get` asks the phone: do I know a way to send a packet to this address? It answers from the phone's own table, and it is equivalent to sending a packet along that path [S32]. `ping` asks the network: does a packet arrive, and does an answer come back? A route can exist while the packet never arrives. A learner who reads a failed `ping` as "there is no route" will look in the wrong place.

## Check 1 and check 2: the link and the address

Start with the link. The command is `ip link`. It lists the network interfaces and their state. A working interface shows `state UP`. This line comes from a recorded run in the lab, where an interface was up. The flags in angle brackets also say `UP`.

```
8: veth-laptop@if7: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP group default qlen 1000
```

On a phone you will not type this command, and you do not need to. The word Connected already tells you that the radio link to the router works. That is why chapter 7.1 listed five places and not six. In the lab, though, a cable or an interface can be switched off, so the link is the first check.

If the link is up, check the address with `ip addr`. A phone that got a lease has a line that starts with `inet`. This line is the address part of a recorded lab interface.

```
    inet 192.168.1.20/24 scope global veth-phone
```

A phone with no lease has no `inet` line on that interface. This is what chapter 7.2 taught: the lab's Linux client gives up after about three seconds and is left with no address, while Windows and macOS give themselves a `169.254.x.x` address [S12]. Both mean the same for this check: the phone found no DHCP server. An empty pool is a hypothetical case, because no incident source was found for it. This lab uses it only as an example of a missing lease.

## Check 3: the gateway

If the phone has an address, find out whether its gateway answers. Ping the gateway only. Two pings with a one second wait are enough: `ping -c2 -W1 192.168.1.1`. A working gateway answers both. A gateway that does not answer gives silent loss. This is a recorded ping to an address that nobody owns. It shows the shape of silent loss: two sent, none received, and no error message at all.

```
PING 192.168.1.99 (192.168.1.99) 56(84) bytes of data.

--- 192.168.1.99 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss, time 1029ms
```

Now think about what a wrong gateway is. Suppose the phone has a gateway that nobody owns, such as `192.168.1.10` on a network where the router is `192.168.1.1`. It sends an ARP request for that address, and nobody answers. The ping looks exactly like the one above, because the lab found that the ARP requests go unanswered (dossier 5.7). So silent loss at this check means one of two things: the gateway address is wrong, or the router is off. It does not tell you which. Both are the same layer, and the fix is on the router side.

## Check 4: the route out

A working gateway is not yet a way out. Check 4 has two parts. First ask the phone for its route to a public address. In the lab the public server is `203.0.113.80`, an address from a range kept for examples [S10]. The command is `ip route get 203.0.113.80`. This is a recorded answer from the capstone network:

```
203.0.113.80 via 192.168.1.1 dev veth-home1 src 192.168.1.30 uid 0
    cache
```

Read it from left to right: to reach `203.0.113.80`, send through `192.168.1.1`, out of the interface `veth-home1`, using the source address `192.168.1.30`. The phone has a route. If it had none, the command would say `RTNETLINK answers: Network is unreachable`, and then you know the phone itself has no way out [S32].

Second, send a ping to that address: `ping -c2 -W1 203.0.113.80`. Three different things can happen. If both pings come back, the route out works. If the router has no route onward, the router answers with Destination Net Unreachable. In the lab this appears when the home router's default route is removed: the device gets the message from the router, `192.168.1.1`, and a request fails at once (dossier 5.7). That is a clear answer, and it names the router's route as the broken layer. The third thing is silence. Silence has more than one cause. A route that exists but has no way back is silent loss [dossier 5.8], and a typical captive portal is silent too. So a silent ping at check 4 does not stop you. It tells you to go on.

## Check 5 and check 6: the name and the page

Now ask for a name. In the lab, ask the router directly: `dig +short +time=2 +tries=1 @192.168.1.1 web.test`. A working DNS server prints the address on one line:

```
203.0.113.80
```

A DNS server that does not answer gives a different ending. The tool waits, then reports the time-out. This is the message it printed in a recorded failure, where the DNS port on the router was blocked.

```
;; communications error to 192.168.1.1#53: timed out
```

If you can ping `203.0.113.80` but `dig` times out, the broken layer is DNS. The packets can go out and come back, and only the name lookup fails. The program `curl` shows the same failure with a different message: `curl: (28) Resolving timed out after 3000 milliseconds`. In the lab, a name that the server does not know gives a different answer, `status: REFUSED`, because dnsmasq there has no upstream server. A refusal is an answer. A time-out is silence.

The last check is a plain web request: `curl -sS -m 3 http://web.test:8080/cgi-bin/whoami`. When everything works, the server prints the address it sees, which is the router's outside address:

```
the server sees you as 203.0.113.1:53406
```

When the server refuses the connection, `curl` fails at once, as in this recorded line from a server that listened on the wrong address:

```
curl: (7) Failed to connect to 192.168.1.80 port 8080 after 0 ms: Couldn't connect to server
```

A refusal comes at once, and a missing return route is silent loss, as in 6.9. The two look different if you wait for the time-out.

## The six networks, and the portal

Here are the six broken networks and the check that names each one. Number 6 is a model of a typical captive portal, not a recording. Real portals differ, and this lab does not claim that every portal behaves like this one.

| # | What is broken | The check that fails | What you see |
|---|---|---|---|
| 1 | The link is down | 1, link | `ip link` does not show `state UP` |
| 2 | No address (pool empty, hypothetical) | 2, address | No `inet` line on the interface |
| 3 | Wrong gateway, `192.168.1.10` | 3, gateway | Silent loss: 2 sent, 0 received |
| 4 | The router has no default route | 4, route out | The router answers Destination Net Unreachable |
| 5 | The DNS server is unreachable | 5, name | A ping to `203.0.113.45` works, `dig` times out |
| 6 | A captive portal (model) | 6, web request | A route, a silent ping, a name that resolves, and a login page from `curl` |

<Callout type="warning" title="The portal is one typical behaviour">
Scenario 6 is a model. A portal may block names too, or let pings through. It is here to teach one lesson: a silent ping does not name a layer, and the login page from the web request is what tells the portal apart.
</Callout>

## Answer the three questions

The first and third questions use the lab network: the router is `192.168.1.1` and the public servers are `203.0.113.80` and `203.0.113.45`. The second question moves to the café of 7.1, where the router is `10.5.0.1`. Decide each answer from what the checks show, in order.

```quiz
type: mcq
question: "A laptop in the lab loads nothing. You do not know yet whether its link is even up. You must commit to one command before you see any output. Which do you run first?"
options:
  - "curl http://web.test:8080/, to see the page fail"
  - "dig @192.168.1.1 web.test, because DNS is the usual cause"
  - "ip link, to see whether the link is up"
correct: 2
explanations:
  - "A failed page tells you almost nothing, because it can fail at any of the six layers. Start where a failure is exact."
  - "DNS is only the fifth check. If the link or the address is broken, the lookup fails too, and you would blame the wrong layer."
  - "Right. The link is the bottom check. If it passes, everything above has a chance to work. If it fails, you have already found the problem."
```
