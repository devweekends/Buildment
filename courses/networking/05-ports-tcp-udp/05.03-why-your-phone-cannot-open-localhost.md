Your web app works at `http://localhost:3000` on your laptop. Your phone, on the same Wi-Fi, cannot open it. Why?

## On the phone, localhost is the phone

<InteractiveCanvas slug="net-m5-phone-localhost" />

The name <GlossaryTerm term="localhost" definition="A name for this computer itself." /> always means the computer that uses the name. On the laptop, that is the laptop. On the phone, it is the phone. So the phone's request goes to its own <GlossaryTerm term="loopback" definition="The address 127.0.0.1, which points back at the same computer." />, and loopback is never forwarded to another computer [S9]. Pick where the request goes.

<GoDeeper title="Go deeper: the loopback block">

The special-purpose address registry lists the block 127.0.0.0/8 as not forwardable and not reachable from the internet [S9]. So a packet for 127.0.0.1 is not passed on to another computer. The computer that sends it receives it itself. The IPv6 version of the same idea is `::1` [S3].

This makes `localhost` useful for talking to your own computer and useless for talking to any other one. On the phone, there is also no app on port 3000, so even the phone's own loopback has nothing to answer. This is why the page does not open, and why it fails in the same way on every phone, whatever its make: the name always points back at the phone.

</GoDeeper>

## Use the laptop's address instead

<InteractiveCanvas slug="net-m5-laptop-address" />

To reach the laptop, the phone must use the laptop's own address and the app's port: `http://192.168.1.23:3000`. With the mask /24, both devices start with 192.168.1, so they are on the same network (chapter 3.2). Press Next and watch the request leave the phone and reach the laptop.

<GoDeeper title="Go deeper: finding the laptop's address, and why it changes">

On the laptop, run `ipconfig` (Windows), `ip addr` (Linux) or `ifconfig` (macOS), as in chapter 3.1. Look for the IPv4 address of the connection you use. Check it against the phone's address: with a /24 mask, the first three numbers must match.

The address may be different tomorrow. A router that hands out addresses with DHCP gives each one for a fixed time, called a lease [S23], so the laptop's address can change. If the page stops opening one day, check the address again before you check anything else. Many "it worked yesterday" problems are only a changed address.

</GoDeeper>

## A server promises certain addresses

<MermaidDiagram title="What a listening address promises" chart={`flowchart LR
  subgraph A["App listens on 127.0.0.1:3000"]
    A1["Laptop itself"] -->|"answered"| A3["App"]
    A2["Phone"] -->|"refused"| A3
  end
  subgraph B["App listens on 0.0.0.0:3000"]
    B1["Laptop itself"] -->|"answered"| B3["App"]
    B2["Phone"] -->|"answered"| B3
  end
`} legend="Left: an app that listens on 127.0.0.1 answers only the laptop itself. Right: an app that listens on 0.0.0.0 answers every address, so the phone gets through too." />

A server's <GlossaryTerm term="listening address" definition="The address a server promises to answer on." /> says which of the computer's addresses it will answer on. 127.0.0.1 answers only the computer itself. <GlossaryTerm term="0.0.0.0" definition="In a listening address, any address this computer has." /> means every address the computer has. You never type 0.0.0.0 into a browser.

<GoDeeper title="Go deeper: a promise, not a destination">

A computer can have several addresses at once: the loopback address, a Wi-Fi address, and more. When a server starts, it says which of them it will answer on. 127.0.0.1 is one address. 0.0.0.0 stands for all of them. A server can also name one real address, such as 192.168.1.23, and then it answers on that address only.

The lab's server command takes the address and the port together, in the form `ADDRESS:PORT`. Chapter 5.6 uses it. A page you open in a browser always needs a real address. The address 0.0.0.0 belongs only in the listening column. If you see it in a list from `ss -tlnp`, read it as the server's promise: it answers on every address of this computer.

</GoDeeper>

## 127.0.0.1 answers only the laptop

<InteractiveCanvas slug="net-m5-listen-loopback" />

The app listens on 127.0.0.1:3000. On the laptop it works. The phone's request reaches the laptop, but nothing listens on that address, so the laptop says no at once. That quick no is a refusal. In the lab, curl shows a refusal as exit code 7. Compare this with the first beat: there the request never left the phone, and here it reaches the laptop.

<GoDeeper title="Go deeper: a refusal is not silence">

Here is what the lab recorded for a server on 127.0.0.1. In the lab the server is at 192.168.1.80 and uses port 8080, but the idea is the same. First come the listening sockets, from `ss -tlnp`. Then curl from the other computer.

```
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      9          127.0.0.1:8080      0.0.0.0:*    users:(("busybox",pid=198,fd=3))
curl: (7) Failed to connect to 192.168.1.80 port 8080 after 0 ms: Couldn't connect to server
```

Read the column `Local Address:Port`. It shows where the server promises to answer. The curl line says `after 0 ms`, so the answer came back at once. Exit code 7 means curl could not connect. A silent drop would give no answer, and curl would give up much later with exit code 28, a timeout. You will build this yourself in chapter 5.6.

</GoDeeper>

## 0.0.0.0 answers on every address

<InteractiveCanvas slug="net-m5-listen-all" />

Start the app again on 0.0.0.0:3000. Only the listening row changes. The laptop still works. Now the phone's request meets a listening app too, and the page opens. One promise serves both devices. The port, 3000, did not change. In the lab, the only change is the address before the colon in the server's command.

<GoDeeper title="Go deeper: the same app with a different promise">

After the lab moved the server to 0.0.0.0, it recorded this line:

```
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      9            0.0.0.0:8080      0.0.0.0:*    users:(("busybox",pid=207,fd=3))
```

The program, `busybox`, and the port, 8080, are the same as before. Only the first half of `Local Address:Port` changed, from 127.0.0.1 to 0.0.0.0. Then the laptop's curl got the page: `hello from the server`.

<Callout type="warning" title="0.0.0.0 is not a place to go">
The address 0.0.0.0 appears only in the listening column. In a browser, type the laptop's real address, never 0.0.0.0.
</Callout>

</GoDeeper>

## Two blockers the 5.6 lab does not show

<MermaidDiagram title="Three checks between the phone and the app" chart={`flowchart TD
  P["Phone request to 192.168.1.23:3000"] --> W{"Wi-Fi client isolation?"}
  W -->|"blocks"| X1["Silent wait"]
  W -->|"allows"| F{"Laptop firewall?"}
  F -->|"drops"| X2["Silent wait"]
  F -->|"allows"| L{"Listening address?"}
  L -->|"127.0.0.1 only"| X3["Refused at once"]
  L -->|"0.0.0.0"| OK["App answers"]
`} legend="The request passes three checks. The first two, on the Wi-Fi and on the laptop, the lab in 5.6 does not show. The third, the listening address, you can read with ss -tlnp." />

A correctly bound server can still be blocked on a real network. The laptop's firewall may drop the request. The Wi-Fi may use client isolation, which stops one device from talking to another. A silent block looks like a long wait, not a quick refusal. The lab in chapter 5.6 has no firewall rule and no Wi-Fi, so it does not show these two.

<GoDeeper title="Go deeper: tell the cause by how the failure looks">

The lab shows both kinds of failure. A server that listens on 127.0.0.1 turns a remote computer away at once: curl exits with 7, after 0 ms. A rule that drops a request gives no answer. In challenge 4, a guest device was blocked by such a rule, and curl ended like this:

```
curl: (28) Connection timed out after 3002 milliseconds
```

So a quick refusal says the computer is there, but nothing listens on that address. A long wait says something is dropping the request. Check the listening address first, because `ss -tlnp` shows it. Then think about the firewall, and on Wi-Fi, client isolation. The lab cannot show client isolation, so this course gives no figure for how often it happens.

</GoDeeper>
