In a video call, a packet that arrives half a second late is useless. Would you wait for it?

## A late packet in a call is useless

<InteractiveCanvas slug="net-m5-scene-late-audio" />

A call sends one small audio packet every 20 ms. Packets 1 to 3 arrive and play. Packet 4 is held up and arrives about half a second late. By then the call has moved on, so the friend skips it and plays packet 5. For a call, a late packet is worse than a missing one.

<GoDeeper title="Go deeper: model numbers, not measurements">

The 20 ms, the 100 ms and the 560 ms in the picture are model numbers. They show the idea. They are not measurements of a real call or a real network.

A real call app is more careful. It keeps a short buffer of packets and decides how late is too late. This course does not teach how. The picture shows only that a packet which arrives after its moment has no use, so waiting for it does not help the call.

</GoDeeper>

## TCP holds back everything behind a loss

<InteractiveCanvas slug="net-m5-tcp-loss-timeline" />

The same ten packets cross a link over <GlossaryTerm term="TCP" definition="The protocol that delivers every byte, in order." />. Drag the loss rate up. A lost packet is sent again one round trip later. TCP gives data to the app in order, so every packet behind the lost one waits. The orange bars show the waiting. At 10%, one lost packet makes five packets late.

<GoDeeper title="Go deeper: the numbers in this model">

The model sends a packet every 20 ms, and a packet needs 40 ms to cross, so a round trip is 80 ms. When a packet is lost, the model sends it again 90 ms after the first try: one round trip plus 10 ms to notice. The resend crosses in 40 ms. So the lost packet reaches the receiver 130 ms after it was sent, instead of 40 ms.

TCP gives the app its bytes in order [S25], so the packets behind the lost one must wait for it. At a loss rate of 10% the model drops packet 4. Packets 5 to 8 arrive before packet 4's resend, so they wait. Packet 9 arrives after it and does not wait. That is five late packets out of ten. At 30% the model drops packets 4, 6 and 8, and seven packets are late.

The model drops packets in a fixed order so that you can compare TCP and UDP on the same run. A real link loses packets at random. The numbers are a model, not a measurement of any real network.

</GoDeeper>

## UDP delivers what arrives and moves on

<InteractiveCanvas slug="net-m5-udp-loss-timeline" />

Now the same ten packets over <GlossaryTerm term="UDP" definition="The protocol that sends each message once, with no promise." />. Drag the loss rate up. A lost packet is just missing. The other packets reach the app 40 ms after they left, and nothing waits. UDP sends each <GlossaryTerm term="datagram" definition="One self-contained message sent by UDP." /> once, with no promise that it arrives [S26].

<GoDeeper title="Go deeper: what UDP leaves to the app">

<Callout type="warning" title="UDP is not faster">
A packet needs the same 40 ms to cross in both pictures. UDP only skips the waiting for a lost packet.
</Callout>

UDP is a datagram service with no delivery guarantee [S26]. With no promise to keep, it has no handshake and no resend. An app that needs more than that must build it itself. A call app can accept a gap. A file transfer cannot, so it uses TCP.

DHCP is another user of UDP: a client uses port 68 and a server uses port 67 [S23].

</GoDeeper>

## Sort six apps by what a loss costs

<InteractiveCanvas slug="net-m5-sort-tcp-udp" />

Ask one question for each app: what does a lost or late packet cost? If every byte must arrive in order, pick TCP. If waiting hurts more than a gap, pick UDP. Sort the six apps. A wrong try tells you what the app would lose. If two cards feel close, decide by the cost of a gap.

<GoDeeper title="Go deeper: the choice is about cost">

A file backup, an email and a web page need every byte, so they use TCP and accept the wait. A video call and a live score can live with a gap, because the next packet makes an old one useless, so they use UDP. A DNS question is one short message. A TCP handshake is three packets before the first byte, so for one question it costs more than the question itself.

This is a rule for thinking, not a survey of products. Real apps may use both protocols, and this chapter does not cover protocols that are built on top of UDP.

</GoDeeper>

## DNS uses UDP, and TCP when cut short

<MermaidDiagram title="A DNS answer that is too big" chart={`sequenceDiagram
  participant C as Client
  participant R as DNS server
  C->>R: 1 Question over UDP
  R->>C: 2 Answer cut short, TC flag set
  C->>R: 3 Same question over TCP
  R->>C: 4 Full answer over TCP
`} legend="A DNS question goes over UDP first. If the answer is cut short, it carries the TC flag, and the client asks again over TCP." />

The DNS question you met in chapter 1.5 went over UDP. DNS software must support both UDP and TCP [S71]. If a UDP answer is too big, it is cut short and marked truncated, with the TC flag set. The client then asks the same question again over TCP [S71]. So DNS uses both protocols.

<GoDeeper title="Go deeper: why DNS keeps both">

A short question and a short answer suit UDP: one packet each way, no handshake. When an answer does not fit, the client falls back to TCP, which carries any amount in order [S71]. So DNS is not a case of choosing one protocol for good. The choice is made again for each question, by what the answer needs.

Module 7 comes back to DNS. For now, keep the shape: UDP first because it is cheap, TCP when the answer is cut short.

</GoDeeper>

<GoDeeper title="Sources">

[S23] RFC 2131, DHCP: client port 68, server port 67. [S25] RFC 9293, Transmission Control Protocol. [S26] RFC 768, User Datagram Protocol: a datagram service with no delivery guarantee. [S71] RFC 7766, DNS over TCP: implementations must support both UDP and TCP, and a truncated UDP answer makes the client retry over TCP. </GoDeeper>
