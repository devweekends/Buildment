The handshake from chapter 5.4 is only words until you capture it. In this chapter you watch a real one, with real numbers, from your own lab. You also see what chapter 5.3 could only draw. A server that promises to answer on `127.0.0.1` turns a visitor away. The same server on `0.0.0.0` lets the visitor in.

Two ideas carry the whole chapter. First, where a server listens decides whether the handshake even starts. Second, `tcpdump` and `ss` show the same conversation from two sides, so the numbers you find with one must match the numbers you find with the other. This is challenge 3, part 1. It is gapped: the script is almost complete, and you fill in four small gaps. The test tells you which gap is wrong.

## Two computers, one cable, one server

You have built this network before. In challenge 1 you made two computers inside the lab and joined them with a virtual cable. This part builds the same pair again, with new names for the job: a `laptop` at `192.168.1.23/24` and a `server` at `192.168.1.80/24`. The script builds them for you and deletes the old network first, so it is safe to run twice.

The server is a tiny web program called `busybox httpd`, and it listens on port 8080. The client is `curl`, running in the laptop. First the server listens on `127.0.0.1` only. Then it listens on `0.0.0.0`. Nothing else changes between the two runs, so any difference you see comes from the listening address alone.

Work on one gap at a time and run `bash conversation.sh` after each. The script prints a short note where a gap is still empty, so you always know which part is missing. Each gap has a ladder of hints. Try the first rung. Open the next one only if you are still stuck.

Gap 1 starts the server. The function `start_server` receives an address, and your line must start the server for that address. The first hint is a question to ask yourself: read the Local Address column of the output, and decide who the server is promising to answer. The second hint names the program, `busybox httpd`, whose `-p` option takes an address and a port together. The third hint gives the shape of the line: `bg_start web server busybox httpd -f -p ADDRESS:PORT -h FOLDER`. Use the name `web`. The line above your gap, `stop_proc web`, looks for that name, and it is how the script stops the old server before it starts the new one.

Gap 2 saves what the server is listening on. The tool is `ss`, and four letters tell it what to show: `-t` for TCP, `-l` for listening sockets, `-n` for numbers instead of names, and `-p` for the name of the program. So the command is `ss -tlnp`. It has to run inside the server computer, so the line has the shape `ip netns exec NAMESPACE ss -tlnp > FILE`.

Gap 3 saves the open conversations from both sides. Now you do not want listening sockets, so the letter `-l` goes away: the command is `ss -tn`. You run it twice, once in the laptop and once in the server, and you save the answers in two different files. The shape is `ip netns exec NAMESPACE ss -tn > FILE`, two times.

Gap 4 captures the handshake. The capture must already be running when `curl` starts, so it runs in the background, with `&` at the end. It is `tcpdump` inside the server computer, watching the plug `veth-server`. The option `-n` shows numbers, `-c 3` stops after three packets, and the filter `tcp port 8080` keeps ARP and IPv6 chatter out of your file. Wrap it in `timeout 10` as a safety stop. The shape is `timeout 10 ip netns exec NAMESPACE tcpdump -n -i INTERFACE -c 3 FILTER > FILE 2>&1 &`.

## What you should see

When all four gaps are filled, `bash conversation.sh` prints six parts. This is what the course recorded in its own lab. Your pid numbers, port numbers and times will differ. The shape will not. The first two parts compare the two listening addresses.

```
--- 3. the server listens on 127.0.0.1 only
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      9          127.0.0.1:8080      0.0.0.0:*    users:(("busybox",pid=198,fd=3))
curl: (7) Failed to connect to 192.168.1.80 port 8080 after 0 ms: Couldn't connect to server
curl from the laptop exited with 7. Exit code 7 means: connection refused.
--- 4. the server listens on 0.0.0.0
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      9            0.0.0.0:8080      0.0.0.0:*    users:(("busybox",pid=207,fd=3))
hello from the server
```

The script says that exit code 7 means a refused connection. More exactly, 7 means curl failed to connect, and a refusal is one cause. Here it was a refusal, because the answer came back after 0 ms from a computer that is up.

Read the column `Local Address:Port` in both listings. The first says `127.0.0.1:8080`, the second `0.0.0.0:8080`. The program and the port are the same. The pid is different only because the second server is a new process. That one change of address is the whole difference between a refusal and a page. The refusal came at once: the line says `after 0 ms`, and curl exited with code 7, which means it could not connect. It did not hang, which answers the guess you wrote down. The server's computer received the SYN, found nobody listening on that address, and said no immediately.

Part 5 is the handshake itself. Here are its three packets.

```
--- 5. the handshake
...
10:39:05.171782 IP 192.168.1.23.48158 > 192.168.1.80.8080: Flags [S], seq 557210665, win 64240, options [mss 1460,sackOK,TS val 710427391 ecr 0,nop,wscale 7], length 0
10:39:05.171824 IP 192.168.1.80.8080 > 192.168.1.23.48158: Flags [S.], seq 1089803950, ack 557210666, win 65160, options [mss 1460,sackOK,TS val 2147467152 ecr 710427391,nop,wscale 7], length 0
10:39:05.171850 IP 192.168.1.23.48158 > 192.168.1.80.8080: Flags [.], ack 1, win 502, options [nop,nop,TS val 710427393 ecr 2147467152], length 0
3 packets captured
12 packets received by filter
0 packets dropped by kernel
```

Read the first line from left to right. After the time, `192.168.1.23.48158 > 192.168.1.80.8080` means: from the laptop's address and port to the server's address and port. In tcpdump's style the port follows the address after a dot. The server's port, 8080, is the one the server promised. The laptop's port, 48158, is one that Linux chose for this conversation. It sits inside Linux's default range of 32768 to 60999 [S28]. It is below 49152, so it is outside IANA's dynamic range [S27]. This is the difference chapter 5.2 showed you.

The flag `[S]` is SYN: "I want to talk", with the starting number `seq 557210665`. The second line comes back from the server. The flag `[S.]` is SYN-ACK. It carries the server's own starting number, `seq 1089803950`, and `ack 557210666`, which is the laptop's number plus one. The third line is the laptop's `[.]`, the plain ACK. It says `ack 1`, not a long number, because tcpdump counts the later numbers from the start of the conversation. The raw number would be the server's 1089803950 plus one. The rest of each line, `win`, `options` and `length`, is not part of this module. Leave it for later.

Part 6 holds one conversation open, so that `ss` can see it. The script uses `nc`, which connects and then says nothing. The server waits, and the conversation stays open for about eight seconds. Both computers are asked at that moment.

```
--- 6. one open conversation, seen from both sides
laptop sees:
State Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
ESTAB 0      0       192.168.1.23:48172 192.168.1.80:8080
server sees:
State Recv-Q Send-Q Local Address:Port Peer Address:Port Process
ESTAB 0      0       192.168.1.80:8080 192.168.1.23:48172
Done. The server is still listening on 0.0.0.0:8080. Next: bash test.sh
```

Compare the two lines. The laptop says its own end is `192.168.1.23:48172` and the other end is `192.168.1.80:8080`. The server says the same four numbers the other way round. Local always means the computer you asked, so the two answers mirror each other. Add the protocol, TCP, and you have the five numbers of chapter 5.2. This port, 48172, differs from 48158 in the capture because it is a different conversation from the same run. Each new conversation gets its own port.

## The test that must pass and the test that must fail

Now run the test, **in the lab**:

```
bash test.sh
```

This is the recorded result. Your port number in the GAP 3 line will be different.

```
PASS namespaces laptop and server exist
PASS GAP 1: the server listens on 0.0.0.0:8080
PASS curl from the laptop to 192.168.1.80:8080 works
PASS GAP 2: listen-loopback.txt shows the server on 127.0.0.1:8080 only
PASS GAP 2: listen-all.txt shows the server on 0.0.0.0:8080
PASS GAP 3: the laptop says 192.168.1.23:48172 to 192.168.1.80:8080, the server says the same numbers the other way round
PASS GAP 4: handshake.txt shows SYN, SYN-ACK, ACK in that order
PASS GAP 4: the SYN goes laptop to server:8080, the SYN-ACK comes back
PASS the test server listens on 127.0.0.1:8080
PASS with the server on 127.0.0.1, curl from the laptop is refused at once (exit 7)
PASS server is back on 0.0.0.0 and the laptop reaches it again
RESULT: all checks passed
```

The test has a part that must pass and a part that must fail. With the server on `0.0.0.0`, curl must work, and your five files must hold the right evidence. Then the test moves the server to `127.0.0.1` on purpose, and curl must be refused at once, with exit code 7. A refusal that takes more than a moment would fail the test, because a slow failure is a different problem: something silent in the way. Notice that one `PASS` line is about a connection that failed, as it should. At the end the test puts the server back on `0.0.0.0`.

When a check fails, the message begins with the name of the gap, for example `GAP 2`. Go to that gap in `conversation.sh`, fix it, run the script, and run the test again.

## If it does not work

Try these in order. First, is the server in the computer you think? Run `ip netns exec server ss -tlnp` and look for port 8080. Second, does a ping from the laptop reach `192.168.1.80`? That is the layer below, and you built it in challenge 1. Third, is `tcpdump` running inside the `server` computer, and does it watch `veth-server`? Fourth, did the old server stop before the new one started? The script does that with `stop_proc web`, but only if you named your server `web`.

If curl fails when the server should be on `0.0.0.0`, the script says so and points you back to Gap 1. If a file is empty, the gap that writes it is probably still empty. If you want to start again, run `bash conversation.sh`. It deletes what the course built before and builds the network again.
