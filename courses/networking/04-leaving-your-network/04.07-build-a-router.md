You have two networks and nothing between them. Your laptop can reach its own router, but it cannot reach the server on the other side. In this chapter you build the router yourself, out of a computer with two plugs, and then you watch one ping cross it. Linux does not forward packets for other computers unless you switch forwarding on [S28]. And a reply needs a way back, so both directions must be set up. Most of the work is three small settings, and the failure is silent, which is why the chapter has a mid-point check and a test that names the missing setting.

## What you build

The lab makes three computers: `laptop`, `router` and `server`. The laptop is on the home network `192.168.1.0/24`. The server is on a second network, `203.0.113.0/24`, which plays the part of the internet. That range is kept for examples, so no real website uses it [S10]. The router sits between them and has one plug on each network, with one address on each. That is what makes it a router: two plugs, two networks, one computer.

Notice that every cable has a pair of plugs, as in challenge 1, and that the router owns two of them. Nothing in the picture changes the addresses of a packet. This is a plain router, and it does not use NAT.

**No NAT in this chapter.** A real home router also rewrites the source address of what it sends out. This router does not. It only forwards, so the server sees the laptop's own address. Module 6 adds the rewrite. The addresses here belong to the lab and have no link to your real network.

## Before you run anything: a guess

A ping has two halves, a request and a reply, as you saw in 1.5. The request goes out through the router. The reply has to come back through it. For both halves, each computer on the way needs a row in its table that says where to send the packet next, as in 4.3.

Now think about one more thing that makes a ping cross: the server's way back. Suppose the laptop and the router are set up correctly, and only the server has no row for the home network. Make a guess before you build. You will check it in a moment.

## The three gaps

Each gap is one command, and each one fixes one half of the problem. You type them into `router.sh` where the `TODO` marks are, so the script builds the whole network every time you run it. The shapes below are the ones in the README. The words in capitals are blanks that you fill.

The first gap is the laptop's way out. Today the laptop has a row for its own network only. When it has a packet for any other network, it says `Network is unreachable` at once, as in the wrong-mask session of module 3. Give it a default route to the router's address on the laptop's side, which is `192.168.1.1`. The shape is `ip route add default via ROUTER_ADDRESS`, and it runs inside the laptop.

The second gap is the router's willingness to forward. A Linux computer does not pass on packets addressed to someone else unless forwarding is on, and the setting is off by default [S28]. A ping that arrives on one router plug and never leaves the other means that the router is not forwarding. The setting is `net.ipv4.ip_forward`, and the value 1 means on. The shape is `sysctl -w SETTING=VALUE`, and it runs inside the router only.

The third gap is the server's way back. The server gets the laptop's request, but its reply has no row to follow, because the server has never heard of `192.168.1.0/24`. Give the server a route for the home network through the router's address on the server's side, `203.0.113.1`. The shape is `ip route add NETWORK via ROUTER_ADDRESS`, and it runs inside the server.

Which gap fails how? The first gap shows itself at once: an error message. The second and the third are silent. With forwarding off, or with no return route, the laptop sends a request and hears nothing. That is why you check the test output and not the screen alone. If you are stuck, ask yourself four questions, in this order. Do both sides reach their own router? Is `sysctl net.ipv4.ip_forward` equal to 1 in the router? Does `ip route` on the server show the way back to `192.168.1.0/24`? Where does the echo stop, if you run `tcpdump` on both router plugs?

## What a finished build looks like

When the three gaps are filled, `router.sh` prints the routes of each computer, and then the ping across the router works. This is the recorded output of a finished build, with the first lines left out. Read each table as you read tables in 4.3. Each line is a row. The laptop has a row for its own network and a default row. The router has a row for each of its two networks. The server has a row for its own network and one for the home network.

```
default via 192.168.1.1 dev veth-laptop
192.168.1.0/24 dev veth-laptop proto kernel scope link src 192.168.1.23
192.168.1.0/24 dev veth-rin proto kernel scope link src 192.168.1.1
203.0.113.0/24 dev veth-rout proto kernel scope link src 203.0.113.1
192.168.1.0/24 via 203.0.113.1 dev veth-server
203.0.113.0/24 dev veth-server proto kernel scope link src 203.0.113.80
```

Look at the router's two lines, the third and the fourth above. The router has no default row, and the README asks you why it does not need one here. Answer it in `results.md` in your own words. Then look at the ping across the router. This is the recorded result. The `ttl=63` is not a mistake: the reply came through the router, and the router lowered the counter by one.

```
PING 203.0.113.80 (203.0.113.80) 56(84) bytes of data.
64 bytes from 203.0.113.80: icmp_seq=1 ttl=63 time=3.13 ms
64 bytes from 203.0.113.80: icmp_seq=2 ttl=63 time=0.061 ms

--- 203.0.113.80 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1001ms
rtt min/avg/max/mdev = 0.061/1.597/3.134/1.536 ms
```

Your times will differ. The shape will not: two packets out, two back, and a TTL that is one lower than the starting 64.

```

```

This is the recorded result of a finished build. The mid-point lines come first, then one line for each gap, then the ping across, then the two lines about the MACs and the last one about the IP addresses.

```
PASS namespaces laptop, router and server exist
PASS all four plugs have their addresses
PASS mid-point: laptop reaches its own router, 192.168.1.1
PASS mid-point: server reaches its own router, 203.0.113.1
PASS GAP 1: the laptop has a default route via 192.168.1.1
PASS GAP 2: forwarding is on in the router
PASS GAP 3: the server has a route to 192.168.1.0/24 via 203.0.113.1
PASS laptop pings the server, 203.0.113.80, with 0% loss
PASS server pings the laptop, 192.168.1.23, with 0% loss
PASS traceroute shows two hops: 192.168.1.1, then 203.0.113.80
PASS 198.51.100.7: the router, 192.168.1.1, answers Destination Net Unreachable, as it should
PASS inside link: the echo goes from the laptop's MAC to the router's inside MAC, ttl 64
PASS outside link: the same echo goes from the router's outside MAC to the server's MAC, ttl 63
PASS the IP addresses are the same on both sides: 192.168.1.23 > 203.0.113.80
RESULT: all checks passed
```

When a gap is wrong, the matching check does not pass. Its line starts with the word `GAP` and a number, and it names the command to run. That is the point of the test: it turns a silent failure into a sentence with a number in it. Fix the gap that it names, run `bash router.sh` again, and run the test again.

One line in the list is about a ping that must fail. The router has no row for `198.51.100.7`, which is another documentation address, and it has no default row either. So when the laptop pings it, the router answers the laptop with `Destination Net Unreachable`. You can see it yourself:

```
ip netns exec laptop ping -c1 -W1 198.51.100.7
```

Read the answer carefully. It comes from `192.168.1.1`, the router. The router received the packet and did not know where to send it, and it said so. That is different from silent loss, where nobody says anything. In our own test of a home router whose default route was removed, a device behind it also got `Destination Net Unreachable` from the router, and `curl` failed at once [D5.7]. Write the difference in `results.md`. You will need it in 4.8.

The test also checks the route with `traceroute`. In the lab, `ip netns exec laptop traceroute -n 203.0.113.80` shows two lines: the router `192.168.1.1`, then the server [D5.5]. Chapter 4.4 explained why: the router is the first device that stops the probe with TTL 1, and the server answers the probe with TTL 2.

## Capture the MAC change

The last proof is the one you came for. You will watch one ping on both cables of the router and compare them. You have one terminal, so run both captures in the background with `&`. These are the lines from the README, **in the lab**:

```
ip netns exec router tcpdump -n -e -v -i veth-rin -c 2 icmp > inside.txt 2>&1 &
ip netns exec router tcpdump -n -e -v -i veth-rout -c 2 icmp > outside.txt 2>&1 &
sleep 1
ip netns exec laptop ping -c1 -W1 203.0.113.80
wait
cat inside.txt outside.txt
```

Take the lines one at a time. The option `-i veth-rin` watches the router's inside plug, and `-i veth-rout` its outside plug. The option `-n` shows numbers and not names. The option `-e` shows the hardware addresses, which are the MACs. The option `-v` shows more detail, such as the TTL. The word `icmp` keeps only the pings, because a new cable also carries IPv6 messages that would hide the lines you want. The option `-c 2` stops after two packets, the request and the reply. The line `sleep 1` gives `tcpdump` a second to start, and `wait` waits until both are done.

To find the MAC addresses of the four plugs, run `ip netns exec router ip link`, and the same in `laptop` and `server`. Look for `link/ether`. Linux picks these numbers when it makes the cable, so your MACs are different from everyone else's. That is why this chapter prints no capture lines: yours will not match any that we could show.

This is the shape of what you should see. The README gives it as a table, and the test checks the same lines.

| Cable | Line | Source MAC to destination MAC | IP addresses | TTL |
|---|---|---|---|---|
| Inside | request | laptop to router (`veth-rin`) | `192.168.1.23 > 203.0.113.80` | 64 |
| Inside | reply | router (`veth-rin`) to laptop | `203.0.113.80 > 192.168.1.23` | 63 |
| Outside | request | router (`veth-rout`) to server | `192.168.1.23 > 203.0.113.80` | 63 |
| Outside | reply | server to router (`veth-rout`) | `203.0.113.80 > 192.168.1.23` | 64 |

The IP addresses are the same on both cables. The MAC addresses are not. The TTL goes down by one at the router. The MAC pair belongs to one cable only, and the router makes a new frame for the next cable. This is the picture from 4.2, now in your own capture. Mark in `inside.txt` and `outside.txt` which MAC is which plug, and answer the four questions in `results.md`.
