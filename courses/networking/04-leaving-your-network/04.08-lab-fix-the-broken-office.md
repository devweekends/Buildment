Three complaints came in from one office network. The first person cannot reach the computer next to them. The second can reach the neighbours but not the server. The third can reach the router, and still nothing comes back from the server. Each complaint hides one fault, and each fault leaves a different trace in the output of a few commands. Your job is to find the fault by reading the output, not by guessing.

For now this lab is a graded quiz on a fixed scenario: you read the recorded output of real commands and choose the fix. An interactive version, where you type the commands yourself, comes later.

## Walk the path, one question at a time

When a ping fails, the temptation is to change something and try again. That works once in a while, and it teaches nothing. A better habit is to walk the path of the packet from the sender to the far side and ask one question at each hop. You stop at the first question whose answer is wrong. That is where the fault is.

The path has three places where a packet can be lost for a reason you can name. At the sender, the mask decides whether the destination is local or far (3.2). If the mask is wrong, the sender makes the wrong choice. On the way out, the gateway must be a real device on the sender's own network, because the sender has to find its MAC with ARP (4.2). If the gateway address is wrong, nobody answers. On the way back, the far side needs a row for the sender's network (4.3). If it has none, the reply cannot leave.

The takeaway: do not change three things at once. Ask the question for the first hop, read the answer in the output, and fix only what the output shows is wrong. Then run the same check again.

## Three kinds of answer

Before you read the tickets, learn to sort the answers a failing ping can give. There are three families, and they point to three different places.

The first family is an error that appears at once, on the sender's own screen. `Network is unreachable` means that this computer has no row in its own table for the destination. In the wrong-mask session of module 3, the phone printed it as soon as it tried to ping the laptop [R-wrong-mask]. In our test of a home router whose default route had been removed, the device behind the router got `Destination Net Unreachable` from the router itself, `192.168.1.1`, and `curl` failed at once [D5.7]. The word "Net" in both messages means a network that has no row. The sender, or the router, knew it could not deliver and said so.

The second family is an answer from a router in the middle, with the router's own address. You met it in 4.7: the router answered `Destination Net Unreachable` for the address it had no route for. It tells you which hop gave up, so you know where to look first.

The third family is silence. The packet left, and nothing came back, with no error message at all. Silence has several causes, and all of them leave the output looking the same: an address on your own network that nobody owns, so ARP goes unanswered [D5.7]; a router that does not forward; a far side with no row back [D5.8]. The ping shows `2 packets transmitted, 0 received, 100% packet loss`, and that is all. Silence does not say which hop failed. You must find out by asking the three questions in order.

## Ticket 1: the computer next to me

A person in the office cannot reach the computer on the next desk. Their computers share one cable. The first computer is the `laptop` and the second is the `phone`. The laptop pings the phone and gets silence. The phone pings the laptop and gets an error at once. This is the recorded `ip addr` output of the two computers, with the lines about their addresses:

```
10: veth-laptop@if9: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP group default qlen 1000 link-netns phone
    inet 192.168.1.10/24 scope global veth-laptop
       valid_lft forever preferred_lft forever
9: veth-phone@if10: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP group default qlen 1000 link-netns laptop
    inet 192.168.1.20/28 scope global veth-phone
       valid_lft forever preferred_lft forever
```

And these are two lines of the recorded test, which reports what each ping did:

```
PASS laptop to 192.168.1.20: silent loss (2 sent, 0 received)
PASS phone to 192.168.1.10: Network is unreachable
```

Start at the first question, the mask. Look at the two lines that begin with `inet`. The laptop has `/24`, and the phone has `/28`. A `/28` is a much smaller network, with only 16 addresses: from `192.168.1.16` to `192.168.1.31`. The laptop's address, `192.168.1.10`, is not inside that block. So the phone decides that the laptop is far away. It has no default route, so it has no way to reach a far address, and it says so at once. The laptop still thinks the phone is local, so it sends and hears nothing. The two computers disagree about the mask.

```quiz
type: mcq
question: "The laptop's ping to the phone gets no answer. The phone's ping to the laptop fails at once with Network is unreachable. What is the fault?"
options:
  - "The phone's /28 mask calls the laptop far"
  - "The laptop has no default route to a gateway"
  - "The cable between the two is cut or unplugged"
correct: 0
explanations:
  - "Right. The phone's block, 192.168.1.16 to 31, does not contain 192.168.1.10. It calls the laptop far, and it has no row for far addresses."
  - "A default route matters only for a far destination. The laptop calls the phone local, so it sends the ARP question straight to the cable."
  - "A cut cable would give silence in both directions. Here the phone gets an answer from its own table at once, so the cable carries traffic."
```

The fix is to give both computers the same mask. Both `/24` repaired it in the recorded run, and the test's last two lines showed `0% loss` in both directions.

## Ticket 2: the neighbours, but not the server

The second complaint is different. A person can reach everyone on their own network, and cannot reach the server on the other network. Their laptop has a default route, and it says `via 192.168.1.99`. Someone typed the wrong number. The router is at `192.168.1.1`, which you can see in the recorded table of the router:

```
192.168.1.0/24 dev veth-rin proto kernel scope link src 192.168.1.1
```

Now do the second question, the gateway. Does `192.168.1.99` answer? Nobody in the office owns that address. In module 1 you pinged it on purpose, as a ping that must fail. This is the recorded result of that ping:

```
PING 192.168.1.99 (192.168.1.99) 56(84) bytes of data.

--- 192.168.1.99 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss, time 1029ms
```

There is no error message. The laptop asks its cable who has `192.168.1.99`, and nobody answers. In our test of an address on the same network that nobody owns, the ARP requests went unanswered and the ping showed silent loss [D5.7]. The same thing happens to every packet for the server. The laptop's table says to hand the packet to `192.168.1.99`. The laptop needs that device's MAC, and it can never get it. So the packet never leaves the laptop. From the outside the symptom is plain silence, as in the output above.

```quiz
type: mcq
question: "A laptop's default route says via 192.168.1.99, and nobody owns that address. The router is at 192.168.1.1. Which change repairs the laptop's ping to the server?"
options:
  - "Switch forwarding on in the router"
  - "Change the default route to go via 192.168.1.1"
  - "Add a route on the server back to the laptop's network"
correct: 1
explanations:
  - "Forwarding matters once the packet reaches the router. This packet never gets there, because the laptop cannot find the MAC of its gateway."
  - "Right. The gateway must be a device that answers on the laptop's own network. The router owns 192.168.1.1, so that is the address for the default route."
  - "The server's way back matters after the request arrives. Here the request never leaves the laptop, so the server sees nothing yet."
```

Notice what the wrong gateway did not do: it did not print an error. In our tests, a wrong gateway on your own network gave silence [D5.7]. That is why the second question says "ping the gateway" and not just "look at the table".

## Ticket 3: the router answers, and still no reply

The third complaint is the hardest. The person checked the first two questions. Both sides reach their own router. Forwarding is on in the router: the setting prints `net.ipv4.ip_forward = 1`. The mask is right and the gateway is right. And the laptop's ping to the server still gets no answer at all. This is the recorded result of that ping, from a run of the course lab where the server had no way back:

```
--- before masquerade: the laptop pings the server
PING 203.0.113.80 (203.0.113.80) 56(84) bytes of data.

--- 203.0.113.80 ping statistics ---
1 packets transmitted, 0 received, 100% packet loss, time 0ms

(no answer, as expected: the server has no way back to 192.168.1.23)
```

The first line of that output says `before masquerade`. Masquerade is a rule from module 6, so ignore the word here. What matters is the last line: the server has no way back.

The request does cross the router. It arrives at the server. The server builds a reply, looks in its own table for a row that holds `192.168.1.23`, and finds none. Its table has one row only: its own network, `203.0.113.0/24`. The reply goes nowhere, and the laptop hears nothing. In a test with two routers between the sender and the far host, where the second router had no route back, the sender saw 2 packets sent and 0 received, and adding the return route fixed it [D5.8]. The router in the middle looks fine, which is why people lose time on it.

Do the third question, the return route, on the far side. Run `ip route` on the server and look for a row for `192.168.1.0/24`. If it is not there, that is the fault.

```quiz
type: mcq
question: "Both sides reach their own router, and forwarding is on. The laptop's ping to the server gets no answer, and no error. Where do you look next?"
options:
  - "At the router: it needs its own default route"
  - "At the laptop: its mask must be wrong too"
  - "At the server: its ip route has no way back"
correct: 2
explanations:
  - "In this build the router has a row for each of its two networks, so it needs no default route. The request already crossed it."
  - "A wrong mask would show up at the first question, and the mid-point ping to the router passed. Move on to the next hop."
  - "Right. The request arrived, but the reply has no row to follow. The missing return route gives plain silence, and ip route on the server shows it."
```

## What the three faults have in common

Look back at the three tickets. In each one, the first sign was a failed ping, and the ping alone could not tell you why. The tickets differ in what the output added. The wrong mask gave two different results on the two sides, one of them an error. The wrong gateway gave silence on a single side, and it was a ping to the gateway that exposed it. The missing return route gave silence too, and only `ip route` on the far side showed it.

So the habit is this. Read the kind of answer first: an error at once, an answer from a router, or silence. Then ask the three questions in order, and use the command that matches each one. Use `ip addr` for the mask, `ip route` and a ping to the gateway for the gateway, and `ip route` on the far side for the return route. Fix one thing, and run the same check again. In 4.10 you will use the same habit on your own trace, and in module 7 the broken hop will be harder to find. The method stays the same.
