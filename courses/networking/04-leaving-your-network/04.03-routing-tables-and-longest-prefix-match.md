A router at your provider could have routes for `10.0.0.0/8`, `10.1.0.0/16` and a default. A packet for `10.1.2.3` arrives. Which route wins, and why not the first one in the list?

## A router keeps a table of routes

<InteractiveCanvas slug="net-m4-route-table" />

A <GlossaryTerm term="routing table" definition="The list of rows that a router or computer uses to choose where to send each packet." /> is a list of rows. Each row names a block of addresses and a next hop. This table has four rows, and one of them has no next hop. Press Next to read the rows one by one.

<GoDeeper title="Go deeper: reading one row">

Every computer has a table, and `ip route` prints it [S32]. A row says: for any address in this block, hand the packet to this next hop. The block is written with a prefix, as in 2.3. The row `10.0.0.0/8 via 10.0.0.2` means: for any address that starts with 10, hand the packet to the device at `10.0.0.2`.

A row with no next hop is a connected row. The router has a plug on that network, so it delivers there directly. The last row, `default`, is the block `0.0.0.0/0`. The `ip route` manual page defines `default` that way [S32].

The table in the picture is a model of what `ip route` lists, and the next hops are made up. A trace never shows you a router's table. So the provider router in the opening question is a plausible one, not one that you can see.

<Callout type="info" title="Static rows only">
This chapter uses rows that someone wrote by hand. Routers can also learn rows from each other, and chapter 4.5 gives a first look. No routing protocol is taught here.
</Callout>

</GoDeeper>

## Several rows can match one address

<InteractiveCanvas slug="net-m4-route-matches" />

The packet is for `10.1.2.3`. The `/8` row holds it, because the first number is 10. The `/16` row holds it, because the first two numbers are 10.1. The default row holds every address. The `192.168.1.0/24` row does not. Three rows match.

<GoDeeper title="Go deeper: how to check whether a row holds an address">

In 3.2 you applied a mask to an address. A row holds an address when the address, after the row's mask, equals the row's network. For the `/16` row, the mask is `255.255.0.0`. The address `10.1.2.3` becomes `10.1.0.0`, which is the row's network, so the row holds it. For the `/8` row the mask is `255.0.0.0`, and `10.1.2.3` becomes `10.0.0.0`, which is also the row's network.

A short prefix compares few bits, so it holds a large block. The `/8` row compares only the first 8 bits, so it holds 16,777,216 addresses. The `/16` row compares 16 bits and holds 65,536. The default row compares no bits, so it holds all addresses.

For `192.168.1.0/24`, the mask is `255.255.255.0`. The address `10.1.2.3` becomes `10.1.2.0`, which is not `192.168.1.0`. So that row does not hold it.

</GoDeeper>

## The longest prefix wins

<InteractiveCanvas slug="net-m4-route-longest" />

The router uses the most specific matching row, the one with the longest prefix [S30]. The `/16` fixes 16 bits, the `/8` only 8, and default none. So `10.1.2.3` goes by the `/16`. A <GlossaryTerm term="longest prefix match" definition="Choosing, among the rows that hold the address, the one with the longest prefix." /> also lets a `/32` row beat a `/24`.

<GoDeeper title="Go deeper: why the most specific row wins">

RFC 1812 says that routers must use the most specific matching route, which is the longest matching network prefix [S30]. The `ip route` manual page does not use the words "longest prefix match" [S32], so we cite the RFC for the rule.

A more specific row says something exact about a small part of the address space. A less specific row says something general. When both hold the address, the exact statement is the better one to follow. That is how a network can say: send everything for `198.51.100.0/24` this way, except the one host `198.51.100.9`, which goes that way. A `/32` row is a block of exactly one address, so it beats every `/24` that holds it.

Try it with numbers. A router has `198.51.100.0/24 via 192.168.1.2` and `198.51.100.9/32 via 192.168.1.3`. A packet for `198.51.100.9` is held by both rows, and the `/32` is longer, so it goes to `192.168.1.3`. A packet for `198.51.100.10` is held only by the `/24`, so it goes to `192.168.1.2`.

</GoDeeper>

## List order never decides

<InteractiveCanvas slug="net-m4-route-reorder" />

Here the same three rows are listed in another order, with default first. The router still picks the `/16`. The place of a row in the list never decides. Length does.

<GoDeeper title="Go deeper: a list is not a priority">

`ip route` prints rows in some order, and that order is for people to read. The router does not walk down the list and stop at the first match. It compares every row that holds the address and keeps the most specific.

You may meet the phrase "first listed wins" in the code exercise in 4.6. It is a rule that exercise uses so that your code returns one answer when two rows are exactly equal. It is not a fact about how routers work.

Reading a table from top to bottom is the usual mistake. In the picture, the `/8` row was listed first on purpose, and the answer was still the `/16`. If you keep the idea that the router picks by length, you can read any table in any order.

</GoDeeper>

## Same length: the lower metric wins

<InteractiveCanvas slug="net-m4-route-metric" />

Two rows can have the same prefix length: two ways to reach one block. Then the <GlossaryTerm term="metric" definition="A number that says how costly a route is. Lower is better." /> breaks the tie. Metric 100 beats metric 200 [S32]. Raise the first metric to 300 and the other row wins.

<GoDeeper title="Go deeper: the metric only breaks ties">

The metric is the second test, not the first. The router compares prefix lengths first. Only when two rows have the same length does it look at the metric. So a row with a very low metric and a short prefix still loses to a row with a longer prefix.

A metric is a number that someone sets when the row is added. In this course it has no unit. You compare it only between rows that tie on length. In the picture, both `10.1.0.0/16` rows hold the same addresses, so the metric decides: 100 is lower than 200, so the first row is used. After the metric of the first row goes up to 300, the second row has the lower number and takes over.

The numbers in the picture are made up, and the picture is a model, so no real output is shown. The rule that the lower metric wins comes from the `ip route` manual: routes with lower values are preferred [S32]. If the better row goes away, the next one takes over, as the last step of the picture shows.

</GoDeeper>

## Connected routes and the default

<InteractiveCanvas slug="net-m4-route-default" />

Your laptop has a table too. Its connected row has no next hop, so a packet for the printer goes straight there. The default row holds everything else, so a packet for `203.0.113.80` goes to the gateway. The <GlossaryTerm term="default route" definition="The row for 0.0.0.0/0. It holds every address, so it is used only when no more specific row holds the address." /> is the last resort.

<GoDeeper title="Go deeper: where connected rows come from, and what happens with no match">

A connected row appears by itself when an address is added to a plug. In the lab, `ip addr add 192.168.1.23/24` on the laptop's plug made this row, and the words `proto kernel` on the line show that the system added the row itself [R-router]:

```
192.168.1.0/24 dev veth-laptop proto kernel scope link src 192.168.1.23
```

The default row is different. Someone adds it, or a setting adds it, as in challenge 2, where the laptop's gateway is a default row.

If no row holds the address and there is no default, the computer says so at once. In the wrong-mask session of module 3, the phone printed `Network is unreachable` [R-wrong-mask]. A router with no row for a destination answers the sender. In our test of a home router whose default route was removed, the device behind it got `Destination Net Unreachable` from `192.168.1.1` [D5.7]. You will see that message again in 4.7. Silence is a different failure, and 4.8 trains you to tell them apart.

</GoDeeper>

## Ask the system: ip route get

<InteractiveCanvas slug="net-m4-route-get" />

Do not guess a route: ask. `ip route get` names the row that the system would use for a destination [S32]. Each machine answers for itself. These two answers are real. They were recorded in the course lab on home1 and hrouter, two machines of a later project in this course.

<GoDeeper title="Go deeper: reading the answer">

Here are the two answers, copied from the recording [R-capstone-1]:

```
203.0.113.80 via 192.168.1.1 dev veth-home1 src 192.168.1.30 uid 0
203.0.113.80 via 198.51.100.1 dev veth-hout src 198.51.100.2 uid 0
```

The word `via` is followed by the next hop. The word `dev` names the plug to use. The word `src` is the machine's own address on that plug. The manual page says that `get` is equivalent to sending a packet along this path [S32]. So it is a safe question. It sends nothing, and it tells you which row would be used.

The first line is home1. Its next hop is the router, `192.168.1.1`. The second line is the router itself, hrouter. Its next hop is another router, `198.51.100.1`, one step closer to the server. The same destination gives a different answer on each machine, because each machine has its own table.

On macOS the similar command is `route get`. We have not yet checked it on a Mac [S65]. In the lab you can run `ip route get` any time you are unsure which row a packet will take.

</GoDeeper>
