A tunnel needs ground to stand on. Before you build one in 11.5, you build the two places it joins. One is an office with a test server at `10.20.0.5`. The other is a café, where your laptop sits. Each hides behind its own router with NAT, as your home does. Between them is a small internet that knows only public addresses. At the end of this chapter you will see, in your own lab, the same failure as in 11.1: the laptop cannot reach `10.20.0.5`. You will also open one door in the office router, and prove that the door works by closing it again.

This is challenge 8, part 1, and it is **guided**. Nothing is missing. The script builds everything, and your job is to read each step, run it and understand what it printed. The office router does the same two jobs as your home router from challenge 4: it masquerades whatever leaves, and it forwards one port inward.

There are seven computers, and each one is a namespace, as in every challenge so far. The internet is one router with three plugs. It knows the three public ranges and nothing else, so it has no route to `10.20.0.0/24` or to `192.168.50.0/24`. The website at `192.0.2.80` has one useful page: it prints the address and port it sees. You used the same idea in 1.1 to find your own public address.

The two private ranges are different on purpose. The office is `10.20.0.0/24` and the café is `192.168.50.0/24`. In 11.1 you saw why: if both sides used the same range, the laptop could not tell an office address from a café neighbour.

The addresses `203.0.113.x`, `198.51.100.x` and `192.0.2.x` come from the ranges kept for examples. In this lab they play public addresses on the internet. The hardware addresses start with `02:`, which marks an address as made up, never burned into a real card.

## Why the office needs one open door

In 11.5 the laptop will start a tunnel to the office. Its first packet will be UDP to `203.0.113.2`, port 51820. That packet arrives at the office router's outside address. You know from 6.3 what happens next. The router has no NAT row for it, because nobody in the office sent anything first. So unless a rule says otherwise, the packet stops at the router.

The rule is a <GlossaryTerm term="port forward" definition="A router rule that sends packets for one of its own ports on to a computer inside." />, which you built in 6.8. Here it says: UDP for port 51820 that arrives on the outside plug goes on to the VPN box, `10.20.0.2`. This is the line in step 7 of the script, in the office router's `prerouting` chain:

```
iifname "veth-office-out" udp dport 51820 dnat to 10.20.0.2:51820
```

The café needs no such rule. The laptop starts every conversation, so the café router makes a NAT row on the way out, and the answers find their way back through it. That asymmetry matters again in 11.5, in the box about keepalive.

## Break the door on purpose

A test that only passes proves little. So the script proves the forward works by removing it and watching packets stop. It sends one small UDP packet, the word `hello`, from the laptop to `203.0.113.2` port 51820, five times. Each time the VPN box listens with tcpdump. The laptop always sends from its own port 51820, so all five packets look the same to the routers.

Before the five sends, think about one fact from 6.2. A router keeps a row for each conversation in its NAT table, the conntrack table, and it handles later packets of that conversation from the row. It reads the rules only for the first packet of a new conversation.

```predict
prompt: "Send 1 reaches the VPN box through the forward rule. Then the script deletes the rule and, a second later, sends send 2: the same packet, from the same address and port. Does send 2 still reach the VPN box?"
options:
  - id: arrives
    label: "Yes, it still arrives"
  - id: stops
    label: "No, it stops at the router"
correctOptionId: arrives
explanation: "It still arrives. Send 1 made a row in the office router's conntrack table. Send 2 belongs to the same conversation, so the router handles it from the row and never reads the rules again."
allowRetry: true
```

This is `forward-test.txt` from the recorded run:

```
1 rule on: arrived at the VPN box (16:16:05.269626 IP 198.51.100.2.51820 > 10.20.0.2.51820: UDP, length 6)
2 rule off, old NAT state kept: arrived at the VPN box (16:16:06.419357 IP 198.51.100.2.51820 > 10.20.0.2.51820: UDP, length 6)
3 rule off, NAT state flushed: nothing arrived at the VPN box
4 rule back, old NAT state kept: nothing arrived at the VPN box
5 rule back, NAT state flushed: arrived at the VPN box (16:16:13.612356 IP 198.51.100.2.51820 > 10.20.0.2.51820: UDP, length 6)
```

Take the five lines in order. Line 1: the rule sends the packet to `10.20.0.2`. The source is `198.51.100.2`, because the café router masqueraded it, and the port stayed 51820. `length 6` is the word `hello` and a new line. Line 2: the rule is gone, yet the packet arrives. Did you predict that? Line 3: the script ran `conntrack -F`, which tells the router to forget every conversation. Now the router reads its rules again, finds no forward, and the packet stops. Line 4: the rule is back, and still nothing arrives. The router now remembers the failed conversation from line 3, and handles the new packet the failed way. Line 5: flush again, and the first packet of the new conversation meets the rule and arrives.

Between lines 2 and 3 the script printed the row the router remembered:

```
udp      17 29 src=198.51.100.2 dst=203.0.113.2 sport=51820 dport=51820 [UNREPLIED] src=10.20.0.2 dst=198.51.100.2 sport=51820 dport=51820 mark=0 use=1
```

The first half is the packet as it arrived. The second half says answers will come from `10.20.0.2`: that is the forward, kept in memory. `[UNREPLIED]` means the VPN box never answered, because nothing listens there yet. `29` is the number of seconds left before the router forgets this row by itself. That is the idle timer from 6.5.

Lines 2 and 4 are a trap you will meet in real work. You change a NAT rule, and nothing changes. The rule is fine, but an old row is still in charge. The first thing to check is the conntrack table, and the fix is to clear it.

## If it does not work

Work from the nearest link outward, as the mid-point checks do. A computer cannot reach its router? Look at its address and routes with `ip netns exec NAME ip addr` and `ip netns exec NAME ip route`. The website sees no answer? Check that forwarding is on in all three routers, for example `ip netns exec officert sysctl net.ipv4.ip_forward`. The forward does not work? Read the rules with `ip netns exec officert nft list ruleset`, then the remembered conversations with `ip netns exec officert conntrack -L`. If you edited the script and lost track, run `bash office-cafe.sh` again. It starts from nothing.

If the test fails with `no port forward for UDP 51820`, the rule is missing. This happens when you remove it by hand after the script, to experiment, and forget to put it back. Run the script again.
