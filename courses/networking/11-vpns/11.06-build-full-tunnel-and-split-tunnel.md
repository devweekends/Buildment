Remember the first question of the course, in 1.1: which address does a website see? In 6.1 you learned the answer is your router's outside address. In this chapter you change that answer on purpose. You send **everything** the laptop does through the office, so the lab website sees the office's address, not the café's. That is exactly what a VPN app means when it says "your address is hidden". Then you look for what the tunnel still lets slip, and you find it in your own capture. Last, you split the tunnel: only office traffic goes inside, and the rest goes out through the café as before.

This is challenge 8, part 4, and it is **gapped**: five small gaps in `full-split.sh`, each marked `TODO`. The script starts by running your part 2, so part 2's test must pass first. It also starts a small name server in each router. Both config files are given: the café's answers `web.test`, and the office's answers `web.test` and `intranet.test`, a name only the office knows.

In a <GlossaryTerm term="full tunnel" definition="Every packet goes into the tunnel: the default route points at the tunnel." />, the laptop's default route is `wg0`. In a <GlossaryTerm term="split tunnel" definition="Only some networks go into the tunnel; everything else goes the normal way." />, only the office network goes into `wg0`. Part 2 left you with a split tunnel already: the laptop sent `10.20.0.0/24` into `wg0` and everything else to the café router. So you build the full tunnel first, and then undo it.

## Gaps 1 to 3: three things a full tunnel needs

**In the lab**:

```
cd /work/challenges/challenge-8-vpn/part-4-full-and-split-tunnel
```

**Gap 2** is the obvious part, so read it first. Two settings decide what goes into the tunnel and to which peer, and you need both. The laptop's AllowedIPs for the VPN box become `0.0.0.0/0`, every IPv4 address, so the VPN box is the peer for anything. And the default route is replaced with one into `wg0`. With only the route, WireGuard has no peer for `192.0.2.80` and refuses to send. With only AllowedIPs, nothing goes into `wg0` at all, as 11.3 showed.

**Gap 1** is the one people forget. The laptop's own outer packets go to `203.0.113.2`. With a default route into `wg0`, they would be caught too, and WireGuard would try to send the tunnel through itself. The fix is one route for one address, a `/32`: `203.0.113.2` via the café router, `192.168.50.1`. A `/32` is more specific than the default, so the longest match from 4.3 keeps the outer packets on the normal path. `wg-quick` solves the same problem for you, with a routing rule of its own, when AllowedIPs holds a default route; here you write the `/32` by hand. Without it, the website visit times out.

**Gap 3** is the way back, in the office router. The VPN box hands `10.99.0.2 > 192.0.2.80` to the office router. The router masquerades it, so the website sees `203.0.113.2`. When the answer returns, the router turns the destination back into `10.99.0.2`, and now it needs a route to `10.99.0.0/24` via the VPN box, `10.20.0.2`. This is part 2's Gap 4 again, in another computer. Another fix would be masquerade on the VPN box, so the office router only ever sees `10.20.0.2`. The challenge uses the route.

Read the routes from the most specific. `203.0.113.2` is one address, Gap 1. The two `/24` rows are the office and the tunnel network. `192.168.50.0/24` is the laptop's own café cable. While it happened, the café's outside plug carried only UDP on port 51820 between `198.51.100.2` and `203.0.113.2`: even the website visit is hidden inside the tunnel.

## The name question still goes to the café

The full tunnel works, and the website sees the office. Is everything inside the tunnel now? Think about the name server. The laptop got it from the café, as a real café's DHCP would give it: `192.168.50.1`, the café router.

This is `dns-cafe.txt`, a capture on the café router's inside plug during the full tunnel:

```
listening on veth-cafe-in, link-type EN10MB (Ethernet), snapshot length 262144 bytes
16:18:02.361874 IP 192.168.50.23.41288 > 192.168.50.1.53: 57993+ [1au] A? web.test. (49)
16:18:02.362061 IP 192.168.50.1.53 > 192.168.50.23.41288: 57993* 1/0/1 A 192.0.2.80 (53)

```

The question `A? web.test.` and the answer `A 192.0.2.80` crossed the café's network in plain text, to port 53. Your web traffic is hidden, but the café knows every name you look up. Nothing in the tunnel is broken. The name server is simply on the near side of it.

**Gap 4** points the laptop's name server through the tunnel, at the office's, `10.20.0.1`. The laptop reads its name server from `/etc/netns/laptop/resolv.conf`, so the gap is one line in that file. After it, `dns-cafe-after.txt` has `0 packets captured`, and the VPN box's `wg0` shows the questions:

```
16:18:07.348564 IP 10.99.0.2.55450 > 10.20.0.1.53: 43424+ [1au] A? web.test. (49)
16:18:07.348840 IP 10.20.0.1.53 > 10.99.0.2.55450: 43424* 1/0/1 A 192.0.2.80 (53)
16:18:07.363386 IP 10.99.0.2.45189 > 10.20.0.1.53: 17050+ [1au] A? intranet.test. (54)
16:18:07.363538 IP 10.20.0.1.53 > 10.99.0.2.45189: 17050* 1/0/1 A 10.20.0.5 (58)
```

Now the café sees no names, and the office sees them all. There is a bonus: the laptop can now use office names such as `intranet.test`, which the café's name server cannot answer. A VPN app can change the name server for you when it connects; `wg-quick` does it from a `DNS=` line in its config. When an app does not, you get what you just captured.

## Gap 5: split the tunnel

**Gap 5** undoes Gap 2. AllowedIPs go back to `10.20.0.0/24,10.99.0.1/32`, and the default route goes back to the café router, `192.168.50.1`. The route for `10.20.0.0/24` into `wg0` from part 2 is still there, so office traffic still goes into the tunnel. The script removes the `/32` from Gap 1, which is not needed any more. The recorded `routes-split.txt`:

```
=== laptop: ip route
default via 192.168.50.1 dev veth-laptop 
10.20.0.0/24 dev wg0 scope link 
10.99.0.0/24 dev wg0 proto kernel scope link src 10.99.0.2 
192.168.50.0/24 dev veth-laptop proto kernel scope link src 192.168.50.23 
```

The website saw the café again, `the server sees you as 198.51.100.2:60596`. And `cafe-outside-split.txt` shows both kinds of traffic side by side, shortened:

```
16:18:11.444511 IP 198.51.100.2.60596 > 192.0.2.80.80: Flags [P.], seq 1:88, ack 1, win 502, options [nop,nop,TS val 3789324696 ecr 2592675610], length 87: HTTP: GET /cgi-bin/whoami HTTP/1.1
...
16:18:11.451187 IP 198.51.100.2.51820 > 203.0.113.2.51820: UDP, length 128
16:18:11.451420 IP 203.0.113.2.51820 > 198.51.100.2.51820: UDP, length 128
```

The website visit is plain TCP to `192.0.2.80` port 80, and the café can even read `GET /cgi-bin/whoami`. The ping to the office is one UDP packet each way. Only office traffic is inside the tunnel. A company VPN can be split like this: you reach the office systems, and your video calls do not travel through the office.

## If it does not work

The website times out in the full tunnel? Run `ip netns exec laptop wg show` and look at `latest handshake`. If it is old or missing, the outer packets may be caught in the tunnel. The sure check is `ip netns exec laptop ip route get 203.0.113.2`: it must say `via 192.168.50.1`. If it says `dev wg0`, look at Gap 1. The handshake is fine but the page does not come? Ask the office router where answers go, `ip netns exec officert ip route get 10.99.0.2`, and look at Gap 3. The website still sees `198.51.100.2` in the full tunnel? `ip netns exec laptop ip route get 192.0.2.80` should say `dev wg0`; if not, look at Gap 2. Not sure which name server the laptop uses? `cat /etc/netns/laptop/resolv.conf`.
