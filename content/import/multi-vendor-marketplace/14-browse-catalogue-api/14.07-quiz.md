```quiz
type: mcq
question: A naive catalogue loads 20 products, then queries each product's store separately. How many database queries does that usually create?
options:
  - "1"
  - "2"
  - "20"
  - "21"
correct: 3
explanations:
  - "This counts only the product query and misses all 20 store lookups."
  - "Two queries would require loading stores in one batch, which this naive version does not do."
  - "This counts the store lookups but leaves out the initial product query."
  - "Correct. One query loads the products, then 20 separate queries load their stores."
```

```quiz
type: mcq
question: Which products should a shopper-facing catalogue return?
options:
  - Every product in the collection, including vendor draft listings
  - Products the public publication and availability rules allow
  - Only the products currently owned by the signed-in shopper
  - Deleted products that old orders still reference by id
correct: 1
explanations:
  - "Vendor drafts are private and should not appear in the public catalogue."
  - "Correct. Shoppers should see only products that pass the publication and availability rules."
  - "Shoppers browse vendors' products; they do not own the listings."
  - "Deleted products can remain in old order records without appearing in the catalogue."
```

```quiz
type: mcq
question: Why should GET /vendor/products remain separate from public GET /products?
options:
  - Each audience needs its own filters, fields, and auth
  - Express cannot reuse a single Product model for both
  - Public routes cannot accept query parameters of any kind
  - Vendors should never be shown their unpublished products
correct: 0
explanations:
  - "Correct. Vendor and public routes use different access rules and return different product views."
  - "Both routes can use the same Product model; the route behavior differs."
  - "Public routes can accept safe filters and pagination query parameters."
  - "Vendors need to see their own drafts so they can finish and publish them."
```
