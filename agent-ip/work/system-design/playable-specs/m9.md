# Module 9 playable specs (partitioning and sharding)

Five reserved slugs. The builder creates each folder (`frontend/src/canvas/<slug>/`), registers it and writes its `spec.md`. All five sit on `BeatFrame` (`primitives/beat-frame.tsx`), draw on a 420 wide viewBox with labels of at least 13 units, use `SvgNode` cards, `DotGrid` and `VerdictBanner`, take at most two controls outside the picture, and end on a verdict of 38 characters or fewer. All hashing uses one shared pure function, `hash32` below, so the numbers match the chapters. Each model is pure (no React) in a `model.ts` beside the canvas, with the "numbers to check" below as its unit tests.

```ts
// The course hash (chapter 9.7). Same function in every playable and in the challenge.
function hash32(text: string): number {
  let h = 0x811c9dc5;
  for (let i = 0; i < text.length; i++) { h ^= text.charCodeAt(i); h = Math.imul(h, 0x01000193); }
  h ^= h >>> 16; h = Math.imul(h, 0x85ebca6b); h ^= h >>> 13; h = Math.imul(h, 0xc2b2ae35); h ^= h >>> 16;
  return h >>> 0;
}
```

## sysdesign-m9-range-vs-hash

- **Chapter and beat:** 9.2 beat 3, "Range or hash? Slide a week across".
- **Claim:** Range partitioning keeps a week of orders on one or two shards but sends every new write to the newest range. Hash partitioning spreads writes evenly but scatters a week over every shard.
- **Primitives:** `year-strip.tsx` (365 day grid with a cursor for the played week), `picture-slider.tsx` (drag the week), four `SvgNode` shard cards with a write bar and a limit line. One toggle outside the picture: Range | Hash (44px, labelled).
- **Input:** (1) toggle Range or Hash, default Range. (2) The start day of a 7 day window, 1 to 359, on a linear rail inside the picture. Snap to days 88, 179 and 271 (windows that cross a quarter border) and to 120 (inside one quarter). Arrow keys step 1 day, Page keys step 7. Default 120.
- **Model:** Year 2026, not a leap year. Today is day 297 (24 October). Range shards are quarters: shard 1 days 1 to 90, shard 2 days 91 to 181, shard 3 days 182 to 273, shard 4 days 274 to 365. `shardsTouchedRange(start)` is the count of distinct quarters among days start to start+6. `shardsTouchedHash = 4`. Writes: 3,000 a second, all dated today. Range: shard 4 takes 3,000, others 0. Hash: 750 each. Shard limit 1,000 writes a second (dashed line on each bar; 3,000 on the bar is clipped with a "3x" marker).
- **Picture:** the year strip on top with the 7 day window highlighted and "today" marked. Four shard cards below, each with a write bar against the limit line. Shards the window touches get an accent ring and a read dot. Under Hash, seven small order dots per day fall onto the four cards at random but fixed positions, so the learner sees them scatter.
- **Numbers to check:** window start 120: range touches 1 shard. Start 88 (days 88 to 94): range touches 2 (shards 1 and 2). Start 179: 2. Start 271: 2. Hash always 4. Range: shard 4 at 3,000 (300% of limit). Hash: 750 each (75%).
- **Verdicts:** Range, one shard touched: "Week: 1 shard; all writes: shard 4" (warn). Range, two: "Week: 2 shards; all writes: shard 4" (warn). Hash: "Week: all 4 shards; writes even" (warn).
- **Reduced motion:** dots appear in place; no travelling.
- **Accessibility:** the rail is a `role="slider"` whose value text reads "week starting day 120, touches 1 shard". The toggle is a real button pair.
- **Sources:** DynamoDB hashes the partition key [S40]; per-partition write limit 1,000 a second [S40]. Suq is a course story.

## sysdesign-m9-ring-play

- **Chapter and beat:** 9.3 beat 4, "Virtual nodes: many small points per node".
- **Claim:** Giving each node many points evens out the load, adding a node moves only about 1 key in N+1 and only to the new node, and removing a node shares its keys over the survivors.
- **Primitives:** custom canvas on `BeatFrame`. `picture-slider.tsx` for the points dial; `SvgNode` cards for the nodes; a ring drawn as an SVG circle. No existing primitive draws a ring, so this one is new. Two buttons outside the picture: "Add node" and "Remove node" (removes the most recently added node; disabled at 2 nodes and at 8 nodes).
- **Input:** the points per node dial, on a snap rail: 1, 2, 5, 10, 20, 50, 100, 200. Default 1, so the first look is the lumpy ring. Start with 4 nodes named node-a to node-d. Added nodes are named node-e, node-f and so on.
- **Model:** 10,000 sample keys `order:0` to `order:9999`, hashes cached once. A node `name` with `v` points has points at `hash32(name + "#" + i)` for i from 0 to v-1. A key belongs to the first point at or after `hash32(key)`, wrapping to the first point; equal positions are ordered by node name. Outputs: key count per node, busiest divided by fair share, and after an Add or Remove the percent of keys that changed owner and how many changed between nodes that were already on the ring (always 0 on an add).
- **Picture:** a ring with each node's arcs coloured (at 200 points, colours blend into thin bands, which is the point). Beside it, one bar per node against a dashed fair-share line. After an Add or Remove, the keys that moved flash once and a pill under the ring says "moved 19.7%". A pill shows the ideal ("ideal 20%").
- **Numbers to check** (10,000 keys, nodes node-a to node-d, adding node-e):

| Points per node | Busiest / fair, 4 nodes | Moved when adding node-e | Busiest / fair, 5 nodes | Moved when removing node-b from the 4 |
|---|---|---|---|---|
| 1 | 1.68 | 1.3% | 2.10 | 25.9% |
| 5 | 1.56 | 16.0% | 1.45 | 16.8% |
| 10 | 1.26 | 20.9% | 1.17 | 31.4% |
| 50 | 1.26 | 17.7% | 1.32 | 19.3% |
| 100 | 1.15 | 19.7% | 1.17 | 23.7% |
| 200 | 1.08 | 18.9% | 1.07 | 22.9% |

  With 100,000 keys the chapter reports 1.68, 1.26, 1.14 and 1.09 for busiest / fair at 1, 10, 100 and 200 points, and 1.4%, 21.1%, 19.4%, 19.1% moved; 10,000 keys is noisier. Hash mod 4 to mod 5 moves 80% (79.9% on the 10,000 keys); show it as a grey reference tick on the "moved" pill.
- **Verdicts:** after a drag: "Busiest node: 1.68 times its share" (bad above 1.5, warn above 1.15, otherwise good). After an add: "Added node-e: 19.7% of keys moved" (good when at most 1.3 times ideal, else warn). After a remove: "Removed node-b: 23.7% of keys moved".
- **Reduced motion:** no flash; the moved keys are listed as a count.
- **Accessibility:** the dial is a slider ("100 points per node, busiest node 1.15 times its share"). Buttons are real buttons. Colours are paired with node labels on the bars.
- **Sources:** Karger et al. 1997 [S18]; Dynamo virtual nodes [S45]; Envoy ring hash [S16]. Figures are the course's own simulation.

## sysdesign-m9-celebrity-play

- **Chapter and beat:** 9.4 beat 2, "More shards do not help; splitting does".
- **Claim:** Adding shards cools every shard except the one holding a hot key. Splitting the key into sub-keys (salting) brings the hottest shard under its limit, but the sub-keys land by hash, so the result depends on luck.
- **Primitives:** `picture-slider.tsx` for the shard count rail, plus a row of salt chips (1, 2, 4, 8, 16) inside the picture, each a 44px target. One button outside the picture: "Reset". Shard bars drawn as SVG with `SvgNode`-style cards for the busiest shard only.
- **Input:** (1) shard count S on a linear rail, 4 to 16, snap to 4, 8, 12, 16, default 4. (2) the salt chips, default 1 (no salt).
- **Model:** Background load 1,200 writes a second spread over many keys: 1,200 / S per shard. Noor's key `seller:noor-crafts` takes 1,800 writes a second. Salt k: sub-keys `seller:noor-crafts#0` to `#(k-1)`, each taking 1,800 / k; with k = 1 the plain key. A key goes to shard `hash32(key) mod S`. Shard limit 1,000 writes a second. Read cost pill: "Reading Noor's total: k reads".
- **Numbers to check** (busiest shard, writes a second):

| Shards | Salt 1 | Salt 2 | Salt 4 | Salt 8 | Salt 16 |
|---|---|---|---|---|---|
| 4 | 2,100 | 1,200 | 1,200 | 975 | 1,088 |
| 6 | 2,000 | 2,000 | 1,100 | 650 | 763 |
| 8 | 1,950 | 1,050 | 600 | 600 | 600 |
| 12 | 1,900 | 1,000 | 550 | 550 | 438 |
| 16 | 1,875 | 975 | 525 | 300 | 413 |

  At 4 shards and salt 4, the sub-keys land on shards 2, 4, 4 and 1, with loads 750, 750, 300 and 1,200 (shards 1 to 4). At 4 shards with no salt, Noor's key lands on shard 4 with 2,100 and the others have 300. Do not smooth the non-monotone cells (4 shards: salt 16 is worse than salt 8; 6 shards: salt 2 is 2,000); they are the lesson.
- **Picture:** S shard bars in rows of up to 8, each against a dashed limit line at 1,000. The busiest bar is red above 1,000, amber from 800 to 1,000, green below, and carries its value. Sub-key chips fall onto their shards as small dots (one per sub-key) so collisions are visible. A thin "average" tick shows how misleading the average is (3,000 / S).
- **Verdicts:** over the limit: "Hottest shard: 2,100 of 1,000 limit" (bad). Between 800 and 1,000: "Hottest shard: 975 of 1,000 limit" (warn). Under 800: "Hottest shard: 600 of 1,000 limit" (good).
- **Reduced motion:** dots appear in place.
- **Accessibility:** the rail is a slider ("8 shards, hottest shard 1,950 writes a second"); chips are radio buttons. The verdict repeats the hottest number in words.
- **Sources:** per-partition limit [S40]; hot partitions as the most common early problems [S44]. Figures are the course's own simulation with Suq's made-up load.

## sysdesign-m9-rebalance-play

- **Chapter and beat:** 9.5 beat 3, "Moving data while requests keep coming".
- **Claim:** The scheme decides how much data must move (80% for hash mod N, about 20% for fixed partitions or a ring), and while the move runs, clients with an old map send requests to the wrong node in proportion to how much has already moved.
- **Primitives:** `picture-slider.tsx` for the time rail (drag the move forward); custom bars for data moved. Two toggles outside the picture: "Hash mod N | Fixed partitions" and "Clients: old map | fresh map".
- **Input:** (1) scheme toggle, default Hash mod N. (2) map toggle, default Old map. (3) progress of the move, 0 to 100% of the move time, on a linear rail inside the picture, arrow keys step 1%, Page keys 10%, default 0.
- **Model:** Data 1.8 TB, four nodes to five, requests 5,000 a second spread evenly over keys, copy speed 100 MB a second. Changed share: Hash mod N 0.80 (N over N+1); Fixed partitions 0.20 (13 of 64 partitions, rounded). `bytesToMove = share x 1.8 TB`: 1.44 TB or 360 GB. `moveSeconds = bytesToMove / 100 MB/s`: 14,400 s (4 h) or 3,600 s (1 h). At progress p: `moved = p x bytesToMove`; `movedShare = moved / 1.8 TB`; `wrongNodePerSecond = 5,000 x movedShare` when clients hold the old map, else 0.
- **Numbers to check:** half way (p = 0.5), old map: Hash mod N moved 720 GB, 2,000 wrong-node requests a second. Fixed partitions moved 180 GB, 500 a second. At p = 1 with the old map: 4,000 (mod) and 1,000 (fixed) wrong-node requests a second, because every moved key now lives somewhere else; with a fresh map both are 0.
- **Picture:** two bars: "data moved" (GB so far of the total) and "wrong-node requests a second" (against the 5,000 line), plus a small row of five node cards where moved volume flows from the four old nodes to the new one. Under Hash mod N the flow also arrows between old nodes (waste: about 75% of the moved keys, 59,935 of 80,152 in the challenge test).
- **Verdicts:** at p = 0: Hash mod N "1.44 TB to move: about 4 hours" (bad); Fixed "360 GB to move: about 1 hour" (good). With an old map and p above 0: "2,000 requests/s hit the wrong node" (warn, bad above 1,500). With a fresh map and p above 0: "Map is fresh: no wrong-node requests" (good).
- **Reduced motion:** the picture shows the state at p; no flow animation.
- **Accessibility:** the rail is a slider ("move 50% done, 720 GB moved, 2,000 wrong-node requests a second"); toggles are real buttons.
- **Sources:** N over N+1 is arithmetic; Envoy ring hash [S16]; Dynamo [S45]. Suq numbers and the copy speed are course assumptions.

## sysdesign-m9-scatter-play

- **Chapter and beat:** 9.6 beat 4, "Drag the shard count: the tail grows".
- **Claim:** A search that must ask every shard is slow whenever any shard is slow, so the share of slow searches climbs with the shard count. A global index asks one shard, but each write becomes two writes.
- **Primitives:** extend `models/fan-out.ts` (`slowChance`, `pageLoad`, `tallyLoads`) and the `sysdesign-m2-fan-out-play` canvas (`FanOutPlayCanvas`, `picture-slider.tsx`, `backendGrid`). Rename "backends" to "shards" in the copy. One toggle outside the picture: "Local index | Global index" (44px, labelled). Reuse the "Load the page" button as "Run a search".
- **Input:** (1) shard count n, 1 to 100 on the same snapping rail as the fan-out canvas (snap 1, 10, 20, 50, 100), default 20. (2) the index toggle, default Local.
- **Model:** each shard is slow (200 ms) with chance 1 in 100, otherwise 5 ms. Local index: a search asks all n shards; its time is the slowest; `slowChance(n) = 1 - 0.99^n`. Global index: a search asks 1 index shard; `slowChance = 1%`. Write cost: Local 1 write per order, Global 2 writes per order (the row and its index entry), shown as a pill "Each order = 2 writes".
- **Numbers to check:** Local: n = 1 gives 1%, 10 gives 9.6%, 20 gives 18%, 50 gives 39%, 100 gives 63%. Global: 1% at every n.
- **Picture:** the fan of n shard tiles as in the fan-out canvas; under Global, only one index tile is lit and one line goes out. A tally of the last 12 searches (green fast, red slow) and a counter "3 slow of 14".
- **Verdicts:** "18% of searches hit a slow shard" (good under 5%, warn under 30%, bad from 30%), same colours as the fan-out canvas. Under Global: "1% of searches hit a slow shard" (good).
- **Reduced motion:** no automatic searches; each press of "Run a search" shows the next result and adds to the tally.
- **Accessibility:** as the fan-out canvas: slider with value text "20 shards, 18 percent slow"; toggle is a real button pair; the tally is also said in words.
- **Sources:** Dean and Barroso [S8] (100 servers, 1 in 100 slow, 63%); DynamoDB global secondary indexes are asynchronous [S41]. Times are made-up story numbers.
