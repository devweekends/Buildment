# Module 3 playable specs

Five reserved playable slugs for Module 3 ("Networking for system designers"). None has a folder yet; each chapter already places `<InteractiveCanvas slug="..." />` and tells the learner what to drag or tap. Source ids refer to `agent-ip/work/system-design/01-research-dossier.md`. Every playable sits in a `BeatFrame` with at most two controls outside the picture. Every verdict below is 38 characters or fewer.

## sysdesign-m3-handshake-cost (3.2, beat 4: "Distance multiplies every round trip")

- **Claim:** The time before the first byte on a new connection is the number of round trips times one round trip. The protocol sets the count; the distance sets the round trip.
- **Model:** first byte = n × RTT.
  - Plain TCP (HTTP): n = 2.
  - TCP with TLS 1.3: n = 3.
  - QUIC first visit: n = 2.
  - QUIC 0-RTT on a return visit: n = 1.
  - Reused connection: n = 1.
  - The counts are derived from [S10], [S11] and [S13].
  - Leave TLS 1.2 out until its source note in 3.2 is resolved (RFC 5246). Challenge 2 measured 2 round trips for its handshake.
- **Inputs:** a distance rail with four snaps, from napkin-math [S3]:
  - Same region: 0.25 ms.
  - North America east to west: 60 ms.
  - Western Europe to North America East: 80 ms.
  - Western Europe to Singapore: 160 ms.
  - Five protocol chips drawn inside the picture.
- **What moves:** A phone card and a server card, spaced by the distance. Dots fly once per round trip. A stacked bar has one segment per round trip, labelled TCP, TLS and request, with the total in ms on the bar.
- **Worked values:**
  - TCP with TLS 1.3: 0.75, 180, 240 and 480 ms.
  - QUIC: 0.5, 120, 160 and 320 ms.
- **Verdicts:**
  - "Same region: under 1 ms, any way"
  - "TCP+TLS: 3 round trips, 480 ms"
  - "QUIC saves one round trip: 160 ms"
  - "Reused: 1 round trip, 160 ms"
  - "0-RTT: safe-to-repeat requests only"
- **Primitive:** `picture-slider` for the distance rail, with the bars drawn in the picture.

## sysdesign-m3-ttl-spread (3.3, beat 3: "A change spreads only as caches expire")

- **Claim:** After a DNS change, the share of resolvers that have the new answer grows in a straight line, and every resolver has it after one TTL [S9].
- **Model:**
  - There are 20 resolvers. At the moment of the change, resolver i holds a copy aged (i + 0.5) / 20 × TTL.
  - Each resolver switches to the new answer at TTL minus its copy's age.
  - So the share on the new answer is share(t) = min(1, t / TTL).
  - With TTL 0, every resolver gets the new answer at once.
- **Inputs:**
  - TTL snaps: 0 s, 60 s (the ELB TTL [S15]), 300 s, 3,600 s and 86,400 s. The last three are illustrative.
  - A time-after-change rail from 0 to 1.2 × TTL, with a tick at the TTL.
- **What moves:** Dots flip from the old address (amber) to the new one (green) as time is dragged. A time label and a counter show how many of the 20 are on the new address.
- **Worked values:** With a TTL of 3,600 s, about 1 in 6 resolvers has the new answer after 10 minutes, half after 30 minutes, and all after an hour.
- **Verdicts:**
  - "TTL 0: every lookup gets the change"
  - "{k} of 20 still on the old address"
  - "All 20 on the new address"
  - "1-day TTL: up to a day to move"
- **Primitive:** `picture-slider` for time, with the TTL as ladder steps (a second slider or chips).

## sysdesign-m3-loss-toggle (3.4, beat 5: "Drop a packet, compare the versions")

- **Claim:** One lost packet delays different files depending on the HTTP version.
  - HTTP/1.1: the lost file and every file queued behind it on that connection.
  - HTTP/2: every stream.
  - HTTP/3: only the stream that lost the packet.
  - Sources: [S12] and [S13].
- **Model:**
  - Three files (a, b, c), one packet each, RTT 80 ms [S3].
  - A dropped packet's resend arrives one RTT later. This is illustrative and matches the scenes `sysdesign-m3-h2-stall` and `sysdesign-m3-h3-streams`.
  - No drop:
    - HTTP/1.1 on one connection: a at 80 ms, b at 160 ms, c at 240 ms.
    - HTTP/2 and HTTP/3: all three at 80 ms.
  - Drop file k:
    - HTTP/1.1: file k and every later file arrive 80 ms later. If a is dropped: 160, 240 and 320 ms.
    - HTTP/2: all three at 160 ms.
    - HTTP/3: k at 160 ms, the others at 80 ms.
- **Inputs:**
  - Three version chips inside the picture.
  - Tap a packet in flight to drop it (tap again to undo).
  - Replay.
- **What moves:** Packets fly from the server to the browser. The dropped packet falls with a cross. On HTTP/2, packets that arrived wait in a "held" box until the resend arrives. Arrival tags land on an ms strip.
- **Verdicts:**
  - "No loss: all 3 in 80 ms"
  - "HTTP/2: 1 loss delays all 3 files"
  - "HTTP/3: only a waits, 160 ms" (the dropped file's name is filled in)
  - "HTTP/1.1: a and those behind it wait"
- **Primitive:** None of the listed primitives fits directly. Use a scene inside controls, built per input by a model, the way `models/replica-lag-scene.ts` builds its variants. Or use `design-stepper`, whose steps can hold a "break a part" action.

## sysdesign-m3-chat-four-ways (3.5, beat 5: "Same chat, four ways, side by side")

- **Claim:** Polling spends requests and delay. Long polling, server-sent events and WebSockets spend open connections instead.
- **Model:** N users, each getting M = 2 messages a minute (illustrative). Long polls are held up to H = 30 s (illustrative). One-way network delay is 40 ms, half the 80 ms round trip [S3].
  - **Polling every P seconds:** average delay P / 2, worst case P. Requests per second: N / P. Open connections: about none.
  - **Long polling:** delay 40 ms. Requests per second: about N × (M / 60 + 1 / H). Open connections: N.
  - **SSE:** delay 40 ms. Requests per second: about 0 (reconnects only). Open connections: N.
  - **WebSocket:** delay 40 ms. Requests per second: about 0 (reconnects only). Open connections: N. It also carries the app's own messages on the same connection.
  - Check at N = 10,000 and P = 5 s: polling makes 2,000 requests per second with a 2.5 s average delay. Long polling makes about 667 requests per second with 10,000 connections open.
  - Sources: [S104], [S105] and [S106].
- **Inputs:**
  - A users rail with snaps at 1,000, 10,000 and 100,000.
  - Poll interval chips: 1, 5, 30 and 60 s.
  - Tap a lane to focus on that way.
- **What moves:**
  - Four lanes, with dots flowing at each way's request rate (one dot stands for many requests).
  - A delay clock on each lane.
  - A server card whose pill shows open connections and requests per second.
- **Verdicts:**
  - "Polling 5 s: 2,000 req/s, 2.5 s late"
  - "Long poll: 10,000 open, 667 req/s"
  - "SSE: 10,000 open, almost no requests"
  - "WebSocket: same, plus two-way"
- **Primitive:** `traffic-playground` (one configuration per way), with `picture-slider` for the users rail.

## sysdesign-m3-blocking-call (3.6, beat 5: "One blocking call stops everyone")

- **Claim:** On an event loop, one blocking call stalls every request and lowers the server's ceiling. A thread pool contains the block but tops out far lower.
- **Model:** All numbers are illustrative.
  - Each request needs c = 1 ms of CPU and w = 50 ms of async wait. Arrivals: 100 per second.
  - A share s of requests (snaps 0, 1% and 5%) also does B ms of CPU (snaps 0, 20, 100 and 200 ms).
  - **Event loop:**
    - Ceiling = 1000 / (c + sB) requests per second: 1,000 per second with no slow calls; about 333 per second at s = 1% and B = 200 ms.
    - Busy share of the loop = λ(c + sB) / 1000.
    - While a slow call runs, every other request waits up to B ms, so p99 rises by about B for every route.
  - **Thread pool (T = 8 threads):**
    - Each request holds a thread for c + w + sB ms.
    - Ceiling = 8000 / (c + w + sB): about 157 per second, or about 151 with s = 1% and B = 200 ms.
    - A slow call ties up only 1 of the 8 threads.
  - Fold references: Little's law [S5]; a context switch costs about 10 microseconds [S3].
- **Inputs:**
  - Drag B along a rail.
  - Tap the share chips.
  - One toggle between event loop and thread pool (the one control outside the picture).
- **What moves:**
  - Request dots flow into the server.
  - Event loop: one lane. It turns red during a slow call, and incoming dots pile up in front of it.
  - Thread pool: eight lanes. One turns red; the others keep flowing.
  - A small inset curve plots the ceiling against B.
- **Verdicts:**
  - "Loop blocked 200 ms: all requests wait"
  - "Ceiling falls to 333 requests/s"
  - "Pool: 1 of 8 threads stuck"
  - "Pool tops out near 157 requests/s"
  - "No blocking: loop ceiling 1,000/s"
- **Primitive:** `traffic-playground`, which has a queue in front of the server, pill tones and an inset curve.
