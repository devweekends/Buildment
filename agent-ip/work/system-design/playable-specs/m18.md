# Module 18 playable specs

Six reserved playable slugs for Module 18 ("Running it: Linux, containers, Kubernetes, CI/CD and the cloud"). None has a folder yet; each chapter already places `<InteractiveCanvas slug="..." />` and tells the learner what to drag or tap. Source ids refer to `agent-ip/work/system-design/01-research-dossier.md`. Every playable sits in a `BeatFrame` with at most two controls outside the picture. Every verdict below is 38 characters or fewer. Numbers marked "course measurement" come from challenge 17 on a Windows laptop with Docker Desktop on 2026-10-24 and are round-trip checkable by running that challenge.

## sysdesign-m18-isolation-layers (18.2, beat 2: "Namespaces decide what a process sees")

- **Claim:** A container is an ordinary process with a limited view (namespaces) and limited resources (cgroups). Each namespace hides one kind of thing. A memory limit kills; a CPU limit only slows.
- **Model:** One service process on a host that has 212 processes (made up). The host has another service listening on port 3000 and a host name `ops-server`. The service needs 150 MB of memory and a request needs 200 ms of CPU on one thread.
  - Four namespace switches, each on by default: PID, Network, Mount, Host name.
  - What the process sees: PID on: 1 process (itself, as process 1); off: 212 processes. Network on: its own address and a free port 3000; off: the host's network, where port 3000 is already taken. Mount on: only the image's files; off: the host's `/etc` and `/home`. Host name on: `a1b2c3d4e5f6` (a container id); off: `ops-server`.
  - Memory limit rail, 64 to 512 MB. Below 150 MB the process is killed.
  - CPU limit rail, 0.25 to 2 CPUs. Request time = 200 ms divided by min(CPUs, 1).
- **Formulas:** killed if limit < 150 MB. Request time (ms) = 200 / min(cpu, 1).
- **Check points:**

  | Memory limit | CPU limit | Result |
  |---|---|---|
  | 256 MB | 1 | Runs, request 200 ms |
  | 128 MB | 1 | Killed (exit 137) |
  | 256 MB | 0.5 | Runs, request 400 ms (course measurement 406 ms) |
  | 256 MB | 0.25 | Runs, request 800 ms |

- **Inputs:** tap four switches drawn on the container card. Drag two rails (memory with snap points at 128 and 256 MB, CPU with snap points at 0.5 and 1).
- **What moves:** the "what it sees" panel inside the container card: a process list that shrinks to one line when PID is on, a port row that turns red on a clash, a file list that swaps between image files and host files. A memory bar fills to 150 MB with a red cut line at the limit. A request dot takes longer to cross as the CPU limit falls.
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | All four on, limits fine | "Isolated: it sees only itself" |
  | PID off | "It can see and signal host processes" |
  | Network off | "Port 3000 clashes with the host" |
  | Mount off | "It can read the host's files" |
  | Host name off | "It sees the host's name" |
  | Memory limit under 150 MB | "Over the memory limit: killed" |
  | CPU under 1 | "CPU limit: slower, never killed" |

- **Primitive:** `block-map.tsx` for the switches and card, plus `picture-slider.tsx` for the two rails.
- **Sources:** namespaces(7) and cgroups(7) [S117]; course measurements for 213 ms and 406 ms.

## sysdesign-m18-layer-cache (18.3, beat 2: "Change one file, see what rebuilds")

- **Claim:** A Docker build reuses every layer above the first changed one and rebuilds everything from there. Where a step sits decides how often it runs.
- **Model:** Two Dockerfiles, each a stack of layer cards with a build time in seconds (round numbers close to the course measurement, where the install is the slow layer).
  - Order A, copy everything first: `FROM node:24-alpine` 0 s (cached), `COPY . .` 0.3 s, `RUN npm install` 8 s, `CMD` 0 s.
  - Order B, package files first: `FROM` 0 s, `COPY package.json package-lock.json` 0.1 s, `RUN npm ci` 8 s, `COPY server.js` 0.3 s, `CMD` 0 s.
  - Three files that can change: `README.md` (listed in `.dockerignore`, so it is never copied), `server.js` (code), `package.json` (a dependency).
- **Formulas:** the first layer whose input changed, and every layer after it, is rebuilt. All earlier layers are CACHED. Total = sum of rebuilt layer times.
- **Check points:**

  | Dockerfile | File changed | Layers rebuilt | Total |
  |---|---|---|---|
  | A | server.js | COPY . ., npm install, CMD | 8.3 s |
  | B | server.js | COPY server.js, CMD | 0.3 s |
  | A | package.json | COPY . ., npm install, CMD | 8.3 s |
  | B | package.json | COPY package files, npm ci, COPY server.js, CMD | 8.4 s |
  | A or B | README.md | none | 0 s |

- **Inputs:** tap one of three file chips drawn above the stack. One toggle outside the picture swaps the Dockerfile order (A or B).
- **What moves:** layer cards stacked bottom to top. Rebuilt cards flash amber and show their seconds. Cached cards show a green CACHED pill. A total-seconds counter runs under the stack. When the order changes, the cards animate to their new positions.
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | B, server.js | "Only the last copy step runs" |
  | A, server.js | "Everything after the copy reruns" |
  | B, package.json | "Install reruns: dependencies changed" |
  | README.md | "Nothing changed: all layers cached" |

- **Primitive:** `design-stepper.tsx` (stack of steps) or `block-map.tsx` (chips); a small new stack view is acceptable if neither fits.
- **Sources:** Docker build cache documentation (add to dossier); course measurement: editing server.js reused 1 of 4 steps with the naive order and 3 of 5 with the good order (7.3 s and 5.6 s). Seconds are noisy because of the network; the reused steps are the reliable signal. The sample service has only 13 packages; a real project's install is much longer.

## sysdesign-m18-cluster-play (18.4, beat 5: "Play: kill, fail, scale")

- **Claim:** Pods are replaceable. Readiness decides who gets traffic. CPU decides how many pods run, and a saturated CPU reading under-counts the need.
- **Model:** A Deployment of 3 pods behind a Service, with an autoscaler. Each pod can serve 100 requests a second at 100% CPU. The offered load is a rail from 0 to 600 requests a second, default 180.
  - Ready pods share the load equally. CPU per ready pod = min(100, 100 x load / (100 x ready pods)). Anything above capacity is dropped.
  - Tap a pod to kill it: a replacement appears, starts, warms up for 3 play-seconds, then becomes ready.
  - Tap a pod's probe chip to make its readiness check fail: the pod stays running (and keeps its place) but leaves the Service until the chip is tapped again.
  - Autoscaler switch (on or off). When on, every 3 play-seconds (stands for 15 s): desired = ceil(pods x CPU / 60), ignoring a ratio within 10% of 1, minimum 2, maximum 8. Scale-down only after 8 play-seconds of lower readings (stands for the 300 s window). New pods take 3 play-seconds to become ready.
- **Check points:**

  | State | CPU per ready pod | Note |
  |---|---|---|
  | Load 180, 3 ready | 60% | On target, no scaling |
  | Load 180, one killed (2 ready) | 90% | Near the knee until the replacement is ready |
  | Load 180, one readiness failed | 90% | Third pod running but not serving |
  | Load 300, autoscaler on, 3 ready | 100% | Desired = ceil(3 x 100 / 60) = 5; then 60% |
  | Load 600, autoscaler on, 3 ready | 100%, 300 dropped | Desired 5; still saturated; next desired = ceil(5 x 100 / 60) = 9, capped at 8 |

- **Inputs:** tap a pod (kill), tap a probe chip on each pod (fail or fix readiness), drag the load rail. One toggle outside the picture switches the autoscaler.
- **What moves:** pod cards in a row, each with a CPU bar and a ready/not-ready pill. A Service bar above sends request dots only to ready pods. A killed pod flashes red and a new card grows in as "starting". Dropped requests fall off the bottom as red dots.
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | All ready, near 60% | "On target: 60% busy" |
  | A pod died or is unready, rest under 100% | "One pod short: the rest take its load" |
  | Over capacity | "Over capacity: requests dropped" |
  | Scaling up, new pods not ready | "Scaling: new pods are not ready yet" |
  | Probe failed on a running pod | "Alive but not ready: no traffic" |

- **Primitive:** `block-map.tsx` for the pods and chips, plus `traffic-playground.tsx` for the load rail and request dots.
- **Sources:** Kubernetes probes [S20], rolling and Deployment behaviour [S35], HPA formula, 15 s loop, 10% tolerance and 300 s scale-down window [S34]; chapter 4.6 for the saturated-reading effect. Course measurement: a deleted pod was replaced in under 1 s and 3 pods were ready again after about 6 s.

## sysdesign-m18-pipeline-step (18.5, beat 2: "Play: step through, then break a stage")

- **Claim:** A red stage stops the pipeline and every later stage is skipped. The cost of a failure is the time up to the red stage, so the order of stages matters.
- **Model:** Six stages in order with their seconds (course measurement with a cold cache for the first five, the sixth illustrative): lint 0.2, service tests 2.8, build image 38.0, smoke test 6.4, size gate 1.0, publish image 2.0. One toggle scales every time by 10 ("on a shared runner"), so lint is 2 s, tests 28 s, build 380 s and so on.
  - Time until you know = sum of the stage times up to and including the first red stage, or all of them if none is red.
- **Check points:**

  | Broken stage | Time until you know (laptop) | Time (shared runner, x10) |
  |---|---|---|
  | None | 50.4 s | 8 min 24 s |
  | Lint | 0.2 s | 2 s |
  | Service tests | 3.0 s | 30 s |
  | Smoke test | 47.4 s | 7 min 54 s |
  | Size gate | 48.4 s | 8 min 4 s |

- **Inputs:** a Step button outside the picture moves the commit one stage. Tap a stage card to break it or fix it. One toggle outside the picture scales the times (laptop or shared runner).
- **What moves:** a commit token slides along a conveyor of six cards. A passed stage turns green and shows its seconds. A broken stage turns red; later stages turn grey with "skipped". A clock under the conveyor counts the seconds the commit has waited.
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | All green | "All gates passed: ready to ship" |
  | Red at stage N | "Red at <stage>: known in <time>" (shorten the name to stay within 38 characters) |
  | Red at the first stage | "Cheap check first: known at once" |

- **Primitive:** `design-stepper.tsx` for the step-through, with `svg-button.tsx` for tapping a stage.
- **Sources:** course measurements from challenge 17 part 2 (cold-cache pipeline run of 48.4 s; the naive Dockerfile failing lint in 0.2 s in the fast-first order against 24.6 s in the slow-first order).

## sysdesign-m18-canary-blast (18.6, beat 4: "Play: the share and the error rate")

- **Claim:** A canary limits how many users a bad release can reach. The whole-service dashboard hides a small canary's errors, and a bigger share finds the bug sooner.
- **Model:** The service handles R = 3,000 requests a minute (made up). The stable version fails 0.2% of requests. The canary gets a share s of traffic and a bug makes e of its requests fail. An alert fires once the canary has produced F = 30 failed requests (made up).
- **Formulas:**
  - Canary requests a minute = R x s.
  - Canary failures a minute = R x s x e.
  - Minutes to the alert = F / (R x s x e).
  - Requests that reached the bug before the alert = R x s x minutes = F / e.
  - Dashboard error rate = (1 - s) x 0.2% + s x e.
- **Check points:**

  | Share s | Bug rate e | Failures a minute | Minutes to alert | Requests exposed | Dashboard |
  |---|---|---|---|---|---|
  | 5% | 20% | 30 | 1.0 | 150 | 1.2% |
  | 5% | 2% | 3 | 10 | 1,500 | 0.29% |
  | 1% | 5% | 1.5 | 20 | 600 | 0.25% |
  | 25% | 20% | 150 | 0.2 (12 s) | 150 | 5.15% |

- **Inputs:** drag the canary's share on one rail, 1% to 50% with snap points at 5%, 10% and 25%. Drag the bug's error rate on a second rail, 1% to 50% with snap points at 5% and 20%.
- **What moves:** a crowd of user dots streams into two lanes, stable and canary, in the proportion s. The canary lane fills with red dots at rate e. A bell lights when F failures have piled up. Three numbers sit by the lanes: minutes to the alert, requests exposed and the whole-service dashboard rate.
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | Dashboard under 1% and e at least 2% | "Bug hidden in the average" |
  | Minutes to alert over 10 | "Slow to see: raise the share" |
  | Share 25% or more | "Fast alert, but 1 in 4 users on it" |
  | Otherwise | "Small share, quick alert" |

- **Primitive:** `picture-slider.tsx` for both rails and `traffic-playground.tsx` for the dots.
- **Sources:** Google SRE Workbook, canarying releases: a 20% error rate on a 5% canary shows as about 1% overall [S110]. All other numbers are made up for the example.

## sysdesign-m18-cloud-explorer (18.7, beat 3: "Play: pick a block for each need")

- **Claim:** Every need maps to a block, and the best block is the one that matches the shape of the load. Managed blocks cost more per unit and remove work.
- **Model:** Six needs and eight blocks, with made-up round prices (not AWS prices; the dossier says exact cloud prices are volatile).
  - Needs: (1) serve the Daftar API, steady load of 100 requests a second; (2) resize an uploaded photo, 10 a day; (3) keep 2 TB of note exports; (4) store notes in a relational database; (5) queue the order emails; (6) speed up repeated reads.
  - Blocks with AWS names and illustrative unit prices: virtual machine (EC2) $0.04 an hour; containers (ECS or EKS) $0.05 an hour per container; function (Lambda) $0.20 per million requests plus $0.0000167 per second of 1 GB; object storage (S3) $0.02 per GB-month; block storage (EBS) $0.10 per GB-month; managed database (RDS) $0.10 an hour; queue (SQS) $0.40 per million requests; cache (ElastiCache) $0.05 an hour.
  - Fit table: each need has one best block, one acceptable block and the rest wrong, each with a one-line reason shown when tapped.

  | Need | Best | Acceptable | Example wrong pick and its reason |
  |---|---|---|---|
  | API, steady | Containers | Virtual machine | Function: per-request billing costs more at steady load |
  | Photo resize, 10 a day | Function | Containers | Virtual machine: paid all day for 20 seconds of work |
  | 2 TB exports | Object storage | Block storage | Cache: loses data and costs more per GB |
  | Notes in a database | Managed database | Virtual machine | Object storage: no queries or transactions |
  | Order emails queue | Queue | Managed database | Cache: a restart loses the jobs |
  | Faster repeated reads | Cache | Managed database | Queue: it passes work, it does not answer reads |

- **Formulas:** monthly price = unit price x quantity, 720 hours in a month; 2 TB = 2,000 GB (S3 about $40, EBS about $200 for the same data in this model).
- **Check points:** the 2 TB need costs about $40 a month on object storage and about $200 on block storage. The photo need costs under $1 a month on a function and about $29 a month on one virtual machine (720 x $0.04).
- **Inputs:** tap a need chip, then tap a block card. No sliders.
- **What moves:** the chosen block card lifts and a line connects need to block. A panel inside the picture shows the AWS name, "you manage" and "provider manages" lines, and the illustrative monthly price, in green for the best fit, amber for acceptable and red for wrong.
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | Best fit | "Best fit for this load" |
  | Acceptable | "Works, but costs more or needs work" |
  | Wrong | "Wrong shape for this need" |

- **Primitive:** `sorter.tsx` or `block-map.tsx` (tap a card to place it); no new primitive is needed.
- **Sources:** AWS service names and one-line definitions from AWS documentation (S3, EBS, EFS, EC2, ECS, Lambda; fetched 2026-10-24, dossier ids to be added); ALB and NLB [S15]; Aurora [S39]; DynamoDB [S40]; ElastiCache [S26]; SQS [S83 to S85]. Prices are made up and must be labelled "illustrative, not AWS prices".
