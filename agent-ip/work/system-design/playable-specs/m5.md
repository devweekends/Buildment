# Module 5 playable specs (Caching and CDNs)

Six reserved playable slugs, one per Learn chapter. The chapters already contain `<InteractiveCanvas slug="..." />` and beat text that tells the learner what to drag or tap. Numbers come from the research dossier (source IDs in brackets) or are labelled story numbers (Matjar is a fictional shop). Every verdict below is 38 characters or fewer. Use the card style (`SvgNode`, `DotGrid`, `VerdictBanner`) and `BeatFrame`.

## 1. sysdesign-m5-cache-path (5.2 "Add up the path")

- **Claim:** The layer nearest the user decides the wait; the layer nearest the database decides the database load. A design needs both numbers.
- **Picture:** a vertical path of cards: Shopper (Singapore) > CDN edge (Singapore) > [160 ms trip] > App memory > Valkey > Database. Each cache card has a small hit-rate handle (a horizontal bar inside the card, dragged left and right). Requests flow down; dots stop and turn back at the layer that hits, in proportion to its hit rate. Two live numbers sit next to what they describe: "time added after the edge" beside the edge-to-origin link, and "queries/s" beside the Database card.
- **Model:** costs from the dossier: edge to origin round trip 160 ms (EU West to Singapore) [S3]; app memory hit about 0 ms (main memory 100 ns [S2]); Valkey read 0.5 ms [S3]; the page needs 5 queries of 0.5 ms = 2.5 ms [S3, story]. Traffic: 1,000 page views a second (story).
  - T = (1 - h_e) x (160 + (1 - h_m) x (0.5 + (1 - h_v) x 2.5)) ms
  - DB queries/s = 1,000 x (1 - h_e) x (1 - h_m) x (1 - h_v) x 5
  - With no Valkey hits the Valkey miss still costs 0.5 ms (a weak cache is slower than none).
- **Inputs:** h_e, h_m, h_v each 0 to 99%, step 1, snap points 0, 50, 80, 90, 95. Defaults: h_e 80, h_m 0, h_v 90. Arrow keys step 1, Page keys 10.
- **Numbers to check:** defaults give T = 32.2 ms and 100 queries/s. h_e 90: T = 16.1 ms, 50 queries/s. h_e 80, h_v 50: T = 32.4 ms, 500 queries/s. All zero: T = 163 ms, 5,000 queries/s.
- **Verdicts:** T under 20 ms and queries under 200: "Fast for shoppers, calm database" (32). T under 20 ms, queries 200 or more: "Fast pages, busy database" (25). T 20 ms or more, queries under 200: "Calm database, slow far away" (28). Otherwise: "Slow pages and a busy database" (30).
- **Primitive:** `block-map` (tap/drag on blocks along a path) is the closest; a hit-rate handle per block is new. Alternatively `estimate-chain` with three draggable inputs, drawn as a vertical chain.
- **Limits fold:** the phone-to-edge trip is left out (paid either way; source needed for a typical value); napkin-math numbers can be 2 to 3 times off; one request per page.

## 2. sysdesign-m5-pattern-stepper (5.3 "Pick a pattern, then crash it")

- **Claim:** Every pattern except write-back treats the cache as a copy, so a cache crash costs speed and load, not data. Write-back loses writes that were confirmed but not flushed.
- **Picture:** App, Cache, Database cards (as in `sysdesign-m5-aside-read`). A row of five pattern chips on top: cache-aside, read-through, write-through, write-back, write-around. Four steps (Back/Next): 1 read p42 (miss then hit), 2 write p42 = 899, 3 crash the cache node, 4 read p42 again. Three status pills update per step: "cache copy" (fresh / stale / none), "database has write" (yes / not yet / lost), "reads to database after crash" (count).
- **Model (per pattern, per step):**
  - cache-aside: read: 3 trips on miss, 1 on hit [S26]; write: DB then delete copy [S24]; crash: copy gone, DB has 899; read after: miss, DB read, fresh.
  - read-through: as cache-aside, but the arrows on a miss go App > Cache > Database (the cache loads).
  - write-through: write: cache and DB before "ok" [S26]; crash: copy gone, DB has 899; read after: miss, fresh.
  - write-back: write: cache only, "ok" at once, DB "not yet"; crash before flush: DB still 999, "write lost"; read after: miss, loads 999 (old).
  - write-around: write: DB only, cache untouched or deleted; crash: nothing lost.
- **Inputs:** tap a pattern chip (5), step with Back/Next or tap a step chip (4).
- **Verdicts (after step 4):** cache-aside / read-through / write-around: "Crash cost speed, not data" (26). write-through: "Cold cache, but no write lost" (29). write-back: "Crash lost a confirmed write" (28). After step 2 for write-back: "Fast ok, database not updated yet" (33).
- **Primitive:** `design-stepper` (step chips, Back/Next, one choice per step).
- **Sources:** [S24], [S26]; write-back and read-through/write-around have no primary source in the dossier (taught as trade-offs).

## 3. sysdesign-m5-hit-rate-curve (5.4 "Drag the size, watch the hits")

- **Claim:** With skewed traffic, a small cache catches most reads and each extra slot helps less; with even traffic the hit rate equals the share cached.
- **Picture:** a hit-rate curve (x: cache size as % of 10,000 products, log scale 0.1% to 100%; y: hit rate 0 to 100%). A dot rides the curve as the learner drags along it. A second handle (or the vertical drag) sets the skew s; the curve redraws. A faint reference line shows even traffic (s = 0, the diagonal). The live label beside the dot: "1,000 items: 76.5% of reads".
- **Model:** N = 10,000. Cache holds the top k items. Hit rate = H_s(k) / H_s(N), with H_s(n) = sum over i = 1..n of 1 / i^s. s = 0 gives k / N.
- **Inputs:** k from 10 to 10,000 (0.1% to 100%), log rail, snap points 100, 1,000, 2,000; s from 0 to 1.2, step 0.1, snap points 0, 0.8, 1.0.
- **Numbers to check (computed):** s = 1: k = 100: 53.0%; k = 1,000: 76.5%; k = 2,000: 83.6%; k = 5,000: 92.9%. s = 0.8: k = 1,000: 57.1%. s = 1.2: k = 1,000: 90.3%. s = 0: k = 1,000: 10%.
- **Verdicts:** marginal gain of doubling k (H(2k) - H(k), as points) under 5: "Past here, more memory buys little" (34). s = 0: "Even traffic: hits = share cached" (33). Otherwise: "Each extra slot still helps" (27).
- **Primitive:** `picture-slider` (drag on the picture, log rail, snap points) with an inset curve like the one in `traffic-playground`.
- **Sources:** the Zipf model is an assumption; a source that shop traffic is Zipf-like is needed (source needed in the chapter). LRU/LFU approximate the top-k cache [S27].

## 4. sysdesign-m5-stale-race (5.5 "Move the slow reader, find the race")

- **Claim:** With delete-on-write, the danger is the order of two events: a stale set after the delete keeps the old value until the TTL. Leases refuse that set.
- **Picture:** a timeline strip 0 to 60 ms with fixed tags: "read 999" at 10 ms, "write 899" at 20 ms, "delete" at 25 ms. A draggable tag "set 999" (the slow reader's cache set). Cards above: Reader app, Cache, Database, Writer app (as in `sysdesign-m5-stale-set-race`). The Cache card's pill shows its final value. A toggle outside the picture: "Leases on".
- **Model:** set time s from 11 to 60 ms (the reader's read stays at 10 ms).
  - s < 20: cache holds 999, correct until 20, stale 20 to 25, deleted at 25. Stale window 5 ms.
  - 20 <= s < 25: stale from s to 25. Stale window 25 - s ms.
  - s >= 25 (leases off): cache holds 999 until the TTL, 60 s. Stale window "up to 60 s".
  - s >= 25 (leases on): set refused (its lease was cancelled by the delete) [S24]; cache empty, next read loads 899. Stale window 0 after 25.
- **Inputs:** drag "set 999" from 11 to 60 ms, step 1, snap points 15, 25, 40. Toggle leases. Default s = 40, leases off.
- **Verdicts:** s < 25: "Delete wins: stale for a few ms" (31). s >= 25, leases off: "Old price back until the TTL" (28). s >= 25, leases on: "Lease refused the late set" (26).
- **Primitive:** `log-ruler` (horizontal drag along a ruler with rungs) with a linear scale, or the scene renderer inside a `picture-slider`.
- **Sources:** Facebook memcache, stale sets and leases [S24]; timings are course examples.

## 5. sysdesign-m5-stampede-toggles (5.6 "Toggle the fixes, watch the database")

- **Claim:** A hot key's expiry sends rate x rebuild time queries at once; coalescing cuts it to one per app server, a shared lease to one; stale-while-revalidate removes the wait; random TTLs spread many keys' expiries.
- **Picture:** Shoppers > 20 App server cards (drawn as a stack) > Cache > Database, with the Database's queue drawn as dots and a small chart of database queries over 3 minutes (the key expires every 60 s). Toggles as chips inside the picture: "Coalesce", "Shared lease", "Serve stale", and a mode switch "1 hot key / 1,000 keys stored together" which enables "Random TTL".
- **Model (story numbers):** R = 5,000 reads a second, rebuild W = 50 ms, 20 app servers, database capacity about 800 page queries a second. Queries per expiry: none: R x W = 250 [Little's law, S5]; coalesce: min(20, 250) = 20; lease: 1 [S24: one lease per key at most every 10 s]. Shopper wait during rebuild: 50 ms unless "Serve stale" is on, then 0 [S23]. 1,000-keys mode: all expire in the same second: 1,000 misses in 1 s; with random TTL 54 to 66 s: 1,000 / 12 = about 83 a second (reasoning from [S90]; no named source).
- **Inputs:** three toggles (any combination; lease wins over coalesce), mode switch, random TTL toggle (only in 1,000-keys mode).
- **Verdicts:** none: "250 queries at once: database falls" (35). coalesce only: "20 queries: one per app server" (30). lease: "One query per expiry" (20). lease + serve stale: "One query, and nobody waits" (27). 1,000 keys, no jitter: "1,000 misses in the same second" (31). with jitter: "Misses spread: about 83 a second" (32).
- **Primitive:** `traffic-playground` (request dots, a queue in front of the server card, an inset chart), with toggle chips instead of the rail.
- **Sources:** [S24], [S25], [S23], [S90], [S5].

## 6. sysdesign-m5-cdn-origin-load (5.7 "Predict the origin's load")

- **Claim:** A longer edge lifetime cuts origin load and raises staleness; a shield collapses many edges' misses into one per lifetime without much more staleness.
- **Picture:** 20 edge cards in an arc (or 4 drawn plus "x 5"), an optional Shield card, the Origin card. Fetch dots travel from edges (or the shield) to the origin at the computed rate. Live numbers: edge hit rate on an edge card, "origin requests/min" by the Origin card, "oldest page shown" by the shopper.
- **Model:** E = 20 edges (story), r = requests a second per edge for the page, T = lifetime (max-age/s-maxage) in seconds [S22]. Miss rate per edge = 1 / (1 + r x T) (each copy serves r x T hits after its miss; derived). Origin requests/s without shield = E x r / (1 + r x T). With shield: shield sees a = E x r / (1 + r x T) per second; origin gets a / (1 + a x T). Worst-case age: T without shield, about 2 x T with shield.
- **Inputs:** T from 1 s to 3,600 s on a log rail (snap points 10, 60, 300, 3,600); r from 0.1 to 100 a second, log rail (snap 1, 5, 50); shield toggle. Defaults: T = 60, r = 5, shield off.
- **Numbers to check:** T 60, r 5: hit rate 99.7%, origin about 20/min; with shield about 1/min, oldest page about 120 s. T 10, r 5: hit 98.0%, origin about 118/min; with shield about 5.7/min.
- **Verdicts:** origin under 5/min: "Origin barely notices the traffic" (33). origin 5 to 60/min: "About one fetch per edge per TTL" (32). origin above 60/min: "Short lifetime: origin works hard" (33). shield on and T over 300 s: "Fewer fetches, older pages" (26).
- **Primitive:** `picture-slider` (two log rails inside the picture) plus a toggle; or `estimate-chain` with T and r as draggable inputs.
- **Sources:** RFC 9111 [S22]; the formula and numbers are derived for the course; origin shield needs a source (source needed in the chapter).
