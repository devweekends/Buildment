# Module 16 playable specs (microservices and resilience)

Eight reserved slugs. The builder creates each folder (`frontend/src/canvas/<slug>/`), registers it and writes its `spec.md`. All eight sit on `BeatFrame` (`primitives/beat-frame.tsx`), draw on a 420 wide viewBox with labels of at least 11.5 units, use `SvgNode` cards and `VerdictBanner`, take theme tokens only, and keep every verdict at 38 characters or fewer. The nine watch-only scenes of the module (`sysdesign-m16-*`, kind `scene`, already in `frontend/src/canvas/`) use the same names (Checkout, Picks, Payments) and the same numbers as the playables below, so the picture and the play agree.

Every number below was computed with code that sits in this file or in the challenge repository: the retry storm and the jitter herd with the two small models printed at the end of this file, the latency table with the quantile function in the timeout section, the breaker timeline with the same `createBreaker` that chapter 16.7 asks the learner to write, and the pool figures by the arithmetic shown. The models are deterministic (expected values, no randomness), so a given setting always gives the same picture. They are toy models for the shape of an effect, and each chapter says so in its limits fold.

Chapter beats that use these slugs: 16.2 beat 5; 16.3 beat 3; 16.4 beats 2, 4 and 5; 16.5 beats 2 and 4; 16.6 beat 2.

## sysdesign-m16-split-or-not

- **Chapter and beat:** 16.2 beat 5, "Weigh team, releases and clarity".
- **Claim:** Whether to split depends on three things that can be weighed: how many people must coordinate, how often releases wait for other teams, and how stable the boundaries are. A big team with many collisions and stable walls has a reason to split the parts that hurt; a small team with unclear walls does not.
- **Primitives:** the factor model (`frontend/tests/unit/canvas/factor-model.test.ts` shows its shape) or three `picture-slider.tsx` / `rail-slider.tsx` rails with snap points, `SvgNode` note cards for the three shapes, `VerdictBanner`. No toggle.
- **Input:**
  - Team size on a snap rail: 3, 8, 15, 30, 60, 120 people (default 15).
  - Releases that waited for another team last month, on a snap rail: 0, 1, 3, 6, 10 (default 3).
  - Boundary clarity, three snap points: "New idea", "Mostly clear", "Stable for a year" (default "Mostly clear").
  - Arrow keys step along the snap points.
- **Model (a course rule of thumb, not a law):**
  - Team points: 0 for 8 or fewer, 1 for 15, 2 for 30, 3 for 60 or more.
  - Collision points: 0 for 0 or 1, 1 for 3, 2 for 6, 3 for 10.
  - Clarity points: 0 New idea, 1 Mostly clear, 2 Stable.
  - Total T = sum (0 to 8). T of 0 or 1: monolith. T of 2 to 4: modular monolith. T of 5 or more: split the parts that hurt. If clarity is "New idea" and T is 5 or more, the answer is capped at modular monolith.
- **Picture:** three cards in a row (Monolith, Modular monolith, Microservices), with the recommended one filled and ringed, the others dim. Under the cards, the three point bars (team, collisions, clarity) and a total out of 8. Each bar sits next to its rail so the learner drags the bar itself.
- **Numbers to check:**

  | Team | Collisions | Clarity | Points | Recommendation |
  |---|---|---|---|---|
  | 3 | 0 | New idea | 0 | Stay one monolith |
  | 8 | 1 | Mostly clear | 1 | Stay one monolith |
  | 15 | 3 | Mostly clear | 3 | Modular monolith (Tawseel in 16.2, 14 people rounded to 15) |
  | 15 | 3 | Stable | 4 | Modular monolith |
  | 3 | 0 | Stable | 2 | Modular monolith |
  | 30 | 6 | Mostly clear | 5 | Split the parts that hurt |
  | 60 | 6 | Stable | 7 | Split the parts that hurt |
  | 120 | 10 | New idea | 6 | Walls unclear: stay modular (capped) |
  | 120 | 10 | Stable | 8 | Split the parts that hurt |

- **Verdicts (tone):** "Stay one monolith" (good), "Modular monolith, hard walls" (accent), "Split the parts that hurt" (accent), "Walls unclear: stay modular" (warn).
- **Reduced motion:** the ring jumps to the new card; bars are drawn at their final length.
- **Accessibility:** each rail is a `role="slider"` with value text such as "team size 15 people, 1 point". The verdict has an `aria-live` region.
- **Sources:** Fowler, "Monolith First" [S36] is the only anchor; the points are a course rule of thumb, and the chapter says so.

## sysdesign-m16-order-path

- **Chapter and beat:** 16.3 beat 3, "Wait for the answer, or send a message".
- **Claim:** For each call in an order, waiting for the answer gives certainty but ties your time and availability to the other service; sending a message frees you from it but you learn the result later. Wait when the customer needs the answer now; send a message when they do not.
- **Primitives:** `design-stepper.tsx` or `block-map.tsx` for the three call cards in a row (tap a card to switch its call between "wait" and "message"), a failure tap on each service icon, `VerdictBanner`. One control outside the picture at most (Reset).
- **Input:** Three calls from Checkout, in this order: Stock (30 ms), Payments (80 ms), Notifications (40 ms). Tap a call card to toggle Wait or Message (default: all Wait). Tap a service icon to fail or revive it (default: all up). 44px targets.
- **Model:**
  - Customer wait = the sum of the times of the calls set to Wait (calls run one after another).
  - The order fails when any service set to Wait is down. The verdict names the first one in the order Stock, Payments, Notifications.
  - A call set to Message never delays or fails the order. If its service is down, the message stays in a small queue card ("1 waiting").
  - Availability line: 0.999 to the power (number of Wait calls), shown as a percentage with one decimal.
  - Risk notes: Payments set to Message gives "Placed; payment unconfirmed" (warn). Stock set to Message gives "Placed; stock may run out" (warn).
- **Numbers to check:**

  | Wait calls | Customer waits | Availability if each is 99.9% |
  |---|---|---|
  | Stock, Payments, Notifications | 150 ms | 99.7% (0.997003) |
  | Stock, Payments | 110 ms | 99.8% (0.998001) |
  | Stock only | 30 ms | 99.9% |
  | Payments, Notifications | 120 ms | 99.8% |

- **Verdicts:** "Order placed in 150 ms" (good); "Order failed: Notifications is down" (36 characters, bad); "Order failed: Payments is down" (bad); "Order failed: Stock is down" (bad); "Placed in 110 ms; email waits" (good); "Placed; payment unconfirmed" (warn); "Placed; stock may run out" (warn). Never longer than 38 characters.
- **Reduced motion:** the request dot is replaced by a drawn path; the queue card changes without sliding.
- **Accessibility:** each call card is a toggle button whose label reads "Notifications, waits for the answer, 40 ms".
- **Sources:** SQS at-least-once delivery [S83]; outbox [S79]; series availability from chapter 2.6. The call times and the 99.9% are course numbers.

## sysdesign-m16-timeout-line

- **Chapter and beat:** 16.4 beat 2, "Drag the limit and see the price".
- **Claim:** A short timeout cuts off calls that would have worked; a long timeout lets a hanging dependency hold many workers. The right limit sits near the latency percentile you accept as false timeouts, and the pool size must be checked against it.
- **Primitives:** `picture-slider.tsx` for the limit line (inside the picture), a skyline of bars like the beat gaps strip in `sysdesign-m12-timeout-slider`, `SvgNode` for Checkout and Picks, `VerdictBanner`. No toggle.
- **Input:** Limit T on a rail from 50 ms to 1,000 ms, snap points 50, 100, 150, 250, 400, 500, 600, 900 and 1,000; arrow keys move one snap point; default 250.
- **Model:** Latency of a call to Picks is the quantile function Q(u), interpolated linearly in log latency between these points (u, ms): (0, 15), (0.5, 40), (0.9, 80), (0.99, 250), (0.999, 900), (1, 3000). The share of calls slower than T is 1 minus F(T), where F is the inverse of Q (also log-linear between the same points). Workers held when Picks hangs, at 100 pages a second, are 100 times T in seconds. Pool: 50 workers.
- **Picture:** 50 bars, the latency of calls at u = (i + 0.5) / 50 for i from 0 to 49, drawn in sorted order on a log-scaled height, with a horizontal line at T. Bars above the line are red. Beside the line, two numbers: "calls cut off" (exact percentage from the formula, not the bar count) and "workers held in a hang" with a bar against 50.
- **Numbers to check** (computed with the formulas above, mean hold by numeric integration over 200,000 points):

  | T | Calls cut off | Workers held when Picks hangs | Workers busy when healthy |
  |---|---|---|---|
  | 50 ms | 37.1% | 5 | 3.7 |
  | 100 ms | 8.2% | 10 | 4.6 |
  | 150 ms | 5.0% | 15 | 4.9 |
  | 250 ms | 1.0% | 25 | 5.2 |
  | 400 ms | 0.67% | 40 | 5.3 |
  | 500 ms | 0.51% | 50 | 5.4 |
  | 600 ms | 0.38% | 60 | 5.4 |
  | 900 ms | 0.10% | 90 | 5.5 |
  | 1,000 ms | 0.09% | 100 | 5.5 |

  The mean latency is 55.6 ms. p50 40 ms, p90 80 ms, p99 250 ms and p99.9 900 ms are the points of the quantile function.
- **Verdicts:** held workers above 50: "A hang takes 90 of 50 workers" (number filled in, bad). Cut-off share at least 5%: "37% of good calls cut off" (warn). Otherwise: "1% cut; a hang holds 25 of 50" (good). Never longer than 38 characters.
- **Reduced motion:** the line jumps; bars do not animate.
- **Accessibility:** the rail is a `role="slider"` with value text "limit 250 ms, 1.0 percent of calls cut off, a hang holds 25 of 50 workers".
- **Sources:** Timeout from the percentile you accept as false timeouts, p99.9 in Brooker's example [S89]; Little's law from chapter 2.5. The latency points are course numbers.

## sysdesign-m16-retry-storm

- **Chapter and beat:** 16.4 beat 4, "Retries can keep a system down".
- **Claim:** A short blip can leave a system down for good when clients retry, because each failed request comes back and the load stays above capacity. Waiting between retries does not change that; only fewer attempts do, for example a retry budget.
- **Primitives:** `traffic-playground.tsx` for the strip chart, or `log-ruler.tsx` for the time axis, with one `picture-slider.tsx` rail for the number of retries and a three-way segmented chip inside the picture for the retry rule, `VerdictBanner`.
- **Input:** Retries per request on a snap rail: 0, 1, 2, 3 (default 3). Retry rule, three chips in the picture: "At once", "Backoff and jitter", "Budget 10%" (default "At once"). Replay button outside the picture.
- **Model:** the function `simulate` printed at the end of this file. It is a fluid model with steps of 0.1 s: a FIFO queue, a server of capacity 100 requests a second, normal load 80 original requests a second, a blip from 5 s to 10 s that cuts capacity to 30 a second, clients that give up after 1 second and retry up to `retries` times, a server that still spends work on a request whose client has left. "Backoff and jitter" waits 0.5 s times 2 to the power (attempt minus 1), spread over 10 equal parts across that wait. "Budget 10%" earns 0.1 token per original request (cap 10) and a retry costs 1 token.
- **Picture:** a 60 second strip. Bars show goodput per second (answers delivered in time), a line shows attempts per second arriving at the server, a dashed line at 100 shows capacity, and a shaded band marks the blip. Under it, the queue length at 60 s.
- **Numbers to check** (computed with `simulate`, horizon 60 s; "recovered" = goodput stays at 76 a second or more for the rest of the run):

  | Retries | Rule | Recovered at | Peak attempts per second | Queue at 60 s |
  |---|---|---|---|---|
  | 0 | any | 20 s (10 s after the blip) | 80 | 0 |
  | 1 | At once | never in 60 s | 160 | 3,517 |
  | 2 | At once | never | 240 | 7,696 |
  | 3 | At once | never | 320 | 11,787 |
  | 1 | Backoff and jitter | never | 160 | 3,504 |
  | 2 | Backoff and jitter | never | 240 | 7,637 |
  | 3 | Backoff and jitter | never | 320 | 11,609 |
  | 1, 2 or 3 | Budget 10% | 27 s (17 s after the blip) | 92 | 0 (peak 286) |

  Goodput per second at 5 s steps for 0 retries: 5 s: 80, 10 s: 0, 15 s: 0, 20 s: 100, then 80. For 3 retries at once: 80, then 0 from 10 s to 60 s with 320 attempts a second. For 3 retries with the budget: 80, 0 until 25 s, 100 at 30 s, then 80.
- **Verdicts:** 0 retries: "Back to normal 10 s after the blip" (34, good). Stuck: "Still down a minute later" (25, bad). Budget: "Back 17 s after the blip" (24, good).
- **Reduced motion:** show the final 60 s strip; no sweeping cursor.
- **Accessibility:** the retries rail reads "3 retries, system still down after 60 seconds".
- **Sources:** metastable failure, work amplification from retries [S94]; retry budgets [S91]; the numbers come from the course model, made up to show the shape.

## sysdesign-m16-jitter-herd

- **Chapter and beat:** 16.4 beat 5, "A herd needs jitter".
- **Claim:** When many clients fail at the same moment, backoff alone makes them retry together in waves. Full jitter spreads the retries so the server can use all its capacity, and it needs fewer calls overall.
- **Primitives:** `traffic-playground.tsx` or a bar strip like the m12 beat-gap strip, one `picture-slider.tsx` rail for retries, a three-way chip for the wait rule, `VerdictBanner`.
- **Input:** Retries allowed per client on a snap rail 2, 4, 6, 8 (default 6). Wait rule, three chips: "At once", "Backoff", "Backoff + jitter" (default "Backoff").
- **Model:** the function `herd` printed at the end of this file. 1,000 clients call in second 0. The server serves 100 calls per one-second slot and rejects the rest at once. A rejected client retries after a delay: "At once" = next slot; "Backoff" = 2 to the power (n minus 1) seconds for retry n, capped at 16 s; "Backoff + jitter" = a uniform random whole number of seconds from 1 to min(16, 2 to the power n), applied as expected values. After the last allowed retry a client gives up.
- **Picture:** arrivals per second at the server for seconds 0 to 19 as bars, a dashed line at 100 (capacity), and a counter "served so far" out of 1,000 that fills as the strip plays.
- **Numbers to check** (computed with `herd`):

  | Retries | Rule | Peak arrivals | Total calls | Served | Gave up | Served by 10 s | by 20 s |
  |---|---|---|---|---|---|---|---|
  | 6 | At once | 1,000 | 4,900 | 700 | 300 | 700 | 700 |
  | 6 | Backoff | 1,000 | 4,500 | 600 | 0 | 400 | 500 |
  | 6 | Backoff + jitter | 1,000 | 3,020 | 1,000 | 0 | 844 | 995 |
  | 2 | Backoff | 1,000 | 2,700 | 300 | 700 | 300 | 300 |
  | 2 | Backoff + jitter | 1,000 | 2,616 | 692 | 308 | 692 | 692 |
  | 4 | Backoff + jitter | 1,000 | 3,019 | 999 | 1 | 843 | 994 |
  | 8 | Backoff | 1,000 | 4,500 | 600 | 0 | 400 | 500 |
  | 8 | Backoff + jitter | 1,000 | 3,020 | 1,000 | 0 | 844 | 995 |

  Arrivals per second for 6 retries, seconds 0 to 19. At once: 1000 900 800 700 600 500 400, then 0. Backoff: 1000 900 0 800 0 0 0 700 then zeros, with 600 at second 15. Backoff + jitter: 1000 450 538 188 199 210 136 48 48 48 48 39 29 17 6 3 3 3 3 3.
- **Verdicts:** "Waves of 900, 800, 700: lockstep" (32, bad) for Backoff; "All 1,000 served by 40 s" (24, good) for jitter with 6 or more retries; "Only 700 of 1,000 served" (24, warn) for At once with 6; a number filled in each time.
- **Reduced motion:** draw the full strip; the counter shows the final value.
- **Accessibility:** the rule chips are a radio group; the strip has a text alternative that lists the peak arrival and the number served.
- **Sources:** full, equal and decorrelated jitter compared [S90]; the 243 times example [S89] is a different effect (amplification) and is drawn in a Mermaid diagram. The 1,000 clients and 100 calls per second are course numbers.

## sysdesign-m16-breaker-play

- **Chapter and beat:** 16.5 beat 2, "Tap Picks, watch the breaker".
- **Claim:** A breaker opens after a run of failures, so a failing dependency gets almost no calls, and it probes with one call at a time to find out when the dependency is back.
- **Primitives:** `SvgNode` cards for Checkout and Picks (Picks is tappable: healthy or broken), a pill for the breaker state with the three state colours, a strip of the last 60 calls as dots (green worked, red failed, grey refused, amber probe), `VerdictBanner`. Controls outside the picture: Replay and "Pause" at most.
- **Input:** Tap Picks to break it or fix it (44px). Time runs on its own at 10 calls a second (one simulated second takes 0.5 s on screen at most; the builder may choose the speed).
- **Model:** the breaker of chapter 16.7 (`createBreaker`) with `failureThreshold` 5 and `openMs` 10,000, driven by a fake clock. A call to a healthy Picks takes 40 ms and works; a call to a broken Picks fails after a 300 ms time limit. The breaker is asked before each call; a refused call fails at once and does not reach Picks.
- **Scripted run to check** (Picks broken at 5.0 s and fixed at 35.0 s, 10 calls a second for 60 s, simulated with the real `createBreaker`):

  - half-open at 26.00 s; the probe fails at 26.30 s, so open again;
  - half-open at 36.30 s; the probe works and the breaker closes at 36.34 s.

- **Verdicts:** closed and healthy "Closed: calls go through" (24, good); open "Open: no calls reach Picks" (26, warn); half-open "Half-open: one probe call" (25, accent); fixed but not yet probed "Picks is back; waiting to probe" (31, warn); after an outage "9 of 300 calls reached Picks" (28, good, numbers filled in).

- **Accessibility:** the Picks card is a toggle button "Picks: healthy, press to break it". The breaker pill reads as text.

## sysdesign-m16-bulkhead-pools

- **Chapter and beat:** 16.5 beat 4, "Drag the wall between the pools".
- **Claim:** With one shared pool, a slow dependency used by the home page starves payments that never call it. A wall (a separate pool for payments) keeps payments served, and it costs idle capacity.
- **Primitives:** `block-map.tsx` for 50 worker dots in a grid with a draggable wall (picture-slider on the boundary), a tappable Picks card (healthy or slow), two bars for "payments served" and "home served", `VerdictBanner`.
- **Input:** Payment pool size P on a rail from 0 to 45 workers; 0 means one shared pool; snap points 0, 2, 5, 10, 20, 30, 45; arrow keys step 1; default 0. Tap Picks to switch healthy and slow (default slow).
- **Model:** 50 workers. Payments: 20 requests a second, 0.1 s each. Home: 80 a second, 0.1 s each when Picks is healthy and 3 s each when it is slow. Shared pool (P = 0): the share of every kind served is s = min(1, 50 / (20 x 0.1 + 80 x h)) with h the home hold time. Walled: payments served = min(1, P / 0.1 / 20); home served = min(1, (50 minus P) / h / 80).
- **Numbers to check:**

  | Picks | P | Payments served | Home served | Total served per second |

  | healthy | 10 | 100% | 100% | 100 |

  | slow | 0 (shared) | 20.7% | 20.7% | 20.7 |
  | slow | 1 | 50% | 20.4% | 26.3 |
  | slow | 2 | 100% | 20.0% | 36.0 |
  | slow | 5 | 100% | 18.8% | 35.0 |
  | slow | 10 | 100% | 16.7% | 33.3 |
  | slow | 20 | 100% | 12.5% | 30.0 |
  | slow | 30 | 100% | 8.3% | 26.7 |

## The two models

The builder may port these two functions to TypeScript as the pure model files of `sysdesign-m16-retry-storm` and `sysdesign-m16-jitter-herd`, with unit tests that check the tables above.

```js
// Fluid cohort model of a retry storm. Deterministic. dt = 0.1 s.
// One server, FIFO queue. Each step adds one cohort per attempt number.
// Clients give up after `patience` seconds and retry; the server still
// spends work on a request whose client has left.
export function simulate({
  retries = 0,
  mode = "now", // "now" | "backoff" | "jitter"
  budget = false, // retries may add at most 10% of original requests
  seconds = 60,
  base = 80,
  capacity = 100,
  dipFrom = 5,
  dipTo = 15,
  dipCapacity = 30,
  patience = 1,
  backoffBase = 0.5,
  jitterParts = 10,
} = {}) {
  const dt = 0.1;
  const steps = Math.round(seconds / dt);
  const queue = []; // {step, attempt, n, gaveUp}
  const due = new Map(); // step -> [{attempt, n}]
  const patienceSteps = Math.round(patience / dt);
  let tokens = 0;
  const rows = [];
  let good = 0, attempts = 0, wasted = 0, orig = 0, goodOrig = 0;
  const addDue = (step, attempt, n) => {
    if (!due.has(step)) due.set(step, []);
    due.get(step).push({ attempt, n });
  };
  for (let i = 0; i < steps; i++) {
    const t = i * dt;
    const cap = t >= dipFrom && t < dipTo ? dipCapacity : capacity;
    const n0 = base * dt;
    queue.push({ step: i, attempt: 0, n: n0 });
    attempts += n0;
    orig += n0;
    tokens = Math.min(10, tokens + n0 * 0.1);
    for (const r of due.get(i) ?? []) {
      queue.push({ step: i, attempt: r.attempt, n: r.n });
      attempts += r.n;
    }
    due.delete(i);
    // give-up check: a cohort that has waited patience seconds triggers its retry once
    for (const c of queue) {
      if (!c.gaveUp && i - c.step >= patienceSteps) {
        c.gaveUp = true;
        if (c.attempt < retries) {
          let n = c.n;
          if (budget) {
            n = Math.min(n, tokens);
            tokens -= n;
          }
          if (n > 0) {
            const attempt = c.attempt + 1;
            const delay = mode === "now" ? 0 : backoffBase * 2 ** (attempt - 1);
            if (mode === "jitter") {
              for (let j = 0; j < jitterParts; j++) {
                const d = ((j + 0.5) / jitterParts) * delay;
                addDue(i + Math.max(1, Math.round(d / dt)), attempt, n / jitterParts);
              }
            } else addDue(i + Math.max(1, Math.round(delay / dt)), attempt, n);
          }
        }
      }
    }
    let work = cap * dt;
    while (work > 1e-9 && queue.length) {
      const c = queue[0];
      const take = Math.min(c.n, work);
      work -= take;
      c.n -= take;
      if (i - c.step <= patienceSteps) good += take;
      else wasted += take;
      if (c.n <= 1e-9) queue.shift();
    }
    if (i % 10 === 9) {
      const qlen = queue.reduce((s, c) => s + c.n, 0);
      rows.push({ t: Math.round(t + dt), good, attempts, wasted, queue: qlen });
      good = attempts = wasted = 0;
    }
  }
  return rows;
}
```

```js
// Herd model: N clients call at second 0. The server serves `capacity` calls per
// one-second slot and rejects the rest at once. A rejected client retries after
// a delay that depends on the mode. Expected values, no randomness.
export function herd({ clients = 1000, capacity = 100, retries = 6, mode = "now", cap = 16, slots = 40 } = {}) {
  // pending[t][k] = clients who make their k-th retry in slot t (k = 0 is the first call)
  const pending = Array.from({ length: slots + 200 }, () => Array.from({ length: retries + 1 }, () => 0));
  pending[0][0] = clients;
  const arrivals = [];
  let served = 0, gaveUp = 0, calls = 0;
  const servedBy = [];
  for (let t = 0; t < slots; t++) {
    const row = pending[t];
    const total = row.reduce((a, b) => a + b, 0);
    arrivals.push(total);
    calls += total;
    const ok = Math.min(total, capacity);
    served += ok;
    // reject the excess in proportion to each attempt group
    const failShare = total > 0 ? (total - ok) / total : 0;
    for (let k = 0; k <= retries; k++) {
      const fail = row[k] * failShare;
      if (fail <= 0) continue;
      if (k === retries) { gaveUp += fail; continue; }
      const nextAttempt = k + 1;
      if (mode === "now") pending[t + 1][nextAttempt] += fail;
      else if (mode === "backoff") {
        const d = Math.min(cap, 2 ** (nextAttempt - 1));
        pending[t + d][nextAttempt] += fail;
      } else {
        // full jitter: uniform over 1..min(cap, 2^nextAttempt) whole seconds
        const max = Math.min(cap, 2 ** nextAttempt);
        for (let d = 1; d <= max; d++) pending[t + d][nextAttempt] += fail / max;
      }
    }
    servedBy.push(served);
  }
  return { arrivals, calls, served, gaveUp, servedBy, peak: Math.max(...arrivals) };
}
```
