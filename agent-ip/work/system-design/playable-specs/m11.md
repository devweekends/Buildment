## Shared: the history picture (used by 11.2, 11.3 and 11.4)

Four of the playables draw a **history**: clients as lanes, operations as bars. The kit calls this renderer `history` (`03-simulation-kit.md`). It does not exist yet, so build it once, with a tested model, and drive all four slugs from `data.ts`.

- **Picture:** one lane per client (at most 4), a time axis with a unit and ticks, and one bar per operation from `start` to `end`. A write bar is accent blue and reads `write x = 1`. A read bar is neutral and reads `read x -> 0`. A key other than `x` is written before the value (`read q -> none`). On a phone the lanes stack and every bar is a 44 px tappable row with its start and end.
- **Data format** (the same one the 11.8 exercise uses, plus `key`): `{ id, client, kind: "write" | "read", key, value, start, end }`. The register starts at 0 ("none" for the forum keys). Times are made-up integers.
- **Real-time order:** operation a is before b when `a.end < b.start`. Two bars that touch at one instant overlap. This is the rule of chapters 11.2 and 11.8.
- **What a read may return (the "may return" chip):** let F be the writes on the same key with `end < read.start`, and O the writes on that key that overlap the read. A write in F is a candidate only if no other write in F starts after it ends. The set is the values of O, plus the values of the candidates in F, plus the starting value only when F is empty.
- **Checkers (the three verdicts):** brute-force search with a memory of failed states, as in 11.8.
  - Linearizable: one order of all operations in which a before b is kept whenever `a.end < b.start`, and every read returns the last write before it on its key (or the starting value).
  - Sequential: the same search, but the only ordering rule is each client's own order (by start time).
  - Causal: build the relation "program order, plus a write before every read that returned its value", then take its closure. Each client needs a legal order of all writes plus its own reads that keeps that relation. A read of the starting value reads from no write.
  - The reference implementation that produced every table below follows. It is small on purpose; the rules above are all it does.

```js
// op: { id, client, kind: "write"|"read", key, value, start, end }
const INIT = 0;

function legalSearch(ops, mustPrecede, initial = INIT) {
  // ops: array; mustPrecede(a,b) true if a must come before b.
  const n = ops.length;
  const placed = new Array(n).fill(false);
  const order = [];
  const state = new Map();
  function rec(count) {
    if (count === n) return true;
    for (let i = 0; i < n; i++) {
      if (placed[i]) continue;
      // i is available if no unplaced j must precede i
      let ok = true;
      for (let j = 0; j < n; j++) if (!placed[j] && j !== i && mustPrecede(ops[j], ops[i])) { ok = false; break; }
      if (!ok) continue;
      const op = ops[i];
      const cur = state.has(op.key) ? state.get(op.key) : initial;
      if (op.kind === "read" && op.value !== cur) continue;
      const had = state.has(op.key); const prev = state.get(op.key);
      if (op.kind === "write") state.set(op.key, op.value);
      placed[i] = true; order.push(op.id);
      if (rec(count + 1)) return true;
      placed[i] = false; order.pop();
      if (op.kind === "write") { if (had) state.set(op.key, prev); else state.delete(op.key); }
    }
    return false;
  }
  return rec(0) ? order.slice() : null;
}

export function linearizable(h) {
  return legalSearch(h, (a, b) => a.end < b.start);
}
export function sequential(h) {
  return legalSearch(h, (a, b) => a.client === b.client && a.start < b.start);
}
export function causal(h) {
  // causal order: program order + reads-from, transitive closure.
  const idx = new Map(h.map((o, i) => [o.id, i]));
  const n = h.length;
  const before = Array.from({ length: n }, () => new Array(n).fill(false));
  for (let i = 0; i < n; i++) for (let j = 0; j < n; j++) {
    if (i !== j && h[i].client === h[j].client && h[i].start < h[j].start) before[i][j] = true;
  }
  for (let j = 0; j < n; j++) if (h[j].kind === "read" && h[j].value !== INIT) {
    const w = h.findIndex((o) => o.kind === "write" && o.key === h[j].key && o.value === h[j].value);
    if (w >= 0) before[w][j] = true;
  }
  for (let k = 0; k < n; k++) for (let i = 0; i < n; i++) for (let j = 0; j < n; j++) if (before[i][k] && before[k][j]) before[i][j] = true;
  const clients = [...new Set(h.map((o) => o.client))];
  for (const c of clients) {
    const view = h.filter((o) => o.kind === "write" || o.client === c);
    const ok = legalSearch(view, (a, b) => before[idx.get(a.id)][idx.get(b.id)]);
    if (!ok) return null;
  }
  return true;
}
export const verdicts = (h) => ({ lin: !!linearizable(h), seq: !!sequential(h), causal: !!causal(h) });
```

## sysdesign-m11-build-history (11.2, beat 1: "A history is a list of bars")

- **Beat text:** "Each operation is a bar. It starts when a client sends the request and ends when the client gets the answer. A write says what it stored. A read says what it got back. Tap a lane to add a bar. Bars that overlap are concurrent: neither clearly came first."
- **Claim:** A history is a list of operations with a start, an end and a result. Two bars are ordered when one ends before the other starts, and concurrent otherwise.
- **Model:** the shared history picture, with lanes Ada, Ben and Cam on a time axis from 0 to 100 (made-up milliseconds). The preset history is Ada: write x = 1 from 10 to 30; Ben: read x from 20 to 40; Cam: read x from 50 to 70.
  - A tap on empty lane space adds a bar of length 20 whose start snaps to the nearest 5, clipped to 0 to 80. The new bar is a read unless the Write chip is on. The k-th write stores x = k.
  - A lane never holds two overlapping bars (a client does one thing at a time). A tap that would overlap is refused with a chip.
  - At most 6 operations. Tap a bar twice to remove it.
  - Each read shows its "may return" chip.
- **Check points (the preset):** the pair Ada and Ben overlap (30 is not less than 20 and 40 is not less than 10). Ada before Cam (30 < 50). Ben before Cam (40 < 50). Ben's read may return 0 or 1 (the write overlaps it; no write finished before it). Cam's read may return only 1 (Ada's write finished before it and nothing hides it).
- **Verdicts:** "N operations, M pairs overlap" with the numbers filled in (at most 29 characters); preset "3 operations, 1 pair overlaps" (29). Refused add: "A client does one thing at a time" (34). Sixth add done: "Six operations is the most" (26).
- **Primitive:** the shared history picture.
- **Limits text:** "Times are made up. A history lists what clients saw. It says nothing about copies or networks."
- **Sources:** [S47] Herlihy and Wing, operations with an invocation and a response.

## sysdesign-m11-session-reads (11.5, beat 2: "Switch each promise on and watch")

- **Beat text:** "Two readers, five reads. Amna wrote the comment, and Omar only reads it. Switch on \"my own writes\" and Amna's reads are fixed, but Omar's are not. Switch on \"no going back\" and Omar's are fixed. Watch how many reads the leader has to take."
- **Claim:** Each session guarantee stops its own anomaly and nothing else. Read-your-writes protects the writer, monotonic reads protects any reader, and the sure way to get either is sometimes the leader.
- **Model:** a leader and two replicas on a time axis from 0 to 700 ms (same story as chapter 8.4, with Omar added). Amna writes a comment at time 0, which is position 1 in the leader's log. Replica 1 applies it at 150 ms and replica 2 at 600 ms (course numbers, in the range of a PostgreSQL replica under heavy writes [S38]). Five reads, each drawn as a dot on its lane:

  | Read | Who | Time | Replica with no promises |
  |---|---|---|---|
  | 1 | Amna | 100 ms | Replica 1 |
  | 2 | Amna | 350 ms | Replica 2 |
  | 3 | Omar | 200 ms | Replica 1 |
  | 4 | Omar | 350 ms | Replica 2 |
  | 5 | Omar | 500 ms | Replica 1 |

  - A replica "has the comment" when its applied position is 1 (replica 1 from 150 ms, replica 2 from 600 ms). A read shows the comment when its node has it.
  - Amna's token: wrote = 1. Omar's token: wrote = 0. Both start with seen = 0.
  - With "my own writes" on, a read needs a node at position `wrote`. With "no going back" on, a read needs a node at position `seen`, where `seen` rises to what each read showed. ## sysdesign-m11-cut-the-network (11.7, beat 1: "Cut the cable: refuse or answer")

- **Beat text:** "Cut the cable between the regions. Then switch between \"Refuse\" and \"Answer\". With \"Refuse\", the cut-off region says try again later, and the copies never disagree. With \"Answer\", both regions take writes, and after the link returns the copies hold two values. You cannot have both."
- **Claim:** While the network is cut, a system must choose: refuse requests on the side that cannot reach a majority (stay consistent) or answer on both sides (stay available, and let copies diverge).
- **Model:** three copies of one value x (start x = 0): West 1 and West 2 in one region, East in another. The link between the regions can be cut. Ada is a client in the West, Bao and Cam are clients in the East. Script, played in order after each press of Cut: Ada writes x = 1; Bao writes x = 2; Cam reads x.
  - A side with 2 of 3 copies is the majority (chapter 12.3 explains majorities).
  - **Refuse mode:** West has the majority, so Ada's write is accepted (West 1 and West 2 hold 1). East has 1 of 3, so Bao's write and Cam's read are refused with `try again later`. When the link returns, East copies x = 1. Copies never disagree.
  - **Answer mode:** every side accepts. West holds 1, East holds 2. Cam reads 2 while West says 1. When the link returns, the two copies exchange and find a conflict: x = 1 and x = 2. A rule must settle it (last writer wins loses one write; a merge keeps both: module 13).
- **Inputs:** two controls outside the picture: a toggle "Refuse / Answer" (default Refuse) and a button "Cut the cable" that becomes "Mend the cable". One hint line: "Cut the cable, then switch the mode."
- **What moves:** a cable between the regions that breaks into two ends with a cross between them; message dots for the three requests; refused requests bounce back with a red chip; accepted writes change the copy's value chip; after mending, copies exchange dots and either match (Refuse) or show a clash chip (Answer).

## sysdesign-m11-latency-or-fresh (11.7, beat 3: "No cut: pay in time or in freshness")

- **Beat text:** "Now there is no cut. A write in the West must reach a copy in the East. Choose how far away that copy is. If the write waits for the East copy, East readers always see it, and the write takes a round trip. If it does not wait, the write is fast, and East readers can be stale for one trip."
- **Claim:** With no partition, waiting for a faraway copy buys freshness and costs the round trip. Not waiting is fast, and readers near the far copy are stale for one one-way trip.
- **Model:** a writer and a local copy in the West, a far copy in the East. Disk write with fsync 0.3 ms [S3]. Let R be the round trip to the far copy.
  - Write time when it waits: `0.3 + R` ms. East readers see the write as soon as the writer is told done: stale window 0.
  - Write time when it does not wait: `0.3` ms. East readers can read the old value for a window of `R / 2` ms (one way).
  - Distances (round trip) from napkin-math [S3]: same region 0.25 ms; North America East to West 60 ms; EU West to North America East 80 ms; EU West to Singapore 160 ms.
- **Check points:**

  | Far copy is | R | Waits: write time | Does not wait: write time | Stale window |
  |---|---|---|---|---|
  | in the same region | 0.25 ms | 0.55 ms | 0.3 ms | about 0.1 ms (0.125) |
  | North America East to West | 60 ms | 60.3 ms | 0.3 ms | 30 ms |
  | EU West to North America East | 80 ms | 80.3 ms | 0.3 ms | 40 ms |
  | EU West to Singapore | 160 ms | 160.3 ms | 0.3 ms | 80 ms |

- **Inputs and snaps:** drag the far copy along a rail with four snap points (the four rows above; default North America East to West). One toggle outside the picture: "Write waits for the far copy: on / off" (default on). One hint line: "Drag the far copy; switch the wait."
- **What moves:** the writer's wait ring grows to the write time (to scale, with a break mark above 20 ms); a message dot travels to the far copy and back when the write waits; a stale-window bar appears under the East copy when it does not wait, with an East reader tap that shows `x = old` inside the window.
- **Verdicts:** waits: "Fresh; the write takes {t} ms" (at most 31 characters, e.g. "Fresh; the write takes 60.3 ms", 30). Does not wait: "Fast: 0.3 ms; far reads stale {s} ms" (at most 36, e.g. "Fast: 0.3 ms; far reads stale 30 ms", 35; same region: "Fast: 0.3 ms; far reads stale 0.1 ms", 36).
- **Primitive:** `picture-slider` (snapped rail) with a timeline drawing on `beat-frame.tsx`; toggle via `BeatToggle`.
- **Limits text:** "One writer, one far copy, rounded numbers for reasoning, not benchmarks. Real systems also queue, retry and batch."
- **Sources:** [S3] napkin-math round trips and fsync write; [S57] PACELC (the \"else\" choice is latency against consistency).
