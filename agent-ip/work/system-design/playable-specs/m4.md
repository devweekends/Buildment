## 7. Playable specs

### sysdesign-m4-instance-picker (4.2 beat "Pick sizes and counts yourself")
- **Claim:** One server going down takes out one server's share. N+1 holds back one server of spare, and that spare is cheapest when servers are small.
- **Model:** Demand is 500 requests a second (Daftar in exam week). The made-up price list is:

  | Size | Requests a second | Price per hour |
  |---|---|---|
  | small | 100 | $0.10 |
  | medium | 200 | $0.20 |
  | large | 400 | $0.40 |
  | xlarge | 800 | $0.80 |

  A load balancer costs $0.05 an hour whenever there is more than one server.
- **Formulas:**
  - Capacity = size × count.
  - Busy = 500 / capacity.
  - Cost = price × count, plus the balancer.
  - After one failure, capacity = size × (count − 1).
- **Check points:**

  | Fleet | Busy | After one fails | Cost per hour |
  |---|---|---|---|
  | 8 small | 63% | 71% | $0.85 |
  | 5 medium | 50% | 63% | $1.05 |
  | 3 large | 42% | 63% | $1.25 |
  | 1 xlarge | 63% | down | $0.80 |
  | 7 small | | 83% | |
  | 2 large | | 125% | |

- **Inputs:** tap one of four size chips drawn in the picture. Drag the count from 1 to 8, step 1, with snap points at 3, 5 and 8.
- **What moves:** the server cards multiply as the count rises, request dots flow, and each card's busy pill changes colour. A "fail one" ghost card shows the load after one failure. There is a cost tag and a capacity tag.
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | Capacity under 500 | "Too small: 500/s will not fit" |
  | Count is 1 | "One server: one failure takes all" |
  | After one failure, over 100% | "Fits, but one failure overloads it" |
  | After one failure, 80% to 100% | "Survives one failure, near the knee" |
  | After one failure, 80% or less | "Survives one failure: N+1 at 80%" |

- **Primitive:** `block-map.tsx` for tapping cards, plus `picture-slider.tsx` for the count rail.
- **Sources:** made-up prices (dossier "What not to teach"); queueing knee from chapter 2.5 [S6, S7].

### sysdesign-m4-kill-server (4.3 beat "Kill a server, count the logouts")
- **Claim:** In-memory sessions break as soon as there is a second server. Sticky sessions lose a server's users when it dies. A shared store loses nobody, until the store itself fails.
- **Model:** 4 app servers and 1,200 logged-in students, 300 per server.
  - In memory, no stickiness: 3 in 4 requests miss their session (round robin over 4).
  - Sticky: killing a server logs out its 300, or 300 × k for k servers killed.
  - Shared store: killing an app server logs out 0. Killing the store logs out all 1,200.
- **Inputs:**
  - One mode toggle outside the picture: "In memory", "Sticky", "Shared store".
  - Tap a server card to kill it or bring it back.
  - Tap the store card to kill it; it shows only in "Shared store" mode.
- **What moves:** a crowd of student dots per server, a logged-out counter, and dots turning red and falling away when their server dies. In "In memory" mode, request dots bounce between servers and flash "who is this?".
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | In memory | "Every 3 in 4 requests miss a session" |
  | Sticky, one server killed | "Sticky: 300 students logged out" |
  | Shared store, app server killed | "Shared store: nobody logged out" |
  | Store killed | "Store down: all 1,200 logged out" |
  | Sticky, before any kill | "Each server down: its users log out" |

- **Primitive:** `block-map.tsx` (tap to break a block; the banner says what users lose).
- **Sources:** stateless servers (dossier domain model); [S46, S49] for "sticky".

### sysdesign-m4-failover-play (4.4 beat "Fail a backend, watch the load shift")
- **Claim:** A dead server keeps getting its share until interval × threshold has passed, so those requests fail. The survivors then carry its load.
- **Model:** 180 requests a second over 3 servers, each able to do 100 a second, so 60% busy each.
  - Detection time = interval × 3 failed checks.
  - Failed requests = 60 per second × detection time: 1,800 with 10-second checks, 360 with 2-second checks.
  - After one server fails: 2 servers at 90%.
  - After two fail: 1 server receiving 180 a second, overloaded.
  - If all three are failed, the picture fails open.
- **Inputs:**
  - Tap a server card to fail it or bring it back.
  - One toggle outside the picture for the interval: "every 2 s" or "every 10 s".
  - Replay.
- **What moves:**
  - Request dots go to each server.
  - Dots to the dead server turn red and are counted.
  - A check ring counts the seconds by the balancer.
  - Per-server load bars rise and change colour.
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | All up | "All 3 up: each 60% busy" |
  | Before removal | "Dead server still gets traffic" |
  | After removal | "Out after checks: 2 at 90%" |
  | Two failed | "2 down: 1 server, 180/s, overloaded" |
  | All failed | "No healthy server: fail open" |

- **Primitive:** `traffic-playground.tsx` extended to three server cards, or `design-stepper.tsx` with a break-a-part step.
- **Sources:** [S19], [S20], [S15]. The settings are examples.

### sysdesign-m4-algorithm-race (4.5 beat "Same traffic, four algorithms")
- **Claim:** At high load, pickers that look at queues (least connections, two choices) keep p99 low. Pickers that do not (random, round robin) let one server's line grow while others idle.
- **Model:**
  - One seeded arrival sequence goes through four balancers, each in front of 4 servers.
  - Each server does 100 requests a second at 10 ms average work. 1 request in 20 costs 20 times more.
  - The algorithms are random, round robin, least connections (tie goes to the first server), and two choices using 4.7's exact draw rule.
  - Each balancer gets its own p99 from the shared simulation core (`frontend/src/canvas/sim/`).
  - Expected order near the top: least connections and two choices well below round robin and random.
  - The exact numbers come from the simulation, so the builder must compute and fix them for the chosen seed.
- **Inputs:** drag the load from 30% to 99% busy, with snap points at 50, 80 and 95.
- **What moves:** four small panels, each with queue dots per server and a p99 tag.
- **Verdicts:**

  | When | Verdict |
  |---|---|
  | Under 50% | "Low load: all four look alike" |
  | 50% to 100% | "Queue-blind pickers bend first" |
  | Load over 100% (if allowed) | "Over 100%: every picker falls over" |

- **Primitive:** `traffic-playground.tsx` for the rail and queue dots, with four lanes. It may need a small new multi-lane primitive.
- **Sources:** [S16], [S17], [S21].

### sysdesign-m4-spike-play (4.6 beat "Set the delay, count the drops")
- **Claim:** Requests are dropped in the gap between a spike and new capacity. A faster boot cuts drops at no hourly cost; a lower target cuts them by paying for headroom every hour.
- **Model:**
  - 300 requests a second before 8 pm, 600 from 8 pm. Each server does 100 a second.
  - Starting fleet: ceil(300 / (100 × target)) servers.
  - Every second, drops = max(0, load − ready servers × 100).
  - Every 15 seconds [S34], the autoscaler reads min(1, load / capacity), computes desired = ceil(ready × reading / target), and starts desired − ready − booting new servers. Each is ready after the boot time.
  - The simulation runs 600 seconds.
- **Check numbers:**

  | Boot time | 60% target: drops (final fleet) | 80% target: drops (final fleet) |
  |---|---|---|
  | 0 s | 1,600 (10 servers) | 4,700 (8 servers) |
  | 30 s | 4,500 | 12,000 |
  | 60 s | 7,500 | 21,000 |
  | 90 s | 10,500 | 30,000 |
  | 120 s | 13,500 | 39,000 |
  | 180 s | 19,500 | 57,000 |

  The 90-second figures and the 30-second, 60% figure appear in the chapter fold.
- **Inputs:** drag the boot time from 0 to 180 s, snapping every 30 s. One toggle outside the picture for the target: 60% or 80%.
- **What moves:**
  - A time strip from 0 to 300 s with a cursor.
  - Server cards appear as "booting", then turn ready.
  - Spill-over dots fall away as drops, with a drop counter.
- **Verdicts:** "Dropped {n} requests in the gap", at most 34 characters with "30,000". Use "No spike drops: headroom covered it" when there are none.
- **Primitive:** `year-strip.tsx`'s strip idea, or `traffic-playground.tsx` with a timeline. A new small timeline playable may be simplest.
- **Sources:** [S34]. The boot times are made up.
