# Module 09: IPv6: enough addresses for everyone

Source IDs such as [S3] point to the source table in `01-research-dossier.md`. "Dossier 5.6" means that section of the dossier. Anything marked "untested, verify at G3" is not in a dossier test.

## Outcome

The learner can find the IPv6 addresses on their own computer and phone, read and shorten an IPv6 address by the standard rules, explain why a normal subnet is a `/64`, and explain how a network works without NAT: every device has its own global address, and a filter, not NAT, decides who can reach it. They can state one reason IPv6 helps and one reason IPv4 and NAT will last.

Roadmap outcome served: O2, as evidence for why IPv6 removes the need for NAT (quiz 9.4 and gate 9.5). Other evidence is the module's own: recorded addresses, an in-chapter v6 exercise and quiz (9.2) and a netlab check (9.3).
Opening question, unchanged: *Open your phone's Wi-Fi details. Next to the familiar `192.168.x.x` there is probably a long address with colons, such as `2001:db8:4a1:20::5c`. Where did a second address come from, and why does your phone need it?*

## Why this module exists

Module 2 said IPv4 ran out; module 6 showed NAT as the workaround. IPv6 is the long-term answer, and the learner's own phone probably uses it already. The module sits after the capstone so that the IPv4 and NAT story stays whole; the learner has the full picture before seeing the version where much of it is not needed. It is short on purpose: reading addresses and understanding a network without NAT. There is no build in the core path (decision 10); the build is stretch S5.

### 9.1 The address you did not know you had (Read, 10 min) `09.01-the-address-you-did-not-know.md`
- Hook (derived): the opening question, shown as a phone screen with two addresses.
- Claim: your devices very likely already hold an IPv6 address, often next to the IPv4 one. The output shows at least a link-local address (`fe80::/10`, never forwarded off the link [S3]) and, on networks that offer IPv6, a global one. How each system labels them differs, so the chapter reads real outputs.
- Worked example: an annotated sample using the documentation prefix [S69]: link-local `fe80::1c2b:3aff:fe4d:5e6f` and global `2001:db8:4a1:20::5c`. Writers must record real outputs on Windows, Linux and a phone screen before drafting; macOS is unverified (dossier). A branch for "no global address": that is normal on a network without IPv6.
- Diagram: none (Read). The annotated outputs carry the point.
- Interactive: none (roadmap, "on your computer"). RealWorldEvent: Google's IPv6 share passed 50 percent, 50.10 percent on 28 March 2026 [S33], dated and re-checked before publish.
- Assessment: none. The evidence is the learner recording their addresses (Checklist, self-attested). Near miss: assuming a missing IPv6 address means something is broken, or pasting a real global address into a public repository.

### 9.2 Reading IPv6 addresses (Learn, 35 min) `09.02-reading-ipv6-addresses.md`
- Hook (roadmap): your phone shows `fe80::1c2b:3aff:fe4d:5e6f`. How many bits is that, and where did the missing zeros go?
- Claim: an IPv6 address is a 128-bit number written as eight 16-bit groups in hex; `::` stands for exactly one run of zero groups, so every valid short form has one expansion. A normal subnet is a `/64` because the second half of the address names the interface [S3].
- Worked example: `fe80::1c2b:3aff:fe4d:5e6f` expands to eight groups (`::` is three zero groups, 48 bits). `2001:db8:4a1:20::5c` expands to `2001:0db8:04a1:0020:0000:0000:0000:005c`. `2001:0db8:0000:0000:0001:0000:0000:0001` shortens to `2001:db8::1:0:0:1` (two equal zero runs, the first is compressed; tie rule is RFC 5952 section 4.2.3, check the text because the dossier lists only the first three rules [S4]). A single zero field stays `0`, never `::`. Invalid: `2001:db8::1::5c`. Valid but non-standard: `2001:0DB8:0:0:0:0:0:5C` and `2001:db8:0:0:0::5c`. Under the documentation `/32` there are 32 bits for subnets and 64 for hosts: 2^32 subnets of 2^64 addresses, derived arithmetic. The `/64` wording is the practical reading of "64-bit interface ID" [S3]; say so.
- Diagram: static SVG through `VisualDiagram`, not raw SVG in the page: a 128-bit bar of eight groups with the `/64` cut after the fourth group and the `::` run marked. Claim: the structure of an address is eight groups with a fixed cut at 64 bits.
- Interactive: `[addr: v6]`, shorten and expand, invalid forms refused with the rule. Predict first: in `2001:db8:4a1:20::5c`, how many zero groups does `::` stand for? Options 2 / 3 / 4. Correct: 3.
- Assessment: one PREDICT, one QUIZ question (pick the standard short form). MustRead: RFC 5952 section 4 [S4]. BigWordAlert: interface ID. Near miss: two `::`, a single zero field compressed, uppercase letters. Do not say the interface ID comes from the MAC; modern systems often use other values and the dossier has no source (UNVERIFIED).

### 9.3 A network without NAT (Learn, 35 min) `09.03-network-without-nat.md`
- Hook (roadmap): with IPv6 your phone and laptop each have their own global address. Then what stops anyone on the internet from reaching them?
- Claim: NAT was never what kept the internet out (module 6: an unsolicited packet has no mapping and the internet has no route to private ranges, and NAT is not a firewall). With a global address on every device, reachability is decided by a filter that drops packets nobody asked for. A host forms its global address by SLAAC, from a router-advertised prefix plus its own interface identifier after duplicate address detection [S72]; temporary addresses are randomised and replaced over time for privacy [S73]; dual stack means complete support for both IPv4 and IPv6 [S74].
- Worked example, with documentation addresses [S10, S69]: IPv4 side: phone `192.168.1.24` and laptop `192.168.1.23` both appear to the server as `198.51.100.2`. IPv6 side: router prefix `2001:db8:4a1:20::/64`, phone `2001:db8:4a1:20::5c`, laptop `2001:db8:4a1:20::23`, server `2001:db8:ffff::80`; the server sees each device's own address and can tell them apart. The IPv6 view's filter is stateful: replies to outbound connections pass, and an unsolicited packet to the phone is dropped. This is the lab's model, not a dossier test (IPv6 forwarding is untested, dossier 5.6).
- Diagram: MermaidDiagram: one device with two addresses and two paths, IPv4 through NAT and IPv6 direct. Claim: dual stack is two networks side by side on one interface; NAT is only in the IPv4 path.
- Interactive: `[netlab: IPv6 view]`: the same home network with IPv4 and NAT, then with IPv6; compare what the server sees. Predict first: with IPv6, what source address does the server see for the phone? Options: the router's address / the phone's own address / a new random address. Correct: the phone's own address.
- Assessment: one PREDICT, one QUIZ question (what protects a device without NAT: a filter). A Callout says real home routers differ in what they filter by default. Near miss: "no NAT means anyone can reach my laptop", or the opposite, "IPv6 is unsafe".

### 9.4 IPv6 (Check, 15 min) `09.04-ipv6-quiz.md`
- Hook, claim: none (quiz only). Five questions, one instrument: (1) shorten `2001:0db8:0000:0000:0001:0000:0000:0001`; (2) IPv4, one device behind NAT: what the server sees (`198.51.100.2`); (3) IPv4, two devices using the same source port: address the same, port may change only on a clash (module 6, dossier 5.6); (4) IPv6, phone with a global address: the server sees the phone's own address; (5) IPv6, an unsolicited packet from the server to the phone with a filter in place: dropped.
- Two of the four "what a server sees" cases are IPv4 and NAT, which is how this Check mixes in earlier modules without adding questions.
- Near miss: option length and position balanced; the short-form question must not be answerable by the longest option. Check questions are plain quiz fences in the drill style, with no canvas.

### 9.5 Why IPv4 is still here (Gate, 20 min) `09.05-gate-why-ipv4-is-still-here.md`
- Hook (derived): a friend says IPv4 is finished, or that IPv6 will replace it next year. What do you say?
- Claim: both are true at once. IPv6 removes the shortage and the need for NAT; IPv4 persists because sharing addresses (NAT and provider NAT) keeps it working and a large share of users still reaches services over it.
- Worked example, using only facts from earlier chapters and the dossier: the four exhaustion dates (IANA 2011, APNIC 2011, ARIN 2015, RIPE NCC 2019 [S13 to S16]); `100.64.0.0/10` as the provider NAT range [S11]; Google's 50.10 percent on 28 March 2026, so about half the users do not [S33]; the 2016 study with CGN over 92 percent of cellular networks, dated [S34]. State a model answer shape, not new content.
- Diagram, interactive: none (gate). Assessment: one OPEN_QUESTION, `text`, about 80 to 150 words with an honest `minWords`; link-only answers need `minWords: 0`.
- Near miss: an answer that names no number or observation from the learner's own network or the course. The module bridge is one sentence: the Linux course reuses challenges 2 and 4 for container networking, and cloud networking arrives in the AWS course.

## Risks

- Likeliest stall: 9.2, the `::` rules (two `::`, a single zero field compressed, a missing tie rule). Mitigation: the canvas refuses invalid forms with the rule, and the drill repeats until the rule is used unprompted. Long addresses wrap badly at 375 px; the canvas and text must break at colons.
- Accuracy traps (dossier "Care" lines): `/64` is the practical reading of "64-bit interface ID" [S3]. IPv6 calls TTL "Hop Limit" and RFC 8200 alone does not say a router sends an error [S2]; make no Time Exceeded claim for IPv6. The Google figure is dated and fast-moving [S33]; re-check before publish. Use `2001:db8::/32` for every IPv6 example [S69] and never a real learner address.
- Source gaps: SLAAC [S72], temporary addresses [S73] and dual stack [S74] are sourced. The default filtering of home routers still has no source, so the Callout says only that routers differ. Router advertisements and IPv6 forwarding were not tested (dossier 5.6), so nothing in this module claims lab IPv6 behaviour beyond the netlab's stated model.
- Privacy: a learner's real global IPv6 address can identify their network. 9.1 and the gate ask the learner to keep it out of public repositories and use a stand-in in any public write-up.
- The gate must not invent facts: build the answer shape only from the exhaustion dates, `100.64.0.0/10`, the Google figure and the dated CGN study.
