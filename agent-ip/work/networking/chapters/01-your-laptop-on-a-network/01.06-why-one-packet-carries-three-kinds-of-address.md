Your Wi-Fi only reaches your router, yet your packet can cross the world and land in one program. One packet does all of that. How?

## Wi-Fi reaches the router, not the world

<MermaidDiagram title="One link, many links" chart={`flowchart LR
  A["Your laptop 192.168.1.23"] ---|"link 1"| B["Your router"]
  B ---|"link 2"| C["Provider router"]
  C ---|"more links"| D["More routers"]
  D ---|"last link"| E["Server 203.0.113.80"]
`} legend="Each line is one link, a cable or a Wi-Fi connection between two neighbours. Your laptop touches only link 1. The server is at the end of many links." />

Your laptop talks to your router over one link. The server is many links away, and your laptop never touches the last one. Each link needs its own delivery. The far end also needs the right computer and the right program. One packet must carry a label for each job.

<GoDeeper title="Go deeper: a link and a path are different things">

A link joins two neighbours: a cable between two devices, or a Wi-Fi connection between your laptop and your router. A path is the whole chain of links from your laptop to the server. Your laptop can only send a message across the first link. After that, each router passes the message across the next link.

So a message needs three labels. One names the device at the other end of the current link. One names the far computer, so that every router can decide where to send it next. One names the program on that computer, so the web page goes to the web server and not to some other program. Three jobs need three kinds of address. A MAC address alone cannot do all three, because a MAC address only names a device on one link. That is reasoning, not a rule from a standard. The next beats show the labels.

The example in this chapter is a web request from your laptop, `192.168.1.23`, to a server, `203.0.113.80`, an address from the documentation ranges. It is made up for the picture.

</GoDeeper>

## Three jobs, three kinds of address

<InteractiveCanvas slug="net-m1-packet-jobs" />

A packet carries three <GlossaryTerm term="header" definition="Labelled numbers placed in front of a message." />. The Ethernet header names the next device on this link, by MAC address. The IP header names the far computer. The TCP header names the program, by port. Each device reads only the header for its own job. Tap each header to see its job and who reads it.

<GoDeeper title="Go deeper: what each header answers">

The Ethernet header answers: who gets this on the next link? It holds two MAC addresses, the receiver's and the sender's. A MAC address is 48 bits, written as six pairs of letters and digits [S22]. It names one network end, and it only matters on one link.

The IP header answers: which computer is this finally for? It holds the source address and the destination address, here `192.168.1.23` and `203.0.113.80`. It also holds the TTL from chapter 1.5. Routers read this header to choose the next link.

The TCP header answers: which program? It holds a source port and a destination port. A port is a 16-bit number [S25]. The web server listens on port 80, so the request goes to port 80, and the reply comes back to the port your laptop picked. TCP also does other work, such as making sure no data is lost. Module 5 covers it. Here we only use its ports.

Wi-Fi frames are laid out differently from Ethernet frames. The lab and the pictures use Ethernet. The three jobs are the same in both.

</GoDeeper>

## Wrap a message, outermost last

<InteractiveCanvas slug="net-m1-packet-wrap" />

Sending wraps from the inside out. The message gets a TCP header first, then an IP header around that, and Ethernet last. So Ethernet is the outermost layer, the first thing any device sees. The hardware addresses in this picture are made up, such as `02:00:00:00:00:23`. Add the headers in order and watch the packet grow. A wrong order is refused, with the reason.

<GoDeeper title="Go deeper: the order on the wire, and why it is this order">

Written from first to last on the wire, the packet looks like this. The brackets show one header each.

```
[ Ethernet: to the router, from the laptop ][ IP: from 192.168.1.23 to 203.0.113.80 ][ TCP: to port 80 ][ message ]
```

The order follows the jobs. The program's label sits closest to the message, because only the program at the far end needs it. The far computer's label goes around that, because every router reads it. The link's label goes on last, because it only matters for one link, and the first device to receive the packet must find it first. The picture refuses a wrong order and says why, so you can try it.

The destination hardware address in the Ethernet header is the router's, not the server's. Your laptop does not send the packet to the server directly. It hands it to the router, the gateway from chapter 1.1, and the router passes it on. The hardware addresses here start with `02`, made up for the picture, so they cannot match any real device.

</GoDeeper>

## The router opens only the outer layer

<InteractiveCanvas slug="net-m1-packet-unwrap" />

The router strips the Ethernet header and reads the IP header. It lowers the TTL from 64 to 63 and puts a new Ethernet header on for the next link. It never opens the TCP header or the message. The IP addresses stay the same. The hardware addresses change at every link. Step the packet through the router. The picture shows one packet going one way.

<GoDeeper title="Go deeper: why a new Ethernet header, and one exception">

The Ethernet header named one link, and the packet has now left that link. The next link has different devices, so it needs different hardware addresses. The router builds a new Ethernet header for it, with its own MAC address as the sender and the next device as the receiver. That is why a hardware address only ever lasts one link.

The router lowers the TTL by at least one, and drops the packet if it reaches zero [S30]. In a test of the course lab with two routers between two computers, a packet that started at TTL 64 arrived with TTL 62. Module 4 follows the TTL across real routers and explains the routing choice the router makes from the IP header.

The IP addresses stay the same on the way, with one exception that module 6 builds. Your home router rewrites the source address when a packet leaves your home. That is part of why the website in chapter 1.1 saw `203.0.113.45` and not your laptop's number.

The picture shows one packet going one way, with Ethernet only and no TCP behaviour. It is a model of the headers, not of everything a router does.

</GoDeeper>

## A broadcast MAC reaches everyone

<InteractiveCanvas slug="net-m1-scene-broadcast-mac" />

The address `ff:ff:ff:ff:ff:ff` is the broadcast MAC address: every device on the link accepts a frame sent to it. Your laptop used it for the question in 1.4. The phone's answer went only to the laptop's MAC, so only the laptop heard it. Watch who hears each frame.

<GoDeeper title="Go deeper: broadcast and the answer to it">

In chapter 1.4 your capture showed the first line sent to `ff:ff:ff:ff:ff:ff`. That is the question: who has `192.168.1.20`? Every device on the cable hears it, but only the owner answers. The answer goes to one MAC address only, the laptop's, so nobody else on the cable has to read it.

<Callout type="info" title="Wi-Fi frames look different">
At the Ethernet level, a packet with its Ethernet header is called a frame. Wi-Fi frames are laid out differently from Ethernet frames. The lab and the pictures use Ethernet, because the lab has no Wi-Fi. The idea of three jobs holds for both.
</Callout>

The `-e` option of `tcpdump` is what showed these addresses in your capture. Run the capture from 1.4 again with it, and find the broadcast line yourself. Module 3 explains how a switch uses these addresses to decide where a frame goes.

</GoDeeper>
