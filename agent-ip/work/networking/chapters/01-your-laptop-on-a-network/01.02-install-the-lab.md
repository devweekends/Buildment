Start the download now and read while it runs. The lab needs Docker Desktop, and Docker Desktop is a big download. Docker's page does not state its size, so start it on Wi-Fi if you can, not on mobile data. Everything below is worth reading while the installer works.

By the end of this chapter you will have a small Linux computer running inside your own laptop. We call it the lab. A checker will print `PASS` on every line. That is the only thing you build here, and every later challenge runs inside it. Your real network is never touched. When you type `exit`, the lab is deleted, and you start a fresh one next time.

## What the lab is, and why it lives inside your laptop

Windows, macOS and Linux each have their own tools for networks. The commands that build virtual networks, such as the ones in chapter 1.4, exist on Linux. If every learner used a different system, every learner would see different output and a different set of errors. So the course gives everyone the same small Linux computer, with the same tools in the same versions. It runs inside a program called <GlossaryTerm term="Docker" definition="A program that runs other programs in small sealed boxes called containers." />. The lab is one such <GlossaryTerm term="container" definition="A sealed box that runs one program or one small computer, and is deleted when it stops." />.

This means there are now two places to type commands, and mixing them up is a common early mistake. The diagram shows where each one lives.

Look at what is inside the lab and what is not. On Windows and macOS, Docker Desktop runs containers inside a Linux virtual machine of its own [S38]. If you run plain Docker Engine on a Linux laptop, that extra machine is not there. In every case the lab does not contain your real router, your real address or your real path to the internet. Those stay on your computer. In our own test, running `traceroute` inside the lab showed Docker's private network and then the destination. It hid the routers of a real home and provider. So commands about your real network run on your computer, and commands about networks you build run in the lab.

Every command block in this course says which place it is for. A block marked **On your computer** goes in your normal terminal. A block marked **In the lab** goes at the prompt that starts with `(lab)`. If a command is not found, or prints numbers you do not recognise, check first that you typed it in the right place.

## Does your laptop meet the requirements?

Docker states what a computer needs, and the list is short but strict. The page below is Docker's own, for Windows. Read it and answer one question: does my laptop meet the list? On the page we read, the list included Windows 11 version 23H2 or later for the Pro, Enterprise and Education editions. It also listed WSL 2.1.5 or later and 8 GB of memory [S57]. The page did not make clear whether the Home edition is supported, so check the page for your own edition. This course does not promise that Home works.

If you use a Mac or Linux, start from Docker's main page for Docker Desktop, `https://docs.docker.com/desktop/`, and read the page for your system. The lab image takes about 200 MB on disk once it is built. We have not yet measured the size of the download itself, so keep a little more free space than that.

A phone cannot run the lab. If you only have a phone, read this chapter to see the whole procedure and use the replay at the end. Then carry on with the reading chapters. Your mentor can help you find a laptop to borrow for the build chapters.

## Start the lab and run the checker

Start with the lab itself. This is the one command that begins the whole course, so type it exactly. **On your computer**, in a terminal opened inside your repository folder:

```
bash lab/start.sh
```

If you use Windows PowerShell, the same step is `.\lab\start.ps1`. The first time, the script builds the lab image from the recipe in the `lab` folder. On our test laptop, with a fast connection, this took about 40 seconds. It downloads packages, so it needs the internet and it takes longer on a slow connection. After the first time, the image is already on your computer and the lab starts in a moment.

Look at the prompt. If it starts with `(lab)`, you are inside the lab, and your repository folder appears there as `/work`. If Docker is not running, the script stops and says: "Docker is not running. Start Docker Desktop, wait until it says it is running, then run this again." That message is the script's own. It is a common first problem. Now run the checker. **In the lab**:

```
bash toolkit/check-setup.sh
```

This is the output from a working lab, recorded in the course lab. Yours should match line for line.

```
PASS in-lab
PASS repo-visible
PASS tool-ip
PASS tool-nft
PASS tool-tcpdump
PASS tool-dnsmasq
PASS tool-dig
PASS tool-traceroute
PASS tool-ping
PASS tool-nc
PASS tool-curl
PASS tool-conntrack
PASS tool-busybox
PASS tool-nano
PASS tool-dhclient
PASS namespace-create
PASS veth-create
PASS line-endings
RESULT: all checks passed
```

Each line is one question. `in-lab` asks whether you are inside the lab at all. `repo-visible` asks whether your repository folder is at `/work`. The thirteen `tool-` lines ask whether each tool the course needs is installed. The two lines that matter most are `namespace-create` and `veth-create`. They try to build the two things that chapter 1.4 needs, a separate network space and a virtual cable. If either fails, the rest of the course cannot work, so the checker tests them now, while a fix is cheap.

<Callout type="warning" title="Safety note: privileged">
The start script runs the lab with a Docker setting called `--privileged`. It gives the container all Linux powers and access to devices on Docker's virtual machine [S37]. We need that so you can build virtual networks. Use it only for this lab image. Never use it for an image you do not know.
</Callout>

## The test that must fail

A checker that has never failed proves nothing. It might print PASS whatever you do. So the second half of this chapter makes it fail on purpose, in a way you understand, and then fixes it. This is the pattern for every challenge in the course: one test that must pass, and one that must fail.

Type `exit` to leave the lab. **On your computer**, start the lab again, this time without the privileged setting. In Git Bash or Linux or macOS type `bash lab/start.sh --no-privilege`. In PowerShell type `.\lab\start.ps1 -NoPrivilege`. Then run the checker again in the new lab. A lab started without the privileged setting cannot make a network space, so one line must fail. This is the recorded output. The lines above the failing one are all `PASS`, as before.

```
FAIL no-privilege: a namespace could not be made. The lab needs --privileged. Type exit, then start it with: bash lab/start.sh
PASS line-endings
RESULT: 1 check(s) failed. Read the first FAIL line. Its name tells you which check.
```

Type `echo $?` straight after the checker. It prints `1`, not `0`. An exit code of 0 means success and anything else means failure, and the course tests rely on this. Now `exit`, and start the lab the normal way. You have seen the checker pass and fail, so you can trust it.

## Reading a failure: the five names

The checker gives every problem a name. Read the first `FAIL` line only, because one cause often makes later lines fail too. The word after `FAIL` names the problem, and the rest of the line is the fix. There are five names, and each one has a different cause.

| Name | What it means | Fix |
|---|---|---|
| `not-in-lab` | You ran the checker on your computer, not in the lab | Run `bash lab/start.sh`, then run the checker in the lab |
| `no-privilege` | The lab was started without `--privileged` | Type `exit`, then start with `bash lab/start.sh` |
| `wrong-image` | A tool is missing, so the image is old or wrong | On your computer: `docker rmi networking-lab`, then `bash lab/start.sh` |
| `crlf-line-endings` | A script has Windows line endings | Run the `sed` command the checker prints, then run the checker again |
| `repo-not-visible` | Your folder is not at `/work`, so the lab sees nothing | Type `exit`, then start the lab again from inside your repository folder |

The first name is one you may well meet. If you run the checker on your own computer by mistake, this is what it prints. It is recorded output, and it already contains the fix.

```
FAIL not-in-lab: this is not the lab. On your computer run: bash lab/start.sh (Windows PowerShell: .\lab\start.ps1). Then run this checker again inside the lab. If you did that, rebuild the image: docker build -t networking-lab lab/
RESULT: 1 check(s) failed. Read the first FAIL line. Its name tells you which check.
```

The line-endings problem needs a short explanation, because it looks strange. Windows ends each line of a file with two hidden characters. Linux wants one. A script saved the Windows way stops with errors such as `invalid option name` or `command not found` followed by odd characters. The template has a `.gitattributes` file and an `.editorconfig` file that keep scripts in the Linux form. If a script still has the Windows form, run this once in the lab, then try again.

```
find /work -name '*.sh' -exec sed -i 's/\r$//' {} +
```

## If you are stuck

Work through the hints in order and stop as soon as one helps. First, read the first `FAIL` line again. Its name tells you which check failed, and that is usually enough. Second, find the name in the table above, which maps each name to its fix. Third, run the fix command and run the checker again. Every script in the course is safe to run again, so there is no harm in trying twice.

If the checker will not run at all, check the likeliest causes first. Is Docker Desktop running? Start it and wait until it says so. Are you in the right place? The prompt must start with `(lab)` for the checker, and must not for `lab/start.sh`. On your computer you can also type `docker version` and `docker info`. We have not recorded their output for this course, so read them for words such as "error" or "cannot connect". Those words mean Docker is not running. If none of this helps, copy the first `FAIL` line and send it to your mentor. That one line is more useful to them than a screenshot of everything.

Run `bash toolkit/check-setup.sh --versions` in the lab and paste its extra lines too. They show the version of each tool. Copy the long `sha256:` code from line 1 of `lab/Dockerfile`.
