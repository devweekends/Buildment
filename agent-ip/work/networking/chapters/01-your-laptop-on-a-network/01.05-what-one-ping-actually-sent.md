Your capture from 1.4 is a few lines of numbers. What exactly crossed the virtual cable? Open the packets: every number has a job, and a different party set each one.

## One ping is more than one packet

<MermaidDiagram title="The packets of one ping" chart={`sequenceDiagram
  participant L as laptop 192.168.1.10
  participant P as phone 192.168.1.20
  L->>P: 1 ARP request, who has 192.168.1.20?
  P->>L: 2 ARP reply, 192.168.1.20 is at my hardware address
  L->>P: 3 echo request
  P->>L: 4 echo reply
`} legend="Four packets, in order. Packets 1 and 2 are the laptop finding the phone. Packets 3 and 4 are the ping itself." />

A ping is not one packet. In your capture, the laptop first asked the whole cable who owns `192.168.1.20`, and the phone answered. Only then did the echo request and the echo reply cross. So the first ping is four packets. With `-v`, tcpdump prints each ping packet on two lines, so count packets, not lines.

<GoDeeper title="Go deeper: why the question comes first">

The laptop knows the phone's address, but a message on a cable is delivered by hardware address. So the laptop sends a question to every device on the cable: who has `192.168.1.20`? The owner answers with its hardware address, and the laptop keeps the answer for a while. This is ARP, the Address Resolution Protocol [S22]. Module 3 shows it step by step. Chapter 1.6 explains the hardware address and the special address that means everyone.

That is why the second ping in 1.4 had no question before it. Your laptop already knew the answer. The `ip neigh flush` line in the capture step made it forget, so you could see the question again.

<Callout type="warning" title="Do not read the ARP lines as ping lines">
The first two lines are not part of the ping. They are packets the ping needed. If you count them as pings, you will think the laptop pinged twice.
</Callout>

The capture used the filter `arp or icmp`. Without it, the same capture would also show IPv6 packets that the two lab computers send when a cable comes up. They are real, and they are not part of this story.

</GoDeeper>

## A DNS query carries two ports

<InteractiveCanvas slug="net-m1-packet-dns" />

This real packet asks the phone to turn the name `web.test` into an address. Two addresses name the two computers. Two <GlossaryTerm term="port" definition="A number that names one program on a computer." /> numbers name the program at each end: 37028 asks, 53 answers. In a capture, a port follows its address after a dot, as in `192.168.1.10.37028`.

<GoDeeper title="Go deeper: ports, and the same packet as tcpdump writes it">

Here is the query as `tcpdump` wrote it in the lab. The phone ran a small DNS program, `dnsmasq`, that answered with the address `203.0.113.80`, an address from the documentation ranges.

```
192.168.1.10.37028 > 192.168.1.20.53: 31431+ [1au] A? web.test. (49)
```

Read it left to right. The source is address `192.168.1.10` with port 37028. The destination is address `192.168.1.20` with port 53, where the DNS program on the phone listens. After the colon come the question number, `31431`, and `A? web.test.`, which means: what is the address of web.test? The reply swaps the two ends. It comes from port 53 and goes to port 37028, so the asking program can match the answer to its question.

The asker did not choose 37028 on purpose. The computer picked a free number for this one question. Linux picks from 32768 to 60999 by default [S28]. The official registry names a different range for these short-lived ports, 49152 to 65535 [S27]. So 37028 is a normal Linux choice, and another system may choose from a different range.

The TTL in this packet is 64, the same as in the ping. You will meet it in the next beat.

</GoDeeper>

## A ping has addresses and TTL, no ports

<InteractiveCanvas slug="net-m1-packet-echo" />

The echo request from 1.4 has two addresses, a <GlossaryTerm term="TTL" definition="A counter in each packet. Every router lowers it by one." /> of 64, and a type, which `tcpdump` writes as `echo request`. It has no port field, because ping asks the whole computer. Tap the empty port slot to see why. The phone's reply swaps the two addresses and has its own TTL, also 64.

<GoDeeper title="Go deeper: ICMP, the id and the TTL">

Ping uses a message type called ICMP echo, from the Internet Control Message Protocol. The computer that receives an echo request answers it by itself, with no program involved. That is why there are no ports.

Two numbers on the second line of a ping packet are easy to mix up. In the lab capture, the echo request says `id 584, seq 1`. The `id` names this run of the ping command, and `seq` counts the pings in the run. A different number, `id 12923`, sits on the line above, inside the brackets. That one belongs to the IP packet itself. They are different fields with the same word.

The TTL is 64 because Linux starts every packet at 64 [S28]. Each router on the way lowers it by one, and drops the packet when it reaches zero [S30]. Here there is no router between the two computers, so it stays 64. The reply carries its own TTL, set by the phone, and the phone also starts at 64. Module 4 follows a TTL across real routers.

</GoDeeper>

## Match your own capture to the fields

<InteractiveCanvas slug="net-m1-packet-own-lines" />

Tap a capture line to light its fields. The ARP request names the address it is looking for and goes to every device on the cable. In an echo line, the arrow `>` runs from source to destination. The `ttl 64` sits in the brackets on the line above the arrow. Find the same fields in your own capture from 1.4.

<GoDeeper title="Go deeper: how to read a tcpdump -n -v -e line">

Here is an echo request exactly as the lab captured it. Your times, hardware addresses and numbers will differ.

```
20:08:20.632402 a2:bb:8c:3a:32:03 > da:dc:29:fd:5e:bf, ethertype IPv4 (0x0800), length 98: (tos 0x0, ttl 64, id 12923, offset 0, flags [DF], proto ICMP (1), length 84)
    192.168.1.10 > 192.168.1.20: ICMP echo request, id 584, seq 1, length 64
```

The first line starts with the time. Then come two hardware addresses with an arrow, source first. Then `ethertype IPv4` says what kind of packet this is, and `length 98` is its size in bytes. The brackets hold details of the IP packet, among them `ttl 64`. The second line shows the two addresses, the type, `echo request`, and the ping numbers. An ARP line has no brackets. It reads like a sentence: `Request who-has 192.168.1.20 tell 192.168.1.10`.

The option `-e` is what shows the hardware addresses, and `-v` is what shows the TTL. If your capture has no `ttl`, check that you typed `-v`.

</GoDeeper>

## Change the target, see what changes

<InteractiveCanvas slug="net-m1-packet-change" />

Pick a different destination and compare. The destination address changes, and so does the destination <GlossaryTerm term="MAC address" definition="The hardware address of one network end, six pairs of letters and digits." />. The source address, the TTL and the type stay the same. The second hardware address in the picture is made up.

<GoDeeper title="Go deeper: what the picture leaves out">

The picture holds two real packets only: the ICMP echo from your lab and one DNS query. It is not a live capture. The second destination, `192.168.1.30`, and its hardware address `02:00:00:00:00:30` do not exist in your lab. They show what would change if the laptop pinged a third computer.

The pattern is the point. The source address and the TTL describe the sender, so they stay. The type says what kind of packet this is, so it stays too. The destination address says who the packet is for, so it changes. The destination hardware address changes with it, because it names the receiving end of the cable. Why a hardware address and an address both exist is the question of the next chapter.

Another thing is missing from the picture: the source hardware address stays the same here only because the same laptop sends both packets. A packet that passes a router gets new hardware addresses at each step. Chapter 1.6 shows this.

</GoDeeper>

<GoDeeper title="Sources">

[S22] RFC 826, an Ethernet Address Resolution Protocol (November 1982): a broadcast request carries the sender's addresses and the address being asked for. The owner replies directly. [S27] RFC 6335: dynamic or ephemeral ports run from 49152 to 65535. [S28] Linux kernel documentation, `ip-sysctl`: `ip_local_port_range` defaults to 32768 to 60999 and `ip_default_ttl` to 64. [S30] RFC 1812: a router must lower the TTL and drop the packet at zero. The packets shown come from the course lab's own captures, recorded on 2026-10-26.

</GoDeeper>
