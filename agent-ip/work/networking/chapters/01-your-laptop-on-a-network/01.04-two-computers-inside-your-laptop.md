Can you make a network with no cable and no Wi-Fi? Yes. You will make two small computers inside the lab. You will join them with a cable that exists only as software. Then you will send a ping from one to the other. Then you will capture the ping and look at every message that crossed the cable. This is your first working network, and it takes about the length of this chapter.

Before the commands, you need one idea. A network is at least two things that each have an address on the same wire and can send messages along it. The commands only create those parts: two computers, one wire between them, and an address on each end.

## Two computers and one cable, made of software

A real computer has its own network settings: its addresses, its cables and its routes. Linux can make a separate copy of those settings inside one machine. That copy is called a network namespace, and a program placed inside it sees only that copy. If you give each of two namespaces its own address, each one behaves like a separate computer, even though both are inside your laptop.

<BigWordAlert term="Network namespace" plainEnglish="A separate set of network settings, such as addresses and cables, inside one machine. Here each namespace plays one computer." whyItMatters="It lets you build a whole network inside your laptop, so you can break it and look at it without touching your real network." />

A <GlossaryTerm term="virtual cable" definition="Two network ends joined together in software. What goes in one end comes out of the other." /> joins them. Linux calls it a veth pair: two ends, made together. You put one end in each namespace, like plugging each end of a real cable into a different computer. In this chapter the first computer is called `laptop` and the second `phone`. They live in the lab only. The diagram shows what the commands will build.

Look at the two addresses. Both start with `192.168.1`, and both end in `/24`. For now, `/24` means: the first three numbers name the network. So `192.168.1.10` and `192.168.1.20` are on the same network, and they can talk along the cable directly. Chapter 2.2 and module 3 explain exactly how. The name `phone` is only a label we chose.

<Callout type="info" title="The lab is separate from your home">
The addresses `192.168.1.10` and `192.168.1.20` belong to the lab only. They may look like the numbers on your real home network, but they have no connection to it. Nothing you build here can change your home network.
</Callout>

These are the lines, in order. **In the lab**:

```
ip netns add laptop
ip netns add phone
ip link add veth-laptop type veth peer name veth-phone
ip link set veth-laptop netns laptop
ip link set veth-phone netns phone
ip netns exec laptop ip addr add 192.168.1.10/24 dev veth-laptop
ip netns exec phone ip addr add 192.168.1.20/24 dev veth-phone
ip netns exec laptop ip link set veth-laptop up
ip netns exec phone ip link set veth-phone up
ip netns exec laptop ip addr show dev veth-laptop
```

Read the commands as three groups. The first two make the computers. The next three make the cable and plug each end into a computer. The last group gives each end an address and switches it on. The phrase `ip netns exec laptop` means: run the command that follows inside the laptop. Without it, the command would act on the lab itself, and the laptop would stay empty.

The last command shows the laptop's end. This is what `cable.sh` printed in a recorded run. Your hardware address on the `link/ether` line will be different, because Linux picks it at random.

```
8: veth-laptop@if7: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP group default qlen 1000
    link/ether 92:84:33:2d:7d:3f brd ff:ff:ff:ff:ff:ff link-netns phone
    inet 192.168.1.10/24 scope global veth-laptop
       valid_lft forever preferred_lft forever
    inet6 fe80::9084:33ff:fe2d:7d3f/64 scope link tentative 
       valid_lft forever preferred_lft forever
```

Check two things. The word `UP` is there, so the end is switched on. The line that starts with `inet` shows `192.168.1.10/24`. Notice also the line that starts with `link/ether`. That number is the hardware address of this end of the cable. Every end of every cable has one, and it is different from the address you gave it. You will meet it again in the capture.

## The test that must pass and the test that must fail

Now ping, and see one ping succeed and one fail. **In the lab**, send two pings to the phone. The option `-c2` sends two and `-W1` waits one second for each answer:

```
ip netns exec laptop ping -c2 -W1 192.168.1.20
```

This is recorded output. You should see `2 received` and `0% packet loss`. The `ttl=64` in each line is a counter that chapter 1.5 explains.

```
PING 192.168.1.20 (192.168.1.20) 56(84) bytes of data.
64 bytes from 192.168.1.20: icmp_seq=1 ttl=64 time=0.542 ms
64 bytes from 192.168.1.20: icmp_seq=2 ttl=64 time=0.039 ms

--- 192.168.1.20 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1002ms
rtt min/avg/max/mdev = 0.039/0.290/0.542/0.251 ms
```

That is the test that must pass: the laptop reaches the phone with no packets lost. Now the test that must fail. Ping an address that nobody owns, `192.168.1.99`. A test that only passes proves little, so you also send a ping that must fail, to make sure you can tell the difference.

```
ip netns exec laptop ping -c2 -W1 192.168.1.99
```

This is also recorded. There is no error message. Nothing says "unreachable" or "no such computer". The ping simply gets no answer.

```
PING 192.168.1.99 (192.168.1.99) 56(84) bytes of data.

--- 192.168.1.99 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss, time 1029ms
```

Silence is the answer. A real network usually fails this way, without a message, and that is what makes real faults hard to find. You will meet the same silence again in chapter 3.9, when two computers disagree about the network. It will help to remember that you saw it here first.

## Before you capture: what do you expect to see?

Next you will capture the pings. A capture is a list of every message that crossed the cable, one line each. Think about what the cable must carry before you look.

You saw one fact in the output above. Every end of a cable has a hardware address, on the `link/ether` line. A message that crosses a cable is addressed to the hardware address of the end that should receive it. But the laptop only knows the phone by its address, `192.168.1.20`. It does not know the phone's hardware address. So before it can send anything, it has to find that out. It does this by asking everyone on the cable, and the owner of that address answers. The question and the answer are two messages. The laptop keeps what it learned for a while, so it does not ask again at once.

Use this to count. You will send two pings. Each ping is one message out and one message back. How many packets do you expect in the capture?

## Capture the ping

The capture runs in the background while you ping, because you have only one terminal. This is the exact step from the challenge README. **In the lab**:

```
cd /work/challenges/challenge-1-two-computers/part-1-virtual-cable
ip netns exec laptop ip neigh flush dev veth-laptop
timeout 10 ip netns exec phone tcpdump -n -v -e -i veth-phone -c 6 arp or icmp > capture.txt 2>&1 &
sleep 1
ip netns exec laptop ping -c2 -W1 192.168.1.20
wait
cat capture.txt
```

Take the lines one at a time, because each has a reason. The `ip neigh flush` line makes the laptop forget what it has learned. You pinged the phone a moment ago, so without this line the laptop would already know the phone and the question would not appear. The `tcpdump` line watches the phone's end of the cable. The option `-n` shows numbers and not names, `-v` shows more detail such as the TTL, and `-e` shows hardware addresses. The words `arp or icmp` keep only the messages that matter here. Without that filter you would also see IPv6 lines, because the lab's computers announce themselves as soon as the cable comes up. Those lines would hide the ones you want. The option `-c 6` stops after six messages, and `timeout 10` stops it after ten seconds in any case. The `sleep 1` gives `tcpdump` a second to start before the ping begins.

This is the recorded result. Your hardware addresses and times will differ, but the shape will not.

Count the packets: six, as you predicted or not. The first two are the question and the answer, called ARP. Module 3 explains them in full. The first one is sent to `ff:ff:ff:ff:ff:ff`, which means everyone on the cable. The next four are the two pings. Now read one ping line. In `192.168.1.10 > 192.168.1.20: ICMP echo request, id 45, seq 1`, the arrow shows the direction, from the sender to the receiver. The words `echo request` say this is the question and `echo reply` is the answer. The number `seq` counts the pings, so `seq 2` is the second one. The next chapter goes through every field. For now, you need only to find the lines.

## If it does not work

Try these in order. First, ask yourself: a ping reaches the other end of the cable, so does that end have an address, and is it up? Second, both ends need `ip link set ... up`. People forget one of the two. Third, look at what exists. **In the lab**, run `ip netns list`. You should see `laptop` and `phone`. Then run `ip netns exec laptop ip addr` and `ip netns exec phone ip addr`. Each should show its own address and the word `UP`.

If you want to start again, run `bash cable.sh`. It deletes what the course built before and builds the network again, so it is safe to run twice. Two other causes are common. If a command says it is not found or not allowed, check the prompt. You may be typing on your own computer and not in the lab. If the capture file is empty, the pings may have started before `tcpdump` was ready, so run the capture lines again.
