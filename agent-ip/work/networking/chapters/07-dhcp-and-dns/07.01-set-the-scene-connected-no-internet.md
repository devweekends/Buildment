## Connected, but the page says no internet

The word Connected says only that the Wi-Fi link to the router works. It says nothing about what comes after the link. The browser's "No internet" is not a diagnosis either. It only means that one request failed, and it does not say at which step.

<GoDeeper title="Go deeper: the café network in the picture">

The numbers are made up, and they stay the same through this module. The phone is `10.5.0.84`. The café router is `10.5.0.1`. It is the phone's <GlossaryTerm term="gateway" definition="The router your phone hands every packet for outside its own network." />, as in chapter 4.2, and here it is also the DNS server. The website is `203.0.113.45`, an address from a range kept for examples, so no real computer uses it [S10].

The status line is about the radio only. A phone can be Connected to a router whose cable to the provider is cut. The link works, and nothing leads out. The browser then shows its own words, such as "No internet". Those words come from the browser. They are not a measurement.

So the useful question is not "is the internet down?". It is "which step failed first?". The next picture lists the steps, in the order a page needs them.

</GoDeeper>

## Five places it can break

<MermaidDiagram title="What a web page needs, in order" chart={`flowchart TD
  A["1. An address: the phone has one"] --> B["2. A gateway that answers: the router replies"]
  B --> C["3. A route out: the router can send packets on"]
  C --> D["4. A name turned into an address: DNS answers"]
  D --> E["5. A server that replies: the website answers"]
  E --> OK["The page loads"]
`} legend="Five things, in order. If step 3 fails, steps 4 and 5 never get a chance. The first step that fails names the broken place." />

A page needs five things, in this order: an address, a gateway that answers, a route out, a name turned into an address, and a server that replies. The first one that fails names the broken place. A <GlossaryTerm term="captive portal" definition="A login page that a network shows before it lets you out." /> can stop a page even when the address, the gateway and the name steps look fine.

<GoDeeper title="Go deeper: place, what breaks, what you see">

Each place fails in its own way. The table says what the phone would show. Later chapters teach each row, and chapter 7.5 turns the table into an order of commands.

| Place | What breaks | What you see |
|---|---|---|
| 1. Address | The phone never got a lease (7.2) | No address at all. Windows and macOS give themselves a `169.254.x.x` address [S12]; the Linux client in the lab is left with none |
| 2. Gateway | The router does not answer | A ping to it gets no answer and no error message: silent loss (3.9) |
| 3. Route out | The router has no way to send packets on | The router answers Destination Net Unreachable and a request fails at once (4.8) |
| 4. Name | The DNS server is silent or gives no address | A ping to an address works, but a lookup by name times out (7.3) |
| 5. Server | The server refuses or does not answer | A closed port is refused at once (6.9); a missing return route is silent loss (4.8) |

Look at row 2 and row 5. Both can look like silence. That is why you need a command for each place, and why you read the places in order.

A captive portal is a login page that many café networks show first. In a typical portal the Wi-Fi link works and names often still resolve, but your traffic to the internet is held back until you accept its terms. This course has no measurement of portals, so this chapter says "a typical portal". Chapter 7.5 treats it as a model.
