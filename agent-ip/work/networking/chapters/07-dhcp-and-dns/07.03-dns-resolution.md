No computer knows every name on the internet. Yet your laptop finds the address of a site it has never visited. It asks one helper, a <GlossaryTerm term="resolver" definition="A server that looks up names for other computers." />, and the resolver does the work. How?

## Nobody knows every name

<MermaidDiagram title="Each level knows who is below it" chart={`flowchart TD
  R["Root: knows who runs .com"] --> C[".com servers: know who runs example.com"]
  C --> E["example.com servers: know the address of shop.example.com"]
  E --> A["Answer: 203.0.113.45"]
`} legend="Three levels below the resolver. The root does not know the address of shop.example.com. It only knows who runs .com. Each level points one step further down." />

No server holds every name. The root knows who runs `.com`. The `.com` servers know who runs `example.com`. The servers of `example.com` know the address of `shop.example.com`. Each level knows only who is below it, so a lookup walks down the tree one step at a time.

<GoDeeper title="Go deeper: reading a name, and what authoritative means">

Read a name from the right. In `shop.example.com`, the last part is `com`, then `example`, then `shop`. Each part to the left lives inside the part to its right. The tree follows the same order: the root, then `.com`, then `example.com`.

DNS servers are <GlossaryTerm term="authoritative server" definition="The server that holds the answers for its own names." /> for parts of the tree [S24]. The word means: its answer for these names is the official one. The servers of `example.com` are authoritative for `example.com`. They are not authoritative for `.com`, and they cannot tell you who runs `.org`.

The names here are stand-ins: `example.com` and `shop.example.com` stand for any site you have not visited. The address `203.0.113.45` is from a range kept for examples [S10]. In the café of 7.1, the laptop is `10.5.0.84` and its resolver is `10.5.0.1`.

The key idea of this chapter is one sentence: a server that does not know the answer knows who to ask next. Everything else follows from it.

</GoDeeper>

## The resolver walks the tree for you

<InteractiveCanvas slug="net-m7-dns-empty-cache" />

Your laptop sends one question to its resolver, `10.5.0.1`. The cache is empty, so the resolver asks the root, then `.com`, then the server of `example.com`, and then answers. That is eight messages in all. The laptop sees only the first and the last.

<GoDeeper title="Go deeper: who does the walking, and what a cache is">

A resolver asks questions on behalf of programs [S24]. The laptop's program sends one question and waits. The resolver does the walking and keeps the answer. A resolver may or may not be willing to do the walking for a client. That choice is called recursion, and a flag in the question says whether the client wants it [S24]. Your laptop does want it.

The messages are small and ride on UDP, which does not promise delivery [S26]. DNS must also work over TCP. When an answer is too big for one UDP message, the server marks it as cut short, and the client asks again over TCP [S71].

The list in the picture: 1, the laptop asks. 2 and 3, the root is asked and points to `.com`. 4 and 5, a `.com` server is asked and points to `example.com`. 6 and 7, an `example.com` server is asked and gives the address. 8, the resolver answers the laptop. The picture draws the laptop's two messages on the resolver's lane, because a sequence picture shows at most four lanes.

<InterestingRead title="A resolver is one address" hook="On 14 July 2025 Cloudflare's public resolver could not be reached. The routes to its addresses had been withdrawn." readMinutes={5}>
A device that is set to use one resolver depends on the route to that address. Cloudflare's own post-incident report says an internal configuration error withdrew the routes for the resolver's address, and that a hijack seen at the same time did not cause it [S50]. The idea matches 7.4: a name is only as reachable as the route to the server that answers for it.
</InterestingRead>

</GoDeeper>

## The second visit needs no walk

<InteractiveCanvas slug="net-m7-dns-warm-cache" />

Now the resolver already holds the answer in its cache. The laptop asks, and the resolver replies at once from memory. That is two messages, and no question to any server above. The answer, `203.0.113.45`, carries a TTL of 300: the seconds a copy may be kept.

<GoDeeper title="Go deeper: TTL, and why a cache makes DNS fast">

Every answer comes with a <GlossaryTerm term="TTL" definition="The number of seconds a copy of an answer may be kept." />. The resolver keeps its copy for that many seconds, and a TTL of zero means do not keep a copy at all [S24]. Chapter 7.4 follows what happens when the copy gets old.

Compare the two runs. With an empty cache the laptop's question causes six extra messages: three questions and three answers on the way. With a warm cache it causes none. Nothing about the laptop changes; only the resolver's memory does.

A cache is useful because many people ask for the same names. If a hundred phones in the café open the same site within one TTL, the first question walks the tree. The other ninety-nine are answered from memory.

Notice what the picture does not show: it does not count seconds. The copy is "warm" in the sense that it has not expired. How long that lasts is the subject of the next chapter.

</GoDeeper>

## Who knows what? Sort the answers

<InteractiveCanvas slug="net-m7-sort-who-answers" />

Drop each question on the server that can answer it. The root answers who runs a top-level name such as `.com`. A top-level server answers who runs a name under it. Only the <GlossaryTerm term="authoritative server" definition="The server that holds the answers for its own names." /> holds the address itself. A wrong try says why.

<GoDeeper title="Go deeper: the three kinds of server, side by side">

| Server | It knows | It does not know |
|---|---|---|
| Root | Who runs each top-level name, such as `.com` and `.org` | Who runs `example.com`, or any address |
| Top-level (`.com`) | Who runs each name under it, such as `example.com` | The address of `shop.example.com` |
| Authoritative (`example.com`) | The addresses of its own names | Who runs `.com`, or the names of other sites |

If you can fill the table from memory, you have the idea of delegation: each server hands the question to the next level down, and only the last one answers it.

Two cards in the game ask about `.org` and `example.org`. They have the same shape as the `.com` cards, with another top-level name. The tree has many top-level servers, and the root knows who runs each of them. The game uses only the names in this chapter.

</GoDeeper>

## A, AAAA and CNAME records

<MermaidDiagram title="Three kinds of record" chart={`flowchart LR
  N["shop.example.com"] -->|"A record"| V4["203.0.113.45, an IPv4 address"]
  N -->|"AAAA record"| V6["2001:db8::45, an IPv6 address"]
  W["www.shop.example.com"] -->|"CNAME record"| N
`} legend="An A record gives an IPv4 address. An AAAA record gives an IPv6 address. A CNAME record says that one name is another name, so the lookup continues with that name." />

Each fact that a DNS server holds is a <GlossaryTerm term="record" definition="One fact that a DNS server knows." />. An A record gives a name's IPv4 address, here `203.0.113.45`. An AAAA record gives its IPv6 address, here `2001:db8::45`. A CNAME record says that one name is another name: you look up that name instead [S77] [S78].

<GoDeeper title="Go deeper: the records, one by one">

An IPv4 address is 32 bits [S1]. An IPv6 address is 128 bits [S2]. The A record holds the first kind and the AAAA record holds the second, so one name can have both.

The IPv6 address `2001:db8::45` comes from the block `2001:db8::/32`, which is reserved for examples [S69]. Module 9 reads IPv6 addresses in detail.

A CNAME record has no address of its own. It points to another name. If the laptop asks for `www.shop.example.com` and the answer is "CNAME `shop.example.com`", the resolver looks up `shop.example.com` the same way, and the A record of that name gives the address. A site owner uses a CNAME to say that two names lead to the same place without writing the address twice.

A record is the unit of DNS. Each record has a name, a type (A, AAAA, CNAME and others), a value and a TTL. The type tells you how to read the value. The TTL tells the resolver how long it may keep a copy, as in the previous beat.

</GoDeeper>

## dig +trace walks the tree itself

<MermaidDiagram title="What dig +trace does" chart={`flowchart LR
  D["dig +trace"] -->|"1. asks"| R["Root"]
  R -->|"points to .com"| D
  D -->|"2. asks"| T[".com server"]
  T -->|"points to example.com"| D
  D -->|"3. asks"| A["example.com server"]
  A -->|"203.0.113.45"| D
`} legend="dig +trace does the resolver's walk by itself and shows each answer. A laptop never does this: it asks its resolver." />

The tool `dig` can do the resolver's walk by itself. With `+trace`, it asks the root first and follows each answer down. A laptop never does this. It asks its resolver and waits. The lab cannot run `dig +trace`: on Docker Desktop it got no answer within 40 seconds (dossier 5.6).

<GoDeeper title="Go deeper: when to use dig +trace, and why not in the lab">

`dig +trace` is a tool for people who want to see the walk. It shows who answered at each level, so it helps when a name does not resolve and you want to know at which level the chain breaks. It does not show what your laptop does. Your laptop asks its resolver, and the resolver does the walk.

The command would look like this. Run it on your own computer, if it has `dig`, and never in the lab:

```
dig +trace shop.example.com
```

The lab test found that this command gets no answer within 40 seconds on Docker Desktop (dossier 5.6). So the course does not use `dig +trace` as a lab step. What you saw in the picture above stands in for it.

In the lab, `dig` has two other uses that do work, and challenge 5 uses both. Ask one server directly with `dig @192.168.1.1 web.test`. Ask with the resolver file of the computer, in the way a program would, with `curl`. 7.6 builds both and explains which asks whom.

</GoDeeper>

<GoDeeper title="Sources">

[S1] RFC 791: an IPv4 address is 32 bits. [S2] RFC 8200: an IPv6 address is 128 bits. [S10] RFC 5737: documentation addresses such as `203.0.113.45`. [S24] RFC 1034: resolvers ask on behalf of programs, servers are authoritative for parts of the tree, recursion is optional, and the TTL is a number of seconds that limits caching, with zero meaning do not cache. [S26] RFC 768: UDP gives no delivery guarantee. [S50] Cloudflare's report on its public resolver incident of 14 July 2025. [S69] RFC 3849: `2001:db8::/32` is reserved for IPv6 examples. [S71] RFC 7766: DNS must work over UDP and TCP, and a cut-short UDP answer makes the client retry over TCP. [S77] RFC 1035: type A is a host address, CNAME is the canonical name for an alias, and servers answer on port 53. [S78] RFC 3596: an AAAA record stores one IPv6 address.

</GoDeeper>
