In 11.4 the internet router answered `Destination Net Unreachable` for `10.20.0.5`. In this chapter you make the same ping work. You build a WireGuard tunnel from the café laptop to the VPN box in the office, so your private packet travels inside a public one. Then you watch the tunnel from both ends, and you check by capture everything 11.2 and 11.3 claimed: the café sees only UDP, the office sees the ping, an 84-byte ping becomes 156 bytes, and a packet from the wrong source is thrown away.

This is challenge 8, parts 2 and 3. Both are **gapped**. The scripts are almost complete. Part 2 has four small gaps and part 3 has three, each marked `TODO`, and each test names the gap that is wrong. Part 1's test must pass first, because part 2 starts by running your `office-cafe.sh`.

The tunnel has its own small network, `10.99.0.0/24`. The laptop's end of the tunnel is `10.99.0.2` and the VPN box's end is `10.99.0.1`. It is a third private range, different from the office and the café, for the reason in 11.1. Follow one ping down the picture before you open the script. Every gap below is one box of it.

## Part 2, Gaps 1 and 2: keys and the laptop's end

**In the lab**, go to the folder and open the script:

```
cd /work/challenges/challenge-8-vpn/part-2-the-tunnel
```

**Gap 1** makes two key pairs, one for the VPN box and one for the laptop, in `/tmp/networking-course-wg`. The comment gives the shape from 11.3: `wg genkey | tee PRIVATE_FILE | wg pubkey > PUBLIC_FILE`, once for each side, with the file names it lists. The keys live in `/tmp` so that they never land in your repository. Never commit a private key.

**Gap 2** sets up the laptop's end. You do not start from nothing: the office end, on the VPN box, is given in step 4 of the script, and Gap 2 is its mirror.

```
in_ns vpnbox ip link add wg0 type wireguard
in_ns vpnbox wg set wg0 private-key "$KEYS/vpnbox.key" listen-port 51820 \
  peer "$(cat "$KEYS/laptop.pub")" allowed-ips 10.99.0.2/32
```

Read it as 11.3 taught. The VPN box uses its own private key and listens on 51820, the port the office router forwards. Its one peer is the laptop's **public** key. Its AllowedIPs for that peer is `10.99.0.2/32`: packets to `10.99.0.2` go to the laptop, and the laptop may send from `10.99.0.2` only. The VPN box has no endpoint for the laptop. It will learn one from the laptop's first packet.

Your line for the laptop needs five things: the laptop's private key file, listen port 51820, the VPN box's public key as the peer, an endpoint, and AllowedIPs. The endpoint is where the outer packets go: the office router's public address and the forwarded port, `203.0.113.2:51820`. The AllowedIPs are the inner addresses that should go to the VPN box: the office network `10.20.0.0/24` and the VPN box's own tunnel address `10.99.0.1/32`, with a comma between them and no space.

## Part 2, Gaps 3 and 4: the two routes

AllowedIPs picks the peer once a packet is in `wg0`, but it does not put the packet there. 11.3 ended on this. So the laptop needs a route.

**Gap 3**, on the laptop: send `10.20.0.0/24` into `wg0`. The shape is `ip route add NETWORK dev INTERFACE`, inside the laptop. Without it, `ip netns exec laptop ip route get 10.20.0.5` names `via 192.168.50.1`, the café router, and the ping dies at the internet router as in part 1. The helper `wg-quick` would add this route for you; here you add it by hand to see it.

**Gap 4** is on the other end, and it is the one people forget. The office server gets a ping whose source is `10.99.0.2`. It must answer that address.

```predict
prompt: "Gap 4 is empty. The office server, 10.20.0.5, gets a ping from 10.99.0.2 through the VPN box. The server's only routes are its own network and a default route via the office router, 10.20.0.1. Where does it send the answer?"
options:
  - id: router
    label: "To the office router, its default"
  - id: vpnbox
    label: "To the VPN box, which passed it in"
correctOptionId: router
explanation: "To the office router. A computer answers by its routing table, not by remembering who handed it the packet. 10.99.0.2 matches only the default route, so the answer goes to the office router, which sends it out to the internet, where it is lost."
allowRetry: true
```

So the server needs a route to the tunnel network through the VPN box: `10.99.0.0/24` via `10.20.0.2`. The shape is `ip route add NETWORK via ADDRESS`, inside the office server. Here is a clue that this gap is the one missing: the laptop can ping `10.99.0.1` without Gap 4, because the VPN box itself knows the tunnel network. Only the ping to `10.20.0.5` fails.

```
PING 10.99.0.1 (10.99.0.1) 56(84) bytes of data.

```

Before the tunnel, the same wall as in 11.1. With the tunnel, `10.20.0.5` answers, and the office test page arrives. Look at `ttl=63`. The server starts its answer at 64, as every Linux machine in this course does, and one machine lowered it: the VPN box, which passed the answer into the tunnel. The routers on the internet lowered only the TTL of the outer packet. They never saw the inner one.

The script then saves `wg show` from both ends in `wg-show.txt`. On the VPN box, the laptop's entry reads:

```
peer: 9vxbHy8OFTSseJbNOaHtBbods1HcOYIMZDDONqatdRo=
  endpoint: 198.51.100.2:51820
  allowed ips: 10.99.0.2/32
  latest handshake: 1 second ago
```

You never typed `198.51.100.2:51820`. The VPN box learned it from the laptop's first checked packet: the café's public address after masquerade. That is why the café needs no port forward. The laptop starts the conversation, and the café router's NAT row carries the answers back.

<Callout type="warning" title="Gotcha: who starts the conversation">
The café router forgets a quiet conversation after a while, as every NAT does (6.5). That is fine while the laptop starts things. But if the office wants to reach the laptop first, after a quiet time, its packet hits the café router and no row is waiting. The fix is `PersistentKeepalive`, on the side behind NAT: the laptop sends a tiny packet at a fixed interval, shorter than the NAT timeout, to keep its row alive. It is off by default, and WireGuard's quickstart suggests 25 seconds. It matters only when the other side starts the conversation. Part 3 has an optional extra where you watch it work.
</Callout>

## The false source

The last step of `tunnel.sh` tests the second job of AllowedIPs. The laptop gets a second tunnel address, `10.99.0.66`, and pings the server from it. The laptop sends it, because `10.20.0.5` is in the laptop's AllowedIPs for the VPN box. The VPN box unlocks it, checks the source against its own list for this peer, `10.99.0.2/32`, and drops it. The recorded run:

```
--- one packet from 10.99.0.66, a source the VPN box does not allow
PING 10.20.0.5 (10.20.0.5) from 10.99.0.66 : 56(84) bytes of data.

--- 10.20.0.5 ping statistics ---
1 packets transmitted, 0 received, 100% packet loss, time 0ms

(no answer)
VPN box wg0 receive errors: before 0, after 1
```

The drop counts as one receive error on the VPN box's `wg0`. And `spoof-capture.txt`, a capture on that `wg0` during the ping, says `0 packets captured`: the packet was thrown away before it reached `wg0`. A peer can speak only from its own addresses.

## Part 3: what each side sees

Part 3 builds nothing new. You only look. Its script starts by running your part 2.

```
cd ../part-3-what-each-side-sees
```

**Gap 1** captures every IPv4 packet on the café router's outside plug, `veth-cafe-out`, for six seconds, while the laptop pings `10.20.0.5` three times and fetches the office page. Use the filter `ip`, not a port: you want to see that nothing else is there. **Gap 2** captures pings on the VPN box's `wg0`. **Gap 3** is the sum from 11.2: round 84 up to a multiple of 16, then add 32, 8 and 20. Then run `bash captures.sh`. This is the café's view from the recorded run, shortened:

```

16:16:32.566143 IP 198.51.100.2.51820 > 203.0.113.2.51820: UDP, length 128
16:16:32.566335 IP 203.0.113.2.51820 > 198.51.100.2.51820: UDP, length 128

16:16:34.631465 IP 203.0.113.2.51820 > 198.51.100.2.51820: UDP, length 304
```

Sixteen packets, all UDP between port 51820 on two public addresses, both ways. No ICMP, no TCP, and no `10.20.0.5` anywhere. What the café sees is the outer addresses, the ports, the sizes and the timing. It does not see the inner destination or what you sent. The six packets of `length 128`, one pair per second, still have the shape of three pings.

The office's view, `wg0.txt`, shows the same ping plain:

```
16:16:38.604418 IP 10.99.0.2 > 10.20.0.5: ICMP echo request, id 879, seq 1, length 64
16:16:38.604475 IP 10.20.0.5 > 10.99.0.2: ICMP echo reply, id 879, seq 1, length 64
```

And the size check:

```
inner 84, padded 96, outer 156
tcpdump: listening on veth-cafe-out, link-type EN10MB (Ethernet), snapshot length 262144 bytes
16:16:40.725329 IP (tos 0x0, ttl 63, id 12214, offset 0, flags [none], proto UDP (17), length 156)
```

`length 156` is the whole outer packet, and `UDP, length 128` is the cargo, exactly as 11.2 worked out. If your sum is 144, you forgot the padding, and the test tells you so.

One more look, by hand. Capture the café router's **inside** plug, `veth-cafe-in`, during a ping. The recorded run showed:

```
16:16:50.073435 IP 192.168.50.23.51820 > 203.0.113.2.51820: UDP, length 128
16:16:50.073837 IP 203.0.113.2.51820 > 192.168.50.23.51820: UDP, length 128
```

That is the laptop's own address, before masquerade, and still only UDP. The tunnel starts on the laptop itself, so even someone on the café Wi-Fi sees only the outer packet.

## If it does not work

No `latest handshake` in `wg show`? Check the endpoint and both public keys: the laptop's peer must be the VPN box's **public** key. Ping says `sendmsg: Required key not available`? The packet went into `wg0`, but no peer has that address in its AllowedIPs: look at Gap 2. `10.99.0.1` answers but `10.20.0.5` does not? That is Gap 4, or forwarding is off on the VPN box: `ip netns exec vpnbox sysctl net.ipv4.ip_forward`. Not sure where a packet goes? `ip netns exec laptop ip route get 10.20.0.5`. Not sure the outer packets leave? `ip netns exec caferouter tcpdump -n -i veth-cafe-out udp port 51820`.
