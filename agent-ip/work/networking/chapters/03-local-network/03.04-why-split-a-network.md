In this fictional school, 100 staff laptops, one exam server, and 499 guest phones share one network. A guest phone can reach the exam server, so the school needs a different arrangement.

## 600 devices, one network

<InteractiveCanvas slug="net-m3-scene-flat-school" />

The scene groups the staff, guests, and exam server on one shared network, then shows a guest reaching the server. Those groups have different jobs, but their names alone create no separation. A phone carrying unwanted traffic has the same path in this simplified picture. The school needs a boundary where it can decide which traffic is allowed to cross.

<GoDeeper title="Go deeper: 600 devices, one network">

This is a fictional design problem, not a report about a real school or an attack demonstration. Reaching the exam server means the model permits traffic to arrive there. It does not mean a login succeeds or data is stolen. Keep that difference clear when explaining the risk.

The school has three reasons to split. First, one address block can serve several networks. RFC 950 describes that use of subnetting. [S7] Second, separating groups provides places to contain faults and apply access rules. Third, a local broadcast need reach fewer devices. The last two reasons are design reasoning shown by the following controlled comparison.

The counts stay constant while the arrangement changes. That lets you see whether the result came from fewer devices or from a boundary. We do not remove guests to make the comparison look better.

</GoDeeper>

## Every broadcast reaches every device

<InteractiveCanvas slug="net-m3-flat-broadcast" />

Press Next to send one staff laptop's ARP broadcast across the flat network, and read the recipient count. The sender is one of the 100 staff devices, leaving 99 staff, 499 guests, and the exam server to hear it. That makes 599 other devices in total. Every recipient hears the question, although only the address owner should answer it. [S22]

<GoDeeper title="Go deeper: every broadcast reaches every device">

The table counts end devices, not switch ports or the sender. In a flat network, 99 + 499 + 1 equals 599 recipients. The picture uses group cards because drawing 600 separate icons would hide the comparison. Each card's count is part of the model, not a measurement of a real school.

An ARP request uses destination MAC ff:ff:ff:ff:ff:ff. [D5.8] Forwarding that request to the other devices is expected behaviour. It does not mean each device sends a reply, and it does not mean every frame on this network is broadcast.

In the next arrangement, each group has a separate local link and a router joins the networks. The shown staff broadcast stays on its own link. You can therefore count recipients using only the staff group. This is the boundary rule the next prediction applies; the router's internal routing decisions wait until module 4.

</GoDeeper>

## Three networks joined by a router

<InteractiveCanvas slug="net-m3-split-broadcast" />

Step through the same staff request after the groups move onto separate links joined by a router. The staff count rises to 99 recipients, while the guest and exam counts remain zero. The router box joins networks without extending this local ARP broadcast into each one. That reduces the reach of this request while preserving a place for traffic between groups.

<GoDeeper title="Go deeper: three networks joined by a router">

The flat and split pictures use exactly the same end-device counts. Only their local-link arrangement changes. The split request has 99 recipients rather than 599, a reduction of 500 for this one broadcast. This is arithmetic about the model; it is not a prediction of bandwidth or application speed.

A fault that produces local broadcast traffic is now limited to fewer end devices in the picture. That is a useful containment boundary, but it is not a promise that all possible faults stop there. Traffic that the router carries between networks needs a separate decision.

The compact canvas groups some devices with their switches to fit the phone screen. Each labelled link is separate. You can restart the steps to compare the counts again. It is a scripted comparison rather than a live network that lets you drag cables or add hosts.

</GoDeeper>

## Splitting alone does not keep guests out

<InteractiveCanvas slug="net-m3-split-filter" />

Follow a guest packet first with the rule absent, then with the labelled rule enabled at the router. The first packet reaches the exam server; the second stops at the rule. A filter rule is a stated decision to allow or drop matching traffic. The split creates a place to apply that decision, but the rule itself supplies the access restriction.

<GoDeeper title="Go deeper: splitting alone does not keep guests out">

The rule here has one narrow purpose: drop traffic from guests to the exam server. It does not claim to inspect every possible threat, protect the server's software, or decide all other traffic. The model assumes routes between these groups exist. With no blocking rule, the guest packet follows that available path.

You have already seen this distinction in the dossier's environment tests. A router using address translation alone allowed a connection when a route was added. A separate forwarding drop rule blocked guest-to-home traffic. [D5.6] The present picture uses the same separation between a path and an access decision, without teaching translation here.

The canvas advances between two preset rule states. Its pick asks you to apply the rule you just saw; it does not provide a free-form firewall editor. Compare the destination before and after the change. A smaller broadcast group and a blocked application path are two different results.

</GoDeeper>

## One block can serve several networks

<MermaidDiagram title="A block supports separate school networks" chart={`flowchart TD
 P["One /22 address block"] --> G["Guest network: /23"]
 P --> S["Staff network: /25"]
 P --> E["Exam network: /30"]
 P --> F["Remaining addresses kept free"]`} legend="Illustrative sizes for 499 guests, 100 staff, and one exam server; the next chapter teaches the cuts." />

The picture cuts one address block into separate networks while keeping some space free. A subnet is one smaller network carved from a larger block, and each piece has its own boundary. [S7] Different group sizes can use different pieces instead of treating every group alike. Chapter 3.5 shows how to choose these sizes and place them without wasting a boundary.

<GoDeeper title="Go deeper: one block can serve several networks">

The /22 parent contains 1,024 total addresses. A /23 supplies 510 ordinary host addresses, enough for the 499 guest devices in this example. A /25 supplies 126, enough for the 100 staff devices. A /30 supplies two, enough for the exam server and a router connection in this simplified design. These are arithmetic examples, not the growth policy for the later school planning lab.

The diagram deliberately keeps the leftover space visible. Splitting does not require consuming the whole parent immediately. Unused space can support a later group if the required block fits on an aligned boundary. The next chapter teaches that check rather than asking you to guess a start address now.

Sources: [S7] RFC 950, dossier 4.2, one block across several networks. [S22] RFC 826, dossier 4.5, ARP requests and replies. [D5.6] and [D5.8] are the supplied environment tests. The school counts and the comparisons are a fictional model.

</GoDeeper>
