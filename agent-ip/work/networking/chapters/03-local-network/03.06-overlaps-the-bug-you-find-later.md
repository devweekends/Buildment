On the course's test machine, Docker's default bridge used `172.17.0.0/16`. A container at `172.17.0.3` then shares address space with an office using `172.17.5.0/24`, even though the written prefixes differ.

## The office range sits inside Docker's

<MermaidDiagram title="An office block nested in a container block" chart={`flowchart TD

The outer box includes every address from `172.17.0.0` through `172.17.255.255`, so the office's entire /24 fits inside it. An overlap means two allocated ranges share at least one address, even when their starts differ. The separate labels describe intended uses, but they do not make the underlying numbers separate. Check the ranges before trying to join those networks.

<GoDeeper title="Go deeper: the office range sits inside Docker's">

The Docker range here is an observation from the course's test machine, not a promise about every installation. Its bridge inspection showed 172.17.0.0/16. You can inspect your own bridge with this command. Your output will show your own subnet.

```text
docker network inspect bridge
```

Docker's documentation describes default address pools that start at 172.17.0.0/16, cover 172.17 through 172.31 and 192.168.0.0/16, and can be changed in its settings. It does not say which pool your particular bridge receives. [S46] Copy the actual subnet when comparing it with home, office, and VPN ranges.

For a container using the shown /16, applying its own mask to an office destination in 172.17.5.0/24 produces the local network result. That explains the conflicting local view. It does not establish the exact packet outcome for every host and VPN configuration.

</GoDeeper>

## Ranges on one number line

<InteractiveCanvas slug="net-m3-overlap-line" />

Drag a range along the number line and compare its first and last addresses with the other range. The larger example runs from 2,886,795,264 to 2,886,860,799, while the office range lies between those endpoints. Looking at complete intervals exposes the overlap immediately. Matching text prefixes is unnecessary because each IPv4 address already represents one number, as module 2 taught.

<GoDeeper title="Go deeper: ranges on one number line">

The office's 172.17.5.0/24 runs from 2,886,796,544 to 2,886,796,799. Both endpoints are inside the outer /16. The numbers come from multiplying the four bytes by their place values, then adding. You can use the address conversion helper from module 2 to check them.

For any two inclusive intervals, an overlap exists when the first start is at most the second end and the second start is at most the first end. Both comparisons are needed. A shared endpoint counts as a shared address; an end immediately followed by another start does not.

The line is a picture of address space. Moving a range changes the proposed allocation in the model. It does not change Docker, a router, or a running VPN. Keep that distinction when using it to explore a future plan.

</GoDeeper>

## Valid blocks nest or stay apart

<InteractiveCanvas slug="net-m3-overlap-nest" />

Move the second valid CIDR block and watch the overlap highlight appear only when one block contains the other. Aligned CIDR blocks cannot partly cross like two arbitrary intervals of equal length. Either their leading fixed bits disagree and they stay apart, or the shorter prefix contains the longer one. Identical blocks also overlap, because every address belongs to both.

<GoDeeper title="Go deeper: valid blocks nest or stay apart">

Consider a /16 and a /24. The /24 fixes eight more leading bits. If its first sixteen bits match the /16, all its addresses lie in that /16. If they differ, none do. The same reasoning works for any two valid, aligned CIDR blocks.

That nesting property gives the calculator in 3.8 a simple check. Normalise each CIDR to its network start. Then see whether one block contains the other's start. Check both directions, because either block may be the larger one. Identical starts count as overlap too.

Adjacent /25 blocks are a useful near miss. 192.168.1.0/25 ends at .127, and 192.168.1.128/25 starts at .128. They have no shared address. Saying they touch on the drawing must not turn into saying their inclusive numeric ranges overlap.

</GoDeeper>

## An overlap shows up late

<InteractiveCanvas slug="net-m3-scene-late-overlap" />

Watch the two networks work separately, then become connected by a VPN, a link used here to join distant networks. Both sides claim the same local range when they need to communicate. Reusing private numbers was harmless while the networks were separate; joining them exposes the conflict. The scene shows that change in requirements without pretending to calculate which path every packet takes.

<GoDeeper title="Go deeper: an overlap shows up late">

Private address space can be reused where global uniqueness is not required. [S8] That makes it useful for independent homes and offices. The benefit becomes a planning constraint when those independently chosen ranges must meet. A home and an office can both choose 192.168.1.0/24 without either noticing the other beforehand.

Before joining networks, collect the ranges from every side that will participate: home, office, containers, the VPN, and cloud networks. Record network starts and prefix lengths, not only a sample device address. A device at 192.168.1.23 might belong to a /24 or to a wider range.

The scene does not model routing priority, packet loss, or a VPN product's repair options. An overlap check identifies a conflict in the plan. It does not replace investigation of the configured routes. Module 4 opens that next layer after this module establishes the arithmetic.

</GoDeeper>

## Overlapping cloud blocks prevent this peering

<MermaidDiagram title="A cloud peering restriction" chart={`flowchart TD
 A["AWS VPC: 10.40.0.0/16"] --> X["Matching or overlapping CIDRs"]
 B["AWS VPC: 10.40.8.0/24"] --> X
 X --> N["Peering is not allowed"]`} legend="This is the AWS VPC rule, not a rule claimed for every cloud service." />

The diagram shows a specific cloud restriction: AWS does not allow VPC peering when the networks have matching or overlapping CIDR blocks. [S47] A VPC is the cloud network in this example, and peering would connect two such networks. Check the intended ranges before requesting that connection. Choosing different names for the networks does not remove an overlap in their addresses.

<GoDeeper title="Go deeper: overlapping cloud blocks prevent this peering">

The /24 in the picture sits inside the /16. Giving the two networks separate labels or accounts does not change that containment. The provider's peering restriction therefore catches a conflict that numeric comparison could have found during planning. [S47]

Do not reverse the claim. Non-overlapping ranges remove this particular obstacle, but they are not a guarantee that a peering request meets every other requirement. This chapter teaches the overlap test and the stated restriction only.

For a plan you control, reserve distinct ranges before connecting the networks. If existing allocations overlap, record which ones need revision and check the replacement against the complete list. Replacing one conflict with another is easy when you inspect only two rows at a time.

Sources: [S8] RFC 1918: private ranges can be reused. [S46] Docker documentation: default address pools. [S47] AWS documentation: no VPC peering between matching or overlapping CIDR blocks. The bridge range 172.17.0.0/16 was observed on the course's test machine on 2026-10-24. Numeric intervals are derived arithmetic.

</GoDeeper>
