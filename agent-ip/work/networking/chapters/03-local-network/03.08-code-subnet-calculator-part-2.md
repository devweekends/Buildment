In 3.5 you cut a `/24` into three pieces by hand. In 3.6 you compared ranges on a number line to find an overlap. Both jobs follow fixed rules, so a program can do them. That matters for two reasons. A plan done by code can be run again in one second when the needs change, as they will in 3.12. And a program does not get tired, so it finds the one overlap hidden in a list of twenty ranges that your eyes would skip.

In this chapter you write the two functions that finish the calculator: `splitBlock` and `overlaps`. Part 1 gave you the arithmetic for one block. Part 2 uses it for many blocks at once. You will need the address helpers again, and the exercise gives them to you.

## Five steps, always in this order

Splitting is not one clever trick. It is five small steps, and the order matters. Look at the picture before you read the reasons.

<MermaidDiagram title="How splitBlock decides" chart={`flowchart TD
  A["Host counts, any order"] --> B["Sort: largest block first"]
  B --> C["Size: smallest block that holds the count"]
  C --> D["Align: round the next free address up to a multiple of the block size"]
  D --> E["Place: record the block, move the free address to its end plus one"]
  E --> F["Check: still inside the parent?"]
  F -->|"yes, next block"| C
  F -->|"no"| G["Throw RangeError"]`} legend="The loop repeats size, align, place and check for each block. Sorting happens once, at the start." />

Why sort first? A big block has the fewest legal starts. A `/26` can start only at four places in a `/24`. A `/29` can start at thirty-two places. If you place the small blocks first, they can sit in the way of the big one, and the big one then has nowhere to go. Placing the big blocks first leaves the small blocks to fill the gaps.

Why check after every block, and not once at the end? Because you want to stop at the first block that does not fit and say which one it was. A message such as "does not fit: 50 hosts" tells the caller what to change.

## Sizing one block

A block must hold the devices and the two reserved addresses, the first and the last, as you saw in 3.2. So the rule is: find the smallest prefix `p` where 2 to the power of (32 minus `p`), minus 2, is at least the host count. Start with the smallest block you may use, `/30`, and move to bigger blocks until one fits.

A worked example for counts that are not in the tests. A clinic has 45 devices. A `/27` holds 32 addresses, which is 30 usable, so it is too small. A `/26` holds 64 addresses, which is 62 usable, so it fits. The answer is `/26`. Now a clinic printer room with 3 devices. A `/30` holds 4 addresses, which is 2 usable, so it is too small. A `/29` holds 8 addresses, which is 6 usable. The answer is `/29`.

Why does the loop stop at `/30`? A `/31` has two addresses and is meant for a point-to-point link [S70]. A `/32` is a single address. Neither is a network for ordinary devices. So even one device gets a `/30`. This is the same rule you used in 3.5, and the tests check it with counts of 1 and 2.

If no prefix works, the count is too big for the whole address space, and the function throws a <GlossaryTerm term="RangeError" definition="A JavaScript error type that says a value is outside the range that is allowed." />. The same error type covers a count of 0, a negative count, a count with a fraction, and a count that is not a number. All of these are values outside the allowed range.

## Aligning and placing

After sizing, each block needs a start. Keep one number, the next free address, and set it to the parent's first address at the beginning. For each block, round that number up to the nearest multiple of the block size. If it is already a multiple, it stays. Then the block runs from that start to the start plus its size minus 1, and the next free address becomes the start plus its size.

Here is a worked example with a parent you have not seen: `172.20.9.0/24` and the counts 12, 60, 5 and 12. The sizes are `/28` (16 addresses), `/26` (64), `/29` (8) and `/28` again. Sorted largest first they are 64, 16, 16 and 8. The `/26` takes `172.20.9.0` to `172.20.9.63`. The next free address is `.64`, which is a multiple of 16, so the first `/28` runs from `.64` to `.79`. The second `/28` runs from `.80` to `.95`. The next free address is `.96`, which is a multiple of 8, so the `/29` runs from `.96` to `.103`. Nothing needed rounding, and no address is wasted.

That is not luck. When the sizes only get smaller, each size divides the sizes before it, so the next free address is always already a multiple. The rounding step is still in the code, because it is the rule, and it matters when something breaks the order. Suppose you placed the `/29` first. It would take `.0` to `.7`, and the next free address would be `.8`. A `/26` cannot start at `.8`. It must wait for `.64`, and the 56 addresses between are lost. That is the cost of placing the small block first.

## The parent must be a real block

`splitBlock` throws a `RangeError` if the parent has host bits set, such as `192.168.10.5/24`. In 3.7 you did the opposite: `network("192.168.1.23/24")` quietly gave `192.168.1.0`. The two cases are different. In 3.7 the caller held a device address and asked which block it belongs to. Here the caller hands you the space to give out. A start with host bits set is probably a typing mistake, and a plan built from the wrong start is wrong in every line. Refusing is safer than guessing.

A parent that is not written correctly at all, such as `192.168.10.0/33`, is a different kind of failure. It throws an `Error` whose message starts with `invalid`, the same rule as in 3.7. Your 3.7 `network` and `contains` already know how to find that out, or you can reuse their parsing.

## Finding overlaps

For `overlaps`, you have the rule from 3.6: valid blocks either nest or stay apart. So two blocks overlap when one contains the other's first address. Normalise each block first, so that `10.1.2.3/16` is treated as `10.1.0.0/16`. Then test both directions. The first block may be the bigger one, or the second may be.

Compare every pair, with the earlier entry first. For four blocks that is six pairs. Each pair appears once, and the pair keeps the order of the input list. Return the strings the caller gave you, not the normalised ones, so the caller can find them in their own list.

Two edge cases decide whether your code is right. Identical blocks overlap, because every address belongs to both. Blocks that only touch do not overlap. `192.168.1.0/25` ends at `.127` and `192.168.1.128/25` starts at `.128`, so they share nothing. If your code says they overlap, check whether you wrote "at most" where you meant "less than", or the other way round.

## The contract

`splitBlock(parent, hostCounts)` takes a CIDR string and a list of host counts. It returns a list of objects in placement order. Each object has two fields: `hosts`, the count the caller asked for, and `cidr`, the block you gave it, for example `{ hosts: 100, cidr: "192.168.10.0/25" }`. Largest blocks come first. Two blocks of the same size keep the order of the input list. This is about block size, not host count: the counts 40 and 50 both need a `/26`, so 40 stays before 50 if the caller listed it first. An empty list gives an empty result. The list the caller passed in must not be changed, so sort a copy.

`overlaps(cidrs)` takes a list of CIDR strings and returns a list of pairs. Each pair is `[earlier, later]`, and no pair appears twice. No overlap gives an empty list.

  function ipToNumber(ip) {
    if (typeof ip !== "string") throw new Error("invalid address: expected text");
    const parts = ip.split(".");
    if (parts.length !== 4) throw new Error("invalid address: need four parts");
    let value = 0;
    for (const part of parts) {
      if (!/^(0|[1-9][0-9]{0,2})$/.test(part) || Number(part) > 255)
        throw new Error("invalid address: bad part");
      value = value * 256 + Number(part);
    }
    return value;
  }
  function numberToIp(n) {
    if (!Number.isInteger(n) || n < 0 || n > 4294967295)
      throw new Error("invalid address number");
    return [n >>> 24, (n >>> 16) & 255, (n >>> 8) & 255, n & 255].join(".");
  }
  function subnet(cidr) {
    if (typeof cidr !== "string") throw new Error("invalid CIDR: expected text");
    const parts = cidr.split("/");
    if (parts.length !== 2 || !/^(0|[1-9][0-9]?)$/.test(parts[1]))
      throw new Error("invalid prefix");
    const prefix = Number(parts[1]);
    if (prefix > 32) throw new Error("invalid prefix");
    const ip = ipToNumber(parts[0]);
    const mask = prefix === 0 ? 0 : (0xffffffff << (32 - prefix)) >>> 0;
    const start = (ip & mask) >>> 0;
    const end = (start | ~mask) >>> 0;
    return { ip, prefix, start, end, size: 2 ** (32 - prefix) };
  }

  function splitBlock(parent, hostCounts) {
    const block = subnet(parent);
    if (block.ip !== block.start) throw new RangeError("parent has host bits set: " + parent);
    if (!Array.isArray(hostCounts)) throw new RangeError("hostCounts must be a list");
    const needs = hostCounts.map((hosts, index) => {
      if (!Number.isInteger(hosts) || hosts < 1)
        throw new RangeError("a host count must be a positive whole number: " + hosts);
      let prefix = -1;
      for (let p = 30; p >= 0; p--) {
        if (2 ** (32 - p) - 2 >= hosts) { prefix = p; break; }
      }
      if (prefix === -1) throw new RangeError("no block holds " + hosts + " hosts");
      return { hosts, prefix, size: 2 ** (32 - prefix), index };
    });
    needs.sort((a, b) => b.size - a.size || a.index - b.index);
    let next = block.start;
    const placed = [];
    for (const need of needs) {
      const start = Math.ceil(next / need.size) * need.size;
      if (start + need.size - 1 > block.end)
        throw new RangeError("does not fit: " + need.hosts + " hosts");
      placed.push({ hosts: need.hosts, cidr: numberToIp(start) + "/" + need.prefix });
      next = start + need.size;
    }
    return placed;
  }

  function overlaps(cidrs) {
    if (!Array.isArray(cidrs)) throw new Error("invalid list: expected an array");
    const blocks = cidrs.map(subnet);
    const pairs = [];
    for (let i = 0; i < blocks.length; i++) {
      for (let j = i + 1; j < blocks.length; j++) {
        const a = blocks[i];
        const b = blocks[j];
        const aHasB = a.start <= b.start && b.start <= a.end;
        const bHasA = b.start <= a.start && a.start <= b.end;
        if (aHasB || bHasA) pairs.push([cidrs[i], cidrs[j]]);
      }
    }
    return pairs;
  }

## When a test fails

Read the message first. It names the input and shows what your code returned. Then match it to the likely cause.

If the first test fails and the blocks come out in the order of the input, you forgot to sort, or you sorted by host count when you should sort by block size. If the blocks are in the right order but some starts are wrong, look at the rounding step. The start of a block must be a multiple of its own size.

If the edge-size test fails at a count such as 126 or 127, you probably forgot the two reserved addresses. A `/25` holds 128 addresses but only 126 devices. The number 127 needs a `/24`. If it fails at a count of 1, the loop is allowed to choose `/31` or `/32`, and it should stop at `/30`.

If the test about the input list fails, your sort changed the list the caller passed in. The method `sort` changes the array it is called on. Copy the list first. If the test about equal sizes fails, check that your comparison falls back to the input position when two sizes are equal.

If an overlap test fails on touching blocks, print the last address of the first block and the first address of the second. They are different numbers, so a correct comparison says "no". If the nested test fails, you probably tested only one direction.

After three failed attempts, the last hint shows a small helper from 3.7 that turns a CIDR into a first and a last number. It is there so that a parsing problem does not stop you from learning the splitting. Use it, and then try to replace it with your own 3.7 code.
