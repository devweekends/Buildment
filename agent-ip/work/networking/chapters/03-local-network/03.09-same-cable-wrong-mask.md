In 3.1 you saw that your mask changed when you changed Wi-Fi. Each network told your laptop its own mask. So here is a question the first chapters could not answer. What happens if two computers on the same cable are given two different masks? Nobody would do that on purpose. It can happen by accident, for example when someone types a mask by hand or copies a setting from another network.

In this chapter you cause that mistake on purpose, in the lab, where it can hurt nothing. You will see two failures that look very different. One computer stops at once with an error message. The other waits and says nothing. Learning to read the difference between an error at once and silence is a real skill. It tells you which computer to look at first.

## Each computer decides alone

You learned in 3.2 that a computer asks one question before it sends anything: is the destination on my own network? It answers by applying its own mask to the destination and comparing the result with its own network. Nothing in that question asks the other computer. There is no vote. So two computers on one cable can give two different answers about the same pair of addresses.

Here is a worked example with numbers that are not in the lab. A computer has the address `10.0.0.37` and the mask `/28`. The mask keeps the first 28 bits. The last number, 37, is `00100101` in bits, and the mask byte is `11110000`. The AND keeps the first four bits, which gives `00100000`, or 32. So this computer's network runs from `10.0.0.32` to `10.0.0.47`. Now ask it about `10.0.0.50`. That number is above 47, so the computer answers: not local.

When a computer decides that a destination is not local, it does not send the packet to the neighbour directly. It looks for a <BigWordAlert term="Route" plainEnglish="A rule that says where to send a packet for a given destination." whyItMatters="When a computer has no route for an address, it cannot send to it, and the error message says so: Network is unreachable." /> that covers the destination. Normally that route points to a <GlossaryTerm term="gateway" definition="The router a computer sends to when the destination is not on its own network." />, and module 4 builds one. In this lab there is no router at all. So when a computer decides that a destination is not local, it has no route, and it has nowhere to send the packet.

The picture shows the two views side by side. In this lab the laptop will have `192.168.1.10/24` and the phone will have `192.168.1.20/28`. The names are only labels, as in 1.4.

## The silent side: the laptop pings the phone

Now ping from the laptop, the computer with `/24`. **In the lab**:

```
ip netns exec laptop ping -c2 -W1 192.168.1.20
```

You will wait a second or two, and then the last lines will say `2 packets transmitted, 0 received, 100% packet loss`. There is no error message. Nothing says "unreachable". This is the same silence you saw in 1.4 when you pinged `192.168.1.99`. The laptop followed its own rule. Its mask says `192.168.1.20` is a neighbour, so it sent the ping toward the phone and then waited for an answer that never came. The likely reason is the mirror image of the next section: by its own `/28` mask, the phone has no route back to `192.168.1.10`. We did not record the phone's side of this step, so treat that as the likely reason and look at your capture.

The capture will show what crossed the cable. You make it in a moment. First look at the other side.

## The loud side: the phone pings the laptop

Now ping the other way, from the phone, the computer with `/28`. **In the lab**:

```
ip netns exec phone ping -c2 -W1 192.168.1.10
```

You do not wait this time. The answer comes at once, on one line:

```
ping: connect: Network is unreachable
```

This is the line from the recorded run, and it is your own computer talking. The phone applied its `/28` mask to `192.168.1.10`, found that the address is outside `192.168.1.16` to `192.168.1.31`, and looked for a route. It had none. The words "Network is unreachable" are the operating system's way of saying: I have no route for that address. The computer gave up before it sent anything, so there was nothing to wait for.

Notice the strange part. The two computers share one cable. Their addresses differ only in the last number. Yet one says "unreachable" and the other just waits. The cable is fine. Both ends are up. The only thing wrong is a number after a slash, and that number lives in each computer, not on the cable. You can look for the problem forever with the cable and find nothing.

If you want to ask the phone directly which route it would use for the laptop, run `ip netns exec phone ip route get 192.168.1.10`. The command is documented [S32]. We did not record what it prints for this case, so read the answer with the idea of a route in mind, and do not wait for a particular line.

## An address nobody owns, with a capture

Last, ping an address that no one has: `192.168.1.99`. You did this in 1.4 and saw silence. Now you can explain it. With a `/24` mask the laptop thinks `192.168.1.99` is a neighbour, so it asks who has that address. No one answers, because no one owns it. Pings follow the same silent path as before.

This time capture it. The capture runs in the background on the phone's end of the cable, and it records ARP messages only. **In the lab**:

```
cd /work/challenges/challenge-1-two-computers/part-2-wrong-mask
timeout 8 ip netns exec phone tcpdump -n -e -i veth-phone arp > capture.txt 2>&1 &
sleep 1
ip netns exec laptop ping -c2 -W1 192.168.1.20
ip netns exec laptop ping -c2 -W1 192.168.1.99
wait
cat capture.txt
```

The `sleep 1` gives the capture a second to start. The `timeout 8` stops it after eight seconds. This is the recorded result of the second ping, to the address nobody owns. There is a header line, an empty line, and then the statistics, with no error line at all:

```
PING 192.168.1.99 (192.168.1.99) 56(84) bytes of data.

--- 192.168.1.99 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss, time 1029ms
```

Your times will differ. In your capture, look for lines that ask who has `192.168.1.99` and say that the sender is `192.168.1.10`. They have the same shape as the request line you saw in 1.4, with a different address. You should see more than one request and no reply line for `.99`. A request that nobody answers is what "an address nobody owns" looks like on the wire.

Also look at the lines for `192.168.1.20`. The laptop's request for the phone is on the cable, and in our test run the phone's capture showed it. Whether a reply line follows is something this course did not record. Your capture is the evidence. Write down what you see in `results.md`.

Some guides say a failed ping prints "Destination Host Unreachable". With these options we did not see that line, so do not wait for it. You will see silence.

## Test, fix and save

Run the test **in the lab**:

```
bash test.sh
```

This is the recorded result. The first half checks the failures. The second half applies the fix, both masks `/24`, and checks that the pings work:

```
--- masks disagree: laptop /24, phone /28
PASS laptop to 192.168.1.20: silent loss (2 sent, 0 received)
PASS phone to 192.168.1.10: Network is unreachable
PASS laptop to 192.168.1.99: silent loss (2 sent, 0 received)
PASS the ARP request for 192.168.1.99 goes unanswered
--- the fix: both /24
PASS laptop to 192.168.1.20: 0% loss
PASS phone to 192.168.1.10: 0% loss
RESULT: all checks passed
```

Look at what passed. Four of these `PASS` lines are about failures, as they should be. A test can pass because something failed, when the failure is the expected result. Then the fix makes both pings work, with 0% loss in each direction. One number changed. That shows the masks were the whole problem.

## If it does not work

Try these in order. First, compare the masks. **In the lab**, run `ip netns exec laptop ip addr` and `ip netns exec phone ip addr`. You should see `/24` on one and `/28` on the other. If both say `/24`, the pings will work and nothing fails, so run `bash wrong-mask.sh` again. If an old network is still in the way, run `bash ../part-1-virtual-cable/cable.sh` first. It deletes what the course built before and builds the network again, so it is safe to run twice. Then run `wrong-mask.sh`. Second, ask which address each side treats as its network. For `/28` the last number must be between 16 and 31. Third, if a command says it is not found or not allowed, check the prompt. You may be typing on your own computer, not in the lab. Fourth, if `capture.txt` is empty, the pings started before the capture was ready. Run the capture lines again.
