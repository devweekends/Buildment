A friend runs a test on their home connection and sends you the result. One line says that hop 1, their own router, loses 20% of the packets. "The router is broken," they say. "I will buy a new one." Should they? A report that shows loss at one hop is not always a report of a broken hop. By the end of this chapter you can tell the two cases apart in a few seconds.

**mtr answers one question: at which hop does loss start, and does it go on to the end?** It combines traceroute and ping [S110]. Like traceroute in 4.4, it finds each router on the path with probes whose TTL starts at 1. Unlike traceroute, it keeps going. It sends probe after probe to every hop and counts how many come back. In 12.1, three probes per hop were too few to catch one loss in ten. mtr sends fifty.

mtr is already in the lab. On your own computer:

| Computer | How to get it | Command |
|---|---|---|
| Linux (Ubuntu) | the `mtr-tiny` package: 3 packages, about 0.2 MiB [S141] | `mtr -rn -c 50 example.com` |
| macOS | Homebrew, if you use it | `sudo mtr -rn -c 50 example.com` |
| Windows | no mtr: `pathping` is built in, or WinMTR | `pathping -n example.com` |

On Ubuntu, take `mtr-tiny`, not `mtr`. The plain `mtr` package pulls in a window system, 108 packages and about 36 MiB [S141]. `mtr-tiny` has the same `-r`, `-n` and `-z` options [S110]. The course has not tested the macOS and Windows commands, so treat them as options to try, not as promises.

## Three commands

All of these run **in the lab**, with the round 1 faults planted.

**Command one: the report.** `-r` prints one report at the end instead of a live screen. `-n` prints addresses, not names. `-c 50` sends 50 probes to each hop [S110]. `-i 0.2` waits 0.2 seconds between rounds, so the run takes about ten seconds. An interval below one second needs root, and in the lab you are root.

```
cd /work/challenges/challenge-9-toolbox/part-3-mtr
ip netns exec laptop mtr -rn -c 50 -i 0.2 203.0.113.80
```

This is the recorded report:

```
Start: 2026-10-27T16:26:23+0000
HOST: 9acde94c9099                Loss%   Snt   Last   Avg  Best  Wrst StDev
  1.|-- 192.0.2.1                  0.0%    50    0.1   0.1   0.1   0.2   0.0
  2.|-- 198.51.100.2              10.0%    50    0.1   0.1   0.1   0.2   0.0
  3.|-- 203.0.113.80              10.0%    50    0.2   0.2   0.2   0.4   0.1
```

Hop 1 shows `0.0%`. Hops 2 and 3 both show `10.0%`. The loss starts at hop 2 and goes on to the last hop, as you may have predicted. So the lossy cable is the one that leads to hop 2: from r1 to r2.

**Command two: find the cause.** Fault 1 lives in the queue of a router's interface. Linux's `tc` tool shows each queue. A queue of the kind called netem can add loss, delay or a speed limit on purpose, to the packets that leave that interface [S152]. Look at the two routers at the ends of cable 2:

```
ip netns exec r1 tc qdisc show
ip netns exec r2 tc qdisc show dev veth-r2wan
```

```
qdisc noqueue 0: dev lo root refcnt 2
qdisc noqueue 0: dev veth-r1lan root refcnt 2
qdisc netem 802b: dev veth-r1wan root refcnt 21 limit 1000 loss 10%
```

```
qdisc noqueue 0: root refcnt 2
```

r1's interface toward r2, `veth-r1wan`, has `netem ... loss 10%`. r2's end of the cable has a normal queue. Remove r1's netem queue, and fault 1 is gone. The command prints nothing:

```
ip netns exec r1 tc qdisc del dev veth-r1wan root
```

**Command three: a router that limits itself.** The lab's build script switched off one setting in both routers, so that your first report would be clean. Linux limits how often it sends some kinds of ICMP message to the same computer. The setting is `net.ipv4.icmp_ratelimit`: the shortest gap between two such replies, in milliseconds. Its default is 1000, and 0 switches the limit off [S151]. The run below shows that "time exceeded" is one of the limited kinds. Switch r1's limit back on, and run the same report:

```
ip netns exec r1 sysctl -w net.ipv4.icmp_ratelimit=1000
ip netns exec laptop mtr -rn -c 50 -i 0.2 203.0.113.80
```

```
net.ipv4.icmp_ratelimit = 1000
```

```
Start: 2026-10-27T16:26:43+0000
HOST: 9acde94c9099                Loss%   Snt   Last   Avg  Best  Wrst StDev
  1.|-- 192.0.2.1                 70.0%    50    0.1   0.1   0.1   0.5   0.1
  2.|-- 198.51.100.2               0.0%    50    0.1   0.1   0.1   0.2   0.0
  3.|-- 203.0.113.80               0.0%    50    0.3   0.3   0.2   0.5   0.1
```

Hop 1 now loses `70.0%`. Hops 2 and 3 lose nothing. Every probe for hop 3 passed through r1, so r1 forwarded all of them. It only stopped answering most of the probes that were meant for itself. Switch the limit off again, and run the report a last time:

```
ip netns exec r1 sysctl -w net.ipv4.icmp_ratelimit=0
ip netns exec laptop mtr -rn -c 50 -i 0.2 203.0.113.80
```

```
net.ipv4.icmp_ratelimit = 0
```

```
Start: 2026-10-27T16:27:13+0000
HOST: 9acde94c9099                Loss%   Snt   Last   Avg  Best  Wrst StDev
  1.|-- 192.0.2.1                  0.0%    50    0.1   0.1   0.0   0.2   0.0
  2.|-- 198.51.100.2               0.0%    50    0.1   0.1   0.1   0.2   0.0
  3.|-- 203.0.113.80               0.0%    50    0.3   0.2   0.2   0.4   0.0
```

A clean report: `0.0%` at every hop.

## How to read the report

Each row is one hop. Three columns matter most.

| Column | Meaning |
|---|---|
| `Loss%` | The share of probes to that hop with no answer |
| `Snt` | How many probes went to that hop: your `-c` |
| `Avg` | The average time for an answer, in milliseconds. `Last`, `Best`, `Wrst` and `StDev` are the latest, the best, the worst and how much the times jump |

Then read the rows together, from the top. **Real loss goes on.** If a hop shows loss and every hop after it shows loss too, down to the last hop, packets are lost on the cable just before the first lossy hop. **Loss at one hop only is not your traffic.** If a hop shows loss but the hops after it show `0.0%`, that router is slow to answer probes about itself, while it forwards traffic well. The last hop is the one that matters most: it is your real destination, and its loss is the loss your traffic feels.

Now answer your friend. Hop 1 shows 20%, but what does the last hop show? If the last hop is clean, their router is limiting its own replies, and it is not broken.

## The trap: loss that is not loss

The mtr manual warns about this itself: some routers give lower priority to ICMP echo, the kind of probe mtr sends unless you ask for TCP or UDP, so the reported loss can look worse than it really is [S110]. On a real path through the internet you will see it often. A hop in the middle shows 30% or 60% loss, and the last hop shows 0%. That is almost always a router protecting itself.

A second, smaller trap is in the recorded run too. With r1's limit at 1000 and mtr's normal pace of one round each second, ten probes showed no loss at all:

```
ip netns exec laptop mtr -rn -c 10 203.0.113.80
```

```
Start: 2026-10-27T16:26:58+0000
HOST: 9acde94c9099                Loss%   Snt   Last   Avg  Best  Wrst StDev
  1.|-- 192.0.2.1                  0.0%    10    0.1   0.1   0.1   0.1   0.0
  2.|-- 198.51.100.2               0.0%    10    0.2   0.1   0.1   0.2   0.1
  3.|-- 203.0.113.80               0.0%    10    0.3   0.3   0.2   0.3   0.1
```

The limit allows a small burst of replies before it starts to refuse. Ten probes, one each second, fit inside it. So a short, slow test can hide the limit, and a fast one can show it. That is why the challenge uses `-i 0.2`. Neither changes the rule: read the last hop.

<GoDeeper title="Go deeper: why routers limit their replies, and what mtr cannot see">

A router's main job is to forward packets. Answering probes is extra work for its own processor, and anyone on the internet can ask a router for replies. So routers protect themselves. Linux does it with `icmp_ratelimit`: with 1000, a router leaves at least 1000 milliseconds between such replies to one computer [S151], so roughly one per second. The recorded runs show a small burst first, which is why ten slow probes all got answers. Other routers have their own rules, and some give these probes a lower priority than real traffic [S110]. The forwarding path does not change. Your web page, your file copy and your video call cross the router at full speed while it ignores most of mtr's questions about itself.

mtr's `Loss%` for a hop is a count of answers, so there are two ways to lose one. The probe can be lost on the way to the hop, or the answer can be lost on the way back. mtr cannot tell which. If the hops after a lossy cable show loss, either direction can be the lossy one. In this lab you found the cause with `tc qdisc show`, on r1's way out: netem acts on outgoing packets [S152], so the probes toward r2 and the server were lost, and the answers coming back were not. On the real internet you cannot look inside other people's routers. You can only show a report, with the first lossy hop and the last hop, to someone who can.

Two more options are worth knowing. `-z` prints the AS number, the number of the network that the address belongs to, beside each hop [S110]. If you took module 10, run it on your own computer to see where your path crosses from one network into another. It does not work in the lab, because the lab's real path to the internet is hidden. And `-T` and `-u` send TCP or UDP probes instead of the usual ones [S110]. Some networks treat those differently, so a second report with another kind of probe is a good check before you blame a hop.

</GoDeeper>

In `faults.md`, under **Fault 1**, write four lines: the tool, the exact command, the one output line that proves the loss, and the command that fixed it. Keep each line inside backticks, as the template shows. Here is an example entry. It is not a file from the recorded run: it is put together from the recorded command, report row and fix above. Yours has your own numbers:

```
### Fault 1

- Tool: mtr
- Command: `ip netns exec laptop mtr -rn -c 50 -i 0.2 203.0.113.80`
- Output line: `  2.|-- 198.51.100.2              10.0%    50    0.1   0.1   0.1   0.2   0.0`
- Fix: `ip netns exec r1 tc qdisc del dev veth-r1wan root`
```

The test checks patterns, never an exact percentage. Your report with the fault must show no loss at hop 1 and loss at hops 2 and 3. Your "limiting itself" report must show loss at hop 1 and none at the last hop. Your last report must be clean. Your Fault 1 line must be an mtr row of hop 2 or hop 3 with some loss. A row of hop 1 fails, with a reason you now understand: loss at one hop only can be the router limiting itself. Last, the test looks at r1's queue and checks that the loss is gone. Commit `results.md` and `faults.md`.

If your first report shows loss at hop 1 too, r1's limit was on when you ran it. Switch it off with `icmp_ratelimit=0` and run the report again. If your later report still shows loss at hops 2 and 3, you ran `bash faults.sh` again after the fix, which plants every fault again. Remove the queue once more.
