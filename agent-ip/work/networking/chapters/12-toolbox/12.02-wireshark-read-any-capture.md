Look back at the capture from 1.4. Six packets already filled more than ten lines of dense text, and you had to find the ARP lines by eye. A real capture holds hundreds of packets. Reading it line by line is slow, and it is easy to miss the one packet that matters. Is there a better way to read the same packets?

There is. **Wireshark answers one question: what is inside each packet of a capture file?** It shows the same packets as tcpdump, but as a list you can click, filter and follow. Each packet opens layer by layer, and each value has a name. You capture in the lab with tcpdump, as before. Then you read the file on your own computer, in Wireshark.

## If you came here from module 1

This first section stands alone. You can do it right after 1.5, before the rest of this module. It is not graded.

Wireshark is a free program for your own computer, for Windows, macOS and Linux [S139]. It opens a capture and shows each packet as a row you can click, with every layer of the packet named. The download is about 93 MiB for Windows and about 140 MiB for macOS [S146], so wait for Wi-Fi if your data is limited. The next section, **Install Wireshark on your computer**, has the details.

In 1.4 you saved the capture as text, with `> capture.txt`. Wireshark cannot read that text. It reads a <GlossaryTerm term="capture file" definition="A file that holds the captured packets themselves, not a printout of them. tcpdump writes one with -w, and Wireshark opens it." />, which tcpdump writes when you give it `-w` and a file name [S130]. So capture the 1.4 ping once more, into a file. These lines are not in the 1.4 README: they are the 1.4 capture step, changed to write a file. **In the lab**, in the 1.4 folder:

```
cd /work/challenges/challenge-1-two-computers/part-1-virtual-cable
bash cable.sh
ip netns exec laptop ip neigh flush dev veth-laptop
timeout 10 ip netns exec phone tcpdump -n -i veth-phone -c 6 -w capture.pcap arp or icmp &
sleep 1
ip netns exec laptop ping -c2 -W1 192.168.1.20
wait
```

Compared with 1.4, three things changed. `bash cable.sh` builds the 1.4 network again first. `-w capture.pcap` takes the place of `> capture.txt 2>&1`. And `-v` and `-e` are gone, because they only change what tcpdump prints, and with `-w` it prints no packets: it writes them into the file and stops after six, so the file is complete [S130]. One warning: `cable.sh` deletes every network the course built before. If you have already started challenge 9, run `bash faults.sh` in its part 0 folder again afterwards. The lab's `/work` folder is your repository folder, so the file is now on your own computer too, in `challenges/challenge-1-two-computers/part-1-virtual-cable/`. Install Wireshark, and open `capture.pcap` from that folder. You should see the six packets you counted in 1.4: an ARP question, an ARP answer and two pings, each a request and a reply. Click one ping packet and open its layers one at a time: the Ethernet layer with the two hardware addresses, the IP layer with the TTL of 64, and the ICMP layer with `seq`. These are the fields you tapped in 1.5. You do not need to commit this file.

One rule matters before you open the file: **the capture must be finished**. With `-w`, tcpdump normally keeps packets in a buffer and writes them to the file when the buffer fills [S153]. If you open a file while tcpdump is still writing, Wireshark may say the file is cut short. A capture is finished when tcpdump stops: after its count with `-c`, after Ctrl-C, or after a clean stop like the one `make-capture.sh` does. The option `-U` makes tcpdump write each packet to the file as it is saved [S153], so an early look is less empty. Wait until the script prints `capture.pcap is ready`.

## Three things to do in Wireshark

Open `challenges/challenge-9-toolbox/part-1-wireshark/capture.pcap` from your repository folder. The Wireshark guide covers opening saved files [S126]. You see a list with one row per packet. Below it are the layers of the packet you clicked. Menu names can differ a little between versions.

**First, filter.** Type a <GlossaryTerm term="display filter" definition="Wireshark's own filter, typed in the bar at the top. It hides packets from view. It names fields, such as ip.dst." /> in the bar at the top and press Enter [S128]. These are the filters the challenge uses:

```
ip.src == 192.0.2.10
ip.dst == 203.0.113.80
tcp.flags.syn == 1
ip.src == 192.0.2.10 && tcp.flags.syn == 1
```

The first keeps packets from the laptop. The second keeps packets to the server. The third keeps packets with the SYN flag, the first packet of each TCP handshake from 5.4. The fourth joins two filters with `&&`, so only packets that match both stay.

**Second, read one field.** Click a packet from `203.0.113.80` and open its **Internet Protocol** layer. Find the TTL. Click the field, and Wireshark shows its name, `ip.ttl`, at the bottom of the window. Every field has such a name, and the name is what you type in a display filter.

**Third, follow a conversation.** Click one web packet, then choose **Analyze**, **Follow**, **TCP Stream** [S126]. The challenge README also offers a right-click on the packet, then **Follow**; the menu names were not tested on every version. Wireshark joins the data of that one conversation in order, as text. What the laptop sent is in red, and what the server sent is in blue. Wireshark also puts a display filter for that stream in the bar, so the list now holds only that conversation.

## How to read it: three values

The challenge asks for three values. In the recorded run they were these.

The **source port of the first web connection** is in the first packet from `192.0.2.10` with the SYN flag. In the excerpt it is `192.0.2.10.48452 > 203.0.113.80.80: Flags [S]`, so the port is 48452. In Wireshark it is in the **Transmission Control Protocol** layer, as `tcp.srcport`. The script chose it from your seed with `curl --local-port`. Without that option, Linux picks a port at random.

The **TTL of the server's packets as they reach the laptop** is in the IP layer of any packet from `203.0.113.80`. Before you look, use what 4.4 taught: each router takes one off the TTL [S30].

## The trap: two kinds of filter

Wireshark and tcpdump both filter, and their filters look alike. They are two different languages. A <GlossaryTerm term="capture filter" definition="tcpdump's filter, at the end of its command. It decides which packets are saved at all. It uses words like host and port." /> uses the libpcap language, and it decides what is recorded at all: what it leaves out is never saved [S126]. A display filter uses Wireshark's own language, and it only hides packets that are already in the file. The Wireshark wiki warns about exactly this mix-up: `tcp port 80` is a capture filter, and `tcp.port == 80` is a display filter [S127].

So `host 203.0.113.80` belongs at the end of a tcpdump command, and `ip.addr == 203.0.113.80` belongs in Wireshark's bar. A display filter names a field with a dot, such as `ip.dst`, and compares it with `==`. The part 1 test checks this. For each value, it reads the filter you wrote in `results.md`. A filter that names no field, such as `host 203.0.113.80`, fails: words like `host` and `port` on their own belong to capture filters.

<GoDeeper title="Go deeper: why two languages, and which one to use when">

The two filters work at different moments. A capture filter runs while packets arrive. The packets it rejects are never written, so a capture with a tight filter is small, and you cannot get the other packets back later. That is why chapter 12.3 uses capture filters: to keep a long capture small. A display filter runs on a file you already have. It changes nothing in the file. Clear the bar, and every packet is back.

The languages differ because the tools differ. The capture language is short, with words such as `host`, `net` and `port` [S131]. Wireshark understands many protocols, so its display language names fields inside them: `ip.ttl`, `tcp.srcport`, `tcp.flags.syn`. You can compare a field with a value, and join two tests with `&&`. The guide's own examples include `ip.addr==192.168.0.1` [S128].

Wireshark can also capture by itself, from your own computer's Wi-Fi or cable. Its capture dialog then takes a capture filter in the libpcap language, the same words as tcpdump [S126]. In this course the lab captures, because the lab network lives only inside the lab. Wireshark reads.

Two notes for later. tshark is the text version of Wireshark, for a terminal. It reads a file with `-r`, and it takes a capture filter with `-f` and a display filter with `-Y` [S129]. The two letters keep the two languages apart. And capturing may need special rights on a computer, while reading a saved file does not [S130]. That is why you can open the lab's file on your own computer without any special setup.

</GoDeeper>
