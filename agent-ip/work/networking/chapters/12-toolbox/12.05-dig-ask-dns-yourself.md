You type the address of a course site on your phone. On mobile data it loads. You walk into the campus, the phone joins the Wi-Fi, and the same name gives an error. Your friend's laptop on the same Wi-Fi fails too. The name did not change, and the site did not move. What changed?

The network did, and with it the resolver. In 7.3 you saw that your device does not look names up by itself. It asks a resolver, and the network you join tells your device which one to ask. On mobile data your phone asks the mobile provider's resolver. On the campus Wi-Fi it asks the campus resolver. If those two give different answers for one name, one of them is wrong, and only the network that uses it breaks.

**dig answers one question: what does this resolver say this name means?** Its manual calls it a flexible tool for asking DNS name servers questions [S132]. You choose the name, the kind of record and the server to ask, and dig prints the whole answer, not only the address. dig is already in the lab. On your own computer:

| Computer | How to get it | Commands |
|---|---|---|
| Linux (Ubuntu) | the `bind9-dnsutils` package: 17 packages, about 13.5 MiB [S141] | `dig example.com`, `dig @1.1.1.1 example.com`, `dig +trace example.com` |
| macOS | not checked by the course | the same commands as Linux |
| Windows | not built in | `Resolve-DnsName example.com` and `Resolve-DnsName example.com -Server 1.1.1.1` in PowerShell, or use the lab |

`1.1.1.1` is a real public resolver on the internet. The Windows commands were not tested by the course, so treat them as an option to try.

**Command three: follow a name from the root.** `+trace` does what a resolver does when its cache is empty. It starts at the root servers and follows each step down to the answer, asking each server in turn [S132]. The lab's names exist only in the lab, so trace a real name. Run this **in the lab itself, not in the laptop**, because the laptop cannot reach the internet. This is an excerpt of the recorded run:

```
dig +trace @1.1.1.1 example.com
```

```
; <<>> DiG 9.18.39-0ubuntu0.24.04.8-Ubuntu <<>> +trace @1.1.1.1 example.com
; (1 server found)
;; global options: +cmd
.			510899	IN	NS	a.root-servers.net.
.			510899	IN	NS	b.root-servers.net.
.			510899	IN	NS	c.root-servers.net.
;; Received 525 bytes from 1.1.1.1#53(1.1.1.1) in 24 ms

com.			172800	IN	NS	b.gtld-servers.net.
com.			172800	IN	NS	c.gtld-servers.net.
;; Received 1171 bytes from 192.5.5.241#53(f.root-servers.net) in 32 ms

;; Received 506 bytes from 192.33.14.30#53(b.gtld-servers.net) in 172 ms

example.com.		300	IN	A	104.20.23.154
example.com.		300	IN	A	172.66.147.243
```

Read it from the top, as 7.3 drew it. `1.1.1.1` told dig the names of the root servers. One root server, `f.root-servers.net`, sent dig on to the servers for `com.`. One of those, `b.gtld-servers.net`, sent it on to the servers for `example.com`, and the last step gave the two addresses. Each `Received` line says who answered that step. The lines in between are cut.

## How to read a dig answer

Most of dig's output is detail. Three parts matter.

| Part | Example | Meaning |
|---|---|---|
| ANSWER SECTION | `docs.lab.test. 0 IN A 203.0.113.153` | The name, the TTL in seconds, `IN` for internet, the record type `A`, and the IPv4 address. The dot at the end of the name is the root |
| `SERVER:` line | `SERVER: 192.0.2.1#53(192.0.2.1) (UDP)` | Which server really answered, on port 53, over UDP |
| `flags:` line | `qr aa rd ra` | `rd`: the question asked the server to find the answer for you. `ra`: the server offers to do that [S24]. The other two flags do not matter here |

Look at the TTL in the lab's answers: `0`. In 7.4 you met the DNS TTL: the number of seconds a copy of an answer may be kept. Zero means do not keep it at all [S24]. So every question in this lab goes to the resolver again, and when you fix the fault, the right answer arrives at once. A real wrong answer often has a TTL of minutes or hours, and then a computer keeps the wrong copy until its TTL runs out.

`status: NOERROR` near the top means the server reports no error. A wrong answer is still `NOERROR`. dig cannot know which address is true. Only you can, by comparing with what should be true.

## The trap: asking a different resolver than your computer does

`dig @1.1.1.1 name` asks `1.1.1.1`, and only `1.1.1.1`. Your browser asks the resolver in your computer's settings. So a good answer from `dig @` proves that one resolver is right. It does not prove that your computer gets the right answer. When you test a name for someone, run two commands: one with no `@`, which shows what their computer really gets, and one with `@` and a second resolver, to compare. That pair is what found fault 2.

The lab adds a smaller trap of its own. Without `@1.1.1.1`, `+trace` fails in the lab. This is a separate recorded run:

```
dig +trace example.com
```

```
; <<>> DiG 9.18.39-0ubuntu0.24.04.8-Ubuntu <<>> +trace example.com
;; global options: +cmd
;; Received 17 bytes from 192.168.65.7#53(192.168.65.7) in 2590 ms
```

No root servers, no steps. The lab asked its own resolver, `192.168.65.7`, which it gets from Docker Desktop, and that resolver gave dig only 17 bytes and no list of root servers. With `@1.1.1.1`, dig gets the list from a real resolver and can start. On your own Linux or macOS computer, the README suggests plain `dig +trace example.com`. If that fails too, add `@1.1.1.1`.

<GoDeeper title="Go deeper: who fixes a wrong answer, and what +trace really shows">

In the lab you fix fault 2 the way a user can: you tell the laptop to ask another resolver.

```
echo nameserver 203.0.113.53 > /etc/netns/laptop/resolv.conf
ip netns exec laptop dig +short docs.lab.test; ip netns exec laptop curl -sS -m 5 http://docs.lab.test/
```

```
203.0.113.80
lab web server
```

The right address, and the page loads: `lab web server`. But the wrong line is still in the campus resolver. Every other laptop on the campus still gets `203.0.113.153`. The real fix belongs to the owner of that resolver. In real life you tell the campus IT team, and show them your two dig answers as evidence: the name, the two resolvers, and the two addresses. That is a report they can act on in minutes. "The site does not work on the Wi-Fi" is not.

Now `+trace` again. A normal question to a resolver asks it to do all the work: it asks the root, then the servers for the ending, then the servers for the name, and gives you only the result. With `+trace`, dig does that work itself, one step at a time, and prints each step [S132]. That is useful when you suspect that a resolver gives an old or wrong answer: the trace asks the servers that own the name, so it shows what they say now. It is also why `+trace` needs to reach many servers on the internet, and why it fails where only one resolver can be reached.

The excerpt leaves out many lines: the other root servers, the other servers for `com.`, and the RRSIG and DS lines. The `510899` and `172800` beside the root and `com.` lines are TTLs too: those lists of servers may be kept for days.

Two more options are worth knowing. `+noall +answer` prints only the answer lines, which is handy when you compare two resolvers [S132]. The gate uses it. And `-x ADDRESS` asks the other way round: which name belongs to this address [S132].

</GoDeeper>
