Imagine you capture for ten minutes on a busy laptop. The browser, the mail app and updates all talk at once. The file holds 80,000 packets, and you need the forty that are DNS questions. In Wireshark you could hide the rest with a display filter. But the file is already huge, slow to copy and hard to share, and every packet in it is saved, whatever it carries. Is there a way to keep only what you need?

**tcpdump answers one question: which packets cross this cable, and only the ones I ask for?** You met it in 1.4. This chapter adds the part that makes it useful on a real network: a capture filter at the end of the command, so that tcpdump keeps only the packets that match. tcpdump is already in the lab. On Ubuntu its package is about 1.2 MiB to download [S141], so it is small enough for any computer you manage.

## The filter words

A capture filter is a short sentence in the libpcap language [S131]. It has a few words, and you join them with `and`, `or` and `not`:

| Words | Keeps packets | Example |
|---|---|---|
| `host ADDRESS` | to or from one address | `host 203.0.113.80` |
| `net RANGE` | to or from any address in a range | `net 203.0.113.0/24` |
| `port N` | to or from one port, on UDP or TCP | `port 53` |
| `src` or `dst` before a word | only one direction | `src host 192.0.2.10` |
| `tcp`, `udp`, `icmp`, `arp` | one kind of packet | `arp or icmp`, as in 1.4 |

The filter always goes **last**, after every option. These are the options this chapter uses [S130]:

| Option | What it does |
|---|---|
| `-i NAME` | Capture on this interface, one end of a cable |
| `-n`, `-nn` | Print addresses and ports as numbers, not names. In the lab's tcpdump `-n` already does both; the challenge types `-nn` |
| `-c N` | Stop after N packets. The file is then complete |
| `-w FILE` | Write the packets to a file, and print none of them |
| `-r FILE` | Read packets from a file, not from a cable. The same filters work |
| `-v` | Print more detail, such as the TTL |

`-U` is one more: with `-w`, it makes tcpdump write each packet to the file as it is saved. Without it, tcpdump writes only when its buffer fills [S153], so a file you open too early can look empty.

## How to read a tcpdump line

Every line follows the same shape. Take this one from `dns-only.pcap`:

```
16:25:45.067394 IP 192.0.2.10.44469 > 192.0.2.1.53: 41492+ [1au] A? www.lab.test. (53)
```

| Part | Meaning |
|---|---|
| `16:25:45.067394` | The time, to the millionth of a second |
| `IP` | An IPv4 packet |
| `192.0.2.10.44469` | From the laptop, source port 44469. The last number after the address is the port |
| `> 192.0.2.1.53` | To the campus resolver, port 53 |
| `41492+` | The question's number. The answer to it carries the same number |
| `A? www.lab.test.` | A question: what is the IPv4 address, the A record, of this name? |

Now find the answer to that question. It is further down: `192.0.2.1.53 > 192.0.2.10.44469: 41492* 1/0/1 A 203.0.113.80`. The ports are swapped, the number is the same, and the answer is `A 203.0.113.80`. Matching a question to its answer by that number is how you read DNS in any capture. It also shows something a quick look misses: here the answer came about two seconds after the question, while other questions were answered within a millisecond.

In `public-net.pcap`, the first line is the campus resolver's own question, from `198.51.100.1`, and the second is its answer. The next two lines are the laptop asking the public resolver directly, from `192.0.2.10`. The web visit follows, with the handshake you know from 5.4: `[S]`, `[S.]`, `[.]`. All of it matches `net 203.0.113.0/24`, because each packet has the server or the public resolver at one end.

## The trap: a file that is not finished

With `-w`, tcpdump is silent. It looks stuck, and people press Ctrl-C at once, or open the file from their computer while tcpdump is still writing. Two things go wrong. A file opened too early can look empty or cut short, because tcpdump has not written every packet yet. And a capture with `-c 10` waits until it has ten matching packets. If nothing matches, it waits forever. In this part that happens when `traffic.sh` has already ended: start it again, and the capture finishes by itself.

So finish every file before you open it, in one of three ways. Give it a count with `-c`, and let it stop. Or stop it yourself with Ctrl-C: tcpdump then writes what it has and closes the file cleanly. Or add `-U`, so that each packet reaches the file at once. One more case is worth knowing. A tcpdump that a script starts in the background with `&` ignores Ctrl-C. That is why `make-capture.sh` in part 1 stops its tcpdump with a TERM signal: tcpdump finishes the file when it gets TERM.

<GoDeeper title="Go deeper: capture filter, display filter, and what the counts mean">

A capture filter decides what is saved at all. The packets it rejects are gone: no later filter can bring them back. That is the point of this chapter, and also the risk. If you capture only `port 53` and the real problem was a refused web connection, the file cannot show it. A good habit is a filter that is narrow enough to keep the file small, and wide enough to hold the question you are asking. When you do not know yet what you are looking for, capture a short time without a filter, read it, and then narrow down.

A display filter, from 12.2, runs on a file you already have, so it can be changed as often as you like. The two languages are different. The capture filter `host 203.0.113.80` is written `ip.addr == 203.0.113.80` as a display filter. tcpdump's `-r` takes the capture language, even for a file: that is how the part 2 test checks your files, with `tcpdump -nn -r FILE "not (FILTER)"`. If that prints nothing, every packet in the file matches its filter. You can see the same idea in the recorded run:

```
tcpdump -nn -r dns-only.pcap 'not port 53' | wc -l
```

```
reading from file dns-only.pcap, link-type EN10MB (Ethernet), snapshot length 262144
0
```

The three lines tcpdump prints when it stops are worth reading. `10 packets captured` is what it kept, which is your `-c`. The second count, `12` above, can be higher than the first. What matters for your file is the first. `0 packets dropped by kernel` is what you want to see: if it is not 0, some packets were lost before tcpdump got them, and your capture has holes.

Two smaller points. `port 53` matches UDP and TCP, and DNS uses both [S71]. And `-e` adds the hardware addresses to each line, as in 1.4, which you need when the question is about ARP or a switch. Most questions in this module are about addresses and ports, so `-nn` is enough.

</GoDeeper>
