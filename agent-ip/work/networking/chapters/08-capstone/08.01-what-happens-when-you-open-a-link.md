You press Enter on a link. Before the first byte of the page arrives, your laptop has already used almost everything in this course. Can you name every step?

## Pressing Enter starts ten small steps

<MermaidDiagram title="The ten steps of one connection" chart={`flowchart TD
  A["1 Lease: DHCP gives an address (module 7)"] --> B["2 ARP: find the router's MAC (module 3)"]
  B --> C["3 DNS: web.test becomes 203.0.113.80 (module 7)"]
  C --> D["4 Gateway: not my subnet, so use the router (modules 3 and 4)"]
  D --> E["5 SYN leaves: the server's IP, the router's MAC (module 5)"]
  E --> F["6 Home router: forward, rewrite, lower the TTL (modules 4 and 6)"]
  F --> G["7 Provider router: connected route, lower the TTL (module 4)"]
  G --> H["8 Server sees 198.51.100.2 and answers (module 5)"]
  H --> I["9 Reply returns through the NAT row (module 6)"]
  I --> J["10 Handshake ends, GET, first byte (module 5)"]
`} legend="The ten steps in order. Each box names the module that explained it. Nothing in this picture is new." />

Nothing here is new. You built or measured every step earlier, and each box says which module taught it. Steps 1 to 3 prepare the packet. Steps 4 to 10 follow it to the server and back. Keep this order in mind, because every fault in 8.5 breaks one of these steps.

<GoDeeper title="Go deeper: the ten steps with the capstone's numbers">

This chapter uses the network you will build in 8.2 to 8.5. The device home1 sits on 192.168.1.0/24. The home router, hrouter, has 192.168.1.1 inside and 198.51.100.2 on the link to the provider. The provider router, prouter, has 198.51.100.1 and 203.0.113.1. The server is 203.0.113.80 and listens on port 8080. All the public-looking addresses come from the documentation ranges, so no real website uses them [S10]. In a lab test, a home device reached the server through both routers, and the server saw 198.51.100.2 [D5.7].

Steps 1 to 3 give the laptop what it needs: an address, the router's MAC and the server's address. Step 4 is a decision that the mask makes alone [S7]. Steps 5 to 10 are one packet and its answer. Count the routers on the way: two. That number comes back in beat 6.

This chapter shows plain HTTP, the simplest case. A real browser adds TLS, and often QUIC, before the first byte of the page. The system design course covers both, and this course does not.

</GoDeeper>

## A lease, then the router's MAC

<InteractiveCanvas slug="net-m8-journey-lease-arp" />

home1 starts with no address, so its first message comes from 0.0.0.0. One <GlossaryTerm term="lease" definition="A loan of an address for a set time." /> then brings an address, a gateway and a DNS server. Next, ARP finds the router's MAC. Both answers end up in tables you can read.

<GoDeeper title="Go deeper: four messages and one broadcast">

A DHCP exchange has four messages: DISCOVER, OFFER, REQUEST and ACK. The client uses UDP port 68 and the server uses port 67 [S23]. The lease is for a fixed time. The default lease in dnsmasq is one hour [S64], and the recorded lease below says 3600 seconds, which is the same hour.

The first message comes from 0.0.0.0 and goes to 255.255.255.255, because the client has no address yet and must ask everyone. This is a capture from challenge 5:

```
    0.0.0.0.68 > 255.255.255.255.67: BOOTP/DHCP, Request from 3e:44:4a:51:79:fa, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: Discover
    192.168.1.1.67 > 192.168.1.136.68: BOOTP/DHCP, Reply, length 300, xid 0x88af800e, Flags [none]
	    DHCP-Message (53), length 1: Offer
```

The address 192.168.1.101 in the picture is one possible lease from the pool 192.168.1.100 to 192.168.1.150. A real run picks its own, as this recorded run did:

```
udhcpc: broadcasting select for 192.168.1.126, server 192.168.1.1
udhcpc: lease of 192.168.1.126 obtained from 192.168.1.1, lease time 3600
lease applied: 192.168.1.126/24 router=192.168.1.1 dns=192.168.1.1 lease=3600s
```

After the lease, home1 holds a gateway. It cannot send to the gateway without its MAC, so it sends an ARP request to ff:ff:ff:ff:ff:ff. The router answers straight back [S22].

</GoDeeper>

## The name becomes an address

<InteractiveCanvas slug="net-m8-journey-dns" />

The lease named the router as the DNS server. home1 asks it for web.test and gets 203.0.113.80. This comes before any connection to the server, because a connection needs an address first. If this step fails, a connection by name cannot start.

<GoDeeper title="Go deeper: who answers, and on which port">

A resolver asks questions for programs, and a server answers for the names it knows [S24]. In the lab, dnsmasq on the router answers web.test from its own list. The option `--no-resolv` makes it ignore /etc/resolv.conf [S64], so it has nobody else to ask. A name that is not in the list gets status REFUSED, not NXDOMAIN [D5.8].

The question goes to port 53 [S77]. You can see the port in an error that dig printed in a recorded fault run:

```
    FAIL home1: dig @192.168.1.1 web.test should return 203.0.113.80. It returned: ;; communications error to 192.168.1.1#53: timed out
```

The number after the hash sign is the port. In that run the DNS port was blocked on the router, so the question had no answer. A DHCP lease still worked, because DHCP uses ports 67 and 68 [D5.8].

A common wrong idea is that DNS comes after TCP. It does not. TCP needs the server's address first, and DNS is how home1 gets it.

</GoDeeper>

## Off my subnet: use the gateway

<InteractiveCanvas slug="net-m8-journey-gateway" />

The mask says 203.0.113.80 is not on 192.168.1.0/24. So home1 sends the <GlossaryTerm term="SYN" definition="The first message of a TCP connection." /> to its <GlossaryTerm term="gateway" definition="The router a device uses to leave its subnet." />. The destination IP stays the server's. The destination MAC is the router's.

```predict
prompt: "At the home router, which of the source IP, destination IP, destination MAC, TTL and source port change?"
options:
  - id: p0
    label: "Source IP, MAC and TTL; the port only on a clash"
  - id: p1
    label: "All five fields change every time, even the port"
  - id: p2
    label: "Only the source IP changes, as that is all NAT does"
correctOptionId: p0
explanation: "The router rewrites the source IP (masquerade), sets the MAC for the next link and lowers the TTL by one. The destination IP stays. The source port is kept unless two flows would clash. [S30] [S43] [D5.6]"
allowRetry: true
```

<GoDeeper title="Go deeper: the mask decides, the route table chooses">

A host combines the mask with the destination to decide if the destination is local or must go through a gateway [S7]. Here 203.0.113.80 is outside 192.168.1.0/24. The route table then has one row that matches: the default row, which means 0.0.0.0/0 [S32]. On Linux, `ip route get` shows the choice. This is a recorded line from the capstone:

```
203.0.113.80 via 192.168.1.1 dev veth-home1 src 192.168.1.30 uid 0
```

That run used the placeholder address 192.168.1.30, before any lease. The gateway is 192.168.1.1, as the lease would give.

<Callout type="warning" title="Do not look for the server's MAC">
A capture on the inside link shows the router's MAC as the destination. The server's MAC is two routers away, so it never appears on this link. A MAC covers one link only.
</Callout>

</GoDeeper>

## The home router changes the packet

<InteractiveCanvas slug="net-m8-journey-nat-hop" />

Press Next, and pick a MAC when asked. Three fields change here: the source IP, the destination MAC and the TTL. The source port stays unless two devices would clash. The router also writes one row in its NAT table.

<GoDeeper title="Go deeper: forwarding, rewriting and the clash">

The kernel does not forward by default: `ip_forward` is 0 until you set it [S28], so the home router needs it switched on. A router must lower the TTL by at least one, and it uses the most specific matching route [S30]. A Linux sender starts the TTL at 64 [S28], so the packet leaves hrouter with 63.

Masquerade is a special case of source NAT. It takes the source address from the output interface, and it works only in a postrouting chain [S43]. So the source becomes 198.51.100.2. Nothing else about the connection changes, unless two flows would use the same pair of ports. A lab run showed this in challenge 4, where the router's outside address was 203.0.113.1. Two devices sent from port 41000 at the same time:

```
laptop sent from 41000. The server says: the server sees you as 203.0.113.1:41000
phone sent from 41000. The server says:  the server sees you as 203.0.113.1:15510
```

The second device was given port 15510. The tool that shows the table is `conntrack -L`. This is a recorded line from the capstone, where home1's flow kept its port:

```
tcp      6 119 TIME_WAIT src=192.168.1.30 dst=203.0.113.80 sport=38676 dport=8080 src=203.0.113.80 dst=198.51.100.2 sport=8080 dport=38676 [ASSURED] mark=0 use=1
```

Read it in two halves. The first half is what home1 sent. The second half is what the server's answer looks like when it comes back. Challenge 2 recorded the same packet on both links, before NAT existed:

```
PASS inside link: the echo goes from the laptop's MAC to the router's inside MAC, ttl 64
PASS outside link: the same echo goes from the router's outside MAC to the server's MAC, ttl 63
PASS the IP addresses are the same on both sides: 192.168.1.23 > 203.0.113.80
```

The IP addresses are the same on both sides. The MACs and the TTL change.

</GoDeeper>

## The row sends the reply home

<InteractiveCanvas slug="net-m8-journey-reply" />

The server sees only 198.51.100.2 and answers that address. The reply reaches the home router, and a <GlossaryTerm term="conntrack" definition="The router's table of open connections." /> row says which device it is for. TTL 62 at the server matches a lab capture.

<GoDeeper title="Go deeper: the way back, and what a missing route looks like">

The provider router is plugged into both of its subnets, so it needs no extra route. It lowers the TTL by one, as every router does [S30]. After two routers the TTL is 62, and `tcpdump -v` showed this in a lab run [D5.8]. The reply starts at 64 on the server, so it arrives at home1 with 62 as well. Those reply values follow the rules and were not captured.

The server must also have a way back to 198.51.100.2. Without a return route, the sender sees silent loss, and adding the route fixes it [D5.8]. That is the shape of many faults in 8.5: the packet goes, and nothing comes back.

In the NAT table, the row for the flow stays for a short time after the connection ends. A closed TCP flow showed TIME_WAIT with 119 seconds left in one lab run [D5.8]. The client picks its source port at random, so a test must never check the port number in the row [D5.6].

</GoDeeper>

## The handshake ends and the page arrives

<InteractiveCanvas slug="net-m8-journey-first-byte" />

The last handshake message, an ACK, opens the connection on both sides. Then home1 sends its GET, and the first byte comes back. This lab page is plain HTTP. A real browser adds TLS and often QUIC first. The system design course teaches both.

<GoDeeper title="Go deeper: three messages, then data">

A TCP connection opens with SYN, SYN-ACK and ACK [S25]. A connection is defined by a pair of sockets, so both sides can name it [S25]. This is the handshake that tcpdump recorded in challenge 3, on a simpler network:

```
10:39:05.171782 IP 192.168.1.23.48158 > 192.168.1.80.8080: Flags [S], seq 557210665, win 64240, options [mss 1460,sackOK,TS val 710427391 ecr 0,nop,wscale 7], length 0
10:39:05.171824 IP 192.168.1.80.8080 > 192.168.1.23.48158: Flags [S.], seq 1089803950, ack 557210666, win 65160, options [mss 1460,sackOK,TS val 2147467152 ecr 710427391,nop,wscale 7], length 0
10:39:05.171850 IP 192.168.1.23.48158 > 192.168.1.80.8080: Flags [.], ack 1, win 502, options [nop,nop,TS val 710427393 ecr 2147467152], length 0
```

After the ACK, `ss` shows the same connection on both sides:

```
laptop sees:
State Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
ESTAB 0      0       192.168.1.23:48172 192.168.1.80:8080
server sees:
State Recv-Q Send-Q Local Address:Port Peer Address:Port Process
ESTAB 0      0       192.168.1.80:8080 192.168.1.23:48172
```

Only now can data move. The GET is plain text, so a capture shows it. If you add TLS, the text is hidden, and that is the system design course's subject. You can now name all ten steps. In 8.2 to 8.5 you build every one of them.

</GoDeeper>
