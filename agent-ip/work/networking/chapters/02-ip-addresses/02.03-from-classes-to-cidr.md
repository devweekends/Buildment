In 1993 a company with 300 computers asked for a block of addresses. The only block sizes held 254 or 65,534 usable addresses. 254 is too few. What does taking the big one do to the internet?

## Three sizes and nothing in between

<MermaidDiagram title="The three classes of address" chart={`flowchart TD
  F["The first bits of an address"] --> A["Starts with 0, first number 0 to 127: class A, 128 networks, 16,777,214 usable each"]
  F --> B["Starts with 10, first number 128 to 191: class B, 16,384 networks, 65,534 usable each"]
  F --> C["Starts with 110, first number 192 to 223: class C, 2,097,152 networks, 254 usable each"]
  C --- G["Between 254 and 65,534: no block of that size exists"]
  B --- G
`} legend="Each class has one fixed size. The gap between a class C and a class B is the problem: a company that needs 255 computers must take all 65,534." />

The first bits of an address chose its <GlossaryTerm term="class" definition="One of three fixed block sizes, A, B or C." />: 0 for A, 10 for B and 110 for C. Each class had one size. A class C held 254 usable addresses, a class B held 65,534, and nothing sat between them.

<GoDeeper title="Go deeper: how the first bits decide, and what usable means">

RFC 791 defines the classes by the first bits of the address [S1]. The first number then follows from the bits. A class A address starts with the bit 0, so its first number is 0 to 127. Class B starts with 10, which gives 128 to 191. Class C starts with 110, which gives 192 to 223. The ranges are arithmetic from the bits.

The counts come from RFC 4632: 128 class A networks, 16,384 class B networks of 65,536 addresses each, and 2,097,152 class C networks [S6]. A class C has 8 bits left for computers, which is 256 addresses. Of those, 254 are usable. The first and last address of a block have special jobs, and module 3 shows them. So usable means the size minus 2. A class B has 16 bits left: 65,536 addresses and 65,534 usable. A class A has 24 bits left: 16,777,216 addresses and 16,777,214 usable.

Now the bad choice is clear. A company with 255 to 65,534 computers had to take a class B. This is our reasoning from the sizes, not a quote from a document. The group that studied the problem named three. The class B space was running out. Routing tables were growing. And in time the whole 32-bit space would run out [S5, S6].

There was a way to avoid a class B, and it caused the second problem. A company with 700 computers could take three class C blocks instead, which gives 3 x 254 = 762 usable addresses. It saved class B space. But each block is its own entry in the routing tables of the big routers. Three entries instead of one, for every company that did this. That is how the tables grew.

</GoDeeper>

## Hand blocks to five organisations by class

<InteractiveCanvas slug="net-m2-allocate-class" />

Give each organisation a class C or a class B. A block that is too small is refused. With the smallest block that fits, the unused addresses add up to 254,360. Four of the five organisations take a class B, and each leaves more than 60,000 unused.

<GoDeeper title="Go deeper: the sum, and what the picture leaves out">

Here is the sum for the five fictional organisations. The organisation with 30 computers takes a class C and leaves 254 - 30 = 224 unused. The organisation with 300 takes a class B and leaves 65,534 - 300 = 65,234. The one with 700 leaves 64,834, the one with 2,000 leaves 63,534 and the one with 5,000 leaves 60,534. The total is 224 + 65,234 + 64,834 + 63,534 + 60,534 = 254,360. The total was checked by script.

Five blocks also mean five routing entries, one per block. Taking several class C blocks would cut the waste and raise the number of entries. Neither choice was good, which is why the change to CIDR came.

The picture is a simplification. Real allocations in the 1990s were not this tidy, and the five organisations are made up. It counts addresses and routing entries only. It does not show how a real router uses them.

</GoDeeper>

## Hand the same five out by CIDR

<InteractiveCanvas slug="net-m2-allocate-cidr" />

Now every organisation can get a block of its own size, under <GlossaryTerm term="CIDR" definition="Blocks of any power-of-two size." />. The number after the slash is the <GlossaryTerm term="prefix length" definition="How many bits at the start are fixed." />, and a smaller number gives a bigger block. Pick one for each organisation. The smallest block that fits leaves only 3,768 addresses unused.

<GoDeeper title="Go deeper: how to choose the prefix, and the same company twice">

To choose a prefix, find the smallest block that fits, and count its host bits. A block with h host bits holds 2^h addresses, of which 2^h - 2 are usable. The prefix is then 32 - h. A made-up organisation with 90 computers shows the steps. With 6 host bits, 2^6 - 2 = 62 usable, which is too few. With 7 host bits, 2^7 - 2 = 126 usable, which fits. So h = 7 and the prefix is 32 - 7 = 25. The organisation gets a `/25` and leaves 126 - 90 = 36 unused.

The same steps give the picture's answers. The 30-computer organisation gets a `/27` with 30 usable and nothing unused. The 300-computer one gets a `/23` with 510 usable and 210 unused. The 700-computer one gets a `/22` with 1,022 usable and 322 unused. The 2,000-computer one gets a `/21` with 2,046 usable and 46 unused. The 5,000-computer one gets a `/19` with 8,190 usable and 3,190 unused. The total is 0 + 210 + 322 + 46 + 3,190 = 3,768. Compare 254,360 with 3,768: CIDR leaves about 1.5 percent of the waste.

RFC 1519 introduced CIDR in September 1993 [S5], and RFC 4632 replaced it [S6]. Waste was only one problem. Aggregation, in beat 5, is how CIDR slows the growth of the routing tables.

</GoDeeper>

## Drag the prefix, watch the block change

<InteractiveCanvas slug="net-m2-prefix" />

Drag the prefix length from `/8` to `/32`. The <GlossaryTerm term="mask" definition="The prefix written as an address: that many 1 bits, then 0 bits." /> turns one more bit on at each step, and the block halves. The size is 2 to the power of the host bits, which is 32 minus the prefix. At `/24` that is 256 addresses.

<GoDeeper title="Go deeper: size and mask by hand, in both directions">

Find the size first. Take 32 minus the prefix to get the host bits, then 2 to that power. For `/18` the host bits are 14, so the block holds 2^14 = 16,384 addresses. For `/29` the host bits are 3, so the block holds 8 addresses and 6 are usable.

Find the mask next. Every group of 8 prefix bits is a full 255. The bits left over fill part of the next number. For `/18`, the prefix is 8 + 8 + 2. The third number has 2 bits on: 128 + 64 = 192. The mask is 255.255.192.0. There is a shortcut for the odd number: it is 256 minus the block size counted in that number. The block size in the third number is 64, and 256 - 64 = 192. For `/29` the prefix is 8 + 8 + 8 + 5. The last number has 5 bits on, 128 + 64 + 32 + 16 + 8 = 248, which is 256 - 8. The mask is 255.255.255.248.

Now go the other way, from a size to a prefix. A block of 1,024 addresses is 2^10, so it has 10 host bits and the prefix is 32 - 10 = 22. Do not write 10 as the prefix: that is the slip the wrong options in the drill are built on.

For every prefix from `/8` to `/30`, the usable count is the size minus 2. The two longest prefixes are different: a `/31` holds two addresses for a link between two devices [S70], and a `/32` holds one. Module 3 explains both. The picture uses the address 10.20.143.7 only so that it has something to show.

</GoDeeper>

## Many routes become one

<MermaidDiagram title="Two customer blocks announced as one" chart={`flowchart LR
  A["Customer 1: 10.8.0.0/24, 10.8.0.0 to 10.8.0.255"] --> P["Provider router"]
  B["Customer 2: 10.8.1.0/24, 10.8.1.0 to 10.8.1.255"] --> P
  P -->|"one route: 10.8.0.0/23, 10.8.0.0 to 10.8.1.255"| I["The rest of the internet"]
`} legend="The provider serves two customers. The rest of the internet needs one entry for both, because the two blocks sit side by side and make exactly one bigger block." />

A provider serves two customers: `10.8.0.0/24` and `10.8.1.0/24`. Together they cover 10.8.0.0 to 10.8.1.255, which is exactly `10.8.0.0/23`. The rest of the internet keeps one entry instead of two. Many blocks standing for one is <GlossaryTerm term="aggregation" definition="Announcing many neighbouring blocks as one bigger block." />.

<GoDeeper title="Go deeper: when two blocks can merge, and when they cannot">

Two blocks merge when they have the same size, sit side by side, and make a bigger block that starts in the right place. A `/23` holds 512 addresses, so it starts at a multiple of 512. In the dotted form, a `/23` starts where the third number is even: 10.8.0.0, 10.8.2.0, 10.8.4.0, and so on.

A close case shows the rule. `10.8.1.0/24` and `10.8.2.0/24` are side by side. They cover 10.8.1.0 to 10.8.2.255, which is 512 addresses. But no `/23` block starts at 10.8.1.0, because the third number 1 is odd. So these two cannot be announced as one `/23`. They stay two entries, or one of them merges with its other neighbour.

Aggregation answers the second problem on the ROAD group list, the growth of the routing tables [S5, S6]. A provider that owns one large block can announce it as one entry, however many customers it serves inside. The big routers keep one entry, and the provider keeps the details.

The picture shows the simplest case, two blocks. Only blocks that sit side by side in the right place can be merged.

</GoDeeper>

## Size and mask by hand

<InteractiveCanvas slug="net-m2-cidr-drill" />

Five questions, no calculator. Each asks for the size or the mask of a `/n`. The wrong options are one prefix step away, the slip people really make. You get instant feedback. In 2.4 you will see which ranges were set aside for use inside networks.

<GoDeeper title="Go deeper: four common slips">

- **Size, not usable.** A `/24` holds 256 addresses, and 254 are usable. A question that asks for the size wants 256.
- **The slash is not the size.** A `/27` does not hold 27 addresses. It has 27 prefix bits and 5 host bits, so it holds 32.
- **A bigger prefix is a smaller block.** `/25` is half of a `/24`, not double.
- **A mask has no gaps.** The mask 255.255.255.224 is 27 ones then 5 zeros. A mask such as 255.255.255.100 is not a valid mask here, because its bits are not all ones first and then all zeros. This course teaches only masks without gaps [S7].

</GoDeeper>
