Any network can lose a packet, yet a downloaded file is never missing a byte. Who fixes it?

## Any network can lose a packet

<InteractiveCanvas slug="net-m5-scene-lossy-link" />

A file crosses a link in three parts. The link drops part 2. The sender sends it again, and the phone ends up with the whole file. No person did anything. A protocol called TCP did this work, on the two end computers [S25]. The next beats show how it notices a loss.

<GoDeeper title="Go deeper: what TCP promises, and what it does not">

TCP keeps a conversation whole between two computers. It opens the conversation with a handshake, numbers the bytes it sends, and sends bytes again when they are not confirmed [S25]. The app on top sees a steady stream of bytes in order. It does not see the loss or the second try.

This chapter gives no loss rate for any real network, because this course has no measurement to quote. The picture shows one drop to make the idea visible. How often links lose packets depends on the link, and the lab you build in chapter 5.6 loses none.

TCP does not make a network faster. A second try takes time. Chapter 5.5 shows what that time costs an app that cannot wait.

</GoDeeper>

## Three packets open a conversation

<MermaidDiagram title="The three packets that open a conversation" chart={`sequenceDiagram
  participant C as Client 192.168.1.23
  participant S as Server 203.0.113.80
  C->>S: 1 SYN, seq 1000
  S->>C: 2 SYN-ACK, seq 5000, ack 1001
  C->>S: 3 ACK, ack 5001
`} legend="Three packets, in order. Each side acknowledges the other's number plus one: 1000 becomes ack 1001, and 5000 becomes ack 5001. All numbers are illustrative. Real starting numbers are much larger." />

TCP opens with three packets. The client sends SYN with its <GlossaryTerm term="sequence number" definition="A label for the bytes a side sends." />, 1000. The server answers SYN-ACK with its own number, 5000, and an <GlossaryTerm term="acknowledgement" definition="A reply naming the next byte wanted." />, ack 1001. The client answers ACK, ack 5001. An ack is the other side's number plus one, and it names the next byte expected.

<GoDeeper title="Go deeper: the handshake with real numbers">

The handshake is three packets: SYN, SYN-ACK, ACK [S25]. The first number each side sends is its starting sequence number. The picture uses 1000 and 5000 so that you can follow the arithmetic. Real starting numbers are not 1000. In the lab capture of chapter 5.6, the client started at 557210665 and the server at 1089803950. The server's ack was 557210666, which is the client's number plus one.

The third packet of that capture shows `ack 1`, not a long number. The tool that printed it, tcpdump, prints later numbers counted from the start of the conversation. The raw number would be the server's 1089803950 plus one.

In the capture, the three packets carry the flags `[S]`, `[S.]` and `[.]`. They stand for SYN, SYN-ACK and ACK. You will meet them again in chapter 5.6. Keep two ideas from this fold: the handshake starts the numbering, and every later ack is read against the numbers it started.

</GoDeeper>

## The receiver names the next byte it expects

<InteractiveCanvas slug="net-m5-tcp-loss-ack" />

The client sends three segments of 100 bytes, numbered from 1001. Segment 2 is lost. Segment 3 arrives, yet the server still asks for byte 1101. It names the next byte it needs, not the last one it got. Step through and watch the ack number stop growing. This is how a sender can see a loss it was never told about.

<GoDeeper title="Go deeper: sequence numbers count bytes">

A sequence number counts bytes, not packets. A segment of 100 bytes that starts at 1001 uses the numbers 1001 to 1100, so the next segment starts at 1101. The acknowledgement works the same way. After bytes 1001 to 1100 arrive, the next byte expected is 1101. So the ack is 1101, not 1100 and not 2.

In the picture the server keeps segment 3 while it waits for segment 2. That is why, later, one ack can jump over two segments. A real receiver may also tell the sender which later segments it holds. The picture leaves that out. It shows one loss only, with no windows and no congestion control. Those are real parts of TCP, but they are not needed to understand the idea of an ack.

</GoDeeper>

## The same ack again means: send it again

<InteractiveCanvas slug="net-m5-tcp-loss-resend" />

The client sees ack 1101 a second time, though it has sent bytes up to 1300. It reads this as a sign that the bytes from 1101 are missing, and sends them again. Sending data again is called <GlossaryTerm term="retransmission" definition="Sending data again because it was lost." />. The server already holds bytes 1201 to 1300, so its ack jumps to 1301.

<GoDeeper title="Go deeper: what makes a real sender send again">

<Callout type="info" title="A simple version of one idea">
Real TCP can use a timer, repeated acks, or both to decide when to send again. This chapter shows one simple case and quotes no time and no count.
</Callout>

The picture says: the same ack twice means the bytes from that number are missing. That is the idea with the details removed. A real sender also has to decide when to give up waiting, and how many segments it may have in flight at once. These rules are in the standard [S25]. This course shows no timer value and no count, because it has no measured source to quote.

</GoDeeper>

## Which segments must be sent again?

<InteractiveCanvas slug="net-m5-sort-resend" />

Each card is a segment of 100 bytes, with the receiver's latest ack. If the ack is past the first byte of the segment, the segment arrived. If it is not, the sender must send it again. Sort the six cards. A wrong try tells you what the ack means. The sender does this sum for every segment it sends.

<GoDeeper title="Go deeper: reading acks without a picture">

You can do the same sort by hand on a capture. Take the ack from the receiver, take the first byte of a segment, and compare. If the first byte is smaller than the ack, the segment is covered. If it is equal to the ack or bigger, it is not covered yet, and the sender sends it again.

In a real capture the numbers are long, so tcpdump's counting from the start of the conversation helps: you compare small numbers. Chapter 5.6 and the gate in chapter 5.8 ask you to read the numbers of your own capture.

</GoDeeper>

```quiz
  - "Bytes 4001 to 4100"
  - "Bytes 4101 to 4200"
  - "Bytes 4201 to 4300"
correct: 1
explanations:
  - "The first ack, 4101, says that bytes 4001 to 4100 arrived. They do not need to be sent again."
  - "Right. Ack 4101 twice means the server still needs byte 4101. Segment 2, bytes 4101 to 4200, is the one that is missing."
  - "The second ack appeared because segment 3 arrived while a gap was open. Bytes 4201 to 4300 are not the gap."
```
