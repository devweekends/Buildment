You open a website in another country. Your packet is addressed to the website's IP address, but the frame that carries it is addressed to your router's MAC address. Why both?

## A neighbour gets its own MAC

<InteractiveCanvas slug="net-m4-mac-local" />

The laptop sends to a neighbour at `192.168.1.40`. The mask test from 3.2 says: same network. So the frame goes straight to the neighbour, and its destination <GlossaryTerm term="MAC address" definition="The hardware address of one network plug. It matters on one link only." /> is the neighbour's own. Press Next to watch the laptop find it.

<GoDeeper title="Go deeper: how the laptop knows the neighbour is local">

The laptop applies its mask to the destination and compares the result with its own network. This is the test you did by hand in 3.2, and RFC 950 describes it: a host uses the mask on the destination to decide between a local delivery and a gateway [S7]. For `192.168.1.40` with the mask `255.255.255.0`, the network is `192.168.1.0`. That is the laptop's own network, so the destination is local.

A local destination needs a MAC. The laptop asks the link with ARP and keeps the answer in its neighbour table [S22]. You saw the full exchange in 3.3. This picture skips the question and shows the result: a table row, and then a frame that carries it. The table is a model. `ip neigh` shows the real one.

The MACs here start with `02`. They are made up for the pictures, so no real device owns them. A real capture shows real ones: the lab's `tcpdump -e` showed the ARP request going to `ff:ff:ff:ff:ff:ff` and the reply coming back to one MAC [D5.8].

<Callout type="info" title="Ethernet only, and no NAT">
These pictures draw Ethernet links. Wi-Fi frames look different. The path in this chapter has no NAT. A real home router also rewrites the source IP address; module 6 does that on purpose.
</Callout>

</GoDeeper>

## A far site gets the router's MAC

<InteractiveCanvas slug="net-m4-mac-remote" />

Now the laptop sends to `203.0.113.80`, a site far away. The mask test says: not on my network. So the laptop uses its <GlossaryTerm term="default gateway" definition="The router a computer hands every packet to when the destination is not on its own network." /> as the next stop. The frame carries the site's IP address but the gateway's MAC.

<GoDeeper title="Go deeper: the gateway is a row in the laptop's table">

A computer keeps a table of routes, and one row is the gateway. Here are the two rows of the laptop in challenge 2, as the lab printed them [R-router]:

```
default via 192.168.1.1 dev veth-laptop
192.168.1.0/24 dev veth-laptop proto kernel scope link src 192.168.1.23
```

Read the first row as: for everything that no other row covers, hand the packet to `192.168.1.1`. Read the second as: the network `192.168.1.0/24` is on this plug, so deliver there directly. Chapter 4.3 shows how a computer chooses between rows. In module 1 you wrote down your own gateway. It is the address on the first row.

Why the gateway's MAC and not the site's? A frame can only go to a device on the same link. The gateway is on the laptop's link, and the far site is not. The IP address in the packet stays the site's, so that the gateway knows where the packet is going when it opens the frame.

If the gateway address is wrong, the laptop cannot get a MAC for it. In our test of an address on the same network that nobody owns, the ARP requests went unanswered and the ping showed silent loss [D5.7]. You will meet this fault again in 4.8.

</GoDeeper>

## ARP only reaches the local link

<MermaidDiagram title="Why the laptop asks for the gateway" chart={`flowchart TD
  A["Laptop: is 203.0.113.80 on my network? No, by the mask test"] --> B["ARP only reaches this link, so the far server cannot be asked"]
  B --> C["Ask this link instead: who has 192.168.1.1, the gateway?"]
  C --> D["R1 answers with its MAC"]
`} legend="The mask test says the server is far. ARP can only ask the local link. So the laptop asks for the gateway's MAC, and the gateway answers." />

ARP is a question shouted on one link. Only devices on that link hear it, so the laptop cannot ask the far server for its MAC. It asks for the gateway's MAC instead, and the gateway is on the link. This is why the gateway must always be an address on your own network.

<GoDeeper title="Go deeper: what ARP can and cannot reach">

An ARP request is a broadcast on the link. It goes to `ff:ff:ff:ff:ff:ff`, and the owner of the address answers [S22]. A broadcast stays on its own network, as 3.4 showed when it asked why we split a network. So the question can never reach a server on another network.

The sender must therefore already know which device on its own link is the next stop. That is the job of the default gateway. The mask test finds out that the destination is far. The route table then names the gateway. ARP finds the gateway's MAC. Three steps, in that order.

The same three steps repeat at every router. R1 does not ask the server for its MAC either. It looks at its own table, finds R2 as the next hop, and asks its own link for R2's MAC.

</GoDeeper>

## The MACs change at every hop

<InteractiveCanvas slug="net-m4-mac-per-hop" />

Follow the packet over three links. At each router the frame is opened and a new frame is built for the next link. So the source MAC and the destination MAC change on every link. On the last link the destination MAC is the server's own. Each stop is a <GlossaryTerm term="next hop" definition="The next device that gets the packet on its way." />.

<GoDeeper title="Go deeper: what a router does with a frame">

A router receives a frame addressed to its MAC. It opens the frame and reads the destination IP address. It looks in its table for the row that holds that address, and the row names the next hop. Then it builds a new frame. The source MAC is the router's plug on the next link. The destination MAC is the next hop's MAC, found with ARP on that link [S22]. The old frame is gone.

The real lab shows this. In challenge 2 the test captures one ping on both sides of the router. These are the recorded lines of its result [R-router]:

```
PASS inside link: the echo goes from the laptop's MAC to the router's inside MAC, ttl 64
PASS outside link: the same echo goes from the router's outside MAC to the server's MAC, ttl 63
PASS the IP addresses are the same on both sides: 192.168.1.23 > 203.0.113.80
```

The first line is the inside link. The second is the outside link, and the MACs are different. The third says the IP addresses were the same on both sides. You will capture this yourself in 4.7, and you will see the TTL change from 64 to 63. Chapter 4.4 explains the TTL.

</GoDeeper>

## The IP addresses never change

<MermaidDiagram title="One packet, three links" chart={`flowchart TD
  L["Laptop"] -->|"link 1: IP 192.168.1.23 to 203.0.113.80, MAC laptop to R1"| R1["R1"]
  R1 -->|"link 2: same IPs, MAC R1 to R2"| R2["R2"]
  R2 -->|"link 3: same IPs, MAC R2 to server"| S["Server"]
`} legend="The IP pair is the same on all three links. The MAC pair is new on each link." />

The IP pair is the same on all three links: it says where the packet is going from end to end. The MAC pair is different on each link: it says who takes the packet on that link. This path has no NAT, so nothing rewrites the IP addresses.

<GoDeeper title="Go deeper: two jobs, two addresses">

In 1.6 you met three jobs for three addresses. The MAC address works on one link. The IP address works from end to end. This chapter is where you see both at once in one packet. The IP address says where the packet is going. The MAC address says who takes it next.

One consequence surprises people. The router's IP address is not in the packet at all. The laptop never writes `192.168.1.1` as a destination in the IP part. It writes that device's MAC in the frame part, and the IP part keeps the site's address. The gateway is reached by its MAC, and the destination is reached by its IP.

A real home router also rewrites the source IP address, so a website sees the router's address, not the laptop's. That is NAT. Module 6 builds it. The router in this chapter and in 4.7 has no NAT, so the IP addresses stay as they are.

</GoDeeper>
