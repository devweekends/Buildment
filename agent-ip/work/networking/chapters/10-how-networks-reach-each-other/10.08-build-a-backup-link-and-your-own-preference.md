In 10.4 a network chose a longer path on purpose, because its own preference said so. In 10.6 you wrote that rule as step 4 of `bestRoute`, before path length in step 5. In this chapter you set that preference on a real router. You add a direct cable from r1 to r3, so r1 knows two ways to `203.0.113.0/24`. The direct way has the shorter AS path, and it wins. Then you write one line of policy that makes it lose, so it waits as a backup. Then you cut the main link and watch traffic move to the backup, and back again.

This is challenge 7, part 3. It is **gapped**: the script `backup-link.sh` is almost complete, and four small things are missing, each marked `TODO`. The test tells you which gap is wrong. The script builds the three routers of part 1 again, with one more cable, so do parts 1 and 2 first.

The new cable is `10.0.13.0/24`, named `13` because it joins r1 and r3. r1 is `10.0.13.1` on it and r3 is `10.0.13.3`. Now r1 knows two ways to `203.0.113.0/24`. Through r2 the AS path is `64497 64498`, two numbers. Over the direct cable it is `64498`, one number.

BIRD compares the two in the order you wrote in 10.6. A longer block would win first, but both ways carry the same `/24`, so that does not decide. Higher local preference would win next, but both start at the default 100, so that does not decide either. Then the shorter AS path wins, and the direct way has only one number. So at first, r1 sends everything over the direct cable.

Now give the story a reason. Say the direct cable is cheap but slow, and r2 is your paid provider with a fast link. You want r2 as the main path and the direct cable only as a backup. Path length cannot know that: it counts networks, not speed or money. Local preference can, because it is your own choice, and it counts before path length.

## Gap 1: the other end of the direct cable

**In the lab**, go to the folder:

```
cd /work/challenges/challenge-7-bgp/part-3-backup-link
```

A BGP session needs both ends. The script already gives r1 a session to r3 over the direct cable, inside `write_r1_conf`:

```
protocol bgp to_r3 {
  local as 64496;
  neighbor 10.0.13.3 as 64498;
  ipv4 {
    $1
    export all;
  };
}
```

The `$1` is the import line, which the script fills in. It starts as `import all;` and changes in Gap 2. That is why the script writes the file in a function and can write it again later.

**Gap 1** is the same block for r3, inside `write_r3_conf`. Copy r1's block and change three things: the name, `to_r1`; the local AS, r3's own `64498`; and the neighbour, r1's address on the direct cable with r1's AS number. Keep the import line exactly as it is in r1's block, because the script fills it in for r3 too. If you leave Gap 1 empty, r1 keeps trying to open the session and r3 turns it away. The recorded template run showed r1's side waiting in `Active` with `Socket: Connection reset by peer`.

With Gap 1 filled, the script starts BIRD, waits for the sessions, and saves the mid-point check in `before-preference.txt`. This is the recorded file:

```
203.0.113.0/24       unicast [to_r3 16:40:21.569] * (100) [AS64498i]
	via 10.0.13.3 on veth-to-r3
	Type: BGP univ
	BGP.origin: IGP
	BGP.as_path: 64498
	BGP.next_hop: 10.0.13.3
	BGP.local_pref: 100
                     unicast [to_r2 16:40:21.584] (100) [AS64498i]

	BGP.origin: IGP

	BGP.next_hop: 10.0.12.2

```

Two routes to the same block. The first came from `to_r3`, the direct session, and it has the `*`. Both have `BGP.local_pref: 100`, so the shorter path, `64498`, decided. The second route, through r2, has no `*`. It is not thrown away. BIRD keeps it, ready, in case the first one goes.

## Gap 2: one line of policy

**Gap 2** sets two lines near step 10 of the script, `R1_FROM_R3` and `R3_FROM_R1`. Each is the import line of one end of the direct cable. Today both say `import all;`. You replace each with a one-line import filter of this shape, from the README:

```
import filter { bgp_local_pref = NUMBER; accept; };
```

Read it piece by piece. `import filter` replaces `import all`: instead of taking every route as it is, BIRD runs the commands inside on every route this neighbour sends. `bgp_local_pref = NUMBER;` sets the route's local preference. The README uses 50. Any number below 100 makes the direct link the backup. `accept;` keeps the route. A filter that ends without `accept` drops the route, and then the direct link would not even be a backup.

The filter goes on the direct sessions only. Routes from r2 keep the default 100. And it goes on **both** ends. r1's filter decides how r1 sends to r3. r3's filter decides how r3's answers come back. With only r1's filter, the ping would go out through r2 and the answer would come back direct. It would still work, but the two directions would take different roads. That is common on the internet. In this lab you want both directions on r2.

The script then writes both files again and runs `birdc -s /tmp/bird-r1.ctl configure` and the same for r3. `configure` makes BIRD read its file again without a restart, and the sessions stay up. The recorded output for each was `Reading configuration from` the file, then `Reconfigured`. Then the script saves `after-preference.txt`:

```
203.0.113.0/24       unicast [to_r2 16:40:21.584] * (100) [AS64498i]
	via 10.0.12.2 on veth-to-r2
	Type: BGP univ
	BGP.origin: IGP
	BGP.as_path: 64497 64498
	BGP.next_hop: 10.0.12.2
	BGP.local_pref: 100
                     unicast [to_r3 16:40:21.724] (100) [AS64498i]
	via 10.0.13.3 on veth-to-r3
	Type: BGP univ
	BGP.origin: IGP
	BGP.as_path: 64498
	BGP.next_hop: 10.0.13.3
	BGP.local_pref: 50
```

The `*` moved. The route through r2 is now the chosen one. The direct route is still there, and it still has the shorter path, `64498`. But its `BGP.local_pref` is `50`, so it lost before path length was ever compared. That is step 4 of your `bestRoute` overruling step 5, on a real router. Notice also what did not happen: r3 never received the number 50 from r1. Each end set its own number for its own use, because local preference never leaves the network.

## Gaps 3 and 4: cut the main link and put it back

**Gap 3** cuts the main path. It is one `birdc` command, of the shape `birdc -s SOCKET disable SESSION`. Ask yourself which router and which session carry the main path from r1 to r2. The README's answer: the session `to_r1` in **r2**. Switching off a session is like pulling a cable out, but it comes back cleanly. If you pull the cable itself with `ip link set ... down`, BIRD notices at once, but after the cable comes back it waits a long time before it tries again. `disable` and `enable` come back in a few seconds.

With Gap 3 filled, the script saves `failover.txt`. The recorded file, shortened:

```
### ip netns exec r1 ip route
10.0.12.0/24 dev veth-to-r2 proto kernel scope link src 10.0.12.1 
10.0.13.0/24 dev veth-to-r3 proto kernel scope link src 10.0.13.1 
198.51.100.0/24 dev dummy0 proto kernel scope link src 198.51.100.1 
203.0.113.0/24 via 10.0.13.3 dev veth-to-r3 proto bird metric 32 
### ip netns exec r1 ping -c2 -W1 -I 198.51.100.1 203.0.113.1
PING 203.0.113.1 (203.0.113.1) from 198.51.100.1 : 56(84) bytes of data.
64 bytes from 203.0.113.1: icmp_seq=1 ttl=64 time=0.112 ms
64 bytes from 203.0.113.1: icmp_seq=2 ttl=64 time=0.072 ms
...
to_r2      BGP        ---        start  16:40:22.203  Active        Received: Administrative shutdown
to_r3      BGP        ---        up     16:40:21.569  Established   
```

When r2 closed its session, r1 lost every route from r2, as 10.3 said: a closed session withdraws its routes. The direct route was the only one left, so it won, low preference and all. Linux now sends `203.0.113.0/24` via `10.0.13.3`, and the ping still works. Look at the `ttl=64`. No router stood in between, so nothing lowered it. Through r2 it was 63. r1's `to_r2` line says why the session is down: `Received: Administrative shutdown`, which is r2 saying "I switched this off on purpose".

**Gap 4** is the opposite of Gap 3: the same command with `enable`. The script then waits for r1 to move back and saves `restored.txt`. In the recorded run it showed `203.0.113.0/24 via 10.0.12.2` again and a ping with `ttl=63`. In the course's test run the move took under a second to the backup after `disable`, and about 4 seconds back after `enable`.

## Count the hops

Run a trace with the main link up, then cut it by hand and run it again. **In the lab**:

```
ip netns exec r1 traceroute -n -s 198.51.100.1 203.0.113.1
birdc -s /tmp/bird-r2.ctl disable to_r1
ip netns exec r1 traceroute -n -s 198.51.100.1 203.0.113.1
birdc -s /tmp/bird-r2.ctl enable to_r1
```

The recorded traces, before and during the cut:

```

During the cut, check r3 too with `ip netns exec r3 ip route`. The recorded table had `198.51.100.0/24 via 10.0.13.1`: r3's answers took the direct cable as well.

## If it does not work

Is the direct session up? **In the lab**, `birdc -s /tmp/bird-r1.ctl show protocols` must show `to_r3` as `Established`. If not, Gap 1 is wrong: check the name, the local AS and the neighbour line in r3's block. Does BIRD accept your file? `bird -p -c r3.conf` prints nothing when the file is fine. Did the filter apply? `birdc -s /tmp/bird-r1.ctl show route all 203.0.113.0/24 protocol to_r3` must show `BGP.local_pref: 50`. If the direct route vanished completely, your filter has no `accept`. Are r1 and r3 both on r2 after Gap 2? Check `ip netns exec r3 ip route` as well, because a filter on one end only splits the two directions.
