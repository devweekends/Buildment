In 10.3 a network refused a route with its own number in the path. In 10.4 a network chose a longer path because its own preference said so. In 4.3 and 4.6 a router used the longest block that holds the address. A BGP router does all of these, in a fixed order. In this chapter you write that order as one function, `bestRoute`.

By the end you will have a tested function that takes the routes a network has heard and picks the one its traffic uses. The lab in 10.7 to 10.10 makes the same choices with BIRD, a real BGP program. When you read `birdc show route` there, you will know why each `*` sits where it does.

## The order is the whole job

Every rule on its own is easy. The difficulty is the order, because each rule only gets a say when the rules before it tie. The diagram shows the order this exercise uses. Each step either removes routes or picks among the ones that are left.

<MermaidDiagram title="Six steps from all routes to one" chart={`flowchart TD

The takeaway: step 4 can overrule step 5, which is why a longer path can win, as in 10.4. And step 3 can overrule step 4, which is why a stolen `/25` can win against a well-liked `/24`, as you will see in 10.9.

## The contract

Fix the promises before the code. The tests check each step in order, then the awkward cases.

**The input.** `announcements` is an array of objects. Each one has three fields: `prefix`, a block written as text such as `203.0.113.0/24`; `asPath`, an array of AS numbers with the newest first and the origin last, such as `[64497, 64498]`; and `neighbour`, the AS number of the network that sent it to you, such as `64497`. `myAsn` is your own AS number. `destination` is the address a packet is going to, as dotted text. `policy` is an object that maps a neighbour's AS number to a local preference, such as `{ 64498: 50 }`. It is always an object, and it may be empty.

**The output.** Return the chosen announcement: the same object that is in the array, not a copy, so a test can check which one you chose. Return `null` when no announcement is left after steps 1 and 2. Do not change the array you were given, and do not change its objects.

**Bad input.** If `destination` is not a valid address, throw an `Error` whose message starts with `invalid address`. The `ipToNumber` in the starter code already throws that error. Make sure your function calls it on the destination even when every route is dropped at step 1.

**The rules, in order.** First drop any announcement whose `asPath` contains `myAsn`. Then keep only the ones whose block holds the destination. Among those, the longest block wins. If two have the same length, the higher local preference wins, and a neighbour that is not in `policy` gets 100. If that ties too, the shorter `asPath` wins. If everything ties, the lower `neighbour` number wins. That last rule belongs to this exercise, so that your function always gives one answer. It is not BGP's own last rule.

## Two questions in one function

A real BGP router answers two questions, and this function joins them. The first question is about one block: of all the routes to `203.0.113.0/24`, which is best? BGP answers it with policy first, then the shortest AS path, then more tie-breakers [S83]. The second question is about one packet: of all the blocks in the table, which one does this address use? The router answers it with the longest prefix match from 4.3 [S30].

So BGP picks a best route for each block, and then forwarding uses the most specific block that holds the address. Your function does both in one pass. It keeps the longest block first, then picks the best route inside it. That gives the route the packet will really follow.

The order matters when two blocks overlap. Say a network has a `/24` from a neighbour it likes, and a `/25` inside it from a neighbour it does not. For an address in the `/25`, the `/25` wins, whatever the local preference says. Local preference compares routes to the same block. It never makes a shorter block beat a longer one.

## A worked example from the lab

Here is a case you will build in 10.8. You are r1, AS64496. You know two ways to `203.0.113.0/24`. One came from r2, AS64497, with the AS path `[64497, 64498]`. The other came straight from r3, AS64498, over a direct cable, with the AS path `[64498]`.

Walk the steps. Step 1 drops nothing: neither path holds 64496. Step 2 keeps both, because both blocks hold `203.0.113.1`. Step 3 ties: both are `/24`. Step 4 depends on the policy. With an empty policy, both neighbours get 100, so step 4 ties, and step 5 picks the shorter path: the direct route through AS64498. That is exactly what BIRD chose in the lab before you set a preference.

Now set the policy to `{ 64498: 50 }`, which is the one-line filter of 10.8. Step 4 no longer ties: AS64497 gets 100 by default, AS64498 gets 50, and the route through r2 wins. The shorter path never gets compared. In the lab, BIRD then printed the route through r2 with the `*`, and the direct route below it with `BGP.local_pref: 50`. Your function and BIRD agree.

## Four ways this goes wrong

**A loop that wins.** If you forget step 1, a route that holds your own number can look attractive: it may have a short path or a high preference. The first test gives you exactly that case. Drop such routes before you compare anything.

**Path length before policy.** If you compare the AS path before local preference, the lab case above picks the direct route even with the policy `{ 64498: 50 }`. The test named "policy beats a shorter path" fails and says so.

**A preference of 0 that becomes 100.** Local preference 0 is a real value: a network can give a neighbour the lowest number it likes. If you write `policy[n] || 100`, JavaScript treats 0 as false and gives 100 instead. Check whether the neighbour is in the policy at all, for example with `policy[n] === undefined`, and use 100 only then.

**A sort that changes the input.** Sorting is a fine way to find the best route, but `announcements.sort(...)` sorts the caller's array in place. The caller's list then comes back in a different order. Copy the array first with `[...announcements]`, or keep the best route so far in a loop, which needs no sort.

## Real BGP has more steps

The order in this exercise is short on purpose. RFC 4271 has more tie-breakers after the AS path: the origin of the route, a value called MED, a preference for routes from other networks over routes from inside, the cost to reach the next hop, and finally the lowest router identifier and address [S83]. This exercise stops at the AS path and adds its own simple last rule, the lowest neighbour number, so that every case has one answer you can test.

  function ipToNumber(ip) {
    if (typeof ip !== "string") throw new Error("invalid address: not text");
    const parts = ip.split(".");
    if (parts.length !== 4) throw new Error("invalid address: need four parts, got " + parts.length);
    let total = 0;
    for (const part of parts) {
      if (!/^(0|[1-9][0-9]{0,2})$/.test(part)) throw new Error("invalid address: bad part " + part);
      const value = Number(part);
      if (value > 255) throw new Error("invalid address: " + value + " is more than 255");
      total = (total << 8) | value;
    }
    return total >>> 0;
  }

  function inPrefix(prefix, address) {
    const [base, lengthText] = prefix.split("/");
    const length = Number(lengthText);
    const mask = length === 0 ? 0 : (0xffffffff << (32 - length)) >>> 0;
    return ((ipToNumber(base) & mask) >>> 0) === ((ipToNumber(address) & mask) >>> 0);
  }

  function bestRoute(announcements, myAsn, destination, policy) {
    ipToNumber(destination);
    const lengthOf = (a) => Number(a.prefix.split("/")[1]);
    const prefOf = (a) => (policy[a.neighbour] === undefined ? 100 : policy[a.neighbour]);
    const better = (a, b) => {
      if (lengthOf(a) !== lengthOf(b)) return lengthOf(a) > lengthOf(b);
      if (prefOf(a) !== prefOf(b)) return prefOf(a) > prefOf(b);
      if (a.asPath.length !== b.asPath.length) return a.asPath.length < b.asPath.length;
      return a.neighbour < b.neighbour;
    };
    let best = null;
    for (const a of announcements) {
      if (a.asPath.includes(myAsn)) continue;
      if (!inPrefix(a.prefix, destination)) continue;
      if (best === null || better(a, best)) best = a;
    }
    return best;
  }

## Check before you submit

Run three cases by hand before you press the button. With the lab case above and an empty policy, you must get the direct route from 64498. With `{ 64498: 50 }`, you must get the route from 64497. With an extra announcement whose path is `[64499, 64496, 64498]`, nothing must change, however good it looks, because it holds your own number 64496. If you can say which step decides each case, you have understood the order.

If a test fails, read its message first. It names the case, the step that should decide it, and what your code returned. The tests come in the order of the steps, so fix the first failing one before the others. The test about a preference of 0 and the test about the input list are easy to fail on the first try, and each message names the trap.
