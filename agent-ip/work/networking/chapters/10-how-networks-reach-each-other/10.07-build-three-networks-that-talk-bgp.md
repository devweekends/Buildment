In 10.3 you followed an announcement from network to network in a picture. In this chapter you run it. You build three small networks in a line inside the lab. Each one is its own autonomous system with its own number, and each one runs a real BGP program called BIRD. The two networks at the ends own one block each. You will watch them learn each other's block through the network in the middle, read the AS path that BGP built, and send a ping across. Then you make one network withdraw its block, and you watch the route vanish and the ping fail.

This is challenge 7, parts 1 and 2. Both parts are **guided**: the scripts are complete. Your job is to read each script, run it, and read what it prints. You change nothing yet. Part 3, in 10.8, is the first part with gaps. Plan about an hour for both parts. If this is your first BGP lab, plan longer: reading every line of the config is the real work here, and it pays back in 10.8 and 10.10.

Each router is a namespace, as in challenges 1 to 6. r1 plays the network AS64496, r2 plays AS64497 and r3 plays AS64498. The numbers come from the documentation range of 10.2, so they can never clash with a real network. The two blocks, `198.51.100.0/24` and `203.0.113.0/24`, come from the documentation ranges of module 2. They play two public blocks on the internet.

Each cable is its own small network with private addresses: `10.0.12.0/24` joins r1 and r2, and `10.0.23.0/24` joins r2 and r3. The last number of each address is the router's number, so `10.0.12.2` is r2's end of the first cable. r1 and r3 hold their block on a <GlossaryTerm term="dummy interface" definition="A pretend interface that is always up. It holds an address, like a server inside the network." />: `dummy0` with `198.51.100.1` in r1, and with `203.0.113.1` in r3. That first address plays a server inside each network.

r2 owns no block. It only carries traffic between its two neighbours, the way a provider does in 10.4. Every router has forwarding switched on, as in 4.7, but r2 needs it most, because the ping must cross it.

## BIRD in one minute

BIRD is a routing program for Linux that speaks BGP. Each router runs one `bird` program with one config file. A second program, `birdc`, asks a running `bird` questions: which sessions are up, which routes it knows. The two talk through a small file called a control socket, here `/tmp/bird-r1.ctl` for r1 and so on. Because the socket is a file, you can ask any router from the lab's own shell, without `ip netns exec`. BIRD keeps its own table of routes, and one block of the config hands the BGP routes to Linux, so that Linux can forward packets with them.

## The config, line by line

The script writes `r1.conf` into the part 1 folder. This is the whole file:

```
# r1.conf: BIRD config for r1, the network AS64496. Written by three-networks.sh.
router id 10.0.0.1;

protocol device {
}

protocol direct {
  ipv4;
  interface "dummy0";
}

protocol kernel {
  ipv4 {
    export where source = RTS_BGP;
  };
}

protocol bgp to_r2 {
  local as 64496;
  neighbor 10.0.12.2 as 64497;
  ipv4 {
    import all;
    export all;
  };
}
```

Take it from the top. `router id 10.0.0.1;` gives the router a name written like an address. It does not have to be an address the router owns, and the lab uses `10.0.0.N`, where N is the router number. `protocol device` lets BIRD see the interfaces, the cables and `dummy0`. Every BIRD config needs it.

`protocol direct` takes the blocks on some interfaces and puts them in BIRD's table, so that BIRD can announce them. The line `interface "dummy0";` limits it to the block on `dummy0`. So r1 announces `198.51.100.0/24` and nothing else. The cables are not announced, and that choice comes back below, when one ping fails.

`protocol kernel` joins BIRD's table to Linux's routing table. The line `export where source = RTS_BGP;` gives Linux only the routes that BIRD learned by BGP. Linux already knows its own blocks and cables.

The last block is the BGP session itself. `to_r2` is a name the course chose, and it shows in `birdc` output. `local as 64496;` is r1's own AS number. `neighbor 10.0.12.2 as 64497;` names the other end: its address on the shared cable, and the AS number it must have. BIRD checks that number when the session starts, so a typo here keeps the session down.

Then come two lines that look optional but are not. `import all;` takes every route this neighbour announces, and `export all;` announces every route r1 has: its own block and anything it learned from others. BIRD 2 needs a written rule here for BGP between two networks. Without an import rule, BIRD refuses to take anything from the neighbour, and the session comes up but carries no routes. `import all` and `export all` are the simplest rules there are. Real networks write longer ones, and you write your first one in 10.8.

`r3.conf` has the same lines with r3's numbers. `r2.conf` has two sessions, `to_r1` and `to_r3`, one to each neighbour. Its `protocol direct` names a `dummy0` that does not exist in this part, so r2 announces nothing of its own. It only passes on what it hears.


Read it in three parts. The first table lists r1's protocols. Each block of the config became one: `device1`, `direct1`, `kernel1` and the session `to_r2`. The word `Established` on the `to_r2` line is the state from 10.3 in which routes flow. The times show the session came up about four seconds after BIRD started.

The second table is BIRD's own view. r1 knows two blocks. `198.51.100.0/24` came from `direct1`: it is r1's own block on `dummy0`. `203.0.113.0/24` came from the session `to_r2`. The `*` means it is the route BIRD chose, and only chosen routes go to Linux. `(100)` is BIRD's own preference for the protocol: BGP routes get 100. It is not BGP's local preference from 10.4, even though the number is the same. `[AS64498i]` names the origin, AS64498. The `i` is the origin code IGP: the block came from inside that network, as `BGP.origin: IGP` says in the long form. `via 10.0.12.2 on veth-to-r2` says: send the traffic to r2.

The third table is Linux's view. The last row, `203.0.113.0/24 via 10.0.12.2 ... proto bird`, is the route BIRD handed over. You wrote rows like it by hand in 4.7. This one nobody typed. Then the ping: `ttl=63`. r3 answered with 64, the Linux default, and one router lowered it on the way back: r2.

Now the long form of the route. **In the lab**, `birdc -s /tmp/bird-r1.ctl show route all 203.0.113.0/24` printed:

```
BIRD 2.14 ready.
Table master4:
203.0.113.0/24       unicast [to_r2 16:39:51.919] * (100) [AS64498i]
	via 10.0.12.2 on veth-to-r2
	Type: BGP univ
	BGP.origin: IGP
	BGP.as_path: 64497 64498
	BGP.next_hop: 10.0.12.2
	BGP.local_pref: 100
```

There is your AS path: `64497 64498`, read from the right. `BGP.next_hop: 10.0.12.2` is the address the announcement says to send traffic to. `BGP.local_pref: 100` is r1's own preference for this route, the default from 10.4. r1 did not receive that number from r2. It gave it to the route itself.

## Why one ping needs -I

**In the lab**, ping without the `-I` option:

```
ip netns exec r1 ping -c2 -W1 203.0.113.1
```

The recorded result is silence:

```
PING 203.0.113.1 (203.0.113.1) 56(84) bytes of data.

--- 203.0.113.1 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss, time 1018ms
```

Without `-I`, Linux picks the source address of the cable the packet leaves on: `10.0.12.1`. The ping does reach r3. But nobody announces `10.0.12.0/24`: `protocol direct` names only `dummy0`. So r3 has no route back to `10.0.12.1`, and the answer is lost. With `-I 198.51.100.1`, the ping comes from r1's own block. r3 learned that block by BGP, so the answer finds its way home. A packet needs a way there and a way back, on the internet as much as in the lab.

Look at the other direction too. **In the lab**, `birdc -s /tmp/bird-r3.ctl show route all 198.51.100.0/24` printed, among its lines, `BGP.as_path: 64497 64496`. It is not the same path as r1's, because the origin is now AS64496, and the path always ends with the network that owns the block.

## Part 2: withdraw the block

In part 2, r3 stops announcing its block, and you watch the withdrawal from 10.3 travel the same road the announcement took: r3 tells r2, and r2 tells r1. Guess first, as the README asks.

```predict
prompt: "r3 withdraws 203.0.113.0/24, and r1 pings 203.0.113.1 from its own block straight after. When does the ping start to fail?"
options:
  - id: once
    label: "At once, as soon as the route goes"
  - id: later
    label: "After the 90-second hold time from 10.3"
correctOptionId: once
explanation: "At once. The hold time is for a neighbour that goes silent. A withdrawal is a message, so r1 forgets the route as soon as it arrives. With no row and no default route, Linux drops the packet inside r1."
allowRetry: true
```

**In the lab**:

```
cd /work/challenges/challenge-7-bgp/part-2-read-and-withdraw
bash withdraw.sh
```

The script builds part 1 again, so you always start from the same place, and saves three files: `route-all.txt`, `withdrawn.txt` and `back.txt`. To withdraw, it runs `birdc -s /tmp/bird-r3.ctl disable direct1`. `direct1` is the name BIRD gave r3's `protocol direct` block. Disabling it makes BIRD forget r3's own block, so BIRD withdraws it from every neighbour. The address `203.0.113.1` stays on r3. Only the announcement goes. The recorded run, shortened:

```
--- r2: show route all 203.0.113.0/24
...
	BGP.as_path: 64498
...
--- r3 withdraws 203.0.113.0/24
BIRD 2.14 ready.
direct1: disabled
### birdc -s /tmp/bird-r1.ctl show route all 203.0.113.0/24
BIRD 2.14 ready.
Network not found
### ip netns exec r1 ip route
10.0.12.0/24 dev veth-to-r2 proto kernel scope link src 10.0.12.1 
198.51.100.0/24 dev dummy0 proto kernel scope link src 198.51.100.1 
### ip netns exec r1 ping -c2 -W1 -I 198.51.100.1 203.0.113.1
PING 203.0.113.1 (203.0.113.1) from 198.51.100.1 : 56(84) bytes of data.

--- 203.0.113.1 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss, time 1024ms

### the withdrawal r1 received (birdc -s /tmp/bird-r1.ctl show protocols all to_r2)
    Routes:         0 imported, 1 exported, 0 preferred
    Route change stats:     received   rejected   filtered    ignored   accepted
      Import updates:              1          0          0          0          1
      Import withdraws:            1          0        ---          0          1
--- r3 announces 203.0.113.0/24 again
BIRD 2.14 ready.
direct1: enabled
...
```

First, r2's path for the block is only `64498`. r2 sits next to r3, so the path has one number: the origin. Then the withdrawal. r1's BIRD says `Network not found`. The `203.0.113.0/24` row is gone from Linux's table. The ping fails: `0 received`. The counters on r1's session show one update received, the announcement, and one withdrawal received. Then r3 announces again with `enable direct1`, and `back.txt` shows the row `203.0.113.0/24 via 10.0.12.2` and `2 received` once more.

Back to your guess: does the ping fail at once, or only after a while? It fails at once. When the route goes, r1 has no row at all for `203.0.113.1`, and no default route either. So Linux drops the packet inside r1, and nothing leaves. You can see this yourself. **In the lab**, withdraw again and ask Linux where it would send the packet:

```
birdc -s /tmp/bird-r3.ctl disable direct1
ip netns exec r1 ip route get 203.0.113.1
```

The recorded answer to the second line was `RTNETLINK answers: Network is unreachable`. Then switch r3 back on with `birdc -s /tmp/bird-r3.ctl enable direct1`, and wait a second.

This is the lesson of 7.4 in miniature. r3 is still running, and its address is still there. Nobody can reach it, because nobody knows the way. A network that withdraws its blocks disappears from the internet, even when every one of its computers is fine.

## If it does not work

Start with the session. **In the lab**, `birdc -s /tmp/bird-r1.ctl show protocols` must show `to_r2` as `Established`. If it does not, read the `neighbor` line: is the address on the same cable, and is the AS number the one in the other router's `local as`? If the session sits in `Active` or `Connect`, check that the two routers can reach each other at all: `ip netns exec r1 ping -c1 -W1 10.0.12.2`. If BIRD did not start, read its log with `cat /tmp/networking-course-pids/bird-r1.log`, and check the file with `bird -p -c r1.conf`, which prints nothing when the file is fine.

If the route is in BIRD but not in `ip route`, look at the `protocol kernel` block. If part 2's route does not go away, check that you disabled `direct1` in **r3**: `birdc -s /tmp/bird-r3.ctl show protocols` must show `direct1` as `down`. Times in the output will always differ from the recording. That is not a fault.
