Your friend still cannot see the web server on your laptop. In part 1 your devices learned how to reach out. Nothing taught the router how to let anyone in. In this chapter, you open exactly one door, you check that every other door stays shut, and then you add a guest network that is not allowed into your home at all.

This is the second half of challenge 4. It builds on part 1, so finish that first. By the end, the server on the other side will be able to read a web page from your laptop through one forwarded port. It will be refused on every other port. A guest on a separate network will reach the internet but will not reach your laptop.

## What you build

The network from part 1 stays as it is: the laptop `192.168.1.23` and the phone `192.168.1.24` behind the router, and the server `203.0.113.80` outside. You add three things. The laptop now runs a small web page on port 80. The router gets a third plug, `192.168.50.1`, for a new device called the guest at `192.168.50.10`. And the server starts to play a new part: a friend on the internet who tries to visit your router.

The friend visits `203.0.113.1`, the router's outside address, on port 8080. A forwarding rule sends that request on to the laptop's port 80. The guest, on its own subnet `192.168.50.0/24`, can use the router to reach the internet, but a filter rule stops it from reaching the home network `192.168.1.0/24`.

## The three gaps

Start from the folder, **in the lab**:

```
cd /work/challenges/challenge-4-home-router/part-2-forwarding-and-a-guest-network
```

The script builds the guest, its cable and its subnet, and starts the laptop's web page. It then stops at three marked places, each called `TODO`.

**Gap 1** is the front door: a port forwarding rule. A request to the router's outside address, port 8080, must be sent to the laptop's web server, `192.168.1.23` port 80. The rule rewrites the destination of the packet. That job is called DNAT, destination NAT, and it is the mirror image of masquerade, which rewrites the source. Two lines are needed in the `nat` table you made in part 1. The first is a chain called `prerouting`, of type `nat`, at the hook `prerouting`, with priority `-100`. The hook matters. A packet's destination has to be rewritten before the router decides where to send it, and `prerouting` is the hook that runs on arrival, before that decision. The second line is a rule in that chain: packets that arrive on `veth-rout` for TCP port 8080 get a new destination. The shapes are `add chain ip nat NAME { type nat hook HOOK priority NUMBER ; }` and `add rule ip nat NAME iifname "INTERFACE" tcp dport PORT dnat to ADDRESS:PORT`.

**Gap 2** is the guest rule. NAT does not keep anyone out, so you add a filter. Two lines again, in a table called `filter`. The first is a chain called `forward`, of type `filter`, at the hook `forward`, with priority `0` and policy `accept`. The `forward` hook sees packets that pass through the router, from one side to the other. The second line is a rule in it: packets from the guest network `192.168.50.0/24` to the home network `192.168.1.0/24` are dropped. The shapes are `add chain ip filter NAME { type filter hook HOOK priority NUMBER ; policy accept ; }` and `add rule ip filter NAME ip saddr NETWORK ip daddr NETWORK drop`. The policy `accept` is what the chain does with packets that match no rule, so everything else still passes.

**Gap 3** is the evidence. You run three tests from the server with a helper called `run_check`, which writes one line for each test in `outside-tests.txt`. Each test is one `curl -sS -m 3` from the server, with a label. The shape is `run_check LABEL in_ns NAMESPACE curl -sS -m 3 URL`. The three tests are `forwarded`, for `http://203.0.113.1:8080/`; `unforwarded`, for `http://203.0.113.1:22/`; and `direct`, for the laptop's private address `http://192.168.1.23/`.

Order matters in a filter. The first rule that matches wins. If your guest rule lands after a rule that accepts everything, the guest gets through. And if the front door does not open, ask whether the laptop's web server listens on `0.0.0.0` and not only on loopback, as you learned in module 5.

## What a good run looks like

This is the recorded output of a run of the reference solution. Your port number will differ. Read it in order. The three tests from the server come first. Then the guest reaches the server, and the server sees the router's address. Then the guest asks for the laptop's page and waits. At the end, the router prints its rules.

```
--- building the part 1 network
--- three tests from the server
forwarded: exit 0
unforwarded: exit 7
direct: exit 7
--- the guest reaches the server, which sees the router's address:
the server sees you as 203.0.113.1:56938
--- the guest asks for the laptop's page (this must be blocked, so it times out):
curl: (28) Connection timed out after 3002 milliseconds
(blocked or failed, exit 28)
--- the router's rules:
table ip nat {
	chain postrouting {
		type nat hook postrouting priority srcnat; policy accept;
		oifname "veth-rout" masquerade
	}

	chain prerouting {
		type nat hook prerouting priority dstnat; policy accept;
		iifname "veth-rout" tcp dport 8080 dnat to 192.168.1.23:80
	}
}
table ip filter {
	chain forward {
		type filter hook forward priority filter; policy accept;
		ip saddr 192.168.50.0/24 ip daddr 192.168.1.0/24 drop
	}
}
Done. Next: bash test.sh
```

Read the three results first. `forwarded: exit 0` means the front door works. `unforwarded: exit 7` means port 22 was refused at once, not left to time out. `direct: exit 7` means the server cannot reach the private address `192.168.1.23` at all, because it has no route to a private address. Only the forwarded port gets in. These three lines go into `outside-tests.txt`, and the test checks them.

Then read the guest lines. The guest reached the server, and the server saw `203.0.113.1`, the router's address, because masquerade from part 1 still applies to the guest. The guest's request for the laptop's page timed out after about three seconds. That is a drop: the router threw the packet away without telling anyone. Compare that with the refusal on port 22. One is a quick "no", and the other is silence.

At the end, the router's rules show every piece. In the `nat` table, the masquerade rule is on the outside plug and the forward rule sits in a `prerouting` chain. In the `filter` table, one rule drops packets from `192.168.50.0/24` to `192.168.1.0/24`.

## NAT is not a firewall

Notice what stopped the server from reaching `192.168.1.23` directly. It was not the masquerade rule. The server has no route to a private address, so it cannot send the packet. If the outside had a route to your home network, a masquerade-only router would let the connection through. You saw this in 6.3. Keeping someone out takes a filter, which is a separate rule. The guest rule in this chapter is a filter.

## The capture

Now watch one forwarded request on both sides of the router. You have one terminal, so run both captures in the background with `&`. **In the lab**:

```
ip netns exec router tcpdump -n -i veth-rout -c 3 tcp port 8080 > outside.txt 2>&1 &
ip netns exec router tcpdump -n -i br-home -c 3 tcp port 80 > inside.txt 2>&1 &
sleep 1
ip netns exec server curl -s http://203.0.113.1:8080/
wait
cat outside.txt inside.txt
ip netns exec router nft list ruleset > ruleset.txt
```

On the outside, the SYN should go from the server's address and a port to `203.0.113.1.8080`. On the inside, the same SYN should go from the same source to `192.168.1.23.80`. The destination was rewritten, both the address and the port. The source was not. Copy both captures into `results.md` and answer the two questions beside them: which field was rewritten, and which was not. If your capture looks different, trust it and tell your mentor.

## If it does not work

Work through this list in order. First, is the web server on the laptop listening on `0.0.0.0`? Run `ip netns exec laptop ss -tlnp`. Second, does the port in your rule match? The outside port is `8080` and the inside port is `80`. Third, did the guest rule land after a rule that accepts everything? Order matters. Fourth, does `ip netns exec router nft list ruleset` show both new rules? If you are lost, check that `bash ../part-1-masquerade/test.sh` still passes, then run `bash forwarding-guest.sh` again: it rebuilds the whole network. If the lab is slow for you, plan for 75 minutes instead of 50 and do Gap 1 first. A working forwarded page also proves that the rest of the network still works.
