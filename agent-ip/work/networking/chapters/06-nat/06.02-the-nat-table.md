Your phone and your laptop both send a request from port 41000 to the same server. The replies come back to one address. Which device gets which? The router must keep a record. This chapter shows what it keeps.

## The router rewrites the source address

<InteractiveCanvas slug="net-m6-nat-rewrite" />

A packet leaves the laptop with its private address as the source. Press Next and tap your pick. On the outside link the source is the router's outside address, `203.0.113.1`. This rewriting is <GlossaryTerm term="NAT" definition="Network address translation: a router rewrites addresses in the packets that pass through it." />. The port and the destination stay the same.

<GoDeeper title="Go deeper: what changes and what stays">

The picture shows five fields before and after the router. The source address changes. The source port stays `41000`, because no other conversation uses it. The destination address and port do not change. The TTL goes from 64 to 63, because the router is a router: a packet starts at 64 on a Linux sender and loses one at each router.

The standard calls this many-to-one kind of NAT NAPT: many inside addresses and ports share one outside address [S17]. On Linux, one rule does it, and the rule is called <GlossaryTerm term="masquerade" definition="A Linux NAT rule that takes the new source address from the interface the packet leaves by." />. The nftables wiki calls it a special case of source NAT that takes the address from the output interface [S43]. You write that rule yourself in 6.7.

In the course's own lab test, a client that sent from port 40000 reached the server, and the server saw the router's outside address with port 40000 [D5.6]. The address was rewritten. The port was kept.

</GoDeeper>

## One row per conversation

<InteractiveCanvas slug="net-m6-nat-table-fills" />

Each time a device opens a connection, the router adds a row to its <GlossaryTerm term="NAT table" definition="The router's memory of each conversation: which inside address and port belongs to which outside address and port." />. The laptop opens a second connection, so it gets a second row. The table counts conversations, not devices, and one row serves both directions.

<GoDeeper title="Go deeper: what a conversation is">

In 5.2 you met the five numbers that name a conversation: the protocol, and the address and port at each end. Two conversations differ in at least one of those five. The router keeps one row for each. A NAT mapping ties an inside address and port to an outside address and port [S18].

That is why the laptop and the phone can use the router at the same time, and why one device with two connections has two rows. It is also why the table can grow: a busy home with many apps and tabs holds many rows. Rows do not live forever. Chapter 6.5 shows how a row is removed.

On Linux, the real table belongs to the connection tracker, called conntrack. The command `conntrack -L` lists it [D5.6]. The picture here is a simplified view with two columns. Beat 5 shows the real one.

</GoDeeper>

## The row sends the reply home

<MermaidDiagram title="How a reply finds its device" chart={`flowchart LR
  S["Server 203.0.113.80:8080"] -->|"reply to 203.0.113.1:41000"| R["Router: look up the row"]
  R -->|"row found: inside is 192.168.1.23:41000"| L["Laptop 192.168.1.23"]
  R -->|"no row: nobody to give it to"| X["Packet stopped"]
`} legend="A reply arrives at the router's outside address and port. The router looks for a row with that address and port. If it finds one, it rewrites the destination to the inside address and port and sends the packet to the laptop. If there is no row, the packet goes nowhere." />

The server answers the router's outside address and port. The router looks for the row with that address and port. It rewrites the destination back to the laptop's private address and sends the packet inside. No row, no delivery. That is why the table exists.

<GoDeeper title="Go deeper: the reply is the same trip backwards">

Going out, the router rewrote the source. Coming back, it rewrites the destination. The server's reply has the source `203.0.113.80:8080` and the destination `203.0.113.1:41000`. The router matches that destination against the outside column of its table and swaps in the inside address and port. The data inside the packet is untouched.

This also shows the danger. If two different conversations had the same outside address and port, the router could not tell which device a reply belongs to. The next beat is about that case. The standard names the stored pair a mapping, and says the need for NAT is that internal addresses cannot be used outside the network [S17, S18].

</GoDeeper>

## Two devices, same port: one must change

<InteractiveCanvas slug="net-m6-nat-clash" />

The laptop goes first and keeps `41000`. The phone's packet would look exactly the same after rewriting, so the router gives it a new source port. The server sees two different ports. Press Next to follow the phone's reply. The router's table row for that new port names the phone, so the reply finds its way home.

<GoDeeper title="Go deeper: tested behaviour, and other routers">

In the course's own lab test, a second client used the same source port while the first was still open. The server saw a different port for the second client, and `conntrack -L` listed both mappings [D5.6]. So the Linux router rewrote the port only when it would clash. The kernel chooses the new port, and the choice differs on every run, so never memorise it.

<Callout type="warning" title="Other routers may differ">
The standard says a NAT must reuse the same mapping for the same inside address and port [S18]. Real home routers vary, and this course has no measurement of them. So this chapter teaches what the lab's Linux router does, not what every router does.
</Callout>

If you ever see the same source port on both sides of a router, it means no clash happened. If you see a different port, the router moved it. Both are normal.

</GoDeeper>

## Read the real table with conntrack

<InteractiveCanvas slug="net-m6-conntrack" />

In the lab, `conntrack -L` prints the router's real table. Each line is one conversation, in two halves. The first half is what the device sent. The second half is the reply as it arrives at the router, and its last number, `dport=`, is the port the server saw. In the recorded run, the phone's was `15510`. Yours will differ.

<GoDeeper title="Go deeper: one real row, part by part">

This is a line from the recorded run of challenge 4 part 1. The phone sent from port 41000, and the server saw a different port.

```
tcp      6 115 TIME_WAIT src=192.168.1.24 dst=203.0.113.80 sport=41000 dport=8080 src=203.0.113.80 dst=203.0.113.1 sport=8080 dport=15510 [ASSURED] mark=0 use=1
```

The word `tcp` names the protocol. The number `115` is the seconds left on the row's timer, and `TIME_WAIT` is the state of a closed TCP conversation: both appear in the lab tests [D5.8]. The first `src=`, `dst=`, `sport=` and `dport=` are the first half, what the phone sent: from `192.168.1.24:41000` to `203.0.113.80:8080`. The second `src=`, `dst=`, `sport=` and `dport=` are the second half, the reply: from `203.0.113.80:8080` to `203.0.113.1:15510`. The last port, `15510`, is the port the router chose.

The rest of the line does not matter for now. To check a result of your own, find the line with your source port in the first half, then read the last `dport=` of the same line. If it equals the first `sport=`, the port was kept. If it differs, the router changed it. Challenge 4 part 1 makes you do this with your own two devices.

</GoDeeper>

<GoDeeper title="Sources">

[S17] RFC 3022: NAT and NAPT. [S18] RFC 4787: a NAT mapping ties an internal address and port to an external address and port, and a NAT must reuse the mapping for one inside address and port. [S43] nftables wiki: masquerade is a special case of source NAT that takes its address from the output interface. [D5.6] and [D5.8] are the course's own lab tests: the address is rewritten and the port is kept unless two conversations clash; `conntrack -L` lists the mappings and shows the seconds left and the state of a closed TCP conversation.

</GoDeeper>
