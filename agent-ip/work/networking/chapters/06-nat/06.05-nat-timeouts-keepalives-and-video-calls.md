Your chat app sits untouched for an hour, and messages stop arriving until you open it. What expired? The answer is a row in the router's table, and it has a timer.

## The chat app went quiet

<InteractiveCanvas slug="net-m6-scene-quiet-chat" />

A chat app on a phone sits untouched. An hour later the chat server sends a message, and nothing arrives. When the app is opened, it connects again and messages flow. The router forgot something in the meantime. It did not forget the app. It forgot a row. The next beat says why.

<GoDeeper title="Go deeper: one cause, not every cause">

The picture is a model with a timer of 5 minutes, chosen for teaching. It shows one real cause of missed messages, not every cause. Many chat apps send small packets on purpose to stay connected, and you meet that idea in beat 4. Others reconnect on their own.

The picture also does not say what the router does with the stopped message. One cloud provider's NAT gateway documents that a later packet on an expired connection gets a reset, a quick answer that tells the sender the connection is gone [S51]. Another router may simply drop the packet. Either way, the message does not reach your phone.

</GoDeeper>

## A mapping is a row with a timer

<MermaidDiagram title="The life of a NAT row" chart={`flowchart LR
  C["Created by an outbound packet"] --> A["Active: each packet resets the timer"]
  A --> E["Expired: no packet for the idle timeout"]
  E --> G["Row deleted: a later packet from outside is stopped"]
`} legend="Left to right: an outbound packet creates the row. While packets keep passing, the row stays active and its timer starts again each time. After a quiet time equal to the idle timeout, the row is deleted. A packet from outside after that has no row to use." />

A NAT row is state with a timer. Each packet that uses the row resets the timer. If nothing passes for the <GlossaryTerm term="idle timeout" definition="How long a NAT row may stay unused before the router deletes it." />, the router deletes the row. A later packet from outside has no row, so it does not reach your phone.

<GoDeeper title="Go deeper: why the router forgets">

A router cannot keep every row forever. It would run out of memory, and a home might never use most of them again. So each row gets a timer, and silence deletes it. A NAT mapping ties an inside address and port to an outside address and port [S18]. When the timer ends, that tie is gone.

The standard sets a floor for UDP. A UDP timer must not expire in less than two minutes, and five minutes or more is recommended [S18]. For a provider's NAT, the standard on carrier-grade NAT gives no idle figure for TCP [S19]. So there is no single number to learn. Every NAT sets its own, and the number can differ between UDP and TCP.

</GoDeeper>

## Quiet for an hour: the row is gone

<InteractiveCanvas slug="net-m6-nat-idle-expire" />

Drag the quiet time. In this model the idle timeout is 300 seconds. While the quiet time is under 300 seconds, the row lives, and a message gets through. At 300 seconds the row is gone. Find the exact point where the row survives. These numbers are a model made for teaching, not a real router's.

<GoDeeper title="Go deeper: real timers differ">

The model uses 300 seconds because it is a round number that fits the guidance for UDP: at least two minutes, five recommended [S18]. One cloud provider's NAT gateway uses 350 seconds for idle connections [S51]. The two figures come from different kinds of NAT and are not the same number, and a third NAT would have a third. Never take 300 as a rule.

The boundary matters too. In this model the row is gone at exactly the timeout, not after it. You use the same boundary in the code exercise in 6.6. A real router may count a little differently, so a keepalive that arrives right at the limit is a risk. That leads to the next beat.

</GoDeeper>

## Keepalives reset the timer

<InteractiveCanvas slug="net-m6-nat-keepalive" />

A <GlossaryTerm term="keepalive" definition="A small packet sent on purpose, before the timer runs out, to keep a NAT row alive." /> resets the timer. Set the interval below the timeout, and the row never expires. Set it at or above the timeout, and the row dies between keepalives. Try the timeout at 350 seconds, the figure of one cloud gateway.

<GoDeeper title="Go deeper: the cost, and the lab's own timers">

Each keepalive is a small packet, but a phone that sends many of them uses data and battery. So the best interval is the longest one that is safely below the timeout. For the cloud gateway with the 350 second timeout, its documentation advises keepalives below that figure [S51].

<MustRead title="Troubleshoot NAT gateways" url="https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-troubleshooting.html" source="AWS documentation" description="Read the part about idle connections. Find the timeout, say what a later packet gets, and name one fix that would help a chat app." readMinutes={5} />

In the lab, `conntrack -L` shows the seconds left on each row. On one lab run, an unanswered UDP flow showed 29 seconds left, and a closed TCP flow was in the state `TIME_WAIT` with 119 seconds left [D5.8]. That is one router's behaviour on one day. A different NAT has different timers, so quote the numbers you read, never numbers from memory.

</GoDeeper>

## Calls need STUN or a relay

<MermaidDiagram title="How two phones find each other" chart={`flowchart TD
  A["Each phone asks a STUN server: which address and port do you see?"] --> B["Each phone learns its outside address and port"]
  B --> C["The phones swap what they learned and try to connect directly"]
  C -->|"a path works"| D["Direct call"]
  C -->|"no path works"| E["Relay: a server passes the call between them"]
`} legend="Top to bottom: each phone learns its outside address and port from a STUN server, the phones swap them and try a direct connection, and a relay carries the call when no direct path works." />

A video call wants the two phones to talk directly. Each phone sits behind a NAT, so it first asks a <GlossaryTerm term="STUN" definition="A server that tells a device its outside address and port." /> server, on port 3478 by default [S20]. If a direct path works, the call goes direct. If not, a <GlossaryTerm term="relay" definition="A server that passes a call between two devices." /> carries it.

<GoDeeper title="Go deeper: STUN, ICE and relays in one box">

STUN returns the address and port that a peer sees for you, which the standard calls a reflexive transport address [S20]. That is why "what is my public address?" is a real question for call apps. A phone asks a STUN server and learns the answer.

A method called ICE then collects the choices: addresses on the phone itself, addresses learned from STUN, and addresses on a relay. It tests pairs of them and picks one that works [S21]. A relay is the fallback when no direct pair works, and it needs a server that both phones can reach from inside their NATs. That is also the answer to a question in 6.9: when a provider NAT blocks connections from outside, a relay still works, because every phone starts its connection from the inside. This course does not build STUN or ICE. One box is enough to see why call apps need them.

</GoDeeper>

<GoDeeper title="Sources">

[S18] RFC 4787: a NAT mapping, and a UDP timer of at least two minutes with five minutes or more recommended. [S19] RFC 6888: no TCP idle figure. [S20] RFC 8489: STUN returns the address and port a peer sees, default port 3478. [S21] RFC 8445: ICE gathers host, server-reflexive and relayed candidates and tests pairs. [S51] AWS NAT gateway documentation: idle connections time out after 350 seconds, a later packet gets a reset, and keepalives below that figure help. [D5.8] The course's own lab test: an unanswered UDP flow showed 29 seconds left in `conntrack -L`, and a closed TCP flow showed `TIME_WAIT` with 119.

</GoDeeper>
